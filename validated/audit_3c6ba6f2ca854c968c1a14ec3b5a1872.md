### Title
Claimed instant-withdraw receipts remain in `instantWithdrawClaimsByEpoch`, inflating default-recovery reserve and causing post-default claim insolvency - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.requestInstantWithdraw` records each user's instant receipt in `instantWithdrawsRequestsByEpoch[user][epoch]` and the aggregate in `instantWithdrawClaimsByEpoch[epoch]` (lines 366-372). When the user later claims through `claimInstantWithdrawRequest` (lines 380-393), the code clears `instantWithdrawsRequests[user]` and burns the receipt, but it never decrements `instantWithdrawsRequestsByEpoch` or `instantWithdrawClaimsByEpoch`. The aggregate is only decremented in the post-default path `_claimDefaultedInstantWithdrawRequest` (line 853). This stale basis corrupts default-recovery accounting in `finalizeDefaultRecovery` / `defaultPendingClaimBasis` / `_defaultPrefundedInstantReserve`: funds already paid out to claimed users are counted as "prefunded reserve" and as pending claim basis, so `defaultRecoveryReserve` is recorded larger than the strategy's actual underlying balance. Early post-default claimants then drain more than their fair recovery share, and later claimants' `_transferDefaultRecovery` calls revert on insufficient balance — permanently freezing part of the recovery funds.

### Finding Description
Relevant flow:

1. `requestInstantWithdraw` increments `instantWithdrawsRequests[user]`, `instantWithdrawsRequestsByEpoch[user][epochNumber]`, `instantWithdrawClaimsByEpoch[epochNumber]`, and `pendingInstantWithdraws` (lines 356-375).
2. At `startEpoch`, the CDO calls `collectInstantWithdrawFunds(amount)`, which decrements `pendingInstantWithdraws` by the funded amount and pulls cash into the strategy (lines 398-403). If the borrower supplied less than requested, `pendingInstantWithdraws` stays non-zero.
3. A user whose receipt was funded calls `claimInstantWithdrawRequest` (lines 380-393): it burns `instantWithdrawsRequests[user]` and pays out at par via `_transferFundedClaim`. Critically, `instantWithdrawsRequestsByEpoch[user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` are left untouched.
4. On borrower default, the CDO calls `finalizeDefaultRecovery`:
   - `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0` (lines 644-649) — this includes the already-claimed-and-paid amount.
   - `_defaultPrefundedInstantReserve` computes `instantBasis - pendingInstant` (lines 716-723), which counts the claimed user's payout as underlying "already held" for recovery, even though it was already transferred out.
   - `reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` (line 686) is therefore inflated by the claimed amount `C`, and `totalBasis = activeBasis + pendingBasis` is inflated by the same `C` via `defaultPendingClaimBasis`.

Since `recoveryPrice = reserveAmount * 1e18 / totalBasis` (line 688) with both numerator and denominator inflated by `C`, the price is pushed toward par while the recorded `defaultRecoveryReserve` (line 691) exceeds the strategy's real token balance by `C`. Every `_transferDefaultRecovery` call decrements the recorded reserve and transfers real tokens; once the real balance is exhausted, remaining claims revert in `underlyingToken.safeTransfer`, permanently locking the residual recovery funds in the strategy.

The stale `instantWithdrawsRequestsByEpoch` entry for the already-claimed user also makes their own post-default `claimInstantWithdrawRequest` revert via underflow (`instantWithdrawsRequests[user] -= claimBasis` on line 848 subtracts a positive `claimBasis` from 0), so the inconsistency cannot self-correct.

### Impact Explanation
Direct theft plus permanent freezing of recovery funds, quantified by the claimed instant amount `C`:

- `recoveryPrice` is biased upward (toward 1e18), so every default-epoch receipt claimant (pending withdraws, pending instant receipts, and active holders whose NAV was scaled by the same multiplier) is entitled to `basis * inflatedPrice` — early claimants receive strictly more than the fair pro-rata share.
- Total recorded obligations equal `defaultRecoveryReserve`, which exceeds real balance by `C`. The last claimants in the queue (any unprivileged lender or tranche holder) have their `claimWithdrawRequest`/`claimInstantWithdrawRequest`/`DefaultDistributor` payouts revert permanently — the surplus tokens are stuck in the strategy (`transferToken` is owner-only, and the owner is honest).

An attacker needs only to be a KYC-passing lender with a funded instant receipt: claim it at par, wait for borrower default + `finalizeDefaultRecovery`, then be first to claim recovery — receiving an inflated payout while pushing honest claimants into permanent revert. Loss magnitude equals the pre-default claimed instant volume.

### Likelihood Explanation
- All preconditions are ordinary protocol states: a running epoch with instant withdraws enabled (`allowInstantWithdraw`, APR drop satisfying `instantWithdrawAprDelta`), a partial funding of the instant queue at `startEpoch`, and a subsequent borrower default with non-zero recovery. No privileged misbehavior is required.
- The bug triggers whenever at least one user claims a funded instant receipt while `pendingInstantWithdraws` remains non-zero (partial borrower funding is exactly the scenario the prefunded-reserve logic was built for), and finalization happens in the same `epochNumber`.
- No existing guard prevents it: `_transferFundedClaim` only protects `defaultRecoveryReserve` *after* finalization; `defaultPendingClaimBasis` trusts the stale aggregate; nothing reconciles `instantWithdrawClaimsByEpoch` on the normal claim path.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch receipt accounting the same way the defaulted path does:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol, in claimInstantWithdrawRequest
uint256 amount = instantWithdrawsRequests[_user];
uint256 reqEpoch = lastInstantRequestEpoch[_user]; // track request epoch, or iterate
instantWithdrawsRequestsByEpoch[_user][reqEpoch] = 0;
instantWithdrawClaimsByEpoch[reqEpoch] -= amount;
```

Because receipts can span multiple epochs, consider storing each request's epoch alongside the amount (as is done for normal requests via `withdrawsRequestsByEpoch` + `lastWithdrawRequest`), and ensure `instantWithdrawClaimsByEpoch` always equals the sum of unclaimed per-epoch receipt basis. Additionally, make `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve` reconcile `instantWithdrawClaimsByEpoch[epochNumber]` against actually outstanding receipts (or the strategy's instant-reserve balance) rather than trusting a counter that paid claims never decrement.

### Proof of Concept
Foundry fork-style PoC sketch (deploy via `IdleCreditVaultFactory` as in `test/foundry/IdleCreditVault.t.sol`):

```solidity
// test/foundry/InstantClaimDefaultReserve.t.sol
function testClaimedInstantInflatesRecoveryReserve() external {
    uint256 amount = 10_000 * ONE_SCALE;

    // 1. Lender deposits AA; manager starts epoch. Borrower draws funds.
    idleCDO.depositAA(amount);
    vm.prank(manager);
    cdoEpoch.startEpoch();

    // 2. APR drops enough to trigger instant-withdraw mode.
    vm.prank(manager);
    strategy.setAprs(unscaledAprDropped, scaledAprDropped);

    // 3. Attacker requests instant withdraw of X.
    vm.prank(attacker); // KYC-passed wallet
    cdoEpoch.requestWithdraw(x, address(AAtranche)); // routed to requestInstantWithdraw

    // 4. Next startEpoch: borrower funds only PART of the instant queue.
    //    attacker claims at par once funded -> instantWithdrawsRequests[attacker] = 0
    //    BUT instantWithdrawsRequestsByEpoch[attacker][epoch] == x
    //    and instantWithdrawClaimsByEpoch[epoch] still includes x.
    _partiallyFundInstantQueue(); // collectInstantWithdrawFunds < requested
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    assertGt(strategy.instantWithdrawClaimsByEpoch(strategy.epochNumber()), 0); // stale

    // 5. Borrower defaults; CDO calls finalizeDefaultRecovery.
    _triggerDefaultAndFinalize(recovered);

    // 6. Recorded reserve exceeds real strategy balance by x.
    assertGt(strategy.defaultRecoveryReserve(),
             underlying.balanceOf(address(strategy)));

    // 7. An honest claimant's recovery claim reverts (insufficient balance),
    //    while earlier claimants were overpaid at the inflated recoveryPrice.
    vm.prank(victim);
    vm.expectRevert();
    cdoEpoch.claimWithdrawRequest();
}
```

Key assertion: after step 4, `strategy.instantWithdrawsRequests(attacker) == 0` while `strategy.instantWithdrawClaimsByEpoch(epoch)` still contains `x`; after step 6, `defaultRecoveryReserve > underlyingToken.balanceOf(strategy)` by approximately `x`, and the final claimant reverts — demonstrating theft/overpayment for early claimants and permanent freezing of the remainder.   function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;

    if (instantBasis > pendingInstant) {

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
