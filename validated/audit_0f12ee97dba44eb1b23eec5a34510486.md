Looking deeper at the loss-adjusted claim path and how `lossRecoveryPriceByEpoch` interacts with `lastWithdrawRequest`.### Title
Loss-adjusted withdraw receipts keyed to the post-stop epoch escape the haircut and claim at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external bug is a condition-matching flaw: `header_rewrite` evaluates cookie/CIDR conditions against request state that has already been mutated, so the match operates on stale/ mis-keyed data and corrupts memory. The direct analog in this codebase is `IdleCreditVault.collectWithdrawFunds`, which stores `lossRecoveryPriceByEpoch` under the *already-incremented* `epochNumber`, while the receipts being haircut were tagged by `requestWithdraw` with the *pre-stop* `lastWithdrawRequest` epoch. Because the per-epoch lookup in `_claimLossAdjustedWithdrawRequest` is keyed by `lastWithdrawRequest`, every receipt that existed during a loss-applying `stopEpochWithDuration` misses its haircut entry and is later paid at par through `_claimFundedWithdrawRequest`.

### Finding Description
In `requestWithdraw` (contracts/strategies/idle/IdleCreditVault.sol:243-295) a user's receipt epoch is recorded as `lastWithdrawRequest[_user] = epochNumber` and `withdrawsRequestsByEpoch[_user][epochNumber] += _amount`. When a user requests during a *running* epoch N (allowed — the queue test requests after `startEpoch`), the receipt is tagged N.

`epochNumber` is incremented inside `deposit()` when the CDO deposits the borrower's repayment during `stopEpoch` while `isEpochRunning` is still true (contracts/strategies/idle/IdleCreditVault.sol:596-617: `epochNumber += 1`). After that, `stopEpochWithDuration` calls `collectWithdrawFunds`, which stores the haircut under the new counter:

```
lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;   // epoch N+1
pendingWithdraws = 0;                                        // basis included epoch-N receipts
```

At claim time, `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — i.e. epoch N — finds 0, and skips the haircut. `_claimFundedWithdrawRequest` then only requires `epochNumber > lastWithdrawRequest[_user]` (N+1 > N, satisfied) and pays `withdrawsRequests[_user]` in full via `_transferFundedClaim`, even though the borrower only funded `pendingBasis * lossRecoveryPrice / 1e18`.

The reverse mismatch also exists: buffer-period requests made *after* the stop are tagged N+1 and carry the stored loss price, but they were never part of the haircut `pendingBasis` — so a fresh post-loss request can be incorrectly haircut (or blocked by the `requestWithdraw` guard at lines 263-271 which checks the wrong epoch's price), while the actual loss-epoch receipts claim at par.

### Impact Explanation
Direct theft/insolvency: every withdraw receipt pending when `stopEpochWithDuration` realizes a loss is paid 100% instead of `lossRecoveryPrice`, while the strategy only received the haircut amount. The first claimant(s) to call `claimWithdrawRequest` drain the funded underlying plus strategy-held funds belonging to other claimants and active LPs; the last claimants' transfers underflow/revert, leaving them permanently unpaid. Loss magnitude ≈ `pendingBasis * (1 - lossRecoveryPrice/1e18)` plus any collateral damage to other receipt holders. The `requestWithdraw` guard at lines 263-271 does not help because it reads the same mis-keyed epoch.

### Likelihood Explanation
Requires a partial-loss `stopEpochWithDuration` on an epoch that has pending withdraw requests — a normal adverse-but-supported code path (the price machinery exists precisely for this). Any unprivileged tranche holder who opened a withdraw request during the running epoch automatically receives the overpayment on claim; no special timing or privilege is needed beyond being a requester.

### Recommendation
In `collectWithdrawFunds`, key `lossRecoveryPriceByEpoch` by the epoch the receipts were tagged with (the epoch being stopped, i.e. `epochNumber - 1` when called after the stopEpoch deposit bump, or pass the request epoch explicitly from the CDO), and revert/guard if a loss is applied while `epochNumber` has already advanced past the receipts' tag. Add a test: request during a running epoch → `stopEpochWithDuration(loss)` → assert claim pays `basis * lossRecoveryPrice / 1e18` and that a new post-stop request is not haircut.

// Foundry fork PoC sketch (adapt IdleCreditVault.t.sol harness)
function testLossReceiptsEscapeHaircut() external {
    // 1. depositAA + transferBurnedTrancheTokens as in existing tests
    idleCDO.depositAA(amount);
    _transferBurnedTrancheTokens(address(this), true);

    // 2. manager.startEpoch(); then request withdraw DURING the running epoch N
    vm.prank(manager); cdoEpoch.startEpoch();
    cdoEpoch.requestWithdraw(trancheAmount, address(AAtranche)); // tagged epoch N
    uint256 reqEpoch = strategy.epochNumber();                 // N

    // 3. borrower repays principal + interest - loss; manager.stopEpochWithDuration(loss)
    //    -> strategy.deposit() bumps epochNumber to N+1
    //    -> collectWithdrawFunds stores lossRecoveryPriceByEpoch[N+1], not [N]
    _repayWithLoss(lossAmount); // funds = pendingBasis * price, haircut applied globally
    assertEq(strategy.lossRecoveryPriceByEpoch(reqEpoch), 0);        // miss: keyed to N+1
    assertGt(strategy.lossRecoveryPriceByEpoch(reqEpoch + 1), 0);

    // 4. claim -> _claimLossAdjustedWithdrawRequest sees price 0 for epoch N,
    //    _claimFundedWithdrawRequest pays withdrawsRequests at par
    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    uint256 got = underlying.balanceOf(address(this)) - balPre;

    // expected: full basis (par), while strategy only collected basis * lossRecoveryPrice
    assertGt(got, requested * strategy.lossRecoveryPriceByEpoch(reqEpoch + 1) / 1e18);
    // subsequent claimants for the same epoch revert on insufficient funded balance
}

  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);
  }

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }
