Confirmed vulnerability: `delete_member` (multisig2) and `DeleteKey` (multisig v1) only purge requests that were **originated** by the removed member/key, but do not purge that member's **confirmations recorded on other still-pending requests**. A stale confirmation from a removed member continues to count toward `num_confirmations` when a later `confirm()` call checks `confirmations.len() as u32 + 1 >= self.num_confirmations`, letting a request execute with fewer live, authorized signers than the configured threshold.

### Title
Multisig executes requests using stale confirmations from removed members, bypassing the confirmation threshold - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` (multisig2) and the `DeleteKey` action (multisig v1) remove a member/key from the members set and delete only the *requests they created*, but never scrub their confirmations from other pending requests' `confirmations` sets. Because `confirm()` counts raw confirmation-set size against `num_confirmations` without verifying every confirming identity is still a current member, a request can be executed with one fewer live confirmer than the configured threshold requires.

### Finding Description
`confirm()` in both contracts computes readiness purely from set size: [1](#0-0) [2](#0-1) 

`delete_member`/`DeleteKey` only clean up requests where the removed member/key was the *creator* (`r.member == member` / `r.signer_pk == pk`), and only remove `num_requests_pk` bookkeeping — they never iterate `self.confirmations` to strip the removed identity from confirmation sets of requests it merely *confirmed* (but did not create): [3](#0-2) [4](#0-3) 

Consequently, an outstanding request `R` (created by member A, confirmed by member B) that has not yet reached threshold remains in `confirmations[R] = {B}` even after B is removed via a `DeleteMember`/`DeleteKey` request. When member C later calls `confirm(R)`, the check `confirmations.len() as u32 + 1 >= num_confirmations` uses B's stale confirmation as if B were still live, satisfying the threshold with only A and C as actual current members.

### Impact Explanation
This breaks the equality the multisig is supposed to enforce: `live confirmations at execution == num_confirmations`. Instead, `live confirmations == num_confirmations - (number of stale confirmations from removed members counted)`. A `MultiSigRequest` — including `Transfer`, `AddKey`/`AddMember`, `FunctionCall`, or `DeployContract` — can be executed with fewer currently-authorized approvers than the contract's `k`-of-`n` policy requires, i.e. "a multisig request executed below threshold" moving NEAR or granting privileged access without sufficient live authorization.

### Likelihood Explanation
No privileged capability beyond ordinary multisig membership is required. Any legitimate member who already confirmed a request, and is later removed as part of routine member rotation (a normal, expected operation, not misuse), leaves a live exploitable stale confirmation; a remaining member finishing confirmation triggers execution below the intended threshold. This is a realistic operational sequence for any multisig that rotates members while requests are outstanding.

### Recommendation
When removing a member/key, iterate all `confirmations` entries (not just requests created by that member) and remove the departing identity's entry from every set; alternatively, revalidate at `confirm()` time that every account/key recorded in `confirmations` is still present in `self.members` before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy multisig2 with 3 members `{A, B, C}` and `num_confirmations = 2`.
2. A calls `add_request(transfer_request)` → `request_id = R` (creator = A, `confirmations[R] = {}`).
3. B calls `confirm(R)` → `confirmations[R] = {B}` (1 < 2, not yet executed).
4. A separate already-confirmed `DeleteMember{member: B}` request executes, removing B from `self.members`; `delete_member` only deletes requests created by B (none here) and leaves `confirmations[R] = {B}` untouched.
5. C (now one of only 2 remaining members, A and C) calls `confirm(R)` → `confirmations.len() (=1) + 1 = 2 >= num_confirmations (2)` → request executes.
6. The transfer is executed with confirmations effectively from A and stale-B, i.e., only one live, currently-authorized member (C, since A merely created it) truly re-affirmed it at execution time — the 2-of-3 threshold was not met by two *currently valid* members' active confirmations at execution.     /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self

        );

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
