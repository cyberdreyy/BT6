### Title
`defaultPendingClaimBasis` only counts current-epoch instant receipts, so stale instant receipts from earlier epochs inflate `defaultRecoveryPrice` and strand later claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` records instant-withdraw receipt basis per request epoch in `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch`, keyed by `epochNumber` at request time. At default finalization, `defaultPendingClaimBasis()` adds only `instantWithdrawClaimsByEpoch[epochNumber]` (the *current* epoch) to the recovery basis, even though `pendingInstantWithdraws` is a global aggregate that may include receipts recorded in earlier epochs. This is the same bug class as CVE-2019-15927: an index/length field (`epochNumber` used as the lookup key) is trusted to cover all entries, while the underlying data can span indices the accounting loop never visits.

### Finding Description
In `requestInstantWithdraw`, receipts are stored under the epoch active at request time (`instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, `instantWithdrawClaimsByEpoch[currentEpoch]`) [1](#0-0) . If the manager never calls `getInstantWithdrawFunds` before the epoch ends, those receipts survive into the next epoch — nothing forces funding or expiry, and `claimInstantWithdrawRequest` simply pays whatever is in `instantWithdrawsRequests[_user]` [2](#0-1) .

When a later epoch defaults and `finalizeDefaultRecovery` runs, the claim basis is `pendingWithdraws + instantWithdrawClaimsByEpoch[epochNumber]` gated only on `pendingInstantWithdraws != 0` [3](#0-2) . Older-epoch instant claims are included in the non-zero check but excluded from the basis. `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` is therefore computed against an undercounted denominator [4](#0-3) , and the CDO's active NAV is even minted/burned to that inflated ratio (`activeFinalNAV = activeBasis * recoveryPrice`) [5](#0-4) .

The stale receipt then cannot be paid through the defaulted path — `_claimDefaultedInstantWithdrawRequest` reads `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` where `defaultRecoveryEpoch = epochNumber` (the new, defaulted epoch), returning 0 [6](#0-5)  — and falls through to `_transferFundedClaim`, which either pays at par out of funds meant for other claimants or reverts because `balance - reserve < amount` [7](#0-6) .

### Impact Explanation
Two orderings, both attacker-reachable with only unprivileged actions (tranche holder requesting withdraws):

1. **Inflated recovery drains the reserve.** `totalBasis` excludes the stale instant basis, so `defaultRecoveryPrice` is too high. Current-epoch defaulted claimants and active tranche holders recover at a better-than-pro-rata ratio; the fixed `defaultRecoveryReserve` is exhausted early and later claimants get nothing — direct loss socialized onto whoever claims last.
2. **Permanent freezing.** If the inflated claims consume the reserve, the stale receipt holder's `claimInstantWithdrawRequest` reverts in `_transferFundedClaim` (`balance - reserve < amount`), permanently freezing their receipt, and the reserve-accounting invariant (sum of claims ≤ reserve) is broken.

The quantified loss is bounded by the stale instant receipt size: if a receipt of `X` underlyings from epoch N survives to a default in epoch M, `defaultRecoveryPrice` is overstated by roughly `reserveAmount * X / (basis * (basis + X))`, and up to `X` underlyings of other users' recovery is stolen or frozen.

### Likelihood Explanation
Requires an instant withdraw request that remains unfunded across an epoch boundary (manager simply does not call `getInstantWithdrawFunds` before `epochEndDate` — instant requests are enabled when APR drops via `requestWithdraw`) followed by a borrower default in a later epoch. The attacker only needs to be a KYC-passed tranche holder timing `requestWithdraw` into instant mode and then not claiming; privileged roles stay honest. The index-key mismatch (`epochNumber` vs request epoch) is unconditional once those two events occur, so likelihood is moderate: it needs a default, but no attacker control over privileged calls.

### Recommendation
In `defaultPendingClaimBasis`, include the full unfunded instant basis rather than only `instantWithdrawClaimsByEpoch[epochNumber]`. Options:
- Track a global aggregate `pendingInstantClaimBasis` incremented in `requestInstantWithdraw` and decremented in `claimInstantWithdrawRequest`/`collectInstantWithdrawFunds`, and use it in place of the per-epoch lookup; or
- Iterate/accumulate all prior non-zero `instantWithdrawClaimsByEpoch` entries (e.g., keep a running total since `pendingInstantWithdraws` is already the global unfunded counter and symmetric global claim-basis bookkeeping is missing).

Correspondingly, `_claimDefaultedInstantWithdrawRequest` must clear user receipts across all epochs ≤ `defaultRecoveryEpoch` (e.g., store per-user a list/range of request epochs or a global user instant-claim-basis counter) rather than only `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]`.

### Proof of Concept
Foundry fork sketch against `test/foundry/IdleCreditVault.t.sol` helpers:

```solidity
function testStaleInstantReceiptInflatesRecovery() external {
  // Epoch N: deposit, start epoch, drop APR so requestWithdraw routes to instant path
  idleCDO.depositAA(10_000 * ONE_SCALE);
  _startEpochAndCheckPrices(0);

  // Manager lowers APR -> lastEpochApr > unscaledApr + instantWithdrawAprDelta
  vm.prank(manager);
  IdleCreditVault(address(strategy)).setAprs(0, 0);

  // Attacker requests instant withdraw in epoch N; manager never calls
  // getInstantWithdrawFunds, so pendingInstantWithdraws stays > 0 across epochs.
  cdoEpoch.requestWithdraw(trancheBal, address(AAtranche)); // routes to requestInstantWithdraw
  uint256 staleBasis = strategy.instantWithdrawsRequestsByEpoch(attacker, 0);
  assertGt(staleBasis, 0);

  // Epoch N ends, epoch N+1 starts, then borrower defaults.
  vm.warp(cdoEpoch.epochEndDate() + 1);
  vm.prank(manager); cdoEpoch.stopEpoch(0, 0);
  _startEpochAndCheckPrices(1);
  // borrower repays less than owed -> _handleBorrowerDefault
  vm.warp(cdoEpoch.epochEndDate() + 1);
  vm.prank(manager); cdoEpoch.stopEpoch(0, 0);
  assertTrue(cdoEpoch.defaulted());

  // Finalize: basis omits instantWithdrawClaimsByEpoch[0]
  uint256 basis = strategy.defaultPendingClaimBasis();
  assertEq(basis, strategy.pendingWithdraws() + strategy.instantWithdrawClaimsByEpoch(1));
  // staleBasis from epoch 0 is missing -> recoveryPrice overstated
  vm.prank(manager);
  cdoEpoch.finalizeDefault(recovered, manager);

  // Attacker's stale receipt: defaulted path finds 0 basis at epoch 1,
  // then _transferFundedClaim either overpays or reverts, stranding funds.
  vm.prank(attacker);
  strategy.claimInstantWithdrawRequest(attacker); // par payout or revert
}
```
