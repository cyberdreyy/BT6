### Title
Stale in-memory `BlockInfo` in `process_pending_responses_for_block` lets a locally-finalized state regress to an earlier state, breaking the local state-transition invariant - (File: stacks-signer/src/v0/signer.rs)

### Summary
`BlockInfo::move_to`/`check_state` is the only guard that prevents a block from moving backward between local/global accept/reject states, but that guard is enforced purely against the *in-memory* copy of `BlockInfo`, not against the authoritative row in `signerdb`. `handle_block_proposal` replays buffered "early" pre-commits, rejections, and signatures for a freshly-arrived proposal via `process_pending_responses_for_block`, iterating pre-commits first, then rejections, then signatures, all against the *same* `&mut BlockInfo` object created once at the top of `handle_block_proposal`. But `handle_block_pre_commit`, invoked for each buffered pre-commit, does **not** use that shared object — it re-fetches its own copy of `BlockInfo` from `signer_db` via `block_lookup_by_reward_cycle`, mutates it, and persists it back to the DB independently (e.g., it can reach the pre-commit threshold and drive the block all the way through `mark_locally_accepted`/broadcast). The shared `block_info` still held by `process_pending_responses_for_block` has no knowledge of this DB update. When the subsequent loop iterations over rejections/signatures call `store_and_process_block_rejection` / `store_and_process_block_signature` with that same stale object, they eventually call `self.signer_db.insert_block(block_info)`, which blindly overwrites the DB row — including `state`, `valid`, `signed_group`, `signed_self` — with the stale snapshot, silently undoing the state that `handle_block_pre_commit` had just committed for the same block. [2](#0-1) [3](#0-2) 

### Finding Description
`BlockInfo::check_state` is designed to make certain transitions unreachable — most importantly, `GloballyAccepted`/`GloballyRejected` can never be left, and `PreCommitted` is only reachable from `Unprocessed`. [4](#0-3) 

This invariant is only checked in-process against `self.state` on the object being mutated; it is never re-validated against what is currently stored in `signerdb` at write time — `insert_block` is an unconditional `INSERT OR REPLACE`. [1](#0-0) 

`process_pending_responses_for_block` is the one place where three different vote types (pre-commits, rejections, signatures) for the *same* block are processed in a single pass, using one shared `BlockInfo` for two of the three code paths, while the third (`handle_block_pre_commit`) deliberately re-reads and re-writes its own independent copy: [5](#0-4) 

`handle_block_pre_commit`, when the pre-commit threshold is crossed, can drive the block through `mark_locally_accepted`/self-sign and persist that to the DB via its own `insert_block` call, entirely independent of the `block_info` object held by the caller: [6](#0-5) 

Once that has happened, the caller's loop moves on to replay a buffered rejection or signature against its *stale* `block_info` (still `Unprocessed`/pre-mutation), calling `store_and_process_block_rejection` or `store_and_process_block_signature`, both of which end by calling `self.signer_db.insert_block(block_info)`: [7](#0-6) 

Because `insert_block` performs a blind overwrite, this second write clobbers the DB row that `handle_block_pre_commit` had just advanced (e.g. from `Unprocessed` to `PreCommitted`/`LocallyAccepted`) with the earlier snapshot — potentially reverting `state`, `signed_self`, `signed_group`, and `valid` fields. Because the in-memory guard (`check_state`) was evaluated against the stale copy's `self.state` (still `Unprocessed`), the transition it performs (e.g. `mark_locally_rejected` → `LocallyRejected`) is accepted in-memory even though the DB had already progressed past that point — the invariant that a local decision can't be reached again after a different local/global decision has been made is bypassed because the check and the persisted "true" state have desynchronized. This is a "checks happen against one object, effects land on another, more advanced record" pattern, structurally identical to the CEI violation in the reported Solidity bug: state is read, decided upon, and then written back after another actor's action has already advanced the authoritative state in between, and there is no lock/guard to detect or reject the stale write.

### Impact Explanation
This can cause a signer's own local decision to be recorded in a way that is inconsistent with (and overwrites) the more-advanced decision it had just made moments earlier in the same call stack, purely from the ordering of buffered pre-commit/rejection/signature entries that a remote signer (or the local peer set, replayed from `signer_pending_*` tables) can control the arrival order of relative to the proposal. In the worst case this can un-do a `PreCommitted`/`LocallyAccepted` state back to `LocallyRejected` for the same block on the same signer, which is exactly the kind of state-machine wedge/desync the equivalence rules in scope call out (local state should be a monotonic ratchet once a block is finalized locally, and a signer's local acceptance record should not be silently regressed by unrelated buffered messages for the same block). This does not require a majority of signers or another signer's key — it can be triggered purely by the timing/order of a small number of a single remote signer's (or even the local node's own delayed) pre-commit/response messages relative to when the proposal itself arrives, which `drain_pending_block_responses` collects for exactly this "early vote" replay path. [8](#0-7) 

### Likelihood Explanation
The buffering/replay path (`drain_pending_block_responses` → `process_pending_responses_for_block`) is a normal, frequently-exercised part of message handling for any block whose pre-commit/response messages race ahead of the block proposal itself over StackerDB — the docs explicitly describe this as "Early votes... parked in pending tables and replayed once the proposal is known." Reaching the specific overwrite requires the pre-commit entry to arrive/queue before the rejection or signature entry for the same block and signer set, and for the pre-commit to be sufficient to cross the local threshold during replay — a plausible but non-trivial race that a single well-timed remote signer or gossip relay could induce. [9](#0-8) 

### Recommendation
`process_pending_responses_for_block` should not iterate against a single stale `BlockInfo` object; each helper (`handle_block_pre_commit`, `store_and_process_block_rejection`, `store_and_process_block_signature`) should either re-fetch the current `BlockInfo` from `signer_db` immediately before acting (so decisions are made against the latest known state), or the loop should re-fetch/refresh `block_info` from the DB after each call before passing it into the next. Additionally, `SignerDb::insert_block` should not perform a blind `INSERT OR REPLACE`; it should either use a compare-and-swap keyed on the previously-read `state` (rejecting/merging when the DB has advanced past what the in-memory value expects), or the state-transition check (`BlockInfo::check_state`) should be re-validated against the current DB row at write time rather than only against the writer's own in-memory prior state.

### Proof of Concept
Conceptual reproduction within `handle_block_proposal`/`process_pending_responses_for_block` (stacks-signer/src/v0/signer.rs):
1. Before a signer sees a given block proposal, have a peer signer's `BlockPreCommit` for that block's hash arrive and get buffered via `add_pending_block_pre_commit_response` (unknown-block path in `handle_block_pre_commit`), and also have a peer signer's rejection arrive and get buffered via `add_pending_block_rejection_response` in `handle_block_rejection`.
2. Craft the timing/weights such that, once the actual `BlockProposal` for that hash finally arrives, the single replayed pre-commit is sufficient (combined with the local signer's own implicit vote path) to cross `compute_voting_weight_threshold` inside `handle_block_pre_commit`'s pre-commit replay, driving the signer to `mark_locally_accepted`/self-sign and `insert_block` (this uses its own independently-fetched `BlockInfo`, not the loop's shared object).
3. Immediately afterward in the same `process_pending_responses_for_block` loop, the buffered rejection is replayed via `store_and_process_block_rejection` against the stale `block_info` object created at the top of `handle_block_proposal` (still `Unprocessed`), which then calls `mark_locally_rejected` (passes `check_state` because the stale object's `state` is `Unprocessed`) and calls `self.signer_db.insert_block(block_info)`, overwriting the just-written `LocallyAccepted`/`PreCommitted` DB row with a `LocallyRejected` one for the same block/signer.
4. Inspect the resulting row via `signer_db.block_lookup` — the block's persisted `state`/`signed_self` reflects the reverted, stale decision rather than the advanced one, demonstrating the local-state ratchet invariant was bypassed by cross-referencing two different in-memory snapshots of the same DB row within a single event-processing pass. [5](#0-4) [1](#0-0) 

**Caveat**: I was not able to fully trace/execute this scenario end-to-end (e.g., confirm all the exact weight/threshold preconditions or find an existing test that reproduces the overwrite), so this should be validated with an integration test in `stacks-signer/src/v0/signer.rs` / `stacks-signer/src/signerdb.rs` before treating it as fully confirmed; the structural mismatch (independent fetch-and-write in `handle_block_pre_commit` vs. shared stale object reused by the other two handlers in the same replay loop, combined with `insert_block`'s unconditional overwrite) is verified directly from the cited code.

    /// Check if the block state transition is valid
    fn check_state(&self, state: BlockState) -> bool {
        let prev_state = &self.state;
        if *prev_state == state {
            return true;
        }
        match state {
            BlockState::Unprocessed => false,
            BlockState::LocallyAccepted | BlockState::LocallyRejected => !matches!(
                prev_state,
                BlockState::GloballyRejected | BlockState::GloballyAccepted
            ),
            BlockState::GloballyAccepted => !matches!(prev_state, BlockState::GloballyRejected),
            BlockState::GloballyRejected => !matches!(prev_state, BlockState::GloballyAccepted),
            BlockState::PreCommitted => matches!(prev_state, BlockState::Unprocessed),
        }
    }

    /// Retrieve and clear all pending block response entries matching the given block signer_signature_hash
    /// Returns PendingBlockResponses containing all matching pre-commits, approval signatures, and rejections
    pub fn drain_pending_block_responses(
        &self,
        block_sighash: &Sha512Trunc256Sum,
    ) -> Result<PendingBlockResponses, DBError> {
        let hash_str = block_sighash.to_string();

        // Delete and return pre-commits in one operation
        let pre_commits_qry = "DELETE FROM signer_pending_pre_commit_responses WHERE signer_signature_hash = ?1 RETURNING signer_addr";
        let mut stmt = self.db.prepare(pre_commits_qry)?;
        let pre_commits_rows = stmt.query_map(params![&hash_str], |row| {
            let addr_str: String = row.get(0)?;
            let addr = StacksAddress::from_string(&addr_str).ok_or(
                SqliteError::InvalidColumnType(0, addr_str.clone(), rusqlite::types::Type::Text),
            )?;
            Ok(addr)
        })?;
        let pre_commits: Vec<_> = pre_commits_rows.collect::<Result<Vec<_>, _>>()?;

        // Delete and return signatures in one operation
        let signatures_qry = "DELETE FROM signer_pending_signature_responses WHERE signer_signature_hash = ?1 RETURNING signer_addr, signature";
        let mut stmt = self.db.prepare(signatures_qry)?;
        let signatures_rows = stmt.query_map(params![&hash_str], |row| {
            let addr_str: String = row.get(0)?;
            let sig_str: String = row.get(1)?;
            let addr = StacksAddress::from_string(&addr_str).ok_or(
                SqliteError::InvalidColumnType(0, addr_str.clone(), rusqlite::types::Type::Text),
            )?;
            let signature: MessageSignature = serde_json::from_str(&sig_str).map_err(|_| {
                SqliteError::InvalidColumnType(1, sig_str.clone(), rusqlite::types::Type::Text)
            })?;
            Ok((addr, signature))
        })?;
        let signatures: Vec<_> = signatures_rows.collect::<Result<Vec<_>, _>>()?;

        // Delete and return rejections in one operation
        let rejections_qry = "DELETE FROM signer_pending_rejection_responses WHERE signer_signature_hash = ?1 RETURNING signer_addr, reject_code";
        let mut stmt = self.db.prepare(rejections_qry)?;
        let rejections_rows = stmt.query_map(params![&hash_str], |row| {
            let addr_str: String = row.get(0)?;
            let reject_code: u8 = row.get(1)?;
            let addr = StacksAddress::from_string(&addr_str).ok_or(
                SqliteError::InvalidColumnType(0, addr_str.clone(), rusqlite::types::Type::Text),
            )?;
            let reject_reason = RejectReasonPrefix::from(reject_code);
            Ok((addr, reject_reason))
        })?;
        let rejections: Vec<_> = rejections_rows.collect::<Result<Vec<_>, _>>()?;

        let pending_block_responses = PendingBlockResponses {
            pre_commits,
            signatures,
            rejections,
        };
        if !pending_block_responses.is_empty() {
            debug!("Drained pending block responses for block {block_sighash}";
                "pre_commits_count" => pending_block_responses.pre_commits.len(),
                "signatures_count" => pending_block_responses.signatures.len(),
                "rejections_count" => pending_block_responses.rejections.len());
        }
        Ok(pending_block_responses)
    }
