### Title
StakingRewards `rewardPerToken` uses only 1e18 precision — rewards permanently round to zero for stakers - (File: contracts/StakingRewards.sol)

### Summary
`StakingRewards.rewardPerToken()` accumulates rewards with the formula `elapsed * rewardRate * 1e18 / _totalSupply`. When the staking token is an 18-decimal tranche token with a large total supply (the contract is designed to stake tranche tokens received as fees, see the `stakeFor` comment) and the reward token has few decimals (e.g. USDC, 6 decimals), the per-second accumulator increment truncates to 0. Rewards funded via `notifyRewardAmount` accrue to `rewardPerTokenStored` as 0, so `earned()` returns 0 forever and the reward tokens are permanently locked — an identical bug class to the external `secRewardsPerShare` finding, where a `1e18` multiplier is too small relative to the denominator.

### Finding Description
The reward accumulator is computed as:

```solidity
// contracts/StakingRewards.sol:66-71
return rewardPerTokenStored + ((lastTimeRewardApplicable() - lastUpdateTime) * rewardRate * 1e18 / _totalSupply);
```

and user earnings are scaled back by the same factor:

```solidity
// contracts/StakingRewards.sol:73-75
return (_balances[account] * (rewardPerToken() - userRewardPerTokenPaid[account]) / 1e18) + rewards[account];
```

`rewardRate` is in reward-token wei/sec (`rewardRate * rewardsDuration` is the notified amount, and `rewardsDuration` is initialized to `1 days`). Suppose the staking token is an 18-decimal tranche token with supply `S` and the reward token is USDC (6 decimals). The per-second increment is `rewardRate * 1e18 / S`. For a plausible vault scale — `S = 1e27` (1e9 tranche tokens) — the increment is zero whenever `rewardRate < 1e9` wei/sec, i.e. whenever the notified reward is below `1e9 * 86400 ≈ 86,400` USDC-units-wei ≈ 86.4e9 wei = ~86 USDC/sec ≈ 7.5M USDC/day. Even more simply, mirroring the report's example: any `rewardRate` such that `rewardRate < S / 1e18` yields exactly 0 accumulated per token forever.

Because `updateReward` snapshots `rewardPerTokenStored = rewardPerToken()` and `userRewardPerTokenPaid[account]`, stakers (any tranche-token holder via `stake`, or fee tokens staked via `stakeFor`) accumulate `earned() == 0` while the full reward balance sits in the contract. The notification accounting (`rewardRate = reward / rewardsDuration`) never returns the unaccrued remainder to a distributor — the tokens are stranded. The broken invariant is fair yield distribution: rewards per share must monotonically reflect elapsed time; here it stays flat at 0 while `periodFinish` elapses.

### Impact Explanation
Permanent freezing/theft of unclaimed yield: the entire notified reward balance becomes unclaimable through `getReward()`/`earned()` (which both route through the zeroed accumulator). Loss is limited to yield (same severity rationale as the external finding — Medium), but it is total: 100% of each affected reward period is stranded until an owner `recoverERC20` (if implemented for the reward token) intervenes, and even then no fair distribution among stakers is possible.

### Likelihood Explanation
Likelihood depends on the reward token's decimals and staking supply. With an 18-decimal staking token, a low-decimals reward token (USDC/USDT, 6 decimals) makes the trigger cheap: `rewardRate` below `S / 1e18` wei/sec is common for modest reward streams over large TVL. With an 18-decimal reward token the threshold is `rewardRate < S / 1e18` full tokens/sec — still reachable during early epochs or small top-ups, especially immediately after initialize where `rewardsDuration = 1 days` makes `rewardRate` small for modest rewards. No privileged actor is needed to trigger the loss; it emerges purely from the precision mismatch in the accumulator.

### Recommendation
Scale the accumulator by a larger precision constant (e.g. `PRECISION = 1e27` or `1e36`) in both `rewardPerToken()` and `earned()`, consistent with the external report's recommended `1e27`:

```solidity
// contracts/StakingRewards.sol
uint256 private constant PRECISION = 1e27;

return rewardPerTokenStored + ((lastTimeRewardApplicable() - lastUpdateTime) * rewardRate * PRECISION / _totalSupply);

return (_balances[account] * (rewardPerToken() - userRewardPerTokenPaid[account]) / PRECISION) + rewards[account];
```

Alternatively compute rewards in underlying-seconds first (`elapsed * rewardRate` accumulated as a total, then divide once by supply at claim), which removes the truncation entirely.

### Proof of Concept
Foundry fork PoC sketch — deploy `StakingRewards`, initialize with `stakingToken = MockTranche(18 dec)`, `rewardsToken = MockUSDC(6 dec)`:

```solidity
function test_RewardPerTokenRoundsToZero() public {
    // stake a large 18-decimal tranche supply
    uint256 supply = 1e9 * 1e18;               // S = 1e27
    stakingToken.mint(address(this), supply);
    stakingToken.approve(address(stakingRewards), supply);
    stakingRewards.stake(supply);

    // notify a reward small enough that rewardRate * 1e18 < S
    // rewardsDuration = 1 days; rewardRate = reward / 1 days
    uint256 reward = 1000e6;                    // 1,000 USDC -> rewardRate ~ 11_574 < 1e27/1e18 = 1e9
    rewardsToken.mint(address(stakingRewards), reward);
    vm.prank(rewardsDistribution);
    stakingRewards.notifyRewardAmount(reward);

    vm.warp(block.timestamp + 1 days);          // full period elapses

    assertEq(stakingRewards.rewardPerToken(), 0);     // accumulator never moved
    assertEq(stakingRewards.earned(address(this)), 0); // staker earned nothing
    assertEq(rewardsToken.balanceOf(address(stakingRewards)), reward); // funds stranded
}
```

Expected: `earned()` is 0 despite the full `periodFinish` elapsing and the reward balance remaining in the contract — yield permanently unclaimable, matching the rounding-down loss demonstrated in the external `secRewardsPerShare` report.

Caveat on scope: `StakingRewards.sol` could arguably be classified as a utility rather than core credit-vault surface; however it is in-scope production code in `contracts/`, stakes tranche tokens (including fee tranche tokens via `stakeFor`), and is the only literal rewards-per-share accumulator in the codebase — no closer analog (e.g. a per-share accumulator inside `IdleCDOEpochVariant`/`IdleCDOCreditVault`) exists; their interest paths are per-request divisions (`_calcInterestWithdrawRequest`, `_calcTrancheInterestShare`) where rounding produces only sub-wei dust, not a systemic zero accumulator.
