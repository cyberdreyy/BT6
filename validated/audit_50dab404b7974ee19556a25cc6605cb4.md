### Title
Builder can be charged (and its fee_recipient paid) twice for a single accepted bid when child-block inclusion is delayed 2+ epochs - (File: `specs/gloas/beacon-chain.md`)

### Summary
`apply_parent_execution_payload` settles a builder's committed bid payment through two independent, non-mutually-exclusive code paths: the positional `settle_builder_payment` lookup and a same-epoch/previous-epoch check, versus a "recreate from `parent_bid`" fallback used when the payment slot has aged out of the tracking window. Because the fallback does not verify whether the payment was already resolved by the epoch-boundary quorum mechanism (`process_builder_pending_payments`), a bid whose quorum was reached before its child block is finally included gets paid out twice.

### Finding Description
`process_execution_payload_bid` records a builder's committed payment in `state.builder_pending_payments` at index `SLOTS_PER_EPOCH + bid.slot % SLOTS_PER_EPOCH` [1](#0-0) .

Each epoch boundary, `process_builder_pending_payments` shifts this array by one epoch and, for entries in the *old* first half, pays out (appends to `state.builder_pending_withdrawals`) any payment whose `weight >= quorum`, then unconditionally discards the entry from the tracked array regardless of outcome: [2](#0-1) 

Separately, when the child block that references the bid's slot as its parent is finally processed, `apply_parent_execution_payload` settles the payment by exact index lookup only if the parent block is in the current or previous epoch: [3](#0-2) 

If child-block inclusion is delayed by 2 or more epochs (e.g. missed slots), neither the "current epoch" nor "previous epoch" branch matches, so the code falls back to reconstructing a withdrawal directly from `state.latest_execution_payload_bid` (`parent_bid`), with no check of whether the payment was already resolved:
```python
elif parent_bid.value > 0:
    # Parent is older than the previous epoch, its payment entry has been
    # evicted from builder_pending_payments. Append the withdrawal directly.
    state.builder_pending_withdrawals.append(
        BuilderPendingWithdrawal(
            fee_recipient=parent_bid.fee_recipient,
            amount=parent_bid.value,
            builder_index=parent_bid.builder_index,
        )
    )
```

Tracing the exact epoch offsets: a bid at slot `X` in epoch `E` is placed into the "current epoch" half of `builder_pending_payments`. At the `E→E+1` boundary it is shifted into the "previous epoch" half. At the `E+1→E+2` boundary, `process_builder_pending_payments` performs its *one-time* quorum check on that half — if attesters met quorum during epoch `E+1`, the payment is paid out here and the tracking entry is discarded either way. If the child block whose parent is slot `X` has still not been included by then, once it finally arrives in epoch `E+2` (or later), `parent_epoch (E)` equals neither `current_epoch (E+2)` nor `previous_epoch (E+1)`, so the `elif parent_bid.value > 0` fallback fires and appends a *second* `BuilderPendingWithdrawal` built from the same `parent_bid`, independent of whether the quorum path already paid it.

This exactly parallels the reported Swivel bug class: a single committed obligation (`fee` in Swivel / `bid.value` in gloas) is charged/paid through two independent code paths that are not mutually exclusive, so the payer is debited twice and the recipient receives double payment.

The existing regression test `test_builder_payment_after_missed_epochs` only exercises the "payment lost" branch (it sets `weight=0`, i.e., quorum is never met), so it validates that the fallback *recovers* an unpaid bid, but it does not validate — nor guard against — the case where quorum was already reached before the fallback triggers, leaving the double-payment path untested and unguarded.

### Impact Explanation
This breaks the equality that a single accepted bid results in exactly one payment to the builder's `fee_recipient`. When the double-payment path triggers: (1) the builder's registered balance can be debited up to twice the committed `bid.value` (via two independent `BuilderPendingWithdrawal` entries later applied in `apply_withdrawals`, each deducting `min(amount, balance)` from `state.builders[i].balance`), and (2) the `fee_recipient` execution address is paid twice for work committed to only once. This is a Gwei duplication paid to a non-owner beyond what the bid committed to — matching the "builder payment or withdrawal ... doubled" High-impact criterion.

### Likelihood Explanation
The trigger condition is a builder's payload spending 2+ full epochs without its child block being included in the chain (e.g., due to missed slots), combined with the payment's weight (attester participation referencing that slot as target) reaching the payment quorum threshold before the child block is eventually processed. This does not require a malicious coalition or a foreign key — it only requires normal network conditions producing several consecutive missed slots (which does occur on mainnet, especially around periods of poor connectivity or non-finality) while attestations for the affected slot still accumulate sufficient weight. A single proposer/attesting set naturally reaching quorum during an epoch of missed blocks is a realistic scenario, not a purely theoretical one.

### Recommendation
The `elif parent_bid.value > 0` fallback in `apply_parent_execution_payload` should not unconditionally reconstruct a withdrawal from `parent_bid`. Instead, `process_builder_pending_payments` should mark/flag whether a payment has already been settled (or track a small "already-paid" bit per array slot, or defer discarding the entry until the corresponding parent-execution-payload settlement has definitely occurred), and the fallback branch should only fire when the entry was evicted *without* being paid — i.e., the eviction and the emergency recreation must be a single source of truth for "has this bid already resulted in a withdrawal."

### Proof of Concept
1. Builder `B` submits a bid with `value = V` and `fee_recipient = F` for slot `X` in epoch `E`; `process_execution_payload_bid` records the pending payment at `builder_pending_payments[SLOTS_PER_EPOCH + X % SLOTS_PER_EPOCH]`.
2. No child block is included referencing `X` as parent for the following two epochs (missed slots), but attestations targeting `X` accumulate during epoch `E+1` such that `payment.weight >= quorum` by the `E+1→E+2` epoch boundary.
3. At the `E+1→E+2` boundary, `process_builder_pending_payments` sees `weight >= quorum` and appends `BuilderPendingWithdrawal(fee_recipient=F, amount=V, builder_index=B)` to `state.builder_pending_withdrawals`, then discards the tracking entry as part of the normal rotation.
4. Later, in epoch `E+2` (or later), the first actual block whose parent is slot `X` is finally processed. `apply_parent_execution_payload` computes `parent_epoch == E`, `current_epoch >= E+2`; neither matches `current_epoch` nor `previous_epoch`, so the `elif parent_bid.value > 0` branch fires and appends a second `BuilderPendingWithdrawal(fee_recipient=F, amount=V, builder_index=B)`.
5. `process_withdrawals`/`apply_withdrawals` later processes both queued withdrawals independently, deducting up to `2V` from builder `B`'s balance and paying `F` twice for a single committed bid.

def process_builder_pending_payments(state: BeaconState) -> None:
    """
    Processes the builder pending payments from the previous epoch.
    """
    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:
        if payment.weight >= quorum:
            state.builder_pending_withdrawals.append(payment.withdrawal)

    old_payments = state.builder_pending_payments[SLOTS_PER_EPOCH:]
    state.builder_pending_payments[:SLOTS_PER_EPOCH] = old_payments
    new_payments = [BuilderPendingPayment.empty() for _ in range(SLOTS_PER_EPOCH)]
    state.builder_pending_payments[SLOTS_PER_EPOCH:] = new_payments
