### Title
GraphQL `createCSAKey` mutation allows view/run-role sessions to create a new CSA oracle identity key without an edit/admin role check - ([File: core/web/router.go], [File: core/web/resolver/mutation.go])

### Summary
The REST endpoint for CSA key creation (`POST /v2/keys/csa`) is explicitly wrapped with `auth.RequiresEditRole`, but the GraphQL `/query` endpoint used to reach `Resolver.CreateCSAKey` is only wrapped with `auth.AuthenticateGQL`, which verifies a valid session/token but performs no role check. This asymmetry means a user authenticated with only view or run role can invoke `mutation { createCSAKey { ... } }` and trigger key generation via `App.GetKeyStore().CSA().Create`.

### Finding Description
In `core/web/router.go`, the GraphQL route is registered as: [1](#0-0) 
This chain only authenticates the caller (`auth.AuthenticateGQL`) and attaches the dataloader middleware before dispatching to the graphql-go resolver — there is no role-gating middleware comparable to `auth.RequiresEditRole`/`auth.RequiresAdminRole` applied to the `/query` route or per-mutation.

By contrast, the equivalent REST action for the same underlying capability is explicitly gated: [2](#0-1) 
`csakc.Create` (REST `POST /keys/csa`) requires Edit role, confirming that CSA key creation is intended to be an edit/admin-level privileged action.

The GraphQL resolver `Resolver.CreateCSAKey` in `core/web/resolver/mutation.go` calls into `App.GetKeyStore().CSA().Create(...)` directly from the mutation handler. Because the `/query` route performs only session/token authentication (any valid role: view, run, edit, or admin all pass `auth.AuthenticateGQL`), and no role check exists inside the resolver method itself or as a directive in the GraphQL schema, any authenticated caller — regardless of role — that can reach `/query` can execute `createCSAKey` and cause a new CSA identity keypair to be generated on the node.

This is a genuine authorization-exactness gap: the REST API enforces `RequiresEditRole` for the identical underlying operation, while the GraphQL API for the same operation enforces nothing beyond generic authentication.

### Impact Explanation
A view-role or run-role credential holder (a legitimate but low-privilege API token/session) can create a new CSA (oracle identity) keypair on the node without needing edit/admin privileges. CSA keys are used for the node's identity toward external services (e.g., Feeds Manager registration); unauthorized generation could be leveraged to swap in an attacker-influenced identity or pollute the node's key management state, matching the "role/authorization bypass leading to unauthorized privileged action" bounty impact class. It does not directly leak secrets (the private key material is not returned to the caller by the mutation), but it does allow a privilege-inappropriate mutation of node state.

### Likelihood Explanation
Precondition is a valid session or API token with only view or run role — no special network position, admin credentials, or social engineering is required, and the `/query` endpoint is reachable by any authenticated user of the node's HTTP API. The exploit is a single, repeatable GraphQL POST request; no race condition or timing dependency is involved, making this highly feasible and repeatable.

### Recommendation
Add role-authorization enforcement to the GraphQL mutation layer, either via a role-checking directive in the GraphQL schema for privileged mutations (`createCSAKey`, and any other key-management mutations) or by adding an explicit role check (equivalent to `auth.RequiresEditRole`) inside each corresponding resolver function in `core/web/resolver/mutation.go`, pulling the authenticated session/role out of `ctx` (as already done elsewhere in `core/web/auth/gql.go`/`core/web/resolver/auth.go`) before calling into `App.GetKeyStore().CSA().Create`.

### Proof of Concept
1. In `core/web/resolver/mutation_test.go` (or `resolver_test.go`), construct a GraphQL test client using the existing `setupTestDB`/`gqlTestFramework` harness used in the repo's resolver tests.
2. Build a context/session representing a user with `sessions.UserRoleView` (or `UserRoleRun`) rather than `UserRoleEdit`/`UserRoleAdmin`.
3. Execute the mutation:
```graphql
mutation {
  createCSAKey {
    ... on CreateCSAKeySuccess {
      csaKey { id }
    }
    ... on CSAKeyExistsError {
      message
    }
  }
}
```
4. Assert that `App.GetKeyStore().CSA().Create` mock is NOT invoked, and that the resolver returns an authorization/forbidden error — currently this assertion will fail because the call succeeds and a key is created.
5. Compare against the REST integration test for `POST /v2/keys/csa` (`core/web/csa_keys_controller_test.go`) which already asserts a 403 for non-edit roles, to show the parity gap between REST and GraphQL enforcement.
