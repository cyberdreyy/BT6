### Title
Dust instant-withdraw request permanently bricks `stopEpoch` when `instantWithdrawDelay` exceeds the remaining epoch — (File: contracts/IdleCDOEpochVariant.sol)

### Summary
The external bug is a hang/crash (DoS) class issue. The closest analog in the epoch-based credit vault is the coupling between `IdleCreditVault.requestInstantWithdraw` and the stop-epoch gate in `IdleCDOEpochVariant._stopEpoch`: `stopEpoch` reverts while `pendingInstantWithdraws != 0`, but the only way to clear that counter is `getInstantWithdrawFunds`, which reverts before `instantWithdrawDeadline = epochStart + instantWithdrawDelay`. Because `setInstantWithdrawParams` performs no bound check on `_delay` relative to `epochDuration`, any unprivileged KYC-passing tranche holder can permanently wedge the epoch state machine with a 1-wei instant-withdraw request whenever `instantWithdrawDelay >= epochDuration`.

### Finding Description
Two independent guards combine into a deadlock:

1. `IdleCDOEpochVariant._stopEpoch` reverts if `_pendingInstant() != 0` (line ~345: `_pendingInstant() != 0` in the `_checkNotAllowed` block). Any pending instant request — including a 1-wei one — blocks epoch settlement.
2. `IdleCDOEpochVariant.getInstantWithdrawFunds` is the only function that decrements `pendingInstantWithdraws` (via `IdleCreditVault.collectInstantWithdrawFunds`, line ~401: `pendingInstantWithdraws -= _amount`), and it reverts while `block.timestamp < instantWithdrawDeadline` (line ~561), where `instantWithdrawDeadline = epochStart + instantWithdrawDelay` (line ~268).

`setInstantWithdrawParams` (line ~131) sets `instantWithdrawDelay` with no validation against `epochDuration`. If `instantWithdrawDelay > epochDuration`, then `instantWithdrawDeadline > epochEndDate`, so the deadline can never pass while `isEpochRunning` is true — `getInstantWithdrawFunds` reverts forever and `stopEpoch` reverts forever.

The attacker trigger is cheap and reachable: during the buffer period, if the new APR dropped below `lastEpochApr - instantWithdrawAprDelta`, `requestWithdraw` routes through `IdleCreditVault.requestInstantWithdraw` (lines ~761–769), which unconditionally increments `pendingInstantWithdraws` (line ~374). Withdrawing 1 wei of a tranche suffices. Withdraw requests are only gated by `allowAAWithdrawRequest`/`allowBBWithdrawRequest` and `isWalletAllowed` — all satisfied by a normal lender during the buffer.

After the deadline never arrives, `epochEndDate` passes, `isEpochRunning` stays true, and:

- `stopEpoch` reverts on `_pendingInstant() != 0`.
- `getInstantWithdrawFunds` reverts on `block.timestamp < instantWithdrawDeadline`.
- `startEpoch` reverts (`block.timestamp < epochEndDate + bufferPeriod` fails, and epoch is still running).
- `_beforeUnpause` blocks unpausing while `isEpochRunning`, and `restoreOperations` returns early for the same reason.
- All lender funds are frozen; matured `claimWithdrawRequest` payouts are also blocked because `epochNumber` never advances (`epochNumber <= lastWithdrawRequest` revert in `IdleCreditVault._claimFundedWithdrawRequest`, line ~326).

The only escape is the manager shortening `instantWithdrawDelay` (honest, but requiring an active intervention), or a forced default path — neither of which the protocol can reach autonomously.

### Impact Explanation
The entire pool TVL (AA + BB tranches plus pending withdraw receipts) is frozen for at least `instantWithdrawDeadline - epochEndDate`, and indefinitely if the manager does not or cannot update the delay. All deposited underlyings sit with the borrower while no epoch can stop, no requests can be claimed, and the contract stays paused. This matches the external bug class (hang/crash = availability loss) mapped onto the vault as temporary-to-permanent freezing of user funds.

### Likelihood Explanation
Requires two conditions: (a) `instantWithdrawDelay >= epochDuration` — plausible for short epochs or long delays since the setter does not enforce a bound; and (b) the APR dropped by more than `instantWithdrawAprDelta` between epochs so `requestWithdraw` routes to instant mode — a normal occurrence, and one an attacker can also partially influence only through config, but the request itself needs just dust tranche tokens. No privileged action by the attacker is needed; the cost is ~1 wei of tranche balance plus gas. Likelihood is gated by the delay misconfiguration, so it is conditional rather than universal — but the code gives no guard against it.

### Recommendation
- In `setInstantWithdrawParams`, enforce `_delay < epochDuration` (and/or cap it to a sane maximum) so the instant-withdraw deadline always falls inside the running epoch.
- Alternatively/additionally, allow `stopEpoch` to proceed when `block.timestamp >= epochEndDate` by treating unfunded instant requests as a loss-adjusted or default event instead of a hard revert, so a stale `instantWithdrawDeadline` cannot deadlock the epoch.
- Consider bounding `instantWithdrawDeadline` to `min(epochStart + delay, epochEndDate)` at `startEpoch`.

### Proof of Concept
Foundry fork test sketch:

```solidity
// Setup: pool running normally, epochDuration = 30 days.
// Manager (mis)configures instant withdrawals with a delay longer than the epoch:
vm.prank(manager);
cdoEpoch.setInstantWithdrawParams(60 days, 1000, false); // delay 60d > 30d epoch
// and stopEpoch set a new APR lower than lastEpochApr by > instantWithdrawAprDelta.

// Attacker: any KYC'd lender holding >= 1 wei of AA tranche.
// During buffer (allowAAWithdrawRequest == true, APR dropped):
vm.prank(attacker);
cdoEpoch.requestWithdraw(1, address(AAtranche));
// -> routed to strategy.requestInstantWithdraw -> pendingInstantWithdraws == 1

// Manager starts the epoch:
vm.prank(manager);
cdoEpoch.startEpoch(); // instantWithdrawDeadline = now + 60 days; epochEndDate = now + 30 days

// Epoch ends; borrower is honest and willing to repay.
vm.warp(cdoEpoch.epochEndDate() + 1);

// getInstantWithdrawFunds is impossible (deadline not reached):
vm.prank(manager);
vm.expectRevert(NotAllowed.selector);
cdoEpoch.getInstantWithdrawFunds();

// stopEpoch is impossible (pendingInstantWithdraws != 0):
vm.prank(manager);
vm.expectRevert(NotAllowed.selector);
cdoEpoch.stopEpoch(newApr, 0);

// Warping arbitrarily far does not help unless delay is reconfigured:
vm.warp(block.timestamp + 365 days);
vm.prank(manager);
vm.expectRevert(NotAllowed.selector); // still pendingInstant != 0
cdoEpoch.stopEpoch(newApr, 0);

// All lender funds remain locked with the borrower; no claim/exit path works.
```

Caveat: the validity depends on treating `instantWithdrawDelay >= epochDuration` as a reachable configuration — `setInstantWithdrawParams` does not prevent it, but it is a manager-set parameter. If the audit scope considers arbitrary manager misconfiguration out of scope, this degrades to a hardening recommendation rather than a standalone unprivileged exploit.
