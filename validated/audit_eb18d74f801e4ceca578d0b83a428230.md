Confirmed: `assert_valid_request` in both `multisig/src/lib.rs:293-310` and `multisig2/src/lib.rs:407-423` only checks that the request exists and that the caller (in v1: predecessor==current_account; in v2: `current_member().is_some()`) is presently valid. It never re-validates the *existing* confirmers recorded in `self.confirmations`. Combined with `delete_member`/`DeleteKey` only purging requests *authored* by the removed member (not confirmations *cast* by that member on other members' requests), this creates a stale-confirmation-counts-toward-threshold bug — a direct analog of the reused/stale-ID trust bug in the report.

### Title
Confirmations from removed multisig members are not purged, allowing request execution below the live-member confirmation threshold - ([File: multisig2/src/lib.rs], [File: multisig/src/lib.rs])

### Summary
`delete_member` (multisig2) and the `DeleteKey` action (multisig1) only delete pending *requests that the removed member/key originally authored*. They do not scrub that member's/key's confirmations from the `confirmations` sets of *other* still-pending requests that this member had already confirmed. `confirm()` and `assert_valid_request()` never re-validate that every entry already present in a request's confirmation set still belongs to a current member. As a result, a confirmation cast by a member who is later removed remains permanently counted toward `num_confirmations`, letting the remaining live members execute a request with fewer live approvals than the configured threshold.

### Finding Description
In `multisig2/src/lib.rs`, `confirm()` computes the threshold purely from the size of the stored `confirmations` set plus the new caller: [1](#0-0) 

`assert_valid_request()` validates only that the caller is a current member and that the request/confirmations entries exist — it performs no check on the *contents* of the confirmation set: [2](#0-1) 

`delete_member()` removes membership and purges only requests where `r.member == member` (i.e., requests the removed member proposed). It never scans other requests' `confirmations` maps to strip the removed member's prior approval from requests they merely confirmed: [3](#0-2) 

The exact same pattern exists in the v1 contract: `DeleteKey` purges only requests authored by that key, and `confirm`/`assert_valid_request` never re-validate stored confirmations: [4](#0-3) [5](#0-4) [6](#0-5) 

This breaks the intended custody binding: **confirmations counted == confirmations from currently-live members**. Once a member's confirmation is recorded, it becomes a permanently trusted stale credential that survives that member's removal from the multisig, exactly analogous to the reused/stale-ID trust artifact (`nft.shortOrderId`) in the report that outlived the entity it originally referenced.

### Impact Explanation
This allows a `MultiSigRequest` (e.g., a `Transfer` of the multisig's NEAR balance, a `FunctionCall`, `AddKey`/`AddMember`, etc.) to be executed with confirmations from fewer *currently valid* members than `num_confirmations` requires — i.e., "a multisig request executed below threshold." Given the multisig contracts in this repo are used to control foundation/lockup-owner funds and staking pool administration, this directly enables NEAR to be moved, or privileged actions (adding keys/members) to be taken, by a coalition smaller than the configured k-of-n security guarantee.

### Likelihood Explanation
The scenario only requires normal operational usage of the multisig's own documented flows — no compromised infra, no owner action beyond what governance itself performs: a member confirms a pending request, that member is later removed via a separate, otherwise-legitimate `DeleteMember`/`DeleteKey` governance action (membership changes are a normal event, e.g., rotating signers), and the previously-confirmed request is subsequently pushed over the threshold by fewer than `num_confirmations` *current* members. No special exploit setup, race condition, or foundation cooperation is required.

### Recommendation
When executing `DeleteMember`/`DeleteKey`, iterate over *all* pending requests' confirmation sets (not just requests authored by that member) and remove the departing member's/key's confirmation entry from each. Alternatively/additionally, have `confirm()` (or `assert_valid_request`) re-validate, at confirmation-counting time, that every principal already present in `confirmations.get(&request_id)` is still a current member (`self.members.contains(..)` in v2, or still tracked in `num_requests_pk`/valid access key in v1), discarding stale entries before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `{A, B, C, D}` and `num_confirmations = 3`.
2. `B` calls `add_request_and_confirm(R1)` where `R1` is a `Transfer` action — `confirmations[R1] = {B}`.
3. `C` calls `confirm(R1)` — `confirmations[R1] = {B, C}` (2/3, not yet executed).
4. Separately, an already-approved `DeleteMember { member: C }` request executes (3/4 valid confirmations from the *other* legitimate governance flow) — per `delete_member()` (`multisig2/src/lib.rs:355-379`), only requests *authored by* `C` are purged; `R1` (authored by `B`) is untouched, so `confirmations[R1]` still contains `C`, even though `C` is no longer in `self.members`.
5. Remaining members are `{A, B, D}`. `A` calls `confirm(R1)`: `confirmations.len() (2, including stale C) + 1 == 3 >= num_confirmations (3)` → `execute_request(R1)` fires the `Transfer`.
6. `R1` executed with only 2 currently-live members (`A`, `B`) having approved it — below the configured 3-of-n threshold — because the stale confirmation from removed member `C` was silently counted.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);

            .current_member()

        );

        } else {

            self.confirmations.insert(&request_id, &confirmations);

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
