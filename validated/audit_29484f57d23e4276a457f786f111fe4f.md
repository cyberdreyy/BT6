This confirms the vulnerability: `isReplay` (RLock) and `recordUsage` (Lock) are two separate, non-atomic lock acquisitions in `Authorize`. Between the `isReplay` check and the eventual `recordUsage` call, other authorization steps run without holding any lock, and `WorkflowMetadataHandler.Authorize` itself takes no lock at all around the check-then-act sequence.

### Title
JWT replay-cache check-then-act race allows single-use HTTP trigger token to be replayed for duplicate workflow executions - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

### Summary
`WorkflowMetadataHandler.Authorize` validates a JWT's signature/digest, checks replay via `jwtCache.isReplay(claims.ID)`, performs authorization lookups, and only then calls `jwtCache.recordUsage(claims.ID)` to mark the token consumed. The check and the mark-as-used mutation are not atomic with respect to each other, mirroring the root cause pattern in the referenced report where a state-reducing operation (`idleETH -=`) was separated from the subsequent external call, letting the same balance be reused across a reentrant execution before the "spend" was finalized.

### Finding Description
`Authorize` is invoked per-request from `httpTriggerHandler.authorizeRequest` [1](#0-0) , which is called on every incoming `HandleUserTriggerRequest` from an unauthenticated gateway client [2](#0-1) .

Inside `Authorize`, the sequence is:
1. Verify JWT signature/digest.
2. `h.jwtCache.isReplay(claims.ID)` — acquires `cache.mu.RLock()`, checks membership, releases the lock [3](#0-2) .
3. Workflow-existence and signer-authorization map lookups (no lock held on `h.authorizedKeys` in `Authorize` itself).
4. `h.jwtCache.recordUsage(claims.ID)` — acquires `cache.mu.Lock()` separately and inserts the jti [4](#0-3) .

The full method itself never holds a lock across steps 2–4 [5](#0-4) . If two requests carrying the identical signed JWT (same `jti`, same request digest) arrive concurrently, both can pass `isReplay` before either calls `recordUsage`, because the "read" (check) and "write" (mark used) are two independent, separately-locked operations rather than a single atomic check-and-set. This is the same class of bug as the reported issue: a state mutation intended to prevent double-use is deferred past the point where the guarded action can be repeated, letting an attacker perform the guarded action more than once for a single credential.

### Impact Explanation
An unprivileged client possessing one valid, correctly-signed HTTP-trigger JWT (single intended use — this is the mechanism's entire purpose per the "different JWT IDs should work"/replay tests [6](#0-5) ) can race concurrent identical requests to bypass the single-use guarantee and trigger the same workflow execution multiple times through the internet-facing gateway. This is an authorization/quota-bypass class impact: duplicate unauthorized job runs (workflow executions) from a token meant to authorize exactly one execution, potentially amplifying costs, side effects, or downstream consumption tied to that workflow trigger.

### Likelihood Explanation
Exploitability requires only sending duplicate identical requests concurrently (fast in succession) to the public gateway endpoint that forwards to `HandleUserTriggerRequest`; no special privileges, other nodes' cooperation, or network-layer conditions are needed. Given `isReplay`/`recordUsage` are separate lock acquisitions with request processing (workflow lookup, signer authorization) between them, the race window is real, though narrow (microsecond-scale gap), making this a timing-dependent but concretely reachable race from an unprivileged client.

### Recommendation
Make the check-and-mark atomic: hold a single lock (or a `LoadOrStore`-style atomic map operation) across "is this jti already used?" and "mark jti used" so no two concurrent requests can both observe the token as unused. For example, merge `isReplay` + `recordUsage` into one `jwtReplayCache.checkAndRecord(jti string) (alreadyUsed bool)` method that takes `cache.mu.Lock()` once, checks and inserts the jti in the same critical section, and returns whether it was a replay — mirroring the mitigation for the referenced bug, which fixed the ordering so the balance decrement happens before the external call that could reenter.

### Proof of Concept
1. Register a workflow and its authorized signer key with the gateway's `WorkflowMetadataHandler`.
2. Craft one valid signed JWT for a `HandleUserTriggerRequest` call (fixed `jti`, fixed request digest).
3. Fire two (or more) concurrent HTTP-trigger requests to the gateway using the identical JWT/`Auth` value, e.g. via `go` routines both calling `httpTriggerHandler.HandleUserTriggerRequest` (or the equivalent gateway HTTP endpoint) at the same time.
4. Under the current implementation, because `isReplay` (read lock) and `recordUsage` (write lock, called only after further processing) are not part of one atomic critical section, both concurrent calls can pass the `isReplay(claims.ID)` check before either calls `recordUsage(claims.ID)`, resulting in the workflow being triggered twice from a single-use token — unlike the sequential test in `workflow_metadata_handler_test.go` ("JWT replay protection") which only demonstrates that *sequential* replay is blocked, not concurrent replay [6](#0-5) .

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}
