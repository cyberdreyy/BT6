### Title
Stale rejection weight is never retracted when a signer later accepts, corrupting the miner's aggregated accept/reject tally - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener` tallies `total_weight_approved` and `total_weight_rejected` for a proposed block by watching `BlockResponse` messages from signers. The two counters are gated by two *different* dedup keys: the `Accepted` path gates its weight addition on `gathered_signatures.contains_key(&slot_id)`, while the `Rejected` path gates on `responded_signers.insert(slot_id)`. Because `responded_signers` is a single set shared by both message kinds but the `Accepted` branch never checks it before adding weight, a signer that first rejects and later accepts the same block has its weight added to `total_weight_rejected` and then, independently, also added to `total_weight_approved`. The rejection weight is never retracted. This breaks the intended "aggregated-weight vs verified-accepts" invariant that `SignCoordinator::get_block_status` relies on to decide whether a block is globally accepted or rejected.

Rejected-message handling (weight gated on `responded_signers`): [2](#0-1) 

Sequence that triggers the divergence, driven entirely by **one** signer's own StackerDB slot (no majority, no other signer's key required):

1. Signer `S` (slot `k`, weight `w`) sends `BlockResponse::Rejected` for block `B` (e.g. immediately after a validation failure that is later resolved, or simply a signer that changes its mind after re-evaluating chainstate, which the protocol explicitly allows — see `docs/signer-flows.md` section 6: "a rejection is a revocable opinion"). This causes `responded_signers.insert(k)` to succeed and `total_weight_rejected += w`.
2. Signer `S` later sends `BlockResponse::Accepted` for the *same* block `B` (a legitimate flow: `handle_block_pre_commit`/`store_and_process_block_signature` in `stacks-signer/src/v0/signer.rs` allow a signer to still sign after an earlier rejection once conditions change).
3. In the `Accepted` handler, the gate is `!block.gathered_signatures.contains_key(&slot_id)`. Since `gathered_signatures` has never been touched for slot `k`, this is `true`, so `total_weight_approved += w` runs unconditionally, on top of the `w` already counted in `total_weight_rejected`.
4. `total_weight_rejected` is never decremented anywhere in this file, so the stale rejection weight persists forever for the life of the `BlockStatus` entry.

Now `total_weight_approved + total_weight_rejected` can legitimately exceed `total_weight`, and `total_weight_rejected` reflects an opinion the signer itself retracted. This value is consumed directly by the mining coordinator: [3](#0-2) [4](#0-3) 

The reject-check runs first in this `if/else if` chain, so stale rejection weight left over from a signer that has since flipped to accept can trip `total_weight_rejected.saturating_add(weight_threshold) > total_weight` even while `total_weight_approved` has also independently reached `weight_threshold` in the same or a subsequent poll. Because the check order always prioritizes rejection, the coordinator can declare the block globally rejected (`NakamotoNodeError::SignersRejected`) purely due to the never-retracted stale weight, even though the *current* aggregated approvals already satisfy the 70% threshold.

### Impact Explanation
This breaks the "aggregated-weight vs verified-accepts equality" the coordinator relies on: the tallies in `BlockStatus` no longer reflect a partition of signer weight into "currently rejecting" and "currently accepting" — a single signer's weight can occupy both buckets simultaneously. The direct, single-signer-triggerable consequence is a liveness wedge on the block currently being signed: the miner's coordinator can conclude `SignersRejected` for a block that in fact has legitimate ≥70% weight support, because one signer's stale, already-superseded rejection is permanently counted toward the 30% blocking minority. This can force miners to repeatedly abandon and rebuild valid block proposals, and (via the `temporarily_excluded_txids`/`permanently_excluded_txids` logic keyed off `failed_txids`, which is populated from the same stale-weight rejection) can also cause transactions to be needlessly excluded from future proposals.

### Likelihood Explanation
Trivially reachable: any single signer's StackerDB slot flip-flopping between `Rejected` and `Accepted` for the same block sighash — a sequence the signer-side code explicitly permits (rejections are documented as "revocable," and `handle_block_pre_commit`/`store_and_process_block_signature` allow signing after an earlier local rejection once chainstate checks pass) — is sufficient. No majority collusion, no other signer's key, and no StackerDB transport games are needed; it is purely an accounting bug in how the two weight counters are gated.

### Recommendation
Gate both `Accepted` and `Rejected` weight additions on the *same* dedup key (`responded_signers`), and when a signer's vote flips, subtract the previously counted weight from the old bucket before (or while) adding it to the new bucket, so that at any point in time a signer's weight is counted in at most one of `total_weight_approved` / `total_weight_rejected`, and `total_weight_approved + total_weight_rejected <= total_weight` always holds.

### Proof of Concept
1. Set up a reward set with signers such that a single signer `S` holds weight `w` where `w` is enough to push `total_weight_rejected` close to the blocking-minority threshold (`total_weight - weight_threshold`) once other honest signers have already rejected up to `blocking_minority - w`.
2. Have `S` broadcast `BlockResponse::Rejected` for block `B` — `stackerdb_listener.rs` lines 515-518 add `w` to `total_weight_rejected` and mark `S` in `responded_signers`.
3. Have `S` subsequently broadcast `BlockResponse::Accepted` for the same `B` (a legitimate re-evaluation) — lines 443-465 add `w` again to `total_weight_approved` because the gate checks `gathered_signatures`, not `responded_signers`.
4. Observe that `total_weight_rejected` still includes `w` (never retracted) while `total_weight_approved` also includes `w`; with the right mix of other signers' votes this makes `SignCoordinator::get_block_status` (`signer_coordinator.rs` lines 509-520) return `NakamotoNodeError::SignersRejected` for a block whose current approvals in fact meet the 70% threshold.
