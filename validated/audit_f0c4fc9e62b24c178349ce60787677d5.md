### Title
Unprivileged ERC4626 vault users can manipulate the spot `convertToAssets` price used for epoch interest/loss accounting and share minting in `ProgrammableBorrower` - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary
`ProgrammableBorrower` — the borrower adapter used by `IdleCDOEpochVariant` for revolving-credit facilities — values its vault sleeve exclusively through the spot ERC4626 exchange rate (`vault.convertToAssets(shares)`), the direct analog of the USSD bug where `uniPool.slot0()` was used for valuation. This spot rate is read in `_currentVaultAssets()` and feeds `_vaultNetInterest()`, `totalInterestDueNow()`, `availableToBorrow()`, and the share-minting path in `_depositToVault()`. An attacker that is simply a user of the ERC4626 vault (an allowed attacker profile per the rules) can move this rate within a single transaction, which corrupts both the interest credited to the pool at `stopEpoch` and the number of vault shares the facility receives for its deposits.

### Finding Description
`ProgrammableBorrower` snapshots `epochStartVaultAssets` and `bufferStartVaultAssets` in underlying terms derived from `convertToAssets`, then computes epoch PnL as the delta between the spot-converted position and the tracked baselines:

- `_currentVaultAssets()` = `vault.balanceOf(this)` × spot `convertToAssets` [1](#0-0) 
- `_vaultNetInterest()` turns `bufferedVaultDelta + earnedAssets - principalAssets` into `interest`/`loss` [2](#0-1) 
- `totalInterestDueNow()` is the single value `IdleCDOEpochVariant` reads before `onStopEpoch` to price the epoch [3](#0-2) 
- `_depositToVault()` calls `vault.deposit()` at the manipulated spot rate, so an inflated share price mints the facility fewer shares for the same assets [4](#0-3) 

Two concrete manipulation paths exist for an unprivileged vault user:

1. **Deposit-sandwich / share inflation.** When `onStartEpoch` or `_repay` triggers `_depositToVault` (idle cash is always parked in the vault during an active epoch), the attacker donates a large amount of underlying directly to the vault, inflating `convertToAssets`. `vault.deposit()` then mints the facility fewer shares than economically fair (classic ERC4626 donation/rounding attack); the attacker redeems their own vault shares at the inflated rate and pockets the difference. The facility's share balance is worth less than `epochDepositedToVault`, which `_vaultNetInterest` later crystallizes as `loss` and reports to the CDO — socializing the extracted value to tranche holders (BB first via the loss waterfall in `_virtualPriceAux`).
2. **Inflated `totalInterestDueNow`.** A donation right before `stopEpoch` raises `totalInterestDueNow`, so `IdleCDOEpochVariant` prices the epoch as if extra yield existed. If the vault cannot honor the withdrawal at the inflated valuation (e.g., `maxWithdraw`/liquidity constraints), `onStopEpoch`'s `vault.withdraw` reverts (`StopEpochVaultLiquidityUnavailable`) or the CDO's `transferFrom` under-funds and flows into the default/`_handleBorrowerDefault` path, forcing an unwarranted loss distribution — even though the borrower's contractual debt is unchanged.

There is no TWAP, no min-shares slippage bound on `vault.deposit`/`vault.withdraw`, and no sanity bound on `netDelta`; the only guard is `shortfall > _currentVaultAssets()` returning `true`, which itself trusts the same manipulated spot price [5](#0-4) 

### Impact Explanation
Path 1 causes direct loss to tranche holders: the donation-extracted value is booked as `vaultLoss`, which `stopEpoch` propagates through `_updateAccounting`, hitting BB NAV first and AA if BB is exhausted — i.e., attacker profit is socialized to lenders. Magnitude is bounded by the deposit amount and vault share-supply dynamics, but on a low-supply vault it can approach the full deposited amount (first-depositor-style inflation). Path 2 causes mispriced epochs and can force an unjustified default transition, freezing lender withdrawals behind the default/recovery flow. Both are unprivileged and repeatable each epoch boundary.

### Likelihood Explanation
Requires only that the configured ERC4626 vault computes `totalAssets`/`convertToAssets` from manipulable balances or permits donation-based share inflation — true for many ERC4626 wrappers — and that the attacker can hold vault shares, which the rules explicitly allow ("a user of the programmable borrower's ERC4626 vault"). All privileged roles (owner, manager, borrower, queue) behave honestly; the attack is sequenced purely around `onStartEpoch`/`_repay`/`stopEpoch` calls. If the production vault is a donation-resistant vault (e.g., MetaMorpho with internal accounting), path 1 weakens, but the rate can still be moved by large deposit/withdraw flows, so the spot-rate dependency remains fragile.

### Recommendation
- Do not let a single spot `convertToAssets` reading drive both interest credit and loss recognition. Track the vault position in *shares* and value it conservatively, e.g., recognize losses at `convertToAssets` (spot) but recognize gains only up to a time-based accrual cap or a TWAP/rolling rate.
- Add slippage bounds to `_depositToVault` and `onStopEpoch` withdrawals: compute expected shares/assets before the call and revert if realized output deviates beyond a configured tolerance.
- Snapshot `epochStartVaultAssets` from share count × a price captured at accounting-start, not re-derived from a manipulable spot rate mid-epoch.
- Prefer vaults with donation-resistant (internally accounted) `totalAssets`, or whitelist only such vaults in `setVault`.

### Proof of Concept
Conceptual Foundry fork PoC (deposit-sandwich path):

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;
import "forge-foundry/ProgrammableBorrowerCreditVault.t.sol"; // reuse existing fixture

contract SpotPriceManipulationPoC is ProgrammableBorrowerCreditVault {
    function testDepositSandwichExtractsValue() public {
        // Epoch running; ProgrammableBorrower holds vault shares + idle cash about
        // to be parked via _depositToVault (repay or onStartEpoch).
        uint256 pbDeposit = 1_000e18;

        // Attacker (plain vault user) holds shares and donates to inflate price.
        underlying.mint(attacker, 500e18);
        vm.startPrank(attacker);
        underlying.transfer(address(vault), 500e18); // donation -> convertToAssets spikes

        // Honest borrower repays -> _repay -> _depositToVault(totalRepaidAssets, ...)
        // PB mints far fewer shares than pbDeposit worth at the fair rate.
        borrower.repay(pbDeposit);
        vm.stopPrank();

        // Attacker redeems vault shares at inflated rate, extracting > donation.
        vm.prank(attacker);
        vault.redeem(vault.balanceOf(attacker), attacker, attacker);

        // At stopEpoch: _vaultNetInterest reports vaultLoss because
        // shares*convertToAssets < epochStartVaultAssets + epochDepositedToVault.
        vm.prank(owner);
        cdo.stopEpochWithDuration(duration, 0);
        // Loss is socialized: lastNAVBB decreases; attacker profit == BB tranche loss.
        assertGt(attackerProfit, 0);
        assertLt(cdo.lastNAVBB(), navBBBefore);
    }
}
```

Caveat: the exact profit depends on the deployed vault's `convertToAssets` internals; if the production vault uses internally tracked `totalAssets` immune to direct donations, the PoC must instead move the rate via large vault deposits/withdrawals, which is weaker but still unprivileged. The structural flaw — uncapped reliance on a single spot share price for both interest credit and share minting — is independent of which manipulation vector is cheapest.

  function _vaultNetInterest() internal view returns (uint256 interest, uint256 loss) {
    if (!epochAccountingActive) return (0, 0);
    uint256 earnedAssets = _currentVaultAssets() + epochWithdrawnFromVault;
    uint256 principalAssets = epochStartVaultAssets + epochDepositedToVault;
    int256 netDelta = bufferedVaultDelta + int256(earnedAssets) - int256(principalAssets);
    if (netDelta > 0) {
      interest = uint256(netDelta);
    } else {
      loss = uint256(-netDelta);
    }
  }
