### Title
Lockup address squatting — attacker can front-run `LockupFactory::create` for any `owner_account_id` and permanently deploy attacker-chosen lockup parameters - ([File: lockup-factory/src/lib.rs])

### Summary
`LockupFactory::create` derives the deterministic lockup account id solely from `sha256(owner_account_id)[..20]`, with no dependency on `env::predecessor_account_id()`. Since the sub-action `create_account()` is a first-come-first-served operation, any unprivileged caller can call `create` for a victim's `owner_account_id` before the legitimate grant issuer does, permanently claiming the deterministic address with their own chosen `lockup_duration`, `vesting_schedule`, `release_duration`, and `staking_pool_whitelist_account_id`.

### Finding Description
The intended binding is: `LockupArgs deployed at hex::encode(sha256(owner_account_id)[..20]).<factory>` should equal `LockupArgs submitted by the legitimate/entitled grant issuer for that owner_account_id`. This binding is broken because the address computation at [1](#0-0) `let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes()); let lockup_account_id = format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());` uses only `owner_account_id` and the factory's own account id — `env::predecessor_account_id()` plays no role in the address derivation, and there is no on-chain reservation, allow-list, or registry check tying a specific `owner_account_id` to a specific permitted creator before the `Promise::create_account()` sub-action runs.

`create` is `#[payable]` and callable by anyone with `MIN_ATTACHED_BALANCE` (3.5 NEAR) attached [2](#0-1) . Because NEAR account creation is atomic and exclusive (only the first `create_account()` targeting a not-yet-existing account id succeeds), whichever `create()` call executes first for a given `owner_account_id` wins the account and deploys its own `LockupArgs` via `function_call(b"new".to_vec(), ...)` [3](#0-2) . The later, legitimate `create()` call for the same `owner_account_id` has its `create_account()` fail because the account already exists, and its `on_lockup_create` callback observes `is_promise_success() == false`, refunding the legitimate caller's `attached_deposit` back to their own `predecessor_account_id` rather than deploying anything [4](#0-3) . There is no `assert_self()`, allow-list check, or predecessor validation anywhere in `create` that would prevent an arbitrary predecessor from targeting an arbitrary `owner_account_id`.

Exploit flow: attacker observes (or predicts) that a grant issuer intends to create a lockup for `owner_account_id = victim`. Attacker calls `create(owner_account_id="victim", lockup_duration=0, lockup_timestamp=None, vesting_schedule=None, release_duration=None, whitelist_account_id=None)` with exactly `MIN_ATTACHED_BALANCE` attached, before the legitimate issuer's transaction lands. Attacker's `create_account()` succeeds first and deploys `LockupArgs` chosen entirely by the attacker (e.g., `lockup_duration=0`, no vesting, attacker's own whitelist account). The legitimate issuer's later `create()` call fails at `create_account()` and is refunded. Since account ids on NEAR cannot be redeployed once occupied by a contract without a full-access key on that specific sub-account (which the victim owner does not automatically hold in a useful way, and the legitimate issuer never controls it), the victim is permanently stuck with attacker-chosen lockup terms at that specific address, and the real grant issuer can never deploy the intended lockup at `hex::encode(sha256(victim))[..20]).<factory>`.

### Impact Explanation
The victim `owner_account_id` permanently receives a lockup contract whose `lockup_duration`, `vesting_schedule`, `release_duration`, and `staking_pool_whitelist_account_id` were never chosen by the rightful grant issuer — this is squarely the Critical category "an account whitelisted or a lockup deployed with parameters its rightful creator never chose." The attack is repeatable against every `owner_account_id` for which a lockup has not yet been created, giving unbounded blast radius across all future NEAR Foundation/grant lockups deployed through this factory. Depending on the attacker's chosen `vesting_schedule`/`lockup_duration` (e.g., `lockup_duration=0`, no vesting), the deployed lockup could also allow immediate withdrawal of any subsequently transferred funds, compounding the impact.

### Likelihood Explanation
The attack requires only: (1) knowledge or prediction of the `owner_account_id` that a legitimate grant issuer intends to use (these are typically well-known, e.g., specific employee/investor NEAR accounts, and predictable/public information), (2) `MIN_ATTACHED_BALANCE` (3.5 NEAR) which any unprivileged attacker can hold, and (3) submitting the transaction before the legitimate issuer's `create()` transaction is included. This is a standard front-running/account-squatting scenario, fully within the "unprivileged attacker" capabilities defined in the rules (send transactions, attach deposits). No special privilege, key compromise, or foundation access is required, making this highly feasible and repeatable per un-deployed `owner_account_id`.

### Recommendation
Bind lockup creation authorization to the predecessor, e.g., restrict `create()` to be callable only by `self.foundation_account_id` (or an explicit allow-list of authorized issuers), or require a pre-registered commitment (e.g., a foundation-signed mapping of `owner_account_id -> allowed predecessor`) checked before `create_account()` is scheduled. Alternatively, derive the lockup address so a claim can only be made by the intended issuer, or add a reservation/registry step gated by `assert_called_by_foundation`-style checks before allowing the deterministic account to be created for a given `owner_account_id`.

### Proof of Concept
```rust
// near-sdk-sim / testing_env! style test in lockup-factory/src/lib.rs tests module
#[test]
fn test_lockup_address_squatting() {
    let mut context = VMContextBuilder::new()
        .current_account_id(account_factory())
        .predecessor_account_id(account_near())
        .finish();
    testing_env!(context.clone());
    let mut contract = LockupFactory::new(whitelist_account_id(), foundation_account_id());

    // Attacker calls create() first for victim's owner_account_id with attacker-chosen params
    context.predecessor_account_id = String::from(attacker_account_id());
    context.attached_deposit = MIN_ATTACHED_BALANCE;
    testing_env!(context.clone());
    contract.create(victim_owner_account_id(), 0u64.into(), None, None, None, Some(attacker_whitelist_account_id()));
    // (assert the scheduled Promise's function_call payload equals attacker's LockupArgs)

    // Simulate account_id now exists at hex::encode(sha256(victim))[..20].<factory>
    context.predecessor_account_id = account_factory();
    context.attached_deposit = 0;
    testing_env_with_promise_results(context.clone(), PromiseResult::Successful(vec![]));
    let attacker_result = contract.on_lockup_create(
        lockup_account_for(victim_owner_account_id()),
        MIN_ATTACHED_BALANCE.into(),
        String::from(attacker_account_id()),
    );
    assert_eq!(attacker_result, true); // attacker's deployment succeeded

    // Legitimate issuer later calls create() for the same owner_account_id
    context.predecessor_account_id = String::from(legit_issuer_account_id());
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());
    contract.create(victim_owner_account_id(), LOCKUP_DURATION.into(), None, Some(legit_vesting_schedule()), None, None);

    // create_account() sub-action fails because account already exists -> PromiseResult::Failed
    context.predecessor_account_id = account_factory();
    context.attached_deposit = 0;
    testing_env_with_promise_results(context.clone(), PromiseResult::Failed);
    let legit_result = contract.on_lockup_create(
        lockup_account_for(victim_owner_account_id()),
        ntoy(35).into(),
        String::from(legit_issuer_account_id()),
    );
    assert_eq!(legit_result, false); // legitimate creator's deployment permanently blocked, refunded instead
}
```
This demonstrates: the deployed `LockupArgs` at the deterministic address are the attacker's (not the legitimate issuer's), and the legitimate issuer's `on_lockup_create` returns `false`, confirming the broken binding.

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
