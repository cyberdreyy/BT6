### Title
Permissionless ERC4626 liquidity withdrawal can repeatedly revert `stopEpoch` and freeze withdrawals - (File: `contracts/strategies/idle/ProgrammableBorrower.sol`)

### Summary
In programmable-borrower mode, an unprivileged user of the external ERC4626 vault can front-run `stopEpoch` and withdraw their own shares, consuming the vault’s available liquidity. `ProgrammableBorrower.onStopEpoch()` then reverts while trying to withdraw the CDO-required amount, causing the entire epoch settlement to revert and leaving mature withdrawal receipts temporarily unclaimable.

### Finding Description
`IdleCDOEpochVariant._stopEpoch()` calls `ProgrammableBorrower.onStopEpoch(_amountToPullFromBorrower + _pendingWithdraws, ...)` before pulling funds from the borrower. [1](#0-0) 

Inside `onStopEpoch`, if the programmable borrower does not already hold enough underlying tokens, it checks whether its ERC4626 share valuation covers the shortfall and then calls `vault.withdraw(shortfall, address(this), address(this))`. [2](#0-1) 

The catch block converts any ERC4626 withdrawal failure into `StopEpochVaultLiquidityUnavailable`, which bubbles through the privileged `stopEpoch` call and aborts settlement. [3](#0-2) 

A mempool attacker who owns shares in the configured external ERC4626 vault can therefore:

1. Wait until `block.timestamp >= epochEndDate` and observe the manager’s `stopEpoch` transaction.
2. Front-run it with `vault.redeem(attackerShares, attacker, attacker)` or `vault.withdraw(...)`, consuming enough vault liquidity that the programmable borrower’s subsequent `withdraw(shortfall)` fails.
3. Keep the borrower’s share valuation economically sufficient, so `shortfall <= _currentVaultAssets()` and the code reaches the reverting `withdraw` call.
4. Repeat the same liquidity-consumption transaction whenever enough liquidity returns to the vault.

Because `_stopEpoch` reverts, `epochNumber` is not incremented. Funded withdrawal claims remain gated by `epochNumber <= lastWithdrawRequest[_user]`, so victims who requested withdrawals in the request epoch cannot claim until a later settlement succeeds. [4](#0-3) 

### Impact Explanation
This is temporary freezing of withdrawal funds with a measurable amount equal to the cash required by the stop operation—primarily `pendingWithdraws` in minted-interest programmable mode, and expected interest plus pending withdrawals in cash-funded operation. [5](#0-4) 

While the attack persists:

- Mature normal withdrawal receipts cannot transition to a claimable epoch.
- Pending-withdraw funding is not collected through `collectWithdrawFunds`. [6](#0-5) 
- The epoch remains running because the state transition at the end of `_stopEpoch` is never reached. [7](#0-6) 
- New deposits and withdrawal requests remain disabled because epoch state is not reset.

The attack does not directly steal LP funds, but it can repeatedly delay all pending withdrawals by making an otherwise economically covered ERC4626 position temporarily illiquid at execution time.

### Likelihood Explanation
Likelihood is deployment-dependent. The attacker needs to control enough external-vault shares, or another permissionless liquidity-consumption path, to make `vault.withdraw(shortfall)` fail. This is realistic for shared ERC4626 vaults that keep only part of `totalAssets` liquid or lend assets externally.

No privileged Idle role is required: the attacker only transacts with the programmable borrower’s external ERC4626 vault. The current guard only checks share valuation through `convertToAssets`; it does not verify immediately withdrawable liquidity or reserve pending withdrawals on hand. [2](#0-1) 

### Recommendation
Keep `epochPendingWithdraws` on hand in the programmable borrower instead of depositing all idle underlying into the ERC4626 vault at `onStartEpoch`. The contract already tracks that reserve, but `_depositToVault(underlyingToken.balanceOf(address(this)), 0)` invests the entire balance. [8](#0-7) 

For additional resilience, check `vault.maxWithdraw(address(this))` before calling `withdraw`, and use an asynchronous settlement or emergency-exit path for genuinely illiquid ERC4626 positions rather than allowing a transient external-vault revert to abort the complete epoch transition.

// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IERC4626} from "contracts/interfaces/IERC4626.sol";
import {IERC20Detailed} from "contracts/interfaces/IERC20Detailed.sol";
import {IdleCDOEpochVariant} from "contracts/IdleCDOEpochVariant.sol";
import {ProgrammableBorrower, StopEpochVaultLiquidityUnavailable}
  from "contracts/strategies/idle/ProgrammableBorrower.sol";

contract StopEpochVaultLiquidityGriefingForkTest is Test {
    // Fork configuration supplies the production deployments.
    IdleCDOEpochVariant cdo;
    ProgrammableBorrower borrower;
    IERC4626 externalVault;
    IERC20Detailed underlying;

    address manager;
    address liquidityAttacker;

    function testVaultShareholderCanGriefStopEpoch() external {
        // Preconditions on the fork:
        // - cdo.isProgrammableBorrower() == true
        // - cdo.isEpochRunning() == true
        // - borrower.epochPendingWithdraws() > 0
        // - block.timestamp >= cdo.epochEndDate()
        // - liquidityAttacker owns enough externalVault shares to consume
        //   the vault's liquid underlying balance.
        vm.warp(cdo.epochEndDate());

        uint256 requestEpoch = externalVaultSharesEpochInvariant();
        uint256 attackerShares = externalVault.balanceOf(liquidityAttacker);
        require(attackerShares != 0, "attacker needs external vault shares");

        // Unprivileged state change analogous to Uniswap sync(): it changes the
        // external liquidity state observed by the next transaction in this block.
        vm.prank(liquidityAttacker);
        externalVault.redeem(attackerShares, liquidityAttacker, liquidityAttacker);

        uint256 shortfall =
            borrower.epochPendingWithdraws()
                - underlying.balanceOf(address(borrower));

        assertGt(
            borrower.vault().convertToAssets(
                borrower.vault().balanceOf(address(borrower))
            ),
            shortfall,
            "share valuation still covers the shortfall"
        );

        // The privileged settlement still reverts because ERC4626 liquidity,
        // not economic coverage, is insufficient after the front-run.
        vm.prank(manager);
        vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
        cdo.stopEpoch(0, 0);

        assertTrue(cdo.isEpochRunning(), "epoch settlement must remain pending");

        // A request made in requestEpoch cannot become claimable while
        // epochNumber has not advanced.
        assertEq(requestEpoch, currentVaultEpochNumber());
    }

    function externalVaultSharesEpochInvariant()
        internal
        view
        returns (uint256)
    {
        return IdleCreditVault(cdo.strategy()).epochNumber();
    }

    function currentVaultEpochNumber() internal view returns (uint256) {
        return IdleCreditVault(cdo.strategy()).epochNumber();
    }
}
