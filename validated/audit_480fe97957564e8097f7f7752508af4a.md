### Title
Stale instant-withdraw epoch basis inflates default recovery denominator and permanently locks recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` releases the user's claimable balance (`instantWithdrawsRequests[_user] = 0`) but leaves the per-epoch receipt ledgers `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` untouched. Those "still-referenced" ledgers are later read by `defaultPendingClaimBasis` during `finalizeDefaultRecovery`, so already-claimed receipts continue to count as live recovery basis — the analog of freeing the module reference while the event data is still reachable.

### Finding Description
The withdrawal flow keeps two ledgers for the same receipt:

- Aggregate claimable: `instantWithdrawsRequests[_user]` and `pendingInstantWithdraws` (the unfunded remainder).
- Per-epoch basis: `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`, used for default-recovery accounting [1](#0-0) .

`requestInstantWithdraw` increments both [2](#0-1) . `claimInstantWithdrawRequest` burns the receipt and zeroes the aggregate, but never clears `instantWithdrawsRequestsByEpoch` nor decrements `instantWithdrawClaimsByEpoch` [3](#0-2) .

Those per-epoch values are only consumed on the default path: `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` to the recovery denominator whenever `pendingInstantWithdraws != 0` [4](#0-3) , and `finalizeDefaultRecovery` computes `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` with that inflated basis [5](#0-4) .

Concretely: if the CDO collected only part of the instant queue (`collectInstantWithdrawFunds` reduces `pendingInstantWithdraws` but not `instantWithdrawClaimsByEpoch` [6](#0-5) ), a user whose receipt was funded can fully claim, yet their basis remains in `instantWithdrawClaimsByEpoch`. When the borrower later defaults in that same epoch and `finalizeDefaultRecovery` runs, `totalBasis` includes value that has already been paid out. Additionally, when that same user later calls `claimWithdrawRequest`/`claimInstantWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest` reads the stale `instantWithdrawsRequestsByEpoch[_user][defaultEpoch] != 0` and executes `instantWithdrawsRequests[_user] -= claimBasis` on a zeroed balance, reverting on underflow and permanently bricking that user's claim path [7](#0-6) .

### Impact Explanation
Two effects, both with direct fund impact:

1. **Recovery dilution / permanently locked reserve.** `defaultRecoveryPrice` is computed against a denominator that includes already-paid receipts, so every legitimate defaulted claimant (normal pending receipts and unfunded instant receipts) recovers less than entitled. The corresponding slice of `defaultRecoveryReserve` can never be fully claimed — it stays stranded in the strategy as unclaimable dust, i.e. permanent freezing of unclaimed yield/recovery proportional to the stale basis (`staleBasis / totalBasis` of the reserve).
2. **Permanent claim freeze for the already-claimed user.** Any subsequent claim by that user hits the stale `instantWithdrawsRequestsByEpoch` entry and underflow-reverts in `_claimDefaultedInstantWithdrawRequest`, permanently blocking their other funded or post-default claims routed through the same function.

Quantified: with a $1M epoch instant basis where $600k was claimed after partial funding and $400k left pending, default recovery divides the reserve over the full $1M instead of $400k of live instant basis — recovery price is understated by the stale $600k share and ~`stale * recoveryPrice` of reserve is stranded.

### Likelihood Explanation
Requires a borrower default in the same epoch in which instant withdrawals were only partially funded and at least one funded instant receipt was already claimed before `finalizeDefaultRecovery`. Partial instant funding is an explicitly supported mode (`pendingInstantWithdraws` remainder and `_defaultPrefundedInstantReserve`), and claim-before-default is the normal user flow. All attacker/victim roles are unprivileged tranche holders; only honest manager/owner calls (stopEpoch, finalizeDefaultRecovery) are sequenced around them. No existing guard catches this: the skim/reserve guard in `_transferFundedClaim` only protects the reserve from funded claims, not the reverse.

### Recommendation
In `claimInstantWithdrawRequest` (or in a dedicated clear step it calls), decrement the per-epoch ledgers symmetrically to `requestInstantWithdraw`:

```solidity
instantWithdrawsRequestsByEpoch[_user][epochNumber] -= amount; // or clear all non-zero entries
instantWithdrawClaimsByEpoch[epochNumber] -= amount;
```

Because a user may hold receipts across multiple epochs, the clean fix is to iterate/track the user's open request epochs (or store the claimable epoch set) so that claims reduce `instantWithdrawClaimsByEpoch` exactly by the amount burned. If clearing must remain lazy, `defaultPendingClaimBasis` should use the still-unclaimed basis (`instantWithdrawClaimsByEpoch[epoch]` net of claimed receipts) rather than the raw aggregate.

### Proof of Concept
Foundry fork sketch (modeled on `test/foundry/IdleCreditVault.t.sol` and `test/foundry/IdleCDOEpochQueue.t.sol` patterns):

```solidity
function testStaleInstantBasisDilutesRecovery() external {
    _useStandardEpochVariant();
    _stopCurrentEpochWithApr(10e18);            // epoch 1 buffer
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(100, 1e18, false);

    address user1 = makeAddr('user1');          // will claim before default
    address user2 = makeAddr('user2');          // stays pending
    uint256 t1 = _depositWithUser(user1, 600e6);
    uint256 t2 = _depositWithUser(user2, 400e6);

    vm.prank(manager); cdoEpoch.startEpoch();
    _requestInstantWithdraw(user1, t1);
    _requestInstantWithdraw(user2, t2);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, interest);            // triggers instant bucket

    uint256 epoch = strategy.epochNumber();
    // CDO collects only part of the instant funds (partial funding of the epoch basis)
    vm.prank(manager); // or via CDO internal path: collectInstantWithdrawFunds(t1)
    // ... fund only user1's share so pendingInstantWithdraws == t2 ...

    vm.prank(user1);
    cdoEpoch.claimInstantWithdrawRequest();     // user1 fully paid
    // BUG: instantWithdrawsRequests[user1]==0 but
    // instantWithdrawsRequestsByEpoch[user1][epoch]==t1 and
    // instantWithdrawClaimsByEpoch[epoch] still == t1+t2
    assertEq(strategy.instantWithdrawsRequestsByEpoch(user1, epoch), t1);

    // borrower defaults; manager finalizes recovery
    _handleBorrowerDefault();
    uint256 basis = strategy.defaultPendingClaimBasis(); // includes stale t1
    // finalizeDefaultRecovery with recovered = R
    // recoveryPrice == R * 1e18 / (activeBasis + pendingWithdraws + t1 + t2)
    // while the live instant basis is only t2 -> price understated
    // user2 claims: receives t2 * price < entitled share; difference stranded
    // user1 reverts on any later claim touching _claimDefaultedInstantWithdrawRequest
}
```

The assertions to prove the invariant break: `strategy.instantWithdrawClaimsByEpoch(epoch)` remains `t1 + t2` after user1's full claim, `defaultPendingClaimBasis()` overstates the instant basis by `t1`, and the terminal `defaultRecoveryReserve` leftover equals approximately `t1 * defaultRecoveryPrice / 1e18` locked forever.
