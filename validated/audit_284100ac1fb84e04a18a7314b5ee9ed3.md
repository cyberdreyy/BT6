## Title
A single account with data too large for base58/binary encoding causes `getProgramAccounts`/`getMultipleAccounts`/`getTokenAccountsByOwner` to fail entirely for every other account in the request - (File: rpc/src/rpc.rs)

## Summary
The MultiRewards.sol bug is a class of "one bad item forces failure of an entire batch operation, denying results to all requesters relying on that item." The same pattern exists in several Agave JSON-RPC handlers: `get_program_accounts`, `get_multiple_accounts`, `get_token_accounts_by_owner`, and `get_token_accounts_by_delegate` all iterate over a batch of accounts and propagate the first per-account encoding error with `?`, aborting the whole response instead of skipping/nulling the offending account.

## Finding Description
`encode_account()` returns an `Err` whenever binary/base58 encoding is requested and the (possibly data-sliced) account data exceeds `MAX_BASE58_BYTES` (128 bytes): [1](#0-0) 

In `get_program_accounts`, when the encoding isn't `jsonParsed`-for-token-programs, every matched account is encoded via `encode_account(...)?` inside a `.collect::<Result<Vec<_>>>()?`: [2](#0-1) 

Because any unprivileged user can create an account owned by an arbitrary program with data up to `MAX_PERMITTED_DATA_LENGTH`, a single account under a program with data > 128 bytes causes `encode_account` to `Err`, which propagates through the `collect` and aborts the *entire* `getProgramAccounts` response — even though every other account under that program would have encoded successfully. The same `.collect::<Result<Vec<_>>>()?` pattern (fail-the-whole-batch-on-one-bad-item) recurs in:
- `get_multiple_accounts`, where each pubkey's `get_encoded_account` result is pushed with `?`: [3](#0-2) 
- `get_token_accounts_by_owner`: [4](#0-3) 
- `get_token_accounts_by_delegate`: [5](#0-4) 

In each case, the caller-supplied list mixes multiple independent accounts/pubkeys (analogous to the vault's `rewardTokens` list), and one "poisoned" entry (oversized data, attacker-controlled by simply funding/creating such an account) denies the entire response for all the other entries, for every future caller of that RPC method with default/base58 encoding against that program or pubkey set.

## Impact Explanation
Medium: any caller who queries `getProgramAccounts` (base58/binary encoding, the default is Base64 for `getMultipleAccounts`/`getTokenAccountsByOwner` but `Binary` is default for `get_program_accounts`) for a program that contains one attacker-planted, oversized account will receive an RPC error instead of the account list, for every subsequent call, until the client changes encoding to base64/base64zstd/jsonParsed. This denies legitimate data retrieval for all other accounts of that program to all RPC users hitting that node, mirroring the "DoS for all users in a vault" pattern, though the workaround (switch encoding) is straightforward for a single RPC call and per-request rather than a permanent on-chain state DoS.

## Likelihood Explanation
Low-Medium: requires a caller to actually use base58/binary encoding (not the safer default in most methods) against a program whose account set includes attacker-controlled, oversized accounts. Any unprivileged actor can create such an account for essentially any program that allows account creation with attacker-controlled data length, e.g. any program processing user-supplied PDAs/accounts.

## Recommendation
In `get_program_accounts`, `get_multiple_accounts`, `get_token_accounts_by_owner`, and `get_token_accounts_by_delegate`, avoid using `?`/`collect::<Result<Vec<_>>>()` to abort the whole batch on a single account's encoding error. Instead, encode each account independently and either substitute the pre-existing "error: data too large for bs58 encoding" placeholder value (as `encode_bs58` already does) or return the affected account as `null`/omit it while still returning the rest of the batch, consistent with how `encode_ui_account` already degrades gracefully for `JsonParsed` failures.

## Proof of Concept
1. Deploy/own a program `P` (or use any existing program permitting user-controlled account creation).
2. Have any account owned by `P` write more than 128 bytes of data (`MAX_BASE58_BYTES`).
3. Call `getProgramAccounts` for `P` with default encoding (`Binary`) or explicit `"encoding":"base58"`.
4. Observe the RPC returns an `InvalidRequest` error for the whole call (from `encode_account`'s "Encoded binary (base58) data should be less than 128 bytes..." error) instead of the list of accounts, hiding all other legitimate accounts owned by `P`. Repeat with `getMultipleAccounts`/`getTokenAccountsByOwner` including the oversized pubkey in the batch to observe the same all-or-nothing failure.

```rust
fn encode_account<T: ReadableAccount>(
    account: &T,
    pubkey: &Pubkey,
    encoding: UiAccountEncoding,
    data_slice: Option<UiDataSliceConfig>,
) -> Result<UiAccount> {
    if (encoding == UiAccountEncoding::Binary || encoding == UiAccountEncoding::Base58)
        && data_slice
            .map(|s| min(s.length, account.data().len().saturating_sub(s.offset)))
            .unwrap_or(account.data().len())
            > MAX_BASE58_BYTES
    {
        let message = format!(
            "Encoded binary (base 58) data should be less than {MAX_BASE58_BYTES} bytes, please \
             use Base64 encoding."
        );
        Err(error::Error {
            code: error::ErrorCode::InvalidRequest,
            message,
            data: None,
        })
    } else {
        Ok(encode_ui_account(
            pubkey, account, encoding, None, data_slice,
        ))
    }
}
```
