### Title
Owner-controlled lockup account address can be squatted with attacker-chosen `lockup_timestamp`/`lockup_duration`, permanently bypassing the lockup schedule a legitimate funder intends - ([File: lockup-factory/src/lib.rs])

### Summary
`LockupFactory::create` derives the deployed lockup contract's account ID deterministically from only `owner_account_id` (`sha256(owner_account_id)[:20].factory`), and does not restrict who may call `create` or what `lockup_timestamp`/`lockup_duration` they may pass. Any unprivileged account can pre-emptively call `create` for a target `owner_account_id` (e.g. `"victim.near"`) with `lockup_timestamp=Some(0)`, permanently occupying that deterministic address with a lockup that is already unlocked at genesis, before the legitimate funder ever deploys the intended multi-year schedule.

### Finding Description
The broken binding: `get_locked_amount()` on the lockup contract deployed at `sha256(owner_account_id)[:20].factory` should equal the schedule (`lockup_duration`/`lockup_timestamp`) that the rightful funder of `owner_account_id`'s lockup authorized.

Path: `LockupFactory::create` computes [1](#0-0) 
with no check tying `predecessor_account_id` to `owner_account_id`, and no restriction on the `lockup_timestamp`/`lockup_duration` values supplied: [2](#0-1) 

The `Promise` chain then creates the account, deploys the lockup binary, transfers the attacher's own deposit, and calls `new`: [3](#0-2) 

Inside the lockup contract's `new()`, `lockup_amount` is fixed to whatever balance is on the account at that moment (i.e., only the attacker's own attached deposit) and `lockup_timestamp` is stored verbatim with no plausibility check against `env::block_timestamp()`: [4](#0-3) 

`get_locked_amount()` computes the effective unlock time as `max(transfers_timestamp + lockup_duration, lockup_timestamp)`; if the attacker sets `lockup_timestamp=0` (and a similarly small/zero `lockup_duration`), this max is already `<= block_timestamp` at genesis, so the funds are immediately unlocked/liquid: [5](#0-4) 

Since NEAR account creation is first-come-first-served and the address is a pure function of `owner_account_id`, once the attacker's `create()` call succeeds, the legitimate funder's later `create()` call to the same `owner_account_id` will fail at the `create_account()` action (account already exists), which triggers the refund path in `on_lockup_create` via `is_promise_success()`: [6](#0-5) 
The legitimate funder gets their deposit refunded, but the deterministic address is now permanently occupied by the attacker's contract with `lockup_timestamp=0`, since the account already exists and can't be redeployed. None of `assert_self`, `is_promise_success`, `is_valid_account_id`, etc. address this because they only guard callback authenticity and syntactic account-name validity, not who is entitled to choose the schedule for a given `owner_account_id`.

### Impact Explanation
This matches the Critical category "a lockup deployed with parameters its rightful creator never chose" and "locked or unvested tokens released early." Any tokens later sent to that squatted address (whether via an attempted legitimate `create()` refunded call, or a direct transfer to the now-known deterministic address) are governed by the attacker's `lockup_timestamp=0`/minimal `lockup_duration`, not the multi-year schedule the real grantor intended, so the owner (`victim.near`) can withdraw immediately instead of after the intended vesting/lockup period. This is repeatable for any `owner_account_id` the attacker chooses to squat ahead of time, and costs only `MIN_ATTACHED_BALANCE` (3.5 NEAR) per squatted account.

### Likelihood Explanation
Feasibility is high: the attacker needs no privileges, only knowledge of the target `owner_account_id` (a public, predictable string, e.g. an employee's or grantee's known account name) and `MIN_ATTACHED_BALANCE`. Front-running is straightforward because the target address is fully deterministic and publicly computable before the legitimate transaction is even broadcast/finalized.

### Recommendation
Restrict `LockupFactory::create` so that only the `owner_account_id` itself (or the foundation/whitelisted funder) can set custom `lockup_timestamp`/`lockup_duration`/vesting parameters, or incorporate an additional entropy/salt (e.g., funder account, nonce) into the derived lockup account ID so it can't be pre-computed and squatted purely from `owner_account_id`. At minimum, validate that `lockup_timestamp` (if provided) is not already in the past relative to `env::block_timestamp()` at `new()` time.

### Proof of Concept
```rust
// lockup/src/lib.rs unit test area
#[test]
fn test_squatted_lockup_timestamp_zero_unlocks_immediately() {
    let mut context = VMContextBuilder::new()
        .current_account_id(lockup_account())
        .predecessor_account_id(factory_account())
        .block_timestamp(to_ts(GENESIS_TIME_IN_DAYS)) // "far past 0"
        .account_balance(ntoy(4)) // attacker's minimal MIN_ATTACHED_BALANCE deposit
        .finish();
    testing_env!(context.clone());

    // Attacker calls new() with squatted owner_account_id and lockup_timestamp = 0
    let contract = LockupContract::new(
        "victim.near".to_string(),
        WrappedDuration::from(0u64),          // attacker-chosen small/zero duration
        Some(WrappedTimestamp::from(0u64)),   // attacker-chosen lockup_timestamp = 0
        TransfersInformation::TransfersEnabled { transfers_timestamp: to_ts(GENESIS_TIME_IN_DAYS - 1).into() },
        None,
        None,
        whitelist_account_id(),
        None,
    );

    // Binding under test: get_locked_amount() should equal the multi-year schedule
    // a real grantor would have authorized (non-zero, since block_timestamp is far past genesis
    // but well before any legitimately intended unlock date).
    // Instead:
    assert_eq!(contract.get_locked_amount().0, 0); // fully unlocked at genesis, contradicting any real lockup schedule
}
```
This demonstrates that once squatted with `lockup_timestamp=Some(0)`, `get_locked_amount()` returns `0` immediately at genesis regardless of any lockup duration a legitimate funder intended, and because the account already exists at the deterministic address, no legitimate `create()` call for `"victim.near"` can ever redeploy the correct schedule there (it would fail and only be refunded via `on_lockup_create`'s `is_promise_success()` branch).

        }
    }

    pub fn get_locked_amount(&self) -> WrappedBalance {
        let lockup_amount = self.lockup_information.lockup_amount;
        if let TransfersInformation::TransfersEnabled {
            transfers_timestamp,
        } = &self.lockup_information.transfers_information
        {
            let lockup_timestamp = std::cmp::max(
                transfers_timestamp
                    .0
                    .saturating_add(self.lockup_information.lockup_duration),
                self.lockup_information.lockup_timestamp.unwrap_or(0),
            );
            let block_timestamp = env::block_timestamp();
            if lockup_timestamp <= block_timestamp {
                let unreleased_amount =
                    if let &Some(release_duration) = &self.lockup_information.release_duration {
                        let end_timestamp = lockup_timestamp.saturating_add(release_duration);
                        if block_timestamp >= end_timestamp {
                            // Everything is released
                            0
                        } else {
                            let time_left = U256::from(end_timestamp - block_timestamp);
                            let unreleased_amount = U256::from(lockup_amount) * time_left
                                / U256::from(release_duration);
                            // The unreleased amount can't be larger than lockup_amount because the
                            // time_left is smaller than total_time.
                            unreleased_amount.as_u128()
                        }
                    } else {
                        0
                    };

                let unvested_amount = match &self.vesting_information {
                    VestingInformation::VestingSchedule(vs) => self.get_unvested_amount(vs.clone()),
                    VestingInformation::Terminating(terminating) => terminating.unvested_amount,
                    // Vesting is private, so we can assume the vesting started before lockup date.
                    _ => U128(0),
                };
                return std::cmp::max(
                    unreleased_amount
                        .saturating_sub(self.lockup_information.termination_withdrawn_tokens),
                    unvested_amount.0,
                )
                .into();
            }
        }
        // The entire balance is still locked before the lockup timestamp.
        (lockup_amount - self.lockup_information.termination_withdrawn_tokens).into()
    }
