### Title
Builder sweep withdrawals double-count balance already claimed by pending builder withdrawals, causing Gwei to be created and paid to non-owners - ([File: specs/gloas/beacon-chain.md])

### Summary
`get_builders_sweep_withdrawals` computes a full-balance withdrawal for an exiting builder using the raw, unadjusted `state.builders[builder_index].balance`, without netting out any withdrawal for that same builder already placed earlier in the same payload by `get_builder_withdrawals` (pending payments/bid settlements). This is the direct spec-level analog of the yAxis "insufficient liquidity not checked" bug: a committed payout amount is computed without validating it against what is actually still backed by the underlying balance, so the total amount committed to `payload_expected_withdrawals` (which the execution layer must mint/credit) can exceed the Gwei actually debited from the builder in `apply_withdrawals`.

### Finding Description
In `get_expected_withdrawals`, builder pending withdrawals are collected first, then builder sweep withdrawals, both operating on the *same* `state` snapshot before any mutation: [1](#0-0) 

`get_builder_withdrawals` blindly emits a `Withdrawal` for the *requested* amount taken from `state.builder_pending_withdrawals`, with no balance check at all: [2](#0-1) 

`get_builders_sweep_withdrawals` then independently computes a *second*, full-balance withdrawal for the same builder using the raw `builder.balance` field, ignoring `prior_withdrawals` entirely (the parameter is only used for the length/limit check, never to net out amounts already committed to the same builder index in this payload): [3](#0-2) 

Compare this with the validator equivalent, `get_validators_sweep_withdrawals`, which explicitly nets out `all_withdrawals = list(prior_withdrawals) + withdrawals` via `get_balance_after_withdrawals` before computing the sweep amount — the exact safeguard that is missing for builders: [4](#0-3) 

Finally, `apply_withdrawals` deducts sequentially, using the *live* (already-decremented) balance for each subsequent withdrawal, so the CL-side deduction is correctly capped to what remains: [5](#0-4) 

But the amounts recorded in `payload_expected_withdrawals` (what the execution layer is contractually bound to pay, per the note that "any execution payload that has the corresponding block as parent beacon block is required to honor these withdrawals in the execution layer") are **not** capped — they retain the original, uncapped, pre-computed amounts: [6](#0-5) 

Concrete scenario: builder `B` has balance `N`. A previously accepted bid settles into `state.builder_pending_withdrawals` for amount `X <= N` (fee recipient `F1`, the address named in the bid). In the same slot, `B.withdrawable_epoch <= epoch` (e.g. `B` also submitted a builder-exit request earlier and the delay has elapsed). `get_expected_withdrawals` then produces:
- Withdrawal 1: `address=F1, amount=X` (from `get_builder_withdrawals`)
- Withdrawal 2: `address=B.execution_address, amount=N` (from `get_builders_sweep_withdrawals`, using the still-unmodified `balance=N`)

Total committed: `X + N`, even though `B` only ever had `N` Gwei. `apply_withdrawals` will debit `min(X, N)=X` then `min(N, N-X)=N-X`, for a correctly capped total CL-side debit of `N` — but the execution layer is required to pay `X + N`, i.e. `X` Gwei more than existed, to two different addresses (`F1` and `B.execution_address`), neither of which is backed by a corresponding balance reduction.

### Impact Explanation
This breaks the core equality that a beacon-chain withdrawal payload must never commit to paying more Gwei than the state actually removes from the paying party. It results in `X` Gwei being minted on the execution layer and credited to `F1` and/or `B.execution_address` with no corresponding debit in the consensus-layer state — a direct Gwei-creation event paid to addresses that do not "own" that value. Per the stated impact rubric this is Critical: "Gwei created, destroyed or paid to a non-owner" / "a payload executed or paid that the block did not commit to" (here inverted: the block *does* commit to more than it should, via `payload_expected_withdrawals`, which every honest node and the execution client must accept as valid).

### Likelihood Explanation
No coalition, malicious peer, or client bug is required. The trigger only needs a single builder's own unprivileged, spec-legal actions: (1) get a bid accepted and let its payment queue into `builder_pending_withdrawals` (this settlement can be delayed multiple epochs, as shown by the "missed epochs" test path), and (2) separately trigger its own exit (`process_builder_exit_request` → `initiate_builder_exit`) so that `withdrawable_epoch <= epoch` lands in the same slot the pending withdrawal is processed. Because `MIN_BUILDER_WITHDRAWABILITY_DELAY` and pending-payment settlement delays are both epoch-scale, timing the exit epoch to coincide with the pending-withdrawal processing slot is entirely within a single builder's control.

### Recommendation
`get_builders_sweep_withdrawals` (and any other builder-balance-consuming withdrawal source) must compute the sweep amount net of any withdrawals already accumulated for the same builder index earlier in the same call, mirroring `get_balance_after_withdrawals`'s pattern used for validators, e.g.:
```python
already_committed = sum(w.amount for w in prior_withdrawals if w.validator_index == convert_builder_index_to_validator_index(builder_index))
available = builder.balance - already_committed if builder.balance > already_committed else Gwei(0)
if builder.withdrawable_epoch <= epoch and available > 0:
    withdrawals.append(Withdrawal(..., amount=available))
```
Additionally, `get_builder_withdrawals` should cap `amount=min(withdrawal.amount, builder.balance)` at read time (matching what `apply_withdrawals` will actually deduct) rather than always emitting the raw requested amount, so `payload_expected_withdrawals` is always fully backed by the CL balance being debited.

### Proof of Concept
1. Builder `B` (index `i`) has `balance = N` Gwei.
2. A bid from `B` for value `X <= N` is accepted (`process_execution_payload_bid`), queuing a `BuilderPendingPayment`; it later settles into `state.builder_pending_withdrawals` with `fee_recipient=F1, amount=X, builder_index=i` (via `settle_builder_payment` / `process_builder_pending_payments`), per [7](#0-6) .
3. `B` submits a builder-exit request in an earlier block so that, by the current slot, `state.builders[i].withdrawable_epoch <= get_current_epoch(state)`.
4. At the slot where the pending withdrawal from step 2 is due for processing, call `get_expected_withdrawals(state)`:
   - `get_builder_withdrawals` returns `[Withdrawal(address=F1, amount=X, validator_index=convert_builder_index_to_validator_index(i))]`.
   - `get_builders_sweep_withdrawals` independently reads `state.builders[i].balance == N` (unchanged, since this is a pure read prior to `apply_withdrawals`) and returns `[Withdrawal(address=B.execution_address, amount=N, validator_index=convert_builder_index_to_validator_index(i))]`.
5. `payload_expected_withdrawals` (and thus `ExecutionPayload.withdrawals`, which the execution layer must honor) now sums to `X + N` for builder `i`, while `apply_withdrawals` only debits a total of `N` from `state.builders[i].balance`. `X` Gwei has been created and paid to `F1`/`B.execution_address` with no backing debit — reproducible directly against `specs/gloas/beacon-chain.md`'s `get_expected_withdrawals`/`get_builders_sweep_withdrawals`/`apply_withdrawals` functions cited above.

##### New `get_builder_withdrawals`

```python
def get_builder_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    for withdrawal in state.builder_pending_withdrawals:
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder_index = withdrawal.builder_index
        withdrawals.append(
            Withdrawal(
                index=withdrawal_index,
                validator_index=convert_builder_index_to_validator_index(builder_index),
                address=withdrawal.fee_recipient,
                amount=withdrawal.amount,
            )
        )
        withdrawal_index += 1
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count

##### New `get_builders_sweep_withdrawals`

```python
def get_builders_sweep_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    epoch = get_current_epoch(state)
    builders_limit = min(len(state.builders), MAX_BUILDERS_PER_WITHDRAWALS_SWEEP)
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    builder_index = state.next_withdrawal_builder_index
    for _ in range(builders_limit):
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder = state.builders[builder_index]
        if builder.withdrawable_epoch <= epoch and builder.balance > 0:
            withdrawals.append(
                Withdrawal(
                    index=withdrawal_index,
                    validator_index=convert_builder_index_to_validator_index(builder_index),
                    address=builder.execution_address,
                    amount=builder.balance,
                )
            )
            withdrawal_index += 1

        builder_index = (builder_index + 1) % len(state.builders)
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count

##### Modified `process_withdrawals`

*Note*: This is modified to only take the `state` as parameter. Withdrawals are
deterministic given the beacon state, any execution payload that has the
corresponding block as parent beacon block is required to honor these
withdrawals in the execution layer. `process_withdrawals` must be called after
`process_parent_execution_payload` (which updates `state.latest_block_hash`) and
before `process_execution_payload_bid` as the latter function affects validator
balances.

*Note*: Unlike deposits (which are applied at the child's slot via
`apply_parent_execution_payload`), withdrawal balance deductions are applied
immediately via `apply_withdrawals`. Deferring the deduction to the child's slot
would break the total supply invariant: state transitions between the commitment
slot and the deduction slot (e.g., `process_pending_consolidations` at an epoch
boundary) can reduce a validator's balance below the committed withdrawal
amount, causing `decrease_balance` to saturate at zero. Since the execution
layer mints the full committed amount regardless, any CL-side saturation creates
a net supply inflation. As a consequence, `state.balances` reflects the
withdrawal deduction before the corresponding execution payload is confirmed,
creating a transient asymmetry with the EL state at `state.latest_block_hash`.
Off-chain consumers that require CL/EL balance consistency can reconstruct
pre-deduction balances by adding back `state.payload_expected_withdrawals`.

```python
def get_validators_sweep_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    epoch = get_current_epoch(state)
    validators_limit = min(len(state.validators), MAX_VALIDATORS_PER_WITHDRAWALS_SWEEP)
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD
    # There must be at least one space reserved for validator sweep withdrawals
    assert len(prior_withdrawals) < withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    validator_index = state.next_withdrawal_validator_index
    for _ in range(validators_limit):
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        validator = state.validators[validator_index]
        balance = get_balance_after_withdrawals(state, validator_index, all_withdrawals)
        if is_fully_withdrawable_validator(validator, balance, epoch):
            withdrawals.append(
                Withdrawal(
                    index=withdrawal_index,
                    validator_index=validator_index,
                    address=ExecutionAddress(validator.withdrawal_credentials[12:]),
                    amount=balance,
                )
            )
            withdrawal_index += 1
        elif is_partially_withdrawable_validator(validator, balance):
            withdrawals.append(
                Withdrawal(
                    index=withdrawal_index,
                    validator_index=validator_index,
                    address=ExecutionAddress(validator.withdrawal_credentials[12:]),
                    amount=balance - MAX_EFFECTIVE_BALANCE,
                )
            )
            withdrawal_index += 1

        validator_index = (validator_index + 1) % len(state.validators)
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count
