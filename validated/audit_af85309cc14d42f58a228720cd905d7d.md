### Title
Unscoped `POST /v2/execute_capability` allows any run-role user to directly invoke arbitrary registered capabilities, including write-capable ones - ([File: core/web/capability_controller.go])

### Summary
`CapabilityController.ExecuteCapability` looks up any capability by name from the global `CapabilitiesRegistry` and executes it with a fully attacker-supplied `CapabilityRequest` payload, with no check binding the caller to a specific job, owner, or capability. The route is gated only by `RequiresRunRole`, meaning any authenticated run-role user can execute any capability registered in the node, including ones capable of performing on-chain writes.

### Finding Description
`ExecuteCapability` (`core/web/capability_controller.go:26-68`) reads `capabilityName` and a raw `capabilityRequest` byte payload from the request body, fetches the corresponding executable directly from `cc.App.GetCapabilitiesRegistry()` via `capabilityRegistry.GetExecutable(...)`, unmarshals the attacker-supplied bytes into a `pb.CapabilityRequest`, and calls `capability.Execute(ctx, capabilityRequest)` — returning the raw response to the caller. [1](#0-0) 

There is no code anywhere in this handler that verifies:
- that the requesting user is the owner of the job the capability is bound to,
- that the capability being invoked is scoped/allow-listed for that user or job,
- or that the `CapabilityRequest` payload's target/config matches any pre-approved job spec.

The route is protected by `auth.RequiresRunRole`, which only checks that the authenticated user's role is not `UserRoleView` — it grants access to `UserRoleRun`, `UserRoleEdit`, and `UserRoleAdmin` alike, with no notion of capability or job ownership. [2](#0-1) 

Since capability execution is otherwise driven by job specs/workflows (which encode which capability a given job is authorized to call, with what config), this HTTP endpoint bypasses that binding entirely: any run-role-authenticated caller can name and execute any capability present in the registry (e.g., a write/target capability that performs an on-chain transaction) with request parameters entirely of their choosing.

### Impact Explanation
This maps to "unauthorized job run / fund movement" — a low-privilege, run-role-only credential holder can directly trigger a write-capable capability (e.g., an on-chain write/target capability) without going through the normal job-authorization path that ties a capability invocation to a specific job/owner/config. This could result in unauthorized on-chain transactions or state changes being triggered by a caller who should only be permitted to trigger runs of jobs they already have access to, not arbitrary capabilities with arbitrary parameters.

### Likelihood Explanation
The only precondition beyond a valid run-role session is that the binary was built with `build.IsDev()` returning true, and that a write-capable capability is registered in the node's `CapabilitiesRegistry`. Dev/CI/test builds commonly satisfy the `IsDev()` condition. Given a valid run-role credential (the lowest non-view privilege), the exploit is a single unauthenticated-payload POST request and is fully repeatable — no timing race, no additional bypass needed beyond meeting the existing role check.

### Recommendation
- Bind capability execution requests to the specific job/workflow that a run-role user is authorized to trigger runs for, rather than allowing arbitrary `capabilityName` + raw `capabilityRequest` execution.
- Add an authorization check verifying the requesting user (or the job identified in the request) owns/is entitled to invoke the named capability, and reject execution of capabilities not associated with a job the caller can run.
- Consider restricting this endpoint to `RequiresAdminRole` or removing/hardening it outside of dev/test tooling, and add explicit allow-listing of which capabilities can be invoked via this generic HTTP path.

### Proof of Concept
Go handler-level integration test plan:
1. Build a test `gin.Engine` with `build.IsDev()` forced true and route registration mirroring `core/web/router.go`'s wiring of `POST /v2/execute_capability` to `auth.RequiresRunRole(cc.ExecuteCapability)`.
2. Register a mock `chainlink.Application.GetCapabilitiesRegistry()` returning a fake write-capable `CapabilityExecutable` (e.g., simulate an on-chain write target) that records whatever `CapabilityRequest` it receives.
3. Simulate an authenticated session/token with `clsessions.UserRoleRun` (lowest non-view role) via `c.Set(auth.SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})`.
4. POST to `/v2/execute_capability` with a `CapabilityRequestOuter{CapabilityName: "<write-capable-capability>", CapabilityRequest: <attacker-crafted pb.CapabilityRequest bytes>}`.
5. Assert: HTTP 200 response is returned, the mock capability's `Execute` was invoked with the attacker-supplied request (proving no job/owner scoping occurred), and that no additional authorization check beyond `RequiresRunRole` gated the call — i.e., the same request from a `UserRoleView` user is rejected with 401 but a `UserRoleRun` user (with no job ownership relationship to the capability) succeeds.

```go
func (cc *CapabilityController) ExecuteCapability(c *gin.Context) {
	body := c.Request.Body
	if body == nil {
		jsonAPIError(c, http.StatusBadRequest, errors.New("missing request body"))
		return
	}

	capabilityRegistry := cc.App.GetCapabilitiesRegistry()
	if capabilityRegistry == nil {
		jsonAPIError(c, http.StatusInternalServerError, errors.New("capability registry not initialized"))
		return
	}
	var capabilityRequestOuter CapabilityRequestOuter
	if err := c.BindJSON(&capabilityRequestOuter); err != nil {
		jsonAPIError(c, http.StatusBadRequest, err)
		return
	}

	capability, err := capabilityRegistry.GetExecutable(c.Request.Context(), capabilityRequestOuter.CapabilityName)
	if err != nil {
		jsonAPIError(c, http.StatusNotFound, err)
		return
	}

	capabilityRequest, err := pb.UnmarshalCapabilityRequest(capabilityRequestOuter.CapabilityRequest)
	if err != nil {
		jsonAPIError(c, http.StatusBadRequest, err)
		return
	}

	resp, err := capability.Execute(c.Request.Context(), capabilityRequest)
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	responseBytes, err := pb.MarshalCapabilityResponse(resp)
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	c.JSON(http.StatusOK, gin.H{"capabilityResponse": responseBytes})
```

```go
// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
```
