### Title
Unvalidated ERC4626 share price in `ProgrammableBorrower._depositToVault`/`_currentVaultAssets` allows share-price inflation to steal pool principal - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
`ProgrammableBorrower` prices its vault sleeve exclusively through the external ERC4626 vault's `convertToAssets` and accepts whatever share amount `vault.deposit` returns, with no minimum-share check, no price bound, and no sanity validation — the direct analog of `DelayedOrder.executeOrder` trusting unvalidated external price data. A user of the configured ERC4626 vault (or any direct token sender to it) can inflate the vault's price-per-share before `onStartEpoch` deposits the pool's idle capital, causing the pool to receive near-zero shares for its full deposit. The pool's principal is then captured inside the vault and is redeemable by the attacker, while epoch accounting records the difference as a vault loss.

### Finding Description
When `IdleCDOEpochVariant` starts an epoch it calls `ProgrammableBorrower.onStartEpoch`, which deposits the contract's entire idle underlying balance into the vault via `_depositToVault`. That helper calls `vault.deposit(_assetAmount, address(this))` and accepts the returned `shares` without any lower bound:

```solidity
// contracts/strategies/idle/ProgrammableBorrower.sol:378-385
uint256 shares = vault.deposit(_assetAmount, address(this));
```

All pool-facing valuation then flows through `_currentVaultAssets`, which trusts `vault.convertToAssets(shares)` unconditionally (line 546-549). `_vaultNetInterest` compares this live, manipulable valuation against the asset-denominated baselines `epochStartVaultAssets + epochDepositedToVault` (line 337-347), and `totalInterestDueNow` is the single value `IdleCDOEpochVariant` reads to price the epoch.

The deposit-time manipulation is not corrected by the baseline snapshot: `onStartEpoch` records `startAssets` in *asset* terms before depositing (line 214), but `earnedAssets` is measured in *share-converted* terms afterward. If the deposit minted near-zero shares because the price-per-share was inflated, `earnedAssets ≈ 0 < principalAssets` and the delta is registered as a real loss — which it is: the underlying now sits in the vault under attacker-controlled shares.

Attack sequence (running/buffer transition, programmable mode):
1. A fresh or low-supply ERC4626 vault is configured via `initialize`/`setVault` (both only check `asset()` and zero address — no supply/price floor, lines 119, 160-165).
2. Attacker, as an ordinary vault user, deposits a dust amount to mint the first shares, then direct-transfers a large amount of underlying to the vault, inflating `convertToAssets` (classic first-depositor/donation inflation).
3. Honest lender funds land and `startEpoch → onStartEpoch` deposits the pool balance. The pool receives ~0 shares; its underlying is now claimable pro-rata by vault shareholders — predominantly the attacker.
4. Attacker redeems their vault shares, extracting roughly the pool's deposit. At `stopEpoch`, `onStopEpoch` sees `shortfall > _currentVaultAssets()` and returns without withdrawing (line 245); the CDO either books the loss through `_updateAccounting` (BB-first socialization) or falls into the default path.

No existing guard stops this: the `_checkOnlyIdleCDO` hooks don't gate vault share price, `epochDepositedToVault`/`epochStartVaultAssets` baselines measure assets-in rather than shares-out, `onDefault` deliberately avoids `convertToAssets`, and there is no skim or min-shares-out equivalent for the external vault leg.

### Impact Explanation
Direct theft of pool principal. If the pool parks `P` underlying and the attacker inflates price-per-share so the deposit mints shares worth ~0, the attacker redeems ~`P` (minus their seed deposit and pro-rata share of the donation). Lenders/tranche holders absorb the loss through NAV reduction or a forced default — solvency and loss-waterfall invariants are broken. Cost to the attacker is limited to the vault seed deposit; for a vault the pool is about to enter with `P >>` existing supply, the standard inflation-attack bound applies (attacker captures approximately `P - seed`).

### Likelihood Explanation
Requires the configured vault to have low existing share supply relative to the pool deposit (a newly deployed vault, or `setVault` migration to a thin vault) and the attacker to act before the pool's first `onStartEpoch`/`_depositToVault`. Both conditions are realistic operational events, and the attacker needs no privilege — being an ERC4626 vault user or direct token sender suffices. Front-running the epoch-start deposit is a single-block sandwich.

### Recommendation
Bound the accepted exchange rate on every vault interaction rather than trusting the vault's live price:
- In `_depositToVault`, compute expected shares via `vault.previewDeposit(_assetAmount)`/`convertToShares` and require `shares >= minShares` derived from a stored or pool-enforced fair price; alternatively use `vault.mint(expectedShares, ...)` so a bad rate reverts instead of silently accepting few shares.
- Record the share balance (not only asset baselines) in `epochStartVaultAssets` accounting so a deposit that minted too few shares is detectable.
- Gate `setVault`/`initialize` on a minimum vault `totalSupply`/`totalAssets` (or deploy with a seeded dead-share position) to neutralize first-depositor inflation.

```solidity
function _depositToVault(uint256 _assetAmount, uint256 _principalAssets) internal {
    if (_assetAmount == 0) return;
    uint256 minShares = vault.previewDeposit(_assetAmount);
    uint256 shares = vault.deposit(_assetAmount, address(this));
    if (shares < minShares * (1e18 - MAX_DEPOSIT_SLIPPAGE_BPS) / 1e18) revert InvalidAmount();
    ...
}
```

### Proof of Concept
Fork Foundry test (programmable mode, modeled on `test/foundry/ProgrammableBorrowerCreditVault.t.sol`):

```solidity
function testVaultShareInflationStealsPoolDeposit() external {
    // 1. Deploy/use a fresh ERC4626 vault over USDC; configure ProgrammableBorrower with it.
    // 2. Attacker (unprivileged EOA): vault.deposit(1 wei) -> mints 1 share,
    //    then usdc.transfer(address(vault), D) to inflate pricePerShare to ~D.
    uint256 poolDeposit = 10_000 * oneScale;

    deal(USDC, address(this), poolDeposit, true);
    underlying.approve(address(cdoEpoch), type(uint256).max);
    idleCDO.depositAA(poolDeposit);          // lender funds arrive
    cdoEpoch.startEpoch();                   // onStartEpoch -> _depositToVault(all idle)

    // Pool deposited `poolDeposit` but minted ~0 shares at the inflated price.
    assertLt(morphoVault.convertToAssets(morphoVault.balanceOf(address(programmableBorrower))), poolDeposit / 10);

    // 3. Attacker redeems their vault shares: captures ~poolDeposit of pooled USDC.
    // 4. At epoch end, totalInterestDueNow reports a vaultLoss ~ poolDeposit and
    //    onStopEpoch underfunds -> loss socialized to BB/AA or default triggered.
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);
    // assert attacker profit ≈ poolDeposit and lastNAVAA/BB reduced accordingly
}
```
