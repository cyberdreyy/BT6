### Title
`getMultipleAccounts`/`getProgramAccounts` abort entire batch response due to a single oversized account when base58/binary encoding is requested - (File: `rpc/src/rpc.rs`)

### Summary
`JsonRpcRequestProcessor::get_multiple_accounts` and `JsonRpcRequestProcessor::get_program_accounts` both iterate over a list of accounts and encode each one via `encode_account`/`get_encoded_account`, propagating any single encoding error with `?`. Because `encode_account` returns `Err` whenever the requested encoding is `Binary`/`Base58` and an individual account's data (after slicing) exceeds `MAX_BASE58_BYTES` (128 bytes), one oversized account in the batch causes the whole RPC call to fail, discarding results for every other account in the same request — the same "single bad element aborts the whole batch" root cause described in the external report for `SafEth::stake()`.

### Finding Description
`encode_account` explicitly rejects base58/binary-encoded data over 128 bytes: [1](#0-0) 

`get_multiple_accounts` calls `get_encoded_account` (which calls `encode_account`) once per requested pubkey inside a `for` loop, and propagates the `Result` with `?` on every iteration: [2](#0-1) 

`get_program_accounts` does the same thing over the filtered set of program-owned accounts, using `.collect::<Result<Vec<_>>>()?`, which short-circuits on the first `Err`: [3](#0-2) 

An unprivileged JSON-RPC caller fully controls the `encoding` parameter of `RpcAccountInfoConfig` and can request `"encoding": "base58"` (or the legacy `"binary"`) for `getMultipleAccounts`/`getProgramAccounts`. If any single pubkey in the batch (for `getMultipleAccounts`) — or any single account returned by the on-chain filter match (for `getProgramAccounts`) — has account data whose (sliced) length exceeds `MAX_BASE58_BYTES`, `encode_account` returns an `Err`, which aborts the entire request via `?`/`collect::<Result<_>>()?`. All other accounts in the batch, even ones that would have encoded successfully, are discarded and the caller receives an RPC error instead of any data. Existing repo tests already demonstrate that `encode_account` panics/errors when a single account exceeds the limit: `test_encode_account_throws_when_data_too_large_to_base58_encode` (`rpc/src/rpc.rs:5728-5741`), confirming this is real, reachable behavior, not speculative.

### Impact Explanation
This is a query-availability defect reachable by any unprivileged RPC caller with a single request: batching several unrelated account lookups (or a program filter that happens to match one large account) into `getMultipleAccounts`/`getProgramAccounts` with base58 encoding denies the entire response, even for accounts that would have encoded fine. This mirrors the external report's root cause exactly — an iteration over independent items where one item's failure improperly voids the results for all unrelated items — applied here to a JSON-RPC handler over account/blockstore reads rather than to a staking contract. It does not crash or deadlock the validator process and does not corrupt consensus state, so severity is limited to degraded RPC usability/DoS-of-information for the caller's own request (and any other request that happens to reference the same oversized account), which is the closest in-scope analog given the SECURITY.md restriction on RPC DoS.

### Likelihood Explanation
High for any RPC consumer who requests `encoding: base58`/`binary` on `getMultipleAccounts` or `getProgramAccounts` against accounts holding more than 128 bytes of data (a very common size for token, stake, or program-owned accounts). No special privileges, timing, or multiple calls are needed — a single, ordinary read-only RPC call triggers it.

### Recommendation
In `get_multiple_accounts` and `get_program_accounts` (`rpc/src/rpc.rs`), do not let one account's base58 encoding failure abort the whole batch: catch the per-account `Err` from `encode_account`/`get_encoded_account` and substitute a `null`/error-marker entry (consistent with how `encode_bs58` already degrades gracefully to an `"error: data too large for bs58 encoding"` string in other paths, see `account-decoder/src/lib.rs:34-44`), returning partial, best-effort results instead of failing the entire call.

### Proof of Concept
1. Store two accounts on a bank: account A with ≤128 bytes of data, account B with >128 bytes of data.
2. Call `getMultipleAccounts` with `pubkeys = [A, B]` and `config = { encoding: "base58" }`.
3. Observe: `encode_account(B, ...)` returns `Err` (per `rpc/src/rpc.rs:2575-2601`, mirrored by test `test_encode_account_throws_when_data_too_large_to_base58_encode` at `rpc/src/rpc.rs:5728-5741`), and because of the `?` inside the loop at `rpc/src/rpc.rs:579-591`, the entire `getMultipleAccounts` call errors out — account A's valid, correctly-sized data is never returned.
4. The same holds for `getProgramAccounts` via the `.collect::<Result<Vec<_>>>()?` at `rpc/src/rpc.rs:656-666`: if any single account matched by the program filter exceeds 128 bytes, the whole account list is dropped, denying legitimate results for all other matching accounts.

fn encode_account<T: ReadableAccount>(
    account: &T,
    pubkey: &Pubkey,
    encoding: UiAccountEncoding,
    data_slice: Option<UiDataSliceConfig>,
) -> Result<UiAccount> {
    if (encoding == UiAccountEncoding::Binary || encoding == UiAccountEncoding::Base58)
        && data_slice
            .map(|s| min(s.length, account.data().len().saturating_sub(s.offset)))
            .unwrap_or(account.data().len())
            > MAX_BASE58_BYTES
    {
        let message = format!(
            "Encoded binary (base 58) data should be less than {MAX_BASE58_BYTES} bytes, please \
             use Base64 encoding."
        );
        Err(error::Error {
            code: error::ErrorCode::InvalidRequest,
            message,
            data: None,
        })
    } else {
        Ok(encode_ui_account(
            pubkey, account, encoding, None, data_slice,
        ))
    }
}
