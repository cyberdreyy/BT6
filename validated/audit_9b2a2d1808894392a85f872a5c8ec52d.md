## Finding

Confirmed: both `multisig2` and `multisig` (v1) contracts fail to remove a departing member's *confirmations* from other members' pending requests when that member is deleted, only cleaning up requests *originated* by the deleted member. This lets a request execute having reached `num_confirmations` while containing fewer live-member approvals than the threshold requires.

### Title
Stale confirmations from removed multisig members still count toward the confirmation threshold, allowing execution below the live-member quorum - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::confirm` compares the size of the `confirmations: HashSet<String>` for a request against `num_confirmations` to decide whether to execute it. `delete_member` only purges requests that were *created* by the departing member; it never scans other pending requests to strip that member's *confirmation* entries. As a result, a confirmation recorded by a member who is later removed from the multisig remains permanently counted toward the K-of-N threshold for any request it was cast on, even though that member no longer has any authority over the account.

### Finding Description
`confirm` increments/consults confirmations purely by count, without checking whether the confirming accounts/keys stored in the set are still members at execution time: [1](#0-0) 

`delete_member` is the only cleanup path invoked when a member is removed, and it filters pending requests by `r.member == member` — i.e. requests the departing member *added* — not by scanning `self.confirmations` for entries where the departing member appears as a *confirmer* on requests added by someone else: [2](#0-1) 

Concretely, with members `{A, B, C}` and `num_confirmations = 2`:
1. `A` calls `add_request` for a `Transfer` (or `AddKey`/`FunctionCall`, etc.) to a receiver — request is created with `member = A` and empty confirmations.
2. `B` calls `confirm(request_id)`; since `1 < 2`, `B`'s identity string is inserted into `confirmations` for that request and no execution happens.
3. Separately, via a legitimate `DeleteMember { member: B }` request (e.g. B's key is later considered compromised or B leaves), `delete_member` runs. It only removes requests where `r.member == B` (requests B itself created) — the pending Transfer request created by `A`, which contains `B`'s stale confirmation, is left completely untouched.
4. `B` is now removed from `self.members`, so `current_member()` will never again resolve to `B`, and `B`'s access key has been deleted on-chain.
5. `C` (or even `A` again if it were allowed) calls `confirm(request_id)`. The check at `multisig2/src/lib.rs:304` computes `confirmations.len() as u32 + 1 >= self.num_confirmations` → `1 (stale B) + 1 (C) >= 2` → true, and `execute_request` runs the transfer.

The request executes with only one currently-live member (`C`) having actually approved it at execution time, while the contract's own accounting believes 2-of-3 confirmations were obtained. The equality the multisig is supposed to guarantee — `confirmations recorded == confirmations by members that are live at execution` — is broken; a stale confirmation from a revoked member is silently promoted to count as a live approval indefinitely.

The same structural bug exists in the legacy `multisig` contract, where `DeleteKey` only purges requests whose `signer_pk` equals the deleted key (the requester), not other requests that key had merely confirmed: [3](#0-2) [4](#0-3) 

### Impact Explanation
This is a Critical-class authorization boundary break per the multisig custody model: a request that is supposed to require `K` currently-authorized approvals can be executed with fewer than `K` live members having actually approved it, because a revoked member's stale confirmation persists and is counted. This directly maps to "a multisig request executed below threshold" — funds (`Transfer`), key management (`AddKey`), or arbitrary `FunctionCall`s can be pushed through the multisig's execution path with insufficient live authorization, especially dangerous in exactly the scenario multisig removal is meant to protect against: revoking a compromised or departing member's authority. That member's prior "vote" on any outstanding request keeps counting forever even after removal.

### Likelihood Explanation
No privileged role is required beyond being (or having been) a normal multisig member — this is entirely reachable through documented, ordinary usage: `add_request` → partial `confirm` by another member → member removal (a routine multisig operation, e.g. rotating out a member or revoking a suspected-compromised key) → the remaining members' subsequent `confirm` calls unknowingly complete a below-quorum execution. No malicious deployment, foundation privilege, or victim key theft is needed; it only requires normal timing of member turnover relative to an outstanding request, which is realistic in any long-lived multisig with membership churn.

### Recommendation
When removing a member in `delete_member`, iterate over `self.confirmations` for all active requests (not just those the departing member created) and remove that member's entry from every confirmation set. Alternatively, validate at `confirm`-time / execution-time that every account/key present in `confirmations` is still a current member of `self.members`, discarding stale entries before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C]`, `num_confirmations = 2`.
2. As `A`: `add_request({receiver_id: victim, actions: [Transfer{amount}]})` → `request_id`.
3. As `B`: `confirm(request_id)` → confirmations = `{B}`, request not executed (1 < 2).
4. As a member with quorum, execute `DeleteMember { member: B }` (a separate, otherwise legitimate request/confirm flow) → `B` removed from `self.members`; `delete_member` does not touch `confirmations` map for the Transfer request from step 2 (it only filters `r.member == B`, and the Transfer's `member` is `A`).
5. As `C`: `confirm(request_id)` → `confirmations.len() (1, still containing stale "B") + 1 >= 2` is true → `execute_request` runs the `Transfer`, even though only `C` is a currently live confirming member (`B`'s authority was revoked in step 4). [5](#0-4) [2](#0-1)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
