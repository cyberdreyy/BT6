### Title
Signer weight double-counted toward both rejection and approval tallies via Reject-then-Accept resend - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener`'s block-status tallying uses two different, non-overlapping guards to prevent double-counting a signer's weight: the `Accepted` path guards on `gathered_signatures.contains_key(&slot_id)`, while the `Rejected` path guards on `responded_signers.insert(slot_id)`. Because a single signer slot can transition from "already rejected" to "now accepting" without ever having touched `gathered_signatures`, that signer's weight is added to `total_weight_rejected` and, on a later message, also added to `total_weight_approved` for the very same block. This breaks the invariant that the miner's aggregated approve/reject weight reflects distinct signer votes, analogous to the reported non-atomic pool-state update that let a stale/duplicated value be counted twice.

### Finding Description
In `handle_signer_messages` (stackerdb_listener.rs), the `Accepted` branch is: [1](#0-0) 
which only checks `block.gathered_signatures.contains_key(&slot_id)` before adding `signer_entry.weight` to `total_weight_approved`, and only afterward inserts the slot into both `gathered_signatures` and `responded_signers`.

The `Rejected` branch is: [2](#0-1) 
which guards solely with `block.responded_signers.insert(slot_id)` before adding weight to `total_weight_rejected`.

Sequence of events for a single signer slot `S` with weight `w`:
1. `S` sends `BlockResponse::Rejected` for block `B`. `responded_signers` now contains `S`; `total_weight_rejected += w`.
2. `S` (the same signer, e.g. after re-evaluating, or a byzantine/duplicating relay) later sends `BlockResponse::Accepted` for the same block `B`. The `Accepted` branch's guard is `gathered_signatures.contains_key(&S)`, which is still `false` (this signer never sent an `Accepted` message before), so the branch proceeds: `total_weight_approved += w`, and `S` is now also inserted into `gathered_signatures`/`responded_signers`.

Because the two branches key their duplicate-suppression on different data structures (`gathered_signatures` vs `responded_signers`), a signer's weight `w` ends up counted in *both* `total_weight_rejected` and `total_weight_approved` simultaneously for the same block, even though the signer never contributed more than one honest vote. This is a live cross-tally accounting bug reachable by any single signer (or by a malicious/duplicated relay of a single signer's votes) without needing a majority.

This directly corresponds to the report's "rejection recounted as an accept" impact class: the miner-side coordinator (`get_block_status` in `signer_coordinator.rs`) makes accept/reject decisions purely from `block_status.total_weight_approved`/`total_weight_rejected`: [3](#0-2) 
so a spuriously inflated `total_weight_approved` can push a block over the 70% signing threshold, or a spuriously inflated `total_weight_rejected` can push a block over the 30% blocking-minority threshold, using less genuine distinct signer support than required.

### Impact Explanation
This is High/Critical: it allows the miner-side weight aggregation to diverge from the true set of distinct signer votes ("aggregated-weight vs verified-accepts" equality break). A single signer flipping its vote from reject to accept (which the flow explicitly allows — pre-commit/response re-evaluation is a normal part of the protocol) causes its weight to count toward both outcomes, effectively giving it double voting power at the miner's tally. In a close vote near the 70%/30% boundary, this can let the coordinator gather and push a block (or bail out with `SignersRejected`) based on a fabricated majority that didn't actually exist among distinct signers.

### Likelihood Explanation
Medium-High: no majority is required — the flaw is triggered by any single signer (or by a stale/duplicated resend of that signer's own two responses) sending a `Rejected` message followed later by an `Accepted` message for the same block, which is an entirely normal occurrence during the re-evaluation flow described in `docs/signer-flows.md` section 6 (`should_reevaluate_reject_reason`, capitulation, etc.). It requires no cryptographic forgery, no cooperation from other signers, and no node access — only ordinary message replay/resend behavior already anticipated by the protocol.

### Recommendation
Use a single, shared guard for weight accounting across both branches — e.g., check/set membership in `responded_signers` (or a per-slot "already tallied" map) before adding weight in *either* the `Accepted` or `Rejected` branch, and if a slot has already been tallied on one side, either ignore the contradicting later message for weight-accounting purposes or explicitly move the previously-tallied weight from one bucket to the other (subtracting from `total_weight_rejected` and adding to `total_weight_approved`, or vice versa) so a signer's weight is only ever counted once across both tallies.

### Proof of Concept
1. Signer slot `S` (weight `w`) sends `SignerMessageV0::BlockResponse(BlockResponse::Rejected(...))` for block `B`. Result: `responded_signers = {S}`, `total_weight_rejected += w`.
2. Signer slot `S` sends `SignerMessageV0::BlockResponse(BlockResponse::Accepted(...))` for the same block `B` (e.g., a legitimate re-evaluation, or a replayed/duplicated earlier accept). Because `gathered_signatures` does not yet contain `S`, the guard at line 443 passes: `total_weight_approved += w`.
3. Now `total_weight_approved + total_weight_rejected` for block `B` exceeds the total signer weight actually represented by distinct votes by `w`. If enough near-threshold votes exist, this can push `total_weight_approved >= self.weight_threshold` in `signer_coordinator.rs::get_block_status` (or trigger the `>30%` rejection branch) earlier/incorrectly compared to genuine distinct-signer consensus.
