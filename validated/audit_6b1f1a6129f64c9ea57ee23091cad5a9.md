## Title
Confidential Relay Gateway handler keys in-flight requests solely by client-supplied `req.ID`, allowing cross-caller request-ID collision/griefing - (File: `core/services/gateway/handlers/confidentialrelay/handler.go`)

### Summary
The external report describes a Governor bug where `proposalHash()` is derived only from proposal content (targets/values/calldatas/descriptionHash) and not from the proposer, so an unprivileged attacker can front-run a legitimate proposal by submitting an identical proposal first and then cancelling it, blocking the intended proposer. The root cause pattern is: **a request/action identifier that is meant to uniquely track a specific caller's request is derived without binding to the caller's identity**, letting an unrelated unprivileged actor collide with and interfere with someone else's in-flight request.

The Confidential Relay gateway handler exhibits the same structural pattern: it tracks in-flight requests in a map keyed **only by the client-supplied JSON-RPC `req.ID` string** [1](#0-0) , with no binding to workflow owner, workflow ID, or any other caller-identity attribute in the key.

### Finding Description
`HandleJSONRPCUserMessage` only validates that `req.ID` is non-empty and ≤200 chars before calling `newActiveRequest`: [2](#0-1) 

`newActiveRequest` then inserts the request into `h.activeRequests` keyed purely by `req.ID`, rejecting the request if that exact string key already exists: [3](#0-2) 

Node responses are subsequently matched back to the pending request purely by `resp.ID` as well: [4](#0-3) 

This is architecturally identical to the Governor's `proposalHash()` griefing bug: the identifier used to deduplicate/track a caller's action is derived from attacker-controllable material (the request content, `req.ID`) without incorporating any caller-identity component. By contrast, the Vault gateway handler in the same codebase explicitly avoids this class of bug by namespacing the tracked ID with the caller's owner: `expectedRequestID := owner + vaulttypes.RequestIDSeparator + requestID` (see the test expectation) [5](#0-4) , i.e. the Vault handler prefixes/binds the request key to the caller's owner before using it as a lookup key, which is exactly the missing "add proposer to the hash" mitigation recommended in the report. The Confidential Relay handler has no equivalent binding.

### Impact Explanation
Any caller who can reach this gateway handler with a JSON-RPC request (an unprivileged/pre-authorization client, since the ID uniqueness check happens before any DON-side authorization result is known) can pick an arbitrary `req.ID` string. If that string collides with an ID that a legitimate caller is concurrently using for an in-flight secrets/capability-exec relay request, the second submission is rejected with "request ID already exists" [6](#0-5) . This lets an attacker grief/deny a specific victim's in-flight `MethodSecretsGet` / `MethodCapabilityExec` request by winning the race on a guessed or observed ID, exactly mirroring the "front-run with same identifying parameters" griefing described in the report. Because responses are also demultiplexed purely by `resp.ID` [7](#0-6) , if IDs are reused/collide across time windows (e.g., attacker's request ID matches a just-expired/just-cleared entry for a different caller), there is also a risk of stale or misdirected node responses being bundled against the wrong caller's request object, which is a cross-user response confusion pattern.

### Likelihood Explanation
Exploitability depends on how `req.ID` is chosen by legitimate callers (e.g., predictable counters, workflow-derived nonces) and whether the gateway's transport layer already scopes callers before this handler runs. I could not fully verify from the available index whether the gateway enforces per-sender authentication/authorization prior to invoking `HandleJSONRPCUserMessage`, or whether `req.ID` is generated with sufficient entropy by legitimate clients to make guessing infeasible — this needs further verification against the gateway connector/auth layer, which the index did not surface in full. Given the explicit contrast with the Vault handler's owner-namespaced ID pattern in the same codebase, this appears to be a real, structurally analogous gap rather than a false positive, but the concrete likelihood (how easy it is for an unprivileged party to predict/collide with a specific victim's `req.ID`) is uncertain without further investigation.

### Recommendation
Namespace the `activeRequests` map key (and the response-matching key) by a caller-identity component in addition to the raw `req.ID` — analogous to the Vault handler's `owner + RequestIDSeparator + requestID` scheme — so that two different callers' requests can never collide on the same map key, even if they choose (or are made to choose) the same `req.ID` value. This is the direct analog of the report's recommendation to add `proposer` into `proposalHash()`.

### Proof of Concept
Conceptual PoC (unverified against live authentication flow, since caller-identity binding prior to this handler was not confirmed):
1. Victim submits a legitimate `MethodSecretsGet`/`MethodCapabilityExec` JSON-RPC request with `req.ID = "X"` to the Confidential Relay gateway handler; it is registered in `h.activeRequests["X"]`.
2. Attacker, without needing any privileged workflow ownership, submits a JSON-RPC request to the same handler using the same `req.ID = "X"` before the victim's request completes.
3. `newActiveRequest` rejects the attacker's request with "request ID already exists" — or, depending on timing, if the attacker submits first, the victim's legitimate request is instead rejected, denying the victim service using an identifier the attacker does not own or need permission for. func (h *handler) HandleJSONRPCUserMessage(ctx context.Context, req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) error {
	if req.ID == "" {
		return errors.New("request ID cannot be empty")
	}
	if len(req.ID) > 200 {
		return errors.New("request ID is too long: " + strconv.Itoa(len(req.ID)) + ". max is 200 characters")
	}

	l := logger.With(h.lggr, "method", req.Method, "requestID", req.ID)
	l.Debugw("handling confidential relay request")

	ar, err := h.newActiveRequest(req, callback)
	if err != nil {
		return err
	}

	return h.fanOutToNodes(ctx, l, ar)

func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	ar := &activeRequest{
		Callback:  callback,
		req:       req,
		createdAt: h.clock.Now(),
		responses: map[string]*jsonrpc.Response[json.RawMessage]{},
	}
	h.activeRequests[req.ID] = ar
	return ar, nil
}

func (h *handler) HandleNodeMessage(ctx context.Context, resp *jsonrpc.Response[json.RawMessage], nodeAddr string) error {
	l := logger.With(h.lggr, "method", resp.Method, "requestID", resp.ID, "nodeAddr", nodeAddr)
	l.Debugw("handling node response")

	nodeRateLimiter, ok := h.perNodeRateLimiters[nodeAddr]
	if !ok {
		return fmt.Errorf("received message from unexpected node %s", nodeAddr)
	}
	if !nodeRateLimiter.Allow(ctx) {
		l.Debugw("node is rate limited", "nodeAddr", nodeAddr)
		return nil
	}
	if !h.globalNodeRateLimiter.Allow(ctx) {
		l.Debug("global relay rate limit exceeded")
		return nil
	}

	ar := h.getActiveRequest(resp.ID)
	if ar == nil {
		l.Debugw("no pending request found for ID")
		return nil
	}
