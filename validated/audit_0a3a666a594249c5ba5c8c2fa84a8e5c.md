## Analysis Result

The externally reported EnsoWallet.sol issue is a "write access to arbitrary storage via unchecked delegatecall" bug. In GitLab Runner (a Go codebase, no delegatecall concept), the closest architectural analog is **arbitrary file write during archive extraction** ("Zip Slip" / path traversal), which is explicitly one of the vulnerability classes named in the objective ("archive extraction"). I found a legacy zip extraction path that lacks the path-containment checks present in the other extractors.

### Title
Unsanitized zip entry paths allow arbitrary file write during extraction (Zip Slip) - (File: `helpers/archives/zip_extract.go`)

### Summary
The legacy zip extractor used by GitLab Runner's cache/artifact archive handling writes files using the raw `zip.File.Name` field with no validation that the resolved path stays inside the intended extraction directory. This is architecturally analogous to the reported issue: an untrusted, attacker-influenced input (a zip entry name, playing the role of the "library" address in the delegatecall analog) is used directly to determine a filesystem write target with no whitelist/containment check.

### Finding Description
`extractZipFileEntry` and `extractZipDirectoryEntry`/`extractZipSymlinkEntry` in `helpers/archives/zip_extract.go` operate directly on `file.Name` from the zip archive: [1](#0-0) 

`extractZipFile` only creates parent directories via `filepath.Dir(file.Name)` — it never verifies the final path is confined to a base extraction directory: [2](#0-1) 

This contrasts with the `tarzstd` extractor, which explicitly resolves the path and rejects entries that would escape the target directory: [3](#0-2) 

and with `fastzip`, which is backed by a well-audited library (`github.com/saracen/fastzip`) that performs its own containment checks: [4](#0-3) 

The legacy path (`ExtractZipArchive` / `ExtractZipFile`) is wired up through `commands/helpers/archive/ziplegacy/zip_legacy_extractor.go`, which just forwards to `archives.ExtractZipArchive`: [5](#0-4) 

**I could not fully verify from the index which platform/build configuration selects `ziplegacy` vs. `fastzip` as the active extractor for the `Zip` format** — this is registered through the `archive.Register` mechanism (`commands/helpers/archive/archive.go`), and the exact build-tag/runtime selection logic was not visible in the retrieved context. This is a genuine gap in my verification, not an assumption I'm treating as fact.

### Impact Explanation
If `ziplegacy` is reachable (e.g., as a fallback on unsupported platforms, or via the `cache-extractor`/`artifacts-downloader` commands that call into `archive.NewExtractor`), a malicious zip archive (crafted cache or artifact content, which is influenced by CI job configuration/output) containing entries like `../../../../home/user/.ssh/authorized_keys` or absolute paths could write files outside the intended build/cache directory on the runner host, similar in spirit to the "write access to any storage slot" impact in the original report (arbitrary write outside the intended sandbox).

### Likelihood Explanation
Likelihood depends entirely on the unresolved question above: whether `ziplegacy` is ever the active extractor in a default/realistic GitLab Runner deployment, or purely a build-time fallback/test-only path. Without confirming this, I cannot assert this is a live, reachable vulnerability in a standard configuration — it may only be reachable in limited build configurations. Given this uncertainty, I am not confident this fully satisfies the "Disqualify Immediately" criterion of having a proven reachable attacker-controlled entry path in the default runtime.

### Recommendation
Add the same path-containment check used in `tarzstd_extractor.go` (resolve `filepath.Join(dir, file.Name)`, verify with `filepath.Abs` + prefix check against `dir`) to `helpers/archives/zip_extract.go` before performing any filesystem write, directory creation, or symlink creation, regardless of which extractor implementation ends up being selected at runtime.

### Proof of Concept
Not confirmed end-to-end due to the unresolved extractor-selection question above; a full PoC would require constructing a zip archive with a `../` traversal entry name and confirming, via `commands helpers cache-extractor` or `artifacts-downloader`, that `ziplegacy.NewExtractor` (rather than `fastzip`) is invoked to process it.

func extractZipFileEntry(file *zip.File) (err error) {
	var out *os.File
	in, err := file.Open()
	if err != nil {
		return err
	}
	defer func() { _ = in.Close() }()

	// Remove file before creating a new one, otherwise we can error that file does exist
	_ = os.Remove(file.Name)
	out, err = os.OpenFile(file.Name, os.O_WRONLY|os.O_CREATE|os.O_TRUNC, file.Mode().Perm())
	if err != nil {
		return err
	}
	defer func() { _ = out.Close() }()
	_, err = io.Copy(out, in)

	return
}

func extractZipFile(file *zip.File) (err error) {
	// Create all parents to extract the file
	err = os.MkdirAll(filepath.Dir(file.Name), 0o777)
	if err != nil {
		return err
	}

	switch file.Mode() & os.ModeType {
	case os.ModeDir:
		err = extractZipDirectoryEntry(file)

	case os.ModeSymlink:
		err = extractZipSymlinkEntry(file)

	case os.ModeNamedPipe, os.ModeSocket, os.ModeDevice:
		// Ignore files of these types
		logrus.Warningf("File ignored: %q", file.Name)

	default:
		err = extractZipFileEntry(file)
	}
	return
}
