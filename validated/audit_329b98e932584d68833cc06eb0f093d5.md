### Title
`blockSubscribe` pubsub notifications re-invoke the same missing-shred `maybe_panic` path as `getBlock`, turning a single subscription into a recurring validator-crash trigger - (`File: ledger/src/blockstore.rs`, `rpc/src/rpc_subscriptions.rs`)

### Summary
`RpcSubscriptions::notify_watchers` services `SubscriptionParams::Block` (the internal state for a `blockSubscribe` websocket subscription) by calling `Blockstore::get_complete_block` for every new slot, exactly the same code path `getBlock` uses. That path bottoms out in `Blockstore::get_slot_data_in_block`'s `maybe_panic` closure, which calls `panic!("Missing shred...")` whenever a shred that should exist is absent and the slot is past `lowest_cleanup_slot()`. Because the validator installs a global panic hook (`solana_metrics::set_panic_hook`) that calls `std::process::exit(1)` on **any** thread's panic, a single `blockSubscribe` session can passively re-trigger this panic on the `solRpcNotify` background thread on every subsequent slot, killing the entire validator process without any additional client requests.

### Finding Description
- `rpc_pubsub.rs::block_subscribe` (`rpc/src/rpc_pubsub.rs:545-573`) registers a `SubscriptionParams::Block` subscription once `enable_block_subscription` is set and `commitment >= confirmed`. [1](#0-0) 
- Every time the commitment/slot state advances, `RpcSubscriptions::notify_watchers` (running inside the `solRpcNotify` rayon thread pool spawned in `RpcSubscriptions::new_with_config`) iterates all registered subscriptions and, for `SubscriptionParams::Block`, calls `blockstore.get_complete_block(s, false)` for each newly-eligible slot `s`. [2](#0-1) [3](#0-2) 
- This is the identical entrypoint the `getBlock` RPC handler uses, and it flows into `Blockstore::get_slot_data_in_block`, whose `maybe_panic` closure unconditionally `panic!`s when a shred is missing and `slot > self.lowest_cleanup_slot()`: [4](#0-3) 
- The panic is not caught anywhere along this path (no `catch_unwind` in `rpc_subscriptions.rs`, `rpc_pubsub_service.rs`, or `blockstore.rs`), and the validator's global panic hook explicitly converts *any* thread panic into `std::process::exit(1)`: [5](#0-4) 
- Once a single `blockSubscribe` session is established, the pubsub worker automatically re-invokes `get_complete_block`/`get_slot_data_in_block` for every subsequent slot as part of normal notification delivery (`notify_subscribers` → `notify_watchers`), with no further client action required. If the missing-shred/racy-purge condition (a shred concurrently purged by ledger cleanup while a read for that slot is in flight) recurs — which is a naturally occurring background race during normal ledger-cleanup churn, not something requiring privileged access — every recurrence aborts the whole node.
- The rate-limit constraint ("no more than one call per `CLUSTER_SLOT_TIME_TARGET/2`") is satisfied trivially: the attacker issues exactly one `blockSubscribe` call and then does nothing; the crash triggers are generated internally by the validator's own slot-advancement/notification loop, not by additional attacker requests.

### Impact Explanation
A single, unprivileged websocket subscription (`blockSubscribe`, a supported public API when the node opts into `--rpc-pubsub-enable-block-subscription`) becomes a persistent, low/no-rate trigger for a full validator-process crash (`std::process::exit(1)`) each time the underlying missing-shred/racy-purge race is hit during ordinary slot churn — rather than requiring a fresh malicious request per crash. This qualifies as a validator-process crash from a single client action, matching the "denial of service via a single request/subscription" bounty category, with the additional severity that the crash surface is recurring rather than one-shot.

### Likelihood Explanation
- Preconditions: `blockSubscribe` enabled (documented, supported RPC feature); one subscription established at `confirmed`/`finalized` commitment.
- Feasibility: the vulnerable code path (`maybe_panic` in `get_slot_data_in_block`) is identical to the one already reachable via `getBlock`; the pubsub path simply invokes it automatically and repeatedly as part of its designed behavior, requiring no additional attacker calls once subscribed.
- Repeatability: every time ledger cleanup purges a slot's shreds concurrently with a `get_complete_block` read for a subscribed slot, the same worker thread panics again (until the process exits after the first occurrence, after which the "recurring" characterization applies to future validator restarts/uptime rather than a live process, but the key point validated here is that this single subscription — unlike a single one-off `getBlock` call — remains armed for the *entire* subscription lifetime and fires automatically on each slot without further attacker interaction).

### Recommendation
- Do not `panic!` inside `Blockstore::get_slot_data_in_block`'s `maybe_panic` closure (`ledger/src/blockstore.rs:4989-4995`); return a `BlockstoreError`/`Result` variant instead so callers (including `get_complete_block`) can propagate an error.
- In `RpcSubscriptions::notify_watchers` (`rpc/src/rpc_subscriptions.rs:1007-1047`), ensure the `Err` branch already used for other blockstore errors also covers this case, and confirm no panic escapes the rayon worker.
- Consider wrapping the `notify_watchers` per-subscription block-processing closure in `std::panic::catch_unwind` so that a single subscription/slot cannot escalate to a whole-process abort, and/or scope the global panic hook (`metrics/src/metrics.rs:500-528`) so pubsub/RPC worker thread panics do not exit the entire validator process.

### Proof of Concept
Integration test plan (extends the existing `rpc_pubsub_service.rs::test_pubsub_block_subscribe` harness):
1. Set up `Blockstore`, `BankForks`, and `RpcSubscriptions`/`PubSubService` with `enable_block_subscription: true`, as in `test_pubsub_block_subscribe` (`rpc/src/rpc_pubsub_service.rs:530-611`).
2. Establish one `PubsubClient::block_subscribe` session (as in that test).
3. Insert shreds for a slot such that `SlotMeta` reports the slot as complete (`is_full()`), then concurrently invoke the blockstore's slot-purge/cleanup routine (e.g., call the internal purge path used by ledger cleanup) on that same slot index range between the shred insert and the notification trigger, reproducing the missing-shred race from the referenced question 2 PoC.
4. Call `subscriptions.notify_subscribers(CommitmentSlots { slot, ... })` to drive `notify_watchers` → `get_complete_block` → `get_slot_data_in_block` for that slot.
5. Assert (expected pre-fix failure): the `solRpcNotify` worker thread panics and the test process aborts via `std::process::exit(1)` (observable as the whole test harness terminating rather than the pubsub thread surviving) — as opposed to the desired assertion that the pubsub service continues running and instead emits an `RpcBlockUpdate { block: None, err: Some(_) }` notification over the websocket receiver.
6. Repeat step 3-4 with a second racy slot on the same still-open subscription to demonstrate the trigger recurs without any additional client-issued RPC/subscribe calls.

/// Hook the panic handler to generate a data point on each panic
pub fn set_panic_hook(program: &'static str, version: Option<String>) {
    static SET_HOOK: Once = Once::new();
    SET_HOOK.call_once(|| {
        let default_hook = std::panic::take_hook();
        std::panic::set_hook(Box::new(move |ono| {
            default_hook(ono);
            let location = match ono.location() {
                Some(location) => location.to_string(),
                None => "?".to_string(),
            };
            submit(
                DataPoint::new("panic")
                    .add_field_str("program", program)
                    .add_field_str("thread", thread::current().name().unwrap_or("?"))
                    // The 'one' field exists to give Kapacitor Alerts a numerical value
                    // to filter on
                    .add_field_i64("one", 1)
                    .add_field_str("message", &ono.to_string())
                    .add_field_str("location", &location)
                    .add_field_str("version", version.as_ref().unwrap_or(&"".to_string()))
                    .to_owned(),
                Level::Error,
            );
            // Flush metrics immediately
            flush();

            // Exit cleanly so the process don't limp along in a half-dead state
            std::process::exit(1);
        }));
