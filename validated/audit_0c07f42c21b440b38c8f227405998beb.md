### Title
Stale rejection weight is never retracted when a signer switches to acceptance, letting `total_weight_rejected` and `total_weight_approved` double-count the same signer's weight - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The node-side vote tally in `StackerDBListener` (used by `SignCoordinator` to decide whether a block is signable, dead, or still pending) accumulates `total_weight_approved` and `total_weight_rejected` as two independent saturating counters keyed off different membership sets. A signer that first rejects a block and later legitimately re-evaluates and accepts it (a transition the signer state machine explicitly allows, `LocallyRejected --> LocallyAccepted`) has its weight added to *both* tallies, because the acceptance path never checks whether the signer already rejected. This breaks the invariant that a signer's weight should be attributed to at most one side of the tally at any time, producing an aggregated-weight vs. verified-current-vote mismatch — the same class of accounting error as the WithdrawProxy `y0` bug, where a state variable was updated without properly accounting for what had already been attributed.

### Finding Description
Two message handlers in `handle_signer_message` in `stackerdb_listener.rs` update `BlockStatus`:

- On `BlockResponse::Accepted`, weight is only guarded against being double counted on repeat *acceptances* — the check is `!block.gathered_signatures.contains_key(&slot_id)` — before `total_weight_approved` is incremented. [1](#0-0) 

- On `BlockResponse::Rejected`, the guard is `block.responded_signers.insert(slot_id)`, which is a set shared with the acceptance path (the acceptance path also inserts into `responded_signers` at line 465). [2](#0-1) 

Because `responded_signers` is shared, an **Accept-then-Reject** sequence is correctly guarded (the reject arm's `insert` returns `false` since the slot was already recorded, so `total_weight_rejected` is not incremented). But the reverse, **Reject-then-Accept**, is not: the accept arm never inspects `responded_signers` (or any record of a prior rejection) before adding the signer's weight to `total_weight_approved`. The rejection's weight contribution to `total_weight_rejected` is never removed. The result is that both tallies simultaneously contain the same signer's weight, so `total_weight_approved + total_weight_rejected` can exceed `self.total_weight` — an equality (each signer's weight counted exactly once, attributed to their current, latest vote) that the coordinator's threshold math implicitly assumes.

This tally directly drives `SignCoordinator::run_sign_coordinator` in `signer_coordinator.rs`, which computes the blocking-minority condition from `block_status.total_weight_rejected` alone: [3](#0-2) 
and the acceptance condition from `block_status.total_weight_approved` alone: [4](#0-3) 

Because `total_weight_rejected` is not corrected downward when the same signer switches to acceptance, a phantom/stale rejection weight lingers and can push the block past the `>30%` blocking-minority threshold even though, counting only current opinions, fewer than 30% of weight is actually opposed to the block. Conversely, since the accepted weight is also legitimately recorded, the same event can also (at a different moment in the loop) satisfy the `>=70%` acceptance threshold; whichever check the loop evaluates to on a given pass, the miner's decision is being made against an inflated/unreconciled total rather than the verified current votes of each signer, which is exactly the "aggregated-weight vs verified-accepts" mismatch called out as in-scope.

### Impact Explanation
This is a liveness wedge reachable by a single signer's ordinary vote transition plus normal gossip — no majority or key compromise is required. If enough (even honest) signers re-evaluate a block from reject to accept (which the state machine explicitly supports, see the `LocallyRejected → LocallyAccepted` transition in the signer flow model), their now-stale rejection weight remains counted in `total_weight_rejected`. This can trip the blocking-minority branch in `SignCoordinator` (`SignersRejected`, causing the miner to give up on a legitimately signable block and instead treat it as dead / exclude its transactions), or it can distort which branch of the `if/else if` in the coordinator loop fires first, since the two tallies are no longer complementary. Both outcomes fall under "a signer wedged into never signing valid blocks" / node acting on a stale, uncorrected vote tally rather than the true current signer state.

### Likelihood Explanation
Vote re-evaluation from reject to accept is an explicitly supported, ordinary state transition (documented in `docs/signer-flows.md` section 2, `LocallyRejected --> LocallyAccepted : re-evaluated`), so this is not a contrived edge case — it can happen naturally whenever a chainstate check that initially failed later passes (e.g., a burn-chain view catches up, or a competing sibling becomes stale). No adversarial majority, key compromise, or auth-token access is needed: a single honest signer flipping its vote due to normal state re-evaluation triggers the double count.

### Recommendation
Before adding weight to `total_weight_approved`, check whether the signer's slot is already present in a rejection-tracking set (symmetric to how the reject arm checks `responded_signers`), and if so, subtract/retract the signer's weight from `total_weight_rejected` (or maintain a single per-signer "current vote" map instead of two independent additive counters) so that `total_weight_approved + total_weight_rejected` never exceeds `self.total_weight` and always reflects only each signer's most recent response.

### Proof of Concept
1. Node proposes block B; `BlockStatus` starts with `total_weight_approved = 0`, `total_weight_rejected = 0`.
2. Signer S (weight w) sends `BlockResponse::Rejected` for B — matches `SignerMessageV0::BlockResponse(BlockResponse::Rejected(...))`; `responded_signers.insert(slot_id)` succeeds, `total_weight_rejected += w`. [5](#0-4) 
3. S's local chainstate check subsequently passes (e.g., a stale sibling/tenure conflict clears) and S re-evaluates, moving to `LocallyAccepted` and broadcasting `BlockResponse::Accepted` for the same block hash.
4. The Accept handler checks only `!block.gathered_signatures.contains_key(&slot_id)` (true, since S never signed before) and adds `total_weight_approved += w`, with no check against `responded_signers` or any record of S's prior rejection. [1](#0-0) 
5. Now `total_weight_approved + total_weight_rejected = 2w` while only `w` of real distinct signer weight has actually voted — `total_weight_rejected` still contains S's now-superseded vote. If additional signers push `total_weight_rejected` (inflated by this stale `w`) past `total_weight - weight_threshold`, `SignCoordinator` returns `NakamotoNodeError::SignersRejected` and abandons the block even though, counting only current votes, the rejecting weight is below the true blocking minority. [6](#0-5) 

**Uncertainty:** I was not able to fully read the bodies of `SignerDb::add_block_signature` / `SignerDb::add_block_rejection_signer_addr` (signer-side, `stacks-signer/src/signerdb.rs`) before the tool budget ran out, so I cannot confirm whether the analogous local-signer tally (`store_and_process_block_signature` / `store_and_process_block_rejection` in `stacks-signer/src/v0/signer.rs`, which separately query the `block_signatures` and `block_rejection_signer_addrs` tables) has the same unguarded cross-tally issue or whether it's mitigated elsewhere (e.g. by clearing a prior rejection row when a signature is later added). The confirmed, exploitable instance is the node-side `stackerdb_listener.rs` / `signer_coordinator.rs` path documented above.
