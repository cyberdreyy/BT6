### Title
Claimed instant-withdraw receipts are never removed from `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch`, inflating default-recovery basis and price — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to `stakedButUnverifiedNativeETH` being incremented on stake but never decremented on unstake, `IdleCreditVault` increments the per-epoch instant-withdraw accounting in `requestInstantWithdraw` but never decrements it on the normal funded claim path. `claimInstantWithdrawRequest` zeroes `instantWithdrawsRequests[_user]` and burns the receipt tokens, but leaves `instantWithdrawsRequestsByEpoch[_user][epoch]` and the aggregate `instantWithdrawClaimsByEpoch[epoch]` untouched. If the borrower defaults in that same epoch, `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()` treat already-paid receipts as still-outstanding basis and as "prefunded" reserve, producing an inflated `defaultRecoveryPrice` in `finalizeDefaultRecovery`. Early defaulted claimants are overpaid and the recovery reserve is drained before all claims are served; the last claimants' transfers revert, permanently freezing their recovery share.

### Finding Description
In `requestInstantWithdraw`, three counters grow: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and `instantWithdrawClaimsByEpoch[currentEpoch]` (lines 366–374). `pendingInstantWithdraws` is decremented when the CDO collects funding via `collectInstantWithdrawFunds` (line 401), but the per-epoch claim-basis counters are only ever decremented inside `_claimDefaultedInstantWithdrawRequest` (lines 847–853) — i.e., only on the *defaulted* path. The normal claim path does not clear them:

```
// claimInstantWithdrawRequest, lines 387-392
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

At default finalization, `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` to the recovery basis whenever `pendingInstantWithdraws != 0` (lines 644–649), and `_defaultPrefundedInstantReserve()` computes `instantBasis - pendingInstant` as already-held reserve (lines 716–723). Amounts already paid out to claimed users remain inside `instantBasis`, so the counted "prefunded" reserve includes money the strategy no longer holds. `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` (line 688) therefore exceeds the real reserve ratio. Each `_transferDefaultRecovery` decrements `defaultRecoveryReserve` (line 915) faster than the true backing, so the reserve is exhausted before all claimants are paid; remaining `_transferDefaultRecovery`/`safeTransfer` calls revert, permanently freezing those users' recovery.

Additionally, `_claimDefaultedInstantWithdrawRequest` executes `instantWithdrawsRequests[_user] -= claimBasis` (line 848), which underflows for a user whose aggregate was already zeroed by a normal claim — so the inflated epoch basis also blocks that user's `claimInstantWithdrawRequest` entirely once `defaultInstantWithdrawsFinalized` is set.

### Impact Explanation
- Broken invariant: one receipt, one payout — paid receipts continue to occupy default-recovery basis.
- Recovery price is overstated by the ratio `(trueReserve + alreadyPaidOut) / (trueBasis + alreadyPaidOut)`; defaulted-epoch claimants who claim early receive more than their fair pro-rata recovery, paid for by later claimants whose claims revert on insufficient reserve/balance. Quantified loss: up to the full amount of same-epoch instant receipts that were funded and claimed before default finalization, duplicated as phantom basis.
- Alternatively, any user who claimed an instant receipt funded earlier in the defaulted epoch has `claimInstantWithdrawRequest` permanently bricked via the line-848 underflow — temporary-to-permanent freezing of any other instant receipts for that user.

### Likelihood Explanation
Requires: (1) an instant withdraw requested and funded via `collectInstantWithdrawFunds` in epoch N, (2) the user claims it while still in epoch N or the epoch counter is unchanged, (3) another instant request arrives in epoch N leaving `pendingInstantWithdraws != 0`, and (4) the borrower defaults and `finalizeDefaultRecovery` runs while `epochNumber == N`. The attacker is unprivileged (a KYC'd lender/tranche holder making ordinary instant-withdraw requests and claims); the default itself is triggered by honest borrower/keeper behavior. Epochs with instant-withdraw queues partially funded are a normal operating state, so the precondition is realistic but depends on the sequencing of an honest default — medium likelihood.

### Recommendation
Mirror the fix for `stakedButUnverifiedNativeETH`: decrement the epoch-scoped counters when the receipt is settled on the funded path. In `claimInstantWithdrawRequest`, also subtract the claimed amount from `instantWithdrawsRequestsByEpoch[_user][<requestEpoch>]` and `instantWithdrawClaimsByEpoch[<requestEpoch>]`. Because the per-epoch mapping needs the request's epoch, record each instant request's epoch (e.g., a `lastInstantWithdrawRequest` marker or per-epoch aggregation cleared at claim) so that `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` reflect only still-unclaimed basis. The underflow-prone `instantWithdrawsRequests[_user] -= claimBasis` in `_claimDefaultedInstantWithdrawRequest` should be consistent with whatever the funded path clears.

### Proof of Concept
Foundry fork PoC sketch ( against `IdleCreditVault` + `IdleCDOEpochVariant` in `test/foundry/`):

```solidity
function test_ClaimedInstantReceiptInflatesDefaultRecovery() public {
    // epoch N running, pool funded by AA/BB deposits (honest lender + attacker)
    // 1. Attacker: requestInstantWithdraw(A) via CDO -> instantWithdrawClaimsByEpoch[N] += A
    // 2. Honest keeper/CDO: collectInstantWithdrawFunds(A) -> pendingInstantWithdraws = 0,
    //    strategy holds A underlying
    // 3. Attacker: claimInstantWithdrawRequest(attacker)
    //    -> receives A underlying; instantWithdrawsRequests[attacker] = 0
    //    -> BUG: instantWithdrawsRequestsByEpoch[attacker][N] == A still
    //           instantWithdrawClaimsByEpoch[N] == A still
    // 4. Honest lender: requestInstantWithdraw(B) in same epoch N, unfunded
    //    -> pendingInstantWithdraws = B; instantWithdrawClaimsByEpoch[N] = A + B
    // 5. Borrower fails to fund at stopEpoch -> CDO defaults ->
    //    finalizeDefaultRecovery(R, source)
    //    basis = pendingWithdraws + (A + B)            // A is phantom
    //    prefundedReserve = (A + B) - B = A            // money already paid out!
    //    recoveryPrice = (R + A + reserve) / (activeBasis + pendingBasis)  // inflated
    // 6. Honest lender's defaulted instant claim pays claimBasis * inflatedPrice / 1e18,
    //    overdrawing defaultRecoveryReserve; a subsequent legitimate claim
    //    reverts in _transferDefaultRecovery (reserve underflow) or safeTransfer
    //    (insufficient balance) -> funds permanently frozen.
    // Also: attacker's own claimInstantWithdrawRequest now reverts at
    //    instantWithdrawsRequests[attacker] -= claimBasis  (0 - A underflows)
}
```

Key assertion for the test: after step 3, `assertGt(instantWithdrawClaimsByEpoch(epochNumber), 0)` even though no funded instant receipt remains outstanding — the direct analog of the undecremented `stakedButUnverifiedNativeETH` counter.

Uncertainty: I could not fully trace every call site in `IdleCDOEpochVariant.sol` that updates `epochNumber` or calls `collectInstantWithdrawFunds` in this iteration; the PoC assumes `epochNumber` in the vault is unchanged between funding/collection and finalization within one epoch, which matches the vault's own comments that `epochNumber` is bumped at `stopEpoch`/deposit-on-stop.
