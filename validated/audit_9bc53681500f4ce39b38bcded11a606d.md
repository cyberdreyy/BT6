### Title
Gateway `web_api_trigger` callback map keyed only by client-controlled `MessageId` allows in-flight request hijacking / cross-user response confusion - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The gateway's user-facing HTTP endpoint accepts unauthenticated legacy JSON-RPC requests and, for `web_api_trigger` (and similarly in `handlers/handler.dummy.go`), stores the response callback in `h.savedCallbacks` keyed solely by the client-supplied `MessageId`, with no per-sender namespacing and no collision check. `JsonRPCCodec.DecodeJSONRequest` copies the raw `jsonrpc2.Request.ID` verbatim into `msg.Body.MessageId` with no uniqueness enforcement, so a second concurrent request using the same `id` silently overwrites the first request's saved callback.

### Finding Description
`gateway.ProcessRequest` (`core/services/gateway/gateway.go`) decodes the incoming HTTP JSON-RPC body via `g.codec.DecodeJSONRequest` [1](#0-0) , which sets `msg.Body.MessageId = request.ID` directly from attacker-controlled input, with no per-sender namespacing.

For a "legacy" request with a `DonId`, the gateway only validates the message signature format/length via `msg.Validate()` (which merely recovers `Body.Sender` from the ECDSA signature over the message, without checking the signer is an allow-listed DON member) [2](#0-1) , then routes it straight to `h.HandleLegacyUserMessage(ctx, msg, callback)` [3](#0-2) . No handler-level check ties the request to a specific caller identity or session, and nothing prevents an unauthenticated attacker from crafting a fresh signature over an arbitrary `MessageId` chosen to collide with another party's in-flight ID.

In `handler.HandleLegacyUserMessage` (the `web_api_trigger` legacy handler), the pending-request map is written unconditionally:
```
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
...
h.mu.Unlock()
``` [4](#0-3) 
There is no existence check (`if _, ok := h.savedCallbacks[id]; ok { return error }`) before this assignment, unlike the equivalent pattern used elsewhere in the same codebase (`newActiveRequest` in `confidentialrelay/handler.go` and `vault/handler.go` explicitly reject duplicate IDs) [5](#0-4) . The same unguarded overwrite pattern exists in the dummy handler as well [6](#0-5) .

When a DON node later reports a matching `MessageId` via `HandleNodeMessage` → `handleWebAPITriggerMessage`, the lookup is purely by `MessageId`:
```
savedCb, found := h.savedCallbacks[msg.Body.MessageId]
delete(h.savedCallbacks, msg.Body.MessageId)
...
return savedCb.SendResponse(...)
``` [7](#0-6) 
Whichever caller's callback occupies the slot at delivery time receives the node's response — regardless of who actually originated the request the node is responding to.

Exploit flow:
1. User A submits a legitimate `web_api_trigger` request with `{id: "X", ...}` signed with A's key. `HandleLegacyUserMessage` stores A's callback under key `"X"` and fans the request out to DON nodes.
2. Before a node responds, attacker (unauthenticated, any keypair) submits their own request `{id: "X", ...}` with a different/unrelated payload, signed with the attacker's own key (message signature validation only checks that *some* valid signer produced the signature, not identity/authorization).
3. `HandleLegacyUserMessage` overwrites `h.savedCallbacks["X"]` with the attacker's callback.
4. When a DON node later replies to `MessageId "X"` (which was originally sent for A's request), `handleWebAPITriggerMessage` looks up key `"X"`, finds only the attacker's callback (A's reference was overwritten and lost), and delivers the node's response — potentially containing data derived from A's original trigger context/payload — to the attacker instead of to A. A's request silently hangs until pruning/timeout.

### Impact Explanation
This is a cross-user response confusion / request-binding violation: an unprivileged, unauthenticated network client can hijack another user's in-flight gateway request slot purely by guessing or observing a `MessageId` and racing a colliding request. Depending on what data the node's `web_api_trigger` response carries, this can leak response content intended for another caller to the attacker and denies the legitimate request (it never gets a response until the internal prune/timeout logic clears it). This matches the Chainlink bounty impact class of unauthorized access to another user's response/data via request impersonation in the gateway.

### Likelihood Explanation
Preconditions are minimal: only network access to the gateway's user-facing HTTP endpoint is required, no authentication or DON membership check gates the legacy request path before it reaches `HandleLegacyUserMessage`. The attacker only needs to predict/observe a `MessageId` for a request that is currently in flight (client-chosen IDs are often predictable/sequential/UUIDs visible via other channels) and race their own signed request against it before the target node response arrives — feasible and repeatable given no rate limiting or collision defense on this specific code path.

### Recommendation
In `handler.HandleLegacyUserMessage` (and the analogous `handler.dummy.go` `HandleLegacyUserMessage`), reject the request with an error if `h.savedCallbacks[msg.Body.MessageId]` already exists, matching the pattern already used in `vault/handler.go` and `confidentialrelay/handler.go`'s `newActiveRequest`. Additionally, consider namespacing the callback map key by `(Sender, MessageId)` (as already done in `handlers/common/requestcache.go`'s `globalId{sender, id}`) rather than by `MessageId` alone, so that even legitimate distinct senders using coincidentally identical IDs cannot collide.

### Proof of Concept
Go handler-level integration test (in `core/services/gateway/handlers/capabilities/handler_test.go`):
1. Build two distinct signed `web_api_trigger` messages with the same `MessageId = "X"` but signed by two different private keys (`keyA`, `keyAttacker`), simulating User A and the attacker.
2. Call `handler.HandleLegacyUserMessage(ctx, msgA, cbA)` — assert `handler.savedCallbacks["X"].Callback == cbA`.
3. Before responding from any node, call `handler.HandleLegacyUserMessage(ctx, msgAttacker, cbAttacker)` — assert `handler.savedCallbacks["X"].Callback` is now `cbAttacker` (overwritten), demonstrating loss of `cbA`.
4. Simulate a DON node responding with `MessageId "X"` via `handler.HandleNodeMessage`/`handleWebAPITriggerMessage`.
5. Assert `cbAttacker.Wait(ctx)` receives the response instead of `cbA`, and `cbA.Wait(ctx)` times out/never resolves — proving cross-user response delivery.

Expected result on the vulnerable code: step 3 succeeds without error and step 5 confirms the attacker receives A's response. After applying the recommended fix (reject duplicate IDs), step 3 should return an error (`"request ID already exists"`) and A's callback remains intact.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
