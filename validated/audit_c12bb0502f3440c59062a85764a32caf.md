### Title
Confirmations from removed multisig members remain counted toward the confirmation threshold, allowing a request to execute below the intended `num_confirmations` threshold - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
The confirmation counting logic in both `multisig` and `multisig2` checks only the raw size of the `confirmations` set against `num_confirmations` [1](#0-0) . When a member is removed via `DeleteMember` (or a key is removed via `DeleteKey` in `multisig`), the cleanup logic only purges requests and confirmations for requests *created by* that member/key, not confirmations that member/key had already cast on other, still-pending requests [2](#0-1) . A stale confirmation from a now-removed member therefore still counts toward reaching the threshold, letting a request execute with fewer live-member confirmations than `num_confirmations` requires.

### Finding Description
The binding that should hold is: `live-member confirmations on a request >= num_confirmations` before `execute_request` runs. Instead the code enforces: `confirmations.len() >= num_confirmations`, where `confirmations` is a `HashSet` keyed by member/pk strings that is never revalidated against current membership.

In `multisig2`:
- `confirm()` reads `self.confirmations.get(&request_id)` and compares its length to `self.num_confirmations` without checking that each entry in the set is still `self.members.contains(...)` [3](#0-2) .
- `delete_member()` removes requests whose `r.member == member` (i.e., requests *created* by the removed member) and their confirmations, and clears `num_requests_pk` for that member [4](#0-3) . It does **not** scan other requests' `confirmations` sets to strip entries belonging to the removed member.

The identical pattern exists in the older `multisig` contract: `DeleteKey` only deletes requests created by that key (`r.signer_pk == pk`) and their confirmations, but does not strip that key's confirmations from other pending requests [5](#0-4) , while `confirm()` again just compares `confirmations.len()` to `self.num_confirmations` [6](#0-5) .

This is the same bug class as the referenced report: a validity check ("this confirmation/forge is allowed") is decoupled from the later state that should invalidate it (member/key removal), so state from before the invalidating event is still trusted afterward.

### Impact Explanation
This breaks the core multisig guarantee "a request needs `K` confirmations from current members to execute." An attacker (or even an honest but stale-confirmation scenario) can get a request executed by combining confirmations, some of which come from members who have since been removed — i.e., a **multisig request executed below threshold**, one of the explicitly listed Critical impacts. Since `execute_request` can perform `Transfer`, `DeployContract`, `AddKey`/`AddMember`, or arbitrary `FunctionCall` actions on behalf of the multisig account, this can directly move NEAR funds or hand out permissions with fewer genuinely-live confirmations than configured.

### Likelihood Explanation
This requires only benign operational sequencing available to unprivileged members (no owner/foundation/redeploy assumptions): (1) a request is confirmed by some members, (2) later, a separate request removes one of those confirming members (a normal governance action, not requiring any special privilege beyond being an existing member and following normal multisig flow), (3) a remaining member confirms the still-pending request, crossing the threshold using the stale confirmation. Because pending requests can be added and left open indefinitely and deletion of a member is a normal, expected operation, the sequence is easily reachable without needing malice from a member being removed — a member could even accidentally leave a stale confirmation. Likelihood is moderate-to-high in any account where membership changes over time while requests remain outstanding.

### Recommendation
When removing a member/key, iterate over all pending `requests`/`confirmations` (not just the ones created by that member) and remove that member's/key's entry from every `confirmations` set. Alternatively, in `confirm()`, filter the confirmation set to only currently valid members/keys before comparing its length to `num_confirmations`:
```rust
let live_confirmations = confirmations
    .iter()
    .filter(|m| self.members.contains(&MultisigMember::from_str(m)))
    .count();
if live_confirmations as u32 + 1 >= self.num_confirmations { ... }
```
The analogous fix (`< count` before an increment / revalidate-at-use) applies to both `multisig/src/lib.rs` (`DeleteKey`) and `multisig2/src/lib.rs` (`delete_member`).

### Proof of Concept
Using `multisig2` with `num_confirmations = 3` and members `A, B, C, D`:
1. `A` calls `add_request_and_confirm(R)` — `R.member = A`, `confirmations = {A}`.
2. `B` calls `confirm(R)` — `confirmations = {A, B}` (2 < 3, not yet executed).
3. Separately, `D` proposes and the group confirms (`A`, `C`, `D`) a `DeleteMember{B}` request, which executes via `delete_member`. This removes `B` from `self.members`, and removes requests created by `B` (none, since `R.member == A`), but leaves `B`'s confirmation entry inside `confirmations` for `R` untouched [4](#0-3) .
4. `C` calls `confirm(R)`. `confirmations.len() as u32 + 1 == 3 >= num_confirmations (3)`, so `R` executes [7](#0-6) , even though only `A` and `C` are genuinely live members who confirmed — one short of the configured 3-of-N threshold.

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
