### Title
Client-controlled `MessageId` collision in `web_api_trigger` flow allows cross-user response confusion / callback hijack - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` stores each pending user callback in `h.savedCallbacks` keyed solely by the attacker-controlled `msg.Body.MessageId`, with no uniqueness check before overwrite. Because the corresponding node response (`handleWebAPITriggerMessage`) is later matched and delivered purely by this same `MessageId`, two concurrent `web_api_trigger` requests sharing an ID cause the gateway to deliver whichever node response arrives first to whichever callback is currently registered for that ID, regardless of which logical request produced it.

### Finding Description
`gateway.ProcessRequest` decodes the JSON-RPC request, sets `msg.Body.MessageId = request.ID` directly from the attacker-supplied JSON-RPC `id` field [1](#0-0) , validates the message (length/signature format only, no uniqueness check) [2](#0-1) , and calls `h.HandleLegacyUserMessage(ctx, msg, callback)` [3](#0-2) .

Inside `HandleLegacyUserMessage`, the handler unconditionally overwrites any existing entry in the shared map: [4](#0-3) 
There is no check for whether `msg.Body.MessageId` is already present, and no binding of the map entry to the requesting signer/session — only the raw ID is used as the key.

When a node later replies with `MethodWebAPITrigger` and the same `MessageId`, `handleWebAPITriggerMessage` looks the ID up, deletes it, and forwards the raw node response to *whichever* callback is currently stored: [5](#0-4) 

Exploit flow:
1. Attacker (or two colluding/racing parties) sends `web_api_trigger` request R1 with `MessageId = "X"`, signed with any ECDSA key via `Message.Sign` — no allowlist/session/token is checked before this point (the `// TODO: apply allowlist and rate-limiting here` comment at line 384 confirms no authorization gate exists yet) [6](#0-5) . `savedCallbacks["X"]` = callback1.
2. Before nodes respond, a second request R2 (own or colliding with a victim's chosen ID "X") arrives and overwrites `savedCallbacks["X"]` = callback2.
3. The first node response tagged with `MessageId="X"` (which may correspond to R1's underlying trigger, forwarded independently to all DON members) is delivered to whichever callback is currently registered — typically callback2, not callback1.
4. R1's caller receives no reply and times out (`RequestTimeoutError`, HTTP 504) in `gateway.ProcessRequest`'s `callback.Wait(ctx)` [7](#0-6) , while R2's caller receives a response that was actually produced in response to R1's payload/signer.

No existing check (signature verification, allowlist, rate limiter) prevents this, because signature verification only proves who signed a given message — it does not enforce ID uniqueness or bind the `savedCallbacks` map slot to a specific sender.

### Impact Explanation
This is a cross-user response confusion vulnerability: an unprivileged holder of any ECDSA key can, by colliding `MessageId` values, cause the gateway to route a `web_api_trigger` node response intended for one request to a different caller's HTTP connection, and cause the original caller to silently time out. Depending on payload content, this could leak DON/node-produced webhook trigger response data to an unintended requester. It also enables trivial denial-of-service against a specific pending request by an unauthenticated party who merely needs to guess/observe the target's chosen `MessageId` (client-controlled, up to 128 bytes) and race a second signed message with the identical ID before the legitimate response arrives.

### Likelihood Explanation
- No preconditions beyond possessing an ECDSA key (any address) — matches the stated attacker capability exactly, since `web_api_trigger` allowlisting/rate-limiting is explicitly not yet implemented at this stage of the handler (`// TODO: apply allowlist and rate-limiting here`).
- Colliding with a *specific victim's* ID requires knowing/guessing that victim's `MessageId`, which is not enforced to be unpredictable (no server-side uniqueness or randomness requirement) — feasibility for targeted victim collision therefore depends on how calling clients generate IDs (not verified in this codebase snapshot); however the self-inflicted duplicate-ID race (attacker vs. attacker) is trivially and repeatably reproducible with zero preconditions, and confirms the map-overwrite root cause is real and exploitable in principle for any two concurrent requests that happen to share an ID.
- Repeatable: the race only requires timing two signed requests before the first node response returns (window bounded by `CallbackMaxAgeSec`, default 120s).

### Recommendation
Reject a `web_api_trigger` message if `msg.Body.MessageId` already exists in `h.savedCallbacks` (return a `HandlerError`/duplicate-ID error to the second request instead of overwriting), and additionally scope the map key by sender address (e.g. `sender+":"+messageID`) so that two different signers can never collide on the same logical slot even if they choose the same ID string.

### Proof of Concept
Go handler-level test plan (`core/services/gateway/handlers/capabilities/handler_test.go`):
1. Construct a `handler` via `NewHandler` with a fake `handlers.DON` mock capturing `SendToNode` calls.
2. Create two `handlers.Callback` instances (`cb1`, `cb2`) and two `*api.Message` with `Body.Method = MethodWebAPITrigger`, identical `Body.MessageId = "X"`, valid `Timestamp`, but distinct payload/signature (sign with two different ECDSA keys via `Message.Sign`).
3. Call `h.HandleLegacyUserMessage(ctx, msg1, cb1)` then immediately `h.HandleLegacyUserMessage(ctx, msg2, cb2)`.
4. Assert `h.savedCallbacks["X"].Callback == cb2` (proving cb1 was silently overwritten/lost) — this alone demonstrates the missing-uniqueness root cause.
5. Simulate a node reply: build `jsonrpc.Response` with `ID`/body mapping to `MessageId="X"`, call `h.HandleNodeMessage(ctx, resp, nodeAddr)`.
6. Assert that `cb2.SendResponse` (not `cb1`) receives the payload, and that `cb1.Wait(ctx)` (or equivalent) times out / never resolves — confirming cross-callback response delivery and the resulting DoS/response-confusion for the first request's caller.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
