### Title
Stale Confirmations From Removed Multisig Members Count Toward the Confirmation Threshold, Allowing a Request to Execute Below the Live-Member Threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::confirm` counts confirmations only by their raw size (`confirmations.len()`), never validating that every recorded confirmer is still a current multisig member. When a member is removed via `DeleteMember`, `delete_member` only purges confirmations belonging to requests *that member itself created* (`r.member == member`), but never scrubs that member's confirmation entries from *other* pending requests they had previously confirmed. As a result, a stale confirmation from a now-removed member is still counted when a later confirmation pushes the tally to `num_confirmations`, letting a transfer/function-call/key-management request execute with fewer live-member approvals than the configured threshold requires.

### Finding Description
The equality that must hold is:

`confirmations.len()` counted toward the threshold == number of **currently live** members who approved the request.

`confirm()` breaks this by comparing raw confirmation-set size to `num_confirmations` without re-validating membership of each entry: [1](#0-0) 

`delete_member` only cleans confirmations for requests the removed member *originated*, not confirmations the removed member cast on requests created by others: [2](#0-1) 

Concretely:
1. Members: `A, B, C, D`, `num_confirmations = 3`.
2. `A` calls `add_request(R)` (a `Transfer` action), leaving `confirmations[R] = {}`.
3. `B` calls `confirm(R)` → `confirmations[R] = {B}`.
4. `C` calls `confirm(R)` → `confirmations[R] = {B, C}` (2 < 3, still pending).
5. Separately, the multisig executes a `DeleteMember { member: C }` request (reached its own threshold through normal governance). `delete_member` checks `self.requests` for requests whose `r.member == C` (i.e. requests *created* by `C`) — `R` was created by `A`, so it is untouched. `confirmations[R]` still equals `{B, C}`, even though `C` is no longer a member.
6. `D` calls `confirm(R)` → `confirmations.len() + 1 == 3 >= num_confirmations (3)` → `execute_request(R)` fires.

At execution time the live membership is `{A, B, D}` (3 members) with `num_confirmations = 3`, meaning all three current members should be required to approve. In reality, only `B` and `D` (2 live members) approved; the third "confirmation" came from `C`, who had already been removed. The threshold check passed on a stale confirmation, so `R` (e.g., a `Transfer`) executed with confirmations from only 2 of 3 live members.

`assert_valid_request` does not fix this either — it only checks that the *caller* is a current member and that the request/confirmations exist, never that entries already stored in `confirmations[request_id]` are still valid members: [3](#0-2) 

### Impact Explanation
This directly matches the Critical impact category "a multisig request executed below threshold." Because `MultiSigRequestAction::Transfer`, `FunctionCall`, `AddKey`, etc. are all gated by the same `confirm()` logic, an attacker (or any member benefiting from lax governance) can get a fund transfer, a key addition, or a contract upgrade executed with fewer live approvals than the K-of-N scheme is supposed to enforce. This is used by `multisig-factory/src/lib.rs` to deploy every multisig account, so it affects any multisig instance created from this factory or the `multisig2` contract directly. [4](#0-3) 

### Likelihood Explanation
The bug is triggered purely by ordinary multisig operations — creating a request, confirming it, and later removing a member who had confirmed it — with no requirement to compromise any key or impersonate the foundation. Membership changes over the life of a long-running multisig account are routine (offboarding a team member, rotating keys), making this stale-confirmation window realistically reachable.

### Recommendation
When executing `DeleteMember` (and the `DeleteKey`/`delete_member` equivalent in `multisig/src/lib.rs`), scrub the removed member's confirmation entry from **every** pending request's `confirmations` set, not just requests they created. Alternatively, when tallying confirmations in `confirm()`, filter `confirmations` to only entries that are still `self.members.contains(...)` before comparing against `num_confirmations`.

### Proof of Concept
```
members = [A, B, C, D], num_confirmations = 3

A: add_request(R = Transfer{amount, receiver_id})      // confirmations[R] = {}
B: confirm(R)                                           // confirmations[R] = {B}
C: confirm(R)                                           // confirmations[R] = {B, C}

// Separate governance action removes C
(A,B,D or however threshold reached): DeleteMember{C} executed
  -> delete_member only removes requests where r.member == C; R.member == A, so R and
     confirmations[R] == {B, C} are left untouched.
  -> members now = {A, B, D}, num_confirmations still 3

D: confirm(R)
  -> confirmations.len() (2) + 1 == 3 >= num_confirmations (3)
  -> execute_request(R) fires: Transfer executes
  -> Only B and D (2 of 3 live members) actually approved; C's stale confirmation
     satisfied the 3rd slot despite C no longer being a member.
```

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
