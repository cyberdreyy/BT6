## Title
Multisig requests can be executed using stale confirmations from removed members, allowing execution below the intended confirmation threshold - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

## Summary
The reported bug class is "an actor identity that was authorized for one context gets trusted in another without re-validation" (the `liquidator` parameter in Notional was never checked against who was actually entitled to act). The direct analog in this repository is in the multisig contracts: `delete_member`/`DeleteKey` only purges requests **authored by** the removed member, but does not purge that member's **confirmations left on other pending requests**. Those stale confirmations continue to count toward `num_confirmations` in `confirm()`, so a request can execute even though the number of *currently live* members who approved it is below the configured threshold.

## Finding Description
In `multisig2/src/lib.rs`, `confirm()` decides whether to execute a request purely by counting entries in the `confirmations: LookupMap<RequestId, HashSet<String>>` set: [1](#0-0) 

There is no re-check that each entry in `confirmations` corresponds to an account/key that is still present in `self.members` at execution time.

When a member is removed via `MultiSigRequestAction::DeleteMember`, `delete_member()` only cleans up requests where `r.member == member` (i.e., requests *authored* by the removed member) — it does not touch `self.confirmations` for other requests that the removed member had previously *confirmed*: [2](#0-1) 

So, if member `A` confirms request `R` (authored by member `B`) while `A` is still a live member, and `A` is later removed from `self.members` via a separate `DeleteMember` request, `A`'s confirmation string remains stored under `confirmations[R]`. That stale confirmation still counts toward the `num_confirmations` quorum the next time `confirm(R)` is called, letting `R` execute with fewer *actually live* approving members than `num_confirmations` requires.

The identical pattern exists in the older `multisig/src/lib.rs` contract, where `DeleteKey` only removes requests whose `r.signer_pk == pk`, not the deleted key's confirmations recorded on other requests: [3](#0-2) [4](#0-3) 

The equality that should hold is:
```
confirmations_counted(R) == number of CURRENT live members who confirmed R
```
but in reality:
```
confirmations_counted(R) >= number of CURRENT live members who confirmed R
```
because stale entries from removed members are never pruned from other requests' confirmation sets.

## Impact Explanation
This directly matches the "Critical" impact category of "a multisig request executed below threshold." A transfer, `AddKey`/`AddMember`, `FunctionCall`, or any other multisig action can be executed with effectively fewer live approvers than `num_confirmations` mandates, because a removed member's earlier confirmation is silently retained and counted. This breaks the fundamental custody/authorization guarantee of the multisig: funds or privileged actions controlled by the multisig account can move or execute without the intended number of currently-authorized signers agreeing.

## Likelihood Explanation
No `owner`, redeploy, or external actor is required — the flaw is triggered purely through the multisig's own normal operations: (1) a member confirms a pending request, (2) that member is later removed via a standard `DeleteMember`/`DeleteKey` request (a routine membership-rotation action), and (3) a subsequent confirm from a live member completes the quorum using the stale confirmation. This can happen unintentionally during any legitimate member rotation while requests are pending, or be engineered deliberately by a member about to be removed who first "banks" a confirmation on a request they want to see execute later with insufficient live signers.

## Recommendation
When counting confirmations in `confirm()` (and in any view like `get_confirmations`), filter `confirmations` to only those entries that are still present in `self.members` (multisig2) or still correspond to an existing access key (multisig). Alternatively, when removing a member/key, iterate all `confirmations` entries (not just requests authored by that member) and strip that member's identifier from every confirmation set, decrementing/re-evaluating quorum status accordingly.

## Proof of Concept
1. Deploy `multisig2` with members `[A, B, C]` and `num_confirmations = 2`.
2. `B` calls `add_request(R)` where `R` is `Transfer { amount }` to some receiver (`R` starts with 0 confirmations).
3. `A` calls `confirm(R)` → `confirmations[R] = {A}` (1 < 2, not yet executed) — see `confirm()` at [1](#0-0) .
4. Members `B` and `C` create and confirm a `DeleteMember { member: A }` request (this only requires 2 live confirmations, satisfied by B and C) — `A` is removed from `self.members`, but `delete_member()` only removes requests where `r.member == A`; since `R.member == B`, `R` and its confirmations are untouched — see [5](#0-4) .
5. `C` calls `confirm(R)` → `confirmations[R].len() + 1 == 2 >= num_confirmations`, so `R` (the `Transfer`) executes, even though `A` is no longer a member and only `B` (author) and `C` are the actual live approvers with `A`'s stale confirmation making up the quorum.

This shows a multisig transfer executing while relying on a confirmation from an account that had already been removed from the member set, i.e., execution below the intended live-member threshold.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
