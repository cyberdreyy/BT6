### Title
External Initiator credentials satisfy `isUser` check in `PipelineRunsController.Create`, bypassing the "EIs not allowed" int-ID restriction - ([File: core/web/pipeline_runs_controller.go])

### Summary
The `POST /v2/jobs/:ID/runs` route is mounted with `auth.AuthenticateExternalInitiator` as one of its accepted auth methods, and that method sets `SessionUserKey` to a synthetic `&clsessions.User{Role: UserRoleRun}` in addition to `SessionExternalInitiatorKey`. `PipelineRunsController.Create` uses `auth.GetAuthenticatedUser(c)` to decide whether the caller is a "user" allowed to trigger jobs by int32 ID, so an EI credential holder passes this check despite the code comment explicitly stating "EIs not allowed."

### Finding Description
The route is registered in [1](#0-0) , using `auth.Authenticate` with methods `AuthenticateExternalInitiator`, `AuthenticateByToken`, `AuthenticateBySession`, and wrapped only in `auth.RequiresRunRole`. In `AuthenticateExternalInitiator`, after validating the EI access-key/secret, the code sets both `SessionExternalInitiatorKey` and `SessionUserKey` to a synthetic run-role user: [2](#0-1) . `RequiresRunRole` only checks `user.Role != UserRoleView`, so the synthetic run-role user passes: [3](#0-2) . Inside `Create`, the guard `isUser := auth.GetAuthenticatedUser(c)` merely checks presence of `SessionUserKey`, which is now true for EI-authenticated requests, allowing `prc.App.RunJobV2` to execute for int32 job IDs: [4](#0-3) . This directly contradicts the code's own comment "only users are allowed to run jobs using int IDs - EIs not allowed" at line 110.

### Impact Explanation
An external-initiator credential (a lower-privilege, narrowly-scoped credential intended only to trigger webhook-UUID job runs) can be used to trigger arbitrary jobs by integer ID via `RunJobV2`, which is the exact behavior the code comment says should be restricted to real users. This matches the "unauthorized job run" bounty impact class — a non-user credential holder gains job-execution capability equivalent to a run-role user without ever authenticating as one.

### Likelihood Explanation
Precondition is only possession of a valid EI access-key/secret pair (`X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret`), which is a lower-trust credential than a user session/API token by design (used for external initiators to trigger webhook jobs, not general job management). The exploit is trivially repeatable: any request to `POST /v2/jobs/<int32-id>/runs` with valid EI headers reaches `Create` and satisfies `isUser`.

### Recommendation
In `PipelineRunsController.Create`, explicitly reject requests authenticated via `SessionExternalInitiatorKey` (i.e., check `auth.GetAuthenticatedExternalInitiator(c)` and deny if present) instead of relying solely on the presence of `SessionUserKey`, since `AuthenticateExternalInitiator` populates both keys. Alternatively, do not set `SessionUserKey` for EI-authenticated requests at all, and instead have `RequiresRunRole`/callers check `GetAuthenticatedExternalInitiator` separately from `GetAuthenticatedUser` so the two identity types are never conflated.

### Proof of Concept
Go handler-level test plan:
1. Build a `gin.Context` with a request `POST /v2/jobs/123/runs`.
2. Manually mimic `AuthenticateExternalInitiator`'s effect: `c.Set(auth.SessionExternalInitiatorKey, &bridges.ExternalInitiator{...})` and `c.Set(auth.SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})`.
3. Provide a mock `chainlink.Application` (or mock `JobORM`/`PipelineORM`) with `RunJobV2` instrumented to record invocation.
4. Call `PipelineRunsController{App: mockApp}.Create(c)`.
5. Assert `RunJobV2` **was** invoked with `jobID == 123` under current code (demonstrating the bug) — the fix should make this assertion **fail** (i.e., `RunJobV2` NOT invoked, and response is `422 bad job ID` or `401`/`403`) after remediation.

func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
