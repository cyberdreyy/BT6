### Title
`LockupFactory::create` has no owner/foundation gate, allowing account-squatting of a victim's deterministic lockup address with attacker-chosen whitelist - ([File: lockup-factory/src/lib.rs])

### Summary
`LockupFactory::create` derives the lockup subaccount deterministically from `sha256(owner_account_id)` and deploys it via a `Promise` chain, but never checks that `env::predecessor_account_id()` is the `owner_account_id`, the `foundation_account_id`, or any other authorized caller. Any unprivileged account holding `MIN_ATTACHED_BALANCE` (3.5 NEAR) can call `create` first for a victim's `owner_account_id`, permanently occupying `hex::encode(sha256(victim)[..20]).<factory>` with a `LockupArgs.staking_pool_whitelist_account_id` of the attacker's choosing.

### Finding Description
The binding that should hold is: `staking_pool_whitelist_account_id` deployed at `lockup_account_id` == the whitelist the entitled sponsor (owner/foundation) would have chosen for `owner_account_id`. In `create` [1](#0-0) , the only guard is `assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE, ...)` [2](#0-1) ; there is no check tying `env::predecessor_account_id()` to `owner_account_id.as_ref()` or to `self.foundation_account_id`. The `whitelist_account_id` parameter is fully attacker-controlled and, when supplied, overrides the factory-configured default [3](#0-2) . The resulting `Promise::new(lockup_account_id).create_account().deploy_contract(CODE).transfer(...).function_call(b"new", LockupArgs{...})` [4](#0-3)  executes with the *factory contract* as predecessor for the `create_account` action (since the promise originates from the factory's own execution context), so NEAR's subaccount-creation rule (`predecessor == parent account`) is always satisfied regardless of who externally called `create`. `utils::assert_self` only guards the `on_lockup_create` callback [5](#0-4)  and does nothing to restrict who may invoke `create` itself.

Exploit flow: attacker calls `create(owner_account_id=victim, ..., whitelist_account_id=Some(attacker_whitelist))` with `attached_deposit == MIN_ATTACHED_BALANCE`, before the victim's legitimate sponsor (owner or foundation) ever calls `create`. The account `hex(sha256(victim)[..20]).<factory>` is created and deployed with `LockupArgs.staking_pool_whitelist_account_id = attacker_whitelist`, permanently binding that address to the attacker's chosen whitelist. Because the account name is deterministic and NEAR disallows re-creating an existing account, any subsequent legitimate `create` call for the same `owner_account_id` will have its `create_account()` action fail, triggering `on_lockup_create`'s failure branch which refunds the deposit to the legitimate caller [6](#0-5)  — so the legitimate lockup for that owner can never be deployed at the canonical address, and the victim is left as "owner" of a squatted lockup contract whose `staking_pool_whitelist_account_id` was chosen by the attacker rather than by the entitled sponsor.

### Impact Explanation
No `assert_owner`, `assert_called_by_foundation`, or predecessor check exists anywhere in `create`, so the account-naming binding is broken exactly as claimed: a lockup is deployed with parameters (`staking_pool_whitelist_account_id`) its rightful creator never chose. This matches the Critical category explicitly listed in scope: "an account whitelisted or a lockup deployed with parameters its rightful creator never chose." Once the victim eventually acts as owner of the squatted lockup and calls `select_staking_pool`, they are constrained to the attacker's whitelist contract, letting the attacker later add/point to an attacker-controlled staking pool for any future funds the victim routes there. The attack is repeatable against any `owner_account_id` that has not yet had `create` called for it, for a cost of only 3.5 NEAR per victim.

### Likelihood Explanation
Preconditions are minimal and fully attacker-controlled: no account must yet exist at the deterministic subaccount address, and the attacker needs only `MIN_ATTACHED_BALANCE` (3.5 NEAR) plus a self-deployed `attacker_whitelist` contract. `create` is a public, unauthenticated, `#[payable]` method with no allowlist of callers, making this trivially and cheaply exploitable/front-runnable against any known or predictable victim `owner_account_id` before the legitimate sponsor transacts.

### Recommendation
Restrict `create` so that `env::predecessor_account_id()` must equal `self.foundation_account_id` (or another explicitly authorized deployer role), rejecting calls from arbitrary accounts; alternatively, require the caller to equal `owner_account_id.as_ref()` when no foundation-authorized flow is used, so an attacker cannot squat an owner's deterministic lockup address with attacker-chosen `LockupArgs`.

### Proof of Concept
```rust
// lockup-factory/src/lib.rs tests module
#[test]
fn test_attacker_squats_victim_lockup_with_own_whitelist() {
    let mut context = VMContextBuilder::new()
        .current_account_id(account_factory())
        .predecessor_account_id(account_near())
        .finish();
    testing_env!(context.clone());

    let mut contract = LockupFactory::new(whitelist_account_id(), foundation_account_id());

    const LOCKUP_DURATION: u64 = 63036000000000000;
    let lockup_duration: WrappedTimestamp = LOCKUP_DURATION.into();

    // Attacker (unprivileged, not owner/foundation) calls create for victim's owner_account_id
    context.is_view = false;
    context.predecessor_account_id = String::from("attacker.near");
    context.attached_deposit = MIN_ATTACHED_BALANCE; // exactly minimum
    testing_env!(context.clone());
    contract.create(
        account_tokens_owner(), // victim owner_account_id
        lockup_duration,
        None,
        None,
        None,
        Some(custom_whitelist_account_id()), // attacker-chosen whitelist
    );

    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Successful(vec![]));
    contract.on_lockup_create(
        lockup_account(),
        MIN_ATTACHED_BALANCE.into(),
        String::from("attacker.near"),
    );

    // Binding check: deployed staking_pool_whitelist_account_id (custom_whitelist_account_id())
    // != canonical whitelist_account_id() set at LockupFactory::new.
    // (Verify by inspecting the LockupArgs bytes passed in the function_call, or by
    // deploying the real lockup wasm in a near-workspaces integration test and reading
    // its `staking_pool_whitelist_account_id` state after `new` executes.)
    assert_ne!(custom_whitelist_account_id().to_string(), whitelist_account_id().to_string());

    // Legitimate sponsor now attempts create() for the same owner_account_id and fails
    // because the account already exists; deposit is refunded, lockup is never deployed
    // with the sponsor's intended whitelist.
}
```
This demonstrates the identity failure: `deployed staking_pool_whitelist_account_id (attacker-chosen) != whitelist_account_id the entitled sponsor would have selected`, with no existing guard (`assert_self`, `assert!` on deposit only) preventing it.
