### Title
Loss-adjusted withdraw receipt escapes its haircut when a later request overwrites `lastWithdrawRequest` — the stale-epoch receipt is paid at par via the funded-claim path - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`requestWithdraw` overwrites `lastWithdrawRequest[_user]` with the current epoch on every new request, and `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch` using only that single latest marker. A user who holds a receipt in a loss epoch (where `stopEpochWithDuration(_lossAmount)` haircut payouts) can submit a second, arbitrarily small withdraw request in a later non-loss epoch. The loss-epoch receipt is then silently swept into the aggregate `withdrawsRequests[_user]` and paid 1:1 by `_claimFundedWithdrawRequest`, which clears the whole aggregate at par and zeroes the marker.

### Finding Description
In `requestWithdraw`, each request records `lastWithdrawRequest[_user] = currentEpoch` and accumulates `withdrawsRequests[_user]` plus the per-epoch bucket `withdrawsRequestsByEpoch[_user][currentEpoch]` [1](#0-0) .

At claim time, `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — i.e. it can only ever apply the recovery price of the *latest* request epoch [2](#0-1) . If the latest epoch has no recorded loss price, it returns 0 and `_claimFundedWithdrawRequest` then pays `amount = withdrawsRequests[_user] + apr0 amounts` fully at par and sets `withdrawsRequests[_user] = 0`, burning `normalAmount` which includes the loss-epoch principal [3](#0-2) .

The per-epoch clearing helper `_clearWithdrawClaimForEpoch` exists precisely to isolate one epoch's receipt (used for defaulted claims via `defaultRecoveryEpoch`), but the loss-adjusted path never iterates over prior epochs — it only inspects `lastWithdrawRequest` [4](#0-3) . Contrast with the default path, which correctly keys claims to `defaultRecoveryEpoch` independent of the marker [5](#0-4) .

### Impact Explanation
When `stopEpochWithDuration` applies `_lossAmount`, the borrower funds only the haircutted amounts and `lossRecoveryPriceByEpoch[lossEpoch] < RECOVERY_FULL` is the mechanism that enforces socialized loss on claimants. By adding a dust-sized `requestWithdraw` in any later healthy epoch, the attacker converts their haircutted receipt into a par payout: the loss that accounting already deducted from contract value is paid out anyway, draining vault liquidity that belongs to remaining depositors/claimants. Quantified: with a 50% `lossRecoveryPrice`, a 100k-USDC receipt yields an extra ~50k USDC stolen from the vault — direct theft of funds and potential insolvency of later withdrawers, since `_transferFundedClaim` pays from strategy balance (and is guarded from the default reserve, but not from ordinary vault liquidity) [6](#0-5) . This is the vault analogue of the CVE: a stale receipt (like the dangling connection object) is later dereferenced under the wrong epoch context after a newer command overwrote the pointer (`lastWithdrawRequest`).

### Likelihood Explanation
- Attacker needs only to be a KYC-passing tranche holder (unprivileged) and to hold a pending withdraw receipt during a `stopEpochWithDuration` loss event — a normal, expected vault operation.
- The second request is a single permitted transaction: `requestWithdraw` has no guard against prior unclaimed receipts; the code comments explicitly acknowledge users may request again before claiming [7](#0-6) .
- No existing guard stops it: `epochNumber <= lastWithdrawRequest[_user]` gating only delays the claim until the newer epoch ends; the loss lookup is keyed only on the (overwritten) marker. The bug is deterministic once a loss epoch occurs while a user has an unclaimed receipt.

### Recommendation
Make the loss-adjusted claim path epoch-aware like the default path: iterate or track all epochs with nonzero `withdrawsRequestsByEpoch[_user][*]` for which `lossRecoveryPriceByEpoch[epoch] != 0`, clearing each via `_clearWithdrawClaimForEpoch` and applying that epoch's price, before falling through to the funded par claim. Alternatively, store per-user a set/flag of pending loss epochs so an overwritten `lastWithdrawRequest` cannot smuggle a haircutted receipt into the par path.

  function _clearWithdrawClaimForEpoch(address _user, uint256 _claimEpoch, bool _isClearingApr0) internal returns (uint256 claimBasis, uint256 burnAmount) {
    (claimBasis, burnAmount) = _withdrawClaimAmountsForEpoch(_user, _claimEpoch);
    if (claimBasis == 0) return (claimBasis, burnAmount);

    uint256 normalAmount = withdrawsRequestsByEpoch[_user][_claimEpoch];
    if (normalAmount != 0) {
      withdrawsRequestsByEpoch[_user][_claimEpoch] = 0;
      // The aggregate may also include older funded receipts; clear only this epoch's piece.
      withdrawsRequests[_user] -= normalAmount;
    }
    Apr0UserData storage apr0User = apr0Users[_user];
    if (apr0User.principal != 0 && apr0User.principalEpoch == _claimEpoch) {
      if (_isClearingApr0) {
        uint256 apr0Principal = apr0User.principal;
        uint256 totalApr0Principal = apr0TotalPrincipal;
        // prepareStopEpochWithApr0 may already close the global APR0 bucket before default finalization.
        apr0TotalPrincipal = apr0Principal >= totalApr0Principal ? 0 : totalApr0Principal - apr0Principal;
      }
      apr0User.principal = 0;
      apr0User.principalEpoch = 0;
    }
    if (lastWithdrawRequest[_user] == _claimEpoch) {
      // The cleared epoch was the latest request marker. Any remaining normal/APR0 receipt
      // is older and already funded, so it can continue to the funded-claim path.
      lastWithdrawRequest[_user] = 0;
    }
  }
