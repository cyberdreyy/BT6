### Title
Single opted-out recipient can permanently block commission/stake distribution to *all* other shareholders in `staking_contract::distribute_internal` and `vesting::distribute` - ([File: aptos-move/framework/aptos-framework/sources/staking_contract.move])

### Summary
Both `staking_contract::distribute_internal` and `vesting::distribute` pay out every shareholder/beneficiary of a shared distribution pool in a single atomic loop, using `aptos_account::deposit_coins` for each recipient. `aptos_account::deposit_coins` aborts if the recipient has disabled direct coin transfers (`DirectTransferConfig.allow_arbitrary_coin_transfers = false`) and is not already registered for `AptosCoin`. Since Move transactions are atomic, one non-cooperative or malicious recipient in the pool can cause the entire distribution transaction to abort every time it's called, freezing payouts to *every other* staker/shareholder in the same pool — the functional analog of the "insufficient gas stipend blocks a whole payout" issue from the external report, except here the "gas griefing" primitive is a boolean opt-out flag rather than gas cost.

### Finding Description
`staking_contract::distribute_internal` iterates over `distribution_pool.shareholders()` and, for each one, redeems shares and calls `aptos_account::deposit_coins`: [1](#0-0) 

`aptos_account::deposit_coins` will `create_account`/auto-register a *new* address, but for an *existing* account that is not registered for the coin and has disabled direct transfers, it asserts `can_receive_direct_coin_transfers(to)` and aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`: [2](#0-1) 

Any account can flip that flag off for itself at any time via the public `DirectTransferConfig` API (`set_allow_direct_coin_transfers`), which is unprivileged and reachable at will.

The same atomic batch-loop-then-abort pattern exists in `vesting::distribute`, which pays every shareholder's beneficiary in one loop: [3](#0-2) 

Because a Move transaction either commits fully or reverts fully, if `deposit_coins` aborts for *any single* recipient inside these loops, none of the share redemptions or other recipients' transfers from that call persist — even though `distribute`/`request_commission`/`distribute_internal` are `public entry` functions callable by anyone, so any user could keep re-triggering the failing distribution.

Note: `vesting::set_beneficiary` does defensively call `assert_account_is_registered_for_apt(new_beneficiary)` when an admin explicitly sets a beneficiary via that function: [4](#0-3) 
but this check only fires at beneficiary-set time; a beneficiary/shareholder can still register and *later* call `set_allow_direct_coin_transfers(false)` (or simply not maintain registration) to re-arm the block at any time before the next `distribute()` call. It also does not protect `staking_contract::set_beneficiary_for_operator`, which performs no registration check at all: [5](#0-4) 
nor does it protect the original staker/other pre-existing shareholders that were never routed through `set_beneficiary`.

### Impact Explanation
This can permanently strand rewards and stake-withdrawal proceeds owed to *every other participant* in a shared `staking_contract` or `vesting` pool, because the payout mechanism has no way to skip or isolate a single failing recipient — it is all-or-nothing per call. A staker sharing a `staking_contract` with an operator (or an operator's chosen beneficiary), or shareholders in a shared vesting contract, could see their legitimate stake/commission become non-withdrawable indefinitely if one co-participant (accidentally or via griefing/extortion) disables direct-transfer acceptance. This matches the "Permanent lock or non-recoverable loss of claim rights in ... commission, beneficiary, or vesting flows" and "Operator commission ... corruption that ... traps value" impact categories.

### Likelihood Explanation
Likelihood is limited by the fact that the affected account must deliberately (or via some automation) disable direct-transfer acceptance — this is not a spontaneous or economically incentivized default state, and any account can simply re-enable transfers to unblock the pool. It requires either malicious intent from a co-participant (e.g., an operator's beneficiary extorting the staker, or a disgruntled shareholder blocking a shared vesting pool) or accidental misconfiguration. I was not able to fully verify within the available tool budget whether any alternate code path (e.g., a "skip failed recipient" fallback, or a way to remove a stuck shareholder from `distribution_pool`) exists elsewhere in `staking_contract.move` or `pool_u64.move` that would mitigate this; that would need further review before treating this as conclusively unmitigated.

### Recommendation
- Wrap the per-recipient `aptos_account::deposit_coins` call in `distribute_internal`/`distribute` in a way that isolates failures per-recipient (e.g., use `coin::is_account_registered` / `can_receive_direct_coin_transfers` checks first, and if the recipient can't accept the transfer, redirect their share to an escrow/claimable balance instead of aborting the whole batch).
- Alternatively, provide a per-recipient "pull" style claim function instead of a "push" batch distribution, so one recipient's opted-out state cannot block others.
- Apply `assert_account_is_registered_for_apt`-style checks consistently to `staking_contract::set_beneficiary_for_operator` and `delegation_pool::set_beneficiary_for_operator` as already done for `vesting::set_beneficiary`, and re-validate at distribution time rather than only at beneficiary-set time.

### Proof of Concept
1. Staker A creates a `staking_contract` with operator B, `create_staking_contract`.
2. Operator B sets a beneficiary address C via `set_beneficiary_for_operator` (no registration check performed). [5](#0-4) 
3. C calls `aptos_account::set_allow_direct_coin_transfers(false)` (public, unprivileged, standard framework API) after registering, or simply never registers `CoinStore<AptosCoin>` and disables direct transfers.
4. Time passes, rewards accrue, and stake becomes unlockable/inactive for both A and the operator's commission share.
5. Anyone calls `staking_contract::distribute(staker_address, operator_address)`. The loop reaches the redemption for beneficiary C, calls `aptos_account::deposit_coins(C, ...)`, which hits `can_receive_direct_coin_transfers(C) == false` and aborts. [6](#0-5) 
6. The entire `distribute` transaction reverts — staker A's own unlocked stake, which was also queued in the same `distribution_pool` batch, is not paid out either, and this repeats on every subsequent call to `distribute` until C changes their configuration, which C (a griefing operator/beneficiary) has no incentive to do.

        operator: &signer, new_beneficiary: address

        assert!(
            features::operator_beneficiary_change_enabled(),
            std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
        );
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator =
                new_beneficiary;
        } else {
            move_to(
                operator,
                BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary }
            );
        };

        emit(
            SetBeneficiaryForOperator {
                operator: operator_addr,
                old_beneficiary,
                new_beneficiary
            }
        );
    }

    /// Distribute any withdrawable stake from the stake pool.
    public entry fun distribute(contract_address: address) acquires VestingContract {
        assert_active_vesting_contract(contract_address);

        let vesting_contract = borrow_global_mut<VestingContract>(contract_address);
        let coins = withdraw_stake(vesting_contract, contract_address);
        let total_distribution_amount = coin::value(&coins);
        if (total_distribution_amount == 0) {
            coin::destroy_zero(coins);
            return
        };

        // Distribute coins to all shareholders in the vesting contract.
        let grant_pool = &vesting_contract.grant_pool;
        let shareholders = &grant_pool.shareholders();
        shareholders.for_each_ref(|shareholder| {
            let shareholder = *shareholder;
            let shares = pool_u64::shares(grant_pool, shareholder);
            let amount = pool_u64::shares_to_amount_with_total_coins(grant_pool, shares, total_distribution_amount);
            let share_of_coins = coin::extract(&mut coins, amount);
            let recipient_address = get_beneficiary(vesting_contract, shareholder);
            aptos_account::deposit_coins(recipient_address, share_of_coins);
        });

        // Send any remaining "dust" (leftover due to rounding error) to the withdrawal address.
        if (coin::value(&coins) > 0) {
            aptos_account::deposit_coins(vesting_contract.withdrawal_address, coins);
        } else {
            coin::destroy_zero(coins);
        };
