The `account_subscribe` and `program_subscribe` PubSub RPC handlers accept `min_context_slot` in their config but never enforce it, unlike the equivalent HTTP RPC methods (`getAccountInfo`, `getProgramAccounts`) which use it to gate on a `RpcContextConfig` and return `MinContextSlotNotReached` if the bank hasn't caught up.

### Title
PubSub `accountSubscribe`/`programSubscribe` accept `minContextSlot` but never enforce it, silently returning notifications from stale bank state - (File: rpc/src/rpc_pubsub.rs)

### Summary
`RpcAccountInfoConfig`/`RpcProgramAccountsConfig` expose a `min_context_slot` field that is the documented mechanism by which an unprivileged RPC caller asserts a freshness floor for the data it receives [1](#0-0) . The HTTP RPC handlers for `getAccountInfo`/`getMultipleAccounts`/`getProgramAccounts` honor this by threading `min_context_slot` into `RpcContextConfig` and calling `get_bank_with_config`, which errors with `MinContextSlotNotReached` if the highest available bank hasn't reached that slot [2](#0-1) . The PubSub implementation of the same operations discards the parameter instead: `account_subscribe` explicitly comments it out as `min_context_slot: _, // ignored` [3](#0-2) , and `program_subscribe` never destructures or reads `min_context_slot` from `config.account_config` at all, only consuming `filters`, `encoding`, `data_slice`, `commitment`, and `with_context` [4](#0-3) .

### Finding Description
This is structurally the same bug class as the WormholeFacet report: the API surface (config struct) accepts and documents a parameter that implies a guarantee (asset transfer / minimum slot freshness), but the code path that actually performs the operation drops it silently instead of enforcing it or rejecting the request. A caller who explicitly sets `minContextSlot` on `accountSubscribe`/`programSubscribe` — precisely to avoid consuming account/program state from a node lagging behind a known slot — gets no such guarantee: the subscription is created and delivers notifications based on whatever bank/slot the node is currently processing, with no check against `min_context_slot` and no error returned to the caller to signal that the guarantee cannot be honored.

### Impact Explanation
This falls under "wrong-slot/fork/account data returned" from a query. A caller relying on `minContextSlot` for correctness (e.g., waiting for a specific slot before trusting account state) can silently receive notifications reflecting stale, pre-`minContextSlot` account or program data through `accountNotification`/`programNotification`, with no indication that the freshness constraint was unmet. This is a correctness/misreporting issue for JSON-RPC/pubsub consumers of an unprivileged, publicly reachable API.

### Likelihood Explanation
Any client can trigger this with a single unprivileged `accountSubscribe` or `programSubscribe` call including `minContextSlot`, so the likelihood of hitting the divergent behavior is high whenever a client actually depends on that parameter (mirroring how the HTTP counterparts are used in practice, per the tests referencing `min_context_slot` throughout `rpc/src/rpc.rs`).

### Recommendation
In `RpcSolPubSubImpl::account_subscribe` and `program_subscribe`, read and enforce `min_context_slot` the same way `get_bank_with_config` does for the HTTP handlers — either reject the subscribe call synchronously with `MinContextSlotNotReached` when the current highest bank hasn't reached the requested slot, or gate the first notification/subscription creation on it. At minimum, remove the misleading acceptance of the field if it will never be honored, to avoid an API contract mismatch between the HTTP and PubSub surfaces.

### Proof of Concept
1. Call `accountSubscribe(pubkey, {"minContextSlot": <future_slot>})` against a node whose current bank slot is behind `<future_slot>`.
2. Observe the subscription succeeds immediately and begins emitting `accountNotification`s reflecting the current (pre-`future_slot`) account state, in contrast to calling `getAccountInfo(pubkey, {"minContextSlot": <future_slot>})`, which returns a `-32016`/`MinContextSlotNotReached` JSON-RPC error until the bank catches up [5](#0-4) .
