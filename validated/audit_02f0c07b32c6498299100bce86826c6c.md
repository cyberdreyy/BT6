### Title
External Initiator credential can trigger job runs for arbitrary job IDs, not just its provisioned webhook job - ([File: core/web/auth/auth.go])

### Summary
`AuthenticateExternalInitiator` unconditionally sets the request's `SessionUserKey` to a synthetic `User{Role: UserRoleRun}`, and the only route that mixes EI auth with `RequiresRunRole` is `POST /v2/jobs/:ID/runs`. That handler's "only users, not EIs" guard is broken because it checks `GetAuthenticatedUser`, which is also true for EI-authenticated requests, letting any valid EI credential trigger a run on any integer job ID.

### Finding Description
`auth.AuthenticateExternalInitiator` authenticates the caller against `bridges.ExternalInitiator` credentials, then does: [1](#0-0) 
It sets `SessionUserKey` to a role-`UserRoleRun` user regardless of which specific job/webhook the EI was provisioned for, and there is no per-EI job binding recorded anywhere else in the request context (`GetAuthenticatedExternalInitiator` is set but never consulted again in the codebase outside `auth.go`).

The only router group combining `AuthenticateExternalInitiator` with a run-role-gated route is: [2](#0-1) 
i.e. `GET /v2/ping` and `POST /v2/jobs/:ID/runs`. All other `RequiresRunRole` routes (`/replay_from_block/:number`, `/find_lca`, `/lp_skip_to_block`, `/pipeline/runs`, `/jobs/:ID/runs` GET, `/execute_capability`) live in the separate `authv2` group that is authenticated only by session/API-token, so EI tokens cannot reach those — the over-grant is therefore confined to `POST /v2/jobs/:ID/runs`.

In `PipelineRunsController.Create`, the code comment states EIs should not be able to trigger int-ID job runs, and attempts to gate that with `isUser`: [3](#0-2) 
However, `isUser := auth.GetAuthenticatedUser(c)` returns `true` for EI-authenticated requests too, because `AuthenticateExternalInitiator` populates the exact same `SessionUserKey` used by real user sessions. There is no check that ties the authenticated `ExternalInitiator` to the specific `jobID` in the URL param, and no filtering by `job.Webhook` type for int IDs. As a result, any request bearing valid EI headers (`X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret`) can call `POST /v2/jobs/<any-int-id>/runs` and successfully invoke `prc.App.RunJobV2(ctx, jobID, nil)` for a job completely unrelated to the one the EI credential was created for.

### Impact Explanation
An external-initiator credential — typically provisioned narrowly to trigger a single specific webhook/job — can be used to trigger pipeline runs on *any* job addressable by integer ID on the node (e.g., another team's cron, flux monitor, direct-request, or VRF-adjacent job configured with a webhook-style run trigger). This is an authorization/role-scoping bypass: unauthorized triggering of job execution for jobs the credential was never meant to access, potentially causing unwanted on-chain transactions, resource exhaustion, or interference with other jobs' state — matching Chainlink's "unauthorized job run" bounty impact class.

### Likelihood Explanation
Minimal precondition: possession of any single valid, currently-enabled external initiator credential (access key + secret) issued for an unrelated job. No admin/session/user token needed. The call is a straightforward, repeatable, unauthenticated-relative-to-target-job HTTP POST once EI credentials are known, requiring only guessing/knowing an integer job ID (job IDs are sequential and enumerable via `GET /v2/jobs` if the attacker also has any run/view-level access, or via brute force of small integers).

### Recommendation
- In `PipelineRunsController.Create`, explicitly reject EI-authenticated callers instead of relying on `GetAuthenticatedUser`; use `auth.GetAuthenticatedExternalInitiator(c)` to detect EI sessions and return `403`/`422` for them, or
- Bind each `ExternalInitiator` to its associated job (if not already tracked in the DB) and verify `ei.JobID == jobID` before invoking `RunJobV2` when the caller is EI-authenticated.
- More generally, stop overloading `SessionUserKey` for EI auth; introduce a distinct context flag/type so downstream handlers can differentiate EI vs. real user role grants precisely instead of relying on role level alone.

### Proof of Concept
Handler-level integration test in `core/web/pipeline_runs_controller_test.go`:
1. Create two jobs, JobA (int ID) and JobB (int ID), plus one `ExternalInitiator` provisioned/intended only for JobA's webhook trigger.
2. Send `POST /v2/jobs/{JobB.ID}/runs` with headers `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` set to the EI's credentials (not JobA's UUID, but JobB's integer ID).
3. Assert response is `200 OK` with a `pipelineRun` resource for JobB, proving the EI credential triggered an unrelated job.
4. Add regression assertion: after the fix, the same request should return `403 Forbidden`/`422` because the EI is not authorized for JobB.
