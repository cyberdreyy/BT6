### Title
Silent zero-price fallback on oracle fetch failure in borrow flow may bypass withdrawal rate-limit accounting - (File: programs/marginfi/src/instructions/marginfi_account/borrow.rs)

### Summary
In the `lending_pool_borrow`/borrow flow, the oracle price used to update the outflow rate-limiter is fetched with `.ok()`, silently discarding any error (stale oracle, wrong oracle accounts, etc.) and substituting `I80F48::ZERO` as the price for that operation, mirroring the ZecWallet bug class where a failed price fetch degrades to zero rather than halting the operation.

### Finding Description
After the account health check passes, the code re-fetches the oracle price purely to record the USD value of the outflow for rate-limiting purposes: [1](#0-0) 

Here, `fetch_unbiased_price_for_bank_with_cache(...).ok()` converts any error from the oracle lookup into `None`, and the subsequent `.unwrap_or(I80F48::ZERO)` substitutes a hardcoded zero price when the fetch fails, then this `rate_limit_price` is passed into `record_withdrawal_outflow`. This is structurally the same failure pattern described in the report: a price source that can fail (staleness, wrong oracle accounts, wrong number of oracle accounts, etc., all of which are `MarginfiResult` errors surfaced by `OraclePriceFeedAdapter::try_from_bank`/`load_oracle_context_with_max_age`, see [2](#0-1) ) is converted into a zero value that is fed into downstream financial accounting rather than causing the operation to fail safely.

Unlike the health-check price path — which does reject stale/invalid oracle data via `check_account_init_health` before this block executes — this specific rate-limiter price fetch does not gate the transaction on success; it only affects what value gets *recorded* against the rate limiter. If an attacker can cause the oracle lookup at this second call site to fail (e.g., by presenting oracle accounts that fail `check_primary_oracle_key`/`WrongOracleAccountKeys`, or by timing a borrow when the oracle is stale relative to `oracle_max_age` while the health check portion still passes for other reasons, or through any other error path enumerated in `load_oracle_context_with_max_age`), the withdrawal outflow will be recorded as $0 of value for rate-limiting purposes, even though real value is being borrowed out of the bank.

### Impact Explanation
If `record_withdrawal_outflow`'s purpose is to cap the USD-denominated outflow rate from a bank over a rolling window (a common anti-drain / anti-bank-run safety control), silently recording $0 for a borrow whose oracle price fetch failed would let that borrow amount evade the rate limiter entirely. Repeated exploitation of this path could let an attacker drain a bank's liquidity faster than the rate limiter is designed to allow, defeating a safety control with direct financial effect (bank insolvency/liquidity risk).

### Likelihood Explanation
Likelihood depends on how easy it is to trigger an oracle fetch error at this specific call site without also failing the earlier health check (which uses a different price-fetch path via `check_account_init_health` and remaining_accounts). I was not able to fully confirm within the available tool budget whether the same remaining_accounts/oracle data is reused for both calls (which would make it hard to fail one while passing the other) or whether `record_withdrawal_outflow` actually implements a hard security-critical rate limit versus a soft telemetry counter. This uncertainty should be resolved by reviewing `record_withdrawal_outflow`'s implementation in `programs/marginfi/src/utils/general.rs` and the semantics/consequences of exceeding or evading the outflow limit.

### Recommendation
- Do not silently coerce oracle-fetch failures to `I80F48::ZERO` for values used in security-relevant accounting (rate limiting, outflow tracking, etc.). Either fail the transaction, or use the last-known-good cached price (`bank.cache.last_oracle_price`) with an explicit staleness/validity check, consistent with how `check_account_init_health` handles this data.
- Audit all other `.ok()` / `.unwrap_or(I80F48::ZERO)` patterns around oracle price fetches (e.g., `fetch_asset_price_for_bank_low_bias`, `fetch_unbiased_price_for_bank`) to ensure none of them can be used to zero out values that feed into limits, caps, or liquidation math.
- Add regression tests that intentionally fail the second oracle fetch (post-health-check) while keeping the first fetch valid, and assert the rate limiter still accounts for the true value of the operation.

### Proof of Concept
Not independently verified — this requires confirming (1) that the remaining_accounts/oracle data consumed by `check_account_init_health` differs enough from the data consumed by `fetch_unbiased_price_for_bank_with_cache` that one can fail while the other succeeds, and (2) the concrete effect of `record_withdrawal_outflow` receiving a `$0` price, both of which need direct inspection of `programs/marginfi/src/utils/general.rs::record_withdrawal_outflow` that I could not complete before exhausting available tool calls.
