## Title
Blockstore transaction-status lookups silently swallow protobuf-decode errors and report "not found" instead of an error - (File: `ledger/src/blockstore.rs`)

### Summary
`Blockstore::get_transaction_status_with_counter` (used by the public `get_transaction_status`, `get_rooted_transaction_status`, and ultimately by RPC handlers such as `get_signature_statuses`/`get_transaction`) discards the error when converting a stored protobuf `TransactionStatusMeta` back into the in-memory type. If that conversion fails, the function treats the transaction as if it were never found, instead of surfacing the decode failure. This mirrors the class of bug in the Sherlock report: a caught/ignored internal error causes the caller to silently fall back to a "nothing happened" state rather than reverting/erroring, so the consumer of the result makes decisions based on incorrect information.

### Finding Description
`read_transaction_status` and `get_transaction_status_with_counter` both call `.and_then(|meta| meta.try_into().ok())`, discarding any `TryFrom` error: [1](#0-0) [2](#0-1) 

The `TryFrom<generated::TransactionStatusMeta> for TransactionStatusMeta` conversion can genuinely fail — for example, when the stored `err` field fails to deserialize with `wincode::deserialize`, it returns a `DecodeError`: [3](#0-2) 

When this happens inside `get_transaction_status_with_counter`, the loop still matches on the correct signature and slot (the row genuinely exists in `transaction_status_cf`), but because `try_into().ok()` swallows the error, `status` becomes `None` and the function returns `Ok((None, counter))` — functionally identical to "signature never found," even though a status row does exist for that signature/slot: [4](#0-3) 

This propagates through `get_transaction_status` / `get_rooted_transaction_status`: [5](#0-4) 

and further into `get_transaction_with_status`, `map_transactions_to_statuses` (used when building full confirmed blocks), and the RPC-facing `get_transaction`/`get_signature_statuses` code paths in `rpc/src/rpc.rs`, which rely on the blockstore call returning `None` as a legitimate "not found" signal: [6](#0-5) [7](#0-6) 

Just as the Sherlock `pullReward` catch block swallowed the revert reason and let `_stake` continue with a zeroed reward state instead of failing the whole operation, here a genuine decode error is swallowed and the caller (RPC) continues with a "not found" state instead of surfacing an internal error to the operator/caller.

### Impact Explanation
An unprivileged RPC caller querying `getSignatureStatuses`/`getTransaction` for a signature whose stored metadata fails to decode will receive a "not found"/`null` response instead of an error, i.e., wrong data is returned for a read query. This can mislead wallets/clients into believing a transaction was never processed (potential double-submission) or into missing finality/confirmation status for a transaction that did in fact execute — this falls under the accepted "wrong-slot/fork/account data returned" class since the validator returns an incorrect state for legitimately-stored ledger data due to an internally-swallowed error rather than propagating it as an RPC error.

### Likelihood Explanation
This requires an actual protobuf/wincode decode failure of a stored `TransactionStatusMeta` row, which is not triggerable per-request by an unprivileged caller directly; it depends on data corruption or schema-incompatible historical data. It is a genuine code-level defect (swallowed `Result` in the read path) rather than a directly attacker-controlled trigger, so likelihood is low-to-moderate and mostly latent/defensive-programming in nature.

### Recommendation
Do not use `.ok()` to discard `TryFrom` errors in `read_transaction_status` / `get_transaction_status_with_counter`. Propagate the decode error via the `Result` return type (e.g., `Result<(Option<(Slot, TransactionStatusMeta)>, u64)>`) so RPC layers can distinguish "row not found" from "row found but failed to decode," and surface the latter as an internal error rather than silently reporting "not found."

### Proof of Concept
Not directly exploitable by an external caller without first corrupting/mismatching the stored protobuf `TransactionStatusMeta` bytes for a given `(signature, slot)` key in `transaction_status_cf` (e.g., via a schema migration edge case or ledger corruption). Once such a row exists, any call to `Blockstore::get_transaction_status`, `get_rooted_transaction_status`, or the RPC `getTransaction`/`getSignatureStatuses` endpoints for that signature returns `None`/"not found" instead of an error, as traced through [8](#0-7)  and [9](#0-8) .

    // Returns a transaction status, as well as a loop counter for unit testing
    fn get_transaction_status_with_counter(
        &self,
        signature: Signature,
        confirmed_unrooted_slots: &HashSet<Slot>,
    ) -> Result<(Option<(Slot, TransactionStatusMeta)>, u64)> {
        let mut counter = 0;
        let (lock, _) = self.ensure_lowest_cleanup_slot();
        let first_available_block = self.get_first_available_block()?;

        let iterator = self.transaction_status_cf.iter(IteratorMode::From(
            (signature, first_available_block),
            IteratorDirection::Forward,
        ))?;

        for ((sig, slot), _data) in iterator {
            counter += 1;
            if sig != signature {
                break;
            }
            if !self.is_root(slot) && !confirmed_unrooted_slots.contains(&slot) {
                continue;
            }
            let status = self
                .transaction_status_cf
                .get_protobuf((signature, slot))?
                .and_then(|status| status.try_into().ok())
                .map(|status| (slot, status));
            return Ok((status, counter));
        }

        drop(lock);
        Ok((None, counter))
    }
