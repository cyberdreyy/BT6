### Title
Blacklisted lender cannot claim funded withdraw receipts and receipt tokens are non-transferable, permanently freezing underlying in the vault - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
Withdraw and instant-withdraw claims in `IdleCreditVault` pay underlying tokens to the stored `_user` address, which is bound to the requester, and the strategy-token receipt minted in `requestWithdraw`/`requestInstantWithdraw` cannot be transferred (`_transfer` reverts unless `msg.sender == idleCDO`). If a lender's address is later blacklisted by the underlying ERC20 (e.g., USDC-style blacklist), every claim path reverts on `safeTransfer(_user, ...)`, and there is no way to redirect the payout or move the receipt to a clean address. The funded underlyings remain locked in the vault indefinitely.

### Finding Description
- `requestWithdraw` mints the receipt to `_user` and records `withdrawsRequests[_user]` / `withdrawsRequestsByEpoch[_user][epoch]` keyed to that address (IdleCreditVault.sol:271-295).
- `claimWithdrawRequest` and `claimInstantWithdrawRequest` always call `_transferFundedClaim(_user, amount)` / `_transferDefaultRecovery(_user, amount)`, which do `underlyingToken.safeTransfer(_user, _amount)` (IdleCreditVault.sol:301-314, 380-393, 897-917). There is no `_to` parameter.
- The receipt is deliberately address-bound: `_transfer` reverts for anyone other than `idleCDO`, and `setCanTransfer` can only clear a legacy flag, never enable transfers (IdleCreditVault.sol:937-951). Tests explicitly assert receipt transfers revert (`testReceiptTransfersRemainDisabledAfterDefault`).
- `DefaultDistributor.claim(address _to)` exists post-default, but defaulted-epoch and post-default claims inside the vault (`_claimPostDefaultWithdrawRequest`, `_claimDefaultedWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest`) still pay to `_user` (IdleCreditVault.sol:760-785, 841-856).

So a user who deposited tranche tokens, burned them into a receipt, and whose address is subsequently blacklisted by the underlying token (sanctions, compliance freeze) has every claim revert, cannot delegate the claim to another address, and cannot sell/transfer the receipt. The funded underlyings sit in `IdleCreditVault` forever (barring discretionary owner `transferToken` rescue).

### Impact Explanation
Permanent freezing of the user's claim. The vault has already funded the receipt (`pendingWithdraws`/`pendingInstantWithdraws` backed by collected underlyings), so the tokens exist and are earmarked, yet unreachable by the legitimate owner. Loss equals the full claim amount (`claimBasis * recoveryPrice` or funded amount at par). Unlike the fixed-receiver analog, here the receiver equals the requester, but the same invariant breaks: a funded claim has no alternative payout path when the payout address can no longer receive the token.

### Likelihood Explanation
Requires the lender's address to be blacklisted by the underlying token's admin after the request is created — an external, low-frequency event. For KYC'd institutional lenders (the intended users, gated by `isWalletAllowed`/Keyring) this is plausible exactly because they interact with regulated tokens like USDC. It affects any phase with claimable receipts: funded normal epoch, loss-adjusted, defaulted, and post-default claims.

### Recommendation
Allow the payout destination to differ from the receipt holder: add a `claimWithdrawRequest(address _user, address _to)` variant (callable only by `idleCDO` on behalf of the owner) or a user-callable `setClaimReceiver`/`claimTo` that burns the `_user` receipt but transfers underlyings to a chosen `_to`. Alternatively, add a governance-approved claim re-routing for addresses demonstrably frozen by the token contract.

### Proof of Concept
Fork test sketch (Foundry, against an existing `IdleCreditVault` deployment using USDC-like underlying):

```solidity
// test/foundry/IdleCreditVaultBlacklist.t.sol
function testBlacklistedUserCannotClaimFundedReceipt() external {
    uint256 amountWei = 10000 * ONE_SCALE;
    address user = makeAddr("user");

    // running epoch: user deposits and requests withdraw
    _depositWithUser(user, amountWei, true);
    vm.prank(user);
    uint256 claimAmount = cdoEpoch.requestWithdraw(0, address(AAtranche));

    // epoch stops normally; borrower funds the pending receipts
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

    // external event: underlying token admin blacklists `user`
    // (on a mock/blacklistable underlying or via USDC admin prank on fork)
    _blacklistUnderlying(user);

    // receipt cannot be transferred to a clean address
    vm.prank(user);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    IERC20Detailed(address(strategy)).transfer(makeAddr("alt"), claimAmount);

    // every claim path reverts on safeTransfer to the blacklisted user
    vm.prank(user);
    vm.expectRevert(); // token blacklist revert
    cdoEpoch.claimWithdrawRequest();

    // funded underlyings remain locked in the vault
    assertGt(underlying.balanceOf(address(strategy)), 0);
    assertEq(strategy.withdrawsRequests(user), claimAmount);
}
```

Same flow applies to `claimInstantWithdrawRequest`, `_claimDefaultedWithdrawRequest`, and `_claimPostDefaultWithdrawRequest`, since all terminate in `safeTransfer(_user, ...)` with no alternative recipient.
