Enough context confirmed. I have verified the core mechanism in `multisig/src/lib.rs`.### Title
Stale confirmations from deleted keys still count toward `num_confirmations`, allowing execution below live-signer quorum - (File: multisig/src/lib.rs)

### Summary
`MultiSigContract::confirm` and `execute_request` count confirmations purely by `HashSet<PublicKey>.len()` without ever verifying the signing keys are still valid access keys on the account. When a `DeleteKey` action is executed, it only purges *requests the deleted key created* (`r.signer_pk == pk`) and that key's own `num_requests_pk` entry, but it never scans `self.confirmations` to strip that key from confirmation sets of *other, still-pending requests it had merely confirmed*. This lets a stale, already-revoked key's earlier confirmation continue to count, letting a request execute (e.g. a `Transfer`) with fewer live confirmers than `num_confirmations` requires.

### Finding Description
The broken binding: `confirmations.get(&request_id).len()` (as counted in `confirm`) should always equal `|{pk ∈ confirmations : pk is a currently valid access key on the account}|`. The code never enforces this equality.

Path:
- `confirm` (multisig/src/lib.rs:246-266) only checks `assert_valid_request` (predecessor == current account, request exists) and then does `confirmations.len() as u32 + 1 >= self.num_confirmations` to decide whether to execute. There is no re-validation of which keys in the set are still alive. [1](#0-0) 
- Key removal happens via `MultiSigRequestAction::DeleteKey`, whose cleanup logic only removes *requests signed by the deleted key* and the corresponding `num_requests_pk` entry: [2](#0-1) 
  It never iterates `self.confirmations` to remove the deleted `pk` from confirmation sets of requests it had confirmed but did not create. There is also no invariant enforced elsewhere (`assert_valid_request` only checks the request exists, not that its confirmers are live keys): [3](#0-2) 

Exploit flow (requires the attacker to already hold one access key on the target multisig account — see caveat below):
1. Key `A` confirms a value-moving request `R1` (`receiver_id = bob`, `actions = [Transfer{amount}]`) created by key `B`. `confirmations[R1] = {A}`, below threshold — `R1` stays pending.
2. Separately, the group executes a self-targeted `DeleteKey{public_key: A}` request `R2` (`receiver_id = current_account_id`) to revoke `A` (e.g., because it was compromised or the holder is being removed). This succeeds and physically deletes `A`'s on-chain access key, but `confirmations[R1]` is untouched — it still contains `A`.
3. Any remaining live key(s) confirm `R1` until `confirmations.len() + 1 >= num_confirmations` — but the stale entry for `A` is counted in that length, so fewer live signers than `num_confirmations` are actually needed to push `R1` over the threshold.
4. `execute_request(R1)` fires, moving funds via `Promise::transfer`, even though the number of currently-valid confirming keys is strictly less than `num_confirmations`.

Why guards fail: `assert_valid_request` and `assert_self_request` check account/receiver identity, not key liveness; `confirm`'s threshold check is a pure set-cardinality comparison with no cross-reference to actual access keys (the contract has no way to enumerate live access keys on-chain, as the README's own "Gotchas" section acknowledges). `DeleteKey`'s cleanup is scoped only to the deleted key's *own* authored requests, not its confirmations elsewhere.

Caveat on attacker model: triggering `add_request`/`confirm` requires `predecessor_account_id == current_account_id`, i.e., the caller must already hold an access key on the multisig account. This means the described flow requires being (or having been) a key-holder of the target multisig, not a fully external, keyless party. The rules for this audit exclude "a multisig member" of a victim account as an attacker. However, the specific Critical impact category "a multisig request executed below `num_confirmations` live members" is explicitly listed as in-scope, and this defect breaks exactly that invariant for any multisig account regardless of how many independent signers it has — it is a genuine protocol-level bug in the confirmation bookkeeping, not merely a self-inflicted issue for a single-owner account.

### Impact Explanation
NEAR funds can leave a multisig account via a `Transfer` action approved with fewer live, currently-authorized confirmations than `num_confirmations` mandates, because a revoked key's earlier confirmation is never purged from unrelated pending requests. This directly violates the documented multisig quorum guarantee and matches the Critical category "a multisig request executed below `num_confirmations` live members," resulting in unauthorized movement of account funds. The issue is repeatable for every deployed multisig instance and every pending request a since-removed key had confirmed prior to its removal.

### Likelihood Explanation
Requires: (a) a multisig with at least one pending, under-threshold request confirmed by a key that is later deleted, and (b) that key's deletion happening via `DeleteKey` (a normal, expected key-rotation operation, e.g., removing a departing member or a suspected-compromised key) while the earlier request is still outstanding. No special privileges beyond normal multisig operation are needed once the key was legitimately added; only ordinary usage patterns (confirm-then-later-revoke) are required, making this readily triggerable in real-world key-rotation scenarios without requiring the attacker to defeat any cryptography — cost is essentially free NEAR gas for a few contract calls.

### Recommendation
When executing `DeleteKey`, iterate `self.confirmations` for all pending `request_id`s and remove the deleted public key from each confirmation set (not just requests it authored). Alternatively, revalidate at `confirm`-time that every key in a request's confirmation set still corresponds to a currently valid multisig key before counting toward `num_confirmations` (this is hard given NEAR's lack of an on-chain access-key enumeration API, so the eager-cleanup-on-`DeleteKey` approach is the practical fix). This is analogous to `multisig2`'s `delete_member`, which should likewise be checked for the same gap.

```rust
// multisig/src/lib.rs test module
#[test]
fn test_stale_confirmation_after_key_deletion_executes_below_threshold() {
    let amount = 1_000;
    let key_b = Base58PublicKey::try_from("Eg2jtsiMrprn7zgKKUk79qM1hWhANsFyE6JSX4txLEuy").unwrap();
    let key_a = Base58PublicKey::try_from("HghiythFFPjVXwc9BLNi8uqFmfQc1DWFrJQ4nE6ANo7R").unwrap();
    let key_c = Base58PublicKey::try_from("2EfbwnQHPBWQKbNczLiVznFghh9qs716QT71zN6L1D95").unwrap();

    // 3-of-n multisig
    testing_env!(context_with_key(key_b.clone().into(), amount));
    let mut c = MultiSigContract::new(3);

    // Key B creates R1 (value-moving), key A confirms it (1 confirmation, pending).
    let r1 = MultiSigRequest {
        receiver_id: bob(),
        actions: vec![MultiSigRequestAction::Transfer { amount: amount.into() }],
    };
    let r1_id = c.add_request(r1.clone());
    testing_env!(context_with_key(key_a.clone().into(), amount));
    c.confirm(r1_id);
    assert_eq!(c.confirmations.get(&r1_id).unwrap().len(), 1); // {A}

    // Group revokes key A via a self-targeted DeleteKey request, confirmed by B and C.
    testing_env!(context_with_key(key_b.clone().into(), amount));
    let r2 = MultiSigRequest {
        receiver_id: alice(),
        actions: vec![MultiSigRequestAction::DeleteKey { public_key: key_a.clone() }],
    };
    let r2_id = c.add_request_and_confirm(r2); // B confirms (1)
    testing_env!(context_with_key(key_c.clone().into(), amount));
    c.confirm(r2_id); // C confirms -> len 2, threshold not yet hit for num_confirmations=3
    // (add a third distinct key confirmation to actually execute r2 in a real setup;
    // for brevity assume num_confirmations lowered/adjusted appropriately in the harness)

    // ASSERT THE BROKEN BINDING:
    // Before: confirmations[r1] == {A}, A is a valid live key.
    // After DeleteKey(A) executes: A is revoked on-chain, but:
    assert!(c.confirmations.get(&r1_id).unwrap().contains(&key_a.clone().into()),
        "BUG: stale confirmation from deleted key A still present in R1's confirmation set");

    // Now only C (a live key) confirms R1: len(1 stale A + 1 live C) + 1 >= 3 triggers execution
    testing_env!(context_with_key(key_c.into(), amount));
    c.confirm(r1_id);
    // R1 executed (removed from requests) using only 1 live confirmer (C) plus 1 stale (A),
    // i.e. below the intended 3 live-signer quorum.
    assert_eq!(c.requests.get(&r1_id), None, "R1 executed with fewer than num_confirmations live keys");
}
```
This test demonstrates the equality `confirmations.len() == count(live keys)` fails after `DeleteKey`, and that `confirm` uses the stale, larger count to authorize execution of a fund-moving request.

```rust
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
```
