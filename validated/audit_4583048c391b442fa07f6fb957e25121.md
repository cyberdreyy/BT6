Note: only `BridgeType.IncomingTokenHash` is stored (a salted SHA-256 hash), not the plaintext `IncomingToken`; the plaintext incoming token is returned only once at creation time (`bta.IncomingToken` set explicitly in `Create`, line 99 of `core/web/bridge_types_controller.go`). So `Show`/`Index`/`Update`/`Destroy` cannot leak the incoming token (it's never stored in plaintext). However, `OutgoingToken` **is** stored in plaintext on `BridgeType` and is unconditionally serialized by `presenters.NewBridgeResource` with no `omitempty`, so it is returned on every bridge read, including `Show`.

### Title
Unauthorized disclosure of bridge OutgoingToken to any authenticated low-privilege user via unrestricted GET /v2/bridge_types/:BridgeName - ([File: core/web/router.go])

### Summary
`GET /v2/bridge_types/:BridgeName` (`bt.Show`) and `GET /v2/bridge_types` (`bt.Index`) are registered without any role wrapper, unlike the sibling `Create`/`Update`/`Destroy` routes which use `auth.RequiresEditRole`. Any authenticated session or API token — including view/run role — can call these endpoints and receive the bridge's plaintext `OutgoingToken` in the JSON response, since `presenters.BridgeResource.OutgoingToken` has no `omitempty` and is always populated from the stored plaintext value.

### Finding Description
In `core/web/router.go`: [1](#0-0) 
`bt.Show` and `bt.Index` have no `auth.RequiresEditRole`/`RequiresRunRole`/`RequiresAdminRole` wrapper, while `Create`, `Update`, and `Destroy` do. This means any user who can authenticate at all — including one with only the view role — reaches `BridgeTypesController.Show`.

`Show` fetches the bridge and serializes it via `presenters.NewBridgeResource(bt)`: [2](#0-1) 

The presenter always includes `OutgoingToken` (no `omitempty` tag), while `IncomingToken` is `omitempty` and only ever populated in the `Create` handler (`resource.IncomingToken = bta.IncomingToken` at line 99), never in `Show`/`Index`/`Update`/`Destroy`: [3](#0-2) 

The underlying `bridges.BridgeType` struct stores `OutgoingToken` in plaintext in the database (unlike the incoming token, which is only stored as a salted hash `IncomingTokenHash`): [4](#0-3) 

So the incoming token (used to authenticate inbound EI/adapter callbacks into the node) cannot be re-disclosed this way since it isn't persisted in plaintext, but the outgoing token (used by the node to authenticate itself to the external adapter) is fully recoverable via `Show`/`Index` by any authenticated user regardless of role.

### Impact Explanation
Any authenticated low-privilege user (view or run role) can read a bridge's `OutgoingToken`, which is the shared secret the node uses to authenticate its outbound requests to the external adapter. This falls under the credential/secret disclosure impact class — an attacker with read-only access can extract a secret meant to be confined to edit/admin roles, potentially enabling them to impersonate the node to the external adapter or replay/tamper with adapter interactions if the adapter trusts this token for other purposes.

### Likelihood Explanation
Requires only a valid authenticated session or API token with the lowest privilege (view role) — no special preconditions. The request is a single unauthenticated-role GET to a documented, always-available route (`/v2/bridge_types/:BridgeName`), fully repeatable and requires no timing or race conditions.

### Recommendation
Wrap `bt.Show` and `bt.Index` with `auth.RequiresEditRole` (or a dedicated read-role check that excludes view/run if that's the intended confinement), consistent with `Create`/`Update`/`Destroy`. Alternatively/additionally, remove `OutgoingToken` from `presenters.BridgeResource` in read paths (make it `omitempty` and only populate it on `Create`, mirroring the `IncomingToken` handling), and never return it for `Show`/`Index`.

### Proof of Concept
Add/extend a presenter+handler test:
1. In `core/web/bridge_types_controller_test.go`, create a bridge as an admin/edit user (populating `OutgoingToken`).
2. Create an HTTP client authenticated with a view-role (or run-role) user via `cltest`.
3. Call `GET /v2/bridge_types/<name>` and `GET /v2/bridge_types` with that client.
4. Assert current (vulnerable) behavior: `resp.StatusCode == 200` and `resource.OutgoingToken` is non-empty and equals the stored secret — demonstrating the leak.
5. Expected fixed behavior: either the request is rejected with `403` for view/run roles, or `resource.OutgoingToken` is empty/redacted for non-edit roles.

Existing `TestBridgeController_Show` (`core/web/bridge_types_controller_test.go` lines 271-300) already exercises `Show` but does not assert role restriction or check `OutgoingToken`/`IncomingToken` redaction — extending it with a view-role client and an assertion on `resource.OutgoingToken` reproduces the finding. 	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

}
