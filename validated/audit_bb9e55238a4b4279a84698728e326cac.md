### Title
FunctionCall receipts that hit a `Module::deserialize` `VMRunnerError::LoadingError` are converted into a zero-gas NOP outcome, letting the signer recover a near-full gas refund for prepaid gas that covered real compile/deserialize/link work already performed - (File: `runtime/runtime/src/function_call.rs`, `runtime/near-vm-runner/src/wasmtime_runner/mod.rs`, `runtime/runtime/src/lib.rs`)

### Summary
When `Module::deserialize` fails inside `WasmtimeVM::with_compiled_and_loaded` and `config.fix_contract_loading_error` is `false` (the mainnet/stable default; the fix is nightly-only PV129), the failure is returned as `VMRunnerError::LoadingError` rather than a `FunctionCallError`. `execute_function_call` converts this into `VMOutcome::nop_outcome`, which reports zero `burnt_gas`/`used_gas`, even though `Contract::get_code`, contract compilation, and `Module::deserialize` were fully executed on every validator. `refund_unspent_gas_and_deposits` then computes `gross_gas_refund = prepaid_gas + prepaid_exec_gas - result.gas_burnt` with `result.gas_burnt == 0`, refunding the signer almost the entire prepaid gas instead of charging for the loading-phase work performed.

### Finding Description
`WasmtimeVM::with_compiled_and_loaded` (`runtime/near-vm-runner/src/wasmtime_runner/mod.rs:686-834`) resolves a compiled artifact, then attempts `unsafe { Module::deserialize(&self.engine, &module) }` (line ~747). If this fails:

```
Err(err) => {
    if self.config.fix_contract_loading_error {
        let err = FunctionCallError::LoadingError { msg: err.to_string() };
        return Ok((..., to_any((wasm_bytes, Ok(Err(err))))));
    }
    return Err(VMRunnerError::LoadingError(err.to_string()));
}
``` [1](#0-0) 

On stable (`fix_contract_loading_error == false`), this early `return Err(...)` happens **inside the memory-cache lookup closure**, before `gas_counter.before_loading_executable`/`after_loading_executable` are ever invoked (those calls happen later at `mod.rs:814`/`:821`). The loading fee (`contract_loading_base + contract_loading_bytes * len`) is thus never charged for this path.

`runtime/runtime/src/function_call.rs::execute_function_call` explicitly maps this runner error to a graceful, zero-gas outcome:
```
Err(VMRunnerError::LoadingError(msg)) => {
    return Ok(VMOutcome::nop_outcome(FunctionCallError::LoadingError { msg }));
}
``` [2](#0-1) 

`VMOutcome::nop_outcome` produces `burnt_gas = 0, used_gas = 0` (this is the same "NOP" pattern used for other pre-loading failures such as `MethodEmptyName`, documented at `logic.rs:4533`, `abort_but_nop_outcome_in_old_protocol`). That outcome's `burnt_gas`/`used_gas` propagate to `result.gas_burnt` via `result.gas_burnt = result.gas_burnt.checked_add_result(outcome.burnt_gas)?` in `action_function_call` (`runtime/runtime/src/function_call.rs:140`).

Downstream, `refund_unspent_gas_and_deposits` (`runtime/runtime/src/lib.rs:1230-1262`) computes, on the failure branch (`result.result.is_err()`, which is true because the `aborted` error sets `result.result = Err(...)` at `function_call.rs:138`):
```
let gross_gas_refund = prepaid_gas
    .checked_add(prepaid_exec_gas.gas)?
    .checked_sub(result.gas_burnt).unwrap();
``` [3](#0-2) 

With `result.gas_burnt == 0`, `gross_gas_refund` equals the full prepaid gas + prepaid exec gas. The only deduction applied is the small NEP-536 `gas_penalty_for_gas_refund` (mainnet ratio `0/100`, i.e. effectively zero on mainnet per the config snapshot), so the signer is refunded essentially the entire prepaid gas via `Receipt::new_gas_refund` (`lib.rs:1354-1362`), despite the compile + `Module::deserialize` work having actually consumed CPU/memory on every validator that processed the receipt.

**Attacker reachability**: this is not limited to disk/cache corruption. The repo's own regression test documents a deterministic, attacker-controllable trigger: a contract with ~100,000 WASM globals passes `prepare` (structural validation) but blows the Wasmtime pooling allocator's `max_core_instance_size` at `Module::deserialize` time — deterministically, on every validator, based purely on the contract's own compiled structure:
```
/// Pre-`FixContractLoadingError` this surfaces as `VMRunnerError::LoadingError`,
/// which the runtime maps to a zero-gas nop — the contract-loading work is left
/// uncharged. Post-feature the same failure finalizes as a gas-bearing abort
/// that charges the contract-loading fee.
``` [4](#0-3) 
The corresponding test asserts exactly the stable-vs-fixed behavior difference, confirming pre-fix `Err(VMRunnerError::LoadingError(_))` and post-fix a gas-bearing abort with `expected_gas > 0`: [5](#0-4) 

An unprivileged attacker can: (1) deploy such a crafted contract via ordinary `DeployContract`, (2) submit `FunctionCall` transactions/receipts invoking any method on it. Every such receipt costs the validator real compile+deserialize work but the signer recovers nearly all prepaid gas back through `refund_unspent_gas_and_deposits`, because `result.gas_burnt` for the loading-failure receipt is 0.

Existing checks do not stop this: gas metering (`GasCounter`) simply is never engaged for this specific failure path since the fee-charging calls (`before_loading_executable`/`after_loading_executable`) are unreachable when the closure returns early with `VMRunnerError`; nonce/access-key/signature checks are orthogonal and pass normally; storage-staking is unaffected.

### Impact Explanation
This is a fee-payment bypass, not (by itself) a direct theft of another party's funds: the underpayment benefits the same signer who caused the work. Its scoped/matching impact is that validators perform real, non-trivial CPU/memory work (contract compilation + Wasmtime module deserialization for oversized/crafted modules) while the network fails to burn the fee designed to cover exactly that work (`contract_loading_base`/`contract_loading_bytes`), and the signer recovers that gas back at near-100% (only the negligible/zero NEP-536 penalty is retained). Repeated at scale this is an underpriced-compute vector: attacker pays close to nothing for validator-side compile+deserialize work that should be charged. This matches the "Fee Payment Bypass" category explicitly scoped in the question. It does not, by itself, cause double-spend, state-root divergence, or a shard halt — the outcome is deterministic across all validators (same compiled module, same allocator limit), so no consensus divergence results; and the runtime explicitly avoids panicking on this VMRunnerError variant (unlike `Nondeterministic`/`WasmUnknownError`, which do panic), so no crash occurs either.

### Likelihood Explanation
- Preconditions: mainnet is stable at PV86 and `fix_contract_loading_error`/`FixContractLoadingCost` is nightly-only (PV129), so the vulnerable code path is live on the current mainnet configuration.
- Cost to attacker: one contract deployment (crafted to breach `max_core_instance_size`, e.g. via a very large number of globals, while still passing `prepare`'s structural limits) plus ordinary `FunctionCall` transactions against it. Fully repeatable — every call against that contract hits the same deterministic `Module::deserialize` failure.
- No validator/node privilege, no leaked keys, and no reliance on cache/disk corruption is required — the failure is deterministic given the contract's compiled shape.

### Recommendation
Do not treat `Module::deserialize` failures as an unconditional zero-gas NOP on stable. Either:
1. Charge the contract-loading fee (`before_loading_executable`/`after_loading_executable`) unconditionally before/around the `Module::deserialize` attempt, regardless of `fix_contract_loading_error`, so the fee reflects the compile+deserialize work performed even when that step fails; or
2. Backport the `FixContractLoadingCost`/`fix_contract_loading_error` behavior (pre-charging and turning loading-phase failures into gas-bearing aborts, as it does when the flag is `true`) to stable via a protocol upgrade, closing the gap the code/tests already acknowledge exists on stable.

### Proof of Concept
Extend/adapt the existing `test_max_core_instance_size_breached` in `runtime/near-vm-runner/src/tests/runtime_errors.rs` (already exercises exactly this scenario) into a runtime-level integration test:
1. Deploy an account with a contract crafted to pass `prepare` but overflow `max_core_instance_size` at `Module::deserialize` (e.g., `near_test_contracts::contract_with_num_globals(100_000)`, as used by the existing unit test).
2. On a runtime configured with `fix_contract_loading_error = false` (current mainnet default), submit a `FunctionCall` receipt against it with `prepaid_gas` set high enough to have covered `contract_loading_base + contract_loading_bytes * code_len` plus the base action fees.
3. Assert:
   - The action outcome's `aborted` is `Some(FunctionCallError::LoadingError { .. })`.
   - `result.gas_burnt == 0` for the receipt (via the outcome/`ExecutionOutcome.gas_burnt`).
   - The gas-refund receipt (`Receipt::new_gas_refund`) issued by `refund_unspent_gas_and_deposits` credits back essentially the full `prepaid_gas + prepaid_exec_gas` (modulo the near-zero NEP-536 penalty), confirming the loading-phase fee was never deducted despite the compile+deserialize work having executed on the node.
4. Repeat with `fix_contract_loading_error = true` and confirm `gas_burnt` equals `contract_loading_base + contract_loading_bytes * len` (non-zero) and the refund is correspondingly smaller — demonstrating the stable/nightly behavioral gap directly.
