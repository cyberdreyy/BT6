### Title
Cross-user response delivery via colliding `message_id` in WebAPI trigger handler's `savedCallbacks` map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`DecodeJSONRequest` in `core/services/gateway/api/jsonrpccodec.go` copies the caller-supplied JSON-RPC `id` directly into `msg.Body.MessageId` with no binding to the authenticated sender extracted later during `msg.Validate()`. The legacy WebAPI-trigger handler (`core/services/gateway/handlers/capabilities/handler.go`) then keys its pending-callback map solely by this attacker-chosen `MessageId`, and unconditionally overwrites any existing entry, so a second signed request that reuses a victim's in-flight `message_id` can capture the DON's response meant for the victim.

### Finding Description
The public gateway entrypoint `gateway.ProcessRequest` (core/services/gateway/gateway.go:218-262) decodes the raw JSON-RPC body with `g.codec.DecodeJSONRequest(jsonRequest)`: [1](#0-0) 
`request.ID` is fully attacker-controlled (any string up to 200 chars, enforced only by a length check in `gateway.go`), and it is written into `msg.Body.MessageId` before signature-derived `msg.Body.Sender` is ever computed by `msg.Validate()`: [2](#0-1) 

For legacy (`DonId`-bearing) requests, `ProcessRequest` calls `h.HandleLegacyUserMessage(ctx, msg, callback)`: [3](#0-2) 

In the WebAPI trigger handler, the callback used to eventually deliver the DON's response to the calling HTTP client is stored keyed **only** by `msg.Body.MessageId`, with no existence check and no inclusion of `msg.Body.Sender`: [4](#0-3) 

When a node's response arrives, it is routed back purely by `msg.Body.MessageId`: [5](#0-4) 

Exploit flow:
1. Victim A signs and sends a legacy request with `message_id = "X"`. `HandleLegacyUserMessage` stores `savedCallbacks["X"] = A's callback` and forwards the request to all DON members.
2. Before the DON responds, attacker B (any EOA, no privileges needed) sends their own signed request reusing `message_id = "X"`. This silently overwrites `savedCallbacks["X"]` with B's callback (no `errors.New("request already exists")`-style guard exists here, unlike the vault/confidential-relay handlers).
3. When the DON node's response for A's original request arrives with `MessageId == "X"`, `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds B's callback, and delivers A's response payload to B.

This directly violates the intended invariant that "request identity must include the authenticated sender" — the map key is `msg.Body.MessageId` alone, never combined with `msg.Body.Sender`.

Note: this pattern does **not** affect the vault (`core/services/gateway/handlers/vault/handler.go`) or confidential-relay (`core/services/gateway/handlers/confidentialrelay/handler.go`) handlers — both explicitly reject a colliding `req.ID` in `newActiveRequest` before storing: [6](#0-5) 
So no vault/DKG secret disclosure results from this specific bug; the confirmed impact is limited to the WebAPI-trigger (`web_api_trigger`) legacy handler.

### Impact Explanation
An unprivileged attacker who can guess or race a victim's `message_id` can hijack delivery of another user's WebAPI trigger response, receiving data intended for a different caller — a concrete cross-user response confusion / unauthorized data disclosure. This does not reach vault/DKG secret material because those handlers reject ID collisions, so the "Critical — vault secret theft" impact class claimed in the question does not apply here; the realistic impact is response/data leakage scoped to the WebAPI-trigger capability path.

### Likelihood Explanation
Exploitation requires only an externally-owned key capable of signing gateway requests (no operator/admin/DB access) and requires winning a timing race: the attacker's colliding-ID request must be received and processed by the gateway after the victim's request is registered but before the DON's response returns. This is feasible but non-trivial without knowledge of the victim's chosen `message_id` and precise timing, so likelihood is moderate rather than trivial.

### Recommendation
Key `savedCallbacks` (and any other message-identity-based routing table in the legacy/JSON-RPC gateway paths) by `(Sender, MessageId)` instead of `MessageId` alone, and reject/refuse to overwrite an existing entry for the same key, mirroring the guard already present in `vault/handler.go`'s and `confidentialrelay/handler.go`'s `newActiveRequest`.

### Proof of Concept
Go handler-level test plan for `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct two signed `api.Message`s with different private keys (different senders) but identical `Body.MessageId = "collide-1"` and `Body.DonId`/`Method = MethodWebAPITrigger`.
2. Call `handler.HandleLegacyUserMessage(ctx, msgA, cbA)`; assert `don.SendToNode` was invoked for msgA.
3. Call `handler.HandleLegacyUserMessage(ctx, msgB, cbB)` before resolving any node response; assert internal `h.savedCallbacks["collide-1"]` now references `cbB` (i.e., `cbA`'s entry was silently dropped) — this can be checked via an exported test hook or by proceeding to step 4 and observing which callback receives the response.
4. Simulate a DON node response addressed to `msgA` (`resp.ID`/`MessageId = "collide-1"`, sender = victim's DON member) via `handler.HandleNodeMessage`.
5. Assert that `cbB.Wait(ctx)` (attacker B's callback) receives the response — i.e., `cbA.Wait(ctx)` times out/never resolves while `cbB` receives msgA's payload — demonstrating cross-user delivery.

func (*JsonRPCCodec) DecodeJSONRequest(request jsonrpc2.Request[json.RawMessage]) (*Message, error) {
	var msg Message
	err := json.Unmarshal(*request.Params, &msg)
	if err != nil {
		return nil, err
	}
	msg.Body.MessageId = request.ID
	msg.Body.Method = request.Method
	return &msg, nil
}

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
