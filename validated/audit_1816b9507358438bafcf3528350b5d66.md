### Title
Stale instant-withdraw ledger entries enable double claim from default recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestInstantWithdraw` allocates three pieces of per-epoch state for every request — `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` — but the normal claim path frees only the first. The per-epoch records are never decremented on a successful claim, mirroring the rpcapd leak where each request allocates memory that is never released. When the borrower later defaults in that same epoch, `_claimDefaultedInstantWithdrawRequest` reads the stale per-epoch basis and pays the user a second time from `defaultRecoveryReserve`.

### Finding Description
In `requestInstantWithdraw` each request accumulates:

- `instantWithdrawsRequests[_user] += _amount` (line 366)
- `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount` (line 371)
- `instantWithdrawClaimsByEpoch[currentEpoch] += _amount` (line 372)
- `pendingInstantWithdraws += _amount` (line 374)

The normal claim `claimInstantWithdrawRequest` (lines 387-392) only does `instantWithdrawsRequests[_user] = 0`, burns the receipt, and transfers funds. It never clears `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` nor decrements `instantWithdrawClaimsByEpoch[currentEpoch]`. By contrast, the default-claim path `_claimDefaultedInstantWithdrawRequest` (lines 842-856) clears both per-epoch ledgers — confirming they are intended to track unclaimed basis, but they leak for anyone who already claimed.

Two impacts follow:

1. `_defaultPrefundedInstantReserve` (lines 716-723) computes `instantBasis = instantWithdrawClaimsByEpoch[epochNumber]` and treats `instantBasis - pendingInstant` as already-held underlying reserved for instant claims. Stale amounts from already-claimed requests inflate `prefundedReserve`, which is added into `reserveAmount` (line 686) and thus inflates `defaultRecoveryPrice` (line 688) beyond the real backing.
2. `_claimDefaultedInstantWithdrawRequest` computes `claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` (line 844) — including requests the user already claimed at par — and pays `(claimBasis * defaultRecoveryPrice) / RECOVERY_FULL` from the recovery reserve (line 855).

Attack sequence: a KYC-passing lender requests an instant withdrawal during epoch N and claims it normally once funded. Both per-epoch ledgers retain the amount. If `finalizeDefaultRecovery` executes while `epochNumber == N` (default finalization occurs in the epoch where `stopEpochWithDuration`/default handling ran, before a new epoch starts), the user can hold strategy tokens again (e.g. via a `postDefaultRequests` receipt minted at line 255, or residual balance) to satisfy the `_burn(_user, claimBasis)` at line 854, and receives `claimBasis * defaultRecoveryPrice` a second time. Because `pendingInstantWithdraws` floors at 0 (line 852), nothing stops the stale basis from being paid.

### Impact Explanation
The recovery reserve is funded by the actual recovered amount; every stale-basis claim is paid from that finite pool. The attacker extracts up to their full prior instant-withdraw amount again (scaled by `defaultRecoveryPrice`), directly stealing recovery funds owed to other defaulted-epoch receipt holders and active LPs. Additionally, the inflated `defaultRecoveryPrice` misprices all recovery claims and can leave later claimers unable to withdraw — permanent loss for honest users. Broken invariant: one receipt, one payout; recovery reserve solvency.

### Likelihood Explanation
Requires the attacker to have completed an instant withdrawal in the same epoch in which the borrower default is finalized — a plausible sequence since instant withdrawals are designed to be requested and claimed intra-epoch, and default finalization happens at epoch end before `epochNumber` advances. The attacker is an ordinary KYC'd tranche holder. The burn requirement is satisfiable because users retain or re-acquire strategy-token receipts (`postDefaultRequests` mints to the user). No privileged cooperation is needed.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch ledgers alongside `instantWithdrawsRequests`: decrement `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and `instantWithdrawClaimsByEpoch[epochNumber]` by the claimed amount (or track and delete the entry per epoch). Similarly audit `withdrawsRequestsByEpoch`, which `_claimFundedWithdrawRequest` (lines 344-345) also leaves stale, for analogous default-basis inflation via `_withdrawClaimAmountsForEpoch`.

### Proof of Concept
Foundry fork PoC sketch:

```solidity
function testStaleInstantBasisDoubleClaim() external {
    // 1. Epoch N running, user1 deposits, requests instant withdraw of X
    vm.prank(user1); cdo.requestInstantWithdraw(X, trancheAA);
    // borrower/manager funds instant requests; user1 claims at par
    cdo.collectInstantWithdrawFunds(...); // via CDO flow
    vm.prank(user1); cdo.claimInstantWithdrawRequest();
    // ledgers still hold stale basis:
    assertGt(strategy.instantWithdrawsRequestsByEpoch(user1, epochN), 0);
    assertGt(strategy.instantWithdrawClaimsByEpoch(epochN), /* includes claimed X */);

    // 2. Borrower defaults; recovery finalized while epochNumber == N
    strategy.finalizeDefaultRecovery(recovered, source); // privileged but honest call

    // 3. user1 acquires strategy tokens (post-default request mints receipt)
    vm.prank(user1); cdo.requestWithdraw(X2, trancheAA); // mints postDefaultRequests receipt

    // 4. Second claim pays stale basis again from defaultRecoveryReserve
    uint256 balPre = underlying.balanceOf(user1);
    vm.prank(user1); cdo.claimInstantWithdrawRequest();
    assertGt(underlying.balanceOf(user1) - balPre, 0); // double payout
}
```

Uncertainty: I could not exhaustively read all 42 matches of the instant-withdraw ledgers, so it is possible an intermediate CDO/queue wrapper clears them in a path I did not see; the strategy-level claim path shown (lines 387-392) does not. The PoC should be validated against the exact default-finalization epoch timing in `IdleCDOEpochVariant._handleBorrowerDefault`/`finalizeDefaultRecovery`.
