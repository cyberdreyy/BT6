### Title
Stale confirmations from removed multisig members remain counted toward execution threshold - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::confirm` and `delete_member` in `multisig2/src/lib.rs` never reconcile the `confirmations: LookupMap<RequestId, HashSet<String>>` map against the current `members: UnorderedSet<MultisigMember>` set when a member is removed. `delete_member` (lines 356-379) only purges confirmations for requests the removed member *originated* (filtered by `r.member == member`), leaving behind confirmations that removed member cast on requests originated by other members. `confirm` (lines 292-315) then executes a request once `confirmations.len() + 1 >= num_confirmations`, counting these stale entries as valid signatures. ### Finding Description
The contract's core custody guarantee is that a request is only executed once `num_confirmations` *live* members have approved it — i.e., `len(confirmations ∩ live_members) >= num_confirmations`. The implementation instead checks `len(confirmations) >= num_confirmations` without intersecting against current membership.

Sequence:
1. Member `X` confirms request `R1` (created by member `Y`). `confirmations[R1] = {X}`.
2. The multisig later executes a separate confirmed request that removes `X` via `MultiSigRequestAction::DeleteMember`. `delete_member` only looks for requests where `r.member == X` (requests `X` created) to purge; `R1` was created by `Y`, so `confirmations[R1]` is untouched and still contains `X`.
3. `X` is no longer in `self.members`, so `X` can no longer call `confirm` again, but their prior confirmation on `R1` still counts.
4. When enough of the remaining live members confirm `R1`, the stale entry from removed `X` is added to the tally, meaning `R1` can execute with one fewer *live* confirming member than `num_confirmations` actually requires.

This breaks the equality the multisig is supposed to enforce: `confirmations_counted == live_members_who_approved`. After removal, the binding becomes `confirmations_counted > live_members_who_approved`.

### Impact Explanation
This allows a request (e.g., a `Transfer` of NEAR, a `FunctionCall`, or an `AddKey`) to execute despite having fewer live/current approving members than `num_confirmations` requires, directly weakening the K-of-N custody threshold that protects funds and control of the account. Per the impact classification, "a multisig request executed below threshold" is a Critical-severity outcome, since a request can move NEAR or grant access with fewer authorized signers than the security model demands.

### Likelihood Explanation
Requires only ordinary multisig operational activity: a member confirms a pending request, and that same member is later removed from the multisig (a routine key-rotation/offboarding event). No malicious insider collusion beyond normal usage is needed for the stale confirmation to persist; the flaw is triggered anytime membership changes while other requests are outstanding.

### Recommendation
When removing a member in `delete_member`, iterate over **all** active requests (not just those originated by the removed member) and strip the removed member's string identifier from each `confirmations` `HashSet`. Alternatively, in `confirm`/execution, recompute the confirmation count by filtering `confirmations` against `self.members.contains(...)` before comparing to `num_confirmations`.

### Proof of Concept
1. Initialize `MultiSigContract::new(members: [A, B, C, D], num_confirmations: 3)`.
2. Member `A` creates request `R1` (e.g., `Transfer`) via `add_request`.
3. Member `D` calls `confirm(R1)` → `confirmations[R1] = {D}` (1/3).
4. Separately, members `A`, `B`, `C` create and confirm a `DeleteMember { member: D }` request, which executes via `execute_request` → `delete_member` removes `D` from `self.members` and its access key, but does not touch `confirmations[R1]` because `R1` was originated by `A`, not `D` (`request_ids` filter in `delete_member` only matches `r.member == member`).
5. Now only `A`, `B`, `C` remain as live members, but `confirmations[R1]` still contains the stale entry from the removed `D`.
6. Member `A` calls `confirm(R1)` → `confirmations.len() == 1` (`D`'s stale entry) `+ 1 == 2`, still below 3; but if `A` had also confirmed R1 as its originator elsewhere (or if two of the remaining three members confirm), the stale `D` entry contributes to reaching `3`, letting `R1` execute (a `Transfer`) with only 2 truly live confirmations instead of the required 3.     /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }

    /// Removes request, removes confirmations and reduces num_requests_pk - used in delete, delete_key, and confirm
    fn remove_request(&mut self, request_id: RequestId) -> MultiSigRequest {
        // remove confirmations for this request
        self.confirmations.remove(&request_id);
        // remove the original request
        let request_with_signer = self
            .requests
            .remove(&request_id)
            .unwrap_or_else(|| env::panic_str("Failed to remove existing element"));
        // decrement num_requests for original request signer
        let original_member = request_with_signer.member;
        let mut num_requests = self
            .num_requests_pk
            .get(&original_member.to_string())
            .unwrap_or(0);
        // safety check for underrun (unlikely since original_signer_pk must have num_requests_pk > 0)
        if num_requests > 0 {
            num_requests = num_requests - 1;
        }
        self.num_requests_pk
            .insert(&original_member.to_string(), &num_requests);
        // return request
        request_with_signer.request
    }
