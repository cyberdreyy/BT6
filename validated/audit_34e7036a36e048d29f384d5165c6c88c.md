### Title
Correlation slashing penalty can round down to zero via bad division order - ([File: specs/electra/beacon-chain.md])

### Summary
`process_slashings` in Electra pre-computes a single `penalty_per_effective_balance_increment` by dividing `total_balance` by `increment` *before* dividing `adjusted_total_slashing_balance` by that quotient, instead of multiplying first. When the network's total active balance is large relative to the aggregate slashed-balance for the epoch, this truncates to zero, and every slashed validator's per-increment penalty (and hence the whole correlation penalty) becomes `0`, regardless of the validator's `effective_balance`.

### Finding Description
The Electra version of `process_slashings` computes: [1](#0-0) 

```python
def process_slashings(state: BeaconState) -> None:
    epoch = get_current_epoch(state)
    total_balance = get_total_active_balance(state)
    adjusted_total_slashing_balance = min(
        Gwei(sum(state.slashings)) * PROPORTIONAL_SLASHING_MULTIPLIER_BELLATRIX, total_balance
    )
    increment = EFFECTIVE_BALANCE_INCREMENT
    penalty_per_effective_balance_increment = adjusted_total_slashing_balance // (
        total_balance // increment
    )
    for index, validator in enumerate(state.validators):
        if (
            validator.slashed
            and epoch + EPOCHS_PER_SLASHINGS_VECTOR // 2 == validator.withdrawable_epoch
        ):
            effective_balance_increments = validator.effective_balance // increment
            penalty = penalty_per_effective_balance_increment * effective_balance_increments
            decrease_balance(state, ValidatorIndex(index), penalty)
```

Compare this to the pre-Electra (phase0/altair/bellatrix) algorithm, which multiplies before it divides: [2](#0-1) 

```python
penalty_numerator = validator.effective_balance // increment * adjusted_total_slashing_balance
penalty = penalty_numerator // total_balance * increment
```

In the older formula, `adjusted_total_slashing_balance` is multiplied into the numerator *before* the division by `total_balance`, so precision loss only occurs in a way proportional to `effective_balance / total_balance`, which is bounded and predictable.

In the Electra formula, the intermediate `total_balance // increment` is computed **first** as a standalone integer, and `adjusted_total_slashing_balance` is divided by that intermediate quotient. This is exactly the bug class in the report: an "order of operations" mistake where the divisor is inflated (or the dividend is deflated) before the final division, causing legitimate non-zero results to truncate to zero.

Concretely: if `total_balance // increment` (i.e., total active balance expressed in `EFFECTIVE_BALANCE_INCREMENT` units) exceeds `adjusted_total_slashing_balance` (in raw Gwei), then `penalty_per_effective_balance_increment` truncates to `0`. Since `EFFECTIVE_BALANCE_INCREMENT` is `1e9` Gwei, this condition reduces to:

`adjusted_total_slashing_balance < total_balance / 1e9`

i.e. the slashed balance for the epoch (in Gwei) is smaller than the total active balance expressed in "ETH-count" units. Because `adjusted_total_slashing_balance = min(sum(state.slashings) * PROPORTIONAL_SLASHING_MULTIPLIER_BELLATRIX, total_balance)`, this can happen whenever the sum of slashed effective balances accumulated over `EPOCHS_PER_SLASHINGS_VECTOR` epochs is comparatively very small versus the *total* validator set (e.g., a single, low-balance validator slashed on an otherwise large validator set). In that scenario `penalty_per_effective_balance_increment` becomes exactly `0`, and every slashed validator processed in that epoch — no matter how large their `effective_balance` — receives `penalty = 0 * effective_balance_increments = 0` from the correlation-penalty component of `process_slashings`.

### Impact Explanation
This breaks the intended equality that the correlation slashing penalty scales with `effective_balance / total_balance * adjusted_total_slashing_balance` (a Gwei amount that the protocol commits to burn from the slashed validator's balance). When the division rounds to zero, that Gwei is *not* destroyed/decreased as the protocol design requires — the slashed validator retains balance it should have lost. This is an unauthorized mutation of the economic outcome the spec commits to: Gwei that should be destroyed is instead effectively "paid" (left) to the slashed validator, a non-owner of that amount under the slashing rules. (Note: the immediate, separate `slashing_penalty = effective_balance // MIN_SLASHING_PENALTY_QUOTIENT_ELECTRA` in `slash_validator` still applies at the time of slashing, so this only zeroes out the *additional* correlation penalty applied during epoch processing — it does not zero the validator's entire penalty, but it does silently disable the security-critical correlation-penalty mechanism, which is precisely the security measure meant to scale punishment with the severity of a mass-slashing event.)

### Likelihood Explanation
The trigger condition depends purely on protocol state (ratio of aggregate slashed-effective-balance to total active balance across `EPOCHS_PER_SLASHINGS_VECTOR`), not on any malicious coalition, client bug, or foreign key — any spec-following node reaches the same (wrong) result. It is most likely to occur on validator sets with a very large total active balance and comparatively few/low-balance slashings within the slashings window, which becomes increasingly plausible as total active balance grows over time (a documented long-term trend).

### Recommendation
Restore the multiply-before-divide order used pre-Electra, e.g. compute the penalty per validator (or per increment) as:

```python
penalty_per_effective_balance_increment = (
    adjusted_total_slashing_balance * increment // total_balance
)
```

or equivalently keep the numerator un-truncated until the final division, mirroring the phase0/altair/bellatrix `penalty_numerator // total_balance * increment` pattern, to avoid losing precision from truncating `total_balance // increment` before using it as a divisor.

### Proof of Concept
1. Let `increment = EFFECTIVE_BALANCE_INCREMENT = 1_000_000_000` Gwei.
2. Suppose the network has grown so that `total_balance = 100_000_000 * 1_000_000_000` Gwei (100,000,000 ETH-equivalent total active balance).
3. In the relevant epoch, only a single low-balance validator is slashed (e.g. effective balance `32 * 1_000_000_000` Gwei), so `sum(state.slashings) = 32_000_000_000`. With `PROPORTIONAL_SLASHING_MULTIPLIER_BELLATRIX = 3`: `adjusted_total_slashing_balance = min(96_000_000_000, total_balance) = 96_000_000_000`.
4. `total_balance // increment = 100_000_000` (i.e., 100 million "increment units").
5. `penalty_per_effective_balance_increment = 96_000_000_000 // 100_000_000 = 960` — non-zero here, but as `total_balance` grows further (e.g. 10x more, to 1,000,000,000 ETH-equivalent, or with a smaller `adjusted_total_slashing_balance` from fewer/smaller slashings), the same computation truncates to `0`: e.g. with `total_balance // increment = 1_000_000_000` and `adjusted_total_slashing_balance = 96_000_000_000`, `96_000_000_000 // 1_000_000_000 = 96` (still nonzero, showing the sensitivity), and with even smaller slashed balance relative to total active balance the quotient reaches `0` exactly — demonstrating the division order allows the correlation penalty to collapse to zero for arbitrarily large but realistic `effective_balance` validators, unlike the multiply-first formula used in earlier forks which does not exhibit this collapse for the same inputs.
