### Title
Malicious current-tenure miner can indefinitely refresh its own inactivity timer with stale/conflicting proposals, preventing fallback to the prior miner - (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary

### Finding Description
`SortitionData::check_latest_block_in_tenure` in `stacks-signer/src/chainstate/mod.rs` explicitly calls `signer_db.update_last_activity_time(&block.header.consensus_hash, get_epoch_time_secs())` whenever a *conflicting or too-low* block proposal is received for the current tenure, treating the mere receipt of an invalid proposal as "miner activity": [1](#0-0) 

This activity timestamp is later consumed by `SortitionState::is_timed_out` (v1) to decide whether the current miner has gone silent for longer than `block_proposal_timeout`: [2](#0-1) 

`is_timed_out` is the sole gate that lets the signer fall back to the prior tenure's miner when the current sortition winner stalls (`check_miner_inactivity` -> `is_timed_out` -> fall back to `make_miner_state(prior sortition)`), as documented in the signer flow doc: [3](#0-2) 

Because a single miner (the current sortition winner - a "one-slot" actor requiring no other signer's cooperation) can broadcast an arbitrary stream of block proposals that reference its own tenure's `consensus_hash` but are lower than / conflicting with the tenure's already-known tip, each such proposal resets `last_activity_time` for that tenure via `check_latest_block_in_tenure` (reached through `confirms_latest_block_in_same_tenure` on every proposal evaluation path, both for own-tenure and tenure-change checks). As long as the miner keeps sending such junk proposals more frequently than `block_proposal_timeout`, `is_timed_out` never returns `true`, and the miner is never invalidated nor is the state machine capable of falling back to the previous tenure's miner.

This is the analog of the report's root cause: a piece of signer state (the activity/liveness timer) is refreshed based on an elapsed-time computation triggered by attacker-controlled input, without the refresh being gated on the *validity* of what triggered it (a signature or accepted block), enabling the timer to be perpetually "renewed" and defeating the purpose of the timeout it feeds. In the reward-farming report, a missing update let stale state be reused to double-count a reward; here, an over-eager update lets stale/invalid miner behavior be perpetually counted as fresh activity, wedging the fallback state machine.

### Impact Explanation
This is a liveness wedge reachable by a single actor (the current sortition's miner) with no cooperation from other signers, no majority, and no compromised keys. By feeding a continuous stream of invalid/conflicting proposals for its own tenure, a malicious current miner can indefinitely suppress `is_timed_out`, preventing:
- The signer set from marking the miner `InvalidatedBeforeFirstBlock`/falling back to the prior tenure via `check_miner_inactivity`.
- Chain progress being handed to the honest prior miner even though the current miner is not actually producing any signable, valid block.

This matches the accepted High-impact class: "a signer wedged into never signing valid blocks... or acting on a stale reward set/threshold" - here the signer network is wedged from timing out the miner and progressing the state machine, even though no valid block is ever produced.

### Likelihood Explanation
The comment at the call site ("The miner may just be slow, so count this invalid block proposal towards valid miner activity") indicates this behavior is a deliberate design trade-off intended to tolerate a legitimately slow/rebuilding miner, not an oversight. This substantially reduces confidence that it is an unintended vulnerability versus an accepted trade-off, since the same mechanism is exercised by every test exercising `check_latest_block_in_tenure`/`is_timed_out` without apparent guardrails against abuse (e.g., no rate limiting or bound on how many times a single miner's junk proposals can extend the window). I could not find any additional bound (e.g., "activity can only be extended a limited number of times" or "extension requires the elapsed time since the *first* invalid proposal to stay under some cap") that would prevent an attacker from indefinitely renewing the window purely by rate of proposal submission alone. Without being able to fully verify node-side proposal-rate limiting (`stacks-node/src/nakamoto_node/`) outside the excerpts reviewed, I can't rule out that a network-level or node-level throttle mitigates the practical exploitability of this path, which is why likelihood is assessed as uncertain rather than confirmed high.

### Recommendation
Bound how much cumulative time an inactive/never-producing miner can gain from repeated invalid or conflicting proposals — for example, cap `update_last_activity_time` extensions per tenure to a fixed number of occurrences, or track the elapsed time since the *first* activity-qualifying invalid proposal in the tenure (analogous to `first_proposal_burn_block_timing`) rather than resetting a rolling clock on every subsequent invalid proposal. Only genuine progress (a locally/globally accepted or pre-committed block) should be able to indefinitely extend the inactivity window.

### Proof of Concept
1. Attacker wins a sortition and becomes the current tenure's miner.
2. Attacker never produces a valid block that advances the chain, but repeatedly broadcasts `BlockProposal` messages for its own tenure (`consensus_hash` = current tenure) with `chain_length` at or below the tenure's already-known tip (or, if none exists yet, any input that reaches the `check_latest_block_in_tenure` early-rejection branch).
3. Each such proposal, evaluated via `confirms_latest_block_in_same_tenure` -> `check_latest_block_in_tenure`, triggers `signer_db.update_last_activity_time(&block.header.consensus_hash, get_epoch_time_secs())` because it is treated as valid miner activity (per the "the miner may just be slow" branch).
4. As long as the interval between such proposals stays under `block_proposal_timeout`, `SortitionState::is_timed_out` (or the v2 equivalent) never returns `true` for this tenure.
5. `check_miner_inactivity`'s fallback path to the prior tenure's miner is never triggered, wedging the network on a miner that produces no valid, signable blocks. [4](#0-3) [5](#0-4)

    pub fn check_latest_block_in_tenure(
        tenure_id: &ConsensusHash,
        block: &NakamotoBlock,
        signer_db: &mut SignerDb,
        client: &StacksClient,
        tenure_last_block_proposal_timeout: Duration,
        reorg_attempts_activity_timeout: Duration,
    ) -> Result<bool, ClientError> {
        let last_block_info = SortitionData::get_tenure_last_block_info(
            tenure_id,
            signer_db,
            tenure_last_block_proposal_timeout,
        )?;

        if let Some(info) = last_block_info {
            // N.B. this block might not be the last globally accepted block across the network;
            // it's just the highest one in this tenure that we know about.  If this given block is
            // no higher than it, then it's definitely no higher than the last globally accepted
            // block across the network, so we can do an early rejection here.
            if block.header.chain_length <= info.block.header.chain_length {
                warn!(
                    "Miner's block proposal does not confirm as many blocks as we expect";
                    "proposed_block_consensus_hash" => %block.header.consensus_hash,
                    "signer_signature_hash" => %block.header.signer_signature_hash(),
                    "proposed_chain_length" => block.header.chain_length,
                    "expected_at_least" => info.block.header.chain_length + 1,
                );
                if info.signed_group.is_none_or(|signed_time| {
                    signed_time + reorg_attempts_activity_timeout.as_secs() > get_epoch_time_secs()
                }) {
                    // Note if there is no signed_group time, this is a locally accepted block (i.e. tenure_last_block_proposal_timeout has not been exceeded).
                    // Treat any attempt to reorg a locally accepted block as valid miner activity.
                    // If the call returns a globally accepted block, check its globally accepted time against a quarter of the block_proposal_timeout
                    // to give the miner some extra buffer time to wait for its chain tip to advance
                    // The miner may just be slow, so count this invalid block proposal towards valid miner activity.
                    if let Err(e) = signer_db.update_last_activity_time(
                        &block.header.consensus_hash,
                        get_epoch_time_secs(),
                    ) {
                        warn!("Failed to update last activity time: {e}");
                    }
                }
                return Ok(false);
            }

    pub fn is_timed_out(
        sortition: &ConsensusHash,
        db: &SignerDb,
        block_proposal_timeout: Duration,
    ) -> Result<bool, SignerChainstateError> {
        // If we've already signed a block in this tenure, the miner can't have timed out: we have
        // committed a signature to this tenure and must not help abandon it.
        //
        // Importantly, a block we have only pre-committed to does not count! A pre-commit carries
        // no signature, and if it never reaches the pre-commit threshold the tenure can stall
        // indefinitely. Treating it as signed here would suppress the inactivity timeout for
        // exactly the signers that pre-committed, so they could never fall back to the prior
        // miner and the tenure could never recover.
        let has_block = db.has_signed_block_in_tenure(sortition)?;
        if has_block {
            return Ok(false);
        }
        let Some(received_ts) = db.get_burn_block_receive_time_ch(sortition)? else {
            return Ok(false);
        };
        let received_time = UNIX_EPOCH + Duration::from_secs(received_ts);
        let last_activity = db
            .get_last_activity_time(sortition)?
            .map(|time| UNIX_EPOCH + Duration::from_secs(time))
            .unwrap_or(received_time);

        let Ok(elapsed) = std::time::SystemTime::now().duration_since(last_activity) else {
            return Ok(false);
        };

        if elapsed > block_proposal_timeout {
            info!(
                "Tenure miner was inactive too long and timed out";
                "tenure_ch" => %sortition,
                "elapsed_inactive" => elapsed.as_secs(),
                "config_block_proposal_timeout" => block_proposal_timeout.as_secs()
            );
        }
        Ok(elapsed > block_proposal_timeout)
    }
