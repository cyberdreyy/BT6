### Title
Instant-withdraw receipt double payout after funded claim leaves stale per-epoch basis claimable in default recovery - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external bug is about a recycled map slot retaining "special fields" that are only cleaned up by a later path. `IdleCreditVault` has the same shape: `claimInstantWithdrawRequest` clears only the aggregate `instantWithdrawsRequests[_user]` and pays the user, but never clears the per-epoch fields `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`. Those stale fields are later consumed by `finalizeDefaultRecovery` / `_claimDefaultedInstantWithdrawRequest`, letting a user be paid twice for the same receipt and inflating the default recovery basis.

### Finding Description
In `claimInstantWithdrawRequest` (IdleCreditVault.sol:380-393) the claim path burns the receipt tokens, zeroes `instantWithdrawsRequests[_user]` and transfers the funded underlyings, but does not touch:

- `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` (written at line 371)
- `instantWithdrawClaimsByEpoch[currentEpoch]` (written at line 372)

If the borrower defaults later in the same epoch (epochNumber only increments on `deposit` during `stopEpoch`, lines 607-610), `finalizeDefaultRecovery` reads `instantWithdrawClaimsByEpoch[epochNumber]` inside `defaultPendingClaimBasis` (lines 644-649) — which still includes the already-claimed amount — inflating `totalBasis` and diluting `defaultRecoveryPrice` for every other claimant (line 688).

Worse, `_claimDefaultedInstantWithdrawRequest` (lines 842-856) reads the stale `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` and pays `claimBasis * defaultRecoveryPrice` from `defaultRecoveryReserve`. The only guard is `instantWithdrawsRequests[_user] -= claimBasis` (line 848), which underflows only if the user has no newer instant request. An attacker who re-requests an instant withdrawal in the same epoch after claiming keeps the aggregate non-zero, so the stale basis pays out again — one receipt, two payouts.

Attack sequence (instant mode, epoch N, all roles honest):

1. Attacker (KYC'd lender holding tranche tokens) calls `requestInstantWithdraw` → `instantWithdrawsRequestsByEpoch[attacker][N] = A`, `instantWithdrawsRequests = A`.
2. Honest borrower/manager funds the request via `collectInstantWithdrawFunds`; `pendingInstantWithdraws` decreases but `instantWithdrawClaimsByEpoch[N]` stays at A.
3. Attacker calls `claimInstantWithdrawRequest` → receives A underlying; aggregate zeroed; per-epoch fields left attached (the "uncancelled field on recycle").
4. Attacker calls `requestInstantWithdraw` again for B → aggregate = B, `instantWithdrawsRequestsByEpoch[attacker][N] = A+B`.
5. Borrower defaults and `finalizeDefault`/`finalizeDefaultRecovery` runs in epoch N → `defaultRecoveryEpoch = N`, `defaultInstantWithdrawsFinalized = true` (any unfunded remainder keeps `pendingInstantWithdraws != 0`), basis inflated by A.
6. Attacker calls `claimInstantWithdrawRequest` → `_claimDefaultedInstantWithdrawRequest` returns `claimBasis = A+B`, subtracts B from aggregate (no underflow), burns B, and transfers `(A+B) * defaultRecoveryPrice` from the recovery reserve — paying A a second time.

### Impact Explanation
Direct theft from `defaultRecoveryReserve`: the attacker is paid `A * defaultRecoveryPrice` more than entitled, depleting the reserve that backs other defaulted-epoch receipt holders and post-default requesters (`_claimPostDefaultWithdrawRequest`, `DefaultDistributor` claims). Additionally, `instantWithdrawClaimsByEpoch[N]` is never decremented on funded claims, so `defaultPendingClaimBasis` permanently overstates the recovery basis, lowering `defaultRecoveryPrice` and socializing the loss onto honest claimants. Quantified loss: up to the attacker's claimed instant amount A (bounded only by their tranche balance) per defaulted epoch.

### Likelihood Explanation
Requirements: instant withdrawals enabled on the vault, a funded-then-claimed instant receipt, a second instant request, and a borrower default finalized in the same epoch. Defaults are a designed-for flow (`finalizeDefaultRecovery`, `defaultRecoveryEpoch` machinery exists precisely for this), and the attacker controls all timing except the honest manager/borrower funding and default calls. No privileged collusion, no donation, no oracle dependence — the stale bookkeeping alone causes the overpayment.

### Recommendation
Mirror the "cancel fields on recycle" fix: when a funded instant receipt is claimed in `claimInstantWithdrawRequest`, also clear `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and decrement `instantWithdrawClaimsByEpoch[epochNumber]` by the claimed amount, so only genuinely unfunded receipts remain in the default-recovery basis. Alternatively, track funded-vs-pending instant basis per user/epoch explicitly so `_claimDefaultedInstantWithdrawRequest` can never pay basis that was already satisfied at par.

```solidity
// SPDX-License-Identifier: MIT
// Foundry fork PoC sketch against the deployed vault + IdleCDOEpochVariant.
// Assumes instant withdrawals enabled, attacker is a KYC-passed AA holder.
function testInstantReceiptDoubleClaim() public {
    // --- epoch N running ---
    uint256 A = 100e6;
    vm.prank(attacker);
    cdo.requestInstantWithdraw(A);              // strategy.requestInstantWithdraw
    // honest ops fund the instant request
    vm.prank(borrowerOps);
    cdo.collectInstantWithdrawFunds(A);         // pendingInstantWithdraws -> 0
    vm.prank(attacker);
    cdo.claimInstantWithdrawRequest();          // paid A at par; per-epoch fields stale
    // recycle the slot in the SAME epoch (epochNumber unchanged)
    uint256 B = 50e6;
    vm.prank(attacker);
    cdo.requestInstantWithdraw(B);
    // borrower defaults; manager finalizes recovery in epoch N
    vm.prank(manager);
    cdo.finalizeDefaultRecovery(recovered, source);
    // stale A is inside instantWithdrawClaimsByEpoch[N] => basis inflated,
    // defaultRecoveryPrice diluted for everyone.
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdo.claimInstantWithdrawRequest();          // pays (A+B)*price, not B*price
    assertGt(underlying.balanceOf(attacker) - balPre,
             B * strategy.defaultRecoveryPrice() / 1e18);
}
```
