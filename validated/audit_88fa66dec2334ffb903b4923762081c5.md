### Title
Stale confirmations from removed multisig members are still counted toward the execution threshold - (File: `multisig/src/lib.rs`, `multisig2/src/lib.rs`)

### Summary
The confirmation-counting logic in both multisig implementations tallies confirmations stored in a per-request set without re-validating that every confirming principal is still a current, live member/key of the multisig at the moment the threshold check (`confirmations.len() as u32 + 1 >= self.num_confirmations`) is evaluated. When a member/key is removed via `DeleteKey`/`DeleteMember`, only requests that member *originated* are cleaned up; confirmations that member previously cast on *other* still-pending requests are left in the `confirmations` map. A later confirmation by a genuinely live member can then push the count to threshold, executing the request even though one of the counted approvals came from an account that is no longer part of the multisig.

### Finding Description
`confirm()` in `multisig2/src/lib.rs` performs the following check: [1](#0-0) 

It compares `confirmations.len()` (a historical record of who confirmed) against `self.num_confirmations` (a live threshold), but never intersects the stored confirmation set with the currently live `self.members` set.

In the original `multisig/src/lib.rs`, `DeleteKey` handling only purges requests whose *signer_pk* (the original requester) equals the deleted key — it does not walk other pending requests to strip that key's confirmation from their `confirmations` sets: [2](#0-1) 

`multisig2`'s `DeleteMember` action follows the same execution pattern (`self.delete_member(promise, member)` inside `execute_request`), with no visible reconciliation of `self.confirmations` for requests the removed member had previously confirmed but did not create: [3](#0-2) 

The binding that should hold is: *confirmations counted toward `num_confirmations` == confirmations from members who are members at execution time*. Because stale entries persist, `confirmations counted > confirmations from live members`, i.e. the equality is broken and a request can execute with fewer live approvals than the configured threshold.

### Impact Explanation
This falls under the Critical impact category explicitly listed as in-scope: "a multisig request executed below threshold." A transfer, `AddKey`/`AddMember`, `DeployContract`, or arbitrary `FunctionCall` request could be pushed to execution with only `K-1` (or fewer) currently-authorized approvals, with the deficit filled by a stale confirmation from a member that governance intentionally removed (e.g., after a suspected key compromise or an off-boarded signer). This directly undermines the core custody guarantee of the multisig (funds/authority movement gated by exactly K live members).

### Likelihood Explanation
Exploitation requires a realistic operational sequence with no privileged/red-flag actions beyond ordinary multisig governance:
1. Member/key A confirms pending request R (1 of K confirmations).
2. Multisig later executes a separate, unrelated request that removes A via `DeleteMember`/`DeleteKey` (routine key rotation).
3. R is still pending; a different live member confirms R, and R's confirmation count reaches `num_confirmations`, executing R — counting A's earlier confirmation even though A no longer has authority.
No attacker needs special privileges beyond being a normal (even soon-to-be-former) member; the flaw is triggered by ordinary multisig lifecycle events (member rotation) rather than by an external attacker forging signatures.

### Recommendation
When tallying confirmations in `confirm()`, filter the stored confirmation set against the current `self.members` (or, for `multisig/src/lib.rs`, verify each stored pk still has an active access key) before comparing against `num_confirmations`. Additionally, on `DeleteMember`/`DeleteKey`, iterate over **all** pending requests (not just ones originated by that member) and remove the departing member's entry from each request's `confirmations` set, mirroring the cleanup already partially done for self-originated requests.

### Proof of Concept
1. Deploy a 2-of-3 `multisig2` contract with members A, B, C (`num_confirmations = 2`).
2. A calls `add_request_and_confirm` for a large `Transfer` request R (1 confirmation: A).
3. Separately, submit and fully confirm a `DeleteMember { member: A }` request (using B and C's confirmations), removing A from `self.members`.
4. B now calls `confirm(R)`. `confirmations.len()` for R is `1` (from A, still stored) `+ 1` (from B) `= 2 >= num_confirmations`, so `execute_request` runs the transfer — even though A is no longer a member and only one currently-live member (B) actually approved R.

Note: I was unable to view the full body of `delete_member`/`add_member` in `multisig2/src/lib.rs` (index truncation), so I cannot fully confirm whether it performs confirmation cleanup elsewhere in the file; the analysis is based on the visible `execute_request` dispatch and the confirmed absence of such cleanup in the analogous `multisig/src/lib.rs` `DeleteKey` path. A Devin session with full repository access would be needed to verify `delete_member`'s complete implementation.
