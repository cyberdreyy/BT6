### Title
Time-of-check/time-of-use race in `jwtReplayCache` allows a JWT `jti` to authorize two concurrent requests instead of exactly one - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
`WorkflowMetadataHandler.Authorize` checks JWT replay status via `jwtCache.isReplay(claims.ID)` and only marks the token as used via `jwtCache.recordUsage(claims.ID)` after several unguarded checks (`authorizedKeys` lookup, signer validation). The check and the commit are two separate lock acquisitions with no atomicity across the whole `Authorize` call, so two goroutines that call `Authorize` concurrently with the same intercepted, still-valid JWT can both pass the `isReplay` check before either calls `recordUsage`, resulting in the single signed token authorizing two distinct requests.

### Finding Description
In `Authorize` [1](#0-0) , the sequence is:
1. `claims, signer, err := utils.VerifyRequestJWT(token, *req)` — validates the JWT signature/claims.
2. `if h.jwtCache.isReplay(claims.ID) { ... return err }` — check-only, takes an `RLock` on `jwtReplayCache.mu` and releases it immediately [2](#0-1) .
3. `keys, exists := h.authorizedKeys[workflowID]` and signer-authorization lookup — no locking of `jwtCache` at all.
4. `h.jwtCache.recordUsage(claims.ID)` — the commit step, takes a separate `Lock` on `jwtReplayCache.mu` [3](#0-2) .

Because the check (`isReplay`) and the commit (`recordUsage`) are not performed under a single critical section covering the whole `Authorize` execution, an attacker holding one valid, intercepted JWT (with a fixed `jti` in `claims.ID`) can fire two (or more) requests in parallel to the same `Authorize` path. Both goroutines can observe `isReplay(claims.ID) == false` before either calls `recordUsage(claims.ID)`, since there's a window between step 2 and step 4 during which the cache is not locked. Both requests then proceed to pass the authorized-key check and both return a valid `*gateway.AuthorizedKey`, defeating the intended "exactly-once" JWT semantics documented in the comment "jwtReplayCache manages used JWT IDs to prevent replay attacks" [4](#0-3) .

`Authorize` is invoked from `http_trigger_handler.go`, which is the code path serving inbound gateway/HTTP trigger requests (attacker-reachable via a signed, intercepted JWT that they possess), confirming the entry point is attacker-controllable. I was not able to fully inspect `http_trigger_handler.go`'s exact call context (parameters, whether it's per-request or otherwise gated) due to tool budget, so the precise upstream wiring around the `Authorize` call is not fully verified, but the vulnerable check-then-act pattern itself is unambiguous from the function body shown.

### Impact Explanation
This is a request-binding / exactly-once violation: an attacker who has one valid, signed JWT (e.g., intercepted via any legitimate means available to them as a low-privileged caller) can cause it to authorize two concurrent workflow-trigger executions instead of one. This maps to duplicate authorized action / double execution from a single signed grant, potentially causing duplicate job/workflow triggers, resource consumption, or (depending on what the authorized action does downstream) duplicate fund-moving or state-changing operations if such actions are gated solely by this JWT-based authorization.

### Likelihood Explanation
Preconditions: attacker must possess a single valid signed JWT for a workflow trigger request (obtainable through normal use by any caller entitled to send one signed request) and the ability to send it twice in quick succession/parallel — both are trivial for an unprivileged party who already has one valid token. No elevated privileges are required beyond what's needed to obtain any single valid JWT for this endpoint. The race window is narrow but real and deterministically reproducible under concurrent load or with synchronization primitives in a test, making it a realistic, repeatable condition rather than a theoretical one.

### Recommendation
Make check-and-set atomic: acquire the `jwtReplayCache` lock once and perform both the existence check and insertion under the same critical section (e.g., add a `checkAndRecord(jti) bool` method using a single `Lock()` that returns false if already present or inserts and returns true), and call it immediately after JWT signature verification, before doing any other work. Example:
```go
func (cache *jwtReplayCache) checkAndRecord(jti string) bool {
    cache.mu.Lock()
    defer cache.mu.Unlock()
    if _, exists := cache.cache[jti]; exists {
        return false
    }
    cache.cache[jti] = time.Now()
    return true
}
```
And in `Authorize`, replace the separate `isReplay`/`recordUsage` calls with a single `checkAndRecord` call guarding the rest of the authorization logic.

### Proof of Concept
Go concurrency test in `workflow_metadata_handler_test.go`:
1. Construct a `WorkflowMetadataHandler` with a registered `workflowID` and one authorized signer key.
2. Create a single valid JWT (fixed `claims.ID`/`jti`) signed by the authorized key for a given `req`.
3. Launch two goroutines that both call `h.Authorize(workflowID, token, req)` simultaneously (use a `sync.WaitGroup` and a barrier/channel to maximize the race window, or inject a small `time.Sleep` between `isReplay` and `recordUsage` via test hook to reliably trigger the race).
4. Collect both results; assert that exactly one call returns `(*gateway.AuthorizedKey, nil)` and the other returns an error ("JWT token has already been used..."). 
5. Run under `go test -race -count=100` to demonstrate the race is real and repeatable; observe that the current implementation intermittently allows both calls to succeed, whereas after the fix exactly one always succeeds.

```go
func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}
```
