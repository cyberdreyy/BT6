### Title
Anyone can set `unscaledApr` and `lastApr` on `IdleCreditVault` while `idleCDO` is unset - (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`IdleCreditVault.setApr` deliberately disables its only access check while `idleCDO == address(0)`, mirroring the RocketPool `deployed`-flag bug: a permission gate that is inert until a later "wiring" transaction. During that window any EOA can call `setApr`, `setAprs`, or `setAprsWithBuffer` and write both `lastApr` and `unscaledApr`. `unscaledApr` is written unconditionally in `setAprs`/`setAprsWithBuffer` *before* `setApr` runs and is not bounded by `maxApr`, so the attacker controls a value that persists after wiring and drives epoch accounting (`unscaledApr == 0` selects the APR0 request path and gates `prepareStopEpochWithApr0`).

### Finding Description
In `setApr` (lines 225-235):

```solidity
function setApr(uint256 _apr) public {
    address _cdo = idleCDO;
    // if cdo is not yet set we skip the check (this can happen only during the setup)
    if (_cdo != address(0)) {
      if (msg.sender != _cdo && msg.sender != manager) revert NotAllowed();
    }
    uint256 _maxApr = maxApr;
    if (_maxApr != 0 && _apr > _maxApr) revert NotAllowed();
    lastApr = _apr;
}
```

`setAprs` (lines 206-210) and `setAprsWithBuffer` (lines 217-220) assign `unscaledApr = _unscaledApr` with **no cap and no access check at all**, then delegate to `setApr`. Until the owner calls `setWhitelistedCDO` (lines 954-957), `idleCDO` is `address(0)` and the `if (_cdo != address(0))` guard is skipped — identical structure to the RocketPool `onlyDAOProtocolProposal` modifier that is inert until `settingsNameSpace.deployed` is set.

After wiring, the attacker-written `unscaledApr` is live state: `requestWithdraw` branches on `unscaledApr == 0` (line 285), and `prepareStopEpochWithApr0` reverts if `apr0TotalPrincipal != 0 && unscaledApr != 0` (lines 502-508). `lastApr` feeds `getApr()`/`expectedEpochInterest`, i.e. the borrower debt the CDO will demand at `stopEpoch`.

### Impact Explanation
If the strategy is ever initialized and wired in separate transactions, an attacker front-runs the wiring tx:

1. **Yield theft via APR manipulation**: set `lastApr`/`unscaledApr` so that `expectedEpochInterest` is priced at attacker-chosen values (up to `maxApr`, default `DEFAULT_MAX_APR = 20e18`, for `lastApr`). If the attacker is a KYC'd LP, inflated borrower interest accrues to their tranche; if set to 0, depositors' yield for the epoch is destroyed and the honest borrower underpays, breaking the fair yield split invariant.
2. **Permanent freezing via `unscaledApr` poisoning**: `unscaledApr` is uncapped and unchecked at write time. Setting it non-zero while APR0 requests exist (or setting it such that later APR0 flows revert in `prepareStopEpochWithApr0` line 506-508) bricks `stopEpoch`, freezing all pending withdraws — a permanent freezing of user funds until owner intervention, or insolvency-equivalent accounting corruption since `unscaledApr` is only re-writable by CDO/manager going forward.

Either way the broken invariant is access control on a state-changing pricing parameter, with quantified impact bounded by `maxApr * TVL` of misdirected/frozen yield.

### Likelihood Explanation
Requires `initialize` and `setWhitelistedCDO` to be in different transactions/blocks. The in-code comment ("this can happen only during the setup") confirms the authors anticipated a multi-transaction setup; `setWhitelistedCDO` is a separate owner call, not part of `initialize` (lines 124-158). Deployment via `IdleCreditVaultFactory` appears to wire contracts together, but the contract is also upgradeable and can be re-pointed or deployed manually — any non-atomic deployment path exposes the window. I could not fully verify the factory's atomicity for every deployment path within the available context, so the residual risk hinges on operational setup rather than code correctness — the same class the RocketPool finding flagged.

### Recommendation
Remove the "setup window" entirely: require `msg.sender == owner()` when `idleCDO == address(0)` (or set `idleCDO` inside `initialize`), and apply the `maxApr` bound to `unscaledApr` in `setAprs`/`setAprsWithBuffer` before the write. Do not let any access check be conditional on a flag that is set in a later transaction.

### Proof of Concept
Foundry fork PoC sketch:

```solidity
// Strategy deployed and initialized, but setWhitelistedCDO not yet called.
IdleCreditVault strategy = IdleCreditVault(proxyAddress); // idleCDO == address(0)

address attacker = makeAddr("attacker");
vm.prank(attacker);
strategy.setAprs(type(uint256).max, strategy.maxApr()); // succeeds: guard skipped

assertEq(strategy.unscaledApr(), type(uint256).max); // uncapped, persists after wiring

// Owner wires the CDO afterwards
vm.prank(owner);
strategy.setWhitelistedCDO(address(cdo));

// Attacker value is now locked in: requestWithdraw APR0 routing and
// prepareStopEpochWithApr0 now operate on attacker-chosen unscaledApr,
// and lastApr == maxApr inflates expectedEpochInterest owed by borrower.
```

Note: success of the full exploit chain depends on a non-atomic initialize → `setWhitelistedCDO` sequence; I could not exhaustively confirm the factory always wires both in one transaction, but the guard-skip branch exists precisely because such a window was contemplated.
