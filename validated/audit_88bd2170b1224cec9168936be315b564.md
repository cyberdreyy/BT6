### Title
Job-controlled `::add-mask::` fragmentation defeats static masking of `CI_JOB_TOKEN`/protected variables in the same job's trace - ([File: common/buildlogger/build_logger.go], [File: commands/helpers/proxy_exec.go], [File: common/buildlogger/internal/masker/masker.go])

### Summary
When `ProxyExec` is enabled, a job's script output is masked twice, sequentially: first by the external `addmask` trie (dynamic, `::add-mask::`-driven, running inside the `gitlab-runner-helper proxy-exec` child process) and then by the runner's own contiguous-byte `masker` (static, driven by `MaskPhrases` such as `CI_JOB_TOKEN` and other `Masked: true` variables, running in the parent process via `buildlogger.Logger.wrap`). Because `addmask` runs upstream of `masker` and both operate on raw byte streams, a job can register (via `::add-mask::`) a phrase that is a proper substring of its own already-masked `CI_JOB_TOKEN`/protected-variable value; `addmask` then breaks the token's byte run apart when it substitutes that substring, so the downstream `masker` phrase-matcher — which only recognizes an exact contiguous run of the full secret — never re-assembles a match and lets the surrounding prefix/suffix bytes of the secret pass through to the trace unmasked.

### Finding Description
- `shells/proxy_exec.go`'s `ProxyExecShell.GetEntrypointCommand`/`GetConfiguration` wrap the entire job entrypoint with `gitlab-runner-helper proxy-exec` when `IsProxyExec()` is set. [1](#0-0) 
- Inside that helper subprocess, `commands/helpers/proxy_exec.go`'s `Proxy.Stdout()/Stderr()` route the job script's raw stdout/stderr through `addmask.Get(...)`, which applies any phrases registered at runtime via `::add-mask::` directives (persisted in the encrypted `store`, so registrations accumulate for the life of the job/temp dir). [2](#0-1) 
- The already-addmask-processed bytes are what actually reach the parent runner process's `os.Stdout/os.Stderr`, which are the very writers passed as `cmdOpts.Stdout/Stderr = s.BuildLogger.Stream(buildlogger.StreamWorkLevel, ...)` in every executor (`shell`, `custom`, `instance`, `virtualbox`, etc.). [3](#0-2) 
- `buildlogger.Logger.wrap` then applies the runner's own masking chain to that stream, and per its own documented order the phrase `masker` (built from `MaskPhrases`, i.e. `b.GetAllVariables().Masked()`, which includes `CI_JOB_TOKEN` and any protected/masked CI variable) is the *first* filter data hits after the sync writer. [4](#0-3) 
- `masker.Write` only recognizes a secret if its bytes arrive as one *contiguous* run matching `m.phrase` byte-for-byte (with a narrow fast path only for buffers that are exactly `"[MASKED]"`, `bytes.Equal(p, mask)`). [5](#0-4) 
- Because `addmask` (upstream) already substituted a substring of the secret with its own marker before the static `masker` ever sees the bytes, the byte run for the full secret is broken into `prefix + <marker> + suffix`, none of which contiguously matches `m.phrase`. The static masker therefore emits `prefix` and `suffix` as cleartext into the job trace, leaking fragments of `CI_JOB_TOKEN`/protected variable value that would otherwise have been fully replaced with `[MASKED]`.
- Attacker-controlled input: any pipeline author who can write job script content and has `ProxyExec` enabled can issue `echo "::add-mask::<substring-of-CI_JOB_TOKEN>"` followed by printing `$CI_JOB_TOKEN` (or any other masked/protected variable it can read from its own environment) to trigger this.
- Existing checks that fail to stop it: the static `masker` has no mechanism to detect that upstream masking already fragmented a secret it is supposed to protect; the `addmask` layer has no knowledge of, and no coordination with, the runner's static `MaskPhrases` set, so overlapping/substring registrations are never rejected or reconciled between the two layers.

### Impact Explanation
This lets an unprivileged pipeline author intentionally leak fragments (and, by chaining multiple substring `::add-mask::` calls, effectively the whole value byte-by-byte) of `CI_JOB_TOKEN` or any other job-scoped masked/protected variable into the job's own trace/log, which violates the runner's masking invariant ("masked values must remain masked regardless of add-mask ordering/overlap") and defeats the purpose of trace masking — namely, preventing exposure of secret values to anyone with read access to job logs but not to the underlying variable (e.g. broader project members with log-viewing rights, log exporters, downstream log-scraping tooling, or a compromised/negligent viewer without CI/CD variable permissions).

### Likelihood Explanation
- Requires only `ProxyExec` enabled for the job (a runner/job configuration option, not an admin-only control) and permission to write job script content — both squarely within a normal pipeline author's capability.
- No race condition or timing dependency: the interaction is deterministic based on write ordering/fragmentation, and reproducible on every run once the substring `::add-mask::` call precedes the print of the target secret.
- Easily repeatable and directly testable by extending the existing masking test harness.

### Recommendation
Do not let dynamically-registered `::add-mask::` phrases run upstream of, and independently from, the static secret masker. Options: (a) feed all `::add-mask::`-registered phrases back into the same runner-side `masker` phrase set (or vice versa, unify both into a single masking stage) so overlap/substring relationships are resolved with knowledge of all secrets simultaneously, longest-phrase-first as `masker.New` already does for its own phrase set; (b) reject/ignore `::add-mask::` registrations that are substrings of already-registered protected/masked variable values; (c) at minimum, run the static `masker` pass *before* handing data to the `addmask` layer (or re-run the static pass on `addmask`'s output while also treating any `addmask` marker byte sequence as fully opaque, and treat protected-variable phrases as impossible to arrive already-fragmented) so the full-token contiguous match is not deprived by upstream substitution.

### Proof of Concept
Extend `testBuildWithMasking` in `common/buildtest/masking.go` for the `proxy=true` case:
```go
if proxy {
    resp.Steps = append([]spec.Step{
        {
            Name: "before_script",
            Script: []string{
                // register a mask for only the middle chunk of MASKED_KEY's value
                `echo "::add-mask::ASKED_VAL"`, // substring of "MASKED_VALUE"
            },
            When: spec.StepWhenAlways,
        },
        {
            Name:   "script",
            Script: []string{`echo "leak: $MASKED_KEY"`},
        },
    }, resp.Steps...)
}
```
Then assert:
```go
assert.NotContains(t, string(contents), "MASKED_VALUE")
assert.NotContains(t, string(contents), "leak: M")   // prefix fragment must not leak
assert.NotContains(t, string(contents), "UE")         // suffix fragment must not leak
```
Currently, because `masker` requires a contiguous byte run and `addmask` already substituted the `"ASKED_VAL"` slice with its own marker before the static masker sees it, the surrounding `M` / `UE` fragments of `MASKED_VALUE` are expected to leak in cleartext — demonstrating the bypass. Running this against the current code should fail the "no fragment leaks" assertions, confirming the bug.

```go
type Proxy struct {
	store   *store.Store
	addmask *addmask.AddMask
}

func NewProxy(dir string, stdout, stderr io.Writer) (*Proxy, error) {
	db, err := store.Open(dir)
	if err != nil {
		return nil, err
	}

	pe := &Proxy{store: db}

	pe.addmask, err = addmask.New(db, stdout, stderr)
	if err != nil {
		return nil, err
	}

	return pe, nil
}

func (p *Proxy) Stdout() io.Writer {
	return p.addmask.Get(0)
}

func (p *Proxy) Stderr() io.Writer {
	return p.addmask.Get(1)
}
```
