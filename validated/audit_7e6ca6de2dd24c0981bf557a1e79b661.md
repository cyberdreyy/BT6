## Analog Found

### Title
JupLend deposit handler can revert on legitimate small deposits when the CPI-computed fToken share amount rounds to zero - ([File: programs/marginfi/src/instructions/juplend/deposit.rs])

### Summary
The Napier M-8 bug class ("adapter reverts when 0 shares are minted, blocking valid deposits") has a direct analog in marginfi's JupLend integration. `juplend_deposit` computes the number of fTokens it expects to mint from a user's underlying deposit using floor-division math, and this computation can legitimately floor to `0` for small (but non-zero) deposit amounts when the JupLend liquidity/token exchange prices are not exactly `1e12`. The handler unconditionally forwards the user's `amount` to a CPI `deposit()` call into the (real, on-chain) JupLend Earn program without ever checking whether the expected share output is non-zero/significant.

### Finding Description
`juplend_deposit` computes the expected shares to be minted using `expected_shares_for_deposit_from_rates`, which mirrors JupLend's two-step floor-division formula: [1](#0-0) 

This computation is proven, by the program's own unit tests, to floor to exactly `0` shares for small non-zero deposit amounts whenever the token exchange price exceeds `1e12`: [2](#0-1) [3](#0-2) 

Despite this known zero-floor behavior, `juplend_deposit` performs no minimum-output check before executing the transfer and CPI deposit call: [4](#0-3) 

The underlying (real, production) JupLend Earn program that this CPI targets explicitly defines an error for this exact scenario — `FTokenDepositInsignificant` (error code `6000`, `F_TOKEN_DEPOSIT_INSIGNIFICANT`) — indicating that the live JupLend program reverts deposits whose resulting fToken mint amount is insignificant/zero: [5](#0-4) 

Compare this to `juplend_init_position`, which at least enforces a minimum raw deposit amount (`amount >= 10`) — but that check is based on raw token amount, not on the resulting share count, so it does not protect `juplend_deposit` from the same class of failure at different (larger, but still price-sensitive) exchange-price ratios: [6](#0-5) 

This mirrors the Napier M-8 root cause precisely: the adapter/wrapper (`juplend_deposit`) forwards a user-chosen deposit amount straight into an underlying protocol's stake/deposit call without pre-validating that the resulting minted-share amount will be non-zero/significant, so the underlying protocol's own zero-share guard reverts the transaction.

### Impact Explanation
Users attempting a legitimate, non-zero deposit into a JupLend-wrapped marginfi bank can have their transaction unconditionally revert with `FTokenDepositInsignificant` whenever the deposit amount is small relative to the pool's current `token_exchange_price`/`liquidity_exchange_price` ratio (which grows over time as the pool accrues interest). This is a denial-of-service on deposits for affected amounts — as JupLend pools mature and exchange prices drift further from `1e12`, the "insignificant" amount threshold effectively rises, silently shrinking the range of deposit amounts that succeed. This does not cause fund loss or accounting corruption, but it is a durable availability/consistency issue matching the reported bug class (funds cannot be deposited under conditions the protocol should otherwise support).

### Likelihood Explanation
Likelihood is moderate: it requires (a) a JupLend bank whose `token_exchange_price` has drifted meaningfully above `1e12` (which happens naturally as yield accrues over the bank's lifetime), and (b) a user depositing a small amount relative to that price. Both conditions are permissionless/organic and require no privileged actor — any ordinary depositor can encounter this as pool age/yield increases.

### Recommendation
Before calling `cpi_juplend_deposit`, compute `expected_shares` (already done) and `require_gt!(expected_shares, 0, ...)` (or a reasonably small minimum threshold) so that the instruction fails early and predictably with a marginfi-specific error rather than depending on the downstream JupLend program's `FTokenDepositInsignificant` revert. Optionally, expose the minimum viable deposit amount for a given bank (as a function of current exchange prices) so integrators/UIs can proactively prevent users from submitting doomed-to-fail deposits.

### Proof of Concept
1. Let a JupLend-wrapped bank accrue interest so that `token_exchange_price > 1e12` (e.g., `1_200_000_000_000` / `1_500_000_000_000` per the existing test fixture) as shown in the repository's own test: [2](#0-1) 
2. A user calls `juplend_deposit` with a small non-zero `amount` (e.g., `amount = 1`) such that `expected_shares_for_deposit_from_rates(amount, liquidity_exchange_price, token_exchange_price)` evaluates to `0`, as demonstrated by the unit test `shares_for_deposit_tiny_amount_can_floor_to_zero`: [3](#0-2) 
3. The handler proceeds unconditionally to transfer the amount and CPI into the JupLend Earn program's `deposit`: [7](#0-6) 
4. On production JupLend, this CPI reverts with `FTokenDepositInsignificant` (code `6000`), causing the user's otherwise-valid deposit transaction to fail.
