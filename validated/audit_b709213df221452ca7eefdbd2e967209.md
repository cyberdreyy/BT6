**Analysis:**

The scenario described conflates two distinct staking mechanisms that don't operate on the same pool:

1. **`staking_contract::switch_operator`/`switch_operator_with_same_commission`** operate on a `StakingContract` resource stored in the staker's `Store`, tied to a stake pool owned by a per-staker/operator resource account [1](#0-0) . These pools are not `DelegationPool` resources.

2. **`delegation_pool::synchronize_delegation_pool`** requires a `DelegationPool` resource to exist at the target address via `assert_delegation_pool_exists(pool_address)` [2](#0-1) . A pool managed through `staking_contract` is not a delegation pool, so calling `synchronize_delegation_pool` on it would simply abort.

For delegation pools specifically, operator rotation happens through `delegation_pool::set_operator`, which calls `synchronize_delegation_pool(pool_address)` **before** invoking `stake::set_operator`, all within the same atomic transaction/function execution: [3](#0-2) 

Because Move transactions execute atomically, no external transaction (including an unprivileged call to `synchronize_delegation_pool`) can be interleaved between the `synchronize_delegation_pool` call and the subsequent `stake::set_operator` call inside `set_operator`. By the time the operator field changes on the stake pool, all commission accrued up to that point has already been bought into shares under the **old** operator's `beneficiary_for_operator` mapping via `buy_in_active_shares`/`buy_in_pending_inactive_shares`: [4](#0-3) 

Any subsequent call to `synchronize_delegation_pool` — by anyone, since it's permissionless by design — only computes drift (`calculate_stake_pool_drift`) accumulated *since* the last synchronization point, which is now under the new operator. It reads `stake::get_operator(pool_address)` and `beneficiary_for_operator(...)` at call time to route commission to whoever is *currently* the on-chain operator/beneficiary — this is correct attribution, not misrouting, since the caller's identity has no bearing on which operator/beneficiary receives the shares. The existing test `test_change_operator` confirms correct old/new operator commission separation across the switch boundary: [5](#0-4) .

There is no window where an unprivileged actor's call to `synchronize_delegation_pool` can cause pre-switch rewards to be attributed to the new operator's beneficiary instead of the old one.
