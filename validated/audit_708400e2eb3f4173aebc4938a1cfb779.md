### Title
Builder payment settlement bypasses the PTC quorum check — a builder payment can be escaped to `builder_pending_withdrawals` without meeting the weight threshold ([File: specs/gloas/beacon-chain.md])

### Summary
This is the same bug class as the `recoverTokens`/`creatorClaimSoldTokens` issue: two code paths mutate the *same* accounting record, but only one of them enforces the invariant that gates the payout, while the other path moves the value into the payable state unconditionally. In `specs/gloas/beacon-chain.md`, a `BuilderPendingPayment` accumulates a `weight` field via attester votes, and `process_builder_pending_payments` only turns a payment into a `BuilderPendingWithdrawal` if `payment.weight >= quorum`. However, `settle_builder_payment`, called from `apply_parent_execution_payload` on essentially every ordinary block, moves the *same* payment into `builder_pending_withdrawals` unconditionally whenever `payment.withdrawal.amount > 0`, with no weight/quorum check at all.

### Finding Description
`get_builder_payment_quorum_threshold` and the quorum check exist specifically to gate whether a builder payment is honored: [1](#0-0) 

```python
def process_builder_pending_payments(state: BeaconState) -> None:
    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:
        if payment.weight >= quorum:
            state.builder_pending_withdrawals.append(payment.withdrawal)
    ...
```

`payment.weight` is only ever incremented inside `process_attestation`, when attesters vote for the block/slot in the same slot they attest to: [2](#0-1) 

But the *same* `BuilderPendingPayment` record, indexed identically (`SLOTS_PER_EPOCH + parent_slot % SLOTS_PER_EPOCH` or `parent_slot % SLOTS_PER_EPOCH`), is also drained by `settle_builder_payment`, which is called from `apply_parent_execution_payload` for essentially every block whose parent is in the current or previous epoch — i.e. normal, non-degenerate chain operation: [3](#0-2) [4](#0-3) 

```python
def settle_builder_payment(state: BeaconState, payment_index: Uint64) -> None:
    assert payment_index < len(state.builder_pending_payments)
    payment = state.builder_pending_payments[payment_index]
    if payment.withdrawal.amount > 0:
        state.builder_pending_withdrawals.append(payment.withdrawal)
    state.builder_pending_payments[payment_index] = BuilderPendingPayment.empty()
```

`settle_builder_payment` checks only `payment.withdrawal.amount > 0` — it never reads `payment.weight` or compares it to `get_builder_payment_quorum_threshold(state)`. Because `apply_parent_execution_payload` runs `process_parent_execution_payload` *before* `process_operations` (which is what runs `process_attestation` and increments `weight`) in the very same block that would settle the *previous* slot's payment, and because this settlement path executes on every canonical block (the "current epoch"/"previous epoch" branches cover the overwhelming majority of blocks, leaving only the "> 2 epochs of missed slots" fallback to the weight-checked `process_builder_pending_payments` path — as shown explicitly by the regression test `test_builder_payment_after_missed_epochs`), the quorum requirement that `process_builder_pending_payments` enforces is dead weight for ordinary chain progression: `settle_builder_payment` pays the builder's fee out to `builder_pending_withdrawals` regardless of whether any attester ever confirmed the payload's timeliness/availability. [5](#0-4) 

This exactly mirrors the report's root cause: `creatorClaimSoldTokens` mutated contract-visible token balances via a path that never touched `redeemedDepositTokens`, so a second function (`recoverTokens`) that relied on that field being kept in sync produced wrong results. Here, `settle_builder_payment` mutates `builder_pending_withdrawals` via a path that never touches/consults `payment.weight`, so the quorum invariant that the spec's own epoch-processing function enforces on the same record is silently skippable.

### Impact Explanation
If the quorum/weight check is meant to be a real gate on whether a builder payment is honored (i.e., "was the payload actually attested-to/available"), then under normal block production this gate is never actually enforced — a builder is paid via `settle_builder_payment` as soon as any subsequent block simply exists with the parent slot in the current or previous epoch, independent of `payment.weight`. This is a builder-payment-escaping-its-required-authorization bug: `builder_pending_withdrawals` (which later pays out real value to `fee_recipient`) is populated without the check that the spec's own dedicated function (`process_builder_pending_payments`) treats as mandatory for the same data structure.

### Likelihood Explanation
This triggers on virtually every block under normal, honest chain operation (no adversarial input needed) — `apply_parent_execution_payload` runs on every proposed block and calls `settle_builder_payment` whenever the parent's payment slot has `amount > 0`, which is the common case whenever a builder submitted a non-zero bid. The weight-checked path only ever fires in the rare "more than ~2 missed epochs" fallback branch.

### Recommendation
Clarify/verify intended semantics with spec authors: either (a) `settle_builder_payment` should also require `payment.weight >= get_builder_payment_quorum_threshold(state)` before appending to `builder_pending_withdrawals` (mirroring `process_builder_pending_payments`), or (b) if the immediate settlement path is intentionally unconditional (because canonical extension is itself considered sufficient proof), then the quorum/weight mechanism in `process_builder_pending_payments` should be documented as applying only to the missed-slot fallback case, and its purpose/necessity there re-examined for consistency.

### Proof of Concept
1. A builder submits a bid with `amount > 0`, recorded via `process_execution_payload_bid` into `state.builder_pending_payments[SLOTS_PER_EPOCH + slot % SLOTS_PER_EPOCH]` with `weight = 0` [6](#0-5) .
2. No attester includes a same-slot attestation for this slot before the next block is proposed (so `payment.weight` stays `0`, well below `get_builder_payment_quorum_threshold`).
3. The very next block is proposed normally; `process_parent_execution_payload` → `apply_parent_execution_payload` computes `payment_index` for the parent slot and calls `settle_builder_payment(state, payment_index)` [7](#0-6) .
4. `settle_builder_payment` appends `payment.withdrawal` to `state.builder_pending_withdrawals` solely because `amount > 0`, never inspecting `weight` [8](#0-7) .
5. Contrast with `process_builder_pending_payments`, which for an identical `weight = 0` payment would refuse to create the withdrawal [9](#0-8) , confirming the two paths disagree on whether the same payment should be honored.

**Uncertainty**: I could not fully verify, within the available index, whether `apply_parent_execution_payload`'s unconditional settlement is deliberately designed this way (e.g., because canonical-chain extension is deemed sufficient proof of payload validity, making the PTC-weight quorum check purely a fallback for the missed-slot case) or is an unintended asymmetry. This determination would require reading the full rationale/notes in `specs/gloas/beacon-chain.md` and any related design docs, which exceed what the indexed context surfaced. I recommend a Devin session with full file access to confirm intended behavior before treating this as confirmed exploitable.

def process_builder_pending_payments(state: BeaconState) -> None:
    """
    Processes the builder pending payments from the previous epoch.
    """
    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:
        if payment.weight >= quorum:
            state.builder_pending_withdrawals.append(payment.withdrawal)

    old_payments = state.builder_pending_payments[SLOTS_PER_EPOCH:]
    state.builder_pending_payments[:SLOTS_PER_EPOCH] = old_payments
    new_payments = [BuilderPendingPayment.empty() for _ in range(SLOTS_PER_EPOCH)]
    state.builder_pending_payments[SLOTS_PER_EPOCH:] = new_payments

@with_gloas_and_later
@spec_state_test
def test_builder_payment_after_missed_epochs(spec, state):
    """
    Test that a builder is correctly charged when their canonical payload
    is processed after 2+ epochs of missed blocks.
    """
    # Advance to get finalization
    for _ in range(4):
        next_epoch_with_full_participation(spec, state)
    assert state.finalized_checkpoint.epoch == 2

    # Build Block 1 with a non-zero value bid from a builder
    block_1 = build_empty_block_for_next_slot(spec, state)
    builder_index = 0
    value = spec.Gwei(1000000)  # 0.001 ETH
    fee_recipient = b"\xab" * 20
    block_hash = spec.Hash32(b"\x42" * 32)

    bid = block_1.body.signed_execution_payload_bid.message
    bid.block_hash = block_hash
    bid.builder_index = builder_index
    bid.value = value
    bid.fee_recipient = fee_recipient
    bid.execution_requests_root = spec.hash_tree_root(spec.ExecutionRequests())

    # Sign the bid with the builder's private key
    signature = spec.get_execution_payload_bid_signature(
        state, bid, builder_privkeys[builder_index]
    )
    block_1.body.signed_execution_payload_bid = spec.SignedExecutionPayloadBid(
        message=bid,
        signature=signature,
    )

    # Ensure builder can cover the bid
    state.builders[builder_index].balance = spec.MIN_DEPOSIT_AMOUNT + value

    yield "pre", state

    # Process Block 1 — creates a pending payment for the builder
    signed_block_1 = state_transition_and_sign_block(spec, state, block_1)

    # Verify pending payment was created
    payment_idx = spec.SLOTS_PER_EPOCH + block_1.slot % spec.SLOTS_PER_EPOCH
    payment = state.builder_pending_payments[payment_idx]
    assert payment.withdrawal.amount == value
    assert payment.withdrawal.builder_index == builder_index
    assert payment.weight == 0

    pre_builder_balance = state.builders[builder_index].balance

    # Build Block 2 with 2+ epochs of missed slots. During the slot advancement,
    # process_builder_pending_payments runs at each epoch boundary:
    #   1st boundary: shifts payment from second half to first half
    #   2nd boundary: checks quorum on first half — weight 0 < quorum → evicted
    # When Block 2 is processed, parent is FULL so apply_parent_execution_payload
    # runs. Since parent_epoch is older than previous_epoch, payment_index is None.
    # The fix creates the withdrawal directly from the bid in this case.
    block_1_epoch = spec.compute_epoch_at_slot(block_1.slot)
    block_2_slot = spec.compute_start_slot_at_epoch(block_1_epoch + 2) + 1
    block_2 = build_empty_block(spec, state, slot=block_2_slot)
    block_2.body.signed_execution_payload_bid.message.parent_block_hash = block_hash
    signed_block_2 = state_transition_and_sign_block(spec, state, block_2)

    yield "blocks", [signed_block_1, signed_block_2]
    yield "post", state

    # Verify apply_parent_execution_payload actually ran (parent was FULL)
    parent_slot_index = bid.slot % spec.SLOTS_PER_HISTORICAL_ROOT
    assert state.execution_payload_availability[parent_slot_index]
