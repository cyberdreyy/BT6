### Title
Stale confirmations from removed/revoked multisig members still count toward execution threshold, allowing requests to execute below the true live-member threshold - (File: `multisig2/src/lib.rs`, also `multisig/src/lib.rs`)

### Summary
`MultiSigContract::confirm` executes a request once `confirmations.len() + 1 >= num_confirmations` [2](#0-1) . When a member is removed via `DeleteMember` (or `DeleteKey` in the legacy `multisig` contract), `delete_member` purges confirmations/requests *only* for requests whose original signer (`r.member`) is the removed member [3](#0-2) . It does not scan other pending requests to strip confirmations the removed member had already cast on requests authored by someone else. The equivalent logic in the original `multisig` contract's `DeleteKey` handler has the same gap, filtering only by `r.signer_pk == pk` [4](#0-3) .

### Finding Description
The binding that should hold is: `confirmations counted toward num_confirmations == confirmations from currently live members`. Because `self.confirmations` is a flat `LookupMap<RequestId, HashSet<String>>` indexed only by `RequestId` and never cross-referenced against `self.members` at confirm-time or at member-removal-time (except for requests the removed member itself created), a member's confirmation on someone else's still-pending request survives that member's removal from `self.members`. `confirm()` never re-checks that every entry in the stored `confirmations` set still belongs to a live member — it only checks that the *new* confirmer (`current_member()`) is live and hasn't already confirmed [5](#0-4) . This lets a since-removed (e.g., compromised or malicious) member's vote continue to satisfy the K-of-N threshold.

### Impact Explanation
This directly matches the "multisig request executed below threshold" Critical impact class. Concretely, with N=4 members (A, B, C, D) and K=3 confirmations required:
1. A creates request R1 (e.g., `Transfer` to an attacker-controlled account) and confirms it (`confirmations = {A}`).
2. B, who is later found to be compromised, also confirms R1 (`confirmations = {A, B}`, 2/3 — not yet executed).
3. The remaining legitimate members submit and confirm a separate `DeleteMember{B}` request (R2), which executes and removes B from `self.members`. Because `delete_member` only cleans requests where `r.member == B` (i.e., requests *authored* by B), R1 — authored by A — is untouched; its confirmations `{A, B}` remain intact.
4. C then confirms R1: `confirmations.len() + 1 = 3 >= num_confirmations (3)`, so R1 executes and transfers funds, even though B is no longer an authorized member.

The transfer executes with only 2 truly live confirmers (A, C) plus one stale confirmation from a removed member (B), i.e., below the intended live-member threshold — funds move despite the security guarantee that K *current* members must approve it.

### Likelihood Explanation
This requires no privileged access beyond being a normal multisig member who confirms a request before being removed (or being removed for cause, e.g. suspected key compromise) — exactly the scenario the removal mechanism exists to protect against. Any DAO/org multisig that rotates members (a routine operation, e.g. `AddMember`/`DeleteMember` for key rotation or offboarding) while requests are pending is exposed. It does not require a redeploy, foundation privilege, or any out-of-scope actor.

### Recommendation
On every `confirm()` call, re-validate that all previously-recorded confirmations for the request still correspond to current members (filtering the stored `HashSet<String>` against `self.members` before counting), or alternatively, on every `DeleteMember`/`DeleteKey`, iterate all pending requests (not just those authored by the removed member) and strip the removed member's confirmation from each `confirmations` set.

### Proof of Concept
Given `multisig2/src/lib.rs`'s `confirm` and `delete_member`:
```rust
// N=4 members: A,B,C,D ; num_confirmations = 3
let r1 = c.add_request_and_confirm(transfer_request); // confirmations = {A}
// as B:
c.confirm(r1); // confirmations = {A, B}  (2/3, not executed)

// separate request R2 authored by C, confirmed by C, D, A -> executes, removes B
c.add_request_and_confirm(delete_member_b_request); // as C
c.confirm(r2); // as D
c.confirm(r2); // as A -> 3/3, executes DeleteMember{B}
// self.members no longer contains B, but self.confirmations[r1] still == {A,B}

// as C:
c.confirm(r1); // confirmations.len()+1 == 3 >= num_confirmations(3) -> R1 EXECUTES
// B's stale confirmation counted toward the 3-of-4 threshold despite B being removed.
``` [3](#0-2)  shows the cleanup is scoped to `r.member == member` only, leaving other requests' stale confirmations from the removed member unaddressed.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
