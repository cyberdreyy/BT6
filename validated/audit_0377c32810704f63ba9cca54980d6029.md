## Finding: Permissionless `vest`/`unlock_rewards` funds get permanently trapped in the shareholder-inaccessible `admin_withdraw` path after `terminate_vesting_contract`

### Summary
`vest` and `unlock_rewards` in `vesting.move` are `public entry` functions that take only a `contract_address` — no signer/ownership check is performed, so **anyone** can call them for **any** vesting contract. [1](#0-0) [2](#0-1)  Calling either function moves the newly-vested/reward amount from `active` to `pending_inactive` in the underlying stake pool via `unlock_stake`. [3](#0-2)  If an admin then calls `terminate_vesting_contract` before that specific unlock finishes its lockup cycle (i.e., before it becomes fully `inactive`), the amount is not swept by the pre-termination `distribute()` call (which only pulls already-`inactive`/withdrawable funds), and after termination `distribute()` can never be called again because it (and `total_accumulated_rewards`) require `VESTING_POOL_ACTIVE` state. [4](#0-3)  The only remaining path to reclaim any inactive stake from the pool is `admin_withdraw`, which withdraws the *entire* inactive balance and sends it in one lump sum to `withdrawal_address`, with no accounting against shareholder pool shares. [5](#0-4) [6](#0-5) 

### Finding Description
`terminate_vesting_contract` reads `active_stake` from the pool and unlocks it, then sets `remaining_grant = 0`: [7](#0-6) 

Because `unlock_stake`/`unlock_rewards` moves funds out of `active` into `pending_inactive` *before* termination, that amount is excluded from the `active_stake` variable read here — it survives the termination call as a `pending_inactive` balance in the same underlying stake pool used by the vesting contract (`staking_contract`/`stake` pool), indistinguishable from the residual unvested grant that termination itself unlocks. There is no per-tranche bookkeeping in the stake pool that ties a specific `pending_inactive` amount back to "already vested, owed to shareholder X" versus "unvested grant, owed to admin after termination" — that distinction only exists conceptually in `vesting.move`'s `distribute()` logic, which is gated behind `assert_active_vesting_contract` and therefore permanently unusable once `state == VESTING_POOL_TERMINATED`.

Once the lockup cycle completes and both amounts become `inactive`, `admin_withdraw` is the only remaining entry point that can pull funds out of the pool, and it forwards the *whole* balance to `withdrawal_address`: [5](#0-4) 

So a shareholder's tranche that was legitimately vested (and unlocked via `vest`/`unlock_rewards`, callable by anyone) prior to termination — but whose lockup had not yet elapsed at termination time — is silently redirected to the admin's withdrawal address instead of being distributed pro-rata via `distribute()`'s `pool_u64` share logic. [8](#0-7) 

### Impact Explanation
The already-vested amount permanently loses its association with the shareholder/beneficiary and is paid out entirely to the vesting contract's `withdrawal_address` (controlled by the admin), rather than being split by `grant_pool` shares to shareholders/beneficiaries. This breaks the stated invariant ("Admin can call terminate_vesting_contract to terminate the vesting. This would first finish any distribution...") because "finishing distribution" (the pre-termination `distribute()` call) only covers stake that has *already fully unlocked*, not stake still mid-lockup from a recent `vest`/`unlock_rewards` call. Any shareholder relying on a just-called `vest()`/`unlock_rewards()` whose lockup has not yet expired at the moment of termination permanently forfeits that tranche to the admin.

### Likelihood Explanation
`vest` and `unlock_rewards` require no privilege at all — any address can call them for any `contract_address`, so the precondition (funds sitting in `pending_inactive` at termination time) is trivial to engineer or can occur naturally whenever an admin terminates shortly after a shareholder's own routine `vest()`/`unlock_rewards()` call within the same lockup cycle. `terminate_vesting_contract` itself is admin-gated (`verify_admin`), so the misdirection is triggered by the combination of the permissionless unlock call plus the admin's termination timing — the admin does not need any malicious intent for the loss to occur, but an unprivileged caller can also proactively call `vest`/`unlock_rewards` to force pending_inactive stake into existence right before an anticipated termination.

### Recommendation
Before allowing `terminate_vesting_contract` to complete, either (a) require that the stake pool have zero `pending_inactive` balance in addition to zero `pending_active` (i.e., require any in-flight unlocks to have fully resolved and been distributed first), or (b) track vested-but-undistributed amounts explicitly (e.g., an accrued "owed to shareholders" balance) so that `admin_withdraw` only ever withdraws the residual unvested grant, forwarding any pre-termination vested/reward tranches to shareholders even after termination (e.g., by allowing `distribute()` to still run once more after termination for any amount that was unlocked pre-termination).

### Proof of Concept
1. Admin creates a vesting contract for `shareholder`, funds it, and lets a vesting period elapse.
2. Anyone (attacker or shareholder) calls `vest(contract_address)` right before lockup renewal, unlocking tranche `X` into `pending_inactive`. `X` has not yet completed its lockup cycle.
3. Admin calls `terminate_vesting_contract(admin, contract_address)`. The pre-call `distribute()` withdraws `0` (nothing inactive yet), `active_stake` (excluding `X`) is unlocked, `state = VESTING_POOL_TERMINATED`, `remaining_grant = 0`.
4. Fast-forward past lockup expiration — `X` plus the residual unvested grant both become `inactive`.
5. `distribute(contract_address)` now aborts with `EVESTING_CONTRACT_NOT_ACTIVE` (per spec.move's documented requirement), so it can never route `X` to the shareholder.
6. Admin calls `admin_withdraw(admin, contract_address)`: the entire inactive balance, including tranche `X`, is deposited to `withdrawal_address`, and `shareholder`/`beneficiary` never receives it.

This can be adapted directly into the existing `#[test]` harness in `vesting.move` (e.g., extending `test_cannot_vest_after_contract_is_terminated`/`test_vest_...` patterns) by inserting a `vest()` call immediately before `terminate_vesting_contract`, then asserting `coin::balance<AptosCoin>(shareholder_address)` is unchanged while `coin::balance<AptosCoin>(withdrawal_address)` gains tranche `X`. [9](#0-8)
