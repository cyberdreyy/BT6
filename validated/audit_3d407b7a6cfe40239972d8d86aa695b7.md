Confirmed: `CapabilityRequestParams` has `Owner` and `WorkflowID` fields (used to seed the CRE context) but `handleCapabilityExecute` never calls `verifyWorkflowAuthorization`, unlike its sibling `handleSecretsGet`.

### Title
Missing Workflow-DON authorization check in `handleCapabilityExecute()` allows a compromised enclave to impersonate another workflow owner - (File: `core/capabilities/confidentialrelay/handler.go`)

### Summary
`Handler.handleCapabilityExecute()` in `core/capabilities/confidentialrelay/handler.go` verifies TEE attestation and enclave-config match against the onchain DON but, unlike its sibling `handleSecretsGet()`, never calls `verifyWorkflowAuthorization()`. This mirrors the reported bug class: one function in a validation pair enforces an authorization/quorum check that a structurally similar function omits.

### Finding Description
`handleSecretsGet` performs three checks before serving a request: attestation hash verification (`verifyAttestationHash`), enclave-config-vs-DON verification (`verifyEnclaveConfigMatchesDON`), and — critically — Workflow-DON authorization (`verifyWorkflowAuthorization`), which cryptographically confirms that a `2*F+1`/`F+1` quorum of the Workflow DON actually signed a `ComputeRequest` naming the specific `Owner`/`WorkflowID` in the request [1](#0-0) . The comment explicitly states the purpose: "A TEE breach passes attestation but cannot forge a Workflow DON quorum over a different owner (PRIV-433)" [2](#0-1) .

`handleCapabilityExecute` handles `confidentialrelaytypes.CapabilityRequestParams`, which likewise carries `Owner` and `WorkflowID` (used to seed `contexts.WithCRE`) and is documented as receiving the same class of enclave-forwarded compute requests [3](#0-2) . It performs attestation and enclave-config checks, mirroring `handleSecretsGet`'s comments ("same as handleSecretsGet (PRIV-458)") [4](#0-3) , but it never calls `verifyWorkflowAuthorization` before executing the capability with `handler.CallCapability(ctx, sdkReq)` [5](#0-4) . `verifyWorkflowAuthorization` itself is typed to accept only `SecretsRequestParams`, confirming it was never designed to be invoked from the capability-execute path [6](#0-5) .

The unit test `TestHandler_HandleGatewayMessage`'s "capability execute success" case builds a `CapabilityRequestParams` with an `Owner`/`WorkflowID` and a valid `EnclaveConfig`, but supplies no `SignedComputeRequests` at all, and the request still succeeds — demonstrating the code path never checks Workflow-DON authorization for this method [7](#0-6) .

### Impact Explanation
Attestation alone only proves the request originated from genuine enclave code; per the handler's own documented threat model, a compromised or misbehaving TEE host can still self-assert an arbitrary `Owner`/`WorkflowID` in the request params. For `MethodSecretsGet` this is caught because `verifyWorkflowAuthorization` requires a quorum of real Workflow-DON signatures binding the request to a specific owner/workflow. For `MethodCapabilityExec`, no equivalent check exists, so a breached enclave (or any caller able to reach this handler with a validly-attested-but-forged owner) could invoke `CallCapability` under an arbitrary `Owner`/`WorkflowID` tenant context, causing capability execution, associated resource consumption, and CRE-tenant-scoped side effects to be attributed to and run against a victim's workflow identity rather than the actual caller.

### Likelihood Explanation
The check is reachable directly from `HandleGatewayMessage` → `serveGatewayMessage` → `handleCapabilityExecute`, the standard gateway-facing entry point for `MethodCapabilityExec` [8](#0-7) . No additional privilege beyond passing attestation is required, and the codebase's own PRIV-433/PRIV-458 comments confirm the underlying assumption (attestation doesn't prove Workflow-DON authorization) applies equally to both methods, making the omission a straightforward logical inconsistency rather than a hardened design choice.

### Recommendation
Add an owner/workflow authorization check to `handleCapabilityExecute`, analogous to `verifyWorkflowAuthorization` used in `handleSecretsGet`. Either generalize `verifyWorkflowAuthorization` to accept a common parameter shape (owner, workflowID, signed compute requests) shared by both `SecretsRequestParams` and `CapabilityRequestParams`, or add `SignedComputeRequests` to `CapabilityRequestParams` and invoke the same quorum-verification logic before calling `handler.CallCapability`.

### Proof of Concept
1. Attacker controls or has compromised an enclave instance that can still produce a genuinely-attested Nitro document (e.g., a legitimate-but-buggy or partially-compromised TEE host that can execute enclave code but forge which owner/workflow request it services).
2. Attacker sends a `MethodCapabilityExec` JSON-RPC request through the gateway with `CapabilityRequestParams{Owner: <victim>, WorkflowID: <victim-workflow>, ...}`, a valid `Attestation` over these exact params, and a valid `EnclaveConfig` matching the onchain DON.
3. `handleCapabilityExecute` verifies the attestation hash and enclave config successfully (both only bind to the request bytes/config, not to any proof that the Workflow DON authorized this specific owner) and proceeds to resolve the execution handler and call `handler.CallCapability(ctx, sdkReq)` under the victim's `Owner`/`WorkflowID` CRE context, with no check equivalent to `verifyWorkflowAuthorization` ever executed, as shown by the passing "capability execute success" test that supplies no `SignedComputeRequests` [9](#0-8) .
