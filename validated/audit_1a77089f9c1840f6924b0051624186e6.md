### Title
Ambiguous, unescaped semicolon-joined variable name list in `GetAllVariableNames` allows variable-name injection - ([File: common/spec/variables.go])

### Summary
`Variables.GetAllVariableNames()` joins all job variable `Key` values with a raw `;` delimiter and no escaping, then this string is exposed to the job container as `RUNNER_JOB_VAR_NAMES` for step-runner to split back into names. If an attacker-controlled variable `Key` itself contains a `;`, the resulting list becomes ambiguous and can be split into a different name set than the original keys.

### Finding Description
`GetAllVariableNames` at [1](#0-0)  builds the name list purely from `variable.Key` with `strings.Join(names, ";")` and performs no validation or escaping of the `;` character (or any other delimiter-conflicting byte) in the key. The comment at [2](#0-1)  confirms this string is specifically produced so that "step-runner [can] identify and filter out job variables from the OS environment" via `RUNNER_JOB_VAR_NAMES` — i.e., it is a security-relevant filtering input consumed by a downstream, delimiter-splitting parser.

Nothing in `common/spec/variables.go` rejects or sanitizes `Key` values containing `;` before they enter this join. If GitLab (or any intermediary) allows a job payload to define a variable with a key such as `FOO;BAR=evil` (or a key equal to the name of a masked/protected variable plus a trailing `;`), the emitted list `...;FOO;BAR=evil;...` becomes indistinguishable from two separate legitimate names `FOO` and `BAR=evil` (or otherwise shifts the boundaries of adjacent names). Since step-runner's consumer logic splits strictly on `;` to build its exclusion set, a crafted key can synthesize an extra bogus name, alter the boundary of a following real name, or otherwise desynchronize the exclusion set from the runner's actual name set — allowing an intended-to-be-filtered name to no longer match anything in the split output and thus not be stripped from the environment.

### Impact Explanation
If exploitable end-to-end (the actual splitting/filtering logic lives in step-runner, outside this repository, so its precise matching semantics could not be directly verified here), the scoped impact is that a masked/protected CI variable that should be stripped from the job container's OS environment before user step code runs is instead left present, exposing its secret value to job step code within the container.

### Likelihood Explanation
Exploitability depends entirely on the stated precondition — that GitLab's job payload does not sanitize/validate variable `Key` characters before they reach Runner. GitLab CI variable key naming is normally constrained (typically `[A-Za-z_][A-Za-z0-9_]*`) at the GitLab server/UI/API level, which would block a literal `;` in a key before it ever reaches this Runner code path. Whether some CI configuration surface (e.g., dynamically generated variables, dotenv artifacts, or certain API paths) can smuggle a `;` into a `Key` all the way to `Variables.GetAllVariableNames()` could not be confirmed from the code available in this repository. If such a path exists, the root cause here — unescaped, ambiguous delimiter-based join — is real and repeatable.

### Recommendation
Use an unambiguous, injection-proof encoding for `RUNNER_JOB_VAR_NAMES`, e.g.:
- Reject/strip variable keys containing `;`, `\n`, or NUL before they participate in `GetAllVariableNames`, or
- Switch to a length-prefixed or percent/URL-encoded name list (e.g., escape `;` and any encoding metacharacter within each key, or use a format like `strconv.Quote` per element joined by `;`), and update step-runner's parser to match the new, unambiguous format.

### Proof of Concept
```go
func TestGetAllVariableNames_AmbiguousDelimiter(t *testing.T) {
    vars := Variables{
        {Key: "FOO;BAR=evil", Value: "x"},
        {Key: "MASKED_SECRET", Value: "s3cr3t"},
    }
    names := vars.GetAllVariableNames()
    // Naive consumer split logic (mirroring step-runner's expected behavior)
    split := strings.Split(names, ";")
    got := map[string]bool{}
    for _, n := range split {
        got[n] = true
    }
    want := map[string]bool{"FOO;BAR=evil": true, "MASKED_SECRET": true}
    // FAILS: split introduces "FOO", "BAR=evil", "MASKED_SECRET" instead of the two original keys
    require.Equal(t, want, got)
}
```
Expected assertion failure demonstrates that the derived name set from splitting on `;` does not equal the original `Key` set, confirming the ambiguous encoding. Full end-to-end exploitation additionally requires confirming (outside this repo, in step-runner) that its filter uses this same naive `strings.Split(..., ";")` logic and that a real GitLab job payload can smuggle a `;` into a variable `Key` — neither of which could be verified from the code present in this repository.

```go
func (b Variables) GetAllVariableNames() string {
	names := make([]string, 0, len(b))
	for _, variable := range b {
		names = append(names, variable.Key)
	}

	return strings.Join(names, ";")
}
```
