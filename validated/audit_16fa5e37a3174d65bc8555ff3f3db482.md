### Title
Multisig request can execute below the configured confirmation threshold because stale confirmations from removed members are not purged - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` only removes *requests created by* the removed member, but never scrubs that member's *confirmations* on other members' pending requests. Because `confirm()` counts entries in the `confirmations` set without checking that each confirmer is still a current member of `self.members`, a request can accumulate the required number of confirmations even though some of the accounts/keys that "confirmed" it were removed from the multisig before the request was executed.

### Finding Description
`confirm()` determines whether to execute a request purely by the size of the stored confirmation set versus `num_confirmations`: [1](#0-0) 

`delete_member()` is the only place that cleans stale multisig state when a member is removed, and its cleanup is scoped to requests where `r.member == member` (i.e., requests *authored* by the removed member) — it does not touch `self.confirmations` for requests authored by *other* members that the removed member had already confirmed: [2](#0-1) 

Sequence:
1. Multisig has members `{A, B, C, D}` with `num_confirmations = 3`.
2. `A` calls `add_request` creating request `R` (a `Transfer`). `R.member = A`; confirmations for `R` = `{}`.
3. `B` calls `confirm(R)`. Since `0 + 1 < 3`, `B`'s key/account is inserted into `confirmations[R]` → `{B}`.
4. Separately, the multisig (via its own request/confirm flow) executes a `DeleteMember{member: B}` action, removing `B` from `self.members` and deleting `B`'s own authored requests/`num_requests_pk` entry — but request `R` (authored by `A`) and its confirmation set `{B}` are left untouched.
5. `C` calls `confirm(R)`: `confirmations[R].len() == 1`, `1 + 1 = 2 < 3`, so `C` is added → `{B, C}`.
6. `D` calls `confirm(R)`: `confirmations[R].len() == 2`, `2 + 1 = 3 >= 3` → threshold satisfied → `execute_request(R)` runs.

At execution time, the only *live* confirmers are `C` and `D` (2), yet the contract believes 3 confirmations were given because `B`'s stale confirmation is still counted. The equality the contract is supposed to preserve — `live confirmations on a request == num_confirmations before it can execute` — is broken; the actual invariant enforced is `len(confirmations set, including confirmations from now-removed members) >= num_confirmations`.

### Impact Explanation
This directly matches the "Critical" impact bucket: a multisig request (e.g., a `Transfer` of NEAR, a `DeployContract`/upgrade, or an `AddKey`) executes with fewer live confirmations than `num_confirmations` requires. A single stale confirmation from a removed member is enough to lower the effective threshold by one signer indefinitely for any request they confirmed before being removed, undermining the entire security assumption of the k-of-n multisig.

### Likelihood Explanation
This requires no external/unprivileged attacker at all — it is triggerable through entirely normal multisig lifecycle operations (membership rotation is a documented, expected use case per the README's `DeleteMember`/`AddMember` actions). Any organization that rotates multisig membership while a request is still pending confirmation is exposed. It only requires ordinary sequencing (a pending request + a membership change) rather than any privilege escalation, exploit of a bug in a third-party contract, or race with validators.

### Recommendation
When executing `DeleteMember`, iterate over **all** pending requests' confirmation sets (not just those authored by the removed member) and remove the deleted member's entry from each. Alternatively, validate at `confirm()`/`execute_request()` time that every account/key present in the confirmation set is still contained in `self.members`, and only count still-live confirmations toward `num_confirmations`.

### Proof of Concept
```rust
// members: A, B, C, D ; num_confirmations = 3
let request_id = a_ctx.add_request(transfer_request); // authored by A
b_ctx.confirm(request_id);                             // confirmations = {B}

// separately, via its own fully-confirmed multisig flow:
// DeleteMember{ member: B } executes, removing B from self.members
// but confirmations[request_id] still contains B

c_ctx.confirm(request_id); // confirmations = {B, C}, 2 < 3, no execute
d_ctx.confirm(request_id); // len=2, +1=3 >= 3 => execute_request() runs
// Transfer executes with only C and D as genuinely live confirmers (2 of the required 3)
```
This can be reproduced by extending the existing `test_multi_3_of_n` test in `multisig2/src/lib.rs` to insert a `DeleteMember` execution between the first and second `confirm()` calls.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
