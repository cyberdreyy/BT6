### Title
`get_mint_owner_and_additional_data` unpacks mint-account bytes as an SPL `Mint` without verifying the account is owned by a known SPL-Token program, allowing attacker-controlled `decimals`/extension data to be merged into `getTokenAccountBalance` / `getTokenLargestAccounts` / JSON-parsed token account results - ([File: rpc/src/parsed_token_accounts.rs])

### Summary
`get_mint_owner_and_additional_data` fetches the account referenced by a token account's `mint` field and immediately hands its raw bytes to `StateWithExtensions::<Mint>::unpack` without first checking that the fetched account is owned by `spl_token` or `spl_token_2022`. Because the `mint` field only needs to match the address stored inside an existing, legitimately-owned token account (which the attacker fully controls), and because that address can later be repointed to attacker-controlled account data at the RPC/bank level, the function can decode arbitrary bytes as if they were a trusted `Mint`, and its `decimals`/extension configuration are merged into RPC responses.

### Finding Description
`get_mint_owner_and_additional_data` in `rpc/src/parsed_token_accounts.rs` resolves the token-program owner and decimals for a mint pubkey: [1](#0-0) 

The non-native-mint branch calls `bank.get_account(mint)` and passes its raw data straight to `get_additional_mint_data`, which does: [2](#0-1) 

`get_additional_mint_data` calls `StateWithExtensions::<Mint>::unpack(data)` unconditionally - there is **no check that `mint_account.owner()` is `spl_token::id()` or `spl_token_2022::id()`**. This is inconsistent with `get_token_supply` in `rpc/src/rpc.rs`, which explicitly performs `is_known_spl_token_id(mint_account.owner())` before unpacking as `Mint`: [3](#0-2) 

`get_mint_owner_and_additional_data` is reachable from `get_token_account_balance` (used by `getTokenAccountBalance`), `get_token_largest_accounts`, and `get_parsed_token_accounts` (used for `jsonParsed` encoding of `getTokenAccountsByOwner`, etc.): [4](#0-3) 

In `get_token_account_balance`, only the **token account itself** (`account.owner()`) is checked with `is_known_spl_token_id`; the `mint` pubkey extracted from that account's data is passed unchecked into `get_mint_owner_and_additional_data`, which trusts whatever bytes currently live at that address on-chain.

Exploit flow (fully achievable by an unprivileged single-writer/single-caller attacker using on-chain writes later read via RPC):
1. Attacker creates a legitimate SPL Token-2022 mint `M` with the `MintCloseAuthority` extension and mints/burns so supply is 0, with themselves as close authority.
2. Attacker creates a legitimate token account `A` owned by the real `spl_token_2022` program with `mint = M`. This account passes `is_known_spl_token_id` in `get_token_account_balance`/`get_parsed_token_accounts`.
3. Attacker invokes `CloseAccount` on mint `M` (permitted via `MintCloseAuthority`), returning `M`'s lamports and resetting the account to system-owned/empty. `M`'s pubkey is a keypair the attacker controls, so it can be reused.
4. Attacker creates a brand-new account at the same pubkey `M` (owned by System Program or any attacker-controlled program) containing arbitrary bytes that happen to satisfy `StateWithExtensions::<Mint>::unpack` (e.g., a fixed-size 82-byte packed `Mint` struct with `is_initialized = true` and attacker-chosen `decimals`/authorities).
5. Any subsequent `getTokenAccountBalance`/`getTokenLargestAccounts`/`jsonParsed` query touching account `A` calls `get_mint_owner_and_additional_data(bank, &M)`, which fetches the new, non-token-program-owned account at `M` and successfully unpacks attacker-controlled `decimals` (and possibly `InterestBearingConfig`/`ScaledUiAmountConfig` extension bytes), which are then merged into the RPC response as if from a trusted mint.

This violates the "data must belong to the requested key/program" parse-fidelity invariant: the RPC returns balance/decimal information derived from bytes that are not actually owned or maintained by any SPL-Token program.

### Impact Explanation
This causes misreported `decimals` (and possibly interest-bearing/scaled-UI-amount configuration) for `getTokenAccountBalance`, `getTokenLargestAccounts`, and `jsonParsed`-encoded token account responses tied to the compromised mint address. Any wallet/indexer relying on RPC-reported `uiAmount`/`decimals` for that mint can display an incorrect balance for the attacker's own account (and for any other account still referencing that now-repurposed mint address, if such existed). This is a data-integrity/parse-fidelity bug in the JSON RPC decoding path, matching Agave's "RPC returns wrong/incorrect data" bounty category rather than a consensus or crash impact.

### Likelihood Explanation
Fully attacker-controlled and repeatable: all steps (mint creation, mint closing via `MintCloseAuthority`, address reuse, single RPC query) use only standard SPL Token-2022 instructions and a single low-rate `getTokenAccountBalance` call, requiring no validator/operator privileges. The only precondition is using the Token-2022 program's `MintCloseAuthority` extension, which is a normal, permissionless on-chain feature.

### Recommendation
In `get_mint_owner_and_additional_data` (`rpc/src/parsed_token_accounts.rs`), verify `mint_account.owner()` is a known SPL-Token program id (matching the check already performed in `get_token_supply` in `rpc/src/rpc.rs`) before calling `get_additional_mint_data`/`StateWithExtensions::<Mint>::unpack`, and return an explicit RPC error (e.g., "Invalid param: not a Token mint") when the owner check fails.

### Proof of Concept
Integration test outline (using `RpcHandler`/`BankTestConfig` test harness already present in `rpc/src/rpc.rs` tests):
1. Create a Token-2022 mint `M` with `MintCloseAuthority` extension, decimals = 6, supply eventually 0.
2. Create token account `A` (owned by `spl_token_2022`) with `mint = M`, `amount = 1_000_000`.
3. Close mint `M` via `CloseAccount` (attacker is close authority), freeing the account (owner reverts to System Program).
4. Directly `bank.store_account(&M, ...)` (simulating a follow-up on-chain write by the attacker reusing keypair `M`) with a system-owned account whose bytes unpack as `Mint` with `decimals = 0` (or any different attacker-chosen value) and no re-assignment to a token program.
5. Call `rpc.get_token_account_balance(&A, None)`.
6. Assert expected behavior: the RPC should either return an error (e.g., "Invalid param: not a Token mint") because `M`'s current owner is not a known SPL-Token program, **not** silently return a `UiTokenAmount` using the attacker-forged `decimals`.
   Currently, the call succeeds and returns the attacker-controlled `decimals`, demonstrating the vulnerability.

pub(crate) fn get_mint_owner_and_additional_data(
    bank: &Bank,
    mint: &Pubkey,
) -> Result<(Pubkey, SplTokenAdditionalDataV2)> {
    if mint == &spl_token_interface::native_mint::id() {
        Ok((
            spl_token_interface::id(),
            SplTokenAdditionalDataV2::with_decimals(spl_token_interface::native_mint::DECIMALS),
        ))
    } else {
        let mint_account = bank.get_account(mint).ok_or_else(|| {
            Error::invalid_params("Invalid param: could not find mint".to_string())
        })?;
        let mint_data = get_additional_mint_data(bank, mint_account.data())?;
        Ok((*mint_account.owner(), mint_data))
    }
}

fn get_additional_mint_data(bank: &Bank, data: &[u8]) -> Result<SplTokenAdditionalDataV2> {
    StateWithExtensions::<Mint>::unpack(data)
        .map_err(|_| {
            Error::invalid_params("Invalid param: Token mint could not be unpacked".to_string())
        })
        .map(|mint| {
            let interest_bearing_config = mint
                .get_extension::<InterestBearingConfig>()
                .map(|x| (*x, bank.clock().unix_timestamp))
                .ok();
            let scaled_ui_amount_config = mint
                .get_extension::<ScaledUiAmountConfig>()
                .map(|x| (*x, bank.clock().unix_timestamp))
                .ok();
            SplTokenAdditionalDataV2 {
                decimals: mint.base.decimals,
                interest_bearing_config,
                scaled_ui_amount_config,
            }
        })
}
