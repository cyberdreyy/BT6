### Title
Unbounded memory allocation via zstd decompression bomb in `UiAccountData::decode` (Base64Zstd) - ([File: account-decoder-client-types/src/lib.rs])

### Finding Description
`UiAccountData::decode` handles the `Base64Zstd` variant by base64-decoding the client-supplied blob and then feeding it directly into `zstd::stream::read::Decoder::read_to_end`, with no cap on the size of the decompressed output: [1](#0-0) 

This function is the sole decoding path used to turn a client-supplied `UiAccount`/`UiAccountData` (as accepted in JSON-RPC account-override configs, e.g. `simulateTransaction`'s `accounts` override) into runtime account bytes via `UiAccount::to_account_shared_data`/`to_account`: [2](#0-1) 

Zstd supports extremely high compression ratios ("zstd bombs"), so a small (few-KB) base64 payload can expand to gigabytes when decompressed. Because `read_to_end` has no length limit and there is no pre-check on decompressed size (no `MAX_PERMITTED_DATA_LENGTH`-style guard applied before/during decompression in this function), a single call can force the process to allocate an arbitrarily large `Vec<u8>`, exhausting memory for one low-rate request.

### Impact Explanation
If this decode path is reachable from a JSON-RPC handler that accepts client-supplied account overrides (e.g. `simulateTransaction`'s accounts-override config), a single unprivileged client request containing a small, malicious `base64+zstd`-encoded account blob could trigger unbounded memory allocation, leading to OOM/crash or severe resource exhaustion in the validator process — a violation of the "cost bounded by explicit limits" invariant and matching Agave's RPC DoS bounty category (single-call, no elevated privileges needed).

### Likelihood Explanation
The precondition is only that the RPC surface (or any client type consumer) accepts a `UiAccountData::Binary(_, UiAccountEncoding::Base64Zstd)` payload from the caller and calls `.decode()` on it (directly or via `to_account`/`to_account_shared_data`), which is exactly the shape of `simulateTransaction`'s account-override mechanism. Crafting a small zstd bomb (e.g. compressing a large run of zeros) is trivial and requires no special access — a single JSON-RPC call suffices, well within the "one call per CLUSTER_SLOT_TIME_TARGET/2" constraint.

Note: I was unable to fully confirm, within this indexed snapshot, the exact call site in `rpc/src/rpc.rs` that wires `simulateTransaction`'s accounts-override config into `UiAccountData::decode`/`to_account_shared_data` (searches for `.decode()`/`to_account_shared_data` inside `rpc/src/rpc.rs` did not surface a match, and `account-decoder-client-types` is gated behind the `agave-unstable-api` feature). The decode function itself is unambiguously unbounded, but full end-to-end reachability from the live RPC handler should be verified against the actual `rpc/src/rpc.rs` simulate-transaction account-resolution code before treating this as fully confirmed.

### Recommendation
Enforce a hard cap on decompressed size before/while decoding, e.g. use `zstd::stream::read::Decoder` with `Decoder::single_frame()` plus a bounded reader (`Read::take(MAX_ACCOUNT_DATA_LEN)`), or use `zstd::bulk::decompress` with an explicit `capacity` limit, rejecting/erroring if the limit is exceeded, matching Solana's existing `MAX_PERMITTED_DATA_LENGTH` for account data.

### Proof of Concept
```rust
// account-decoder-client-types/tests/zstd_bomb.rs
use {
    base64::{engine::general_purpose::STANDARD, Engine},
    account_decoder_client_types::{UiAccountData, UiAccountEncoding},
};

#[test]
fn zstd_bomb_causes_unbounded_allocation() {
    // Compress 2 GiB of zeros into a tiny payload.
    let huge = vec![0u8; 2 * 1024 * 1024 * 1024];
    let compressed = zstd::stream::encode_all(huge.as_slice(), 19).unwrap();
    assert!(compressed.len() < 1_000_000); // small payload
    let b64 = STANDARD.encode(&compressed);

    let ui_data = UiAccountData::Binary(b64, UiAccountEncoding::Base64Zstd);

    // Expected (after fix): decode() should return None/Err due to exceeding
    // a bounded output-size cap, instead of allocating ~2 GiB.
    let decoded = ui_data.decode();
    assert!(decoded.is_none(), "decompression bomb should be rejected by a size cap");
}
```
Expected current behavior: the test allocates ~2 GiB for a small input, demonstrating unbounded memory cost for a single call; expected fixed behavior: `decode()` returns `None`/error once a defined output cap (e.g. `MAX_PERMITTED_DATA_LENGTH`) is exceeded.
