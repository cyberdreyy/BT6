### Title
Truncating `as u8` cast on inner-instruction index causes misreported instruction indices for transactions with ≥256 top-level instructions - (File: `transaction-status/src/lib.rs`)

### Summary
`map_inner_instructions` unconditionally truncates the `usize` position of each top-level instruction into a `u8` via `index as u8` when building the `InnerInstructions` list returned to RPC clients. This mirrors the reported bug class (unconditional narrowing cast of a count/index without bounds validation), and can be triggered by a single crafted transaction containing 256 or more top-level instructions, causing wraparound and duplicate/incorrect outer-instruction indices in `getTransaction`/`getConfirmedBlock`-style responses.

### Finding Description
`map_inner_instructions` enumerates the per-instruction inner-instruction lists produced during transaction execution and truncates the enumeration index to `u8` with no bounds check: [1](#0-0) 

Unlike the vote-state-view length parsing elsewhere in the codebase, which uses `u8::try_from(len).map_err(...)` to reject out-of-range lengths [2](#0-1) , this cast is an infallible `as u8`, so any `index >= 256` silently wraps modulo 256 (256→0, 257→1, ...), exactly the truncation pattern described in the external report.

A Solana transaction message imposes no explicit cap on the number of top-level instructions other than the 1232-byte transaction size limit; a minimal compiled instruction (program_id_index + empty accounts + empty data) occupies only 3 bytes, so hundreds of trivial instructions — each invoking a program that performs at least one CPI (to populate an inner-instruction entry) — can fit in a single transaction while staying well under default compute-budget limits. When such a transaction executes, `solana_message::inner_instruction::InnerInstructionsList` will contain more than 256 entries, and converting it via `map_inner_instructions` produces multiple `InnerInstructions` entries whose `index` field collides due to the wraparound.

This output is consumed by the transaction-status pipeline that backs RPC methods (`getTransaction`, `getConfirmedBlock`, etc.), an unprivileged, JSON-RPC-reachable read path, matching the "transaction-status and instruction parsing" category explicitly in scope.

### Impact Explanation
The wrapped index causes `innerInstructions[].index` in RPC responses to misattribute inner (CPI) instructions to the wrong top-level instruction once the transaction has 256+ top-level instructions. Any client, indexer, or block explorer relying on this field to map inner instructions back to their originating outer instruction will get wrong-instruction-index (misreporting) results — this falls under the accepted "decoder... misreporting" impact category. It does not require multiple RPC calls or a malicious validator; a single confirmed transaction (crafted and submitted by any user) is sufficient to poison decode of its own transaction-status query.

### Likelihood Explanation
Requires an attacker to construct and land a transaction with ≥256 top-level instructions, each triggering at least one CPI so an inner-instruction entry is recorded for it. This is achievable with cheap loopback/no-op-CPI programs and fits within standard transaction size (1232 bytes) and default compute budget, making it low-cost and fully within the reach of any unprivileged transaction submitter — no special validator/operator role needed.

### Recommendation
Change the `index` field (and this conversion) to use a width that cannot silently overflow within realistic transaction bounds — e.g., `u16`/`u32` — or explicitly reject/report an error when `index` exceeds `u8::MAX`, consistent with the fallible `u8::try_from` pattern already used elsewhere in this codebase (e.g., `vote/src/vote_state_view/field_frames.rs`) rather than the current infallible `as u8` cast.

### Proof of Concept
1. Construct a transaction containing 260 top-level instructions, each invoking a small on-chain program that performs one CPI to another program (so each generates one inner-instruction entry). Keep total transaction size under 1232 bytes and total compute under the default limit by using minimal-size, minimal-cost instructions/programs.
2. Submit and confirm the transaction.
3. Query the transaction via `getTransaction`/`getConfirmedBlock`. The `meta.innerInstructions` field will contain multiple entries whose `index` values collide (e.g., the entries for top-level instructions 256 and 0 both report `index: 0`), because `map_inner_instructions` computed `index: index as u8` [3](#0-2)  without range-checking `index`.

```rust
pub fn map_inner_instructions(
    inner_instructions: solana_message::inner_instruction::InnerInstructionsList,
) -> impl Iterator<Item = InnerInstructions> {
    inner_instructions
        .into_iter()
        .enumerate()
        .map(|(index, instructions)| InnerInstructions {
            index: index as u8,
            instructions: instructions
                .into_iter()
                .map(|info| InnerInstruction {
                    stack_height: Some(u32::from(info.stack_height)),
                    instruction: info.instruction,
                })
                .collect(),
        })
        .filter(|i| !i.instructions.is_empty())
```
