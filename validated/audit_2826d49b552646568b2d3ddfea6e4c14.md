## Binding

`get_confirmations(request_id).len()` **filtered to members still in `self.members`** should equal `num_confirmations` before `confirm()` finalizes and calls `execute_request`. In the actual code, `get_confirmations` returns the raw, unfiltered `HashSet<String>` contents, and `confirm()`'s threshold check (`confirmations.len() as u32 + 1 >= self.num_confirmations`) also counts raw entries without checking membership — so both sides of the binding can diverge when a confirming member is later removed via `delete_member`.

### Title
Stale confirmations from removed members are never purged from non-owned requests, letting `confirm()` execute below live-member threshold - ([File: multisig2/src/lib.rs])

### Summary
`delete_member` only scrubs `self.confirmations` for requests that the *removed member itself created* (`r.member == member`), never for requests created by someone else that the removed member merely *confirmed*. `get_confirmations` and `confirm()`'s quorum check both operate on the raw, unfiltered `HashSet<String>`, so a stale confirmation from a deleted member keeps counting toward `num_confirmations` forever, letting a request execute with fewer live members than required.

### Finding Description
`get_confirmations` simply reads and returns the stored set with no cross-check against `self.members`: [1](#0-0) 

`confirm()` uses the same unfiltered set length for its quorum decision: [2](#0-1) 

`delete_member` removes `self.members` entry and the deleted member's *own* requests/`num_requests_pk`, but only purges `self.confirmations` for requests where `r.member == member` — i.e. requests the removed member originally *created*, not requests they merely *confirmed*: [3](#0-2) 

Exploit/repro flow (no privileged actor needed beyond normal multisig membership turnover, which is exactly the scenario the question asks about):
1. Multisig with members `{A, B, C, D}`, `num_confirmations = 3`.
2. `A` calls `add_request` for request `R1` (e.g. `Transfer`). `A` confirms → `confirmations[R1] = {A}`. `B` confirms → `confirmations[R1] = {A, B}` (2 < 3, stored, not executed).
3. Separately, members create and confirm request `R2 = DeleteMember{B}` with `A`, `C`, `D` (3 confirmations, none from `B`). This reaches quorum and executes `delete_member(B)`. Since `R1.member == A` (not `B`), `delete_member`'s cleanup loop skips `R1`; `confirmations[R1]` still contains `"B"`. `self.members` is now `{A, C, D}`.
4. `get_confirmations(R1)` at this point returns `["A", "B"]` (len 2) even though `B` is absent from `get_members()` — the stale entry is exposed exactly as the question describes.
5. `C` now confirms `R1`: `confirmations.len() + 1 == 3 >= num_confirmations` → `execute_request` runs the `Transfer`, even though only `A` and `C` are live members who ever confirmed (2 live approvals, not 3).

No existing guard prevents this: `assert_valid_request` only checks the request/confirmations map exist, not member-liveness; `current_member()` guards who *can* confirm going forward but never re-validates historical confirmations already stored in the set.

### Impact Explanation
A multisig request (e.g. `Transfer`, `AddKey`, `DeployContract`, `SetNumConfirmations`) can execute with strictly fewer live-member approvals than `num_confirmations` mandates, moving NEAR or changing multisig control below the configured quorum. This is squarely the Critical category "a multisig request executed below `num_confirmations` live members." It is repeatable on every multisig contract instance that experiences member turnover combined with concurrently pending requests, and the blast radius covers any funds/actions the multisig controls.

### Likelihood Explanation
This requires normal, expected multisig lifecycle events (a pending request plus a subsequent legitimate member removal) rather than any exotic attacker capability — membership changes are a routine, intended operation of the contract. Any multisig deployment that rotates members while requests are outstanding is exposed; no special balances or privileged roles beyond the multisig's own configured members are needed to trigger it, and it can recur every time membership changes while a request is pending.

### Recommendation
When deleting a member, iterate all entries in `self.confirmations` (not just requests the member created) and remove the deleted member's string from each confirmation set; alternatively, filter `get_confirmations` and the quorum check in `confirm()` to only count entries whose corresponding member is still present in `self.members`.

### Proof of Concept
```rust
#[test]
fn test_stale_confirmation_after_delete_member() {
    // members = [A, B, C, D], num_confirmations = 3
    let mut c = MultiSigContract::new(members_abcd(), 3);

    // Step 1: A adds R1, A and B confirm (2/3, pending)
    testing_env!(context_with_account(alice(), amount));
    let r1 = c.add_request(transfer_request());
    c.confirm(r1);
    testing_env!(context_with_account(bob(), amount));
    c.confirm(r1);
    assert_eq!(c.confirmations.get(&r1).unwrap().len(), 2);

    // Step 2: A, C, D delete member B via R2 (reaches quorum 3, none from B)
    testing_env!(context_with_account(alice(), amount));
    let r2 = c.add_request(delete_member_request(bob_member()));
    c.confirm(r2);
    testing_env!(context_with_account(carol(), amount));
    c.confirm(r2);
    testing_env!(context_with_account(dave(), amount));
    c.confirm(r2); // executes DeleteMember{B}

    assert!(!c.get_members().contains(&bob_member()));

    // BINDING CHECK: get_confirmations(r1) still lists B, who is not a live member
    let live_confirmations: Vec<_> = c.get_confirmations(r1);
    let stale: Vec<_> = live_confirmations.iter()
        .filter(|m| !c.get_members().iter().any(|mem| mem.to_string() == **m))
        .collect();
    assert!(!stale.is_empty(), "stale confirmation from removed member B is exposed");

    // Step 3: C confirms r1, reaching raw quorum 3 despite only 2 live approvers (A, C)
    testing_env!(context_with_account(carol(), amount));
    c.confirm(r1); // executes despite only 2 live-member approvals, not 3
    assert_eq!(c.requests.len(), /* r1 removed */ 0);
}
```
This demonstrates `get_confirmations(r1)` reporting a stale entry from `B` (absent from `get_members()`) prior to the finalizing `confirm()`, and that the finalizing `confirm()` executes the request using that stale entry to reach the raw `num_confirmations` threshold.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
