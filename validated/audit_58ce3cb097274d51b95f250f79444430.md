### Title
Fee-on-transfer underlying mints unbacked strategy tokens, leaving last claimants unpaid - (contracts/strategies/idle/IdleCreditVault.sol:596)

### Summary
`IdleCreditVault.deposit` mints strategy tokens 1:1 against the *requested* `_amount`, not the *received* amount. If the vault's underlying `token` ever charges a fee on transfer, the CDO's strategy-token balance (its NAV, since `price() == oneToken`) exceeds the underlying actually held, creating permanently unbacked claims that the last withdrawers cannot collect. The same pull-full-amount assumption exists in `collectInstantWithdrawFunds`, `collectWithdrawFunds`, and `finalizeDefaultRecovery`. IdleCDO's own `_deposit` already uses the balance-delta mitigation for tranche minting, but it forwards the gross `_amount` to the strategy, so the mitigation is undone one hop deeper.

### Finding Description
In `IdleCDOCreditVault._deposit`, tranche shares are correctly minted on the measured delta: [1](#0-0) 

but the strategy deposit uses the unadjusted `_amount`: [2](#0-1) 

Inside `IdleCreditVault.deposit`, the strategy pulls `_amount` and mints `_amount` strategy tokens to the CDO regardless of what actually arrived: [3](#0-2) 

Because `price()` is hardwired to `oneToken`, every minted strategy token is NAV'd 1:1 against underlying. With a FoT token, the vault receives `_amount - fee` while the CDO is credited `_amount` of backing. The identical gross-amount assumption appears where funded claims are pulled: [4](#0-3) [5](#0-4) 

and in `finalizeDefaultRecovery`, where `defaultRecoveryReserve` is booked at the nominal `_recoveredAmount` while the reserve balance is smaller: [6](#0-5) 

### Impact Explanation
The broken invariant is solvency: outstanding strategy tokens (CDO backing) plus funded receipt claims exceed actual underlying held by the cumulative fee skimmed on every inbound transfer. Loss is quantified as `totalDeposited * feeRate` (e.g., 1% FoT on 1M USDC deposits → ~10k unbacked). Since there is no mechanism to realize this deficit, the shortfall materializes as permanent freezing for the last withdraw/instant-withdraw claimants, or a `defaultRecoveryPrice`/`lossRecoveryPriceByEpoch` that overstates the real reserve, so defaulted receipts revert or underpay at the tail end.

### Likelihood Explanation
Low-to-medium. It requires the credit vault to be initialized (via the factory/owner) with a fee-on-transfer or rebasing underlying — e.g., a USDT fee toggle or an emerging FoT stablecoin — rather than the currently intended USDC/USDT pool currencies. No unprivileged attacker can *cause* the condition or profit from it directly; the loss is socialized onto claimants, and an early withdrawer can still extract full value, draining the deficit onto later claimants. The finding is the genuine analog of the reported bug class: the codebase partially mitigated it (balance-delta share minting) but left the strategy-funding paths on nominal amounts.

### Recommendation
In `IdleCreditVault.deposit`, `collectInstantWithdrawFunds`, `collectWithdrawFunds`, and `finalizeDefaultRecovery`, measure `underlyingToken.balanceOf(address(this))` before and after `safeTransferFrom` and account/mint only the delta (and reconcile `pendingWithdraws`/`defaultRecoveryReserve` against received amounts). Alternatively, enforce at `initialize`/factory level that the underlying is a known non-FoT token, and document the assumption.

### Proof of Concept
Conceptual Foundry sketch (requires a mock FoT ERC20 since none exists in `test/`):

```solidity
// MockFoTToken: transferFrom moves amount but credits recipient amount*99/100 (1% fee)
function testFoTDepositShortfall() public {
    uint256 amount = 1_000_000e6;
    // lender deposits amount into AA tranche
    fotToken.approve(address(cdo), amount);
    cdo.depositAA(amount); // vault receives 990k, CDO minted 1M strategy tokens

    assertEq(strategy.balanceOf(address(cdo)), amount);       // unbacked
    assertEq(fotToken.balanceOf(address(strategy)), 990_000e6);

    // request + fund withdraw for the full nominal amount;
    // claim pulls amount from strategy -> fails/underflows
    // or second depositor's claim reverts on insufficient balance
}
```

Confirmed behavior: mint uses nominal `_amount` while incoming balance is short, so `claimWithdrawRequest`/`claimInstantWithdrawRequest` revert once cumulative fees exceed the vault's residual balance — reproducible on a fork only if the deployed underlying exhibits FoT behavior.

Caveat: I could not verify whether the credit-vault factory restricts which underlying tokens are permitted; if it whitelists only known compliant tokens, this is a hardening issue rather than a live vulnerability.
