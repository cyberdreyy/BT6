### Title
Instant-withdraw receipts are never cleared per-epoch, so an already-claimed receipt is paid again from the default recovery reserve - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`claimInstantWithdrawRequest` clears only the aggregate `instantWithdrawsRequests[_user]` counter and burns the receipt tokens, but it never zeroes `instantWithdrawsRequestsByEpoch[_user][epoch]` or decrements `instantWithdrawClaimsByEpoch[epoch]`. If a user requests an instant withdrawal in the epoch that later defaults, gets funded via `collectInstantWithdrawFunds`, and claims at par before finalization, the stale per-epoch basis remains. After `defaultRecoveryFinalized`, `_claimDefaultedInstantWithdrawRequest` reads that same stale basis and pays the user a second time out of `defaultRecoveryReserve`. This is the direct analog of the kernel bug: two objects (funded receipt vs defaulted receipt) are merged under one claim path without checking that the per-epoch ownership record was already consumed — a double-spend instead of a UAF.

### Finding Description
- `requestInstantWithdraw` records the basis in both `instantWithdrawsRequests[_user]` and `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and adds to `instantWithdrawClaimsByEpoch[currentEpoch]` [1](#0-0) .
- The normal claim path burns the receipt and pays at par but leaves all per-epoch mappings untouched [2](#0-1) .
- After a default is finalized, `claimInstantWithdrawRequest` first runs `_claimDefaultedInstantWithdrawRequest`, which re-reads `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]`, decrements the reserve-backed counters, burns `claimBasis` strategy tokens, and transfers `claimBasis * defaultRecoveryPrice` from the recovery reserve [3](#0-2) .
- Because the funded claim path never cleared the epoch entry, the defaulted-epoch branch finds a nonzero basis for a receipt whose tokens were already burned and whose underlying was already paid. `_burn(_user, claimBasis)` succeeds only if the user re-acquired strategy tokens (e.g., via a new request or a normal deposit receipt minted post-default via `requestWithdraw`'s post-default path, which mints `_amount` tokens to the user at line 255), or if the user still holds any minted receipt balance — the burn is against the ERC20 balance, not the epoch entry.
- Guard check: `_transferDefaultRecovery` decrements `defaultRecoveryReserve` but cannot distinguish an already-paid basis, and `defaultRecoveryInitialized` gating does not prevent instant withdrawals from being requested and claimed in the default epoch before finalization [4](#0-3) .

### Impact Explanation
One receipt, two payouts. The second payout is drawn from `defaultRecoveryReserve`, which is sized at finalization to cover *unfunded* default-epoch claims. A stale (already-funded) basis inflates the reserve requirement and then directly transfers reserve tokens to the double-claiming user, reducing the recovery pro-rata available to genuine defaulted claimants — quantified theft equal to `staleBasis * defaultRecoveryPrice / 1e18`.

### Likelihood Explanation
Requires a specific sequence: instant withdrawal requested and funded in the same epoch where the borrower subsequently defaults, user claims before `finalizeDefault`, and the user must hold enough strategy-token balance at second-claim time to satisfy the `_burn`. The receipt-minting post-default `requestWithdraw` path (which mints `_amount` tokens to the user) provides a way to re-acquire burnable balance. Triggerable by an unprivileged KYC'd lender; no privileged misbehavior needed.

### Recommendation
In `claimInstantWithdrawRequest`, clear `instantWithdrawsRequestsByEpoch[_user][epoch]` and decrement `instantWithdrawClaimsByEpoch[epoch]` for every epoch contributing to the paid amount (or track and clear the current epoch entry), mirroring how `_clearWithdrawClaimForEpoch` zeroes `withdrawsRequestsByEpoch` on funded normal claims. Alternatively, in `_claimDefaultedInstantWithdrawRequest`, verify the receipt basis is still unfunded rather than relying on the per-epoch mapping alone.

```text
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);

    // burn strategy tokens from user
    _burn(_user, amount);
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
```
