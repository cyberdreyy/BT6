The external report itself contains no exploitable technical detail (it's about a documentation link mislabeled as an access-control bug), so it cannot be used as proof — only as a "bug-class hint" per the rules. Mapping the access-control hint to the strongest reachable custody binding in scope, I found a genuine mismatch between "confirmations counted" and "live members" in the basic multisig contract.

### Title
Stale confirmations from removed multisig keys still count toward the confirmation threshold, allowing a request to execute below the required number of live signers - (File: `multisig/src/lib.rs`)

### Summary
`DeleteKey` only purges requests and confirmations for requests where the deleted key was the *original requester* (`signer_pk`). It never scans other pending requests where that key was merely a *confirmer*. Those stale confirmations remain in the `confirmations` map and are later counted by `confirm()` toward `num_confirmations`, even though the underlying access key no longer exists on the account.

### Finding Description
`add_request`/`confirm` build up a `HashSet<PublicKey>` of confirmations per `request_id` [1](#0-0) . When a member is removed via `MultiSigRequestAction::DeleteKey`, the cleanup logic only removes requests/confirmations for requests *originally added by* that public key: [2](#0-1) 

It does not walk the `confirmations` map to strip that key out of confirmation sets on *other* pending requests it had merely confirmed (without being the original signer). Because `confirm()` only checks `confirmations.len() as u32 + 1 >= self.num_confirmations` [3](#0-2) , a stale confirmation from a now-deleted key counts identically to a confirmation from a currently valid member — the contract has no way to distinguish "confirmed by a live member" from "confirmed by a member that has since been removed," and the code comment in the README itself acknowledges the contract cannot query current live access keys.

### Impact Explanation
This breaks the K-of-N custody binding the multisig is supposed to enforce: `num_confirmations` is meant to equal the number of *currently authorized* signers that approved a request, but the accounting can diverge so that a request executes (including `Transfer`, `FunctionCall`, `DeployContract`, `AddKey`) with fewer live members having actually approved it than the configured threshold. This matches the Critical impact category "a multisig request executed below threshold" — funds can be moved, or contract code/keys changed, by fewer distinct live approvers than the multisig was configured to require.

### Likelihood Explanation
This requires a realistic and even routine sequence of multisig operations: a member confirms a pending request, is later removed (e.g., because their key was compromised or role revoked — the very reason `DeleteKey` exists), and the pending request they touched is left with their orphaned confirmation. Any remaining member(s) confirming afterward will silently push the stale-inclusive count over threshold. No special privilege beyond being a still-valid signer is required to trigger execution; the flawed cleanup logic alone creates the exposure.

### Recommendation
On `DeleteKey`, iterate `self.confirmations` and remove the deleted public key from every confirmation set (not just the requests it originally signed), or alternatively re-validate at `confirm()`-time that each recorded confirming public key is still a valid access key on the account before counting it toward the threshold.

### Proof of Concept
1. Deploy a 3-of-3 multisig with keys A, B, C (`MultiSigContract::new(3)`), analogous to `add_key_delete_key_storage_cleared` test setup [4](#0-3) .
2. A calls `add_request` then `confirm` on a `Transfer` request `R` → `confirmations(R) = {A}`.
3. B calls `confirm(R)` → `confirmations(R) = {A, B}` (2 < 3, not yet executed).
4. A separate request removing B's key is created and confirmed by A and C (a legitimate 3-of-3-minus-B admin action, or 3-of-3 while B still counted) via `MultiSigRequestAction::DeleteKey { public_key: B }`; this only clears requests where `signer_pk == B` — request `R` (added by A) is untouched, so `confirmations(R)` still contains B's now-deleted key.
5. C calls `confirm(R)` → `confirmations(R).len() + 1 == 3 >= num_confirmations(3)`, and `execute_request` fires the `Transfer`, even though only A and C are currently live signers (2 of the 3 configured threshold), with B's stale, no-longer-valid confirmation making up the difference.

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
