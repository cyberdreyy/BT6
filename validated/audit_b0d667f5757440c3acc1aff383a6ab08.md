### Title
Stale confirmations from removed multisig members are not purged, allowing request execution below the live-member threshold - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::confirm` counts entries in the `confirmations` `HashSet<String>` for a request against `num_confirmations` without verifying that every counted confirmer is still a current member of the multisig. `delete_member` only purges confirmations/requests that a removed member *originally created* (`r.member == member`), but it never scans the `confirmations` map to strip a removed member's confirmation from *other* pending requests that member had merely confirmed. This allows a request to execute with fewer live-member confirmations than `num_confirmations` requires.

### Finding Description
`confirm()` reaches execution once `confirmations.len() as u32 + 1 >= self.num_confirmations`: [1](#0-0) 

`delete_member()` is the only cleanup path for a removed member, and it filters requests by `r.member == member` (i.e., requests *originated* by that member), removing those requests/confirmations entirely — it does not touch the `confirmations` set of any other request where the removed member's confirmation is merely recorded but did not originate the request: [2](#0-1) 

`assert_valid_request()`, called by both `confirm` and `delete_request`, only checks that the *current caller* is a member and that the request/confirmation entries exist — it performs no validation that the confirmations already stored for the request belong to accounts/keys that are still members: [3](#0-2) 

Consequently:
1. Member `A` confirms a pending request `R1` (created by member `B`), so `confirmations(R1) = {A}`.
2. The multisig (via a separate, fully-confirmed `DeleteMember` request) removes `A` as a member — e.g., because `A`'s key was compromised or `A` is no longer trusted.
3. `delete_member` does not touch `R1`'s confirmation set because `R1.member == B`, not `A`. `confirmations(R1)` still contains `A`.
4. A single additional live member (`C`) confirms `R1`. `confirmations.len() + 1` reaches `num_confirmations`, and `R1` executes — even though only `B`(implicit, as the request creator does not auto-confirm unless `add_request_and_confirm` was used) and `C` are still legitimate members, while `A`'s stale confirmation is counted as if it were a live approval.

This breaks the intended equality "distinct confirmations from *current* members == threshold satisfied." The binding that should hold — `num_confirmations` live-member approvals authorize execution — is violated because a removed member's historical approval still counts.

### Impact Explanation
This falls under the Critical impact category "a multisig request executed below threshold." An attacker who once held a member key (later revoked, e.g. after a suspected compromise or an off-boarded signer) leaves a permanent, uncleared "ghost vote" on any request they confirmed before removal. If that request is later pushed to completion by fewer live members than `num_confirmations` requires, arbitrary `Transfer`, `FunctionCall`, `AddKey`/`AddMember`, or `DeployContract` actions on the multisig account can be executed with fewer independent, currently-authorized approvals than the K-of-N policy demands — a direct threshold-bypass on an account custody mechanism (funds, keys, and contract code of the multisig account).

### Likelihood Explanation
Likelihood is moderate to high in realistic operational scenarios: multisig membership changes (onboarding/offboarding signers, rotating a compromised key) are a normal, expected admin action, and any request pending at the time of a `DeleteMember` action that was not created by the removed member will silently retain that member's stale confirmation. No malicious collusion is strictly required beyond the removed member having confirmed a request before being deleted; a currently malicious or compromised (former) member can deliberately pre-confirm many pending requests before being caught and removed, banking "votes" that survive removal and can later push those requests past a threshold with fewer live approvers than intended.

### Recommendation
When removing a member (`delete_member`), iterate over `self.confirmations` (or maintain a reverse index from member → confirmed request IDs) and strip that member's confirmation from every pending request, not just requests the member originally created. Alternatively, at confirmation-count time in `confirm()`, recompute the confirmation count by filtering `confirmations.get(&request_id)` against `self.members.contains(...)` for each stored entry before comparing against `num_confirmations`, ensuring only currently valid members' confirmations are counted.

### Proof of Concept
1. Deploy `MultiSigContract::new(members = [A, B, C, D], num_confirmations = 3)`.
2. As `B`, call `add_request(R1: Transfer{...})` → `confirmations(R1) = {}`.
3. As `A`, call `confirm(R1)` → `confirmations(R1) = {A}` (below threshold of 3, not executed).
4. Separately, get a 3-of-4 confirmed request `R2: DeleteMember{A}` executed (via `B`, `C`, `D` confirming) — `delete_member(A)` runs; since `R1.member == B` (not `A`), `R1`'s confirmation set is untouched and still contains `A`. Members are now `{B, C, D}`.
5. As `C`, call `confirm(R1)` → `confirmations(R1).len() + 1 == {A, C}.len() + 1 == 3 >= num_confirmations (3)` → `execute_request(R1)` fires the `Transfer`, even though only `B` (implicitly, if `add_request_and_confirm` was not used, not even confirmed) and `C` are live members who ever explicitly approved `R1`, and `A` — now removed — is counted as an approver.     /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
