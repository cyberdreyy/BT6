### Title
Zip cache extraction path traversal via crafted `zip.File.Name` allows writes outside the destination directory - (File: `helpers/archives/zip_extract.go`)

### Summary
`CacheExtractorCommand.Execute` passes the current working directory (`wd`) to `archive.NewExtractor(archive.Zip, ...)`, but the resulting `ziplegacy.extractor.Extract` never uses that `dir` value at all — it calls `archives.ExtractZipArchive(zr)` directly. Inside `extractZipFile`, the code does `os.MkdirAll(filepath.Dir(file.Name), 0o777)` and `os.OpenFile(file.Name, ...)` using the raw, attacker-controlled `zip.File.Name` with no join against a base directory and no containment check, unlike the sibling `tarzstd` extractor which explicitly validates `strings.HasPrefix(path, e.dir+string(filepath.Separator))`.

### Finding Description
The reachable path is:
`commands/helpers/cache_extractor.go: CacheExtractorCommand.Execute` (`commands/helpers/cache_extractor.go:655`) → `archive.NewExtractor(format, f, size, wd)` → for zip format, `ziplegacy.NewExtractor` (`commands/helpers/archive/ziplegacy/zip_legacy_extractor.go:20-22`), which stores `dir` in the `extractor` struct but its `Extract` method (`zip_legacy_extractor.go:26-32`) ignores `e.dir` entirely and calls `archives.ExtractZipArchive(zr)`.

`ExtractZipArchive` (`helpers/archives/zip_extract.go:85-110`) iterates `archive.File` and calls `extractZipFile(file)` (`zip_extract.go:61-83`), which does:
```go
err = os.MkdirAll(filepath.Dir(file.Name), 0o777)
...
out, err = os.OpenFile(file.Name, os.O_WRONLY|os.O_CREATE|os.O_TRUNC, file.Mode().Perm())
```
`file.Name` comes straight from the zip entry header with **no `filepath.Join(dir, ...)`, no `filepath.Abs`, and no prefix check** against any base directory. The only validation applied is `errorIfGitDirectory` (`helpers/archives/path_check_helper.go`), which only checks if the cleaned path's first component is `.git` — it does nothing to block `..` traversal or absolute paths.

Compare this to `commands/helpers/archive/tarzstd/tarzstd_extractor.go:58-64`, which explicitly joins against `e.dir`, takes `filepath.Abs`, and rejects any path escaping the directory prefix. The zip legacy path has no equivalent guard.

Attacker control: a CI job can produce and upload `cache.zip` (via `cache-archiver`) with arbitrary control over entry contents when a subsequent job in the same pipeline restores that cache via `cache-extractor` (invoked internally by the Runner as `gitlab-runner-helper cache-extractor`). By crafting an entry name like `../../../etc/cron.d/x` (or an absolute path such as `/etc/cron.d/x`), the extractor will create/write that file relative to (or ignoring) the job's working directory `wd`, rather than confining it there.

### Impact Explanation
Because `os.MkdirAll(filepath.Dir(file.Name))` and `os.OpenFile(file.Name)` operate on the raw entry name with no directory confinement, a malicious cache archive can write files anywhere the runner process's OS user has permission to write, outside the job's build/cache root — violating the "file operations must stay within intended build/cache/artifact roots" invariant. Depending on the runner's execution context (e.g. shell executor, or any executor where the helper process runs with meaningful host filesystem permissions), this can corrupt or plant files outside the sandboxed job directory.

### Likelihood Explanation
Feasible and repeatable: the CI cache mechanism explicitly allows a job to define and upload a cache archive that is later downloaded and extracted by a subsequent job/pipeline. The zip archive format and entry names are fully attacker-controlled since a job can write the `cache.zip` itself before calling `cache-archiver`/before triggering the download-extract flow (or by directly crafting the cache blob if it can also control the storage location, which is the documented mechanism for GitLab cache). No special privilege beyond normal pipeline authoring is needed; the vulnerable code path executes on every zip-based cache restore. The only precondition is that the executor's zip decompression path is used (as opposed to `fastzip`/`tarzstd`, which are the modern implementations) — legacy/`ziplegacy` extractor selection depends on `archive.NewExtractor`'s dispatch logic (build/environment configuration), so applicability may be scoped to configurations that use the zip legacy extractor rather than fastzip.

### Recommendation
Add path containment validation in `ziplegacy.extractor.Extract` (or in `archives.ExtractZipArchive`/`extractZipFile`) analogous to `tarzstd_extractor.go`: for each `file.Name`, compute `path := filepath.Join(e.dir, file.Name)` (or `filepath.Abs`), verify `strings.HasPrefix(path, e.dir+string(filepath.Separator))` (or equals `e.dir`), and reject/skip entries that escape, before any `MkdirAll`/`OpenFile`/`Symlink` calls. Since `ExtractZipArchive` currently takes no `dir` parameter, thread the destination directory through from `ziplegacy.extractor.Extract` into `ExtractZipArchive`/`extractZipFile` so the check can be enforced centrally for both `ExtractZipArchive` and `ExtractZipFile` callers.

### Proof of Concept
Go unit test in `helpers/archives`:
```go
func TestExtractZipArchive_PathTraversal(t *testing.T) {
    tmpDir := t.TempDir()
    outside := filepath.Join(filepath.Dir(tmpDir), "outside-poc.txt")
    defer os.Remove(outside)

    buf := new(bytes.Buffer)
    zw := zip.NewWriter(buf)
    w, err := zw.Create("../" + filepath.Base(outside))
    require.NoError(t, err)
    _, err = w.Write([]byte("pwned"))
    require.NoError(t, err)
    require.NoError(t, zw.Close())

    zr, err := zip.NewReader(bytes.NewReader(buf.Bytes()), int64(buf.Len()))
    require.NoError(t, err)

    oldWd, _ := os.Getwd()
    defer os.Chdir(oldWd)
    require.NoError(t, os.Chdir(tmpDir))

    err = ExtractZipArchive(zr)
    require.NoError(t, err)

    _, statErr := os.Stat(outside)
    // Expected (fixed): traversal should fail to create the file
    require.True(t, os.IsNotExist(statErr), "file was created outside destination dir: %s", outside)
}
```
Current behavior: the assertion fails because `outside-poc.txt` is created outside `tmpDir`, confirming the path traversal.
