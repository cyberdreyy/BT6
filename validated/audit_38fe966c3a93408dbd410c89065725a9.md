### Title
Builder withdrawal amount is not capped to available balance before being committed to the execution payload, allowing Gwei to be minted beyond the builder's deducted balance - (File: specs/gloas/beacon-chain.md)

### Summary
`get_builder_withdrawals` builds each `Withdrawal.amount` directly from the *requested* `BuilderPendingWithdrawal.amount` in `state.builder_pending_withdrawals` without capping it to the builder's current `balance`. That uncapped amount is placed into `state.payload_expected_withdrawals`, which the execution layer is required to honor and mint to `withdrawal.fee_recipient`. Meanwhile, `apply_withdrawals` deducts only `min(withdrawal.amount, builder_balance)` from the builder's consensus-layer balance. When `amount > balance`, the EL mints the full requested amount while the CL only debits the (smaller) available balance, creating Gwei that is not backed by any decrease in stake.

### Finding Description
The withdrawal pipeline for builders is:
1. `process_execution_payload_bid` / `apply_parent_execution_payload` enqueue a `BuilderPendingWithdrawal(fee_recipient, amount, builder_index)` into `state.builder_pending_withdrawals` for the committed bid value [5](#0-4) .
2. `get_builder_withdrawals` (called from `get_expected_withdrawals`) converts each pending entry into a `Withdrawal` using the **raw requested `amount`**, with no comparison against `state.builders[builder_index].balance`:
```python
withdrawals.append(
    Withdrawal(
        index=withdrawal_index,
        validator_index=convert_builder_index_to_validator_index(builder_index),
        address=withdrawal.fee_recipient,
        amount=withdrawal.amount,
    )
)
``` [1](#0-0) 
3. `update_payload_expected_withdrawals` writes this list verbatim to `state.payload_expected_withdrawals` [2](#0-1) . This field is the CL's binding commitment to what the EL must mint to each `address` (analogous to the `withdrawals` list in an execution payload in earlier forks).
4. `apply_withdrawals`, applied in the *same* block, deducts only the capped amount from the builder's own balance:
```python
if is_builder_index(withdrawal.validator_index):
    builder_index = convert_validator_index_to_builder_index(withdrawal.validator_index)
    builder_balance = state.builders[builder_index].balance
    state.builders[builder_index].balance -= min(withdrawal.amount, builder_balance)
``` [3](#0-2) 

If `withdrawal.amount > builder_balance`, the deduction saturates at `builder_balance` (balance goes to 0), but the *committed* `Withdrawal.amount` that the EL must mint to `fee_recipient` remains the full, uncapped `withdrawal.amount`. This breaks the equality "Gwei minted to an address == Gwei removed from state," creating Gwei that is not backed by any corresponding stake reduction — the exact "asset paid without corresponding deduction" pattern described in the external report (where `whbar` was unwrapped/paid without a matching balance decrease from the correct account).

Notably, this is the *opposite* fix from the one gloas made for validator sweep/full withdrawals, where the spec authors explicitly note they moved the balance deduction to be applied immediately (rather than deferred) specifically "to prevent CL-side saturation from creating a net supply inflation" (see `process_withdrawals` note) [6](#0-5) . That reasoning was not applied consistently to the builder withdrawal amount used to populate `payload_expected_withdrawals` — the commitment amount itself is never capped, only the state deduction is.

### Impact Explanation
This falls under "Gwei created ... paid to a non-owner": the execution layer mints `withdrawal.amount` (uncapped) to `fee_recipient`, while consensus state only ever loses `min(amount, balance)`. The difference is unbacked Gwei injected into the EL account of `fee_recipient`, i.e., a supply-invariant violation reachable purely by a builder (or proposer/builder collusion) requesting a withdrawal amount that exceeds the builder's actual balance — which is entirely possible since `BuilderPendingWithdrawal.amount` is taken from `bid.value` at bid-acceptance time, and time can pass (multiple slots, exits, other withdrawals) before the pending withdrawal is actually processed, during which the builder's balance can shrink below the pending amount.

### Likelihood Explanation
The test suite itself demonstrates this scenario is a reachable, spec-legal state (`test_builder_withdrawal_insufficient_balance`, `test_builder_withdrawal_insufficient_balance_realistic_bounds`), confirming `builder_pending_withdrawals` amounts are not re-validated against current balance at the time of processing, and that the discrepancy between committed `amount` and actual deduction is treated as expected/normal behavior in tests rather than flagged as a bug in the state transition itself.

### Recommendation
Cap the committed `Withdrawal.amount` in `get_builder_withdrawals` to `min(withdrawal.amount, state.builders[builder_index].balance)` (accounting for withdrawals already queued ahead of it in `prior_withdrawals`, similar to how `get_pending_partial_withdrawals` computes `balance = get_balance_after_withdrawals(...)`), so the amount placed into `state.payload_expected_withdrawals` never exceeds what `apply_withdrawals` will actually deduct.

### Proof of Concept
1. A builder submits/accepts a bid with `value = V`, causing a `BuilderPendingWithdrawal(fee_recipient=F, amount=V, builder_index=B)` to be appended to `state.builder_pending_withdrawals`.
2. Before this pending withdrawal is processed, `state.builders[B].balance` drops below `V` (e.g., through other withdrawals/exits that reduce it, or simply because further pending withdrawals for the same builder are queued first and drain the balance).
3. In a later block, `process_withdrawals` runs: `get_builder_withdrawals` emits `Withdrawal(amount=V, address=F)` into `payload_expected_withdrawals` (as demonstrated by `test_builder_withdrawal_insufficient_balance_realistic_bounds`, which explicitly sets `withdrawal_amount = MIN_DEPOSIT_AMOUNT + 123`, `available_balance = MIN_DEPOSIT_AMOUNT + 122` and asserts `withdrawal_amounts_builders={builder_index: withdrawal_amount}` while `builder_balances={builder_index: 0}`) [4](#0-3) .
4. `apply_withdrawals` only deducts `min(V, balance) = balance` from the builder, i.e., strictly less than `V`.
5. The execution layer, honoring `payload_expected_withdrawals`, mints the full `V` Gwei to `F`. Total supply increases by `V - balance`, Gwei created without a matching deduction anywhere in the system.

*Note*: Unlike deposits (which are applied at the child's slot via
`apply_parent_execution_payload`), withdrawal balance deductions are applied
immediately via `apply_withdrawals`. Deferring the deduction to the child's slot
would break the total supply invariant: state transitions between the commitment
slot and the deduction slot (e.g., `process_pending_consolidations` at an epoch
boundary) can reduce a validator's balance below the committed withdrawal
amount, causing `decrease_balance` to saturate at zero. Since the execution
layer mints the full committed amount regardless, any CL-side saturation creates
a net supply inflation. As a consequence, `state.balances` reflects the
withdrawal deduction before the corresponding execution payload is confirmed,
creating a transient asymmetry with the EL state at `state.latest_block_hash`.
Off-chain consumers that require CL/EL balance consistency can reconstruct
pre-deduction balances by adding back `state.payload_expected_withdrawals`.
