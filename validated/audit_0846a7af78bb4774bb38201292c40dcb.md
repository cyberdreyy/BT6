### Title
Loss-adjusted withdraw receipt is paid at par when a later request overwrites `lastWithdrawRequest` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
When `stopEpochWithDuration` funds pending withdraw receipts only partially, `collectWithdrawFunds` stores a haircut in `lossRecoveryPriceByEpoch[requestEpoch]`. The only place that haircut is enforced is `_claimLossAdjustedWithdrawRequest`, which looks the epoch up via `lastWithdrawRequest[user]` — i.e. the user's *latest* request epoch. If the user makes a second withdraw request in a later epoch, the earlier loss-adjusted receipt falls through to `_claimFundedWithdrawRequest`, which pays the aggregate `withdrawsRequests[user]` at par. The denied portion of the haircutted receipt is returned in full, draining funded underlyings that belong to other claimants.

### Finding Description
The external bug class is a value that was supposed to be replaced/redacted falling through a generic path that returns the original value in full. Here:

1. `collectWithdrawFunds` records `lossRecoveryPriceByEpoch[epoch] = funded / pendingBasis` when the borrower funds less than `pendingWithdraws` (IdleCreditVault.sol:411-420).
2. `claimWithdrawRequest` tries `_claimLossAdjustedWithdrawRequest` first, but it only checks `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]]` (IdleCreditVault.sol:789-792).
3. `requestWithdraw` sets `lastWithdrawRequest[user] = currentEpoch` and aggregates into `withdrawsRequests[user] += amount` on every request, and the code comments explicitly allow a second request while the first is unclaimed (IdleCreditVault.sol:282-293, 323-324).
4. After a later request, `lastWithdrawRequest` points at a non-loss epoch, so `_claimLossAdjustedWithdrawRequest` returns 0 and `_claimFundedWithdrawRequest` pays `withdrawsRequests[user]` — which still contains the epoch-1 haircutted basis — at par (IdleCreditVault.sol:319-349). `_clearWithdrawClaimForEpoch` even encodes the flawed assumption that "any remaining … receipt is older and already funded" (line 833-834), which is false for loss-adjusted epochs.
5. `_transferFundedClaim` only protects `defaultRecoveryReserve`; it does not segregate other users' funded claim balances (IdleCreditVault.sol:897-907).

### Impact Explanation
The attacker receives `claimBasis * (1 - lossRecoveryPrice)` more than funded for the loss-adjusted epoch. That excess is paid from the strategy's underlying balance, i.e. from funded underlyings reserved for other users' withdraw claims — direct theft / insolvency of the funded-claim pool. Loss scales with the haircut size; a 50% recovery epoch-1 receipt yields a 50% overpayment.

### Likelihood Explanation
Fully unprivileged path: any tranche holder can call `requestWithdraw` twice across epochs. Requires an honest `stopEpochWithDuration` partial funding (a real loss event) followed by a later normal epoch, and the attacker requesting again after the loss epoch before claiming. No privileged misbehavior required; all gating (epoch ended check at line 326, `_onlyIdleCDO`) is satisfied.

### Recommendation
In `_claimLossAdjustedWithdrawRequest`, iterate or track all epochs with a non-zero `lossRecoveryPriceByEpoch` for the user (e.g. store the loss-epoch per user, or apply the haircut per `withdrawsRequestsByEpoch` entry), and subtract the loss-adjusted basis from `withdrawsRequests[user]` so the funded path never pays it at par. Alternatively, revert `requestWithdraw` when the user has an unclaimed loss-adjusted receipt.

### Proof of Concept
Foundry fork sketch (mirroring existing helpers in `test/foundry/IdleCreditVault.t.sol`):

```solidity
// epoch 0: deposit + start epoch
_depositWithUser(attacker, 100_000 * ONE_SCALE, true);
_startEpochAndCheckPrices(0);
_stopEpochAndCheckPrices(0, apr, expected);

// epoch 1 buffer: attacker requests withdraw of half
vm.prank(attacker);
uint256 basis1 = cdoEpoch.requestWithdraw(50_000 * ONE_SCALE, address(AAtranche));
_startEpochAndCheckPrices(1);

// borrower funds only 50% of pending basis -> lossRecoveryPriceByEpoch[1] = 0.5e18
// (drive via cdoEpoch.stopEpochWithDuration with _lossAmount, which calls
//  strategy.collectWithdrawFunds with the shortfall)

// epoch 2: attacker requests again (allowed; comment: "will have to wait
// for another epoch to claim both requests")
vm.prank(attacker);
cdoEpoch.requestWithdraw(1 * ONE_SCALE, address(AAtranche));
// strategy.lastWithdrawRequest(attacker) == 2, lossRecoveryPriceByEpoch[2] == 0

// end epoch 2 so epochNumber > lastWithdrawRequest
_startEpochAndCheckPrices(2);
_stopEpochAndCheckPrices(2, apr, expected);

uint256 balPre = underlying.balanceOf(attacker);
vm.prank(attacker);
cdoEpoch.claimWithdrawRequest();

// BUG: paid 50_000e18 + 1e18 at par, while only 25_000e18 was funded for epoch 1.
assertGt(underlying.balanceOf(attacker) - balPre, 25_000 * ONE_SCALE + 1 * ONE_SCALE);
```

Uncertainty note: I verified the claim-path logic in `IdleCreditVault.sol` but could not re-confirm in this iteration the exact `stopEpochWithDuration` → `collectWithdrawFunds` wiring in `IdleCDOEpochVariant.sol`; the loss-price storage path is directly evidenced at `IdleCreditVault.sol:411-420` and consumed at `789-801`, so the overpayment follows provided a partial-funding epoch is reachable, which the codebase's own tests (e.g. `lossRecoveryPriceByEpoch` usage) assume.
