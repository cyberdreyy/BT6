### Title
External Initiator credentials can trigger runs on ANY job by integer ID with no binding to the initiator's registered job - authorization bypass via `isUser` conflation - ([File: core/web/pipeline_runs_controller.go])

### Summary
The route `userOrEI.POST("/jobs/:ID/runs", auth.RequiresRunRole(prc.Create))` in `core/web/router.go` is reachable via either a real user session/token OR External-Initiator (EI) credentials, because `auth.AuthenticateExternalInitiator` sets the same `SessionUserKey` as real authenticated users. `PipelineRunsController.Create` uses `auth.GetAuthenticatedUser` only to distinguish "is this a user vs. an unauthenticated caller" for the purpose of allowing integer job IDs, but that check is trivially satisfied by any valid EI credential, letting an EI-holder run any job by numeric ID with no verification that the EI is associated with that job at all.

### Finding Description
The route is wrapped with three chained auth methods: `auth.AuthenticateExternalInitiator`, `auth.AuthenticateByToken`, `auth.AuthenticateBySession` [1](#0-0) .

`AuthenticateExternalInitiator` authenticates solely via `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers matched against `FindExternalInitiator`, and on success sets **both** `SessionExternalInitiatorKey` and a synthetic `SessionUserKey` = `&clsessions.User{Role: clsessions.UserRoleRun}` [2](#0-1) .

`auth.RequiresRunRole` only checks `user.Role == clsessions.UserRoleView` to reject; since the synthetic EI user has `Role: UserRoleRun`, this check passes trivially and the handler proceeds to `prc.Create` [3](#0-2) .

Inside `PipelineRunsController.Create`, the code calls `_, isUser := auth.GetAuthenticatedUser(c)` and treats `isUser == true` as license to parse `idStr` as an int32 job ID and call `prc.App.RunJobV2(ctx, jobID, nil)` directly — with **no check whatsoever that the job identified by `jobID` is associated with, or was registered for, the authenticated External Initiator** [4](#0-3) .

The comment in the code ("only users are allowed to run jobs using int IDs - EIs not allowed") reflects the intended design, but the implementation is broken: `GetAuthenticatedUser` cannot distinguish a genuine session/token user from the synthetic EI-user object set by `AuthenticateExternalInitiator`, since both are stored under the identical `SessionUserKey` as a `*clsessions.User`. This means the "EIs not allowed" comment is factually false in the current code path — any EI credential holder satisfies `isUser` and can invoke `RunJobV2` for an arbitrary integer job ID, regardless of which job(s) that EI was registered against.

No binding/verification logic between the External Initiator's name/identity (obtainable via `auth.GetAuthenticatedExternalInitiator`) and the target job's `ExternalInitiatorWebhookSpec`/associated initiator name exists anywhere in the `Create` handler.

### Impact Explanation
This is an authorization bypass / unauthorized action on another party's resource: a caller who only holds credentials for an external initiator scoped to trigger a specific job (e.g., name `foo`) can trigger pipeline runs for **any** other job in the node by integer ID (e.g., a job with initiator name `bar`, or any non-webhook job entirely), matching Chainlink's "unauthorized job run" bounty impact class. Since job runs can execute arbitrary pipeline tasks (HTTP calls, on-chain transactions via `ethtx`, bridge calls, etc.), this can lead to unauthorized fund movement or unauthorized external side effects depending on job composition, and it breaks the tenant/initiator isolation the code comment explicitly claims to enforce.

### Likelihood Explanation
The only precondition is possession of valid credentials for **any** registered External Initiator on the node (an `X-Chainlink-EA-AccessKey`/`Secret` pair) — this is exactly the "external-initiator credential holder" attacker class permitted by the rules. No admin/edit/view role or extra privilege is required beyond that single EI credential; the attack is a single unauthenticated-w.r.t.-jobs HTTP POST to `/v2/jobs/:ID/runs` with an arbitrary integer job ID, fully repeatable.

### Recommendation
In `PipelineRunsController.Create`, distinguish real authenticated users from EI-derived synthetic users (e.g., by checking `auth.GetAuthenticatedExternalInitiator` is absent, or by using a distinct context key/type for EI-originated "users"), and reject EI-originated requests from the integer-ID/`RunJobV2` code path entirely, consistent with the existing code comment intent. If EI-triggered runs by integer ID are to be supported going forward, add an explicit check that the target job's configured external initiator name/spec matches the authenticated EI's identity before calling `RunJobV2`.

### Proof of Concept
Go handler-level integration test (extending `core/services/job/runner_integration_test.go` patterns and `pipeline_runs_controller_test.go`):
1. Start a `TestApplication` with `JobPipeline.ExternalInitiatorsEnabled = true`.
2. Create External Initiator `foo` via `cltest.CreateExternalInitiatorViaWeb`, capture `AccessKey`/`Secret`.
3. Create (or insert directly via ORM) a second, unrelated job `jobB` (int32 ID, e.g. a `directrequest` or `cron` job) that has no relation to initiator `foo` (e.g., named/associated with `bar` or with no external initiator at all).
4. Send `POST /v2/jobs/<jobB.ID>/runs` with headers `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` set to `foo`'s credentials, using `cltest.UnauthenticatedPost`.
5. Assert: expected/secure behavior would be `401`/`403` due to missing initiator-to-job binding; actual current behavior is `200 OK` with a `PipelineRunResource` created for `jobB`, and `pipeline_runs` count incremented for `jobB` — demonstrating the bypass. Compare against `TestRunner_WebhookJobRemoved` at `core/services/job/runner_integration_test.go:779-850`, which shows the existing test suite only checks the (now-removed) UUID webhook path, not this integer-ID EI-bypass path.

func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionExternalInitiatorKey, ei)

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
