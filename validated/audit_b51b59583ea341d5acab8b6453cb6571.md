## Title
Stale confirmations from deleted multisig keys still count toward `num_confirmations`, allowing a request to execute below the effective live-signer threshold - (`multisig/src/lib.rs`)

### Summary
The `MultiSigContract::confirm` function in `multisig/src/lib.rs` tallies confirmations purely by the size of a `HashSet<PublicKey>` stored per `request_id`, without re-validating that every public key in that set still corresponds to a currently authorized multisig access key. When a key is removed via the `DeleteKey` request action, the cleanup logic only purges *requests originated by* that key — it does not purge that key's *confirmations* recorded on other still-pending requests. A pending request can therefore be executed later using a mix of live and already-revoked confirmations, moving fewer than `num_confirmations` currently-authorized signers.

### Finding Description
`confirm()` compares `confirmations.len() + 1 >= self.num_confirmations` to decide whether to execute a request: [1](#0-0) 

The only place stale confirmations are cleaned up is inside `execute_request`'s `DeleteKey` branch, and it only removes **requests** whose `signer_pk` equals the deleted key — not confirmation entries left by that key on *other* outstanding requests: [2](#0-1) 

Sequence:
1. Multisig has keys A, B, C with `num_confirmations = 3`.
2. Key A adds request R1 (transfer funds) and confirms it (`confirmations = {A}`). Key B also confirms R1 (`confirmations = {A, B}`), which is 2/3 — not yet executed.
3. Separately, the multisig (with 3/3 confirmations from A, B, C) executes a `DeleteKey { public_key: A }` request to revoke key A (e.g., rotating out a suspected-compromised key). This only removes requests where `signer_pk == A`; R1 was signed/added by A too in this scenario, so pick a slightly different ordering where R1 is added by B instead, so it survives: `signer_pk = B`, confirmations set still `{A, B}` — this is untouched by A's deletion.
4. Key A is now deleted from the account's access keys, but `confirmations` for R1 still literally contains A's old public key.
5. Key C now confirms R1: `confirmations.len() + 1 == 3 >= num_confirmations (3)`, so R1 executes — using a confirmation count that includes a public key no longer present on the account at all.

The binding that should hold is: `count(confirmations that belong to currently-authorized signers) >= num_confirmations`. Instead the code enforces `count(confirmations ever recorded, including from revoked keys) >= num_confirmations`, breaking the authorization threshold guarantee the multisig is supposed to provide.

### Impact Explanation
This is a threshold-bypass on a multisig contract that directly custodies NEAR and controls arbitrary `Transfer`, `FunctionCall`, `AddKey`/`DeleteKey`, and `DeployContract` actions. Execution of a request with fewer than the intended number of *currently valid* confirmations is exactly the "a multisig request executed below threshold" Critical impact category — funds or contract control can move with less authorization than configured, e.g., after legitimately rotating out a compromised or departing signer, that signer's stale sign-off can still count toward executing a stale pending transfer request.

### Likelihood Explanation
This requires: (a) an outstanding unconfirmed request signed/confirmed by a key that is later removed via `DeleteKey`, and (b) that request later reaching threshold via remaining live keys plus the stale confirmation. This is a realistic operational sequence for any multisig that rotates keys while requests are in flight — no attacker-controlled deployment or foundation privilege is needed beyond being one of the legitimate multisig signers, and key rotation for security reasons is an expected, encouraged workflow, not an edge case.

### Recommendation
When executing `DeleteKey` (or any key/member removal), iterate over `self.confirmations` for **all** requests and remove the deleted `public_key` from every confirmation set, not just requests where it is the original `signer_pk`. Alternatively, when confirming, filter `confirmations` down to keys still valid at confirm-time before comparing to `num_confirmations`. This is analogous to what the newer `multisig2/src/lib.rs::delete_member` attempts to do for `requests`, but it likewise does not scrub `confirmations` entries for other pending requests.

### Proof of Concept
1. Deploy `multisig` with 3 keys (A, B, C), `num_confirmations = 3`.
2. As B, `add_request` for R1 (a `Transfer`), then `confirm` as B (`confirmations = {B}`); confirm again as A (`confirmations = {A, B}`), R1 pending at 2/3.
3. Separately create and fully confirm a request `{ actions: [DeleteKey { public_key: A }] }` with A, B, C (3/3) — this executes and removes A's access key, since the cleanup in the `DeleteKey` branch (`multisig/src/lib.rs:198-216`) only removes requests where `r.signer_pk == A`, and R1 was signer_pk `B`, so R1's confirmation set `{A, B}` is left untouched.
4. As C, call `confirm(R1)`: `confirmations.len() + 1 == 3 >= num_confirmations (3)` at `multisig/src/lib.rs:255`, so R1 (the `Transfer`) executes, despite A no longer being an authorized key on the account.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
