### Title
Unprivileged ERC4626 vault withdrawal can repeatedly block `stopEpoch` and freeze pending withdrawals - (File: `contracts/strategies/idle/ProgrammableBorrower.sol`)

### Summary
In programmable-borrower mode, an unprivileged user of the configured ERC4626 vault can remove vault liquidity immediately before the manager calls `IdleCDOEpochVariant.stopEpoch`. `ProgrammableBorrower.onStopEpoch` recognizes that the borrower’s vault shares may economically cover the required amount, but reverts if the vault withdrawal itself fails because liquid assets are unavailable. The entire stop transaction is therefore retryable only if vault liquidity returns, and an attacker can repeatedly front-run each retry to keep the epoch open and prevent pending withdrawal receipts from maturing.

### Finding Description
`IdleCDOEpochVariant._stopEpoch` calls `IProgrammableBorrower.onStopEpoch` for `_amountToPullFromBorrower + _pendingWithdraws` before collecting funds from the borrower. [1](#0-0) 

Inside `onStopEpoch`, if borrower cash is insufficient, the shortfall is withdrawn from the ERC4626 vault. The code deliberately returns `true` only when the vault shares do not economically cover the shortfall. If coverage exists but `vault.withdraw` reverts, it throws `StopEpochVaultLiquidityUnavailable`, reverting the whole epoch stop. [2](#0-1) 

An attacker who is an ordinary shareholder/depositor in the external ERC4626 vault can withdraw or redeem their own position and reduce the vault’s liquid underlying balance below `shortfall`. Because the borrower still owns vault shares whose reported asset value covers the shortfall, the code enters the guarded withdrawal path and reverts rather than treating the situation as an economic borrower default. [3](#0-2) 

The failed call occurs before epoch rollover, withdrawal funding, accounting updates, and `epochNumber` advancement. [4](#0-3)  Pending withdrawal holders consequently remain unable to claim: `_claimFundedWithdrawRequest` reverts while `epochNumber <= lastWithdrawRequest[_user]` and `epochEndDate` is nonzero. [5](#0-4) 

### Impact Explanation
An unprivileged ERC4626 vault participant can indefinitely delay settlement of the credit pool by keeping the vault’s immediately withdrawable liquidity below the required stop amount.

The directly frozen amount is at least:

```text
_amountToPullFromBorrower + pendingWithdraws
```

where `pendingWithdraws` is the aggregate amount owed to pending receipt holders. In minted-interest mode this is normally the pending withdrawal amount; in cash-interest or close-pool operation it can also include epoch interest or recalled principal. Because the epoch never rolls, pending receipt holders cannot convert their receipts to underlying, even though the borrower’s vault shares still have sufficient reported value to cover them.

This is a temporary freezing of user funds rather than a claim bypass or permanent loss. The duration is attacker-controlled for as long as the attacker can keep vault liquidity unavailable or repeatedly front-run `stopEpoch` with withdrawals.

### Likelihood Explanation
Likelihood is moderate when programmable-borrower mode is configured with a public ERC4626 vault whose liquidity can be withdrawn by external users.

The attacker needs only to be a normal vault shareholder and to observe the mempool or predictable epoch-end boundary. `stopEpoch` cannot be called before `epochEndDate`, so the attack window is deterministic. [6](#0-5) 

Existing guards do not prevent the condition:

- `epochAccountingActive` remains true after the retryable failure.
- The borrower is not defaulted because the shortfall is economically covered.
- `StopEpochVaultLiquidityUnavailable` intentionally preserves the running epoch so the call can be retried.
- Repeated withdrawals by ordinary vault users can make every retry fail.

The repository’s own test coverage establishes the intended behavior for this exact branch: covered borrower shares plus insufficient vault withdrawal liquidity causes `stopEpoch` to revert while leaving the epoch running and `pendingWithdraws` untouched. [7](#0-6) 

### Recommendation
Do not make epoch settlement depend on an atomic ERC4626 withdrawal succeeding while reported share value covers the shortfall.

Possible mitigations:

1. Add a delayed/settlement-tolerant withdrawal path that treats covered but unavailable vault liquidity as a borrower liquidity default after a bounded grace period.
2. Track failed covered-withdrawal attempts in `ProgrammableBorrower`; after a configurable number or duration, allow `IdleCDOEpochVariant` to route the position through default/recovery accounting instead of leaving the epoch open.
3. Reserve withdrawal liquidity earlier, before external vault users can remove it.
4. Use a vault with predictable withdrawal liquidity or an explicit redemption-queue state that the epoch accounting can represent safely.
5. Bound the retry window and expose a manager/owner fallback that can finalize the epoch using a loss-adjusted amount rather than requiring the same reverting `vault.withdraw` call forever.

The key invariant to enforce is that an external vault depositor cannot indefinitely prevent a covered epoch settlement without the protocol transitioning to an explicit default or recovery state.

### Proof of Concept
A Foundry fork PoC can reproduce the issue by using the programmable-borrower setup and an ERC4626 vault in which an attacker controls enough shares to drain available liquidity.

```solidity
function testVaultUserCanRepeatedlyBlockStopEpoch() external {
    _setUpProgrammableBorrowerCreditVault(FORK_BLOCK, ERC4626_VAULT);

    uint256 lpDeposit = 10_000 * oneScale;
    idleCDO.depositAA(lpDeposit);

    // Create a pending normal withdrawal that must be funded at stopEpoch.
    uint256 pendingAmount = cdoEpoch.requestWithdraw(
        aaTranche.balanceOf(address(this)) / 2,
        address(aaTranche)
    );
    assertGt(pendingAmount, 0);

    _startEpochAndCheckPrices(0);

    uint256 pendingWithdraws = strategy.pendingWithdraws();
    assertGt(pendingWithdraws, 0);

    // Attacker is an ordinary ERC4626 shareholder. They redeem/withdraw their
    // own position before the manager's stopEpoch transaction.
    vm.startPrank(vaultAttacker);
    uint256 shares = vault.balanceOf(vaultAttacker);
    vault.redeem(shares, vaultAttacker, vaultAttacker);
    vm.stopPrank();

    // The borrower still has enough vault-share value, but the vault lacks
    // enough immediately withdrawable underlying for the required shortfall.
    uint256 borrowerAssets =
        vault.convertToAssets(vault.balanceOf(address(programmableBorrower)));
    assertGe(borrowerAssets, pendingWithdraws);
    assertLt(vaultLiquidityAvailable(), pendingWithdraws);

    vm.warp(cdoEpoch.epochEndDate() + 1);

    vm.prank(manager);
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    cdoEpoch.stopEpoch(0, 0);

    assertTrue(cdoEpoch.isEpochRunning());
    assertFalse(cdoEpoch.defaulted());
    assertEq(strategy.pendingWithdraws(), pendingWithdraws);

    // The withdrawal receipt has not matured because epochNumber did not roll.
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.claimWithdrawRequest();
}
```

This matches the repository’s regression scenario at `test/foundry/ProgrammableBorrowerCreditVault.t.sol:372`, replacing the synthetic withdraw limit with an unprivileged vault shareholder withdrawing or redeeming their own position immediately before `stopEpoch`.
