### Title
Stale/broken oracle on any single liability position permanently blocks withdrawal of unrelated, healthy collateral in the same account - ([File: programs/marginfi/src/state/marginfi_account.rs])

### Summary
The reported bug class is "one failing component in a loop over multiple positions/strategies causes the entire withdrawal to revert, freezing user funds until manual/administrative intervention." marginfi-v2's architecture is fundamentally different from the reported `PrimeStrategy` (a single `withdraw()` that auto-fetches funds from a priority queue of strategies) — in marginfi, a user withdraws from exactly one `Bank` per instruction, so there is no queue-iteration DoS in the reported form. However, an architecturally analogous freeze exists in the risk engine's per-account health check, which iterates over **all** of a user's active balances (not just the bank being withdrawn from) and unconditionally propagates a price/oracle error found on any **liability** balance, aborting the whole transaction.

### Finding Description
`get_health_components` loops over every active `Balance` on the account (assets *and* liabilities across every bank the user is in, including third-party integration banks like Kamino/Drift/Solend/Juplend) to compute total health, which is required for every withdraw/borrow via `check_account_init_health`: [1](#0-0) 

For each balance, `OraclePriceFeedAdapter::try_from_bank` is attempted and the result is routed to either the asset-side or liability-side valuation helper: [2](#0-1) 

Critically, the two sides handle oracle failures asymmetrically:
- **Asset side** (`calc_weighted_asset_value_standalone`): if the oracle price fetch fails and the requirement type is `Initial`, the error is swallowed and the position is simply valued at zero — it does **not** abort the transaction. [3](#0-2) 

- **Liability side** (`calc_weighted_liab_value_standalone`): any oracle error (e.g. `PythPushStalePrice`, `SwitchboardStalePrice`, or any custom error surfaced by `OraclePriceFeedAdapter::try_from_bank`) is always re-raised and propagated out of the loop, unconditionally failing the whole health check regardless of `RequirementType`. [4](#0-3) 

Because `check_account_init_health` runs on every `lending_account_withdraw` (and on every integration withdraw: Kamino, Drift, Solend, Juplend) unless the account is in receivership/order-execution, a single unrelated liability position whose oracle becomes stale, decommissioned, or otherwise unreadable will cause `check_account_init_health` to error out for **every** withdraw call on that account — even a withdraw targeting a completely different, healthy collateral bank: [5](#0-4) [6](#0-5) [7](#0-6) 

This mirrors the reported bug class: iterating a list of "sub-components" (balances/strategies) to satisfy an operation, where the failure of a single, unrelated component (a strategy in the original report; a liability-bank oracle here) blocks the entire user action, requiring out-of-band remediation before the user regains liquidity.

### Impact Explanation
If a bank the user has borrowed from develops a permanently or semi-permanently broken price feed (decommissioned Switchboard feed, prolonged Pyth staleness, or a broken/paused third-party integration oracle), the user cannot withdraw *any* collateral from *any other, healthy* bank in the same `MarginfiAccount`, because `check_account_init_health` always requires and always fails on that one bad liability price. The user's only escape is to `repay`/`repay_all` that specific liability (repay/deposit skip the risk-engine check per the documented flow), which is not always immediately possible (insufficient liquid funds, or dependency on the same broken integration for repay in some flows). This produces a durable, unrelated-asset freeze with real financial impact (illiquidity of otherwise-healthy collateral) driven by a single external dependency (oracle/venue) rather than by the user's own risk.

### Likelihood Explanation
This is reachable by any unprivileged user who holds more than one active balance (a very common configuration, and explicitly supported/tested via multi-bank remaining-accounts packing) where one of the balances is a liability whose oracle can go stale or fail (Pyth/Switchboard staleness, or an integration's price/refresh dependency breaking). Oracle staleness is a routine, permissionless, externally-triggerable condition (not admin/validator-privileged), making this moderately likely to occur in production over time, especially for less-liquid or third-party-integration liability banks (Kamino/Drift/Solend/Juplend), which have their own additional oracle/refresh dependencies.

### Recommendation
Consider decoupling the liability-oracle failure from blocking withdrawals of unrelated, sufficiently-collateralized positions. Options include: (1) allowing the risk engine to use the last known/cached price (with a conservative bias) for liabilities when the live oracle is stale, subject to a staleness ceiling, similar to how some caller flows already tolerate limited staleness for collateral during borrows; (2) providing a permissionless/keeper-callable "freeze bad-oracle position" path that isolates a single balance from the live health computation without requiring the account to already be in receivership; or (3) ensuring `repay`/`repay_all` for the liability with the broken oracle can always be executed without depending on the same broken oracle/venue, so users always retain a self-service unblock path.

### Proof of Concept
1. User deposits collateral in Bank A (e.g., a native SOL bank with a healthy oracle) and borrows from Bank B (e.g., a bank using a Switchboard pull oracle, or a Kamino/Drift/Solend/Juplend wrapped bank).
2. Bank B's oracle feed stops being cranked/updated (Switchboard) or becomes stale/unavailable (Pyth outage, integration pause), so `OraclePriceFeedAdapter::try_from_bank` returns an error for Bank B.
3. User calls `lending_account_withdraw` on Bank A, passing Bank A + Bank B (and their oracles) as required by the risk engine, per `get_health_components`'s requirement that all active balances be represented in `remaining_accounts`.
4. In `get_health_components`, the loop reaches Bank B's liability balance; `calc_weighted_liab_value_standalone` re-raises the oracle error (e.g. `PythPushStalePrice`), unlike the asset-side path which would have zeroed the value.
5. `check_account_init_health` returns `Err`, and the entire withdraw from Bank A reverts — even though Bank A and its collateral are completely healthy and uninvolved in the failure.
6. Until the user repays/closes the Bank B liability (or the oracle recovers), all withdrawals from the account fail, regardless of which bank is targeted.

Note: I was not able to fully verify from the index whether every third-party integration's `repay`/`repay_all` path is guaranteed to work independently of a broken oracle for that same bank (e.g., whether Kamino/Drift/Solend/Juplend `repay` CPIs have their own oracle/refresh dependency that could also be affected by the same outage). This should be confirmed with the underlying source, and I recommend starting a full Devin session to inspect the complete `repay` instruction implementations for each integration if that guarantee needs to be verified precisely.
