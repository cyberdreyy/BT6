### Title
Missing mutex synchronization in `Authorize` allows unsynchronized reads of `h.authorizedKeys` racing with `syncMetadata`'s full-map swap - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
`WorkflowMetadataHandler.Authorize` reads `h.authorizedKeys[workflowID]` at line 92 without acquiring `h.mu` at all, while `syncMetadata` performs a full map replacement (`h.authorizedKeys = authorizedKeys`) under `h.mu.Lock()`. This is a genuine unsynchronized concurrent access to shared state with no happens-before relationship, which the Go race detector will flag and which can cause `Authorize` to observe a stale/superseded map indefinitely (not just briefly), including one that still contains a since-revoked signer.

### Finding Description
`Authorize` is reached from gateway requests carrying a `workflowID` and a signed JWT (`core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go:80-108`). It looks up authorized keys via a plain map read with no lock: [1](#0-0) 

Meanwhile, `syncMetadata` runs on a periodic ticker (`h.runTicker(..., h.syncMetadata)`) and performs a full-map replacement under the write lock: [2](#0-1) 

Because `Authorize` never takes `h.mu.RLock()`, there is no happens-before edge between the writer (which holds `h.mu.Lock()`) and this reader. Per the Go memory model, a goroutine that never synchronizes on the same lock is not guaranteed to ever observe the write — it can legally keep returning a cached/stale reference to the previous `authorizedKeys` map value across an unbounded number of iterations, not merely during a narrow TOCTOU window. Other accessors of shared handler state (`WorkflowShards`, `GetWorkflowID`, `GetWorkflowReference`) correctly take `h.mu.RLock()`, confirming `Authorize`'s omission is an inconsistency/bug rather than intentional lock-free design: [3](#0-2) [4](#0-3) 

Note that because `syncMetadata` always constructs a brand-new, fully-populated map before publishing it via a single pointer assignment, a properly synchronized reader would never see a "mixed-generation" map (partial keys from two generations) — each generation's map is internally self-consistent. The exploitable defect is specifically the missing lock in `Authorize`, which removes the memory-model guarantee that the reader will observe the swap at all, allowing indefinite continued admission of a key that was already revoked in the currently-published `authorizedKeys` map.

### Impact Explanation
An attacker whose signer key was authorized for a workflow and is later revoked (workflow update/owner rotation removes the key from subsequent aggregated metadata) could continue to have gateway requests authorized past the point the revocation should have taken effect, because `Authorize`'s unsynchronized read is not guaranteed to observe `syncMetadata`'s published update. This maps to Chainlink's "allowlist/quota bypass" and "unauthorized job run" impact classes — a revoked signer improperly retains authorization to trigger workflow-scoped gateway operations.

### Likelihood Explanation
No special privilege is required beyond having once been a legitimately authorized signer for a workflow that is later revoked/rotated; the attacker only needs to keep sending gateway `Authorize`-gated requests around the aggregation-tick boundary (`MetadataAggregationIntervalMs`, attacker-observable/predictable cadence). The race is real and mechanical (confirmed by direct code inspection showing zero lock usage in `Authorize`), and is trivially reproducible with `go test -race` running `syncMetadata` and `Authorize` concurrently.

### Recommendation
Acquire `h.mu.RLock()`/`defer h.mu.RUnlock()` at the start of `Authorize` before reading `h.authorizedKeys`, matching the pattern already used in `WorkflowShards`, `GetWorkflowID`, and `GetWorkflowReference`.

### Proof of Concept
1. In `core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler_test.go`, construct a `WorkflowMetadataHandler` with a workflow ID `W` and authorized signer `S`.
2. Spawn goroutine A: loop calling `h.Authorize(W, validJWTFromS, req)` in a tight loop for N iterations.
3. Spawn goroutine B: loop calling `h.syncMetadata(ctx)` where alternating aggregator outputs first include then omit `S` from `AuthorizedKeys` for `W` (simulating revocation), each iteration replacing `h.authorizedKeys`.
4. Run `go test -race ./core/services/gateway/handlers/capabilities/v2/...`.
5. Expected (pre-fix) result: `-race` reports a DATA RACE between the unsynchronized read at `workflow_metadata_handler.go:92` and the locked write at `workflow_metadata_handler.go:178`; additionally assert that after B has published a generation without `S`, A's `Authorize` calls eventually (and deterministically, given no synchronization) can still return success for `S` for an unbounded number of iterations, demonstrating the revoked key is not reliably excluded.
6. After adding `h.mu.RLock()`/`RUnlock()` to `Authorize`, re-run: `-race` reports no data race, and `Authorize` correctly rejects `S` immediately after the generation without `S` is published (bounded by mutex-provided happens-before).

func (h *WorkflowMetadataHandler) WorkflowShards(workflowID string) []*shardEndpoint {
	h.mu.RLock()
	defer h.mu.RUnlock()
	shards := h.workflowShards[workflowID]
	out := make([]*shardEndpoint, len(shards))
	copy(out, shards)
	return out
}

	h.mu.RLock()
	defer h.mu.RUnlock()

		workflowOwner: workflowOwner,
		workflowName:  workflowName,
		workflowTag:   workflowTag,
