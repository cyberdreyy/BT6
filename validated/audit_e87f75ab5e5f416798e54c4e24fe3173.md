### Title
Operator fee scalar/constant derived from L1 SystemConfig updates have no upper bound, allowing fees to grow to a chain-halting magnitude - (File: `crates/common/genesis/src/updates/operator_fee.rs`)

### Summary
The reported bug is that `TokenBridgeBase.sol`'s `setBrc20TransferFee`/`setRunesTransferFee`/`setBtcTransferFee` accept arbitrary `uint256` values with no upper bound, letting fees grow to “infinite.” Base has the same bug class in the derivation of the Isthmus **operator fee**: `OperatorFeeUpdate::try_from` decodes `operator_fee_scalar` (u32) and `operator_fee_constant` (u64) straight from an L1 `SystemConfigLog` and applies them to the L2 `SystemConfig` with no range check, and the fee-charging formula that consumes these values likewise has no ceiling.

### Finding Description
`OperatorFeeUpdate::try_from` parses the scalar/constant directly out of the L1 log payload and returns them unchecked: [1](#0-0) 

`OperatorFeeUpdate::apply` writes these values into `SystemConfig` unconditionally, with no maximum enforced: [2](#0-1) 

These scalars flow into the per-transaction fee formula, which uses `saturating_mul`/`saturating_add` (so it cannot panic) but also has no upper limit on the resulting fee: [3](#0-2) 

The computed `operator_fee_charge` is then deducted from the transaction sender/payer up front, before any call executes, both in the revm handler path and the EIP-8130 payer-authorization path: [4](#0-3) [5](#0-4) 

Because `operator_fee_scalar`/`operator_fee_constant` are never bounded during decoding, application, or fee computation, they mirror exactly the reported class of “fee can grow to infinite”: an unbounded, protocol-critical value with no sanity ceiling.

### Impact Explanation
If the `operator_fee_scalar`/`operator_fee_constant` fields are pushed to large values (e.g., near `u32::MAX`/`u64::MAX`) via the L1 `SystemConfig` update path, the computed `operator_fee_charge` for every L2 transaction becomes astronomically large. Since this fee is charged up-front from every sender's/payer's balance before execution, no ordinary account could afford to pay it, which would make the L2 chain unable to process any transactions — a node/chain halt from the standpoint of transaction processing, not merely a "high fee" nuisance.

### Likelihood Explanation
This requires the operator-fee fields to be updated to extreme values via the L1 `SystemConfig` update mechanism (a privileged, L1-owner-controlled path), the same privileged-actor precondition as the original report (an owner calling `setXTransferFee`). The code path performs zero bounds validation at any stage (decode, apply, or fee computation), so likelihood of the class of bug being present is confirmed by direct code inspection; whether it is exploitable in practice depends entirely on the trust assumptions placed on the L1 `SystemConfig` owner/deposit encoding pipeline.

### Recommendation
Add explicit upper bounds (and ideally reasonableness checks, e.g., relative to a max expected fee-per-gas) when decoding and applying `operator_fee_scalar`/`operator_fee_constant` in `OperatorFeeUpdate::try_from`/`apply`, and/or clamp the final `operator_fee_charge_inner` result to a protocol-defined ceiling so a single L1 system-config update cannot render the L2 chain unusable.

### Proof of Concept
1. Craft an L1 `SystemConfigLog` operator-fee-update event whose payload encodes `operator_fee_scalar = u32::MAX` and `operator_fee_constant = u64::MAX` (format shown in the existing test `test_operator_fee_update_try_from`). [6](#0-5) 
2. Once this log is included in an L1 block and derived by the rollup node, `SystemConfig.operator_fee_scalar`/`operator_fee_constant` are set to these unchecked maximum values via `OperatorFeeUpdate::apply`.
3. Every subsequent post-Isthmus L2 transaction's `operator_fee_charge_inner(gas, upgrade)` computes a value on the order of `gas * u32::MAX [* 100 for Jovian] + u64::MAX`, which is deducted up-front from the sender/payer balance in `before_execution`/`prepay`.
4. No account can hold enough balance to cover this fee, so all L2 transactions fail with insufficient funds, halting the chain's transaction processing.

    /// Calculates the operator fee for a given `gas` amount.
    ///
    /// Missing scalars fall back to zero to match the execution path during the
    /// txpool bootstrap window before the first L1 attributes deposit.
    pub fn operator_fee_charge_inner(&self, gas: U256, upgrade: BaseUpgrade) -> U256 {
        let operator_fee_scalar = self.operator_fee_scalar.unwrap_or_default();
        let operator_fee_constant = self.operator_fee_constant.unwrap_or_default();

        let product = if Self::is_enabled(upgrade, BaseUpgrade::Jovian) {
            gas.saturating_mul(operator_fee_scalar)
                .saturating_mul(U256::from(OPERATOR_FEE_JOVIAN_MULTIPLIER))
        } else {
            gas.saturating_mul(operator_fee_scalar) / U256::from(OPERATOR_FEE_SCALAR_DECIMAL)
        };
        product.saturating_add(operator_fee_constant)
    }

impl TxHandlerHooks<BaseEvmTypes> for BaseTxHandlerHooks {
    fn before_execution(
        host: &mut Evm<'_, BaseEvmTypes>,
        envelope: &BaseTxEnvelope,
        caller: Address,
        upfront_fee: U256,
    ) -> HandlerResult<()> {
        // Charge the upfront gas cost, the L1 data fee, and the operator fee (on the gas limit)
        // from the caller. Both fees are stashed for settlement so it charges/refunds against the
        // exact amounts collected here, without recomputing them.
        let l1_fee = Self::l1_fee(host, envelope);
        let operator_fee = Self::operator_fee(host, envelope, envelope.gas_limit());
        let ext = host.ext_mut();
        ext.l1_fee = l1_fee;
        ext.operator_fee = operator_fee;
        // `validate_sender` only checks the gas cost and value; the L1 and operator fees are
        // charged on top here via `charge_upfront`'s wrapping subtraction, so reject an
        // underfunded caller up front rather than let its balance wrap to a spurious value.
        Self::ensure_can_pay_fees(host, envelope, caller, l1_fee, operator_fee)?;
        charge_upfront(
            host,
            caller,
            upfront_fee.saturating_add(l1_fee).saturating_add(operator_fee),
        )
    }
