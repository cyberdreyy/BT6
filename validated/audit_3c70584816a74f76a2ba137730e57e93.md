### Title
Loss-adjusted withdraw receipt is paid at par when the user re-requests in a later epoch - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The Irssi use-after-free maps to a stale-state double-accounting bug: a withdraw receipt survives a state transition (a `stopEpochWithDuration` loss) and is later paid twice — once implicitly through `lossRecoveryPriceByEpoch` accounting, and again at par through the funded-claim path. In `IdleCreditVault`, `_claimLossAdjustedWithdrawRequest` only looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`. If a user has a receipt in the loss epoch N and then makes a second `requestWithdraw` in a later epoch M, `lastWithdrawRequest` is overwritten to M, the epoch-N haircut is never applied, and `_claimFundedWithdrawRequest` pays the full aggregate `withdrawsRequests[_user]` (including the haircutted epoch-N basis) at par. [1](#0-0) 

### Finding Description
- `requestWithdraw` records `withdrawsRequestsByEpoch[_user][currentEpoch]` and always overwrites `lastWithdrawRequest[_user] = currentEpoch` [2](#0-1) 
- When a stop epoch realizes a loss, `collectWithdrawFunds` funds less than `pendingWithdraws` and stores `lossRecoveryPriceByEpoch[epochNumber]`, so receipts of that epoch must claim at the haircutted price via `_claimLossAdjustedWithdrawRequest` [3](#0-2) 
- But `_claimLossAdjustedWithdrawRequest` uses only `lastWithdrawRequest[_user]` as the lookup epoch — it cannot see a second, earlier loss-epoch receipt once `lastWithdrawRequest` moves forward [4](#0-3) 
- `_claimFundedWithdrawRequest` then pays `withdrawsRequests[_user]` in full; `_clearWithdrawClaimForEpoch` was never invoked for epoch N, so `withdrawsRequestsByEpoch[N]` was never subtracted from the aggregate [5](#0-4) 
- Re-requesting before claiming is explicitly supported ("if a user does not claim a withdraw request and instead requests another withdraw, he will have to wait for another epoch to claim both") so no guard blocks the sequence. [6](#0-5) 

### Impact Explanation
An attacker (any tranche-token holder) claims their loss-epoch receipt at 100% instead of `lossRecoveryPrice`, stealing `basis * (1 - lossRecoveryPrice)` of underlyings from the vault's funded-claim balance. That overpayment is socialized: other funded/default-recovery claimants or the reserve absorb the shortfall, and `_transferFundedClaim`'s reserve guard can make later claimants revert (permanent freezing of their claims). Broken invariant: loss waterfall / one receipt one haircut. Quantified loss = receipt basis × (1 − lossRecoveryPrice); e.g., a 1M USDC receipt at a 70% recovery price yields a 300k USDC overpayment.

### Likelihood Explanation
Requires only unprivileged actions: request a withdraw, let a `stopEpochWithDuration(_lossAmount)` occur (honest manager call after borrower underpayment — plausible in a credit vault), then request a second withdraw in a later epoch and claim once. No privileged misbehavior needed; the attacker just sequences ordinary calls.

### Recommendation
Iterate all epochs with nonzero `lossRecoveryPriceByEpoch` for the user (or track a per-user set of request epochs) instead of only checking `lastWithdrawRequest[_user]`; alternatively, clear each epoch's `withdrawsRequestsByEpoch` slice out of `withdrawsRequests` at claim time so funded claims never include a haircutted basis. Also block new `requestWithdraw` while an uncleared loss-adjusted receipt exists, mirroring the APR0 lifecycle gating.

function testLossReceiptPaidAtParAfterSecondRequest() external {
    uint256 amount = 1_000_000 * ONE_SCALE;
    idleCDO.depositAA(amount);                    // attacker deposits
    _startEpochAndCheckPrices(0);

    // Epoch 1: request withdraw (epoch N = epochNumber at request time)
    cdoEpoch.requestWithdraw(IERC20(AAtranche).balanceOf(address(this)) / 2, address(AAtranche));

    _startEpochAndCheckPrices(1);
    // Borrower underpays -> manager calls stopEpochWithDuration with _lossAmount > 0
    deal(defaultUnderlying, borrower, shortfallFunding);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(lossAmount, funding); // sets lossRecoveryPriceByEpoch[N]

    // Epoch 2: attacker requests again -> lastWithdrawRequest = M
    cdoEpoch.requestWithdraw(remaining, address(AAtranche));
    _startEpochAndCheckPrices(2);
    // fund epoch-M stop fully
    deal(defaultUnderlying, borrower, expectedFunds);
    vm.prank(manager); cdoEpoch.stopEpoch(0, 0);

    // Claim: loss claim misses epoch N, funded claim pays aggregate at par
    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    assertEq(underlying.balanceOf(address(this)) - balPre,
        basisN + basisM, // epoch-N slice paid at par, not basisN * lossRecoveryPrice
        'loss receipt paid at par');
}

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }
