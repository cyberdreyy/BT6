### Title
Unchecked `u64` subtraction in `L1BlockInfo::operator_fee_refund` can panic/underflow on ordinary post-Isthmus transaction execution - (File: `crates/common/evm/src/l1block.rs`)

### Summary
`L1BlockInfo::operator_fee_refund` computes the gas actually used with a raw, non-checked subtraction: [1](#0-0) 

```rust
let operator_cost_gas_used = self.operator_fee_charge_inner(
    U256::from(gas.limit() - (gas.remaining() + gas.refunded() as u64)),
    spec_id,
);
```

Unlike essentially every other cost computation in the same file and in `crates/common/l1-fees/src/params.rs`, which consistently use `saturating_sub`/`checked_sub`/`saturating_add` (e.g. `l1_fee`, `total_cost`, `prepay`, `debited`, `refund_amount` in `eip8130.rs`), this specific expression performs plain integer subtraction on `u64` values.

### Finding Description
`operator_fee_refund` is called unconditionally for every non-deposit transaction post-Isthmus from `BaseHandler::reimburse_caller`: [2](#0-1) 

The expression `gas.limit() - (gas.remaining() + gas.refunded() as u64)` is intended to equal `gas.used()` (spent minus refund), but it is computed independently of the engine's own tracked "total gas spent" value, by re-deriving it from `limit`, `remaining`, and `refunded`. If `gas.remaining() + gas.refunded()` can ever exceed `gas.limit()` — e.g. through an interaction between the EIP-8037 reservoir/spill gas-tracking model (visible in the `GasTracker`/`handle_reservoir_remaining_gas` logic in `handler.rs`) and refund accounting that is not perfectly synchronized with this ad-hoc formula — the subtraction underflows. In debug builds this panics; in release builds (typical node deployment) it wraps to a huge `u64`, which is then fed into `operator_fee_charge_inner`, producing a bogus, enormous operator fee charge.

This mirrors the Noya finding's bug class precisely: a shared arithmetic helper invoked on the hot path of every transaction performs an unchecked/unguarded subtraction instead of a saturating one, unlike its sibling functions in the same file which were deliberately fixed to use `saturating_sub` (see the comment in `l1block.rs:228-230` referencing a similar prior fix for `operator_fee_charge_inner`'s scalar-lookup panic). The refund-cap logic in `capped_refund`/`billable_gas` (EIP-8130 path) explicitly documents that its subtraction is "safe" because of bounding invariants — no equivalent invariant is documented or enforced for this specific expression.

### Impact Explanation
Because `reimburse_caller`/`operator_fee_refund` executes on every ordinary Isthmus+ transaction as part of block execution (not just a corner-case query), a panic here would abort block processing on all full nodes — a chain-wide node halt / consensus-critical panic, not merely a single RPC failure. A wraparound (release-mode) would instead silently overcharge or undercharge the operator fee vault, corrupting protocol-level fee accounting (an unauthorized/incorrect balance mutation) rather than a benign revert. Either outcome is more severe than the original Medium-severity Noya DOS, since it sits in the base-layer transaction-settlement path rather than a view-only aggregator.

### Likelihood Explanation
Likelihood depends on whether `gas.remaining() + gas.refunded()` can practically exceed `gas.limit()` given revm's/Base's own gas-refund capping (EIP-3529 typically caps refund at `gas_used/5`, which should keep this invariant safe under normal EVM semantics). I could not fully verify from the indexed code whether Base's custom EIP-8037 reservoir/spill gas model (`GasTracker`, `handle_reservoir_remaining_gas`, `refill_reservoir`, `spend_all` in `handler.rs`) preserves this invariant in all halt/revert/spill interaction cases, since that logic is substantially customized versus vanilla revm. This is the main area of uncertainty in this analog, and would need dynamic/property testing (e.g., fuzzing gas-tracker state combinations through `reimburse_caller`) to confirm exploitability from a single crafted transaction.

### Recommendation
Replace the raw subtraction with `checked_sub`/`saturating_sub` and either bail out with `BaseTransactionError` (matching the defensive style already used throughout `eip8130.rs`) or clamp defensively:

```rust
let gas_used = gas.limit().saturating_sub(gas.remaining().saturating_add(gas.refunded() as u64));
let operator_cost_gas_used = self.operator_fee_charge_inner(U256::from(gas_used), spec_id);
```

Additionally, prefer deriving "gas used" from the engine's own authoritative `gas.total_gas_spent()`/`gas.used()` accessor (as used elsewhere, e.g. `handler.rs:291` `frame_result.gas().used()`) rather than re-deriving it via a separate formula, to eliminate the possibility of the two bookkeeping paths diverging.

### Proof of Concept
Not independently reproducible from static review alone: exploitability requires constructing a transaction whose execution path (through the EIP-8037 reservoir/spill/halt gas-tracking transitions in `handler.rs`) drives `gas.remaining() + gas.refunded()` above `gas.limit()` before `reimburse_caller` invokes `operator_fee_refund`. This would need to be confirmed via targeted unit/property tests exercising `GasTracker` state combinations (similar in spirit to the existing `test_reservoir_spill_recovered_on_revert`/`test_halt_gas_non_deposit` tests in `crates/common/evm/src/handler.rs`) feeding into `operator_fee_refund`.

```rust
    pub fn operator_fee_refund(&self, gas: &Gas, spec_id: BaseSpecId) -> U256 {
        if !spec_id.is_enabled_in(BaseUpgrade::Isthmus) {
            return U256::ZERO;
        }

        let operator_cost_gas_limit =
            self.operator_fee_charge_inner(U256::from(gas.limit()), spec_id);
        let operator_cost_gas_used = self.operator_fee_charge_inner(
            U256::from(gas.limit() - (gas.remaining() + gas.refunded() as u64)),
            spec_id,
        );

        operator_cost_gas_limit.saturating_sub(operator_cost_gas_used)
    }
```
