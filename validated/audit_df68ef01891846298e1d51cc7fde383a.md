### Title
Cross-workflow HTTP action response-cache poisoning via WorkflowID-independent cache key - (File: core/services/gateway/handlers/capabilities/v2/response_cache.go)

### Summary
The Gateway's HTTP Action `responseCache` computes its cache key from `gateway.OutboundHTTPRequest.Hash()`, which the codebase's own tests confirm is **independent of `WorkflowID`** while the documented design explicitly promises workflow-scoped isolation ("Cache entries are scoped by workflow ID to prevent cross-workflow data leakage"). This is analogous to the reported class of bug: a discrepancy between the intended/documented behavior (isolating one channel of a value/response) and what the code actually does, leading to unintended cross-context mixing.

### Finding Description
`responseCache.Fetch`/`Set` key the cache exclusively on `req.Hash()` [1](#0-0) , and the comment states the hash is derived from "method, URL, headers, body, workflowOwner" [2](#0-1) . The handler test suite explicitly proves `WorkflowID` is **not** part of that hash: `"having different workflowID results in same Hash"` asserts `hash1 == hash2` for two requests that only differ by `WorkflowID` [3](#0-2) .

This contradicts the module's own README, which documents: "**Workflow Isolation**: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage" [4](#0-3) .

In `makeOutgoingRequest`, any node-originated `OutboundHTTPRequest` with matching method/URL/headers/body/workflowOwner will hit the same cache entry across different `WorkflowID`s, regardless of which workflow issued the request [5](#0-4) . Because caching is keyed by the actual `OutboundHTTPRequest` content (which is entirely under the workflow node's/DON's control and unmarshalled from a node response, not validated against the workflow that is supposed to own the request), a workflow belonging to the same owner but with a different `WorkflowID` could receive an HTTP response that was fetched and cached on behalf of a *different* workflow, if it crafts (or coincidentally sends) a request with the same method/URL/headers/body. This is a cross-workflow response confusion: the cache is meant to be workflow-isolated, but the actual isolation key omits `WorkflowID` entirely.

### Impact Explanation
This can result in data leakage/cross-tenant response confusion between distinct workflows sharing the same owner (multi-workflow accounts, or scenarios where the "workflowOwner" identity is coarser-grained than a fully authorized workflow). A malicious or buggy workflow could retrieve a cached HTTP response (which may contain another workflow's sensitive request results, tokens embedded in response bodies, or session data returned by third-party services) that it was never authorized to see, by mimicking the method/URL/headers/body of a target workflow's outbound HTTP action. This directly conflicts with the documented workflow-isolation guarantee and constitutes cross-user (cross-workflow) response confusion.

### Likelihood Explanation
Likelihood is limited by several factors: (1) exploitation requires two workflows to share the same `workflowOwner` (an account controlling multiple workflows) and for the attacking workflow to be able to predict/construct an identical method+URL+headers+body request as the victim workflow's HTTP action, (2) `CacheSettings.MaxAgeMs` and `Store` must be set by the request author to enable cache read/write, and (3) exploitation depends on workflow logic and off-chain node behavior, which the Gateway does not fully control end-to-end. However, the test suite explicitly demonstrates and encodes this behavior as intentional/expected ("Hash should be the same regardless of WorkflowID"), meaning it's a real, exercised code path, not a theoretical edge case, and it directly contradicts the documented security property.

### Recommendation
Include `WorkflowID` (or another workflow-scoping identifier consistently controlled/authenticated by the gateway) in `OutboundHTTPRequest.Hash()` so that the cache key truly enforces workflow isolation as documented, or explicitly update the documentation/tests if owner-level (not workflow-level) sharing is the intended, reviewed behavior. If owner-level sharing is intentional, ensure `workflowOwner` is authenticated end-to-end (not attacker-suppliable) before being trusted as an isolation boundary.

### Proof of Concept
1. Workflow A (owner `O`, `WorkflowID = W1`) issues an `OutboundHTTPRequest{Method: "GET", URL: "https://svc/data", WorkflowOwner: O, WorkflowID: W1, CacheSettings:{Store:true, MaxAgeMs: 600000}}`, gateway fetches and caches the response keyed by `Hash()` (which excludes `WorkflowID`) [6](#0-5) .
2. Workflow B (same owner `O`, different `WorkflowID = W2`) sends an `OutboundHTTPRequest` with identical `Method`, `URL`, `Headers`, `Body`, and `WorkflowOwner`, but `WorkflowID = W2`.
3. Per `TestRequestHash`'s "having different workflowID results in same Hash" assertion, `req.Hash()` for A and B requests are equal [3](#0-2) , so `responseCache.Fetch` for Workflow B's request returns Workflow A's cached response without ever contacting the target service or verifying that this response was intended for `W2`.

	if err != nil {

	}

		URL:              req.URL,

		MultiHeaders:     req.MultiHeaders,
		Body:             req.Body,
		MaxResponseBytes: req.MaxResponseBytes,
		Timeout:          timeout,
	}

	sendResponseTimeout := time.Duration(defaultSendResponseTimeoutMs) * time.Millisecond

	// send response to node async

		// not cancelled when parent is cancelled to ensure the goroutine can finish

			if req.CacheSettings.Store {
