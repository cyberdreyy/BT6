Based on my research, I found a legitimate path-traversal (Zip Slip, CWE-22 analog) issue in the legacy zip extraction code path, distinct from and less protected than the sibling `tarzstd` extractor.

### Title
Zip Slip / Path Traversal in legacy zip extractor - (File: `helpers/archives/zip_extract.go`)

### Summary
The legacy zip extraction routine writes archive entries to disk using the raw `zip.File.Name` value with no validation that the resolved path stays within the intended extraction directory. This is invoked through `commands/helpers/archive/ziplegacy/zip_legacy_extractor.go`, which is registered as an `archive.Extractor` implementation for the `zip` format and accepts a `dir` parameter that it silently discards.

### Finding Description
`ExtractZipArchive`/`extractZipFile` in `helpers/archives/zip_extract.go` create files/directories/symlinks directly at `file.Name` (the path stored inside the zip entry), with the only sanitization being a check for `.git` directory entries via `errorIfGitDirectory`: [1](#0-0) [2](#0-1) 

The `ziplegacy` extractor implements the shared `archive.Extractor` interface (which is documented to "extract files to the directory provided") and is constructed with a `dir` argument, but its `Extract` method never uses `e.dir` — it calls `archives.ExtractZipArchive(zr)` directly: [3](#0-2) [4](#0-3) 

This contrasts with the sibling `tarzstd` extractor, which explicitly joins entries to `e.dir`, resolves them with `filepath.Abs`, and rejects any path that escapes that directory ("cannot be extracted outside of chroot"): [5](#0-4) 

Because a zip entry name can contain `../` sequences (or be an absolute path), `extractZipFile`/`extractZipDirectoryEntry`/`extractZipSymlinkEntry`/`extractZipFileEntry` will happily create/overwrite files anywhere the runner process has filesystem permissions, and can plant arbitrary symlinks (`extractZipSymlinkEntry` calls `os.Symlink(string(data), file.Name)` with no destination validation either).

The `archives.ExtractZipArchive` function is reachable from `commands/helpers/artifacts_downloader.go`, which downloads an artifacts archive from the GitLab server/coordinator and extracts it via `archive.NewExtractor(format, f, size, wd)`: [6](#0-5) 

If the `zip` format resolves to the `ziplegacy` extractor for a given execution (this repository shows `zip` registered in multiple archiver files, and I could not fully confirm from the index whether `fastzip` or `ziplegacy` is the default registration for the `zip` format in `commands/helpers/archiver.go` — this would need to be confirmed in a full checkout), any job/dependency artifact whose zip contains traversal path entries would be extracted outside `wd`.

### Impact Explanation
An attacker who can influence the contents of a zip artifact/cache archive processed by a runner (e.g., a malicious job in the same pipeline producing artifacts consumed by a dependent job, or a malicious cache archive) could write files outside the intended build directory on the runner host/container — including overwriting files, planting symlinks, or (in shell/non-containerized executors) writing to arbitrary filesystem locations reachable by the runner process. This mirrors the CWE-22 pattern in the referenced external report, but here it's a write-path traversal (Zip Slip) rather than a read-path traversal.

### Likelihood Explanation
Likelihood depends on whether the vulnerable legacy path is actually reachable in a default configuration. The `fastzip` extractor (backed by the `saracen/fastzip` library, which has its own path-containment protections) appears to be the modern implementation, and `ziplegacy` looks like a fallback/legacy code path (historically gated by a feature flag such as `FF_USE_FASTZIP` in GitLab Runner). If `ziplegacy` is only reachable when an operator explicitly disables the fastzip feature flag, this would fall under the "admin-chosen setting" disqualifier. I was not able to fully verify, within the available index, which extractor is registered by default in `commands/helpers/archiver.go` for the `zip` format — this requires reading that file's `init()`/registration logic in a full checkout to make a final determination.

### Recommendation
Regardless of default-registration status, `helpers/archives/zip_extract.go` should apply the same containment check used by `tarzstd_extractor.go` — resolve each entry against a base extraction directory with `filepath.Abs`/`filepath.Join` and reject any entry whose resolved path is not a descendant of that directory (and reject/normalize symlink targets similarly). The `ziplegacy` extractor should also actually use its `dir` parameter as the extraction root, consistent with the `archive.Extractor` interface contract.

### Proof of Concept
Craft a zip archive with an entry named e.g. `../../etc/cron.d/malicious` (or `../../../home/gitlab-runner/.ssh/authorized_keys`), and cause it to be processed via the legacy zip extraction path (`archives.ExtractZipArchive`) — e.g. as a job artifact/cache with `FF_USE_FASTZIP` disabled if that gates the extractor choice. On extraction, `extractZipFile` writes the file at the traversal-resolved path relative to the current working directory rather than the intended artifact directory, since no confinement check exists in `helpers/archives/zip_extract.go`.

func extractZipFileEntry(file *zip.File) (err error) {
	var out *os.File
	in, err := file.Open()
	if err != nil {
		return err
	}
	defer func() { _ = in.Close() }()

	// Remove file before creating a new one, otherwise we can error that file does exist
	_ = os.Remove(file.Name)
	out, err = os.OpenFile(file.Name, os.O_WRONLY|os.O_CREATE|os.O_TRUNC, file.Mode().Perm())
	if err != nil {
		return err
	}
	defer func() { _ = out.Close() }()
	_, err = io.Copy(out, in)

	return
}
