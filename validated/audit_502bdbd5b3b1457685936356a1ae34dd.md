### Title
Stale-epoch instant-withdraw receipts escape default recovery haircut and drain the recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
CVE-2014-8178 is an identifier-collision / cache-poisoning bug: Docker stored image layers under non-globally-unique IDs, so a crafted image could poison another layer's cache entry. The analog in `IdleCreditVault` is the epoch-scoped instant-withdraw accounting: `instantWithdrawsRequestsByEpoch` / `instantWithdrawClaimsByEpoch` are keyed by `epochNumber`, but the aggregate payout in `claimInstantWithdrawRequest` pays the whole cross-epoch `instantWithdrawsRequests[_user]` balance at par. Default finalization (`defaultPendingClaimBasis`, `_defaultPrefundedInstantReserve`, `_claimDefaultedInstantWithdrawRequest`) only ever looks at `instantWithdrawClaimsByEpoch[epochNumber]` — i.e. the *current* epoch key. An unfunded instant receipt recorded under an older epoch key is invisible to recovery accounting: it is neither haircutted nor reserved, yet it remains inside `instantWithdrawsRequests[_user]` and is paid 1:1.

### Finding Description
`requestInstantWithdraw` books claims under the *current* `epochNumber` (lines 367–372), while the user-level total `instantWithdrawsRequests[_user]` aggregates across all epochs. When the borrower defaults and `finalizeDefault` → `finalizeDefaultRecovery` runs, the haircut basis is `defaultPendingClaimBasis()` = `pendingWithdraws + instantWithdrawClaimsByEpoch[epochNumber]` (line 644–648) — only the *default epoch's* instant claims are included, and `_defaultPrefundedInstantReserve` similarly only counts `instantWithdrawClaimsByEpoch[epochNumber]` (line 719). If `pendingInstantWithdraws != 0` contains receipts keyed under an earlier epoch (borrower failed to fund instant withdrawals in epoch N, epoch rolled, then default in epoch M>N), those receipts contribute to `pendingInstantWithdraws` but add zero basis and zero prefunded reserve.

Post-finalization, `claimInstantWithdrawRequest` (lines 380–393) clears only `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` via `_claimDefaultedInstantWithdrawRequest`, then burns the *entire* `instantWithdrawsRequests[_user]` and calls `_transferFundedClaim(_user, amount)` at par. The stale-epoch slice was never haircutted and never reserved, so it is paid from whatever non-reserve balance exists — which post-default is other users' already-funded withdraw claims collected by `collectWithdrawFunds` / `collectInstantWithdrawFunds`. If no such surplus exists, `_transferFundedClaim`'s `balance - reserve < _amount` guard (lines 900–904) reverts permanently, freezing the receipt forever because there is no path to claim only part of the aggregate.

### Impact Explanation
Two failure modes, both fund-impacting: (1) if the strategy holds underlying beyond `defaultRecoveryReserve` (funded normal/instant claims of other users collected but not yet claimed), the attacker with a stale-epoch instant receipt withdraws it at par, directly stealing funds owed to other claimants; (2) otherwise the claim reverts forever — `claimInstantWithdrawRequest` is the only exit and it always tries to pay the full aggregate, so the user's legitimate defaulted-epoch receipt is permanently frozen along with the stale one. The broken invariant is "one receipt, one recovery price": a receipt's haircut is determined by which epoch key it happened to be recorded under, not by whether it was actually funded.

### Likelihood Explanation
Requires an unprivileged user to hold an unfunded instant withdrawal across an epoch boundary — which occurs whenever the borrower under-funds the instant queue at `startEpoch` (`pendingInstant > totUnderlyings`, IdleCDOEpochVariant.sol:286) and a later epoch ends in default. Any KYC-passed lender can create the receipt; the trigger conditions (partial instant funding, borrower default) are normal distressed-operation states, not privileged misconfiguration. The attacker need only call `claimInstantWithdrawRequest` after `finalizeDefault`.

### Recommendation
In `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve`, account for the full outstanding instant basis, not just `instantWithdrawClaimsByEpoch[epochNumber]` — e.g. track a global `instantWithdrawClaimsTotal` incremented in `requestInstantWithdraw` and decremented in both claim paths. In `_claimDefaultedInstantWithdrawRequest`, haircut all of `instantWithdrawsRequests[_user]` that predates finalization (not only the default-epoch slice), or iterate/record per-user unfunded epochs so no receipt escapes the recovery price.

### Proof of Concept
Foundry fork sketch (mirroring `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
// Epoch N: user requests instant withdraw; borrower under-funds at startEpoch
// so pendingInstantWithdraws > 0 carries into epoch N+1 (attacker's receipt is
// keyed under instantWithdrawsRequestsByEpoch[user][N]).
cdoEpoch.requestInstantWithdraw(amount, AAtranche);      // epoch N
cdoEpoch.startEpoch();                                    // partial funding only

// Epoch rolls to M = N+1 without the instant queue being filled.
cdoEpoch.stopEpoch(...); cdoEpoch.startEpoch();          // epochNumber -> M

// Borrower defaults in epoch M; manager finalizes with partial recovery.
cdoEpoch.stopEpoch(0, expectedFunds);                    // triggers default
cdoEpoch.finalizeDefault(recovered, manager);            // reserve haircut e.g. 70%

// Attacker's epoch-N instant receipt is NOT in instantWithdrawClaimsByEpoch[M],
// so it was excluded from defaultPendingClaimBasis and is unhaircutted.
// claimInstantWithdrawRequest pays the full aggregate at par, spending
// underlying that backs other users' funded claims (or reverting forever
// if balance == defaultRecoveryReserve).
cdoEpoch.claimInstantWithdrawRequest();                  // pays stale receipt 1:1
```

Key assertion: attacker receives `instantClaimBasis` (not `instantClaimBasis * defaultRecoveryPrice / 1e18`), while `defaultRecoveryReserve` is unchanged — the par payout consumes non-reserve funds reserved for other claimants, or the call permanently reverts under the `_transferFundedClaim` guard.
