### Title
Stale-epoch instant-withdraw claims excluded from `defaultPendingClaimBasis()` inflate `defaultRecoveryPrice`, overpaying early claimants and permanently freezing the recovery reserve - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault.finalizeDefaultRecovery` sizes the recovery reserve using `defaultPendingClaimBasis()`, which only adds `instantWithdrawClaimsByEpoch[epochNumber]` — instant receipts recorded in the *current* epoch. Instant receipts requested in an earlier epoch that are still partially unfunded (`pendingInstantWithdraws != 0`) are missing from `totalBasis`, so `recoveryPrice = reserveAmount * 1e18 / totalBasis` is computed against an under-counted denominator. The result is the credit-vault analog of the FFMPEG integer-overflow undersized allocation: the "allocation" (the haircut ratio applied to the reserve) is too generous, claims pay out more than their fair share, the reserve is exhausted early, and remaining defaulted claimants are permanently frozen. This mirrors CVE-2022-2566's pattern of a loop/aggregate producing a count smaller than the data actually written.

### Finding Description
- `requestInstantWithdraw` records receipts per request epoch: `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and `instantWithdrawClaimsByEpoch[currentEpoch]` (`IdleCreditVault.sol:367-374`).
- `claimInstantWithdrawRequest` has no epoch-expiry check — an instant receipt survives across `stopEpoch`/`epochNumber` increments and can remain partially unfunded via `collectInstantWithdrawFunds`, which only decrements the global `pendingInstantWithdraws` counter (`IdleCreditVault.sol:398-403`).
- At finalization, `defaultPendingClaimBasis()` returns `pendingWithdraws + instantWithdrawClaimsByEpoch[epochNumber]` (`IdleCreditVault.sol:644-649`). If the still-pending instant claims were recorded under epoch N but default finalizes in epoch N+1, `instantWithdrawClaimsByEpoch[N+1]` excludes them.
- `_defaultPrefundedInstantReserve()` repeats the same current-epoch-only lookup, so already-collected cash backing stale-epoch instant claims is not added to `reserveAmount` either (`IdleCreditVault.sol:716-723`).
- `finalizeDefaultRecovery` then sets `defaultRecoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` with the too-small `totalBasis` (`IdleCreditVault.sol:679-692`), and `_claimDefaultedInstantWithdrawRequest`/`_claimDefaultedWithdrawRequest` pay `claimBasis * defaultRecoveryPrice / 1e18` while decrementing `defaultRecoveryReserve` (`IdleCreditVault.sol:772-783, 842-856`).
- Broken invariant: sum over all payable claims > reserve. Early claimants are overpaid; when `defaultRecoveryReserve -= _amount` underflows (or the ERC20 transfer fails), every subsequent recovery claim reverts permanently.

Attack sequence (unprivileged KYC lender as attacker):
1. Epoch N (running): attacker calls `requestInstantWithdraw` via `IdleCDOEpochVariant`; borrower/strategy liquidity covers only part, so `pendingInstantWithdraws > 0` and the receipt is keyed to epoch N.
2. `stopEpoch` → `epochNumber` = N+1; attacker also opens a normal `requestWithdraw` in epoch N+1 (included in `pendingWithdraws`, so it *is* in `totalBasis`).
3. Borrower defaults; manager/owner finalizes via `finalizeDefaultRecovery`. `totalBasis` omits the stale epoch-N instant basis → `defaultRecoveryPrice` inflated.
4. Attacker calls `claimWithdrawRequest`; `_claimDefaultedWithdrawRequest` pays `claimBasis * inflatedPrice`, over-consuming `defaultRecoveryReserve`.
5. Honest claimants' `_transferDefaultRecovery` underflows/reverts → their recovery is permanently unclaimable. The attacker's own stale instant receipt additionally remains payable at par through `_transferFundedClaim` when non-reserve balance exists.

Existing guards do not stop this: `_transferFundedClaim`'s reserve check protects the reserve only from funded-claim spending, not from the inflated `defaultRecoveryPrice`; nothing re-keys `instantWithdrawClaimsByEpoch` on epoch rollover.

### Impact Explanation
Direct theft plus permanent freezing: the attacker extracts more underlying than a pro-rata haircut allows, and the shortfall is socialized onto later defaulted-epoch claimants whose claims revert forever (reserve is only funded once at finalization). Loss magnitude ≈ stale-epoch instant basis × recoveryPrice — bounded by the instant queue size but fully extractable.

### Likelihood Explanation
Requires: an instant-withdraw receipt that survives an epoch boundary with residual `pendingInstantWithdraws`, followed by a borrower default and recovery finalization. Instant withdrawals are a normal lender action and partial funding is expected (that's why `pendingInstantWithdraws` exists), so the precondition is reachable without privileged misbehavior. I did not fully verify inside `IdleCDOEpochVariant` the exact path by which an instant request can remain unfunded across `stopEpoch` (e.g., `getInstantWithdrawFunds` partial collection); if the CDO always fully funds or reverts, likelihood drops.

### Recommendation
In `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()`, aggregate instant claims across all epochs with pending receipts rather than `instantWithdrawClaimsByEpoch[epochNumber]` only — e.g., track a global `instantWithdrawClaimsTotal` incremented in `requestInstantWithdraw` and decremented on claim/collection, and use that as the instant basis. Symmetrically, let `_claimDefaultedInstantWithdrawRequest` clear a user's full `instantWithdrawsRequests[_user]` basis regardless of request epoch.

### Proof of Concept
A Foundry fork test in `test/foundry/IdleCreditVault.t.sol` style:
1. Deposit via `cdoEpoch.depositAA`, `startEpoch`, then `requestInstantWithdraw` sized so `collectInstantWithdrawFunds` funds only part (leave `pendingInstantWithdraws > 0`).
2. `vm.warp(epochEndDate + 1)`; `stopEpoch` → epoch N+1. Open a normal `requestWithdraw`.
3. Trigger borrower default path (`_handleBorrowerDefault`/`finalizeDefault` → `finalizeDefaultRecovery` with partial `_recoveredAmount`).
4. Assert `defaultRecoveryPrice` equals `reserveAmount * 1e18 / (pendingWithdraws)` while true claimable basis also includes the epoch-N instant amount.
5. Call `claimWithdrawRequest` as attacker: received amount exceeds fair pro-rata; a second honest claimant's claim reverts on `defaultRecoveryReserve -= _amount` underflow — demonstrating overpayment and permanent freeze.
