### Title
Deleted multisig members' stale confirmations still count toward `num_confirmations`, allowing execution with fewer than the required threshold of live approvers - (File: `multisig2/src/lib.rs`)

### Summary
`delete_member` (and the equivalent `DeleteKey` action in the legacy `multisig` contract) only purges confirmations/requests that the removed member *created*. It never scans other pending requests to strip confirmations the removed member had previously *added as a confirmer*. Those stale confirmations remain in the `confirmations` `HashSet` and are still summed by `confirm()` against `num_confirmations`, so a request can execute having been approved by fewer live members than the configured threshold.

### Finding Description
`confirm()` decides whether to execute a request purely by comparing the size of the stored confirmation set to `num_confirmations`: [1](#0-0) 

`delete_member()` removes the member from `self.members` and cleans up only the requests that member *originally created* (`r.member == member`), plus their `num_requests_pk` entry: [2](#0-1) 

It never iterates `self.confirmations` to remove the deleted member's entries from *other* requests they had confirmed but did not create. Since `confirmations` is a separate `LookupMap<RequestId, HashSet<String>>` keyed independently of `requests`, a confirmation string like `member.to_string()` recorded for request `R` (created by someone else) survives the member's removal untouched.

The intended custody/authorization binding is:
```
confirmations.len() on execution == number of currently-live members who approved R
```
After a member deletion with a stale confirmation still counted, the real binding becomes:
```
confirmations.len() on execution == (live approvers) + (approvals from members who no longer exist)
```
so a request can cross the `num_confirmations` threshold while having fewer than `num_confirmations` *currently authorized* approvers — a threshold-execution bypass, which matches the "Critical: multisig request executed below threshold" impact class in scope.

The same root cause exists in the legacy `multisig` contract's `DeleteKey` handling, which filters and cleans confirmations only for requests created by the deleted key, not requests that key merely confirmed: [3](#0-2) 

### Impact Explanation
This lets a multisig execute a sensitive request (`Transfer`, `FunctionCall`, `AddKey`/`AddMember`, `DeployContract`, etc.) with real, current authorization below the contract's stated `num_confirmations` policy. Funds can be moved, or the multisig's member/key set can be further manipulated, using approval from an account/key that is no longer trusted — directly breaking the confirmations-vs-live-members custody binding and enabling unauthorized fund movement or governance takeover of the multisig account, which is Critical severity per the given impact classes ("a multisig request executed below threshold").

### Likelihood Explanation
This requires only ordinary multisig operation, no attacker privilege escalation beyond being (or having been) a legitimate member/keyholder at some point:
1. A member is removed at some point (e.g., routine key rotation, suspected compromise, employee offboarding) via the normal `DeleteMember`/`DeleteKey` flow.
2. That member had previously confirmed a still-pending request that had not yet reached threshold.
3. Any subsequent confirmation from a remaining live member can push the count over `num_confirmations`, causing execution with a stale, no-longer-authorized confirmation counted.

Because request cooldown is only 15 minutes and requests can sit un-executed for a long time (`active_requests_limit` allows up to 12 concurrent requests per member by default), this scenario is realistic in normal multisig lifecycle usage, not merely theoretical.

### Recommendation
When executing `DeleteMember`/`DeleteKey`, iterate all pending requests' confirmation sets and strip the deleted member's/key's confirmation entry (not just requests they created), or alternatively re-validate at execution time in `confirm()` that every entry in the stored confirmation set still corresponds to a current member of `self.members` before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `{A, B, C, D}` and `num_confirmations = 3`.
2. `A` calls `add_request_and_confirm` with a malicious `Transfer` request `R` to an attacker-controlled account → confirmations = `{A}`.
3. `B` calls `confirm(R)` → confirmations = `{A, B}` (2/3, not yet executed).
4. Separately, the group legitimately removes `B` (e.g., suspected key compromise) by confirming a `DeleteMember { member: B }` request with `{A, C, D}` → `delete_member` runs: `B` is removed from `self.members`; only requests *created* by `B` are purged. Request `R`'s confirmation set `{A, B}` is untouched.
5. `C` calls `confirm(R)` → `confirmations.len() (2) + 1 = 3 >= num_confirmations (3)` → `execute_request(R)` fires the `Transfer`.

Only `A` and `C` are live members who actually approved `R` at execution time — `B`'s stale confirmation (from before removal) was counted toward the threshold, so the transfer executed with 2 live approvals instead of the required 3. [1](#0-0) [2](#0-1)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
