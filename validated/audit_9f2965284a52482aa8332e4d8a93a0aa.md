### Title
Rejection weight is double-counted as acceptance weight when a signer flips its vote - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The miner-side `StackerDBListener`, which the block-broadcast coordinator (`signer_coordinator.rs`) relies on to decide when a block has crossed the 70% signing threshold, tracks per-block `total_weight_approved` / `total_weight_rejected` using two *different* dedup guards for the accept and reject code paths. A single signer that first rejects a block and then (later, in a subsequent StackerDB message) accepts the same block gets its weight added to **both** `total_weight_rejected` and `total_weight_approved`, because the guard used to decide whether to add weight on the "Accepted" path is not the same set that the "Rejected" path uses to mark the signer as already having responded.

### Finding Description
In the `Accepted` branch, weight is added to `total_weight_approved` only if the slot is not already present in `block.gathered_signatures`: [1](#0-0) 

In the `Rejected` branch, weight is added to `total_weight_rejected` only if the slot was not already present in `block.responded_signers`: [2](#0-1) 

`block.responded_signers.insert(slot_id)` is called unconditionally in the `Accepted` branch too (line 465), but only *after* the weight has already been added via the `gathered_signatures` check — so the two branches use different keys to decide "have I already counted this signer's weight for this bucket":

- `Accepted` path dedups on `gathered_signatures` (keyed by slot).
- `Rejected` path dedups on `responded_signers` (keyed by slot, shared across both message types).

Sequence that produces the double count for a single signer, slot `S`, weight `W`:
1. Signer `S` broadcasts `BlockResponse::Rejected` for block `B`. `responded_signers.insert(S)` → `true` (first time) → `total_weight_rejected += W`.
2. The *same* signer `S` later broadcasts `BlockResponse::Accepted` for the same block `B` (a legitimate flip-flop, or a signer that simply resent an old cached decision after initially rejecting). `gathered_signatures.contains_key(S)` is `false` (this signer never previously accepted) → `total_weight_approved += W`.

At this point `W` counts toward *both* `total_weight_rejected` and `total_weight_approved` for the same underlying signer. This is exactly the bug-class analog of the report: a value that should only be attributed to one bucket (claimed vs. unclaimed reward; here, reject vs. accept) is silently double-counted because the code that decides whether to add it uses an inconsistent/incomplete condition relative to the other bucket's bookkeeping.

The coordinator that drives block broadcast consumes exactly these two counters and treats them as if they partition the same underlying signer weight: [3](#0-2) 

Because a byzantine (or merely flip-flopping) minority signer's weight can appear in both totals, `total_weight_approved` can cross `self.weight_threshold` (70%) using weight that is also recorded as having rejected the block — i.e. a rejection gets partially recounted as an acceptance in the miner's local tally that gates broadcast timing.

### Impact Explanation
This breaks the "aggregated-weight vs. verified-accepts" equality the coordinator relies on: `total_weight_approved` is supposed to reflect only signers who currently endorse the block, but it can include weight from a signer who is simultaneously recorded as rejecting it. This causes the miner to believe the 70% acceptance threshold has been reached earlier/using fewer genuinely-accepting signers than actually required, triggering `cvar.notify_all()` and early broadcast attempts (`Ok(block_status.gathered_signatures.values()...)` in `signer_coordinator.rs`).

Because the final on-chain acceptance check independently recomputes `total_weight_signed` from the real signature list via `NakamotoBlockHeader::verify_signer_signatures` / `compute_voting_weight_threshold`, a block with insufficient genuine signature weight will still be rejected at the chainstate layer. So the practical effect is confined to the node/coordinator's local view: premature/incorrect threshold-crossing decisions, incorrect logging/telemetry, and wasted broadcast attempts of a block that chainstate will reject — a liveness/efficiency degradation of the block-production pipeline rather than a chain-consensus safety break, since consensus safety is re-enforced independently at `stackerslib/src/chainstate/nakamoto/mod.rs::verify_signer_signatures`.

### Likelihood Explanation
Triggering this requires only a single signer (no majority) to send a `Rejected` message for a block followed by an `Accepted` message for the same block — an action fully within a lone signer's control via ordinary StackerDB gossip, with no need for another signer's key or majority collusion. Whether this happens in practice depends on signer client behavior (most reference signer implementations settle on one verdict per block and don't flip after rejecting), so likelihood in the wild is low, but the code path itself imposes no protocol-level barrier against it.

### Recommendation
Use a single, consistent per-signer/per-block dedup key that tracks which *bucket* (approve vs. reject) a signer's weight has already been counted toward, and make it symmetric between the two branches, e.g.:
- Maintain one `HashMap<slot_id, Vote>` (Vote::Accepted/Rejected) instead of the two loosely-coupled structures (`gathered_signatures` and `responded_signers`).
- Before adding weight on either path, check that the signer has not already been counted in *either* bucket; if a signer's vote flips, subtract/adjust the previous bucket's tally rather than only adding to the new one, or simply refuse to change a signer's counted vote once tallied (first-vote-wins), consistent with how blocks in `stacks-signer/src/signerdb.rs`'s `BlockState` machine forbid moving back from a globally-decided state.

### Proof of Concept
1. Miner proposes block `B`; `signer_coordinator` starts waiting for signatures via `StackerDBListener`.
2. Malicious/careless signer `S` (weight `W`) sends `SignerMessageV0::BlockResponse(BlockResponse::Rejected(...))` for `B`.
   - `stackerdb_listener.rs:515-518`: `responded_signers.insert(S)` → true → `total_weight_rejected += W`.
3. Signer `S` then sends `SignerMessageV0::BlockResponse(BlockResponse::Accepted(...))` for the same `B` with a valid signature.
   - `stackerdb_listener.rs:443-465`: `gathered_signatures.contains_key(S)` is false → `total_weight_approved += W`; `gathered_signatures.insert(S, sig)`; `responded_signers.insert(S)` (already present, no-op for dedup purposes).
4. Now `total_weight_approved` and `total_weight_rejected` both include `W` for the same signer `S`.
5. If other signers' weight brings `total_weight_approved` (inflated by `W`) to ≥ `self.weight_threshold` while true unique-accept weight is below threshold, `signer_coordinator.rs:541-545` returns `Ok(...)` and the miner attempts to broadcast the block prematurely, before enough distinct signers have actually endorsed it.
