### Title
Stale confirmation entries from a removed-then-re-added member let a request execute with fewer real confirmations than `num_confirmations` - ([File: multisig2/src/lib.rs])

### Summary
`MultiSigContract::delete_member` only purges pending requests *created by* the removed member; it never scans other requests' `confirmations: LookupMap<RequestId, HashSet<String>>` to strip that member's confirmation string from requests they merely *confirmed*. Because `MultisigMember::to_string()` is a deterministic serialization of the public key/account id, re-adding the same member via `add_member` with an identical key/account reproduces the identical string, so the stale confirmation silently counts again once the member rejoins, letting one additional live confirmer push the request past `num_confirmations` without the required number of distinct *current* confirmations.

### Finding Description
The binding that must hold is:
`confirmations.get(&R).len() == |{ members m : m is currently a member AND m called confirm(R) since becoming a member }|`

`delete_member` breaks this binding: [1](#0-0) 
It filters `self.requests` for entries where `r.member == member` (i.e., requests the removed member *created*) and only for those does it call `self.confirmations.remove(&request_id)`. Any request `R` where the member merely appears inside `confirmations.get(&R)` as a *confirmer* (not the creator recorded in `MultiSigRequestWithSigner::member`) is untouched — `M.to_string()` remains inside `confirmations.get(&R)` forever, even though `self.members.remove(&member)` just revoked M's membership.

`add_member` then re-inserts the member without ever touching `confirmations`: [2](#0-1) 
Because `MultisigMember::to_string()` is a pure serialization of `public_key`/`account_id`: [3](#0-2) 
re-adding M with the same key/account id produces the exact same string that is still sitting in `confirmations.get(&R)`.

`confirm` never re-validates that every string already inside the `HashSet<String>` still belongs to a current member — it only checks membership of the *new* caller via `current_member()`/`assert_valid_request`, then just does a length check: [4](#0-3) 
So when any other live member calls `confirm(R)`, `confirmations.len() as u32 + 1 >= self.num_confirmations` is satisfied using M's stale, pre-removal confirmation plus the one live signer, even though M never called `confirm(R)` after rejoining. `execute_request` then runs the pending `Transfer`/`AddKey`/etc. with fewer real, current confirmations than `num_confirmations`.

No existing guard (`assert_valid_request`, `assert_self_request`, `assert_one_action_only`, `current_member`) checks the *provenance* or *freshness* of entries already present in a request's confirmation set — they only gate the calling transaction's own confirmation, not stale ones left behind by membership churn.

### Impact Explanation
This allows a multisig-controlled account to execute a `Transfer` (or `AddKey`, `DeleteMember`, `FunctionCall`, etc.) with fewer genuinely current confirmations than the configured `num_confirmations`, i.e., NEAR can leave the multisig account (or a full-access key can be added) under a weaker security threshold than governance configured. This matches the explicitly listed Critical category: "a multisig request executed below `num_confirmations` live members." The effect is repeatable any time a member is removed and later re-added with the same public key/account id while they have an outstanding confirmation on some other pending request — a realistic churn scenario (e.g., a team member leaving and returning, or a key being deleted and re-registered for other operational reasons).

### Likelihood Explanation
Preconditions: (1) member M confirms some request R without R reaching quorum, (2) M is later removed via `DeleteMember` for reasons unrelated to R, (3) M is re-added via `AddMember` using the identical `public_key` or `account_id` (a common real-world pattern — reusing the same key/account on re-onboarding), (4) any other still-current member confirms R. All of these are standard multisig governance operations already exposed by the contract's own API (`add_request`, `confirm`, `AddMember`/`DeleteMember` actions) — no external unprivileged attacker action is needed beyond normal use of the contract's public interface, and the flaw is purely an internal accounting bug independent of who triggers it.

### Recommendation
In `delete_member`, iterate over all entries of `self.confirmations` (not just requests created by the member) and remove `member.to_string()` from every `HashSet<String>` in which it appears, or equivalently maintain confirmations keyed in a way that is invalidated on membership changes (e.g., re-verify each confirming string is still `self.members.contains(...)` at `confirm` time and lazily prune/reject stale entries before counting `confirmations.len()`).

```rust
// multisig2/src/lib.rs test module (conceptual, cargo test)
#[test]
fn test_stale_confirmation_survives_member_churn() {
    // members: m1 (AccessKey pk1), m2 (AccessKey pk2), m3 (AccessKey pk3), num_confirmations = 2
    testing_env!(context_with_key(pk3, amount));
    let mut c = MultiSigContract::new(vec![
        MultisigMember::AccessKey { public_key: pk1.clone() },
        MultisigMember::AccessKey { public_key: pk2.clone() },
        MultisigMember::AccessKey { public_key: pk3.clone() },
    ], 2);

    // m3 creates request R (transfer), m1 confirms it (not enough for quorum yet)
    let request_id = c.add_request(transfer_request.clone());
    testing_env!(context_with_key(pk1.clone(), amount));
    c.confirm(request_id); // confirmations(R) = { pk1_member.to_string() }, len == 1 < 2

    // Remove m1 via governance (unrelated reason) - R untouched because m1 didn't create it
    testing_env!(context_with_key(pk3.clone(), amount));
    let del_req = c.add_request(delete_member_request(pk1.clone()));
    c.confirm(del_req); // only 1 confirmation needed here for illustration, or repeat with quorum
    assert!(!c.get_members().contains(&MultisigMember::AccessKey{ public_key: pk1.clone() }));
    // confirmations(R) still contains pk1's string:
    assert!(c.get_confirmations(request_id).contains(&pk1_member.to_string()));

    // Re-add m1 with the SAME public key
    let add_req = c.add_request(add_member_request(pk1.clone()));
    c.confirm(add_req);
    assert!(c.get_members().contains(&MultisigMember::AccessKey{ public_key: pk1.clone() }));

    // m1 has NOT called confirm(R) since rejoining. m2 confirms -> pushes over threshold
    testing_env!(context_with_key(pk2.clone(), amount));
    c.confirm(request_id);

    // Assertions on both sides of the binding:
    // LHS: confirmations.len()+1 >= num_confirmations triggered execution (request removed => executed)
    assert_eq!(c.list_request_ids().contains(&request_id), false);
    // RHS: real distinct current members who called confirm(R) AFTER m1's re-admission == 1 (only m2), not 2
    let real_confirmers_after_readd = 1; // only m2; m1's confirmation predates re-admission
    assert_eq!(real_confirmers_after_readd, c.get_num_confirmations() as usize - 1);
    assert!(real_confirmers_after_readd < c.get_num_confirmations() as usize);
}
```

```rust
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
```

```rust
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
```
