## Analysis

I confirmed the analog exists in `multisig2/src/lib.rs`. Both `DeleteKey`/`DeleteMember` cleanup routines only purge outstanding *requests originated by* the removed member/key, but never purge that member's already-recorded *confirmations* on other still-pending requests.

### Title
Stale confirmations from deleted multisig members are still counted toward `num_confirmations` threshold - ([File: multisig2/src/lib.rs])

### Summary
`delete_member` (and the equivalent `DeleteKey` path in the legacy `multisig/src/lib.rs`) removes a member from `self.members` and deletes any *requests that member originated*, but does not scrub that member's entries from `self.confirmations` on *other* pending requests they had previously confirmed. Because `confirm()` only checks `confirmations.len()` against `self.num_confirmations` and never re-validates that each recorded confirmation still belongs to a current member, a confirmation cast by a member who is later removed continues to count toward the K-of-N threshold indefinitely.

### Finding Description
`execute_request`'s `DeleteMember` branch [1](#0-0)  calls `self.delete_member(promise, member)`, whose body only cleans confirmations for requests where `r.member == member` (i.e., requests *added* by the deleted member), and separately removes `num_requests_pk` bookkeeping: [2](#0-1) . It never iterates `self.confirmations` to strip the deleted member's string from confirmation sets belonging to requests added by *other* members.

`confirm()` determines whether a request is ready to execute purely from the size of the stored `HashSet<String>` of confirmations versus `self.num_confirmations`: [3](#0-2) . It re-validates only that the *calling* member is currently valid via `current_member()` [4](#0-3) ; it never re-validates the members recorded in the *existing* confirmation set.

This breaks the intended binding: `len(confirmations) == count of confirmations from members still in self.members`. After a member is removed, `len(confirmations)` on a pending request can still include that removed member's stale confirmation, so the equality becomes `confirmations counted > live members who actually confirmed`.

### Impact Explanation
This is a threshold-bypass, not a DoS: it lets a request execute (e.g., a `Transfer`, `AddKey`/`AddMember`, or `FunctionCall` action moving funds or granting access) with fewer *live* confirming members than `num_confirmations` requires. Concretely:
1. Member A adds a `Transfer` request (deposit N members, threshold K).
2. Member B (still a member) confirms it — 1/K confirmations recorded, request stays pending (does not yet reach K).
3. Separately, the multisig executes a `DeleteMember` request removing member B (e.g., because B's key was compromised, B left the org, or the group intentionally rotated membership).
4. B's earlier confirmation on the still-pending Transfer request from step 2 is never purged.
5. Now only `K-1` *live* members are needed to reach the threshold and execute the transfer — the multisig's `K`-of-current-N guarantee is broken, and the request executes below the intended live-signer threshold.

This matches the in-scope Critical impact class explicitly: "a multisig request executed below threshold."

### Likelihood Explanation
Likelihood is high for any multisig that legitimately rotates membership (a routine operational action, not requiring compromise of a victim key or any privileged/attacker-only action beyond being a normal member who creates the `DeleteMember` request through the normal governance flow). No malicious redeploy, no RPC interception, no social engineering is required — only the ordinary sequence of "confirm a pending request" followed by "remove that confirmer as a member," both of which are supported first-class multisig operations.

### Recommendation
When removing a member (`delete_member`/`DeleteKey`), iterate all pending `self.confirmations` entries and remove any entry belonging to the removed member/key, not just requests they originated. Alternatively, when computing readiness in `confirm()`, filter the stored confirmation set to only those entries that match `self.members.contains(...)` before comparing against `self.num_confirmations`.

### Proof of Concept
1. Deploy multisig with 3 members (A, B, C), `num_confirmations = 2`.
2. A calls `add_request` for `Transfer { amount }` targeting some receiver — this auto-adds A's confirmation is not applied unless `add_request_and_confirm` used; assume `add_request_and_confirm`, giving 1/2 confirmations.
3. B calls `confirm(request_id)` → 2/2 reached in current membership, executes normally (baseline, not yet the bug).
   To demonstrate the actual issue, instead:
2'. A calls `add_request` (no confirm) for `Transfer`.
3'. B calls `confirm(request_id)` → 1/2 confirmations recorded (`confirmations = {B}`), request stays pending.
4'. Members execute a separate `DeleteMember{B}` request (via A + C confirming), reducing membership to {A, C}, `num_confirmations` still 2.
5'. `delete_member` runs: it only deletes requests where `r.member == B` (B's own originated requests) — the Transfer request from step 2' was originated by A, so it is untouched, and B's stale confirmation string remains in `self.confirmations` for that request: [5](#0-4) .
6'. C (now the only other live member besides A) calls `confirm(request_id)`. `confirmations.len()` becomes 2 (`{B, C}`), which is `>= num_confirmations (2)`, so `execute_request` runs the `Transfer` — even though only A (implicitly, as request originator) and C are live members, and B's now-invalid confirmation was needed to hit the threshold. The transfer executes with only 1 live confirming member instead of the required 2.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
