I found a concrete analog of the fickling "builtins blindness" pattern: a self-declared representation that a downstream security check trusts, but that the emitting/serialization path can silently drop, blinding the very enforcement that depends on it — the signer's `tx_replay_set` propagation through `StateMachineUpdateContent::V0`.

### Title
Signer's V0 state-machine wire format silently drops `tx_replay_set`, blinding replay-enforcement and letting a stale/forked chain history be re-signed - ([File: libsigner/src/v0/messages.rs])

### Summary
The fickling bug is a representation gap: a semantically dangerous fact (`builtins` import) is computed internally but never emitted into the AST that the security scanner inspects, so the scanner is blind to it. The stacks-signer has the same shape of bug: `LocalStateMachine::tx_replay_set` is a real, internally-tracked fact (the transactions that must be replayed before the chain can safely resume after a Bitcoin fork), but when a signer serializes its local state into a `StateMachineUpdate` for gossip at protocol version 0, `StateMachineUpdateContent::new` simply omits the field from the `V0` variant. Any consumer that reads that message back out via `StateMachineUpdateContent::tx_replay_set()` gets `ReplayTransactionSet::none()` unconditionally, regardless of what the emitting signer actually believes.

### Finding Description
`StateMachineUpdateContent::new` builds three variants keyed off the negotiated protocol version: [1](#0-0) 

`V0` carries only `burn_block`, `burn_block_height`, `current_miner` — no replay set at all. Correspondingly, `tx_replay_set()` hard-codes `ReplayTransactionSet::none()` for `V0` and only derives a real set from `V1`/`V2`: [2](#0-1) 

Every signer feeds its own `LocalStateMachine` into this same lossy conversion before evaluating a proposal: `check_block_against_state` calls `try_into_update_message_with_version(local_version)` and inserts the (possibly downgraded) update into the shared `GlobalStateEvaluator`: [3](#0-2) 

`try_into_update_message_with_version` deliberately falls back to the *local* supported version whenever the state machine's active version exceeds it ("Cannot create state machine update for future protocol version ... falling back"), which means the emitted content version — and thus whether `tx_replay_set` survives — is driven by `local_supported_signer_protocol_version`, not by whether the signer actually has a non-empty replay obligation: [4](#0-3) 

The global evaluator then aggregates `tx_replay_set()` across all signers' updates to compute the enforced replay set (`GlobalStateEvaluator::determine_global_state`, `find_majority_prefix_replay_set`), and the local (pre-global-state) path pulls the same aggregate via `get_global_tx_replay_set()` and feeds it straight into the chainstate check that is supposed to force miners to replay stranded transactions after a fork: [5](#0-4) 

Downstream, `SortitionsView::check_proposal` takes this `replay_set` as an explicit parameter and is the mechanism that makes signers reject a post-fork block that doesn't replay the required transactions (see the dedicated rejection code `ValidateRejectCode::InvalidTransactionReplay`, exercised in `stacks-node/src/tests/signer/v0/tx_replay.rs`). If the version negotiated across the signer set collapses to 0 — which is exactly what `update_protocol_version`/`try_into_update_message_with_version` are built to do defensively whenever any signer only supports version 0 — the aggregated `tx_replay_set` becomes permanently `ReplayTransactionSet::none()` for every signer using that evaluator, even for signers whose actual `LocalStateMachine.tx_replay_set` is non-empty and correctly computed. The replay obligation is real internally, but the wire representation the rest of the state machine relies on is blind to it, exactly like fickling's dropped `builtins` import node.

### Impact Explanation
This maps to the "acting on a stale reward set/threshold" / equivocation-adjacent High-impact bucket in scope: a signer can be made to treat a chain that has *not* correctly replayed the pre-fork transactions as fully valid, because the check that is supposed to enforce replay (`check_proposal` with `replay_set`) is silently fed an empty set. That breaks the "approved-parent vs canonical" / post-fork consistency equality the replay-set mechanism exists to guarantee: a miner could omit transactions that must be replayed after a Bitcoin fork, and V0-negotiated signers would sign the resulting block anyway, since their aggregated view of "what must be replayed" is empty regardless of reality.

### Likelihood Explanation
Reachable by ordinary protocol-version drift, not by a majority-controlled attack: `determine_active_signer_protocol_version`/`update_protocol_version` are designed to downgrade to whatever the *lowest* commonly supported version is, so a single lagging signer (or a rolling upgrade window where signers advertise version 0) is enough to push the negotiated content version, and hence `tx_replay_set` serialization, to `V0` for the whole evaluator population that observes it. A miner or gossiping party does not need to forge anything cryptographic — they only need the network to be in (or manipulable into) a state where V0 is negotiated, then propose a non-replaying block during/after a fork window.

### Recommendation
Do not let `tx_replay_set` become unrepresentable at any negotiated protocol version that is expected to coexist with active replay enforcement: either (a) make `V0` carry the replay set as well (bumping the wire format), or (b) have `GlobalStateEvaluator`/`check_block_against_local_state` explicitly detect "the effective/negotiated version cannot express tx_replay_set" and treat that as an un-computable/reject case (mirroring the `NoSignerConsensus` rejection used elsewhere) rather than silently substituting `ReplayTransactionSet::none()`. At minimum, `tx_replay_set()` returning `none()` for `V0` should be distinguishable from "the signer set agrees there is no replay obligation."

### Proof of Concept
Not independently exploit-verified in this pass (no test-harness execution available); this is based on static tracing of `try_into_update_message_with_version` → `StateMachineUpdateContent::new`/`tx_replay_set()` → `GlobalStateEvaluator::determine_global_state`/`get_global_tx_replay_set` → `check_proposal`'s `replay_set` parameter. A concrete PoC would: (1) fork the network to give some signers a genuine non-empty `tx_replay_set`; (2) ensure the negotiated `active_signer_protocol_version`/`local_supported_signer_protocol_version` resolves to 0 across the relevant evaluator population (e.g., one or more signers only advertising v0 support); (3) have the miner propose a block that omits the required replay transactions; (4) observe that `check_block_against_local_state`/`check_proposal` receives an empty `replay_set` and does not reject with `RejectReason`/`ValidateRejectCode::InvalidTransactionReplay`, in contrast to the documented behavior in `tx_replay_reject_invalid_proposals_during_replay`. I was not able to execute this scenario against the running signer test harness in this pass, so the described bypass is derived from code paths rather than an observed runtime result — recommend a Devin session with test execution access to confirm end-to-end.
