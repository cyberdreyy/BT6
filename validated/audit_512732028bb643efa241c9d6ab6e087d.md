### Title
`solveRequestsVault` async redeem "solved" path pushes tokens to attacker-chosen `receiver` without fallback, allowing a self-inflicted revert to DoS an entire solver batch - (File: v3/src/core/ProvisionerV2.sol)

### Summary
`requestRedeem` lets an ordinary user set an arbitrary `receiver` (validated only for non-zero address) for their async redeem request [1](#0-0) . When a solver later solves that request via `solveRequestsVault`, the "solved" branches of `_solveRedeemVaultAutoPrice`/`_solveRedeemVaultFixedPrice` push tokens directly to `request.receiver` with an unguarded `token.safeTransfer(...)`, unlike every other transfer path in this file which uses `_transferWithFallback` to fall back to the requester on failure. This mirrors the Rialto/`cancelMinipoolByMultisig` push-payment pattern where a hostile receiver can force a revert.

### Finding Description
`_solveRedeemVaultAutoPrice` and `_solveRedeemVaultFixedPrice` are internal solve functions invoked in a loop by `_solveRequestsVault`, which is called from the externally/`requiresAuth`-gated `solveRequestsVault` [2](#0-1) . Inside the "not expired" branch, after `exit`-ing the vault, both functions do a direct push:

```solidity
token.safeTransfer(request.receiver, tokenOutAfterTip);
``` [3](#0-2) [4](#0-3) 

This is the *only* place in the whole solving/refund surface that omits the `_transferWithFallback` protection that is used consistently everywhere else — the deposit/refund and both "expired" branches of the same functions explicitly note "fallback to requester on transfer failure" and call `_transferWithFallback` [5](#0-4) , `_clearHashAndTransferRefund` [6](#0-5) .

`request.receiver` is fully attacker-controlled at request-creation time (`requestRedeem`), with the only guard being non-zero address [7](#0-6) , [1](#0-0) . If `receiver` is set to a token address that reverts on incoming transfer for that address (e.g., a blacklisted address for a blacklistable stablecoin, or a token with hooks that can be made to revert), then the `safeTransfer` inside `_solveRedeemVaultAutoPrice`/`_solveRedeemVaultFixedPrice` reverts, and since `_solveRequestsVault` iterates over the whole `requests[]` array in a single transaction without try/catch around this call (unlike the pre/post-submit calls which use try/catch), the **entire batch transaction reverts** — including all other unrelated deposit/redeem requests bundled in the same `solveRequestsVault` call.

### Impact Explanation
This is a griefing/DoS vector: any ordinary user can plant a redeem request whose `receiver` cannot accept the token, and every time a solver includes that request in a `solveRequestsVault` batch, the whole batch reverts, temporarily freezing solving (and thus fund settlement) for every other pending request bundled with it. This matches Immunefi's Medium-severity "temporary freezing of funds" category — no funds are permanently lost, and the attacker's own escrowed units simply remain stuck in the Provisioner, but other users' requests bundled in the same batch fail to settle until the solver identifies and excludes the poisoned request.

### Likelihood Explanation
Low-moderate. The precondition (a token whose transfer to a chosen address reliably reverts) is not universally available for arbitrary ERC-20s used as the vault's numeraire/deposit token — it requires either a blacklistable token (e.g., USDC/USDT-style `isBlacklisted` checks) where the attacker sets `receiver` to a known-blacklisted address, or a token with transfer hooks that can be forced to revert. Because the loop processes the whole batch atomically and the malicious request can simply be excluded from future batches once identified, the practical, sustained impact on the protocol is limited to transient griefing rather than persistent fund freezing, and I was not able to confirm from the indexed code whether currently deployed/in-scope tokens for the live vaults are of a type that supports this revert-on-receive precondition.

### Recommendation
Wrap the `token.safeTransfer(request.receiver, tokenOutAfterTip)` calls in `_solveRedeemVaultAutoPrice` and `_solveRedeemVaultFixedPrice` with the same `_transferWithFallback` pattern already used elsewhere in the contract, so a receiver-side revert routes tokens to `request.user` instead of reverting the whole solving batch.

### Proof of Concept
Not fully verifiable from the indexed code alone: constructing a decisive local-fork/Foundry PoC requires confirming that a deployed, in-scope vault's redeem token is a blacklistable/hook-capable token (e.g., USDC) so that a `receiver` address can be made to revert on `safeTransfer`, which I could not confirm from the available index. At a conceptual level the PoC would: (1) call `requestRedeem` with `receiver` set to a blacklisted/reverting address and a short/no-expiry fixed-price request; (2) as an authorized solver, call `solveRequestsVault` with a batch containing this request plus a legitimate second user's request; (3) assert the whole transaction reverts (`token.safeTransfer` revert bubbling up through `_solveRequestsVault`), demonstrating the second user's otherwise-solvable request is blocked in that batch.

    function _solveRequestsVault(IERC20 token, RequestV2[] calldata requests) internal {
        // Requirements: vault is not paused in the priceAndFeeCalculator
        require(!PRICE_FEE_CALCULATOR.isVaultPaused(MULTI_DEPOSITOR_VAULT), Aera__PriceAndFeeCalculatorVaultPaused());

        // Interactions: get price age
        uint256 priceAge = block.timestamp - PRICE_FEE_CALCULATOR.getVaultPriceTimestamp(MULTI_DEPOSITOR_VAULT);

        uint256 solverTip;
        RequestV2 calldata request;

        uint256 length = requests.length;
        TokenDetailsV2 memory tokenDetails = tokensDetails[token];
        bool depositsExist;
        for (uint256 i = 0; i < length; i++) {
            request = requests[i];
            if (_isRequestTypeDeposit(request.requestType)) {
                // Requirements: async deposit is enabled
                if (!tokenDetails.asyncDepositEnabled) {
                    // Log async deposit disabled event
                    emit AsyncDepositDisabled(i);
                    continue;
                }

                if (!depositsExist) {
                    depositsExist = true;
                    token.forceApprove(MULTI_DEPOSITOR_VAULT, type(uint256).max);
                }

                if (_isRequestTypeAutoPrice(request.requestType)) {
                    // Requirements + Effects + Interactions: solve auto price deposit
                    solverTip += _solveDepositVaultAutoPrice(
                        token, tokenDetails.asyncDepositMultiplier, request, priceAge, i
                    );
                } else {
                    // Requirements + Effects + Interactions: solve fixed price deposit
                    solverTip += _solveDepositVaultFixedPrice(
                        token, tokenDetails.asyncDepositMultiplier, request, priceAge, i
                    );
                }
            } else {
                // Requirements: async redeem is enabled
                if (!tokenDetails.asyncRedeemEnabled) {
                    // Log async redeem disabled event
                    emit AsyncRedeemDisabled(i);
                    continue;
                }

                if (_isRequestTypeAutoPrice(request.requestType)) {
                    // Requirements + Effects + Interactions: solve auto price redeem
                    solverTip += _solveRedeemVaultAutoPrice(
                        token, tokenDetails.asyncRedeemMultiplier, request, priceAge, i
                    );
                } else {
                    // Requirements + Effects + Interactions: solve fixed price redeem
                    solverTip += _solveRedeemVaultFixedPrice(
                        token, tokenDetails.asyncRedeemMultiplier, request, priceAge, i
                    );
                }
            }
        }

    function _clearHashAndTransferRefund(
        IERC20 token,
        RequestV2 calldata request,
        address requester,
        uint256 amount,
        IERC20 transferToken
    ) internal {
        bytes32 requestHash = _getRequestHash(token, request);
        // Requirements: hash has been set
        require(asyncRequestHashes[requestHash], Aera__HashNotFound());
        // Effects: unset hash as used
        asyncRequestHashes[requestHash] = false;
        // Interactions: transfer amount to receiver, fallback to requester on transfer failure
        _transferWithFallback(transferToken, requester, request.receiver, amount);

        // Log refund event
        if (_isRequestTypeDeposit(request.requestType)) {
            emit DepositRefunded(requestHash);
        } else {
            emit RedeemRefunded(requestHash);
        }
    }

    /// @notice Transfers amount to receiver and falls back to requester if receiver transfer fails
    /// @param token The ERC20 token being transferred
    /// @param requester The original requester address used as fallback receiver
    /// @param receiver The intended receiver from the request
    /// @param amount The amount of tokens to transfer
    function _transferWithFallback(IERC20 token, address requester, address receiver, uint256 amount) internal {
        // Interactions: transfer to receiver, fallback to requester on transfer failure
        if (receiver == requester || !token.trySafeTransfer(receiver, amount)) {
            token.safeTransfer(requester, amount);
        }
    }

    /// @param receiver The address receiving funds when request is solved
    /// @param solverTip The tip offered to the solver
    /// @param deadline Timestamp until which the request is valid
    /// @param isFixedPrice Whether the request is a fixed price request
    function _validateRequest(address receiver, uint256 solverTip, uint256 deadline, bool isFixedPrice) internal view {
        // Requirements: receiver is not zero address
        require(receiver != address(0), Aera__ZeroAddressReceiver());
        // Requirements: deadline is in the future and not too far in the future
        require(deadline > block.timestamp, Aera__DeadlineInPast());

        // Requirements: fixed price requests cannot have a solver tip
