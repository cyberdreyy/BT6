## Title
Removed multisig members' stale confirmations still count toward `num_confirmations`, allowing requests to execute below the live-member threshold - (File: `multisig2/src/lib.rs`, also present in `multisig/src/lib.rs`)

### Summary
`MultiSigContract::confirm()` decides whether to execute a request purely by comparing the *size* of the stored confirmation set to `num_confirmations`. When a member is removed via `DeleteMember`/`DeleteKey`, `delete_member()` only purges requests that member *originally created* — it never scrubs that member's confirmations recorded on other, still-pending requests. A request that already collected a confirmation from a member who is later removed from the multisig can still be pushed over the threshold and executed, even though the number of confirmations from *currently valid* members is below `num_confirmations`.

### Finding Description
In `multisig2/src/lib.rs`:

- `delete_member()` [1](#0-0)  filters `self.requests` for entries whose `member == member` (i.e. requests *added by* that member) and removes those, plus `num_requests_pk`. It does **not** iterate `self.confirmations` to strip the removed member's entry from confirmation sets of requests they merely *confirmed* but did not create.
- `confirm()` [2](#0-1)  only checks `confirmations.len() as u32 + 1 >= self.num_confirmations` — it never re-validates that every account/key in the stored `confirmations` set is still `self.members.contains(...)`.

Consequently the invariant the contract is supposed to maintain — "a request executes only once `num_confirmations` *current* members have approved it" — silently degrades to "a request executes once `num_confirmations` accounts/keys, current or not, have ever approved it." This is the same class of bug as the reported `_getHigherLevelParents` issue: a counter (`count` / `confirmations.len()`) is trusted to represent a set that has actually changed shape (the level tree / the live member set), but the code never re-derives the counter from the up-to-date state, so it silently diverges from reality.

The identical pattern exists in the older `multisig/src/lib.rs`, where `MultiSigRequestAction::DeleteKey` only removes requests signed by that key [3](#0-2) , and `confirm()` has the same threshold check [4](#0-3) .

### Impact Explanation
This breaks the binding "confirmations counted versus live members": a request can execute — including `Transfer`, `AddKey`/`AddMember`, `DeployContract`, `FunctionCall`, etc. — with fewer than `num_confirmations` approvals from accounts that are actual members of the multisig at execution time. This falls under the Critical impact bucket "a multisig request executed below threshold," since NEAR can be moved (`Transfer`) or the contract's control set can be altered (`AddMember`/`AddKey`) by a request that was never actually approved by the required number of live signers.

### Likelihood Explanation
This requires no external attacker at all beyond normal multisig operation: it happens whenever a member is legitimately removed (e.g., a compromised key being revoked, an employee offboarded) while there is an outstanding request that member had already confirmed. This is a realistic, commonly-triggered sequence in multisig lifecycle management, not a contrived edge case — any organization rotating multisig membership while requests are pending is exposed.

### Recommendation
When removing a member in `delete_member`/`DeleteKey`, also scrub that member's entry from every entry in `self.confirmations` (not just requests they created), and/or have `confirm()` recompute the confirmation count by filtering the stored set against `self.members.contains(...)` before comparing to `num_confirmations`.

### Proof of Concept
1. `MultiSigContract::new(vec![A, B, C, D], 3)` — 4 members, 3 confirmations required.
2. `A` calls `add_request(R1)` (e.g. `Transfer` of the account's NEAR balance to attacker-controlled receiver). `B` calls `confirm(R1)` → `confirmations = {A, B}` (2/3, not executed) [2](#0-1) .
3. Separately, `B`, `C`, `D` confirm a `DeleteMember { member: A }` request, which succeeds and removes `A` from `self.members`, but does not touch `R1`'s confirmation set [5](#0-4) .
4. `C` calls `confirm(R1)`. `confirmations.len() as u32 + 1 == 3 >= num_confirmations`, so `R1` executes and transfers NEAR — even though only `B` and `C` are current members who approved it (`A`'s stale confirmation from before removal still counted) [6](#0-5) .

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
