### Title
Front-run of `lending_account_repay` during receivership can revert legitimate repayments via `OperationRepayOnly` - (File: `programs/marginfi/src/instructions/marginfi_account/repay.rs`, `programs/marginfi/src/state/marginfi_account.rs`)

### Summary
Marginfi's `lending_account_repay` instruction, like the Revert Lend `V3Vault.repay`, reverts if the caller-supplied `amount` exceeds the position's actual outstanding liability. During receivership (and order execution), the authority-signer check is bypassed, meaning any unprivileged key can call `repay` against another account's balance. An attacker can therefore front-run a legitimate exact-amount repayment with a minuscule repay, causing the legitimate transaction to overshoot the (now-reduced) debt and revert.

### Finding Description
`lending_account_repay` calls `BankAccountWrapper::repay(amount)` for non-`repay_all` calls: [1](#0-0) 

This delegates to `increase_balance_internal` with `BalanceIncreaseType::RepayOnly`, which computes `asset_amount_increase` as the portion of `amount` exceeding the current liability, and hard-errors if that excess is not within dust tolerance: [2](#0-1) 

This is the exact same "amount cannot exceed outstanding debt" root cause as the Revert Lend `RepayExceedsDebt`/`DebtChanged` finding: if `amount` is computed off-chain against a stale debt snapshot and someone reduces the debt in between (even by 1 unit), the follow-up exact-amount repay transaction reverts with `MarginfiError::OperationRepayOnly` instead of gracefully capping at the remaining debt.

Normally this would not be exploitable by an unprivileged attacker, since the `LendingAccountRepay` accounts struct requires the caller to be authorized for the specific `marginfi_account`: [3](#0-2) 

However, the instruction's own doc comment states that during receivership or order execution, this authority check is intentionally skipped and *any* signer can call repay on behalf of the account: [4](#0-3) 

That means once an account enters `ACCOUNT_IN_RECEIVERSHIP` (e.g., mid-liquidation/deleverage), any unprivileged actor can submit `lending_account_repay(amount, repay_all=false)` for a trivial amount (e.g. 1 native unit) against the position, shaving off a few liability shares. A subsequent keeper/liquidator/user transaction computing an exact repay `amount` off the pre-frontrun debt snapshot will then overshoot the now-smaller liability and fail with `OperationRepayOnly`.

### Impact Explanation
This enables a repeated, cheap griefing vector against exact-amount repayments occurring during receivership windows (deleverage/liquidation cleanup), forcing transactions to revert and potentially delaying orderly debt resolution for accounts already in a risk-sensitive state. It does not directly bypass authorization or redirect value, but it is a durable DoS against expected repayment flows exactly analogous to the referenced report's impact ("repayments and liquidations can be forced to revert"). The blast radius is narrower than the original report because: (a) normal (non-receivership) repay calls require account-authority signature and are not attackable this way; (b) `lending_account_liquidate` itself is bounded by `asset_amount` (collateral) rather than an exact liability-share target, and uses `withdraw_ignore_borrow_cap`/`OverliquidationAttempt` checks rather than the strict `RepayOnly` equality check, so it is not directly susceptible to the same griefing pattern.

### Likelihood Explanation
Requires an account to be in `ACCOUNT_IN_RECEIVERSHIP` (or order-execution) state and requires the attacker to race (front-run) a specific repay transaction with knowledge of its target amount — an MEV-style precondition, same as the original report ("attack vector includes MEV as a necessary condition"). This narrows applicability to a specific window rather than all repayments.

### Recommendation
In `BankAccountWrapper::repay` / `increase_balance_internal` (`programs/marginfi/src/state/marginfi_account.rs`), clamp `amount` to the actual outstanding liability instead of erroring via `OperationRepayOnly` when it is exceeded, refunding/no-transferring any excess, mirroring the `repay_all` semantics. Alternatively, when called during receivership by a non-authority, always treat repay as "repay up to full liability" and return the difference to the caller rather than reverting on partial overshoot.

### Proof of Concept
Conceptual PoC (mirrors the referenced report's test structure, adapted to marginfi's instruction surface):
1. Put a marginfi account into `ACCOUNT_IN_RECEIVERSHIP` (e.g., via `liquidate_start`).
2. Attacker (unauthorized key) calls `lending_account_repay(marginfi_account, bank, amount=1, repay_all=None)` — this succeeds because signer checks are bypassed in receivership: [4](#0-3) .
3. A keeper/liquidator that computed `amount = outstanding_debt_shares_value` before step 2 now submits `lending_account_repay(marginfi_account, bank, amount, repay_all=None)`.
4. Because `amount` now exceeds the (slightly reduced) liability, `increase_balance_internal`'s `RepayOnly` branch computes a nonzero `asset_amount_increase` beyond dust tolerance and reverts with `MarginfiError::OperationRepayOnly`: [5](#0-4) .
