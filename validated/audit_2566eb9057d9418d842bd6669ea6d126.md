### Title
Stale rejection weight is never retracted when a signer flips its vote from Rejected to Accepted, letting the miner's coordinator wrongly declare a valid block globally rejected - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener` tracks two independent, monotonically-increasing counters per block — `total_weight_approved` and `total_weight_rejected` — from raw `BlockResponse` gossip messages. A single signer is explicitly permitted by the signer state machine to reject a block and later flip to accepting it (`LocallyRejected -> LocallyAccepted`, driven by `capitulate_viewpoint`/re-evaluation). When that happens, the earlier rejection's weight is never subtracted from `total_weight_rejected`, so the same signer's weight ends up counted in both tallies simultaneously. This is the exact analog of the reported bug class: one accounting path (the raw incremental counter) diverges from the true current state (what signers currently think), exactly as `_totalSupplyCheckpoints` diverged from `Karma::totalSupply()`.

### Finding Description
The listener maintains `BlockStatus { total_weight_approved, total_weight_rejected, responded_signers, gathered_signatures, .. }` per block hash [1](#0-0) .

On an `Accepted` response, the code adds the signer's weight to `total_weight_approved` if their slot isn't already in `gathered_signatures`, and unconditionally inserts the slot into `responded_signers`: [2](#0-1) 

On a `Rejected` response, the weight is added to `total_weight_rejected` only guarded by `responded_signers.insert(slot_id)` returning true (i.e., "first time we've heard from this signer for this block"): [3](#0-2) 

Because `responded_signers` is a single shared set for both directions, the guard only prevents double-counting in the *same* direction (reject-then-reject, or accept-then-accept). It does nothing when the order is reject-then-accept: the signer's slot is already in `responded_signers` from the earlier rejection, but the accept branch's weight addition is gated on `gathered_signatures.contains_key(&slot_id)`, which is a *different* set — so the accept weight is added anyway, while the earlier rejection weight is never removed from `total_weight_rejected`.

This is legitimate to trigger by design: the signer state machine allows `LocallyRejected -> LocallyAccepted` re-evaluation (not `Unprocessed`/terminal-only) [4](#0-3) , and the flows doc confirms rejections are treated as revocable opinions that get superseded by a later signature, driven by `capitulate_viewpoint` [5](#0-4) .

Consequently `self.total_weight_approved + self.total_weight_rejected` can legitimately exceed `self.total_weight`, and `total_weight_rejected` becomes a stale high-water mark that is only ever cleared by `reset_rejections`, which fires solely on a full proposal-timeout retry, not in response to the specific signer's flip [6](#0-5) .

### Impact Explanation
`SignerCoordinator::get_block_status` checks the rejection-impossibility condition before the approval condition on every poll iteration: [7](#0-6) 

If stale rejection weight (from signers who have since flipped to accept) combined with fresh rejection weight crosses `total_weight - weight_threshold`, the coordinator immediately returns `NakamotoNodeError::SignersRejected`, excluding transactions and abandoning the block — even though, counting current signer intent correctly, the block may have (or be about to reach) the 70% approval threshold. This is a liveness wedge: a currently-valid, adequately-supported block can be discarded and the miner forced to re-mine, purely because of an accounting artifact rather than actual current signer disagreement. It matches the "High" impact category: the coordinator acts on a stale/incorrect aggregated weight rather than the true current signer state.

### Likelihood Explanation
This requires only a single signer (one slot) to legitimately or maliciously send a `Rejected` response and later an `Accepted` response for the same block hash — both of which are normal, sanctioned behaviors of the v0 signer protocol (re-evaluation/capitulation is a documented, expected code path, not an edge case). No majority collusion, no key compromise, and no StackerDB-sync trickery is needed — just two ordinary gossip messages from one signer.

### Recommendation
Track weight contribution per signer per block with a single source of truth (e.g., a `HashMap<u32 /*slot_id*/, Vote>` recording the signer's *current* vote and weight), and recompute `total_weight_approved`/`total_weight_rejected` by summing over that map rather than maintaining two independently-incremented running counters. When a signer's vote changes, subtract the old contribution before adding the new one, mirroring the guarantee that `verify_signer_signatures` enforces at the chainstate layer (each signer counted exactly once) [8](#0-7) .

### Proof of Concept
1. Node/coordinator waits on `get_block_status` for block `B` with `weight_threshold` = 70% of `total_weight`.
2. Signer `S` (weight `w`) sends `Rejected(B)`. `responded_signers.insert(slot_S)` succeeds → `total_weight_rejected += w`.
3. Other signers push `total_weight_rejected` close to `total_weight - weight_threshold`.
4. `S` re-evaluates (e.g. a rival block's conflict staled out) and legitimately sends `Accepted(B)`. Since `slot_S` is absent from `gathered_signatures`, `total_weight_approved += w` is applied unconditionally at [9](#0-8) ; `total_weight_rejected` still retains `w` from step 2 (never decremented).
5. On the next poll, `total_weight_rejected.saturating_add(weight_threshold) > total_weight` can now be true purely due to the retained stale `w`, causing `get_block_status` to return `SignersRejected` at [10](#0-9)  even though `S`'s current, latest vote is `Accepted`.

    /// Reset rejections for a block proposal.
    /// This is used when a block proposal times out and we need to retry it by
    /// clearing the block's rejections. Block approvals cannot be cleared
    /// because an old approval could always be used to make a block reach
    /// the approval threshold.
    pub fn reset_rejections(&self, signer_sighash: &Sha512Trunc256Sum) {
        let (lock, _cvar) = &*self.blocks;
        let mut blocks = lock.lock().expect("FATAL: failed to lock block status");
        if let Some(block) = blocks.get_mut(signer_sighash) {
            block.responded_signers.clear();
            block.total_weight_rejected = 0;

            // Add approving signers back to the responded signers set
            for (slot_id, _) in block.gathered_signatures.iter() {
                block.responded_signers.insert(*slot_id);
            }
        }
    }
