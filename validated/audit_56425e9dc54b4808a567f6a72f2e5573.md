### Title
Unprivileged cross-user response hijack via attacker-controlled `MessageId` collision in WebAPI Trigger Gateway Handler - (File: `core/services/gateway/handlers/capabilities/handler.go`)

### Summary
The Gateway's legacy WebAPI trigger handler indexes pending user callbacks solely by the client-supplied `MessageId`, with no per-sender scoping and no duplicate-ID rejection. Any unprivileged client can choose an arbitrary `MessageId` (it is copied verbatim from the JSON-RPC request `ID`), so a second unrelated request using the same ID silently overwrites the first request's saved callback, causing the DON's response to be delivered to the wrong (second) requester.

### Finding Description
`HandleLegacyUserMessage` unconditionally stores the callback in a shared map keyed only by `msg.Body.MessageId`: [3](#0-2) 

The `MessageId` used as the map key comes straight from the untrusted, attacker-controlled JSON-RPC `ID` field of the incoming request, and is set before any signature-derived sender identity is attached: [1](#0-0) 

When the DON eventually responds, `handleWebAPITriggerMessage` looks up and deletes the entry by `MessageId` alone and forwards the raw response to whichever callback is currently registered under that key — it performs no sender/requester identity check: [4](#0-3) 

Because the map assignment `h.savedCallbacks[msg.Body.MessageId] = &savedCallback{...}` has no existence check (unlike the newer v2 HTTP trigger handler, which explicitly rejects reused request IDs with `"has already been used"` — see `setupCallback`), an attacker (User B) can submit a request using the same `MessageId` as a victim's (User A) in-flight request. User A's saved callback is overwritten in the map. When the DON later returns User A's response, it is delivered to User B's callback instead — a cross-user response confusion / information disclosure and denial-of-service against User A (whose own request appears to time out or never receives its rightful response).

Contrast with the newer, more careful v2 trigger handler, which enforces uniqueness: [5](#0-4) 

### Impact Explanation
This allows any unprivileged internet-facing client to hijack the DON's response intended for another user's WebAPI trigger request handled through this legacy path, resulting in cross-user response confusion. Depending on what data the WebAPI trigger response carries (e.g., workflow trigger acknowledgements/results), this could leak response content intended for a different caller to an attacker, or cause a legitimate user's request to silently fail (their callback is displaced and never fires until timeout/prune).

### Likelihood Explanation
Likelihood is moderate: an attacker only needs to (a) know or guess a `MessageId`/JSON-RPC `ID` that a victim is about to use or is using concurrently, and (b) send a request using that same ID before the victim's response arrives. Some IDs might be predictable or reused by well-behaved clients (e.g., a UUID, sequence counter, or fixed convention on the client side), and there is no server-side mitigation (uniqueness check, or per-sender namespacing of the map key) to prevent this. This is fully reachable from an unauthenticated/unprivileged gateway client — the same trust boundary the JSON-RPC gateway is designed to serve.

### Recommendation
Namespace the `savedCallbacks` map key by both `Sender` (the signature-verified identity) and `MessageId`, similar to how `RequestCache` already scopes by `globalId{sender, id}`: [6](#0-5) 
Additionally, reject requests whose `(sender, MessageId)` pair is already in-flight, mirroring the `setupCallback` conflict check in the v2 HTTP trigger handler.

### Proof of Concept
1. Attacker (User B) observes or guesses that victim (User A) is about to submit (or has submitted) a `web_api_trigger` request to the Gateway with JSON-RPC `ID` = `"X"`.
2. Attacker submits their own `web_api_trigger` request with the same `ID = "X"` before the DON responds to User A's request. Per `HandleLegacyUserMessage`, this unconditionally overwrites `h.savedCallbacks["X"]` with the attacker's callback: [3](#0-2) 
3. When a DON node responds with `MessageId = "X"`, `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]` (now pointing to the attacker's callback) and forwards User A's response payload to the attacker: [4](#0-3) 
4. User A's original request never completes (its callback reference was silently replaced), demonstrating both response leakage to the attacker and denial-of-service for the victim.

type globalId struct {
	sender string
	id     string
}

type pendingRequest[T any] struct {
	handlers.Callback
	responseData *T
	timeoutTimer *time.Timer
	mu           sync.Mutex
}

func NewRequestCache[T any](timeout time.Duration, maxCacheSize uint32) RequestCache[T] {
	return &requestCache[T]{cache: make(map[globalId]*pendingRequest[T]), timeout: timeout, maxCacheSize: maxCacheSize}
}

func (c *requestCache[T]) NewRequest(lggr logger.Logger, request *api.Message, callback handlers.Callback, responseData *T) error {
	if request == nil {
		return errors.New("request is nil")
	}
	if responseData == nil {
		return errors.New("responseData is nil")
	}
	key := globalId{request.Body.Sender, request.Body.MessageId}
	c.mu.Lock()
	defer c.mu.Unlock()
	_, ok := c.cache[key]
	if ok {
		return errors.New("request already exists")
	}
