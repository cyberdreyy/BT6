### Title
Unlimited `type(uint256).max` approval of pool underlying to an external, upgradeable ERC4626 vault in `ProgrammableBorrower` exposes all on-hand credit-facility funds to a vault compromise - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
`ProgrammableBorrower` grants an unlimited allowance of the pool's underlying token to its configured ERC4626 `vault` at initialization and on every `setVault` call, via `_allowUnlimitedSpend`. The vault is an external, third-party dependency that may be upgradeable. If the vault implementation is ever compromised or upgraded maliciously, it can call `underlyingToken.transferFrom(programmableBorrower, attacker, amount)` and drain the contract's entire on-hand underlying balance — which, during the stop-epoch window and buffer periods, includes liquidity reserved for lender withdraw requests and repaid borrower funds.

### Finding Description
In `initialize`, the contract approves both the vault and the IdleCDO for `type(uint256).max`: [1](#0-0) 

`setVault` revokes the old vault's approval but immediately re-approves the new vault for max: [2](#0-1) 

The approval helper itself: [3](#0-2) 

The vault only ever needs to pull the exact `_assetAmount` passed to `vault.deposit` inside `_depositToVault`: [4](#0-3) 

The standing approval is unnecessary because the contract does not normally hold underlying: `onStartEpoch` deposits the full on-hand balance into the vault, and `_repay` redeposits repayments while an epoch is active. However, there are concrete windows where significant underlying sits as a plain ERC20 balance on `ProgrammableBorrower`:

- `onStopEpoch` withdraws the `shortfall` needed to cover `_amountRequired` (pending withdraw requests plus interest settlement) into the contract's own balance before `IdleCDOEpochVariant` pulls it via `transferFrom`. This is the entire epoch-end liquidity reserved for lenders.
- Buffer-period repayments (`epochAccountingActive == false`) are kept on-hand rather than redeposited (line 528-532 only records `bufferInterest`).
- The borrow shortfall path withdraws from the vault to on-hand before `safeTransfer(borrower, assets)` — a malicious vault `withdraw` can sandwich the draw.

A compromised or maliciously upgraded vault can, at any of these moments, call `transferFrom` on the underlying and take the full on-hand balance, not just the deposits it holds as shares.

### Impact Explanation
Direct theft / insolvency of credit-vault funds. The amount stealable is the full `underlyingToken.balanceOf(programmableBorrower)` at attack time. At the `onStopEpoch` window this equals the amount the IdleCDO needs to honor pending withdraw requests and settle epoch interest — draining it forces the stop/default path and permanently or temporarily freezes lender withdrawals. Unlike a vault-share loss (which is already accounted as `vaultLoss`), an allowance drain removes assets the accounting believes are on-hand, so `_currentVaultAssets()` still reports a healthy share position while cash is gone, worsening the insolvency surprise.

### Likelihood Explanation
Conditional on the external ERC4626 vault being upgradeable and its admin compromised or malicious — the same threat model as the referenced predicate-bridge report. No protocol privileged role is required; the spender is the vault contract itself. The required approval already exists from initialization with no per-transaction scoping, so a single malicious upgrade suffices, and high-value windows (stop-epoch liquidity staging) occur predictably every epoch.

### Recommendation
Approve only the exact deposit amount instead of a standing max allowance. In `_depositToVault`, call `underlyingToken.safeApprove(address(vault), 0)` then `safeApprove(address(vault), _assetAmount)` (or `safeIncreaseAllowance` to `_assetAmount`) immediately before `vault.deposit`, matching the consumed-in-one-go pattern. Keep the max approval to `idleCDO` only if the CDO is treated as a fully trusted in-protocol component; otherwise scope it to `onStopEpoch`'s `_amountRequired` as well. Optionally have `setVault` reset the old vault's allowance to 0 (already done) and document that only non-upgradeable or governance-vetted vaults may be set.

### Proof of Concept
Foundry fork-style PoC outline:

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {ProgrammableBorrower} from "contracts/strategies/idle/ProgrammableBorrower.sol";
import {IERC20Detailed} from "contracts/interfaces/IERC20Detailed.sol";

// Upgradeable-style vault: slot-0 impl pointer swapped by its admin.
contract EvilVault {
    address public asset;
    uint256 public impl; // pretend implementation slot
    constructor(address _asset) { asset = _asset; }
    // minimal IERC4626 surface used by ProgrammableBorrower
    function deposit(uint256 assets, address) external returns (uint256) {
        IERC20Detailed(asset).transferFrom(msg.sender, address(this), assets);
        return assets;
    }
    function withdraw(uint256 assets, address to, address) external returns (uint256) {
        IERC20Detailed(asset).transfer(to, assets);
        return assets;
    }
    function redeem(uint256 s, address to, address) external returns (uint256) {
        IERC20Detailed(asset).transfer(to, s);
        return s;
    }
    function balanceOf(address) external view returns (uint256) { return 0; }
    function convertToAssets(uint256 s) external pure returns (uint256) { return s; }
    // "upgraded" malicious function
    function drain(address victim, address to) external {
        IERC20Detailed t = IERC20Detailed(asset);
        t.transferFrom(victim, to, t.balanceOf(victim)); // uses the max allowance
    }
}

contract ApprovalDrainTest is Test {
    function test_maxAllowanceDrain() public {
        // setup: underlying token, idleCDO mock exposing token(), borrower PB
        // 1. Deploy ProgrammableBorrower, initialize(...) -> _allowUnlimitedSpend grants vault max uint
        // 2. Simulate onStopEpoch staging: vault.withdraw(shortfall, PB, PB) leaves
        //    e.g. 1_000_000 USDC sitting on PB before IdleCDO pulls it
        // 3. Attacker (compromised vault admin) swaps impl and calls:
        //    evilVault.drain(address(pb), attacker)
        // 4. Assert: underlying.balanceOf(pb) == 0, attacker received funds,
        //    pb vault share accounting unchanged (convertToAssets still positive),
        //    subsequent IdleCDO transferFrom of _amountRequired reverts -> default/frozen withdraws
    }
}
```

Key assertion: the stolen amount equals `underlyingToken.balanceOf(pb)` — capped only by the standing `type(uint256).max` allowance rather than by any deposit-scoped amount.
