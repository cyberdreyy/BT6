### Title
Vault secret engine path traversal via unsanitized `path.Join` in `generic`/`kv_v2` engines allows escaping the configured engine mount - (File: `helpers/vault/secret_engines/generic/engine.go`, `helpers/vault/secret_engines/kv_v2/engine.go`)

### Summary
The build-time/duplicate-registration concern is not a real attack vector: `MustRegisterFactory` registration happens once, deterministically, at package `init()` time and is not influenced by any runtime configuration or attacker input [1](#0-0) . However, the second part of the question is valid: because `generic.engine.fullPath` and `kv_v2.engine.dataPath`/`metadataPath` build Vault API paths with Go's `path.Join`, which internally calls `path.Clean` and resolves `..` segments syntactically, an attacker-influenced `SecretPath` (or `EnginePath`) containing `../` sequences can make the resolved path escape the statically configured engine mount prefix.

### Finding Description
`defaultVault.getSecretEngine` instantiates the engine with `engineFactory(v.client, engineDetails.EnginePath())` and callers then invoke `engine.Get(secretDetails.SecretPath())` / `engine.Put(...)` / `engine.Delete(...)` [2](#0-1) . Both `Engine.Path` and `Secret.Path` originate from `spec.VaultSecret`, and both are run through `vars.ExpandValue` during `expandVariables`, meaning CI/job variable expansion is applied to them before they reach the engine [3](#0-2) .

Inside `generic/engine.go`, `fullPath` does:
```
func (e *engine) fullPath(p string) string {
	return path.Join(e.path, p)
}
``` [4](#0-3) 

`kv_v2/engine.go` does the same for `dataPath`/`metadataPath`: [5](#0-4) 

Go's `path.Join` calls `path.Clean` on the joined result, and `path.Clean` resolves `..` elements lexically rather than treating the base as a fixed, un-traversable root. Concretely, `path.Join("engine-a", "../engine-b/secret")` evaluates to `"engine-b/secret"` — the `..` in the caller-supplied `p` (i.e., `SecretPath`) consumes and removes the `engine-a` mount segment entirely, and the resulting string is sent unmodified to `client.Read`/`client.Write`/`client.Delete`. No component in the chain (`defaultVault.GetField/Put/Delete`, `getSecretEngine`, or the engine implementations) validates or rejects `..` segments in `EnginePath` or `SecretPath` before path construction.

### Impact Explanation
If a pipeline's Vault secret configuration (`secrets:` block in `.gitlab-ci.yml`) embeds a job/pipeline variable into the `path` (e.g. `path: "myapp/$SOME_VAR"`), and `SOME_VAR` is influenced by data an unprivileged actor can control (branch/ref name, merge-request-triggered pipeline variables, or trigger-token custom variables), the resolved Vault path can traverse out of the intended engine mount, e.g. requesting `../other-engine/secret` yields `other-engine/secret`. Since the Vault Runner client is scoped to a single authenticated session/mount configuration but the request path is not fenced to the configured mount, this can allow reading secrets that were intended to be isolated to a different engine mount/project’s secrets scope — i.e., cross-mount secret exfiltration, exactly the scoped impact described.

### Likelihood Explanation
Exploitability depends entirely on whether a given `.gitlab-ci.yml`'s `secrets:` configuration interpolates a variable into `path`/`engine.path` that is attacker-influenceable (common patterns: using `$CI_COMMIT_REF_NAME`, `$CI_MERGE_REQUEST_*`, or custom pipeline-trigger variables). Where that pattern exists, the exploit is fully repeatable and deterministic — no timing/race conditions are needed, only crafting a variable value containing `../` sequences. There is no existing validation/sanitization layer (allowed-path checks, canonicalization enforcement, or mount-prefix confinement) anywhere in `defaultVault`, `secret_engines`, or the `generic`/`kv_v2` engines that would block it.

### Recommendation
After computing the joined path in `fullPath` (`generic/engine.go`) and `dataPath`/`metadataPath` (`kv_v2/engine.go`), verify the cleaned result still has the configured `e.path` as a strict path prefix (e.g., compare `path.Clean(e.path)` against the leading segment of `path.Clean(joined)`, or reject any input segment containing `..` before joining). Reject/­error out if the resolved path would escape the configured mount rather than silently sending the traversed path to Vault.

### Proof of Concept
```go
// helpers/vault/secret_engines/generic/engine_traversal_test.go
func TestEngine_Get_PathTraversalEscapesMount(t *testing.T) {
    enginePath := "engine-a/"
    maliciousSecretPath := "../engine-b/secret"

    clientMock := vault.NewMockClient(t)
    // Assert on the actual path sent to Vault client
    clientMock.On("Read", mock.MatchedBy(func(p string) bool {
        return !strings.HasPrefix(p, "engine-a/")
    })).Return(nil, assert.AnError).Once()

    e := engineForName("generic")(clientMock, enginePath)
    _, _ = e.Get(maliciousSecretPath)

    // FAILS today: path.Join("engine-a/", "../engine-b/secret") == "engine-b/secret",
    // i.e. request path escapes the "engine-a" mount entirely.
    clientMock.AssertExpectations(t)
}
```
Expected: the fix should make the resolved path stay prefixed with `engine-a/` (or return an error), whereas the current implementation sends `engine-b/secret` to `client.Read`, confirming the mount-escape.

func (v *defaultVault) GetField(engineDetails Engine, secretDetails Secret) (interface{}, error) {
	engine, err := v.getSecretEngine(engineDetails)
	if err != nil {
		return nil, err
	}

	secret, err := engine.Get(secretDetails.SecretPath())
	if err != nil {
		return nil, fmt.Errorf("reading secret: %w", err)
	}

	field := secretDetails.SecretField()
	for key, data := range secret {
		if key != field {
			continue
		}

		return data, nil
	}

	return nil, nil
}

		return nil, fmt.Errorf("requesting SecretEngine factory: %w", err)
	}

	return engine, nil
}

	dataWrapper := map[string]interface{}{
		"data": data,
	}

	_, err := e.client.Write(e.dataPath(path), dataWrapper)
	if err != nil {
		return fmt.Errorf("writing to Vault: %w", err)
	}

	return nil
}

func (e *engine) Delete(path string) error {
	err := e.client.Delete(e.metadataPath(path))
	if err != nil {
		return fmt.Errorf("deleting from Vault: %w", err)
	}

	return nil
}

func (e *engine) metadataPath(p string) string {
