### Title
Default finalization ignores instant-withdraw receipts from prior epochs, permanently freezing affected claims - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
Analogous to the indexer bug where `getSpentUnbondingTx` returns only the first spent unbonding output, the default-recovery accounting in `IdleCreditVault` looks up instant-withdraw claim basis only for the *current* epoch key (`instantWithdrawClaimsByEpoch[epochNumber]`). Instant receipts are tracked per request epoch, but the unfunded remainder `pendingInstantWithdraws` is aggregate. If an instant request remains partially unfunded across a `stopEpoch` (which increments `epochNumber`), its basis stays under the old epoch key and is silently dropped from `defaultPendingClaimBasis`, `_defaultPrefundedInstantReserve`, and `_claimDefaultedInstantWithdrawRequest`. The recovery price is computed on a smaller basis than the real claim set, and the stale-epoch receipt can never be claimed.

### Finding Description
Instant withdraw requests record basis in two places: aggregate `pendingInstantWithdraws`/`instantWithdrawsRequests[user]` and per-epoch `instantWithdrawsRequestsByEpoch[user][epoch]` / `instantWithdrawClaimsByEpoch[epoch]` (lines 366-374). Funding is partial-friendly: `collectInstantWithdrawFunds(_amount)` decrements `pendingInstantWithdraws` by whatever the CDO collects, but never touches the per-epoch buckets (lines 398-403). `epochNumber` then increments in `deposit()` during the running-epoch path (line 610), so an unfunded instant receipt can survive under epoch key `N` while the vault is in epoch `N+1`.

At borrower default, `finalizeDefaultRecovery` → `defaultPendingClaimBasis` reads only `instantWithdrawClaimsByEpoch[epochNumber]` (lines 644-649), and `_defaultPrefundedInstantReserve` does the same (lines 716-723). The old-epoch basis is excluded from `totalBasis`, so `recoveryPrice` is inflated and `defaultRecoveryReserve` is undersized relative to outstanding receipts. Later, `claimInstantWithdrawRequest` calls `_claimDefaultedInstantWithdrawRequest`, which clears only `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` (lines 842-856), leaving the user's old-epoch basis in `instantWithdrawsRequests[user]`. The funded-claim fallback then pays it at par via `_transferFundedClaim`, which either (a) spends strategy balance that was not part of the recovery reserve — an unbacked payout diluting other claimants — or (b) reverts once only `defaultRecoveryReserve` remains (lines 897-907), permanently freezing the receipt.

### Impact Explanation
Two failure modes from the same root cause:

1. **Recovery reserve dilution / insolvency**: `totalBasis` omits stale-epoch instant claims, so `defaultRecoveryPrice` is too high and the fixed `defaultRecoveryReserve` is overpaid to earlier claimants; later legitimate claimants (including the stale-epoch receipt holder) cannot be paid.
2. **Permanent freezing**: the victim's `instantWithdrawsRequests[user]` balance can only be paid through `_transferFundedClaim`, which reverts if it would touch `defaultRecoveryReserve` (lines 899-905). The receipt tokens stay minted but unclaimable.

Broken invariant: one receipt one payout — every outstanding claim must be included in the recovery basis.

### Likelihood Explanation
Reachable by unprivileged lenders in the normal instant-withdraw mode whenever a `stopEpoch` collects less than the full `pendingInstantWithdraws` (partial borrower repayment / insufficient liquidity at epoch stop). No privileged misbehavior is required: honest manager calls `stopEpoch`/`stopEpochWithDuration`, the CDO collects a partial amount, `epochNumber` advances on the next deposit, and a later borrower default freezes the stranded receipt. Likelihood is moderate: it requires a partial instant funding followed by a default in a subsequent epoch.

### Recommendation
Make the instant-claim basis epoch-agnostic, matching the aggregate counter it backs:

- In `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve`, derive instant basis from the aggregate `pendingInstantWithdraws` plus any already-funded remainder rather than `instantWithdrawClaimsByEpoch[epochNumber]` alone, or track a separate aggregate `instantWithdrawClaimsTotal` alongside the per-epoch map.
- In `_claimDefaultedInstantWithdrawRequest`, clear the user's entire unfunded instant basis (`instantWithdrawsRequests[user]` net of already-funded amounts), not only the `defaultRecoveryEpoch` entry — i.e., process *all* matching receipts, not just the first/last epoch.

### Proof of Concept
A Foundry fork PoC on `IdleCDOEpochVariant` + `IdleCreditVault` (mirroring `test/foundry/IdleCDOEpochQueue.t.sol` helpers):

```solidity
function testStaleEpochInstantClaimExcludedFromDefault() external {
    // epoch N running: lender requests instant withdraw
    _depositWithUser(VICTIM, 100e18);
    vm.prank(manager); cdoEpoch.startEpoch();
    vm.prank(VICTIM); cdoEpoch.requestInstantWithdraw(100e18, address(tranche));

    // stopEpoch: borrower repays only part; CDO collects partial instant funding
    // so pendingInstantWithdraws > 0 while instantWithdrawClaimsByEpoch[N] keeps basis
    _stopCurrentEpochPartialInstantFunding(/* partial amount */);
    // deposit during running epoch bumps epochNumber to N+1
    assertGt(strategy.epochNumber(), 0);
    assertGt(strategy.pendingInstantWithdraws(), 0);
    assertEq(strategy.instantWithdrawClaimsByEpoch(strategy.epochNumber()), 0);

    // borrower defaults in epoch N+1; manager/owner finalize recovery
    _triggerBorrowerDefault();
    _finalizeDefaultRecovery();

    uint256 basis = strategy.defaultPendingClaimBasis();
    // BUG: basis excludes VICTIM's unfunded epoch-N instant receipt
    assertLt(basis, expectedBasisIncludingInstant);

    // VICTIM's claim either reverts against the reserve guard or pays at par
    // from unreserved balance; the receipt is never correctly haircut-settled
    vm.prank(VICTIM);
    vm.expectRevert(NotAllowed.selector); // or observe reserve drained past price
    cdoEpoch.claimInstantWithdrawRequest();
}
```

Note on verification limits: I confirmed the per-epoch vs. aggregate mismatch in `contracts/strategies/idle/IdleCreditVault.sol` (lines 366-374, 398-403, 610, 644-649, 716-723, 842-856, 897-907), but I did not fully trace `IdleCDOEpochVariant.getInstantWithdrawFunds`/`stopEpoch` to confirm a *partial* `collectInstantWithdrawFunds` call is reachable in an honest epoch stop. If the CDO always collects the full `pendingInstantWithdraws` or reverts when it cannot, the stale-epoch state is unreachable and this finding does not hold — that call path should be verified before proceeding.
