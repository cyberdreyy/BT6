### Title
Web API Trigger message freshness check has no upper bound, allowing indefinite replay of stale signed trigger messages to cause unauthorized/duplicate workflow (job) executions - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The legacy Web API Trigger handler's "staleness" check, meant to reject old/expired trigger messages, only enforces a lower bound on `payload.Timestamp`. It never validates an upper bound (i.e., that the timestamp is not in the future), and the handler performs no message-ID/nonce based replay protection. An attacker who once obtains a validly signed `web_api_trigger` message can set (or keep) a timestamp far in the future and resubmit that exact signed message to the gateway at any later point in time — the freshness check will always pass, and the workflow will be re-triggered with stale/duplicated data. This is the same root-cause class as the referenced report: a missing "deadline"/expiry enforcement mechanism that lets requests execute long after their originally-intended validity window, using conditions/data that are no longer current.

### Finding Description
`HandleLegacyUserMessage` is the gateway-side, internet-facing entry point that processes user-submitted (unprivileged, signed) `web_api_trigger` messages and forwards them to workflow DON nodes to trigger execution: [1](#0-0) 

The only freshness/deadline check performed is:
```go
if uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp) {
    // reject as "stale message"
}
```
This only rejects messages whose `payload.Timestamp` is *too old*. It never checks that `payload.Timestamp` is not unreasonably far in the *future*. Because the timestamp is part of the user-supplied, signed `TriggerRequestPayload`, an attacker can set it to an arbitrarily large future value when first crafting/signing the message. From that point on, the check `now - MaxAllowedMessageAgeSec > timestamp` will never be true (since `timestamp` is always ahead of `now`), so the "stale message" rejection can never trigger for that message, no matter how long the attacker waits to submit or resubmit it.

Additionally, the message is only tracked ephemerally in `savedCallbacks` (keyed by `MessageId`, and deleted as soon as a node responds) purely to route the response back to the caller: [2](#0-1) 

There is no persistent replay-protection structure (unlike the JWT `jti` replay caches used elsewhere, e.g. `jwtReplayCache` in the v2 HTTP trigger path or `RequestReplayGuard` in the Vault capability) for this legacy code path, so the exact same signed message (with a manipulated future timestamp) can be resubmitted an unlimited number of times, each time being treated as "fresh" and dispatched to all DON members: [3](#0-2) 

This mirrors the reported bug class exactly: the mechanism that is supposed to bound the validity window of a signed request (a "deadline") is incomplete/asymmetric — it only bounds one side (age) and not the other (future-dating), enabling execution under conditions the original signer no longer controls or intends.

### Impact Explanation
An attacker (or the legitimate signer acting maliciously, or anyone who captures a previously broadcast signed trigger message) can craft or preserve a `web_api_trigger` message with a future timestamp and replay it at will, indefinitely, to force repeated/duplicate workflow executions long after the intended trigger window. Because `MethodWebAPITrigger` messages initiate real workflow runs on the DON (job execution), this can lead to unauthorized or duplicated job runs using stale trigger data — directly analogous to the "swap executes with stale/unintended state due to missing deadline" impact described in the report.

### Likelihood Explanation
Low-to-moderate: it requires the attacker to have (or have captured) one previously valid signed message, and to know or predict that the future-timestamp bypass exists. However, no special network position or node compromise is required — a normal, unprivileged web API trigger client can construct such a message directly, since the timestamp field is entirely user-controlled and only checked as a lower bound.

### Recommendation
Add an upper-bound check on `payload.Timestamp` (reject messages whose timestamp is more than a small tolerance ahead of `time.Now()`), and add persistent message-ID/nonce-based replay protection to the legacy Web API Trigger handling path (similar to the `jwtReplayCache`/`RequestReplayGuard` patterns already used elsewhere in the gateway), so that a given signed trigger message can only be accepted once within its valid window.

### Proof of Concept
1. Client signs a `web_api_trigger` `api.Message` with `TriggerRequestPayload.Timestamp` set to, e.g., `time.Now().Unix() + 10_000_000` (far future) as shown in the trigger construction pattern used by `core/scripts/gateway/web_api_trigger/invoke_trigger.go`.
2. Submit this message to the gateway; `HandleLegacyUserMessage`'s check `now - MaxAllowedMessageAgeSec > timestamp` is false (since `timestamp` is in the future), so it passes the "stale message" check and is dispatched to the DON, as shown in [4](#0-3) .
3. Store the exact same signed message and resubmit it again at an arbitrary later time (hours, days, or months later) — the same check still passes because no upper-bound or replay tracking exists, causing the workflow to be re-triggered with the original (now stale) payload data.
