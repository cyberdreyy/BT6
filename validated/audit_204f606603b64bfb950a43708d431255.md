### Title
Vote account commission (fee) can be unilaterally front-run to the maximum rate to steal stake/reward accrual from delegators - (File: `programs/vote/src/vote_state/mod.rs`)

### Summary
The Agave vote program lets a vote account's `authorized_withdrawer` unilaterally change the validator's commission rate (the "fee" that determines how inflation/block-revenue rewards are split between the validator and its delegators). This is the direct on-chain analog of the NFTX `NFTXVaultUpgradeable` bug: an untrusted, non-consensus-critical "pool manager" (here, the vote account's withdraw authority) can front-run a fee parameter to its maximum value immediately before value accrues to other users (here, delegators/stakers), with no timelock protecting depositors who already committed funds under a lower fee.

### Finding Description
`update_commission` (the legacy `u8` commission path) only restricts *increases* to commission, and only enforces the epoch-boundary rule when `disable_commission_update_rule` is `false`: [1](#0-0) 

Once the `delay_commission_updates` feature is active, `disable_commission_update_rule` is `true`, which makes `enforce_commission_update_rule` `false` unconditionally — i.e. the epoch-boundary check (`is_commission_update_allowed`) is skipped entirely for this path: [2](#0-1) 

The newer basis-points commission path, `update_commission_bps` (SIMD-0291), is explicit in its own comment that there is **no rate-limiting rule at all**: [3](#0-2) 

In both cases, the only gate is a single-signer check (`verify_authorized_signer(vote_state.authorized_withdrawer(), signers)`), not a timelocked or epoch-delayed change. This mirrors the NFTX report precisely: a single "manager" key can change a fee to its maximum value (`1 ether` in NFTX; `u8::MAX` / max bps here) in the same transaction/slot in which it benefits from doing so, harming counterparties (LP depositors in NFTX; delegators/stakers here) who have already committed value under the old fee assumption.

### Impact Explanation
Delegators who stake to a vote account do so expecting rewards to be split at the commission rate they observed. Because commission changes take effect immediately (no delay enforced in the reachable `update_commission`/`update_commission_bps` code paths once the feature-gated rule is bypassed, or when the rule is not enforced for decreases at all), a withdraw authority can raise commission to 100% (or the bps maximum) right before an epoch-boundary reward calculation snapshot is taken, capturing the entire epoch's stake reward that would otherwise flow to delegators, then lower it back afterward. This is a value-extraction vector against unprivileged stakers analogous to the NFTX pool-manager fee front-run, though — as in the original report — the practical severity depends on whether reward-snapshot timing (in `runtime/src/bank/partitioned_epoch_rewards/calculation.rs` / `runtime/src/inflation_rewards/mod.rs`) actually reads the withdrawer-set commission at the moment of accrual with no separate delayed/snapshotted value. I was not able to fully confirm within the available searches whether reward computation reads a delayed/pending commission field distinct from the live value returned by `vote_state.commission()`; this is the primary open uncertainty in this analysis.

### Likelihood Explanation
Likelihood is comparable to the original NFTX finding: low-to-medium. It requires the withdraw authority itself (analogous to the "manager" in the NFTX report) to be the attacker, and depends on precise timing of the update transaction relative to epoch-boundary reward calculation. Unlike the original finding, this does not require frontrunning another user's specific transaction — the withdraw authority alone controls both the timing and the commission update, making it arguably easier to execute than the NFTX scenario (no need to race a victim's transaction, only to time relative to the epoch boundary).

### Recommendation
Enforce a mandatory delay for all commission-changing instructions (`UpdateCommission`, `UpdateCommissionBps`) so that a newly set commission only takes effect starting in a future epoch, and ensure the reward-calculation code path (`runtime/src/inflation_rewards`, `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`) reads a commission value that was locked in prior to the epoch being paid out, not the value live at computation time. If SIMD-0249 was intended to already guarantee this, the `update_commission_bps` docstring/comment ("No commission update rule, per SIMD-0249 and SIMD-0291") and the unconditional bypass in `update_commission` when `disable_commission_update_rule` is true should be reconciled with where/how the delay is actually enforced, and that enforcement point should be verified against the reward-calculation code, not merely against slot/epoch-schedule checks at update time.

### Proof of Concept
1. A withdraw authority holds a vote account with commission set low (e.g. 0%) to attract delegators.
2. Delegators stake to the vote account, expecting rewards under the advertised commission.
3. Near an epoch boundary, the withdraw authority submits `VoteInstruction::UpdateCommission(255)` (or `UpdateCommissionBps` with `commission_bps = u16::MAX` equivalent) signed only by itself — see `update_commission`/`update_commission_bps` in [4](#0-3) .
4. Because the epoch-boundary rule is disabled once `delay_commission_updates` is active for `UpdateCommission`, and `update_commission_bps` has no rule at all, the change applies immediately with no signer other than the withdraw authority and no waiting period.
5. If reward computation reads the live commission at the accrual/snapshot point, delegator rewards for the current epoch are redirected to the validator, after which the withdraw authority can lower commission back to attract further deposits — mirroring the NFTX manager's ability to spike the entry fee to 100% and capture depositor value.

/// Update the vote account's commission
pub fn update_commission<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission: u8,
    signers: &HashSet<Pubkey, S>,
    epoch_schedule: &EpochSchedule,
    clock: &Clock,
    disable_commission_update_rule: bool,
) -> Result<(), InstructionError> {
    let vote_state_result = get_vote_state_handler_checked(vote_account, target_version);
    let enforce_commission_update_rule = !disable_commission_update_rule
        && match vote_state_result.as_ref() {
            Ok(decoded_vote_state) => commission > decoded_vote_state.commission(),
            Err(_) => true,
        };

    if enforce_commission_update_rule && !is_commission_update_allowed(clock.slot, epoch_schedule) {
        return Err(VoteError::CommissionUpdateTooLate.into());
    }

    let mut vote_state = vote_state_result?;

    // current authorized withdrawer must say "yay"
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    vote_state.set_commission(commission);

    vote_state.set_vote_account_state(vote_account)
}

/// Update the vote account's commission in basis points (SIMD-0291, SIMD-0123).
pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}
