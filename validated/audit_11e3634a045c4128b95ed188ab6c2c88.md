Based on my analysis of `staking-pool/src/internal.rs`, this is a confirmed vulnerability.

### Title
Unstake resets `unstaked_available_epoch_height` for the entire pooled unstaked balance, re-freezing already-matured funds - (File: staking-pool/src/internal.rs)

### Summary
`inner_unstake` unconditionally overwrites `account.unstaked_available_epoch_height` on every call, even when the added `receive_amount` is dust. Because the `Account` struct tracks only a single aggregate `unstaked` balance and a single `unstaked_available_epoch_height` (not per-unstake-event maturity), a small follow-up unstake resets the unlock clock for the entire existing (and possibly already-matured/withdrawable) unstaked balance.

### Finding Description
The broken binding is: `withdrawable(account) == withdrawable_before(account)` after any call to `unstake`/`unstake_all` that does not change the withdrawability of previously matured funds, i.e., a new unstake operation should never retroactively delay withdrawal of an amount that was already unlocked.

In `inner_unstake` [1](#0-0) , the code computes `receive_amount` for the newly requested `amount`, adds it to `account.unstaked`, and then does:
```
account.unstaked_available_epoch_height = env::epoch_height() + NUM_EPOCHS_TO_UNLOCK;
``` [2](#0-1) 

This single field applies to the whole `account.unstaked` balance, not just the newly unstaked increment. `internal_withdraw` checks only this single timestamp against the *entire* `account.unstaked` amount being withdrawn:
```
assert!(
    account.unstaked_available_epoch_height <= env::epoch_height(),
    "The unstaked balance is not yet available due to unstaking delay"
);
``` [3](#0-2) 

There is no per-unstake-event bucket or "already matured" marker; `Account` only stores one aggregate `unstaked` value and one `unstaked_available_epoch_height`. Exploit flow: an attacker (or an ordinary delegator, even against themselves — but the same mechanism trivially harms any account that unstakes twice) unstakes an amount and waits `NUM_EPOCHS_TO_UNLOCK` epochs so the balance matures and becomes withdrawable. Immediately after a reward epoch is folded in via `internal_ping` (called automatically before every action) — or at any time before withdrawing — the attacker (predecessor account) calls `unstake(1)` (1 yocto/dust). This routes through `inner_unstake`, which recomputes `unstaked_available_epoch_height = env::epoch_height() + NUM_EPOCHS_TO_UNLOCK` for the account, clobbering the already-elapsed unlock time and pushing the *entire* existing matured `unstaked` balance's availability forward by `NUM_EPOCHS_TO_UNLOCK` more epochs. None of the existing guards (`assert_owner`, `assert_self`, `is_promise_success`, the U256 rounding checks, or `internal_ping`'s balance assert) address this because the flaw is purely in how `unstaked_available_epoch_height` is recomputed as a single scalar tied to the whole balance rather than per-withdrawal-tranche.

Note: this affects the account's own funds under its own control (self-inflicted or accidental), and any account can trigger it on itself with a simple sequence of calls; it does not require an "attacker" targeting a victim's private state because `unstake` operates on `env::predecessor_account_id()`'s own account — the described "attacker" scenario in the question is really describing a self-inflicted freeze pattern reachable by any unprivileged caller acting on their own account (or possibly by front-running their own withdraw with another unstake call).

### Impact Explanation
Funds that were already unlocked and withdrawable become temporarily frozen for an additional `NUM_EPOCHS_TO_UNLOCK` epochs (at least 4 epochs per the near protocol standard staking pool unbonding period), matching the "High - funds frozen for at least one epoch but recoverable" category. No funds leave the contract or are permanently lost — the freeze is recoverable once the new unlock period elapses, and no third party gains from it. The repeatability is limited to the account that performs the follow-up unstake and only affects its own balance, since `unstaked_available_epoch_height` is stored per-account in `self.accounts` map, not globally.

### Likelihood Explanation
This requires only calling `unstake` (or `unstake_all`) twice, with any amount for the second call, while a prior unstaked amount has already matured. This is a normal user-facing action with near-zero attacker cost (a fraction of a yoctoNEAR is sufficient), fully reachable through the public `unstake` entrypoint by any delegator, and easily reproducible in a unit test.

### Recommendation
Track per-tranche unlock times (e.g., a queue or the "epoch of latest unstake" combined with per-tranche amounts) instead of a single aggregate `unstaked_available_epoch_height`, or only extend the unlock height for the *newly added* `receive_amount`, keeping previously matured balances immediately withdrawable — mirroring the eventual fix adopted in the actual NEAR core-contracts staking pool (tracking last unstake action and only resetting the clock if the account had no previously-matured balance, or splitting the balance into "available" vs "pending" buckets).

### Proof of Concept
```rust
// staking-pool/src/tests/... (illustrative)
#[test]
fn test_unstake_resets_maturity_of_already_withdrawable_balance() {
    let mut contract = new_contract(...);
    // 1. Stake and unstake `amount_a` at epoch E.
    contract.unstake(amount_a.into());
    // account.unstaked_available_epoch_height == E + NUM_EPOCHS_TO_UNLOCK

    // 2. Advance epoch height by NUM_EPOCHS_TO_UNLOCK so amount_a matures.
    testing_env!(context_at_epoch(E + NUM_EPOCHS_TO_UNLOCK));
    let can_withdraw_before = contract.internal_get_account(&account_id).unstaked_available_epoch_height
        <= env::epoch_height();
    assert!(can_withdraw_before); // matured, withdrawable

    // 3. Attacker unstakes a dust amount (1 yocto) on the SAME account.
    contract.unstake(1.into());

    // 4. Assert the binding is now broken: previously matured balance is frozen again.
    let can_withdraw_after = contract.internal_get_account(&account_id).unstaked_available_epoch_height
        <= env::epoch_height();
    assert!(!can_withdraw_after); // BUG: withdrawability regressed for already-matured funds
}
```

    pub(crate) fn inner_unstake(&mut self, amount: u128) {
        assert!(amount > 0, "Unstaking amount should be positive");

        let account_id = env::predecessor_account_id();
        let mut account = self.internal_get_account(&account_id);

        assert!(
            self.total_staked_balance > 0,
            "The contract doesn't have staked balance"
        );
        // Calculate the number of shares required to unstake the given amount.
        // NOTE: The number of shares the account will pay is rounded up.
        let num_shares = self.num_shares_from_staked_amount_rounded_up(amount);
        assert!(
            num_shares > 0,
            "Invariant violation. The calculated number of \"stake\" shares for unstaking should be positive"
        );
        assert!(
            account.stake_shares >= num_shares,
            "Not enough staked balance to unstake"
        );

        // Calculating the amount of tokens the account will receive by unstaking the corresponding
        // number of "stake" shares, rounding up.
        let receive_amount = self.staked_amount_from_num_shares_rounded_up(num_shares);
        assert!(
            receive_amount > 0,
            "Invariant violation. Calculated staked amount must be positive, because \"stake\" share price should be at least 1"
        );

        account.stake_shares -= num_shares;
        account.unstaked += receive_amount;
        account.unstaked_available_epoch_height = env::epoch_height() + NUM_EPOCHS_TO_UNLOCK;
        self.internal_save_account(&account_id, &account);
