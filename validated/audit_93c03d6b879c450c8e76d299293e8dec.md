### Title
Unauthenticated front-running of `InitializeNonceAccount` allows attacker to seize authority over a victim's nonce account and drain its funds - (File: `programs/system/src/system_instruction.rs`)

### Summary
The Uniswap v4 report describes a class of bug where a stateful "initialize" instruction can be front-run by anyone because the parameter that establishes control/state (here, `sqrtPriceX96`) is not tied to any privileged signer, allowing an attacker to set that critical parameter before the legitimate actor's own initialization/first-liquidity transaction lands, and then extract value. The Agave System Program's nonce-account initialization path has the same structural weakness: `initialize_nonce_account` sets the nonce authority from unauthenticated instruction data with no signature check binding it to the account's creator.

### Finding Description
`initialize_nonce_account` in [1](#0-0)  only verifies that the target account `is_writable()` and that its current state is `State::Uninitialized`; it does not require any signer (neither the account's own key, nor any pre-agreed authority) to authorize the transition into `State::Initialized(data)`, where `data.authority` is taken directly and unauthenticated from the `nonce_authority` argument supplied in the instruction: [2](#0-1) 

The dispatcher in `system_processor.rs` similarly does not add any signer constraint for this instruction beyond what `initialize_nonce_account` itself checks: [3](#0-2) 

In normal usage the CLI/SDK bundles `CreateAccount` + `InitializeNonceAccount` into one atomic message (`create_nonce_account`), as seen in `cli/src/nonce.rs` [4](#0-3) . However, nothing in the protocol enforces this atomicity. If a funding/creation transaction (`CreateAccount` allocating the nonce-sized, system-owned account and funding it) is submitted separately from the `InitializeNonceAccount` call — which is a supported and even documented pattern (see the seeded/derived-address variants and the two-instruction test flows in `svm/tests/integration_test.rs`, e.g. lines 1881-1893) — an attacker who observes the pending `CreateAccount` transaction can race their own `InitializeNonceAccount` instruction against the account before the legitimate initializer's transaction lands. Because `initialize_nonce_account` accepts any `nonce_authority` pubkey without requiring a signature tying it to the creator, the attacker can set themselves as `data.authority`.

Once the account is `Initialized` with the attacker's key as authority, the attacker fully controls it via `authorize_nonce_account`/`withdraw_nonce_account`, both of which correctly check `signers.contains(&data.authority)` [5](#0-4)  — but that check is meaningless once the authority was itself set by the attacker. The victim's later, legitimate `InitializeNonceAccount` call will simply fail with `InvalidAccountData` because the account is already `Initialized` [6](#0-5) , and the attacker can then withdraw the full balance funded by the victim via `withdraw_nonce_account`.

This mirrors the reported bug class precisely: a state-defining parameter (`sqrtPriceX96` in Uniswap / `nonce_authority` in Agave) is set by whichever transaction lands first on the "initialize" call, with no cryptographic binding to the entity that funded/created the underlying object, enabling a front-runner to seize control and drain value contributed by the legitimate party.

### Impact Explanation
An attacker able to observe pending transactions (via mempool/QUIC ingest visibility, RPC `sendTransaction`/`simulateTransaction` polling, or by racing during multi-instruction/multi-transaction account setup flows) can hijack a freshly-created, not-yet-initialized nonce account and steal all lamports funded into it via `WithdrawNonceAccount`. This is a concrete unauthorized fund transfer at the transaction-processing/builtin-program layer, matching the "unauthorized fund mutation" acceptance criterion.

### Likelihood Explanation
Exploitation requires: (1) a `CreateAccount` (or `CreateAccountWithSeed`) call establishing a nonce-account-shaped account is submitted separately from its `InitializeNonceAccount` call, and (2) the attacker can front-run the initialize call before the legitimate one is processed. Because the default SDK/CLI path (`create_nonce_account`) bundles both instructions atomically, exploitation requires callers (custodians, exchanges, smart wallets, or programs building nonce accounts across separate transactions) to deviate from that pattern — which does happen in practice for programmatic/relayer flows that create an account first and defer initialization. This makes the likelihood moderate rather than trivial, but the root-cause absence of any signer check in `initialize_nonce_account` is a genuine, reachable gap.

### Recommendation
Require that `initialize_nonce_account` be authorized by a signer meaningfully tied to the account (e.g., require the account's own key to be a signer, analogous to `CreateAccount`'s requirement that the new account sign), or require a companion instruction/CPI-level atomicity guarantee so initialization cannot be separated from account funding. At minimum, document prominently (as the Uniswap team ultimately did) that `InitializeNonceAccount` must always be submitted atomically with the account-creation instruction in the same transaction, and that any protocol splitting these into separate transactions is vulnerable to authority hijacking.

### Proof of Concept
1. Victim submits a transaction: `SystemInstruction::CreateAccount { lamports, space: State::size(), owner: system_program::id() }` funding a new keypair `N` sized for nonce state, intending to follow up with `InitializeNonceAccount(victim_authority)` in a later transaction.
2. Attacker observes this transaction (e.g., via QUIC ingest/mempool visibility or RPC) before the victim's follow-up `InitializeNonceAccount` transaction lands.
3. Attacker submits `SystemInstruction::InitializeNonceAccount(attacker_pubkey)` targeting account `N` (no signature over `N`'s keypair is required — only `N.is_writable()` and `State::Uninitialized` are checked per `programs/system/src/system_instruction.rs:163-211`), which succeeds and sets `data.authority = attacker_pubkey`.
4. Victim's later `InitializeNonceAccount(victim_authority)` transaction fails with `InstructionError::InvalidAccountData` since the account is already `Initialized`.
5. Attacker calls `SystemInstruction::WithdrawNonceAccount(full_balance)` signed by `attacker_pubkey`, which passes the `check_signer(&data.authority)` check in `withdraw_nonce_account` [7](#0-6)  and drains all lamports the victim funded into `N`.

pub(crate) fn withdraw_nonce_account(
    from_account_index: IndexOfAccount,
    lamports: u64,
    to_account_index: IndexOfAccount,
    rent: &Rent,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    let mut from = instruction_context.try_borrow_instruction_account(from_account_index)?;
    if !from.is_writable() {
        ic_msg!(
            invoke_context,
            "Withdraw nonce account: Account {} must be writeable",
            from.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }

    let check_signer = |signer: &Pubkey| {
        if !signers.contains(signer) {
            ic_msg!(
                invoke_context,
                "Withdraw nonce account: Account {} must sign",
                signer
            );
            return Err(InstructionError::MissingRequiredSignature);
        }
        Ok(())
    };

    let state: Versions = from.get_state()?;
    match state.state() {
        State::Uninitialized => {
            if lamports > from.get_lamports() {
                ic_msg!(
                    invoke_context,
                    "Withdraw nonce account: insufficient lamports {}, need {}",
                    from.get_lamports(),
                    lamports,
                );
                return Err(InstructionError::InsufficientFunds);
            }
            check_signer(from.get_key())?;
        }
        State::Initialized(data) => {
            if lamports == from.get_lamports() {
                let durable_nonce =
                    DurableNonce::from_blockhash(&invoke_context.environment_config.blockhash);
                if data.durable_nonce == durable_nonce {
                    ic_msg!(
                        invoke_context,
                        "Withdraw nonce account: nonce can only advance once per slot"
                    );
                    return Err(SystemError::NonceBlockhashNotExpired.into());
                }
                check_signer(&data.authority)?;
                from.set_state(&Versions::new(State::Uninitialized))?;
            } else {
                let min_balance = rent.minimum_balance(from.get_data().len());
                let amount = checked_add(lamports, min_balance)?;
                if amount > from.get_lamports() {
                    ic_msg!(
                        invoke_context,
                        "Withdraw nonce account: insufficient lamports {}, need {}",
                        from.get_lamports(),
                        amount,
                    );
                    return Err(InstructionError::InsufficientFunds);
                }
                check_signer(&data.authority)?;
            }
        }
    };

    from.checked_sub_lamports(lamports)?;
    drop(from);
    let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
    to.checked_add_lamports(lamports)?;

    Ok(())
}

pub(crate) fn initialize_nonce_account(
    account: &mut BorrowedInstructionAccount,
    nonce_authority: &Pubkey,
    rent: &Rent,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    if !account.is_writable() {
        ic_msg!(
            invoke_context,
            "Initialize nonce account: Account {} must be writeable",
            account.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }

    match account.get_state::<Versions>()?.state() {
        State::Uninitialized => {
            let min_balance = rent.minimum_balance(account.get_data().len());
            if account.get_lamports() < min_balance {
                ic_msg!(
                    invoke_context,
                    "Initialize nonce account: insufficient lamports {}, need {}",
                    account.get_lamports(),
                    min_balance
                );
                return Err(InstructionError::InsufficientFunds);
            }
            let durable_nonce =
                DurableNonce::from_blockhash(&invoke_context.environment_config.blockhash);
            let data = nonce::state::Data::new(
                *nonce_authority,
                durable_nonce,
                invoke_context
                    .environment_config
                    .blockhash_lamports_per_signature,
            );
            let state = State::Initialized(data);
            account.set_state(&Versions::new(state))
        }
        State::Initialized(_) => {
            ic_msg!(
                invoke_context,
                "Initialize nonce account: Account {} state is invalid",
                account.get_key()
            );
            Err(InstructionError::InvalidAccountData)
        }
    }
}
