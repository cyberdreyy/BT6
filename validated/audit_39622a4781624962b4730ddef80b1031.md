Based on the evidence gathered, I found a genuine structural analog to the reported bug class (a lookup that ignores part of the intended matching key — here `reward_cycle` — analogous to `nftables` ignoring destination IP and matching on port alone).

### Title
SignerDb::block_lookup ignores `reward_cycle`, letting a stale/cross-cycle BlockInfo row satisfy checks meant for the current reward cycle - ([File: stacks-signer/src/signerdb.rs])

### Summary
The `blocks` table's primary key is `(reward_cycle, signer_signature_hash)` [1](#0-0) , meaning the same `signer_signature_hash` can legitimately have multiple rows differing only by `reward_cycle` (e.g. when a block's reward-cycle classification shifts across a boundary and `insert_block`'s `INSERT OR REPLACE` creates a new row instead of replacing, since the full PK didn't match). `SignerDb::block_lookup` — the low-level accessor — queries only by `signer_signature_hash`, dropping `reward_cycle` from the match entirely: [2](#0-1) 

### Finding Description
The codebase itself acknowledges that `reward_cycle` scoping is required for correctness: `Signer::block_lookup_by_reward_cycle` exists specifically to wrap `block_lookup` and discard results whose `reward_cycle` doesn't equal `self.reward_cycle`: [3](#0-2) 
This shows the codebase's own equality key for "is this block info valid in my current context" is `(reward_cycle, signer_signature_hash)`, not `signer_signature_hash` alone — exactly the "destination IP + port" vs "port only" distinction in the CNI advisory. However, the raw `block_lookup` is called directly (bypassing the reward-cycle guard) in multiple places in `stacks-signer/src/v0/signer.rs` and once in `stacks-signer/src/chainstate/mod.rs`, i.e. not every caller goes through `block_lookup_by_reward_cycle`. Any such direct caller receives whatever row SQLite returns for that `signer_signature_hash` without an `ORDER BY` or `reward_cycle` filter, so if two rows exist for the same hash under different `reward_cycle` values, the query result is not guaranteed to belong to the caller's actual/current reward cycle.

### Impact Explanation
If a caller that skips the reward-cycle wrapper receives a `BlockInfo` computed/persisted under a different reward cycle than the one currently governing consensus (e.g. carrying a stale `vote`, `state` (Accepted/Rejected), or `valid` flag from before a reward-cycle recomputation at a boundary), the signer could treat a previously-rejected or unvalidated block as already accepted/valid — a rejection miscounted as an acceptance, or a signature decision made against the wrong context's cached state. This aligns with the "rejection recounted as an accept" / "cross-context" impact class called out in scope.

### Likelihood Explanation
Reaching this requires only a normal reward-cycle-boundary condition (a block whose committed reward-cycle classification is recomputed or a re-proposal that lands with a different `reward_cycle` value) plus a call path that uses `block_lookup` directly instead of `block_lookup_by_reward_cycle`. No majority collusion, other signer's key, or crypto break is needed — the exact same block header/hash simply gets re-recorded under a new reward cycle at a boundary, matching the general pattern noted in the docs of `reward_cycle` and `consensus_hash`/tenure classification being reassessed as burn-view state settles.

### Recommendation
Change `SignerDb::block_lookup` to require and filter on `reward_cycle` (matching the table's primary key), or audit and route every direct call site in `signer.rs` / `chainstate/mod.rs` through the existing `block_lookup_by_reward_cycle` guard so a `BlockInfo` from a stale/other reward cycle can never satisfy a check intended for the signer's current context.

### Proof of Concept
1. A block `B` with `signer_signature_hash = H` is initially recorded via `insert_block` with `reward_cycle = N` (e.g. rejected/`valid=false`).
2. Due to a reward-cycle boundary recomputation (burn height reassessed against a new cycle), the same block `B` (same header, same `H`) is later processed and inserted again with `reward_cycle = N+1`. Because the primary key `(reward_cycle, signer_signature_hash)` differs, `INSERT OR REPLACE` creates a second row rather than overwriting the first — both rows for hash `H` now coexist [4](#0-3) .
3. A code path that calls `signer_db.block_lookup(&H)` directly (not the `block_lookup_by_reward_cycle` wrapper) issues `SELECT block_info FROM blocks WHERE signer_signature_hash = ?` with no `reward_cycle` filter and no `ORDER BY` [5](#0-4) , so it may return the stale row from `reward_cycle = N` (e.g. carrying an outdated `valid`/vote/state) while the signer is currently operating under `reward_cycle = N+1`, causing a decision based on the wrong context's cached verdict.

Note: I could not fully enumerate/confirm the exact downstream consequences at every one of the 12 direct `block_lookup` call sites in `v0/signer.rs` and the single call site in `chainstate/mod.rs` within the available investigation — this analysis is based on the confirmed unscoped query and the codebase's own established need for reward-cycle scoping via the wrapper function. A full audit of each direct call site would be needed to confirm the precise exploitation trigger at each location.

    /// Helper for getting the block info from the db while accommodating for reward cycle
    pub fn block_lookup_by_reward_cycle(
        &self,
        block_hash: &Sha512Trunc256Sum,
    ) -> Option<BlockInfo> {
        let block_info = self
            .signer_db
            .block_lookup(block_hash)
            .inspect_err(|e| {
                error!("{self}: Failed to lookup block hash {block_hash} in signer db: {e:?}");
            })
            .ok()
            .flatten()?;
        if block_info.reward_cycle == self.reward_cycle {
            Some(block_info)
        } else {
            None
        }
    }
