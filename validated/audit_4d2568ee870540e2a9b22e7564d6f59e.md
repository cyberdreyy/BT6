### Title
`previewLossAdjustedWithdrawFunds` excludes `unclaimedFees` from the active loss basis in cash mode, over-haircutting pending withdraw receipts — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external bug is a running total (`entireSystemColl`) that omits one component (collateral gas compensation), producing an inflated ratio that skews a downstream threshold/payout decision. The analog is `_lossActiveBasis`, the denominator component used by `previewLossAdjustedWithdrawFunds` to split a realized `stopEpochWithDuration` loss between active LPs and pending withdraw receipts. In minted-interest mode the function deliberately counts gross strategy-token balance **plus** minted interest so that accrued fee backing joins the active side, but in cash mode it builds the basis from `getContractValue()`, which subtracts `unclaimedFees`. Fees already accrued to `feeReceiver`/`owner` therefore escape the loss split while remaining payable, so `totalBasis = activeBasis + pendingBasis` is understated and pending receipts absorb a larger pro-rata share of every loss than they should.

### Finding Description
In `previewLossAdjustedWithdrawFunds` (IdleCreditVault.sol:440-460) the pending/active split is computed as:

```solidity
uint256 pendingLoss = _lossAmount * pendingBasis / totalBasis;   // totalBasis = activeBasis + pendingBasis
pendingToFund = pendingBasis - pendingLoss;
activeLoss = _lossAmount - pendingLoss;
```

`activeBasis` comes from `_lossActiveBasis` (IdleCreditVault.sol:468-483):

```solidity
if (_cdo.isInterestMinted()) {
    return balanceOf(idleCDO) + _cdo.expectedEpochInterest();   // gross: includes fee backing
}
uint256 activeBasisBeforePerfFee = _cdo.getContractValue();     // net: excludes unclaimedFees
uint256 expectedInterest = _cdo.expectedEpochInterest();
uint256 pendingFees = _cdo.pendingWithdrawFees();
if (expectedInterest > pendingFees) {
    activeBasisBeforePerfFee += expectedInterest - pendingFees;
}
uint256 savedNAV = _cdo.lastNAVAA() + _cdo.lastNAVBB();
activeBasis = activeBasisBeforePerfFee > savedNAV ?
    activeBasisBeforePerfFee - ((activeBasisBeforePerfFee - savedNAV) * _cdo.fee() / FULL_ALLOC) :
    activeBasisBeforePerfFee;
```

`getContractValue()` is defined (IdleCDO.sol:178-187) as `strategyTokens*price + balance - lockedRewards - unclaimedFees`. `unclaimedFees` are already-accrued performance/management fees owed to `feeReceiver`/`owner`; they are *not* reduced when `_lossAmount` is later burned BB-first via `_forceUpdateAccounting` — `_updateAccounting` only accrues more fees on gains and never claws back `unclaimedFees`. So in cash mode:

- The feeReceiver's claim is preserved in full (it stays in `unclaimedFees` and is paid via `_transferFeeUnderlyings`/share mints).
- Yet its backing is excluded from `activeBasis`, so `pendingLoss` is computed against a smaller denominator than the minted-mode path uses for the identical economic situation.
- Result: `pendingLoss` is overstated, `pendingToFund` is understated, `lossRecoveryPriceByEpoch[epoch]` stored by `collectWithdrawFunds` (IdleCreditVault.sol:417-421) is lower than the fair haircut, and `_claimLossAdjustedWithdrawRequest` pays each pending receipt less underlying. The avoided loss stays with active tranche holders (and the preserved `unclaimedFees`).

This mirrors the Liquity bug exactly: a global accounting figure omits a carve-out component (there: gas compensation; here: accrued fees), so the derived ratio is wrong in favor of parties that are not the pending claimants.

### Impact Explanation
Every cash-mode (non-minted) `stopEpochWithDuration(_lossAmount)` with `pendingWithdraws > 0` and `unclaimedFees > 0` transfers part of the intended active-side loss onto pending withdraw requesters. The magnitude is bounded by the fee accrual but is systematic: for pending basis `P`, loss `L`, true active basis `A` (including fee backing `F = unclaimedFees`), pending users lose `L·P·F / ((A+P)·(A+F+P))` more than they should. Concretely: `getContractValue = 99_000`, `unclaimedFees = 1_000`, `pendingWithdraws = 10_000`, `_lossAmount = 20_000` gives `pendingLoss ≈ 1834.9` instead of `1818.2` — ~17 units stolen from receipt holders per stop, scaling linearly with fees, loss, and pending queue size. Broken invariant: loss waterfall — a tranche/fee class silently exempted from its share of loss socialization.

### Likelihood Explanation
Requires (a) cash mode (`isInterestMinted == false`, the default accounting path), (b) a non-zero `unclaimedFees` balance — accumulated automatically by `_updateAccounting`/`_accrueManagementFee` on any profitable epoch, (c) pending withdraw receipts, and (d) an honest manager calling `stopEpochWithDuration` with `_lossAmount > 0` (e.g., a partial borrower shortfall). An unprivileged attacker who is an active LP benefits passively and can additionally inflate the theft surface by depositing a large active position so the excluded-fee asymmetry shifts more loss onto the pending queue; no privileged collusion is needed since the loss amount itself is set by the honest manager to reflect a real shortfall.

### Recommendation
In `_lossActiveBasis`'s cash-mode branch, add the fee backing the same way minted mode does: `activeBasisBeforePerfFee = _cdo.getContractValue() + _cdo.unclaimedFees()` before layering expected interest and the performance-fee adjustment, so accrued-but-unpaid fees participate on the active side of the loss in both modes.

### Proof of Concept
Foundry fork sketch (setup mirrors `test/foundry/IdleCreditVault.t.sol` helpers `_startEpochAndCheckPrices`, `_stopEpochAndCheckPrices`, `_requestWithdrawWithUser`):

```solidity
function testLossBasisExcludesUnclaimedFees() external {
    // cash mode (isInterestMinted == false), fee > 0
    vm.prank(owner);
    cdoEpoch.setFeeParams(TL_MULTISIG, 10000, FULL_ALLOC, 1000); // perfFee 10%, mgmtFee 10%
    idleCDO.depositAA(50_000 * ONE_SCALE);
    _depositWithUser(makeAddr('bb'), 50_000 * ONE_SCALE, false);
    _startEpochAndCheckPrices(0);

    // profitable epoch => unclaimedFees accrue on stopEpoch
    uint256 interest = _scaleAprWithBuffer(100_000 * ONE_SCALE / 100);
    _stopEpochAndCheckPrices(0, initialProvidedApr, interest);
    uint256 fees = cdoEpoch.unclaimedFees();
    assertGt(fees, 0, 'needs accrued fees');

    // user queues a normal withdraw for the next epoch
    _requestWithdrawWithUser(makeAddr('w'), 10_000 * ONE_SCALE);
    _startEpochAndCheckPrices(1);
    vm.warp(cdoEpoch.epochEndDate() + 1);

    uint256 pending = strategy.pendingWithdraws();
    uint256 loss    = 20_000 * ONE_SCALE;

    // actual split used by the vault
    (uint256 pendingToFund, ) = strategy.previewLossAdjustedWithdrawFunds(loss);

    // fair split: fee backing must join the active side (as it does in minted mode)
    uint256 activeFair = cdoEpoch.getContractValue() + fees
                       + (cdoEpoch.expectedEpochInterest() > cdoEpoch.pendingWithdrawFees()
                          ? cdoEpoch.expectedEpochInterest() - cdoEpoch.pendingWithdrawFees() : 0);
    uint256 pendingLossFair = loss * pending / (activeFair + pending);
    uint256 expectedFund    = pending - pendingLossFair;

    assertLt(pendingToFund, expectedFund, 'pending receipts over-haircut by excluded unclaimedFees');
}
```

Run on the mainnet fork configuration already used by `test/foundry/IdleCreditVault.t.sol`; the assertion fails on current code because `previewLossAdjustedWithdrawFunds` → `_lossActiveBasis` omits `unclaimedFees` in the cash branch while minted mode counts equivalent fee backing via `balanceOf(idleCDO) + expectedEpochInterest`.
