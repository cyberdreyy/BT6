### Title
Builder payment can be paid out twice when a parent payload arrives 2+ epochs late after already reaching quorum - (File: specs/gloas/beacon-chain.md)

### Summary
`apply_parent_execution_payload`'s fallback branch for "parent older than the previous epoch" unconditionally re-appends a `BuilderPendingWithdrawal` for `parent_bid.value` whenever the settling block arrives 2+ epochs after the bid, without checking whether `process_builder_pending_payments` already paid out that same payment via the quorum path during the intervening epoch transition(s). This mirrors the UMA `LongShortPair`/`LongShortPairCreator` bug class: two independent code paths both transfer the same value that should only be paid once, so a builder payment can be minted/paid twice from a single bid commitment.

### Finding Description
When a builder's bid is accepted in `process_execution_payload_bid`, a `BuilderPendingPayment` is recorded in `state.builder_pending_payments[SLOTS_PER_EPOCH + bid.slot % SLOTS_PER_EPOCH]` [1](#0-0) . Attestations that reference this payload accumulate voting weight into `payment.weight` over the following slots [2](#0-1) .

At every epoch boundary, `process_builder_pending_payments` runs: it checks the current first half of `builder_pending_payments` (i.e., the *previous* epoch's payments) against a quorum threshold and, if met, appends the withdrawal to `state.builder_pending_withdrawals`; it then shifts the second half down and clears the new second half [3](#0-2) . This is unconditional eviction: whether or not quorum was met, the entry is gone after being checked once — it is not tied to whether the actual settling block for that payload has arrived yet.

Independently, when the real child block (whose parent is the block that carried the bid) is eventually processed, `apply_parent_execution_payload` settles the payment:
```python
if parent_epoch == get_current_epoch(state):
    payment_index = SLOTS_PER_EPOCH + parent_slot % SLOTS_PER_EPOCH
    settle_builder_payment(state, payment_index)
elif parent_epoch == get_previous_epoch(state):
    payment_index = parent_slot % SLOTS_PER_EPOCH
    settle_builder_payment(state, payment_index)
elif parent_bid.value > 0:
    # Parent is older than the previous epoch, its payment entry has been
    # evicted from builder_pending_payments. Append the withdrawal directly.
    state.builder_pending_withdrawals.append(
        BuilderPendingWithdrawal(
            fee_recipient=parent_bid.fee_recipient,
            amount=parent_bid.value,
            builder_index=parent_bid.builder_index,
        )
    )
``` [4](#0-3) 

If the child block is delayed by 2+ epochs (crossing at least two epoch boundaries before the settling block is processed), the comment in the spec itself acknowledges the entry "has been evicted from builder_pending_payments" by `process_builder_pending_payments` — but the code does not distinguish *why* it was evicted. There are two disjoint eviction outcomes in `process_builder_pending_payments`:
- weight < quorum → entry discarded, nothing paid (a legitimate loss the fallback is meant to fix), or
- weight >= quorum → `state.builder_pending_withdrawals.append(payment.withdrawal)` already ran, i.e., the builder was **already paid**.

The `elif parent_bid.value > 0:` fallback branch cannot tell these two cases apart from `state.latest_execution_payload_bid` alone — it only looks at `parent_bid.value`, not at whether the corresponding payment/withdrawal was already settled. In the second case it appends a second, independent `BuilderPendingWithdrawal` carrying the same `amount`, `fee_recipient`, and `builder_index`, resulting in the same bid value being scheduled for payout twice.

### Impact Explanation
This breaks the equality "one accepted builder bid of value V results in exactly one withdrawal of value V to the builder's fee recipient." A double withdrawal mints V extra Gwei paid to the builder's `fee_recipient` (a non-owner from the perspective of the rest of the validator set / protocol) without any corresponding second debit from the builder's balance or bid commitment — Gwei is effectively created and paid out, which falls squarely under the report's Critical impact category ("Gwei created, destroyed or paid to a non-owner").

### Likelihood Explanation
This requires no malicious coalition, only ordinary/adversarial-free network conditions: a proposer being 2+ epochs late to build on a given parent (e.g., due to missed slots/short-lived non-finality of block production, which is explicitly anticipated and tested by the existing spec test `test_builder_payment_after_missed_epochs`), combined with the builder's attestation weight reaching quorum before that late block finally arrives. Because the existing spec tests for this exact scenario (`test_process_parent_execution_payload__older_than_previous_epoch`, `test_builder_payment_after_missed_epochs`) only construct the "weight 0 < quorum" branch, the quorum-already-met branch is not exercised in-repo, meaning the double-payment path is untested and unguarded. This is a plausible, permissionless-triggerable condition, not merely a theoretical edge case.

### Recommendation
Track settlement state explicitly instead of inferring it from epoch arithmetic on `parent_bid`. For example, extend `BuilderPendingPayment`/bid state with an explicit "settled" flag, or have `process_builder_pending_payments` record (e.g. in a small settled-payments map keyed by slot, or by clearing `state.latest_execution_payload_bid.value` when it pays out via quorum) so that `apply_parent_execution_payload`'s fallback branch can check "was this bid already paid by the quorum path?" before appending a fresh `BuilderPendingWithdrawal`. Alternatively, ensure `process_builder_pending_payments`'s quorum-based payout and the direct-append fallback are mutually exclusive by having `process_builder_pending_payments` write into a structure that `apply_parent_execution_payload` can consult (rather than blindly evicting to `BuilderPendingPayment.empty()` with no record of the outcome).

### Proof of Concept
1. Builder B submits a bid of value V for block at slot S in epoch E; `process_execution_payload_bid` records `builder_pending_payments[SLOTS_PER_EPOCH + S % SLOTS_PER_EPOCH]` with `withdrawal.amount = V` [1](#0-0) .
2. Attesters vote for the payload at slot S such that `payment.weight` accumulates to at least `get_builder_payment_quorum_threshold(state)` during epoch E (via `process_attestation`'s weight accumulation) [5](#0-4) .
3. No block is built with parent = block S for 2+ epochs (proposers at slots S+1..S+2*SLOTS_PER_EPOCH are offline/miss their slot).
4. At the E→E+1 epoch boundary, `process_builder_pending_payments` shifts the payment into the first half of `builder_pending_payments` [3](#0-2) .
5. At the E+1→E+2 epoch boundary, `process_builder_pending_payments` checks `payment.weight >= quorum` — true — and appends `BuilderPendingWithdrawal(amount=V, ...)` to `builder_pending_withdrawals`, then clears the slot as part of the shift/reset.
6. In epoch E+2 (or later), a proposer finally builds a block whose parent is block S. `process_parent_execution_payload` → `apply_parent_execution_payload` computes `parent_epoch = E`, which is neither `get_current_epoch(state)` (E+2) nor `get_previous_epoch(state)` (E+1), so it falls into `elif parent_bid.value > 0:` and appends a **second** `BuilderPendingWithdrawal(amount=V, fee_recipient=parent_bid.fee_recipient, builder_index=parent_bid.builder_index)` [6](#0-5) .
7. `builder_pending_withdrawals` now contains two entries of value V for the same bid, and subsequent `get_builder_withdrawals`/`apply_withdrawals` processing pays out 2V total to the builder's fee recipient for a single bid commitment of V [7](#0-6) .

def process_builder_pending_payments(state: BeaconState) -> None:
    """
    Processes the builder pending payments from the previous epoch.
    """
    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:
        if payment.weight >= quorum:
            state.builder_pending_withdrawals.append(payment.withdrawal)

    old_payments = state.builder_pending_payments[SLOTS_PER_EPOCH:]
    state.builder_pending_payments[:SLOTS_PER_EPOCH] = old_payments
    new_payments = [BuilderPendingPayment.empty() for _ in range(SLOTS_PER_EPOCH)]
    state.builder_pending_payments[SLOTS_PER_EPOCH:] = new_payments

def get_builder_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    for withdrawal in state.builder_pending_withdrawals:
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder_index = withdrawal.builder_index
        withdrawals.append(
            Withdrawal(
                index=withdrawal_index,
                validator_index=convert_builder_index_to_validator_index(builder_index),
                address=withdrawal.fee_recipient,
                amount=withdrawal.amount,
            )
        )
        withdrawal_index += 1
        processed_count += 1
