### Title
Stale-epoch instant-withdraw receipts escape the default recovery haircut and are paid at par, draining the shared recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`defaultPendingClaimBasis()` and `_claimDefaultedInstantWithdrawRequest()` only containment-check `instantWithdrawClaimsByEpoch[epochNumber]` / `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` — the *current/default* epoch. But instant-withdraw receipts are keyed to the epoch in which they were *requested*. A receipt requested in an earlier epoch and left unfunded (`pendingInstantWithdraws` carries across epochs) is invisible to both the recovery-basis accounting and the per-epoch clearing step, yet `claimInstantWithdrawRequest` pays the aggregate `instantWithdrawsRequests[_user]` at par. This is the direct analog of the extract-zip bug: the check validates the parent (current epoch bucket) but never the final component (the request's own epoch key), so a "planted" stale entry passes through unpriced.

### Finding Description
- `requestInstantWithdraw` records the receipt under `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and `instantWithdrawClaimsByEpoch[epochNumber]`, and adds to the global `pendingInstantWithdraws` which is never epoch-keyed [1](#0-0) .
- At `finalizeDefaultRecovery`, the claim basis only adds `instantWithdrawClaimsByEpoch[epochNumber]` — the finalization epoch — when `pendingInstantWithdraws != 0` [2](#0-1) . Stale-epoch instant claims contribute to `pendingInstantWithdraws` (so they keep the bucket non-zero) but their basis is excluded from `defaultPendingClaimBasis`, inflating `defaultRecoveryPrice` for everyone else.
- `_claimDefaultedInstantWithdrawRequest` clears only `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` [3](#0-2) . The stale-epoch entry survives, remains inside `instantWithdrawsRequests[_user]`, and `claimInstantWithdrawRequest` then burns and pays it **at par** via `_transferFundedClaim` [4](#0-3) .
- Symmetric hole in the funded-direction: `_defaultPrefundedInstantReserve` computes `instantWithdrawClaimsByEpoch[epochNumber] - pendingInstantWithdraws`, which mis-attributes prefunding when the unfunded remainder belongs to an older epoch [5](#0-4) .

Broken invariant: one receipt one haircut — the recovery ratio is computed over a basis that omits real claims, so honest claimants' pro-rata share is diluted and the reserve is exhausted by claimants who were never priced.

### Impact Explanation
An attacker holding an unfunded prior-epoch instant receipt withdraws 100% of it while every defaulted-epoch claimant receives `defaultRecoveryPrice < RECOVERY_FULL`. The excess payment comes directly out of underlying that honest active LPs and pending receipt holders were allocated — a direct theft/dilution quantified as `attackerReceipt * (1 - defaultRecoveryPrice)` plus the basis-dilution on all other claims. The `_transferFundedClaim` reserve guard (lines 899-905) does not stop it whenever the instant queue was partially or fully prefunded, because the stolen funds are dressed as "funded" balance.

### Likelihood Explanation
Requires instant-withdraw mode and a borrower default occurring with a non-zero `pendingInstantWithdraws` whose claims were requested in an earlier epoch — a normal state whenever `collectInstantWithdrawFunds` under-collected at a prior `startEpoch`. The attacker is an ordinary KYC'd tranche holder; no privileged role misbehavior needed. The only mitigating precondition is instant withdrawals being enabled and an epoch boundary crossing while the queue is partially funded.

### Recommendation
In `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve`, account for instant claims across all epochs with outstanding receipts (e.g., track a global `instantWithdrawClaimsTotal` alongside `pendingInstantWithdraws`, or iterate/clear all per-epoch entries). In `_claimDefaultedInstantWithdrawRequest`, clear the user's *entire* `instantWithdrawsRequests[_user]` at `defaultRecoveryPrice` rather than only the `defaultRecoveryEpoch` entry, since all unpaid instant claims are equally unfunded at finalization.

### Proof of Concept
Foundry fork scenario (mainnet fork of the deployed IdleCDOEpochVariant + IdleCreditVault):
1. Enable instant withdrawals; LP (attacker) deposits AA and calls `requestInstantWithdraw(X)` in epoch 1 → receipt stored under `instantWithdrawsRequestsByEpoch[attacker][1]`, `pendingInstantWithdraws = X`.
2. Honest borrower/manager calls `startEpoch`; `collectInstantWithdrawFunds` collects only part (or the funds were lent out) → `pendingInstantWithdraws` stays `> 0`, `epochNumber` → 2.
3. Epoch 2 runs with new depositors; borrower defaults; `finalizeDefaultRecovery(recovered, source)` runs with `defaultRecoveryEpoch = 2`. `defaultPendingClaimBasis` includes `instantWithdrawClaimsByEpoch[2]` but **not** the attacker's epoch-1 claim → `defaultRecoveryPrice` is set too high; `defaultInstantWithdrawsFinalized = true`.
4. Attacker calls `claimInstantWithdrawRequest` → `_claimDefaultedInstantWithdrawRequest` reads `instantWithdrawsRequestsByEpoch[attacker][2] == 0`, returns early → `_transferFundedClaim` pays the full `X` at par.
5. Assert: attacker received `X` while `defaultRecoveryPrice < RECOVERY_FULL`, and `defaultRecoveryReserve`/strategy balance shortfall equals `X * (1 - price)` borne by defaulted-epoch claimants.

    instantWithdrawsRequests[_user] += _amount;

    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.

    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }

  function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);
    }
    uint256 amount = instantWithdrawsRequests[_user];
    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
  }

  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;
    uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];
    if (instantBasis > pendingInstant) {
      prefundedReserve = instantBasis - pendingInstant;
    }
  }

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
