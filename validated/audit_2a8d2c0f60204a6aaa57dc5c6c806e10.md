### Title
Rejection dropped once a signer has already Accepted the same block hash — silent no-op in `total_weight_rejected` accounting - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
In `StackerDBListener::run`, the `Rejected` match arm only updates `total_weight_rejected` and `failed_txids` inside `if block.responded_signers.insert(slot_id) { ... }`. Because the `Accepted` arm unconditionally calls `block.responded_signers.insert(slot_id)` at [1](#0-0)  when a signer accepts a block hash, any later `Rejected` message from that same slot for the same `signer_signature_hash` finds `responded_signers.insert(slot_id)` returning `false` and the entire rejection-processing block is skipped, so `total_weight_rejected` is never incremented for that signer.

### Finding Description
The equality the aggregator is supposed to maintain is: `total_weight_approved` == sum of weights of signers whose *most recent* response for hash `H` is `Accepted`. The code breaks this equality in the opposite direction from decrementing approval — it simply fails to ever increment rejection weight once the slot has been marked as "responded", regardless of which response type set that flag.

Walking the code:
- `Accepted` arm: on the first accept for a slot, weight is added to `total_weight_approved` (guarded by `!block.gathered_signatures.contains_key(&slot_id)`), then unconditionally `block.gathered_signatures.insert(slot_id, signature)` and `block.responded_signers.insert(slot_id)` are executed [2](#0-1) .
- `Rejected` arm: rejection accounting (`total_weight_rejected` increment, `failed_txids` bookkeeping, and the log line) is gated entirely behind `if block.responded_signers.insert(slot_id) { ... }` [3](#0-2) . Since `responded_signers` already contains `slot_id` from the prior `Accepted` message for the same `signer_signature_hash`, this `insert` returns `false`, and the rejection is silently discarded — no weight change, no log, `gathered_signatures` entry is untouched.
- There is no code path anywhere in the `Rejected` arm (or elsewhere) that decrements `total_weight_approved` or removes an entry from `gathered_signatures` for the same hash.

The net effect matches the question's claim: once a signer accepts hash `H`, a subsequent rejection message for that exact same `H` from the same signer is a complete no-op on the aggregate tallies — `total_weight_approved` stays inflated by that signer's stale accept, and it still counts toward the `total_weight_approved >= self.weight_threshold` check that gates finalization in `SignerCoordinator`/`propose_block` logic (`stacks-node/src/nakamoto_node/signer_coordinator.rs`), and toward `StackerDBListenerComms::wait_for_block_status` conditions.

Where this is bounded/mitigated (and where the attack scenario is questionable):
- `signer_signature_hash` is a deterministic hash of the block header/content. For a signer to legitimately go from "Accepted H" to "Rejected H" for the *identical* hash, the signer's own decision logic in `stacks-signer/src/v0/signer.rs` / `signerdb.rs` would have to change its verdict on the exact same block bytes without any new information distinguishing it (e.g., a timeout-based re-evaluation, or a competing-hash detection routine that then reprocesses/re-emits a response for the original hash). I was not able to fully confirm, within available context, that the honest v0 signer state machine ever re-emits a `Rejected` response for a hash it previously and durably marked `Accepted` in `signerdb.rs`'s block state tracking — typical fork-choice re-evaluation triggered by a *second, conflicting* proposal at the same height would normally produce a `Rejected` for the *new/competing* hash (different `signer_signature_hash`), not a retroactive rejection of the *already-accepted* hash. This is the crux uncertainty: whether the precondition ("the same honest signer emits Rejected for the same H after having Accepted H") is actually reachable by an unprivileged attacker's crafted messages, or whether it requires an internal signer bug/state transition that isn't demonstrated to exist in `signer.rs`.
- Regardless of that uncertainty, the *listener-side* aggregation logic itself is verifiably asymmetric and drops the second, differing verdict for the same slot+hash — this part of the bug is directly confirmed in the code shown above.

### Impact Explanation
If a signer can legitimately transition from Accepted(H) to Rejected(H) for the same hash (e.g., via a bug in the signer's own accept/reject bookkeeping in `signerdb.rs`, or a state machine path not fully traced here), the listener's failure to decrement `total_weight_approved`/remove the stale entry from `gathered_signatures` means that signer's rejection is silently dropped from the tally. This would let `total_weight_approved` stay artificially inflated, potentially letting `propose_block`'s threshold check finalize/broadcast a block that a majority of current signer intent no longer supports — a Critical, chain-safety-adjacent outcome (a rejection recounted as an acceptance) if reachable.

However, this is a single-node-local aggregation cache used by the *miner's* coordinator to decide when it has "enough" signatures to push a block; it does not itself cause a signer to sign an invalid block, and it does not affect other nodes' independent validation of the aggregate signature threshold, which each node/signer verifies independently against the actual signatures present. The severity therefore hinges on whether the stale, inflated `total_weight_approved` can cause the miner to broadcast/finalize a block using signatures that a validator would still consider forming a valid quorum — the `gathered_signatures` map still holds a genuine, validly-signed accept from that signer for hash `H` (the signer did sign it validly at some point), so the aggregate signature itself is not "invalid," only potentially stale relative to the signer's *current* intent.

### Likelihood Explanation
The described precondition (an honest signer accepting `H`, then later rejecting the identical `H`) is unusual and its reachability via attacker-controlled, unprivileged single-slot messages/proposals is not conclusively demonstrated within the code inspected — normal re-evaluation due to a competing proposal at the same height should target a distinct `signer_signature_hash`, not the original one. Without confirming a concrete code path in `stacks-signer/src/v0/signer.rs` or `signerdb.rs` that reproduces "Accept H, then later Reject the same H," the exploit chain described cannot be validated as reachable by a single unprivileged miner slot alone.

### Recommendation
N/A pending confirmation of reachability — if the precondition can be shown to occur (i.e., an honest signer emitting differing verdicts for the identical `signer_signature_hash`), the aggregator in `stackerdb_listener.rs` should track the *latest* verdict per slot per hash and update `total_weight_approved`/`total_weight_rejected`/`gathered_signatures` accordingly (moving weight between the two counters and removing/adding to `gathered_signatures`) rather than gating both arms on a single shared `responded_signers` set that only records "has responded at all."

### Proof of Concept
Not provided — the precondition that an honest signer emits a `Rejected(H)` for a hash `H` it has already `Accepted` could not be confirmed as reachable from the available `stacks-signer/src/v0/signer.rs` and `signerdb.rs` context in this session; a reproducible test would need to first establish that signer-side state-machine path before demonstrating the listener-side aggregation bug in isolation.
