### Title
EI credentials bypass "no EI int-ID runs" restriction in PipelineRunsController.Create - ([File: core/web/pipeline_runs_controller.go])

### Finding Description
`PipelineRunsController.Create` intends to reject int-ID job run requests unless authenticated by a real user session/token, per the comment "only users are allowed to run jobs using int IDs - EIs not allowed" [1](#0-0) . The gate for this is `_, isUser := auth.GetAuthenticatedUser(c)`, which simply checks whether a `*clsessions.User` is present under `SessionUserKey` in the gin context [2](#0-1) .

The root cause is that `AuthenticateExternalInitiator` — the authMethod that authenticates EI access-key/secret headers — stores a synthetic `&clsessions.User{Role: clsessions.UserRoleRun}` under the exact same `SessionUserKey` used by real session/token authentication, explicitly to let EI requests satisfy role-based checks like `RequiresRunRole` [3](#0-2) . Since `GetAuthenticatedUser` only checks for the presence and type of that key — not its provenance (real DB-backed user vs. EI-derived placeholder) — an EI-authenticated request also satisfies `isUser == true` in `Create`, letting the int-ID branch execute and call `prc.App.RunJobV2(ctx, jobID, nil)` [4](#0-3) . This directly contradicts the documented invariant that EIs must go through the UUID-based webhook run path (now removed for webhook type) and are not authorized to trigger arbitrary int-ID job runs.

### Impact Explanation
An external-initiator credential holder — a lower-privileged, narrowly-scoped credential intended only to resume/trigger jobs it registered via UUID — can trigger a run of *any* job by its integer ID, not limited to jobs associated with that EI. This is an authorization/role-boundary bypass leading to unauthorized job execution (job run triggering an off-chain pipeline, potentially consuming funds or writing on-chain transactions depending on job type), and the resulting audit trail/attribution is also incorrect (recorded against a synthetic pseudo-user rather than the actual EI identity), which corresponds to Chainlink's "unauthorized job run" / authorization bypass impact class.

### Likelihood Explanation
The precondition is minimal: possession of any valid EI access key/secret (a common, lower-trust credential type distributed to third-party initiators), no user session, password, or API token needed. The exploit is a single authenticated POST request (`POST /v2/jobs/:ID/runs` with an integer job ID and valid EI headers). It is deterministic and repeatable for any job ID the attacker can guess or enumerate.

### Recommendation
Distinguish real authenticated users from EI-derived pseudo-users, e.g., by using a separate context key/flag (or checking `GetAuthenticatedExternalInitiator(c)` is absent) before allowing the int-ID run path in `Create`, rather than relying solely on `GetAuthenticatedUser`'s presence check. For example: reject the request if `auth.GetAuthenticatedExternalInitiator(c)` returns `ok == true`, regardless of the synthetic user role.

### Proof of Concept
Go handler-level integration test:
1. Set up a gin test router with `PipelineRunsController.Create` behind `auth.Authenticate(store, auth.AuthenticateExternalInitiator)` (mirroring the real EI-authenticated route wiring in `core/web/router.go`).
2. Seed a valid `bridges.ExternalInitiator` with known access key/secret in the mock/store.
3. Send `POST /v2/jobs/123/runs` with `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` headers matching the EI, and no session cookie or API token.
4. Mock `chainlink.Application.RunJobV2` to detect invocation.
5. Assert: currently `RunJobV2` IS invoked and a 200 response with a pipeline run resource is returned — demonstrating the bypass. Expected/fixed behavior: assert `RunJobV2` is NOT invoked and the handler returns `422 Unprocessable Entity` ("bad job ID") instead.
