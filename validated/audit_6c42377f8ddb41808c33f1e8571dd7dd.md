### Title
Fee-on-transfer tokens cause strategy-token over-minting and phantom NAV in credit vault deposits — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external bug class (accounting based on the `transferFrom` argument rather than the actual received amount) has a live analog in the credit-vault deposit path. Although `IdleCDOCreditVault._deposit` correctly mints tranche tokens from the measured balance delta, it then forwards the **gross** `_amount` to `IdleCreditVault.deposit`, which mints strategy tokens 1:1 with the gross parameter while a fee-on-transfer underlying delivers less. The strategy-token supply — which is the NAV backing (`getContractValue` = `balanceOf(idleCDO)` at `price() == 1`) — is permanently inflated by the fee amount, producing phantom gains on the next `_updateAccounting` and eventual insolvency at withdrawal.

### Finding Description
In `IdleCDOCreditVault._deposit` the share minting is delta-based:

- `uint256 _preBal = _contractTokenBalance(_token);`
- `_transferUnderlyingsFrom(msg.sender, address(this), _amount);`
- `_mintSharesAtCurrPrice(_contractTokenBalance(_token) - _preBal, ...)`

so the depositor is only credited for what arrived. But immediately after, the CDO calls `IIdleCDOStrategy(strategy).deposit(_amount)` with the original gross `_amount` — not the received delta (contracts/IdleCDOCreditVault.sol:206-211).

In `IdleCreditVault.deposit` (contracts/strategies/idle/IdleCreditVault.sol:596-617):

```solidity
underlyingToken.safeTransferFrom(msg.sender, address(this), _amount);
_mint(msg.sender, _amount);
...
totEpochDeposits += _amount;
```

Two independent corruptions follow for a fee-on-transfer `token` (e.g., USDT with fee enabled):

1. `safeTransferFrom(idleCDO → strategy, _amount)` delivers `_amount - fee2`, but `_mint(idleCDO, _amount)` credits the CDO the gross amount of strategy tokens. Since `price()` is fixed at `oneToken` and `getContractValue` reads the strategy-token balance, the CDO's NAV permanently overstates real underlying by `fee1 + fee2` (the CDO itself only received `_amount - fee1` from the user). On the next deposit/withdraw/harvest, `_updateAccounting` sees `nav > lastNAV` by that phantom amount and books it as **gain**: `unclaimedFees` is charged and the residual is distributed to tranche prices via `_virtualPriceAux` — fabricated yield with zero backing.
2. `totEpochDeposits += _amount` inflates the borrower principal/interest accounting (`expectedEpochInterest` derives from lent amounts), so `stopEpoch` demands interest computed on tokens that never arrived.

No guard stops this: there is no `_skimDonatedAssets`-style reconciliation between strategy-token supply and `underlyingToken.balanceOf(this)`, `setWhitelistedCDO` only gates callers, and the delta check exists only at the tranche-mint layer.

### Impact Explanation
Direct insolvency / unfair share: every FoT deposit leaves the vault holding fewer underlyings than the strategy-token supply claims. The phantom NAV is crystallized as yield into tranche prices, so a KYC-passing lender who deposits a FoT token during the buffer phase can later `requestWithdraw`/`claimWithdrawRequest` (or instant-withdraw) at the inflated price and receive real underlyings, while the residual shortfall is socialized to remaining tranche holders and to the borrower's repayment schedule (`totEpochDeposits`, `pendingWithdraws` basis in `previewLossAdjustedWithdrawFunds`/`collectWithdrawFunds`). Loss magnitude = the cumulative token fees on the inflated deposit amounts, which can be up to the full deposit size for high-fee tokens. If the vault holds no spare underlying, the CDO→strategy pull itself succeeds (CDO still holds `_amount - fee1`, and `fee2` may exceed it → the whole deposit can also revert, a secondary availability issue).

### Likelihood Explanation
Requires only that the vault's configured `token` charges (or later enables) a transfer fee — the same precondition as the original report (USDT's fee is currently 0 but can be switched on). The attacker is an ordinary KYC-passing lender calling `depositAA`/`depositBB` during the buffer phase; no privileged cooperation needed. The same trusted-parameter pattern exists in `collectWithdrawFunds`/`collectInstantWithdrawFunds`/`finalizeDefaultRecovery` pulls, but those pull from the honest CDO/recovery source, so the exploitable surface is the lender-driven deposit path.

### Recommendation
In `IdleCreditVault.deposit`, measure the actual received amount and mint strategy tokens / update `totEpochDeposits` on the delta:

```solidity
uint256 _preBal = underlyingToken.balanceOf(address(this));
underlyingToken.safeTransferFrom(msg.sender, address(this), _amount);
uint256 _received = underlyingToken.balanceOf(address(this)) - _preBal;
_mint(msg.sender, _received);
totEpochDeposits += _received;
```

and in `IdleCDOCreditVault._deposit` pass the received delta (already computed for minting) into `strategy.deposit(...)` instead of `_amount`. Apply the same balance-delta pattern to `collectWithdrawFunds`, `collectInstantWithdrawFunds`, `sendInterestAndDeposits` accounting, and `finalizeDefaultRecovery`'s `_recoveredAmount` pull, or explicitly document that FoT underlyings are unsupported and enforce it at initialization.
