### Title
Non-tail obsolete-byte accounting can compute a saved storage length that truncates before subsequent alive accounts, corrupting snapshot round-trip data - ([File: runtime/src/serde_snapshot/storage.rs])

### Summary
`SerializableAccountStorageEntry::new` computes the snapshot-saved length of an `AccountStorageEntry` as `accounts.accounts.len() - accounts.get_obsolete_bytes(Some(snapshot_slot))`, i.e. total file length minus the sum of all obsolete-account byte sizes in the file, regardless of where those obsolete bytes are located. `get_obsolete_bytes` in `accounts-db/src/account_storage_entry.rs` sums `calculate_stored_size(data_len)` for every obsolete offset independent of position. This arithmetic is only correct if all obsolete bytes form a contiguous suffix of the file; if an obsolete account sits before an alive account in the same append-only storage, the resulting `accounts_current_len` can be smaller than the offset where a still-alive account begins.

### Finding Description
`SerializableAccountStorageEntry::new` is documented as decreasing "the saved size ... by the amount of obsolete bytes in the storage" [1](#0-0) , implying this value governs how many bytes of the underlying append-vec file are preserved/copied for the snapshot. The obsolete-byte total is computed purely as a flat sum over all obsolete offsets in the storage: [2](#0-1) 

Obsolete marking happens per-offset without regard to position in the file — an account is marked obsolete in place when it is rewritten in a later slot's storage or zeroed out, while other accounts appended after it in the same append-only file remain alive: [3](#0-2) . This is entirely reachable by an unprivileged client via ordinary transactions: write two accounts into the same slot's storage (A at a lower offset, B at a higher offset), then in a later slot rewrite/zero A. A becomes obsolete at its original offset in the original storage while B remains alive at a higher offset in that same file.

When `SerializableAccountStorageEntry::new` runs for that storage, `get_obsolete_bytes` sums A's stored size and subtracts it from the total file length to produce `accounts_current_len`. Because A sits at a lower offset than B, `total_len - sizeof(A)` is not the offset immediately after B — it under-counts, landing at or before B's start offset instead of after it. If this value is used (per its own doc comment) to bound how much of the storage is written into/restored from the archive, the archive would end up containing at most `accounts_current_len` bytes, which excludes all of B's alive bytes and can include only a partial, structurally invalid prefix of A. On restore, `AccountsFile` parsing over this truncated region would misparse whatever partial bytes remain as account headers, and B would be entirely missing from the restored storage.

The existing safeguards (`min(calculate_stored_size(data_len), accounts.len() - offset)` in `get_obsolete_bytes`) only guard against a single obsolete item's size exceeding the remaining file length; they do nothing to ensure obsolete bytes summed are actually the file's trailing bytes.

### Impact Explanation
If confirmed to gate an actual truncation/copy of storage bytes during archive serialization, this causes a validator's own periodic (non-attacker-triggered) snapshot generation to silently drop or corrupt alive account records whenever obsolescence is not confined to the tail of a storage file — a wrong-account-data / data-loss condition surfaced later through `getProgramAccounts(jsonParsed)` or any account read after loading from that snapshot. This falls under "wrong-slot/fork/account data returned" from validator state corrupted by ordinary attacker-controlled on-chain writes, not a maliciously crafted snapshot (the corruption originates in the validator's own writer logic, not in an externally supplied file).

### Likelihood Explanation
Reaching the vulnerable state only requires ordinary, unprivileged transactions: writing two accounts into the same slot's storage, then rewriting/zeroing the first one in a later slot so it is marked obsolete while the second remains alive in the original storage — a routine, easily repeatable on-chain sequence, not privileged validator control. Whether it manifests as an observable corruption depends on the downstream code that consumes `accounts_current_len` when actually slicing/copying storage bytes for the archive (in `accounts-db/src/account_storage_reader.rs` / snapshot restore paths), which I could not fully trace within the available tool budget — this is a residual uncertainty that a background engineer should verify directly by reading `account_storage_reader.rs` and the snapshot storage rebuild logic.

### Recommendation
Compute the saved/truncated length from the maximum offset+size among *alive* records (or explicitly require that obsolete accounting only trims a genuinely contiguous tail), instead of `total_len - sum(obsolete_sizes)`. Alternatively, keep the archive length equal to the full physical file length and rely solely on the offset-based `ObsoleteAccounts`/tombstone exclusion mechanism (as already used in `scan_accounts`) for restore-time filtering, rather than truncating raw bytes.

### Proof of Concept
Integration test plan (Rust, in `accounts-db`/`runtime` snapshot test modules):
1. Create an `AccountStorageEntry` for slot `S`; write account `A` (small, e.g. 0-byte data) then account `B` (distinct pubkey/owner, non-empty data) into the same storage so `B`'s offset > `A`'s stored size.
2. Mark `A` obsolete at slot `S' > S` via `obsolete_accounts().write().unwrap().mark_accounts_obsolete(...)`, mirroring `test_scan_accounts_excludes_obsolete_and_tombstones`.
3. Call `SerializableAccountStorageEntry::new(&storage, S')` and assert `accounts_current_len` returned is `>=` the offset+stored-size of `B` (i.e., large enough to still include all of `B`). Currently it will compute `accounts.len() - stored_size(A)`, which is less than `B`'s end offset when `A` precedes `B`.
4. Extend to a full snapshot round-trip test: serialize the bank snapshot, restore it, and assert that `B`'s account (owner/program, data) queried via the restored `AccountsDb`/RPC-equivalent path still matches the original on-chain data — expect failure (missing or corrupted `B`) if the length is used to bound copied bytes in the storage rebuilder.

    /// Returns the number of bytes that were marked obsolete as of the passed
    /// in slot or earlier. If slot is None, then slot will be assumed to be the
    /// max root, and all obsolete bytes will be returned.
    pub fn get_obsolete_bytes(&self, slot: Option<Slot>) -> usize {
        let obsolete_bytes: usize = self
            .obsolete_accounts_read_lock()
            .filter_obsolete_accounts(slot)
            .map(|(offset, data_len)| {
                self.accounts
                    .calculate_stored_size(data_len)
                    .min(self.accounts.len() - offset)
            })
            .sum();
        obsolete_bytes
    }
