### Título
Falta de vinculação de contexto em `_validateImmutables` no ZkSync permite substituição de parâmetros de custódia - (`contracts/zkSync/EscrowZkSync.sol`)

### Summary
O contrato `EscrowZkSync` utiliza uma verificação de endereço determinística para validar a integridade dos dados imutáveis fornecidos pelo usuário. No entanto, a implementação do ZkSync baseia-se em um `_INPUT_HASH` que é fixado durante a construção da implementação do contrato. Isso cria uma vulnerabilidade onde a validação de contexto pode ser burlada se a mesma implementação for utilizada por diferentes fábricas ou em diferentes contextos de implantação, permitindo que um atacante forneça um conjunto de `Immutables` que resulte no mesmo endereço computado, mas com dados subjacentes (como taxas ou destinatários) alterados, análogo ao bug de troca de chaves cifradas da Uniswap Wallet. [1](#0-0) 

### Finding Description
O sistema de custódia cross-chain depende da imutabilidade dos parâmetros passados durante a criação do clone. No ZkSync, a função `_validateImmutables` [2](#0-1)  verifica se o `immutablesHash` fornecido, quando combinado com o `bytecodeHash`, o endereço da `FACTORY` e o `_INPUT_HASH`, resulta no endereço atual (`address(this)`). 

O `_INPUT_HASH` é definido no construtor da implementação: `_INPUT_HASH = keccak256(abi.encode(address(this)))` [3](#0-2) . Como este contrato é uma implementação para proxies (clones), `address(this)` no construtor é o endereço do contrato de implementação. Se um atacante conseguir induzir uma colisão de endereço ou se o `FACTORY` (msg.sender da implementação) for o mesmo em diferentes instâncias, a falta de vinculação específica do clone ao seu `immutablesHash` único no armazenamento persistente (em vez de depender apenas da derivação de endereço `CREATE2` no ZkSync) permite que parâmetros críticos em `IBaseEscrow.Immutables` sejam trocados por outros que gerem o mesmo hash, mas que desviem fundos via taxas ou alteração de `maker`/`taker`.

### Impact Explanation
Um atacante (unprivileged user) pode manipular os `Immutables` passados para as funções `withdraw` ou `cancel`. Se a validação `_validateImmutables` falhar em distinguir entre dois contextos que resultam no mesmo endereço derivado, o atacante pode:
1.  Redirecionar taxas de protocolo ou integrador para endereços sob seu controle alterando o campo `parameters` nos `Immutables` fornecidos. [4](#0-3) 
2.  Alterar o destinatário do cancelamento (`maker`) para roubar fundos depositados. [5](#0-4) 

### Likelihood Explanation
A probabilidade é considerada baixa/média, pois exige a capacidade de gerar colisões de salt ou explorar a reutilização de implementações entre diferentes fábricas. No entanto, o impacto é Crítico/Alto (roubo de fundos), e a falha de design é um análogo direto da vulnerabilidade de criptografia onde o "ciphertext" (parâmetros imutáveis) não está devidamente vinculado ao contexto de execução único.

### Recommendation
Em vez de confiar exclusivamente na computação do endereço `CREATE2` para validar os imutáveis, o contrato deve armazenar o `immutablesHash` no seu armazenamento (storage) durante a inicialização (através de uma função `initialize` chamada pela fábrica) e validar contra esse valor armazenado em todas as chamadas subsequentes.

### Proof of Concept
1.  O atacante identifica um contrato `EscrowDstZkSync` implantado com `Immutables` `I1`.
2.  O atacante descobre um conjunto de parâmetros `I2` onde `hash(I2) == hash(I1)`, mas os destinatários das taxas em `I2.parameters` são controlados pelo atacante.
3.  O atacante chama `withdraw(secret, I2)`.
4.  A função `_validateImmutables(hash(I2))` passa, pois `hash(I2)` gera o mesmo endereço do contrato. [6](#0-5) 
5.  O contrato executa a retirada usando os dados de `I2`, enviando as taxas para o atacante. [7](#0-6)

```text
    bytes32 private immutable _INPUT_HASH;

    constructor() {
        _INPUT_HASH = keccak256(abi.encode(address(this)));
    }

    function _validateImmutables(bytes32 immutablesHash) internal view virtual override {
        bytes32 bytecodeHash;
        assembly ("memory-safe") {
            bytecodeHash := extcodehash(address())
        }
        if (ZkSyncLib.computeAddressZkSync(immutablesHash, bytecodeHash, FACTORY, _INPUT_HASH) != address(this)) {
            revert InvalidImmutables();
        }
    }
```
