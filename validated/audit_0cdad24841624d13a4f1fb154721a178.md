### Title
Unbounded RocksDB reverse-iteration in `get_confirmed_signatures_for_address2` lets a single `getSignaturesForAddress` call scan an attacker-controlled amount of unrooted/unconfirmed history - ([File: ledger/src/blockstore.rs])

### Summary
`Blockstore::get_confirmed_signatures_for_address2` iterates the `AddressSignatures` column in reverse and only appends to `address_signatures` (the vector whose length is checked against `limit`) when an entry's slot is rooted or in `confirmed_unrooted_slots`. Any entry belonging to a pruned/unconfirmed fork causes a `continue` without growing `address_signatures.len()`, so the `while address_signatures.len() < limit` loop keeps consuming iterator steps proportional to how many disqualifying entries exist for that address rather than to `limit`.

### Finding Description
The relevant loop is: [1](#0-0) 

```rust
while address_signatures.len() < limit {
    if let Some(((key_address, slot, transaction_index, signature), _)) = iterator.next() {
        if slot < lowest_slot {
            break;
        }
        if key_address == address {
            if self.is_root(slot) || confirmed_unrooted_slots.contains(&slot) {
                address_signatures.push((slot, signature, transaction_index));
            }
            continue;
        }
    }
    break;
}
```

`confirmed_unrooted_slots` is computed once from the ancestors of `highest_slot` up to `max_root`, i.e., only the slots on the currently confirmed/active fork path: [2](#0-1) 

Every `AddressSignatures` row for `address` whose slot is neither rooted nor an ancestor of `highest_slot` (e.g., a pruned, forked-away, or since-superseded slot) fails both `is_root(slot)` and `confirmed_unrooted_slots.contains(&slot)`, so the `continue` fires and `address_signatures.len()` is unchanged, but the RocksDB reverse iterator (`self.address_signatures_cf.iter(IteratorMode::From(..., IteratorDirection::Reverse))`, set up at lines 4662-4670) still advances one entry per loop iteration. Because `AddressSignatures` keys are `(address, slot, transaction_index, signature)`, all entries for `address` are contiguous in reverse-sorted key space, meaning the iterator must walk through every disqualifying entry for that address before it can find enough qualifying ones (or hit `lowest_slot`/end of the address's key range) to satisfy `limit`.

An attacker who funds a single address and repeatedly transacts from it, especially in a manner that causes many of its transactions to land on forks that are ultimately not part of the finalized chain (e.g., submitting many low-fee transactions across the ledger's operational lifetime such that a large fraction end up on now-pruned/unrooted forks), accumulates many `AddressSignatures` rows that will always be skipped. A single `getSignaturesForAddress`/`getConfirmedSignaturesForAddress2` RPC call with `limit` (e.g., 1000) then forces the node to iterate through all of that address's historical disqualified entries in the reverse direction, which is proportional to total attacker-authored transaction volume, not to `limit`.

This path is directly reachable from the public RPC surface: `JsonRpcRequestProcessor::get_signatures_for_address` calls `self.blockstore.get_confirmed_signatures_for_address2(address, highest_slot, before, until, limit)` after only checking transaction-history-enabled and commitment level — there is no check limiting how many disqualified entries the iterator may traverse: [3](#0-2) 

No existing guard (parameter-limit clamp, commitment check, or iterator step budget) bounds the number of skipped/disqualified rows scanned per call — the only limits found (`check_is_at_least_confirmed`, `check_if_transaction_history_enabled`) gate access, not iteration cost.

### Impact Explanation
This matches the "unbounded cost for a single low-rate call" impact category: CPU and I/O time for one JSON-RPC request scale with attacker-controlled on-chain data volume (number of `AddressSignatures` rows the attacker's own address accumulated on non-finalized forks) rather than with the caller-supplied `limit`. A single call at or below the `CLUSTER_SLOT_TIME_TARGET / 2` rate can force the validator to perform a RocksDB reverse scan over large key ranges, consuming disproportionate CPU/I/O and degrading RPC responsiveness for that node, without any additional privilege beyond funding one address and sending many self-originated transactions.

### Likelihood Explanation
Preconditions are fully within reach of an unprivileged attacker: fund one address, send many transactions from it over time (some inevitably landing in slots later pruned/forked away, which is a normal, unprivileged occurrence on any live cluster with forking), then issue a single `getSignaturesForAddress` call with a moderate `limit`. No leader/validator control, gossip, or config manipulation is needed — only ordinary transaction submission and one RPC call. The attack is fully repeatable and its cost scales directly with the attacker's own investment in producing history, making it a realistic low-cost-to-attacker, disproportionate-cost-to-victim scenario.

### Recommendation
Bound the work done per call independent of `limit`, e.g.:
- Track a maximum number of iterator steps (or disqualified entries) examined per call and return a partial/paginated result (with an indicator that more data may exist) once that bound is exceeded, rather than looping until `limit` qualifying entries are found or the address's key range is exhausted.
- Alternatively, maintain a per-address index of only rooted/confirmed signatures (or periodically prune `AddressSignatures` rows for slots that fall below `lowest_cleanup_slot`/are known unrooted) so stale unrooted entries do not remain indefinitely, since currently pruning/cleanup only removes very old slots via `ensure_lowest_cleanup_slot`, not specifically unrooted-fork residue.
- Add an explicit `RpcCustomError`/early-return when the scan exceeds a configurable step budget, to cap wall-clock time for a single request.

3. Insert a small number (e.g., 5) of genuinely rooted/confirmed transactions for `address0` at the tail of the key range so the loop can eventually satisfy a small `limit`.

Expected assertion: `iterator step count (or elapsed time) for N=50000 disqualified rows` is approximately proportional to N, violating the invariant that per-call cost should be bounded by `limit`.
