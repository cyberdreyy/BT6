## Finding

### Title
`getVoteAccounts` RPC handler has unbounded per-call cost that scales with the number of on-chain vote accounts, which any unprivileged user can grow indefinitely - (File: `rpc/src/rpc.rs`)

### Summary
The `getVoteAccounts` JSON-RPC method decodes and processes every vote account tracked in the bank's stakes cache on every single call, with no cap on how many vote accounts exist. Because creating a vote account is a permissionless, low-cost operation available to any unprivileged user (no stake delegation required), an attacker can cheaply and continuously grow the set of vote accounts the RPC node must scan, making every future `getVoteAccounts` call progressively more expensive — the same growth-based unbounded-cost pattern described in the `settleFunding` report, where cost scales with the number of "markets" rather than with the size/rate of the caller's own request.

### Finding Description
`JsonRpcRequestProcessor::get_vote_accounts` calls `bank.vote_accounts()` [1](#0-0)  which returns the full `VoteAccountsHashMap` maintained by the bank's stakes cache [2](#0-1) . This map includes every vote account known to the bank, including ones with zero stake, as confirmed by the test that creates a zero-stake vote account and observes `bank.vote_accounts().len()` grow accordingly [3](#0-2) .

The handler then iterates over the *entire* map, unconditionally decoding the vote state (`account.vote_state_view()`), computing `last_voted_slot()`, `num_epoch_credits()`, and building an `epoch_credits_iter()...collect()` for every entry, before any current/delinquent partitioning or stake filtering happens: [4](#0-3) . The only post-processing filter (`keep_unstaked_delinquents`) is applied *after* this expensive per-account decode work has already been paid for every account [5](#0-4) .

Unlike other array-style RPC endpoints in this codebase that explicitly cap the amount of unbounded-growth work a single call can trigger (e.g., `MAX_MULTIPLE_ACCOUNTS`, `MAX_GET_CONFIRMED_BLOCKS_RANGE`, `MAX_GET_INFLATION_REWARD_ADDRESSES` in `rpc-client-types/src/request.rs`) [6](#0-5) , `getVoteAccounts` has no equivalent bound on the number of vote accounts it will scan and decode per call.

Creating a new vote account is a cheap, permissionless operation: any keypair holder can send a `VoteInstruction::InitializeAccount` after allocating a rent-exempt vote account (a modest, fixed lamport cost, no delegated stake required). This mirrors exactly the report's root cause — a per-request cost proportional to the count of some on-chain entity ("markets" in Hubble, vote accounts here) that grows over time and that ordinary users can add to.

### Impact Explanation
As unprivileged users create more vote accounts (at negligible individual cost), the cost of every subsequent `getVoteAccounts` call on any RPC node grows without bound. This is a form of unbounded per-call cost for a low-rate call: a single call today may be cheap, but the attacker's one-time (per account) creation cost permanently raises the cost of all future calls for all clients — directly analogous to the Hubble `settleFunding` finding where the DAO adding more markets caused iterative gas cost growth that could eventually exceed usable limits. In an RPC context this manifests as increased CPU time and latency per call, and at scale, potential request timeouts or resource exhaustion on the JSON-RPC thread pool for a routinely-used, unauthenticated endpoint.

### Likelihood Explanation
Likelihood is moderate to high: creating a vote account requires only paying for a small rent-exempt reserve and issuing a permissionless instruction — no elevated privileges, no significant capital, and no coordination with other actors. An attacker (or several cheap keypairs) could create a large number of dust vote accounts over time, and each one permanently adds to the fixed cost baseline of every `getVoteAccounts` call thereafter.

### Recommendation
- Cap or paginate the number of vote accounts processed by `get_vote_accounts`, mirroring the pattern used elsewhere in `rpc.rs` (`MAX_MULTIPLE_ACCOUNTS`, `MAX_GET_INFLATION_REWARD_ADDRESSES`, etc.).
- Apply cheap filters (e.g., minimum stake, or `filter_by_vote_pubkey`) *before* performing the expensive `vote_state_view()` decode and `epoch_credits_iter()` collection, so zero/low-stake dust vote accounts don't incur full decode cost.
- Consider excluding zero-stake vote accounts from the scan entirely by default unless explicitly requested, since they are already filtered out of the default delinquent set post-hoc.

### Proof of Concept
1. An unprivileged actor repeatedly submits `VoteInstruction::InitializeAccount` transactions to create N zero-stake vote accounts (rent-exempt cost only, no delegated stake needed).
2. As shown in the existing test harness, each such creation increases `bank.vote_accounts().len()` by one [3](#0-2) .
3. Any client calls the public `getVoteAccounts` RPC method; the handler iterates and fully decodes vote state for all N accounts [4](#0-3)  before discarding the zero-stake, non-delinquent-kept ones.
4. As N grows (attacker-controlled, unbounded), the per-call CPU cost of `getVoteAccounts` for every RPC consumer grows correspondingly, with no limit enforced anywhere in the call path.
