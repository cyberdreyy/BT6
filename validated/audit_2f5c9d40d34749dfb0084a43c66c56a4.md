### Title
Confirmations from a deleted/revoked multisig key are not purged from other pending requests, allowing a request to execute below the live-member threshold - (File: `multisig/src/lib.rs`)

### Summary
The external report's bug class is a stale-approval binding failure: `ERC4626RouterBase.withdraw` records an approval sized for the wrong unit (assets instead of shares), so a value that should have been "spent" or invalidated persists and is wrongly reused/counted on a later call, breaking the equality between what was authorized and what is actually consumed. The analogous binding in this repository is `confirmations counted == confirmations from currently live/authorized members`. In `MultiSigContract`, a signing key's `confirm()` votes are stored in a `confirmations: UnorderedMap<RequestId, HashSet<PublicKey>>` map keyed only by `request_id`. When a key is removed via the `DeleteKey` multisig action, the cleanup logic only removes requests and confirmation sets for requests that key itself *originated*; it does not scrub that key's public key from confirmation sets of *other* pending requests it merely confirmed. A stale confirmation from a now-deleted key therefore continues to count toward `num_confirmations` on any pending request, permanently reducing the number of genuinely live signers needed to execute it.

### Finding Description
`MultiSigRequestAction::DeleteKey` execution in `execute_request`: [1](#0-0) 
only filters and removes **requests originated by** the deleted `pk` (`r.signer_pk == pk`), removing their `confirmations` entries wholesale. It never iterates over `self.confirmations` to strip `pk` out of the `HashSet<PublicKey>` of *other* requests that key may have already confirmed as a non-originating signer.

`confirm()` counts confirmations purely by set size, with no check that any public key in the set is still an active/authorized key at the moment of counting: [2](#0-1) 

`add_request` records `signer_pk` only for the request originator, not for confirmers: [3](#0-2) 

The binding that should hold is: `confirmations.len() at execution == number of currently-authorized keys that confirmed`. After a `DeleteKey` action removes a key that had already confirmed some *other* pending request, that equality breaks: the confirmation count includes a key that is no longer live, so a request can cross the `num_confirmations` threshold with strictly fewer currently-authorized confirmers than intended.

### Impact Explanation
This is Critical impact per the rubric: "a multisig request executed below threshold." Concretely, with `num_confirmations = 2` and 3 keys (A, B, C):
1. Key A (compromised or malicious holder) calls `confirm()` on a pending request originated and awaiting confirmation from B (e.g., a `Transfer` or `FunctionCall` request), adding its pk to that request's confirmation set. This alone does not reach the threshold, so the request stays pending.
2. The other members detect A is compromised and remove it via a properly-executed `DeleteKey{public_key: A}` request. `execute_request`'s `DeleteKey` branch only deletes requests A itself created; the pending request from step 1 (created by a different key) is untouched, and A's stale confirmation stays embedded in its `confirmations` set.
3. Now only B and C are legitimately authorized. If just one of them (say C) calls `confirm()` on that same pending request, the set size becomes 2 (`A`'s stale + `C`'s new), satisfying `confirmations.len() + 1 >= num_confirmations`, and `execute_request` runs the transfer/function-call/key-addition — executed with only one genuinely live confirmer instead of the required two.

This breaks the multisig's core custody guarantee (funds/actions gated behind `k`-of-`n` live signers) and can directly move NEAR or grant access below the configured threshold.

### Likelihood Explanation
The prerequisite is a key that confirms (but does not originate) a request and is later removed via `DeleteKey` — a normal incident-response action (e.g., revoking a suspected compromised key) that the contract's own design anticipates. No owner misconfiguration, redeploy, or privileged action is required beyond the multisig's own normal key-management flow. Any actor who briefly holds one of the `n` keys (including one about to be revoked) can leave behind a permanent "ghost vote" simply by calling `confirm()` before deletion. This is a straightforward, self-contained sequence reachable purely through the contract's public `confirm` and `DeleteKey`-triggered `execute_request` paths.

### Recommendation
When executing `DeleteKey`, iterate all entries of `self.confirmations` (not just those for requests originated by the deleted key) and remove the deleted public key from every confirmation set; alternatively, validate at `confirm()`/execution time that every public key in a request's confirmation set still corresponds to a currently authorized access key on the contract account before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy `MultiSigContract::new(2)` with three access keys A, B, C added via `AddKey` requests.
2. Using key B, call `add_request` for a `Transfer{amount}` request (`request_id = R`). This does not auto-confirm from A/C.
3. Using key A, call `confirm(R)` — `confirmations[R] = {A}`, threshold (2) not yet met, request stays pending. [4](#0-3) 
4. Using keys B and C together, add and confirm a `DeleteKey{public_key: A}` request to threshold and execute it. Its `execute_request` branch only removes requests where `r.signer_pk == A` (i.e., none it originated) — `confirmations[R]` is untouched. [1](#0-0) 
5. Key A's access key is now deleted on-chain, so A can no longer sign transactions — but `confirmations[R]` still contains `A`.
6. Using key C alone, call `confirm(R)`. `confirmations.len() (1) + 1 >= num_confirmations (2)` evaluates true, and `execute_request(R)` runs the `Transfer`, moving funds with only C as a genuinely live confirmer instead of the required 2-of-3.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
