### Title
Byzantine signer double-counted across the approval and rejection weight pools in the node's `StackerDBListener` block-status tally - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The mining node's `StackerDBListener` tallies signer weight into two independent pools, `total_weight_approved` and `total_weight_rejected`, keyed by different membership sets (`gathered_signatures` for approvals, `responded_signers` for rejections). The guard that prevents double-counting is asymmetric: a rejection is only counted the first time a slot is seen in `responded_signers` at all, but an acceptance is counted whenever the slot is *not yet in `gathered_signatures`*, with no check against `responded_signers`/prior rejection. This allows a single signer that rejects first and later accepts the same block to have its weight counted in *both* pools simultaneously, breaking the disjointness invariant `total_weight_approved + total_weight_rejected ≤ total_weight` that `SigningCoordinator::get_block_status` relies on to decide "globally accepted" vs "globally rejected."

### Finding Description
In `stacks-node/src/nakamoto_node/stackerdb_listener.rs`, the `Accepted` branch adds weight only guarded by whether the slot already has a stored signature: [1](#0-0) 

and separately marks `block.responded_signers.insert(slot_id)` after adding the weight, with no check of whether that slot previously rejected.

The `Rejected` branch, by contrast, only adds rejection weight the first time the slot is seen at all, via `block.responded_signers.insert(slot_id)`: [2](#0-1) 

Because `responded_signers` is a single set shared by both message kinds, the order of events matters:
- If a signer accepts first, then later sends a rejection, `responded_signers.insert(slot_id)` on the reject path returns `false` (already present), so the rejection weight is correctly *not* added again — no double count.
- If a signer rejects first (adding its weight to `total_weight_rejected` and marking `responded_signers`), and *later* sends an acceptance, the acceptance path only checks `gathered_signatures` (which does not yet contain that slot), so the same signer's weight is added a second time — now to `total_weight_approved` — with no retraction of the earlier rejection weight from `total_weight_rejected`.

This is consumed by `SigningCoordinator::get_block_status` in `signer_coordinator.rs`, which treats the two totals as if they partition the signer set: it checks the reject-threshold first, then the accept-threshold: [3](#0-2) 

With the asymmetric double-count, one byzantine signer (a single slot, reachable purely via gossip over StackerDB — no majority required) can contribute its weight to both sides of the ledger. Combined with genuinely-rejecting signers that are just under the 30% blocking minority, that single signer's weight being recounted into `total_weight_rejected` on top of already being counted in `total_weight_approved` can push the observed rejection weight over the `> total_weight - weight_threshold` bar even though the *distinct* signer weight actually opposing the block never reached the true blocking minority.

### Impact Explanation
This lets a lone signer manufacture a "globally rejected" outcome (`NakamotoNodeError::SignersRejected`) for a block that a genuine supermajority (≥70% distinct weight) already approved, by reject-then-accept sequencing that inflates the tallied rejection weight beyond the real rejecting coalition's weight. That is a rejection being recounted/mixed into a decision that should have been an accept — the exact "rejection recounted as an accept" class of safety break called out for Critical severity: the node's acceptance/rejection accounting no longer reflects the actual, disjoint, signed intents of the signer set, and a legitimately-approved block can be discarded, or conversely the same discrepancy can be steered to make the coordinator return early with a signature set collected via inflated bookkeeping.

### Likelihood Explanation
The trigger requires only one non-honest or misbehaving signer sending its own two ordinary StackerDB messages (`Rejected` then `Accepted`) for the same block hash — no supermajority, no other signer's key, and no node access beyond standard StackerDB gossip that any signer already has. This is directly analogous to the original report's pattern of a single actor controlling both sides of an interaction (there, two colluding accounts feeding `executeTrade`; here, one signer's own reject-then-accept sequence feeding the node's tally) to force a favorable/incorrect outcome through code that assumes counterparties/tally sets are independent and honest.

### Recommendation
Make the acceptance-weight bookkeeping symmetric with the rejection path: before adding to `total_weight_approved`, check that the slot is not already present in a rejection-only membership set (or fold both into one `responded_signers` gate that is consulted by both branches before any weight is added), so a given signer's weight can only ever land in one of the two pools for a given block, preserving `total_weight_approved + total_weight_rejected ≤ total_weight`.

### Proof of Concept
1. Node proposes block `B`; `StackerDBListener` initializes `total_weight_approved = 0`, `total_weight_rejected = 0`, `responded_signers = {}`, `gathered_signatures = {}` for `B`.
2. Byzantine signer `X` (slot `S`, weight `w`) broadcasts `BlockResponse::Rejected` for `B`. Node processes it: `responded_signers.insert(S)` succeeds → `total_weight_rejected += w`.
3. Signer `X` then broadcasts a valid `BlockResponse::Accepted` (with a legitimately-signed signature) for the same `B`. Node checks `!gathered_signatures.contains_key(S)` → true (never signed before) → `total_weight_approved += w`; `gathered_signatures.insert(S, sig)`; `responded_signers.insert(S)` (no-op).
4. Now `X`'s weight `w` is counted in both `total_weight_approved` and `total_weight_rejected`. Combined with other genuine rejecters whose combined weight is just under the 30% blocking minority, `total_weight_rejected` (inflated by `w` a second time) can cross `total_weight - weight_threshold`, causing `get_block_status` in `signer_coordinator.rs` to return `Err(NakamotoNodeError::SignersRejected { .. })` even though the true, distinct approving weight (excluding the double count) had already reached the 70% threshold.
