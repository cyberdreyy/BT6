## #Vulnerability found for this question.

### Title
Missing signer check on `InitializeNonceAccount` allows authority hijacking / front-running of nonce account initialization - (File: `programs/system/src/system_instruction.rs`, `programs/system/src/system_processor.rs`)

### Summary
The `SystemInstruction::InitializeNonceAccount` instruction handler and the underlying `initialize_nonce_account` function never verify that the nonce account (or any other authorized party) has signed the transaction. Any unprivileged transaction sender can submit an `InitializeNonceAccount` instruction against a system-owned, `Uninitialized`, correctly-sized nonce account and set an arbitrary `nonce_authority` of their own choosing — exactly the same class of bug as the reported `Subaccount.sol::init()` issue, where the absence of an access-control check on a one-shot initialization function lets an attacker race the legitimate owner and seize control of the account.

### Finding Description
`initialize_nonce_account` only checks that the account is writable, has sufficient lamports for rent, and is in `State::Uninitialized`. It performs no check that the transaction was signed by the account itself or by any expected authority before writing the caller-supplied `nonce_authority` into the account state: [1](#0-0) 

The dispatcher in `system_processor.rs` likewise does not require the nonce account to be a signer for this instruction — it only fetches the `recent_blockhashes` and `rent` sysvars before calling `initialize_nonce_account`: [2](#0-1) 

This is in stark contrast to every other nonce instruction in the same file, which explicitly call `check_signer` against either the nonce account key or the current `data.authority` (`withdraw_nonce_account`, `authorize_nonce_account`, `advance_nonce_account`): [3](#0-2) [4](#0-3) 

A nonce account only reaches `Uninitialized`-but-funded state after `SystemInstruction::CreateAccount`/`Allocate`+`Assign`, which does require the new account's key to sign (`assign` enforces `address.is_signer(signers)`): [5](#0-4) 

However, `CreateAccount` and `InitializeNonceAccount` are two independent instructions. If they are not submitted atomically in the same transaction (e.g., a wallet or dApp that creates the account first and initializes it in a follow-up transaction, or any protocol that pre-funds a nonce-account address before initializing it), the account sits in a public, `Uninitialized`, rent-exempt state that anyone can observe on-chain. Because `InitializeNonceAccount` requires no signature at all, an attacker can race the legitimate owner with their own single transaction naming themselves as `nonce_authority`.

### Impact Explanation
Once the attacker's `InitializeNonceAccount` transaction lands first, the nonce account's `data.authority` becomes the attacker's pubkey. The legitimate owner's later attempt to initialize will fail with `InvalidAccountData` since the account is no longer `Uninitialized`. The attacker, now holding the authority, can subsequently call `WithdrawNonceAccount`, which only checks `check_signer(&data.authority)` — i.e., the attacker's own signature — to withdraw the full account balance (funded by the legitimate creator) to any address: [6](#0-5) 

This results in concrete unsigned/unauthorized fund loss for the legitimate account creator and full compromise of the nonce account's durable-nonce capability (which can also be leveraged for other durable-transaction abuse), matching the "concrete unsigned fund movement" bar for a valid analog.

### Likelihood Explanation
Exploitation requires only that a nonce account exist on-chain in the `Uninitialized` state (funded and sized correctly) with its `InitializeNonceAccount` instruction not yet executed — a state reachable whenever creation and initialization are not strictly bundled into a single atomic transaction. Any observer monitoring the mempool/recent transactions for such accounts can submit a single, ordinary transaction with higher priority to seize authority; no special privilege, precompile, or leader access is needed.

### Recommendation
Require a signer check in `initialize_nonce_account` (and its `system_processor.rs` dispatch arm), analogous to the other nonce instructions — at minimum, require the nonce account itself (or an explicitly designated authority) to be a signer of the `InitializeNonceAccount` instruction, closing the front-running window.

### Proof of Concept
1. Legitimate user Alice submits a `CreateAccount`/`Allocate`+`Assign` transaction that creates account `N` owned by the system program, sized for `NonceState`, and funded with rent-exempt lamports, intending to initialize it as her durable nonce account in a subsequent transaction.
2. Before Alice's `InitializeNonceAccount(alice_authority)` transaction lands, attacker Mallory observes account `N` in the `Uninitialized` state and submits her own transaction: `InitializeNonceAccount(mallory_authority)` referencing account `N` as a writable, non-signer account, per the dispatch code in `system_processor.rs` lines 448-467.
3. Because `initialize_nonce_account` (`system_instruction.rs` lines 163-211) performs no signer check, Mallory's transaction succeeds and sets `data.authority = mallory_authority`.
4. Alice's subsequent `InitializeNonceAccount` transaction fails with `InstructionError::InvalidAccountData` because the account is no longer `Uninitialized`.
5. Mallory then submits `WithdrawNonceAccount` signed by `mallory_authority`, which passes the `check_signer(&data.authority)` check in `withdraw_nonce_account` (lines 125-151) and drains the account's lamports (originally funded by Alice) to an address of Mallory's choosing.

pub(crate) fn initialize_nonce_account(
    account: &mut BorrowedInstructionAccount,
    nonce_authority: &Pubkey,
    rent: &Rent,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    if !account.is_writable() {
        ic_msg!(
            invoke_context,
            "Initialize nonce account: Account {} must be writeable",
            account.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }

    match account.get_state::<Versions>()?.state() {
        State::Uninitialized => {
            let min_balance = rent.minimum_balance(account.get_data().len());
            if account.get_lamports() < min_balance {
                ic_msg!(
                    invoke_context,
                    "Initialize nonce account: insufficient lamports {}, need {}",
                    account.get_lamports(),
                    min_balance
                );
                return Err(InstructionError::InsufficientFunds);
            }
            let durable_nonce =
                DurableNonce::from_blockhash(&invoke_context.environment_config.blockhash);
            let data = nonce::state::Data::new(
                *nonce_authority,
                durable_nonce,
                invoke_context
                    .environment_config
                    .blockhash_lamports_per_signature,
            );
            let state = State::Initialized(data);
            account.set_state(&Versions::new(state))
        }
        State::Initialized(_) => {
            ic_msg!(
                invoke_context,
                "Initialize nonce account: Account {} state is invalid",
                account.get_key()
            );
            Err(InstructionError::InvalidAccountData)
        }
    }
}

pub(crate) fn authorize_nonce_account(
    account: &mut BorrowedInstructionAccount,
    nonce_authority: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    if !account.is_writable() {
        ic_msg!(
            invoke_context,
            "Authorize nonce account: Account {} must be writeable",
            account.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }
    match account
        .get_state::<Versions>()?
        .authorize(signers, *nonce_authority)
    {
        Ok(versions) => account.set_state(&versions),
        Err(AuthorizeNonceError::Uninitialized) => {
            ic_msg!(
                invoke_context,
                "Authorize nonce account: Account {} state is invalid",
                account.get_key()
            );
            Err(InstructionError::InvalidAccountData)
        }
        Err(AuthorizeNonceError::MissingRequiredSignature(account_authority)) => {
            ic_msg!(
                invoke_context,
                "Authorize nonce account: Account {} must sign",
                account_authority
            );
            Err(InstructionError::MissingRequiredSignature)
        }
    }
}
