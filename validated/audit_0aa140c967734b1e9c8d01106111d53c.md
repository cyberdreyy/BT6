## Verdict

Confirmed root cause path exists, but the exploit is not viable given the checks already present in the codebase.

### Title
Cache key wildcard characters ('*', '?') are not stripped by `cachekey.Sanitize` and flow unescaped into IAM session `Resource` ARN - ([File: cache/s3v2/s3.go])

### Summary
`generateSessionPolicy` builds the IAM `Resource` as `arn:%s:s3:::%s/%s` with `objectName` interpolated directly via `fmt.Sprintf` [1](#0-0) . `cachekey.Sanitize`, which normalizes attacker-controlled `cache:key` values, only handles path separators, dot-traversal, backslashes, and trailing whitespace — it does not strip or reject `*`/`?` [2](#0-1) . This means a cache key like `project-x/*` can reach `generateSessionPolicy` and produce an IAM `Resource` such as `arn:aws:s3:::bucket/.../project-x/*`, which AWS IAM evaluates with wildcard semantics.

### Finding Description
The comment at `cache/s3v2/s3.go:245-248` is misleading: encoding/json only guarantees the *value is syntactically escaped inside the JSON policy document* — it does **not** neutralize IAM's own wildcard-matching semantics for `*`/`?` inside a `Resource` string. JSON escaping and IAM glob-matching operate at different layers; a literal `*` character survives JSON marshalling unchanged (`"..."` is still `*` after unmarshalling by AWS), and AWS STS/IAM then treats it as a wildcard when evaluating `s3:GetObject`/`s3:PutObject` against object keys.

However, whether an attacker can actually get `*`/`?` into `objectName` depends on the upstream object-name construction, which is a different code path from the one in scope:
- `cachekey.Sanitize` normalizes but does not reject `*`/`?` [2](#0-1) .
- `cache.GetAdapter` joins the sanitized/hashed key onto a fixed `basePath` (`<path>/[runner/<token>/]project/<id>/`) and verifies the resulting path stays prefixed by `basePath+"/"` to block `../` traversal [3](#0-2) . This check only defends against path traversal (`..`), not against wildcard characters remaining in the final segment.
- When `FF_HASH_CACHE_KEYS` is enabled, the human key is hashed with SHA-256 before becoming the object name (`resolvedKey = sha256(...)`) [4](#0-3) , which incidentally eliminates any raw wildcard characters from the object path in that mode. When the flag is off (default), the *sanitized but unhashed* human key is used as the object name, and `*`/`?` would pass through untouched into `fullPath`, then into `objectName`, then into `generateSessionPolicy`'s `Resource`.

So the reachable path is: `.gitlab-ci.yml cache:key: 'project-x/*'` → `cachekey.Sanitize` (no-op on `*`) → `cache.GetAdapter` builds `fullPath` containing the literal `*` → `s3v2.New` sets `objectName` → `GetGoCloudURL`/`FetchCredentialsForRole` → `generateSessionPolicy(bucketName, objectName, upload)` → `AssumeRole` with `Resource: "arn:aws:s3:::bucket/.../project-x/*"`.

### Impact Explanation
If reachable, the impact is concrete: the AssumeRole session's temporary credentials would be scoped to `s3:GetObject`/`s3:PutObject` over every object matching the wildcard pattern under the shared bucket, not just the caller's own cache key — enabling cross-job/cross-pipeline cache read/write within the project's namespace (or beyond, if the wildcard is placed at a project-namespace boundary) for the lifetime of the 1-hour AssumeRole session.

### Likelihood Explanation
Feasibility is limited by the effective `objectName` format actually produced by `GetAdapter`/`New` for the `s3v2` adapter in default configuration. I could not fully verify from the index whether an additional segment (e.g., `/cache.zip` suffix, or additional path components appended after the raw key) or another sanitation layer specific to the `s3v2` adapter's object-name construction further constrains where `*`/`?` could land, which affects how much "sibling" scope a wildcard would actually expand to (e.g., `project-x/*` only ever matches within the fixed `project/<id>/` prefix already baked into `basePath`, meaning it cannot escape to other projects — only to sibling cache keys/objects within the same project's cache namespace). This bounds the blast radius to intra-project cross-job/cross-pipeline cache access rather than genuine cross-project access, since `basePath` (containing `project/<id>`) is not attacker-controlled and is prepended before the user-controlled key segment [5](#0-4) .

### Recommendation
In `generateSessionPolicy` (`cache/s3v2/s3.go`), escape or reject IAM wildcard metacharacters (`*`, `?`) in `objectName` before interpolating into the `Resource` ARN — e.g., percent-encode them (`%2A`, `%3F`), which S3/IAM treats as literal characters in ARNs, or reject cache keys containing them at the `cachekey.Sanitize` stage. Add a unit test asserting `generateSessionPolicy` output for `objectName` values containing `*`/`?` never permits access beyond the literal key.

// Sanitize validates and normalises a cache key.
// Cache keys may contain path separators. The function:
//   - decodes URL-encoded '/' (%2f) and '.' (%2e) characters
//   - replaces all '\' with '/'
//   - resolves path traversals (., ..) within a virtual root
//   - strips trailing whitespace from the rightmost path segments,
//     removing any that become empty after trimming
func Sanitize(cacheKey string) (string, error) {
	if cacheKey == "" {
		return "", nil
	}

	// Decode percent-encoded chars and normalise separators, then
	// resolve traversals against a virtual root so ".." can never
	// escape beyond the root.
	cleaned := path.Clean("/" + normaliser.Replace(cacheKey))

	// Strip the leading "/" we added, split into segments, then walk
	// backwards trimming trailing whitespace from the rightmost
	// segments—dropping any that become empty.
	parts := strings.Split(cleaned[1:], "/")
	n := len(parts)
	for n > 0 {
		parts[n-1] = strings.TrimRightFunc(parts[n-1], unicode.IsSpace)
		if parts[n-1] != "" {
			break
		}
		n--
	}

	key := strings.Join(parts[:n], "/")

	if key == "" {
		return "", fmt.Errorf("cache key %q could not be sanitized", cacheKey)
	}

	return key, nil
