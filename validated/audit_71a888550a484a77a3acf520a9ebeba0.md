### Title
Order-dependent floor-at-zero clamping in `process_sync_aggregate` lets a duplicate-committee validator escape an owed penalty, creating Gwei from nothing - (File: specs/altair/beacon-chain.md)

### Summary
`process_sync_aggregate` applies sync-committee rewards and penalties one committee slot at a time via `increase_balance`/`decrease_balance`, in the order the slots appear in `committee_indices`. When a validator occupies the sync committee twice in the same period (a "duplicate committee" — a legitimate outcome of `get_next_sync_committee_indices`'s sampling-with-replacement, not any adversarial action), and its balance is (or is driven to) `0`, the order in which its two slots are processed determines whether an owed penalty is actually collected, because `decrease_balance` floors at zero instead of tracking a signed net delta.

### Finding Description
`process_sync_aggregate` builds `committee_indices` from `state.current_sync_committee.pubkeys` and iterates them in lock-step with `sync_aggregate.sync_committee_bits`, calling `increase_balance` for a participating slot and `decrease_balance` for a non-participating slot, immediately, per slot: [2](#0-1) 

`decrease_balance` (phase0) clamps at zero: it decreases `state.balances[index]` by `min(amount, state.balances[index])`, never going negative. Because the two slot-updates for the same duplicate validator are applied sequentially rather than netted first, the *order* of participation across the two positions changes the outcome even though the economic intent (reward the one participated slot, penalize the one missed slot) should net to the same result regardless of order.

This is confirmed directly by the repo's own test harness, which documents the divergence and explicitly disables the invariant check for one ordering: [3](#0-2) 

- If the validator starts at balance `0` and participates only in the **first** occurring slot, then misses the **second**: reward is applied first (balance becomes `> 0`), then the penalty for the missed slot is applied and brings it back to exactly `0`. Net effect: reward and penalty cancel, balance stays `0` — correct.
- If the validator starts at balance `0` and participates only in the **second** occurring slot (misses the first): the penalty for the missed first slot is applied while balance is still `0`, so `decrease_balance` clamps it to `0 - min(penalty, 0) = 0` (the penalty is effectively lost/unrealized). Then the reward for the participated second slot is applied, raising the balance to `> 0`. Net effect: the validator keeps the reward without ever having paid the penalty it owed — Gwei is created that should have been forfeited.

The test file's own comment on the second case states: "Skip `validate_sync_committee_rewards` because it doesn't handle the balance computation order inside the for loop", confirming the spec authors are aware the general reward/penalty invariant does not hold for this ordering, i.e., the outcome depends on which duplicate slot happens to come first in `committee_indices`.

This breaks the equality that a validator's net sync-committee earnings for a period should equal `(participant_reward × #participated slots) − (participant_reward × #missed slots)`, independent of processing order — the report analog to the InfinityExchange bug where per-order computation (there: `startGasPerOrder`; here: sequential clamped balance mutation instead of a netted delta) produces an outcome that differs depending only on iteration position, not on economic substance.

### Impact Explanation
This is a Gwei-creation bug: a validator that should net to zero (or to a smaller balance) after being selected twice and missing one of the two slots can instead retain reward Gwei it never should have kept, because the corresponding penalty was clamped away by the zero floor before the reward arrived. No other party pays for this discrepancy in the same block; the value is effectively minted relative to the correct accounting the protocol intends (reward cancels penalty for the same increment of duty). While the low-balance trigger condition (near-zero balance immediately followed by exit/slashing-adjacent states) is a narrow window in practice for mainnet-active validators with normal balances, the underlying spec logic unconditionally has this order dependency, and any validator whose balance is driven to (or starts at) zero — e.g., right after being slashed to minimum or immediately post-exit-adjacent processing where balance could be zero/near-zero within the same sync period — is exposed. This is a systemic spec-level equality violation, not a hypothetical: the repository's own test suite proves it occurs under valid, non-adversarial, spec-following execution (duplicate sync committee selection is an expected, permitted outcome of `get_next_sync_committee_indices`).

### Likelihood Explanation
Duplicate sync-committee selection is a normal, unprivileged, non-adversarial outcome of the committee-sampling algorithm (`get_next_sync_committee_indices` samples with replacement), so it occurs periodically on mainnet purely from validator-count/effective-balance statistics — no attacker action, coalition, or malicious peer is required. The zero-balance trigger condition is the main likelihood constraint; it is most easily hit in test/minimal presets (as the repo's own test demonstrates) but is not spec-prohibited for any validator whose balance has been driven to (or created at) zero through other legitimate paths within the same sync-committee period.

### Recommendation
Compute the *net* reward/penalty per validator index before mutating balances, rather than applying `increase_balance`/`decrease_balance` immediately per duplicate slot in `committee_indices` order. Concretely, aggregate `participant_reward * (#participations) - participant_reward * (#misses)` per unique validator index first (e.g., via a `Counter`/dict keyed by validator index, mirroring the reference computation already present in the test helper `compute_sync_committee_participant_reward_and_penalty`), then apply a single signed `increase_balance`/`decrease_balance` call per validator so the result is independent of slot ordering.

### Proof of Concept
Using the repo's own test harness (`_run_sync_committee_selected_twice` in `tests/core/pyspec/eth_consensus_specs/test/altair/block_processing/sync_aggregate/test_process_sync_aggregate.py`), configured on `MAINNET` preset to guarantee a duplicate sync-committee index:

1. Set `pre_balance = 0` for the duplicate validator.
2. Case A — participate in first occurring slot only, miss the second: `process_sync_aggregate` yields `state.balances[validator_index] == 0` (reward then penalty cancels) — as asserted at line 280.
3. Case B — participate in second occurring slot only, miss the first: `process_sync_aggregate` yields `state.balances[validator_index] > 0` (penalty clamped at zero, then reward applied) — as asserted at line 301, with the accompanying code comment explicitly noting the general reward/penalty invariant `validate_sync_committee_rewards` cannot be applied here due to loop-order-dependent balance computation.

Both cases start from identical inputs (same validator, same net participation count: 1 participated / 1 missed) yet produce different final balances purely due to iteration order over `committee_indices` — the spec's per-slot immediate-mutation loop is the exact root cause, directly analogous to the reported `startGasPerOrder`-in-loop bug.
