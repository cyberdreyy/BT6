### Title
Unfunded instant-withdraw receipts from a pre-default epoch are skipped by the defaulted-epoch lookup and their par claim reverts on the recovery-reserve guard — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The Swafe bug was a "wrong-list lookup": an item moved to one collection was searched for in another, so it effectively disappeared and recovery became impossible. `IdleCreditVault` has the same shape: instant-withdraw receipts are stored per-epoch in `instantWithdrawsRequestsByEpoch[user][epoch]` / `instantWithdrawClaimsByEpoch[epoch]`, but the unfunded remainder is tracked only in the aggregate `pendingInstantWithdraws`. After `finalizeDefaultRecovery`, `_claimDefaultedInstantWithdrawRequest` searches **only** `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]`, so any unfunded instant receipt recorded under an earlier epoch is invisible — the direct analog of "recover list never queried".

### Finding Description
- `requestInstantWithdraw` writes `instantWithdrawsRequestsByEpoch[user][currentEpoch]` and bumps `instantWithdrawClaimsByEpoch[currentEpoch]` plus aggregate `pendingInstantWithdraws` [1](#0-0) .
- Instant funding is partial-safe: the CDO collects what it can via `collectInstantWithdrawFunds`, which decrements `pendingInstantWithdraws`; the unfunded part can therefore survive an epoch boundary (the contract's own comments acknowledge "cash covered only part of the instant queue") [2](#0-1) .
- At finalization, `defaultPendingClaimBasis` adds **only** `instantWithdrawClaimsByEpoch[epochNumber]` — claims keyed to older epochs are excluded from `totalBasis`, so `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` is inflated [3](#0-2) .
- On claim, `_claimDefaultedInstantWithdrawRequest` reads only `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]`; older-epoch receipts keep their full `instantWithdrawsRequests[user]` balance [4](#0-3) .
- Execution then falls through to the par path, which pays `instantWithdrawsRequests[user]` via `_transferFundedClaim` — but that function reverts when `balance - defaultRecoveryReserve < amount` [5](#0-4) . The prefunded share of those old receipts was swept into `defaultRecoveryReserve` by `_defaultPrefundedInstantReserve` [6](#0-5) , so the claim reverts permanently.

### Impact Explanation
Permanent freezing of user funds: a user whose instant-withdraw request was only partially funded before the defaulted epoch can never claim — the defaulted path ignores the old-epoch key and the par path reverts on the reserve guard. Additionally, excluding the old-epoch basis from `totalBasis` raises `defaultRecoveryPrice`, overpaying other claimants and draining the reserve (solvency/fair-payout violation). Loss equals the user's unfunded instant receipt amount.

### Likelihood Explanation
Requires a specific sequence: an instant request partially funded at `startEpoch` (borrower liquidity shortfall), epoch advancing, then borrower default and `finalizeDefault`. Instant queues are a normal vault feature and partial funding is explicitly designed-for in the code, so the precondition is reachable without privileged misbehavior. The attacker is any unprivileged lender whose receipt lands in the wrong-epoch bucket — no action needed beyond requesting an instant withdraw and waiting.

### Recommendation
Make the defaulted-instant claim epoch-agnostic: iterate/aggregate `instantWithdrawsRequestsByEpoch` across all epochs with unfunded basis (or track an `unfundedInstantBasis` per user), include the full unfunded instant basis — not just `instantWithdrawClaimsByEpoch[epochNumber]` — in `defaultPendingClaimBasis`, and exclude the already-prefunded share of non-current-epoch receipts from `_defaultPrefundedInstantReserve` or credit it to those users. Add regression tests: (1) request instant withdraw, (2) partially fund at startEpoch, (3) default next epoch and finalize, (4) verify the user can still claim through `claimInstantWithdrawRequest`.

### Proof of Concept
Foundry fork PoC (mirroring `test/foundry/IdleCreditVault.t.sol` default-finalization helpers):

```solidity
function testPreDefaultEpochInstantReceiptFrozen() external {
    address user = makeAddr('instant-user');
    _depositWithUser(user, 10_000 * ONE_SCALE, true);

    // Epoch 0 running: user requests instant withdraw
    vm.prank(user);
    cdoEpoch.requestInstantWithdraw(5_000 * ONE_SCALE, address(AAtranche));

    // startEpoch(1): CDO funds only PART of the instant queue
    // (drain borrower liquidity so collectInstantWithdrawFunds is partial),
    // pendingInstantWithdraws stays > 0 with basis keyed under epoch 0.
    _startEpochWithPartialInstantFunding();

    // Epoch 1: borrower defaults, owner finalizes recovery
    _stopEpochAndCheckPrices(1, initialProvidedApr, 0);
    _checkDefault();
    uint256 recovered = _expectedRecovered();
    deal(defaultUnderlying, manager, recovered);
    vm.startPrank(manager);
    IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();

    // instantWithdrawsRequestsByEpoch[user][0] holds the receipt, but
    // _claimDefaultedInstantWithdrawRequest only reads [defaultRecoveryEpoch].
    // Par path reverts on the reserve guard -> permanent freeze.
    vm.prank(user);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.claimInstantWithdrawRequest();
}
```

Uncertain: whether the CDO's `startEpoch`/`getInstantWithdrawFunds` path can actually leave a non-zero `pendingInstantWithdraws` spanning an epoch boundary — the strategy comments indicate partial instant funding is possible, but I could not fully trace `IdleCDOEpochVariant` funding logic within the iteration budget. If instant queues are always fully funded at startEpoch, the precondition collapses and this finding would not hold.

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
