### Title
Post-default withdraw requests pay 1:1 from the recovery reserve without adding to its basis, draining funds owed to defaulted-epoch claimants and active LPs - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
After `finalizeDefaultRecovery`, `requestWithdraw` mints a receipt for the requester and records it in `postDefaultRequests`, but no new underlying enters the strategy and the claim is paid 1:1 out of `defaultRecoveryReserve` — a reserve that was sized only to cover `activeBasis + pendingBasis` at `defaultRecoveryPrice`. Each post-default claim therefore consumes reserve that was already promised to earlier claimants, leaving the last claimants with an underflow revert (permanent freeze) or a shortfall.

### Finding Description
`finalizeDefaultRecovery` computes `reserveAmount` and `recoveryPrice = reserveAmount * 1e18 / totalBasis` where `totalBasis = activeBasis + pendingBasis` [1](#0-0) . The reserve is the only pot backing (a) defaulted-epoch normal/instant receipts paid at `defaultRecoveryPrice` and (b) active LPs, whose claim was crystallized by burning/minting the CDO's strategy-token balance to `activeBasis * recoveryPrice` [2](#0-1) .

In the post-default branch of `requestWithdraw`, the CDO's strategy tokens are burned, a receipt is minted to the user, and `postDefaultRequests[_user] = _amount` is set — with no `safeTransferFrom` moving underlying into the strategy [3](#0-2) . The claim then routes to `_claimPostDefaultWithdrawRequest`, which pays the full `amount` (1:1, "the haircut was applied when the request was made") via `_transferDefaultRecovery` [4](#0-3) , which decrements `defaultRecoveryReserve` by the full amount [5](#0-4) .

The accounting mismatch: a post-default requester's basis in the CDO was only worth `recoveryPrice` per unit (virtualPrice was lowered at finalization), yet the receipt is redeemable at par against the reserve. When `recoveryPrice < 1e18`, every post-default claim of `A` removes `A` from a reserve in which the requester was only ever owed `A * recoveryPrice`. The excess `A * (1 - recoveryPrice)` is taken from the share of defaulted-epoch receipts and active LPs. Once cumulative post-default claims exceed the surplus, `defaultRecoveryReserve -= _amount` underflows (Solidity 0.8 checked arithmetic), permanently reverting all remaining `_claimDefaultedWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest` and `_claimPostDefaultWithdrawRequest` calls [6](#0-5) .

The guard in `_transferFundedClaim` only protects the reserve from funded-claim spending [7](#0-6) ; nothing limits aggregate post-default payouts to the unallocated remainder of the reserve.

### Impact Explanation
An unprivileged lender (or any address the KYC'd user routes claims through) who deposits after default finalization can request a withdraw and claim underlying at par from the recovery reserve, extracting up to `1/recoveryPrice` times their fair share. Concretely, with `recoveryPrice = 0.5e18` and a reserve of 100 tokens, a post-default requester claiming 60 tokens receives 60 instead of their ~30-token-proportional share, and the remaining 40 tokens cannot cover the outstanding defaulted-epoch basis (which expected ~50). The final claimants' transactions revert on the `defaultRecoveryReserve -= _amount` underflow — permanent freezing of unclaimed recovery funds.

### Likelihood Explanation
Requires only that (a) the vault has defaulted and been finalized with `recoveryPrice < 1e18`, and (b) the CDO still permits deposits/redeems post-default so an attacker can obtain tranche shares and call `requestWithdraw` via `IdleCDOEpochVariant`. Both are normal protocol states; the attacker needs no privileged role. Each post-default claim is a single ordinary user flow — no timing race or reentrancy needed.

### Recommendation
Either fund post-default withdrawals from newly returned borrower liquidity (pull underlying into the strategy at request or claim time, like `collectWithdrawFunds`), or pay post-default claims at `defaultRecoveryPrice` and include their basis in the reserve accounting. At minimum, cap aggregate post-default payouts at `underlyingToken.balanceOf(this) - defaultRecoveryReserve - (reserve already owed)` so they can never consume the finalized recovery allocation.

```solidity
import "forge-std/Test.sol";
import {IdleCreditVault} from "../contracts/strategies/idle/IdleCreditVault.sol";

// Fork mainnet at a block where the credit vault is deployed, or deploy via
// IdleCreditVaultFactory + IdleCDOEpochVariant as in test/foundry/IdleCreditVault.t.sol.
contract PostDefaultReserveDrainTest is Test {
    IdleCreditVault vault;
    address cdo;      // IdleCDOEpochVariant
    address lender;   // KYC'd LP with pending receipt in defaulted epoch
    address attacker; // unprivileged EOA

    function test_PostDefaultClaimDrainsRecoveryReserve() external {
        // 1. Epoch running; lender requests withdraw (receipt in epoch N).
        // 2. Borrower defaults; owner calls _handleBorrowerDefault/finalizeDefaultRecovery
        //    with recoveredAmount < totalBasis  =>  defaultRecoveryPrice = 0.5e18.
        // 3. Attacker deposits into the CDO post-default (buys tranche shares at
        //    the haircut virtualPrice), then calls CDO.requestWithdraw ->
        //    vault.requestWithdraw -> postDefaultRequests[attacker] = amount.
        // 4. Attacker claims: vault.claimWithdrawRequest -> _claimPostDefaultWithdrawRequest
        //    pays `amount` 1:1 from defaultRecoveryReserve.
        // 5. Lender's claim now reverts:
        vm.prank(cdo);
        vm.expectRevert(); // defaultRecoveryReserve -= _amount underflows
        vault.claimWithdrawRequest(lender);
        // Reserve invariant broken: sum(claims paid) > reserveAmount.
    }
}
```

Note on verification limits: I reviewed `IdleCreditVault.sol` in full, but could not trace the post-default deposit/`requestWithdraw` path inside `IdleCDOEpochVariant.sol` within the available iterations — specifically whether the CDO ever transfers underlying to the strategy to back post-default receipts. If such a transfer exists elsewhere, the reserve-drain conclusion would need re-checking; absent that funding leg, the reserve double-spend stands as described.
