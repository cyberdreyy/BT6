### Title
External Initiator credentials bypass job-binding and can trigger runs on arbitrary int-ID jobs - ([File: core/web/auth/auth.go], [File: core/web/pipeline_runs_controller.go])

### Finding Description
`AuthenticateExternalInitiator` in `core/web/auth/auth.go` authenticates the EI's access key/secret against `store.FindExternalInitiator`/`bridges.AuthenticateExternalInitiator`, but on success it unconditionally sets a synthetic run-role user in the Gin context: [1](#0-0) 

This synthetic `*clsessions.User` is indistinguishable from a real logged-in user via `auth.GetAuthenticatedUser`: [2](#0-1) 

The `/v2/jobs/:ID/runs` route is mounted with `AuthenticateExternalInitiator` as one of the accepted auth methods, ahead of token/session auth: [3](#0-2) 

Inside `PipelineRunsController.Create`, the code attempts to gate int-ID job runs to "users only, EIs not allowed" via the comment, but it implements this check using `auth.GetAuthenticatedUser`, which — as shown above — also returns `ok=true` for EI-authenticated requests because `AuthenticateExternalInitiator` stores the same `SessionUserKey`: [4](#0-3) 

The actual `*bridges.ExternalInitiator` object obtained during authentication is separately stored under `SessionExternalInitiatorKey` and retrievable via `GetAuthenticatedExternalInitiator`, but that accessor is never called anywhere else in the codebase (confirmed by search — the only usages are its definition and the setter in `auth.go`), so nothing ever checks which specific EI issued the request or which job/bridge it is scoped to. Consequently, any valid EI credential can pass the `isUser` check in `Create` and trigger `prc.App.RunJobV2(ctx, jobID, nil)` for an arbitrary int job ID that has nothing to do with the EI's registered bridge/job.

### Impact Explanation
An attacker holding valid credentials for one external initiator (registered for bridge/job X) can call `POST /v2/jobs/<unrelated-int-ID>/runs` for a completely unrelated job Y and successfully trigger a pipeline run, because: (1) the run-role check only verifies presence of a `SessionUserKey`, which is populated identically for both real users and any authenticated EI, and (2) no code anywhere binds the authenticated EI (`GetAuthenticatedExternalInitiator`) to the job ID being triggered. This is unauthorized cross-EI job/pipeline triggering — matching the "unauthorized job run" bounty impact class, and could result in unintended fund movement or on-chain actions for jobs unrelated to the EI's registration.

### Likelihood Explanation
Precondition is minimal: only a valid access key/secret pair for any registered external initiator is required (no admin/edit privileges, no knowledge of other jobs' bridge configuration beyond guessing/enumerating int job IDs, which are sequential integers and thus easily enumerable). The flaw is deterministic and repeatable — every EI credential will pass `isUser` for every int-ID job.

### Recommendation
- In `PipelineRunsController.Create`, explicitly reject requests where the caller is an EI rather than checking only for a `SessionUserKey` — use `auth.GetAuthenticatedExternalInitiator` to detect EI-authenticated requests and reject them from the int-ID path (restoring the comment's stated intent), or
- If EI-triggered int-ID runs are intended to be supported, add explicit binding validation: look up the job's associated external initiator/webhook spec and compare it against `GetAuthenticatedExternalInitiator(c).ID`/`Name`, rejecting the request if they don't match.
- Consider not reusing `SessionUserKey` for EI pseudo-authentication; use a distinct marker/type so `GetAuthenticatedUser` cannot conflate real users with EI principals.

### Proof of Concept
Handler-level Go test plan:
1. Create two external initiators X and Y via `ExternalInitiatorsController.Create` (or ORM directly), and two jobs, JobX (intended to be triggered by EI X) and JobY (intended to be triggered by EI Y), both with int IDs.
2. Send `POST /v2/jobs/<JobY.ID>/runs` with headers `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` set to EI X's credentials (not EI Y's).
3. Assert current (buggy) behavior: response is `200/201` and `prc.App.RunJobV2` is invoked for JobY — i.e., EI X successfully triggered JobY despite having no registered relationship to it.
4. After the fix, assert the same request returns `401/403` (or is otherwise rejected), and only requests bound to the correct EI/job succeed.
