### Title
Session.Kill() does not force-close an in-flight terminal exec/attach connection, allowing pod/container terminal access to survive job cancellation - ([File: session/session.go])

### Summary
`Session.Kill()` and `Session.closeTerminalConn()` both call `terminal.Conn.Close()` and then nil out `s.terminalConn`, but for the Kubernetes executor `Close()` is a no-op, and for the Docker executor `Close()` only cancels a `context.Context` that is no longer read by the already-running proxy loop. A WebSocket `/exec` request that has already passed `withAuthorization` and is blocked inside `terminal.ProxyTerminal`/`terminal.ProxyStream`/`terminal.ProxyWebSocket` is therefore not interrupted by job cancellation, letting a previously-authorized terminal session keep talking to the executor's exec/attach stream after the job has been killed.

### Finding Description
`Session.execHandler` (`session/session.go:146-191`) obtains a `terminal.Conn` via `newTerminalConn()`, stores it in `s.terminalConn`, and then blocks inside `terminalConn.Start(w, r, s.TimeoutCh, s.DisconnectCh)` [1](#0-0) . `Start` for both executors ultimately blocks inside `terminal.ProxyTerminal`, which just runs `proxyFunc()` synchronously and returns only when it completes [2](#0-1) .

When the job is canceled, `Session.Kill()` and `closeTerminalConn()` each independently lock `s.lock`, call `conn.Close()`, and nil `s.terminalConn` [3](#0-2) [4](#0-3) . Neither passes any cancellation signal into the blocked `Start`/`ProxyTerminal` call, they merely dereference the field.

- Kubernetes: `terminalConn.Close()` in `executors/kubernetes/terminal.go` is a literal no-op (`return nil`) [5](#0-4) . There is no mechanism at all to stop `terminal.ProxyWebSocket(w, r, t.settings, wsProxy)` once it's running; the exec/attach WebSocket to the pod keeps proxying traffic until the client disconnects or the pod itself terminates.
- Docker: `terminalConn.Close()` cancels `t.ctx` via `cancelFn()` [6](#0-5) , but `t.ctx` is only used for `ContainerExecCreate`/`ContainerExecAttach` (already completed by the time `Start` is blocked in `ProxyTerminal`) and for `t.executor.waiter.Wait(t.ctx, ...)`. The actual data-plane proxy, `terminal.ProxyStream(w, r, dockerTTY, proxy)`, operates on the already-established hijacked connection (`dockerTTY`) and is not wired to `t.ctx` at all [7](#0-6) . Cancelling the context therefore does not interrupt an in-progress attach/exec stream; only the container-exit watcher goroutine and future context-dependent calls are affected, and the exit watcher path only fires `stopCh` when the container actually exits, not on job cancellation.

Thus, once a `/exec` WebSocket has passed `withAuthorization` and is inside `Start`/`ProxyTerminal`, calling `Kill()` does not actually interrupt the shell session; it only clears runner-side bookkeeping (`s.terminalConn = nil`). The `TimeoutCh`/`DisconnectCh` mechanism inside `ProxyTerminal` is the only path that can stop the loop, and cancellation of the *build* is not plumbed into either channel.

### Impact Explanation
An attacker/user who has already opened an interactive terminal to their job's container/pod (a legitimate feature) retains a live, functioning shell into the torn-down job's sandbox after the job/pipeline is canceled by GitLab, because the underlying exec/attach stream is not force-closed — only the Runner's session bookkeeping is cleared. For Kubernetes this is unconditional (Close is a no-op); for Docker it depends on whether cancellation happens to also race with attach/exec creation, but once the stream is established, cancellation has no effect on the live data-plane connection. This violates the invariant that terminal access must not survive job cancellation and gives persistent access to a job's container/pod for as long as the underlying process/container keeps running or the client keeps the WebSocket open.

### Likelihood Explanation
Preconditions: the interactive web terminal feature must be enabled and the user must open a terminal session for their own job (a normal, self-authorized action any pipeline author can do) and then have the job canceled while the terminal is attached. This is easily and repeatably reproducible — it does not require exploiting `withAuthorization` or any other auth boundary, only using a documented user-facing feature and canceling the job at the right point, which a user fully controls (they can trigger their own job cancellation or a pipeline can be canceled independently while their terminal remains attached).

### Recommendation
Plumb job/session cancellation into the in-flight terminal proxy loop instead of relying solely on `Conn.Close()` dereferencing a shared field:
- Add a cancellation channel/context to `terminal.Conn.Start`/`ProxyTerminal` (e.g., a `killCh chan struct{}` or `context.Context`) that `Session.Kill()` explicitly signals, and have `ProxyTerminal`'s select statement also watch for it to unblock `proxyFunc()`/force-close the underlying stream.
- For Kubernetes, implement `terminalConn.Close()` to actually terminate the WebSocket exec connection (e.g., store and close the underlying `wsProxy`/websocket connection rather than a no-op).
- For Docker, wire `dockerTTY`/`ContainerExecAttach`'s hijacked connection to `t.ctx` (or an explicit close call) so that cancelling the context actually closes the hijacked stream used by `ProxyStream`.
- Ensure `Kill()` blocks (with a bounded timeout) until the underlying stream is confirmed closed, not just until the local reference is nilled.

### Proof of Concept
Go integration test outline (in `session` package, extended with fake executors mirroring `executors/kubernetes/terminal.go` and `executors/docker/terminal.go`):
```go
func TestSessionKillForceClosesInFlightExec(t *testing.T) {
    // 1. Build a fake terminal.Conn whose Start() blocks on a real
    //    net.Pipe()/httptest exec stream (simulating ProxyWebSocket/ProxyStream),
    //    and whose Close() mirrors the Kubernetes/Docker no-op/ctx-cancel behavior.
    // 2. Start a Session, SetInteractiveTerminal with the fake terminal.
    // 3. Open a websocket client to `${Endpoint}/exec`, wait until Start() is
    //    confirmed blocked inside the proxy loop (e.g. via a signal channel).
    // 4. Call session.Kill() and start a timer.
    // 5. Assert that the underlying simulated exec/attach connection
    //    (net.Pipe end) receives EOF/is closed within a bounded time
    //    (e.g. 2s), failing the test if it is still readable/writable,
    //    proving the connection was only dereferenced, not terminated.
}
```
Expected result on current code: the pipe/stream remains open and readable/writable well past the bounded timeout for the Kubernetes-style fake `Conn` (Close is no-op) and, for the Docker-style fake `Conn`, cancelling the context does not close the already-hijacked stream, demonstrating that `Kill()` fails to terminate live terminal access.

```go
func (s *Session) closeTerminalConn(conn terminal.Conn) {
	s.lock.Lock()
	defer s.lock.Unlock()

	err := conn.Close()
	if err != nil {
		s.log.WithError(err).Warn("Failed to close terminal connection")
	}

	if reflect.ValueOf(s.terminalConn) == reflect.ValueOf(conn) {
		s.log.Warningln("Closed active terminal connection")
		s.terminalConn = nil
	}
}
```

```go
func ProxyTerminal(timeoutCh, disconnectCh, proxyStopCh chan error, proxyFunc func()) {
	disconnected := make(chan bool, 1)
	// terminal exit handler
	go func() {
		// wait for either session timeout or disconnection from the client
		select {
		case err := <-timeoutCh:
			proxyStopCh <- err
		case <-disconnected:
			// forward the disconnection event if there is any waiting receiver
			nonBlockingSend(
				disconnectCh,
				errors.New("finished proxying (client disconnected?)"),
			)
		}
	}()

	proxyFunc()
	disconnected <- true
}
```
