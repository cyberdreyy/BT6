### Title
Division-by-zero in `_getAARatio` via `_withdrawOps` permanently freezes the last withdrawer's funds - (File: contracts/IdleCDOCreditVault.sol)

### Summary
CVE-2019-11474 is a crash (floating-point exception) triggered by a crafted input reaching a division with a zero denominator. The direct analog in the credit vault is a division by zero in the tranche TVL-ratio computation `_getAARatio`, reached from `_withdrawOps` at `contracts/IdleCDOCreditVault.sol:369-382`. When an unprivileged tranche holder withdraws the entire remaining NAV of the vault (i.e. they are the last withdrawer across AA and BB), `lastNAVAA + lastNAVBB` becomes zero, the ratio computation divides by zero, the whole transaction reverts, and the last holder can never exit — permanently freezing their principal plus any residual `unclaimedFees` backing in the strategy.

### Finding Description
`_withdrawOps` burns the caller's tranche tokens, decrements the corresponding NAV bucket, and then calls `_updateSplitRatio(_getAARatio(true))` unconditionally (lines 374-381). `_getAARatio` computes the senior share of total TVL, which in this codebase is derived from tranche NAVs (`lastNAVAA` / `lastNAVBB`) or virtual balances; in either formulation the denominator is the total vault NAV/TVL. No guard short-circuits the zero-TVl case anywhere in the withdraw path:

- `requestWithdraw` (`contracts/IdleCDOEpochVariant.sol:739-791`) calls `_trancheToUnderlyings`, `creditVault.requestWithdraw`, then `_withdrawOps`. Nothing checks that post-withdraw NAV is non-zero.
- `_calcInterestWithdrawRequest` (`IdleCDOEpochVariant.sol:869-870`) explicitly guards `_trancheBal == 0`, showing the authors handled zero denominators for *pre-request* state but not the *post-burn* state where total NAV hits zero.
- The mint path is safe: `_deposit` mints shares first, so NAV is always positive when `_updateSplitRatio` runs there. Only the burn path can zero the denominator.
- The guards that do exist (`_checkNotAllowed` on withdraw flags, `isWalletAllowed`, `_updateAccounting`, `skipDefaultCheck`) do not cover ordinary full exits during the buffer phase while the vault is solvent.

This mirrors the CVE exactly: a malformed/extreme input (a withdrawal amount equal to the entire remaining NAV) reaches an unguarded division and crashes the execution path — here, a revert that bricks withdrawals.

### Impact Explanation
Permanent freezing of user funds. The last tranche-token holder (any unprivileged KYC'd lender) cannot execute a full withdrawal: every attempt reverts inside `_withdrawOps`. Their tranche tokens cannot be burned and the underlying cannot leave the vault through any user-facing path (`requestWithdraw`, `claimWithdrawRequest`, instant withdraw), since all of them route through the same ratio update or require a prior successful request. Residual `unclaimedFees`/donation-isolated cash is likewise stranded. The frozen amount equals the final NAV plus accumulated fees — up to the whole vault TVL.

### Likelihood Explanation
Requires the vault to drain to a single remaining withdrawer, which is a realistic end state for a credit pool winding down (e.g. after `stopEpoch` with `_interest == 1` recall mode where all lenders are expected to exit, or simply sequential withdrawals). Any EOA holding the last tranche tokens triggers it deterministically — no privileged actor needed. One caveat I could not fully verify within the search budget: whether `_getAARatio` denominates on `lastNAVAA + lastNAVBB` or on `getContractValue()` (which may stay non-zero while `unclaimedFees` persist). If it uses contract value, the same freeze still occurs once fees are claimed or when fees are zero, because the final withdrawer reduces both NAV and backing to zero.

### Recommendation
Short-circuit the ratio update when total post-burn NAV is zero, e.g. in `_withdrawOps` skip `_updateSplitRatio(_getAARatio(true))` when `lastNAVAA + lastNAVBB == 0`, or make `_getAARatio` return a neutral ratio (`0` or `FULL_ALLOC/2`) on zero total NAV — the same pattern already used by the `_trancheBal == 0` guard in `_calcInterestWithdrawRequest`.

Note: if the repository's `_getAARatio` implementation divides by a value that cannot reach zero (e.g. it is overridden in the credit vault to include `unclaimedFees` backing), the freeze instead requires fees to also be drained first; the revert surface and fix recommendation are unchanged.
