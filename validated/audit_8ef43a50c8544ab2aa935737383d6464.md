### Title
Stale rejection weight is never cleared when a signer flips from Rejected to Accepted, letting a single signer permanently inflate the miner's blocking-minority tally - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The `SuperPool` finding is a case where an *asymmetric* accounting of two opposing state transitions (deposit vs. withdraw ordering) lets an attacker shift losses without exposing themselves to any. The direct analog in this codebase lives in the miner-side `StackerDBListener::handle_new_stackerdb_chunks` aggregation of `BlockResponse::Accepted` vs. `BlockResponse::Rejected` messages: the two directions of a signer's vote-flip are handled asymmetrically, so a signer who rejects and later reconsiders and accepts leaves a permanent "ghost" rejection behind, silently inflating `total_weight_rejected` forever.

### Finding Description
`StackerDBListener` maintains a single `BlockStatus` per proposed block with two independently-accumulated tallies, `total_weight_approved` and `total_weight_rejected`, plus a shared `responded_signers` set [1](#0-0) .

When an `Accepted` message arrives, the code gates the *approve* weight add on whether the slot already has a stored signature (`gathered_signatures.contains_key`), not on `responded_signers`, and it unconditionally inserts the slot into `responded_signers` afterward: [2](#0-1) 

When a `Rejected` message arrives, the code instead gates the *reject* weight add on `responded_signers.insert(slot_id)` returning `true` (i.e., "have we heard from this signer at all yet"): [3](#0-2) 

This creates two different outcomes depending on which order the signer's votes are observed in, exactly like the reordering-dependent imbalance in the SuperPool report:

- **Accept, then Reject** (a signer reconsiders and rejects after accepting): the `Rejected` handler's `responded_signers.insert(slot_id)` returns `false` because the earlier `Accepted` already inserted it, so `total_weight_rejected` is *not* incremented for this signer. This is a deliberate design choice: elsewhere in the codebase (`signerdb.rs`), once a signature exists it cannot be overwritten by a rejection, because "an old approval could always be used to make a block reach the approval threshold" [4](#0-3) , and the same "approvals are sticky" invariant is echoed in the miner's own `reset_rejections` comment [5](#0-4) .
- **Reject, then Accept** (a signer reconsiders and accepts after rejecting — an explicitly supported flow per `should_reevaluate_reject_reason` [6](#0-5) ): the `Accepted` handler adds the signer's weight to `total_weight_approved`, but nothing in the `Accepted` branch subtracts that signer's weight from `total_weight_rejected`. The stale rejection weight recorded from the earlier message is never removed from the tally.

The result is a permanent, order-dependent asymmetry: a signer who once rejected a block and later reconsiders continues to count against it forever in the miner's blocking-minority computation, even though their current (and final) vote is an acceptance.

### Impact Explanation
`get_block_status` in `signer_coordinator.rs` uses exactly this `total_weight_rejected` field to decide whether to give up on a block proposal and mark it globally rejected, including permanently/temporarily banning transactions the rejecting minority complained about: [7](#0-6) 

Because the ghost rejection weight from a reconsidering signer is never cleared, a single signer (no majority needed) that rejects once and later legitimately accepts can, together with the genuine current opposition of other signers, push `total_weight_rejected` over the `blocking_minority` threshold even though the signer's *current* vote is "accept." This causes the miner to spuriously treat an actually-approved (or approvable) block as globally rejected, abandon the proposal, and potentially move transactions into `temporarily_excluded_txids` / `permanently_excluded_txids` based on stale sentiment — a liveness wedge on block/transaction inclusion driven purely by message-arrival order, mirroring how the SuperPool bug let queue order (not economic reality) determine who bears a loss.

### Likelihood Explanation
This does not require a majority of signers, another signer's key, or node/auth access — a single signer voting Reject and then legitimately Accept (a flow the protocol explicitly supports for reconsiderable reject reasons) is sufficient to poison the tally. It can also be intentionally triggered by one malicious signer to bias the miner against a block it has actually accepted, by rejecting first for a reconsiderable reason and then accepting, leaving its earlier rejection permanently counted.

### Recommendation
Track a single current vote per slot (e.g., an enum `Approved`/`Rejected` per `slot_id` instead of two independently-accumulating counters gated by different sets), and derive `total_weight_approved`/`total_weight_rejected` from that map so a later message from the same signer always supersedes — and correctly reverses the weight contribution of — an earlier one, in both directions.

### Proof of Concept
1. Miner proposes block `B`; signer `S` (weight `w`) rejects `B` for a reconsiderable reason (e.g., `ProposalTooOld`). `handle_new_stackerdb_chunks` processes this, inserting `S`'s slot into `responded_signers` and adding `w` to `total_weight_rejected` [3](#0-2) .
2. `S` reconsiders per `should_reevaluate_reject_reason` and sends `Accepted` for the same `signer_signature_hash`. The `Accepted` branch adds `w` to `total_weight_approved` because `gathered_signatures` doesn't yet contain `S`'s slot, but it never decrements `total_weight_rejected` [2](#0-1) .
3. `total_weight_rejected` now permanently retains `w` even though `S`'s live vote is "accept."
4. If other, currently-genuine rejecting signers' weight plus this stale `w` crosses `total_weight - weight_threshold`, `get_block_status` reports `SignersRejected` and the miner abandons/excludes transactions for a block that in fact has enough real, current acceptance [7](#0-6) .
