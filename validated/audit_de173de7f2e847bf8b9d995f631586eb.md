### Title
Loss-adjusted withdraw receipts are paid at par when the user files a new request in a later epoch — ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The Cacti report is a *stored* injection: a user-controlled value persisted in one context is later interpreted in a privileged query context without re-validation. The vault analog is `lastWithdrawRequest[_user]`: an attacker-controlled stored epoch marker that `claimWithdrawRequest` trusts to locate a loss-adjusted receipt. Because `requestWithdraw` unconditionally overwrites it, a user can "launder" a haircutted receipt (created in an epoch where `stopEpochWithDuration` funded less than `pendingWithdraws`) into a later clean epoch, causing `_claimLossAdjustedWithdrawRequest` to skip it and `_claimFundedWithdrawRequest` to pay it at 100% par.

### Finding Description
- `requestWithdraw` stores `lastWithdrawRequest[_user] = currentEpoch` and accumulates `withdrawsRequests[_user]` / `withdrawsRequestsByEpoch[_user][currentEpoch]` (`IdleCreditVault.sol:282-293`).
- On a partial-funding stop, `collectWithdrawFunds` records `lossRecoveryPriceByEpoch[epochNumber] < RECOVERY_FULL` and zeroes `pendingWithdraws`, but per-user `withdrawsRequests`/`withdrawsRequestsByEpoch` entries for the loss epoch are left intact to be cleared lazily at claim time (`IdleCreditVault.sol:411-430`).
- `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` only (`IdleCreditVault.sol:789-801`). If the user made a second `requestWithdraw` in a later, normally-funded epoch, `lastWithdrawRequest` points at that clean epoch, the price lookup returns 0, and the haircutted receipt is never cleared or haircutted.
- `_claimFundedWithdrawRequest` then pays `withdrawsRequests[_user]` — which still contains the full pre-haircut loss-epoch amount — at par, once `epochNumber > lastWithdrawRequest[_user]` (`IdleCreditVault.sol:319-349`). `_transferFundedClaim` only guards the default recovery reserve, which is 0 in this scenario (`IdleCreditVault.sol:897-906`).

Attack sequence (unprivileged KYC'd lender):
1. Epoch E1 (running): deposit, `requestWithdraw(full)`. Epoch ends with `stopEpochWithDuration(_lossAmount > 0)` → borrower funds `pendingToFund < pendingBasis`; `lossRecoveryPriceByEpoch[E1] = p < 1`.
2. Epoch E2 (buffer): instead of claiming, `requestWithdraw(dust)` → `lastWithdrawRequest[user] = E2`, `withdrawsRequests[user] = lossAmount + dust`.
3. Epoch E2 ends normally → `epochNumber = E2+1 > E2` → `claimWithdrawRequest` pays `lossAmount + dust` at par. The vault only ever received `p * lossAmount` for the E1 receipt; the `(1-p) * lossAmount` difference is paid out of underlyings reserved for other funded receipts.

### Impact Explanation
Direct theft/insolvency equal to `(1 - lossRecoveryPrice) * attacker's loss-epoch claim basis`. The haircut intended to socialize the stop-epoch loss across pending receipts is fully escaped by the attacker and transferred to the remaining funded-receipt claimants, breaking the loss-waterfall and solvency invariants. The attacker only needs to be a tranche-token holder able to call `requestWithdraw`.

### Likelihood Explanation
Requires an epoch ending in `stopEpochWithDuration` with a realized loss — an abnormal but supported code path explicitly designed for borrower shortfalls. All attacker steps are ordinary user calls (`requestWithdraw`, `claimWithdrawRequest`) with no privileged cooperation. The only cost is waiting one additional epoch before claiming.

### Recommendation
Track loss-adjusted receipts per-epoch rather than via a single `lastWithdrawRequest` marker: e.g., iterate/check `lossRecoveryPriceByEpoch` for all epochs with nonzero `withdrawsRequestsByEpoch[_user][e]`, or record the user's earliest pending loss epoch separately so a later request cannot hide it. Alternatively, in `requestWithdraw`, revert or force-claim when `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]] != 0`.

### Proof of Concept
Foundry fork PoC (extends `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
function testLossAdjustedReceiptPaidAtParAfterRerequest() external {
    address attacker = makeAddr('attacker');
    _depositWithUser(attacker, 10_000 * ONE_SCALE, true);

    // Epoch 1: attacker requests full withdraw
    vm.prank(attacker);
    uint256 basis = cdoEpoch.requestWithdraw(0, address(AAtranche));
    _startEpochAndCheckPrices(0);

    // stopEpochWithDuration: borrower funds only 70% of pending basis
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(initialProvidedApr, lossAmount); // loss such that pendingToFund = 0.7 * basis
    uint256 price = IdleCreditVault(address(strategy)).lossRecoveryPriceByEpoch(1);
    assertLt(price, 1e18);

    // Epoch 2 buffer: attacker files dust request, overwriting lastWithdrawRequest
    idleCDO.depositAA(1_000 * ONE_SCALE);           // keep pool alive
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(1, address(AAtranche)); // dust -> lastWithdrawRequest = 2

    _startEpochAndCheckPrices(1);
    _stopEpochAndCheckPrices(1, initialProvidedApr, _expectedFundsEndEpoch()); // epochNumber = 3

    // Claim: loss path skipped (price[2] == 0), funded path pays basis + dust at par
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    // Paid 'basis' at par although vault only received 0.7*basis -> 0.3*basis stolen
    assertGt(underlying.balanceOf(attacker) - balPre, basis * price / 1e18);
}
```
