### Title
Withdrawal requests underpay management fees when epoch start is delayed - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`requestWithdraw` charges a fixed projected management fee of one `epochDuration` once the minimum buffer has elapsed. Because `startEpoch` has no maximum delay, an honest manager can start the next epoch later than `epochEndDate + bufferPeriod`; the withdrawing user then spends longer outside live NAV without paying the corresponding management fee.

### Finding Description
During a withdrawal request, `IdleCDOEpochVariant.requestWithdraw` updates accounting, projects the next-epoch interest, calculates `_totalWithdrawFees`, and permanently fixes the user's net receipt amount. It then adds those projected fees to `pendingWithdrawFees`. [1](#0-0) 

The management-fee duration is calculated as `epochDuration` plus only the remaining buffer time. Once `block.timestamp >= epochEndDate + bufferPeriod`, the function returns exactly `epochDuration`, regardless of how much later the next epoch actually starts. [2](#0-1) 

However, `startEpoch` only enforces the buffer as a minimum delay. It does not require the epoch to start at or before `epochEndDate + bufferPeriod`. [3](#0-2) 

The intended model is explicit: receipts leave live NAV at request time and therefore pay management fees for the remaining buffer plus the following epoch. When the manager starts late, the actual waiting period exceeds the charged period. [4](#0-3) 

For example, with a 30-day epoch, a 2% annualized management fee, and a request submitted exactly at `bufferEnd`, the user is charged for 30 days. If the honest manager starts the epoch 30 days later, the receipt waits 60 days but still pays only the 30-day fee. On 1,000,000 USDC, the underpayment is approximately:

```solidity
1_000_000e6 * 20_000 / 100_000 * 30 days / 365 days
= 16_438.356164e6 // with FULL_ALLOC-equivalent 2% = 2,000:
= 1_643.835616e6
```

### Impact Explanation
The receipt pays less management fee than economically owed for its actual time outside live NAV, so the user receives excess underlying at claim while `feeReceiver`/owner receive correspondingly less. The loss grows linearly with the delayed-start interval and requested principal; with 1,000,000 USDC and a 2% annualized fee, each additional 30-day delay undercollects about 1,643.84 USDC.

This is a direct fee-calculation mismatch rather than rounding. Existing guards do not stop it: withdrawal requests are enabled while the pool is stopped, `requestWithdraw` is callable by an allowed lender, and delayed `startEpoch` remains valid because the buffer is only a lower bound. [5](#0-4) [3](#0-2) 

### Likelihood Explanation
No malicious privileged role is required. The sequence only needs:

1. A normal epoch to stop.
2. The manager to start the next epoch later than `bufferEnd`.
3. An allowed tranche holder to request withdrawal after `bufferEnd`.
4. The manager to later start and stop the epoch normally.
5. The user to claim the undercharged receipt.

Management fees must be nonzero. The issue affects every request made during an extended stopped period and compounds across users.

### Recommendation
Do not finalize waiting-period management fees from a projected fixed epoch duration when the next `startEpoch` timestamp is unknown. Store each receipt's principal and request timestamp, then true-up the management fee at `stopEpoch` or claim using the actual elapsed period from request to the funding stop. Deduct any shortfall before paying the funded claim.

Alternatively, include pending withdrawal principal in the management-fee accrual base until it is funded, so actual elapsed time is naturally charged consistently with live NAV.

### Proof of Concept
A Foundry regression test can reproduce the undercharge:

```solidity
function testWithdrawRequestUnderchargesDelayedEpochStartManagementFee() external {
    uint256 amount = 1_000_000e6;
    uint256 mgmtFeeRate = 2_000; // 2% annualized with FULL_ALLOC = 100_000

    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());
    _setManagementFee(mgmtFeeRate);

    idleCDO.depositAA(amount);
    _transferBurnedTrancheTokens(address(this), true);

    _startEpochAndCheckPrices(0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

    // Request exactly when the minimum buffer has elapsed.
    vm.warp(cdoEpoch.epochEndDate() + cdoEpoch.bufferPeriod());

    uint256 trancheAmount = AAtranche.balanceOf(address(this));
    uint256 principal =
        trancheAmount * cdoEpoch.tranchePrice(address(AAtranche)) / ONE_TRANCHE_TOKEN;

    uint256 requested = cdoEpoch.requestWithdraw(trancheAmount, address(AAtranche));
    uint256 bookedFee = cdoEpoch.pendingWithdrawFees();

    uint256 chargedFee =
        principal * mgmtFeeRate * cdoEpoch.epochDuration() /
        (FULL_ALLOC * 365 days);
    assertEq(bookedFee, chargedFee);

    // Honest delayed start: 30 additional days beyond the required buffer.
    vm.warp(block.timestamp + 30 days);
    _startEpochAndCheckPrices(0);

    uint256 actualFee =
        principal * mgmtFeeRate * (cdoEpoch.epochDuration() + 30 days) /
        (FULL_ALLOC * 365 days);

    // The request fixed only the one-epoch charge.
    assertLt(bookedFee, actualFee);
    assertEq(actualFee - bookedFee, chargedFee);

    // Fund the epoch and stop normally.
    deal(
        defaultUnderlying,
        borrower,
        cdoEpoch.expectedEpochInterest() +
            IdleCreditVault(address(strategy)).pendingWithdraws()
    );
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    uint256 claimed = cdoEpoch.claimWithdrawRequest();

    // Claim reflects the stale fixed fee, not the actual 60-day wait.
    assertEq(claimed, requested);
}
```

The assertion `actualFee - bookedFee == chargedFee` demonstrates a quantified protocol-fee loss equal to the extra 30 days that the receipt remained outside live NAV.
