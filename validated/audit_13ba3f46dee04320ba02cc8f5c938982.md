### Title
Multisig executes requests using confirmations from removed members, allowing execution below the live-member threshold - (File: `multisig2/src/lib.rs`)

### Summary
The `MultiSigContract::confirm` function counts previously stored confirmations toward `num_confirmations` without verifying that each confirming identity (`MultisigMember`) is still a current member. `delete_member` only purges confirmations/requests that a removed member *authored*, not confirmations that member cast on other, still-open requests. A request can therefore reach the confirmation threshold using a mix of a stale (removed) member's confirmation and fewer than `num_confirmations` live members, letting it execute below the intended live-member threshold.

### Finding Description
`confirm` retrieves the stored confirmation set for a request and simply checks its size: [1](#0-0) 

It never re-validates that the accounts/keys already present in `confirmations` are still in `self.members`; it only checks that the *current* caller hasn't already confirmed.

`delete_member` removes the member from `self.members` and cleans up only the requests that member itself created (`r.member == member`), plus that member's own `num_requests_pk` entry: [2](#0-1) 

It does not scan `self.confirmations` for other, still-pending requests that the removed member confirmed. Those stale confirmation entries remain in storage and continue to count toward `num_confirmations` for any request they were recorded on.

`current_member` is used only to identify/authorize the *new* confirmer for the current call, not to filter the previously stored confirmations set: [3](#0-2) 

The equality that should hold is: `confirmations counted == confirmations from members currently in self.members`. The code allows `confirmations counted > confirmations from live members`, because it never re-checks membership of previously recorded confirmers before using `confirmations.len()` to decide whether to execute the request.

### Impact Explanation
This breaks the multisig's core authorization guarantee. A request (e.g., `Transfer`, `AddKey`, `FunctionCall`) can be executed with fewer live/current member confirmations than `num_confirmations` requires, because a confirmation from an already-removed member is still counted. This is a "multisig request executed below threshold" scenario, which is explicitly listed as Critical impact: unauthorized transfer of funds, addition of access keys, or arbitrary function calls can be pushed through with insufficient live-member consent.

### Likelihood Explanation
Requires an unprivileged sequence achievable by any current members without any special access: (1) a member confirms a pending request, (2) that member is later removed via a normal `DeleteMember` multisig action (independent, valid governance action), (3) another live member then confirms the still-pending request, and the stale confirmation is counted, tipping it over threshold. No malicious insider is strictly required — a normal offboarding of a member while a request is mid-flight is sufficient to trigger under-threshold execution. This makes the likelihood realistic in normal operational flows (member rotation), not just adversarial ones.

### Recommendation
When counting confirmations in `confirm` (and when displaying `get_confirmations`/`get_num_confirmations`), filter the stored confirmation set to only those entries still present in `self.members` before comparing against `num_confirmations`. Alternatively, when a member is deleted, iterate all entries in `self.confirmations` (not just requests they authored) and strip their confirmation record from every pending request.

### Proof of Concept
1. Multisig initialized with members `{A, B, C}` and `num_confirmations = 2`.
2. `A` calls `add_request` to create request `R1` (e.g., `Transfer`).
3. `B` calls `confirm(R1)` → `confirmations[R1] = {B}` (`1 < 2`, not executed yet). See `confirm` logic: [4](#0-3) 
4. Separately, `A` and `C` execute a `DeleteMember { member: B }` request (2/3 confirmations, a normal valid action) — `B` is removed from `self.members`. Since `B` authored no requests, `delete_member`'s cleanup loop removes nothing from `confirmations[R1]`: [5](#0-4) 
5. Members are now `{A, C}`; `num_confirmations` is still `2`.
6. `C` calls `confirm(R1)`. `confirmations[R1].len()` (still `{B}`, size 1) `+ 1 = 2 >= num_confirmations (2)` → `execute_request` runs `R1`.
7. `R1` executes having only one truly live confirming member (`C`), plus a stale confirmation from removed member `B`, i.e., executed below the intended 2-live-member threshold.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Returns current member: either predecessor as account or if it's the same as current account - signer.
    fn current_member(&self) -> Option<MultisigMember> {
        let member = if env::current_account_id() == env::predecessor_account_id() {
            MultisigMember::AccessKey {
                public_key: env::signer_account_pk()
                    .try_into()
                    .unwrap_or_else(|_| env::panic_str("Failed to deserialize public key")),
            }
        } else {
            MultisigMember::Account {
                account_id: env::predecessor_account_id(),
            }
        };
        if self.members.contains(&member) {
            Some(member)
        } else {
            None
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
