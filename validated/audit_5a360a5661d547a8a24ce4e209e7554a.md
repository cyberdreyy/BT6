### Title
Unsanitized raw underlying donations are crystallized as NAV gains in the deposit path, enabling first-depositor share inflation - (File: contracts/IdleCDOCreditVault.sol)

### Summary
The MISP bug class is "output/data used without sanitization." The credit-vault analog is a code path that consumes the raw on-chain `token` balance without first skimming donations. The codebase explicitly treats unsolicited `token` transfers as donations that must be skimmed via `_skimDonatedAssets()` — it is called in `requestWithdraw`, `startEpoch`, `updateAccounting` and `finalizeDefault` — but **not** in `_deposit`, the most frequently called entry point. Worse, `_updateAccounting()` (invoked at the top of `_deposit`) values the vault with `getContractValue()`, which *includes* the raw `token` balance, while `virtualPrice()` and `_accrueManagementFee()` deliberately use `_managedContractValue()` which excludes it. A donation therefore gets "sanitized" differently depending on which path hits it first: if a deposit hits it, the donation is folded into tranche NAV and `unclaimedFees` as real yield. ### Finding Description
During the buffer phase (`epochEndDate + bufferPeriod` not yet passed, pool unpaused):

1. `_deposit` calls `_updateAccounting()` **before** pulling the depositor's funds, and `_updateAccounting` computes `nav = getContractValue()` = `strategyTokenBalance + rawTokenBalance - unclaimedFees`. Any `token` sitting in the contract is treated as accrued gain: `unclaimedFees += (nav - lastNAV) * fee / FULL_ALLOC` and the remainder is split AA/BB via `_virtualPriceAux`, permanently raising `priceAA`/`priceBB` and `lastNAV*`.
2. Because the donation is converted into tranche price (not kept as liquid `token`), the attacker — if they hold the tranche supply — owns the inflated NAV. This enables the classic first-depositor/donation inflation attack:
   - Attacker makes the first deposit of 1 wei → mints `1 * ONE_TRANCHE_TOKEN / oneToken` share (or seeds NAV via a minimal deposit), becoming the sole tranche holder.
   - Attacker `token.transfer(cdo, D)` (direct send, allowed to any EOA).
   - Victim calls `depositAA(V)`. `_updateAccounting` crystallizes `D` into the attacker's tranche NAV, so `_tranchePrice` is huge. `_mintSharesAtCurrPrice` computes `V * ONE / price` which rounds down — for `V < price` it mints **0 shares** while `lastNAVAA += V` and the underlying goes to the strategy. The victim's entire deposit is captured by the attacker's tranche.
   - Even for `V > price`, the victim is under-minted and the rounding dust accrues to the attacker.
3. Skimming does not save this: `_skimDonatedAssets` is absent from `_deposit`, and `virtualPrice`'s use of `_managedContractValue` only affects the view — the state-changing `_updateAccounting` uses the donation-inclusive `getContractValue`.

### Impact Explanation
Direct theft of user deposits: any victim depositing after the attacker's seed+donation receives fewer or zero tranche tokens while their full `V` is credited to `lastNAVAA`/`lastNAVBB` backing the attacker's shares. Loss ≈ victim deposit amount (bounded by attacker's donation `D`; attacker profits `min(V, captured rounding)` — with `V < price` the entire `V` is stolen for cost `D`). Additionally, a non-inflation variant: any donation left before a deposit is partially converted to `unclaimedFees` (performance fee on phantom "yield"), misallocating value to `feeReceiver`. Broken invariant: donation isolation + fair mint/burn.

### Likelihood Explanation
Requires being the first/sole tranche holder (fresh vault, or full exit then re-seed) plus a direct token transfer — both available to any unprivileged EOA during the buffer phase. No privileged action needed; `startEpoch`, `requestWithdraw` skims arrive too late because deposits are the first user-facing interaction. Medium likelihood (needs vault-lifecycle timing), high severity when it lands.

### Recommendation
- Call `_skimDonatedAssets()` at the top of `_deposit` (and `depositDuringEpoch`, which already exists in tests as a skim path — verify it is covered) so raw `token` can never enter `getContractValue` during accounting.
- Alternatively, make `_updateAccounting` use `_managedContractValue()` so state accounting matches `virtualPrice`/`_accrueManagementFee` semantics.
- Revert in `_mintSharesAtCurrPrice`/`_mintShares` when computed `_minted == 0` for a nonzero deposit.
- Seed initial tranche supply/NAV at initialization (dead-share pattern) to kill the first-depositor precondition.

### Proof of Concept
Foundry fork test (buffer phase, pool unpaused, fresh vault):

```solidity
function testDepositDonationInflation() public {
  // attacker seeds vault with dust deposit, becomes sole AA holder
  deal(underlying, attacker, 1);
  vm.startPrank(attacker);
  IERC20(underlying).approve(address(cdo), 1);
  cdo.depositAA(1);
  // donate D directly (no skim in _deposit path)
  uint256 D = 10_000e18;
  deal(underlying, attacker, D);
  IERC20(underlying).transfer(address(cdo), D);
  vm.stopPrank();

  // victim deposits V < price-inflated NAV per share
  uint256 V = 5_000e18;
  deal(underlying, victim, V);
  vm.startPrank(victim);
  IERC20(underlying).approve(address(cdo), V);
  uint256 minted = cdo.depositAA(V);
  vm.stopPrank();

  // victim mints ~0 / dust shares; attacker owns victim's V
  assertLt(minted, 1e18);            // victim effectively got nothing
  // attacker redeems via requestWithdraw / withdrawAA capturing D + V - 1
}
```

Note: I verified `_skimDonatedAssets` is present in `requestWithdraw`, `startEpoch`, `updateAccounting`, and `finalizeDefault`, and that `getContractValue` (used by `_updateAccounting`) includes raw `token` balance while `virtualPrice`/`_accrueManagementFee` use the donation-excluding `_managedContractValue`. I could not fully enumerate every override in `IdleCDOEpochVariant.sol` (e.g., whether a child `_deposit` adds a skim) before finalizing; if a child overrides `_deposit`/`_updateAccounting` to exclude raw tokens, the same reasoning should be re-checked there — the inconsistency between `getContractValue` and `_managedContractValue` inside the same contract remains the core defect either way.

  function getContractValue() public override view returns (uint256) {
    // Credit vault strategy tokens are minted 1:1 with underlyings and use the same decimals.
    return _contractTokenBalance(strategyToken) + _contractTokenBalance(token) - unclaimedFees;
  }

  /// @notice Calculates the current managed net TVL.
  /// @dev Raw underlyings held by the CDO are excluded because unsolicited transfers are skimmed on interactions.
  /// @return Strategy-token-backed TVL net of accrued fees.
  function _managedContractValue() internal virtual view returns (uint256) {
    uint256 strategyTokenBalance = _contractTokenBalance(strategyToken);
    uint256 fees = unclaimedFees;
    return strategyTokenBalance > fees ? strategyTokenBalance - fees : 0;
  }

  function _deposit(uint256 _amount, address _tranche) internal virtual whenNotPaused returns (uint256 _minted) {
    if (_amount == 0) {
      return _minted;
    }
    // check that we are not depositing more than the contract available limit
    _guarded(_amount);
    // interest accrued since last depositXX/withdrawXX is splitted between AA and BB
    // according to trancheAPRSplitRatio. NAVs of AA and BB are updated and tranche
    // prices adjusted accordingly
    _updateAccounting();
    // get underlyings from sender
    address _token = token;
    uint256 _preBal = _contractTokenBalance(_token);
    _transferUnderlyingsFrom(msg.sender, address(this), _amount);
    // mint tranche tokens according to the current tranche price
    _minted = _mintSharesAtCurrPrice(_contractTokenBalance(_token) - _preBal, msg.sender, _tranche);
    // update trancheAPRSplitRatio
    _updateSplitRatio(_getAARatio(true));

    // direct deposit in the strategy
    IIdleCDOStrategy(strategy).deposit(_amount);
  }

  function _updateAccounting() internal virtual returns (bool shutdown) {
    _accrueManagementFee();
    uint256 _lastNAVAA = lastNAVAA;
    uint256 _lastNAVBB = lastNAVBB;
    uint256 _lastNAV = _lastNAVAA + _lastNAVBB;
    uint256 nav = getContractValue();
    uint256 _aprSplitRatio = trancheAPRSplitRatio;
    // If gain is > 0, then collect some fees in `unclaimedFees`
    if (nav > _lastNAV) {
      unclaimedFees += (nav - _lastNAV) * fee / FULL_ALLOC;
    }
    (uint256 _priceAA, int256 _totalAAGain) = _virtualPriceAux(AATranche, nav, _lastNAV, _lastNAVAA, _aprSplitRatio);
    (uint256 _priceBB, int256 _totalBBGain) = _virtualPriceAux(BBTranche, nav, _lastNAV, _lastNAVBB, _aprSplitRatio);
    lastNAVAA = uint256(int256(_lastNAVAA) + _totalAAGain);
    lastNAVBB = uint256(int256(_lastNAVBB) + _totalBBGain);

    // Ordinary losses exhaust BB before reducing AA. Stop normal interactions once BB is wiped,
    // or when an AA-only vault is fully wiped, so the loss must be crystallized explicitly.
    if ((_totalBBGain < 0 && -_totalBBGain >= int256(_lastNAVBB)) || (_lastNAV != 0 && nav == 0)) {
      shutdown = true;
      if (!skipDefaultCheck) revert Default();
      // Keep a total wipe distinguishable from an uninitialized vault when no BB NAV existed.
      if (nav == 0) _priceAA = 0;
      _emergencyShutdown(true);
    }
    priceAA = _priceAA;
    priceBB = _priceBB;
  }
