### Title
`parse_signers` misreports a plain owner as a multisig authority based solely on account count - ([File: transaction-status/src/parse_token.rs])

### Summary
`parse_signers` in `transaction-status/src/parse_token.rs` decides whether to emit an `"authority"`/`"owner"` field or a `"multisigAuthority"`/`"signers"` pair purely by comparing `accounts.len()` to `last_nonsigner_index`, without ever inspecting on-chain account state to confirm the trailing account is actually an initialized SPL Token `Multisig`. An attacker can submit a `Transfer` (or similar) instruction with one extra trailing account pubkey that is not a real multisig, and `getTransaction`/`getConfirmedTransaction` with `jsonParsed` encoding will report the transaction as multisig-authorized even though it isn't.

### Finding Description
`parse_token` dispatches `TokenInstruction::Transfer { amount }` by calling [1](#0-0)  with `parse_signers(map, 2, account_keys, &instruction.accounts, "authority", "multisigAuthority")`.

`parse_signers` itself only checks the length of the accounts slice: [2](#0-1) 

If `accounts.len() > last_nonsigner_index + 1` (i.e., there is at least one account beyond index `last_nonsigner_index`), the function unconditionally treats `accounts[last_nonsigner_index]` as a `Multisig` account address and everything after it as `signers`, emitting `multisigAuthority` + `signers` instead of `authority`. There is no lookup of account data, no check that the account at `last_nonsigner_index` is actually owned by the token program or unpacks as a valid `Multisig` struct - the decision is made from instruction shape alone.

Only a minimum-count check is performed upstream via `check_num_token_accounts`/`check_num_accounts`, which rejects instructions with *too few* accounts but places no upper bound, so an attacker is free to add extra trailing accounts: [3](#0-2) 

An attacker can therefore submit a transaction whose `Transfer` instruction accounts are `[source, destination, ownerPubkey, extraPubkey]` (4 accounts instead of the minimum 3). The instruction will typically fail on-chain at runtime (because `extraPubkey` is not a real multisig and would fail unpacking in the actual SPL Token program), but Agave still records the transaction (success or failure) in the block, and `getTransaction`/`getConfirmedTransaction` with `encoding=jsonParsed` still runs `parse_token`/`parse_signers` over the raw instruction to build the JSON-parsed view regardless of execution outcome. The resulting parsed JSON will contain `"multisigAuthority": "<ownerPubkey>"` and `"signers": ["<extraPubkey>"]` instead of `"authority": "<ownerPubkey>"`, misrepresenting a plain single-owner transfer as multisig-authorized.

This same account-count heuristic is used identically for every `TokenInstruction` variant that calls `parse_signers` (Transfer, Approve, Revoke, SetAuthority, MintTo, Burn, CloseAccount, FreezeAccount, ThawAccount, TransferChecked, ApproveChecked, MintToChecked, BurnChecked, WithdrawExcessLamports, UnwrapLamports), so the misreporting surface spans essentially all common SPL Token instructions.

### Impact Explanation
This falls under the "decoder panic and misreporting" accepted impact category: a downstream integrator (exchange, explorer, indexer) that trusts `jsonParsed` output from `getTransaction` will see a `multisigAuthority`/`signers` structure and conclude the transfer was authorized by a multisig configuration, when in fact no such on-chain multisig exists and the transaction may not even have succeeded. This can cause incorrect authority/owner attribution in downstream systems that rely on RPC-parsed data rather than raw instruction bytes. It does not cause a validator crash, consensus mutation, or unbounded cost - the impact is confined to the display/parsing layer.

### Likelihood Explanation
Trivially reachable: the attacker needs only to submit a single ordinary transaction containing an SPL Token instruction (e.g., `Transfer`) with one extra trailing account appended to the instruction's account list, then issue a single `getTransaction` call with `jsonParsed` encoding. No special privileges, staking, or leader/validator control is required, and the transaction does not even need to succeed on-chain for the ledger entry (and its parsed view) to be produced.

### Recommendation
`parse_signers` (and callers of `parse_token`) should not infer multisig status purely from account count. Where feasible, RPC jsonParsed decoding of token instructions should either (a) clearly document/label this as a "possible multisig" heuristic rather than asserting a definitive `multisigAuthority` field, or (b) when account-state lookups are available in the RPC context, verify the account at `last_nonsigner_index` is actually owned by the token program and successfully unpacks as `Multisig` before choosing the multisig branch, falling back to the plain `owner_field_name` label otherwise.

### Proof of Concept
```rust
// transaction-status/src/parse_token.rs (test module)
#[test]
fn test_transfer_extra_account_misreports_multisig() {
    let program_id = spl_token_2022_interface::id();
    let source = Pubkey::new_unique();
    let destination = Pubkey::new_unique();
    let owner = Pubkey::new_unique();
    let extra_non_multisig_account = Pubkey::new_unique(); // NOT an initialized Multisig

    // Build a raw Transfer instruction with an extra trailing account.
    let mut ix = spl_token_2022_interface::instruction::transfer(
        &program_id, &source, &destination, &owner, &[], 100,
    ).unwrap();
    ix.accounts.push(solana_instruction::AccountMeta::new_readonly(
        extra_non_multisig_account, false,
    ));

    let message = solana_message::Message::new(&[ix], None);
    let compiled_instruction = &message.instructions[0];
    let account_keys = AccountKeys::new(&message.account_keys, None);

    let parsed = parse_token(compiled_instruction, &account_keys).unwrap();
    let info = parsed.info;

    // BUG: parser reports a multisig authority even though `extra_non_multisig_account`
    // is not a real Multisig account - no on-chain state was consulted.
    assert!(info.get("multisigAuthority").is_some());
    assert!(info.get("signers").is_some());
    assert!(info.get("authority").is_none());
    // Expected (fixed) behavior: parser should not assert multisig usage without
    // validating the account state, or should flag this as unverified.
}
```

```rust
fn parse_signers(
    map: &mut Map<String, Value>,
    last_nonsigner_index: usize,
    account_keys: &AccountKeys,
    accounts: &[u8],
    owner_field_name: &str,
    multisig_field_name: &str,
) {
    if accounts.len() > last_nonsigner_index + 1 {
        let mut signers: Vec<String> = vec![];
        for i in accounts[last_nonsigner_index + 1..].iter() {
            signers.push(account_keys[*i as usize].to_string());
        }
        map.insert(
            multisig_field_name.to_string(),
            json!(account_keys[accounts[last_nonsigner_index] as usize].to_string()),
        );
        map.insert("signers".to_string(), json!(signers));
    } else {
        map.insert(
            owner_field_name.to_string(),
            json!(account_keys[accounts[last_nonsigner_index] as usize].to_string()),
        );
    }
}
```
