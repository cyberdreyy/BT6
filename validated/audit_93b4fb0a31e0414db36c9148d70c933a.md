### Title
Deterministic lockup account address allows front-running griefing that permanently occupies `victim.near`'s lockup with attacker-chosen minimal-deposit `LockupArgs` - (File: lockup-factory/src/lib.rs)

### Summary
`LockupFactory::create` derives the lockup account id solely from `sha256(owner_account_id)[..20]` with no binding to the caller, the attached deposit, or any prior-claim check. Because NEAR's `create_account` action fails if the target account already exists, any unprivileged attacker can pre-create `victim.near`'s lockup with only `MIN_ATTACHED_BALANCE` and attacker-chosen `LockupArgs`, permanently blocking the real grantor's later `create` call for the same owner, whose deposit is then refunded rather than delivered.

### Finding Description
The binding the system is supposed to guarantee is:

`NEAR held at sha256(owner_account_id)[..20].<factory> == the real grantor's intended attached_deposit for owner_account_id, established exactly once, by the intended grantor`

In `LockupFactory::create` [1](#0-0) , the lockup account id is computed purely as a deterministic function of `owner_account_id`:

```
let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
let lockup_account_id = format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());
```

There is no check for whether this account already exists, no restriction on who may call `create` for a given `owner_account_id`, and no requirement that `attached_deposit` match any expected grant size — only the floor check `attached_deposit() >= MIN_ATTACHED_BALANCE` [2](#0-1) . The promise chain then does `create_account().deploy_contract(...).transfer(attached_deposit).function_call("new", LockupArgs{...})`, followed by `on_lockup_create` [3](#0-2) .

Exploit flow:
1. Attacker calls `create(owner_account_id="victim.near", lockup_duration=..., ...)` with `attached_deposit == MIN_ATTACHED_BALANCE` exactly, choosing whatever `lockup_duration`, `vesting_schedule`, `release_duration`, and `whitelist_account_id` they like.
2. Since the target account does not yet exist, `create_account()` succeeds, the contract deploys, and the transfer of the attacker's minimal deposit lands. `is_promise_success()` returns true in `on_lockup_create` [4](#0-3) , and the lockup is finalized with attacker-chosen parameters and a trivial balance.
3. The real grantor later calls `create(owner_account_id="victim.near", ...)` with the intended (larger) deposit. `create_account()` now fails because the account id already exists, so the whole promise chain fails, `is_promise_success()` returns false in `on_lockup_create`, and the deposit is refunded to `predecessor_account_id` (the grantor) rather than delivered to `victim.near`'s lockup [5](#0-4) .

None of the existing guards prevent this: there is no `assert_owner`, no foundation-only restriction, no per-owner uniqueness check, and `is_promise_success()` only detects the outcome after the fact — it does not stop the attacker's initial creation from succeeding first. The MIN_ATTACHED_BALANCE floor only bounds the minimum, not the correctness of who is allowed to create the account or with what parameters.

### Impact Explanation
The real grantor can never deliver the intended NEAR/vesting grant to `victim.near`, because that address is permanently occupied by a lockup contract deployed with attacker-chosen `LockupArgs` (duration, vesting schedule, whitelist) and only `MIN_ATTACHED_BALANCE` funded. This matches the Critical category "a lockup deployed with parameters its rightful creator never chose." The griefing is repeatable across any owner account for which the real grant has not yet been created, and costs the attacker only `MIN_ATTACHED_BALANCE` (currently 3,500 NEAR) per victim address, which remains locked in the attacker's own deployed lockup — sunk cost that permanently freezes the addressing slot for that intended beneficiary.

### Likelihood Explanation
The precondition is simply that the attacker calls `create` for a target `owner_account_id` before the legitimate grantor does, which requires no special privilege — any account with `MIN_ATTACHED_BALANCE` NEAR can do it. Since the factory account id and the intended beneficiary account names are typically public/predictable (e.g., known employee or investor NEAR account names), an attacker can front-run the grantor for any address whose real grant transaction hasn't yet landed. The attack is fully deterministic and reproducible.

### Recommendation
Before scheduling `create_account`, check whether `lockup_account_id` already exists (e.g., via a `Promise::new(lockup_account_id).account_balance()` view style check is not directly available on-chain, but the underlying design flaw should be fixed by binding lockup account creation authorization to a trusted party (e.g., only the foundation or a signed request from the intended owner), rather than allowing any depositor to create a lockup for an arbitrary `owner_account_id`. Alternatively, maintain a persistent on-chain set of already-created owner account ids and reject `create` calls for owners that already have (or have attempted) a lockup, refunding immediately instead of racing on `create_account`.

### Proof of Concept
```rust
#[test]
fn test_lockup_frontrun_griefing() {
    let mut context = VMContextBuilder::new()
        .current_account_id(account_factory())
        .predecessor_account_id(account_near())
        .finish();
    testing_env!(context.clone());

    let mut contract = LockupFactory::new(whitelist_account_id(), foundation_account_id());

    let lockup_duration: WrappedTimestamp = 63036000000000000u64.into();

    // Attacker front-runs with MIN_ATTACHED_BALANCE and their own chosen args
    context.is_view = false;
    context.predecessor_account_id = String::from(attacker_account());
    context.attached_deposit = MIN_ATTACHED_BALANCE;
    testing_env!(context.clone());
    contract.create(account_tokens_owner() /* == victim */, lockup_duration, None, None, None, None);

    // Simulate successful account creation for attacker
    context.predecessor_account_id = account_factory();
    context.attached_deposit = 0;
    testing_env_with_promise_results(context.clone(), PromiseResult::Successful(vec![]));
    let attacker_ok = contract.on_lockup_create(
        lockup_account(),
        MIN_ATTACHED_BALANCE.into(),
        String::from(attacker_account()),
    );
    assert_eq!(attacker_ok, true); // attacker's minimal-deposit lockup is now permanent

    // Real grantor now tries to fund the correct amount for the same owner
    context.predecessor_account_id = String::from(account_near()); // grantor
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());
    contract.create(account_tokens_owner(), lockup_duration, None, None, None, None);

    // create_account fails because lockup_account already exists
    context.predecessor_account_id = account_factory();
    context.attached_deposit = 0;
    testing_env_with_promise_results(context.clone(), PromiseResult::Failed);
    let grantor_ok = contract.on_lockup_create(
        lockup_account(),
        ntoy(35).into(),
        String::from(account_near()),
    );
    assert_eq!(grantor_ok, false); // grantor's deposit refunded, never delivered to victim's lockup
}
```
This demonstrates the binding `NEAR held at sha256(owner)[..20].<factory> == the real grantor's intended grant size` breaks: after the attacker's call it equals `MIN_ATTACHED_BALANCE` funded with attacker-chosen `LockupArgs`, and the grantor's subsequent attempt to establish the correct value fails entirely with a refund to themselves rather than to `victim.near`'s lockup.
