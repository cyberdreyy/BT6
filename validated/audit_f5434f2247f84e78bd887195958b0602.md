## Analog Confirmed: `start_liquidation` / `start_deleverage` gate account health without accruing interest first

### Title
Stale interest accrual in `start_receivership()` skews liquidation/deleverage entry checks and the equity snapshot used for post-liquidation premium validation - ([File: programs/marginfi/src/instructions/marginfi_account/liquidate_start.rs])

### Summary
`start_liquidation` and `start_deleverage` both funnel into the shared `start_receivership()` helper, which computes the account's health and equity snapshot to decide whether receivership may begin — but it never calls `bank.accrue_interest()` on any of the account's banks before doing so [1](#0-0) . This is the same bug class as the reported `topUpInterestShortfall()` issue: a health/shortfall-gating function that runs against stale share values because interest wasn't accrued first.

### Finding Description
`start_receivership()` calls `check_pre_liquidation_condition_and_get_account_health()` and `get_health_components()` directly against the loaded `MarginfiAccount`/bank state [2](#0-1) , with no preceding `accrue_interest()` call on any bank in the account's position set. Contrast this with `lending_account_liquidate`, which explicitly accrues interest on both `asset_bank` and `liab_bank` before performing the equivalent pre-liquidation health check: [3](#0-2)  followed by [4](#0-3) . The convention elsewhere in the codebase (`deposit.rs`, `withdraw.rs`, `borrow.rs`, `repay.rs`, `handle_bankruptcy.rs`) is always to accrue interest before any solvency/health-relevant computation [5](#0-4) , but `start_receivership()` breaks this pattern for the multi-bank account it evaluates (it only accrues interest for a single bank later, incidentally, if/when `lending_account_withdraw` or `lending_account_repay` are used inside the receivership window).

The values computed here — `assets`, `liabs`, `assets_equity`, `liabs_equity` — are written into `liq_record.cache` (`asset_value_maint`, `liability_value_maint`, `asset_value_equity`, `liability_value_equity`) [6](#0-5) . These cached values are later read by `end_liquidation` as `pre_assets_equity` to decide whether the account was "healthy enough to ignore" and to gate whether the liquidator's premium exceeded the allowed maximum: [7](#0-6) . Because the snapshot is taken pre-accrual, it can misrepresent the true equity/liability of the account at receivership start.

### Impact Explanation
- `start_liquidation` (called by an unprivileged/permissionless liquidator) can revert with an "account healthy" error even though the account would actually be unhealthy once interest is accrued, blocking a legitimate liquidation opportunity.
- Conversely, the pre-liquidation equity snapshot (`asset_value_equity`/`liability_value_equity`) used later in `end_liquidation`'s premium check (`seized <= repaid * max_fee`, and the `ignore_healthy` threshold check) is computed from stale share values, which can allow a liquidator's excess-fee check to pass/fail incorrectly, and can misjudge whether the closeout-threshold "ignore healthy" bypass should apply — both of which have direct financial consequences for the liquidatee.
- This is a durable misvaluation in a permissionless, financially consequential code path (liquidation entry and premium gating), not merely a display/UX issue.

### Likelihood Explanation
Any account with active borrows accrues interest continuously; the longer the account has gone since its last bank interaction, the larger the discrepancy. A liquidator (or MEV searcher) does not need special privileges to trigger `start_liquidation` on any account, and stale-interest windows are common for banks with infrequent activity, per the project's own documentation on interest accrual only happening "when any transaction that changes funds occurs" [8](#0-7) .

### Recommendation
In `start_receivership()` (or in `start_liquidation`/`start_deleverage` before calling it), explicitly call `bank.accrue_interest()` on every bank in which the target account holds an active balance before computing health/equity, mirroring the pattern already used in `lending_account_liquidate`.

### Proof of Concept
1. A borrower's account has an active liability in Bank X that has not been touched (no deposit/withdraw/borrow/repay) for a long period, so `last_update` is stale and real accrued interest is not yet reflected in `liability_share_value`.
2. Using the stale liability value, the account currently appears healthy (or healthier than it truly is) under `check_pre_liquidation_condition_and_get_account_health`.
3. A liquidator calls `start_liquidation`; `start_receivership()` reverts with "account healthy" (or, in the deleverage path, the risk admin's forced deleverage similarly misjudges health), even though accruing interest first would show the account is actually unhealthy — delaying necessary liquidation and letting bad debt grow.
4. Alternatively, if the account happens to look unhealthy pre-accrual due to another bank's stale higher liability, `liq_record.cache.asset_value_equity`/`liability_value_equity` snapshot values used later in `end_liquidation`'s premium check are skewed, potentially permitting a liquidator to extract a premium above the intended cap once actual post-accrual values are considered.

Note: I was not able to fully inspect the body of `check_pre_liquidation_condition_and_get_account_health` (only its call sites) within the available tool budget; its exact internal logic should be double-checked to confirm it performs no implicit accrual before this analog is treated as fully proven.

pub fn start_receivership<'info>(
    marginfi_account: &mut MarginfiAccount,
    liq_record: &mut LiquidationRecord,
    remaining_ais: &'info [AccountInfo<'info>],
    ignore_healthy: bool,
) -> MarginfiResult {
    // Note: the receiver can use the health cache state after this ix concludes to plan their
    // liquidation/deleverage strategy.
    let mut health_cache = HealthCache::zeroed();
    let mut liq_price_cache = LiquidationPriceCache::default();
    let (_pre_health, assets, liabs) = check_pre_liquidation_condition_and_get_account_health(
        marginfi_account,
        remaining_ais,
        None,
        &mut Some(&mut health_cache),
        HealthPriceMode::Live {
            liq_cache: Some(&mut liq_price_cache),
        },
        ignore_healthy,
    )?;

    // Use heap-efficient equity calculation
    let (assets_equity, liabs_equity) = get_health_components(
        marginfi_account,
        remaining_ais,
        RequirementType::Equity,
        &mut Some(&mut health_cache),
        HealthPriceMode::Live {
            liq_cache: Some(&mut liq_price_cache),
        },
    )?;

    write_liquidation_price_cache_from(marginfi_account, remaining_ais, &liq_price_cache)?;
    marginfi_account.health_cache = health_cache;
    marginfi_account.set_flag(ACCOUNT_IN_RECEIVERSHIP, false);
    marginfi_account.indexer_flags.has_ever_been_liquidated = 1;

    // Snapshot values to use in later checks
    liq_record.cache.asset_value_maint = assets.into();
    liq_record.cache.liability_value_maint = liabs.into();
    liq_record.cache.asset_value_equity = assets_equity.into();
    liq_record.cache.liability_value_equity = liabs_equity.into();

    Ok(())
}
