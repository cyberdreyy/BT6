## Title
Node-side signer weight aggregator double-counts a signer that first rejects then later accepts a block, breaking the aggregated-weight-vs-verified-accepts equality — (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

## Summary
The node-side `StackerDBListener`, which aggregates per-signer `BlockResponse` messages into `BlockStatus.total_weight_approved` / `total_weight_rejected` for the miner's `SignerCoordinator::get_block_status` decision loop, uses two different de-duplication keys for the two response kinds: `Accepted` guards its weight-add with `gathered_signatures.contains_key(&slot_id)`, while `Rejected` guards its weight-add with `responded_signers.insert(slot_id)` — the *same* `responded_signers` set that the `Accepted` branch also populates. Because the `Accepted` handler inserts into `responded_signers` too, a signer that rejects first and then legitimately (or maliciously) accepts the same block later has its weight added once to `total_weight_rejected` (on the reject) and once to `total_weight_approved` (on the accept, since `gathered_signatures` was still empty for that slot), with no removal of the earlier reject weight. This is a direct “double accounting” of a single signer's weight across two supposedly mutually-exclusive tallies, mirroring the external report's pattern of a single actor's contribution being counted twice due to unguarded/mismatched bookkeeping.

## Finding Description
`BlockStatus` tracks per-block weight totals for consensus decisions: [1](#0-0) 

For `Accepted` responses, the weight add is guarded against re-processing the same slot by checking `gathered_signatures`, then the slot is recorded into **both** `gathered_signatures` and `responded_signers`: [2](#0-1) 

For `Rejected` responses, the weight add is guarded by inserting into `responded_signers` directly — the exact same set the `Accepted` branch writes to: [3](#0-2) 

Consequences of sharing one set across two different guards:
- **Reject → later Accept (unguarded double count):** On `Rejected`, `responded_signers.insert(slot_id)` returns `true` the first time, so `total_weight_rejected` is incremented. If the same signer later sends `Accepted` for the same block, the `Accepted` branch checks `gathered_signatures.contains_key(&slot_id)`, which is still `false` (this slot was never added there), so `total_weight_approved` is *also* incremented by that signer's weight. The signer's weight now counts in both totals simultaneously, and the stale reject weight is never retracted.
- **Accept → later Reject (accidentally guarded, asymmetric):** On `Accepted`, the slot is inserted into `responded_signers`. A subsequent `Rejected` from the same slot finds `responded_signers.insert(slot_id)` returns `false`, so `total_weight_rejected` is *not* incremented — this direction happens to be blocked, but only as a side effect of key reuse, not by design.

This breaks the “aggregated-weight vs verified-accepts” equality the report rules call out explicitly: `SignerCoordinator::get_block_status` assumes `total_weight_approved` and `total_weight_rejected` represent disjoint, current-opinion weight sets summing to at most `total_weight`. With the bug, `total_weight_approved + total_weight_rejected` can exceed the true distinct weight of signers who have voted, because one signer's weight is counted in both buckets: [4](#0-3) 

The reject-threshold check runs before the approve-threshold check in this loop. An inflated `total_weight_rejected` (containing weight from a signer who has *since* moved to accept) can push the block into `NakamotoNodeError::SignersRejected` even though the currently-accepting weight, if the stale/retracted reject were excluded, would have reached the 70% approval threshold — i.e., a block that should be accepted can instead be wrongly killed, or conversely the aggregate bookkeeping simply no longer reflects reality, undermining the correctness of the miner's accept/reject decision.

Critically, this is not solely a malicious/Byzantine scenario: the signer's own local state machine explicitly allows `LocallyRejected --> LocallyAccepted` upon re-evaluation (a block can be rejected, then legitimately re-evaluated and accepted, e.g. after a timeout resolves or a proposal is superseded and re-validated): [5](#0-4) 

So a fully honest signer flipping from reject to accept for the same `signer_signature_hash` (allowed by `BlockInfo::check_state`) will trigger this double-count on the node aggregator without any attacker involvement — a single signer (the "one-slot" actor permitted by the rules) plus normal StackerDB gossip is sufficient to trigger it.

## Impact Explanation
This breaks the aggregated-weight-vs-verified-accepts equality that the miner's consensus decision relies on. Because the reject branch is checked first in `get_block_status`, an inflated (stale) rejection weight can cause the miner to conclude a blocking minority exists and abort/mark txids as failed/excluded, even though the true, current opinion of the network may have crossed the 70% approval threshold. This is a **High**-impact liveness/decision-integrity issue: it can wedge legitimate blocks out of acceptance (miner treats a signable block as globally rejected, forcing re-proposals, excluding transactions, or stalling tenure progress) based on stale, double-counted weight rather than the signers' actual current votes.

## Likelihood Explanation
High. It requires no majority and no cryptographic forgery — only a single signer sending `Rejected` for a block sighash and later sending `Accepted` for the same sighash, which is explicit, legitimate signer behavior per the documented `LocallyRejected → LocallyAccepted` re-evaluation transition. It is trivially reproducible by any one signer (or by an adversarial signer deliberately flip-flopping) and is delivered purely through the existing StackerDB message-gossip path that the node's `StackerDBListener` already consumes.

## Recommendation
Use independent de-duplication keys for the two response kinds instead of sharing `responded_signers` as the guard for `Rejected`. Concretely:
- Guard the `total_weight_rejected` increment with a dedicated `rejected_signers` set (or check `gathered_signatures`-style rejected map) rather than `responded_signers`.
- When a signer's vote flips (accept↔reject) for the same block, decide an explicit policy: either (a) retract/replace the previous vote's weight from the opposite tally so only the signer's most recent vote counts, or (b) ignore later flips entirely and log them, but never allow a single signer's weight to be simultaneously present in both `total_weight_approved` and `total_weight_rejected`.
- Add a regression test that sends `Rejected` then `Accepted` (and vice versa) from the same slot for the same `signer_signature_hash` and asserts that the signer's weight appears in exactly one of `total_weight_approved`/`total_weight_rejected` at any time.

## Proof of Concept
Conceptual trace against `stacks-node/src/nakamoto_node/stackerdb_listener.rs`:
1. Signer `S` (slot `k`, weight `w`) broadcasts `BlockResponse::Rejected` for `signer_signature_hash = H`.
   - `responded_signers.insert(k)` → `true` → `total_weight_rejected += w`.
2. Signer `S` later re-evaluates (per `BlockInfo::check_state` allowing `LocallyRejected → LocallyAccepted`) and broadcasts `BlockResponse::Accepted` for the same `H`.
   - `gathered_signatures.contains_key(&k)` → `false` (never inserted by the reject path) → `total_weight_approved += w`.
   - `gathered_signatures.insert(k, signature)`; `responded_signers.insert(k)` (already present, no-op).
3. Now both `total_weight_rejected` and `total_weight_approved` include `w` for the same signer `S`, even though `S` currently holds only one opinion (accept). `get_block_status` in `signer_coordinator.rs` evaluates the inflated `total_weight_rejected` against the blocking-minority check before evaluating `total_weight_approved`, so this stale weight can incorrectly tip the miner toward treating the block as rejected.
