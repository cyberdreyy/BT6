Confirmed: `delete_member` only purges requests **originated** by the removed member (`requests` where `r.member == member`), but does not scan other pending requests' `confirmations` sets for stale entries left by that member on requests they merely *confirmed* (not authored) [1](#0-0) . The same gap exists in the original `multisig` contract's `DeleteKey` handling, which removes only requests keyed by the deleted signer, not confirmations by that key on other requests [2](#0-1) .

### Title
Multisig `confirm()` counts confirmations from removed members toward the execution threshold, allowing requests to execute below the live-member quorum - (File: multisig2/src/lib.rs, multisig/src/lib.rs)

### Summary
`confirm()` decides whether to execute a request purely by comparing the size of the request's stored `confirmations: HashSet` (or `HashSet<String>` in `multisig2`) against `num_confirmations` [3](#0-2) [4](#0-3) . This set is never re-validated against the current, live set of multisig members/keys. `DeleteMember`/`DeleteKey` only clean up requests *authored* by the removed member; they do not scan the `confirmations` map to strip that member's prior confirmations from requests authored by someone else [5](#0-4) [2](#0-1) .

### Finding Description
The custody binding that should hold is: `confirmations counted == confirmations from currently-live members`. Instead the code enforces `confirmations.len() + 1 >= num_confirmations`, where `confirmations` can contain entries from members who have since been deleted [6](#0-5) .

Sequence:
1. Member A creates request R (e.g. a `Transfer` or `FunctionCall`) via `add_request`.
2. Member B confirms R (`confirm`); B's identity is added to R's `confirmations` set. Suppose `num_confirmations = 3` and B is the only confirmer so far (2 total: A's implicit add + B's confirm, still below 3).
3. Via a separate, already-confirmed `DeleteMember`/`DeleteKey` request, B is removed from the multisig (e.g., because B's key was compromised or the group decided to revoke B). `delete_member`/`DeleteKey` only removes requests where `r.member == B` (requests B authored) — R (authored by A) is untouched, and B's confirmation entry inside R's `confirmations` set is never purged.
4. A third live member C confirms R. `confirmations.len() + 1 >= num_confirmations` (2 + 1 >= 3) evaluates true using B's stale confirmation, and `execute_request` runs — even though only 2 currently-live members (A, C) ever approved R.

### Impact Explanation
This breaks the multisig's core custody guarantee that `K` *live* members must approve any `Transfer`, `FunctionCall`, `AddKey`, `DeployContract`, etc. A request can execute with fewer live approvals than the configured threshold, i.e. "a multisig request executed below threshold" — funds can move, keys can be added, or contracts can be deployed with less authorization than intended. Per the impact taxonomy this is Critical.

### Likelihood Explanation
No privileged role beyond normal multisig membership is required — any member set undergoing routine turnover (removing a compromised or departing member) while requests are pending is enough to trigger the stale-confirmation counting bug. It requires a specific but plausible ordering of operations (confirm-then-remove-that-member-then-confirm-again) rather than any special access, so likelihood is moderate-to-high in any multisig with membership churn and concurrently pending requests.

### Recommendation
When a member is removed (`DeleteMember`/`DeleteKey`), iterate all pending requests' `confirmations` sets and strip the removed member's identity, or re-validate `confirmations` against the live `members` set at `confirm()`-time before comparing against `num_confirmations` (e.g., filter `confirmations` to only those entries still present in `self.members` before checking length).

### Proof of Concept
Given `num_confirmations = 3`, members `{A, B, C, D}`:
1. `A.add_request(R)` — creates R.
2. `B.confirm(R)` — `confirmations = {B}` (len 1, 1+1=2 < 3, stored).
3. Separately, `D.add_request_and_confirm(delete_member(B))`, then any 1 more live member confirms to remove B (assuming threshold already met via other pending confirmations) — B is deleted; `self.requests`/`self.confirmations` for requests **authored by B** are purged, but R's `confirmations = {B}` remains untouched.
4. `C.confirm(R)` — `confirmations.len() + 1 = 2 >= num_confirmations`? Only if `num_confirmations <= 2`; adjust scenario with `num_confirmations = 2` for a clean minimal repro: after step 2, `confirmations={B}` len 1, 1+1=2>=2 → would already execute on B's confirm alone if B is sole confirmer, so the more precise minimal PoC uses `num_confirmations=3`: after B confirms (len=1) and B is removed, C confirms (len=2, 2+1=3>=3) → `execute_request(R)` runs using only A (author, not itself a "confirmation" in the set) and stale B plus live C — i.e., only 1 live confirming member (C) plus the stale B entry satisfies the threshold meant to require 2 live confirming members beyond the author.

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
