### Title
Signer rejection tracking table keys on `signer_addr` alone, silently dropping rejection weight for later blocks - ([File: stacks-signer/src/signerdb.rs])

### Summary
The `block_rejection_signer_addrs` table, which the signer uses to tally per-block rejection weight toward the 30%+1 "globally rejected" threshold, is keyed only by `signer_addr` instead of `(signer_signature_hash, signer_addr)`. Once a signer has recorded a rejection for one block, the persistence layer treats any rejection they cast for a *different* block as a duplicate/conflict and the call is treated as "already recorded," so the vote is silently dropped rather than counted toward the new block's tally.

### Finding Description
The table is defined with a primary key that does not include the block identifier: [1](#0-0) 

Compare this to the analogous acceptance table, `block_signatures`, whose primary key is the (unique) `signature` value itself, and to every other per-block table in this file (`blocks`, keyed by `(reward_cycle, signer_signature_hash)`). `block_rejection_signer_addrs` is the odd one out: a signer address can appear at most once in the *entire* table, regardless of how many distinct blocks that signer has rejected over the life of the reward cycle.

The consumer of `add_block_rejection_signer_addr`'s return value confirms an insert-or-ignore semantic keyed on this constraint: [2](#0-1) 

```
Ok(false) => return, // We already have this signature, do not process it again.
```

Because the underlying primary key is `signer_addr` alone, this "already have it" branch fires not only for a genuine duplicate rejection of the *same* block, but also the first time that signer rejects any *subsequent, different* block after having rejected an earlier one. The rejection is discarded before `store_and_process_block_rejection`'s weight computation: [3](#0-2) 

so `total_reject_weight` for the new block never includes that signer's vote, and the record is never persisted for the new block's hash either — the signer's weight is permanently "spent" on the first block they ever rejected.

### Impact Explanation
A one-slot miner (plus ordinary gossip) can trigger this repeatedly: propose an invalid/conflicting block, let it accumulate a handful of rejections, then propose additional invalid or conflicting blocks (e.g. rejected siblings/tenure-change conflicts, cf. the sibling-conflict handling documented in `docs/signer-flows.md:271-330`). Every signer who rejected the first bad block has its rejection vote for every subsequent bad block silently swallowed. Over a reward cycle this steadily erodes the signer set's *effective* rejection weight, making it progressively harder — and eventually impossible — to reach the 30%+1 threshold needed to mark a bad block `GloballyRejected`: [4](#0-3) 

A block that can be neither signed (it is genuinely invalid) nor driven to `GloballyRejected` (because its rejection tally is artificially suppressed) leaves the signer set's local `BlockInfo` state machine wedged for that proposal, and starves the miner state machine, which depends on rejection outcomes to move past a bad tenure. This is a liveness defect that degrades over the life of a reward cycle purely from ordinary bad-block gossip, requiring no majority collusion and no key compromise.

### Likelihood Explanation
High likelihood of occurrence in practice: any miner that produces more than one invalid/conflicting proposal per reward cycle (misconfiguration, a stale/forked miner, or a malicious single miner) will cause distinct rejection events across multiple signers, and the very first rejection each signer casts "consumes" their row for the rest of the cycle. No coordination between attackers or signers is required — it degrades naturally from repeated normal rejection traffic.

### Recommendation
Change `block_rejection_signer_addrs`'s primary key to the composite `(signer_signature_hash, signer_addr)` (matching the pattern already used for `blocks`), and add the corresponding index change, so a signer's rejection is recorded independently per block instead of being globally deduplicated by address alone.

### Proof of Concept
1. Signer set S includes signer X.
2. Miner proposes block A (invalid). Enough signers, including X, reject it: `add_block_rejection_signer_addr(hash_A, X, ...)` succeeds, inserting row `(hash_A, X)`.
3. Same or new miner proposes block B (a different, also-invalid or conflicting block, e.g. a sibling tenure-start block per `stacks-signer/src/v0/tests.rs` sibling-conflict scenarios). X also (correctly) rejects B: `add_block_rejection_signer_addr(hash_B, X, ...)` attempts to insert `(hash_B, X)`, but the primary key `(signer_addr)` already contains a row for X (from block A), so the insert is treated as a duplicate and returns `Ok(false)`.
4. `handle_block_rejection`'s caller sees `Ok(false)` and returns immediately (`stacks-signer/src/v0/signer.rs:2286`), never adding X's weight to B's `total_reject_weight` computation.
5. B's rejection tally permanently lacks X's weight, even though X genuinely rejected B, moving B further from ever reaching `GloballyRejected` and wedging its `BlockInfo` state indefinitely.
