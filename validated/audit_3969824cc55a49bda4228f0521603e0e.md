The report's bug class—stale authorization state that isn't invalidated when the underlying entitlement changes—maps onto a concrete flaw in `multisig2/src/lib.rs`: confirmations recorded by a member are never purged when that member is removed from the multisig, except for requests that member itself created.

### Title
Stale confirmations from deleted multisig members are still counted toward the confirmation threshold, allowing request execution below the live-member quorum - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::confirm` counts entries in a per-request `HashSet<String>` of confirmations against `num_confirmations` to decide whether to execute a request [1](#0-0) . When a member is removed via `DeleteMember`, `delete_member` only deletes requests *created by* that member and their `num_requests_pk` entry; it does not scan other members' pending requests to strip confirmations the removed member had already cast on them [2](#0-1) . As a result, a removed member's confirmation on someone else's still-pending request remains in the `confirmations` set and continues to count toward the quorum.

### Finding Description
The custody/authorization binding that should hold is: `confirmations counted == confirmations from current live members`. Instead, the code lets `confirmations counted ⊇ confirmations from members that were live at confirm-time`, which can include accounts no longer in `self.members`.

Trace:
- `confirm()` inserts `member.to_string()` into `self.confirmations[request_id]` and executes once `confirmations.len() + 1 >= self.num_confirmations` [1](#0-0) .
- `delete_member()` removes only requests where `r.member == member` (i.e., requests *authored* by the removed member), and removes `num_requests_pk` for that member, then removes the member from `self.members` [3](#0-2) . It never inspects or edits the `confirmations` map for requests authored by other members that the removed member had confirmed.
- `assert_valid_request()` / `current_member()` only gate who can *newly* confirm or create requests — they do not re-validate previously stored confirmation entries against current membership [4](#0-3) [5](#0-4) .

### Impact Explanation
This breaks the equality "confirmations executed == confirmations from members entitled at execution time," which is exactly the Critical-impact criterion "a multisig request executed below threshold." Example with `num_confirmations = 2` and members `{A, B, C}`:
1. `B` calls `add_request` (not `add_request_and_confirm`) for a `Transfer` — confirmations = `{}`.
2. `A` calls `confirm(request_id)` — confirmations = `{A}` (len 1 < 2, not executed).
3. Multisig later executes `DeleteMember { member: A }` (e.g., because `A`'s key was compromised) — this only deletes requests *authored by A*, so the transfer request created by `B` is untouched, and its confirmations set still contains `A`.
4. `C` calls `confirm(request_id)` — `confirmations.len() + 1 == 2 >= num_confirmations`, so the request executes.

At execution time the only actual live member who confirmed is `C`; `A` is no longer a member. The multisig has effectively been convinced by a single live confirmation plus one ghost confirmation from a deleted (potentially compromised/malicious) key — a quorum bypass.

### Likelihood Explanation
This requires no privileged action from the attacker beyond being (or having been) a legitimate member at some point and having confirmed a pending request before being removed — a realistic operational scenario (e.g., key rotation after a suspected compromise, or removing a departing team member) where the operators reasonably assume removal revokes that member's influence. The remaining members do not need to know that a stale confirmation exists to trigger the under-threshold execution; a normal subsequent `confirm` call by another legitimate member will inadvertently trip it.

### Recommendation
When executing `DeleteMember`, iterate over `self.confirmations` for all pending requests (not just those authored by the removed member) and remove the deleted member's entry from each confirmation set, re-checking whether removal drops any request below its cooldown/expected state. Alternatively, validate at `confirm()`/execution time that every account/key present in a request's confirmation set is still a current member before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C]`, `num_confirmations = 2`.
2. As `B`, call `add_request` with a `Transfer` action to some `receiver_id` (do not confirm).
3. As `A`, call `confirm(request_id)` → confirmations = `{A}`.
4. As two members meeting quorum, execute `DeleteMember { member: A }` (e.g. `B` and `C` confirm a `DeleteMember` request) — `A` is removed from `self.members`; the earlier transfer request (authored by `B`) is untouched because `delete_member`'s filter only matches requests authored by `A`.
5. As `C`, call `confirm(request_id)` on the original transfer request → `confirmations.len() (1, from A) + 1 (C) == 2 >= num_confirmations`, so `execute_request` runs and the `Transfer` is sent, despite only one currently-live member (`C`) having actually approved it.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
