### Title
IAM session policy Resource ARN is built by naive string interpolation of the cache object name, allowing `*`/`?` in the cache key to widen the AssumeRole session policy beyond the intended object - (File: `cache/s3v2/s3.go`)

### Summary
`s3Client.generateSessionPolicy` builds the `Resource` field of the STS `AssumeRole` session policy with `fmt.Sprintf("arn:%s:s3:::%s/%s", s3Partition, bucketName, objectName)` [1](#0-0)  where `objectName` is the runner-computed cache path that embeds the job-controlled cache key (`key:` / `CACHE_FALLBACK_KEY`), passed through unmodified from `s3Adapter.GetGoCloudURL` [2](#0-1) . AWS IAM's ARN resource matcher treats `*` and `?` as wildcards regardless of how the surrounding JSON was escaped, so a cache key containing these characters can broaden the `Resource` match beyond the single literal object the runner intended to grant access to.

### Finding Description
The code comment at `cache/s3v2/s3.go:245-248` claims that building the JSON via `encoding/json` prevents "special characters in objectName ... from alter[ing] the policy structure." That claim is only true for JSON syntax (quotes, braces) — it does not protect against AWS IAM's own ARN wildcard semantics. IAM policy `Resource` values support `*` (any sequence) and `?` (any single character) as glob-style wildcards, evaluated by AWS after the policy JSON is parsed. Escaping `*`/`?` inside a valid JSON string does nothing to stop IAM from interpreting them as wildcards once AWS parses the ARN value.

`objectName` is derived from the job's cache `key`/`CACHE_FALLBACK_KEY`, which is attacker-controlled by any pipeline author. If the object path is `runner/<token>/project/<id>/<cacheKey>`, injecting `*` into `cacheKey` produces a `Resource` such as `arn:aws:s3:::bucket/runner/<token>/project/<id>/foo*`, which IAM will match against any object sharing that prefix. Since S3 key namespaces are shared bucket-wide and cache keys are user-defined free text, this can match sibling cache archives for other jobs/branches, and — depending on how much of the path prefix is attacker-influenced or how object naming falls back (e.g., `CACHE_FALLBACK_KEY` allowing cross-branch/cross-job fallback keys) — potentially other objects sharing a much broader prefix than the single intended cache archive.

Existing protections reviewed:
- `presignURL`/`FetchCredentialsForRole` do not validate or sanitize `objectName` for IAM metacharacters before injecting it into the ARN string.
- The JSON-based `policyDocument` construction only guards against JSON structural injection, not IAM wildcard semantics — this is a mismatch between what the comment claims to defend against and what the actual attacker capability is.
- No allowlist or escaping of `*`/`?` occurs anywhere in `generateSessionPolicy`.

### Impact Explanation
A widened `Resource` ARN in the AssumeRole session policy grants the returned temporary STS credentials (returned in `GoCloudURL.Environment` to the job runtime) `s3:GetObject`/`s3:PutObject` over any S3 object matching the wildcard pattern, not just the single object the job legitimately owns. Depending on how much of the key path is attacker-influenced, this can expose or allow overwrite of other jobs' or projects' cache contents within the same bucket — a concrete cross-tenant cache confidentiality/integrity breach scoped to S3 cache storage.

### Likelihood Explanation
Precondition: the runner must be configured with S3 cache using `RoleARN`/`UploadRoleARN` (STS AssumeRole session-policy scoping), which is a supported and documented configuration for shared/multi-tenant runners specifically to isolate cache access per job. Any pipeline author can set an arbitrary `cache: key:` value or `CACHE_FALLBACK_KEY` variable containing `*` or `?` with no special privilege, making the trigger trivial and fully repeatable.

### Recommendation
Before interpolating `objectName` into the ARN `Resource` string, reject or escape IAM-significant wildcard characters (`*`, `?`) in the computed object name (or in the raw cache key upstream), e.g. return an error if the object name contains these characters, or percent-encode/escape them so they can't be interpreted as wildcards by IAM's resource matcher. Add a regression test asserting that `generateSessionPolicy` never produces a `Resource` value that matches anything other than the literal `objectName`.

### Proof of Concept
```go
func TestGenerateSessionPolicy_RejectsWildcardObjectName(t *testing.T) {
    c := &s3Client{
        awsConfig: &aws.Config{Region: "us-east-1"},
        s3Config:  &cacheconfig.CacheS3Config{},
    }

    // Cache key containing an IAM wildcard character, as could be set via
    // `cache: key:` or CACHE_FALLBACK_KEY.
    objectName := "runner/TOKEN/project/123/foo*"

    policy, err := c.generateSessionPolicy("my-bucket", objectName, false)
    require.NoError(t, err)

    var doc policyDocument
    require.NoError(t, json.Unmarshal([]byte(policy), &doc))

    resource := doc.Statement[0].Resource
    // Assert the Resource ARN matches ONLY the literal objectName and cannot
    // be interpreted by AWS IAM as a wildcard pattern.
    assert.NotContains(t, resource, "*", "Resource ARN must not contain IAM wildcard '*'")
    assert.NotContains(t, resource, "?", "Resource ARN must not contain IAM wildcard '?'")
}
```
Expected: current implementation fails this assertion because `*`/`?` are passed through verbatim into the `Resource` ARN.
