### Title
Unbounded token multiplier/interest-rate values in mint extensions produce non-JSON-representable `Infinity`/`NaN` UI amounts, misreporting account data in JSON-RPC token queries - (File: `account-decoder/src/parse_token.rs`)

### Summary
`token_amount_to_ui_amount_v3` computes a token's UI-facing amount from raw on-chain values (`amount`) combined with `InterestBearingConfig`/`ScaledUiAmountConfig` extension data taken directly from a SPL-Token-2022 mint account, with no bound checking on the resulting multiplier/rate before it is used to compute `ui_amount`.

### Finding Description
`token_amount_to_ui_amount_v3` in `account-decoder/src/parse_token.rs` delegates to `interest_bearing_config.amount_to_ui_amount(...)` or `scaled_ui_amount_config.amount_to_ui_amount(...)`, whose inputs (`current_rate`, `pre_update_average_rate`, `multiplier`, `new_multiplier`) originate unchecked from mint account extension data set by the token/mint authority. [1](#0-0) 

The mint authority fully controls these values (e.g., `ScaledUiAmountConfig::new_multiplier`), and the code performs no validation that the computed multiplier/rate is a finite, sane number before combining it with an account's `amount`. The repository's own tests demonstrate that a mint with `new_multiplier = f64::INFINITY` (or an extreme interest rate) causes `ui_amount` to become `Some(f64::INFINITY)` and `ui_amount_string` to become the literal string `"inf"`. [2](#0-1) [3](#0-2) 

This function is reachable directly from unprivileged, single-call JSON-RPC handlers such as `getTokenAccountBalance` and `getTokenSupply`, as well as `jsonParsed` account/`getProgramAccounts` decoding paths, all of which read the mint's extension config live from the bank and feed it straight into `token_amount_to_ui_amount_v3` without sanity-checking the multiplier/rate: [4](#0-3) [5](#0-4) [6](#0-5) 

`UiTokenAmount.ui_amount` is a `f64` serialized via `serde` into the JSON-RPC response. [7](#0-6) 
JSON has no representation for `Infinity`/`NaN`; `serde_json`'s float serializer silently emits `null` for non-finite `f64` values. As a result, any caller (including automated tooling) querying balance/supply for a token whose mint has an out-of-range scaled/interest-bearing configuration receives a `null` `ui_amount` for an account that actually holds a well-defined, finite raw `amount`, i.e., the RPC silently returns incorrect/misleading account data rather than an error or the true value — the same root-cause pattern as the reported Chainlink issue: an external, unchecked "answer" (here, the mint-supplied multiplier/rate) is used as-is instead of being validated against sane bounds, corrupting the value ultimately surfaced to the caller.

### Impact Explanation
Any unprivileged RPC client calling `getTokenAccountBalance`, `getTokenSupply`, `getParsedAccountInfo`/`getProgramAccounts` (jsonParsed encoding), or reading parsed instruction/transaction-status data for accounts under a mint with an extreme `ScaledUiAmountConfig`/`InterestBearingConfig` value receives a corrupted (`null`) `ui_amount` field while the true, finite balance exists, misrepresenting account data returned by a single low-rate RPC call. This does not require any operator/validator privilege — only that a mint authority create/update a token-2022 mint with the extension, which any user can be affected by simply querying that mint's accounts.

### Likelihood Explanation
Low-to-moderate: it requires a spl-token-2022 mint with `interest_bearing_mint` or `scaled_ui_amount` extension configured with a rate/multiplier extreme enough to overflow to infinity via `checked_pow`/exponential rate math, or explicitly set to `f64::INFINITY`. This is plausible since these extension fields are attacker (mint-authority) controlled and not validated by the token program to prevent extreme values from reaching RPC decoding paths in agave.

### Recommendation
In `token_amount_to_ui_amount_v3` (and its callers in `rpc/src/rpc.rs`, `rpc/src/parsed_token_accounts.rs`), validate that the computed `ui_amount` is finite before returning it; if it is not finite (`NaN`/`Infinity`), return `ui_amount: None` explicitly (as is already done elsewhere for decimal overflow) rather than allowing serialization to silently coerce it to `null`, and consider surfacing a distinguishable error/flag so RPC consumers do not conflate "unrepresentable" with "zero/none".

### Proof of Concept
1. Create an SPL-Token-2022 mint with a `ScaledUiAmountConfig` extension where `new_multiplier` is set to a value that (combined with `amount_to_ui_amount`'s exponent/rate math) evaluates to `f64::INFINITY` — the repository's own unit test constructs exactly this scenario: [8](#0-7) 
2. Query `getTokenAccountBalance` for a token account under that mint. The handler computes `token_amount_to_ui_amount_v3(token_account.base.amount, &data)`: [9](#0-8) 
3. The resulting `UiTokenAmount.ui_amount` is `Some(f64::INFINITY)`. Upon JSON serialization of the RPC response, this is emitted as `null` (per `serde_json` float handling), even though `ui_amount_string` will read `"inf"` and `amount` will contain the true finite raw value — an inconsistent, misleading response returned from a single unprivileged RPC call.

pub fn token_amount_to_ui_amount_v3(
    amount: u64,
    additional_data: &SplTokenAdditionalDataV2,
) -> UiTokenAmount {
    let decimals = additional_data.decimals;
    let (ui_amount, ui_amount_string) = if let Some((interest_bearing_config, unix_timestamp)) =
        additional_data.interest_bearing_config
    {
        let ui_amount_string =
            interest_bearing_config.amount_to_ui_amount(amount, decimals, unix_timestamp);
        (
            ui_amount_string
                .as_ref()
                .and_then(|x| f64::from_str(x).ok()),
            ui_amount_string.unwrap_or("".to_string()),
        )
    } else if let Some((scaled_ui_amount_config, unix_timestamp)) =
        additional_data.scaled_ui_amount_config
    {
        let ui_amount_string =
            scaled_ui_amount_config.amount_to_ui_amount(amount, decimals, unix_timestamp);
        (
            ui_amount_string
                .as_ref()
                .and_then(|x| f64::from_str(x).ok()),
            ui_amount_string.unwrap_or("".to_string()),
        )
    } else {
        let ui_amount = 10_usize
            .checked_pow(decimals as u32)
            .map(|dividend| amount as f64 / dividend as f64);
        (ui_amount, real_number_string_trimmed(amount, decimals))
    };

    fn test_ui_token_amount_with_multiplier() {

    pub fn get_token_supply(
        &self,
        mint: &Pubkey,
        commitment: Option<CommitmentConfig>,
    ) -> Result<RpcResponse<UiTokenAmount>> {
        let bank = self.bank(commitment);
        let mint_account = bank.get_account(mint).ok_or_else(|| {
            Error::invalid_params("Invalid param: could not find account".to_string())
        })?;
        if !is_known_spl_token_id(mint_account.owner()) {
            return Err(Error::invalid_params(
                "Invalid param: not a Token mint".to_string(),
            ));
        }
        let mint = StateWithExtensions::<Mint>::unpack(mint_account.data()).map_err(|_| {
            Error::invalid_params("Invalid param: mint could not be unpacked".to_string())
        })?;

        let interest_bearing_config = mint
            .get_extension::<InterestBearingConfig>()
            .map(|x| (*x, bank.clock().unix_timestamp))
            .ok();

        let scaled_ui_amount_config = mint
            .get_extension::<ScaledUiAmountConfig>()
            .map(|x| (*x, bank.clock().unix_timestamp))
            .ok();

        let supply = token_amount_to_ui_amount_v3(
            mint.base.supply,
            &SplTokenAdditionalDataV2 {
                decimals: mint.base.decimals,
                interest_bearing_config,
                scaled_ui_amount_config,
            },
        );
        Ok(new_response(&bank, supply))
    }
