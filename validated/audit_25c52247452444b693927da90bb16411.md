### Title
Shared writable `scripts` emptyDir lets attacker-controlled service containers tamper with the privileged helper binary used by the build container - (File: executors/kubernetes/steps_pod.go)

### Summary
In Concrete/steps mode, `stepsVolumeMounts()` is mounted into the bootstrap init container, the build container, *and* every user-declared service container, all pointing at the same `scripts` `emptyDir` volume with no `ReadOnly` flag. That volume is where `buildStepsBootstrapInitContainer` copies the `gitlab-runner-helper` binary that the build container later executes as `steps serve`/`steps proxy` to mediate the entire CI job protocol (including env-var injection). A pipeline author's fully attacker-controlled `services:` image gets write access to this same path, breaking the intended build/helper/service trust boundary.

### Finding Description
`buildStepsBootstrapInitContainer` (executors/kubernetes/steps_pod.go:121-147) creates the `init-steps-bootstrap` container whose sole job is to copy `gitlab-runner-helper` into the shared `scripts` emptyDir at `s.stepsRunnerBinaryPath()`. That path is later executed by the build container as its overridden `Command` (`stepsBuildContainer`, executors/kubernetes/steps_pod.go:289-355, line 314: `command := []string{s.stepsRunnerBinaryPath(), "steps", "serve"}`) and by the dialer via `pods/exec` (`execStepsProxy`, executors/kubernetes/steps.go:239-296).

All three roles — bootstrap init container, build container, and service containers — get their volume mounts from the single helper `stepsVolumeMounts()` (executors/kubernetes/steps_pod.go:532-557):

```go
mounts := []api.VolumeMount{
    {
        Name:      "scripts",
        MountPath: s.scriptsDir(),
    },
}
```

No `ReadOnly: true` is set, and there is no per-role variant of this mount. `stepsServiceContainer` (executors/kubernetes/steps_pod.go:388-443, line 438: `VolumeMounts: s.stepsVolumeMounts()`) reuses the exact same call for service containers built directly from the CI-author-controlled `services:` definitions (`s.options.Services`, verified only via `verifyAllowedImages`, which is an allow-list on image name/tag — it does not restrict filesystem access once the container is scheduled).

Because the `scripts` emptyDir is a pod-level shared volume and the mount is read-write for every container that references it, a service container — whose image name, command, and args are entirely attacker-controlled CI config — can write into `s.scriptsDir()` at the same path the init container populates and the build container later executes. This is a role-confusion bug: content that should exist only in the trust boundary shared between the "helper" role (bootstrap init container) and the "build" role (which executes it) is exposed read-write to the "service" role, which is architecturally the least-trusted, network-facing role.

### Impact Explanation
A malicious or compromised service image can race the bootstrap/build sequence and overwrite the `gitlab-runner-helper` binary (or plant files) at `stepsRunnerBinaryPath()` before/while the build container execs `<path> steps serve`. Since the build container's `Command` blindly executes whatever is at that path with no integrity check, this allows attacker-controlled code (originating from the service trust role) to execute with the build container's identity, security context, and access to the bidirectional stdin/stdout steps protocol that carries CI job variables. This crosses a role boundary — service-controlled content executing as build/helper-trusted code — and can result in secret/variable exposure or stronger-context execution inside the build container.

### Likelihood Explanation
Preconditions are minimal and fully within reach of an unprivileged pipeline author: define a `services:` entry with a custom image/command in `.gitlab-ci.yml` under a Runner configured with the Kubernetes executor and `FF_CONCRETE`/`FF_USE_ADVANCED_POD_SPEC_CONFIGURATION` steps mode enabled. No cluster-admin or GitLab-admin compromise is required — `verifyAllowedImages` only gates image name/tag, not filesystem access granted via shared volumes. The race window depends on container start ordering, which is influenced by init-container completion and kubelet scheduling, but the mount itself is unconditionally writable regardless of timing, so tampering (even outside a race, e.g., overwriting after the bootstrap completes but before "steps serve" is invoked, or persisting a payload for reconnects) is repeatable.

### Recommendation
- Do not reuse the same `stepsVolumeMounts()` for service containers; build a separate, minimal mount set for services that excludes the `scripts` volume entirely (services do not need the helper binary).
- If services must share any volume with the build/init containers, mount it `ReadOnly: true` for service containers.
- Consider mounting `scripts` `ReadOnly: true` for the build container as well once bootstrap has completed, or verifying the helper binary's integrity (e.g., checksum) immediately before exec.

### Proof of Concept
Go unit test in `executors/kubernetes/steps_pod_test.go`:
```go
func TestStepsServiceContainer_DoesNotMountScriptsWritable(t *testing.T) {
    ex := newStepsTestExecutor(t)
    ex.options.Services = kubernetesServices{
        "svc": &spec.Image{Name: "attacker/service:latest"},
    }
    svcContainer, err := ex.stepsServiceContainer("svc", *ex.options.Services["svc"], nil)
    require.NoError(t, err)

    for _, m := range svcContainer.VolumeMounts {
        if m.Name == "scripts" {
            assert.True(t, m.ReadOnly,
                "service container must not get writable access to the scripts emptyDir shared with the helper binary")
        }
    }
}
```
Expected (current) result: the assertion fails because `ReadOnly` is unset (`false`), demonstrating the service container is mounted read-write onto the same volume that hosts `gitlab-runner-helper`, confirming the role-confusion path described above.
