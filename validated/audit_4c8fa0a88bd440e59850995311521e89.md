### Title
Stale confirmations from removed multisig members are still counted toward the confirmation threshold - (File: `multisig/src/lib.rs`, `multisig2/src/lib.rs`)

### Summary
The multisig contracts count confirmations toward `num_confirmations` from a `confirmations` set keyed by request ID, but when a member/key is removed via `DeleteKey`/`DeleteMember`, the code only purges requests and confirmation entries that were *originated* by that key — it does not scrub that key's confirmation from *other* outstanding requests it had already confirmed but did not create. This breaks the binding: `confirmations counted == confirmations from currently live members`.

### Finding Description
`confirm()` in both contracts checks the number of stored confirmations against the static `num_confirmations` threshold and, once met, executes the request: [1](#0-0) 

When a member is removed, `execute_request`'s `DeleteKey` (v1) / `DeleteMember` (v2) branch only removes **requests originated by that key** (`r.signer_pk == pk` in v1, `r.member == member` in v2) and their confirmation sets — it does not walk all other outstanding requests to strip a confirmation the removed key had already cast as a non-originating confirmer: [2](#0-1) [3](#0-2) 

Consequently, if member A confirms request R (created by member B) and is later removed from the multisig (e.g., because A's key was compromised, or as routine membership rotation), R's `confirmations` set still contains A's public key/member id. A subsequent `confirm()` call by a live member simply does `confirmations.len() as u32 + 1 >= self.num_confirmations`, counting A's stale confirmation as valid, potentially executing R with fewer live-member confirmations than `num_confirmations` actually requires.

The `assert_valid_request`/`confirm` flow validates only that the *calling* signer is a current member (`current_member().is_some()`); it never re-validates the previously stored confirmations set against the current member list before using its length for the threshold check.

### Impact Explanation
This crosses the authorisation/threshold boundary explicitly called out in the rules ("confirmations counted versus live members"). A multisig configured for K-of-N can be made to execute privileged actions (transfers, key additions, function calls) with fewer than K *live* confirmations, because a removed member's earlier confirmation is silently retained and still counted. Since `execute_request` can perform `Transfer`, `AddKey`/`AddMember`, or `FunctionCall` actions, this can result in a multisig request executed below the intended live threshold — moving NEAR or granting access without the required number of currently-authorized approvers. This matches the Critical impact bucket ("a multisig request executed below threshold").

### Likelihood Explanation
Likelihood is Medium: it requires an ordinary, expected lifecycle event (removing a member/key after that member had already confirmed an outstanding, not-yet-executed request) rather than any privileged bypass, exploit of an owner, or malicious infrastructure. Multisig membership rotation and key revocation (e.g., for a suspected compromised key) are normal operational events explicitly supported by `DeleteKey`/`DeleteMember`; no assumption of a malicious foundation/owner/validator is needed — only a routine sequence of legitimate confirm/remove operations, some of which any current member can trigger, and the executing confirm can be finalized by any remaining member unaware that a stale confirmation is inflating the count.

### Recommendation
When removing a member/key, iterate all outstanding requests and remove the departing member's confirmation entry from every request's `confirmations` set (not just requests it originated), and/or re-validate at `confirm()` time that every public key/member stored in a request's confirmation set is still a current member before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy a multisig with members `[A, B, C]` and `num_confirmations = 2`.
2. `B` calls `add_request` to create request `R` (e.g., `Transfer`) — `R.confirmations = {}`.
3. `A` calls `confirm(R)` → `R.confirmations = {A}` (1 < 2, not yet executed).
4. Members execute a `DeleteKey`/`DeleteMember` request removing `A` (e.g., because `A`'s key is suspected compromised). This only clears requests originated by `A`; `R` is untouched, so `R.confirmations` still contains `A`.
5. `C` (a live member) calls `confirm(R)`. `confirmations.len() as u32 + 1 = 2 >= num_confirmations (2)` → `R` executes, even though only one currently-live member (`C`) ever confirmed it live plus the calling member — effectively 1 live-confirmer + 1 stale (removed) confirmer meeting a 2-of-3 threshold that should require two *live* approvers.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
