### Title
Peer-signature threshold count bypasses the signer's own validation state - ([File: stacks-signer/src/v0/signer.rs])

### Summary
`store_and_process_block_signature` tallies a peer's `BlockResponse::Accepted` signature toward the 70% group-signature threshold and, once reached, calls `mark_locally_accepted` and `broadcast_signed_block` (pushing the assembled signature set to the node) without ever checking `block_info.valid`, `block_info.state`, or whether this signer itself has locally validated/pre-committed to the block.

### Finding Description
The pre-commit → sign flow is designed as a two-step gate: a block must first pass this signer's own validation (`handle_block_validate_ok`, which sets `block_info.valid` and moves the block to `PreCommitted`) before this signer's pre-commit/signature logic is trusted to count toward consensus (`handle_block_pre_commit`, `stacks-signer/src/v0/signer.rs:1250-1345`, which explicitly checks `if !block_info.valid.unwrap_or(false) { ...; return; }` at line 1323).

However, `store_and_process_block_signature` (`stacks-signer/src/v0/signer.rs:2442-2538`) — reached from `handle_block_response`/`handle_block_signature` when a *peer's* acceptance arrives, and also from `process_pending_responses_for_block` (`stacks-signer/src/v0/signer.rs:1766-1778`) when replaying early votes for a freshly-inserted `block_info` — performs none of this gating: [1](#0-0) 

It stores the signature, optionally re-routes it to `handle_block_pre_commit` only in the "outdated peer, no prior pre-commit seen" branch (line 2463), and otherwise falls straight through to weight-tallying and, at threshold, to `mark_locally_accepted(true)` and `broadcast_signed_block` (`stacks-signer/src/v0/signer.rs:2503-2537`). There is no check of `block_info.valid` (whether *this* signer's own node validated the block), nor of `block_info.state` (whether the block even reached `PreCommitted`/passed `check_block_against_signer_db_state`). This is exactly the class of bug in the report: a later step in a multi-step protocol (crossing the signature-aggregation threshold and pushing a signed block) proceeds without a hard constraint that the necessary earlier step (local validation / re-checked chainstate) was actually completed by this signer instance for this specific `block_info`.

Compare this to `handle_block_pre_commit`, which re-runs `check_block_against_signer_db_state` immediately before threshold-crossing (line ~1345), and to `handle_block_validate_ok`, which re-checks DB state before `mark_pre_committed` (`stacks-signer/src/v0/signer.rs:1946-1970`). `store_and_process_block_signature` has no equivalent re-validation step before it assembles and broadcasts the aggregate signature set to the stacks-node.

### Impact Explanation
If a `block_info` record with `valid == None` (never locally validated — e.g., still pending validation, or the local `submitted_block_proposal` slot was busy per `stacks-signer/src/v0/signer.rs:1701-1714`, where the block is still `insert_block`-ed) accumulates enough peer `Accepted` signatures, this code path will call `mark_locally_accepted` and `broadcast_signed_block` for a block this signer never validated. `broadcast_signed_block` assembles and pushes the aggregate signature set to the stacks-node (`handle_post_block`), i.e., this signer becomes party to distributing/pushing a block it has not confirmed is valid or non-conflicting — breaking the "a signer signs/pushes only what it validated" equality the two-phase-commit design (`docs/signer-flows.md:229-272`) is meant to guarantee. This matches the High/Critical impact bar: a signer acting on unvalidated/unverified block state as if it had gone through the required gating.

### Likelihood Explanation
Reachable purely through gossip that a one-slot miner (plus a set of colluding/careless signers who sign without doing local validation, or a signer whose validation submission is delayed/queued) can trigger: peers broadcasting `BlockResponse::Accepted` for a block the local signer stored via `insert_block` but has not yet had `handle_block_validate_ok` run for. The `process_pending_responses_for_block` replay path (`signer.rs:1766-1778`) explicitly invokes `store_and_process_block_signature` for early-arriving signatures on a `block_info` that was *just* freshly created (`FRESH` path in section 3 of `docs/signer-flows.md:185-192`) and has not yet been submitted/validated, making the "unvalidated but signature-threshold-reached" state plausible under normal timing (busy validation slot, queued proposal, or race between proposal fan-out and peer signature fan-out), without requiring a signer majority to be malicious — just requiring peers to have already signed (which they must have, since this is exactly a >=70%-of-signatures-received state) while this local signer's own validation hasn't kept pace.

### Recommendation
In `store_and_process_block_signature`, before tallying weight and calling `mark_locally_accepted`/`broadcast_signed_block`, require that `block_info.valid == Some(true)` (or equivalently `block_info.state` is at least `PreCommitted`/`LocallyAccepted`), mirroring the guard already present in `handle_block_pre_commit` (line 1323). If the block has not been locally validated yet, the signature should be parked (as pending) and reprocessed once `handle_block_validate_ok`/`mark_pre_committed` runs for that `block_info`, consistent with how `add_pending_block_pre_commit_response` handles unknown blocks in `handle_block_pre_commit`.

### Proof of Concept
1. A miner proposes block `B`; the local signer stores `block_info` for `B` via `insert_block` but its own validation submission slot is busy (`self.submitted_block_proposal.is_some()`), so `B` is queued via `insert_pending_block_validation` (`stacks-signer/src/v0/signer.rs:1701-1719`) — `block_info.valid` remains `None`.
2. Other signers (already validated `B` on their own nodes) broadcast `BlockResponse::Accepted(B)` and reach ≥70% weight among themselves.
3. Local signer receives these `BlockResponse::Accepted` messages via `handle_block_response` → `handle_block_signature` → `store_and_process_block_signature` (`stacks-signer/src/v0/signer.rs:2442`); since each peer already has a recorded pre-commit, the `OLD` peer-fallback branch (line 2463) is skipped, and the function proceeds straight to weight tally at line 2495-2514 using only stored signatures, with no check of this signer's own `block_info.valid`.
4. Weight threshold is reached (using peers' weight, independent of this signer's own validation status) → `mark_locally_accepted(true)` and `broadcast_signed_block` execute (lines 2528-2537), causing this signer to push/assemble a signature set for a block it never confirmed was valid.

Note: I was unable to directly view the definitions of `BlockInfo::check_state`/`mark_locally_accepted` in `stacks-signer/src/signerdb.rs` in this session (grep did not return matches, possibly due to index limitations), so I could not fully confirm whether `mark_locally_accepted`'s internal state-transition guard independently blocks this call when `valid` is `None`. Given the design documentation explicitly states `check_state`'s rule is about `BlockState` reachability, not about `valid`, and the parallel gate in `handle_block_pre_commit` operates on `valid` as a separate condition, this exposure appears real, but confirming there is no last-mile guard inside `mark_locally_accepted` itself would benefit from a full Devin session with direct file access to `stacks-signer/src/signerdb.rs`.
