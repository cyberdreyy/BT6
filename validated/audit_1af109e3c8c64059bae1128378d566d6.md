### Title
Stale role/session caching in `ldap_sessions` allows revoked LDAP users to retain elevated access until the next `Work()` cycle, which never runs automatically under default config - ([File: core/sessions/ldapauth/sync.go])

### Summary
`LDAPServerStateSyncer.Work` is the only mechanism that purges or downgrades locally cached `ldap_sessions`/`ldap_user_api_tokens` rows to reflect upstream LDAP group membership changes, but with the default `UpstreamSyncInterval = '0s'` it only runs once at `Start()` and never again on a timer. Per-request authorization via `AuthenticateBySession` → `AuthorizedUserWithSession` reads the role directly from the local `ldap_sessions` table rather than revalidating against the upstream LDAP server, so a session created while the user held Admin/Edit privileges continues to authorize requests with that stale role indefinitely (until `SessionTimeout` expiry or a node restart), even after the user is demoted or fully removed from all LDAP groups.

### Finding Description
`ldapauth.ldapAuthenticator.AuthorizedUserWithSession` (`core/sessions/ldapauth/ldap.go:345-373`) authorizes a session purely by looking up the cached row in the local `ldap_sessions` table: [1](#0-0) 
It never re-queries the upstream LDAP server per request. The only code path that reconciles local role state with the upstream directory is `LDAPServerStateSyncer.Work` (`core/sessions/ldapauth/sync.go:93-284`), which re-queries LDAP groups and updates/purges `ldap_sessions` rows via `UPDATE ldap_sessions SET user_role = CASE ...` and `DELETE FROM ldap_sessions WHERE user_email = ANY(...)`.

`Work` is only invoked from two places:
- `Start()`, which runs `Work` a single time at startup when `UpstreamSyncInterval().IsInstant()` is true (the `'0s'` default): [2](#0-1) 
- The `run()` goroutine ticker, which is only started when `UpstreamSyncInterval` is non-zero: [3](#0-2) 

With the default `'0s'` value, `run()` is never started, so `Work()` executes exactly once (at node startup) and never again automatically. Meanwhile, `AuthenticateBySession` (`core/web/auth/auth.go:55-71`) simply forwards the session cookie's ID to `AuthorizedUserWithSession` and sets the returned (possibly stale) role in the Gin context with no additional per-request revalidation against LDAP: [4](#0-3) 

`POST /v2/jobs/:ID/runs` is wired to `auth.RequiresRunRole(prc.Create)` behind session/token auth only: [5](#0-4) 
`RequiresRunRole` only checks that `user.Role != UserRoleView` (`core/web/auth/auth.go:202-217`), and the `user.Role` value it checks is exactly the stale, DB-cached value from `AuthorizedUserWithSession`.

Attacker flow: (1) a user with an active `clsession` cookie backed by an `ldap_sessions` row with `user_role = 'admin'`/`'edit'` is removed from all upstream LDAP groups by an admin; (2) since `UpstreamSyncInterval` defaults to `'0s'`, no background sync occurs; (3) the attacker replays their existing session cookie against `POST /v2/jobs/123/runs`; `AuthorizedUserWithSession` returns the still-present `ldap_sessions` row with the old role, `RequiresRunRole` passes (any non-view role, including a role that should no longer exist), and the pipeline run is triggered via `prc.App.RunJobV2`.

### Impact Explanation
This is stale-privilege confinement failure (`AUTHORIZATION_EXACTNESS`): a fully de-provisioned upstream identity retains local elevated capabilities (not just "run" but whatever role — admin/edit — was cached at session creation, since the CASE-statement sync only updates roles for sessions still present after purge and purge only happens on `Work()`), enabling unauthorized job-run triggering and continued use of admin/edit-only endpoints. This maps to Chainlink's "unauthorized job run triggering / role-authorization bypass" bounty impact class. The scoped impact is limited to session-cookie continuation of already-granted actions until natural session expiry (`SessionTimeout`) or a node restart, but by default this window is effectively unbounded relative to the moment of upstream revocation, since no automatic periodic revalidation occurs.

### Likelihood Explanation
Preconditions: the attacker must already hold a valid, unexpired `clsession` cookie obtained while they had Admin/Edit/Run role (this is not privilege escalation from zero — it requires a prior valid authenticated session). No additional credentials, admin, or host access are required beyond the already-issued cookie. This is entirely feasible under the documented default configuration (`UpstreamSyncInterval = '0s'`), which is explicitly called out in `docs/CONFIG.md` as "sync-on-startup only" for the periodic path, though the same docs claim login/logout re-syncs occur — that claim does not cover the case of an *existing, still-cached* session simply continuing to be used without any further login/logout event. The exploit is deterministic and repeatable for the life of the session (bounded by `SessionTimeout`, default value not confirmed here) or until the next node restart or non-default configuration of `UpstreamSyncInterval`/manual restart triggers a fresh `Work()` execution.

### Recommendation
Perform (or optionally allow forcing) an upstream LDAP revalidation on a per-request or short-TTL basis rather than relying solely on the `Work()` sync cycle, e.g., by checking a "last synced" timestamp per session and forcing a targeted upstream lookup if it exceeds a maximum staleness bound, independent of whether `UpstreamSyncInterval` is configured to `'0s'`. At minimum, treat `UpstreamSyncInterval = '0s'` as "sync only at startup" explicitly in documentation and warn operators that revoked users retain access until the configured `SessionTimeout` elapses; consider enforcing a mandatory non-zero default/minimum for `UpstreamSyncInterval` in `ldapConfig` validation so that periodic reconciliation cannot be silently disabled.

### Proof of Concept
Go handler-level integration test plan (using `LDAPServerStateSyncer` and the `ldapauth` authenticator with a mock `LDAPClient`):
1. Configure `UpstreamSyncInterval` to the zero value (default) and start `LDAPServerStateSyncer` via `Start(ctx)`, mocking the LDAP client to initially return the target user as a member of the Admin group.
2. Assert `Work()` was invoked exactly once (at `Start()`), and that a row is created/synced in `ldap_sessions` with `user_role = 'admin'` for a fabricated session ID.
3. Insert (or drive via `CreateSession`) an `ldap_sessions` row for `user@example.com` with `user_role = admin`, simulating an active session.
4. Reconfigure the mock LDAP client so the same user is no longer present in any group (simulating upstream removal), but do **not** call `Work()` again and do not restart the syncer — assert no ticker/goroutine exists since `UpstreamSyncInterval().IsInstant()` is true.
5. Call `ldapAuthenticator.AuthorizedUserWithSession(ctx, sessionID)` directly (or drive the full `auth.AuthenticateBySession` gin middleware chain with a cookie for that session ID) and assert it still returns `Role: UserRoleAdmin` (no error), demonstrating no per-request LDAP revalidation occurs.
6. Drive a full HTTP integration test hitting `POST /v2/jobs/:ID/runs` with the stale session cookie and assert `http.StatusOK` / a pipeline run is created via `prc.App.RunJobV2`, proving the demoted/removed user can still trigger job runs.
7. As a control, manually invoke `Work(ctx)` again and re-run step 5/6, asserting the session is now purged from `ldap_sessions` and the same cookie yields `sessions.ErrUserSessionExpired` / HTTP 401.

```go
func (l *LDAPServerStateSyncer) Start(ctx context.Context) error {
	// If enabled, start a background task that calls the Sync/Work function on an
	// interval without needing an auth event to trigger it
	// Use IsInstant to check 0 value to omit functionality.
	if !l.config.UpstreamSyncInterval().IsInstant() {
		l.lggr.Info("LDAP Config UpstreamSyncInterval is non-zero, sync functionality will be called on a timer, respecting the UpstreamSyncRateLimit value")
		go l.run()
	} else {
		// Ensure upstream server state is synced on startup manually if interval check not set
		l.Work(ctx)
	}
	return nil
}
```

```go
func (l *LDAPServerStateSyncer) run() {
	defer close(l.done)
	ctx, cancel := l.stopCh.NewCtx()
	defer cancel()
	ticker := time.NewTicker(l.config.UpstreamSyncInterval().Duration())
	defer ticker.Stop()

	for {
		select {
		case <-ctx.Done():
			return
		case <-ticker.C:
			l.Work(ctx)
		}
	}
}
```

```go
func AuthenticateBySession(c *gin.Context, authr Authenticator) error {
	ctx := c.Request.Context()
	session := sessions.Default(c)
	sessionID, ok := session.Get(SessionIDKey).(string)
	if !ok {
		return auth.ErrorAuthFailed
	}

	user, err := authr.AuthorizedUserWithSession(ctx, sessionID)
	if err != nil {
		return err
	}

	c.Set(SessionUserKey, &user)

	return nil
}
```
