**Analysis:**

`append_action_transfer_to_gas_key` (`runtime/runtime/src/receipt_manager.rs:424-434`) simply appends a `TransferToGasKeyAction { public_key, deposit }` into the target receipt's action list, exactly mirroring `append_action_transfer` for regular `Transfer`. [1](#0-0) 

The caller-side host function `promise_batch_action_transfer_to_gas_key` (`runtime/near-vm-runner/src/logic/logic.rs:3197-3245`) deducts the deposit from the calling contract's own balance via `self.result_state.deduct_balance(amount)` before appending the action — so the attacker is only ever spending its own funds, not the victim's. [2](#0-1) 

On execution, `action_transfer_to_gas_key` (`runtime/runtime/src/access_keys.rs:257-288`) looks up the access key by `public_key` on the receiver account, requires it to already be a gas key (else `GasKeyDoesNotExist`), and does nothing but `checked_add` the deposit into `GasKeyInfo.balance`. [3](#0-2) 

This confirms the stated invariant holds: the action only increases balance and never touches `AccessKeyPermission` (FullAccess/FunctionCall/GasKeyFullAccess/GasKeyFunctionCall), which is fixed at `AddKey` time. [4](#0-3) 

Regarding the "reverse direction" the question raises (crediting an attacker-controlled gas key on the victim's account to later drain the victim): that would require the attacker to first have added its own public key as a gas key on the victim's account via `AddKey`, which itself requires either a `FullAccess`/`GasKeyFullAccess` signing key on the victim's account already — i.e., pre-existing full control of the victim account, which is out of scope and not something `TransferToGasKeyAction` grants. Gas-key balance only funds gas/deposit costs for transactions signed with the private key matching `public_key`; an attacker who merely observes `PK` on-chain does not possess the corresponding private key and thus cannot sign any nonce-indexed gas-key transaction, per `verify_and_charge_gas_key_tx_ephemeral` (`runtime/runtime/src/verifier.rs:383`). [5](#0-4) 

Value conservation holds exactly: attacker's account balance decreases by `deposit`, victim's gas key `balance` increases by the same `deposit` — this is functionally identical to the attacker donating funds via a plain `Transfer` action to the victim, and grants the attacker no new capability, permission, or reachable path to drain the victim's account balance. There is no authorization escalation, no double-spend, and no freezing of funds; the scenario does not meet the bounty-worthy impact criteria.

pub(crate) fn action_transfer_to_gas_key(
    state_update: &mut TrieUpdate,
    result: &mut ActionResult,
    account_id: &AccountId,
    action: &TransferToGasKeyAction,
) -> Result<(), RuntimeError> {
    let Some(mut access_key) = get_access_key(state_update, account_id, &action.public_key)? else {
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        // Key exists but is not a gas key
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };

    gas_key_info.balance = gas_key_info.balance.checked_add(action.deposit).ok_or_else(|| {
        RuntimeError::StorageError(StorageError::StorageInconsistentState(
            "gas key balance integer overflow".to_string(),
        ))
    })?;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);
    Ok(())
}
