### Title
Post-finalization `requestInstantWithdraw` reopens the closed default-epoch receipt bucket and drains `defaultRecoveryReserve`, permanently freezing honest claimants' recovery - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`requestInstantWithdraw` has no post-default guard and keeps writing new receipts into `instantWithdrawsRequestsByEpoch[_user][epochNumber]`. After `finalizeDefaultRecovery`, `epochNumber` no longer advances (the pool is defaulted and never restarted), so `epochNumber == defaultRecoveryEpoch` forever. When `defaultInstantWithdrawsFinalized` is true, `claimInstantWithdrawRequest` routes these brand-new receipts through `_claimDefaultedInstantWithdrawRequest`, which pays them out of `defaultRecoveryReserve` — a reserve sized exactly at finalization for pre-default claim basis only. This is the use-after-free analog: a destroyed/finalized accounting bucket (the defaulted epoch's instant-claim set) is reused to allocate new claims against a fixed recovery pool.

### Finding Description
In `requestInstantWithdraw`, the only state updates are: [1](#0-0) 

There is no `defaultRecoveryFinalized` check (unlike `requestWithdraw`, which has a dedicated post-default branch and an explicit `NotAllowed` guard for users with open receipts). After default, `epochNumber` stays equal to `defaultRecoveryEpoch` because no `startEpoch`/`stopEpoch` can run on a defaulted pool, so every new instant request lands in `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]`.

`claimInstantWithdrawRequest` then does: [2](#0-1) 

`_claimDefaultedInstantWithdrawRequest` pays `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` via `_transferDefaultRecovery`, which decrements the fixed `defaultRecoveryReserve`: [3](#0-2) 

The reserve was fixed at finalization as `reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` against `totalBasis` that included only pre-finalization claims (`defaultPendingClaimBasis()` = `pendingWithdraws` + current-epoch instant claims measured before the new request existed). [4](#0-3) 

Additionally, `pendingInstantWithdraws` is decremented toward 0 by the attacker's claim even though the borrower never funds post-default instant requests, corrupting the "unfunded remainder" invariant.

### Impact Explanation
Broken invariant: one receipt, one payout from a correctly-sized reserve; donation/reserve isolation.

Sequence for an unprivileged attacker (any KYC-passed lender):
1. Pool defaults; manager calls `finalizeDefault` with partial recovery (e.g. `recoveryPrice = 0.7e18`). `defaultRecoveryFinalized = true`, `defaultInstantWithdrawsFinalized = true` (some instant receipts were unfunded at finalization).
2. Attacker deposits `X` underlying post-default (`deposit()` mints 1:1 strategy tokens to the CDO and keeps `X` in the strategy's non-reserve balance).
3. Attacker calls `requestInstantWithdraw(X)` → `instantWithdrawsRequestsByEpoch[attacker][defaultRecoveryEpoch] = X`, `pendingInstantWithdraws += X`.
4. Attacker calls `claimInstantWithdrawRequest()` → routed through `_claimDefaultedInstantWithdrawRequest`, receives `X * recoveryPrice / RECOVERY_FULL` from `defaultRecoveryReserve`, and `pendingInstantWithdraws` is decremented (possibly to 0).
5. The reserve is now short by `X * recoveryPrice` relative to outstanding defaulted-epoch claims. The last legitimate claimant(s) calling `claimWithdrawRequest`/`claimInstantWithdrawRequest` hit `defaultRecoveryReserve -= amount` underflow (or an insolvent transfer) → their recovery is permanently unclaimable, while the attacker's deposited `X` sits isolated as non-reserve balance that `_transferFundedClaim` can never move into the reserve post-finalization.

If recovery is above par (`recoveryPrice > RECOVERY_FULL`, explicitly allowed by the code comment at line 687), the attacker's payout exceeds their deposit and the attack becomes directly profitable theft of the over-recovery surplus. Even at `recoveryPrice < 1`, honest claimants suffer a quantified permanent loss of `min(attackerDeposit * recoveryPrice, outstandingClaims)`.

### Likelihood Explanation
Requires a default with `pendingInstantWithdraws != 0` at finalization (partially unfunded instant queue — a normal state when instant liquidity was only partly collected before borrower default) plus any user willing to burn value to grief, or an over-recovery scenario making it profitable. No privileged cooperation needed; the post-default deposit and claim are entirely attacker-initiated.

### Recommendation
- Revert in `requestInstantWithdraw` when `defaultRecoveryFinalized` is true (mirroring the explicit post-default handling in `requestWithdraw`), or route post-default instant requests through a separate `postDefaultRequests`-style bucket paid at par from non-reserve funds.
- Alternatively, gate `claimInstantWithdrawRequest`'s defaulted path on receipts recorded strictly before finalization (e.g. snapshot `defaultRecoveryEpoch` claims via a finalized flag on the epoch bucket rather than re-reading the mutable `epochNumber` key).

```solidity
function testPostDefaultInstantWithdrawDrainsReserve() external {
    // 1. honest user deposits and creates an instant request that stays partially unfunded
    _depositWithUser(honest, 10_000 * ONE_SCALE, true);
    _depositWithUser(attacker, 10_000 * ONE_SCALE, true);
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr / 2, _expectedFundsEndEpoch()); // partial funding
    vm.prank(honest);
    cdoEpoch.requestWithdraw(0, address(AAtranche)); // becomes instant-mode request in instant mode
    // ... configure instant withdraw via setInstantWithdrawParams as in testFinalizeDefaultHaircutsPendingInstantRedeems

    // 2. borrower defaults; manager finalizes with recoveryRatio < 1
    uint256 recoveryRatio = 7e17;
    IdleCreditVault cv = IdleCreditVault(address(strategy));
    uint256 totalBasis = cdoEpoch.getContractValue() + cdoEpoch.expectedEpochInterest()
        - cdoEpoch.pendingWithdrawFees() + cv.defaultPendingClaimBasis();
    uint256 recovered = totalBasis * recoveryRatio / ONE_TRANCHE;
    deal(defaultUnderlying, manager, recovered);
    vm.startPrank(manager);
    IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();
    assertTrue(cv.defaultRecoveryFinalized());
    assertTrue(cv.defaultInstantWithdrawsFinalized()); // pendingInstantWithdraws != 0 at finalization

    // 3. attacker deposits X post-default and instantly requests withdrawal
    uint256 x = 1_000 * ONE_SCALE;
    deal(defaultUnderlying, attacker, x);
    vm.startPrank(attacker);
    IERC20Detailed(defaultUnderlying).approve(address(cdoEpoch), x);
    idleCDO.depositAA(x); // strategy mints 1:1, underlying kept as non-reserve balance
    cdoEpoch.requestInstantWithdraw(x, address(AAtranche)); // lands in byEpoch[defaultRecoveryEpoch]
    uint256 balPre = IERC20Detailed(defaultUnderlying).balanceOf(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    vm.stopPrank();
    assertGt(IERC20Detailed(defaultUnderlying).balanceOf(attacker) - balPre, 0);

    // 4. honest claimant's recovery is now short and reverts / is frozen
    vm.prank(honest);
    vm.expectRevert(); // defaultRecoveryReserve underflow or insolvent transfer
    cdoEpoch.claimInstantWithdrawRequest();
}
```

```text
  function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);
    }
    uint256 amount = instantWithdrawsRequests[_user];
    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
```
