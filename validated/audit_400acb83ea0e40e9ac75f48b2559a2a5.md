### Title
Standing write-off offers in `IdleCreditVaultWriteOffEscrow` have no expiry and can be executed at a stale price after tranche appreciation - (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
`createWriteOffRequest` records a lender's standing offer (escrowed tranche tokens in exchange for a fixed `underlyingsRequested`) with no `expirationTime`/deadline. `fullfillWriteOffRequest` lets **any** caller execute that offer at any later time — across epochs, after borrower repayments that appreciate tranche price, or after `stopEpoch` — as long as the offer was not manually deleted. This is the same bug class as the Gondi finding: a user-signed/recorded intent that remains executable long after the price context in which it was made has changed.

### Finding Description
In `createWriteOffRequest` the lender escrows `amount` tranche tokens and sets `underlyingsRequested` denominated in underlying:

```solidity
// contracts/IdleCreditVaultWriteOffEscrow.sol:97-101
userRequests[msg.sender] = WriteOffRequest({
  tranches: currentRequest.tranches + amount,
  underlyings: currentRequest.underlyings + underlyingsRequested
});
pendingUnderlyings += underlyingsRequested;
```

Any fulfiller can later settle it — the only check is `_underlyings >= currentRequest.underlyings` (line 129), i.e. the price is frozen at creation time forever:

```solidity
// :123-151
if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
  revert WrongRequest();
}
...
underlyingToken.safeTransferFrom(msg.sender, address(this), _underlyings);
...
IERC20Detailed(tranche).safeTransfer(msg.sender, _tranches);
```

There is no expiry, no epoch bound, and no oracle/price sanity check. Meanwhile tranche price (`IdleCDOEpochVariant.tranchePrice`) increases every `stopEpoch` as interest accrues. A lender who prices an exit during epoch N at, say, 90% of NAV can have that identical offer executed in epoch N+k when the same tranches are worth substantially more underlying — the fulfiller pockets the accrued interest that would otherwise belong to the lender.

Note `createWriteOffRequest` reverts unless `isEpochRunning()`, but `fullfillWriteOffRequest` has **no epoch-state gating at all**, so a request created in epoch N is fulfillable during the buffer period, in later epochs, or even after pool default, at the stale quote. `deleteWriteOffRequest` is the only escape and requires the lender to actively monitor and win a race against the fulfiller's transaction.

### Impact Explanation
Direct value extraction from the lender: the fulfiller pays `underlyingsRequested` set at an old, lower tranche price and receives tranche tokens redeemable at the current higher `tranchePrice`. The profit equals `(currentPrice - priceAtRequest) * tranches` — i.e. all yield accrued on the escrowed position since the offer was created, which economically belongs to the lender. Quantified example: lender escrows 1000 tranches priced at 1.00 asking 900 USDC; after one epoch of 10% APR accrual, a fulfiller pays 900 USDC for tranches worth ~1100 USDC, a ~200 USDC (~18%) theft from the lender.

### Likelihood Explanation
Medium. Write-off offers exist precisely because lenders want out during distress, so they are typically created below par and left standing; tranche price drifts upward every successful `stopEpoch`, monotonically increasing the gap. Anyone (any EOA — the fulfiller is permissionless per the comment "this function can be called by any wallet") can scan `userRequests` and fulfill profitable stale offers atomically. The victim's only defense is proactively calling `deleteWriteOffRequest`, identical to the "just set a short expiration" mitigation that was judged insufficient in the source finding.

### Recommendation
Add an `expiry`/`deadline` field to `WriteOffRequest` set by the lender at creation (bounded, e.g. `block.timestamp + maxTTL`), and revert in `fullfillWriteOffRequest` when `block.timestamp > expiry`. Alternatively, price fulfillment against current `tranchePrice` (require `_underlyings >= tranches * tranchePrice(tranche) / ONE_TRANCHE * agreedDiscount`) rather than the frozen `underlyingsRequested`, or auto-invalidate requests at `stopEpoch`/`startEpoch` transitions.

### Proof of Concept
Foundry fork PoC sketch (pattern after `test/foundry/IdleCreditVault.t.sol`):

```solidity
// lender deposits and gets AA tranches
uint256 tranches = _depositWithUser(lender, 1000e6, true);
uint256 staleQuote = 900e6; // 90% of current NAV

// epoch must be running to create the request
_startEpochAndCheckPrices(0);
vm.prank(lender);
IERC20(AAtranche).approve(address(escrow), tranches);
vm.prank(lender);
escrow.createWriteOffRequest(tranches, staleQuote);

// epoch stops; borrower repays principal + interest -> tranchePrice rises ~10%
_stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

// attacker fulfills the STALE offer during the buffer period (no epoch gating on fulfill)
address attacker = makeAddr("attacker");
deal(defaultUnderlying, attacker, staleQuote);
vm.startPrank(attacker);
IERC20Detailed(defaultUnderlying).approve(address(escrow), staleQuote);
escrow.fullfillWriteOffRequest(lender, tranches, staleQuote);
vm.stopPrank();

// attacker holds tranches worth > staleQuote at the new tranchePrice
uint256 attackerValue = tranches * cdoEpoch.tranchePrice(AAtranche) / 1e18;
assertGt(attackerValue, staleQuote); // attacker profit = accrued yield stolen from lender
```

The lender received `staleQuote - exitFee` for a position whose market value had already grown past it, with no mechanism to have limited the offer's validity window.
