## Analysis: Stale confirmations from removed multisig members still count toward the execution threshold

I found a valid analog. The Buyout bug is fundamentally about a **stored/cached authorization value diverging from the live state that should govern it** (stored `fractionPrice` vs. current `totalSupply`). The equivalent divergence in this repository is in the `multisig` and `multisig2` contracts: **a request's recorded `confirmations` set can retain a confirmation from a member whose signing authority has since been revoked**, and that stale confirmation still counts toward `num_confirmations` when a request is executed.

### Root cause

`confirm()` in both contracts only checks the *size* of the `confirmations` set against `num_confirmations` — it never re-validates that every already-recorded confirmer is still a current member: [1](#0-0) [2](#0-1) 

When a key/member is removed, the cleanup logic only purges **requests created by** that member — it does not scan other pending requests to strip out confirmations that member had already cast on requests created by someone else: [3](#0-2) [4](#0-3) 

So the binding that should hold — `confirmations counted == confirmations from currently-authorized members` — is broken: a confirmation recorded by member X before removal keeps counting after X is removed, even though X is no longer entitled to authorize spends from the account.

### Exploit path

1. Multisig has members `{A, B, C, D}`, `num_confirmations = 3`.
2. `A` creates request `R` (e.g. `Transfer` to an attacker-controlled account).
3. `B` calls `confirm(R)` — `confirmations[R] = {B}`.
4. The remaining members legitimately vote to remove `B` (e.g. because of a compromised key or offboarding) via `DeleteKey`/`DeleteMember`. This only removes requests *authored* by `B`; `R`'s confirmation set is untouched, so `confirmations[R]` still contains `B`.
5. `C` confirms `R` → `{B, C}` (2 entries, one of which is now from a non-member).
6. `D` confirms `R` → `{B, C, D}`, size `3 >= num_confirmations`, so `execute_request` fires the `Transfer`.

The transfer executes with only 2 *live* member confirmations (`C`, `D`) even though the contract's security policy requires `3` current members to agree — the threshold guarantee ("K of N live signers") is violated using a stale, revoked confirmation as the third vote.

### Title
Stale confirmations from removed multisig members count toward the execution threshold, allowing requests to execute below the live-member K-of-N threshold - (File: multisig/src/lib.rs, multisig2/src/lib.rs)

### Summary
`MultiSigContract::confirm` counts the size of a request's `confirmations` set against `num_confirmations` without verifying that each confirming key/account is still a current member. Removing a member (`DeleteKey`/`DeleteMember`) only deletes requests *created* by that member, leaving that member's confirmations on other pending requests intact. As a result, a request can be executed with fewer than `num_confirmations` *currently authorized* signers.

### Finding Description
`confirm()` in `multisig/src/lib.rs` (lines 246-266) and `multisig2/src/lib.rs` (lines 292-315) executes the request once `confirmations.len() + 1 >= self.num_confirmations`, purely a cardinality check on the stored `HashSet`. Membership removal (`DeleteKey` at `multisig/src/lib.rs:198-216`, `delete_member` at `multisig2/src/lib.rs:356-379`) filters and purges only requests where the removed key/member is the *creator* (`r.signer_pk == pk` / `r.member == member`); it never iterates `self.confirmations` for *other* requests to strip entries belonging to the removed member. There is no invariant re-check at `confirm`-time or `execute_request`-time that all recorded confirmers are still members. This is the direct analog of the reported Buyout bug: a value recorded at an earlier point in time (`fractionPrice` / a confirmer's authorization) is trusted at settlement time without being reconciled against the live state (`totalSupply` / current membership) that should govern it.

### Impact Explanation
This allows a multisig request (including a `Transfer` moving NEAR out of the account, or an `AddKey`/`AddMember` granting new signing authority) to be executed with strictly fewer live, currently-authorized confirmations than the configured `num_confirmations` threshold. This directly matches the Critical impact class "a multisig request executed below threshold" — funds can move, or governance actions can be taken, without the intended level of live agreement among currently trusted signers.

### Likelihood Explanation
This requires no privileged action by the attacker beyond having once been a legitimate multisig member/key holder — a realistic operational scenario (key rotation, offboarding a departing employee, revoking a compromised key) that every K-of-N multisig deployment using these contracts will eventually perform. Any request that received a confirmation from that member before their removal remains silently "primed" with a stale vote indefinitely, since there is no expiry or invalidation tied to membership changes.

### Recommendation
When removing a key/member (`DeleteKey` / `DeleteMember`), iterate all entries in `self.confirmations` (not just requests authored by the removed member) and remove the removed member's public key/account from every confirmation set. Alternatively, at `confirm()`/`execute_request()` time, re-validate that every entry in the request's `confirmations` set still corresponds to a current member before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C, D]`, `num_confirmations = 3`.
2. `A.add_request(Transfer{amount, receiver_id: attacker})` → request id `R`.
3. `B.confirm(R)` → `confirmations[R] = {B}` [2](#0-1) .
4. Members execute a separate, legitimately-confirmed `DeleteMember{member: B}` request → `delete_member` removes `B` from `self.members` and from requests it authored, but `confirmations[R]` is untouched [4](#0-3) .
5. `C.confirm(R)` → `confirmations[R] = {B, C}`.
6. `D.confirm(R)` → `confirmations[R].len() + 1 == 3 >= num_confirmations` → `execute_request(R)` fires the `Transfer` to the attacker [5](#0-4) , despite only `C` and `D` being live members who actually confirmed.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************

            ********************************/

        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
