### Title
View-role authenticated users can access `pprof` heap/goroutine/cmdline dumps via unauthorized `metricRoutes` mount - ([File: core/web/router.go])

### Summary
`metricRoutes(authv2)` is mounted inside the `authv2` group in `v2Routes`, which only enforces `auth.Authenticate` (valid session or API token) with no role check, unlike every sibling privileged route that wraps handlers with `auth.RequiresAdminRole`, `auth.RequiresEditRole`, or `auth.RequiresRunRole`. As a result, any authenticated user regardless of role, including `view`, can reach `GET /v2/debug/pprof/heap`, `/goroutine`, `/cmdline`, `/profile`, `/trace`, etc.

### Finding Description
`v2Routes` builds the `authv2` group with only `auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateByToken, auth.AuthenticateBySession)` [1](#0-0) . Every route with elevated privilege requirements explicitly wraps its handler in a role check, e.g. `authv2.GET("/users", auth.RequiresAdminRole(uc.Index))` [2](#0-1) . In contrast, the debug/pprof mount at the end of the group is called bare: `metricRoutes(authv2)` with no role wrapper at all [3](#0-2) .

`metricRoutes` registers the raw `net/http/pprof` handlers (`Index`, `Cmdline`, `Profile`, `Symbol`, `Trace`, `allocs`, `block`, `goroutine`, `heap`, `mutex`, `threadcreate`) directly under `/debug/pprof` off the passed-in router group, with no additional authorization middleware inside the function itself [4](#0-3) .

The role-check helpers `RequiresRunRole`, `RequiresEditRole`, and `RequiresAdminRole` in `core/web/auth/auth.go` are the only mechanism in this codebase that differentiate `view`/`run`/`edit`/`admin` roles after `Authenticate` succeeds [5](#0-4) . Since `metricRoutes` bypasses all of them, any user who passes `Authenticate` — including one with `UserRoleView` — reaches the pprof handlers. `pprof.Handler("heap")` and `pprof.Handler("goroutine")` dump full heap/goroutine state including any Go-managed process memory, which in a Chainlink node can transiently hold decrypted private keys, K/V store secrets, or plaintext values processed in pipeline runs.

### Impact Explanation
A low-privileged `view` credential holder (session or API token) can extract full heap/goroutine/profile dumps via `GET /v2/debug/pprof/heap`, `/v2/debug/pprof/goroutine`, `/v2/debug/pprof/profile`, etc. This is an authorization-bypass allowing a `view`-only user to obtain data intended to be admin-only, matching the "unauthorized data disclosure via role bypass" impact class. This does not itself compromise fund movement but does provide a path toward secret/key material disclosure (e.g., keys or credentials that may be held in Go heap memory during processing), and clearly violates the intended role separation asserted by every other route in the same group.

### Likelihood Explanation
The precondition is minimal: possession of any valid `view`-role session cookie or API token (the lowest privilege level explicitly defined in `clsessions.UserRoleView`). No additional exploitation steps, timing, or race conditions are required — a single authenticated GET request suffices, and the endpoint is deterministically reachable every time. This is fully reproducible via a router-level Go test.

### Recommendation
Wrap `metricRoutes`'s handlers with `auth.RequiresAdminRole` (consistent with the sensitivity of memory/goroutine dumps and consistent with other diagnostic-adjacent admin-only routes like `/log` PATCH), either by changing the call site to `metricRoutes(authv2.Group("", ...))` with a `RequiresAdminRole`-wrapping middleware, or by modifying `metricRoutes` to accept and apply a role-gating middleware/wrapper to each handler registration.

### Proof of Concept
Table-driven `httptest`/gin router test in `core/web/router_test.go` style:
1. Build a test app + router via `NewRouter`, seeding four users with roles `view`, `run`, `edit`, `admin` and valid sessions/tokens for each.
2. For each role, issue `GET /v2/debug/pprof/heap` (and repeat for `/cmdline`, `/goroutine`, `/profile`) with the corresponding session cookie/API-key headers.
3. Assert: only the `admin` role returns HTTP 200 with pprof binary/profile content; `view`, `run`, and `edit` should return `403 Forbidden` (matching behavior of `RequiresAdminRole`-gated routes like `/v2/users`).
4. Currently, with no role gate, all four roles (including `view`) return `200 OK`, confirming the bypass.

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// RequiresEditRole extracts the user object from the context, and asserts the user's role is at least
// 'edit'
func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// RequiresAdminRole extracts the user object from the context, and asserts the user's role is 'admin'
func RequiresAdminRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role != clsessions.UserRoleAdmin {
			c.Abort()
			addForbiddenErrorHeaders(c, "admin", string(user.Role), user.Email)
			jsonAPIError(c, http.StatusForbidden, errors.New("Forbidden"))
			return
		}
		handler(c)
	}
}
