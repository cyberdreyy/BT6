### Title
Stale confirmations from a deleted multisig member still count toward `num_confirmations`, allowing execution of a request below the effective live-member threshold - ([File: multisig2/src/lib.rs])

### Summary
`MultiSigContract::delete_member` only purges requests *authored* by the member being removed; it does not scan the `confirmations` map to strip that member's confirmation(s) recorded on requests authored by *other* members. Because `confirm()` counts confirmations purely by set size (`confirmations.len() as u32 + 1 >= self.num_confirmations`) without checking whether every confirming identity is still a current member, a confirmation cast by a member before they are removed remains valid and can push a pending request over the threshold using votes from members who are no longer part of the multisig.

### Finding Description
The custody binding a K-of-N multisig must preserve is: `confirmations counted toward threshold == confirmations from members that are live at execution time`. This binding is broken here.

`confirm()` in `multisig2/src/lib.rs` decides execution solely from the size of the stored confirmation set for the request: [1](#0-0) 

`delete_member()` removes the member from `self.members` and cleans up only the requests where `r.member == member` (i.e., requests the removed member originally *authored*), plus their `num_requests_pk` entry. It never iterates `self.confirmations` to remove the removed member's identity from confirmation sets of requests authored by other members: [2](#0-1) 

Contrast this with the request-cleanup logic, which is scoped to "requests by this member" rather than "confirmations by this member": [3](#0-2) 

Because `confirm()` never re-validates that each string in `confirmations` corresponds to `self.members.contains(...)`, a removed member's earlier vote is silently retained as valid weight forever (or until the request is separately deleted/executed).

The legacy `multisig/src/lib.rs` contract has the analogous `DeleteKey` action, which likewise only removes requests where `r.signer_pk == pk` and only clears `num_requests_pk`, not other requests' `confirmations` entries containing that key — the same class of bug.

### Impact Explanation
This directly matches the Critical impact category "a multisig request executed below threshold." The number of confirmations required (`num_confirmations`) is meant to represent votes from the *current* member set. If a member is removed (e.g., because their key is suspected compromised, or they leave the organization) after having confirmed an outstanding request, that stale confirmation remains counted. The remaining live members then only need `num_confirmations - 1` fresh confirmations to execute an arbitrary request (`Transfer`, `FunctionCall`, `AddKey`, `DeployContract`, etc.), effectively lowering the real security threshold below what `num_confirmations` was configured/believed to guarantee. In the worst case — a removed member whose key was compromised specifically because an attacker used it to confirm a malicious `Transfer` request — deleting that member as a remediation step does not invalidate the vote the attacker already cast, so the malicious transfer can still be pushed through with fewer legitimately live signers than the threshold requires.

### Likelihood Explanation
No privileged action or victim key is required from the attacker's perspective beyond the normal multisig operation flow (create request, get partial confirmations, member removal happens as ordinary multisig governance/key-rotation). This is a logic bug reachable through the contract's standard, well-documented operations (`add_request`, `confirm`, `DeleteMember`), not a misconfiguration or ignored initialization step, making it readily triggerable in real-world usage whenever membership changes while requests are outstanding.

### Recommendation
When removing a member (`delete_member` / `DeleteKey` in the legacy contract), iterate over `self.confirmations` for all pending requests and remove the departing member's identity from every confirmation set (not just requests they authored). Alternatively, validate at `confirm()`-time and at threshold-check-time that every entry in the confirmation set still belongs to `self.members`, discarding stale entries (or recomputing the live count) before comparing against `num_confirmations`.

### Proof of Concept
1. Initialize `MultiSigContract` with `num_confirmations = 3` and members `{A, B, C, D}`.
2. `D` calls `add_request_and_confirm` (or `add_request` + `confirm`) with a `Transfer` request sending funds to an attacker-controlled account. Confirmations = `{D}` (1/3).
3. Through normal governance, the multisig executes a `DeleteMember { member: D }` request (e.g., because D's key was flagged as compromised). `delete_member` removes `D` from `self.members`; it does **not** touch the confirmations set of the Transfer request from step 2, which still contains `"D"`.
4. `A` calls `confirm(request_id)` → confirmations = `{D, A}` (2/3).
5. `B` calls `confirm(request_id)` → confirmations = `{D, A, B}` (3/3) → `confirmations.len() + 1 >= num_confirmations` is satisfied → `execute_request` fires the `Transfer` to the attacker.

Only 2 currently-live members (A, B) plus one stale, revoked confirmation (D) authorized a transfer that was supposed to require 3 confirmations from the live 3-member set `{A, B, C}` — the request executed below the effective threshold.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
