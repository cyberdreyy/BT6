## Title
Stale confirmations from removed multisig members still count toward the confirmation threshold, allowing a request to execute below the live-member threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::confirm` in `multisig2/src/lib.rs` counts a request as approved once the size of its stored `confirmations` set reaches `num_confirmations`, without re-checking that every account/key in that set is still a current member. `delete_member` only purges requests *created* by the removed member; it never scans and scrubs the `confirmations` sets of *other* pending requests that the removed member had already confirmed. As a result, a member can be voted out of the multisig, yet its earlier confirmation on an unrelated pending request keeps counting toward the K-of-N threshold, letting that request execute with fewer than K currently-authorized confirmations.

### Finding Description
The confirmation-threshold check is: [1](#0-0) 

It compares `confirmations.len() + 1` against `self.num_confirmations`, where `confirmations` is a `HashSet<String>` keyed by member identity (public key or account id) stored independently of the live `members: UnorderedSet<MultisigMember>` set: [2](#0-1) 

When a member is removed via the `DeleteMember` action, `delete_member` only removes *requests the member itself created* and the member's own `num_requests_pk` entry — it never walks `self.confirmations` to strip the removed member's entry from confirmation sets of requests created by *other* members: [3](#0-2) 

`assert_valid_request`, called at the top of `confirm`, only validates that the *current caller* is a member — it performs no validation that the previously-recorded confirmers in the set are still members: [4](#0-3) 

This breaks the intended invariant "number of confirmations counted == number of confirmations from currently authorized (live) members." A removed member's stale confirmation is indistinguishable from a live member's confirmation and is counted equally when the threshold check runs.

The same pattern (no scrubbing of confirmations on unrelated requests when a key is deleted) exists in the legacy `multisig/src/lib.rs` contract as well: [5](#0-4) 

### Impact Explanation
This is a Critical-severity issue per the custody-binding categories in scope ("a multisig request executed below threshold"). A request that legitimately requires K live confirmations can execute with only K−1 live confirmations plus one stale confirmation from an already-removed member, effectively lowering the multisig's real security threshold without any of the current members noticing or intending it. Since multisig requests can include `Transfer`, `FunctionCall`, `AddKey`, or `AddMember`/`DeleteMember` actions, this can be leveraged to move NEAR funds or grant/alter access with less real authorization than configured.

### Likelihood Explanation
The attack requires no privileged pre-conditions beyond ordinary multisig operation:
- Any member can confirm a pending request at any time before its removal is finalized.
- Removal of a member is a normal multisig lifecycle event (e.g., revoking a compromised or departing member's access), which is exactly the scenario where this flaw matters most — the entity being removed can leave "landmine" confirmations behind on any request it confirmed before removal.
- No special timing constraints beyond having one unexecuted, unconfirmed request pending when the member is removed, and the remaining live members simply continuing to confirm it as usual (they have no way of detecting that one of the recorded confirmations belongs to a removed member, because `get_confirmations` just returns the raw stored set).

### Recommendation
When removing a member in `delete_member`, iterate over `self.confirmations` (not just `self.requests` filtered by creator) and remove the departing member's entry from every request's confirmation set. Alternatively/additionally, in `confirm`, before counting toward the threshold, filter the stored confirmation set to only those entries still present in `self.members`, and use that filtered length for the threshold comparison so removed members can never contribute to execution of any request.

### Proof of Concept
1. Deploy `multisig2` with members `[A, B, C, D]` and `num_confirmations = 3`.
2. `A` calls `add_request` to create request `R` (e.g., a `Transfer` action).
3. `B` calls `confirm(R)` → `confirmations = {B}` (len 1, `1+1=2 < 3`, not executed).
4. `C` calls `confirm(R)` → `confirmations = {B, C}` (len 2, `2+1=3 >= 3`... note: with num_confirmations=3 this specific step would actually execute; use `num_confirmations = 4` and members `[A,B,C,D,E]` to leave room for one pending confirmation after removal).
5. Separately, the remaining members submit and confirm a `DeleteMember { member: B }` request, which succeeds via `execute_request` → `delete_member`, removing `B` from `self.members` — but `R`'s `confirmations` set (which still contains `B`) is untouched, per `delete_member` at [6](#0-5) .
6. `D` and then `E` call `confirm(R)`. The threshold check in `confirm` counts `B`'s stale confirmation together with `C`, `D`, `E`, reaching `num_confirmations` and executing `R` even though `B` is no longer a member — i.e., the request executed with only 3 live confirmations (`C`, `D`, `E`) against a configured 4-of-N threshold.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
