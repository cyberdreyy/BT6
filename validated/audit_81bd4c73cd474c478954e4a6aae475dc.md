### Title
View-role authenticated user can list all external initiators and obtain their `AccessKey`/`OutgoingToken` credentials via unrestricted GET /v2/external_initiators - ([File: core/web/router.go])

### Summary
The route `GET /v2/external_initiators` is registered as `authv2.GET("/external_initiators", paginatedRequest(eia.Index))` with no role-restriction wrapper, while the sibling `POST`/`DELETE` routes for the same resource require `auth.RequiresEditRole`. Any authenticated user — including the minimum-privilege `view` role — can call this endpoint and receive `AccessKey` and `OutgoingToken` values for every external initiator, which are secret authentication credentials.

### Finding Description
The `authv2` group only requires successful authentication (`auth.Authenticate` via session or token), not any specific role. `ExternalInitiatorsController.Index` at `core/web/external_initiators_controller.go` builds `presenters.ExternalInitiatorResource` for each initiator and returns it unfiltered: [1](#0-0) 
That presenter includes the raw `AccessKey` and `OutgoingToken` fields with no redaction: [2](#0-1) 
In `router.go`, the route registration lacks any `auth.RequiresEditRole`/`RequiresRunRole` wrapper that the `Create`/`Destroy` endpoints for the same resource use: [3](#0-2) 
Compare this with other sensitive listing endpoints, such as `/users`, which is explicitly wrapped with `auth.RequiresAdminRole`: [4](#0-3) 
Since the `authv2` middleware only checks that a valid session/token exists (any role, including `view`), and `Index` performs no additional role check itself, a `view`-role session is sufficient to reach the handler and receive the full, unredacted list of `AccessKey`/`OutgoingToken` values.

### Impact Explanation
This is a credential/secret-disclosure vulnerability: an unprivileged (`view`-role) authenticated user can retrieve the `AccessKey` and `OutgoingToken` of every configured external initiator on the node. `AccessKey`+`Secret` pairs are used to authenticate external initiators to trigger webhook job runs (`AuthenticateExternalInitiator` in `core/web/auth/auth.go`), and `OutgoingToken`/`OutgoingSecret` are used by the node to call back into the external initiator's own API. Disclosure of `AccessKey`/`OutgoingToken` values to a low-privilege user enables identification/enumeration of the initiator population and, combined with the (separately non-disclosed) secret, could facilitate impersonation of external initiators or webhook job triggering — this fits the "sensitive-data/credential disclosure to unprivileged user" bounty impact class.

### Likelihood Explanation
Minimal precondition: attacker only needs a valid `view`-role session or API token (the lowest privilege tier), which is explicitly the "unprivileged user" persona in scope. The exploit is a single unauthenticated-role-but-authenticated GET request with no other barriers, fully deterministic and repeatable.

### Recommendation
Wrap the `GET /v2/external_initiators` route with an appropriate role check (at minimum `auth.RequiresEditRole`, matching the `Create`/`Destroy` handlers for the same resource) in `core/web/router.go`:
```go
authv2.GET("/external_initiators", auth.RequiresEditRole(paginatedRequest(eia.Index)))
```
Additionally, consider redacting `AccessKey`/`OutgoingToken`/secret fields from list responses regardless of role, similar to how `ExternalInitiatorAuthentication` only returns secrets once on creation.

### Proof of Concept
Go handler-level integration test (extending `core/web/external_initiators_controller_test.go`):
1. Start `cltest.NewApplicationWithConfig` with `ExternalInitiatorsEnabled = true`.
2. Create a user with `sessions.UserRoleView` (see helpers used in `core/web/auth/auth_test.go` for role-based session creation) and obtain an authenticated HTTP client bound to that view-role session/token.
3. Insert an external initiator via `cltest.MustInsertExternalInitiatorWithOpts`.
4. Issue `client.Get("/v2/external_initiators")` using the view-role client.
5. Assert `http.StatusOK` (not `401`/`403`).
6. Parse the JSON:API response into `[]presenters.ExternalInitiatorResource` and assert `AccessKey` and `OutgoingToken` fields are non-empty and match the inserted initiator's values — demonstrating credential disclosure to a `view`-role user.
