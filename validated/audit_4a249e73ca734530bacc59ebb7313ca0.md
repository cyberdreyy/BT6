Based on my research, the `create` function in `lockup-factory/src/lib.rs` lets the caller (whoever funds the lockup) supply an arbitrary `whitelist_account_id`, which is baked into the deployed lockup contract's `staking_pool_whitelist_account_id` field with no validation that it is the NEAR Foundation's official whitelist contract.

### Title
Attacker-supplied `whitelist_account_id` in `LockupFactory::create` lets a lockup owner bypass the staking-pool whitelist and release locked/unvested NEAR early - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create` accepts an optional `whitelist_account_id` parameter directly from the (unprivileged) caller and, if provided, uses it verbatim as the `staking_pool_whitelist_account_id` baked into the newly deployed lockup contract's `new` args, instead of always enforcing the factory's own vetted `self.whitelist_account_id`.

### Finding Description
`lockup-factory/src/lib.rs`'s `create` method computes: [1](#0-0) 
which lets the caller override the whitelist account with any account they choose, including one they deploy and control themselves. This value is written unchecked into `LockupArgs.staking_pool_whitelist_account_id` and shipped to the new lockup contract's `new` constructor: [2](#0-1) 

Inside the deployed `lockup` contract, `staking_pool_whitelist_account_id` is the sole trust anchor used to authorize which staking pool the owner may delegate to: `select_staking_pool` calls `ext_whitelist::is_whitelisted` against exactly this stored account and, on a `true` callback, unconditionally accepts the pool as the "known-safe" delegation target: [3](#0-2) [4](#0-3) 

The whitelist contract's entire purpose is to be the NEAR Foundation-controlled guarantee that a staking pool "faithfully implement[s] the spec" and "can not be lost or locked," per the whitelist contract's own documentation: [5](#0-4) 

Because the factory lets the funding caller pick this whitelist account, the owner of a newly created lockup (who is also typically the funding caller, or can arrange to be) can point `staking_pool_whitelist_account_id` at a contract they deploy themselves that always returns `true` from `is_whitelisted`. `select_staking_pool` will then accept an attacker-controlled "staking pool" account, and subsequent `deposit_and_stake` / `deposit_to_staking_pool` calls will transfer the lockup's NEAR — including tokens still under a vesting schedule or lockup timestamp that the owner is not supposed to be able to move — to that attacker-controlled account, from which it can be withdrawn immediately, bypassing the lockup/vesting release schedule entirely. The existing test `test_create_lockup_with_custom_whitelist_success` in the same file confirms this override path is live and exercised, but it treats it as a supported feature rather than validating that only the Foundation's whitelist can be used: [6](#0-5) 

### Impact Explanation
The lockup contract's stated guarantee is that "the owner can not withdraw tokens locked due to lockup period, disabled transfers, or vesting schedule," enforced only via the whitelist-gated staking pool selection, per `lockup/README.md`: [7](#0-6) 
By supplying a self-controlled `whitelist_account_id` at lockup-creation time, the owner (or the funding party who controls the created lockup's owner_account_id) breaks the equality binding `staking_pool_whitelist_account_id == Foundation-approved whitelist`, which the entire staking-delegation security model of the lockup contract depends on. This lets the lockup owner move locked/unvested NEAR out to an account they fully control, i.e., release of locked or unvested tokens early — a Critical-severity outcome per the rubric ("locked or unvested tokens released early... a wrongly whitelisted or wrongly parameterised deployment").

### Likelihood Explanation
`create` is a `#[payable]` method callable by any unprivileged NEAR account with the minimum attached deposit; no foundation or owner privilege is required to invoke it or to pass a custom `whitelist_account_id`. The only extra work required by the attacker is deploying a trivial "always whitelisted" contract, which is straightforward and inexpensive on NEAR. This makes the likelihood high for any lockup created through this factory with a maliciously chosen `whitelist_account_id` (particularly relevant for vesting lockups, where the owner has a direct financial incentive to bypass the vesting schedule).

### Recommendation
Remove the ability for the caller to override the whitelist account, or restrict overriding to only the foundation-controlled caller path. `LockupFactory::create` should always use `self.whitelist_account_id` (the value fixed at factory initialization by the Foundation) for `staking_pool_whitelist_account_id`, and drop the `whitelist_account_id: Option<ValidAccountId>` parameter, or gate it behind an `assert_eq!(env::predecessor_account_id(), self.foundation_account_id)` check so only the Foundation can choose a non-default whitelist.

### Proof of Concept
1. Attacker deploys `EvilWhitelist` contract exposing `is_whitelisted(staking_pool_account_id) -> bool { true }`.
2. Attacker deploys `EvilPool` contract that accepts `deposit_and_stake`/`deposit` and simply keeps/forwards any NEAR sent to it.
3. Attacker calls `lockup_factory.create(owner_account_id: attacker, lockup_duration, ..., vesting_schedule: Some(schedule_with_foundation_control), whitelist_account_id: Some("EvilWhitelist"))` with the minimum attached deposit, per `lockup-factory/src/lib.rs:107-166`.
4. Once the lockup contract is created with `staking_pool_whitelist_account_id = "EvilWhitelist"`, attacker (as owner) calls `select_staking_pool("EvilPool")`; the lockup calls `EvilWhitelist::is_whitelisted` which returns `true`, so `on_whitelist_is_whitelisted` accepts `EvilPool` as the staking pool per `lockup/src/owner_callbacks.rs:6-25`.
5. Attacker calls `deposit_and_stake` (or `deposit_to_staking_pool`) to move the full locked/unvested lockup balance to `EvilPool`, per `lockup/src/owner.rs:122-166`, from which attacker withdraws freely — releasing tokens that should still be locked/unvested under the schedule enforced by the Foundation.

    pub fn select_staking_pool(&mut self, staking_pool_account_id: AccountId) -> Promise {
        self.assert_owner();
        assert!(
            env::is_valid_account_id(staking_pool_account_id.as_bytes()),
            "The staking pool account ID is invalid"
        );
        self.assert_staking_pool_is_not_selected();
        self.assert_no_termination();

        env::log(
            format!(
                "Selecting staking pool @{}. Going to check whitelist first.",
                staking_pool_account_id
            )
            .as_bytes(),
        );

        ext_whitelist::is_whitelisted(
            staking_pool_account_id.clone(),
            &self.staking_pool_whitelist_account_id,
            NO_DEPOSIT,
            gas::whitelist::IS_WHITELISTED,
        )
        .then(ext_self_owner::on_whitelist_is_whitelisted(
            staking_pool_account_id,
            &env::current_account_id(),
            NO_DEPOSIT,
            gas::owner_callbacks::ON_WHITELIST_IS_WHITELISTED,
        ))
    }

The purpose of this contract is to maintain the whitelist of the staking pool contracts account IDs that are approved
by NEAR Foundation.

In order for the lockup contracts to be able delegate to a staking pool, the staking pool should faithfully implement the spec.
The staking pool should guarantee that the delegated tokens can not be lost or locked, such as the lockup contract should be
able to recover delegated tokens back to the lockup from a staking pool. In order to enforce this, only approved (whitelisted)
accounts of staking pool contracts can receive delegated tokens from lockup contracts.

### Guarantees

With the guarantees from the staking pool contracts, whitelist, and voting contract, the lockup contract provides the following guarantees:
- The owner can not lose tokens or block contract operations by using methods under the staking section.
- The owner can not prevent the foundation from withdrawing the unvested balance in case of termination.
- The owner can not withdraw tokens locked due to lockup period, disabled transfers, or vesting schedule.
