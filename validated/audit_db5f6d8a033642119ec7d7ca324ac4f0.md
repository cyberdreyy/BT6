### Title
Instant-withdraw receipts from epochs prior to the default epoch are excluded from recovery basis and become permanently unclaimable - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`defaultPendingClaimBasis()` and `_claimDefaultedInstantWithdrawRequest()` index instant-withdraw claims only by `instantWithdrawClaimsByEpoch[epochNumber]` / `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` — i.e., only the *current* epoch. Unfunded instant receipts requested in earlier epochs are omitted from the default recovery basis, yet remain in `instantWithdrawsRequests[user]`. After finalization, `claimInstantWithdrawRequest` tries to pay the leftover balance at par via `_transferFundedClaim`, which reverts because the entire strategy balance is now recovery reserve. The receipt is permanently frozen and was never allocated recovery funds — a stale-index/count-mismatch bug analogous to the libheif chunk-index OOB (a lookup keyed by an index that does not match the recorded entries).

### Finding Description
`requestInstantWithdraw` tags each receipt with the *current* `epochNumber` in `instantWithdrawsRequestsByEpoch[user][epochNumber]` and `instantWithdrawClaimsByEpoch[epochNumber]`, while the unfunded remainder is tracked globally in `pendingInstantWithdraws` [1](#0-0) . There is no per-epoch rollover: an instant request that cannot be funded stays pending across subsequent epochs with its original epoch tag.

When the borrower defaults and `finalizeDefaultRecovery` runs, the claim basis is `pendingWithdraws + instantWithdrawClaimsByEpoch[epochNumber]` (only when `pendingInstantWithdraws != 0`) [2](#0-1) . Any instant receipt whose request epoch is *older* than the default epoch contributes to `pendingInstantWithdraws` (the unfunded remainder) but is not in `instantWithdrawClaimsByEpoch[epochNumber]`, so it is silently dropped from `totalBasis`. Correspondingly, `_defaultPrefundedInstantReserve` computes `instantBasis(current epoch) - pendingInstant`; when the global remainder exceeds the current-epoch basis it returns 0, so no part of the old-epoch claim enters `defaultRecoveryReserve` either [3](#0-2) .

Post-default, `claimInstantWithdrawRequest` clears only `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` via `_claimDefaultedInstantWithdrawRequest` [4](#0-3) , then burns the entire remaining `instantWithdrawsRequests[user]` and calls `_transferFundedClaim` [5](#0-4) . `_transferFundedClaim` reverts with `NotAllowed` whenever `balance - defaultRecoveryReserve < amount` [6](#0-5) . After finalization the strategy balance equals the reserve (reserve includes external recovery + prefunded instant cash + `defaultRecoveryReserve` [7](#0-6) ), so the call always reverts — the transaction rolls back and the user's old-epoch receipt can never be claimed.

### Impact Explanation
Permanent freezing of unclaimed yield/withdrawals. A user whose instant-withdraw request went unfunded in epoch N and whose pool defaults in epoch M>N loses access to the entire receipt amount: it is excluded from the recovery distribution (no haircut payout) and the par-value fallback path reverts forever. Quantified loss = 100% of the old-epoch unfunded instant receipt (e.g., 100,000 USDC receipt → 0 claimable). Additionally, because the old basis was excluded from `totalBasis`, `defaultRecoveryPrice` is marginally overstated for all other claimants, but the reserve is still fully consumed, so the primary harm is the frozen receipt. This is exactly the scenario where instant requests go unfunded — borrower illiquidity preceding default — making it a realistic path rather than an edge case.

### Likelihood Explanation
Medium-low. Requirements: (1) an instant-withdraw request must remain unfunded across an epoch boundary — `instantWithdrawsRequestsByEpoch` entries are only cleared on claim, and unfunded requests persist since `collectInstantWithdrawFunds` only decrements the global counter [8](#0-7) ; (2) the borrower must later default and the CDO must call `finalizeDefaultRecovery` (owner/manager are honest and would do this to unlock recovery). No attacker privilege is needed — any KYC'd lender can request an instant withdraw during a liquidity-short epoch. The guard in `_claimFundedWithdrawRequest`/`requestWithdraw` for `lossRecoveryPriceByEpoch` does not apply to the instant path, and `postDefaultRequests`/`_hasWithdrawRequest` gating does not cover instant receipts [9](#0-8) .

### Recommendation
Include all unfunded instant receipts in the default claim basis, not just the current epoch's. Two options:

1. In `defaultPendingClaimBasis`, use the global unfunded remainder directly: `basis += pendingInstantWithdraws` (which already aggregates all unfunded instant claims across epochs), and compute the prefunded reserve against the same aggregate rather than `instantWithdrawClaimsByEpoch[epochNumber]`.
2. On the claim side, iterate/accumulate `instantWithdrawsRequestsByEpoch` across all epochs ≤ `defaultRecoveryEpoch` when clearing in `_claimDefaultedInstantWithdrawRequest`, instead of only `defaultRecoveryEpoch`.

Add a regression test: request instant withdraw in epoch N with insufficient liquidity, advance epochs, default + `finalizeDefaultRecovery`, then assert the user receives `amount * defaultRecoveryPrice / 1e18`.

### Proof of Concept
Foundry fork test (extends `test/foundry/IdleCreditVault.t.sol` helpers `_depositWithUser`, `_startEpochAndCheckPrices`, `_stopEpochAndCheckPrices`):

```solidity
function testOldEpochInstantReceiptFrozenAfterDefault() external {
    _useStandardEpochVariant();
    // epoch 0 -> 1: setup, enable instant withdraws
    _stopCurrentEpochWithApr(10e18);
    address user1 = makeAddr('user1');
    uint256 tranches1 = _depositWithUser(user1, 100e6);

    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(100, 1e18, false);
    vm.prank(manager);
    cdoEpoch.startEpoch();

    // Drain strategy liquidity so the instant request stays UNFUNDED
    // (borrower takes all cash; instant request remains pending in epoch 1)
    uint256 epoch1 = strategy.epochNumber();
    vm.prank(user1);
    cdoEpoch.requestWithdraw(tranches1, address(tranche)); // routes to instant path
    assertEq(strategy.instantWithdrawsRequestsByEpoch(user1, epoch1), tranches1);
    assertGt(strategy.pendingInstantWithdraws(), 0); // unfunded remainder > 0

    // epoch advances; receipt keeps its old epoch tag
    _stopCurrentEpochWithApr(10e18);
    vm.prank(manager);
    cdoEpoch.startEpoch(); // now epoch2; user1 instant receipt still tagged epoch1

    // borrower defaults in epoch2
    deal(address(underlying), strategy.borrower(), 0, true);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(cdoEpoch.owner());
    cdoEpoch.stopEpoch(0, 0);
    assertTrue(cdoEpoch.defaulted());

    // finalize recovery with partial recovered funds
    uint256 recovered = strategy.balanceOf(address(cdoEpoch));
    deal(address(underlying), manager, recovered, true);
    vm.startPrank(manager);
    underlying.approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();

    // old-epoch instant basis was excluded from totalBasis -> priced for nothing
    // claim path: clears epoch2 basis (0), then tries par payout of the epoch1 remainder
    vm.prank(user1);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.claimInstantWithdrawRequest(); // reverts in _transferFundedClaim forever
}
```

Key assertion: `instantWithdrawClaimsByEpoch[epoch1]` holds the user's basis but `defaultPendingClaimBasis()` reads only `instantWithdrawClaimsByEpoch[epochNumber] = epoch2` (0 for this user), so the receipt is neither haircut-paid nor par-payable — permanently frozen.

```text
  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```

```text
  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
```
