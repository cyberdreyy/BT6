### Title
Raw ANSI/control bytes in job commands bypass escaping in POSIX-mode trace sections, enabling terminal/log spoofing - (File: functions/script_legacy/internal/trace_section.go, functions/script_legacy/internal/escape.go)

### Summary
When `FF_SCRIPT_SECTIONS`/`trace_sections=true` is combined with the POSIX shell escaping mode (`posixMode=true`), `TraceSectionWriter.writeSectionStart` routes the command preview through `EscapeForPosix` instead of `EscapeForAnsiC`. Unlike `EscapeForAnsiC`, `EscapeForPosix` does not neutralize control bytes such as ESC (`0x1b`), so a multi-line job command containing raw ANSI/CSI/OSC sequences is written verbatim into the trace stream between the fixed `ansiClear`/`ansiBoldGreen` constants and the command echo.

### Finding Description
`CommandProcessor.ProcessCommand` (`functions/script_legacy/internal/command_processor.go:38-39`) calls `TraceSectionWriter.WriteSection` whenever `shouldUseTraceSection` is true (`traceSections && isMultiline(command)`), which is fully attacker-influenceable via a multi-line `script:` entry once `trace_sections`/`FF_SCRIPT_SECTIONS` is enabled. [1](#0-0) 

Inside `writeSectionStart`, the command is escaped via `w.escape(...)`, and `escape()` branches on `posixMode`: [2](#0-1) 

- Non-posix branch: wraps with ANSI-C quoting and calls `EscapeForAnsiC`, which explicitly hex-escapes all control characters `0x00-0x1F`, `0x7F`, and non-ASCII bytes — this correctly neutralizes ESC (`0x1b`) and prevents terminal manipulation, as documented in its own comment ("This prevents jobs from clearing the screen or rewriting logs using ANSI escape sequences"). [3](#0-2) 

- Posix branch: calls `EscapeForPosix`, which only escapes the shell metacharacters `` ` ``, `"`, `\`, `$` and a handful of shell-special characters for double-quoting purposes. It does **not** hex-escape or otherwise transform raw control bytes such as `0x1b` (ESC), `0x07` (BEL, used to terminate OSC sequences), or other C0 control codes — they pass straight through into the quoted output. [4](#0-3) 

Because `writeSectionStart` builds the emitted line as `ansiClear + w.escape(ansiBoldGreen + commandPrefix + command + ansiResetTrace)`, any raw ESC bytes embedded in the attacker-controlled `command` string are concatenated with the fixed ANSI constants and then passed unmodified through `EscapeForPosix`, ending up literally in the generated shell script's `printf` argument, which is echoed as-is into the job trace. [5](#0-4) 

The existing check that would normally stop this (control-byte neutralization) exists in `EscapeForAnsiC` but is simply not applied on the POSIX-escape code path, which is a genuine asymmetry/missing check rather than a defense-in-depth choice — the code comment for `EscapeForAnsiC` documents the security intent that is absent from `EscapeForPosix`.

### Impact Explanation
An attacker who authors a CI job (no special privileges needed) can, when the runner/shell is configured with POSIX escaping and trace sections enabled, inject raw CSI (`\x1b[2J`, `\x1b[0m`, etc.) or OSC (`\x1b]0;...\x07`) sequences into the command preview line of a `section_start:...` trace marker. Because terminal/log renderers interpret these bytes, this can be used to clear or rewrite parts of the visible job log, forge fake section boundaries, or otherwise visually hide/mask injected or malicious command content from a human reviewer inspecting the CI log in a terminal or ANSI-aware viewer — matching the described "malicious-log spoofing" impact.

### Likelihood Explanation
Preconditions are narrow but realistic and fully attacker-triggerable: (1) `trace_sections`/`FF_SCRIPT_SECTIONS=true`, (2) the shell/escaping mode resolves to POSIX (`posixMode=true`, e.g. `sh`-based shells), and (3) the job script step is multi-line (`isMultiline(command)` true) so `shouldUseTraceSection` selects the trace-section path. All of these are configuration/job-content choices under normal pipeline-author control; no admin action or external compromise is required. This makes it a reliably repeatable single-job PoC.

### Recommendation
Make `EscapeForPosix` (or a wrapper used specifically for the trace-section preview) hex-escape/strip C0 control bytes (`0x00-0x1F`, `0x7F`) the same way `EscapeForAnsiC` does, before embedding attacker-controlled command text next to the fixed ANSI constants in `writeSectionStart`/`writeSectionEnd`. Alternatively, always sanitize control bytes out of the command-preview string in `writeSectionStart` regardless of `posixMode`, since that string is only used for the printed preview, not as a functional shell argument.

### Proof of Concept

```go
func FuzzWriteSectionPosixEscaping(f *testing.F) {
    f.Add("echo hi\n\x1b[2Jecho done")
    f.Add("printf x\n\x1b]0;pwned\x07echo y")
    f.Fuzz(func(t *testing.T, cmd string) {
        if !isMultiline(cmd) {
            cmd += "\n" // force multiline to trigger trace-section path
        }
        w := NewTraceSectionWriter(true /*checkForErrors*/, true /*posixMode*/)
        var buf strings.Builder
        w.WriteSection(&buf, 0, cmd)
        out := buf.String()
        // Assert no raw ESC byte appears outside the fixed ansi constants.
        stripped := strings.ReplaceAll(out, ansiClear, "")
        stripped = strings.ReplaceAll(stripped, ansiBoldGreen, "")
        stripped = strings.ReplaceAll(stripped, ansiResetTrace, "")
        if strings.ContainsRune(stripped, 0x1b) {
            t.Fatalf("unescaped ESC byte leaked into trace output: %q", out)
        }
    })
}
```
Expected result with current code: the fuzz test fails when `posixMode=true` and the fuzzed command contains raw `0x1b`, because `EscapeForPosix` passes it through unescaped, while the same test passes when `posixMode=false` (`EscapeForAnsiC` path).

```go
// EscapeForAnsiC escapes a string for use in ANSI-C quoting ($'...').
// Control characters and non-ASCII bytes are hex-escaped to prevent terminal manipulation.
// This prevents jobs from clearing the screen or rewriting logs using ANSI escape sequences.
// Matches GitLab Runner's ShellEscape behavior.
func EscapeForAnsiC(s string) string {
	var buf strings.Builder

	for i := 0; i < len(s); i++ {
		c := s[i]
		switch c {
		case '\\':
			buf.WriteString("\\\\")
		case '\'':
			buf.WriteString("\\'")
		case '\n':
			buf.WriteString("\\n")
		case '\r':
			buf.WriteString("\\r")
		case '\t':
			buf.WriteString("\\t")
		case '\a':
			buf.WriteString("\\a")
		case '\b':
			buf.WriteString("\\b")
		case '\f':
			buf.WriteString("\\f")
		case '\v':
			buf.WriteString("\\v")
		default:
			// Hex-escape control characters (0x00-0x1F, 0x7F) and non-ASCII (>0x7F)
			// This prevents ANSI escape sequences (ESC = 0x1B) from manipulating terminal
			if c < 0x20 || c == 0x7F || c > 0x7F {
				fmt.Fprintf(&buf, "\\x%c%c", hextable[c>>4], hextable[c&0x0f])
			} else {
				buf.WriteByte(c)
			}
		}
	}

	return buf.String()
}
```

```go
// EscapeForPosix escapes a string for use in POSIX double-quoted strings.
// Matches GitLab Runner's PosixShellEscape behavior.
// Escapes: `, ", \, $
func EscapeForPosix(s string) string {
	if s == "" {
		return "''"
	}

	var buf strings.Builder
	needsQuoting := false

	for _, r := range s {
		switch r {
		case '`', '"', '\\', '$':
			buf.WriteRune('\\')
			buf.WriteRune(r)
			needsQuoting = true
		case ' ', '!', '#', '%', '&', '(', ')', '*', '<', '=', '>', '?', '[', '|':
			buf.WriteRune(r)
			needsQuoting = true
		default:
			buf.WriteRune(r)
		}
	}

	if needsQuoting {
		return `"` + buf.String() + `"`
	}

	return buf.String()
}
```
