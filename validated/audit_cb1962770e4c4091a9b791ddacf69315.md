## Analysis: Beneficiary bypass in `staking_contract.move` after `switch_operator`

Reducing the external TWAP report to its core invariant: **a value that should route through role-based indirection (beneficiary lookup) must remain correctly redirected even as the underlying role mapping (operator) changes.** In Uniswap's case the bug was a stale/shared config value; the Aptos analog is a stale distribution-pool entry that stops being correctly redirected to a beneficiary once the operator key it was recorded under is remapped.

### Root cause

`distribute_internal` decides whether to redirect a payout to a beneficiary by comparing the distribution-pool shareholder address to the **current function-call `operator` parameter**, not to the operator identity that originally earned the commission: [1](#0-0) 

Commission is recorded into the pool under the *operator's own address* as the shareholder key inside `request_commission_internal` → `add_distribution`: [2](#0-1) 

`switch_operator` flushes only the currently-inactive stake (via `distribute_internal`) and unlocks any not-yet-inactive commission (via `request_commission_internal`), both called with the *old* operator, then re-keys the entire `StakingContract` object — including its `distribution_pool`, which may still contain an unredeemed share for `old_operator` corresponding to commission that is `pending_inactive` (still in the lockup window) — under the *new* operator's address in the map: [3](#0-2) 

Once re-keyed, any later call to the permissionless `distribute` entry function passes the *new* operator as the `operator` parameter into `distribute_internal`: [4](#0-3) 

Inside the loop, the leftover shareholder is `old_operator`'s address, but the comparison `recipient == operator` compares it against `new_operator`, which is always false. The beneficiary substitution `recipient = beneficiary_for_operator(operator)` at line 897 is therefore never applied for that leftover share, and the funds are paid directly to `old_operator`'s address instead of `old_operator`'s configured beneficiary.

### Why this breaks the invariant

`set_beneficiary_for_operator`'s own doc-comment states the invariant this violates: "Any existing unpaid commission rewards will be paid to the new beneficiary": [5](#0-4) 

That guarantee only holds if the pending amount is fully flushed at switch time. But `switch_operator` only distributes stake that is **already inactive** at that moment; commission requested moments earlier that is still `pending_inactive` (within the active lockup cycle) is left as an unresolved share in the pool, keyed by the old operator's address, and permanently loses beneficiary routing once the map key changes to the new operator.

### Impact

This is a beneficiary payout corruption that credits the wrong account: an operator's already-configured beneficiary is entitled to unpaid commission per the module's own documented semantics, but a legitimate, permissionless sequence of `request_commission` → `switch_operator` (before lockup end) → `distribute` (called by anyone after lockup end) silently redirects that commission to the old operator's own address instead. No attacker privilege beyond normal staker/operator actions is required, and `distribute` is explicitly permissionless ("Allow anyone to distribute already unlocked funds").

### Recommendation

In `distribute_internal`, resolve the beneficiary for each `recipient` shareholder based on `recipient` itself rather than the function's `operator` parameter, e.g. compare `recipient` against `staking_contract`'s recorded original commission-earner or simply always call `beneficiary_for_operator(recipient)` when `recipient` is an address that has ever earned commission, instead of relying on equality with the current `operator` argument.

### Confidence / limitations

I traced this through the visible source of `staking_contract.move` and confirmed the exact comparison logic, the re-keying in `switch_operator`, and the beneficiary redirection contract stated in the doc-comments. I was not able to execute the Move test suite to empirically reproduce the exact state transition (e.g., confirm `pool_u64` share-pool mechanics don't coincidentally normalize this), so this should be validated with a concrete unit test (request commission with lockup not yet expired → switch_operator → advance time → distribute → assert old operator's beneficiary balance) before treating it as fully confirmed.
