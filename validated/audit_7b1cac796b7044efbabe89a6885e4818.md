### Title
External Initiator credentials bypass the "EIs not allowed" restriction in `PipelineRunsController.Create` and can trigger arbitrary job runs by integer ID - ([File: core/web/pipeline_runs_controller.go])

### Summary
`auth.AuthenticateExternalInitiator` forges a fake `clsessions.User{Role: UserRoleRun}` into `SessionUserKey` for every successfully authenticated External Initiator request. `PipelineRunsController.Create` uses `_, isUser := auth.GetAuthenticatedUser(c)` — which only checks whether `SessionUserKey` is set — as its gate for "only users are allowed to run jobs using int IDs; EIs not allowed." Because EI auth sets the same key, any EI credential holder satisfies `isUser` and can trigger `RunJobV2` on any job by integer ID, not just its own webhook-scoped job.

### Finding Description
The route `POST /v2/jobs/:ID/runs` is registered in the `userOrEI` group and accepts authentication via `auth.AuthenticateExternalInitiator`, `auth.AuthenticateByToken`, or `auth.AuthenticateBySession`, then wraps the handler in `auth.RequiresRunRole`: [1](#0-0) 

`AuthenticateExternalInitiator` authenticates the EI token, and then — in addition to setting `SessionExternalInitiatorKey` — also sets `SessionUserKey` to a synthetic `User{Role: UserRoleRun}` object so that `RequiresRunRole` will pass: [2](#0-1) 

Inside `PipelineRunsController.Create`, the code explicitly intends to forbid EIs from triggering runs via integer job IDs (comment: "only users are allowed to run jobs using int IDs - EIs not allowed"), but the check it uses is `auth.GetAuthenticatedUser(c)`, which merely checks presence of `SessionUserKey`: [3](#0-2) [4](#0-3) 

Since `AuthenticateExternalInitiator` also populates `SessionUserKey`, `isUser` evaluates to `true` for EI-authenticated requests exactly the same as for a real session/token user. The distinct `SessionExternalInitiatorKey`/`GetAuthenticatedExternalInitiator` accessor exists but is never consulted in `PipelineRunsController.Create` to exclude EI-originated requests — grep confirms `GetAuthenticatedExternalInitiator` is defined but not referenced from any controller. Consequently the intended restriction is dead code, and an EI credential can call `RunJobV2(ctx, jobID, nil)` for **any** integer job ID in the system, not merely the UUID-scoped webhook job the EI was originally created for (and webhook-by-UUID triggering has in fact been removed entirely, per the `job.ErrJobTypeRemoved` check just above).

Regarding the first half of the described chain (edit-role user creating an EI via `POST /v2/external_initiators`), this is **not** itself a bug: the route is intentionally gated with `auth.RequiresEditRole`, and `core/web/auth/auth_test.go`'s `routesRolesMap` explicitly encodes `{"POST", "/v2/external_initiators", false, false, true}` (edit-allowed, not view/edit-minimal), confirmed by `TestRBAC_Routemap_Edit` passing for this route: [5](#0-4) [6](#0-5) 
So edit-role EI creation is by design. The real, exploitable defect is the second step: the EI-forged `SessionUserKey` defeats the `isUser` bypass check in `PipelineRunsController.Create`, granting EI credentials unrestricted job-run-triggering power across all jobs addressable by integer ID.

### Impact Explanation
This is an authorization/logic bypass: a low-privilege credential (an External Initiator token, obtainable by any edit-role user, or otherwise leaked/compromised EI credentials) can trigger pipeline runs of **arbitrary** jobs by integer ID — a capability the code comment states should be reserved for real users only. This corresponds to Chainlink's "unauthorized job run" impact class, since EI credentials are meant to be scoped to triggering their own registered webhook/job, not ambient run-triggering power over the whole node's job set.

### Likelihood Explanation
Feasibility is high and requires only:
1. An edit-role session to create an EI (`POST /v2/external_initiators` — intended, minimal privilege), or possession of any existing EI's `AccessKey`/`Secret`.
2. Sending `POST /v2/jobs/<int-ID>/runs` with only the `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers (no session/API token) targeting any known integer job ID.

No race conditions, no admin/host access, and the flaw is deterministic and repeatable on every request.

### Recommendation
In `PipelineRunsController.Create`, distinguish real users from EI-authenticated requests explicitly, e.g., reject the request if `auth.GetAuthenticatedExternalInitiator(c)` returns a value, or introduce a dedicated context flag set only by `AuthenticateBySession`/`AuthenticateByToken` (not by `AuthenticateExternalInitiator`) instead of overloading `SessionUserKey` for role-satisfaction purposes across differing authentication origins.

### Proof of Concept
Handler-level integration test plan:
1. Start `cltest.NewApplicationWithConfig` with `ExternalInitiatorsEnabled = true` and create a real int-ID job via `AddJobV2` (e.g., an OCR/direct-request job that can be run via `RunJobV2`).
2. As an edit-role user, `POST /v2/external_initiators` with `{"name":"attacker-ei"}`, capture `AccessKey`/`Secret` from the `ExternalInitiatorAuthentication` response.
3. Build a raw HTTP request to `POST /v2/jobs/<jobID>/runs` (integer job ID) setting only `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers (no session cookie, no `X-API-KEY`).
4. Send via `router.ServeHTTP` / test server.
5. Assert expected-secure behavior: response should be `401 Unauthorized` or `422 Unprocessable Entity` ("bad job ID") since EIs should not run jobs by int ID.
6. Show actual current behavior: response is `200 OK` with a `pipelineRun` resource, proving `isUser` incorrectly evaluated to `true` for the EI-only request and `RunJobV2` executed for an arbitrary job ID.
