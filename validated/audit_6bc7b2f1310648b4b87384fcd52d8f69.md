### Title
Attacker-drained ERC4626 liquidity permanently/temporarily blocks `stopEpoch` via `StopEpochVaultLiquidityUnavailable`, freezing all tranche funds - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
The kona-node bug was a missing external resource (`get_block_by_hash` → `Ok(None)`) hitting an `unreachable!()` panic instead of a recoverable error. The analog in this codebase is `ProgrammableBorrower.onStopEpoch`: when the IdleCDO stop flow needs to recall liquidity, a *missing* withdrawable position in the external ERC4626 vault (`vault.withdraw` reverting even though the shares nominally cover the shortfall) is surfaced as a hard revert (`StopEpochVaultLiquidityUnavailable`) that aborts the entire `stopEpoch` transaction. An unprivileged actor who can drain the underlying market liquidity of the ERC4626 vault (e.g., borrow all available liquidity in the Morpho markets backing a MetaMorpho/Gauntlet vault — any user of the vault's markets can do this) can force every `stopEpoch` call to revert, freezing the epoch in the "running" state and locking all LP withdrawals and interest settlement for as long as the attacker keeps the market illiquid (open-term borrow until liquidation).

### Finding Description
In `contracts/strategies/idle/ProgrammableBorrower.sol`, `onStopEpoch` (lines 231-268) handles the liquidity recall:

```solidity
if (_amountRequired > onHand) {
  uint256 shortfall = _amountRequired - onHand;
  if (shortfall > _currentVaultAssets()) return true;      // true insolvency -> default path
  try vault.withdraw(shortfall, address(this), address(this)) returns (uint256 shares) {
    ...
  } catch {
    revert StopEpochVaultLiquidityUnavailable();            // covered-but-unwithdrawable -> hard revert
  }
}
```

The design distinguishes two "missing resource" cases: shares that don't cover the shortfall (graceful — return `true` and let the CDO's `transferFrom` fail into the default path) and shares that *do* cover but whose withdrawal fails (hard revert). The second branch assumes a reverting `withdraw` is purely transient and retryable.

An attacker breaks that assumption. MetaMorpho-style vaults (the deployment target; see `test/foundry/ProgrammableBorrowerCreditVault.t.sol` using `GAUNTLET_USDC_PRIME`) hold positions in underlying lending markets. `vault.withdraw` reverts whenever market liquidity is exhausted. Any unprivileged user can borrow the full available liquidity in the market the vault allocates to (or flash-borrow it each block while the epoch is overdue). Every subsequent `stopEpoch`/`stopEpochWithDuration` call then reverts inside `onStopEpoch`, the epoch stays `isEpochRunning`, `pendingWithdraws` stay unfunded, and no `claimWithdrawRequest`/`claimInstantWithdrawRequest` or new `startEpoch` can proceed. Because Morpho loans are open-term, the attacker can hold the borrowed liquidity (with collateral) for the entire loan duration — not just a block — making the freeze effectively as long as the attacker chooses, at the cost of interest on their borrow which is recouped from griefing a pool many times larger.

Note the other "missing valuation" case is already correctly hardened in the same file: `onDefault` (lines 289-300) deliberately avoids `convertToAssets` so a stressed vault can't block default handling — showing the codebase recognizes this bug class but left the `stopEpoch` liquidity-recall path as a panic-equivalent revert.

### Impact Explanation
Temporary-to-indefinite freezing of all pool funds with quantifiable scale: while `stopEpoch` cannot execute, every pending normal withdrawal (`requestWithdraw` receipts), all queued claims, and all tranche redemptions are blocked, and borrower interest continues accruing against LP principal. The frozen amount equals the full `getContractValue` of the CDO (e.g., the entire deployed USDC position parked in the vault plus borrower principal). The attacker is unprivileged — borrowing liquidity in a public Morpho market requires only collateral, and vault share holders / market users are explicitly in-scope attackers. Duration is bounded only by the attacker's willingness to carry the borrow, not by any protocol timeout.

### Likelihood Explanation
Medium. Requirements: the programmable-borrower variant is in use, `pendingWithdraws` (or interest recall) exceed the borrower's on-hand cash so the `withdraw` branch executes, and the vault's underlying markets have borrowable liquidity an attacker can corner. All three hold in the reference Gauntlet/MetaMorpho deployment. Cost is the collateral plus borrow interest for the freeze duration; there is no capital burn and the attack is repeatable each time liquidity returns. Mitigating factor: the revert is retryable, so a sufficiently incentivized keeper/operator can race liquidity replenishments, and a flash-loan drain only guarantees a single-block revert — a sustained freeze needs a real carried borrow.

### Recommendation
Treat the covered-but-unwithdrawable case like the uncovered case: instead of reverting, return `true` (or a distinct "liquidity deferred" signal) and let `IdleCDOEpochVariant` either (a) settle the epoch with what's on-hand and park the unrecalled shortfall as `epochPendingWithdraws`-backed vault shares claimable later, or (b) record the recall failure and allow a dedicated `claimVaultShares`/delayed-claim path so LPs are paid when liquidity returns rather than blocking the whole epoch state machine. At minimum, wrap the entire recall in a bounded retry with an escape hatch (e.g., manager-invokable `emergencyExitVault` already exists at lines 361-372 — wire it so a permanently illiquid vault degrades to default handling instead of an infinite revert loop).

### Proof of Concept
Conceptual Foundry fork PoC (mainnet, `GAUNTLET_USDC_PRIME` as in `test/foundry/ProgrammableBorrowerCreditVault.t.sol`):

```solidity
function testStopEpochFrozenByDrainedVaultLiquidity() external {
  _setUpProgrammableBorrowerCreditVault(GAUNTLET_FORK_BLOCK, GAUNTLET_USDC_PRIME);
  uint256 amount = 10_000 * oneScale;
  vm.prank(owner); cdoEpoch.setIsInterestMinted(true);
  idleCDO.depositAA(amount);
  cdoEpoch.requestWithdraw(aaTranche.balanceOf(address(this)) / 2, address(aaTranche));
  _startEpochAndCheckPrices(0);

  // Attacker: unprivileged EOA borrows all available liquidity from every
  // Morpho market GAUNTLET_USDC_PRIME allocates to (or flash-drains).
  _drainMorphoMarketLiquidity(GAUNTLET_USDC_PRIME);
  assertEq(IERC4626(GAUNTLET_USDC_PRIME).maxWithdraw(address(programmableBorrower)), 0);
  // Shares still cover the shortfall -> we land on the `catch` revert branch,
  // not the graceful `return true` insolvency branch.
  assertGt(IERC4626(GAUNTLET_USDC_PRIME).convertToAssets(
      IERC4626(GAUNTLET_USDC_PRIME).balanceOf(address(programmableBorrower))),
      strategy.pendingWithdraws());

  vm.warp(cdoEpoch.epochEndDate() + 1);
  vm.prank(manager);
  vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
  cdoEpoch.stopEpoch(0, 0);

  // Frozen: epoch still running, withdrawals unclaimable, attacker holds borrow open-term.
  assertTrue(cdoEpoch.isEpochRunning());
  assertFalse(cdoEpoch.defaulted());
  vm.expectRevert(); cdoEpoch.claimWithdrawRequest();
}
```

Caveat: I could not exhaustively verify whether a sustained liquidity drain on the specific production vault is economically feasible for arbitrary durations; the single-block flash-drain variant is trivially reproducible and suffices for repeated griefing while the epoch is overdue.
