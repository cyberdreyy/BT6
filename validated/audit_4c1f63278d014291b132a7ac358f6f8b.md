### Title
Legacy WebAPI capability handler forwards signed messages to all DON nodes without sender allowlist check - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`gateway.go`'s `ProcessRequest` routes a legacy message purely by `msg.Body.DonId` (`g.handlers[handlerKey]`) after only checking signature well-formedness via `msg.Validate()`, with no authorization tie between the extracted `Sender` and the target DON. `handler.HandleLegacyUserMessage` in `capabilities/handler.go` explicitly defers sender/subscriber authorization ("TODO: apply allowlist and rate-limiting here") and unconditionally forwards any validly-signed message to every member of the target DON via `don.SendToNode`.

### Finding Description
In `core/services/gateway/gateway.go:250-262`, when a legacy request (one with a non-empty `Body.DonId`) arrives, the gateway calls `msg.Validate()` [1](#0-0) , which only checks field lengths/format and that the message carries *a* valid ECDSA signature over its own body (via `ExtractSigner`), populating `Body.Sender` from whatever key signed it [2](#0-1) . It performs no check that `Sender` is authorized for the claimed `DonId`. The gateway then looks up `g.handlers[handlerKey]` keyed only by `DonId` and, if found, calls `h.HandleLegacyUserMessage(ctx, msg, callback)` [3](#0-2) .

Inside `capabilities/handler.go`, `HandleLegacyUserMessage` validates payload structure, timestamp freshness, and method name, but the authorization step is explicitly a stub: `// TODO: apply allowlist and rate-limiting here` [4](#0-3) . No check compares `msg.Body.Sender` against `h.donConfig`'s configured subscribers/allowlist. The message is then queued into `h.savedCallbacks` and forwarded to every DON member via `don.SendToNode` [5](#0-4) .

Regarding the DON-ID-enumeration half of the question: `g.handlers` map lookup returning `api.UnsupportedDONIdError` for an unknown key vs. other error codes for known-but-invalid messages does create a distinguishable oracle for testing whether a given `DonId` string exists [6](#0-5) . However, this alone is only an information-disclosure primitive (DON IDs are also generally non-secret/configured identifiers, not credentials), and by itself doesn't grant any privilege.

The actual exploitable issue is that possessing a valid signing key and knowing/guessing any DON ID lets *any* unprivileged sender have their request forwarded to that DON's nodes and compute resources are consumed processing it — since `HandleLegacyUserMessage` never verifies the sender is a subscriber/allowlisted for that DON before dispatching to `don.SendToNode`.

### Impact Explanation
Impact is unauthorized consumption of DON compute/network resources by an unsubscribed sender (resource abuse / quota bypass), matching Chainlink's "allowlist/quota bypass" bounty impact class. This does not directly yield fund movement, key disclosure, or node compromise; the message still needs a valid MessageId/timestamp/payload matching `webapicap.TriggerRequestPayload`, and every DON member independently receives the forwarded JSON-RPC request via `don.SendToNode`, so actual damage is bounded by whatever the DON nodes themselves do with an unauthorized trigger (e.g., invoking a workflow trigger not subscribed by that sender).

### Likelihood Explanation
Low-to-moderate. The attacker only needs network access to the gateway's HTTP endpoint and any valid ECDSA keypair to self-sign a message (no special credential required), and a target `DonId` (which is typically not a secret — it's a configuration identifier, and the differential error response at `gateway.go:257-261` further makes brute-forcing/confirming valid `DonId`s trivial). The gap is explicitly marked as a known-missing TODO in the code itself, indicating incomplete implementation rather than a defense that was bypassed.

### Recommendation
Implement the allowlist check at `HandleLegacyUserMessage` (or earlier, in `gateway.go` before dispatch) against `h.donConfig`'s configured node/workflow-owner subscriber set, rejecting any message whose `msg.Body.Sender` is not present in the DON's allowlist before it is queued into `savedCallbacks` or forwarded via `don.SendToNode`. Additionally, avoid leaking DON-ID validity via a distinct `UnsupportedDONIdError` versus other validation error codes, or rate-limit/uniformly delay error responses to reduce enumeration feasibility.

### Proof of Concept
Go handler-level integration test plan (in `core/services/gateway/handlers/capabilities/handler_test.go`):
1. Construct a `handler` via `NewHandler` with a `config.DONConfig` whose `Members` do not include an "allowlisted subscribers" concept currently — demonstrate absence of such a check.
2. Build an `api.Message` with `Body.Method = MethodWebAPITrigger`, a valid `TriggerRequestPayload` (fresh `Timestamp`), and `Body.DonId` set to the handler's configured DON ID; sign it with an arbitrary throwaway private key (`msg.Sign(randomKey)`) that is not part of any known/expected subscriber set.
3. Call `h.HandleLegacyUserMessage(ctx, msg, callback)` and assert:
   - Current (vulnerable) behavior: `err == nil`, `don.SendToNode` (mocked) is invoked for every DON member, and no `ErrorCode` such as `api.UnauthorizedError`/`api.Forbidden` is returned.
   - Desired (fixed) behavior: the callback receives an authorization-error response and `don.SendToNode` mock is never called.
4. Separately, add a `gateway_test.go` case sending two `ProcessRequest` calls — one with a valid `DonId` and malformed body, one with an invalid `DonId` — and assert the HTTP status/error codes differ (`api.UnsupportedDONIdError` vs `api.UserMessageParseError`), documenting the enumeration oracle at `gateway.go:257-261`.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
