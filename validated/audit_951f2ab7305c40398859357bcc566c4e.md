### Title
Multisig `DeleteMember` fails to purge stale confirmations, allowing a request to execute below the live-member threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::confirm()` counts entries in the `confirmations: LookupMap<RequestId, HashSet<String>>` set against `self.num_confirmations` without checking that the confirming identities are still current members. `delete_member()` only purges requests that were *added* by the removed member; it never scans other pending requests to strip that member's prior confirmations from their `confirmations` sets. As a result, a confirmation recorded by a member who is later removed remains valid and countable toward the threshold on any request they confirmed before removal.

### Finding Description
In `multisig2/src/lib.rs`, `confirm()` increments/measures the size of the request's confirmation `HashSet<String>` and, once `confirmations.len() + 1 >= self.num_confirmations`, executes the request: [1](#0-0) 

`delete_member()` removes the member from `self.members` and deletes only the *requests* that member originally *added* (`r.member == member`), together with those requests' confirmation sets and `num_requests_pk` entry: [2](#0-1) 

It does not iterate over `self.requests` to find and strip this member's identity string out of `confirmations` sets belonging to requests *added by other members* that this member had already confirmed. `current_member()` is only used to authorize the *caller* of `confirm`/`add_request`, and is never re-checked against historical entries already stored in a request's confirmation `HashSet`: [3](#0-2) [4](#0-3) 

Binding broken: `confirmations counted == live members who approved`. Concretely:
- Before: member set `{A,B,C,D}`, `num_confirmations = 3`. Member B confirms request X (added by C). `confirmations(X) = {B}`.
- Attacker action: a `DeleteMember{B}` request executes, removing B from `self.members`. `delete_member` only cleans up requests where `r.member == B` (i.e., requests B personally added), not request X (added by C), so `confirmations(X)` still contains B.
- After: live members `{A,C,D}` (3, matching threshold), but B — no longer a member — still counts toward X's threshold. If A then confirms X, `confirmations.len()+1 == 2` while only 2 *live* members (A and the historical B) have ever actually approved X as members — B's approval was given while a member but is stale/unrevoked, and worse, if a compromised removed member's approval is combined with only 1 further live confirmation, X executes with only 1 genuinely current member's consent below the intended `num_confirmations` bar for currently-trusted members.

The multisig v1 contract (`multisig/src/lib.rs`) has the analogous gap: `DeleteKey` in `execute_request` only removes requests keyed by `signer_pk == pk` and clears those specific confirmation sets, never scanning other requests' `confirmations` map for the deleted key's entries: [5](#0-4) 

### Impact Explanation
This breaks the "a multisig request executed below threshold" custody binding explicitly called out as Critical impact. A removed/compromised member's stale approval on an already-pending, not-yet-executed request continues to count toward `num_confirmations` indefinitely (no expiry check on confirmations, only on request add/delete cooldown), letting the multisig authorize `Transfer`, `FunctionCall`, `AddKey`/`AddMember`, or `DeployContract` actions with fewer genuinely current approvals than the configured threshold requires.

### Likelihood Explanation
Exploitability requires no attacker code execution — it is a straightforward sequencing issue: (1) a member is compromised or intentionally removed after having confirmed a pending request, (2) `DeleteMember`/`DeleteKey` executes without the removed member's other confirmations being purged, (3) remaining confirmations from current members complete the count. Any organization that rotates or removes a multisig member while requests are in-flight (a routine operational event, not an attack requiring privileged access beyond normal multisig operation) can trigger this.

### Recommendation
On `DeleteMember`/`DeleteKey`, iterate `self.requests`/`self.confirmations` (or maintain a reverse index from member → confirmed request ids) and remove the deleted member's entry from every pending request's confirmation set, not just requests they personally added. Alternatively, validate at `confirm()`-execution time that every entry in the confirmation `HashSet` still corresponds to a current member of `self.members` before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `{A, B, C, D}`, `num_confirmations = 3`.
2. `C` calls `add_request_and_confirm(request_X = Transfer{...})` → `confirmations(X) = {C}`.
3. `B` calls `confirm(X)` → `confirmations(X) = {C, B}` (2 of 3).
4. Members execute a separate request `DeleteMember{B}` (reaching 3-of-4 threshold as normal), removing `B` from `self.members`; `delete_member` does not touch `confirmations(X)` since `X` was added by `C`, not `B` — see `multisig2/src/lib.rs:356-379`.
5. `A` calls `confirm(X)` → `confirmations.len() (2) + 1 >= 3` → request executes, using the stale approval from removed member `B` as one of the three required confirmations, even though only `{C, A}` (2 live members) plus a non-member (`B`) ever confirmed it.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
