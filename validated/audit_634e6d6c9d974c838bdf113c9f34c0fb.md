### Title
Stale confirmations from removed keys let requests execute below the effective quorum - (File: multisig/src/lib.rs)

### Summary
The multisig contract's `DeleteKey` action only clears requests *created by* the removed public key; it does not scan and strip that key's confirmations from *other* pending requests. Combined with `confirm()`'s naive count check, a request can reach the required `num_confirmations` even though one of the counted confirmations came from a key that has since been removed from the account.

### Finding Description
`MultiSigContract::confirm` (multisig/src/lib.rs:246-266) tracks confirmations per `request_id` as a `HashSet<PublicKey>` and executes the request once `confirmations.len() + 1 >= self.num_confirmations`. There is no re-check at execution time that every public key present in that set is still a valid access key/member of the account.

When a `DeleteKey` request executes (multisig/src/lib.rs:198-216), the cleanup logic:
1. Finds requests where `r.signer_pk == pk` (i.e., requests the removed key *itself* created) and deletes those requests and their confirmation sets.
2. Removes the `num_requests_pk` counter entry for that key.
3. Issues the `delete_key` promise.

It never iterates `self.confirmations` to remove the deleted key's vote from requests *created by other keys*. So if key `C` confirmed request `R1` (created by key `A`) before `C` was removed, `R1.confirmations` still contains `C` after the `DeleteKey{C}` action executes. If afterward any other still-valid key confirms `R1`, the count check passes using `C`'s stale vote, even though `C` is no longer an authorized signer on the account — effectively executing the request with one fewer live signature than `num_confirmations` requires.

### Impact Explanation
This is a Critical-class issue per the multisig binding "confirmations counted versus live members": a multisig request can be executed below the intended threshold of live, currently-authorized keys. In a K-of-N scheme, removing a compromised or departing key is supposed to invalidate that key's influence going forward; instead its prior confirmations on other in-flight requests remain valid indefinitely, letting the account be drained/upgraded/have keys added with effectively K-1 live approvals.

### Likelihood Explanation
This requires no signature forgery or privileged access beyond being (or having been) a legitimate multisig key holder — a normal operational sequence (a key confirms a pending request, then is later removed via `DeleteKey` for routine rotation or because it was compromised) triggers the bug automatically. No malicious intent by the remaining signers is required for the vulnerability to matter; it specifically defeats their intent when they remove a key expecting its authority to be revoked.

### Recommendation
When executing `DeleteKey`, iterate all pending `self.confirmations` entries and remove the deleted public key from every confirmation set (not just requests it authored), or alternatively re-validate at `confirm()`/execution time that every key in a request's confirmation set is still present among current keys (e.g., cross-check against `num_requests_pk` or an explicit live-keys set) before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy multisig with `num_confirmations = 3` and keys `A, B, C, D, E`.
2. Key `A` calls `add_request` to create `R1` (e.g., `Transfer`).
3. Key `B` calls `confirm(R1)` → confirmations = `{B}` (1/3).
4. Key `C` calls `confirm(R1)` → confirmations = `{B, C}` (2/3, not yet executed).
5. Separately, keys detect `C` is compromised; a `DeleteKey{C}` request is created and confirmed by 3 keys and executes — `C` is removed as an access key, but `R1.confirmations` still contains `C` because `R1.signer_pk == A`, not `C` (multisig/src/lib.rs:198-216 only cleans requests authored by `C`).
6. Key `D` (any remaining valid key) calls `confirm(R1)` → `confirmations.len() + 1 == 3 >= num_confirmations`, so `R1` executes using `{B, C, D}` even though `C` no longer holds a valid key on the account — the transfer executes with only 2 genuinely live signers' worth of current authority plus one stale/revoked vote.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
