### Title
Unguarded `initializeConfig` Allows Any Caller to Inject a Malicious `BridgeConfig` into `BridgeCommittee` — (`bridge/evm/contracts/BridgeCommittee.sol`)

---

### Summary

`BridgeCommittee.initializeConfig` is a public, permissionless function whose only re-initialization guard checks whether the *state variable* `config` is already non-zero. It never checks whether the *input parameter* `_config` is non-zero. This is the exact same root cause as the reported `AccountantDelegate` bug: a guard that tests existing state instead of validating the incoming parameter. The result is two exploitable paths: (1) any caller can front-run the legitimate deployer and permanently install a malicious `BridgeConfig`; (2) calling with `address(0)` leaves the guard permanently bypassable, allowing a second call with any address.

---

### Finding Description

`BridgeCommittee.initializeConfig` is declared `external` with no access-control modifier:

```solidity
// bridge/evm/contracts/BridgeCommittee.sol  lines 63-66
function initializeConfig(address _config) external {
    require(address(config) == address(0), "BridgeCommittee: Config already initialized");
    config = IBridgeConfig(_config);
}
``` [1](#0-0) 

The guard `address(config) == address(0)` is satisfied whenever the state variable has not yet been set to a real address. It says nothing about whether `_config` itself is non-zero. Two consequences follow:

**Path A – zero-address bypass (exact analog to the report):**
1. Attacker calls `initializeConfig(address(0))`.
2. Guard passes: `config` is still `address(0)`.
3. `config` is written as `IBridgeConfig(address(0))` — no change.
4. Guard still passes on the next call.
5. Attacker (or anyone) calls `initializeConfig(malicious_contract)` and wins.

**Path B – front-run (no access control at all):**
1. Deployer broadcasts `initializeConfig(real_config)`.
2. Attacker sees it in the mempool and front-runs with `initializeConfig(attacker_config)`.
3. Attacker's transaction lands first; guard passes; `config` is set to the attacker's contract.
4. Deployer's transaction reverts with "Config already initialized".

The `config` state variable is the sole source of truth for token addresses, chain IDs, and token support flags used by every bridge operation. It is exposed through the `IBridgeCommittee.config()` interface:

```solidity
// bridge/evm/contracts/interfaces/IBridgeCommittee.sol  line 21
function config() external view returns (IBridgeConfig);
``` [2](#0-1) 

`SuiBridge` calls `committee.config()` in every token transfer and deposit path:

```solidity
// bridge/evm/contracts/SuiBridge.sol  line 67
IBridgeConfig config = committee.config();
``` [3](#0-2) 

`MessageVerifier` calls `committee.config().chainID()` inside the `verifyMessageAndSignatures` modifier that gates every governance action:

```solidity
// bridge/evm/contracts/utils/MessageVerifier.sol  lines 46-47
require(
    message.chainID == committee.config().chainID(), "MessageVerifier: Invalid chain ID"
);
``` [4](#0-3) 

---

### Impact Explanation

A malicious `BridgeConfig` can return arbitrary values for every config query:

| Query | Consequence |
|---|---|
| `tokenAddressOf(id)` returns attacker-controlled ERC-20 | `_transferTokensFromVault` sends real vault funds to a fake token contract; `bridgeERC20` pulls user tokens into the wrong vault |
| `chainID()` returns a spoofed value | `verifyMessageAndSignatures` chain-ID check is bypassed for all governance messages |
| `isTokenSupported(id)` returns `true` for any id | Unsupported tokens accepted for bridging |
| `isChainSupported(id)` returns `false` | All bridge deposits and withdrawals blocked (permanent fund lock) |

The most severe outcome is direct fund theft: `_transferTokensFromVault` transfers ERC-20 tokens and ETH from `BridgeVault` to a `recipientAddress` derived from the message payload, using `tokenAddressOf` from the attacker-controlled config. A malicious config can redirect those transfers to any address.

This matches the HackenProof Critical impact class: *bridge message forgery or bridge governance bypass that enables illegitimate mint or unlock*.

---

### Likelihood Explanation

The function is `external` with no `onlyOwner`, `onlyCommittee`, or `initializer` modifier. Any Ethereum address can call it at any time before the legitimate `initializeConfig` call lands. The deployment window (time between proxy deployment and config initialization) is a well-known front-running target. Path A (zero-address call) additionally creates a permanent re-initialization window that survives indefinitely if the deployer ever calls with `address(0)` by mistake.

---

### Recommendation

Add two fixes:

1. **Validate the input parameter** — reject `address(0)`:
```solidity
function initializeConfig(address _config) external {
    require(_config != address(0), "BridgeCommittee: Invalid config address");
    require(address(config) == address(0), "BridgeCommittee: Config already initialized");
    config = IBridgeConfig(_config);
}
```

2. **Add access control** — restrict to the committee itself or use OpenZeppelin's `initializer` modifier so only the proxy admin can call it during the initialization phase:
```solidity
function initializeConfig(address _config) external onlyCommitteeOrAdmin {
    ...
}
```

Alternatively, fold `_config` into the main `initialize` function (which already carries the `initializer` modifier) so it is set atomically and cannot be called separately.

### Proof of Concept

```solidity
// Attacker contract / script
contract Exploit {
    BridgeCommittee committee; // deployed proxy

    function attack(address maliciousConfig) external {
        // Step 1 (optional): lock out the deployer by calling with address(0)
        //   committee.initializeConfig(address(0));
        //   → guard passes, config stays address(0), can be called again

        // Step 2: set attacker-controlled config
        committee.initializeConfig(maliciousConfig);
        // → guard passes (config == address(0)), config is now maliciousConfig

        // Step 3: verify
        assert(address(committee.config()) == maliciousConfig);
        // All subsequent SuiBridge calls now use maliciousConfig for
        // tokenAddressOf(), chainID(), isTokenSupported(), etc.
    }
}
```
