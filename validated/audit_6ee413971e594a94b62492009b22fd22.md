### Title
Unbounded allocation via attacker-controlled `Vec` length prefix in `parse_vote` bincode deserialization - ([File: transaction-status/src/parse_vote.rs])

### Summary
`parse_vote` deserializes raw Vote-program instruction bytes using the plain `bincode::deserialize` call rather than the size-limited `solana_bincode::limited_deserialize` helper used everywhere else in the codebase for `VoteInstruction`. Because bincode/serde's `Vec<T>` deserialization pre-allocates capacity from the attacker-supplied length prefix (`Vec::with_capacity(size_hint)`) before validating that enough bytes remain to fill it, a crafted `VoteStateUpdate`/`TowerSync` instruction with a huge claimed `lockouts`/`slots` length can trigger a massive allocation attempt independent of the actual instruction payload size.

### Finding Description
`parse_vote` deserializes the raw compiled-instruction bytes directly: [1](#0-0) 

This differs from every other Vote-instruction decode site in the repo, all of which use `solana_bincode::limited_deserialize(data, PACKET_DATA_SIZE)`: [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) 

`limited_deserialize` uses bincode's `with_limit` option, which bounds/rejects a claimed sequence length against the byte-size limit *before* allocating. Plain `bincode::deserialize()` (used only in `parse_vote`) has no such limit: serde's generic `Vec<T>` deserialization calls `Vec::with_capacity(seq.size_hint().unwrap_or(0))`, and bincode's `SeqAccess::size_hint()` returns the raw attacker-controlled `u64` length prefix directly, with no check against the number of bytes actually remaining in the buffer. This means for enum variants carrying `Vec<Lockout>`/`Vec<Slot>` (`VoteInstruction::UpdateVoteState`, `CompactUpdateVoteState`, `TowerSync`, and their `*Switch` variants — all reachable in `parse_vote.rs`), an attacker can encode a small instruction payload (well within `PACKET_DATA_SIZE`/transaction size limits) whose length prefix claims an enormous element count while providing few actual trailing bytes.

Attack flow:
1. Attacker submits a transaction whose single Vote-program instruction contains bincode bytes for e.g. `TowerSync` with the `lockouts` length prefix set to a huge value (e.g. `u64::MAX` or a large multiple), followed by insufficient trailing bytes.
2. On-chain, `vote_processor`'s `limited_deserialize` correctly rejects this cheaply (size-limit check fails before allocation), so the instruction execution fails with an error — but the transaction, having passed transaction-level and signature checks, is still included in a block as a failed transaction (fee-charged).
3. A client calls `getBlock`/`getTransaction` with `encoding: jsonParsed` on that block/transaction. Transaction-status parsing invokes `parse_vote` on the stored raw instruction bytes, which calls unlimited `bincode::deserialize`, triggering the `Vec::with_capacity(attacker_length)` allocation attempt with no relationship to the actual (small) instruction byte count.
4. Depending on the claimed length, this either aborts the process via Rust's `handle_alloc_error` (huge allocation request fails) or consumes gigabytes of memory, causing OOM/DoS on the RPC node — from a single low-rate RPC call reading previously-stored data.

### Impact Explanation
This is an unbounded-cost/DoS from a single `getBlock`/`getTransaction(jsonParsed)` call processing one attacker-crafted (already-included) Vote instruction, matching the "unbounded cost for a single low-rate call" and RPC decoder-panic/crash bounty categories. It can crash or memory-exhaust the RPC-serving process without requiring privileged access, multiple calls, or unfiltered `getProgramAccounts`.

### Likelihood Explanation
Preconditions are minimal and attacker-controlled: craft one transaction with a malformed Vote instruction (fails on-chain execution but is still recorded), then issue a single `jsonParsed` `getBlock`/`getTransaction` RPC call referencing that block/signature. No special privileges, staking, or leader control needed — fully reproducible with a unit test constructing the byte pattern directly.

### Recommendation
Change `parse_vote.rs` to use `solana_bincode::limited_deserialize::<VoteInstruction>(&instruction.data, solana_packet::PACKET_DATA_SIZE as u64)` instead of raw `bincode::deserialize`, matching all other Vote-instruction decode sites, so oversized/inconsistent length prefixes are rejected before any large allocation is attempted.

### Proof of Concept
```rust
// transaction-status/src/parse_vote.rs (new test)
#[test]
fn test_parse_vote_huge_lockouts_length_prefix_does_not_oom() {
    use std::io::Write;

    // Build raw bytes: 4-byte enum discriminant for TowerSync variant,
    // followed by an 8-byte little-endian length prefix claiming an
    // enormous number of `Lockout` elements, followed by only a few
    // truncated bytes (not enough to actually deserialize that many).
    let variant_index: u32 = /* index of VoteInstruction::TowerSync */ 14; // adjust to actual discriminant
    let huge_len: u64 = u64::MAX / 2; // attacker-claimed length, unrelated to actual bytes present

    let mut data = Vec::new();
    data.write_all(&variant_index.to_le_bytes()).unwrap();
    data.write_all(&huge_len.to_le_bytes()).unwrap();
    data.extend_from_slice(&[0u8; 4]); // truncated payload, far too short for `huge_len` elements

    let instruction = CompiledInstruction {
        program_id_index: 0,
        accounts: vec![0, 1],
        data,
    };
    let account_keys = AccountKeys::new(&[Pubkey::new_unique(), Pubkey::new_unique()], None);

    // Expected (after fix): parse_vote should return
    // Err(ParseInstructionError::InstructionNotParsable(..)) quickly,
    // with no attempt to allocate memory proportional to `huge_len`.
    //
    // Current behavior (bug): `bincode::deserialize` inside parse_vote
    // attempts `Vec::with_capacity(huge_len)` for the `lockouts` field,
    // which aborts the process or allocates unbounded memory.
    let result = parse_vote(&instruction, &account_keys);
    assert!(result.is_err(), "malformed vote instruction with huge claimed vector length must fail fast without large allocation");
}
```
Run under a bounded-memory harness (e.g., `cgroup`-limited or an allocator that panics instead of aborting on failed allocation) to assert the process does not attempt to allocate proportional to `huge_len`. After applying the recommended fix (switching to `limited_deserialize`), the call fails immediately with no large allocation, since `with_limit` rejects the claimed sequence length against the transaction-size bound before calling `Vec::with_capacity`.
