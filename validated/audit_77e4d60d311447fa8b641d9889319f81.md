### Title
Stale confirmations from removed multisig members are still counted toward `num_confirmations`, allowing a request to execute without current-member approval - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::confirm` authorizes execution of a request purely by counting entries in the `confirmations` `HashSet` against `num_confirmations`. When a member is removed via `delete_member`, only requests **added** by that member are purged; confirmations that member previously cast on **other** requests remain in those requests' `confirmations` set and continue to count toward the threshold, even though that member is no longer part of the multisig. This breaks the intended invariant that execution requires `num_confirmations` approvals from *currently live* members.

### Finding Description
`confirm()` checks only the size of the stored confirmation set against the threshold: [1](#0-0) 

When a member is deleted, `delete_member` cleans up requests *originated* by that member, and removes that member's `num_requests_pk` entry, but it never scans other requests' `confirmations` sets to strip that member's prior confirmations: [2](#0-1) 

Because of this, a confirmation recorded while a signer was a valid member is never invalidated after that signer is removed. The equality that should hold is:

`|{confirmations from currently-live members}| >= num_confirmations`

but the code actually enforces:

`|{all recorded confirmations, live or removed}| >= num_confirmations`

This is directly analogous to the reported bug class: a recorded count (`_computeFeePerClaim`'s claim count in the Sherlock report) diverges from the true, currently-valid state (claims that actually succeeded), and that stale count is used to authorize a value-affecting action (`_vault.claimPrize`). Here the recorded confirmation count diverges from the currently-valid member set and is used to authorize `execute_request`, which can transfer NEAR or grant keys.

The same pattern exists in the legacy `multisig` contract, where `DeleteKey` only purges requests signed by the deleted key, not that key's confirmations on other requests: [3](#0-2) [4](#0-3) 

### Impact Explanation
This is a Critical-class impact per the custody binding: "a multisig request executed below threshold." A request (e.g. a `Transfer` of NEAR, an `AddKey`/`AddMember` granting new control, or a `FunctionCall`) can be executed with fewer *live, currently-trusted* confirmations than `num_confirmations` mandates, because a stale confirmation from a member who has since been revoked still counts. This directly undermines the K-of-N security guarantee the contract is meant to provide, and the recovered/removed member's earlier confirmation effectively becomes a permanent, unrevocable vote on any request it was cast on.

### Likelihood Explanation
Exploitability requires: (1) a member confirms a request that isn't yet at threshold, (2) that member is later removed from the multisig (a normal governance action, e.g. due to key compromise, offboarding, or rotation), and (3) the original request is left pending and later gets its remaining confirmation(s) from current members. This is a plausible sequence in any multisig with request cooldowns/pending requests and periodic membership rotation — it does not require any privileged/attacker-only capability beyond being (or having been) a legitimate member, and no additional trust boundary is crossed beyond normal request/confirm/delete-member flows already exposed by the contract.

### Recommendation
When removing a member (`delete_member` / `DeleteKey`), iterate over all pending requests' `confirmations` sets and strip the removed member's confirmation entry (not just requests originated by that member). Alternatively, validate at `confirm()`-time / execution-time that every entry in the `confirmations` set still corresponds to a `self.members`-contained (or still-valid key) member before counting it toward `num_confirmations`.

### Proof of Concept
1. Initialize `MultiSigContract::new(members = [A, B, C], num_confirmations = 2)`.
2. `A` calls `add_request(R)` (a `Transfer` to an attacker-controlled or third-party account) — no confirmation yet.
3. `B` calls `confirm(R)` → `confirmations[R] = {B}` (1/2, not yet executed). [5](#0-4) 
4. Separately, `A` and `C` submit and confirm a `DeleteMember{member: B}` request (2/2 confirmations, meets threshold, executes) — `B` is removed from `self.members`; `delete_member` only purges requests where `r.member == B` (requests originated by `B`), so `R` (originated by `A`) and its `confirmations[R] = {B}` are untouched. [6](#0-5) 
5. `C` calls `confirm(R)` → `confirmations[R] = {B, C}`, `len() == 2 >= num_confirmations(2)` → `execute_request(R)` fires the `Transfer`. [7](#0-6) 

The transfer executes with only one currently-live member (`C`) plus one removed member's (`B`'s) stale confirmation, never receiving `num_confirmations` worth of approval from members that were live/trusted at execution time.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
