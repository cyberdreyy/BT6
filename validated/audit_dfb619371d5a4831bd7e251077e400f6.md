### Title
EI credential holder bypasses "no EI int-ID runs" restriction via synthetic SessionUserKey user - ([File: core/web/pipeline_runs_controller.go])

### Summary
`AuthenticateExternalInitiator` sets `SessionUserKey` to a synthetic `&clsessions.User{Role: clsessions.UserRoleRun}` in the gin context in addition to `SessionExternalInitiatorKey`. `PipelineRunsController.Create` uses `auth.GetAuthenticatedUser(c)`'s boolean return (`isUser`) to gate the "run job by integer ID" branch, intending that only real logged-in users (session/API token) can take this path — but the check cannot distinguish the synthetic EI-derived user from a genuine user, so an EI credential holder also satisfies `isUser`.

### Finding Description
`AuthenticateExternalInitiator` (`core/web/auth/auth.go`, lines 119-151) authenticates via `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers, and on success stores both the external initiator object under `SessionExternalInitiatorKey` and a synthetic user under `SessionUserKey`: [1](#0-0) 

`GetAuthenticatedUser` (lines 177-187) simply reads `SessionUserKey` from context and returns `(user, true)` whenever that key is set, with no way to tell whether the value originated from a real session/token auth or from the EI synthetic assignment: [2](#0-1) 

`PipelineRunsController.Create` (`core/web/pipeline_runs_controller.go`, lines 109-125) explicitly documents the intended invariant ("only users are allowed to run jobs using int IDs - EIs not allowed") and gates the integer-job-ID `RunJobV2` call on `isUser`: [3](#0-2) 

Because `isUser` is true whenever `SessionUserKey` exists in context — regardless of whether it was populated by `AuthenticateBySession`, `AuthenticateByToken`, or `AuthenticateExternalInitiator` — an EI-authenticated request also takes the `isUser` branch. The synthetic user has an empty `Email` and `Role: UserRoleRun`, which passes the intended "user" check, defeating the code's own stated restriction that EIs should not be allowed to run jobs by integer ID.

The route this controller serves is mounted with combined authenticator middleware supporting session, token, and external-initiator authentication methods (confirmed via `core/web/router.go` references to `AuthenticateExternalInitiator`, `AuthenticateByToken`, `AuthenticateBySession` alongside the pipeline-run routes), so a request authenticated purely via EI headers reaches `Create` with `SessionUserKey` set.

### Impact Explanation
An external-initiator credential — intended only to trigger the single webhook job it is bound to — can invoke `prc.App.RunJobV2(ctx, jobID, nil)` for **any** integer job ID in the node, not just its own bound job. This breaks the "requests are bound to the correct principal" invariant and matches the Chainlink bounty impact class of unauthorized job run / authorization bypass: an attacker with only a low-privilege EI credential can trigger execution of arbitrary jobs (including ones with side effects such as on-chain transactions), which is a scoped but real cross-principal authorization bypass.

### Likelihood Explanation
Precondition is only a valid EI AccessKey/Secret pair (no user session, no API token, no admin/operator access) — this is the exact "unprivileged EI credential holder" threat model. The exploit requires nothing more than sending a normal `POST /v2/jobs/:ID/runs` request with EI headers and a non-UUID (integer) job ID, which is fully attacker-controlled and repeatable at will.

### Recommendation
Distinguish EI-derived synthetic users from real authenticated users. Options:
1. Do not set `SessionUserKey` in `AuthenticateExternalInitiator`; instead have `RequiresRunRole`/handlers consult `SessionExternalInitiatorKey` explicitly where EI-triggered runs are intended.
2. In `PipelineRunsController.Create`, additionally check `auth.GetAuthenticatedExternalInitiator(c)` and reject (or handle separately) if an EI is present, so the `isUser` branch is only reachable for genuine session/token-authenticated users with a non-empty `Email`/real DB identity.
3. Add a distinguishing marker (e.g., a `IsSynthetic`/`Source` field on the context value or a separate context key) so downstream code can reliably differentiate real users from EI-role placeholders.

### Proof of Concept
Go handler-level integration test plan (extends existing `core/web/pipeline_runs_controller_test.go` patterns):
1. Build a test app (`cltest.NewApplicationWithConfig`/httptest server) in non-prod mode with an `ExternalInitiator` registered and bound to job A, and a separate job B (different integer ID) with no relation to that initiator.
2. Authenticate the HTTP client using only EI headers (`X-Chainlink-EA-AccessKey`, `X-Chainlink-EA-Secret`) — no session cookie, no API token.
3. POST to `/v2/jobs/<jobB.ID>/runs` (integer ID of job B, unrelated to the EI).
4. Assert response is `200 OK` with a created pipeline run resource for job B (demonstrating `isUser` branch executed and `RunJobV2` was invoked), rather than the expected `401/422` rejection.
5. Add a unit test on `auth.GetAuthenticatedUser` directly following `AuthenticateExternalInitiator` in a `gin.Context`, asserting it returns `(user, true)` with `user.Role == clsessions.UserRoleRun` and `user.Email == ""`, proving indistinguishability from a real user object.
