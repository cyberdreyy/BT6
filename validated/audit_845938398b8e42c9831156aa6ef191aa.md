### Title
Node-side signer-weight tally double-counts a signer that first Rejects then later Accepts the same block, corrupting `total_weight_approved`/`total_weight_rejected` — (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener` accumulates `total_weight_approved` and `total_weight_rejected` for a proposed block from `BlockResponse` messages, gated by two *separate* de-duplication sets: `gathered_signatures` (a map keyed by `slot_id`) for acceptances, and `responded_signers` (a `HashSet<slot_id>`) for rejections. Because a signer is allowed by design to reject a proposal and later reconsider and sign the *same* `signer_signature_hash` once the rejection reason becomes stale, the ordering Reject → Accept lets that signer's weight be added to `total_weight_rejected` first and then, independently, to `total_weight_approved` later — the same signer's weight ends up counted in both tallies at once.

### Finding Description
The Accepted branch only guards against double counting via `gathered_signatures.contains_key(&slot_id)`; it does not check `responded_signers` before adding weight: [3](#0-2) 

The Rejected branch guards via `responded_signers.insert(slot_id)`, which returns `false` (skips) only if the slot has *already* responded — including via a prior Accepted message: [4](#0-3) 

Both branches unconditionally insert into `responded_signers` at the end, so the sets are populated identically regardless of vote kind, but only the Rejected branch actually *checks* that shared set before adding weight; the Accepted branch checks a different, vote-kind-specific set (`gathered_signatures`).

Consequently:
- Accept → Reject (same signer, same block): Accept adds to `total_weight_approved` and inserts into `responded_signers`. The later Reject's `responded_signers.insert` returns `false`, so no reject weight is added — correctly no double count.
- Reject → Accept (same signer, same block): Reject adds to `total_weight_rejected` and inserts into `responded_signers`. The later Accept checks `gathered_signatures.contains_key(&slot_id)`, which is still `false` (the signer never actually signed before), so the Accept branch adds the *same signer's weight* to `total_weight_approved` too. The signer's weight is now present in both `total_weight_rejected` and `total_weight_approved` simultaneously, and nothing ever removes it from `total_weight_rejected`.

This Reject → Accept path is not hypothetical: `should_reevaluate_reject_reason` in `stacks-signer/src/v0/signer.rs` allows a signer to reconsider and sign a block it previously rejected for causes such as `ValidationFailed(UnknownParent)`, `ValidationFailed(NotFoundError)`, `NoSortitionView`, or `ConnectivityIssues` once a re-proposal arrives, and this is exercised by the test `signer_can_accept_rejected_block` in `stacks-node/src/tests/signer/v0/mod.rs` and `signers_reprocess_bitcoin_block_not_found_proposals`.

### Impact Explanation
`total_weight_rejected` and `total_weight_approved` are the two quantities the miner-side `SignCoordinator` uses to decide the fate of a block: [5](#0-4) 

Once a signer's weight is double-counted, `total_weight_rejected` retains stale weight from a vote the signer itself has since retracted by signing. This breaks the intended equality between "weight that currently stands behind rejection" and the value used for the `>30%`-blocks-70% rejection decision: the coordinator can compute `total_weight_rejected.saturating_add(weight_threshold) > total_weight` as true (declaring the block dead, bumping `bump_naka_rejected_blocks`, and permanently/temporarily excluding transactions) using weight that has, in fact, moved over to acceptance. Depending on relative timing, it can also let `total_weight_approved` reach the 70% threshold using weight simultaneously still "stuck" in the rejection side, i.e. weight is credited to both outcomes at once instead of exactly one, corrupting the miner's live view of signer consensus and its rejection-timeout backoff/txid-exclusion logic that is keyed off `total_weight_rejected`.

### Likelihood Explanation
This requires no majority collusion and no key compromise: it is triggered purely by the ordinary, sanctioned reconsideration path (a legitimate re-proposal after a transient rejection reason like `UnknownParent`/`NotFoundError`/`ConnectivityIssues`/`NoSortitionView` becomes stale), which the codebase explicitly implements and tests as expected signer behavior. Any race where the node receives a signer's Reject message before that signer's later Accept for the identical `signer_signature_hash` triggers the bug; a slow network delivering out-of-order or delayed `BlockResponse` messages over StackerDB is enough — no attacker action is required, though a single signer strategically re-signaling could reliably trigger it.

### Recommendation
Before adding weight in either branch of `stackerdb_listener.rs`, check the *other* tally's membership as well as the current one, and if the signer previously contributed weight to the opposite outcome, subtract it from that opposite tally when moving the vote (mirroring `gathered_signatures` state into the rejection accounting, or vice versa) rather than leaving stale weight behind. Concretely: in the Accepted branch, if `slot_id` is present in `responded_signers` due to a prior rejection (not a prior acceptance), remove that signer's weight from `total_weight_rejected` before/while adding it to `total_weight_approved`; symmetrically guard the Rejected branch against a slot that previously had a stored signature in `gathered_signatures`.

### Proof of Concept
1. Node proposes block B with hash `H`. Signer S (slot `k`, weight `w`) rejects B with `RejectCode::ValidationFailed(UnknownParent)` because its own node hasn't processed B's parent yet.
2. `StackerDBListener` processes the Rejected message: `responded_signers.insert(k)` → `true`, `total_weight_rejected += w`. [4](#0-3) 
3. The stacks-signer side, per `should_reevaluate_reject_reason`, treats `UnknownParent` as reconsiderable; once the parent is processed, on re-proposal of the same block, signer S proceeds through pre-commit and signs B, broadcasting `BlockResponse::Accepted` for the same `signer_signature_hash` `H`. [6](#0-5) 
4. `StackerDBListener` processes the Accepted message for the same `slot_id` `k`: `gathered_signatures.contains_key(&k)` is `false` (never previously signed), so `total_weight_approved += w` is executed. [7](#0-6) 
5. Result: `total_weight_rejected` still includes `w` from step 2 (nothing ever decremented it), and `total_weight_approved` now also includes `w` from step 4 — signer S's weight is counted in both tallies simultaneously, corrupting the coordinator's accept/reject decision inputs.

/// Determine if a block should be re-evaluated based on its rejection reason˝
fn should_reevaluate_reject_reason(block_info: &BlockInfo) -> bool {
    if let Some(reject_reason) = &block_info.reject_reason {
        match reject_reason {
            RejectReason::ValidationFailed(ValidateRejectCode::UnknownParent)
            | RejectReason::ValidationFailed(ValidateRejectCode::NotFoundError)
            | RejectReason::NoSortitionView
            | RejectReason::ConnectivityIssues(_)
            | RejectReason::TestingDirective
            | RejectReason::InvalidTenureExtend
            | RejectReason::ConsensusHashMismatch { .. }
            | RejectReason::NoSignerConsensus
            | RejectReason::NotRejected
            | RejectReason::Unknown(_) => true,
            RejectReason::ValidationFailed(_)
            | RejectReason::RejectedInPriorRound
            | RejectReason::SortitionViewMismatch
            | RejectReason::ReorgNotAllowed
            | RejectReason::InvalidBitvec
            | RejectReason::PubkeyHashMismatch
            | RejectReason::InvalidMiner
            | RejectReason::NotLatestSortitionWinner
            | RejectReason::InvalidParentBlock
            | RejectReason::DuplicateBlockFound
            | RejectReason::IrrecoverablePubkeyHash
            | RejectReason::ProblematicTransactions
            | RejectReason::ProposalTooOld => {
                // No need to re-validate these types of rejections.
                false
            }
        }
    } else {
        false
    }
}
