### Title
Stale rejection weight is never revoked when a signer switches its vote to acceptance, letting the same signer's weight be counted in both `total_weight_approved` and `total_weight_rejected` - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
`StackerDBListener` accumulates per-block signer weight into two independent counters, `total_weight_approved` and `total_weight_rejected`, but only guards the *rejected* counter against double counting with the `responded_signers` set — a set that is also populated by the *accepted* path. A signer who first rejects and later accepts the same block (a legitimate, protocol-supported re-evaluation) has its weight added to `total_weight_rejected` on the reject, and then — because the accept-path's guard checks the unrelated `gathered_signatures` map, not `responded_signers` — its weight is *also* added to `total_weight_approved` on the later accept, without the stale rejection weight ever being removed.

### Finding Description
`BlockStatus` tracks consensus tallies per block: [1](#0-0) 

On an `Accepted` response, the code guards weight addition using `gathered_signatures` (a signature map keyed by `slot_id`), then inserts into both `gathered_signatures` and `responded_signers`: [2](#0-1) 

On a `Rejected` response, the guard is `block.responded_signers.insert(slot_id)`, which only prevents a *second reject* from the same signer from re-adding weight: [3](#0-2) 

The two branches use two different sets/maps as their "already counted" guard, and neither branch removes a signer's weight from the *other* counter when the signer's vote flips. Concretely:

- Signer S (weight w) sends `Rejected` first → `responded_signers.insert(S)` succeeds → `total_weight_rejected += w`.
- Signer S later sends `Accepted` for the same block (a normal re-evaluation) → the accept guard checks `gathered_signatures.contains_key(S)`, which is still `false` (only the reject path ran before) → `total_weight_approved += w` is executed *again*, using S's weight a second time, while `total_weight_rejected` still retains S's original `w`.

This breaks the implicit invariant that a signer's weight should only ever be attributed to at most one side of the tally at a time, i.e. `total_weight_approved + total_weight_rejected` should never exceed the sum of *distinct responding* signers' weight. After the flip, both counters simultaneously contain S's weight.

This vote-flip is not a contrived edge case: `stacks-signer`'s local `BlockInfo` state machine explicitly allows re-evaluation in both directions (`LocallyAccepted ↔ LocallyRejected`) as documented in `BlockInfo::check_state`: [4](#0-3) 

so a single signer legitimately re-broadcasting an updated `BlockResponse` after a state re-evaluation is sufficient to trigger the bug — no majority or malicious collusion is required, only ordinary signer behavior (or a signer deliberately sending Reject then Accept, which the listener does not forbid either).

### Impact Explanation
The node's decision loop in `SignerCoordinator` checks the rejection condition *before* the acceptance condition every iteration: [5](#0-4) 

Because `total_weight_rejected` retains stale weight from signers who have since switched to acceptance, the blocking-minority (>30%) condition (`total_weight_rejected + weight_threshold > total_weight`) can become true using weight that no longer represents an active rejection — weight that is simultaneously present in `total_weight_approved`. Since the reject branch is evaluated first and returns immediately (`NakamotoNodeError::SignersRejected`), a block that has legitimately reached the 70% approval threshold can instead be discarded as globally rejected due to unretracted, double-counted weight from signers who already changed their vote to accept. This is a liveness wedge on block production/signing: valid, sufficiently-signed blocks can be treated as rejected, forcing miners to reassemble/retry tenures, and it corrupts the fundamental equality that the aggregated weight tally should reflect verified, current-vote-only accepts/rejects (the "aggregated-weight vs verified-accepts" equality named in scope).

### Likelihood Explanation
Triggering requires only one signer to emit a `Rejected` message for a block followed later by an `Accepted` message for the *same* `signer_signature_hash` — well within a single signer's own message flow via ordinary StackerDB gossip, and explicitly supported by the signer's own local state machine (`LocallyRejected → LocallyAccepted` re-evaluation). No majority, no key compromise, and no protocol violation by the sending signer is needed; the flaw is entirely in how the node-side `StackerDBListener` accumulates weight.

### Recommendation
Use a single per-slot "current vote" record (e.g., a `HashMap<u32, Vote>` mapping slot id to its most recent Accepted/Rejected weight) instead of two independently-guarded counters/sets. When a signer's vote changes, subtract its previously-counted weight from the old bucket before adding it to the new bucket, so `total_weight_approved` and `total_weight_rejected` always reflect only the most recent, mutually-exclusive vote per signer.

### Proof of Concept
1. Reward set has signers A (weight 3), B (weight 3), C (weight 4); `total_weight = 10`, `weight_threshold = 7` (70%).
2. Signer A sends `BlockResponse::Rejected` for block H. In `stackerdb_listener.rs`: `responded_signers.insert(A) == true` → `total_weight_rejected = 3`.
3. Signer A re-evaluates locally (`LocallyRejected → LocallyAccepted`, permitted by `BlockInfo::check_state`) and sends `BlockResponse::Accepted` for the same block H.
4. In the Accepted handler, `gathered_signatures.contains_key(A) == false` (A's slot was never inserted into `gathered_signatures`, only into `responded_signers`) → guard passes → `total_weight_approved = 3`. `A` is now counted in both totals.
5. Signers B and C also accept normally → `total_weight_approved = 3 + 3 + 4 = 10 ≥ 7` (accept condition true) while `total_weight_rejected = 3` remains stale from step 2, never cleared.
6. In this specific numeric example the reject branch (`3 + 7 > 10` → false) does not trigger, so the block still gets accepted — but by adjusting weights/timing (e.g., a signer holding weight > blocking minority initially rejects, then flips to accept while other signers are still deciding) the stale `total_weight_rejected` can independently cross `weight_threshold` blocking-minority math and cause `SignersRejected` to fire even though the true, current vote tally (excluding the stale reject) would show acceptance — since the reject-check runs first and returns unconditionally, the coordinator discards a block that in fact has (or would have) sufficient current acceptance weight.

    fn check_state(&self, state: BlockState) -> bool {

        if *prev_state == state {
            return true;
        }
