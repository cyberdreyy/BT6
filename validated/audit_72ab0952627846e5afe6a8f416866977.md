### Title
Unprivileged ERC4626 liquidity withdrawal can freeze epoch settlement - ([File: contracts/strategies/idle/ProgrammableBorrower.sol])

### Summary
`ProgrammableBorrower.onStopEpoch` treats an economically backed but unavailable ERC4626 withdrawal as a hard revert, and `IdleCDOEpochVariant._stopEpoch` deliberately lets that hook revert bubble rather than entering borrower-default handling. An unprivileged user who removes or keeps occupied the external vault’s available liquidity before the honest manager calls `stopEpoch` can repeatedly prevent settlement while `ProgrammableBorrower` still holds valuable vault shares.

### Finding Description
During a running programmable-borrower epoch, `startEpoch` pauses normal deposits and disables ordinary withdrawal requests. [1](#0-0) 

When the manager stops the epoch, IdleCDO calculates `amountRequired` from pool-facing interest plus loss-adjusted pending withdrawals and calls `IProgrammableBorrower.onStopEpoch` outside a `try/catch`. [2](#0-1) 

`onStopEpoch` checks whether the shortfall is covered by `convertToAssets(vaultShares)`; if covered, it calls `vault.withdraw` and converts any withdrawal failure into `StopEpochVaultLiquidityUnavailable`. [3](#0-2) 

Because IdleCDO does not catch this error, the entire `stopEpoch` call reverts before `isEpochRunning` is cleared on the success path. [4](#0-3) 

The vault-valuation check does not verify currently withdrawable liquidity, so an attacker only needs to make the ERC4626 withdrawal fail while keeping `convertToAssets` greater than or equal to the shortfall. [3](#0-2) 

The same external liquidity failure also prevents `emergencyExitVault` from unwinding the position, while `setVault` cannot switch integrations until the existing share balance reaches zero. [5](#0-4) [6](#0-5) 

### Impact Explanation
An attacker can indefinitely defer epoch settlement for as long as the ERC4626 vault lacks redeemable liquidity, freezing the pending withdrawal amount and all pool assets represented by `ProgrammableBorrower`’s vault position. In a normal minted-interest epoch the directly blocked liability is the pending-withdrawal shortfall; in the close-pool path it extends to the recalled pool principal because IdleCDO adds the borrowed strategy-token balance to the amount required. [7](#0-6) 

This is temporary freezing rather than direct theft: the attacker does not need to make the shares worthless, only temporarily unredeemable. The broken invariant is timely settlement of matured withdrawal receipts despite adequate reported vault backing. [3](#0-2) 

### Likelihood Explanation
The attacker only needs the ability to affect the integrated ERC4626 vault’s available liquidity, for example by withdrawing a pre-existing position or borrowing in an underlying market until idle liquidity is below `ProgrammableBorrower`’s required withdrawal. No owner, manager, guardian, borrower, fee receiver, queue, Keyring role, or forged vault balance is required. [8](#0-7) 

The exploit is easiest when the pool has a matured normal withdrawal request or when the manager attempts to close the pool; if `amountRequired` is zero or already held as cash, the external vault is not queried for liquidity. [9](#0-8) 

### Recommendation
Use `vault.maxWithdraw(address(this))` or an equivalent liquidity-aware check before treating the position as withdrawable, and define an explicit bounded outcome for persistent illiquidity rather than indefinitely reverting settlement. [3](#0-2) 

Preferably withdraw up to the available amount, atomically return the residual state needed by IdleCDO, and let the CDO choose between retrying, accounting for a realized liquidity shortfall, or invoking controlled default/recovery accounting. Separately, provide a non-vault-dependent recovery path for cases where `convertToAssets` reports backing but redemption remains unavailable. [5](#0-4) 

### Proof of Concept
The following Foundry fork test can be added to `TestProgrammableBorrowerCreditVault`; the public `setWithdrawLimit` call models an unprivileged external ERC4626 liquidity withdrawal, while all production CDO and borrower calls remain unchanged. [10](#0-9) 

```solidity
function testUnprivilegedVaultLiquidityBlocksStopEpoch() external {
    MockStopEpochLiquidityVault illiquidVault =
        new MockStopEpochLiquidityVault(USDC);

    // The programmable borrower has not started an epoch and holds no vault
    // shares yet, so the honest manager can point it at the integrated ERC4626.
    vm.prank(manager);
    programmableBorrower.setVault(address(illiquidVault));

    uint256 depositAmount = 10_000 * oneScale;
    uint256 tranches = idleCDO.depositAA(depositAmount);

    // A KYC-passing lender creates a matured withdrawal liability before epoch
    // start. This receipt is what stopEpoch must fund from the vault position.
    uint256 pending = cdoEpoch.requestWithdraw(tranches, address(aaTranche));
    assertGt(pending, 0);

    vm.prank(manager);
    cdoEpoch.startEpoch();
    assertEq(illiquidVault.balanceOf(address(programmableBorrower)), depositAmount);

    // Unprivileged vault-side activity removes currently withdrawable liquidity.
    // On a real ERC4626 this corresponds to another vault user withdrawing or
    // market borrowing exhausting idle assets, not to changing reported NAV.
    illiquidVault.setWithdrawLimit(0);

    vm.warp(cdoEpoch.epochEndDate() + 1);

    // The position is still fully backed according to convertToAssets, but its
    // withdrawal fails and the hook error bubbles through CDO.stopEpoch().
    assertEq(
        illiquidVault.convertToAssets(
            illiquidVault.balanceOf(address(programmableBorrower))
        ),
        depositAmount
    );

    vm.prank(manager);
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    cdoEpoch.stopEpoch(0, 0);

    // Settlement stays frozen: the epoch remains running and the LP receipt is
    // still unfunded while vault liquidity remains unavailable.
    assertTrue(cdoEpoch.isEpochRunning());
    assertEq(strategy.pendingWithdraws(), pending);

    // The freeze is temporary rather than a valuation loss: restoring external
    // liquidity allows the same honest manager call to settle normally.
    illiquidVault.setWithdrawLimit(type(uint256).max);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    assertFalse(cdoEpoch.isEpochRunning());
    assertEq(strategy.pendingWithdraws(), 0);
}
```

The decisive condition is that `convertToAssets` reports enough backing while `withdraw` cannot currently deliver the requested assets, which sends the covered-liquidity branch into the catch and blocks the uncaught CDO settlement call. [3](#0-2) [11](#0-10)
