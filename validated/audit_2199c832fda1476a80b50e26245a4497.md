Found a valid analog in `multisig2/src/lib.rs`: `delete_member` fails to purge a removed member's confirmations from *other* pending requests, so a stale confirmation from a no-longer-live member still counts toward `num_confirmations` in `confirm`, letting a request execute below the true live-member threshold — the same class of bug as the report (a counted value that doesn't track the actual live/current set).

### Title
Multisig request can be executed with fewer live-member confirmations than `num_confirmations` due to stale confirmations surviving member deletion - (File: multisig2/src/lib.rs)

### Summary
`delete_member` only removes requests that the deleted member *originated*, but does not scan and strip that member's confirmations from requests originated by *other* members. `confirm` later counts all strings stored in the `confirmations` set for a request, without checking whether each entry still corresponds to a current member. A confirmation recorded by a member who is later deleted therefore remains valid and can be the deciding vote that pushes a request over the `num_confirmations` threshold, even though the real number of currently-live members who approved the request is one less than required.

### Finding Description
`confirm` computes the pass condition purely from the size of the stored `HashSet<String>` of confirmer identities: [1](#0-0) 

`delete_member` cleans up only the requests whose *original signer* (`r.member`) equals the deleted member, and removes that member's `num_requests_pk` entry — it never inspects or prunes `confirmations` entries on other requests that the deleted member may have already confirmed: [2](#0-1) 

Because `confirmations` is a bare `LookupMap<RequestId, HashSet<String>>` with no cross-reference back to `members`, once a member's identity string is inserted here (via `confirm`, line 311), it persists for that request regardless of subsequent membership changes: [3](#0-2) 

This breaks the intended binding: "count of confirmations for a request" should equal "count of currently-live members who confirmed it." Instead it equals "count of confirmation strings ever inserted," including from members later removed via `DeleteMember`.

### Impact Explanation
This matches the Critical impact category "a multisig request executed below threshold." A request nominally requiring `k` confirmations can execute with only `k-1` (or fewer) confirmations from members that are still live at execution time, because a stale confirmation from a removed member is silently counted. Since `MultiSigRequestAction::Transfer`, `FunctionCall`, `AddKey`/full-access-key grants, and `DeployContract` are all executable via `confirm`, this can lead to unauthorized fund transfers or contract takeover approved by fewer genuine parties than the configured security threshold.

### Likelihood Explanation
This requires no external attacker privilege beyond being (or colluding as) a normal multisig member — it is reachable through ordinary contract usage: create a request, get partial confirmations, later delete one of those confirmers via a separate `DeleteMember` request, then have the remaining live members supply just enough new confirmations to reach the nominal count. No foundation, owner, redeploy, or key compromise is needed; it's an internal accounting flaw in `delete_member`/`confirm`.

### Recommendation
When executing `DeleteMember`, iterate over **all** requests' confirmation sets (not just requests originated by that member) and remove the deleted member's identity string from each. Alternatively, when counting confirmations in `confirm`, filter the stored set to only entries that are still `self.members.contains(...)` before comparing against `num_confirmations`.

### Proof of Concept
1. Initialize multisig with 4 members `A, B, C, D` and `num_confirmations = 3`.
2. `A` calls `add_request_and_confirm` for request `R1` (e.g., `Transfer`) → confirmations `{A}`.
3. `B` calls `confirm(R1)` → confirmations `{A, B}` (2 of 3, not yet executed).
4. Separately, members `C, D, A` submit and confirm a `DeleteMember{B}` request (`R2`), which executes (3 confirmations, valid since 4-1=3 members remains ≥ `num_confirmations`). `delete_member` removes `B` from `members` and cleans up only requests *originated* by `B`; `R1` (originated by `A`) is untouched, so its confirmations remain `{A, B}`.
5. Now `C` (a live member) calls `confirm(R1)`. `confirmations.len() == 2` (`A`,`B`) `+ 1 == 3 >= num_confirmations(3)` → the request executes.
6. Result: `R1` executed with only two currently-live members (`A`, `C`) actually approving it at execution time, one below the configured `num_confirmations = 3`, because `B`'s stale confirmation was counted.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
