### Title
`eth_subscribe("logs")` filter match leaks logs from unrelated contract addresses to WebSocket subscribers - ([File: crates/execution/flashblocks/src/pending_blocks.rs])

### Summary
The Nextcloud advisory describes a search/query API that, when scoped to a specific target, returns unrelated third-party data because the underlying query didn't enforce the requested scope on the returned records — only used the filter to decide whether to include a record at all. `PendingBlocks::get_latest_flashblock_transactions_with_logs_filtered` in Base's flashblocks pending-state RPC layer has the same root-cause shape: a caller-supplied `Filter` (e.g. `address` or `topics`) is used only to test whether *any* log in a transaction matches, and if so, *all* logs of that transaction — including logs emitted by unrelated contract addresses that do not match the filter — are returned to the caller.

### Finding Description
`get_latest_flashblock_transactions_with_logs_filtered` iterates pending transactions and, for each transaction whose receipt contains at least one log matching the filter, returns the transaction with its *entire* log set rather than only the matching logs: [1](#0-0) 

The unit test explicitly documents and asserts this over-broad behavior: [2](#0-1) 

Any unrelated transaction that happens to also touch the filtered address/topic (e.g. a DEX router transaction, a multicall, or any batched transaction that emits many events from many different downstream contracts) will disclose the logs of every other contract touched in that transaction to any WebSocket client subscribing with a narrow filter — even for contracts, tokens, or counterparties the requester has no legitimate reason to see event data for. This mirrors the Nextcloud contacts-search flaw: the filter/query is used purely as a "does this record qualify" gate, not as a per-item projection that scopes exactly what is disclosed.

This function is exposed as part of the flashblocks-specific pending-state pubsub/RPC surface (`crates/execution/flashblocks/src/rpc/pubsub.rs` references it), reachable by any anonymous WebSocket RPC client subscribing to `eth_subscribe("logs", filter)` while flashblocks pending state is active — no authentication or privilege is required to open a log subscription with an address/topic filter.

### Impact Explanation
This is an information-disclosure issue: an unprivileged RPC/WebSocket client can obtain event log data (addresses, topics, event payloads) belonging to unrelated contracts/counterparties simply by using a narrow filter and waiting for it to co-occur in a transaction with unrelated activity, contrary to the documented and expected filter semantics of `eth_getLogs`/log subscriptions. It does not directly cause loss of funds or a chain split, but it violates the confidentiality/authorization expectation that a log filter scopes exactly what is returned, and could leak sensitive on-chain application data (e.g., internal accounting events, other users' approvals/transfers bundled in the same transaction) to parties not authorized/expecting to see them — directly analogous to the "authenticated user retrieves other users' data via search" pattern in the reference advisory.

### Likelihood Explanation
Trivially reachable: any client can open a WebSocket subscription with a filter on pending flashblocks logs; multi-log transactions (batched calls, router/aggregator contracts, multicalls) that touch several contracts are extremely common on L2s, making the over-broad disclosure very likely to occur incidentally, and trivially triggerable deliberately by crafting or observing transactions that bundle a filtered address with other contract calls.

### Recommendation
Change `get_latest_flashblock_transactions_with_logs_filtered` (and any callers that rely on "match at transaction granularity, return everything") to filter the returned log set down to only the logs that actually match the supplied `Filter`, consistent with standard `eth_getLogs` semantics, unless full-transaction-context disclosure is an explicit product requirement — in which case that must be documented and the RPC method should not be presented as a scoped filter.

### Proof of Concept
1. Start a Base node with flashblocks pending state enabled.
2. Submit (or wait for) a transaction that emits logs from two different contract addresses, `addr_match` and `addr_other`, in the same transaction (as in the existing test fixture).
3. Open `eth_subscribe("logs", {"address": addr_match})` (or call the internal `get_latest_flashblock_transactions_with_logs_filtered` path with `Filter::new().address(addr_match)`).
4. Observe that the response/notification includes logs for `addr_other` as well, even though the filter only requested `addr_match` — as directly demonstrated by the existing test `filtered_transactions_returns_all_logs_when_any_matches` asserting `txs[0].logs.len() == 2` and containing `addr_other`'s log.     /// Returns transactions with their associated logs from only the latest flashblock (delta),
    /// filtered to include only transactions where at least one log matches the given filter.
    ///
    /// When a transaction matches, all of its logs are returned (not just the matching ones).
    /// This preserves full transaction context for subscribers who need complete log sets.
    pub fn get_latest_flashblock_transactions_with_logs_filtered(
        &self,
        filter: &Filter,
    ) -> Vec<TransactionWithLogs> {
        let prev_count = self.previous_flashblocks_tx_count();

        self.transactions
            .iter()
            .skip(prev_count)
            .filter_map(|tx| {
                let receipt = self.transaction_receipts.get(&tx.tx_hash())?;
                let logs = receipt.inner.logs();

                let has_match = logs.iter().any(|log| filter.matches(log.as_ref()));
                if !has_match {
                    return None;
                }

                Some(Self::transaction_with_logs(tx, receipt))
            })
            .collect()
    }
