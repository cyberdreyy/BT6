### Title
Vote-account VAT burn can panic the validator via a stale balance-sufficiency assumption - ([File: runtime/src/bank.rs])

### Summary
`Bank::maybe_burn_vat_from_staked_accounts` unconditionally subtracts a fixed `vat_to_burn_per_epoch` amount from every vote account's *live* lamport balance at epoch boundary, relying entirely on an earlier filtering step (`Stakes::clone_and_filter_for_vat` / `VoteAccounts::clone_and_filter_for_vat`) having already excluded vote accounts with insufficient balance. This mirrors the reported Solidity bug class: a balance check performed against a stale/cached value is used to guarantee a later unchecked (`.expect()`-guarded) arithmetic subtraction, and the actual balance can be reduced in the interim by an ordinary, permission-scoped transaction (a vote-account `Withdraw` instruction) before the burn executes.

### Finding Description
`maybe_burn_vat_from_staked_accounts` reads the *current* on-chain vote account lamports via `self.get_account(vote_pubkey)` and does: [1](#0-0) 
using `.expect("Vote accounts should have already been filtered to contain enough balance for the VAT")` on the `checked_sub`. The correctness of this code depends entirely on the comment's invariant: that `epoch_stakes.stakes().vote_accounts()` was produced by `clone_and_filter_for_vat`, which filters out any vote account whose balance is insufficient to survive the burn: [2](#0-1) 

However, `EpochStakes`/`Stakes` snapshots used for epoch-boundary processing (as is standard in Solana/Agave) are computed ahead of the epoch in which they take effect (the stakes cache is filtered/frozen at the time epoch stakes for the *next* epoch are computed, not at the exact moment the VAT burn runs). Between that snapshot point and the actual invocation of `maybe_burn_vat_from_staked_accounts` at the new epoch's boundary, the vote account's authorized withdrawer can submit an ordinary `Withdraw` transaction that reduces the vote account's lamport balance below the amount required to survive the burn: [3](#0-2) 
The vote-state `withdraw` function only checks against the rent-exempt minimum and pending delegator rewards — it has no knowledge of, and does not reserve, the pending VAT burn amount. This is analogous to `_getPairBalance`/`_getBalance` in the reported bug: a balance-dependent invariant established earlier (a "sufficient-balance" filter) is silently invalidated by a legitimate, later state-changing action, and the code that depends on the invariant holding does an unchecked subtraction.

### Impact Explanation
Because `checked_sub(...).expect(...)` panics rather than returning an error when the assumption is violated, and `maybe_burn_vat_from_staked_accounts` runs deterministically as part of bank epoch-boundary processing (Alpenglow feature-gated) on every validator, the panic would occur identically and simultaneously on all validators processing that epoch boundary. This is not a single-node crash; it is a consensus-wide, transaction-triggered liveness failure that would halt the entire cluster (all replaying validators panic in the same deterministic bank code path), matching the accepted "transaction-triggered cluster halt" impact category.

### Likelihood Explanation
Triggering this requires only:
1. A vote account holding delegated stake that survives the `clone_and_filter_for_vat` admission filter at the time epoch stakes are computed.
2. The vote account's `authorized_withdrawer` submitting a normal `Withdraw` transaction (permission is scoped to that specific vote account, not a validator/leader/operator-only privilege) after the filtering snapshot but before the VAT burn executes at the new epoch boundary, reducing the balance below `vat_to_burn_per_epoch` plus rent-exempt minimum.

This requires the feature to be active (`feature_snapshot.alpenglow`, part of SIMD-0357), and I was unable to fully confirm within this pass the exact timing offset between the epoch-stakes snapshot point (`clone_and_filter_for_vat`) and the invocation point of `maybe_burn_vat_from_staked_accounts`, i.e., whether there is always a state-mutable window between the two. This ordering should be verified directly against `runtime/src/bank.rs` (the call site around line 2644) and `runtime/src/alpenglow_epoch_type.rs`/`slot_params.rs`, which reference `MAX_ALPENGLOW_VOTE_ACCOUNTS`/`vat_to_burn_per_epoch`, before treating this as fully confirmed rather than a strong structural analog.

### Recommendation
Do not rely on a balance filter computed at a separate point in time for an unchecked (`.expect()`-panicking) later subtraction. Either:
- Re-validate/re-filter vote account balances against `vat_to_burn_per_epoch` at the exact point of burning (using `checked_sub` with graceful handling — e.g., skip or clamp accounts that no longer qualify — instead of `.expect()`), or
- Reserve/lock the VAT amount at withdrawal time so `vote_state::withdraw` cannot reduce a vote account below `rent_exempt_minimum + pending_delegator_rewards + pending_vat_burn`, closing the gap between the filtering snapshot and the burn.

### Proof of Concept
Conceptual PoC (requires Alpenglow feature active):
1. A validator's vote account has just enough stake/balance to pass `clone_and_filter_for_vat`'s minimum-balance admission check when epoch stakes for epoch `N` are computed.
2. Before the epoch-`N` boundary is processed, the vote account's `authorized_withdrawer` submits a `VoteInstruction::Withdraw` transaction (reachable via `programs/vote/src/vote_state/mod.rs::withdraw`) that withdraws lamports down to just above the rent-exempt minimum, below what `vat_to_burn_per_epoch` requires.
3. At the epoch-`N` boundary, `Bank::maybe_burn_vat_from_staked_accounts` (`runtime/src/bank.rs:2648-2694`) loads the now-reduced balance via `self.get_account(vote_pubkey)`, and `checked_sub(vat_to_burn_per_epoch)` returns `None`, triggering the `.expect(...)` panic on every validator processing that slot, halting the cluster.
