### Title
Ramping/Delay Protection for Vote Commission Changes Is Circumvented for New Vote Accounts and by `UpdateCommissionBps` - ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
The Curve/Balancer report describes a management function (`add_asset`) that lets a privileged actor change economically sensitive parameters (weights, amplification) outside the normal ramping mechanism designed to prevent sandwiching/front-running attacks that harvest value from unsuspecting users. Agave's analog is the vote-account commission mechanism: normal `UpdateCommission` changes are throttled by `is_commission_update_allowed` and further delayed by the `delay_commission_updates` feature via a cached, one-epoch-old commission snapshot used at reward-calculation time. However, this delay protection is bypassed both by the newer `UpdateCommissionBps` instruction, which explicitly has "no timing restrictions," and, more importantly, by an edge case in the reward-calculation fallback logic for newly created/newly-staked vote accounts, which uses the *live* (undelayed) commission instead of the delayed snapshot.

### Finding Description
`UpdateCommission` enforces a within-epoch timing rule (`is_commission_update_allowed`, only allowed in the first half of an epoch for increases) [1](#0-0) , and when `delay_commission_updates` is active, reward calculation additionally uses a commission value cached from the *previous* epoch snapshot rather than the live value, specifically to prevent "last minute commission rugs" [2](#0-1) [3](#0-2) .

`UpdateCommissionBps` (SIMD-0291) removes the timing-rule check entirely — the code comment states "No commission update rule, per SIMD-0249 and SIMD-0291," and only requires the authorized-withdrawer signature [4](#0-3) . A test explicitly documents this: "Unlike test_update_commission, SIMD-0291 has no timing restrictions (per SIMD-0249). Updates are always allowed regardless of epoch position" [5](#0-4) .

The critical gap is in `calculate_stake_rewards_and_commissions`/`redeem_delegation_rewards`: the delayed-commission lookup only falls back to `snapshot_epoch_vote_accounts` (an epoch-old cache) or `rewarded_epoch_vote_accounts`; if the vote account did not exist far enough in the past (e.g., it is newly created or newly staked within the current/prior epoch), the code falls back to the *live* `vote_state` view instead of an old, "safe" value [6](#0-5) . This is validated by an in-repo test, `test_calculate_stake_vote_rewards_prestaked_vote_account`, whose comment states: "Check that if a new vote account is somehow already staked and earning rewards in the epoch in which it was created, the reward commission falls back to the latest commission rate for that epoch," and again "if a vote account didn't exist two epochs ago, the reward commission falls back to the commission from the previous epoch" [7](#0-6) .

Together, these mean the ramping/delay mechanism that is supposed to give delegators/stakers a full epoch's notice before a raised commission takes effect (thereby preventing a validator operator from spiking commission right before a rewards distribution to skim delegator rewards, then lowering it again) can be circumvented in two ways reachable from ordinary transactions signed only by the vote account's authorized withdrawer:
1. Using `UpdateCommissionBps` instead of the legacy `UpdateCommission`, which has no timing restriction at the instruction level.
2. Creating a brand-new vote account (or delegating stake to one shortly before it starts earning rewards) so that the "delay" fallback in reward calculation has no old snapshot to fall back on and instead uses the live/current commission.

### Impact Explanation
A validator operator (management analog) controlling only the authorized-withdrawer key of a vote account can set commission arbitrarily high immediately before a rewards distribution for a fresh vote account (bypassing the epoch-delay safeguard), or use `UpdateCommissionBps` to instantly raise commission with no notice period at all, extracting delegator staking rewards that the ramping/delay design was explicitly built to protect against ("prevent last minute commission rugs"). This is a stake/reward-accounting correctness and economic-fairness issue: honest delegators' effective rewards are silently reduced without the intended one-epoch warning window, directly harming stakers' fund distribution, analogous to the sandwiching-of-ramping issue in the source report.

### Likelihood Explanation
Reaching this requires only that the account is the vote account's authorized withdrawer and can submit ordinary signed transactions (`UpdateCommissionBps`, or `CreateAccount`/`InitializeAccount` + `DelegateStake` + `UpdateCommission`) — no special privilege beyond normal vote-account key ownership is needed. The `UpdateCommissionBps` bypass is unconditional whenever `commission_rate_in_basis_points` and `delay_commission_updates` features are active (i.e., in the intended, "fixed" configuration). The new-vote-account fallback is a legitimate, always-reachable code path (any operator can create a vote account and immediately delegate/earn), so likelihood is high for both.

### Recommendation
- For `UpdateCommissionBps`, evaluate whether the removed timing restriction is compensated for elsewhere; if reward-calculation still relies on the epoch-old snapshot for safety, ensure that guarantee actually holds for all account ages (see below), rather than relying solely on the instruction-level absence of restriction being "safe by construction."
- Close the fallback gap in `redeem_delegation_rewards`/`calculate_stake_rewards_and_commissions`: when no epoch-old snapshot commission exists for a vote account, do not fall back to the live commission value; instead treat the account as ineligible for rewards that epoch, or use the commission at delegation time, so a newly created vote account cannot use elevated commission on its very first reward-earning epoch.
- Add an explicit test asserting that a fresh vote account cannot realize a commission change that would have been blocked/delayed had the account existed for the requisite number of epochs.

### Proof of Concept
Not independently executable from the available index (no local runtime/CLI environment); the concrete path is inferable directly from code and existing unit tests:
1. Authorized withdrawer creates a new vote account and delegates stake to it (`CreateAccount` + vote `InitializeAccount` + stake `DelegateStake`), reaching the `create_with_balance`/`delegate_stake_amount` path exercised in `test_calculate_stake_vote_rewards_prestaked_vote_account` [8](#0-7) .
2. In the same or immediately following epoch (before two full epochs elapse), the withdrawer submits `VoteInstruction::UpdateCommissionBps` with a maximal commission (e.g., 100%) [9](#0-8) , which succeeds unconditionally since "No commission update rule" applies [4](#0-3) .
3. Because the vote account has no snapshot from two epochs prior, `calculate_stake_rewards_and_commissions` falls back to the live `vote_state` commission rather than a delayed value [10](#0-9) , so delegators' rewards for that epoch are computed and paid using the just-set maximal commission with none of the intended one-epoch notice.
4. The withdrawer then lowers commission back down (also unrestricted under `UpdateCommissionBps`), leaving no trace of the temporary spike being blocked by ramping logic — mirroring the "circumvention of ramping" pattern in the source report.

/// Given the current slot and epoch schedule, determine if a commission change
/// is allowed
pub fn is_commission_update_allowed(slot: Slot, epoch_schedule: &EpochSchedule) -> bool {
    // always allowed during warmup epochs
    if let Some(relative_slot) = slot
        .saturating_sub(epoch_schedule.first_normal_slot)
        .checked_rem(epoch_schedule.slots_per_epoch)
    {
        // allowed up to the midpoint of the epoch
        relative_slot.saturating_mul(2) <= epoch_schedule.slots_per_epoch
    } else {
        // no slots per epoch, just allow it, even though this should never happen
        true
    }
}
