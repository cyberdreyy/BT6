This scenario is a genuine, reproducible property of the current code rather than a theoretical stretch.

## Analysis

`rescueFunds` in `BaseEscrow.sol` only enforces three things: the caller is `immutables.taker`, the immutables hash matches the deployed clone, and `block.timestamp` is past `rescueStart(RESCUE_DELAY)` (a fixed absolute timestamp = `deployedAt + RESCUE_DELAY`, independent of what stage the escrow is actually in): [1](#0-0) 

There is no check that `token`/`amount` correspond to genuinely "stray" assets rather than the exact principal that `_cancel` would otherwise send to the maker. Compare with `EscrowSrc._cancel`, which is the only function contractually obligated to return `immutables.amount` of `immutables.token` to `immutables.maker`: [2](#0-1) 

Because `rescueFunds` is gated purely on `onlyCaller(immutables.taker.get())` and a time check, the same `taker` who is entitled to call `cancel()` (returns funds to maker) can instead simply wait until `RESCUE_DELAY` elapses and call `rescueFunds(immutables.token, immutables.amount, immutables)` to redirect the identical principal to themselves via `_uniTransfer`: [3](#0-2) 

The README explicitly frames `rescueFunds` as intended only for "assets that are accidentally stuck on a contract," but this intent is not enforced in code — no distinction exists on-chain between "stuck" funds and the live, expected maker principal: [4](#0-3) 

The only real-world mitigation is that `SrcPublicCancellation` (reachable by any `_ACCESS_TOKEN` holder via `publicCancel`) is expected to occur well before `RESCUE_DELAY`, giving other resolvers a chance to return funds to the maker first: [5](#0-4) 

But this is a race that depends on a third, unrelated access-token holder acting — it is not a protocol-enforced invariant, and the taker retains a guaranteed path to seize the principal once `RESCUE_DELAY` passes if no one else intervenes. The "malformed fee parameters bricking the destination path" framing in the question is not actually necessary to trigger this — a taker can achieve the same result in any order fill by simply never revealing the secret and never calling `cancel()`/`publicCancel()`, then waiting out `RESCUE_DELAY`. Existing tests (`test_RescueFundsSrc`, `test_RescueFundsSrcNative` in `test/unit/Escrow.t.sol`) only validate that rescue works *after* legitimate withdraw/cancel already emptied the principal — none of them assert that `rescueFunds` is blocked from grabbing an *un-cancelled* live maker principal, confirming the code has no such guard.

### Title
Taker can use `rescueFunds` to seize the maker's live source principal instead of returning it via `cancel` - (File: `contracts/BaseEscrow.sol`, `contracts/EscrowSrc.sol`)

### Summary
`BaseEscrow.rescueFunds` allows the escrow's `taker` to withdraw an arbitrary `token`/`amount` once `block.timestamp >= deployedAt + RESCUE_DELAY`, with no check that the funds are actually "stuck" rather than the maker's original principal still due back to the maker via `EscrowSrc.cancel`.

### Finding Description
`rescueFunds` (`contracts/BaseEscrow.sol:71-79`) is guarded only by `onlyCaller(immutables.taker.get())`, `onlyValidImmutables`, and `onlyAfter(rescueStart(RESCUE_DELAY))`. It performs an unconditional `_uniTransfer(token, msg.sender, amount)`. If a taker deploys an `EscrowSrc` (via order fill) and then simply never calls `withdraw`/`withdrawTo` (revealing the secret) and never calls `cancel`/allows `publicCancel`, the maker's principal (`immutables.token`, `immutables.amount`) remains sitting in the clone. Once `RESCUE_DELAY` elapses, the same taker calls `rescueFunds(immutables.token, immutables.amount, immutables)` and receives the maker's original principal directly, instead of it flowing to the maker through `_cancel` (`contracts/EscrowSrc.sol:125-132`).

### Impact Explanation
This is direct theft of the maker's at-rest principal by the taker, a normal unprivileged protocol participant reachable via a documented public entrypoint (`rescueFunds`). This matches the Critical bounty category: "direct theft of user funds at rest ... caused by these production contracts."

### Likelihood Explanation
The only practical obstacle is that other access-token holders could call `publicCancel` before `RESCUE_DELAY` is reached. `RESCUE_DELAY` is set to multi-day values in tests/config (e.g., 7-8 days) while cancellation windows are comparatively short, so there is ample time for the acting taker (who controls the order fill) to simply be the only party monitoring the swap, or to target long-tail/less-monitored orders, and then claim the funds once the rescue window opens. No on-chain mechanism prevents this regardless of intervening conditions.

### Recommendation
`rescueFunds` should not be permitted to transfer out `immutables.token` in the amount equal to `immutables.amount` (i.e., the principal) while the escrow's core lifecycle for that token has not yet completed (secret not consumed / not yet cancelled), or the contract should track/zero-out the "protected" principal upon deployment and only allow rescue of balances in excess of the amounts owed under `withdraw`/`cancel`, or the function should require that the corresponding `withdraw`/`cancel` has already executed for that token before allowing a matching rescue.

### Proof of Concept
1. Taker fills a maker order via the Limit Order Protocol, causing `EscrowSrc` clone deployment and maker token deposit equal to `immutables.amount`.
2. Taker never calls `withdraw`/`withdrawTo` (does not reveal the secret) and never calls `cancel`.
3. No other access-token holder calls `publicCancel` before `RESCUE_DELAY` elapses (`immutables.timelocks.rescueStart(RESCUE_DELAY)` passed).
4. Taker calls `rescueFunds(immutables.token, immutables.amount, immutables)`.
5. `_uniTransfer` sends the full maker principal to the taker; the maker never receives their tokens back, and `cancel`'s guarantee is bypassed. This mirrors the exact mechanics validated in `test_RescueFundsSrc`/`test_RescueFundsSrcNative` in `test/unit/Escrow.t.sol`, except performed *before* any legitimate `cancel`/`withdraw` has run.
