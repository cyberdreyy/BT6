### Title
Loss-adjusted withdraw receipt haircut can be bypassed by re-requesting in a later epoch, letting the user claim the full un-haircut amount — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestWithdraw` protects loss-adjusted receipts by looking up `lossRecoveryPriceByEpoch` only under `lastWithdrawRequest[_user]` — the single most recent request epoch. If a user's pending receipt was haircut in an earlier epoch, a new request in a later (non-loss) epoch moves `lastWithdrawRequest` forward, the guard sees `lossRecoveryPrice == 0`, and the old haircut is permanently masked — mirroring the kernel bug where the flush fault was hidden by instruction nullification and the "flushed range" covered the wrong pages. The stale haircutted basis remains inside `withdrawsRequests[_user]` and is later paid out 1:1 through `_transferFundedClaim`.

### Finding Description
In `requestWithdraw` (IdleCreditVault.sol:259-271) the loss check is:

```solidity
uint256 lossEpoch = lastWithdrawRequest[_user];
uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
if (lossRecoveryPrice != 0 && (withdrawsRequestsByEpoch[_user][lossEpoch] != 0 || ...)) revert NotAllowed();
```

It only inspects the epoch stored in `lastWithdrawRequest`. When `stopEpochWithDuration` is executed with a loss, `collectWithdrawFunds` (lines 411-420) stores `lossRecoveryPriceByEpoch[epoch]` for the epoch(s) containing pending receipts and zeroes `pendingWithdraws`. After that, an affected user can call `requestWithdraw` again in a subsequent epoch E2:

- `lastWithdrawRequest[_user]` is overwritten to E2 (line 282).
- `withdrawsRequestsByEpoch[_user][E2]` is credited, while the old basis at the loss epoch E1 remains in both `withdrawsRequestsByEpoch[_user][E1]` and the aggregate `withdrawsRequests[_user]`.

Later, in `claimWithdrawRequest`, `_claimLossAdjustedWithdrawRequest` (lines 789-801) computes `lossEpoch = lastWithdrawRequest[_user]` = E2, finds `lossRecoveryPriceByEpoch[E2] == 0`, and returns 0 without clearing E1. The normal claim path then burns receipt tokens and calls `_transferFundedClaim(_user, amount)` where `amount` includes the full un-haircut E1 basis — the haircut is never applied. `_clearWithdrawClaimForEpoch` is never invoked for E1 because it is only reached through the loss-adjusted/default paths keyed off `lastWithdrawRequest` or `defaultRecoveryEpoch`.

### Impact Explanation
The attacker receives `claimBasis_E1 * (1 - lossRecoveryPrice)` more underlyings than entitled, paid directly from funded withdraw reserves held by the strategy. Because `lossRecoveryPriceByEpoch` exists precisely to socialize a borrower shortfall across pending receipts, paying one claimant at 100% makes the funded pool insolvent for the remaining claimants of that same loss epoch — the last claimant(s) cannot be paid. Quantified loss: up to the entire haircut portion of the attacker's E1 receipt, e.g. with a 50% recovery price and a 100k USDC receipt, the attacker steals ~50k USDC belonging to other withdrawing lenders.

### Likelihood Explanation
Requires only an unprivileged user who: (1) has a withdraw request pending in an epoch that ends via `stopEpochWithDuration` with `_lossAmount > 0` (a routine, honest-manager action during borrower stress), and (2) submits a second `requestWithdraw` in any later epoch, then claims. No privileged cooperation is needed; the second request is a normal user operation. The bug is deterministic once a loss-adjusted epoch exists.

### Recommendation
In `requestWithdraw`, iterate or track all epochs with a nonzero `lossRecoveryPriceByEpoch` for which the user still holds `withdrawsRequestsByEpoch[_user][e] != 0` (or keep a per-user flag/oldest-loss-epoch pointer set by `collectWithdrawFunds`), and revert until every loss-adjusted receipt is claimed — not just the one at `lastWithdrawRequest`. Alternatively, settle the loss-adjusted claim inline before accepting a new request.

### Proof of Concept
Foundry fork test sketch (same harness as `test/foundry/IdleCreditVault.t.sol`):

```solidity
// 1. user deposits, epoch starts, user calls cdoEpoch.requestWithdraw(fullBal, AA)
// 2. manager stops epoch with loss: cdoEpoch.stopEpochWithDuration(apr, interest, duration, loss)
//    -> collectWithdrawFunds(amount < pendingBasis) stores lossRecoveryPriceByEpoch[E1] < 1e18
// 3. buffer period: user calls cdoEpoch.requestWithdraw(small, AA) again
//    -> guard sees lossRecoveryPriceByEpoch[lastWithdrawRequest=E2] == 0, succeeds
//    -> lastWithdrawRequest[user] = E2
// 4. after funding, user calls cdoEpoch.claimWithdrawRequest()
//    -> _claimLossAdjustedWithdrawRequest uses E2, returns 0
//    -> normal path pays withdrawsRequests[user] (E1+E2 basis) at 1:1
// assert user received E1 basis * (1 - lossRecoveryPrice) more than entitled
// assert subsequent claimant of epoch E1 reverts on insufficient funded balance
```

Note: the exact claim entry point between `claimWithdrawRequest`'s loss-adjusted branch and the funded aggregate payout (lines 300-330 of `IdleCreditVault.sol`) was not fully visible in the index; the PoC should assert whether the E1 basis escapes via the funded path or remains permanently unclaimable (both outcomes are protocol losses — theft or frozen funds).
