### Title
Unauthorized front-running of `InitializeNonceAccount` due to missing signer/authority check - (File: `programs/system/src/system_instruction.rs`)

### Summary
The system program's `initialize_nonce_account` function transitions a nonce account from `Uninitialized` to `Initialized`, setting the `nonce_authority` from instruction data, but never verifies that the transaction was authorized by the entity that created (or is entitled to control) the account. Any unprivileged transaction sender who knows the nonce account's public key can submit a competing `InitializeNonceAccount` instruction naming themselves (or any address) as `nonce_authority`, and if that transaction lands before the legitimate initializer's transaction, it silently wins — exactly the same class of bug reported in the external report (`ERC20Pool.initialize` lacking an `onlyOwner`/caller check).

### Finding Description
`initialize_nonce_account` only validates that the account is writable, has sufficient rent-exempt lamports, and is currently `Uninitialized`. It never checks that the account itself (or any specific authorized party) is a transaction signer: [1](#0-0) 

Compare this to the vote program's `initialize_account`, which explicitly requires the `node_pubkey` supplied in `VoteInit` to be present among the transaction signers before allowing initialization: [2](#0-1) 

The vote program pattern demonstrates the correct mitigation (an authorization check tied to the party that should legitimately control initialization). The system program's nonce-account initializer has no equivalent check — `SystemInstruction::InitializeNonceAccount(authorized)` is dispatched straight to `initialize_nonce_account` with no signer validation on account index 0 or on the caller in general: [3](#0-2) 

Because a nonce account's public key becomes known as soon as its `CreateAccount` (or `CreateAccountWithSeed`) transaction is created/broadcast — before it necessarily lands and before the corresponding `InitializeNonceAccount` instruction executes (if issued as a separate transaction, e.g. by wallets/tooling that don't bundle create+initialize atomically) — an unprivileged attacker who observes the pending create transaction can race a higher-priority-fee `InitializeNonceAccount` transaction naming the same nonce account and an attacker-controlled `nonce_authority`, permanently seizing control of that nonce account.

### Impact Explanation
If successful, the attacker becomes the `nonce_authority` of the account. This lets the attacker later `AdvanceNonceAccount` or `WithdrawNonceAccount` (once balance drops to zero) under their own authority, and more importantly denies the intended owner any control over the durable nonce — breaking the nonce's replay-protection guarantee for its intended use (e.g., blocking or hijacking flows that rely on that specific durable-nonce account for offline-signed/nonce-based transactions). The victim's own `InitializeNonceAccount` instruction fails with `InvalidAccountData` once the state is no longer `Uninitialized`, so the race is winner-take-all, matching the "front-run initialization" bug class exactly.

### Likelihood Explanation
Likelihood is constrained by common tooling: the Solana CLI/SDK helpers typically bundle `CreateAccount` and `InitializeNonceAccount` into a single atomic transaction, closing the race window. The vulnerability is only reachable when the two steps are split into separate transactions (custom integrations, multi-step flows, or programs that create a nonce account and initialize it later). In that scenario, no signature or origin check whatsoever prevents any unprivileged sender from winning the race, so likelihood is non-trivial when the (fairly common) two-step pattern is used, but not universal.

### Recommendation
Add an authorization/signer check to `initialize_nonce_account` analogous to the vote program's `verify_authorized_signer` pattern in `vote_state::initialize_account` — for example, requiring the account itself (or a designated creator/authority passed at `CreateAccount` time) to be a signer of the `InitializeNonceAccount` instruction, so that only the legitimate creator can complete initialization.

### Proof of Concept
1. Alice submits transaction T1 containing only `SystemInstruction::CreateAccount` for a new nonce account `N` (owned by the system program, sized/funded for nonce state), intending to send a follow-up `InitializeNonceAccount(alice_authority)` in transaction T2.
2. Attacker observes T1 (via gossip/RPC before/as it lands) and learns `N`'s public key.
3. Attacker submits transaction T3 = `SystemInstruction::InitializeNonceAccount(attacker_authority)` targeting account `N`, with a higher compute-unit price so it is processed before Alice's T2.
4. `initialize_nonce_account` in `programs/system/src/system_instruction.rs` (lines 163-211) does not check any signer tied to `N`'s creator; it only checks `is_writable`, rent-exemption, and `State::Uninitialized`, all of which are satisfied — the instruction succeeds and sets `nonce_authority = attacker_authority`.
5. When Alice's T2 (`InitializeNonceAccount(alice_authority)`) executes, `account.get_state::<Versions>()?.state()` is now `State::Initialized`, so it returns `Err(InstructionError::InvalidAccountData)` — Alice permanently loses control of the nonce authority for account `N`.

pub(crate) fn initialize_nonce_account(
    account: &mut BorrowedInstructionAccount,
    nonce_authority: &Pubkey,
    rent: &Rent,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    if !account.is_writable() {
        ic_msg!(
            invoke_context,
            "Initialize nonce account: Account {} must be writeable",
            account.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }

    match account.get_state::<Versions>()?.state() {
        State::Uninitialized => {
            let min_balance = rent.minimum_balance(account.get_data().len());
            if account.get_lamports() < min_balance {
                ic_msg!(
                    invoke_context,
                    "Initialize nonce account: insufficient lamports {}, need {}",
                    account.get_lamports(),
                    min_balance
                );
                return Err(InstructionError::InsufficientFunds);
            }
            let durable_nonce =
                DurableNonce::from_blockhash(&invoke_context.environment_config.blockhash);
            let data = nonce::state::Data::new(
                *nonce_authority,
                durable_nonce,
                invoke_context
                    .environment_config
                    .blockhash_lamports_per_signature,
            );
            let state = State::Initialized(data);
            account.set_state(&Versions::new(state))
        }
        State::Initialized(_) => {
            ic_msg!(
                invoke_context,
                "Initialize nonce account: Account {} state is invalid",
                account.get_key()
            );
            Err(InstructionError::InvalidAccountData)
        }
    }
}
