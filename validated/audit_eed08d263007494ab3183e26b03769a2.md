### Title
Unbounded per-call cost in `getVoteAccounts` scales linearly with total vote accounts ever created on-chain - ([File: rpc/src/rpc.rs])

### Summary
`get_vote_accounts` in `rpc/src/rpc.rs` iterates the entire `bank.vote_accounts()` map with no cap, pagination, or minimum-stake filter applied before constructing `RpcVoteAccountInfo` entries. Because vote accounts are permissionlessly creatable and are retained in the bank's `VoteAccounts` cache indefinitely (regardless of stake), an attacker can grow this map without bound and force each single RPC call to do work proportional to the total count.

### Finding Description
`JsonRpcRequestProcessor::get_vote_accounts` (rpc/src/rpc.rs:1155-1246) calls `bank.vote_accounts()` [1](#0-0)  which returns `Arc<VoteAccountsHashMap>` derived from `self.stakes_cache.stakes().vote_accounts()` [2](#0-1) . This map is populated by `StakesCache::check_and_store`, which caches any account owned by the vote program keyed only by ownership/state validity, not by stake amount [3](#0-2) . `VoteAccounts::insert` never evicts zero-stake entries automatically — only explicit removal drops them [4](#0-3) .

`get_vote_accounts` then does a single unbounded `.iter().filter_map(...).partition(...)` over the whole map [5](#0-4) , building a full `RpcVoteAccountInfo` for every entry not excluded by the optional `vote_pubkey` filter. For each entry it also copies up to `MAX_RPC_VOTE_ACCOUNT_INFO_EPOCH_CREDITS_HISTORY` epoch-credit tuples via `epoch_credits_iter().skip(...).collect()` [6](#0-5) . There is no limit on the number of vote accounts processed, no minimum-stake precondition, and no pagination in the RPC method signature (`config: Option<RpcGetVoteAccountsConfig>`) [7](#0-6) , unlike `getProgramAccounts`, which at least has secondary-index/`dataSlice` mitigations elsewhere. The `keep_unstaked_delinquents` filter only removes zero-stake delinquents *after* the full map has already been mapped/partitioned [8](#0-7) , so it doesn't bound the initial allocation/iteration cost.

Vote account creation is a normal, permissionless runtime operation (any funded account can be initialized as a vote account via the vote program), so an attacker can grow the map size V arbitrarily across many slots without triggering any RPC rate limit, then issue a single `getVoteAccounts` call whose CPU/memory cost is O(V).

### Impact Explanation
A single, rate-limit-compliant `getVoteAccounts` call causes the validator's JSON-RPC handling thread to allocate and populate a `Vec<RpcVoteAccountInfo>` (and its serialized JSON response) proportional to V, the cumulative number of never-cleaned-up vote accounts on-chain, with per-entry cost additionally scaled by `MAX_RPC_VOTE_ACCOUNT_INFO_EPOCH_CREDITS_HISTORY`. This is unbounded CPU/memory cost for a single low-rate call, driven entirely by attacker-authored on-chain state rather than by any explicit protocol limit — matching the "unbounded cost for a single low-rate call" bounty category.

### Likelihood Explanation
Feasible and repeatable: creating a vote account requires only funding an account and issuing a vote-program `initialize_account`-type instruction, which is permissionless and not gated by RPC rate limits (it's an on-chain transaction, not an RPC call). The attacker can create V such accounts over time (across many slots, well below `CLUSTER_SLOT_TIME_TARGET / 2` RPC rate), then issue exactly one `getVoteAccounts` call to trigger the O(V) cost. No stake, no leader/validator control, and no operator misconfiguration are required.

### Recommendation
Bound the work done per `getVoteAccounts` call independent of total on-chain vote-account count: e.g., require/apply a minimum-stake or `keep_unstaked_delinquents=false`-equivalent filter *before* building `RpcVoteAccountInfo` entries (short-circuit in the `filter_map` rather than after), add an explicit maximum result size / pagination to `RpcGetVoteAccountsConfig`, and/or cap the number of iterated vote accounts with a hard limit and return an error or truncated response when exceeded.

### Proof of Concept
Rust integration test sketch (extending existing `test_get_vote_accounts` in `rpc/src/rpc.rs`):
```rust
#[test]
fn test_get_vote_accounts_unbounded_cost() {
    let rpc = RpcHandler::start();
    let bank = rpc.working_bank();

    // Create V synthetic zero-stake vote accounts directly in the bank,
    // mirroring rpc.store_vote_account(...) used elsewhere in this file.
    const V: usize = 200_000; // attacker-feasible scale, cheap per-account
    for _ in 0..V {
        let vote_keypair = Keypair::new();
        let vote_state = VoteStateV4::new_with_defaults(
            &vote_keypair.pubkey(),
            &VoteInit {
                node_pubkey: rpc.mint_keypair.pubkey(),
                authorized_voter: vote_keypair.pubkey(),
                authorized_withdrawer: vote_keypair.pubkey(),
                commission: 0,
            },
            &bank.get_sysvar_cache_for_tests().get_clock().unwrap(),
        );
        rpc.store_vote_account(&vote_keypair.pubkey(), vote_state);
    }
    assert_eq!(bank.vote_accounts().len(), V + 1);

    let start = std::time::Instant::now();
    let req = r#"{"jsonrpc":"2.0","id":1,"method":"getVoteAccounts"}"#;
    let _res = rpc.io.handle_request_sync(req, rpc.meta.clone());
    let elapsed = start.elapsed();

    // Expectation for a bounded implementation: elapsed stays under a fixed
    // ceiling regardless of V (e.g. < 50ms). Current implementation instead
    // scales linearly with V, demonstrating unbounded per-call cost.
    assert!(elapsed < std::time::Duration::from_millis(50), "cost scaled with V: {elapsed:?}");
}
```
Expected result on current code: the single call's latency/allocation grows linearly with V, violating the invariant that per-request cost be bounded independent of attacker-authored on-chain data size.

    pub fn insert(
        &mut self,
        pubkey: Pubkey,
        new_vote_account: VoteAccount,
        calculate_stake: impl FnOnce() -> u64,
    ) -> Option<VoteAccount> {
        let vote_accounts = Arc::make_mut(&mut self.vote_accounts);
        match vote_accounts.entry(pubkey) {
            Entry::Occupied(mut entry) => {
                // This is an upsert, we need to update the vote state and move the stake if needed.
                let (stake, old_vote_account) = entry.get_mut();

                if let Some(staked_nodes) = self.staked_nodes.get_mut() {
                    let old_node_pubkey = old_vote_account.node_pubkey();
                    let new_node_pubkey = new_vote_account.node_pubkey();
                    if new_node_pubkey != old_node_pubkey {
                        // The node keys have changed, we move the stake from the old node to the
                        // new one
                        Self::do_sub_node_stake(staked_nodes, *stake, old_node_pubkey);
                        Self::do_add_node_stake(staked_nodes, *stake, *new_node_pubkey);
                    }
                }

                // Update the vote state
                Some(mem::replace(old_vote_account, new_vote_account))
            }
            Entry::Vacant(entry) => {
                // This is a new vote account. Use the caller-provided stake for the initial
                // cache entry.
                let (stake, vote_account) = entry.insert((calculate_stake(), new_vote_account));
                if let Some(staked_nodes) = self.staked_nodes.get_mut() {
                    Self::do_add_node_stake(staked_nodes, *stake, *vote_account.node_pubkey());
                }
                None
            }
        }
    }

    pub fn remove(&mut self, pubkey: &Pubkey) -> Option<(u64, VoteAccount)> {
        let vote_accounts = Arc::make_mut(&mut self.vote_accounts);
        let entry = vote_accounts.remove(pubkey);
        if let Some((stake, ref vote_account)) = entry {
            self.sub_node_stake(stake, vote_account);
        }
        entry
    }
