### Title
Freshness-cutoff bypass in `handle_block_pre_commit` lets a signer sign a conflicting/non-canonical sibling block once the earlier signature goes "stale" - ([File: stacks-signer/src/v0/signer.rs])

### Summary
`Signer::handle_block_pre_commit` in [1](#0-0)  only asks the stacks-node whether an earlier signed conflicting block is still canonical/live (`conflict_still_blocks`) when that conflict is still "fresh" (`conflict.last_endorsed > freshness_cutoff`). The freshness window is `tenure_last_block_proposal_timeout`, which defaults to 30 seconds. Once a signed block's endorsement timestamp is older than that window, its cross-tenure conflict protection disappears unconditionally — the node is never consulted again — and the signer proceeds to sign a new, conflicting sibling block at the same (or higher) chain height in a different tenure, as long as that new block is not in its own tenure or the block's declared parent tenure.

### Finding Description
The double-sign ("equivocation") guard is documented and implemented in two layers:
1. **Chainstate checks** (`check_block_against_signer_db_state`) only validate (a) a tenure-change block's declared parent tenure via `check_tenure_change_confirms_parent`, and (b) that a block is the highest in its *own* tenure via `check_latest_block_in_tenure`, see [2](#0-1)  and [3](#0-2) . Neither check inspects a *third*, unrelated tenure that happens to have a sibling block at the same chain height — this blind spot is explicitly acknowledged in the repository's own documentation: "a signed sibling at the same height in a third tenure is invisible to it" [4](#0-3) .

2. **The pre-commit conflict guard** in `handle_block_pre_commit` is supposed to be the backstop for that blind spot, by querying `get_signed_conflicts` (any signed block at `stacks_height >= h`, in *any* tenure) and refusing to sign if a conflict is fresh and `conflict_still_blocks` (a node-derived, still-live check) [5](#0-4) . But this guard is gated by `conflict.last_endorsed > freshness_cutoff`, where `freshness_cutoff = now - tenure_last_block_proposal_timeout` (default 30s, see `sample/conf/signer/mainnet-signer-conf.toml` lines 137-142). `last_endorsed` is simply `MAX(signed_self, signed_group)` — the local timestamp of when *we* signed or observed group signing, not any measure of whether the block is still canonical [6](#0-5) .

Once a conflict is stale (i.e. signed more than ~30 seconds ago — true for essentially every prior tenure's blocks, since tenures normally last minutes), the code falls through to a second check that only handles conflicts *in the proposed block's own tenure* (`conflict.consensus_hash == block_info.block.header.consensus_hash`) [7](#0-6) . A stale conflict belonging to any *other* tenure is not checked against the node at all and simply falls through to being signed: `"...but none of those conflicts still blocks it. Signing the replacement."` [8](#0-7) .

The result: an adversarial/opportunistic block proposer (single "one-slot" miner for a sortition) can wait past `tenure_last_block_proposal_timeout` after a competing tenure last signed a block, then present a rival tenure-start block at the same chain height. Even though `conflict_still_blocks` would have correctly identified the earlier block as still canonical (e.g. globally accepted and still the node's tip), that node round-trip is never made because the staleness check short-circuits it. The signer set can then sign a genuinely conflicting/non-canonical block, producing two independently signed blocks at the same absolute chain height on different forks.

### Impact Explanation
This directly matches the Critical impact category: "a signer signing an invalid, non-canonical, or conflicting block." Signing two conflicting blocks at the same chain height (an equivocation) is exactly the safety property the pre-commit conflict guard exists to prevent, per the code's own comments ("the guard exists to stop us endorsing two blocks that could both end up in the chain," [9](#0-8) ). Because the default timeout (30s) is far shorter than typical tenure duration, this protection is effectively disabled for nearly every cross-tenure conflict in normal operation, not just under contrived configurations.

### Likelihood Explanation
The only capability required is that a block proposer (miner) presents a rival tenure-start block after the freshness window elapses relative to when the earlier conflicting block was signed — well within a single miner's control given normal tenure timing, and requiring no majority of signers, no key compromise, and no special node access. The staleness gap is deterministic and reachable through the ordinary block-proposal/pre-commit path, not a corner-case race.

### Recommendation
Do not let staleness alone drop the node-liveness check for conflicts outside the block's own tenure. `conflict_still_blocks` should be consulted for stale, cross-tenure conflicts too (or the fallback branch at lines 1432-1457 should be extended to cover all conflicting consensus hashes, not just the proposed block's own tenure), so that a genuinely still-canonical block can never be silently replaced merely because our local endorsement timestamp aged past `tenure_last_block_proposal_timeout`.

### Proof of Concept
1. Signer signs block `X` at `chain_length = H` in tenure `A` (tracked via `signed_self`/`signed_group` in `signerdb`).
2. Wait longer than `tenure_last_block_proposal_timeout` (default 30s) — trivial given normal tenure durations of minutes.
3. A different miner proposes block `Y` at `chain_length = H` in tenure `B`, where `B` is neither `A`'s child nor references `A` as its tenure-change parent (e.g. `B` diverges from an earlier common ancestor with an equal-length chain).
4. `B`'s pre-commit threshold is reached; `handle_block_pre_commit` runs `get_signed_conflicts(H, hash(Y))`, finds `X`, but `X.last_endorsed <= freshness_cutoff`, so the `conflict_still_blocks` node check at [5](#0-4)  is skipped.
5. The own-tenure fallback at [7](#0-6)  does not match (`X`'s consensus hash != `Y`'s), so no node query happens for `X` at all.
6. The signer marks `Y` locally accepted and signs it, even though `X` may still be the canonical, globally accepted tip — producing two independently valid signer signatures on conflicting forks at the same chain height.

    pub fn check_latest_block_in_tenure(
        tenure_id: &ConsensusHash,
        block: &NakamotoBlock,
        signer_db: &mut SignerDb,
        client: &StacksClient,
        tenure_last_block_proposal_timeout: Duration,
        reorg_attempts_activity_timeout: Duration,
    ) -> Result<bool, ClientError> {
        let last_block_info = SortitionData::get_tenure_last_block_info(
            tenure_id,
            signer_db,
            tenure_last_block_proposal_timeout,
        )?;

        if let Some(info) = last_block_info {
            // N.B. this block might not be the last globally accepted block across the network;
            // it's just the highest one in this tenure that we know about.  If this given block is
            // no higher than it, then it's definitely no higher than the last globally accepted
            // block across the network, so we can do an early rejection here.
            if block.header.chain_length <= info.block.header.chain_length {
                warn!(
                    "Miner's block proposal does not confirm as many blocks as we expect";
                    "proposed_block_consensus_hash" => %block.header.consensus_hash,
                    "signer_signature_hash" => %block.header.signer_signature_hash(),
                    "proposed_chain_length" => block.header.chain_length,
                    "expected_at_least" => info.block.header.chain_length + 1,
                );
                if info.signed_group.is_none_or(|signed_time| {
                    signed_time + reorg_attempts_activity_timeout.as_secs() > get_epoch_time_secs()
                }) {
                    // Note if there is no signed_group time, this is a locally accepted block (i.e. tenure_last_block_proposal_timeout has not been exceeded).
                    // Treat any attempt to reorg a locally accepted block as valid miner activity.
                    // If the call returns a globally accepted block, check its globally accepted time against a quarter of the block_proposal_timeout
                    // to give the miner some extra buffer time to wait for its chain tip to advance
                    // The miner may just be slow, so count this invalid block proposal towards valid miner activity.
                    if let Err(e) = signer_db.update_last_activity_time(
                        &block.header.consensus_hash,
                        get_epoch_time_secs(),
                    ) {
                        warn!("Failed to update last activity time: {e}");
                    }
                }
                return Ok(false);
            }
        }

    pub fn get_signed_conflicts(
        &self,
        height: u64,
        excluded_signer_signature_hash: &Sha512Trunc256Sum,
    ) -> Result<Vec<SignedConflictInfo>, DBError> {
        let query = "SELECT b.consensus_hash, b.signer_signature_hash, b.stacks_height, b.state,
                MAX(COALESCE(b.signed_self, 0), COALESCE(b.signed_group, 0)) AS last_endorsed,
                st.superseded_by_consensus_hash, st.superseded_by_burn_block_hash
            FROM blocks b
            LEFT JOIN superseded_tenures st ON st.consensus_hash = b.consensus_hash
            WHERE (b.signed_self IS NOT NULL OR b.signed_group IS NOT NULL)
                AND b.stacks_height >= ?1
                AND b.signer_signature_hash != ?2
            ORDER BY b.stacks_height DESC";
        let args = params![
            u64_to_sql(height)?,
            excluded_signer_signature_hash.to_string(),
        ];
        query_rows(&self.db, query, args)
    }
