## Title
Under-signed `BlockRejection` allows any signer to relabel another signer's rejection reason and forge rejection-tallied fields — ([File: libsigner/src/v0/messages.rs])

### Summary
`BlockRejection::hash()` only binds `signer_signature_hash` and `chain_id` into the signature; `reason`, `reason_code`, and `response_data` (which carries `reject_reason`, `failed_txid`, `tenure_extend_timestamp`, `tenure_extend_read_count_timestamp`) are transmitted but never covered by the signature. Because these unsigned fields drive weight tallies that gate safety- and liveness-relevant decisions (marking a miner invalid on `ReorgNotAllowed`, banning/pausing txids), any party that has observed one genuine rejection signature from signer X for block B can re-emit a message still attributed to X but carrying attacker-chosen reason data.

### Finding Description
`BlockRejection::hash()` computes the signed digest as: [1](#0-0) 


`sign()`, `verify()`, and `recover_public_key()` all operate solely on this `hash()` value: [2](#0-1) 

The struct itself carries much more than `signer_signature_hash`/`chain_id`: [3](#0-2) 

`reason`, `reason_code`, and the entire `response_data` (including `reject_reason`, `failed_txid`, and the two tenure-extend timestamps) are *not* part of what is signed. Consequently, once signer X has broadcast one genuine `BlockRejection` for block B (a normal, unavoidable event — every rejection is broadcast in cleartext over StackerDB, which every node and signer reads), any observer possesses a signature σ that is valid for **any** combination of `reason`/`reason_code`/`response_data` paired with that same `signer_signature_hash` and `chain_id`. A forged message `(signer_signature_hash=B, chain_id=X's chain_id, reason_code=<attacker choice>, response_data=<attacker choice>, signature=σ)` still passes `verify()`/`recover_public_key()` and is indistinguishable from an authentic rejection by X for that reason.

The consuming code trusts these unsigned fields for safety- and liveness-relevant tallying on both the signer side and the node side:

- Signer-side rejection handling recovers the public key purely from the (under-signed) `hash()` and checks only that it belongs to the signer set — there is no re-derivation of `reason_code`/`response_data` from anything the signature actually covers: [4](#0-3) 

- The stored/tallied `reject_reason` (derived from the forgeable `response_data.reject_reason`) directly feeds the "mark miner invalid" decision once 30% weight is attributed to `ReorgNotAllowed`: [5](#0-4) 

- On the node side, `stackerdb_listener.rs` verifies only that the recovered pubkey from the embedded (under-signed) signature matches the slot owner, then trusts `rejected_data.reason_code` / `response_data.failed_txid` to accumulate per-txid rejection weight, which can lead to `temporarily_excluded_txids`/`permanently_excluded_txids`: [6](#0-5) [7](#0-6) 

Because none of `reason`, `reason_code`, or `response_data` is part of the digest that `sign`/`verify`/`recover_public_key` operate on, this is a genuine analog of the bestzip bug class: data that is trusted and acted upon (here, the rejection reason/txid/timestamp fields) is not sanitized/bound before being consumed by a downstream, security-relevant operation (the signature check only authenticates a narrower payload than what is actually processed).

### Impact Explanation
This breaks the "aggregated-weight vs. verified-accepts" equality that the spec relies on: the 30%-weight `ReorgNotAllowed` tally and the per-txid `failed_txid`/`problematic_weight` tallies are supposed to reflect what each signer actually asserted, authenticated by their signature. Because the signature doesn't bind the reason/txid/timestamp fields, a single relayed/observed genuine rejection from signer X can be repackaged with a different reason category or fabricated `failed_txid` and still be accepted as X's authentic assertion by any receiver that (like the v0 signer's `handle_block_rejection`) checks only signer-address validity, not slot provenance nor a signature over the full content. This can (a) contribute forged `ReorgNotAllowed` weight toward marking the current miner invalid when X never intended that, and (b) contribute forged per-txid rejection/problematic weight on the node side toward `temporarily_excluded_txids`/`permanently_excluded_txids`, both of which are "signer signing an invalid, non-canonical, or conflicting block" / "rejection recounted as acceptance"-class safety/liveness deviations gated by weight tallies that no longer reflect verified signer intent.

### Likelihood Explanation
Requires only a single, otherwise-ordinary event that already happens regularly in the network: signer X rejecting some proposal for block B (any reason). All such rejections are broadcast in the clear via StackerDB, which every full node and every other signer reads by design, so obtaining σ requires no special access — no majority, no other signer's key, and no compromise of auth_token or local access to X. The only privileged step is writing a chunk to the attacker's own slot, and the attacker (any single participating signer) already legitimately holds their own slot-writing key — a one-slot miner/gossip actor can trigger this end-to-end without needing X's key at all, satisfying the "one-slot miner (plus gossip)" scope.

### Recommendation
Bind the full semantic content of the rejection into the signed digest. `BlockRejection::hash()` should incorporate `reason_code` (or a canonical serialization of `response_data`, including `reject_reason`, `failed_txid`, and the tenure-extend timestamps) in addition to `signer_signature_hash` and `chain_id`, e.g. by hashing a structured tuple/buffer that includes a serialization of `RejectCode`/`BlockResponseData` alongside the block hash before computing `structured_data_message_hash`. Additionally, on the signer side, mirror the node-side defense of cross-checking the message's recovered public key against the StackerDB slot the chunk was received on (not solely `is_valid_signer`), so a forged-but-differently-labeled rejection cannot be smuggled in through a slot the true signer doesn't own.

### Proof of Concept
1. Signer X legitimately rejects block B for `ValidationFailed(BadTransaction)`, producing `BlockRejection { signer_signature_hash: B, chain_id: C, reason_code: ValidationFailed(BadTransaction), response_data: { reject_reason: ValidationFailed(BadTransaction), failed_txid: Some(T0), .. }, signature: σ }` and broadcasts it over StackerDB (visible to all).
2. Attacker (any participating signer/relay) observes this message, extracts `σ`, `B`, `C`.
3. Attacker constructs `BlockRejection { signer_signature_hash: B, chain_id: C, reason_code: ValidationFailed(ProblematicTransaction), response_data: { reject_reason: ReorgNotAllowed, failed_txid: Some(T_attacker), tenure_extend_timestamp: <attacker value> }, signature: σ }` — reusing σ unmodified.
4. `BlockRejection::verify()`/`recover_public_key()` ( [8](#0-7) ) succeed and recover X's pubkey, because `hash()` never included the changed fields.
5. Other signers' `handle_block_rejection` ( [4](#0-3) ) accept it as X's authentic assertion of `ReorgNotAllowed` with `failed_txid=T_attacker`, feeding forged weight into the `ReorgNotAllowed` invalidation tally ( [5](#0-4) ) and, on the node side, into `permanently_excluded_txids`/`temporarily_excluded_txids` accounting ( [9](#0-8) ).

```rust
    /// Sign the block rejection and set the internal signature field
    fn sign(&mut self, private_key: &StacksPrivateKey) -> Result<(), String> {
        let signature_hash = self.hash();
        self.signature = private_key.sign(signature_hash.as_bytes())?;
        Ok(())
    }

    /// Verify the rejection's signature against the provided signer public key
    pub fn verify(&self, public_key: &StacksPublicKey) -> Result<bool, String> {
        if self.signature == MessageSignature::empty() {
            return Ok(false);
        }
        let signature_hash = self.hash();
        public_key
            .verify(&signature_hash.0, &self.signature)
            .map_err(|e| e.to_string())
    }

    /// Recover the public key from the rejection signature
    pub fn recover_public_key(&self) -> Result<StacksPublicKey, &'static str> {
        if self.signature == MessageSignature::empty() {
            return Err("No signature to recover public key from");
        }
        let signature_hash = self.hash();
        StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            signature_hash.as_bytes(),
            &self.signature,
        )
    }
```

```rust
    fn handle_block_rejection(
        &mut self,
        rejection: &BlockRejection,
        sortition_state: &mut Option<SortitionsView>,
    ) {
        debug!("{self}: Received a block-reject signature: {rejection:?}");

        let block_hash = &rejection.signer_signature_hash;
        let signature = &rejection.signature;

        // recover public key
        let Ok(public_key) = rejection.recover_public_key() else {
            debug!("{self}: Received block rejection with an unrecovarable signature. Will not store.";
               "signer_signature_hash" => %block_hash,
               "signature" => %signature

            return;
        };

        // authenticate the signature -- it must be signed by one of the stacking set
        let signer_address = StacksAddress::p2pkh(self.mainnet, &public_key);
        if !self.is_valid_signer(&signer_address) {
            debug!("{self}: Received block rejection with an invalid signature. Will not store.";
                "signer_public_key" => ?public_key,
                "signer_address" => %signer_address,
                "signer_signature_hash" => %block_hash,
                "signature" => %signature
            );
            return;
        }

        let Some(mut block_info) = self.block_lookup_by_reward_cycle(block_hash) else {
            if let Err(e) = self.signer_db.add_pending_block_rejection_response(
                block_hash,
                &signer_address,
                (&rejection.response_data.reject_reason).into(),
            ) {
                warn!("{self}: Failed to add pending block rejection response: {e:?}");
            }
            return;
        };

        info!("{self}: Received block rejection";
            "signer_pubkey" => public_key.to_hex(),
            "signer_signature_hash" => %block_hash,
            "consensus_hash" => %block_info.block.header.consensus_hash,
            "block_height" => block_info.block.header.chain_length,
            "reject_reason" => ?rejection.response_data.reject_reason,
        );

        self.store_and_process_block_rejection(
            sortition_state,
            &mut block_info,
            &signer_address,
```
