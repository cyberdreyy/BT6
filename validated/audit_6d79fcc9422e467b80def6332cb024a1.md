### Title
Stale confirmations from removed multisig members are not purged from pending requests, allowing execution below the live-member confirmation threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` in `multisig2/src/lib.rs` only deletes requests that were *originally proposed* by the member being removed. It never scans the `confirmations` map to strip that member's already-recorded confirmation from *other* pending requests they had previously confirmed but did not propose. Once the member is removed, their stale confirmation entry remains counted toward the `num_confirmations` threshold check in `confirm()`, letting a request execute with fewer live, currently-trusted members actually approving it than `num_confirmations` requires.

### Finding Description
`confirm()` decides whether to execute a request purely by counting entries in the `confirmations` `HashSet` for that `request_id`: [1](#0-0) 

`delete_member()` removes the member from `self.members` and deletes only the requests where `r.member == member` (i.e., requests *proposed* by that member). It calls `self.confirmations.remove(&request_id)` solely for those self-proposed requests — it never iterates other requests' confirmation sets to strip the departing member's public key/account entry: [2](#0-1) 

The binding that should hold is:
`confirmations.len()` for a request == number of *currently live* members who have actively approved it.

After a `DeleteMember` request executes, this equality breaks for any other pending request that the removed member had previously confirmed: the confirmation count still includes the now-removed member, even though that member no longer belongs to `self.members` and cannot legitimately consent to anything.

### Impact Explanation
If a request proposed by member B is sitting with one confirmation from member A (`confirmations = {A}`), and A is subsequently removed via a `DeleteMember` request (which is itself validated only against `self.members.len() - 1 >= self.num_confirmations`, a check about the size of the remaining member set, not about existing confirmation sets), request B's confirmation set still contains A. A single additional live confirmation from member C then satisfies `confirmations.len() + 1 >= num_confirmations`, and the request (which can be an arbitrary `MultiSigRequestAction`, including `Transfer`, `AddKey`, or `FunctionCall`) executes — even though only one currently-trusted member (C) actually approved it, not the `num_confirmations` required. This is exactly the "multisig request executed below threshold" scenario called out as Critical impact: NEAR can be transferred, keys added, or contract calls executed with fewer genuine approvals than the security model requires.

### Likelihood Explanation
This requires a specific but realistic ordering of operations that any set of members could hit unintentionally or be maneuvered into: a request gets partially confirmed, then the confirming member is later removed for unrelated reasons (rotation, compromise response, etc.), and the stale request is left dangling with the phantom confirmation still counted. No privileged bypass is needed beyond normal multisig operation sequencing — no code change, no owner action outside the documented API, and no reliance on any other party's mistake beyond ordinary membership rotation.

### Recommendation
In `delete_member` (and the analogous `delete_key`/`remove_request` paths in `multisig/src/lib.rs` if the same pattern exists there), iterate all entries in `self.confirmations` and remove the departing member's identifier from every confirmation set, not just the sets belonging to requests the member itself proposed. Alternatively, validate at `confirm()`/execution time that every public key/account recorded in a request's confirmation set is still a current member before counting it toward `num_confirmations`.

### Proof of Concept
1. Initialize `MultiSigContract::new(members = [A, B, C], num_confirmations = 2)`.
2. B calls `add_request` for a `Transfer` action (or any other sensitive action) — request `id=1`, `confirmations = {}`.
3. A calls `confirm(1)` → `confirmations = {A}` (below threshold, not yet executed) — see the increment logic at [3](#0-2) .
4. Separately, a `DeleteMember { member: A }` request is proposed and confirmed by B and C, executing `delete_member` which removes A from `self.members` but does **not** touch `confirmations[1]` — see [4](#0-3) .
5. Now `self.members = {B, C}`, `num_confirmations = 2`, but `confirmations[1] = {A}` still contains the removed member.
6. C calls `confirm(1)` → `confirmations.len() + 1 == 2 >= num_confirmations(2)` → request executes, even though only C (a single live member) actually approved it; A's stale, now-illegitimate confirmation counted as the second approval.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
