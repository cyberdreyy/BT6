## Title
Front-running `InitializeNonceAccount` allows an attacker to seize nonce authority and drain the account's lamports - (File: `programs/system/src/system_instruction.rs`)

### Summary
`InitializeNonceAccount` is the Agave analog of `UniswapV3Pool.initialize`: it is a state-setting instruction that can be invoked on any already-created (but still `Uninitialized`) System-program account, and it performs **no signature check on the account being initialized or on any owner/creator relationship** — only a writability check is enforced. This mirrors the reported bug class exactly: an unprivileged, unauthenticated "first write wins" initializer whose caller-supplied parameter (the nonce authority) becomes permanently trusted state.

### Finding Description
`initialize_nonce_account` only requires the target account to be writable and to currently be `State::Uninitialized`; it does not require the account itself, its creator, or any privileged party to sign the transaction: [1](#0-0) 

The `nonce_authority` value stored as the account's future controlling authority is taken directly from instruction data supplied by whoever submits the `InitializeNonceAccount` instruction: [2](#0-1) 

Because Solana's nonce-account lifecycle is normally created as two instructions — `SystemInstruction::CreateAccount` (which requires the new account's own signature, since it doesn't exist yet) followed by `SystemInstruction::InitializeNonceAccount` (which does not require any signature) — a legitimate user who submits these as **separate transactions**, or whose second transaction sits in the mempool, exposes a race window. An attacker who observes the pending/first `CreateAccount` transaction (or an already-created-but-not-yet-initialized durable nonce account address) can front-run and submit their own `InitializeNonceAccount` instruction naming themselves as `nonce_authority` before the legitimate owner's initialize instruction lands. Once `State::Uninitialized` transitions to `State::Initialized`, any subsequent initialize call is rejected (`InstructionError::InvalidAccountData`) — permanently locking in the attacker's authority: [3](#0-2) 

From that point on, the legitimate depositor's lamports funding rent-exemption of the nonce account are governed by `WithdrawNonceAccount`, which checks the signer against `data.authority` — now the attacker's key — allowing the attacker to withdraw the account's full balance: [4](#0-3) 

This is structurally identical to the reported Uniswap issue: a state-defining `initialize` call with no access control that can be front-run to poison state that legitimate funds are then deposited/exposed against.

### Impact Explanation
If a wallet, exchange, or program creates a nonce account and initializes it in a separate follow-up transaction (rather than atomically as `system_instruction::create_nonce_account` bundles it), an attacker monitoring the mempool/QUIC ingest can front-run `InitializeNonceAccount`, hijack the `authority` field, and later drain all lamports funding that account via `WithdrawNonceAccount`. This is a concrete unauthorized fund mutation reachable from an ordinary user's transaction with no special privileges required.

### Likelihood Explanation
Exploitability depends on the initializer being sent as a standalone (non-atomic) transaction distinct from `CreateAccount` — which the SDK's `create_nonce_account` helper avoids by bundling both instructions atomically and signing with the new account key. However, any client, script, or contract that separates account creation and initialization into different transactions (e.g., pre-funding a derived/known nonce account address, or multi-step tooling) reintroduces this exact race window, since the processor itself enforces no signer requirement in `initialize_nonce_account`.

### Recommendation
- Require the account being initialized (or a designated creator/authority) to be a signer in `initialize_nonce_account`, closing the "anyone can initialize" gap.
- Alternatively, document and strongly enforce (at the SDK/CLI level, already partially done via `create_nonce_account`) that `CreateAccount` and `InitializeNonceAccount` must always be submitted atomically in the same transaction, and add defensive checks/warnings against separate submission.
- Consider re-validating the authority against the original account creator recorded at account-creation time rather than trusting instruction-data-supplied `nonce_authority` unconditionally.

### Proof of Concept
1. Alice submits `SystemInstruction::CreateAccount` to create nonce account `N` (signed by `N`'s keypair), intending to submit `InitializeNonceAccount(alice_authority)` in a follow-up transaction.
2. Eve observes `N` on-chain in `State::Uninitialized` (e.g., via RPC polling or mempool observation) before Alice's initialize transaction lands.
3. Eve submits `SystemInstruction::InitializeNonceAccount(eve_pubkey)` targeting account `N`. Per `initialize_nonce_account` [5](#0-4) , this succeeds with no signature from `N` or Alice required.
4. Alice's later `InitializeNonceAccount(alice_authority)` now fails with `InstructionError::InvalidAccountData` since state is already `Initialized` [3](#0-2) .
5. Eve calls `WithdrawNonceAccount` signed as `eve_pubkey` (the stored `data.authority`) and drains the lamports Alice funded into `N` for rent-exemption [4](#0-3) .

    account: &mut BorrowedInstructionAccount,
    nonce_authority: &Pubkey,
    rent: &Rent,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    if !account.is_writable() {
        ic_msg!(
            invoke_context,
            "Initialize nonce account: Account {} must be writeable",
            account.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }

    match account.get_state::<Versions>()?.state() {
        State::Uninitialized => {
            let min_balance = rent.minimum_balance(account.get_data().len());
            if account.get_lamports() < min_balance {
                ic_msg!(
                    invoke_context,
                    "Initialize nonce account: insufficient lamports {}, need {}",
                    account.get_lamports(),
                    min_balance
                );
                return Err(InstructionError::InsufficientFunds);

            let durable_nonce =
                DurableNonce::from_blockhash(&invoke_context.environment_config.blockhash);

                *nonce_authority,
                durable_nonce,
                invoke_context
                    .environment_config
                    .blockhash_lamports_per_signature,
            );
            let state = State::Initialized(data);
            account.set_state(&Versions::new(state))
        }
