### Title
Loss-adjusted withdraw receipt escapes haircut when a later request overwrites `lastWithdrawRequest`, letting the user claim the haircutted amount at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault._claimLossAdjustedWithdrawRequest` derives the epoch to haircut solely from `lastWithdrawRequest[_user]`, which only stores the *most recent* request epoch. A user whose receipt was haircut via `stopEpochWithDuration`/`collectWithdrawFunds` can make a new `requestWithdraw` in a later epoch; the loss-adjusted claim path then reads the wrong epoch (price 0), returns early without clearing the loss-epoch receipt, and `_claimFundedWithdrawRequest` pays the full `withdrawsRequests[_user]` — including the haircutted receipt — at par. Like the Apache `r:wsread()` bug that returns a length pointing past the allocated buffer, the vault "reads" a claim amount beyond what was actually funded for that receipt.

### Finding Description
When a loss is realized, `collectWithdrawFunds` receives `_amount < pendingBasis`, zeroes `pendingWithdraws`, and stores `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis`. The strategy only holds `_amount` against total receipts of `pendingBasis`. Each user's haircutted receipt must later be claimed through `_claimLossAdjustedWithdrawRequest`, which pays `claimBasis * lossRecoveryPrice / RECOVERY_FULL` and clears the epoch's accounting via `_clearWithdrawClaimForEpoch`.

The lookup key is `lossEpoch = lastWithdrawRequest[_user]` (`IdleCreditVault.sol:790`). `lastWithdrawRequest` is overwritten on every `requestWithdraw` (`IdleCreditVault.sol:282`). If the user makes a second request in a subsequent epoch `E+1`:

1. `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[E+1] == 0` and returns 0 without touching the epoch-`E` receipt.
2. Once `epochNumber > E+1`, `_claimFundedWithdrawRequest`'s epoch gate passes and it pays `amount = withdrawsRequests[_user] + apr0 amounts` at par via `_transferFundedClaim`. `withdrawsRequests[_user]` still contains the never-cleared epoch-`E` receipt.
3. `_burn(_user, normalAmount + ...)` burns exactly the minted receipt tokens, so no revert occurs.

The analogous cross-epoch confusions are handled elsewhere — per-epoch mappings `withdrawsRequestsByEpoch`, `instantWithdrawsRequestsByEpoch`, `apr0RateByEpoch`, `defaultRecoveryEpoch` exist precisely to isolate epochs — but the loss-adjusted path alone keys on the mutable `lastWithdrawRequest` marker instead of searching/storing which epochs carry a `lossRecoveryPriceByEpoch`.

### Impact Explanation
The user recovers `claimBasis_E * (1 - lossRecoveryPrice)/RECOVERY_FULL` more than entitled. Because the strategy was only funded `lossRecoveryPrice`-proportional underlyings for epoch `E` receipts, the excess is paid from funds belonging to other funded claimants or, post-default, is only blocked by the `defaultRecoveryReserve` guard in `_transferFundedClaim`. Result: direct theft / insolvency of the withdraw-claim pool, up to the attacker's haircutted receipt size times the haircut. An attacker can scale this by sizing the epoch-`E` request (e.g., full tranche balance) and forcing/awaiting a `stopEpochWithDuration` loss — even a 1 wei loss triggers `lossRecoveryPrice < RECOVERY_FULL`, but more importantly any large loss epoch makes the par claim steal the difference.

### Likelihood Explanation
Requirements: an epoch ends via `stopEpochWithDuration` with `_lossAmount > 0` while the attacker has a pending receipt (normal epoch-loss flow driven by honest borrower/manager, not attacker-controlled), then the attacker submits one additional `requestWithdraw` in a later epoch and waits one more epoch to claim. No privileged collusion needed; the attacker is an ordinary KYC'd tranche holder. The loss is bounded by the attacker's receipt size and the haircut magnitude.

### Recommendation
Iterate or record which epochs carry `lossRecoveryPriceByEpoch` instead of keying solely on `lastWithdrawRequest`; e.g., store a per-user list/bitmap of request epochs, or check `withdrawsRequestsByEpoch[_user][epoch] != 0` across epochs with a nonzero loss price, or prevent new `requestWithdraw` while an unclaimed loss-adjusted receipt exists. At minimum, `_claimLossAdjustedWithdrawRequest` should examine all epochs in `withdrawsRequestsByEpoch` where `lossRecoveryPriceByEpoch[epoch] != 0`, not only `lastWithdrawRequest`.

### Proof of Concept
```solidity
// Foundry fork test sketch (mirroring test/foundry/IdleCreditVault.t.sol helpers)
function testLossHaircutBypassedByLaterRequest() external {
    uint256 amount = 10_000 * ONE_SCALE;
    uint256 mintedAA = idleCDO.depositAA(amount);
    _transferBurnedTrancheTokens(address(this), true);

    // Epoch E: request full withdraw -> receipt R
    uint256 receipt = cdoEpoch.requestWithdraw(mintedAA, address(AAtranche));
    uint256 epochE = strategy.epochNumber();

    _startEpochAndCheckPrices(0);
    vm.warp(cdoEpoch.epochEndDate() + 1);

    // Borrower realizes a loss; stopEpochWithDuration funds < pendingBasis
    uint256 pending = strategy.pendingWithdraws();
    uint256 funded = pending / 2; // 50% recovery price
    deal(defaultUnderlying, borrower, funded + cdoEpoch.expectedEpochInterest());
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(/*_lossAmount>0*/ LOSS, /*interest*/ 0);
    // collectWithdrawFunds(funded) internally sets lossRecoveryPriceByEpoch[epochE]
    assertGt(strategy.lossRecoveryPriceByEpoch(epochE), 0);

    // Epoch E+1: deposit again (or keep residual tranche) and request a small withdraw
    uint256 mintedAA2 = idleCDO.depositAA(1_000 * ONE_SCALE);
    _transferBurnedTrancheTokens(address(this), true);
    cdoEpoch.requestWithdraw(mintedAA2, address(AAtranche));
    // lastWithdrawRequest[this] == epochE+1 now; lossEpoch lookup misses epochE

    _startEpochAndCheckPrices(1);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, strategy.pendingWithdraws() + cdoEpoch.expectedEpochInterest());
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    // BUG: paid `receipt` at par instead of receipt * lossRecoveryPrice / 1e18
    assertGt(underlying.balanceOf(address(this)) - balPre,
             receipt * strategy.lossRecoveryPriceByEpoch(epochE) / 1e18 + 1);
}
```

Note: verification was limited — I could not confirm the exact ordering between `epochNumber` increment and `collectWithdrawFunds` within `stopEpochWithDuration` in `IdleCDOEpochVariant.sol`, but the described flaw (single-slot `lastWithdrawRequest` used as the only loss-epoch key while per-epoch receipt data persists in `withdrawsRequestsByEpoch`) holds under either ordering.
