### Title
EI authentication bypasses "int job ID" restriction in PipelineRunsController.Create via SessionUserKey conflation - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` decides whether to allow running a job by integer ID solely via `auth.GetAuthenticatedUser(c)` returning `ok==true`, but `AuthenticateExternalInitiator` also sets `SessionUserKey` (with `UserRoleRun`) at [1](#0-0) , making `isUser` true for EI-authenticated requests as well. This directly contradicts the code comment "only users are allowed to run jobs using int IDs - EIs not allowed" at [2](#0-1) , letting an EI-only credential holder invoke `RunJobV2` with an integer job ID.

### Finding Description
The route `POST /v2/jobs/:ID/runs` is registered in the `userOrEI` group with `auth.AuthenticateExternalInitiator`, `auth.AuthenticateByToken`, and `auth.AuthenticateBySession` as alternative auth methods, wrapped by `auth.RequiresRunRole`: [3](#0-2) . `AuthenticateExternalInitiator` authenticates purely via EI access key/secret headers and then sets `c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})` — an entirely synthetic user object, not a real chainlink user: [4](#0-3) . `RequiresRunRole` only checks `user.Role != UserRoleView`, so this synthetic run-role user passes: [5](#0-4) .

Inside `Create`, the code does `_, isUser := auth.GetAuthenticatedUser(c)` and treats `isUser == true` as proof of "real user" to gate integer-ID job execution: [6](#0-5) . Since `GetAuthenticatedUser` only checks presence of `SessionUserKey` and type-asserts to `*clsessions.User` ( [7](#0-6) ), and EI auth sets exactly that key with that type, `isUser` is `true` for EI requests too. The intended distinction (users vs. EIs) can only be reliably made by checking `auth.GetAuthenticatedExternalInitiator(c)` for absence, which the function never does.

Attack flow: attacker holds only valid EI access key/secret (no user session, no user API token). They send `POST /v2/jobs/<int-job-id>/runs`. `AuthenticateExternalInitiator` succeeds, sets both `SessionExternalInitiatorKey` and `SessionUserKey`. `RequiresRunRole` passes because the synthetic user's role is `UserRoleRun`. In `Create`, `isUser` is `true`, `idStr` parses as int32, and `prc.App.RunJobV2(ctx, jobID, nil)` executes directly — bypassing the documented "EIs not allowed" restriction for integer job IDs.

### Impact Explanation
This is an authorization-bypass allowing an EI credential holder (typically scoped to trigger specific webhook jobs referenced by their configured external initiator, not arbitrary integer job IDs) to run **any** job in the node by numeric ID, including jobs unrelated to that EI, potentially triggering unauthorized on-chain transactions, fund movement, or unintended job side effects. This matches the "unauthorized job run" impact class in the Chainlink bounty scope. It is a role/authorization bypass rather than a full node compromise, but it grants an attacker with a lesser-privileged credential type action equivalent to a "run"-role user across the whole job set by integer ID.

### Likelihood Explanation
Precondition is simply possession of valid EI access key + secret (which the codebase's own comment implies should be a weaker/narrower trust boundary than a session/API-token user). No additional exploitation steps needed — a single crafted HTTP request. Fully repeatable, deterministic, no timing or race requirements.

### Recommendation
In `PipelineRunsController.Create`, explicitly require that the caller is a session/token user and not an EI, e.g. reject if `_, isEI := auth.GetAuthenticatedExternalInitiator(c); isEI` before allowing the int32 path, or add a dedicated `SessionUserIsRealUser`/context flag set only by `AuthenticateBySession`/`AuthenticateByToken`, rather than relying on presence of `SessionUserKey`, which `AuthenticateExternalInitiator` also populates.

### Proof of Concept
Go handler-level test in `core/web/pipeline_runs_controller_test.go`:
1. Build a gin test context/router using only `auth.AuthenticateExternalInitiator` (mock `Authenticator.FindExternalInitiator` to return a valid `ExternalInitiator`), wrapped with `auth.RequiresRunRole(prc.Create)`.
2. Send `POST /v2/jobs/123/runs` with valid EI access key/secret headers, no session cookie, no API token.
3. Mock `app.RunJobV2` and assert it is **NOT** called (expected per the "EIs not allowed" comment).
4. Actual result: `RunJobV2` **is** called with `jobID=123`, `isUser` is `true`, demonstrating the bypass — assert `mockApp.AssertNotCalled(t, "RunJobV2", ...)` fails, proving the vulnerability.

func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
