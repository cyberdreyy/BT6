### Title
`claimInstantWithdrawRequest` pays the full aggregate instant-withdraw ledger, including receipts requested but not yet funded in the current epoch - (contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The kernel bug is a missing bounds check: `list_devices` wrote past the end of a fixed buffer because it trusted a caller-controlled count instead of validating the boundary. The analog in this codebase is the same class of failure — an aggregate counter is trusted as a boundary marker while per-epoch entries can exceed what has actually been funded. In `IdleCreditVault`, `requestInstantWithdraw` credits `instantWithdrawsRequests[_user]` and `instantWithdrawsRequestsByEpoch[_user][epochNumber]` immediately at request time (lines 356-375), but `claimInstantWithdrawRequest` burns and pays out the *entire* aggregate `instantWithdrawsRequests[_user]` (lines 387-392) with no check that all epochs composing that aggregate have been funded via `collectInstantWithdrawFunds` (lines 398-403). A user with an already-funded receipt from a previous epoch who opens a fresh instant-withdraw request can claim once and receive underlying for both receipts — the unfunded portion is paid out of underlying held for other claimants.

### Finding Description
- `requestInstantWithdraw` mints receipt strategy tokens to the user and increments `instantWithdrawsRequests[_user] += _amount`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount`, `instantWithdrawClaimsByEpoch[currentEpoch] += _amount`, and `pendingInstantWithdraws += _amount` (lines 360-374). No underlying is moved at this point; funding arrives only when the CDO calls `collectInstantWithdrawFunds`, which does `pendingInstantWithdraws -= _amount` and `safeTransferFrom(idleCDO, this, _amount)` (lines 398-403).
- `claimInstantWithdrawRequest` reads `amount = instantWithdrawsRequests[_user]` — the sum across all epochs — burns that whole receipt balance, zeroes the ledger, and calls `_transferFundedClaim(_user, amount)` (lines 380-393). `_transferFundedClaim` only guards the `defaultRecoveryReserve` (lines 897-907); it does not verify the claimed amount is covered by funded, non-reserved balance attributable to this user.
- The epoch boundary bookkeeping exists (`instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`, `pendingInstantWithdraws`) but none of it bounds the claim: the claim uses the flat aggregate, exactly like `list_devices` trusting a count without checking it against the real buffer boundary. Contrast with `requestWithdraw`, which explicitly reverts if a user still holds a loss-adjusted receipt for `lastWithdrawRequest[_user]` before allowing a new request (lines 261-271) — no equivalent guard exists on the instant path, so a second request is allowed while an old funded receipt is pending.
- Sequence (running epoch, instant withdrawals enabled):
  1. User requests instant withdraw of amount A in epoch N. Epoch stops; CDO funds it via `collectInstantWithdrawFunds(A)`; vault now holds A backing the user's receipt.
  2. Epoch N+1 starts. User requests instant withdraw of amount B. `instantWithdrawsRequests[user] = A + B`, `pendingInstantWithdraws += B`, but B's underlying has not been collected.
  3. After the instant delay, CDO calls `claimInstantWithdrawRequest(user)`: it burns A+B receipt tokens and transfers A+B underlying. The vault pays B out of the funded balance destined for other users' pending claims.
  4. When other claimants (or the borrower funding `pendingWithdraws`/recovery) later claim, the vault is short by B.

### Impact Explanation
Direct theft / insolvency: the user extracts B underlying they never paid for (receipt tokens for B were minted, not backed by collected funds). The loss B is socialized onto remaining claimants — either later instant-withdraw claims revert on insufficient balance (permanent freezing of unclaimed yield for victims) or `collectWithdrawFunds`/`stopEpoch` accounting underflows, breaking solvency. Loss is quantified as the size of the second request B, bounded only by the user's tranche position.

### Likelihood Explanation
Medium. The attacker needs tranche tokens and two transactions in adjacent epochs; the CDO's instant-withdraw delay gate controls *when* a claim is callable but nothing ties the claim amount to what was funded for the current epoch. The main uncertainty is whether the CDO-side flow (`IdleCDOEpochVariant`) always interleaves `collectInstantWithdrawFunds` and `claimInstantWithdrawRequest` such that an unfunded receipt can never coexist with a funded one at claim time; the vault-level code itself does not enforce this invariant, and the per-epoch ledgers added precisely to distinguish epochs are not consulted on the claim path.

### Recommendation
In `claimInstantWithdrawRequest`, bound the claim to funded epochs: subtract `pendingInstantWithdraws` per user or track `instantWithdrawsRequestsByEpoch` separately for unfunded current-epoch requests and only pay the funded remainder. Alternatively, add the same guard used by `requestWithdraw` — revert a new `requestInstantWithdraw` while `instantWithdrawsRequests[_user] != 0` and the prior epoch is unfunded, or snapshot the claimable amount at funding time (`collectInstantWithdrawFunds`) into a per-user funded-balance mapping and pay only from that.

  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }

  function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);
    }
    uint256 amount = instantWithdrawsRequests[_user];
    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
  }

  /// @notice collect the instant withdraw funds
  /// @dev only IdleCDO can call this function
  /// @param _amount number of tokens to collect
  function collectInstantWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    if (_amount == 0) return;
    pendingInstantWithdraws -= _amount;
    underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
  }

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
