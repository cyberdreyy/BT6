### Title
External initiator role bypasses job-ownership check and can trigger runs on any job ID via `POST /v2/jobs/:ID/runs` - ([File: core/web/pipeline_runs_controller.go])

### Summary
`auth.AuthenticateExternalInitiator` sets both `SessionExternalInitiatorKey` and a synthetic `SessionUserKey` object (`&clsessions.User{Role: clsessions.UserRoleRun}`) into the gin context. `RequiresRunRole` only checks `user.Role != clsessions.UserRoleView` and never checks `SessionExternalInitiatorKey`, so it lets external-initiator requests through indistinguishably from real "run" role users. `PipelineRunsController.Create`'s own attempt to exclude external initiators (`isUser` check) is broken by the same root cause and does not verify that the target job ID (`:ID`) belongs to the calling initiator.

### Finding Description
The route `authv2.POST("/jobs/:ID/runs", ...)`-equivalent for EI/user traffic is registered as: [1](#0-0) 
`userOrEI` accepts `AuthenticateExternalInitiator`, `AuthenticateByToken`, or `AuthenticateBySession`, then wraps `prc.Create` with `auth.RequiresRunRole`.

`AuthenticateExternalInitiator` authenticates the caller against `bridges.AuthenticateExternalInitiator(eia, ei)` for a specific `ExternalInitiator` record (tied to a specific job/bridge), then does: [2](#0-1) 
This sets `SessionUserKey` to a fresh `User{Role: UserRoleRun}` with no `Email`/`ID`, and also records the actual initiator identity under `SessionExternalInitiatorKey`.

`RequiresRunRole` only inspects the `User.Role` field: [3](#0-2) 
It never reads `SessionExternalInitiatorKey`/`GetAuthenticatedExternalInitiator`, so it cannot distinguish "a real run-role human user" from "an external initiator credential for job X."

Inside the handler, `PipelineRunsController.Create` attempts to gate int-ID job runs to "users" only, with a comment claiming EIs are not allowed: [4](#0-3) 
However, `isUser` comes from `auth.GetAuthenticatedUser(c)`: [5](#0-4) 
which simply checks for the presence of `SessionUserKey` — the very same synthetic `User{Role: UserRoleRun}` object that `AuthenticateExternalInitiator` sets for every EI request. Therefore `isUser` is `true` for external-initiator-authenticated requests too, defeating the intended "EIs not allowed" restriction. The handler then calls `prc.App.RunJobV2(ctx, jobID, nil)` using the caller-supplied `:ID` path parameter with **no check at all** that `jobID` corresponds to the job associated with the initiator recorded in `SessionExternalInitiatorKey`.

Net effect: a holder of valid external-initiator credentials scoped to job X can send `POST /v2/jobs/{Y}/runs` for any arbitrary job ID `Y` (belonging to any other job/user) and trigger `RunJobV2` for it, because neither `RequiresRunRole` nor `PipelineRunsController.Create` cross-checks the target job against the initiator's own job.

### Impact Explanation
This is an authorization bypass allowing an external-initiator credential (scoped to trigger runs only for its own bound job) to trigger pipeline runs on **any job spec** in the node, including jobs owned by other integrations/initiators. Depending on job task graphs, this can cause unauthorized on-chain transactions, unintended fund movement (e.g., ETH transfer jobs, VRF fulfillment jobs), resource exhaustion, or unauthorized invocation of jobs the attacker has no legitimate relationship to — matching the "unauthorized job run" / "authorization bypass" bounty impact class.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs one valid external-initiator access key/secret pair (the lowest privilege credential type designed to trigger a single job's runs). No admin/edit/view-user session or API token is required. The exploit is a single unauthenticated-relative-to-target-job HTTP POST with a job ID they don't own; it's fully repeatable and requires no timing or race conditions.

### Recommendation
- In `RequiresRunRole` (or a dedicated wrapper used on the `userOrEI` group), check `auth.GetAuthenticatedExternalInitiator(c)`; if present, require that the requested job ID matches the `ExternalInitiator`'s associated job (e.g., load `ei.JobID`/associated webhook spec and compare with `c.Param("ID")`) before invoking the handler.
- In `PipelineRunsController.Create`, do not rely on `GetAuthenticatedUser` to distinguish EI vs. real users, since `AuthenticateExternalInitiator` also populates `SessionUserKey`. Instead explicitly check `GetAuthenticatedExternalInitiator` first and reject/scope the run to that initiator's own job.
- Consider giving the synthetic EI-run `User` a distinguishable marker (or a separate context key) rather than reusing `SessionUserKey`, so role-based middlewares and handlers can reliably differentiate EI-run vs interactive-user-run requests.

### Proof of Concept
Handler-level Go test plan (in `core/web/pipeline_runs_controller_test.go` style):
1. Create two webhook/job specs, Job A and Job B, each with distinct `ExternalInitiator` records `EI_A` (bound to Job A) and `EI_B` (bound to Job B).
2. Authenticate as `EI_A` using its access key/secret via `static.ExternalInitiatorAccessKeyHeader`/`SecretHeader`.
3. Send `POST /v2/jobs/{JobB.ID}/runs` (Job B's integer ID, not Job A's) using `EI_A`'s credentials.
4. Assert current (vulnerable) behavior: `http.StatusOK` and a pipeline run resource for Job B is returned — i.e., `EI_A` successfully triggered a run on Job B despite having no association with it.
5. Expected secure behavior: response should be `403 Forbidden` (or `422`) because `EI_A` is not authorized to trigger runs for jobs other than the one referenced by its `ExternalInitiator` record.
6. Repeat with `EI_A` targeting Job A's own ID to confirm the legitimate case still returns `200 OK` after the fix.

func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
