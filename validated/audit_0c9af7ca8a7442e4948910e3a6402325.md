### Title
Unprotected `initializeConfig()` in `BridgeCommittee` — Any Caller Can Set a Malicious Config Before the Deployer Does - (File: bridge/evm/contracts/BridgeCommittee.sol)

### Summary

`BridgeCommittee.initializeConfig()` is an `external` function with no caller restriction. Its only guard is a one-time check (`config == address(0)`). Because the deployment script calls `initializeConfig` in a separate transaction from the proxy deployment, any attacker monitoring the mempool can front-run the deployer and permanently install a malicious `BridgeConfig` contract as the committee's config.

### Finding Description

The function is declared as:

```solidity
function initializeConfig(address _config) external {
    require(address(config) == address(0), "BridgeCommittee: Config already initialized");
    config = IBridgeConfig(_config);
}
``` [1](#0-0) 

There is no `onlyOwner`, `onlyCommittee`, or any other caller-identity check. The only protection is the one-time guard, which only prevents a *second* call — it does not prevent an *unauthorized first* call.

The deployment script issues `initializeConfig` as a separate broadcast transaction, after the proxy is already live on-chain:

```solidity
BridgeCommittee(bridgeCommittee).initializeConfig(address(bridgeConfig));
BridgeCommittee committeeImplementation =
    BridgeCommittee(Upgrades.getImplementationAddress(bridgeCommittee));
committeeImplementation.initializeConfig(address(bridgeConfig));
``` [2](#0-1) 

Between the proxy deployment transaction and the `initializeConfig` transaction, the `config` slot is `address(0)` and the function is callable by anyone.

The `BridgeCommittee.initialize()` (the main initializer) is correctly protected by the OpenZeppelin `initializer` modifier, and the constructor calls `_disableInitializers()`: [3](#0-2) 

But `initializeConfig` is a *separate* function that was never given the same protection.

### Impact Explanation

`SuiBridge.transferBridgedTokensWithSignatures()` reads `committee.config()` to obtain the chain ID and token addresses used for every bridge transfer: [4](#0-3) 

A malicious `IBridgeConfig` contract installed by the attacker can:

1. **Return a wrong `chainID()`** — causing the `require(tokenTransferPayload.targetChain == config.chainID(), ...)` check to always revert, permanently blocking all outbound token transfers from the vault. Funds already deposited in the vault become locked.
2. **Return a malicious `tokenAddressOf(tokenID)`** — corrupting the ERC-20 decimal lookup used in `BridgeUtils.convertSuiToERC20Decimal`, producing wildly incorrect transfer amounts for any transfer that does succeed.
3. **Return `false` for `isChainSupported()`** — blocking all inbound bridge messages from legitimate chains.

Because `config` can only be set once (the one-time guard prevents overwriting), the committee cannot fix this without a full UUPS upgrade signed by a quorum. During the window before an upgrade is executed, all bridge operations are halted and vault funds are inaccessible — a permanent fund lock until governance acts.

### Likelihood Explanation

The attack requires only:
- Watching the mempool for the `BridgeCommittee` proxy deployment transaction.
- Submitting a higher-gas `initializeConfig(maliciousConfig)` call before the deployer's `initializeConfig` lands.

This is a standard front-running attack, executable by any ordinary Ethereum user with no special privileges. The deployment script confirms the two calls are in separate transactions. [5](#0-4) 

### Recommendation

Add a caller restriction to `initializeConfig`. The simplest fix is to restrict it to the address that called `initialize()` (i.e., the deployer), or to require a committee-signed message analogous to other governance operations. Alternatively, pass `_config` as a parameter to `initialize()` and set it atomically in the same transaction, eliminating the deployment-time race entirely.

### Proof of Concept

```solidity
// Attacker contract
contract MaliciousConfig is IBridgeConfig {
    function chainID() external pure override returns (uint8) { return 255; } // wrong chain
    function tokenAddressOf(uint8) external pure override returns (address) { return address(0); }
    function tokenSuiDecimalOf(uint8) external pure override returns (uint8) { return 0; }
    function tokenPriceOf(uint8) external pure override returns (uint64) { return 0; }
    function isTokenSupported(uint8) external pure override returns (bool) { return false; }
    function isChainSupported(uint8) external pure override returns (bool) { return false; }
}

// Attack sequence (front-run the deployer):
// 1. Deployer broadcasts: deployUUPSProxy("BridgeCommittee.sol", initData)
//    -> BridgeCommittee proxy is live, config == address(0)
// 2. Attacker sees the pending initializeConfig tx in the mempool
// 3. Attacker broadcasts with higher gas:
BridgeCommittee(committeeProxy).initializeConfig(address(new MaliciousConfig()));
// 4. Deployer's initializeConfig reverts: "BridgeCommittee: Config already initialized"
// 5. All SuiBridge transfers now revert: "SuiBridge: Invalid target chain"
// 6. Vault funds are locked until the committee executes a UUPS upgrade
```

The existing test `testBridgeCommitteeInitializeConfig` only verifies that a *second* call reverts after the config is already set — it does not test that an unauthorized *first* call is rejected: [6](#0-5)
