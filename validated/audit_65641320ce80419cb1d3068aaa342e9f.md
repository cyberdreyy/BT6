### Title
`IdleCreditVault` tracks only the latest withdraw-request epoch, letting earlier loss-adjusted receipts escape the haircut and be claimed at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestWithdraw` stores a single "last request epoch" pointer per user (`lastWithdrawRequest`), while `pendingWithdraws` aggregates receipts across *all* epochs. When `stopEpochWithDuration`/`collectWithdrawFunds` books a partial loss, the recovery price is recorded under the *current* epoch and `_claimLossAdjustedWithdrawRequest` haircuts only the receipts registered under `lastWithdrawRequest`. A user who stacked requests in two consecutive epochs before any loss occurred gets the older receipt paid at full par via `_claimFundedWithdrawRequest`, even though its basis was included when the haircut was computed — draining the funded recovery pool owed to other receipt holders. This is the analog of the kernel bug: a raw single-slot reference (`lastWithdrawRequest`) is kept to a resource (the set of loss-bearing receipts) that actually spans more than it points at, so part of the referent escapes the lifetime/loss guarantee on later use.

### Finding Description
- `requestWithdraw` writes `lastWithdrawRequest[_user] = currentEpoch` and accumulates `withdrawsRequestsByEpoch[_user][currentEpoch]` plus aggregate `pendingWithdraws` (lines 260–294). Claiming is optional; a user may simply request again the next epoch, which *overwrites* the epoch pointer while the older `withdrawsRequestsByEpoch` entry persists. The guard at lines 263–271 only blocks a new request **if a loss price already exists** at `lossRecoveryPriceByEpoch[lastWithdrawRequest]`; it does not prevent accumulating multi-epoch receipts while `lossRecoveryPriceByEpoch` is still empty.
- On a lossy stop, `collectWithdrawFunds` computes `lossRecoveryPrice = funded * RECOVERY_FULL / pendingBasis` over the *aggregate* `pendingWithdraws` and stores it under `lossRecoveryPriceByEpoch[epochNumber]` (lines 411–430). All pending receipts — including the attacker's stale epoch-E1 receipt — are part of `pendingBasis`.
- Claim order in `claimWithdrawRequest` is `_claimLossAdjustedWithdrawRequest` then `_claimFundedWithdrawRequest` (lines 301–314). The loss path only clears `withdrawsRequestsByEpoch[_user][lossEpoch]` where `lossEpoch = lastWithdrawRequest` (lines 789–800), and `_clearWithdrawClaimForEpoch` then resets `lastWithdrawRequest` to 0 (lines 832–835). `_claimFundedWithdrawRequest` then sees `epochNumber > lastWithdrawRequest` and pays the *remaining* `withdrawsRequests[_user]` — the E1 receipt — at par via `_transferFundedClaim` (lines 319–349).

Broken invariant: loss waterfall / "one receipt one haircut". Every receipt in `pendingBasis` was priced with `lossRecoveryPrice`, but receipts whose epoch is not `lastWithdrawRequest` redeem 1:1 from the same funded pool.

### Impact Explanation
Direct theft / insolvency of funded claims: the attacker withdraws `E1_amount` at par instead of `E1_amount * lossRecoveryPrice`, extracting `E1_amount * (1 - lossRecoveryPrice)` of underlying that belongs to other pending receipt holders. With a 50% recovery price and a large first-epoch request, the attacker roughly doubles that portion of their claim; the last claimants' `_transferFundedClaim` will underflow/revert on an empty pool, permanently freezing their recovery. Quantified loss: `min(attackerE1, pool) * (RECOVERY_FULL - lossRecoveryPrice) / RECOVERY_FULL`.

### Likelihood Explanation
Requires only unprivileged actions: deposit tranche tokens, call `requestWithdraw` in epoch N buffer, skip claiming, call `requestWithdraw` again in epoch N+1 buffer (allowed — no loss price exists yet), then a lossy `stopEpochWithDuration` executed by the *honest* manager (a routine borrower-underpayment event, which the preview function `previewLossAdjustedWithdrawFunds` explicitly supports). No privileged misbehavior, no default, no timing race needed; any KYC-passing lender can do this whenever a partial loss lands.

### Recommendation
Track loss-bearing receipts per epoch, not just the latest one. Options: in `_claimLossAdjustedWithdrawRequest`, apply `lossRecoveryPrice` to *all* of `withdrawsRequests[_user]` / all unsettled `withdrawsRequestsByEpoch` entries and `apr0Users` principal that contributed to `pendingBasis` at collect time (e.g., record `lossRecoveryAppliedAt`/`pendingBasisAtLoss` and clear every open receipt at the haircut), or revert in `requestWithdraw` when `withdrawsRequests[_user] != 0 || apr0Users[_user].principal != 0` so a user can never hold receipts from more than one epoch at loss time. The single-slot `lastWithdrawRequest` must not silently orphan earlier receipts from the loss epoch's haircut.

```solidity
// setup: attacker is KYC'd; pool has other pending withdrawers or funded claims
uint256 e1 = 100e6;  // epoch N request
uint256 e2 = 100e6;  // epoch N+1 request

// --- buffer period of epoch N ---
vm.prank(attacker);
cdo.requestWithdraw(trancheBal / 2, address(AAtranche)); // -> strategy.requestWithdraw, lastWithdrawRequest=N
// do NOT claim after epoch N stops

// --- stopEpoch N (fully funded, no loss) ---
_stopCurrentEpochWithApr(apr);            // pendingWithdraws += e1

// --- buffer period of epoch N+1 ---
vm.prank(attacker);
cdo.requestWithdraw(remaining, address(AAtranche));      // lastWithdrawRequest=N+1
// other users also request so pendingBasis is shared

// --- manager stops epoch N+1 with a realized loss (honest call) ---
vm.prank(manager);
cdo.stopEpochWithDuration(duration, lossAmount);         // -> collectWithdrawFunds(partial)
// lossRecoveryPriceByEpoch[N+1] = funded / pendingBasis (includes e1+e2)

// --- attacker claims ---
vm.prank(attacker);
cdo.claimWithdrawRequest();
// _claimLossAdjustedWithdrawRequest: only withdrawsRequestsByEpoch[N+1] haircutted
// _claimFundedWithdrawRequest: epochNumber > lastWithdrawRequest(=0) -> e1 paid at par

uint256 stolen = e1 * (RECOVERY_FULL - lossRecoveryPriceByEpoch[N+1]) / RECOVERY_FULL;
assertGt(underlying.balanceOf(attacker), e2 * price / RECOVERY_FULL + e1); // e1 escaped haircut
```
