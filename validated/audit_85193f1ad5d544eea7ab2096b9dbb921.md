### Title
External ERC4626 vault liquidity withdrawal can indefinitely block epoch settlement - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary

`ProgrammableBorrower` treats an ERC4626 withdrawal revert as a retryable liquidity failure and propagates that revert through `onStopEpoch`, causing `IdleCDOEpochVariant.stopEpoch` to revert while leaving the epoch running. Any unprivileged holder of the configured external ERC4626 vault can drain available liquidity immediately before the manager stops the epoch. Because `convertToAssets` can still report that the programmable borrower’s shares economically cover the recall, the code attempts `vault.withdraw`, catches the vault’s revert, and deliberately reverts `StopEpochVaultLiquidityUnavailable`. All matured withdrawal proceeds remain unavailable until vault liquidity returns, and an attacker with vault shares can repeat the drain to keep settlement blocked.

### Finding Description

During a running programmable-borrower epoch, undrawn pool assets are deposited into the configured ERC4626 vault by `onStartEpoch`. [1](#0-0) 

At epoch end, `IdleCDOEpochVariant._stopEpoch` calls `IProgrammableBorrower(_borrower()).onStopEpoch(_amountToPullFromBorrower + _pendingWithdraws, ...)` before pulling funds from the programmable borrower. [2](#0-1) 

`ProgrammableBorrower.onStopEpoch` compares the cash shortfall with `convertToAssets`, not with `maxWithdraw` or another realizable-liquidity measure. If the share valuation is sufficient, it calls `vault.withdraw(shortfall, ...)`; any vault revert is converted into `StopEpochVaultLiquidityUnavailable`. [3](#0-2) 

An ERC4626 valuation can remain sufficient while immediately withdrawable liquidity is exhausted. For example, in a public MetaMorpho-style vault, another vault shareholder can redeem their own shares and consume the vault’s liquid underlying. The programmable borrower still owns valuable shares, so `shortfall <= _currentVaultAssets()`, but the vault withdrawal fails because there is insufficient underlying liquidity. The propagated revert causes the entire `stopEpoch` call to revert before `isEpochRunning` is cleared or pending withdrawals are funded.

The same transaction sequence can be repeated whenever liquidity returns:

1. Epoch is running with programmable borrower funds parked in an ERC4626 vault.
2. The manager calls `stopEpoch` after `epochEndDate`.
3. An external vault shareholder front-runs or precedes that call and withdraws enough underlying liquidity.
4. `totalInterestDueNow` and `_currentVaultAssets` still recognize the borrower’s share value.
5. `vault.withdraw(shortfall, ...)` reverts.
6. `StopEpochVaultLiquidityUnavailable` reverts `stopEpoch`.
7. The epoch remains running and matured withdrawal requests cannot be claimed.

The repository already demonstrates this exact branch in `testProgrammableBorrowerStopEpochRevertsWhenVaultLiquidityUnavailable`, where a withdrawal limit below `pendingWithdraws` makes `stopEpoch` revert and leaves the epoch running, accounting active, and withdrawals pending. [4](#0-3) 

### Impact Explanation

An unprivileged external ERC4626 vault participant can temporarily freeze every withdrawal whose liquidity must be recalled through `onStopEpoch`. The frozen amount is the full `_amountToPullFromBorrower + _pendingWithdraws` requested by `stopEpoch`; in a normal minted-interest programmable deployment, that includes all pending withdrawal requests. In close-pool mode it additionally includes recalled principal.

The attacker does not need to compromise the vault, borrower, manager, owner, or IdleCDO. Redeeming their own ERC4626 position is enough when that redemption removes the liquidity needed by the programmable borrower. The impact is a temporary freeze rather than permanent loss, but it can be maintained while the attacker controls enough vault shares or vault liquidity conditions continue to make `withdraw` fail.

### Likelihood Explanation

Likelihood depends on the configured vault having public shareholders and less immediately available liquidity than the programmable borrower’s stop-epoch recall. That condition is realistic for ERC4626 vaults with queued liquidity, allocated markets, withdrawal caps, or utilization stress. The attacker only needs an existing vault position or the ability to acquire one; no Idle credit-vault role is required.

The issue is limited to programmable-borrower deployments and to settlement paths that need external vault liquidity. It cannot steal funds by itself, and it ends once the vault can satisfy the requested withdrawal.

### Recommendation

Make stop-epoch settlement robust against partial ERC4626 liquidity instead of treating “economic coverage” as equivalent to withdrawable cash:

- Recall only the vault’s currently executable liquidity, using a bounded `maxWithdraw`-aware amount, while preserving the failure state for the unrecalled remainder.
- Consider entering a controlled liquidity-shortfall state that records the unpaid withdrawal amount and allows later recall/claim funding without requiring the whole `stopEpoch` call to revert.
- Alternatively, partially withdraw `min(shortfall, maxWithdraw(address(this)))`, transfer what is available to the strategy, and expose a permissioned retry function for the remaining amount.
- If partial funding cannot be represented safely by the credit-vault accounting, document that external vault liquidity can halt epoch settlement and impose vault-selection criteria requiring guaranteed redemption capacity.

Avoid relying solely on `convertToAssets` before calling `withdraw`; ERC4626 share value does not guarantee immediately withdrawable liquidity.

### Proof of Concept

The following Foundry-style sequence reproduces the issue using the same mock-vault pattern already present in `test/foundry/ProgrammableBorrowerCreditVault.t.sol`:

```solidity
function testExternalVaultLiquidityDrainBlocksStopEpoch() external {
    uint256 amount = 10_000 * oneScale;

    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);

    idleCDO.depositAA(amount);
    cdoEpoch.requestWithdraw(
        aaTranche.balanceOf(address(this)) / 2,
        address(aaTranche)
    );
    _startEpochAndCheckPrices(0);

    uint256 pendingWithdraws = strategy.pendingWithdraws();
    assertGt(pendingWithdraws, 0);

    // Attacker is only an external ERC4626 shareholder. Their redemption leaves the
    // programmable borrower's shares economically valuable but not withdrawable.
    vm.prank(externalVaultShareholder);
    morphoVault.redeem(
        morphoVault.balanceOf(externalVaultShareholder),
        externalVaultShareholder,
        externalVaultShareholder
    );

    assertGe(
        morphoVault.convertToAssets(
            morphoVault.balanceOf(address(programmableBorrower))
        ),
        pendingWithdraws
    );
    assertLt(
        morphoVault.maxWithdraw(address(programmableBorrower)),
        pendingWithdraws
    );

    vm.warp(cdoEpoch.epochEndDate() + 1);

    vm.prank(manager);
    vm.expectRevert(
        ProgrammableBorrower.StopEpochVaultLiquidityUnavailable.selector
    );
    cdoEpoch.stopEpoch(0, 0);

    assertTrue(cdoEpoch.isEpochRunning());
    assertFalse(cdoEpoch.defaulted());
    assertEq(strategy.pendingWithdraws(), pendingWithdraws);
}
```
