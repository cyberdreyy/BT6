### Title
Unauthenticated capability-execution / resource-exhaustion via unauthorized DON dispatch in legacy gateway messages - ([File: core/services/gateway/gateway.go], [File: core/services/gateway/handlers/handler.dummy.go], [File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`gateway.ProcessRequest` routes legacy messages (`msg.Body.DonId != ""`) purely by looking up `g.handlers[msg.Body.DonId]` after calling `msg.Validate()`, which only checks field lengths/format and recovers a `Sender` address from the ECDSA signature — it never checks that the recovered `Sender` belongs to the target DON's member/subscriber list. Both `dummyHandler.HandleLegacyUserMessage` and the capabilities `handler.HandleLegacyUserMessage` then broadcast the request to every node in `donConfig.Members` with no sender allowlist check, so any externally-owned address with a fresh keypair can force message delivery to a DON it has no relationship with.

### Finding Description
`gateway.ProcessRequest` (`core/services/gateway/gateway.go:250-262`) treats any message with a non-empty `DonId` as a legacy request: it calls `msg.Validate()` and then does `h, ok = g.handlers[handlerKey]` using `handlerKey = msg.Body.DonId`. `Message.Validate()` (`core/services/gateway/api/message.go:54-88`) checks field lengths/null-byte suffixes and calls `ExtractSigner()` to recover `m.Body.Sender` from the signature — it performs no lookup against `DONConfig.Members` or any allowlist; **any** validly-formed, self-signed message from a brand-new key passes.

Downstream, `dummyHandler.HandleLegacyUserMessage` (`core/services/gateway/handlers/handler.dummy.go:62-82`) unconditionally iterates `d.donConfig.Members` and calls `don.SendToNode` for every member — no check that `msg.Body.Sender` is a subscriber/allowlisted address. The capabilities handler `handler.HandleLegacyUserMessage` (`core/services/gateway/handlers/capabilities/handler.go:341-421`) explicitly documents this gap with `// TODO: apply allowlist and rate-limiting here` (line 384) before forwarding to `don.SendToNode` for every `h.donConfig.Members` entry. Neither handler, nor `gateway.ProcessRequest`, verifies sender membership/subscription before dispatch.

Attack flow: attacker generates a fresh ECDSA keypair, constructs an `api.Message` with any publicly known `DonId` and an advertised `Method`, signs it with `msg.Sign(key)`, and POSTs it to the gateway's user HTTP endpoint. `ProcessRequest` decodes and validates the message (signature format only), looks up the handler by `DonId`, and dispatches to `HandleLegacyUserMessage`, which broadcasts the message to every DON node — with no authorization check on the sender.

### Impact Explanation
This enables unauthenticated capability execution/consumption of DON resources by any attacker who can guess or enumerate a DonId (DON IDs are not secret) — matching the "unauthorized job run/capability invocation" and "resource-quota theft from legitimate subscribers" bounty impact classes. Every DON node receives and processes the forwarded request, letting an attacker with zero prior relationship to the DON trigger workflow/webhook capability execution or exhaust node processing capacity meant for legitimate subscribers.

### Likelihood Explanation
Feasibility is high: no credentials beyond a self-generated keypair are required, DonId values are often public/discoverable via configuration or prior interactions, and the exploit is fully repeatable (a single signed HTTP POST per attempt) with no rate limiting or allowlist gate blocking it in either `gateway.ProcessRequest` or the affected handlers' `HandleLegacyUserMessage` implementations.

### Recommendation
Add an explicit sender-authorization check before dispatch: after `msg.Validate()` recovers `msg.Body.Sender`, verify that the sender is present in the target `DONConfig`'s allowlist/subscriber registry for the requested method/DON before calling `HandleLegacyUserMessage`, either centrally in `gateway.ProcessRequest` or inside each handler's `HandleLegacyUserMessage` (implement the pending `// TODO: apply allowlist and rate-limiting here` in `core/services/gateway/handlers/capabilities/handler.go` and add the equivalent check to `handler.dummy.go`). Reject unauthorized senders with a distinct authorization error rather than silently broadcasting.

### Proof of Concept
1. In a handler-level Go test (e.g., extending `handler.dummy_test.go` or `capabilities/handler_test.go`), construct a `config.DONConfig` with `Members` containing known node addresses but no entry/allowlist for an arbitrary fresh key.
2. Generate a fresh `ecdsa.PrivateKey` never referenced in `DonConfig.Members` or any allowlist, sign a well-formed `api.Message` with `DonId` set to the configured DON, call `msg.Validate()` to confirm it passes.
3. Call `handler.HandleLegacyUserMessage(ctx, &msg, cb)` (or run through `gateway.ProcessRequest` end-to-end with a mocked `DON`/connection manager) and assert on the mock `DON.SendToNode` call count.
4. Expected (failing) result today: `SendToNode` is invoked for every DON member and no error is returned — proving dispatch occurs despite the sender never being authorized. After the fix, assert `HandleLegacyUserMessage`/`ProcessRequest` returns an authorization error and `SendToNode` is never called.
