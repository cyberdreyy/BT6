### Title
EI credentials satisfy `auth.GetAuthenticatedUser`, bypassing the intended "EIs not allowed" restriction in `PipelineRunsController.Create` - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` gates int32-ID job runs on `_, isUser := auth.GetAuthenticatedUser(c)`, with a comment stating "only users are allowed to run jobs using int IDs - EIs not allowed." However, the middleware chain used for this exact route sets the same session key for External Initiator (EI) requests, so `GetAuthenticatedUser` returns `ok=true` for EI credentials too, defeating the intended restriction.

### Finding Description
The route is registered in `core/web/router.go` as:
```go
userOrEI := r.Group("/v2", auth.Authenticate(app.AuthenticationProvider(),
    auth.AuthenticateExternalInitiator,
    auth.AuthenticateByToken,
    auth.AuthenticateBySession,
))
userOrEI.POST("/jobs/:ID/runs", auth.RequiresRunRole(prc.Create))
``` [1](#0-0) 

`auth.AuthenticateExternalInitiator`, on successful EI credential verification, explicitly sets **both** `SessionExternalInitiatorKey` and `SessionUserKey` to a synthetic `&clsessions.User{Role: clsessions.UserRoleRun}`:
```go
c.Set(SessionExternalInitiatorKey, ei)
c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})
``` [2](#0-1) 

`GetAuthenticatedUser` simply reads `SessionUserKey` from the gin context:
```go
func GetAuthenticatedUser(c *gin.Context) (*clsessions.User, bool) {
	obj, ok := c.Get(SessionUserKey)
	...
}
``` [3](#0-2) 

Because `AuthenticateExternalInitiator` populates `SessionUserKey`, a request authenticated purely via EI headers (`X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret`, per `static.ExternalInitiatorAccessKeyHeader`/`SecretHeader`) will make `isUser` true in `Create`:
```go
_, isUser := auth.GetAuthenticatedUser(c)
// only users are allowed to run jobs using int IDs - EIs not allowed
if isUser {
	...
	jobRunID, err := prc.App.RunJobV2(ctx, jobID, nil)
	...
}
``` [4](#0-3) 

This directly matches the question's hypothesis: the `isUser` check does not distinguish an EI-derived synthetic user from a real user session/token, because the middleware itself performs the "confusion" by writing the same context key for both authentication paths. The code comment's stated intent ("EIs not allowed") is contradicted by the actual behavior enabled by the shared `SessionUserKey`.

### Impact Explanation
An EI-only credential holder (which is meant to have only `run`-role access, historically scoped to triggering webhook-type jobs by UUID) can invoke `POST /v2/jobs/:ID/runs` with an integer job ID and successfully trigger `prc.App.RunJobV2`, running arbitrary jobs identified by int32 ID — the exact action the code comment says should be denied to EIs. This is an authorization-boundary violation (unauthorized job run) reachable by an unprivileged EI credential holder, matching the "unauthorized job run" bounty impact class. However, note that `auth.RequiresRunRole` also permits any real user with `run` role to hit this same route, and the EI's synthetic user is deliberately given `UserRoleRun` "by design" per the comment in `auth.go` ("External initiator endpoints ... inherently assume the role of 'run'"), so the elevated access is a natural consequence of the role model, not a full privilege escalation to edit/admin — it is scoped to running jobs, not modifying them.

### Likelihood Explanation
This requires only a valid EI access key/secret pair (an unprivileged, non-admin credential class explicitly in scope per the rules) and is 100% deterministic/repeatable — no race condition or timing dependency, since `AuthenticateExternalInitiator` unconditionally sets `SessionUserKey` on every successful EI authentication for this route.

### Recommendation
In `PipelineRunsController.Create`, do not rely solely on `auth.GetAuthenticatedUser`; also check `auth.GetAuthenticatedExternalInitiator(c)` and reject the request if an EI is present (i.e., check `SessionExternalInitiatorKey` is unset), or introduce a distinct context flag/synthetic type that differentiates a real authenticated user from an EI-synthesized run-role user, so `isUser` accurately reflects "genuine user credential" rather than "any principal with a user-role context value."

### Proof of Concept
Go handler-level integration test plan (in `core/web/pipeline_runs_controller_test.go` or similar):
1. Set up a test app with a job spec created with an int32 ID (a job that is not `job.Webhook`).
2. Register a valid External Initiator (`bridges.ExternalInitiator`) via the app's ORM/factory, obtaining `AccessKey`/`Secret`.
3. Send `POST /v2/jobs/{intID}/runs` with headers `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` set to the EI's credentials (no session cookie, no `X-API-KEY`/`X-API-SECRET`).
4. Assert the response status: expected `422 Unprocessable Entity` ("bad job ID") per the comment's intent that EIs are not allowed to trigger int-ID runs; actual observed behavior (pre-fix) is `200 OK` with a `pipelineRun` resource, proving `isUser` was true for the EI.
5. Unit-test `auth.GetAuthenticatedUser` directly: build a `gin.Context`, call `auth.AuthenticateExternalInitiator(c, mockAuthenticator)` with a valid EI token, then call `auth.GetAuthenticatedUser(c)` and assert `ok == false` (this assertion currently fails, demonstrating the root cause).
