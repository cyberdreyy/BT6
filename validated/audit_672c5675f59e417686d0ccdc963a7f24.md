This confirms the vulnerability: the properly-designed `RequestCache` in `core/services/gateway/handlers/common/requestcache.go` keys pending requests by `globalId{sender, id}` (a per-sender-scoped key) and explicitly rejects a `NewRequest` call if the key already exists (`"request already exists"` at [1](#0-0) ). The legacy WebAPI trigger handler, however, does not use this safe cache and instead keys purely by the client-supplied `MessageId` with no collision check.

### Title
Unauthenticated cross-user response hijacking via MessageId collision in legacy WebAPI trigger callback map - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The Gateway's legacy `web_api_trigger` HTTP entrypoint stores per-request callbacks in a shared, node-wide map keyed solely by the client-supplied `MessageId` (JSON-RPC request `id`), with no per-sender scoping and no duplicate-key check. Any unauthenticated external caller can submit a trigger request re-using another in-flight request's `MessageId`, silently overwriting the original caller's callback entry. When a DON node later responds with that `MessageId`, the response is routed to whichever callback currently occupies the map slot — potentially the attacker's — rather than the original requester's.

### Finding Description
`HandleLegacyUserMessage` is invoked directly from `gateway.ProcessRequest` for any HTTP POST hitting the gateway with a `DonId` set, with **no authentication, allowlist, or rate limiting applied** — this is explicitly called out in the code: `// TODO: apply allowlist and rate-limiting here` [2](#0-1) .

The `MessageId` used as the map key is taken verbatim from the caller-controlled JSON-RPC request `id` field (`msg.Body.MessageId = request.ID`) [3](#0-2)  and, for legacy requests, from `jsonrpc2.Request.ID` decoded in `gateway.ProcessRequest` [4](#0-3) . The only validation applied is a length check (`≤200` chars) and non-empty/non-null-terminated checks in `Message.Validate()` — no uniqueness enforcement [5](#0-4) .

`HandleLegacyUserMessage` then unconditionally overwrites the `savedCallbacks` map entry for that `MessageId`, with no check for an existing entry: [6](#0-5) 

Later, when any DON node replies with `MethodWebAPITrigger` and the same `MessageId`, the response is delivered to whatever callback currently exists at that map key: [7](#0-6) 

Because the key omits the sender/nonce, and because assignment silently clobbers rather than rejecting duplicates, a second unauthenticated request using the same `MessageId` as an in-flight one will replace the original entry. The original caller's HTTP connection will simply hang until it times out via the gateway's context deadline (`callback.Wait(ctx)` in `gateway.go`) and receive `RequestTimeoutError`, while the second request's `savedCallback` receives whichever node response arrives first for that `MessageId` — which corresponds to the *original* victim's trigger payload/response, since the DON nodes still process and respond based on the original signed message content that was routed to them under that `MessageId`.

This is directly analogous to the referenced bug class: an unprivileged party can manipulate shared state (here, a map entry instead of a burn-accounting counter) that the system trusts to be uniquely and correctly attributed, causing outcomes intended for one party to be misdirected/confused with another's, without any privileged access.

By contrast, the properly hardened `RequestCache` used elsewhere in the Gateway explicitly scopes the key to `{sender, id}` and rejects duplicate `NewRequest` calls: [8](#0-7) . Similarly, `OutgoingConnectorHandler`'s `responses.new` rejects duplicate message IDs: [9](#0-8) . The legacy `handler.go` `savedCallbacks` map lacks both protections.

### Impact Explanation
An unauthenticated external HTTP client can:
- Cause another concurrent caller's `web_api_trigger` request to never receive its intended response (denial of response / silent hang until timeout).
- Potentially receive the response payload belonging to another caller's trigger request under a colliding `MessageId`, i.e., cross-user response confusion — an explicitly accepted impact class for this analysis.
- Since the legacy trigger path is completely unauthenticated (`// TODO: apply allowlist and rate-limiting here`), any anonymous internet client reaching the gateway's public trigger endpoint can attempt this, requiring no credentials, keys, or roles.

### Likelihood Explanation
Exploitation only requires guessing or observing a `MessageId` in use during the callback's live window (`CallbackMaxAgeSec`, default 120s) [10](#0-9) . Since `MessageId` is entirely attacker-controlled and there is no per-sender namespace, an attacker with any knowledge of, or even brute-forcing over, commonly used IDs (e.g., sequential/predictable IDs used by legitimate integrators, as shown by the reference script using `"12345"` as a default ID [11](#0-10) ) can trigger the collision. Given the endpoint requires no authentication at all, likelihood of exploitation is high wherever this legacy path remains reachable/enabled.

### Recommendation
- Key `savedCallbacks` by `{sender, MessageId}` (or a server-generated unique identifier) instead of `MessageId` alone, mirroring `RequestCache`'s `globalId{sender, id}` scheme.
- Reject `HandleLegacyUserMessage` calls that reuse an existing, still-pending `MessageId` (return an error to the caller) instead of silently overwriting the map entry.
- Implement the still-outstanding `// TODO: apply allowlist and rate-limiting here` for the legacy trigger path.
- Consider migrating fully off the legacy per-`MessageId`-map handler to the hardened `RequestCache`/`httpTriggerHandler` (v2) pattern, which already includes JWT-based authentication and BFT response aggregation.

### Proof of Concept
Conceptual PoC (cannot be executed here, but derivable from the code):
1. Legitimate user A signs and sends a `web_api_trigger` legacy request to the gateway with `MessageId = "X"`, targeting DON `D`. This calls `HandleLegacyUserMessage`, which stores `savedCallbacks["X"] = callbackA` and forwards the signed message to DON `D`'s nodes [12](#0-11) .
2. Before DON `D` responds (within the 120s window), attacker B, with no authentication, sends its own `web_api_trigger` request also using `MessageId = "X"` (valid per `Message.Validate()`, which does not check for uniqueness). This overwrites `savedCallbacks["X"] = callbackB`.
3. When DON `D` node(s) respond to `MessageId = "X"` (from user A's original triggered request), `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, now finds `callbackB`, and delivers user A's response to attacker B [7](#0-6) .
4. User A's original HTTP request stalls until `gateway.ProcessRequest`'s `callback.Wait(ctx)` times out, returning `RequestTimeoutError` [13](#0-12) .

Note: I was unable to fully verify from the index whether this legacy `handler.go` path is still wired into production Gateway deployments alongside the newer v2 `httpTriggerHandler` (which does add JWT auth per its README) or has been fully deprecated/disabled — the coexistence and current default routing configuration would need confirmation via a full checkout of gateway service configuration, since the indexed context shows both implementations present in the repository.
