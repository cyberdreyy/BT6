### Title
Owner-mismatch authorization failures leak the authorized workflow owner and distinguish auth-failure reasons via `HandlerError` responses - ([File: core/services/gateway/gateway.go])

### Summary
When `h.requestProcessor.ProcessRequest` fails authorization in `HandleJSONRPCUserMessage`, the vault handler returns a plain Go `error` (`"request not authorized: " + err.Error()`) instead of using `h.sendImmediateUserResponse` to build a sanitized JSON-RPC error. This error string is propagated unmodified by `gateway.ProcessRequest` into `newError(jsonRequest.ID, api.HandlerError, err.Error())`, which places the raw underlying error text directly in the JSON-RPC `Error.Message` field returned to the caller over HTTP.

### Finding Description
The authorization chain is: `authorizer.AuthorizeRequest` → `validateSecretOwnersMatchAuthorized` (in `core/capabilities/vault/authorizer.go`). When a request's declared secret owner does not match the authenticated caller's authorized owner, the code returns errors such as:
`fmt.Errorf("encrypted secret owner at index %d %q does not match authorized workflow owner %q", idx, encryptedSecret.Id.Owner, workflowOwner)` [1](#0-0) , and similarly for delete/list flows [2](#0-1) .

This error propagates up through `authorizer.AuthorizeRequest` (line 113-116) unmodified [3](#0-2) , into `GatewayVaultRequestProcessor.ProcessRequest`, and then into `handler.HandleJSONRPCUserMessage`'s error branch:
```go
h.lggr.Errorw("request not authorized", ...)
return errors.New("request not authorized: " + err.Error())
``` [4](#0-3) 

Unlike the sibling branch for `IsInvalidVaultParamsError`, which correctly calls `h.sendImmediateUserResponse(ctx, req, callback, api.InvalidParamsError, err)` to produce a controlled JSON-RPC response, this branch instead returns a bare Go `error` from `HandleJSONRPCUserMessage`. That return value is caught in `gateway.ProcessRequest`:
```go
err = h.HandleJSONRPCUserMessage(ctx, jsonRequest, callback)
...
if err != nil {
    return newError(jsonRequest.ID, api.HandlerError, err.Error())
}
``` [5](#0-4) 

`newError` places `err.Error()` verbatim into the JSON-RPC `Error.Message` field of the HTTP response body [6](#0-5) , with no redaction. Because `validateSecretOwnersMatchAuthorized`'s error message embeds the caller's *authorized workflow owner* value (`workflowOwner`) alongside the mismatched requested owner, this discloses to the attacker the true authorized-owner string bound to their auth credential/signature — and more generally, the error text differs qualitatively between different failure classes (e.g., "encrypted secret owner ... does not match authorized workflow owner %q" vs. replay-guard errors vs. JWT/allowlist rejection errors), letting an attacker distinguish "signature/auth mechanism itself failed" from "signature valid but owner field mismatched," and see exactly what owner string the backend associated with their credentials.

No downstream layer sanitizes this: `errorResponse` in the vault handler (used by other paths) does perform message-specific handling per error code, but this particular authorization-failure path bypasses `errorResponse`/`sendImmediateUserResponse` entirely, going straight to a generic `error` return that the gateway echoes without inspection.

### Impact Explanation
This is an information-disclosure issue, not a full authentication/authorization bypass: the request is still rejected (HTTP error, `api.HandlerError` code, no secrets or actions performed). However it discloses internal authorization state — specifically the authorized owner value bound to a caller's signature/JWT — to an unprivileged party who only needs a validly-signed (or validly-JWT'd) request with a *mismatched* owner. This maps to Chainlink's "sensitive information disclosure" bounty class rather than a fund-movement or privilege-escalation class, since no unauthorized action, job run, or fund movement occurs.

### Likelihood Explanation
Trivial to trigger: any unprivileged client capable of producing a validly-signed (or valid-JWT) vault request need only set a mismatched `Owner`/secret ID owner field in the params. No special role or node/DON access is needed — this exactly matches the described threat model (unauthenticated/low-privilege gateway client). It is deterministic and repeatable via a single HTTP call.

### Recommendation
In `core/services/gateway/handlers/vault/handler.go`, replace the raw `errors.New("request not authorized: " + err.Error())` return with a call to `h.sendImmediateUserResponse(ctx, req, callback, api.<AuthorizationError code>, errors.New("request not authorized"))` (or a similarly generic, non-parameterized message), stripping the underlying `err` details from what is returned to the caller while still logging the full `err` server-side via `h.lggr.Errorw`. Additionally, harden `validateSecretOwnersMatchAuthorized`/`validateEncryptedSecretOwnerMismatch`/`validateSecretIdentifierOwnerMismatch` in `core/capabilities/vault/authorizer.go` to avoid embedding the authorized owner value in error messages that could ever reach a client, or ensure all such errors are only ever logged and never forwarded verbatim in HTTP responses.

### Proof of Concept
Handler-level integration test in `core/services/gateway/handlers/vault/handler_test.go`:
1. Set up `h, callback, don, _ := setupHandler(t)` with an allowlist/JWT authorizer configured for owner `0xAAAA`.
2. Submit a `vault.secrets.create` (or `.list`) request signed/authorized as `0xAAAA` but with `EncryptedSecrets[0].Id.Owner` (or `ListSecretIdentifiersRequest.Owner`) set to `0xBBBB`.
3. Call `err := h.HandleJSONRPCUserMessage(ctx, req, callback)`.
4. Assert `err != nil` and `strings.Contains(err.Error(), "0xAAAA")` — demonstrating the authorized owner leaks into the returned error (currently true, proving the bug).
5. Simulate the gateway wrapper: `rawResp, status := gateway.newError(req.ID, api.HandlerError, err.Error())`; unmarshal `rawResp` into a JSON-RPC response and assert `Error.Message` contains the owner string `0xAAAA` — proving the leak reaches the HTTP body.
6. As a companion negative-case test, submit a request with an invalid signature/JWT (auth-mechanism failure, not owner mismatch) and confirm today the error text differs (e.g., "JWT validation failed" vs. "does not match authorized workflow owner"), demonstrating an attacker can distinguish failure reasons.
7. After the fix, re-run steps 3-6 and assert the returned/serialized error message is a generic, non-parameterized string (e.g., `"request not authorized"`) for both cases, with no owner value or mechanism-distinguishing detail present.

func validateEncryptedSecretOwnerMismatch(encryptedSecrets []*vaultcommon.EncryptedSecret, workflowOwner string) error {
	if len(encryptedSecrets) == 0 {
		return errors.New("request batch must contain at least 1 item")
	}
	for idx, encryptedSecret := range encryptedSecrets {
		if encryptedSecret == nil {
			return fmt.Errorf("encrypted secret must not be nil at index %d", idx)
		}
		if encryptedSecret.Id == nil {
			return fmt.Errorf("secret ID must not be nil at index %d", idx)
		}
		if vaultutils.NormalizeOwner(encryptedSecret.Id.Owner) != vaultutils.NormalizeOwner(workflowOwner) {
			return fmt.Errorf("encrypted secret owner at index %d %q does not match authorized workflow owner %q", idx, encryptedSecret.Id.Owner, workflowOwner)
		}
	}
	return nil

func newError(id string, errCode api.ErrorCode, errMsg string) ([]byte, int) {
	response := jsonrpc2.Response[json.RawMessage]{
		Version: jsonrpc2.JsonRpcVersion,
		ID:      id,
		Error: &jsonrpc2.WireError{
			Code:    api.ToJSONRPCErrorCode(errCode),
			Message: errMsg,
			Data:    nil,
		},
	}
	rawResponse, err := json.Marshal(response)
	if err != nil {
		rawResponse = []byte("fatal error" + err.Error())
	}
	promRequest.WithLabelValues(errCode.String()).Inc()
	return rawResponse, api.ToHttpErrorCode(errCode)
}
