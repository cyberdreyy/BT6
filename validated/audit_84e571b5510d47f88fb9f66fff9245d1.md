### Title
KYC/eligibility is only verified at request time — expired-KYC users can still claim tranche tokens and withdraw proceeds - (File: contracts/IdleCDOEpochQueue.sol, contracts/IdleCDOEpochVariant.sol)

### Summary
The external bug is an eligibility check that proves *past* entitlement (holding an ERC1155 minted on first subscription) rather than *current* entitlement (an active subscription). The direct analog in idle-tranches is the Keyring KYC gate: `isWalletAllowed` is enforced live on deposits and withdraw *requests*, but every *claim* path — `IdleCDOEpochQueue.claimDepositRequest`, `IdleCDOEpochQueue.claimWithdrawRequest`, and `IdleCDOEpochVariant.claimWithdrawRequest`/`claimInstantWithdrawRequest` — releases tranche tokens or underlying to `msg.sender` with no eligibility re-check. A user whose KYC lapses (or is revoked) after queueing still mints tranche tokens and collects epoch yield, and since `IdleCDOTranche` is a plain ERC20 with no transfer hooks, the position is freely movable to a KYC'd address for withdrawal.

### Finding Description
`IdleCDOEpochVariant._deposit` checks `isWalletAllowed(msg.sender)` and `requestWithdraw` re-checks it at `contracts/IdleCDOEpochVariant.sol:741-744`. `depositDuringEpoch` does the same at line 668. In the queue, `_checkAllowed` gates `requestDeposit` and `requestWithdraw` at `contracts/IdleCDOEpochQueue.sol:415-421`.

However:

- `claimDepositRequest(_epoch)` (`contracts/IdleCDOEpochQueue.sol:373-389`) transfers freshly minted tranche tokens to `msg.sender` based solely on the stale `userDepositsEpochs` ledger — the KYC check from `requestDeposit` may be epochs old.
- `claimWithdrawRequest(_epoch)` (`contracts/IdleCDOEpochQueue.sol:393-411`) pays underlying to `msg.sender` with no wallet check.
- `IdleCDOEpochVariant.claimWithdrawRequest`/`claimInstantWithdrawRequest` (`contracts/IdleCDOEpochVariant.sol:967-979`) forward to `IdleCreditVault.claim*Request(msg.sender)` without calling `isWalletAllowed`, so the payout goes to whoever holds the receipt even if KYC was revoked.
- `deleteRequest`/`deleteWithdrawRequest` also refund without checks, and `IdleCDOTranche` has no `_transfer`/`isWalletAllowed` hook (no match in the file), so claimed tranche tokens are transferable to any KYC'd wallet that can then call `requestWithdraw` legitimately.

The invariant "only currently-allowed wallets may hold minted tranche positions or receive vault funds" is broken — it is only enforced at request submission, exactly like the report's stale ERC1155 subscription token.

### Impact Explanation
An unprivileged lender queues a deposit while KYC'd, has their credential expire or be revoked (e.g., sanction flag in Keyring), and still calls `claimDepositRequest` to receive tranche tokens plus all accrued epoch yield — participation the pool's compliance model intends to deny. They then either (a) wait for re-credentialing to withdraw, mirroring the original "redeem after renewal" flow, or (b) transfer the unrestricted tranche tokens to a KYC'd address and exit via `requestWithdraw`/`claimWithdrawRequest`. Loss to the protocol is the yield and principal payout to an ineligible wallet, quantified as the full claimed amount (`amount * epochPrice` / `amount * epochWithdrawPrice`), plus a compliance/permit breach on a regulated-lender product where KYC gating is a core advertised control.

### Likelihood Explanation
Requires only a formerly-KYC'd user whose credential lapses between `requestDeposit`/`requestWithdraw` and the claim — a routine event since epochs span days/weeks and Keyring credentials have finite validity. No privileged cooperation, timing race, or capital beyond the deposit itself is needed. Severity is bounded by the fact that the attacker had to be eligible at request time, but the elapsed window across multi-day epochs makes stale eligibility common rather than exceptional.

### Recommendation
Re-check eligibility at claim time, mirroring the report's `getSubDetails` fix:

- In `IdleCDOEpochQueue.claimDepositRequest` and `claimWithdrawRequest`, add `IdleCDOEpochVariant(idleCDOEpoch).isWalletAllowed(msg.sender)` (or reuse `_checkAllowed` minus the `isEpochRunning` requirement, since claims legitimately happen between epochs).
- In `IdleCDOEpochVariant.claimWithdrawRequest`/`claimInstantWithdrawRequest`, add `_checkNotAllowed(!isWalletAllowed(msg.sender))` before forwarding to the strategy.
- Optionally add a transfer hook or claim-time check on `IdleCDOTranche` if the compliance intent is that only allowed wallets may *hold* tranche tokens at all.

### Proof of Concept
Foundry test against the epoch-queue variant (adapt existing `test/foundry/IdleCDOEpochQueue.t.sol` setup with mocked Keyring):

```solidity
function test_claimAfterKycRevoked() external {
    // epoch running, keyring returns true
    vm.mockCall(keyring, abi.encodeWithSelector(IKeyring.checkCredential.selector), abi.encode(true));

    // alice queues a deposit for next epoch while KYC'd
    deal(address(underlying), alice, 1000e6);
    vm.startPrank(alice);
    underlying.approve(address(queue), 1000e6);
    queue.requestDeposit(1000e6);
    vm.stopPrank();

    // buffer period: owner processes deposits, epoch price set
    _stopCurrentEpoch();
    vm.prank(owner);
    queue.processDeposits();
    uint256 epoch = strategy.epochNumber();

    // Keyring revokes alice's credential
    vm.mockCall(keyring, abi.encodeWithSelector(IKeyring.checkCredential.selector), abi.encode(false));

    // alice cannot deposit or requestWithdraw anymore (sanity check)
    vm.startPrank(alice);
    vm.expectRevert(NotAllowed.selector);
    queue.requestDeposit(1e6);

    // ...but still claims tranche tokens minted for the stale request
    uint256 balBefore = IERC20(tranche).balanceOf(alice);
    queue.claimDepositRequest(epoch);        // succeeds despite revoked KYC
    assertGt(IERC20(tranche).balanceOf(alice), balBefore);

    // tranche tokens are unrestricted: move to a KYC'd address to exit
    address kycHolder = makeAddr("kycHolder");
    IERC20(tranche).transfer(kycHolder, IERC20(tranche).balanceOf(alice));
    vm.stopPrank();
}
```

Same pattern applies to `claimWithdrawRequest` (queue) and `IdleCDOEpochVariant.claimWithdrawRequest`/`claimInstantWithdrawRequest`: revoke the mock, then claim pays underlying to the revoked wallet without revert.

Caveat: this is an access-control/eligibility-class finding rather than a direct vault-price manipulation; the fund impact is the payout/yield delivered to an ineligible wallet plus the KYC-gating invariant breach. If the audit treats Keyring revocation semantics as out of scope (Keyring admin is honest per the rules — this relies on a legitimately honest revocation, not a malicious one), it may be downgraded.
