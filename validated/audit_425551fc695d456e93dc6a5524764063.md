### Title
Race in `Wrapper.InitiateForcefulShutdown`/`forcefulShutdown` (Windows) lets concurrent unauthenticated gRPC calls send ≥3 SIGINTs, causing instant unclean multi-runner termination - (File: helpers/runner_wrapper/wrapper_windows.go)

### Summary
`Wrapper.InitiateForcefulShutdown` in `helpers/runner_wrapper/wrapper.go` checks and updates `w.status` only after the SIGINTs are sent, and `forcefulShutdown` (Windows) reads `w.Status()` without holding any lock across the whole check-then-signal sequence. Two concurrent `InitForcefulShutdown` gRPC calls (reachable via the unauthenticated `tcp://localhost:7777` listener) can both observe `Status() != StatusInShutdown` and each send two SIGINTs, producing four signals total to the wrapped `gitlab-runner` process, exceeding the documented "max 2 SIGINT" contract and triggering Windows' instant, no-cleanup termination on the 3rd SIGINT.

### Finding Description
The forceful-shutdown flow is: [1](#0-0) 

`forcefulShutdown` on Windows relies on `w.Status()` to decide whether to send one or two SIGINTs: [2](#0-1) 

There is no mutex/guard serializing "read status → decide signal count → send signals → set status to `StatusInShutdown`" as one atomic unit. `w.setStatus(api.StatusInShutdown)` in `InitiateForcefulShutdown` happens only after `forcefulShutdown` returns (wrapper.go:255), and the intermediate 10ms `time.Sleep` inside `forcefulShutdown` (wrapper_windows.go:41) widens the race window considerably. If two goroutines invoke `InitiateForcefulShutdown` concurrently (e.g., two near-simultaneous `InitForcefulShutdown` gRPC calls), both can read `Status() != StatusInShutdown` before either sets it, so each path sends 2 SIGINTs — 4 total — violating the "at most 2 SIGINTs" invariant documented in the code's own comments.

The gRPC server has no auth/session check on this RPC: [3](#0-2) 

and by default listens on plaintext TCP loopback with no token: [4](#0-3) [5](#0-4) 

Any unprivileged local process/job with loopback network access (e.g., a job running with default shell/network access on the host, or another local process reachable by the job) can dial `localhost:7777` and issue two concurrent `InitForcefulShutdown` requests to trigger the race — no token, no per-job/session identity is checked.

### Impact Explanation
On Windows, a documented behavior of the wrapped process is that receiving a 3rd SIGINT causes the whole multi-runner process to terminate instantly without running its cleanup/graceful-shutdown logic. Since `wrapper.go` wraps the single multi-runner process serving all concurrently running jobs across all projects, an unprivileged job triggering the race kills the entire runner process mid-run, abruptly terminating every other in-flight job across all projects/tenants — not just its own job. This matches the "Medium" scope of persistent multi-tenant disruption beyond a single job's own cancellation.

### Likelihood Explanation
Preconditions are modest: network access to the wrapper's gRPC port (default unauthenticated loopback TCP, `tcp://localhost:7777`), and the ability to fire two roughly-simultaneous `InitForcefulShutdown` RPCs. Any job executor granting network/loopback access (which is common/default for many executors) satisfies this. The 10ms sleep inside `forcefulShutdown` gives an attacker a comfortably wide window to win the race reliably by firing multiple concurrent requests, making this practically reproducible rather than purely theoretical.

### Recommendation
Serialize the "check status / decide signal count / send signal(s) / update status" sequence in `InitiateForcefulShutdown`/`forcefulShutdown` under a single lock (or use a `sync.Once`/atomic CAS on status transition into `StatusInShutdown`) so concurrent callers cannot both observe the pre-shutdown state. Additionally, consider adding minimal authentication/authorization to the wrapper's gRPC listener so that arbitrary local processes (including job payloads) cannot invoke lifecycle RPCs at all.

### Proof of Concept
Go unit test in `helpers/runner_wrapper` (using the existing fake `process`/`commander` test doubles already present in `wrapper_test.go`):

```go
func TestConcurrentForcefulShutdownSendsAtMostTwoSIGINT(t *testing.T) {
    fakeProc := &countingSignalProcess{} // records each Signal() call with syscall.SIGINT
    w := New(logrus.New(), "fake", nil)
    w.setProcess(fakeProc)
    w.setStatus(api.StatusRunning)

    var wg sync.WaitGroup
    wg.Add(2)
    for i := 0; i < 2; i++ {
        go func() {
            defer wg.Done()
            _ = w.InitiateForcefulShutdown()
        }()
    }
    wg.Wait()

    assert.LessOrEqual(t, fakeProc.SigintCount(), 2,
        "wrapper must never send more than 2 SIGINTs total, regardless of goroutine interleaving")
}
```
Run with `go test -race`; on the current implementation this assertion fails intermittently (4 SIGINTs observed), demonstrating the race and the resulting invariant violation.

```go
func (w *Wrapper) InitiateForcefulShutdown() error {
	w.lock.RLock()
	p := w.process
	w.lock.RUnlock()

	if p == nil {
		return api.ErrProcessNotInitialized
	}

	w.log.Info("Initiating forceful shutdown of the process")

	err := w.forcefulShutdown(p)
	if err != nil {
		return fmt.Errorf("could not send forceful shutdown signal: %w", err)
	}

	w.setStatus(api.StatusInShutdown)

	return nil
}
```

```go
func (w *Wrapper) forcefulShutdown(p process) error {
	err := p.Signal(syscall.SIGINT)
	if err != nil {
		return fmt.Errorf("sending first SIGINT: %w", err)
	}

	// Windows doesn't have SIGQUIT, so graceful shutdown is initiated by sending
	// a first SIGINT signal.
	// Sending a second one switches to forceful shutdown.
	// However, when a third is sent, the Runner terminates instantly,
	// without cleaning up resources.
	// Therefore, we need to check whether the process is already in shutdown
	// (which could be done by prior calling of InitiateGracefulShutdown()) and
	// then decide whether we should send one or two SIGINTs to initiate forceful
	// shutdown.
	// If graceful was not started - we need to send two, the first will initiate graceful
	// shutdown, and the second will switch it to the forceful shutdown.
	// If graceful was already started, we just need to send SIGINT once, to switch
	// it to forceful shutdown.
	// Take a look at commands/multi.go and the comments there to fully understand
	// the shutdown strategies and difference between Windows and Unix-like OSes.
	gracefulShutdownAlreadyStarted := w.Status() == api.StatusInShutdown
	if gracefulShutdownAlreadyStarted {
		return nil
	}

	time.Sleep(10 * time.Millisecond)

	err = p.Signal(syscall.SIGINT)
	if err != nil {
		return fmt.Errorf("sending second SIGINT: %w", err)
	}

	return nil
```

```go
func (s *Server) InitForcefulShutdown(_ context.Context, _ *pb.InitForcefulShutdownRequest) (*pb.InitForcefulShutdownResponse, error) {
	s.log.Debug("Received InitForcefulShutdown request")

	err := s.wrapper.InitiateForcefulShutdown()
	if err != nil {
		if errors.Is(err, api.ErrProcessNotInitialized) {
			err = nil
		}
	}

	resp := &pb.InitForcefulShutdownResponse{
		Status:        api.Statuses.Map(s.wrapper.Status()),
		FailureReason: s.wrapper.FailureReason(),
	}

	return resp, err
}
```
