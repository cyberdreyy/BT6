## Finding

### Title
Signer weight double-counted across approve/reject tallies when a signer flips its vote for the same block - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
`StackerDBListener` tallies each signer's weight into `total_weight_approved` or `total_weight_rejected` for a given block using two *different* guard sets (`gathered_signatures` for accept, `responded_signers` for reject/accept-marking). Because these guards are not mutually exclusive against each other in the Reject→Accept direction, a single signer that first rejects and later accepts the same block (a state transition the signer protocol explicitly allows via re-evaluation, see `docs/signer-flows.md` `LocallyRejected --> LocallyAccepted : re-evaluated`) has its weight counted into **both** `total_weight_rejected` and `total_weight_approved`. This mirrors the `distributableERC20s` bug class: a mutable per-entity accounting structure ends up double-crediting one participant because two code paths use inconsistent "already counted" checks.

### Finding Description
`BlockStatus` tracks two independent structures per block: [1](#0-0) 

On `BlockResponse::Accepted`, the code only adds weight if the slot is **not yet in `gathered_signatures`**, then inserts the slot into both `gathered_signatures` and `responded_signers`: [2](#0-1) 

On `BlockResponse::Rejected`, the code only adds weight if the slot was **not yet in `responded_signers`**: [3](#0-2) 

The Reject handler marks the slot in `responded_signers` but *never* touches `gathered_signatures`. Consequently:
- Reject arrives first → `responded_signers.insert(slot_id)` succeeds → weight added to `total_weight_rejected`.
- Accept arrives later (same slot, same block, e.g. signer re-evaluated) → the accept guard checks `gathered_signatures.contains_key(&slot_id)`, which is still `false` (the reject path never touched it) → weight is added to `total_weight_approved` as well.

The result: this signer's weight is now present in **both** `total_weight_approved` and `total_weight_rejected` for the same block, breaking the intended invariant that each signer's weight should count toward at most one bucket of the same tally. The reverse direction (Accept then Reject) is correctly guarded, because Accept also inserts into `responded_signers`, so a later Reject's `responded_signers.insert` is a no-op — but the Reject-then-Accept direction has no equivalent protection.

This tally feeds the miner-side coordinator's decision logic, which checks rejection weight first and approval weight second: [4](#0-3) 

Since `total_weight_rejected` is monotonic and never decremented when a signer flips to accept, the "phantom" rejection weight from a since-flipped signer persists indefinitely for that block. If enough signers exhibit this reject→accept pattern (or even a handful near the 30% blocking-minority boundary), `total_weight_rejected + weight_threshold > total_weight` can become true using weight that no longer reflects a live rejection, causing the coordinator to treat a block as rejected via `NakamotoNodeError::SignersRejected` even though the real, current disposition of signers might support acceptance. Because the reject-check is evaluated before the accept-check (`if ... else if ...`), a false rejection verdict can suppress mining of an otherwise validly-signable block.

### Impact Explanation
This breaks the aggregated-weight vs. verified-accepts equality that the tally is supposed to preserve: the sum of `total_weight_approved` + `total_weight_rejected` for one block can exceed the true `total_weight` of distinct responding signers, because one signer's weight is double-credited. Concretely, this allows a single signer (a "one slot" participant, reachable purely via ordinary StackerDB gossip messages — no majority collusion required) to inflate the rejection tally with weight that has since been superseded by an acceptance, potentially causing the node-side coordinator to falsely conclude a rejection threshold was crossed (`SignersRejected`) for a block that in fact has sufficient live signer support, or to exclude transactions (`temporarily_excluded_txids`/`permanently_excluded_txids`) based on stale/duplicated failed-txid weight. This is a liveness-affecting miscount in the miner/coordinator's vote tally, matching the "rejection recounted as acceptance" / miscounted-response impact class.

### Likelihood Explanation
Only a single signer needs to send a `Rejected` response followed later by an `Accepted` response for the same `signer_signature_hash` — a scenario the signer state machine explicitly permits (`should_reevaluate_block` / `LocallyRejected --> LocallyAccepted`). No majority collusion, key compromise, or auth token is needed; it can happen from ordinary re-evaluation behavior of a single honest-but-flip-flopping signer, or be deliberately triggered by one malicious signer.

### Recommendation
Track a single "current disposition + weight" per slot rather than two independently-guarded weight totals, or make the Accept path check/clear the slot's prior contribution to `total_weight_rejected` (and vice versa) before crediting the new bucket, ensuring each slot's weight is retracted from whichever bucket it previously counted toward before being credited to the other.

### Proof of Concept
1. Node's `StackerDBListener` tracks a `BlockStatus` for `signer_signature_hash = H`.
2. Signer S (slot_id = 5, weight = W) sends `BlockResponse::Rejected` for H → `responded_signers = {5}`, `total_weight_rejected += W`.
3. Signer S re-evaluates and later sends `BlockResponse::Accepted` for H (signed after re-checking chain state, per `handle_block_pre_commit` re-evaluation flow) → guard `!gathered_signatures.contains_key(&5)` is `true` (never populated by step 2) → `total_weight_approved += W`, `gathered_signatures.insert(5, sig)`.
4. Now `total_weight_approved + total_weight_rejected` includes `W` twice for the same slot, even though only one live vote exists.
5. If aggregate rejected weight (including the stale `W`) crosses `weight_threshold` distance from `total_weight`, `signer_coordinator.rs`'s `get_block_status` loop returns `NakamotoNodeError::SignersRejected` despite S's live vote being an accept. [2](#0-1) [3](#0-2) [4](#0-3)
