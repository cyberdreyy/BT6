### Title
Post-default withdraw requests are paid 1:1 from the fixed `defaultRecoveryReserve`, draining funds reserved for defaulted-epoch claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external report (CVE-2015-7849, use-after-free) maps to a stale/dangling-state bug: after `finalizeDefaultRecovery` fixes `defaultRecoveryReserve` and `defaultRecoveryPrice` to cover exactly the defaulted claims at a haircut, `requestWithdraw` still lets any tranche holder create a new `postDefaultRequests` receipt with **no new underlying funding**, and `_claimPostDefaultWithdrawRequest` pays it **1:1 out of that same fixed reserve**. The reserve is "freed" accounting being reused by a claim class it was never sized for.

### Finding Description
- `finalizeDefaultRecovery` computes `reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` and `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis`. When `recoveryPrice < RECOVERY_FULL` (any partial recovery), the reserve can satisfy `claimBasis * recoveryPrice` for defaulted claimants — and nothing more.
- After finalization, `requestWithdraw` (IdleCreditVault.sol:247-257) skips all funding: it burns the CDO's strategy tokens, mints the user a receipt, and sets `postDefaultRequests[_user] = _amount`. No underlying is transferred in and `pendingWithdraws`/`defaultRecoveryReserve` are unchanged.
- `_claimPostDefaultWithdrawRequest` (IdleCreditVault.sol:760-767) then does `defaultRecoveryReserve -= amount` and transfers `amount` **at par**, not at `defaultRecoveryPrice`.
- In the same call, `claimWithdrawRequest` (IdleCreditVault.sol:301-313) falls through to `_claimFundedWithdrawRequest`, whose `_transferFundedClaim` guard (IdleCreditVault.sol:904) only protects the reserve from *funded* claims — it does not stop post-default claims from consuming the reserve itself.

Attack sequence (defaulted/finalized phase):
1. Borrower defaults; manager finalizes recovery at e.g. 50% (`defaultRecoveryPrice = RECOVERY_FULL/2`). Reserve R exactly covers defaulted claims at the haircut.
2. Attacker (any KYC'd tranche holder) calls `cdoEpoch.requestWithdraw` → `postDefaultRequests[attacker] = amount`, no funding.
3. Attacker calls `cdoEpoch.claimWithdrawRequest` → receives `amount` at 1:1 from the reserve (up to 2x the fair share).
4. Repeat until the reserve is drained; defaulted-epoch claimants then hit `defaultRecoveryReserve -= amount` underflow/insufficient balance and can never claim — permanent freezing of their recovery.

### Impact Explanation
Direct theft plus permanent freezing of unclaimed recovery: the attacker extracts underlying at par from a reserve valued at a haircut, up to 2x overpayment per unit (unbounded across repeated requests), and each drained wei is a wei a legitimate defaulted claimant can no longer receive. This breaks the "one receipt, one haircut payout" invariant and the recovery-reserve isolation the code comments claim.

### Likelihood Explanation
Requires only a default with `recoveryPrice < 1` and an unprivileged tranche holder acting before other claimants — no privileged cooperation, no timing race beyond being first. Every post-default request is fully unbacked, so the drain is deterministic.

### Recommendation
Either fund post-default requests at request time (transfer underlying in, or require the CDO to supply it) and keep them out of `defaultRecoveryReserve`, or pay them at `defaultRecoveryPrice` and account their basis into the reserve at finalization. At minimum, route post-default payouts through a separate funded bucket rather than `_transferDefaultRecovery`.

  function _claimPostDefaultWithdrawRequest(address _user) internal returns (uint256 amount) {
    amount = postDefaultRequests[_user];
    if (amount == 0) return amount;
    postDefaultRequests[_user] = 0;
    // Post-default receipts are paid 1:1 because the haircut was applied when the request was made.
    _burn(_user, amount);
