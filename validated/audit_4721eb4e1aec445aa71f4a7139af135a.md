## Finding

### Title
Unprivileged workflow caller can block another workflow's legitimate HTTP trigger request via global, unscoped `requestID` collision - (File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go)

### Summary
The Alchemix report describes an attacker manipulating a piece of shared state (`proposalThreshold`) that a legitimate user's transaction depends on at execution time, causing the legitimate transaction to revert and the honest user to be impeded. The chainlink analog is in the CRE gateway's HTTP trigger handler: pending requests are tracked in a single, gateway-wide map keyed only by the caller-supplied `requestID`, with no per-workflow or per-owner namespacing. Any authenticated-but-unrelated workflow caller can pick an ID that collides with another workflow's in-flight or about-to-be-submitted request, causing the victim's genuine trigger call to be rejected.

### Finding Description
`httpTriggerHandler.setupCallback` stores pending trigger callbacks in `h.callbacks`, a `map[string]savedCallback` keyed purely by the JSON-RPC `requestID` string supplied in the request:
<cite repo="EzraCole/chainlink--025" path="core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go" start="398="405" /> [1](#0-0) 

```go
func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)

``` [2](#0-1) 

The check is a bare existence check against `requestID` alone, `workflowID` is used only afterward to build the response aggregators, it is never combined into the map key. `HandleUserTriggerRequest` calls `setupCallback` only after authorizing the caller for its *own* `workflowID` via `authorizeRequest`/`WorkflowMetadataHandler.Authorize`, but authorization is scoped to whether the caller may act on their workflow, not whether they may claim a particular global `requestID`: [3](#0-2) 

Consequently, two entirely unrelated, independently-authorized workflow owners (Workflow A's key holder and Workflow B's key holder — both "unprivileged" relative to each other and to the gateway) share one global identifier namespace. The existing regression test confirms the collision behavior end-to-end for a single workflow (attacker resubmits the same `requestID` and the victim receives `jsonrpc.ErrConflict`): [4](#0-3) 

Because the map is global rather than namespaced by `workflowID` (or by the authorized key/owner), the same collision denial applies across workflows, not merely within one: a malicious client that knows or predicts a target's chosen `requestID` (e.g., sequential/UUID-timestamp based IDs, IDs observed in logs/telemetry, or externally coordinated IDs shared between cooperating/competing workflow operators) can pre-register that ID for its own (different) workflow just before the victim's legitimate trigger request arrives, causing the victim's request to fail with `jsonrpc.ErrConflict` — exactly the "impeded from submitting a legitimate operation via manipulation of shared state" pattern in the report. This is reachable from a normal, unprivileged client and does not require operator or malicious-node/peer access — only a valid signed JWT for *some* workflow the attacker legitimately controls, per `authorizeRequest`: [5](#0-4) 

### Impact Explanation
An attacker who legitimately controls any workflow on the same gateway/DON can deny service to any other workflow's HTTP-triggered execution by winning a race to register a colliding `requestID` first. Because trigger requests are user/business-critical (each is a workflow execution), this causes targeted denial-of-service against a specific unrelated workflow execution, undermining availability guarantees of the trigger capability. It does not, by itself, leak secrets or bypass authentication, so severity is bounded to griefing/DoS of individual requests rather than fund loss or credential disclosure.

### Likelihood Explanation
Exploitability depends on the attacker being able to predict or learn the victim's `requestID` before the victim's call lands, and on the attacker independently controlling any authorized workflow. If `requestID`s are generated with unpredictable randomness (e.g., full UUIDv4) client-side, likelihood is lower; if callers use predictable/sequential/deterministic IDs (a common integration pattern, and one the code explicitly allows since it only requires a caller-chosen unique string), the collision window is easy to win, making this a Low-to-Medium likelihood issue given attacker still needs a valid signed JWT for a workflow they control.

### Recommendation
Scope the `h.callbacks` map (and its lock/reap logic) by a composite key that includes `workflowID` (or the authorized owner/key) together with `requestID`, e.g. `key := workflowID + "/" + requestID`, instead of `requestID` alone. This restores the intended invariant ("requestID must be unique per caller/workflow") without allowing cross-workflow collisions, and matches the recommended fix pattern of eliminating shared global state that unrelated unprivileged actors can influence to affect one another.

### Proof of Concept
1. Workflow A registers with the gateway and prepares to send `HandleUserTriggerRequest` with `req.ID = "shared-id"`.
2. Workflow B (unrelated, but with its own valid authorized key/JWT) sends `HandleUserTriggerRequest` first with the same `req.ID = "shared-id"` for its own `workflowID`; `setupCallback` inserts `h.callbacks["shared-id"]`.
3. Workflow A's request now hits the `found` branch in `setupCallback` and receives `jsonrpc.ErrConflict` ("requestID: shared-id has already been used..."), exactly as reproduced (single-workflow variant) in the existing test: [4](#0-3) 
Because the map key omits `workflowID`, the same mechanism denies Workflow A's request even though Workflow B's request belongs to a completely different, unrelated workflow.

func (h *httpTriggerHandler) authorizeRequest(ctx context.Context, workflowID string, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback) (*gateway_common.AuthorizedKey, error) {
	h.lggr.Debugw("authorizing request", "workflowID", workflowID, "requestID", req.ID)
	key, err := h.workflowMetadataHandler.Authorize(workflowID, req.Auth, req)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInvalidRequest, "Auth failure: "+err.Error(), callback)
		return nil, errors.Join(errors.New("auth failure"), err)
	}
	return key, nil
}

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}

	// Build one response aggregator per shard the workflow is assigned to.
	assigned := h.workflowMetadataHandler.WorkflowShards(workflowID)
	if len(assigned) == 0 {
		// this shouldn't happen because we checked it in authorizeRequest()
		h.handleUserError(ctx, requestID, jsonrpc.ErrInternal, fmt.Sprintf("Workflow %s is not assigned to any DONs", workflowID), callback)
		return nil, errors.New("workflow is not assigned to any shards")
	}
