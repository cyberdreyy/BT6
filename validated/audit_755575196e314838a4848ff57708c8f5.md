### Title
Storage writes made before a WASM trap are committed to the trie while `storage_usage`/balance bookkeeping is skipped, leaving unbilled bytes on the account - ([File: runtime/runtime/src/function_call.rs])

### Summary
`RuntimeExt::storage_set`/`storage_remove` write directly into the shared, live `TrieUpdate` (`state_update`) as soon as the host call executes, regardless of what happens later in the same contract call. `action_function_call` only gates `account.set_amount`/`account.set_storage_usage` (and receipt creation) behind `execution_succeeded = outcome.aborted.is_none()`, but it never undoes the `TrieUpdate` mutations that a trapped contract already performed. A contract that writes a large value and then deterministically traps therefore leaves real trie bytes committed for account `C` while `C.storage_usage()` is left at its pre-call value.

### Finding Description
`RuntimeExt::storage_set` (`runtime/runtime/src/ext.rs:147-186`) calls `self.trie_update.set(storage_key, Vec::from(value))` unconditionally on every `storage_write` host call: [1](#0-0) 
`self.trie_update` is not a scratch/temporary buffer — it is the `&'a mut TrieUpdate` passed into `RuntimeExt::new` from `action_function_call`'s own `state_update: &mut TrieUpdate` parameter: [2](#0-1) [3](#0-2) 
Writes land in `TrieUpdate.prospective` (`core/store/src/trie/update.rs:35`), the same map used for every other action in the receipt/chunk; there is no per-action checkpoint/rollback API on `TrieUpdate` in this codebase (only `committed`/`prospective` and a whole-update `commit`/finalize path), so a write made before a trap is never removed from `prospective`.

Meanwhile, in `action_function_call`, once the VM returns an outcome with `aborted.is_some()`, `execution_succeeded` is `false`, and the block that applies `account.set_amount(outcome.balance)` / `account.set_storage_usage(outcome.storage_usage)` is skipped entirely: [4](#0-3) [5](#0-4) 
So on a trap, `account.storage_usage()` is left exactly as it was before the call — but any `storage_write` calls the contract performed before the trap have already been applied to `state_update` via `RuntimeExt::storage_set`. There is no code path that reverts those trie mutations when `execution_succeeded` is `false`. The only things gated by `execution_succeeded` are the account's bookkeeping fields and the new receipts; the trie side effects are not part of that gate.

An unprivileged attacker can trigger this simply by deploying a contract with a method that calls `storage_write` and then traps (e.g., an `unreachable` instruction, integer divide-by-zero, or explicit `panic`) and invoking it via an ordinary `FunctionCall` action — no special privileges, keys, or validator access required.

### Impact Explanation
This causes account `C`'s trie state to grow (real bytes stored) without a corresponding increase in `C.storage_usage()`. Any downstream enforcement of the storage-staking invariant (`amount >= storage_usage * storage_byte_cost`) reads the stale, understated `storage_usage`, so the account is never required to hold balance backing the extra bytes it actually stores. This is a state-rent/storage-staking bypass: the account can accumulate unbilled trie bytes indefinitely by repeating the write-then-trap pattern, understating its true storage requirement — falling under "balance manipulation / stealing" (storage rent theft) rather than direct fund theft.

### Likelihood Explanation
Preconditions are trivial and fully within an ordinary user's capability: deploy any wasm contract with a method that performs one or more `storage_write` calls followed by a deterministic trap, then submit a `FunctionCall` transaction/receipt invoking it. Cost is only the gas for the call up to the trap point (which the attacker still pays), and the technique is fully repeatable per call, so bytes can be accumulated over many calls at minimal marginal cost. No race conditions or validator cooperation are needed.

### Recommendation
Ensure trie mutations and storage-usage/balance bookkeeping are committed or discarded together. Either:
- Buffer `storage_write`/`storage_remove` mutations made during a single `FunctionCall`'s WASM execution in a per-call scratch changeset and merge it into `state_update` only when `execution_succeeded` is true, discarding it otherwise (symmetric rollback), or
- If persisting writes-before-trap is intentional protocol behavior, also unconditionally apply `account.set_storage_usage(outcome.storage_usage)` (and the corresponding balance delta) even in the aborted case, so billed usage always matches the bytes actually left in the trie.

### Proof of Concept
1. Deploy a test contract exposing a method `write_then_trap` that calls `storage_write(key, large_value)` (e.g., several KB) and then executes an `unreachable`/trap instruction.
2. In a runtime/apply-level integration test (e.g. under `runtime/runtime/src/tests` or `integration-tests`), construct a `FunctionCall` action receipt invoking `write_then_trap`, run it through `action_function_call`/`apply_action_receipt`.
3. Assert:
   - `outcome.aborted.is_some()` (trap occurred, `FunctionCallError::WasmTrap`).
   - `account.storage_usage()` after the call equals the pre-call value (unchanged), confirming the billing skip at `function_call.rs:151-227`.
   - The write is nevertheless observable in `state_update` (e.g. `state_update.get_ref(&TrieKey::ContractData{...}, ...)` returns the written value, or after `state_update.commit(...)`/`finalize()` the value is present in the resulting trie/state root), confirming the trie mutation was not rolled back.
4. The combination (`storage_usage` unchanged AND the write present post-commit) violates the expected commit/discard symmetry and demonstrates the finding.
