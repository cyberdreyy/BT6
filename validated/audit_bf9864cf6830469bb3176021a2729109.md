### Title
Unsigned integer underflow in gateway legacy message staleness check allows anti-replay bypass - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
`handler.HandleLegacyUserMessage` performs the "stale message" freshness check using unsigned (`uint`) subtraction on attacker-influenced values without any bounds validation, mirroring the class of bug described in the external report (arithmetic operations that don't correctly detect out-of-range/overflow conditions and silently produce an incorrect, security-relevant result).

### Finding Description
The legacy gateway message handler validates a request's freshness like this: [1](#0-0) 

Specifically:
```go
if uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp) {
    // reject as stale
}
```
`h.config.MaxAllowedMessageAgeSec` is a `uint` operator-configured constant, and `payload.Timestamp` is decoded straight from the attacker-supplied JSON payload of an unauthenticated legacy gateway message (`HandleLegacyUserMessage` is invoked from `gateway.ProcessRequest` for legacy DON-routed requests, i.e. directly from the internet-facing user endpoint of the gateway): [2](#0-1) 

Because the subtraction and comparison are both performed as unsigned `uint` (64-bit) arithmetic, this is exactly the class of bug flagged in the external report: signed/negative or out-of-range inputs are not detected before the arithmetic is performed, so the check silently computes an incorrect result instead of failing safe. If `payload.Timestamp` is attacker-controlled and can be a negative number (or any value whose `uint()` conversion wraps to a very large 64-bit value), the right-hand side of the comparison becomes enormous, making `LHS > RHS` always false — the "stale message" branch is never taken regardless of the request's real age. This defeats the intended anti-staleness/anti-replay protection for the `web_api_trigger` message path.

Notably, the code immediately preceding the vulnerable check is annotated: [3](#0-2) 
`// TODO: apply allowlist and rate-limiting here` — confirming this legacy trigger-message path currently has no allowlist or rate-limiting protection either, so the staleness check is one of very few safeguards on this reachable, unprivileged-client endpoint.

### Impact Explanation
If the staleness check can be defeated, previously captured/old `web_api_trigger` messages (or messages with crafted out-of-range timestamps) can be replayed against DON nodes indefinitely, bypassing the intended "message too old" anti-replay safeguard on an internet-facing gateway endpoint. Combined with the missing allowlist/rate-limiting (explicitly marked TODO) on the same code path, this weakens the request-impersonation/replay protections at the gateway boundary that an unprivileged client interacts with directly.

### Likelihood Explanation
Reachability from an unprivileged client is confirmed: `HandleLegacyUserMessage` is called directly from `gateway.ProcessRequest`, the entry point for user-submitted JSON-RPC requests to the gateway, with no signature/authorization check visible ahead of the staleness check. The remaining uncertainty is the exact Go type of `webapicap.TriggerRequestPayload.Timestamp` (I was not able to load its definition within the available tool budget); if it is an unsigned type at JSON-decode time, the underflow trigger described here does not apply directly, though the general risk of unvalidated, unsigned time-delta arithmetic in this stale-check remains a robustness/logic concern.

### Recommendation
Validate `payload.Timestamp` is non-negative and perform the freshness comparison in signed 64-bit arithmetic (or use `time.Unix(payload.Timestamp, 0)` and `time.Since`/`Sub` with explicit bounds checks) instead of subtracting into an unsigned type. Additionally, implement the still-TODO allowlist and rate-limiting enforcement for this legacy `web_api_trigger` message path.

### Proof of Concept
Not independently reproduced (would require exercising the live gateway with a crafted legacy JSON-RPC request containing a negative or out-of-range `Timestamp`); the vulnerable logic itself is directly cited above.
