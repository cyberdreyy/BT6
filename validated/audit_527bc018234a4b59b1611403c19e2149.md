### Title
`ActivationRegistry.setAdmin` performs a single-step admin transfer with no push/pull safeguard, risking permanent, irrecoverable loss of the activation admin role - (File: crates/common/precompiles/src/activation/storage.rs)

### Summary
The activation registry precompile's `setAdmin` immediately overwrites the admin storage slot in one transaction, with no staging/acceptance step. This is the exact bug class described in ADM-1: a privileged role transfer that can be sent to the wrong address with no recovery path. The codebase's own `PolicyRegistry` precompile demonstrates the team already knows the correct pattern — it implements `stageUpdateAdmin` / `finalizeUpdateAdmin` two-step transfer — but the more privileged `ActivationRegistry` admin was never given the same protection.

### Finding Description
`ActivationRegistryStorage::set_admin` writes `new_admin` directly to the `admin` storage slot as soon as the current admin calls it, with no intermediate "pending admin" step requiring the new address to accept the role: [1](#0-0) 

The dispatcher wires `IActivationRegistry::setAdminCall` straight into this one-shot write: [2](#0-1) 

The only mitigations present are a zero-address check and an admin-caller check — neither of which protects against a *valid but wrong* address (e.g., a checksum/typo error, a contract address without the ability to call back, or the wrong environment's admin key): [3](#0-2) 

Contrast this with the `PolicyRegistry` precompile in the same codebase, which implements exactly the two-step push/pull pattern recommended by ADM-1 — `stageUpdateAdmin` writes a pending admin, and `finalizeUpdateAdmin` requires the pending admin itself to call in and accept the role: [4](#0-3) [5](#0-4) 

The activation registry admin is a singleton, chain-wide role: it is the sole account authorized to `activate`/`deactivate` the `PolicyRegistry`, `B20Stablecoin`, and `B20Asset` features gating the entire native B-20 token system: [6](#0-5) [7](#0-6) 

Because `set_admin` requires no acceptance by the destination address, an admin fat-fingering the `newAdmin` argument (or targeting a contract/address that cannot itself send transactions back) permanently and irrecoverably loses the activation admin role in a single transaction — there is no relinquish/renounce function and no way to "pull" the role back.

### Impact Explanation
Losing the activation admin permanently freezes the ability to activate or deactivate any Base-native precompile feature (policy registry, B20 stablecoin, B20 asset) going forward: any feature not yet activated can never be activated, and any currently-active feature can never be deactivated (e.g., to respond to a discovered bug), since `admin()`'s effective value is derived solely from this one non-recoverable storage slot once state-backed admin is enabled: [8](#0-7) 

This is a chain-wide governance/control-plane freeze with no remediation path short of a hard fork, meeting the "permanent freezing" bar for privileged system functionality.

### Likelihood Explanation
The path is reachable by a single signed transaction from the current, legitimately authorized activation admin — the same operational actor targeted by ADM-1/GLOBAL-1. No attacker interaction is required; the class of error (wrong address, typo, wrong key material for the intended environment) is a well-documented real-world failure mode for one-step ownership transfers, which is precisely why the team implemented the two-step alternative elsewhere in the same repository (`PolicyRegistry`) but not here.

### Recommendation
Adopt the same push/pull pattern already implemented for `PolicyRegistry` (`stageUpdateAdmin` / `finalizeUpdateAdmin`) for the activation registry: add a `pendingAdmin` storage slot, have `setAdmin` (or a renamed `stageAdmin`) only stage the proposed address, and require the proposed admin to call a new `acceptAdmin`/`finalizeAdmin` function from that address before the role transfers. Optionally add an explicit `renounceAdmin` if voluntary relinquishment is desired, consistent with the ADM-1 recommendation.

### Proof of Concept
1. Chain is configured with Cobalt's state-backed activation admin enabled (`ActivationAdminConfig::state_backed`), current admin = `A`.
2. Admin `A` calls `ActivationRegistry.setAdmin(newAdmin)` with an incorrectly-typed/checksummed address `B'` (not the intended `B`), as in `set_admin` at [9](#0-8) .
3. The call succeeds immediately (`new_admin` is non-zero and caller was the prior admin), and `admin` storage is overwritten to `B'` with an `AdminChanged` event.
4. No account controls `B'` (it's an EOA typo/dead address). All subsequent `activate`/`deactivate`/`setAdmin` calls from `A` now revert as `Unauthorized`, per the `require_admin_caller` gate exercised in [10](#0-9) , and no path exists to recover control, permanently freezing feature activation state for the chain.

    /// Returns the effective activation admin address.
    ///
    /// When state-backed admin storage is disabled, this always returns the static fallback. When
    /// state-backed admin storage is enabled, a non-zero storage value wins; a zero storage value
    /// falls back to the static chain-config admin so Cobalt can replay historical Beryl activation
    /// transactions before the first admin rotation.
    ///
    /// [`Address::ZERO`] here means "no admin is set": it is not a valid admin address.
    /// Configuration-time validation rejects `Some(Address::ZERO)`, so in a correctly
    /// constructed chain spec the zero return always means `activation_admin_address` was
    /// `None`. Callers must not treat the zero return as a meaningful admin address.
    pub fn admin(&self, admin_config: ActivationAdminConfig) -> Result<Address> {
        if admin_config.state_enabled {
            let stored_admin = self.stored_admin()?;
            if !stored_admin.is_zero() {
                return Ok(stored_admin);
            }
        }
        Ok(admin_config.fallback.unwrap_or(Address::ZERO))
    }

    /// Sets the activation registry admin address.
    pub fn set_admin(
        &mut self,
        new_admin: Address,
        admin_config: ActivationAdminConfig,
    ) -> Result<()> {
        if self.storage.is_static() {
            return Err(BasePrecompileError::revert(IActivationRegistry::StaticCallNotAllowed {}));
        }
        if !admin_config.state_enabled {
            return Err(BasePrecompileError::revert(
                IActivationRegistry::AdminStorageNotEnabled {},
            ));
        }
        if new_admin.is_zero() {
            return Err(BasePrecompileError::revert(IActivationRegistry::ZeroAdminAddress {}));
        }

        let caller = self.require_admin_caller(admin_config)?;

        self.__initialize()?;
        self.admin.write(new_admin)?;
        self.emit_event(IActivationRegistry::AdminChanged {
            previousAdmin: caller,
            newAdmin: new_admin,
            caller,
        })?;

        Ok(())
    }

    fn stage_update_admin(
        &self,
        storage: &mut S,
        policy_id: u64,
        new_admin: Address,
    ) -> Result<()> {
        let (_, caller) = self.require_admin(storage, policy_id)?;
        if new_admin == Address::ZERO {
            storage.delete_pending_admin(policy_id)?;
        } else {
            storage.write_pending_admin(policy_id, new_admin)?;
        }
        storage.emit_event(
            IPolicyRegistry::PolicyAdminStaged {
                policyId: policy_id,
                currentAdmin: caller,
                pendingAdmin: new_admin,
            }
            .encode_log_data(),
        )?;
        Ok(())
    }

The activation registry lives at `0x8453000000000000000000000000000000000001`. It stores feature
flags keyed by `bytes32`, defaults every feature to inactive, and exposes `isActivated(bytes32)`,
`admin()`, `activate(bytes32)`, and `deactivate(bytes32)`. The optional activation admin configured
with `with_activation_admin_address()` is the only account that can change feature state. Without a
configured admin, `admin()` reports the zero address and activation mutations revert as
unauthorized. B-20 tokens, the B-20 factory, and the policy registry all check the registry before
serving their own ABI calls.
