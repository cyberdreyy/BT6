### Title
Missing sender allowlist enables unauthorized job injection into DON via gateway `web_api_trigger` messages - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
`handler.HandleLegacyUserMessage` only validates message structure, payload decodability, and timestamp freshness before forwarding the message to every member of the DON via `don.SendToNode`. There is no check that the cryptographically-recovered sender (`msg.Body.Sender`) is an authorized/allowlisted address for the target DON, as explicitly flagged by the `// TODO: apply allowlist and rate-limiting here` comment.

### Finding Description
The gateway's public HTTP entrypoint `gateway.ProcessRequest` decodes an incoming JSON-RPC request into an `api.Message`, and for legacy DON-targeted requests calls `msg.Validate()` [1](#0-0)  before dispatching to the resolved handler's `HandleLegacyUserMessage` [2](#0-1) .

`Message.Validate()` only checks field lengths/format and calls `ExtractSigner()`, which recovers whatever ECDSA public key produced the signature over the message body and sets it as `m.Body.Sender` — it never compares this recovered address against any known/authorized list [3](#0-2) . Any attacker generating a fresh ECDSA keypair can self-sign an arbitrary payload and produce a structurally valid `Message`.

Inside `HandleLegacyUserMessage`, the checks performed are: payload JSON-decodability, non-zero timestamp, and message staleness — followed immediately by the `// TODO: apply allowlist and rate-limiting here` comment, then a bare method-name check, and finally unconditional forwarding to **all** DON members [4](#0-3) . No per-sender authorization, registration check, or subscription/job binding is enforced anywhere in this path — `msg.Body.Sender` (the attacker-controlled recovered address) is never consulted before the `for _, member := range h.donConfig.Members { don.SendToNode(...) }` loop.

This confirms the described exploit: an unauthenticated attacker with any valid ECDSA key can sign a `web_api_trigger` message with an arbitrary payload/timestamp and have it forwarded to every node in the targeted DON.

### Impact Explanation
This allows unauthorized capability/job invocation on all nodes of a DON by any external party, without prior registration, allowlisting, or subscription — falling under "unauthorized job run" / unauthorized capability invocation. It also enables resource exhaustion (DoS) of DON members since attackers can flood every node in the DON with triggers limited only by the coarse `nodeRateLimiter` applied on the outgoing side (`handleWebAPIOutgoingMessage`), not on the inbound user-triggered path.

### Likelihood Explanation
Trivial and fully repeatable: the only precondition is possessing (generating) an ECDSA keypair and being able to reach the gateway's user-facing HTTP port — no registration, credentials, or prior relationship with the DON/gateway operator is required. The code path is reachable directly from `gateway.ProcessRequest`, the public entrypoint.

### Recommendation
Before forwarding to `don.SendToNode`, enforce a per-sender allowlist check (e.g., verifying `msg.Body.Sender` against a configured/registered set of authorized senders or an on-chain subscription/workflow owner mapping) and apply rate-limiting keyed on sender, as the TODO comment indicates was intended but never implemented.

### Proof of Concept
Go test plan (extends `core/services/gateway/handlers/capabilities/handler_test.go`):
1. Construct a `handler` via `NewHandler` with a mock `handlers.DON` (e.g., existing `mocks.DON`) and a `donConfig` containing at least one member.
2. Generate a fresh, never-registered ECDSA key with `crypto.GenerateKey()`.
3. Build an `api.Message` with `Method: MethodWebAPITrigger`, a valid `TriggerRequestPayload` with `Timestamp: uint32(time.Now().Unix())`, and sign it with `msg.Sign(freshKey)`.
4. Call `msg.Validate()` to populate `msg.Body.Sender` (assert it succeeds, proving no allowlist check occurs at validation).
5. Call `h.HandleLegacyUserMessage(ctx, msg, callback)`.
6. Assert `don.SendToNode` (mock) was invoked for every configured DON member — proving the message was forwarded despite the sender never being registered/allowlisted.
7. Contrast with expected behavior: assert should be that `SendToNode` is NOT called (or an authorization error is returned) unless the sender address matches a configured allowlist entry — which currently fails, confirming the vulnerability.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
