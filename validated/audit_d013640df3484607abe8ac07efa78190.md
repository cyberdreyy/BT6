### Title
Stale confirmations from removed multisig members allow request execution below the live-member threshold - (File: multisig2/src/lib.rs)

### Summary
`confirm()` in the multisig contract only compares the *size* of the stored confirmations set to `num_confirmations`; it never checks whether the members who confirmed are still active. `delete_member()` only purges confirmations/requests that were *authored* by the removed member, not confirmations that the removed member cast on other members' pending requests. A request confirmed by a member who is later removed keeps counting toward the K-of-N threshold, letting a request execute with fewer live approving members than the configured threshold requires.

### Finding Description
`confirm()` decides execution purely by count: [1](#0-0) 

`delete_member()` cleans up only the requests whose `signer`/`member` field equals the member being deleted — i.e. requests *created* by that member — and removes their confirmations. It does not touch the `confirmations` set of other, unrelated pending requests that the removed member had already confirmed: [2](#0-1) 

Binding that should hold: `confirmations_counted(request) == confirmations_from_currently_active_members(request)`.

After a `DeleteMember` action executes, this breaks: a pending request `R` (authored by member A, previously confirmed by member B) keeps B's stale public key/account in `self.confirmations[R]` even though B has just been removed from `self.members`. Since `confirm()` never re-validates confirmer membership, `confirmations.len()` still includes B's vote. Any one additional live confirmation then pushes the count to `num_confirmations`, and the request executes — even though only `num_confirmations - 1` actually-current members approved it.

The same pattern exists in the older single-key-based contract, where `DeleteKey` only purges requests filtered by `r.signer_pk == pk` (the request's original signer), not confirmations cast by that key on other requests: [3](#0-2) 

This is the direct analog of the OHM report: an accounting value (`confirmations` count / `circulatingOhmBurned`) that is supposed to gate an authorization threshold is never fully reconciled when the underlying state (live members / minted-but-tracked OHM) changes, letting the guarded action (`execute_request` / `mintOhmToVault`) bypass the intended cap.

### Impact Explanation
This breaks the fundamental K-of-N custody guarantee of the multisig: a `Transfer`, `AddKey`, `FunctionCall`, or other privileged action can be executed with strictly fewer currently-authorized approvals than `num_confirmations` requires, because a removed member's earlier confirmation is silently retained and counted. This is a **Critical** impact per the rubric — "a multisig request executed below threshold" — since NEAR (or any privileged action controlled by the multisig) can be moved/executed by a party set that is no longer entitled to the full authority represented by the threshold.

### Likelihood Explanation
This requires only ordinary contract usage: an existing member (unprivileged relative to the whole council, i.e., no special admin rights beyond being one of the K/N members) confirms a request, is later removed via a normal `DeleteMember` request (a routine operational action, not a bug in itself), and any remaining live member then supplies the last confirmation. No malicious deployment, redeploy, or out-of-scope actor is needed — it is a natural sequence of member churn combined with a pending, partially-confirmed request, which is a realistic operational pattern for any long-lived multisig.

### Recommendation
When counting confirmations in `confirm()`, filter the confirmations set to only members currently present in `self.members` before comparing against `num_confirmations` (or, when executing `DeleteMember`, remove the deleted member's public key/account from the confirmations sets of *all* pending requests, not just requests it authored).

### Proof of Concept
1. Initialize multisig with members `{A, B, C}` and `num_confirmations = 2`.
2. `A` calls `add_request(R1)` (e.g. `Transfer` to some receiver). `R1.confirmations = {}`.
3. `B` calls `confirm(R1)`. `R1.confirmations = {B}` (size 1, below threshold — not executed).
4. Separately, `A` and `C` create and confirm a `DeleteMember { member: B }` request; it reaches 2 confirmations and executes, removing `B` from `self.members`. `R1` is untouched because `delete_member` only scrubs requests where `r.member == B` (i.e., requests authored by `B`), and `R1` was authored by `A`.
5. `A` calls `confirm(R1)`. `confirmations.len() + 1 == 2 >= num_confirmations`, so `execute_request(R1)` runs and the transfer is executed — despite only one currently-live member (`A`) having actually approved it, with `B`'s stale, post-removal confirmation making up the count.     /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
