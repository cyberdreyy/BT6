### Title
Uncaught `onStartEpoch` hook lets an ERC4626 vault depositor permanently block `startEpoch`, freezing pool funds - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
The external report describes a pool whose core operation (`swap`) can be bricked by a reverting external hook (`AlgebraVirtualPool`). The direct analog in idle-tranches is the epoch state machine: `IdleCDOEpochVariant.startEpoch` unconditionally calls `IProgrammableBorrower(_borrower()).onStartEpoch`, which internally calls `vault.deposit` on an external ERC4626 vault with no `maxDeposit`/capacity check and no `try/catch`. Any unprivileged user of that vault (an allowed attacker persona) can saturate the vault's deposit cap, making every `startEpoch` call revert and freezing the entire epoch lifecycle — and with it all user funds and pending withdraw requests — for as long as the cap stays saturated.

### Finding Description
In `IdleCDOEpochVariant._startEpochProgrammableBorrower`, the hook call is a bare external call:

```solidity
function _startEpochProgrammableBorrower(uint256 _pendingWithdraws) internal {
  if (isProgrammableBorrower) {
    IProgrammableBorrower(_borrower()).onStartEpoch(_pendingWithdraws);
  }
}
``` [1](#0-0) 

This is invoked at the tail of `startEpoch` on both the pending-instant shortfall path (line 288) and inside the `try this.sendFundsToBorrower` success block (line 297) — in both cases a revert propagates out of `startEpoch` (reverts inside a `try` success block are *not* caught). [2](#0-1) 

Inside `ProgrammableBorrower.onStartEpoch`, the contract deposits its entire idle underlying balance into the configured ERC4626 vault via `_depositToVault`:

```solidity
_depositToVault(underlyingToken.balanceOf(address(this)), 0);
``` [3](#0-2) 

```solidity
uint256 shares = vault.deposit(_assetAmount, address(this));
``` [4](#0-3) 

There is no check against `vault.maxDeposit(address(this))` and no `try/catch`. On vaults with supply caps (e.g., Morpho/Gauntlet vaults used in the fork tests), once `maxDeposit == 0`, `deposit` reverts, so `onStartEpoch` reverts, so `startEpoch` reverts — permanently, while the condition holds.

Note the asymmetry already in the code: the `stopEpoch` path explicitly treats hook/vault failures as retryable (`onStopEpoch` reverts are allowed to bubble "so transient ERC4626 liquidity failures can be retried", and `onDefault` deliberately avoids calling `convertToAssets`), but the `startEpoch` path has no equivalent handling for a *deposit*-side failure. ### Impact Explanation
- `startEpoch` is the only transition out of the buffer phase. While it is bricked, `isEpochRunning` stays false but the funds earmarked for the borrower (`sendInterestAndDeposits`, `sendFundsToBorrower`) never move, pending withdraw requests cannot mature (they need a started-then-stopped epoch), and the pool's TVL is stuck in the CDO with no exit path for LPs whose requests already burned tranche tokens.
- The freeze persists as long as the attacker keeps the vault's deposit capacity saturated. The attacker's cost is only the capital temporarily deposited in the ERC4626 vault, which remains withdrawable to them (deposit-side caps do not restrict `withdraw`/`redeem`).
- Unlike the borrower-default path, no `defaulted` flag is set and no recovery flow (`finalizeDefault`, `DefaultDistributor`) is triggered — the pool simply cannot operate, and no honest privileged action (owner/manager calls, `setVault` on the borrower is owner-gated but cannot run while funds are mid-flight semantics aside, and would itself need an epoch boundary) unblocks it other than waiting out the attacker.

### Likelihood Explanation
- Attacker requirements are minimal: any EOA that can deposit into the ProgrammableBorrower's configured ERC4626 vault. No KYC, no tranche holdings, no privileged role needed.
- Vault supply caps / `maxDeposit` limits are common on curated vaults (the fork tests target Gauntlet USDC Prime, a capped Morpho vault). Caps can also be reached organically near capacity, making the failure reachable even without a dedicated attacker.
- The sequence is purely additive: attacker deposits into the vault until `maxDeposit(ProgrammableBorrower) == 0`, then every `startEpoch` (called by the honest owner/manager) reverts at `vault.deposit`. The attacker can top up the cap after any withdrawal by other vault users, sustaining the freeze.
- Existing guards do not help: the `sendFundsToBorrower` `try/catch` only covers the `transferFrom` self-call, not the hook; `_handleBorrowerDefault` is never reached because the revert happens before the catch; KYC/`isWalletAllowed` gates pool users, not vault depositors.

### Recommendation
Apply the same "handle reverts in external calls / pull instead of push" mitigation as the report:
- In `ProgrammableBorrower.onStartEpoch`, query `vault.maxDeposit(address(this))` first and only deposit `min(balance, maxDeposit)`; keep any remainder as on-hand underlying (it is already counted in `startAssets`/`epochStartVaultAssets`, so accounting is unaffected).
- Alternatively wrap the `_depositToVault` call in `try/catch` and leave failed deposits as on-hand balance rather than reverting the whole epoch transition.
- Optionally, in `IdleCDOEpochVariant`, treat a reverting `onStartEpoch` as a retryable condition (like `onStopEpoch`) rather than letting it abort the already-executed strategy transfers mid-flow.

### Proof of Concept
Reproducible Foundry fork PoC (mirroring `testProgrammableBorrowerStopEpochRevertsWhenVaultLiquidityUnavailable` in `test/foundry/ProgrammableBorrowerCreditVault.t.sol`):

```solidity
function testAttackerSaturatesVaultCapBlocksStartEpoch() external {
  _setUpProgrammableBorrowerCreditVault(GAUNTLET_FORK_BLOCK, GAUNTLET_USDC_PRIME);
  IERC4626 gauntletVault = IERC4626(GAUNTLET_USDC_PRIME);

  // Attacker (any vault depositor) fills the vault's supply cap
  uint256 room = gauntletVault.maxDeposit(address(programmableBorrower));
  deal(USDC, attacker, room + 1);
  vm.startPrank(attacker);
  IERC20(USDC).approve(address(gauntletVault), type(uint256).max);
  gauntletVault.deposit(gauntletVault.maxDeposit(attacker), attacker);
  vm.stopPrank();
  assertEq(gauntletVault.maxDeposit(address(programmableBorrower)), 0);

  // Honest LP deposits during buffer, epoch cannot start
  idleCDO.depositAA(10_000 * oneScale);
  vm.prank(manager);
  vm.expectRevert(); // vault.deposit reverts inside onStartEpoch -> startEpoch reverts
  cdoEpoch.startEpoch(epochDuration, apr);

  assertFalse(cdoEpoch.isEpochRunning());
  // Withdraw requests submitted in buffer cannot mature: no epoch ever starts/stops.
  // Attacker can withdraw their vault position at any time; freeze is sustainable.
}
```

The flow: `cdoEpoch.startEpoch` → `sendFundsToBorrower` succeeds → `_startEpochProgrammableBorrower` → `ProgrammableBorrower.onStartEpoch` → `_depositToVault` → `vault.deposit` reverts (`maxDeposit == 0`) → whole tx reverts. Repeated calls keep reverting while the attacker maintains cap saturation.
