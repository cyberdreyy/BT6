### Title
Claimed instant-withdraw receipts remain in the per-epoch claim list and are counted again in default recovery accounting - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
CVE-2022-2585 is a use-after-free: a POSIX CPU timer was freed but left on a list, so later list traversal dereferenced stale data. The analog in `IdleCreditVault` is `claimInstantWithdrawRequest`, which "frees" a user's instant-withdraw receipt (burns the receipt tokens and pays out) but leaves it on the per-epoch lists `instantWithdrawsRequestsByEpoch[user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`. If the borrower then defaults in the same epoch, `finalizeDefaultRecovery` traverses that stale list entry via `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve`, inflating both the recovery claim basis and the "already-funded" reserve. The recovery reserve becomes undercollateralized: earlier claimants drain real tokens while the accounted `defaultRecoveryReserve` covers phantom basis, leaving later claimants (tranche holders, other instant withdrawers) unpaid.

### Finding Description
In `claimInstantWithdrawRequest` the aggregate `instantWithdrawsRequests[_user]` is zeroed and funds are transferred, but the per-epoch entries that record which epoch the receipt belongs to are never cleared: [1](#0-0) 

Compare with the request side, which writes three structures: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and `instantWithdrawClaimsByEpoch[currentEpoch]` — only the first is released at claim time. [2](#0-1) 

The stale entries are only consumed by `_claimDefaultedInstantWithdrawRequest`, which subtracts `claimBasis` from `instantWithdrawsRequests[_user]` (already zeroed) and from `instantWithdrawClaimsByEpoch` — meaning the same receipt is accounted twice on two different ledgers. [3](#0-2) 

The critical reads happen at finalization. `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0`, and `_defaultPrefundedInstantReserve` computes `instantBasis - pendingInstant` as underlying "already held" for current-epoch instant claims: [4](#0-3) [5](#0-4) 

`finalizeDefaultRecovery` then sets `defaultRecoveryReserve = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` and `defaultRecoveryPrice = reserveAmount / totalBasis`, where `totalBasis` and `prefundedReserve` both embed the stale claimed amount: [6](#0-5) 

Attack sequence (epoch N, APR0 or fixed-APR mode, instant withdrawals enabled):
1. Attacker (any KYC'd lender / tranche holder) deposits and calls `requestInstantWithdraw` for X underlying in epoch N.
2. After the instant-withdraw delay, the CDO collects funds (`collectInstantWithdrawFunds` decrements `pendingInstantWithdraws`) and the attacker calls `claimInstantWithdrawRequest`, receiving X tokens. The receipt is burned, but `instantWithdrawsRequestsByEpoch[attacker][N]` and `instantWithdrawClaimsByEpoch[N]` still hold X.
3. Another user queues an instant (or normal) withdraw in epoch N so `pendingInstantWithdraws != 0` / `pendingWithdraws != 0` at finalization.
4. Borrower defaults; `finalizeDefaultRecovery` runs with `epochNumber == N` (epochNumber only increments at `deposit`/`stopEpoch`, not at default).
5. `defaultPendingClaimBasis` includes the phantom X; `prefundedReserve` is inflated by up to X tokens that were already paid to the attacker. `defaultRecoveryReserve` is set higher than the actual underlying balance backing it.

Broken invariant: one receipt one payout / donation isolation. The same X is both paid out at par (step 2) and counted as recovery basis + prefunded reserve (step 5). `_transferFundedClaim`'s reserve guard does not help because the corruption is in the reserve *accounting* itself, not in the funded-claim path.

### Impact Explanation
Direct insolvency of the default recovery reserve, quantified up to the total instant-withdraw volume claimed in the default epoch. Every underlying claimed via `claimInstantWithdrawRequest` before finalization is double-counted: `defaultRecoveryReserve` exceeds the strategy's real token balance by the stale amount. Recovery claims are paid first-come-first-served via `_transferDefaultRecovery` (`defaultRecoveryReserve -= _amount; safeTransfer`), so earlier claimants withdraw tokens that the accounting marks as belonging to later claimants. The last claimants — defaulted-epoch receipt holders and active tranche holders redeeming through the CDO — either receive a diluted `defaultRecoveryPrice` or their claims revert on insufficient balance. Permanent loss equals the sum of same-epoch instant claims replayed into the recovery basis.

### Likelihood Explanation
Requires (a) instant withdrawals enabled and exercised in the same epoch in which the borrower defaults, and (b) a nonzero pending instant or normal withdraw basis at finalization so `defaultPendingClaimBasis` includes `instantWithdrawClaimsByEpoch`. Condition (b) is easily satisfied — the attacker themselves can leave a small instant request pending. Borrower default mid-epoch is an in-scope, designed-for state (`defaulted()`, `finalizeDefaultRecovery`). No privileged-role misbehavior needed; only the honest manager/default-finalization flow is required. No existing guard clears or validates the stale per-epoch entries, and `_ensureDefaultRecoveryInitialized` explicitly does not touch instant accounting. Likelihood is moderate: it needs a same-epoch default, but the window is the entire epoch duration.

### Recommendation
In `claimInstantWithdrawRequest`, also clear the per-epoch records for every epoch contributing to the claimed aggregate, or track the outstanding epoch(s) per user and zero `instantWithdrawsRequestsByEpoch[_user][epoch]` and decrement `instantWithdrawClaimsByEpoch[epoch]` symmetrically with `instantWithdrawsRequests`. Since the aggregate can span epochs, consider storing the user's latest instant-request epoch (mirroring `lastWithdrawRequest`) or iterating/writing the claim epoch at request time. Alternatively, make `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve` derive basis only from entries whose aggregate counterpart is still nonzero.

### Proof of Concept
Foundry fork-style PoC sketch (mirroring `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
// Epoch N running, instant withdraws enabled via cdoEpoch.setInstantWithdrawParams(delay, diff, false)
// 1. attacker deposits, requests instant withdraw of X
cdoEpoch.requestInstantWithdraw(X, address(AAtranche));
skip(instantDelay + 1);
// 2. CDO funds and attacker claims at par
cdoEpoch.claimInstantWithdrawRequest(); // attacker receives X underlying

// stale state check
assertEq(vault.instantWithdrawsRequestsByEpoch(attacker, vault.epochNumber()), X); // BUG: not cleared
assertEq(vault.instantWithdrawClaimsByEpoch(vault.epochNumber()), X);              // BUG: not cleared

// 3. victim requests a small instant withdraw so pendingInstantWithdraws != 0
cdoEpoch.requestInstantWithdraw(small, address(BBtranche));

// 4. borrower defaults in same epoch; owner/manager finalize
//    defaultPendingClaimBasis() now includes X (already paid to attacker)
assertGt(vault.defaultPendingClaimBasis(), pendingWithdraws + small);
// prefundedReserve counts up to X tokens already transferred out
vault.finalizeDefaultRecovery(recovered, recoverySource);

// 5. reserve is over-accounted: sum of claims > strategy underlying balance
//    victim / later claimants' _transferDefaultRecovery reverts or pays diluted price
assertLt(underlying.balanceOf(address(vault)), vault.defaultRecoveryReserve());
```

Uncertainty I could not fully resolve within the iteration limit: the exact `IdleCDOEpochVariant` default path (`_handleBorrowerDefault`/`finalizeDefaultRecovery` caller) was not read, so the precise precondition on `pendingInstantWithdraws != 0` at finalization should be confirmed against the CDO's stop/default flow — but the stale-entry defect itself is unambiguous in the vault code.

```text
  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;

    if (instantBasis > pendingInstant) {
      prefundedReserve = instantBasis - pendingInstant;
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```
