### Title
Operator commission on `distribution_pool` growth can be permanently rounded away to zero via repeated small `unlock_stake`/`request_commission` calls - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
The Morpho report shows how invoking a stateful, per-call rate/accounting update on very small deltas causes systemic rounding distortion that benefits an attacker at another party's expense. `staking_contract.move`'s `update_distribution_pool` has the identical structural weakness: it recomputes operator commission on the *incremental* growth of the `distribution_pool` every time it is invoked, using plain integer division by `100`. A staker who repeatedly triggers this function (via ordinary, permissionless entry points they already have the right to call) can force the growth to be measured in many tiny slices, each of which rounds `unpaid_commission` down to `0`, permanently denying the operator commission that would have been paid had the growth been measured in one larger increment.

### Finding Description
`update_distribution_pool` recalculates, for every existing shareholder other than the operator, how much the `distribution_pool` grew since the last sync and transfers a proportional commission-equivalent number of shares to the operator: [1](#0-0) 

The critical line is:
```
let unpaid_commission = (current_worth - previous_worth) * commission_percentage / 100;
```
This is plain `u64` truncating division with no dust/remainder carry-over between calls. If `(current_worth - previous_worth) * commission_percentage < 100`, `unpaid_commission` truncates to `0` and the operator receives zero shares for that slice of growth, even though the true fractional commission was nonzero.

`update_distribution_pool` is invoked from `add_distribution`, which is itself called both by `request_commission_internal` (to sync growth on the pending_inactive pool before buying the operator's new commission shares) and by `unlock_stake` (to sync the pool before buying the staker's newly-unlocked shares): [2](#0-1) [3](#0-2) 

`request_commission` is a public entry function callable by the staker (as well as operator/beneficiary): [4](#0-3) 

Because `update_distribution_pool` is a pure function of "current total distributable coins vs. last recorded total," the staker fully controls the *cadence* at which growth snapshots are taken by simply calling `unlock_stake` (even with `amount = 1`, since `unlock_stake` short-circuits only on `amount == 0`) or `request_commission` once per epoch (or more). Each such call forces a fresh "current_worth - previous_worth" measurement of that epoch's tiny reward accrual on the pending_inactive pool. Because per-epoch reward growth on a `distribution_pool` is typically minuscule relative to `100 / commission_percentage`, each individual commission computation rounds down to `0`, and — unlike the underlying `stake` module's own reward accounting — there is no accumulator that preserves the truncated remainder for the next cycle. Over many epochs this compounds into the operator being permanently denied commission on that stream of value, which instead stays with the original shareholder (the staker) when they eventually redeem their shares in `distribute_internal`: [5](#0-4) 

This is the direct structural analog of the Morpho bug: a party who can force a stateful accounting function to run against artificially small deltas exploits integer-rounding to permanently strip value that should have flowed to another role (there, the protocol/other lenders; here, the operator/beneficiary).

### Impact Explanation
This corrupts operator commission accounting, crediting value to the wrong party (the staker keeps it instead of the operator/beneficiary), which falls squarely under the required "Operator commission ... share-accounting corruption that credits the wrong account or traps value" impact. The operator has no way to detect or prevent the staker from calling `unlock_stake`/`request_commission` frequently in small increments, and the truncated commission is not recoverable — it is not tracked as a debt and is never repaid, unlike `staking_contract.spec.move`'s test assumptions of clean 10%/90% splits. Because commission is the operator's primary compensation for running the validator, and the loss compounds over the life of every lockup cycle, this can non-trivially degrade or effectively zero out operator income on the `pending_inactive`/reward-growth leg of the contract, particularly for lower-percentage commissions or smaller stake amounts (both common on mainnet delegation setups).

### Likelihood Explanation
Likelihood is moderate-to-high: the entry points involved (`unlock_stake`, `request_commission`) are ordinary, unprivileged, staker-callable functions with no rate limiting, minimum-amount threshold, or cooldown. Gas cost on Aptos is low enough that calling once per epoch (or more) over a multi-day/week lockup period is practical. No special preconditions beyond owning a `staking_contract` are required, and the staker is economically incentivized to do this if commission-avoidance is understood, since it directly increases their own take at the operator's expense.

### Recommendation
Track the truncated remainder (dust) from `unpaid_commission` computations across calls to `update_distribution_pool` and carry it forward so that fractional commission is not permanently lost when growth is measured in many small increments — e.g., accumulate a `u128`/higher-precision running remainder in `StakingContract` and only truncate once, at final settlement, or compute commission using the *cumulative* growth since the operator's last actual payout rather than the growth since the last arbitrary sync call. Alternatively, enforce a minimum elapsed-time or minimum-growth threshold before allowing `update_distribution_pool` to advance its snapshot, similar to the Morpho recommendation to gate the reactive computation on sufficient underlying liquidity/delta.

### Proof of Concept
Conceptual reproduction (Move test, no live network required):
1. Staker creates a `staking_contract` with `commission_percentage = 10`, operator joins validator set, and rewards begin accruing normally, as in `staking_contract.move`'s own tests (`setup_staking_contract`, `test_distribute_*`).
2. Instead of allowing multiple epochs of reward accrual to elapse before calling `request_commission`/`unlock_stake` once (which is what existing tests do and where commission rounds correctly), the staker calls `unlock_stake(staker, operator, 1)` once every epoch, immediately after `stake::end_epoch()`.
3. Because `distribution_pool`'s per-epoch reward growth (`current_worth - previous_worth` in `update_distribution_pool`) is small, `(current_worth - previous_worth) * 10 / 100` truncates to `0` on nearly every call.
4. After many epochs, sum the operator's actual commission received (near `0`) versus the commission the operator would have received had the staker waited and called `request_commission` a single time after the same number of epochs (`accumulated_rewards / 10`, matching the pattern already asserted in existing tests, e.g. `test_distribute_operator_and_staker`): [6](#0-5) 
5. The discrepancy demonstrates that transaction cadence, fully controlled by the unprivileged staker, determines how much commission the operator actually receives — the exact "manipulate low-liquidity/small-delta measurement to distort a stateful accounting function" pattern from the external report, here degrading operator commission instead of an interest rate.

Note: I was not able to fully trace every call site (`distribute`, `switch_operator`, `update_voter`) that also triggers `update_distribution_pool`/`distribute_internal` due to the final tool-call limit being reached; based on the code already reviewed the same rounding weakness in `update_distribution_pool` applies to all of them equally, but a full enumeration of every trigger path would benefit from a dedicated Devin session with full file access.

        let staking_contract = store.staking_contracts.borrow_mut(&operator);

        // Force distribution of any already inactive stake.
        distribute_internal(
            staker_address,
            operator,
            staking_contract,
        );

        // For simplicity, we request commission to be paid out first. This avoids having to ensure to staker doesn't
        // withdraw into the commission portion.
        let commission_paid =
            request_commission_internal(
                operator,
                staking_contract,
            );

        // If there's less active stake remaining than the amount requested (potentially due to commission),
        // only withdraw up to the active amount.
        let (active, _, _, _) = stake::get_stake(staking_contract.pool_address);
        if (active < amount) {
            amount = active;

        staking_contract.principal -= amount;

        // Record a distribution for the staker.
        add_distribution(
            operator,
            staking_contract,
            staker_address,
            amount,

    fun update_distribution_pool(
        distribution_pool: &mut Pool,
        updated_total_coins: u64,
        operator: address,
        commission_percentage: u64
    ) {
        // Short-circuit and do nothing if the pool's total value has not changed.
        if (distribution_pool.total_coins() == updated_total_coins) { return };

        // Charge all stakeholders (except for the operator themselves) commission on any rewards earnt relatively to the
        // previous value of the distribution pool.
        let shareholders = &distribution_pool.shareholders();
        shareholders.for_each_ref(
            |shareholder| {
                let shareholder: address = *shareholder;
                if (shareholder != operator) {
                    let shares = pool_u64::shares(distribution_pool, shareholder);
                    let previous_worth = pool_u64::balance(distribution_pool, shareholder);
                    let current_worth =
                        pool_u64::shares_to_amount_with_total_coins(
                            distribution_pool, shares, updated_total_coins
                        );
                    let unpaid_commission =
                        (current_worth - previous_worth) * commission_percentage / 100;
                    // Transfer shares from current shareholder to the operator as payment.
                    // The value of the shares should use the updated pool's total value.
                    let shares_to_transfer =
                        pool_u64::amount_to_shares_with_total_coins(
                            distribution_pool, unpaid_commission, updated_total_coins
                        );
                    pool_u64::transfer_shares(
                        distribution_pool, shareholder, operator, shares_to_transfer
                    );
                };
            }
        );

        distribution_pool.update_total_coins(updated_total_coins);
    }
