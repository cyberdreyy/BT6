### Title
Validator can unrestrictedly raise vote account commission (basis-points) to 100% immediately before reward distribution, seizing delegator rewards - ([File: programs/vote/src/vote_state/mod.rs])

### Summary
The legacy commission-update path in the vote program enforces a time-window restriction that prevents a validator from raising its commission during the back half of an epoch, specifically to protect delegators from being blindsided by a commission hike right before rewards are calculated. The newer basis-points commission update path (`update_commission_bps`, added for SIMD-0291/SIMD-0123/SIMD-0249) removes this restriction entirely, allowing the vote account's authorized withdrawer to raise the commission to its maximum value at any time, including the instant before rewards are computed and distributed for the epoch — mirroring the reported auction-house bug where the fee owner could change the fee to 100% at any point and leave the counterparty with nothing.

### Finding Description
The legacy `update_commission` function gates commission increases behind `is_commission_update_allowed`, returning `VoteError::CommissionUpdateTooLate` if a validator tries to raise commission too late in the epoch: [1](#0-0) 

This rule exists specifically to stop validators from front-running reward distribution with a last-minute commission increase. However, the newer `update_commission_bps` function, which sets `inflation_rewards_commission_bps` or `block_revenue_commission_bps` (used for SIMD-0123 block revenue sharing / SIMD-0291 basis-point commissions), explicitly documents and implements no such rule: [2](#0-1) 

The only check performed is that the authorized withdrawer signed the transaction — there is no epoch-boundary or timing restriction of any kind, and the value can be raised as high as the basis-points type allows (up to 10000 = 100%). This is dispatched from the vote processor without any additional check: [3](#0-2) 

Because `inflation_rewards_commission_bps`/`block_revenue_commission_bps` directly determine the split of rewards between the validator and its delegators when rewards are calculated and distributed each epoch, a validator can wait until just before the epoch-rewards calculation, set the commission to 100%, and take the entire delegator/staker reward that epoch, then optionally lower it back down afterward.

### Impact Explanation
This allows a validator operator (holder of the vote account's authorized-withdrawer key) to unilaterally and instantly redirect all inflation/block-revenue rewards that would otherwise accrue to delegators for an epoch, with zero advance notice and no on-chain enforcement window — a direct unauthorized fund diversion analogous to the reported auction-fee issue. Unlike the legacy commission field, this basis-points mechanism has no protective delay, so delegators have no chance to un-stake or react before losing their share of that epoch's rewards.

### Likelihood Explanation
Any validator with normal, unprivileged authorized-withdrawer signing rights over their own vote account can trigger this via an ordinary `UpdateCommissionBps` transaction sent through standard transaction submission (no special privilege beyond controlling one's own vote account is required). Because the instruction is intentionally unrestricted ("No commission update rule, per SIMD-0249 and SIMD-0291"), this is not a rare edge case but a designed omission that a rational profit-seeking or malicious validator operator can exploit every epoch.

### Recommendation
Reintroduce a timing restriction on `update_commission_bps` analogous to `is_commission_update_allowed` for the legacy path (e.g., disallow commission increases within some window before the epoch boundary at which rewards are computed), or require a delayed-activation mechanism (new commission bps takes effect only in a future epoch) so delegators have advance notice and the opportunity to react before a commission change affects reward distribution.

### Proof of Concept
1. Validator operator controls a vote account with `inflation_rewards_commission_bps` set low (e.g., 500 = 5%) to attract delegators.
2. Immediately before the epoch's rewards calculation/distribution slot, the authorized withdrawer submits `VoteInstruction::UpdateCommissionBps { commission_bps: 10000, kind: CommissionKind::InflationRewards }` (via `vote_instruction::update_commission_bps`, processed by `update_commission_bps` in `programs/vote/src/vote_state/mod.rs`).
3. Because no timing check exists (unlike `update_commission`'s `is_commission_update_allowed`/`CommissionUpdateTooLate` gate), the transaction succeeds and sets commission to 100%.
4. Reward calculation for that epoch (in `runtime/src/inflation_rewards/mod.rs` / `runtime/src/bank/partitioned_epoch_rewards/`) uses the now-100% commission, so all rewards go to the validator and delegators receive nothing for that epoch.
5. The validator may then lower the commission back down for subsequent epochs, repeating the extraction each epoch.

/// Update the vote account's commission
pub fn update_commission<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission: u8,
    signers: &HashSet<Pubkey, S>,
    epoch_schedule: &EpochSchedule,
    clock: &Clock,
    disable_commission_update_rule: bool,
) -> Result<(), InstructionError> {
    let vote_state_result = get_vote_state_handler_checked(vote_account, target_version);
    let enforce_commission_update_rule = !disable_commission_update_rule
        && match vote_state_result.as_ref() {
            Ok(decoded_vote_state) => commission > decoded_vote_state.commission(),
            Err(_) => true,
        };

    if enforce_commission_update_rule && !is_commission_update_allowed(clock.slot, epoch_schedule) {
        return Err(VoteError::CommissionUpdateTooLate.into());
    }

    let mut vote_state = vote_state_result?;

    // current authorized withdrawer must say "yay"
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    vote_state.set_commission(commission);

    vote_state.set_vote_account_state(vote_account)
}

/// Update the vote account's commission in basis points (SIMD-0291, SIMD-0123).
pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}
