### Title
`postblock_proposal::validate()` scopes tenure/burn-view canonicity checks to a self-declared, potentially stale `sort_tip` instead of the node's current canonical sortition tip - ([File: stackslib/src/net/api/postblock_proposal.rs])

### Summary
`BlockProposal::validate()` derives the sortition handle used for every canonicity/burn check from `burn_view_consensus_hash`, a value the block itself supplies via a `TenureChange` extend payload, and never cross-checks that this snapshot is an ancestor of (or equal to) the node's actual canonical sortition tip. This lets a proposal built on a burnchain fork that has since been abandoned still pass `check_block_has_valid_tenure` and `get_expected_burns`, because both are evaluated purely within the self-referential history rooted at the attacker-chosen `sort_tip`.

### Finding Description
In `validate()`, the burn view used for all downstream checks is computed as: [1](#0-0) 
`get_block_burn_view` derives `burn_view_consensus_hash` from the block's own `TenureChange` payload when the cause is `Extend`: [2](#0-1) 
The only constraint it enforces is that the new burn view is a *descendant* (in sortition-index ancestry) of the parent block's previously recorded burn view - it never checks that the resulting snapshot lies on the sortdb's current canonical fork. `SortitionDB::get_block_snapshot_consensus` is a direct lookup by consensus hash and is not restricted to the canonical chain, so a consensus hash belonging to an abandoned/reorged-out sortition history is resolved successfully as `sort_tip`.

`validate()` then opens `db_handle = sortdb.index_handle(&sort_tip.sortition_id)` and passes this same handle into both:
- `check_block_has_valid_tenure`, whose docstring claims to "verify the block's tenure is on the canonical sortition history" but which actually only calls `db_handle.has_consensus_hash(tenure_id)` - an ancestry check *relative to the handle's own tip*, not the true canonical tip: [3](#0-2) 
- `get_expected_burns(&db_handle, ...)`, whose `None` result is the only gate rejecting a block with no recorded burnchain spend: [4](#0-3) 

Because `db_handle` is scoped to the attacker's self-declared (possibly stale) `sort_tip`, both checks only need to be internally consistent with that abandoned fork's history - which they trivially are, since the fork was once real and its block-commit/burn records still physically exist in the sortdb (sortition history is append-only and not purged on reorg). Nowhere in `validate()` is `sort_tip.sortition_id` compared against `SortitionDB::get_canonical_burn_chain_tip`/`get_canonical_sortition_tip` (no such call exists in this file). This breaks the intended equality "the burn view/tenure the block claims == a burn view/tenure on the chain the node currently considers canonical."

### Impact Explanation
If a signer relies on `BlockValidateOk` from this endpoint to co-sign a proposal, it can be induced to sign a block whose claimed tenure/burn view is anchored to a sortition fork that is no longer canonical at validation time. This is a canonicity violation matching the Critical category: "a signer signing an invalid, non-canonical, or conflicting block (chain safety)." A successful exploit produces a signature over a block that should have been rejected, potentially contributing to conflicting/non-canonical block acceptance.

### Likelihood Explanation
The attacker needs only their own miner slot to craft a `TenureChange` (`Extend`) block whose `parent_block_id` and `burn_view_consensus_hash` reference a fork that was canonical at proposal-construction time but becomes non-canonical before the validation call completes (a natural TOCTOU window during any burnchain/sortition-fork reorg). No majority-signer collusion, node compromise, or auth_token is required - just gossiping the crafted proposal during/after a reorg. The window depends on reorg timing, which is not attacker-controlled with certainty, making this a race-dependent rather than always-repeatable exploit, but it is reproducible whenever a reorg occurs between proposal submission and validation.

### Recommendation
In `validate()`, after resolving `sort_tip` from the block's self-declared burn view, explicitly verify that `sort_tip.sortition_id` is an ancestor of (or equal to) `SortitionDB::get_canonical_burn_chain_tip`/the current canonical sortition tip before using `db_handle` for `check_block_has_valid_tenure` and `get_expected_burns`. Reject the proposal with `NonCanonicalTenure`/`NoSuchTenure` if the claimed burn view is not part of the currently canonical burnchain history.

### Proof of Concept
Rust test plan (chainstate-level, driving `postblock_proposal::validate` directly, as in `stacks-signer/src/chainstate/tests/*`):
1. Build two sortition/tenure forks A and B off a common ancestor, such that fork A is canonical initially.
2. Mine a Nakamoto tenure-start block P on fork A, let a node/chainstate process it so `NakamotoChainState::get_block_header` can find it later.
3. Force a reorg so fork B becomes canonical (`SortitionDB::get_canonical_burn_chain_tip` now points into B), while sortdb retains fork A's sortition history (still queryable by consensus hash).
4. Craft a `NakamotoBlock` with a `TenureChange` (`cause = Extended`) whose `previous_tenure_end` = P's block id and whose `burn_view_consensus_hash` references a sortition snapshot still resolvable on the now-abandoned fork A, descending from P's original burn view.
5. Call `BlockProposal::validate(...)` with this block against the sortdb now canonical on fork B.
6. Assert (documenting the current bug): `validate()` returns `Ok(BlockValidateOk)` even though `sort_tip.sortition_id` used internally is not an ancestor of `SortitionDB::get_canonical_burn_chain_tip(sortdb.conn())`.
7. After the fix, assert `validate()` returns `Err(BlockValidateRejectReason { reason_code: NonCanonicalTenure, .. })` because the added canonical-ancestry check on `sort_tip` fails.
