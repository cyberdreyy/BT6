### Title
Unbounded `lossToleranceBps` silently disables the junior-first loss waterfall, letting junior holders offload losses onto seniors - ([File: contracts/IdleCDO.sol](contracts/IdleCDO.sol))

### Summary
The `MarginCalculator` analog is `IdleCDO.setLossToleranceBps`. Like the reported `dust` setter, it is an owner-only configuration variable documented as a percentage of `FULL_ALLOC` (100000 = 100%), but the setter performs no bounds check while every sibling setter (`setFeeParams`, `setTrancheAPRSplitRatio`, `setMinAprSplitAYS`, `setMaxDecreaseDefault`, `setUnlentPerc`) enforces `AmountTooHigh`. The value feeds the comparison `uint256(-totalGain) <= (lossToleranceBps * _lastNAV) / FULL_ALLOC` in `_virtualPriceAux` (contracts/IdleCDO.sol:403). If it is ever set above ~`FULL_ALLOC` — trivially done by an operator who assumes a different scale (e.g., wei/`1e18`, or who intends "tolerate everything") — the condition is satisfied for any loss below `maxDecreaseDefault`, and every loss is socialized pro-rata across AA and BB instead of being absorbed junior-first.

### Finding Description
`_virtualPriceAux` implements the tranche waterfall in three branches (contracts/IdleCDO.sol:398-426):

1. `totalGain > 0` → gain split per `trancheAPRSplitRatio`.
2. `uint256(-totalGain) <= (lossToleranceBps * _lastNAV) / FULL_ALLOC` → loss split pro-rata by `lastNAVAA / lastNAVBB` (intended only for dust-level losses).
3. Otherwise → the whole loss is routed to the junior (BB) tranche; seniors absorb only what juniors cannot cover.

Branch 2 is the intended "small-loss socialization" escape hatch, but the threshold is entirely owner-controlled and unchecked:

```solidity
/// @param _diffBps tolerance in % (FULL_ALLOC = 100%) for socializing small losses 
function setLossToleranceBps(uint256 _diffBps) external {
  _checkOnlyOwner();
  lossToleranceBps = _diffBps;
}
```

There is no `require(_diffBps <= SMALL_CAP)` or even `<= FULL_ALLOC`. A value such as `1e18` (operator using 18-decimal percentage conventions, exactly the decimal-confusion pattern from the report) or `type(uint256).max` makes `lossToleranceBps * _lastNAV / FULL_ALLOC` larger than any tolerated loss, so branch 2 always wins for every non-defaulting loss.

The remaining gate is `_checkDefault`: losses at or above `maxDecreaseDefault` (itself bounded at `FULL_ALLOC` in `setMaxDecreaseDefault`, IdleCDO.sol:817-820) trigger the default path. So the exploit window is precisely the band `0 < loss < maxDecreaseDefault` — which includes ordinary strategy price drift, redeem slippage/rounding losses on harvests, and any negative accrual the strategy reports.

### Impact Explanation
Broken invariant: **junior-first loss waterfall**. Under correct configuration, a loss `L` below `maxDecreaseDefault` is charged entirely to BB NAV (`_totalTrancheGain = totalGain` for the BB tranche, IdleCDO.sol:416). With an oversized `lossToleranceBps`, the same `L` is split `L * lastNAVBB / (lastNAVAA + lastNAVBB)` to BB and the remainder to AA.

Quantified example: AA NAV = 8,000, BB NAV = 2,000 (80/20 TVL). A tolerated 1% strategy loss = 100 underlyings. Correct behavior: BB loses 100 (5% drawdown), AA loses 0. Misconfigured behavior: BB loses 20, AA loses 80. A junior holder (Eve, an ordinary BB tranche-token holder — unprivileged) captures 80 underlyings of senior principal per such loss event, and repeated tolerated losses compound the theft. No skim, flag, KYC, epoch gate, or revert blocks this: `_updateAccounting` runs automatically inside every `_deposit`/`_withdraw`, and branch 2 is reached by design.

### Likelihood Explanation
The trigger is an owner misconfiguration — the exact scenario class of the source report (operator sets a scaled config value under a wrong decimal assumption, since nothing validates it and the NatSpec only hints at `FULL_ALLOC`). Every other numeric setter in the contract is bounded, which makes this omission a live inconsistency rather than a deliberate choice. Once misconfigured, exploitation requires no attacker transaction: Eve simply holds BB tokens (or buys them cheaply before a harvest) while routine harvest/withdraw accounting socializes each tolerated loss. The impact is bounded above by `maxDecreaseDefault` per event, which for deployed pools is typically non-trivial (e.g., 5–20% of NAV).

### Recommendation
Bound the setter to the intended domain and document the scale explicitly:

```solidity
function setLossToleranceBps(uint256 _diffBps) external {
  _checkOnlyOwner();
  // _diffBps is in FULL_ALLOC units (100000 = 100% of NAV tolerated as socialized loss)
  _checkAmountTooHigh((lossToleranceBps = _diffBps) > MAX_SOCIALIZED_LOSS); // e.g. FULL_ALLOC / 100
}
```

A realistic cap is a small fraction of `FULL_ALLOC` (e.g., 1%), matching the "small losses" comment. Add the same audit pass to the other unchecked value setters (`setLiquidationTolerance`, `setReleaseBlocksPeriod`) to confirm their units and ranges.

### Proof of Concept
Foundry test sketch (extends `test/foundry/TestIdleCDOLossMgmt.sol` harness; run on mainnet fork per `foundry.toml`):

```solidity
function testOversizedLossToleranceSocializesBBLoss() external {
    // Setup: AA deposits 8_000e18, BB deposits 2_000e18 (Eve is the sole BB holder)
    idleCDO.depositAA(8_000 * ONE_SCALE);
    vm.prank(eve);
    idleCDO.depositBB(2_000 * ONE_SCALE);

    // Honest owner misconfigures scale: sets tolerance as 1e18-scaled "100%"
    vm.prank(owner);
    idleCDO.setLossToleranceBps(1e18); // intended 100%, actually unlimited

    // Simulate a tolerated 0.5% strategy-price loss (below maxDecreaseDefault)
    uint256 stratBal = strategy.tokenBalanceWithFees(address(idleCDO));
    _mockStrategyPriceDrop(stratBal * 995 / 1000); // helper: warp/burn strategy value

    uint256 aaPriceBefore = idleCDO.virtualPrice(address(AAtranche));
    uint256 bbPriceBefore = idleCDO.virtualPrice(address(BBtranche));

    idleCDO.harvest(); // or any deposit/withdraw triggering _updateAccounting

    // Waterfall violated: AA absorbed ~80% of a loss that belonged fully to BB
    assertLt(idleCDO.virtualPrice(address(AAtranche)), aaPriceBefore);
    // Eve's BB loss is ~5x smaller than junior-first would impose
    assertGt(
        idleCDO.virtualPrice(address(BBtranche)),
        bbPriceBefore * (ONE_SCALE - 5 * ONE_SCALE / 100) / ONE_SCALE
    );

    // Eve redeems; her redemption is subsidized by senior principal
    vm.prank(eve);
    idleCDO.withdrawBB(0);
}
```

Assumptions/uncertainties: the PoC assumes the deployed `IdleCDO` (or an epoch variant inheriting `_virtualPriceAux`) is in scope; the strategy price drop is simulated by manipulating strategy-side balance/price as the existing loss-management tests do. If `lossToleranceBps` was intentionally unbounded (a documented "socialize all losses" knob), the finding degrades to a medium-risk config footgun; the missing `AmountTooHigh` check relative to every sibling setter and the `% (FULL_ALLOC = 100%)` NatSpec indicate it is not.
