### Title
Miner-Controlled Activity-Timer Reset Suppresses Tenure Timeout, Wedging Signer Failover - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`check_latest_block_in_tenure` refreshes the tenure's "last activity" timestamp whenever it sees *any* competing or duplicate block proposal from the tenure's own miner that fails the chain-length/height check, without requiring that proposal to actually extend the chain or ever be signable. Because `SortitionState::is_timed_out` (the failover gate) measures inactivity from that same timestamp, a single miner who controls the current tenure's proposal slot can indefinitely refresh it with cheap, ultimately-useless re-proposals, permanently suppressing the timeout that is supposed to let signers fail back to the prior miner. This mirrors the report's bug class: an actor is able to freely reset a timer that gates a liveness-critical check, wedging the system that depends on that timer expiring.

### Finding Description
`check_latest_block_in_tenure` in `stacks-signer/src/chainstate/mod.rs` compares an incoming block proposal's `chain_length` against the tenure's last known signed/pre-committed block. If the new proposal is not higher, the function does not simply reject it — it calls `signer_db.update_last_activity_time(...)` twice, both for a proposal that loses to a signed tip and for one that loses to a fresh pre-commit: [1](#0-0) [2](#0-1) 

This "counts as miner activity" bookkeeping is intentional for the case of a slow/reorging miner, but it means the timestamp can be refreshed by any lower/duplicate proposal from the tenure's own miner, not only by a proposal that actually advances the chain.

That same timestamp is the sole input to the tenure-inactivity failover check: [3](#0-2) 

`is_timed_out` only triggers fallback to the prior tenure's miner once `elapsed > block_proposal_timeout` since the last activity update (`docs/signer-flows.md` section 8 confirms this is the only path that lets the signer set "fall back to prior tenure: `make_miner_state(prior sortition)`"): [4](#0-3) 

Because the activity-refresh path is reachable with merely a losing/duplicate proposal — it does not require the proposal to pass the pre-commit threshold, be signed by the signer set, or extend the chain at all — a miner who has stalled (deliberately or otherwise) can keep issuing cheap re-proposals at or below the current height purely to keep resetting `last_activity_time`. This prevents `is_timed_out` from ever firing, which prevents `check_miner_inactivity`/`capitulate_viewpoint` from ever transitioning the local state machine's `current_miner` back to the prior tenure, wedging the signer set's miner-view state machine indefinitely for that tenure.

### Impact Explanation
This is a liveness wedge: a single, tenure-scoped miner (a "one-slot" actor, consistent with the scope's allowance for a one-slot miner plus gossip) can prevent the signer's fallback logic from ever engaging, blocking valid tenure progression without needing a majority of signers, another signer's key, or any auth token. This matches the "High" impact category — a signer wedged into never signing valid blocks because the state machine's view of the current miner can never be corrected away from a stalled miner.

### Likelihood Explanation
Likelihood is moderate-to-high in the sense that it requires only the currently-active miner to be malicious or misbehaving (already a "one-slot" trust assumption granted by the scope), and the refresh path is exercised on the normal proposal-handling flow with no additional privilege check — any proposal from that miner that is not higher than the known tip triggers the update, per `check_latest_block_in_tenure`'s logic at lines 403–417 and 427–447 of `chainstate/mod.rs`. The exact signature/authentication constraints upstream of this path (i.e., whether `check_block_against_state`'s prior static-validity checks require the proposal to be signed by the tenure's already-designated miner key) could not be fully traced within available context, so it is possible this requires the winning miner's key specifically rather than any arbitrary sender — this is noted as an open uncertainty.

### Recommendation
Only refresh `last_activity_time` when the competing/duplicate proposal itself demonstrates genuine liveness — for example gate the activity bump on the proposal being provably fresh (new content, new timestamp, or actually crossing some validation bar) rather than any losing height comparison, or bound how many activity refreshes a single unresolved tenure can accrue before `is_timed_out` is allowed to fire regardless.

### Proof of Concept
1. Miner wins the current tenure and produces one locally-accepted or pre-committed block B at height H (establishing a tip in the signer DB).
2. Miner then repeatedly re-broadcasts new `BlockProposal`s at height ≤ H (e.g., resigning trivial variants of the same or an old block) at an interval shorter than `reorg_attempts_activity_timeout`.
3. Each such proposal reaches `check_latest_block_in_tenure`, fails the height check, and calls `update_last_activity_time`, per `stacks-signer/src/chainstate/mod.rs` lines 403–417/427–447.
4. Because `last_activity_time` never goes stale, `SortitionState::is_timed_out` (`stacks-signer/src/chainstate/v1.rs` lines 55–94) never returns `true`, so `check_miner_inactivity` never triggers `make_miner_state(prior sortition)` fallback (`docs/signer-flows.md` lines 466–468).
5. The signer set remains wedged on the stalled miner indefinitely, unable to fail over, even though the miner produces no further valid, chain-extending blocks.

    pub fn is_timed_out(
        sortition: &ConsensusHash,
        db: &SignerDb,
        block_proposal_timeout: Duration,
    ) -> Result<bool, SignerChainstateError> {
        // If we've already signed a block in this tenure, the miner can't have timed out: we have
        // committed a signature to this tenure and must not help abandon it.
        //
        // Importantly, a block we have only pre-committed to does not count! A pre-commit carries
        // no signature, and if it never reaches the pre-commit threshold the tenure can stall
        // indefinitely. Treating it as signed here would suppress the inactivity timeout for
        // exactly the signers that pre-committed, so they could never fall back to the prior
        // miner and the tenure could never recover.
        let has_block = db.has_signed_block_in_tenure(sortition)?;
        if has_block {
            return Ok(false);
        }
        let Some(received_ts) = db.get_burn_block_receive_time_ch(sortition)? else {
            return Ok(false);
        };
        let received_time = UNIX_EPOCH + Duration::from_secs(received_ts);
        let last_activity = db
            .get_last_activity_time(sortition)?
            .map(|time| UNIX_EPOCH + Duration::from_secs(time))
            .unwrap_or(received_time);

        let Ok(elapsed) = std::time::SystemTime::now().duration_since(last_activity) else {
            return Ok(false);
        };

        if elapsed > block_proposal_timeout {
            info!(
                "Tenure miner was inactive too long and timed out";
                "tenure_ch" => %sortition,
                "elapsed_inactive" => elapsed.as_secs(),
                "config_block_proposal_timeout" => block_proposal_timeout.as_secs()
            );
        }
        Ok(elapsed > block_proposal_timeout)
    }
