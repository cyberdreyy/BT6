### Title
Unrecovered panic in `normalizeHex` via `strings.Repeat` negative count from unauthenticated gateway trigger request - ([File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go])

### Summary
`resolveWorkflowID` calls `normalizeHex(workflowID, workflowIDLength)` after `validateWorkflowID`/`validateHexInput` only checks the *total string length* against `workflowIDLength` (66, i.e. `"0x"` + 64 hex chars), not that the `"0x"` prefix is actually present. An attacker can submit a 66-character lowercase hex string with no `0x` prefix (representing 33 raw bytes) that passes `validateHexInput` (even length, decodes fine, ≤66 chars) but causes `normalizeHex` to compute a negative repeat count, panicking the request-handling path with no `recover()` in the call chain. [1](#0-0) [2](#0-1) 

### Finding Description
The gateway's HTTP trigger flow calls `validateTriggerParams` → `validateWorkflowFields` → `validateWorkflowID`, which invokes `validateHexInput(workflowID, workflowIDLength)`: [3](#0-2) 

```go
func validateHexInput(input string, expectedLength int) error {
	if input != strings.ToLower(input) { return errors.New("must be lowercase") }
	if len(input) > expectedLength { return fmt.Errorf(...) }
	hexStr := strings.TrimPrefix(input, "0x")
	_, err := hex.DecodeString(hexStr)
	...
}
```

This check only bounds `len(input)` (the raw string, whether or not it has `"0x"`) to `workflowIDLength = 66`. It never enforces that the input actually carries the `"0x"` prefix nor that the trimmed hex portion is ≤ 64 characters. A 66-character, lowercase, valid-hex string with **no** `"0x"` prefix (e.g. 66 `f` characters) passes this validation since `len(input) == 66 <= 66`, it's lowercase, and `hex.DecodeString` succeeds (even length).

Later, `resolveWorkflowID` normalizes the already-"validated" workflow ID: [4](#0-3) 

```go
func normalizeHex(input string, length int) string {
	hexStr := strings.TrimPrefix(input, "0x")
	expectedHexLength := length - 2
	paddedHex := strings.Repeat("0", expectedHexLength-len(hexStr)) + hexStr
	return "0x" + paddedHex
}
```

For a 66-character input lacking `"0x"`, `TrimPrefix` is a no-op, so `hexStr` stays 66 characters long. `expectedHexLength = 66 - 2 = 64`. `expectedHexLength - len(hexStr) = 64 - 66 = -2`. `strings.Repeat("0", -2)` panics with `strings: negative Count` — this is unrecovered anywhere in the call chain (`HandleJSONRPCUserMessage` → `HandleUserTriggerRequest` → `resolveWorkflowID`), as no `recover()` exists in `core/services/gateway` for this path. [5](#0-4) 

The attacker is an unauthenticated gateway client sending a JSON-RPC `workflows.execute` request (`MethodWorkflowExecute`) with a crafted `workflowID` in the `WorkflowSelector` — no JWT auth is required to reach this code, since `resolveWorkflowID` runs **before** `authorizeRequest` in `HandleUserTriggerRequest`. [6](#0-5) 

### Impact Explanation
This is a denial-of-service vector, not a workflow-ID conflation/authorization-exactness bug (the originally hypothesized invariant violation was not found — `normalizeHex`'s zero-padding behavior for shorter, correctly-prefixed hex inputs is intentional and does not create ID collisions across distinct on-chain workflow IDs, since `hex.DecodeString` rejects odd-length strings and `validateHexInput` bounds total length). The concrete, exploitable issue is instead an unrecovered runtime panic reachable pre-authentication, which can crash the goroutine/process handling gateway JSON-RPC requests, matching the "unauthorized action causing service disruption / node crash" bounty class rather than authorization bypass.

### Likelihood Explanation
Trivial to trigger: any unauthenticated client capable of sending a gateway JSON-RPC `workflows.execute` message with a 66-hex-char, no-`0x`-prefix `workflowID` (e.g. 66 lowercase hex digits) reaches the vulnerable code path with no auth or rate-limit gating beforehand. Repeatable on demand.

### Recommendation
In `validateHexInput`/`validateWorkflowID`, require the `"0x"` prefix explicitly and bound the *trimmed* hex length (not the raw input length) against `expectedLength-2`. Additionally, harden `normalizeHex` to return an error (or clamp) instead of panicking when `len(hexStr) > expectedHexLength`, and add a top-level `recover()` around gateway JSON-RPC message handling to prevent any single malformed request from crashing shared server/goroutine state.

### Proof of Concept
Go table test in `core/services/gateway/handlers/capabilities/v2/http_trigger_handler_test.go`:
```go
func TestNormalizeHex_PanicOnMissingPrefix(t *testing.T) {
    input := strings.Repeat("f", 66) // 66 hex chars, no "0x" prefix
    require.NoError(t, validateHexInput(input, workflowIDLength)) // passes validation
    require.Panics(t, func() {
        normalizeHex(input, workflowIDLength) // strings.Repeat negative count panic
    })
}
```
Handler-level integration test: send a `jsonrpc.Request` with `Method: gateway_common.MethodWorkflowExecute` and `Workflow.WorkflowID` set to the 66-char non-prefixed hex string via `HandleUserTriggerRequest`/`HandleJSONRPCUserMessage`, asserting the call panics or crashes instead of returning a graceful `handleUserError` JSON-RPC error response.

func (h *httpTriggerHandler) resolveWorkflowID(ctx context.Context, triggerReq *jsonrpc.Request[gateway_common.HTTPTriggerRequest], requestID string, callback handlers.Callback) (string, error) {
	h.lggr.Debugw("resolving workflow ID", "workflowID", triggerReq.Params.Workflow.WorkflowID, "workflowOwner", triggerReq.Params.Workflow.WorkflowOwner, "workflowName", triggerReq.Params.Workflow.WorkflowName, "workflowTag", triggerReq.Params.Workflow.WorkflowTag, "requestID", requestID)

	if workflowID != "" {
		workflowID = normalizeHex(workflowID, workflowIDLength)
		_, found := h.workflowMetadataHandler.GetWorkflowReference(workflowID)
		if !found {
			h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, fmt.Sprintf("Workflow not found. 'workflowID' %s is not a valid workflow ID", workflowID), callback)
			return "", errors.New("workflow not found")
		}
		return workflowID, nil
	}
