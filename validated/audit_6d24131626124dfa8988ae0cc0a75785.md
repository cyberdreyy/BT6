### Title
Miner can indefinitely suppress its own inactivity timeout by re-proposing low/duplicate blocks in its own tenure - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`check_latest_block_in_tenure` treats *any* rejected re-proposal that fails to beat the tenure's current tip as "miner activity" and unconditionally bumps `last_activity_time` for that tenure whenever the tip has not yet been globally signed. Since `SortitionState::is_timed_out` (the sole gate that lets a signer fall back to the prior/valid miner) measures elapsed time from `last_activity_time`, a miner that never manages to get a block globally signed can keep resetting this clock forever by simply re-broadcasting stale/duplicate proposals for its own tenure, permanently blocking the signer set's fallback mechanism — the same "repeatedly call the state-resetting function to freeze the clock" pattern as the Shelter `activate()` bug.

### Finding Description
`check_latest_block_in_tenure` is invoked on every proposal for a given tenure to decide whether the proposal is high enough to be considered further, and as a side effect updates the tenure's activity clock: [1](#0-0) 

If the proposal doesn't beat the known tip (`chain_length <= info.block.header.chain_length`), the function still calls `update_last_activity_time` as long as `info.signed_group` is `None` (i.e. the tip in this tenure has not yet reached global/group signature) **or** the group signature is recent. Critically, the `signed_group.is_none()` branch has *no time bound at all* — it fires on every single re-proposal, however frequent.

This activity timestamp is exactly what gates the fallback logic in `SortitionState::is_timed_out`: [2](#0-1) 

`is_timed_out` only trusts `has_signed_block_in_tenure` (each signer's *own* local signature) to short-circuit to "not timed out"; for every signer that hasn't personally signed a block in that tenure, the elapsed-time check against `last_activity_time` is the only thing standing between the current miner and being marked `InvalidatedBeforeFirstBlock`, which is what ultimately lets `check_miner_inactivity` in `stacks-signer/src/v0/signer_state.rs` fall back to the prior tenure: [3](#0-2) 

Because `check_latest_block_in_tenure` is called at proposal *arrival* (per `docs/signer-flows.md`, "runs in three places: at proposal arrival ... at validate-ok ... at signing", and for a non-tenure-change block the tenure checked is the block's *own* tenure), a miner can simply keep gossiping conflicting/duplicate proposals for its own ongoing tenure — proposals that will be rejected (`chain_length` not higher) — and each rejected proposal still refreshes `last_activity_time` for every signer that receives it, as long as no globally-signed tip yet exists in that tenure. This is functionally identical to the Shelter bug: a party who controls the trigger for a state-reset function (`activate`/re-propose) can call it repeatedly to keep a timer from ever expiring, thereby preventing the state transition (`withdraw`/miner-fallback) that would otherwise occur.

### Impact Explanation
This wedges the signer set's liveness mechanism: the current miner never needs to make real progress (get a block to the 70% global-signature threshold) to remain "the current miner" from the perspective of any signer that hasn't personally signed a block in that tenure. As long as it keeps sending cheap, rejected re-proposals faster than `block_proposal_timeout`, the signer set can never invalidate it and fall back to a legitimate prior miner, stalling chain progress for the tenure — a High-severity liveness wedge ("a signer wedged into never ... acting on a stale reward set/threshold" class: here, the signer is wedged into never timing out a non-productive miner).

### Likelihood Explanation
Only the current sortition-winning miner is required (a "one-slot miner"), matching the analog's requirement (client repeatedly calling `activate`). No majority of signers, no other signer's key, and no special access are needed — simply re-broadcasting an already-known or trivially-crafted lower-height block proposal for the miner's own tenure over StackerDB gossip is sufficient to keep refreshing every recipient signer's activity clock.

### Recommendation
Bound the `signed_group.is_none()` branch of `update_last_activity_time` in `check_latest_block_in_tenure` by an absolute time budget (e.g., since the tenure/burn block started, not per-proposal), similar to how the `signed_group.is_some()` branch is bounded by `reorg_attempts_activity_timeout`. Alternatively, only allow a bounded number of activity-time refreshes per tenure absent an actual global signature, so a miner cannot indefinitely extend its own grace period purely by resending rejected proposals.

### Proof of Concept
1. Miner M wins a sortition and starts tenure T; no block in T has reached the global-signature threshold (`signed_group` stays `None` for the tip candidate), e.g. because M controls a minority of signer weight or the network is otherwise degraded.
2. M proposes block B1 for T with some `chain_length`; some signers locally accept it but it never reaches 70% (`signed_group` remains `None`).
3. M repeatedly re-broadcasts B1 (or any block for T with `chain_length` not exceeding the known tip) to all signers, spaced less than `block_proposal_timeout` apart.
4. For every signer that has not personally signed a block in T, `check_latest_block_in_tenure` → `update_last_activity_time` fires on each re-proposal (line 403-416 in `chainstate/mod.rs`), because `info.signed_group.is_none()` is always true.
5. `SortitionState::is_timed_out` (`chainstate/v1.rs` lines 55-94) never sees `elapsed > block_proposal_timeout`, so `check_miner_inactivity` never falls back to the prior miner, and tenure T never times out even though it never produces a globally accepted block.

    pub fn is_timed_out(
        sortition: &ConsensusHash,
        db: &SignerDb,
        block_proposal_timeout: Duration,
    ) -> Result<bool, SignerChainstateError> {
        // If we've already signed a block in this tenure, the miner can't have timed out: we have
        // committed a signature to this tenure and must not help abandon it.
        //
        // Importantly, a block we have only pre-committed to does not count! A pre-commit carries
        // no signature, and if it never reaches the pre-commit threshold the tenure can stall
        // indefinitely. Treating it as signed here would suppress the inactivity timeout for
        // exactly the signers that pre-committed, so they could never fall back to the prior
        // miner and the tenure could never recover.
        let has_block = db.has_signed_block_in_tenure(sortition)?;
        if has_block {
            return Ok(false);
        }
        let Some(received_ts) = db.get_burn_block_receive_time_ch(sortition)? else {
            return Ok(false);
        };
        let received_time = UNIX_EPOCH + Duration::from_secs(received_ts);
        let last_activity = db
            .get_last_activity_time(sortition)?
            .map(|time| UNIX_EPOCH + Duration::from_secs(time))
            .unwrap_or(received_time);

        let Ok(elapsed) = std::time::SystemTime::now().duration_since(last_activity) else {
            return Ok(false);
        };

        if elapsed > block_proposal_timeout {
            info!(
                "Tenure miner was inactive too long and timed out";
                "tenure_ch" => %sortition,
                "elapsed_inactive" => elapsed.as_secs(),
                "config_block_proposal_timeout" => block_proposal_timeout.as_secs()
            );
        }
        Ok(elapsed > block_proposal_timeout)
    }
