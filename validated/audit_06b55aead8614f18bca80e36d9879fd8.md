## Finding

### Title
Missing fee-amount validation in `createDstEscrow` lets a resolver permanently break destination withdrawals and steal the maker's escrowed funds - (File: `contracts/BaseEscrowFactory.sol`)

### Summary
`BaseEscrowFactory.createDstEscrow` accepts a full `IBaseEscrow.Immutables` struct — including the `parameters` blob that encodes `protocolFeeAmount` and `integratorFeeAmount` — directly from an unprivileged caller with **no validation** that `protocolFeeAmount + integratorFeeAmount < amount`. The equivalent source-side path (`_postInteraction`) explicitly guards this invariant with `if (integratorFeeAmount + protocolFeeAmount >= takingAmount) revert InvalidFeeAmounts();`, but `createDstEscrow` has no such check.

### Finding Description
In `_postInteraction` (source escrow creation), fee amounts are computed on-chain via `FeeTaker._getFeeAmounts` and explicitly checked against `takingAmount`: [1](#0-0) 

In contrast, `createDstEscrow` takes `dstImmutables` verbatim from `msg.sender` and deploys the escrow without ever checking the relationship between `dstImmutables.amount` and the fee amounts packed into `dstImmutables.parameters`: [2](#0-1) 

Those fee values are later read back and subtracted from `immutables.amount` in `EscrowDst._withdraw`, using ordinary Solidity 0.8 checked arithmetic: [3](#0-2) 

If `integratorFeeAmount + protocolFeeAmount > immutables.amount`, the line `uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;` reverts on underflow. Since `withdraw` and `publicWithdraw` both route through `_withdraw`, **every** withdrawal path for that destination escrow becomes permanently unusable — the maker can never be paid on the destination chain, in any withdrawal window. The only remaining action is `cancel()`, which sends the entire `immutables.amount` (and safety deposit) back to `immutables.taker` — the very party (resolver) who crafted the malicious immutables: [4](#0-3) 

Nothing on-chain forces `dstImmutables` to be consistent with the fee parameters that were committed to at `SrcEscrowCreated` time (`DstImmutablesComplement.parameters`, emitted only as an event, not enforced): [5](#0-4) 

### Impact Explanation
A resolver can deploy a destination escrow whose declared `protocolFeeAmount + integratorFeeAmount >= amount`. This deterministically breaks `withdraw`/`publicWithdraw` for that escrow (arithmetic revert), while `cancel()` still functions correctly for the resolver (as `taker`). Combined with the normal swap flow — where the resolver uses the maker's revealed secret to withdraw the maker's funds from `EscrowSrc` on the source chain — the resolver can receive the maker's source-chain funds while ensuring the maker's destination-chain payout can never be withdrawn, then reclaim their own destination-chain deposit via `cancel()` after the cancellation timelock. This is a direct theft of the maker's escrowed funds / permanent freezing of destination-chain funds, matching Critical/High impact under the bounty scope (theft of user funds, permanent freezing of funds).

### Likelihood Explanation
The attack requires no privileged role: `createDstEscrow` is a public, unauthenticated entry point, and the caller fully controls `dstImmutables.parameters` (fee amounts/recipients). The only asymmetry compared to the audited/guarded source path (`InvalidFeeAmounts` check in `_postInteraction`) is that the destination path lacks the analogous check, so exploitation is a one-line malicious parameter choice by any resolver, with no additional preconditions beyond normal participation in a swap as the taker.

### Recommendation
Add an explicit invariant check in `createDstEscrow` mirroring the source-side guard, e.g.:
```solidity
(uint256 protocolFeeAmount, uint256 integratorFeeAmount, , ) = abi.decode(dstImmutables.parameters, (uint256, uint256, address, address));
if (protocolFeeAmount + integratorFeeAmount >= dstImmutables.amount) revert InvalidFeeAmounts();
```
Alternatively, validate that `dstImmutables` (including its fee parameters) matches the `DstImmutablesComplement` committed on the source chain during `_postInteraction`, so a resolver cannot unilaterally substitute inconsistent/malicious fee data when creating the destination escrow.

### Proof of Concept
1. Resolver fills a maker's order via the Limit Order Protocol; `EscrowSrc` is deployed and funded normally.
2. Instead of calling `createDstEscrow` with the fee parameters that were emitted in `SrcEscrowCreated`, the resolver calls `createDstEscrow` with `dstImmutables.parameters = abi.encode(protocolFeeAmount, integratorFeeAmount, protocolFeeRecipient, integratorFeeRecipient)` where `protocolFeeAmount + integratorFeeAmount >= dstImmutables.amount` (e.g., set both fee amounts equal to `amount`).
3. `createDstEscrow` deploys `EscrowDst` without any check, taking the resolver's funds as usual (see `contracts/BaseEscrowFactory.sol` lines 165-185).
4. Once the maker reveals the secret (needed for the resolver to withdraw `EscrowSrc`), the resolver withdraws the maker's tokens from `EscrowSrc`.
5. The maker (or anyone) attempts `EscrowDst.withdraw`/`publicWithdraw` with the correct secret; the call reverts with an arithmetic underflow panic at `uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;` (`contracts/EscrowDst.sol` line 92) — for every window, permanently.
6. After the `DstCancellation` timelock, the resolver calls `cancel()`, reclaiming `immutables.amount` and the safety deposit back to themselves (`contracts/EscrowDst.sol` lines 64-73), while the maker receives nothing on the destination chain despite having lost their source-chain funds.

```text
    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }
```

```text
    function _withdraw(bytes32 secret, Immutables calldata immutables)
        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }
```
