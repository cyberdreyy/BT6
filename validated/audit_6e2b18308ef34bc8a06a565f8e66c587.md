### Title
Loss-adjusted withdraw receipts are paid at par when a newer request epoch overwrites `lastWithdrawRequest` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.claimWithdrawRequest` runs three sequential claim "cleanup" paths (`_claimLossAdjustedWithdrawRequest`, `_claimFundedWithdrawRequest`, and the default paths), mirroring the nvme-fc bug where two unsynchronized cleanup routines race on the same ID space. `_claimLossAdjustedWithdrawRequest` only inspects `lastWithdrawRequest[_user]` — the *latest* request epoch. If a user holds a loss-adjusted receipt from an older epoch `L` (created when `collectWithdrawFunds` was called with less than `pendingBasis`, setting `lossRecoveryPriceByEpoch[L]`) and then files another request in epoch `M > L`, the loss-adjusted path looks up `lossRecoveryPriceByEpoch[M] == 0` and skips. The aggregate `withdrawsRequests[_user]` still contains the epoch-`L` principal, so `_claimFundedWithdrawRequest` pays it **at par**, even though the borrower only funded it at the haircut price. This is a double-crediting of one receipt across two claim paths: the loss-haircut is silently dropped. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

### Finding Description
1. Attacker (KYC'd lender) requests a withdraw in epoch `L`; `withdrawsRequests[user] += amount`, `withdrawsRequestsByEpoch[user][L] += amount`, `lastWithdrawRequest[user] = L`.
2. `stopEpochWithDuration` is invoked and the borrower underpays pending receipts: `collectWithdrawFunds(amount < pendingBasis)` sets `pendingWithdraws = 0` and `lossRecoveryPriceByEpoch[L] = amount * RECOVERY_FULL / pendingBasis < 1`. Only the haircut amount of underlying is pulled into the strategy.
3. Next epoch starts; attacker calls `requestWithdraw` again in epoch `M`, overwriting `lastWithdrawRequest[user] = M` and adding to `withdrawsRequests[user]`.
4. After epoch `M` ends (`epochNumber > M`), attacker calls `cdoEpoch.claimWithdrawRequest()`:
   - `_claimLossAdjustedWithdrawRequest` reads `lossEpoch = lastWithdrawRequest = M`; `lossRecoveryPriceByEpoch[M] == 0` → returns 0 without clearing anything.
   - `_claimFundedWithdrawRequest` passes the gate (`epochNumber > lastWithdrawRequest`), computes `amount = withdrawsRequests[user]` = `receiptL + receiptM` and pays all of it at par via `_transferFundedClaim`.

The epoch-`L` piece escapes its loss haircut entirely. Note the same hole exists after a default: `_claimDefaultedWithdrawRequest` clears only epoch `defaultRecoveryEpoch` and resets `lastWithdrawRequest` to `0`, after which `_claimLossAdjustedWithdrawRequest` checks `lossRecoveryPriceByEpoch[0]` and again misses the orphaned loss epoch `L`, which is then paid at par by `_claimFundedWithdrawRequest`.

### Impact Explanation
The strategy only holds the haircut-funded underlying for epoch-`L` receipts; paying that receipt at par spends underlyings belonging to other funded claimants and APR0 settlers. Excess extracted = `receiptL * (1 - lossRecoveryPrice)` — direct theft from the shared funded-claim balance, and once drained, legitimate `claimWithdrawRequest` calls for other users revert on insufficient balance (permanent freezing of their claims). The `_transferFundedClaim` reserve guard only protects `defaultRecoveryReserve`, not other funded receipts, so it does not stop this.

### Likelihood Explanation
Requires a `stopEpochWithDuration` partial-loss epoch (a real flow: manager closes an epoch with a loss that pending redeemers absorb), the same user filing a subsequent request before claiming, and one further epoch boundary — all reachable by an ordinary KYC'd lender through honest manager/borrower sequencing. No privileged misbehavior needed. Partial-loss epochs are expected in stressed credit markets, which is precisely when defaults (the second trigger path) also occur.

### Recommendation
Track loss-adjusted exposure per epoch rather than only via `lastWithdrawRequest`. In `_claimLossAdjustedWithdrawRequest`, iterate (or keep a per-user set of) epochs in `withdrawsRequestsByEpoch` with `lossRecoveryPriceByEpoch[epoch] != 0`, or store a `lossEpochs` marker per user when `collectWithdrawFunds` records a sub-par price, and clear/pay those receipts at `lossRecoveryPrice` before the funded path computes its aggregate. Equivalently, subtract any loss-adjusted basis from `withdrawsRequests[_user]` inside the funded claim before paying at par.

### Proof of Concept
Reproducible Foundry fork PoC (sketch against `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
// 1. deposit, startEpoch(0), requestWithdraw(amountA) as attacker -> lastWithdrawRequest = epoch L
// 2. borrower funds only 50% of pendingWithdraws; manager calls
//    cdoEpoch.stopEpochWithDuration(apr, 0, duration, lossAmount) with
//    lossAmount = pendingBasis - funded  -> collectWithdrawFunds(funded < pendingBasis)
//    -> lossRecoveryPriceByEpoch[L] = 0.5e18, pendingWithdraws = 0
// 3. manager startEpoch(); attacker requestWithdraw(amountB) -> lastWithdrawRequest = epoch M
// 4. borrower fully repays; stopEpoch normally -> epochNumber > M
// 5. attacker: cdoEpoch.claimWithdrawRequest()
//    expect underlyingReceived == amountA + amountB          (par)
//    instead of amountA * 0.5 + amountB                      (haircut on epoch L)
// 6. a second user with a funded receipt then claims -> reverts/underpays by the stolen delta
```

Uncertainty: I verified the claim-path logic statically; the exact ordering of `epochNumber` increments vs. `collectWithdrawFunds` inside `stopEpochWithDuration` (to confirm the loss epoch key equals the request epoch recorded in `lastWithdrawRequest`) should be confirmed by the PoC run, but the aggregate-vs-latest-epoch mismatch in `_claimLossAdjustedWithdrawRequest` is structurally present regardless.

  function claimWithdrawRequest(address _user) external returns (uint256 amount) {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized) {
      // Post-default requests are already priced after the haircut and backed by the reserve,
      // so they must not fall through to the defaulted-epoch receipt logic.
      amount = _claimPostDefaultWithdrawRequest(_user);
      if (amount != 0) return amount;
      // Only receipts created in the defaulted epoch are haircutted here; old fulfilled
      // receipts are handled below at par if they were already funded before default.
      amount = _claimDefaultedWithdrawRequest(_user);
    }
    amount += _claimLossAdjustedWithdrawRequest(_user);
    return amount + _claimFundedWithdrawRequest(_user);
  }

  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);
  }

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }
