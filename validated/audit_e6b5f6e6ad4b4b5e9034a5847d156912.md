### Title
Stale per-epoch instant-withdraw receipt inflates defaulted-epoch claims and permanently freezes recovery funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` clears only the aggregate `instantWithdrawsRequests[_user]` counter but never clears `instantWithdrawsRequestsByEpoch[_user][epoch]` or decrements `instantWithdrawClaimsByEpoch[epoch]` (IdleCreditVault.sol:387-392). The default-recovery path `_claimDefaultedInstantWithdrawRequest` reads the per-epoch slot as the claim basis (IdleCreditVault.sol:844). A funded, already-paid instant receipt therefore remains registered as an outstanding claim for its epoch — the same class of stale-count/aliasing bug as CVE-2018-16880's OOB write: a counter believed to describe live entries actually includes entries already consumed elsewhere. If a default is finalized for that epoch, the phantom receipt is counted again in the defaulted-epoch claims, inflating `instantWithdrawClaimsByEpoch[defaultEpoch]` and the recovery reserve carved out of recovered funds, while the corresponding claim can never execute.

### Finding Description
The bug chain, all reachable by an unprivileged KYC'd lender (a tranche-token holder) via the CDO, in a running epoch `E`:

1. Attacker deposits, obtains tranche tokens, then calls `requestInstantWithdraw` → `instantWithdrawsRequests[attacker] = X`, `instantWithdrawsRequestsByEpoch[attacker][E] = X`, `instantWithdrawClaimsByEpoch[E] = X`, `pendingInstantWithdraws = X`, and `X` receipt strategy tokens are minted to the attacker (IdleCreditVault.sol:366-374).
2. The CDO funds the request via `collectInstantWithdrawFunds(X)` (`pendingInstantWithdraws -= X`, IdleCreditVault.sol:401) and the attacker claims via `claimInstantWithdrawRequest`, which burns the receipt, zeroes `instantWithdrawsRequests[attacker]` and pays `X` at par — but leaves `instantWithdrawsRequestsByEpoch[attacker][E] = X` and `instantWithdrawClaimsByEpoch[E] = X` untouched (IdleCreditVault.sol:387-392).
3. The borrower is defaulted in epoch `E` (`defaultRecoveryEpoch = E`). Default finalization sizes the isolated `defaultRecoveryReserve` from `instantWithdrawClaimsByEpoch[E]`, which still includes the phantom `X`, so `X * defaultRecoveryPrice / RECOVERY_FULL` of recovered underlyings is set aside for a claim that corresponds to no live receipt.
4. On the attacker's later `claimInstantWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest` reads `claimBasis = X` and computes `instantWithdrawsRequests[attacker] -= X` (IdleCreditVault.sol:848). Any new instant request the attacker opens in `E` increases the aggregate and the per-epoch slot by equal amounts, so the per-epoch slot is always ≥ the aggregate — the subtraction underflows and the whole claim reverts. The phantom `X` locked in the reserve is unclaimable by anyone, forever, because only `_transferDefaultRecovery` can spend the reserve (IdleCreditVault.sol:915) and `transferToken` cannot distinguish it.

The same stale-slot mechanism also applies to `withdrawsRequestsByEpoch`-style flows only partially (funded normal claims do clear per-epoch data through `_clearWithdrawClaimForEpoch`), making the instant path uniquely inconsistent: funded instant claims are the only receipt type whose per-epoch entry is never cleared.

### Impact Explanation
Every defaulted-epoch finalization over-allocates the recovery reserve by the sum of all instant receipts that were already funded and claimed at par earlier in that same epoch. That amount (`Σ phantomX * defaultRecoveryPrice / RECOVERY_FULL`) is carved out of the recovery pool that would otherwise accrue to defaulted-epoch claimants and LPs via the recovery distribution, and it can never be withdrawn — the only code path that spends `defaultRecoveryReserve` reverts on the underflow at `instantWithdrawsRequests[_user] -= claimBasis`. This is permanent freezing of unclaimed recovery yield belonging to honest defaulted-epoch claimants and junior tranche holders, with a quantifiable loss equal to the phantom instant-claim volume times the recovery price. Additionally, any attacker (or honest user) who claimed an instant withdrawal in the defaulted epoch and still holds a new instant receipt in that epoch is permanently unable to claim it — their own receipt freezes, and `processWithdrawalClaims`-style batch flows that iterate claims can revert.

### Likelihood Explanation
Requires only ordinary unprivileged actions: deposit, request instant withdrawal, claim it once funded — all standard operations available to any KYC'd lender during a running epoch. The trigger condition (a borrower default finalized in the same epoch) is an honest-privileged sequence that the attacker cannot cause but also cannot be excluded; defaults are the designed-for scenario. No privileged cooperation is needed, and no existing guard stops it: `_transferFundedClaim`'s reserve check only guards the funded path, `_ensureDefaultRecoveryInitialized` explicitly does not clear instant counters ("Pending instant withdrawals are never cleared automatically", IdleCreditVault.sol:923), and there is no code path that clears `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch` on a funded claim.

### Recommendation
In `claimInstantWithdrawRequest`, after paying a funded receipt, clear the per-epoch bookkeeping symmetrically with `_claimDefaultedInstantWithdrawRequest`: record the request epoch(s) (e.g., a `lastInstantWithdrawRequest[_user]` marker or iterate the known epoch) and set `instantWithdrawsRequestsByEpoch[_user][epoch] = 0` and `instantWithdrawClaimsByEpoch[epoch] -= amount`. Alternatively, make `_claimDefaultedInstantWithdrawRequest` clamp `claimBasis` to `min(instantWithdrawsRequestsByEpoch[_user][defaultEpoch], instantWithdrawsRequests[_user])` and reconcile `instantWithdrawClaimsByEpoch` during finalization against still-unfunded receipts only.

### Proof of Concept
Foundry fork scenario (scaffold as in `test/foundry/IdleCreditVault.t.sol`):

```solidity
// Epoch E running, instant withdrawals enabled via setInstantWithdrawParams
uint256 X = 100e6;
uint256 tranches = _depositWithUser(attacker, X);

// 1) Attacker requests instant withdraw and it gets funded by CDO/borrower
cdoEpoch.requestInstantWithdraw(X, attacker);          // via CDO prank path
strategy.collectInstantWithdrawFunds(X);               // pendingInstantWithdraws -> 0
cdoEpoch.claimInstantWithdrawRequest(attacker);        // paid at par

// Stale slots remain:
assertEq(strategy.instantWithdrawsRequestsByEpoch(attacker, E), X);
assertEq(strategy.instantWithdrawClaimsByEpoch(E), X);
assertEq(strategy.instantWithdrawsRequests(attacker), 0);

// 2) Honest borrower default is finalized in the same epoch E
//    (manager/keeper call sequence: stopEpochWithDuration or default handling)
//    -> defaultRecoveryEpoch == E, reserve sized from instantWithdrawClaimsByEpoch[E]
//    -> reserve includes phantom X * defaultRecoveryPrice / RECOVERY_FULL

// 3) Any later claimInstantWithdrawRequest for attacker reverts on underflow:
vm.expectRevert(); // panic: arithmetic underflow at instantWithdrawsRequests -= claimBasis
cdoEpoch.claimInstantWithdrawRequest(attacker);

// 4) The phantom-reserve slice is unspendable: _transferDefaultRecovery is the only
//    consumer and the claim path that reaches it always reverts first.
assertEq(strategy.defaultRecoveryReserve(), expectedPhantomSlice); // permanently locked
```

The `expectRevert` at step 3 demonstrates both branches of the impact: the attacker's legitimate receipt cannot be claimed, and the inflated `defaultRecoveryReserve` portion is stranded with no reachable spender.
