### Title
Unbounded overwrite of `savedCallbacks` by attacker-chosen `MessageId` causes silent loss / cross-user delivery of `web_api_trigger` responses - (File: `core/services/gateway/handlers/capabilities/handler.go`)

### Summary
The gateway's `capabilities.handler` stores each pending `web_api_trigger` user request in a shared map `h.savedCallbacks`, keyed solely by the caller-supplied `msg.Body.MessageId`, with no check for whether that key already has a pending, unresolved entry before overwriting it — directly analogous to the reported `batchTransfer` flaw where a per-request local state update silently clobbers state belonging to another party.

### Finding Description
In `HandleLegacyUserMessage`, once basic validation passes, the handler unconditionally does: [2](#0-1) 
This assignment is a blind map write: if an entry already exists under `msg.Body.MessageId` (from a still-pending, not-yet-responded-to request — whether from the same signer or a different one, since nothing scopes the key by sender), it is silently replaced. The original caller's `handlers.Callback` reference is discarded, orphaning that HTTP request; it will only ever complete via `pruneCallbacks`'s periodic expiry sweep (default up to `defaultCallbackMaxAgeSec` = 120s later) rather than getting a legitimate response. [3](#0-2) 

Worse, when a DON node later responds for that `MessageId`, `handleWebAPITriggerMessage` looks the ID up and delivers the *first* response found to whatever callback currently occupies that slot: [4](#0-3) 
If attacker B submits a `web_api_trigger` request reusing the same `MessageId` as victim A's still-in-flight request, B's callback overwrites A's. When a node's response for A's original request arrives (still routed by the same `MessageId`, since it echoes back what was sent to nodes), it is delivered to B instead of A — a direct cross-user response confusion. Conversely, if B's own subsequent legitimate request is the one whose response arrives, A never gets any answer and A's original request appears to hang.

This differs from the sibling `vault.handler`, which explicitly guards against this exact class of bug by rejecting duplicate IDs instead of overwriting: [5](#0-4) 
and from `handlers/handler.dummy.go`, which has the identical unguarded overwrite pattern. [6](#0-5) 

The `MessageId` is attacker-controlled input carried in the signed `api.MessageBody`, only checked for length and general message-signature validity before reaching the gateway handler layer, with no per-key collision check performed anywhere on the path from `gateway.ProcessRequest` into `HandleLegacyUserMessage`. [7](#0-6) [8](#0-7) 

### Impact Explanation
An unprivileged client of the gateway can cause another concurrent user's `web_api_trigger` request/response to be silently dropped (denial of service — the legitimate caller only recovers via the ~2 minute prune timeout, or times out at the HTTP layer first) or, in the worse case, cause a node's response intended for one requester's execution to be delivered to a different requester's HTTP connection (cross-user response confusion). This does not require any privileged access — any client able to submit a `web_api_trigger` message with a chosen `MessageId` can trigger it.

### Likelihood Explanation
Exploitation requires only that an attacker (or a client with a buggy/colliding ID generator) send a `web_api_trigger` request whose `MessageId` matches one currently in-flight from another caller — no allowlist bypass, secret knowledge, or timing beyond normal race conditions is needed. `MessageId` collisions could occur adversarially (deliberately reusing a guessed/observed ID before the legitimate request completes) or accidentally, and the existing test suite already documents that this map is written with no uniqueness enforcement (`handler_test.go` tests only check error paths avoid leaving stale entries, not concurrent legitimate ones). [9](#0-8) 

### Recommendation
Mirror the pattern already used in `vault.handler.newActiveRequest`: check for an existing, non-expired entry under the key before inserting, and reject (or return a conflict error) instead of silently overwriting: [5](#0-4) 
Additionally, scope the callback map key by sender/signer (not just the raw `MessageId`) so that different signers can never collide, and apply the same fix to the structurally identical `handlers/handler.dummy.go`.

### Proof of Concept
1. Client A signs and sends a `web_api_trigger` legacy message with `MessageId = "X"` to the gateway; `HandleLegacyUserMessage` stores A's callback at `savedCallbacks["X"]` and forwards to all DON members.
2. Before any node responds, Client B (different signer, or same signer reusing an ID) sends another `web_api_trigger` message also with `MessageId = "X"`. `HandleLegacyUserMessage` overwrites `savedCallbacks["X"]` with B's callback — A's callback reference is lost with no error to A.
3. A DON node responds for `MessageId = "X"` (echoing A's original request/response cycle). `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds B's callback, and delivers A's response payload to B.
4. Client A's HTTP request hangs until its own timeout/prune interval elapses with no response ever delivered, while Client B silently receives a response for a request it never actually issued to the nodes.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)

func (h *handler) HandleLegacyUserMessage(ctx context.Context, msg *api.Message, callback handlers.Callback) error {
	body := msg.Body
	var payload webapicap.TriggerRequestPayload
	codec := api.JsonRPCCodec{}
	err := json.Unmarshal(body.Payload, &payload)
	if err != nil {
		h.lggr.Errorw(ErrDecodingPayload, "err", err)
		return callback.SendResponse(handlers.UserCallbackPayload{
			RawResponse: codec.EncodeNewErrorResponse(
				msg.Body.MessageId,
				api.ToJSONRPCErrorCode(api.UserMessageParseError),
				ErrDecodingPayload+" "+err.Error(),
				nil,
			),
			ErrorCode: api.UserMessageParseError,
		})
	}
