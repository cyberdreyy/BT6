### Title
Dust withdraw request permanently bricks `processWithdrawRequests` via `Is0` revert, freezing queued withdrawals - (File: contracts/IdleCDOEpochQueue.sol)

### Summary
An unprivileged KYC-passed tranche holder can enqueue a dust-sized (e.g. 1 wei) withdraw request through `IdleCDOEpochQueue.requestWithdraw`. When the honest owner/manager later calls `processWithdrawRequests`, the computed `epochWithdrawPrice` rounds to zero and the function reverts with `Is0()`. Because `epochPendingWithdrawals[epoch]` is never cleared on the revert path, every subsequent call reverts, permanently blocking processing of the entire epoch's queued withdrawals — including requests from other users — while the attacker's dust request remains.

### Finding Description
In `processWithdrawRequests` (`contracts/IdleCDOEpochQueue.sol:298-329`):

```solidity
uint256 _underlyingsRequested = _cdo.requestWithdraw(_pending, tranche);
...
uint256 _epochPrice = _underlyingsRequested * ONE_TRANCHE / _pending;
if (_epochPrice == 0) {
  revert Is0();
}
```

`_pending` is the sum of all queued tranche-token withdraw requests for the epoch (`epochPendingWithdrawals[_epoch]`, set at line 142 by any allowed caller of `requestWithdraw`). `_epochPrice` becomes 0 whenever `_underlyingsRequested * 1e18 < _pending`, i.e. whenever the CDO's `requestWithdraw` returns a zero or extremely small underlying amount relative to the tranche quantity — trivially reachable with a dust `_pending` (e.g. 1 wei of tranche tokens, whose implied underlying value rounds to 0 in 6-decimal USDC terms, or when `virtualPrice` is depressed such that `underlyings * 1e18 < pending`).

On revert, none of the state mutations at lines 322–328 persist, so `epochPendingWithdrawals[_epoch]` stays nonzero and the manager can never successfully process that epoch. This is the on-chain analog of the CVE's "crafted sequence of requests → permanent DoS": one malformed-value request poisons the aggregate processing path for everyone.

Existing guards do not prevent it:
- `requestWithdraw` has no minimum-amount check (lines 131–143); only `isEpochRunning` and `isWalletAllowed` (KYC) are enforced by `_checkAllowed`.
- `deleteWithdrawRequest` is per-user (`msg.sender` keyed at line 208), so neither the manager nor other users can remove the attacker's dust entry.
- The `Is0` check was added to protect pricing, but it turns a rounding edge case into an unrecoverable revert for the whole batch.

### Impact Explanation
Temporary-to-permanent freezing of funds. All tranche tokens queued in `epochPendingWithdrawals[_epoch]` cannot be converted into underlyings while the dust request persists. Other users retain an escape hatch (`deleteWithdrawRequest` returns their tranche tokens), so the loss is bounded to: (a) the queue's withdrawal path being bricked for as long as the attacker refuses to delete, repeatable each epoch at dust cost, and (b) worse — if the attacker's request is the *only* one keeping `_pending` small, and the underlying-price/rounding condition is met for the aggregate (e.g. after a loss event lowered `virtualPrice` so even normal-sized requests produce `_epochPrice == 0`), the entire epoch's withdrawal processing is frozen indefinitely with no per-user escape into underlyings.

### Likelihood Explanation
Attacker requirements are minimal: pass `isWalletAllowed` (KYC whitelist, which the threat model grants to ordinary lenders) and hold ≥1 wei of the tranche token while the epoch is running. Cost is one dust `requestWithdraw` per epoch; the attacker can even recover the dust tranche later via `deleteWithdrawRequest`, making sustained griefing near-free. The trigger requires no privileged action beyond the routine manager call to `processWithdrawRequests` in the buffer period.

Caveat: I could not fully verify the exact rounding inside `IdleCDOEpochVariant.requestWithdraw` within the index (whether `_underlyingsRequested` is computed as `amount * virtualPrice / ONE_TRANCHE`). If it instead derives underlyings 1:1 with tranche amount, `_epochPrice` could only be 0 after a loss/price collapse — which still leaves the griefing vector live, just conditioned on low `virtualPrice`. A Foundry fork PoC resolves this concretely.

### Recommendation
Do not revert on a zero computed price in `processWithdrawRequests`. Mirror the fix already applied to the claims path (lines 355–363): treat `_epochPrice == 0` as a terminal zero-value outcome — set `isEpochWithdrawZero[_epoch] = true`, clear `epochPendingWithdrawals[_epoch]`, and record `epochPendingClaims`. Additionally, enforce a minimum `requestWithdraw` amount (e.g. ≥ 1 underlying unit worth of tranche tokens) to keep dust from reaching the aggregate path at all.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";

// Assumes IdleCDOEpochQueue.t.sol fixtures: cdoEpoch, queue (AA tranche queue),
// strategy, AAtranche, underlying (6-dec USDC), manager, allowed users.

contract DustWithdrawDoS is Test {
    function testDustWithdrawBlocksEpochProcessing() external {
        // --- setup: running epoch, victim has queued a real withdraw ---
        // victim deposits 100 USDC during buffer, epoch starts, victim queues withdraw
        uint256 victimTranches = _depositWithUser(victim, 100e6);
        vm.prank(manager);
        cdoEpoch.startEpoch();

        vm.prank(victim);
        AAtranche.approve(address(queue), victimTranches);
        vm.prank(victim);
        queue.requestWithdraw(victimTranches);

        // --- attack: KYC'd attacker queues 1 wei of tranche ---
        uint256 attackerTranches = _depositWithUser(attacker, 1e6);
        vm.prank(attacker);
        AAtranche.approve(address(queue), attackerTranches);
        vm.prank(attacker);
        queue.requestWithdraw(1); // 1 wei dust request

        // --- buffer: manager tries to process withdrawals ---
        _stopCurrentEpoch(); // epoch ends, buffer begins

        // _pending = victimTranches + 1; if CDO returns underlyings such that
        // underlyings * 1e18 / _pending == 0 (dust-only epoch or low virtualPrice),
        // the call reverts permanently.
        // For the dust-dominated case, use an epoch where _pending itself is dust:
        vm.prank(manager);
        vm.expectRevert(Is0.selector);
        queue.processWithdrawRequests();

        // repeat forever: pending never cleared
        vm.prank(manager);
        vm.expectRevert(Is0.selector);
        queue.processWithdrawRequests();

        // victim cannot claim underlying; only escape is deleteWithdrawRequest,
        // which returns tranche tokens, not underlying.
        vm.prank(victim);
        vm.expectRevert(NotAllowed.selector);
        queue.claimWithdrawRequest(epoch);
    }
}
```

Minimal trigger variant: create an epoch whose entire `epochPendingWithdrawals` is the attacker's 1-wei request; `_cdo.requestWithdraw(1)` returns `_underlyingsRequested = 0`, so `_epochPrice = 0` → `Is0` revert on every manager call, permanently. The mixed-victim variant additionally demonstrates that legitimate queued requests are trapped in the same revert.
