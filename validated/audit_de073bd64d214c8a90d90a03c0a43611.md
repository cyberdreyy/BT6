I found a concrete, in-scope binding violation in the multisig contract. This is not the Solidity `ProposedOwnable` bug directly, but the same underlying bug class — "an authorization boundary can be satisfied by a party whose standing has already changed" — reappears here as a stale-confirmation / threshold-bypass issue in `multisig2`.

### Title
Removing a multisig member does not invalidate their prior confirmations on other requests, allowing a request to execute below the live-member confirmation threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` only purges the confirmations of requests that were *created* by the removed member. It never scrubs that member's confirmation entries from the `confirmations` set of requests created by *other* members. Because `confirm` only checks the raw size of the `confirmations` set against `num_confirmations` [1](#0-0) , a stale confirmation from a member who has since been removed still counts toward the threshold, letting a pending request execute with fewer than `num_confirmations` *live* members approving it.

### Finding Description
The confirmation-counting invariant the contract is supposed to enforce is: `count(confirmations for request R) == count(distinct current members who confirmed R)`.

`delete_member` breaks this invariant: [2](#0-1) 

It filters `self.requests` for entries where `r.member == member` (i.e., requests the removed member *authored*) and clears confirmations only for those. It never iterates over the confirmation sets of requests authored by *other* members to remove the departing member's entry from them.

Meanwhile, `confirm` simply compares the raw cardinality of the stored `confirmations` `HashSet<String>` to `num_confirmations`: [3](#0-2) 

`current_member()` correctly prevents a removed member from *adding a new* confirmation (it checks `self.members.contains(&member)`) [4](#0-3) , but it does nothing to retroactively invalidate a confirmation that member already cast before being removed.

### Impact Explanation
This directly matches the Critical category "a multisig request executed below threshold." A request that is supposed to require `K` confirmations from currently-trusted members can execute with as few as `K-1` (or fewer, if multiple confirmers are later removed) live approvals, because a former member's stale confirmation is silently counted. Since `execute_request` can perform `Transfer`, `AddKey`, `FunctionCall`, `DeployContract`, etc. [5](#0-4) , this can move funds or grant access with insufficient live authorization — an authorization/threshold binding is broken.

### Likelihood Explanation
This requires no external/unprivileged attacker at all — it is triggered purely through the contract's own documented lifecycle: a request is created and partially confirmed, then normal governance later removes one of the confirming members via a `DeleteMember` request (a supported, expected operation) [6](#0-5) . No special privilege beyond normal, intended multisig usage is needed to end up with a request executing on stale approval.

### Recommendation
When removing a member in `delete_member`, iterate all outstanding requests (not just those the member authored) and remove the departing member's string from each request's `confirmations` set, or re-validate at `confirm`/execution time that every entry in `confirmations` still corresponds to a current member before counting it toward the threshold.

### Proof of Concept
1. Deploy `multisig2` with `num_confirmations = 3` and `members = {A, B, C, D}`.
2. `A` calls `add_request` to create request `R` (e.g., `Transfer` to an attacker-controlled `receiver_id`), then `A` calls `confirm(R)` → `confirmations(R) = {A}`.
3. `B` calls `confirm(R)` → `confirmations(R) = {A, B}` (still below threshold of 3).
4. Separately, members legitimately create and confirm a `DeleteMember{B}` request through normal governance, and it executes, calling `delete_member` for `B`. Per `delete_member`'s logic [7](#0-6) , since `B` did not author `R`, `R`'s confirmations are untouched — `confirmations(R)` still contains `"B"`.
5. Now only `C` (a single additional *live* member) needs to call `confirm(R)`. `confirmations.len() as u32 + 1 = 3 >= num_confirmations (3)`, so `R` executes [3](#0-2) , even though only `A` and `C` are currently live members who actually approved it — one fewer live approval than the configured threshold requires, with `B`'s stale confirmation making up the difference.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Returns current member: either predecessor as account or if it's the same as current account - signer.
    fn current_member(&self) -> Option<MultisigMember> {
        let member = if env::current_account_id() == env::predecessor_account_id() {
            MultisigMember::AccessKey {
                public_key: env::signer_account_pk()
                    .try_into()
                    .unwrap_or_else(|_| env::panic_str("Failed to deserialize public key")),
            }
        } else {
            MultisigMember::Account {
                account_id: env::predecessor_account_id(),
            }
        };
        if self.members.contains(&member) {
            Some(member)
        } else {
            None
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
