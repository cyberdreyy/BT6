### Title
JWT verification ignores the `iss`/`aud`/`sub` domain-binding claims it defines, enabling cross-context signature reuse - ([File: core/utils/jwt.go])

### Summary
The Velodrome finding is about a `DOMAIN_TYPEHASH` that declares fewer fields than the domain separator actually used for signing/verification, breaking the domain-binding guarantee of EIP-712 and allowing a signature computed for one “domain” context to be misapplied. The Chainlink analog is Chainlink's custom `ETH`-alg JWT scheme: `CreateRequestJWT` defines `iss` (issuer), `aud` (audience), and `sub` (subject) claims that are clearly intended to scope a signed token to a specific verifying context, but `VerifyRequestJWT` never checks any of them.

### Finding Description
`CreateRequestJWT` builds a `JWTClaims` struct with `Issuer`, `Subject`, `Audience`, `Digest`, `ID` (jti), `ExpiresAt`, and `IssuedAt` [1](#0-0) , with `WithIssuer`, `WithAudience`, and `WithSubject` provided as configuration options for signers [2](#0-1) .

`VerifyRequestJWT`, however, only exposes `WithMaxExpiryDuration` and `WithIssuedAtTolerance` as verify options [3](#0-2) [4](#0-3) . Inside `VerifyRequestJWT`, the `jwt.ParseWithClaims` callback only checks the signing algorithm and returns the recovered signer's address as the key — it never calls `jwt.WithIssuer(...)` or `jwt.WithAudience(...)`, and the claims themselves are never checked for `Issuer`/`Audience`/`Subject` correctness [5](#0-4) . The only bindings actually enforced are: signature validity, `jti` presence, `exp`/`iat` presence and bounds, and that the `digest` claim matches the caller-supplied `req.Digest()`.

This means the `iss`/`aud`/`sub` fields are structurally present in the token (just like Velodrome's `EIP712Domain` string that *should* include `version`) but are silently dropped from the actual verification logic — the “domain” the token was minted for is not cryptographically or programmatically enforced at verification time.

A concrete consumer of this API is `WorkflowMetadataHandler.Authorize`, which calls `utils.VerifyRequestJWT(token, *req)` with no options at all, relying solely on digest matching plus a per-workflow signer allowlist for authorization [6](#0-5) .

### Impact Explanation
Because the audience/issuer/subject claims are unauthenticated with respect to the verifying party, any JWT that was legitimately signed by an authorized ECDSA key for one context (one intended audience/subject) will verify successfully in any other caller of `VerifyRequestJWT` as long as the JSON-RPC request content (and thus its digest) happens to match. This weakens the intended isolation between different consumers of this shared JWT scheme (currently `WorkflowMetadataHandler` in the gateway, with the scheme documented for JSON-RPC request authentication generally). If the JWT scheme is reused by additional handlers/services (as its generic design in `core/utils/jwt.go` — decoupled from any specific handler — invites), a token minted for context A could be replayed against context B without any check flagging the audience/issuer mismatch, since those claims are computed but never compared. This is analogous to the missing `version` in `DOMAIN_TYPEHASH`: a field intended to scope/bind the signature is present in the payload but omitted from the verification path.

### Likelihood Explanation
Exploitation requires only sending a valid, previously-observed (or self-obtained) signed JWT to a different `VerifyRequestJWT` consumer than the one it was intended for, with a matching request digest — an unprivileged-client-reachable action, no operator/node privileges needed. The bug is a code-level omission (missing claim validation), not a chance/timing issue, so it is deterministic and reliably reproducible whenever more than one consumer of `VerifyRequestJWT` exists or is added.

### Recommendation
Add explicit `iss`/`aud`/`sub` validation to `VerifyRequestJWT` (mirroring `WithIssuer`/`WithAudience`/`WithSubject` used at creation time), analogous to how `jwtBasedAuth.validateToken` explicitly enforces `jwt.WithIssuer` and `jwt.WithAudience` for the Auth0-based scheme [7](#0-6) . Require callers of `VerifyRequestJWT` to supply the expected issuer/audience/subject and reject tokens that don't match, so the domain-binding claims are enforced consistently everywhere the shared ETH-JWT scheme is used.

### Proof of Concept
1. Party A obtains (or is issued) a signed JWT via `CreateRequestJWT` with `Audience`/`Issuer` set for a specific intended verifying context (e.g., context "X").
2. Party A (or an observer) submits this same token to a different consumer of `utils.VerifyRequestJWT` (context "Y") along with a JSON-RPC request whose `Digest()` matches the `digest` claim embedded in the token.
3. `VerifyRequestJWT` succeeds because it only checks signature validity, `jti` replay, expiry bounds, and digest match — it never inspects `Issuer`/`Audience`/`Subject`, so context Y's verifier accepts a token that was never intended for it [5](#0-4) .

	if err != nil {
		return nil, gethcommon.Address{}, err

		return nil, gethcommon.Address{}, errors.New("JWT ID (jti) is required but missing")

	}
	now := time.Now()
	issuedAt := verifiedClaims.IssuedAt
	if issuedAt.After(now.Add(issuedAtTolerance)) {
		return nil, gethcommon.Address{}, fmt.Errorf("issuedAt (iat) is too far in the future (beyond tolerance of %.0f seconds)", issuedAtTolerance.Seconds())

	}

		return nil, gethcommon.Address{}, fmt.Errorf("claim digest '%s' does not match calculated request digest '0x%s'", verifiedClaims.Digest, reqDigest)
	}

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}
