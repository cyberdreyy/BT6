### Title
External Initiator credentials bypass "EIs not allowed" restriction and can trigger arbitrary job runs by numeric ID - ([File: core/web/auth/auth.go], [File: core/web/pipeline_runs_controller.go])

### Summary
`AuthenticateExternalInitiator` sets the same `SessionUserKey` context value used for real dashboard/API users, giving every successfully authenticated EI a `clsessions.User{Role: clsessions.UserRoleRun}`. `PipelineRunsController.Create` tries to gate numeric-ID job triggering to "users only" via `auth.GetAuthenticatedUser(c)`, but that check cannot distinguish a real user from an EI because both populate `SessionUserKey`. As a result, any EI credential (intended only to invoke its own webhook job) can trigger a run for **any** integer job ID on the node.

### Finding Description
The route `POST /v2/jobs/:ID/runs` is registered with all three auth methods, including EI: [1](#0-0) 

`auth.Authenticate` tries each `authMethod` in order and stops at the first success. If EI headers (`static.ExternalInitiatorAccessKeyHeader`/`SecretHeader`) validate, `AuthenticateExternalInitiator` runs and sets: [2](#0-1) 

This is the *same* `SessionUserKey` that `AuthenticateBySession`/`AuthenticateByToken` set for genuine human/API users: [3](#0-2) [4](#0-3) 

`RequiresRunRole` only rejects `UserRoleView`, so the injected `UserRoleRun` value passes: [5](#0-4) 

Inside `Create`, the code explicitly intends to restrict numeric-ID job triggering to real users, with a comment stating "EIs not allowed": [6](#0-5) 

But `isUser := auth.GetAuthenticatedUser(c)` merely checks whether a `*clsessions.User` object exists in the gin context — it does not check whether the caller actually authenticated as a session/token user versus an EI. Since `AuthenticateExternalInitiator` also populates that key, `isUser` is `true` for EI-authenticated requests too. The intended EI/UUID-only restriction (lines 103-107, which now hard-errors on UUID-format IDs because webhook-by-UUID triggering was removed) is therefore completely bypassed for any EI credential — it can supply an arbitrary integer job ID and reach `prc.App.RunJobV2(ctx, jobID, nil)`, exactly like a legitimate user, for jobs it has no relationship to.

### Impact Explanation
An attacker holding only a low-trust external-initiator access key/secret (meant to authorize triggering of a single specific webhook-linked job) can trigger pipeline runs for any job ID on the node, including jobs owned by other users/bridges. This is an authorization bypass leading to unauthorized job execution ("unauthorized job run" bounty class), which can cascade into unwanted on-chain transactions or resource exhaustion if the targeted job performs fund-moving or side-effecting tasks.

### Likelihood Explanation
The only precondition is possession of any valid EI access key/secret pair for the node (the lowest-trust credential class explicitly in scope). No specific job association, role escalation, or additional secret is required — job IDs are small sequential integers and easily enumerable via `GET /v2/jobs`. The bypass is fully deterministic and repeatable for every request.

### Recommendation
Distinguish EI-derived sessions from genuine user sessions instead of relying on `GetAuthenticatedUser` presence alone — e.g., set a separate context flag (or check `GetAuthenticatedExternalInitiator`) and have `PipelineRunsController.Create` explicitly reject requests where an external initiator is present, regardless of the injected `UserRoleRun` value.

### Proof of Concept
Go handler-level test plan (in `core/web/pipeline_runs_controller_test.go` style):
1. Seed two jobs: `jobA` (associated with EI `ei1`'s intended webhook) and `jobB` (unrelated job owned by a different bridge/user), both with valid int32 IDs.
2. Build a gin router using the real `userOrEI` group wiring from `v2Routes` (or replicate `auth.Authenticate(..., auth.AuthenticateExternalInitiator, ...)` + `auth.RequiresRunRole(prc.Create)`).
3. Send `POST /v2/jobs/{jobB.ID}/runs` with headers `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` set to `ei1`'s valid credentials (not associated with `jobB`).
4. Assert: response is `200 OK` with a pipeline run resource for `jobB` (mock/stub `App.RunJobV2` to record the `jobID` argument and assert it equals `jobB.ID`).
5. Contrast with expected behavior: assert the request should instead be rejected with `422`/`401` since the caller only authenticated via EI, not as a genuine session/token user.

func AuthenticateBySession(c *gin.Context, authr Authenticator) error {
	ctx := c.Request.Context()
	session := sessions.Default(c)
	sessionID, ok := session.Get(SessionIDKey).(string)
	if !ok {
		return auth.ErrorAuthFailed
	}

	user, err := authr.AuthorizedUserWithSession(ctx, sessionID)
	if err != nil {
		return err
	}

	c.Set(SessionUserKey, &user)

	return nil
}

func AuthenticateByToken(c *gin.Context, authr Authenticator) error {
	ctx := c.Request.Context()
	token := &auth.Token{
		AccessKey: c.GetHeader(APIKey),
		Secret:    c.GetHeader(APISecret),
	}
	if token.AccessKey == "" {
		return auth.ErrorAuthFailed
	}

	if token.Secret == "" {
		return auth.ErrorAuthFailed
	}

	// We need to first load the user row so we can compare tokens using the stored salt
	user, err := authr.FindUserByAPIToken(ctx, token.AccessKey)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) || errors.Is(err, clsessions.ErrUserSessionExpired) {
			return auth.ErrorAuthFailed
		}
		return err
	}

	ok, err := clsessions.AuthenticateUserByToken(token, &user)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionUserKey, &user)

	return nil
}

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
