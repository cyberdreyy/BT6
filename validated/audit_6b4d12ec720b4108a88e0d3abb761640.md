### Title
Legacy capabilities handler lacks message-ID replay/duplicate protection, allowing response hijacking on `HandleLegacyUserMessage` - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`Message.ExtractSigner` only verifies that a signature is valid over `MessageId`/`Method`/`DonId`/`Receiver`/`Payload`, so tampering with any of those fields invalidates the signature and is already rejected — but a byte-identical replay of a previously captured, still-valid `Message` is not detected anywhere in the request path. In the legacy capabilities handler, `HandleLegacyUserMessage` unconditionally overwrites the `savedCallbacks[msg.Body.MessageId]` entry instead of rejecting an in-flight/duplicate message ID, unlike the vault and v2 HTTP trigger handlers which explicitly reject duplicates.

### Finding Description
`gateway.ProcessRequest` decodes the request, calls `msg.Validate()` (which calls `ExtractSigner`) to authenticate the sender, then dispatches to the DON handler via `h.HandleLegacyUserMessage(ctx, msg, callback)` [1](#0-0) . `ExtractSigner`/`Validate` only prove who signed the exact bytes of `MessageId`, `Method`, `DonId`, `Receiver`, and `Payload` [2](#0-1) ; they contain no nonce, timestamp-binding, or single-use enforcement, so tampering with any signed field is rejected (signature mismatch) but re-submitting the exact same signed bytes is indistinguishable from the original valid request.

In `core/services/gateway/handlers/capabilities/handler.go`, `HandleLegacyUserMessage` stores the callback keyed only by `msg.Body.MessageId` with no check for an existing/in-flight entry:
```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
don := h.don
h.mu.Unlock()
``` [3](#0-2) 

If an attacker captures another user's previously valid, still in-flight signed legacy `Message` (same `DonId`/`Method`/`Payload`/`Signature`) and resends it via `ProcessRequest` before the DON nodes respond to the original request, the second call to `HandleLegacyUserMessage` silently overwrites the map entry for that `MessageId` with the attacker's new `callback`. When the DON node later responds, `handleWebAPITriggerMessage` looks up and deletes `savedCallbacks[msg.Body.MessageId]` and delivers the response to whichever callback is currently stored — the attacker's, not the original requester's [4](#0-3) . It also causes the request to be re-dispatched to all DON members a second time [5](#0-4) .

This is a real gap compared to sibling handlers that explicitly enforce single-use/in-flight semantics: `vault` handler rejects with "request was already authorized previously" [6](#0-5) , and the v2 HTTP trigger handler rejects duplicate/in-flight request IDs and re-used JWTs [7](#0-6) . The `dummyHandler.HandleLegacyUserMessage` implementation has the identical unguarded overwrite pattern [8](#0-7) , so this is a systemic gap in the legacy webapi/dummy handler path, not merely a hypothetical.

Note: the premise that an attacker can replay to a *different* DON ID or method is incorrect — `DonId`/`Method` are covered by the signature via `GetRawMessageBody`, so altering either field invalidates the signature and `Validate()`/`ExtractSigner` correctly reject it [9](#0-8) . The exploitable path is a byte-identical replay to the *same* DON/method while the original request is still in-flight.

### Impact Explanation
An attacker who observes a legitimate user's in-flight signed legacy gateway `Message` can hijack the DON's response intended for that user by replaying it, causing cross-user response confusion (the attacker receives another user's capability-execution result) and a duplicated dispatch of the request to all DON nodes. This matches "cross-user response confusion" / request-impersonation impact classes rather than fund movement or key disclosure.

### Likelihood Explanation
Requires the attacker to capture a valid, currently in-flight signed `Message` (e.g., via network observation, logging, or being a legitimate but distinct API caller who colludes/observes another tenant's traffic) and resend the exact bytes to the gateway before the original request completes — a narrow timing window but technically feasible and fully replayable/repeatable since the gateway has no idempotency/nonce tracking for legacy messages. No elevated privileges are needed beyond the ability to send HTTP requests to the gateway endpoint.

### Recommendation
In `core/services/gateway/handlers/capabilities/handler.go` (`HandleLegacyUserMessage`) and `core/services/gateway/handlers/handler.dummy.go` (`HandleLegacyUserMessage`), check for an existing `savedCallbacks[msg.Body.MessageId]` entry before storing and reject the request as a duplicate/in-flight if found (mirroring the pattern already used in the vault and v2 HTTP trigger handlers). Consider also binding `MessageId` uniqueness/freshness more broadly (e.g., a short-lived seen-message-ID cache keyed by sender+messageID) to close this gap consistently across all legacy handlers.

### Proof of Concept
Go test plan (handler-level, analogous to existing `handler_test.go` in the same package):
1. Build a valid `api.Message` for `MethodWebAPITrigger` signed by a test node/user key with a fixed `MessageId`.
2. Call `handler.HandleLegacyUserMessage(ctx, msg, callback1)` — assert it succeeds and `handler.savedCallbacks[msg.Body.MessageId]` holds `callback1`.
3. Before delivering any node response, call `handler.HandleLegacyUserMessage(ctx, msg, callback2)` with the identical signed message bytes — assert current behavior succeeds and overwrites the map entry with `callback2` (demonstrating the missing duplicate check), where the expected/fixed behavior should instead return an error such as "request already in-flight" and leave `callback1` intact.
4. Simulate `handler.HandleNodeMessage` delivering the DON response for that `MessageId` and assert which callback (`callback1` vs `callback2`) receives it — showing the response is delivered to the second (attacker) callback, confirming cross-user response hijacking under current code.

func GetRawMessageBody(msgBody *MessageBody) [][]byte {
	alignedMessageId := make([]byte, MessageIdMaxLen)
	copy(alignedMessageId, msgBody.MessageId)
	alignedMethod := make([]byte, MessageMethodMaxLen)
	copy(alignedMethod, msgBody.Method)
	alignedDonId := make([]byte, MessageDonIdMaxLen)
	copy(alignedDonId, msgBody.DonId)
	alignedReceiver := make([]byte, MessageReceiverLen)
	copy(alignedReceiver, msgBody.Receiver)
	return [][]byte{alignedMessageId, alignedMethod, alignedDonId, alignedReceiver, msgBody.Payload}
}

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
