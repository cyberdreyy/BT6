### Title
Blind retry of `attach` command on network-classified errors bypasses the "already executing" safety check and can duplicate script execution - (File: `executors/kubernetes/kubernetes.go`)

### Summary
GitLab Runner's Kubernetes executor uses a Kubernetes `attach` stream to push each build-stage script into the build container by writing the command to `stdin` [1](#0-0) . When the `attach` call fails, the runner retries via `retry.WithFn`, and the decision whether it's safe to resend the command is delegated to `checkScriptExecution` [2](#0-1) . This mirrors the "fail-safe resend guard" pattern in the Babylon `maybeResendFromStore` report: a check meant to prevent double-submission is present, but is bypassed for a specific class of errors, exactly the class most likely to occur when the action already succeeded.

### Finding Description
`checkScriptExecution` is supposed to consult `s.remoteStageStatus` to determine whether the remote container has already started executing the requested `stage` before deciding to retry the `attach` (i.e., resend the command) [3](#0-2) . However, before that check runs, the function short-circuits: if the error string matches any entry in `retryNetworkErrorsGroup`, it immediately returns the error (forcing a retry) without ever consulting `remoteStageStatus`:

```go
// Non-network errors don't concern this function
if slices.ContainsFunc(retryNetworkErrorsGroup, func(v string) bool {
    return err != nil && strings.Contains(err.Error(), v)
}) {
    return err
}
``` [4](#0-3) 

The comment directly above explains the real risk: "the connection might have broken up after ... meaning the command was never executed" *or* "it could have also been broken during the reading of the response stream — meaning that it was executed, but we can't know that" [5](#0-4) . The `remoteStageStatus` check exists precisely to disambiguate these two cases. But network-classified errors (broken connections, resets, timeouts) are exactly the errors this disambiguation is needed for, and the code deliberately skips it for that category, forcing an unconditional retry/resend of the `attach` command via `retry.WithFn` [2](#0-1) .

Because `AttachOptions.Run()` re-sends the full command string over stdin on every attempt [6](#0-5) , a retry after a network error that occurred *after* the in-container script had already started (e.g., the response stream broke while the request itself was already delivered and running) will inject the stage command a second time into the same container/shell session.

### Impact Explanation
If the stage command is re-injected after having already started running remotely, the build container can execute the same build-stage script twice (e.g. duplicated `script:`/`before_script:` commands), which can corrupt build state, cause spurious duplicate side effects (e.g., duplicate artifact pushes, duplicate deployment commands, doubled resource usage), or produce confusing/incorrect exit-code handling since two concurrent invocations may race for the exit-status marker file. This is a correctness/integrity bug in the execution flow rather than a privilege-escalation or data-exfiltration bug.

### Likelihood Explanation
The trigger condition — a transient network error during the `attach` while the container had already begun executing — is a normal operational condition for the Kubernetes executor (API server hiccups, connection resets, `kubelet`/apiserver churn), not something requiring attacker control or unusual configuration. `retryNetworkErrorsGroup` is intended to flag general network hiccups, so this code path is reachable under ordinary intermittent-connectivity conditions without any admin misconfiguration or privileged access.

### Recommendation
For errors classified as network errors, do not unconditionally force a retry. Instead of the current early-return, always consult `s.remoteStageStatus` first (as is already done for non-network errors) to determine if the target stage has already started; only resend the command when the remote stage state indicates the command was not received/started. If the ambiguity cannot be resolved from `remoteStageStatus` alone for network errors, consider adding an explicit idempotency/generation marker per stage invocation so a duplicate `attach` can be detected and safely ignored by the in-container script runner, similar to how the fix for the Babylon issue separated "not found" from generic RPC errors before deciding to resend.

### Proof of Concept
1. Runner starts a build-stage command in the build container by calling `runInContainer`, which calls `attach.Run()` to write the shell command into the container's stdin stream [7](#0-6) [1](#0-0) .
2. The `attach` stream's read/response side breaks due to a transient network condition (e.g., API-server connection reset) even though the command was already delivered and the shell has begun running it.
3. `attach.Run()` returns an error whose text matches an entry in `retryNetworkErrorsGroup`.
4. `checkScriptExecution` takes the early-return path at lines 3325-3330 [4](#0-3)  and returns the error without checking `s.remoteStageStatus`.
5. `retry.WithFn`'s check function treats the error as retryable and calls `attach.Run()` again, re-writing the same command to stdin `strings.Join(p.Command, " ") + "\n"` [8](#0-7) , causing the build container to receive and execute the stage command a second time.

Note: I was unable to inspect the definition/contents of `retryNetworkErrorsGroup` and the exact `remoteStageStatus` update logic (only grep match locations were found, not their bodies) due to index truncation on `kubernetes.go`; confirming the exact error strings included and the precise timing window in which `remoteStageStatus` gets updated relative to the retry decision would require a full read of the file in a Devin session.

func (s *executor) checkScriptExecution(stage common.BuildStage, err error) error {
	// Retrying attach command is a bit different from regular Kubernetes requests.
	// Since the attach commands are executed by openning an HTTP stream to the Kubernetes server
	// and piping the command into that stream and then expecting a response there's no good place to check
	// whether the whole command execution was successful.
	// If we check whether the Stdin stream was read - the connection might have broken up after during transit of that
	// meaning that the command was never executed.
	// It could have also been broken during the reading of the response stream - meaning that it was executed, but we can't know that.
	// The only solution is to check for certain whether the process is already running.
	// For attach that is easy since the process is completely running in the background, and we receive the status of it through
	// the log file and the log processor moves things forward.
