Found a concrete analog. In both `multisig/src/lib.rs` and `multisig2/src/lib.rs`, request confirmations recorded in the `confirmations` map are never revalidated against the *current* membership set when a member is removed, breaking the binding "confirmations counted == live members counted."

### Title
Multisig executes a request with fewer live-member confirmations than the configured threshold, because a removed member's stale confirmation is still counted - ([File: multisig2/src/lib.rs])

### Summary
`MultiSigContract::confirm` in `multisig2/src/lib.rs` decides whether to execute a request purely by comparing the size of the stored `confirmations: LookupMap<RequestId, HashSet<String>>` set against `num_confirmations`. `delete_member` (invoked via a `DeleteMember` request action) only purges requests that the removed member *originally added* (`r.member == member`), and it purges `num_requests_pk` for that member, but it never scans or prunes the `confirmations` set of *other* pending requests that the removed member had previously confirmed. As a result, a member who is deleted from the multisig continues to count toward the confirmation threshold of any request they confirmed before their removal, so a request can execute with strictly fewer *live* confirming members than `num_confirmations` requires.

### Finding Description
`confirm()`: [1](#0-0) 

`delete_member()` only removes requests added by the deleted member and the member's own request-count bookkeeping — it does not touch `self.confirmations` for other requests: [2](#0-1) 

`current_member()` is only used to authorize the *caller* of `confirm`/`add_request`/`delete_request` at call time — it is never used to re-validate the members already recorded inside a request's `confirmations` HashSet: [3](#0-2) 

The binding that should hold is:
```
confirmations_counted(request) == confirmations_from_current_live_members(request)
```
Because `confirmations` is a plain snapshot of member-identifier strings collected over time, and membership can shrink via `DeleteMember` without pruning existing `confirmations` entries, this equality is violated: a stale confirmation from an account/key no longer in `self.members` is still summed toward `self.num_confirmations` in the `>=` check in `confirm()`.

The exact same structural flaw exists in the older `multisig/src/lib.rs`, where `DeleteKey` only removes requests originated by that key (`r.signer_pk == pk`) and never scrubs that key's confirmations from other pending requests' `confirmations` sets: [4](#0-3) [5](#0-4) 

This is the closest reachable in-scope analog to the Alchemix "emergency exit doesn't block a state-changing action" report: instead of an emergency-exit flag failing to gate minting, a membership-removal action fails to gate/retroactively invalidate previously recorded approvals, letting privileged execution ("mint"/"execute request") proceed on stale/invalid state.

### Impact Explanation
This directly matches the Critical impact category "a multisig request executed below threshold." An attacker who is (or colludes with) a current or soon-to-be-removed member can pre-confirm a malicious request (e.g., `Transfer`, `FunctionCall`, `AddKey` granting a full-access key) before being removed from the multisig, and that confirmation still counts after removal, letting the remaining live members unknowingly complete the threshold with one fewer *actual* live approver than intended. Funds custody by the multisig (`Transfer`, `AddKey` full-access) can then move or be authorized by fewer live approvers than `num_confirmations` mandates — an unauthorized move of NEAR held by the multisig account.

### Likelihood Explanation
Requires only ordinary multisig operations: a member confirms a pending request, then a later `DeleteMember` request executes to remove that member (a normal governance/rotation action, not requiring any privileged bug elsewhere). No redeploy, foundation action, or malicious validator is needed — any legitimate member rotation combined with a pending, partially-confirmed request triggers the stale-count condition. This is a realistic, easily reproduced operational sequence for any multisig that rotates members while requests are in flight.

### Recommendation
When executing `delete_member` (and `DeleteKey` in `multisig`), iterate all entries in `self.confirmations` and remove the deleted member's identifier from every request's confirmation set (not just requests they authored), or alternatively re-validate at `confirm()`-execution time that every entry in the stored confirmation set still corresponds to a `self.members.contains(...)` entry before counting it toward the threshold.

### Proof of Concept
1. Deploy `multisig2` with members `{A, B, C, D, E}` and `num_confirmations = 3`.
2. `A` calls `add_request` to create request `R` (e.g. `Transfer` to attacker-controlled account) — `confirmations[R] = {}`.
3. `B` calls `confirm(R)` → `confirmations.len() + 1 = 1 < 3` → inserted, `confirmations[R] = {B}`.
4. `C` calls `confirm(R)` → `1 + 1 = 2 < 3` → inserted, `confirmations[R] = {B, C}`.
5. Separately, members `A, D, E` execute a `DeleteMember{C}` request (reaching its own 3-confirmation threshold) — `delete_member` runs `self.members.remove(&C)`, but only removes requests where `r.member == C` (i.e. requests *C added*, not `R` which C only confirmed). `confirmations[R]` is untouched, still `{B, C}`.
6. `D` (a live member) calls `confirm(R)` → `confirmations.len() + 1 = 2 + 1 = 3 >= num_confirmations` → `execute_request` runs `R`'s `Transfer` action.
7. Result: `R` executed with confirmations from `{B, C, D}`, but `C` was removed from `self.members` in step 5 — only 2 of the 3 counted confirmations (`B`, `D`) came from currently-live members, one confirmation short of the configured threshold of live approvers.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

        let member = if env::current_account_id() == env::predecessor_account_id() {

                account_id: env::predecessor_account_id(),
            }

            Some(member)

            None
        }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
