### Title
Multisig request can execute below the intended confirmation threshold because stale confirmations from removed members are still counted - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::confirm()` in `multisig2/src/lib.rs` decides whether a request has reached quorum purely by counting entries in the `confirmations` `HashSet<String>` for that request, without checking whether each entry still corresponds to a *currently active* member. `delete_member()` only purges pending requests **submitted** by the removed member, but never scrubs that member's identity out of the `confirmations` sets of other requests they had previously confirmed. This breaks the intended equality `confirmations from live members == num_confirmations` and instead enforces `confirmations from live-or-removed members == num_confirmations`.

### Finding Description
- `confirm()` reaches quorum solely via `confirmations.len() as u32 + 1 >= self.num_confirmations`, with no re-validation of membership for existing entries: [1](#0-0) 

- `delete_member()` removes the member from `self.members` and deletes only the requests they **originally submitted** (`r.member == member`). It does not touch `self.confirmations` entries on *other* requests where the removed member had previously called `confirm()`: [2](#0-1) 

- `assert_valid_request()`, called at the top of `confirm()`, only checks that the request/confirmations map exist and that the *caller* is currently a member — it performs no cleanup or re-validation of previously recorded confirmations: [3](#0-2) 

Concretely: for a `K`-of-`N` multisig, suppose member `B` confirms a pending request `R` submitted by member `A` (confirmations = `{A, B}`, `K=3`). If `B` is later removed via a legitimate `DeleteMember` request (e.g., because `B`'s key was compromised or `B` left the organization), `R` is left untouched because `A`, not `B`, is `R`'s submitter. When any remaining live member `C` later calls `confirm(R)`, the set becomes `{A, B, C}`, satisfying `len()+1 >= 3`, and `execute_request()` runs the request's actions (e.g. `Transfer`, `AddKey`, `FunctionCall`) — even though only 2 of the 3 confirming identities (`A`, `C`) are still trusted members.

### Impact Explanation
This lets a multisig request (including a NEAR `Transfer` out of the contract's balance, `AddKey`/`AddMember`, or an arbitrary `FunctionCall`) execute with fewer than `num_confirmations` **currently authorized** approvers. This directly matches the "multisig request executed below threshold" Critical-impact category: the K-of-N custody guarantee the contract is supposed to provide (funds/administration require K live signers) is silently weakened whenever membership changes while requests are in flight.

### Likelihood Explanation
Member removal (key rotation, compromise response, offboarding) is a normal, expected multisig lifecycle operation, and requests can remain pending for extended periods (bounded only by the 15-minute deletion cooldown and the 12-active-request limit — there is no forced expiry). Any request that collected a confirmation from a member who is subsequently removed will silently retain that stale confirmation indefinitely, so this is readily triggerable during ordinary multisig operation rather than requiring a contrived setup.

### Recommendation
When confirming a request, validate that every account/key already present in `confirmations` is still a current member (e.g., filter `confirmations` against `self.members` before counting, or actively prune `confirmations` for a member in `delete_member()` across **all** requests, not just those they submitted). Alternatively, revalidate `confirmations.iter().filter(|m| self.members.contains(m)).count()` against `num_confirmations` inside `confirm()` before executing.

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C, D]`, `num_confirmations = 3` (`new()`).
2. `A` calls `add_request_and_confirm` with a `Transfer` request `R` to attacker/receiver — confirmations(`R`) = `{A}`.
3. `B` calls `confirm(R)` — confirmations(`R`) = `{A, B}` (below threshold, request stays pending) — see `confirm()` at [4](#0-3) .
4. The multisig legitimately removes `B` via a separate `DeleteMember` request/execution (`execute_request` → `delete_member`) — this only deletes requests where `B` was the submitter, not `R` where `B` merely confirmed — see [5](#0-4) .
5. `C` calls `confirm(R)` — confirmations(`R`) = `{A, B, C}`, `len()+1 (3) >= num_confirmations (3)` → `R` executes via `execute_request`, transferring funds, even though `B` is no longer a member and only 2 live members (`A`, `C`) actually endorsed it at execution time.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
