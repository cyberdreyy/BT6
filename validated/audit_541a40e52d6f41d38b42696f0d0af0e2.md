### Title
`BlockRejection` signature only binds the block hash, not the reject reason or `failed_txid` — an attacker can graft a valid signer signature onto a forged rejection reason - ([File: libsigner/src/v0/messages.rs])

### Summary
`BlockRejection::hash()`, which is what both `sign()` and `verify()`/`recover_public_key()` operate over, only covers `signer_signature_hash` (the block hash) plus the `chain_id`-derived domain tuple. It does not cover `reason`, `reason_code`, or `response_data` (including `failed_txid`, `reject_reason`, `tenure_extend_timestamp`). This mirrors the SimpleSAMLphp class of bug: a validator (here, ECDSA signature verification) is scoped to a narrower payload (block hash) than the data that downstream logic treats as attested (the reject reason / failed tx). Anyone who has observed one legitimately signed `BlockRejection` from a signer for a given block can splice a different `reason_code`/`response_data` onto that same signature and it will still pass `verify()`/`recover_public_key()`.

### Finding Description
`BlockRejection::hash()`: [1](#0-0) 
only hashes `self.signer_signature_hash` under a structured-data domain keyed by `chain_id`. `sign()` signs that hash, and `verify()`/`recover_public_key()` both recompute and check against the same restricted hash: [2](#0-1) 

The `BlockRejection` struct, however, carries additional fields that are *not* part of the signed payload but are trusted as if they came from the signer once the signature checks out: `reason`, `reason_code`, and `response_data` (which includes `reject_reason` and `failed_txid`): [3](#0-2) 

Because ECDSA over a fixed message from a fixed key is deterministic (RFC6979), a signer will produce the exact same `signature` value for the exact same `signer_signature_hash`+`chain_id` regardless of which `reason_code`/`response_data` it attaches. Consequently, once any observer (a peer signer, a relaying node, or anyone with StackerDB read access) has seen one authentic `BlockRejection` signature from signer S for block hash H, they can construct a new `BlockRejection` message for the same H with an arbitrary `reason`, `reason_code`, and `response_data` (e.g. a fabricated `failed_txid` and `RejectCode::ValidationFailed(ValidateRejectCode::ProblematicTransaction)`), reuse S's signature verbatim, and every consumer of these fields will treat it as an authentic statement from S.

Consumers that trust the (unauthenticated) reason/response_data fields once the signature checks out:
- In `stacks-node`'s `StackerDBListener`, the miner tallies per-txid rejection weight and a `problematic_weight` based on `rejected_data.reason_code` and `rejected_data.response_data.failed_txid`, gated only on `recover_public_key()` matching the signer's key — not on any binding between the signature and those fields: [4](#0-3) 
- In the signer's own `handle_block_rejection`/`store_and_process_block_rejection`, the `reject_reason` (`RejectReasonPrefix`) derived from the unauthenticated `response_data.reject_reason` is what feeds the rejection-weight tally, the `ReorgNotAllowed` miner-invalidation path, and (via `should_reevaluate_reject_reason`) whether a given rejected block is ever re-evaluated: [5](#0-4) [6](#0-5) [7](#0-6) 

This is the exact bug class from the report: the cryptographic validator was designed/scoped for one narrower claim (here, "signer S rejected block H") but the surrounding protocol logic treats a broader, unsigned claim ("...and specifically for reason R / tx T") as equally authenticated because the check that ran (`verify`/`recover_public_key`) returned success.

### Impact Explanation
An attacker who can observe StackerDB gossip (no signer key, no majority required — this is purely an on-path/observer forgery, well within the "gossip" capability granted by the rules) can:
- Forge a fabricated `ProblematicTransaction`/`BadTransaction` reason with an arbitrary `failed_txid` attributed to a real signer, inflating `total_weight`/`problematic_weight` for that txid in the miner's `StackerDBListener` tally and causing the miner to treat a legitimate transaction as poisoned/excluded — a miscounted response (a rejection re-attributed to a reason the signer never actually gave).
- Forge a `ReorgNotAllowed` reason attributed to a signer's real rejection of block H, contributing forged weight toward the 30% threshold in `store_and_process_block_rejection` that flips `sortition_state.cur_sortition.miner_status` to `InvalidatedBeforeFirstBlock`, invalidating a legitimate miner tenure — a liveness wedge.
- Manipulate whether the local `should_reevaluate_reject_reason` heuristic treats a prior rejection as re-evaluable (e.g. forging a "sticky" reason such as `DuplicateBlockFound` onto a rejection that was really a transient `ConnectivityIssues`), causing a signer to permanently refuse to reconsider a block it would otherwise have re-validated once the transient condition cleared — another liveness wedge, matching the "wedged into never signing valid blocks" High-impact category.

The final decision to sign/accept a block still requires the normal 70% threshold of actual signatures over the block itself, so this cannot directly forge an invalid/non-canonical block signature. But it does let an unprivileged observer manufacture false "reasons" behind otherwise-genuine rejection signatures, corrupting the weight tallies and heuristics that key off `reason_code`/`failed_txid`/`reject_reason`, matching the "rejection recounted" and liveness-wedge impact classes in scope.

### Likelihood Explanation
The only prerequisite is observing one legitimate `BlockRejection` StackerDB chunk from a target signer for a block hash of interest (trivially available — rejections are broadcast on StackerDB, which is exactly the "gossip" capability the rules allow a single miner/observer to have). No signer key, no majority, and no cooperation from the miner's own signing keys is needed; the attacker only needs to relay a modified copy of an already-observed chunk. Because ECDSA signing in this codebase does not add fresh randomness beyond RFC6979-determinism per (key, message), the signature reused for a different `reason_code`/`response_data` payload verifies successfully every time.

### Recommendation
Bind the full response semantics into the signed hash. `BlockRejection::hash()` should incorporate `reason_code`/`response_data` (at minimum `reject_reason`/`failed_txid`) into the structured-data message that is signed and verified, not just `signer_signature_hash`, so any post-signature tampering with the reason/txid is detected by `verify()`/`recover_public_key()` mismatch. Apply the same audit to `BlockAccepted`/`BlockResponseData` to ensure no other "informational" field is treated as authenticated without being covered by the signature.

### Proof of Concept
1. Signer S sends a genuine `BlockRejection` for block hash `H` with `reason_code = RejectCode::ConnectivityIssues("...")` and `signature = sig`. Note `sig` is computed only from `hash(H, chain_id)`.
2. Attacker observes this chunk on StackerDB (`get_stackerdb_signer_messages` style read, no signing key needed).
3. Attacker constructs a new `BlockRejection { signer_signature_hash: H, reason_code: RejectCode::ValidationFailed(ValidateRejectCode::ProblematicTransaction), response_data: BlockResponseData { failed_txid: Some(victim_txid), .. }, signature: sig, chain_id, .. }` — same `H`/`chain_id`, so `sig` is unchanged and still verifies (`BlockRejection::verify`/`recover_public_key` in `libsigner/src/v0/messages.rs:1816-1837`).
4. Attacker rebroadcasts this forged chunk. `StackerDBListener::handle_signer_messages` (`stacks-node/src/nakamoto_node/stackerdb_listener.rs:501-543`) verifies `recover_public_key() == signer_pubkey` — passes — and tallies `problematic_weight` for `victim_txid` as though signer S genuinely flagged it, and/or the signer-side `store_and_process_block_rejection` counts this forged `ReorgNotAllowed`/other reason toward its weight thresholds (`stacks-signer/src/v0/signer.rs:2268-2368`), all without S ever having sent that reason.

    /// Verify the rejection's signature against the provided signer public key
    pub fn verify(&self, public_key: &StacksPublicKey) -> Result<bool, String> {
        if self.signature == MessageSignature::empty() {
            return Ok(false);
        }
        let signature_hash = self.hash();
        public_key
            .verify(&signature_hash.0, &self.signature)
            .map_err(|e| e.to_string())
    }

    /// Recover the public key from the rejection signature
    pub fn recover_public_key(&self) -> Result<StacksPublicKey, &'static str> {
        if self.signature == MessageSignature::empty() {
            return Err("No signature to recover public key from");
        }
        let signature_hash = self.hash();
        StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            signature_hash.as_bytes(),
            &self.signature,
        )
    }

    /// Handle an observed rejection from another signer
    fn handle_block_rejection(
        &mut self,
        rejection: &BlockRejection,
        sortition_state: &mut Option<SortitionsView>,
    ) {
        debug!("{self}: Received a block-reject signature: {rejection:?}");

        let block_hash = &rejection.signer_signature_hash;
        let signature = &rejection.signature;

        // recover public key
        let Ok(public_key) = rejection.recover_public_key() else {
            debug!("{self}: Received block rejection with an unrecovarable signature. Will not store.";
               "signer_signature_hash" => %block_hash,
               "signature" => %signature
            );
            return;
        };

        // authenticate the signature -- it must be signed by one of the stacking set
        let signer_address = StacksAddress::p2pkh(self.mainnet, &public_key);
        if !self.is_valid_signer(&signer_address) {
            debug!("{self}: Received block rejection with an invalid signature. Will not store.";
                "signer_public_key" => ?public_key,
                "signer_address" => %signer_address,
                "signer_signature_hash" => %block_hash,
                "signature" => %signature
            );
            return;
        }

        let Some(mut block_info) = self.block_lookup_by_reward_cycle(block_hash) else {
            if let Err(e) = self.signer_db.add_pending_block_rejection_response(
                block_hash,
                &signer_address,
                (&rejection.response_data.reject_reason).into(),
            ) {
                warn!("{self}: Failed to add pending block rejection response: {e:?}");
            }
            return;
        };

        info!("{self}: Received block rejection";
            "signer_pubkey" => public_key.to_hex(),
            "signer_signature_hash" => %block_hash,
            "consensus_hash" => %block_info.block.header.consensus_hash,
            "block_height" => block_info.block.header.chain_length,
            "reject_reason" => ?rejection.response_data.reject_reason,
        );

        self.store_and_process_block_rejection(
            sortition_state,
            &mut block_info,
            &signer_address,
            (&rejection.response_data.reject_reason).into(),
        );
