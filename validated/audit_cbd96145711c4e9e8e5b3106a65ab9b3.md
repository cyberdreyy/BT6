### Title
Instant-withdraw claims are paid from a commingled strategy balance, letting a new requester steal funded-but-unclaimed instant receipts - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` pays a claimant immediately from whatever underlying the `IdleCreditVault` strategy holds, while instant receipts are only *funded* once per epoch via `collectInstantWithdrawFunds` at `startEpoch`. There is no accounting that reserves already-collected underlying for earlier, still-unclaimed instant receipts. An unprivileged KYC-passing lender can open a new instant-withdraw request during a buffer period and immediately claim it, spending funds that were collected to back another user's receipt.

### Finding Description
The instant-withdraw flow has two phases:

1. `requestInstantWithdraw` burns CDO strategy tokens and mints a receipt, increasing `instantWithdrawsRequests[_user]` and `pendingInstantWithdraws` (`contracts/strategies/idle/IdleCreditVault.sol:356-375`).
2. At `startEpoch`, `IdleCDOEpochVariant` calls `collectInstantWithdrawFunds`, which decrements `pendingInstantWithdraws` and pulls underlying from the CDO into the strategy (`IdleCreditVault.sol:398-403`, `contracts/IdleCDOEpochVariant.sol:279-282`).

The payout path, `claimInstantWithdrawRequest`, burns the user's aggregate `instantWithdrawsRequests[_user]` and calls `_transferFundedClaim`, which only guards `defaultRecoveryReserve` — it does not check that *this* user's receipt was actually funded, nor does it reserve previously collected amounts for prior claimants (`IdleCreditVault.sol:380-393`, `897-907`).

Normal withdraw receipts get per-epoch bookkeeping (`withdrawsRequestsByEpoch`, `lossRecoveryPriceByEpoch`, `lastWithdrawRequest` gating), but instant receipts have no funded-vs-unfunded tracking per user — `pendingInstantWithdraws` only tracks the aggregate *unfunded remainder* and is decremented at collection time, before users claim.

Broken invariant: "one receipt, one payout" — the strategy's underlying balance is a commingled pool, and any instant receipt can be redeemed against funds earmarked for a different receipt.

Attack trace (fixed-APR mode, buffer phase after epoch N stopped):
- Epoch N started earlier; `collectInstantWithdrawFunds` moved X underlying into the strategy to fund victim V's instant receipt. V has not claimed. Strategy balance ≥ X.
- During the buffer, APR was lowered by the manager for the next epoch, so `lastEpochApr > unscaledApr + instantWithdrawAprDelta` and `_isInstantWithdrawEnabled()` is true (`IdleCDOEpochVariant.sol:761-769`).
- Attacker A (KYC'd, holds AA or BB tranche tokens) calls `requestWithdraw(amount, tranche)`. The CDO calls `requestInstantWithdraw`, minting A a receipt and bumping `pendingInstantWithdraws`.
- In the same transaction A calls `claimInstantWithdrawRequest` via the CDO. `_burn(A, amount)` succeeds and `_transferFundedClaim` transfers X worth of V's funded underlying to A.
- When V later claims, the strategy balance is insufficient and the transfer reverts — V's funded claim is permanently frozen (the stolen amount is never re-collected: at the next `startEpoch`, `collectInstantWithdrawFunds` only funds the *current* `pendingInstantWithdraws`, which no longer includes V's already-collected receipt).

Existing guards do not stop this: `_skimDonatedAssets` only affects the CDO's raw token balance; the epoch gating in `_claimFundedWithdrawRequest` does not apply to the instant path (it has no `epochNumber`/`lastWithdrawRequest` check at all); `_transferFundedClaim`'s reserve check only covers `defaultRecoveryReserve`.

### Impact Explanation
Direct theft of underlying held by the strategy to back prior instant-withdraw receipts, and permanent freezing of the victim's funded claim. Loss equals the funded-but-unclaimed instant receipt balance, up to the strategy's full underlying balance. This is equivalent to theft of unclaimed yield/principal owed to withdraw requesters.

### Likelihood Explanation
Requires (a) a fixed-APR, non-programmable vault with instant withdraws enabled (`!disableInstantWithdraw`), (b) an APR decrease large enough to trigger the instant path in `requestWithdraw`, and (c) an unclaimed, already-funded instant receipt sitting in the strategy. Unclaimed receipts persist indefinitely (claims can be made "at any time even if a new epoch started"), so condition (c) is realistic. The attacker needs only to be a wallet-allowed tranche holder — an explicitly in-scope role — and the attack is atomic.

### Recommendation
Track the funded portion of instant receipts instead of paying from the raw strategy balance. Options:
- Keep a `fundedInstantClaims` counter incremented in `collectInstantWithdrawFunds` and decremented on claim, and have `_transferFundedClaim` reject payouts that would dip below funded-but-unclaimed obligations — i.e., extend the existing `defaultRecoveryReserve` guard to also reserve `balance - fundedInstantClaimsOutstanding`.
- Alternatively, gate `claimInstantWithdrawRequest` so a receipt can only be claimed after `collectInstantWithdrawFunds` has funded the epoch in which it was created (store the claim epoch per user, analogous to `lastWithdrawRequest` for normal receipts).

### Proof of Concept
Foundry fork test sketch (against the existing `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
function testInstantClaimStealsFundedReceipt() external {
    uint256 amount = 10_000 * ONE_SCALE;

    // Victim and attacker deposit; both KYC'd via Keyring mock
    idleCDO.depositAA(amount);          // victim
    _depositAs(attacker, amount);       // attacker AA deposit

    // Epoch 0: victim requests instant withdraw (APR lowered by manager beforehand)
    _setApr(loweredApr);
    vm.prank(victim);
    cdoEpoch.requestWithdraw(0, address(AAtranche)); // instant path -> receipt minted

    // startEpoch funds victim's instant receipt: underlying moves CDO -> strategy
    vm.prank(manager);
    cdoEpoch.startEpoch();
    assertEq(underlying.balanceOf(strategy), victimReceiptAmt);

    // borrower repays, epoch stops, buffer begins
    _repayAndStopEpoch();

    // Manager lowers APR again so instant path triggers for attacker
    _setApr(evenLowerApr);

    // Attacker requests instant withdraw and claims in the same tx
    vm.startPrank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche));
    cdoEpoch.claimInstantWithdrawRequest(attacker); // succeeds, paid from victim's funds
    vm.stopPrank();

    assertEq(underlying.balanceOf(strategy), 0);
    assertGt(underlying.balanceOf(attacker), attackerPrincipalBefore);

    // Victim's funded claim now reverts (insufficient strategy balance)
    vm.prank(victim);
    vm.expectRevert();
    cdoEpoch.claimInstantWithdrawRequest(victim);
}
```

Notes on uncertainty: I verified the claim path, funding path, and the absence of per-receipt funding tracking in `IdleCreditVault.sol` (lines 356-430, 897-917) and the `collectInstantWithdrawFunds` call site in `IdleCDOEpochVariant.sol:279-292`. I did not fully trace whether `stopEpoch`/`startEpoch` sweeps residual strategy underlying back to the CDO (which would shrink the attack window); if such a sweep exists, the residual funded balance assumption should be re-verified, but no such sweep appears in the reviewed code — collected funds stay in the strategy until claimed.
