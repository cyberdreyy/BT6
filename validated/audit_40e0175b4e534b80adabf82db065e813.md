### Title
Builder sweep withdrawal amount computed from a stale (pre-deduction) balance can double-pay Gwei to the execution layer - (File: specs/gloas/beacon-chain.md)

### Summary
`get_expected_withdrawals` builds the withdrawal list by calling `get_builder_withdrawals` (pending builder withdrawals) and `get_builders_sweep_withdrawals` (full-balance sweep) back-to-back against the *same* pre-block snapshot of `state.builders[*].balance`, while `apply_withdrawals` only decrements each builder's CL-side balance by `min(withdrawal.amount, current_balance)`. Because the sweep withdrawal's `amount` field is fixed at commit time to the builder's full (undiminished) balance, and the execution layer credits the exact `Withdrawal.amount` unconditionally, a builder that has both a pending withdrawal and becomes sweep-eligible in the same block can be paid more Gwei on the EL side than is ever debited from the CL builder balance.

### Finding Description
`get_builder_withdrawals` enqueues each entry from `state.builder_pending_withdrawals` with its full requested `amount`, with no cap against the builder's current balance: [1](#0-0) 

`get_builders_sweep_withdrawals` then computes a *second* withdrawal for the same builder using the still-uncapped, pre-application `builder.balance`, if `builder.withdrawable_epoch <= epoch`: [2](#0-1) 

Both functions are called sequentially against the same read-only `state` inside `get_expected_withdrawals`, so the sweep withdrawal's `amount` is computed *before* the pending-withdrawal deduction is applied: [3](#0-2) 

The mismatch is only "fixed up" internally by `apply_withdrawals`, which caps the *CL-side* balance deduction with `min()`, but does **not** change the `Withdrawal.amount` that was already committed into `payload_expected_withdrawals` / the payload sent to the execution layer: [4](#0-3) 

Concretely: builder balance = 100. Builder has a `builder_pending_withdrawals` entry for 30, and is also sweep-eligible (`withdrawable_epoch <= epoch`) in the same block.
- `get_builder_withdrawals` emits `Withdrawal(amount=30)`.
- `get_builders_sweep_withdrawals` emits `Withdrawal(amount=100)` (full balance, unaware the 30 will also be withdrawn).
- `apply_withdrawals` processes them in order: first `-= min(30, 100) = 30` → balance 70; then `-= min(100, 70) = 70` → balance 0.
- Total CL-side deduction = 100 (correct, matches original balance).
- But the two `Withdrawal` objects placed in `state.payload_expected_withdrawals` / the execution payload carry amounts **30 + 100 = 130**, not 100. Since the execution layer unconditionally credits `Withdrawal.amount` to `fee_recipient`/`execution_address` (there is no capping on the EL side, analogous to the missing "success" signal in `NFTXSimpleFeeDistributor._sendForReceiver` that let the same fee amount be sent twice), the recipients are collectively over-paid by 30 Gwei that was never actually present as validator/builder balance.

This is the direct analog of the reported bug class: a "returned success" value (`min()`-capped internal deduction) silently diverges from the amount actually paid out (uncapped `Withdrawal.amount` committed to the block), letting an amount be paid out more than once/more than backed by balance.

### Impact Explanation
This creates Gwei paid to a receiver that is not backed by an equivalent decrease in total supply/balances — i.e., Gwei is effectively created out of thin air and paid to the builder's `fee_recipient`/`execution_address`, breaking the fundamental supply invariant between the CL and EL. This matches the Critical impact category: "Gwei created, destroyed, or paid to a non-owner" / a payment executed that the CL-tracked balances do not actually back.

### Likelihood Explanation
The trigger condition (a builder simultaneously has a `builder_pending_withdrawals` entry and is sweep-eligible via `withdrawable_epoch <= current_epoch` in the same slot) is fully reachable by any actor who controls a builder registration: a builder can request/accrue a pending withdrawal (via the normal bid/payment settlement flow) and then trigger/allow its own exit so that `withdrawable_epoch` becomes `<= current_epoch` while the pending withdrawal entry is still queued. No malicious peer, coalition, or client bug is required — it is purely a function of ordinary protocol-following state and timing that any single builder can arrange for itself, and the resulting over-payment benefits the builder's own `fee_recipient`.

### Recommendation
`get_builders_sweep_withdrawals` (and `get_builder_withdrawals`) must compute each Withdrawal's `amount` net of any withdrawal amounts already committed for the same builder in the same batch (i.e., use a running "remaining balance" that subtracts prior-withdrawals-in-this-block for that builder, the same way `is_partially/fully_withdrawable_validator` logic must be balance-aware across the whole batch), rather than each function independently referencing the single un-mutated `state.builders[*].balance`. Equivalently, `apply_withdrawals`' `min()` cap should be reflected back into the committed `Withdrawal.amount` before it is included in `payload_expected_withdrawals`/the execution payload, so the amount credited by the EL never exceeds the amount actually deducted on the CL side.

### Proof of Concept
1. Builder `B` has `balance = 100` and `builder.withdrawable_epoch = current_epoch` (already exiting/sweep-eligible).
2. `state.builder_pending_withdrawals` contains one entry for `B` with `amount = 30` (e.g., from a prior settled builder payment via `settle_builder_payment`, see [5](#0-4) ).
3. Call `get_expected_withdrawals(state)`:
   - `get_builder_withdrawals` returns `[Withdrawal(validator_index=B, amount=30)]`.
   - `get_builders_sweep_withdrawals` computes `builder.balance == 100` (unchanged, since these are pure read functions) and returns `[Withdrawal(validator_index=B, amount=100)]`.
4. `process_withdrawals` asserts `payload.withdrawals == expected.withdrawals` (both entries, `30` and `100`), then calls `apply_withdrawals`, which deducts `30` then `min(100, 70)=70` from `state.builders[B].balance`, ending at `0` — internally consistent.
5. However, the execution payload committed to the block, and thus executed/credited by the EL, contains withdrawals totaling `130` Gwei to builder `B`'s addresses, versus only `100` Gwei actually removed from the builder's CL balance — a `30` Gwei supply inflation paid to `B`.
