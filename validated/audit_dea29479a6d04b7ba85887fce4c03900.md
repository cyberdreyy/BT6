### Title
Stale confirmations from removed multisig members count toward execution threshold, allowing requests to execute below the live-member quorum - (multisig2/src/lib.rs)

### Summary
`MultiSigContract::confirm` in `multisig2/src/lib.rs:294-315` authorizes execution purely by counting entries in the `confirmations` set for a request, without checking that every counted confirmer is still a current member of `self.members`. `delete_member` (`multisig2/src/lib.rs:356-379`) only removes pending requests where the removed member was the original submitter (`r.member == member`); it does not scrub that member's confirmation from other pending requests they had merely confirmed. This is the same class of bug as the reported `PersonalAccountRegistry` issue: a "removed" identity (owner/member) is dropped from one bookkeeping structure (`self.members` / `owners[...].added`) but a stale record of their prior authorization (`confirmations` set entry / `added=true` flag) is still trusted elsewhere, breaking the equality that should hold: **confirmations counted == confirmations from current live members**.

### Finding Description
1. Members `A`, `B`, `C` exist with `num_confirmations = 2` (`multisig2/src/lib.rs:148-152`).
2. `A` calls `add_request` to create request `R` (e.g. a `Transfer` or `FunctionCall`) — `confirmations[R] = {}` (`multisig2/src/lib.rs:170-200`).
3. `B` calls `confirm(R)` — since `confirmations.len()+1 (=1) < num_confirmations (=2)`, it just inserts: `confirmations[R] = {B}` (`multisig2/src/lib.rs:294-315`).
4. Separately, members execute a `DeleteMember { member: B }` request. `delete_member` runs: it purges only requests where `r.member == B` (i.e., requests *B originally submitted*), removes `B` from `self.members`, and (if key-based) deletes `B`'s access key (`multisig2/src/lib.rs:356-379`). Request `R` was submitted by `A`, so it is untouched — `confirmations[R]` still contains `B`.
5. `C` calls `confirm(R)`. `assert_valid_request` only checks that `C` is currently a member (`multisig2/src/lib.rs:407-423`); it does not re-validate old entries in `confirmations[R]`. The check `confirmations.len() as u32 + 1 >= self.num_confirmations` evaluates `1 (stale B) + 1 (C) = 2 >= 2`, so `R` executes (`multisig2/src/lib.rs:304-309`).

`R` executes with only one live-member approval (`C`), plus a leftover approval from an account that has since been kicked out of the multisig and had its access key revoked. This breaks the intended `K`-of-`N` custody guarantee: `confirmations counted != confirmations from live members`.

### Impact Explanation
This crosses the threshold-authorization boundary described in scope: "a multisig request executed below threshold." Depending on the request queued before the removal, this can move funds (`Transfer`), deploy arbitrary code (`DeployContract`), add a new full-access key (`AddKey`), or invoke an arbitrary `FunctionCall` on another contract on behalf of the multisig account — all with fewer genuine approvals than `num_confirmations` requires. This is a Critical-impact finding per the given rubric ("a multisig request executed below threshold").

### Likelihood Explanation
Requires no privileged access beyond being one of the current legitimate members who confirms/creates requests in the ordinary course of multisig operation, plus a member removal happening for unrelated governance reasons while another request is still pending — a realistic and common operational sequence (member rotation, key compromise cleanup) rather than a contrived edge case. No attacker-controlled deployment, redeploy, or social engineering is needed; it is triggered by the contract's own documented add/confirm/delete-member workflow.

### Recommendation
In `confirm` (and anywhere confirmations are counted, e.g. `get_confirmations`), filter/validate the `confirmations` set against `self.members` before comparing its length to `num_confirmations`, or proactively strip a departing member's id from *every* pending request's `confirmations` set in `delete_member` (not just requests they authored), mirroring how requests indexed by the removed member's key are purged.

### Proof of Concept
```rust
// members: A, B, C ; num_confirmations = 2

// A creates request R (transfer funds) - not yet confirmed

// B confirms R -> confirmations[R] = {B}; 1 < 2, not executed

c.confirm(r);

// Members execute DeleteMember{B}; delete_member only purges requests

c.confirm(del); // executes DeleteMember since >=2 confirmations reached
// B is now removed from self.members and its key deleted

// C confirms R: confirmations[R].len()=1 (stale B) + 1 (C) = 2 >= 2 -> executes

c.confirm(r); // R executes with only 1 live-member approval

        self.assert_valid_request(request_id);

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
