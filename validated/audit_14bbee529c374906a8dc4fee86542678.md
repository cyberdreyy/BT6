### Title
Vesting `distribute()` can be permanently DoS'd by any shareholder disabling direct APT transfers, blocking rewards/vested-token payouts for all shareholders - (File: `aptos-move/framework/aptos-framework/sources/vesting.move`)

### Summary
`vesting::distribute` (and its callers `terminate_vesting_contract`, `admin_withdraw`'s sibling flows) iterates over *all* shareholders in a single atomic Move transaction and calls `aptos_account::deposit_coins` for each one's share. Move has no try/catch — any abort inside the loop reverts the entire transaction, including the `withdraw_stake` that already pulled funds out of the stake pool.

### Finding Description
`distribute()` withdraws all inactive stake and then, for every shareholder, computes their share and deposits it directly to `get_beneficiary(vesting_contract, shareholder)` via `aptos_account::deposit_coins`: [1](#0-0) 

`aptos_account::deposit_coins` will abort with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` if the recipient is not registered for `AptosCoin` and has disabled arbitrary/direct coin transfers via `DirectTransferConfig`: [2](#0-1) 

Critically, the developers were clearly aware of this exact failure mode for the `set_beneficiary` path and explicitly guarded it by requiring `assert_account_is_registered_for_apt(new_beneficiary)` "so distribute() wouldn't fail and block all other accounts from receiving APT if one beneficiary is not registered": [3](#0-2) 

However, `create_vesting_contract` performs **no equivalent check** on the `shareholders` list itself — only the `withdrawal_address` is asserted to be registered: [4](#0-3) 

A shareholder is a normal, unprivileged account (no special role required — they already legitimately hold the "shareholder" role granted by the admin at contract creation). At any point *after* being added as a shareholder, that account can call `aptos_account::set_allow_direct_coin_transfers(false)` on itself (or simply never register for `AptosCoin` while direct transfers default to disallowed for accounts that have never received APT and set the flag explicitly false). When `distribute`, `distribute_many`, or `terminate_vesting_contract` is subsequently called by *anyone* (these are permissionless entry functions callable by "anyone" per the code comments), the loop reaches that shareholder's deposit, `deposit_coins` aborts, and the whole transaction — including all other shareholders' rightful payouts and the stake `withdraw` that already happened — reverts.

### Impact Explanation
This breaks the vesting/lockup invariant that unlock → reactivate → withdraw/distribute paths must not strand value or block other participants' legitimate claim rights. A single malicious (or simply misconfigured) shareholder can permanently prevent `distribute()` from ever succeeding for the entire vesting contract, since the funds remain stuck as inactive/pending-inactive stake in the pool and can never be pushed out via `distribute`/`distribute_many`/`terminate_vesting_contract` (which itself calls `distribute` internally, see `aptos-move/framework/aptos-framework/sources/vesting.move` lines 771-793) as long as the griefing shareholder keeps the block condition active. This traps commission, rewards, and vested principal for co-shareholders and the withdrawal address, matching the "operator commission, beneficiary payout, or share-accounting corruption that... traps value" and "permanent lock or non-recoverable loss of claim rights" impact classes. Because there is no per-recipient isolation (no equivalent of a safe/queued pull-payment fallback), the griefing is durable and requires admin intervention (e.g., reworking beneficiaries) that itself may be blocked because the shareholder — not the beneficiary — is the failure point and `set_beneficiary` cannot be forced on a shareholder without an existing beneficiary override, and even then the malicious shareholder can just reject the beneficiary swap effect by having previously registered a griefing beneficiary target too.

### Likelihood Explanation
Likelihood is moderate-to-high: it requires no privilege beyond being one of the (possibly many, up to `MAXIMUM_SHAREHOLDERS = 30`) shareholders of a vesting contract, and the disabling action (`set_allow_direct_coin_transfers(false)`) is a standard, publicly available account-level operation. Any shareholder unhappy with slashing, a contract dispute, or acting maliciously against co-shareholders can trigger this at will, at any time after being onboarded.

### Recommendation
Apply the same defensive check the code already uses for `withdrawal_address` and beneficiaries to every shareholder at `create_vesting_contract` time (reject shareholders not registered/able to receive direct APT transfers), and/or make `distribute()` resilient to a single failing recipient — e.g., skip (and re-queue/accumulate) a shareholder's amount instead of aborting the whole batch, mirroring how a "try/catch"-safe pull-based accounting pattern should isolate per-recipient failures.

### Proof of Concept
1. Admin creates a vesting contract with shareholders `[A, B]` via `create_vesting_contract` — no registration check is done on `A`/`B` themselves (`aptos-move/framework/aptos-framework/sources/vesting.move:536-576`).
2. Time passes; rewards/vesting accrue and become withdrawable via `vest`/`unlock_rewards`.
3. Shareholder `A` calls `aptos_account::set_allow_direct_coin_transfers(false)` on their own account (a normal, permissionless call in `aptos_account.move`), and never registers a `CoinStore<AptosCoin>`.
4. Anyone calls `distribute(contract_address)` (permissionless entry function, `vesting.move:719`). The loop reaches `A`, calls `aptos_account::deposit_coins(A, ...)`, which asserts `can_receive_direct_coin_transfers(A)` and aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` (`aptos_account.move:111-131`).
5. The entire transaction reverts — `B`'s legitimate distribution is also blocked, and the withdrawn stake amount is rolled back into the vesting contract's pending state, unable to be distributed until `A` changes their configuration.

Note: I was unable to fully verify from the indexed code whether `set_beneficiary`/`reset_beneficiary` could be leveraged by the admin to unilaterally reroute payouts away from a griefing shareholder `A` without `A`'s cooperation — if such an admin escape hatch is fully effective, it would reduce this to a temporary rather than permanent lock; confirming this precisely would require reviewing the complete `set_beneficiary`/`reset_beneficiary` implementations and any related access-control in a live session, since the indexed excerpts only show partial logic.
