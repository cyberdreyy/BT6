### Title
IDOR in `ExportDKGResult` allows any authenticated edit-role user to read another workflow's DKG result package by instanceId - ([File: core/web/vault_controller.go])

### Summary
`VaultController.ExportDKGResult` looks up a DKG result package solely by the caller-supplied `instanceId` and returns the raw hex-encoded `ReportWithResultPackage` with no check that the requester is associated with or authorized for that instance/workflow. Any authenticated user whose token/session is permitted to hit the `/v2/vault/dkg_results/export` route (edit role, not necessarily admin) can retrieve DKG key-share material belonging to a completely unrelated workflow simply by supplying its `instanceId`.

### Finding Description
`ExportDKGResult` decodes the request body into `ExportDKGResultRequest{InstanceID}`, validates only that the field is non-empty, and then calls `vault.NewVaultORM(vc.App.GetDB()).ReadResultPackage(ctx, dkgocrtypes.InstanceID(req.InstanceID))`: [1](#0-0) 

There is no comparison of `instanceId` against any per-caller/job/workflow ownership record, no ACL table lookup, and no scoping to the authenticated principal — the ORM call is a direct, unscoped lookup by ID. If found, the handler unconditionally serializes and returns `hexPackage` (the raw `ReportWithResultPackage`) and its SHA-256 digest via `presenters.NewExportDKGResultResource`. The sibling `VerifyDKGResult` handler has the identical pattern (unscoped `ReadResultPackage` by `instanceId`), reinforcing that the vault controller as a whole has no per-instance authorization model — it relies entirely on generic route-level role gating (session/API-token role) rather than resource-level authorization tying a caller to a specific `instanceId`.

Because `instanceId` values are workflow/job identifiers rather than secrets, and the route is reachable by any principal whose token/session satisfies the route's role requirement (edit role, per the question's proof idea), an edit-role user with no relationship to workflow B can guess or enumerate B's `instanceId` and receive B's key-share package.

### Impact Explanation
Successful exploitation discloses another workflow's DKG result package (key share material) to an unrelated edit-role principal — a cross-user response confusion / key-secret disclosure. This matches the Chainlink bounty "key or secret disclosure" impact class, since the `ReportWithResultPackage` contains DKG share/result data intended to be scoped to the owning workflow/job.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs a valid session or API token with edit role (not admin, not the workflow owner) that is authorized to call the `/v2/vault/dkg_results/export` endpoint, plus knowledge or a guess of a valid `instanceId` for another workflow. `instanceId` is not treated as a secret and may be predictable/sequential or discoverable from other unauthenticated/logged surfaces, making enumeration feasible. The exploit is fully repeatable — every call with a valid foreign `instanceId` returns 200 with that instance's data, since the handler has no per-request ownership check.

### Recommendation
Add resource-level authorization in `ExportDKGResult` (and `VerifyDKGResult`): resolve the calling principal to the workflow/job(s) they are entitled to access, and verify the requested `instanceId` belongs to one of those before calling `ReadResultPackage`. Alternatively, store an owner/job reference alongside each vault result package and enforce a `WHERE owner = caller` (or equivalent ACL) constraint in `vault.NewVaultORM(...).ReadResultPackage`, returning 403/404 when the instance does not belong to the caller.

### Proof of Concept
Go handler-level integration test outline:
1. Seed two DKG result packages for `instanceId = "A"` and `instanceId = "B"` via `vault.NewVaultORM(db).SaveResultPackage` (or equivalent), associating B with a distinct owning job/workflow.
2. Create an authenticated test client with an edit-role API token/session that is unrelated to job/workflow B (e.g., only associated with job A or with no job).
3. Send `POST /v2/vault/dkg_results/export` with body `{"instanceId":"B"}` using that edit-role credential.
4. Assert the response is `200 OK` and contains B's `hexPackage`/`sha` (proving cross-tenant disclosure), where the expected secure behavior would be `403 Forbidden` or `404 Not Found`.
5. Repeat with `instanceId = "A"` from a client tied only to B to confirm the issue is bidirectional and not specific to one instance.

func (vc *VaultController) ExportDKGResult(c *gin.Context) {
	var req ExportDKGResultRequest
	err := json.NewDecoder(c.Request.Body).Decode(&req)
	if err != nil {
		jsonAPIError(c, http.StatusBadRequest, errors.New("could not parse request body"))
		return
	}

	if req.InstanceID == "" {
		jsonAPIError(c, http.StatusBadRequest, errors.New("instanceId is required"))
		return
	}

	orm := vault.NewVaultORM(vc.App.GetDB())
	v, err := orm.ReadResultPackage(c.Request.Context(), dkgocrtypes.InstanceID(req.InstanceID))
	if err != nil {
		jsonAPIError(c, http.StatusNotFound, err)
		return
	}

	if v == nil {
		jsonAPIError(c, http.StatusNotFound, errors.New("DKG result not found"))
		return
	}

	hexPackage := hex.EncodeToString(v.ReportWithResultPackage)
	sha := sha256.Sum256(v.ReportWithResultPackage)
	shaStr := hex.EncodeToString(sha[:])
	jsonAPIResponse(c, presenters.NewExportDKGResultResource(hexPackage, shaStr), "exportDKGResult")
