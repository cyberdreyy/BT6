### Title
Stale confirmations from removed multisig members are still counted toward the confirmation threshold - (File: multisig2/src/lib.rs)

### Summary
`delete_member` removes a departing member from `self.members` and deletes only the requests that member *originally created*, but leaves intact any confirmations that member cast on requests created by other members. `confirm` never re-validates that the accounts/keys in a request's `confirmations` set are still current members, so a request can be executed using a mix of live and already-removed members' approvals, letting it pass with fewer than `num_confirmations` currently-authorized approvers.

### Finding Description
`confirm` (multisig2/src/lib.rs:294-315) checks membership only for the *caller* confirming right now via `assert_valid_request` → `current_member()` (multisig2/src/lib.rs:406-423, 321-339). It then reads the existing `HashSet<String>` of confirmations for the request and, once `confirmations.len() + 1 >= num_confirmations`, executes the request — without ever re-checking that every entry already stored in that `HashSet` still belongs to `self.members`.

`delete_member` (multisig2/src/lib.rs:355-379) only purges requests whose `member` field (the original submitter) equals the member being removed:
```rust
let request_ids: Vec<u32> = self
    .requests
    .iter()
    .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
    .collect();
for request_id in request_ids {
    self.confirmations.remove(&request_id);
    self.requests.remove(&request_id);
}
```
It never inspects `self.confirmations` values (the `HashSet<String>` of confirming members) for requests created by *other* members. So if member B confirmed a request created by member A, and B is later removed via `DeleteMember`, B's confirmation string remains inside that request's `confirmations` set. The binding that should hold is:

`confirmations.len() (live members only) >= num_confirmations`

but the actual invariant enforced is:

`confirmations.len() (live + stale members) >= num_confirmations`

These diverge once any confirmer is removed after confirming but before the request reaches the threshold or executes.

### Impact Explanation
This is a Critical-class issue under the given impact bands: "a multisig request executed below threshold." A transfer, `AddKey`, `DeployContract`, or `AddMember`/`DeleteMember` action can be finalized with fewer genuinely-authorized signers than `num_confirmations` requires, effectively lowering the security threshold of the multisig without any of the remaining live members noticing, since the stale confirmation is silently counted.

### Likelihood Explanation
This requires only a normal, no-fault administrative event — a scheduled key rotation or removal of a departing signer — combined with a not-yet-executed pending request that the departing signer had confirmed before being removed. No malicious action, redeploy, or external requirement (unlike the private-key compromise assumption in typical multisig bugs) is needed; it can happen purely as a side effect of routine membership management, making it more likely than a comparable scenario requiring an attacker-controlled setup step.

### Recommendation
When a member is removed in `delete_member`, also strip that member's entry from every request's `confirmations` set (not just requests they authored), or, more robustly, have `confirm` recompute the effective confirmation count by filtering the stored `confirmations` set against current `self.members` before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `{A, B, C, D, E}` and `num_confirmations = 3`.
2. Member A calls `add_request` to create request `R` (e.g. `Transfer`).
3. Member B calls `confirm(R)` → `confirmations[R] = {B}` (1 of 3, not yet executed).
4. Members confirm and execute a separate `DeleteMember { member: B }` request — B is removed from `self.members`; only requests where `r.member == B` (requests B *authored*) are purged, `R` is untouched since it was authored by A.
5. Member C calls `confirm(R)` → `confirmations[R] = {B, C}`, size 2, still below 3.
6. Member D calls `confirm(R)` → size reaches 3 → `execute_request` runs, even though B is no longer a member — the request executed with only 2 genuinely live-member confirmations (C, D) plus A's implicit authorship, despite `num_confirmations = 3` being the intended live-signer threshold.

        self.assert_valid_request(request_id);

        );

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();

            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
