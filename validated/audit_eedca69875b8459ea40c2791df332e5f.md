### Title
Stale confirmations from removed multisig members still count toward execution threshold - (File: `multisig2/src/lib.rs`)

### Summary
`confirm()` in the multisig contracts tallies `confirmations.len()` against `num_confirmations` without verifying that every public key/member already present in the `confirmations` set is still a current member. `delete_member` (multisig2) and the `DeleteKey` action (original multisig) only purge requests and confirmation-sets that the removed member *authored*; they never scrub that member's confirmation entries from other outstanding requests they merely confirmed. This mirrors the reported GaugeController class of bug ("recorded totals diverge from the live/current state that should back them") but applied to the "confirmations counted versus live members" custody binding explicitly called out as in-scope.

### Finding Description
`confirm()` computes readiness purely from the size of the stored `HashSet` of confirming identities: [1](#0-0) 

`delete_member()` only removes requests whose `signer`/`member` field equals the member being removed, and clears `num_requests_pk` for that member — it does not scan other requests' `confirmations` sets to strip entries belonging to the removed member: [2](#0-1) 

The original `multisig/src/lib.rs` has the analogous gap in the `DeleteKey` action handler, which removes requests authored by the deleted key but not that key's confirmations on other requests: [3](#0-2) 

`assert_valid_request()`, called at the top of `confirm()`, only checks that the *caller* is currently a member and that the request/confirmation records exist — it performs no validation of the historical confirmers already recorded in the set: [4](#0-3) 

Consequently the invariant the system is supposed to enforce — "N-of-M confirmations from *currently authorized* members" — silently degrades to "N confirmations, some of which may be from members who no longer hold any authority," exactly analogous to the GaugeController bug where a total is computed from a value that no longer reflects the live/current state.

### Impact Explanation
This lets a request execute (fund transfer, key/member addition or deletion, function call with attached deposit, etc.) with fewer than `num_confirmations` *live* approvals — i.e., a multisig request executed below the effective threshold of current signers. That maps directly to the Critical impact bucket: "a multisig request executed below threshold," which can move NEAR/wNEAR or grant access without the intended quorum of currently-trusted members.

### Likelihood Explanation
Exploitation requires no special privilege beyond the normal multisig workflow: a member confirms one or more pending requests, is later legitimately removed (e.g., offboarded via `DeleteMember`/`DeleteKey`), and any request they confirmed before removal remains in `requests`/`confirmations` with their stale confirmation intact. Any remaining member(s) can then add confirmations to reach `num_confirmations` even though the removed member no longer counts as a valid signer, and `confirm()` performs no re-validation of previously stored confirmers. This does not require compromising a key, redeploying, or social engineering — only ordinary member turnover combined with an outstanding request, which is a realistic operational sequence for any multisig with membership churn.

### Recommendation
When removing a member (via `delete_member` / `DeleteKey`), iterate all `confirmations` entries (not just requests authored by that member) and remove the departing member's entry from every set; alternatively, when tallying in `confirm()`, filter the confirmations set to intersect with `self.members` (or the current key set) before comparing its length to `num_confirmations`, so removed members' historical confirmations never count toward execution.

### Proof of Concept
1. Initialize `MultiSigContract::new(members: [A, B, C], num_confirmations: 2)`.
2. `A` calls `add_request` to create request `R` (e.g., a `Transfer`).
3. `C` calls `confirm(R)` → `confirmations[R] = {C}` (1 confirmation, below threshold of 2), see `confirm()` at [5](#0-4) .
4. The multisig (via a separate fully-confirmed request) executes `DeleteMember { member: C }`; `delete_member` runs — since `R` was authored by `A`, not `C`, it is not touched, and `confirmations[R]` still contains `C`, see [6](#0-5) .
5. Now only `A` and `B` are members. `B` calls `confirm(R)`. `confirmations[R].len() == 2 >= num_confirmations (2)`, so `execute_request` runs — even though `C` (one of the two counted confirmers) is no longer a member, and the currently-live confirming set is really only `{B}` (1 out of 2 required).
6. Result: request `R` executes with only one legitimate/live confirmation, violating the 2-of-N threshold guarantee.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
