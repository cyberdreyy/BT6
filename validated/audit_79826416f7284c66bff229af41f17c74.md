### Title
User enumeration via distinguishable error/timing in `CreateSession` for unknown vs. known emails - ([File: core/sessions/localauth/orm.go])

### Summary
`CreateSession` calls `o.FindUser` first and immediately returns the raw database error (e.g. `sql: no rows in result set`) for a non-existent email, before ever reaching `constantTimeEmailCompare`. For a valid email it always proceeds to `utils.CheckPasswordHash` (bcrypt), returning `"Invalid password"` or an MFA challenge JSON. This produces a distinguishable error message and a computationally-driven timing gap (bcrypt cost) between "unknown email" and "known email, wrong password/MFA" responses, allowing unauthenticated email enumeration despite the comment's claim that the ordering prevents leakage.

### Finding Description
`sessions_controller.go`'s `Create` handler is unauthenticated (`POST /sessions`) and passes the raw `sr.Email`/`sr.Password` straight to `AuthenticationProvider().CreateSession` [1](#0-0) .

In `orm.go`, `CreateSession` first calls `o.FindUser(ctx, sr.Email)`, and if the SQL lookup returns no rows, the function returns immediately with the raw error, `"", err` [2](#0-1) . This happens before `constantTimeEmailCompare` and before `utils.CheckPasswordHash` (bcrypt, which is deliberately slow) are ever invoked. Only when `FindUser` succeeds (i.e., the email exists) does execution reach `constantTimeEmailCompare` and then `utils.CheckPasswordHash` [3](#0-2) .

Because the SQL query is `WHERE lower(email) = lower($1)` [4](#0-3) , a successful `FindUser` guarantees `user.Email` already matches `sr.Email`; the subsequent `constantTimeEmailCompare` can essentially never fail in practice, making the "prevents MFA leaking" comment's premise irrelevant to the actual oracle. The real distinguishing factors are:
1. **Message oracle**: unknown email → raw DB "no rows" error text; known email/wrong password → literal `"Invalid password"`; known email/correct password with MFA → serialized WebAuthn challenge JSON `{...}` [5](#0-4) . These three response bodies are trivially distinguishable by an unauthenticated caller, all surfaced via `jsonAPIError(c, http.StatusUnauthorized, err)` [6](#0-5) .
2. **Timing oracle**: unknown emails short-circuit at a single indexed SQL lookup, while known emails always execute `bcrypt.CompareHashAndPassword` [7](#0-6) , which is deliberately expensive (bcrypt default cost) — creating a measurable, repeatable latency gap correlated with email existence, independent of the constant-time comparison used only for the email string itself.

The MFA branch is reached only *after* a correct password is supplied, so MFA-status disclosure via the WebAuthn JSON requires already knowing valid credentials — that part of the ordering does work as intended. However, the account-existence leak (message + timing) occurs before any password validation and is not mitigated at all.

### Impact Explanation
This enables unauthenticated user enumeration: an attacker can query `/sessions` with arbitrary emails and, using both response-body differences and bcrypt-induced timing differences, build a list of valid Chainlink node user emails. This maps to Chainlink's "sensitive information disclosure" / reconnaissance-enabling bounty class — it does not by itself grant access, but materially aids targeted credential stuffing or brute-force password guessing against confirmed-valid accounts, and confirms which discovered accounts are further protected by MFA (post-credential-guess) versus not.

### Likelihood Explanation
No preconditions are required — the endpoint is fully unauthenticated and public (`POST /sessions`). The only "skill" required is a simple table-driven script comparing response bodies (trivial) or repeated timing measurements (bcrypt cost makes this gap large and stable, not a subtle nanosecond timing attack), making this highly feasible and fully repeatable.

### Recommendation
- Make the non-existent-email path perform an equivalent-cost dummy bcrypt comparison (against a precomputed dummy hash) before returning, so timing is equalized regardless of whether the email exists.
- Normalize all pre-authentication failure responses (`unknown email`, `wrong password`, and the pre-password-verification portion of the MFA flow) to a single generic message (e.g., `"Invalid email or password"`) and identical HTTP status, removing the raw SQL error from ever reaching the client in `sessions_controller.go`'s `Create` handler.
- Ensure `FindUser` errors are wrapped/normalized before being returned by `CreateSession`, rather than passed through directly.

### Proof of Concept

```go
func TestCreateSession_EnumerationOracle(t *testing.T) {
    // setup: create one valid user "valid@example.com" / correct password, no MFA
    // and one valid user "mfauser@example.com" with a WebAuthn credential registered.

    cases := []struct{
        name string
        email string
        password string
    }{
        {"unknown email", "nosuchuser@example.com", "wrongpass"},
        {"valid email wrong password", "valid@example.com", "wrongpass"},
        {"valid email correct password with MFA", "mfauser@example.com", "correctpass"},
    }

    for _, tc := range cases {
        start := time.Now()
        _, err := orm.CreateSession(ctx, sessions.SessionRequest{Email: tc.email, Password: tc.password})
        elapsed := time.Since(start)
        t.Logf("%s: err=%v elapsed=%v", tc.name, err, elapsed)
    }

    // Assertions:
    // 1. err.Error() for "unknown email" case is NOT "Invalid password" and is distinguishable
    //    (e.g. contains "no rows" or differs textually from "Invalid password").
    // 2. err.Error() for "valid email wrong password" == "Invalid password".
    // 3. err.Error() for MFA case is valid JSON (WebAuthn challenge), distinct from both above.
    // 4. elapsed for "unknown email" case is measurably (statistically, over N=100 runs) shorter
    //    than "valid email wrong password" due to skipped bcrypt.CompareHashAndPassword call.
}
```
Expected result: all three assertions pass today, confirming distinguishable messages and a timing gap, demonstrating the enumeration oracle described in the finding.

func CheckPasswordHash(password, hash string) bool {
	err := bcrypt.CompareHashAndPassword([]byte(hash), []byte(password))
	return err == nil
