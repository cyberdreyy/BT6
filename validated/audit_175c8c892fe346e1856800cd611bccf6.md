A block that reached the 70% signing threshold in a signer's local view (`mark_locally_accepted`, `signed_group` set) but has not yet been pushed to / accepted by the node will make `first_block_mined == None` for that tenure. ### Title
Single-miner-triggered reorg permit lets a signer sign two conflicting quorum-approved blocks - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`check_parent_tenure_choice` treats a reorged tenure as harmless and immediately marks it `superseded` whenever the **node** reports `first_block_mined == None` for that tenure, skipping the `first_proposal_burn_block_timing` check entirely. `first_block_mined` is derived solely from the stacks node's chainstate (`get_nakamoto_tenure_start_block_header`), which lags behind the signer set's own quorum state. A single miner racing a tenure-change proposal for the next sortition ahead of the previous quorum-signed block reaching the node can cause the signer to sanction a reorg over a tenure whose block already crossed the 70% signature threshold, permanently voiding the conflict-guard for that tenure via `mark_tenure_superseded`, and get the signer to sign a second, conflicting block at the same height.

### Finding Description
In `check_parent_tenure_choice` (`stacks-signer/src/chainstate/mod.rs`): [1](#0-0) 
the code first checks `signer_db.get_globally_accepted_block_count_in_tenure` — a **local** signer-DB count that only increments once the block is confirmed by a `NewBlock` node event (`mark_globally_accepted`). A block that has only reached `signed_group`/`LocallyAccepted` status (70% signature threshold observed by this signer, but not yet handed to/ingested by the node) does not count here, so this guard passes even though the tenure already has a fully-quorate signature.

The code then asks the **node** (not the signer set) for `first_block_mined` via `client.get_tenure_forking_info`, which is served by `TenureForkingInfo::from_snapshot`: [2](#0-1) 
This is populated exclusively from `NakamotoChainState::get_nakamoto_tenure_start_block_header`, i.e. blocks the node has actually processed — entirely independent of the signer quorum state.

If the node has not yet received/processed the quorum-signed block (a plausible timing gap between `broadcast_signed_block` reaching the miner/node and the next Bitcoin block/sortition), `first_block_mined` is `None`, and the reorg is unconditionally permitted: [3](#0-2) 
The `first_proposal_burn_block_timing` window check is only used in the *else* branch (when `first_block_mined` is `Some`); it is entirely bypassed here. The tenure is then recorded as `superseded`: [4](#0-3) 

This record makes `reorg_permit_stands` return `true` for as long as the permitting sortition stays canonical, which **excludes the conflict outright** ahead of any freshness/staleness check in `handle_block_pre_commit`: [5](#0-4) [6](#0-5) 

Consequence: the signer had already put its signature over block T1 (quorum-signed, `signed_group` set, `LocallyAccepted`), and it now also signs a conflicting sibling T2 at the same height in a different tenure, because the equivocation guard (`get_signed_conflicts` + `reorg_permit_stands` + `conflict_still_blocks`) is told this conflict is excluded. If T1's block subsequently does reach the node (the delay that caused `first_block_mined == None` was transient, not a permanent orphaning), the chain now has two competing, fully-signed blocks at the same height — a signer having signed a conflicting block, which is the exact equality (`one-per-height` / `approved-parent vs canonical`) the guard exists to protect.

### Impact Explanation
This is a Critical-class break per the rules: a signer signs a conflicting block. Two siblings can both accumulate the 70% signature threshold at the same Stacks height, producing a genuine fork with two "valid" (fully co-signed) blocks, which the guard in section 5 of `docs/signer-flows.md` and `get_signed_conflicts`/`conflict_still_blocks` was specifically designed to prevent (a fresh, undead conflict should always block re-signing). Voiding it based on a lag between signer-quorum state and node ingestion breaks the very invariant these functions exist for.

### Likelihood Explanation
The trigger requires only the sortition-winning miner (a single slot) to build a tenure-change block off an *older* sortition instead of the immediately prior one, right after (or racing) a quorum-signed-but-not-yet-broadcast/ingested block in that prior tenure. This is a timing/race condition rather than needing a majority of signers or any other signer's key; it only needs ordinary node/network propagation delay plus a miner deciding to fork. The `globally_accepted_blocks <= 1` and `first_block_mined == None` gates are both satisfiable in normal operation whenever the node hasn't yet absorbed a just-signed block, which is a routine occurrence, not a contrived edge case.

### Recommendation
`check_parent_tenure_choice` should not treat `first_block_mined == None` as proof the reorg is costless. It should additionally cross-check the signer's own `signerdb` for a `LocallyAccepted`/`signed_group` block in that tenure (not just `GloballyAccepted`) before waiving the `first_proposal_burn_block_timing` check, or otherwise fold the "is there a quorum-signed but not yet node-visible block" case into the same rejection path used for globally-accepted blocks (i.e., treat any block with a nonzero `signed_group` weight ≥ threshold identically to a globally-accepted one for the purposes of this reorg-permission decision).

### Proof of Concept
1. Signer set reaches 70% pre-commit weight over block T1 (tenure A, height H); each signer marks it `LocallyAccepted`/`signed_group` in `signerdb`, but the block has not yet been pushed to / processed by the stacks node (`broadcast_signed_block` in flight, or node briefly behind).
2. Before the node ingests T1, the current miner (or the next sortition winner) proposes a tenure-change block T2 (tenure B, height H) whose `prev_tenure_consensus_hash` points at the sortition *before* tenure A, i.e. it "skips" tenure A.
3. Each signer runs `check_parent_tenure_choice`: `get_globally_accepted_block_count_in_tenure(A)` returns 0 (node hasn't confirmed T1 yet), and `client.get_tenure_forking_info` reports `first_block_mined = None` for tenure A (node has no record of T1). The reorg is permitted unconditionally, and tenure A is marked `superseded`, per [3](#0-2) .
4. Each signer proceeds to pre-commit/sign T2; `reorg_permit_stands` reports the permit as standing (tenure B's sortition is canonical), so the existing signature over T1 is excluded from `get_signed_conflicts` filtering, per [7](#0-6) , and T2 is signed.
5. T1 then reaches the node and is broadcast/accepted (the delay was transient, not a true orphaning): the network now has two independently 70%-signed blocks (T1, T2) at height H in different tenures — the equivocation guard failed to prevent the double sign.
