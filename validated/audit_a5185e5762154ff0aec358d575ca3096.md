### Title
Unchecked ERC20 `transfer` permanently consumes Merkle claims - ([File: contracts/MerkleClaim.sol](contracts/MerkleClaim.sol))

### Summary
`MerkleClaim.claim` marks an address as having claimed before calling `IERC20Upgradeable(token).transfer` and never checks the transfer’s boolean return value. For ERC20 tokens that return `false` rather than reverting, a failed payout still sets `hasClaimed[to]`, permanently preventing the recipient from retrying their valid Merkle claim. [1](#0-0) 

### Finding Description
The claim flow is:

1. Reject if `hasClaimed[to]` is already set.
2. Verify the Merkle proof for `(to, amount)`.
3. Set `hasClaimed[to] = true`.
4. Call `IERC20Upgradeable(token).transfer(to, amount)` without checking the result. [1](#0-0) 

Some ERC20 implementations signal transfer failure by returning `false` instead of reverting. If the distribution token follows that behavior and the transfer fails—for example because the claim contract has not yet received the full distribution balance—the call returns normally and `hasClaimed[to]` remains set. Any later call for the same recipient reverts with `AlreadyClaimed`. [2](#0-1) 

The same unchecked pattern exists in `sweep`, although that function is restricted to `TL_MULTISIG` and does not update claim state. [3](#0-2) 

### Impact Explanation
A legitimate recipient can permanently lose their full Merkle allocation. An unprivileged caller can execute `claim` for a known recipient while the contract has an insufficient token balance; the token returns `false`, the transaction succeeds, and the recipient’s claim can never be executed again. The unpaid tokens remain in the claim contract and can later be swept by the multisig after 60 days. [3](#0-2) 

This breaks the “one valid receipt, one payout” invariant: the receipt is consumed without a corresponding payout.

### Likelihood Explanation
Exploitation requires the configured distribution token to return `false` on failure and the claim contract to be unable to complete the payout at the time `claim` is called. The deployment and funding steps are separate—`initialize` only records the token and Merkle root, while the comment states that tokens “must be sent to this contract.” [4](#0-3) 

Because `claim` is permissionless and can be invoked for another recipient, a caller can deliberately front-run full funding or trigger the claim during a temporary shortfall. The required code condition is directly present; the operational condition depends on distribution funding and token behavior.

### Recommendation
Use `SafeERC20Upgradeable.safeTransfer` for the claim transfer, or explicitly require that `transfer` returns `true`. The safer ordering is to verify the proof, attempt the token transfer with a checked transfer, and only retain `hasClaimed[to] = true` if the payout succeeds.

Also use `safeTransfer` in `sweep` for consistency. [5](#0-4) 

### Proof of Concept
The following Foundry test demonstrates the issue using a token that returns `false` when the sender balance is insufficient:

```solidity
// test/foundry/MerkleClaimUncheckedTransfer.t.sol
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import "../../contracts/MerkleClaim.sol";

contract FalseOnFailureToken {
    mapping(address => uint256) public balanceOf;

    function mint(address to, uint256 amount) external {
        balanceOf[to] += amount;
    }

    function transfer(address to, uint256 amount) external returns (bool) {
        if (balanceOf[msg.sender] < amount) {
            return false;
        }

        balanceOf[msg.sender] -= amount;
        balanceOf[to] += amount;
        return true;
    }
}

contract MerkleClaimUncheckedTransferTest is Test {
    MerkleClaim internal claim;
    FalseOnFailureToken internal token;

    address internal victim = address(0xBEEF);
    uint256 internal claimAmount = 100 ether;

    function setUp() external {
        claim = new MerkleClaim();
        token = new FalseOnFailureToken();

        bytes32 leaf = keccak256(
            bytes.concat(keccak256(abi.encode(victim, claimAmount)))
        );

        claim.initialize(leaf, address(token));

        // The distributor is only partially funded when claim is invoked.
        token.mint(address(claim), claimAmount - 1);
    }

    function testFailedTransferConsumesClaim() external {
        bytes32[] memory proof = new bytes32[](0);

        // Does not revert even though the token payout returns false.
        claim.claim(victim, claimAmount, proof);

        assertTrue(claim.hasClaimed(victim));
        assertEq(token.balanceOf(victim), 0);

        // Full funding arrives later, but the valid claim cannot be retried.
        token.mint(address(claim), 1);

        vm.expectRevert(MerkleClaim.AlreadyClaimed.selector);
        claim.claim(victim, claimAmount, proof);
    }
}
```

  function claim(address to, uint256 amount, bytes32[] calldata proof) external {
    // Throw if address has already claimed tokens
    if (hasClaimed[to]) revert AlreadyClaimed();

    // Verify merkle proof, or revert if not in tree,
    // double keccak is preferred https://github.com/OpenZeppelin/merkle-tree#user-content-fn-1-786ed85226485d53b8a7834b144c1642
    bytes32 leaf = keccak256(bytes.concat(keccak256(abi.encode(to, amount))));
    bool isValidLeaf = MerkleProofUpgradeable.verify(proof, merkleRoot, leaf);
    if (!isValidLeaf) revert NotInMerkle();

    // Set address to claimed
    hasClaimed[to] = true;

    // Transfer tokens to claimee
    IERC20Upgradeable(token).transfer(to, amount);
  }

  function sweep(address to) public {
    require(msg.sender == TL_MULTISIG);
    // allow sweep after 60 days
    require(block.timestamp > deployTime + 60 days);
    address _token = token;
    IERC20Upgradeable(_token).transfer(to, IERC20Upgradeable(_token).balanceOf(address(this)));
  }
