### Title
Inflated `deposit_amount` lets `transfer()` release NEAR meant to cover `get_locked_amount()`, because `get_liquid_owners_balance()`'s clamp uses raw `account_balance` instead of `account_balance - locked_amount` - ([File: lockup/src/getters.rs])

### Summary
`get_owners_balance()` computes `account_balance + known_deposited_balance - locked_amount`, and `get_liquid_owners_balance()` clamps this with `min(get_owners_balance(), get_account_balance())` [1](#0-0) . If `known_deposited_balance` (i.e., `staking_information.deposit_amount`, set from a manipulated `on_get_account_total_balance` callback of a malicious "selected" pool) is inflated far above `locked_amount`, `get_owners_balance()` becomes larger than `get_account_balance()`, so the `min()` degenerates to just `get_account_balance()` — with no subtraction of `locked_amount` at all. This lets `transfer()` move up to the entire real NEAR balance sitting in the lockup account (minus `MIN_BALANCE_FOR_STORAGE`), even when that real balance is composed of locked/unvested tokens that were never staked out.

### Finding Description
The binding that should hold is: `transferable_amount <= real_account_balance - locked_amount_actually_backed_by_this_balance`. Concretely, when no tokens are actually deposited at any pool, the only NEAR backing `locked_amount` is `env::account_balance()` itself, so the intended invariant is `get_owners_balance() == account_balance - locked_amount` (clamped at 0), and `get_liquid_owners_balance()` should never exceed `account_balance - locked_amount`.

Trace:
1. Owner selects a malicious "staking pool" (`select_staking_pool`) which passes the whitelist check in the prior scenario, and calls `refresh_staking_pool_balance()` [2](#0-1) . The malicious pool's `on_get_account_total_balance` callback response sets `staking_information.deposit_amount` to an inflated value (this is the "prior scenario" the question references), directly inflating `get_known_deposited_balance()` [3](#0-2) .
2. Owner (acting in good faith) calls `transfer(amount, receiver_id)`. Checks passed: `assert_owner`, `assert_transfers_enabled`, `assert_no_staking_or_idle` (status is `Idle`), `assert_no_termination`, and `get_liquid_owners_balance().0 >= amount.0` [4](#0-3) .
3. `get_owners_balance()` = `account_balance + known_deposited_balance - locked_amount` (saturating) [5](#0-4) . Because `known_deposited_balance` is attacker-inflated, this value can exceed `get_account_balance()` = `account_balance - MIN_BALANCE_FOR_STORAGE` [6](#0-5)  by an arbitrarily large margin, even though `locked_amount` was never actually subtracted from the *real* liquid balance.
4. `get_liquid_owners_balance()` = `min(get_owners_balance(), get_account_balance())` [7](#0-6) . Once `get_owners_balance()` exceeds `get_account_balance()`, the `min()` simply returns `get_account_balance()` — i.e., the *entire* real liquid NEAR in the contract, regardless of `locked_amount`. The subtraction of `locked_amount` that happened inside `get_owners_balance()` is rendered moot because the other operand of `min()` never itself subtracts `locked_amount`.
5. `Promise::new(receiver_id).transfer(amount.0)` then moves up to `get_account_balance()` worth of real NEAR out of the lockup account — NEAR that, absent the deposit-inflation, would have been correctly withheld as locked/unvested (since without inflation, `get_owners_balance() = account_balance - locked_amount`, which would be small/zero if `account_balance ≈ locked_amount`).

None of the existing guards catch this: `assert_transfers_enabled`, `assert_no_staking_or_idle`, and `assert_no_termination` are orthogonal to the balance-math flaw, and the only balance check (`get_liquid_owners_balance() >= amount`) is exactly the vulnerable function.

### Impact Explanation
This allows locked/unvested NEAR (tokens still subject to lockup or vesting schedule) to leave the lockup account early through the legitimate `transfer` code path, matching the Critical category "locked or unvested tokens released early." The owner authorizes the transfer, but the amount released is dictated by a false accounting state (`deposit_amount`) introduced by the attacker-controlled fake pool, not by the actual vesting/lockup math. This is repeatable for any lockup account whose owner is induced to select the attacker's pool and call `refresh_staking_pool_balance`/`transfer` — a single manipulated callback response can permanently corrupt `deposit_amount` and enable up to a full drain of the account's real liquid balance (minus storage) on every subsequent `transfer` call, until `unselect_staking_pool` (which requires `deposit_amount == 0`, blocking cleanup but not blocking prior transfers already executed).

### Likelihood Explanation
Preconditions: (1) the attacker's account must first pass as the "selected staking pool" (assumed achieved in the "prior scenario" per the question) and be able to return a manipulated `get_account_total_balance` response; (2) `are_transfers_enabled() == true`; (3) status must be `Idle`, which it is right after the callback completes and before staking any funds; (4) the owner must call `refresh_staking_pool_balance()` and later `transfer()`, both legitimate owner actions taken in good faith on inflated `deposit_amount`. No special privileges beyond being named as the pool are required by the attacker; the exploit is inexpensive (no deposit needed by the attacker beyond deploying the malicious pool contract and controlling its response). This depends on the owner actually calling `transfer` with the owner's own signing key, which is a normal, expected operation, making it highly feasible whenever the prior "fake selected pool with inflated deposit_amount" precondition holds.

### Recommendation
Fix `get_liquid_owners_balance()` so the clamp is against the balance net of `locked_amount`, not raw `account_balance`, e.g.: `min(get_owners_balance(), get_account_balance().saturating_sub(self.get_locked_amount().0))`, or equivalently ensure `get_owners_balance()` itself is bounded by real liquid balance before combining with `known_deposited_balance` (e.g., separately track "real local liquid balance" vs "balance owed by pool" and only let the pool-owed portion be released once actually withdrawn to the account, never through the local liquid cap). More fundamentally, `deposit_amount` should never be trusted unbounded from a pool response without sanity bounds, but the getters-level fix above directly restores the invariant `transferable_amount <= account_balance - locked_amount`.

### Proof of Concept
```rust
// lockup/src/tests.rs (conceptual, cargo test)
#[test]
fn test_inflated_deposit_bypasses_locked_amount_via_liquid_balance() {
    // Setup: lockup_amount == 1000 NEAR, all still fully locked (locked_amount == 1000 NEAR)
    // account_balance in the contract == 1000 NEAR (never staked, sitting locally) + storage cushion
    let mut context = ...; // testing_env! with account_balance = 1000_NEAR + MIN_BALANCE_FOR_STORAGE
    testing_env!(context.clone());

    let mut contract = LockupContract::new(..., lockup_amount = 1000_NEAR, ...);

    // Baseline (no manipulation): deposit_amount == 0
    assert_eq!(contract.get_owners_balance().0, 0); // account_balance - locked_amount == 0
    assert_eq!(contract.get_liquid_owners_balance().0, 0);

    // Attacker-controlled pool inflates deposit_amount via refresh_staking_pool_balance callback
    contract.staking_information = Some(StakingInformation {
        staking_pool_account_id: "malicious.pool".to_string(),
        status: TransactionStatus::Idle,
        deposit_amount: U128(10_000_NEAR), // fake, far exceeds any real deposit
    });

    // Binding under test: get_liquid_owners_balance() should stay <= account_balance - locked_amount
    let real_liquid_bound = context.account_balance.saturating_sub(1000_NEAR); // should be ~0
    let reported_liquid = contract.get_liquid_owners_balance().0;

    // Vulnerability: reported_liquid == account_balance - MIN_BALANCE_FOR_STORAGE (~1000 NEAR),
    // NOT ~0, proving locked_amount subtraction was bypassed.
    assert!(reported_liquid > real_liquid_bound); // demonstrates the divergence

    // Owner (good faith) can now transfer the locked funds out:
    testing_env!(context.clone(), predecessor_account_id = owner_account_id());
    contract.transfer(WrappedBalance(reported_liquid), "attacker_receiver".to_string());
    // transfer succeeds despite locked_amount == 1000 NEAR still outstanding
}
```
This test sets `account_balance` equal to the fully locked `lockup_amount` (simulating no funds ever actually staked), injects an inflated `deposit_amount`, and shows `get_liquid_owners_balance()` returns the full account balance instead of `~0`, then shows `transfer()` succeeds in moving those locked funds out.
