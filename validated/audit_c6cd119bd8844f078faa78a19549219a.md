### Title
Symlink-through-directory escape bypasses `Extract`'s root check across sequential extractions into the same directory - (File: commands/helpers/archive/tarzstd/tarzstd_extractor.go)

### Summary
`Extract` validates each tar entry's target path with a pure string prefix check (`strings.HasPrefix(path, e.dir+separator)`), but never verifies that intermediate path components are not symlinks. Symlink entries are deliberately deferred to the end of a single `Extract()` call (a correct mitigation against same-archive symlink-then-write attacks), but that protection does not extend across the multiple separate `Extract()` invocations that a real job performs into the same working directory (one per cache config / one per artifact dependency), nor does it protect against a symlink that already exists on disk from an earlier step such as `git checkout`.

### Finding Description
In `commands/helpers/archive/tarzstd/tarzstd_extractor.go` `Extract`, the per-entry path check is: [1](#0-0) 
This only validates the literal joined/cleaned string, never `os.Lstat`-ing intermediate path segments. Symlink entries are intentionally deferred and only materialized in a second pass after all regular files/directories from the *same* archive have been written: [2](#0-1) [3](#0-2) 
That ordering blocks a "plant symlink, then write through it" attack **within one archive**, but a symlink created by this pass persists on disk after `Extract()` returns. Both `cache-extractor` and `artifacts-downloader` construct a fresh extractor with `dir = os.Getwd()` (the job's working directory) and call `Extract` **once per cache config / once per artifact dependency**: [4](#0-3) [5](#0-4) 
Multiple caches (`b.addExtractCacheCommand` is invoked once per cache entry/fallback key) and multiple `dependencies` artifacts (`ArtifactDownload.Run` is invoked once per dependency ID via `e.RunnerCommand`) extract sequentially into that same `wd`: [6](#0-5) [7](#0-6) 

An attacker who controls two attacker-produced archives extracted sequentially into the same `wd` (e.g., two dependency job artifacts, or a poisoned cache followed by an artifact) can:
1. First archive: a symlink entry `escape -> /outside/target` (or any relative `..`-escaping target). It is deferred and created on disk at the end of `Extract()` call #1 since nothing blocks it.
2. Second archive: a regular file entry `escape/pwned.txt`. In `Extract()` call #2, `path := filepath.Join(e.dir, "escape/pwned.txt")` string-passes the `HasPrefix` check (it's still textually under `e.dir`), then `os.MkdirAll(filepath.Dir(path), 0777)` and `os.Create(path)` transparently follow the OS-level symlink `escape` and write outside `e.dir`.

The same effect is achievable with only a single attacker-controlled archive if a symlink with a matching name already exists on disk before extraction runs (e.g., a symlink tracked and checked out by `git checkout`, which precedes cache/artifact restoration in the job).

### Impact Explanation
The escape lets extracted content land outside the intended checkout/cache/artifact root, overwriting arbitrary files reachable via the symlink target and thereby tampering with build state beyond the assigned root. However, the write happens with the same OS-level/container permissions the job process (or helper process, running in the same filesystem namespace as the job in shell/Docker/Kubernetes executors) already has — a job that can run `artifacts-downloader`/`cache-extractor` can typically already write anywhere it wants via its own shell commands within its own sandbox. The scoped "protected-ref escalation" impact described in the question would require this to cross an *actual* trust boundary (e.g., a shared host directory used by concurrent jobs, or a cache key that is shared unprotected-to-protected across branches by GitLab's own cache-key semantics) — both of which are either excluded by the rules (shared-host/shell-executor trust model) or are a property of GitLab's cache-key scoping rather than a Runner code defect. Within a single job/pipeline the attacker already controls, this bug does not grant a new privilege.

### Likelihood Explanation
Constructing the crafted archives is trivial for an unprivileged pipeline author (control over job artifacts/cache content and multiple dependencies/cache entries is fully available). The mechanics of the bypass (multi-invocation symlink pre-creation) are straightforward to reproduce. The remaining uncertainty is whether any deployment configuration actually gives this escape a privilege boundary to cross (e.g., a shared `builds_dir` across concurrent/protected jobs) — this was not confirmed in the codebase and, per the rules, cannot be assumed since it relies on a documented/trusted host-sharing model.

### Recommendation
Harden `Extract` (and the equivalent zip/fastzip extractors) to:
- Resolve/validate each intermediate path component with `os.Lstat` and reject or refuse to traverse through any existing symlink whose target is outside `e.dir`, rather than relying solely on string-prefix comparison of the joined name.
- Validate `hdr.Linkname` itself (for symlink entries) against escaping `e.dir` before creating the link, not just the link's own literal name.
- Treat directory creation (`MkdirAll`) defensively: if any path component already exists and is not a plain directory, fail extraction instead of silently following it.
- Consider using a "secure join" (open-relative / `O_NOFOLLOW` based path resolution, e.g. similar to `containers/storage/pkg/chrootarchive` or `cyphar/filepath-securejoin`) so that OS-level path resolution cannot be tricked by pre-existing or attacker-planted symlinks, including ones left over from a previous `Extract()` invocation into the same directory.

### Proof of Concept
Go unit test plan for `tarzstd` package:
1. Create a temp directory `root`.
2. Build archive A containing one symlink entry `link` -> `..` (escaping root's parent) or an absolute path outside `root`. Call `NewExtractor` + `Extract` with `dir = root`; assert it succeeds and `root/link` is now a symlink pointing outside `root`.
3. Build archive B containing a regular file entry `link/pwned.txt` with attacker content. Call `NewExtractor` + `Extract` again with the same `dir = root`.
4. Assert that either extraction fails with an explicit path-escape error, or (showing the bug) that `pwned.txt` is created outside `root` (e.g., at `filepath.Dir(root)/pwned.txt`) — proving the invariant "restored content must stay inside the assigned extraction root" is violated across sequential `Extract()` calls sharing a directory.

func (s ArtifactDownload) Run(ctx context.Context, e *env.Env) error {
	if s.Filename == "" {
		e.Debugf("Skipping artifact download for %s (%d): no filename", s.ArtifactName, s.ID)
		return nil
	}

	args := []string{
		"artifacts-downloader",
		"--url", e.BaseURL,
		"--token", s.Token,
		"--id", strconv.FormatInt(s.ID, 10),
	}

	attempts := max(s.DownloadAttempts, 1)

	backoff := retry.NewBackoff()
	var err error
	for i := 1; i <= attempts; i++ {
		if i > 1 {
			if s.UseExponentialBackoffStageRetry {
				retry.SleepWithNotice(e, backoff.Duration())
			}
			e.Warningf("Retrying artifact download for %s (attempt %d/%d)...", s.ArtifactName, i, attempts)
		} else {
			e.Noticef("Downloading artifacts for %s (%d)...", s.ArtifactName, s.ID)
		}

		err = e.RunnerCommand(ctx, e.HelperEnvs(nil), args...)
		if err == nil {
			return nil
		}
	}

func (b *AbstractShell) addExtractCacheCommand(
	ctx context.Context,
	w ShellWriter,
	info common.ShellScriptInfo,
	cacheConfigs []cacheConfig,
	cachePaths []string,
) {
	cacheConfig := cacheConfigs[0]

	args := []string{
		"cache-extractor",
		"--file", cacheConfig.ArchiveFile,
		"--timeout", strconv.Itoa(info.Build.GetCacheRequestTimeout()),
	}

	w.Noticef("Checking cache for %s...", cacheConfig.HumanKey)

	extraArgs, env, err := getCacheDownloadURLAndEnv(ctx, info.Build, cacheConfig.HashedKey)
	args = append(args, extraArgs...)
	if err != nil {
		w.Warningf("Failed to obtain environment for cache %s: %v", cacheConfig.HumanKey, err)
	}
	if env != nil {
		cacheEnvFilename := b.writeCacheExports(w, env)
		args = append(args, "--env-file", cacheEnvFilename)
		defer w.RmFile(cacheEnvFilename)
	}

	alternateURLArgs, alternateErr := getAlternateCacheDownloadURL(ctx, info.Build, cacheConfig.AlternateKey)
	if alternateErr != nil {
		w.Warningf("Failed to obtain alternate URL for cache %s: %v", cacheConfig.HumanKey, alternateErr)
	} else {
		args = append(args, alternateURLArgs...)
	}

	w.IfCmdWithOutput(info.RunnerCommand, args...)
	w.Noticef("Successfully extracted cache")
	w.Else()
	w.Warningf("Failed to extract cache")

	// When extraction fails, remove the cache directories to avoid problems in cases
	// where archives may have been partially extracted, leaving the cache in an inconsistent
	// state. If we attempt to extract from fallback caches below, we'll remove the same set
	// of directories if that fails.
	if info.Build.IsFeatureFlagOn(featureflags.CleanUpFailedCacheExtract) {
		for _, cachePath := range cachePaths {
			w.Printf("Removing %s", cachePath)
			w.RmDir(cachePath)
		}
	}

	// We check that there is another key than the one we just used
	if len(cacheConfigs) > 1 {
		b.addExtractCacheCommand(ctx, w, info, cacheConfigs[1:], cachePaths)
	}
	w.EndIf()
}
