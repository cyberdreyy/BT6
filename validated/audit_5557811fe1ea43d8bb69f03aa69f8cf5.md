### Title
Timing side-channel in `CreateSession` enables user enumeration via bcrypt cost gap between unknown-email and known-email/wrong-password paths - ([File: core/sessions/localauth/orm.go])

### Summary
`orm.CreateSession` returns immediately (fast DB miss) when the submitted email does not exist, but performs a deliberately expensive `bcrypt` hash comparison via `utils.CheckPasswordHash` whenever the email does exist, even with a wrong password. This asymmetry produces a large, easily measurable latency gap that lets an unauthenticated attacker enumerate valid account emails.

### Finding Description
In `CreateSession` [1](#0-0) , the flow is:
1. `o.FindUser(ctx, sr.Email)` performs a single indexed DB lookup [2](#0-1) . If the email is unknown, `err != nil` and the function returns immediately with the raw DB error, before reaching `constantTimeEmailCompare` or any password hashing.
2. If the email is known, execution proceeds through `constantTimeEmailCompare` (cheap, constant-time) and then to `utils.CheckPasswordHash(sr.Password, string(user.HashedPassword))` [3](#0-2) , which wraps `golang.org/x/crypto/bcrypt` [4](#0-3) . `bcrypt.CompareHashAndPassword` is intentionally CPU-expensive (its whole purpose is to be slow), typically tens of milliseconds depending on configured cost factor, versus a sub-millisecond-to-few-millisecond indexed DB lookup for a nonexistent row.

The `constantTimeEmailCompare` guard only protects against timing differences in the email-string comparison itself; it does nothing to equalize the much larger timing difference caused by whether bcrypt is invoked at all. Because the "unknown email" branch returns before any bcrypt work happens, and the "known email, wrong password" branch always performs a full bcrypt comparison, the two paths are trivially distinguishable by wall-clock timing from a single request pair, without needing statistical repetition.

The MFA-branch behavioral difference (returning a WebAuthn challenge JSON vs. creating a session directly) only occurs after a correct password has already been supplied, so it does not provide an email-only enumeration primitive for an attacker who lacks valid credentials, and is out of scope for this specific attack in the question.

### Impact Explanation
This is a user-enumeration information disclosure: an unauthenticated attacker can determine which email addresses have registered node accounts, enabling targeted credential-stuffing or phishing campaigns against real operators. It does not by itself grant authentication bypass, key disclosure, or fund movement, so it maps to a low-severity information-disclosure / account-enumeration class rather than a high-severity node-compromise bug.

### Likelihood Explanation
Preconditions are minimal: only unauthenticated network access to the `/sessions` login endpoint is required, and a single request per candidate email is typically sufficient given the large (tens-of-ms) gap introduced by bcrypt vs. a DB miss. The difference is deterministic and repeatable, though real-world exploitability depends on network jitter; averaging a handful of requests would reliably remove noise.

### Recommendation
Perform a constant-cost password comparison regardless of whether the email exists — e.g., when the email lookup fails, run `utils.CheckPasswordHash` against a precomputed dummy bcrypt hash before returning the "Invalid email" error, so both branches always pay the bcrypt cost. Additionally, ensure identical response bodies/status codes for "Invalid email" and "Invalid password" cases to remove the residual message-based enumeration in addition to the timing gap.

### Proof of Concept
Go handler/unit test plan in `core/sessions/localauth/orm_test.go`:
1. Seed one known user with a bcrypt-hashed password.
2. Run `CreateSession` N times (e.g., 50 iterations) with:
   - Case A: known email + wrong password.
   - Case B: unknown/random email + any password.
3. Measure per-call latency with `time.Now()`/`time.Since()` around `o.CreateSession(ctx, sr)`.
4. Assert: mean(Case A latency) is significantly greater (e.g., >5x or a fixed threshold above measurement noise) than mean(Case B latency), demonstrating the bcrypt-vs-no-bcrypt timing gap.
5. After applying the fix (dummy bcrypt compare on unknown-email path), rerun the same benchmark and assert the latencies are statistically indistinguishable (e.g., within a small percentage tolerance).

```go
func (o *orm) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	user, err := o.FindUser(ctx, sr.Email)
	if err != nil {
		return "", err
	}
	lggr := o.lggr.With("user", user.Email)
	lggr.Debugw("Found user")

	// Do email and password check first to prevent extra database look up
	// for MFA tokens leaking if an account has MFA tokens or not.
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		o.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		o.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid password")
	}
```
