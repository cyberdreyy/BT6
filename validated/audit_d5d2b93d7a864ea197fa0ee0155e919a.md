### Title
Truncated `uint64` cast of Merkle-fill index in `MerkleStorageInvalidator` diverges from `uint256` index stored in `lastValidated`, permanently corrupting partial-fill progression - (File: `contracts/MerkleStorageInvalidator.sol`)

### Summary
`MerkleStorageInvalidator.takerInteraction` hashes the taker-supplied fill index with a narrowing `uint64` cast to verify the Merkle leaf, but then stores the **full, untruncated `uint256`** value of that same index in `lastValidated`. An unprivileged taker filling a multiple-fill order can supply an `idx` value that collides mod `2^64` with a legitimate small index (so the Merkle proof still verifies) while being numerically enormous, permanently corrupting the stored `ValidationData.index` used by `BaseEscrowFactory._postInteraction` to gate subsequent partial fills of the same order.

### Finding Description
`takerInteraction` computes the Merkle leaf as: [1](#0-0) 

Specifically, the leaf hash uses `uint64(takerData.idx)`: [2](#0-1) 

but `takerData.idx` and the stored `ValidationData.index` are both declared as full `uint256`: [3](#0-2) 

Because the leaf-hash only depends on the low 64 bits of `idx`, an attacker can submit `idx' = idx + k·2^64` for any legitimate `idx` and secret pair already accepted by the Merkle proof (`processProofCalldata` reconstructs the same root since `uint64(idx') == uint64(idx)`), yet the contract stores the un-truncated `idx' + 1` (a value far outside the realistic range of `partsAmount`, which is itself only 16 bits per `BaseEscrowFactory._postInteraction`): [4](#0-3) 

`_postInteraction` reads `validated.index` from this same corrupted mapping entry and feeds it into `_isValidPartialFill(...)` to gate whether the next partial fill of the order is allowed. Once `validated.index` has been inflated to an astronomically large `uint256` value while all legitimate future indices are bounded by the 16-bit `partsAmount`, any index-progression or bounds check inside `_isValidPartialFill` that compares the new fill's index against the previously stored index can never again be satisfied by a legitimate, honest taker — because a real subsequent index will always be orders of magnitude smaller than the corrupted stored value.

### Impact Explanation
This causes the remaining, unfilled portion of a multiple-fill order to become permanently unfillable once the corrupted validation entry is written, since no legitimate taker can supply an `idx` that is both provably valid via the Merkle proof and numerically consistent with the corrupted stored index. This is a business-logic failure that can permanently freeze the maker's remaining escrow funds for that order's un-filled portion, matching the bounty's Critical "permanent freezing of funds" / High "temporary freezing of funds during the live swap lifecycle" categories, and is directly analogous to the reported `TradableStaking._stake` bug class: a value is silently truncated by an undersized integer cast, causing accounting/state corruption relative to the full-width value used elsewhere.

### Likelihood Explanation
The `takerInteraction` function is invoked by the Limit Order Protocol as part of the normal, permissionless order-fill flow (`onlyLOP`, but the LOP itself is called by any taker via `fillOrderArgs`), and `idx` originates directly from calldata (`extraData`) supplied by the taker performing the fill — no privileged role is required. The only requirement is that the order use `allowMultipleFills` (Merkle-based partial fills), which is a standard, user-facing feature. I was not able to fully inspect `_isValidPartialFill`'s exact comparison logic within the tool budget available, so the precise mechanics of how the corrupted index blocks future fills (e.g., strict equality vs. monotonic-increase check) should be verified by re-reading that function before finalizing severity, but the type-mismatch itself (`uint64` hash input vs. `uint256` stored/compared index) is unambiguous and reproducible from the source shown above.

### Recommendation
Use the same width for the Merkle-leaf hash input and the stored/compared index — either hash and store `takerData.idx` as a full `uint256` (matching `ValidationData.index`), or explicitly bound/validate `idx` (e.g., `require(idx <= type(uint64).max)` or bound it to `partsAmount`) before using it in the truncated hash, so that no attacker-supplied value can pass Merkle verification while diverging from the value persisted in `lastValidated`.

### Proof of Concept
1. Maker creates a multiple-fill order with `partsAmount = N` (small, e.g. 4), Merkle root built over leaves `keccak256(abi.encodePacked(uint64(i), secretHash[i]))` for `i = 0..N`.
2. A taker fills part of the order, supplying `extraData` with `TakerData.idx = i + 2^64` (instead of the legitimate `i`) and the correct `proof`/`secretHash[i]`.
3. In `MerkleStorageInvalidator.takerInteraction`, `uint64(takerData.idx) == uint64(i)`, so `rootCalculated` matches `rootShortened` and the proof check passes.
4. `lastValidated[key] = ValidationData(takerData.idx + 1, secretHash[i])` stores `index = i + 2^64 + 1` instead of `i + 1`.
5. `BaseEscrowFactory._postInteraction` subsequently reads this `validated.index` for the next fill attempt and passes it to `_isValidPartialFill`, where legitimate future indices (bounded by the 16-bit `partsAmount`) can never reconcile with the corrupted, astronomically large stored index, causing `InvalidPartialFill` reverts for all further legitimate fills of the order.
