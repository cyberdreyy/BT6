### Title
Builder payments bypass the PTC/attester quorum check via `settle_builder_payment` - ([File: specs/gloas/beacon-chain.md])

### Summary
In the Gloas fork, `BuilderPendingPayment.weight` is meant to be a quorum accumulator: attesters who vote a payload was available add their effective balance to `payment.weight`, and only payments whose `weight` reaches `get_builder_payment_quorum_threshold(state)` are supposed to be paid out. However, the fast/normal settlement path, `settle_builder_payment`, pays the builder unconditionally whenever `withdrawal.amount > 0`, without ever checking `payment.weight` against the quorum threshold. The quorum check only exists in `process_builder_pending_payments`, which runs at epoch boundaries and only affects entries that were *not* already drained by `settle_builder_payment`. Since `settle_builder_payment` runs on essentially every subsequent block (whenever the parent's payload is processed within the same or previous epoch), builder payments are effectively always made with zero enforced quorum — mirroring the reported Lido `DepositSecurityModule` bug where a quorum-gated action can execute with a single (or even zero) confirming signer.

### Finding Description
`get_builder_payment_quorum_threshold` computes a Gwei quorum based on the average per-slot active balance: [1](#0-0) 

Attesters' weight is accumulated into the pending payment for a slot only when they set new participation flags for a same-slot attestation and the payment's withdrawal amount is non-zero: [2](#0-1) 

The **epoch-boundary** sweep `process_builder_pending_payments` correctly gates on this weight versus the quorum threshold: [3](#0-2) 

But the **block-processing** settlement path `settle_builder_payment`, invoked every time a subsequent block processes its parent's execution payload, pays out unconditionally based only on `withdrawal.amount > 0` — it never reads or checks `payment.weight`: [4](#0-3) 

This is called from `apply_parent_execution_payload`, which runs for the normal case where the parent's slot falls in the current or previous epoch — i.e., on essentially every block that builds directly (or one epoch later) on top of a full parent: [5](#0-4) 

Compounding this, `process_block` calls `process_parent_execution_payload` (which triggers `settle_builder_payment`) **before** `process_operations` (which processes the attestations of the very same block that could add weight to the parent slot's payment): [6](#0-5) 

Because `MIN_ATTESTATION_INCLUSION_DELAY` is 1, the earliest a same-slot attestation for slot N can be included is in block N+1's own `attestations` — but by the time those attestations are processed in `process_operations`, `settle_builder_payment` for slot N's payment has already run and already emptied/paid it out with whatever weight (often 0) existed beforehand. So the quorum mechanism has no practical chance to gate the common payout path.

The equality broken: a Gwei payment (`BuilderPendingWithdrawal.amount`, ultimately builder balance / fee-recipient payout) is committed and released without the required quorum of attester weight confirming the payload, contradicting the design intent embodied by `get_builder_payment_quorum_threshold`/`process_builder_pending_payments` (analogous to the Lido bug where `quorum` was documented as 2/3 of guardians but could effectively be bypassed to `1`).

### Impact Explanation
This falls under "Gwei created, destroyed or paid to a non-owner" / "a payload executed or paid that the block did not commit to (quorum)" — Critical, because it removes the safety mechanism intended to ensure builder payments are contingent on attester/committee confirmation of payload availability. A builder (or a proposer colluding with a builder) can receive payment even when no attester (weight = 0) confirmed the payload, since `settle_builder_payment` does not check `weight` at all. This defeats the purpose of the quorum weight tracked in `process_attestation` and the threshold computed in `get_builder_payment_quorum_threshold`.

### Likelihood Explanation
High — this is not an edge case requiring adversarial coordination; it is the **default, most common** code path. Every time a proposer builds on top of a parent whose payload was FULL, `apply_parent_execution_payload`/`settle_builder_payment` executes and pays out unconditionally. The quorum-checking `process_builder_pending_payments` path is only reached for payments that survive un-settled to the epoch boundary, which is the unusual case (requires the payload to not be built upon for roughly 2 epochs).

### Recommendation
Make `settle_builder_payment` honor the same quorum condition as `process_builder_pending_payments`: only append `payment.withdrawal` to `state.builder_pending_withdrawals` if `payment.weight >= get_builder_payment_quorum_threshold(state)`; otherwise drop/evict the payment (as the epoch-level path does for weight-deficient entries). Additionally, re-order `process_block` so that `process_operations` (which applies same-slot attestations/weight for the parent slot) executes before `process_parent_execution_payload`/settlement, so that attestations included in the settling block itself can still contribute to the quorum weight before the payment decision is made.

### Proof of Concept
Conceptual trace using the state-transition functions themselves:
1. At slot N, a builder wins the bid; `process_execution_payload_bid` records a `BuilderPendingPayment` with `weight=0` and `withdrawal.amount = value > 0` (per `specs/gloas/beacon-chain.md:2124-2141`).
2. No attester (or too few) submits a same-slot attestation for slot N before block N+1 is built (e.g., the proposer of N+1 simply omits attestations, which is always allowed since `process_operations` only bounds attestation count, not minimum).
3. Block N+1 is proposed with `parent_slot = N`. `process_block` runs `process_parent_execution_payload(state, block)` → `apply_parent_execution_payload` → since `parent_epoch == get_current_epoch(state)`, `settle_builder_payment(state, payment_index)` is called.
4. `settle_builder_payment` reads `payment.weight == 0` but does not check it; since `payment.withdrawal.amount > 0`, it unconditionally appends the withdrawal to `state.builder_pending_withdrawals`, guaranteeing the builder is paid via `state.builder_pending_withdrawals` regardless of the fact that `weight (0) < get_builder_payment_quorum_threshold(state)`.
5. `get_builder_payment_quorum_threshold` and `process_builder_pending_payments` (the only functions that reference the quorum) never get a chance to block this payment, because the entry was already drained and reset to `BuilderPendingPayment.empty()` before the epoch-boundary sweep could inspect it.

This confirms that the quorum requirement is bypassable on the standard/common execution path, with the payment always succeeding independent of attester quorum.

def get_builder_payment_quorum_threshold(state: BeaconState) -> Uint64:
    """
    Calculate the quorum threshold for builder payments.
    """
    per_slot_balance = get_total_active_balance(state) // Uint64(SLOTS_PER_EPOCH)
    quorum = per_slot_balance * BUILDER_PAYMENT_THRESHOLD_NUMERATOR
    return Uint64(quorum // BUILDER_PAYMENT_THRESHOLD_DENOMINATOR)

def settle_builder_payment(state: BeaconState, payment_index: Uint64) -> None:
    assert payment_index < len(state.builder_pending_payments)
    payment = state.builder_pending_payments[payment_index]
    if payment.withdrawal.amount > 0:
        state.builder_pending_withdrawals.append(payment.withdrawal)
    state.builder_pending_payments[payment_index] = BuilderPendingPayment.empty()

def process_builder_pending_payments(state: BeaconState) -> None:
    """
    Processes the builder pending payments from the previous epoch.
    """
    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:
        if payment.weight >= quorum:
            state.builder_pending_withdrawals.append(payment.withdrawal)

    old_payments = state.builder_pending_payments[SLOTS_PER_EPOCH:]
    state.builder_pending_payments[:SLOTS_PER_EPOCH] = old_payments
    new_payments = [BuilderPendingPayment.empty() for _ in range(SLOTS_PER_EPOCH)]
    state.builder_pending_payments[SLOTS_PER_EPOCH:] = new_payments
