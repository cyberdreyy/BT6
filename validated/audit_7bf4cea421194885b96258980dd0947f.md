### Title
Node coordinator double-counts a signer's weight when a rejection is later followed by an acceptance for the same block, inflating `total_weight_rejected` (stale) and `total_weight_approved` simultaneously - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener::handle_signer_messages` (the node-side coordinator ingesting `SignerMessageV0::BlockResponse`) tracks per-signer participation using two independently-gated structures: `gathered_signatures`/insert on `Accepted`, and `responded_signers` on `Rejected`, but `responded_signers` is shared and updated by *both* branches. A signer that first rejects a block and later (after re-evaluation) accepts the same block has its weight added to `total_weight_rejected` on the reject, and then—because the accept branch's guard is `!block.gathered_signatures.contains_key(&slot_id)` rather than a check against `responded_signers`—its weight is *also* added to `total_weight_approved`, without ever decrementing the stale rejection weight. This is the same bug class as the Velodrome finding: state built under an assumption ("this signer's weight has only been counted once, in only one bucket") is violated by a later message for the same key, silently duplicating the weight into a tally it should not additionally occupy.

### Finding Description
In `handle_signer_messages`:
- `Accepted` branch: weight is added to `total_weight_approved` only if `!block.gathered_signatures.contains_key(&slot_id)`, and then `gathered_signatures.insert(...)` and `responded_signers.insert(slot_id)` are performed. [1](#0-0) 

- `Rejected` branch: weight is added to `total_weight_rejected` only if `block.responded_signers.insert(slot_id)` returns `true` (i.e., first time this slot appears in `responded_signers`, whether from a prior reject *or* a prior accept). [2](#0-1) 

The asymmetry: if a signer's *first* message for a given block-proposal is `Rejected`, `responded_signers` gets the slot id and `total_weight_rejected` is bumped. If that same signer later sends `Accepted` for the *same* `signer_signature_hash` (e.g., the signer's local view re-evaluates once a competing rival block dies out, or their pending validation stalls and later resolves - the signer-side flow explicitly allows switching Rejected→Accepted, see `should_reevaluate_reject_reason` / `LAST` re-check in the pre-commit flow before signing), the accept branch does **not** check `responded_signers`; it only checks `gathered_signatures`, which is still empty for that slot. So the weight is added to `total_weight_approved` as well, while the earlier `total_weight_rejected` contribution is never removed. The single signer's weight is now counted in both buckets for the same block, exactly the duplicate-counting root cause in the reference report ("assumes the destination bucket is empty / doesn't reconcile the source bucket").

### Impact Explanation
`get_block_status`'s polling loop in `signer_coordinator.rs` treats `total_weight_rejected` and `total_weight_approved` as if they partition the signer set (checking rejection-crossing-blocking-minority first, then approval-crossing-threshold). [3](#0-2) [4](#0-3) 

Because `total_weight_rejected` is a stale, monotonically-non-decreasing counter that is never corrected downward when a rejecting signer switches to accept, the coordinator's rejection-based checks (`total_weight_rejected.saturating_add(weight_threshold) > total_weight`) fire against inflated, no-longer-true rejection weight. This can cause the miner to erroneously treat a block as globally rejected (`SignersRejected`, discarding transactions as "problematic"/excluded) even though the *current* true rejecting weight is below the blocking-minority threshold, because part of the counted rejecting weight has actually flipped to acceptance. This is a liveness degradation on the miner/coordinator side: valid blocks can be spuriously abandoned and correctly-behaving transactions can be wrongly marked temporarily/permanently excluded, based on double-counted stale weight rather than the true current vote tally. It does not, on its own, cause a signer to sign an invalid/conflicting block or produce a cross-context-valid signature, so it sits below the "signer signing invalid block" Critical bar, but it is a concrete miscount of the vote tally (the "rejection is not removed while the same weight is recounted as an accept" pattern the prompt explicitly calls out) that directly degrades the coordinator's decision correctness.

### Likelihood Explanation
Requires only a single signer (the "attacker" or simply a normal signer with a delayed/flip-flopping view) to send `Rejected` then later `Accepted` for the identical `signer_signature_hash` within the same proposal round — this is an ordinary and expected signer-side sequence (the v0 signer flow explicitly re-evaluates and can flip from reject to accept once a conflict becomes stale, per `handle_block_pre_commit`'s re-check path). No majority, no key compromise, and no auth token access is needed; it is triggerable by any one participating signer (or even by the same honest signer under normal state re-evaluation, not necessarily malicious intent), making it a real-world-reachable (not merely theoretical) miscount.

### Recommendation
Make `total_weight_approved` and `total_weight_rejected` mutually exclusive per slot id: before adding rejection weight, check `!block.gathered_signatures.contains_key(&slot_id)`; before adding approval weight, if the slot was previously in the rejected set, subtract its weight from `total_weight_rejected` (and drop it from whatever internal "rejected slots" set backs that decision) before adding to `total_weight_approved`. Concretely, track a per-slot single most-recent vote (accept/reject) rather than two independently-updated counters gated by different keys, and recompute both weight totals from that canonical per-slot map whenever a new response for a previously-responded slot arrives.

### Proof of Concept
1. Node proposes block B; coordinator calls `insert_block` seeding `BlockStatus` with zeroed weights and empty sets. [5](#0-4) 
2. Signer S (weight W) initially rejects B (e.g., it detects a rival block at that height): `BlockResponse::Rejected` is processed, `responded_signers.insert(S)` succeeds, `total_weight_rejected += W`.
3. Later in the same round, the rival dies out and S's local pre-commit re-check (`handle_block_pre_commit`'s `RECHECK`/`CONF`/`FRESH` staleness logic) results in S signing B: `BlockResponse::Accepted` is broadcast for the same `signer_signature_hash`. [6](#0-5) 
4. The coordinator processes the `Accepted` message: `gathered_signatures.contains_key(&S)` is `false` (never populated by the reject path), so `total_weight_approved += W` is applied. [7](#0-6) 
5. Now `total_weight_rejected` still equals `W` (never reverted) and `total_weight_approved` also equals `W` from the same signer — the sum of the two tallies exceeds the true number of distinct participating weight, and the rejection-threshold check in `get_block_status` can fire on stale weight that no longer reflects S's current vote. [3](#0-2)
