### Title
`_guarded` TVL limit can be exceeded because `getContractValue()` undercounts deposits while withdraw-request principal is burned but still owed by the borrower - ([File: contracts/GuardedLaunchUpgradable.sol](contracts/GuardedLaunchUpgradable.sol))

### Summary
The guarded-launch ceiling in `GuardedLaunchUpgradable._guarded` compares `getContractValue() + _amount` against `limit` [1](#0-0) . For the credit-vault CDOs, `getContractValue()` is derived from the strategy-token balance held by the CDO (`IdleCreditVault` mints 1:1 strategy tokens to `idleCDO` on deposit and `mintStrategyTokens`, price is always `oneToken`) [2](#0-1) [3](#0-2) . When a user requests a withdraw, `requestWithdraw` burns `_principal` strategy tokens from the CDO while the corresponding amount stays outstanding as `pendingWithdraws` owed by the borrower [4](#0-3) . The measured value therefore temporarily drops even though the funds are still deployed with the borrower — the same "balanceOf instead of cumulative deposits" bug class as the poolCeiling report.

### Finding Description
1. `limit` is set to L (guarded launch). Alice (any KYC-passing lender) deposits AA up to L. `_guarded` passes since `getContractValue() == ~L`.
2. During the buffer/running epoch, Alice calls `requestWithdraw` for her full position via `IdleCDOEpochVariant`. `IdleCreditVault.requestWithdraw` burns the CDO's strategy tokens (`_burn(msg.sender, _principal)`) and adds the amount to `pendingWithdraws`, which the borrower must fund at `stopEpoch`/`collectWithdrawFunds` [5](#0-4) .
3. `getContractValue()` now reads ≈ 0 (CDO holds no strategy tokens), so the underlying lent to the borrower is invisible to the ceiling check — exactly like the AMO borrow shrinking `balanceOf` in the Ubiquity report.
4. Bob deposits another L of underlying. `_guarded(L)` computes `~0 + L <= L` and passes; `IdleCreditVault.deposit`/`mintStrategyTokens` mints fresh strategy tokens and the funds reach the borrower [6](#0-5) .
5. At `stopEpoch` the borrower repays principal + interest covering both Alice's `pendingWithdraws` and Bob's active position. Total value at risk in the vault is now up to ~2×L — the ceiling invariant is broken while all funds were actually deployed.

No existing guard stops this: the skim/default-revert logic in `_updateAccounting` does not account for burned-but-owed withdraw principal, `requestWithdraw` is open to any tranche holder through the CDO, and `collectWithdrawFunds` happily funds the pending bucket on top of the new deposits.

### Impact Explanation
`limit` is the protocol's explicit TVL risk bound (`ContractLimitReached` in `GuardedLaunchUpgradable`). Bypassing it lets unbounded underlying be lent to a single borrower beyond the intended cap; if the borrower later defaults (a normal, honest protocol event), losses exceed the guarded-launch bound the ceiling was designed to enforce — the same "broken ceiling → larger loss surface" impact as the source finding. Loss magnitude equals the excess deposits (up to `limit` per round-trip, repeatable across users/epochs).

### Likelihood Explanation
High whenever a nonzero `limit` is configured and withdraw requests are permitted while deposits remain open (buffer/running epoch, including prefunded-queue deposits which are also `_guarded` per `testPrefundedRequestRespectsContractLimit`). It only requires ordinary user actions — deposit, request withdraw, deposit — with no privileged cooperation.

### Recommendation
Track cumulative outstanding principal instead of the live strategy-token balance for the ceiling check, e.g. keep an `totalDepositedPrincipal` counter incremented in `_deposit` and decremented only when the withdraw claim is actually paid (claim), or include `pendingWithdraws`/`pendingInstantWithdraws` in the `getContractValue()` value used by `_guarded`. Do not use a burn-able `balanceOf` as the deposit proxy.

### Proof of Concept
Foundry fork test sketch (extend `test/foundry/IdleCDOEpochVariantPrefunded.t.sol` setup):

```solidity
function testCeilingBypassViaWithdrawRequest() external {
    uint256 limit = 1000e6;
    vm.prank(cdoEpoch.owner());
    cdoEpoch._setLimit(limit);

    // Alice deposits up to the cap
    _depositAA(alice, limit);

    // Alice requests a withdraw: CDO strategy tokens burned, pendingWithdraws += limit
    vm.prank(alice);
    cdoEpoch.requestWithdraw(limit, false); // AA withdraw request path

    // Bob deposits another `limit` — _guarded sees near-zero contract value
    _depositAA(bob, limit); // must NOT revert, but currently does not

    // stopEpoch: borrower funds pendingWithdraws + interest
    _fundBorrowerAndStopEpoch();

    // Assert total deployed/exposed value exceeds the configured cap
    assertGt(cdoEpoch.getContractValue() + strategy.pendingWithdraws(), limit);
}
```

Caveat: I verified `_guarded`, the burn in `requestWithdraw`, and the 1:1 strategy-token accounting directly; I could not open `IdleCDO.getContractValue`/`IdleCDOEpochVariant._deposit` in the remaining iterations to confirm line-exactly that the epoch deposit path routes through `_guarded` and that `getContractValue` is purely `strategyToken.balanceOf(cdo) * price / oneToken`. The prefunded-queue test (`testPrefundedRequestRespectsContractLimit`) and `GuardedLaunchUpgradable`'s abstract contract strongly indicate both, but the PoC should confirm the deposit path used mid-epoch triggers `_guarded`.

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }
