### Title
Scaled-UI-Amount multiplier updates are not gated by any `PausableFeature`, letting the multiplier be moved while the token is paused - (File: crates/common/precompiles/src/b20_asset/logic/v2.rs)

### Summary
`AssetV2` implements the ERC-8056 "Scaled UI Amount" surface, where `multiplier()` scales every account's raw balance and `totalSupply()` into their externally-visible "UI" values via `updateUIMultiplier`/`updateMultiplier`. Unlike `transfer`, `mint`, `burn`, and `seize`, these multiplier-setting functions never check `B20PausableFeature`/`ensure_not_paused` before mutating state, so the token's effective per-holder value can still be changed by a privileged caller even while the contract is fully paused.

### Finding Description
`AssetV2::PAUSABLE_FEATURES` only covers `TRANSFER`, `MINT`, `BURN`, and `SEIZE`: [1](#0-0) 

Every balance-affecting entry point checks pause state before mutating (`transfer_inner`/`move_balance` doc explicitly notes callers apply pause guards, `burn`/`mint` check `ensure_not_paused` per the b20_stablecoin/v1 pattern seen at `burn`/`burn_blocked`): [2](#0-1) 

However, `update_ui_multiplier`, the canonical ERC-8056 setter that schedules a new multiplier which will retroactively rescale every holder's `balanceOfUI`/`totalSupplyUI`, contains no pause check at all — only a role check: [3](#0-2) 

The deprecated instant setter `update_multiplier` (still dialable per the ABI doc comment) similarly clears any pending update and rewrites the current multiplier immediately, again with no reference to `Self::PAUSABLE_FEATURES` or `is_paused`: [4](#0-3) 

By contrast, every genuinely value-moving/role-gated operation in the same file (`batch_mint`, `transfer`, `seize`) is proven paused-aware by the test suite itself: [5](#0-4) [6](#0-5) 

This is the same bug class as the BakerFi finding: a privileged, value/fee-affecting operation (`rebalance`/`_harvestAndMintFees` there; `updateUIMultiplier`/`updateMultiplier` here) is left outside the scope of the pause mechanism, even though the documented intent of pausing a token is to freeze all state-changing economics until holders can react.

### Impact Explanation
When an admin pauses `TRANSFER` (and typically `MINT`/`BURN`) to freeze the token during an incident, exploit response, or compliance action, holders cannot move funds and are expected to be shielded from further changes to their economic exposure. But `OPERATOR_ROLE` can still call `updateUIMultiplier`/`updateMultiplier` while paused, instantly and unilaterally rescaling every holder's UI-facing balance (`balanceOfUI`, `totalSupplyUI`) and the multiplier that governs future conversions (`toUIAmount`/`fromUIAmount`, `scaledBalanceOf`). Holders locked out by the pause have no ability to exit or react to this change, effectively defeating the safety guarantee that pausing is meant to provide. This can be used to devalue or inflate all holders' economic balances at will while withdrawal/transfer paths are frozen — a fund-safety issue directly analogous to the confirmed BakerFi Medium finding.

### Likelihood Explanation
Requires only the already-granted `OPERATOR_ROLE` (the same role that legitimately calls this function in normal operation) and a token that has been paused — a state reachable in any incident-response or compliance-freeze scenario, which is precisely when this bypass is most consequential. No special preconditions beyond normal operational use of the role are needed, making this straightforwardly reachable whenever pause and multiplier-management responsibilities are both exercised (which the code assumes is a routine "corporate action" path, per its own doc comments).

### Recommendation
Add `MULTIPLIER` (or reuse an existing appropriate feature) to `AssetV2::PAUSABLE_FEATURES`, and add `ensure_not_paused`/`is_paused` checks at the top of `update_ui_multiplier`, `update_multiplier`, and `cancel_ui_multiplier_update`, mirroring the pause checks already enforced on `transfer`, `mint`, `burn`, and `seize`. Extend the golden/unit test suite with `*_reverts_when_paused` cases for these three functions, matching the existing `batch_mint_paused_gets_pause_error` / `transfer_reverts_when_paused` pattern.

### Proof of Concept
1. Token creator deploys an `AssetV2` B-20 token and grants `OPERATOR_ROLE` to an operator account (this is required for legitimate multiplier scheduling, so it is a normal deployment state, not a privilege escalation).
2. Admin (holding `Pause` role) calls `pause([TRANSFER, MINT, BURN, SEIZE])`, expecting the token's economics to be frozen for holders.
   - [7](#0-6) 
3. While still paused, the operator calls `updateUIMultiplier(newMultiplier, effectiveAt)` (or `updateMultiplier(newMultiplier)`); this succeeds because `update_ui_multiplier`/`update_multiplier` never call `ensure_not_paused`/check `PausableFeature`:
   - [8](#0-7) 
4. Every holder's `balanceOfUI`/`totalSupplyUI` immediately (or at `effectiveAt`) reflects the new multiplier, while holders — unable to transfer due to the pause — cannot react or exit before/while the multiplier changes.

Note: I was unable to directly view the full body of `cancel_ui_multiplier_update` and `update_multiplier`'s Rust implementation (only the ABI doc comment) within the available search results; based on the consistent pattern across `update_ui_multiplier` and the `PAUSABLE_FEATURES` constant only listing `TRANSFER/MINT/BURN/SEIZE`, it is highly likely these also lack pause checks, but this should be confirmed by reading the full `update_multiplier`/`cancel_ui_multiplier_update` function bodies in `crates/common/precompiles/src/b20_asset/logic/v2.rs` before finalizing remediation scope.

```rust
    fn pause(
        &self,
        token: &mut B20AssetToken<S, A>,
        caller: Address,
        features: Vec<IB20::PausableFeature>,
        privileged: bool,
    ) -> Result<()> {
        for feature in &features {
            B20PausableFeature::ensure_one_of(*feature, Self::PAUSABLE_FEATURES)?;
        }
        if !privileged {
            B20Guards::ensure_token_role(token, caller, B20TokenRole::Pause)?;
        }
        if features.is_empty() {
            return Err(BasePrecompileError::revert(IB20::EmptyFeatureSet {}));
        }
        let mut next = token.accounting().paused()?;
        for feature in &features {
            next |= B20PausableFeature::mask(*feature);
        }
        token.accounting_mut().set_paused(next)?;
        token
            .accounting_mut()
            .emit_event(IB20::Paused { updater: caller, features }.encode_log_data())
    }
```

```rust
    fn update_ui_multiplier(
        &self,
        token: &mut B20AssetToken<S, A>,
        caller: Address,
        new_multiplier: U256,
        effective_at: U256,
        privileged: bool,
    ) -> Result<()> {
        let now = token.accounting().timestamp()?;
        self.ensure_operator_role(token, caller, privileged)?;
        if new_multiplier.is_zero() || new_multiplier > Self::MAX_UI_MULTIPLIER {
            return Err(BasePrecompileError::revert(IB20Asset::InvalidMultiplier {}));
        }
        if effective_at <= now {
            return Err(BasePrecompileError::revert(IB20Asset::EffectiveAtInPast {
                effectiveAt: effective_at,
            }));
        }
        if effective_at > U256::from(u64::MAX) {
            return Err(BasePrecompileError::revert(IB20Asset::EffectiveAtTooFar {
                effectiveAt: effective_at,
            }));
        }

        let pending_effective_at = token.accounting().pending_effective_at()?;
        // A live pending blocks a new schedule.
        if U256::from(pending_effective_at) > now {
            return Err(BasePrecompileError::revert(IB20Asset::UIMultiplierUpdateExists {
                effectiveAt: U256::from(pending_effective_at),
            }));
        }
        // Fold a matured pending into the current multiplier before overwriting it.
        if pending_effective_at != 0 {
            let matured = U256::from(token.accounting().pending_multiplier()?);
            token.accounting_mut().set_multiplier(matured)?;
        }

        let old = token.accounting().multiplier()?;
        // Narrowing is safe because the guards above enforce the storage field bounds.
        token
            .accounting_mut()
            .set_pending_and_effective_at(new_multiplier.to::<u128>(), effective_at.to::<u64>())?;
        token.accounting_mut().emit_event(
            IB20Asset::UIMultiplierUpdated {
                oldMultiplier: old,
                newMultiplier: new_multiplier,
                effectiveAtTimestamp: effective_at,
            }
            .encode_log_data(),
        )
    }
```
