### Title
Changing `unscaledApr` while APR0 withdraw requests are pending permanently bricks `stopEpoch`, freezing all vault funds - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`prepareStopEpochWithApr0` reverts with `NotAllowed` whenever `apr0TotalPrincipal != 0` and `unscaledApr != 0`. Because `apr0TotalPrincipal` is only cleared inside that same function *after* the revert, once an honest manager changes the pool APR away from 0 while any APR0 withdraw request is still pending, every subsequent `stopEpoch` call reverts forever. The epoch can never end: no claims, no new epoch, no default handling — all underlying is permanently frozen.

### Finding Description
When `unscaledApr == 0`, `requestWithdraw` routes requests into `_requestWithdrawApr0`, which increments the global `apr0TotalPrincipal` [1](#0-0) . At epoch stop, the CDO calls `prepareStopEpochWithApr0`, which hits this guard: [2](#0-1) 

The comment "APR0 principal is only valid while APR is 0 for that request lifecycle" acknowledges the assumption, but the code enforces it by reverting rather than settling. The only places `apr0TotalPrincipal` is mutated are:

- `+=` in `_requestWithdrawApr0` (line 576)
- `= 0` at line 540 — unreachable because the revert at line 507 fires first.

There is no other escape: `apr0Users[_user].principal` can only move to `settledPrincipal` via `_settleApr0`, which requires `_reqEpoch < epochNumber`, and `epochNumber` is only bumped inside `deposit` when called during `stopEpoch` [3](#0-2) . So the state is unrecoverable:

1. Any unprivileged, KYC-passing lender calls `cdoEpoch.requestWithdraw(...)` during the buffer while `unscaledApr == 0` → `apr0TotalPrincipal > 0`.
2. The honest manager sets a non-zero APR (a normal, legitimate operation — e.g. via `setApr`/manager orchestrator) before `stopEpoch`.
3. `stopEpoch` → `prepareStopEpochWithApr0` → `revert NotAllowed()`.
4. Repeat forever. `epochNumber` never increments, so pending APR0 receipts can never settle, and `apr0TotalPrincipal` can never be cleared.

This mirrors the external report's bug class — a single user-reachable state combination makes the core protocol function (`stopEpoch`, analogous to Cooler's request/rescind/clear) revert unconditionally, halting the protocol.

### Impact Explanation
Permanent freezing of all funds in the vault. While `stopEpoch` reverts:

- `epochNumber` never advances, so no withdraw request (normal, APR0, instant, or queued via `IdleCDOEpochQueue`) can ever be claimed — `_claimFundedWithdrawRequest` requires `epochNumber > lastWithdrawRequest` [4](#0-3) .
- Active LPs cannot exit: tranche redemptions route through withdraw requests that need a stopped epoch.
- The borrower cannot repay and the pool cannot be defaulted or closed — `finalizeDefault`, close-pool (`_interest == 1`), and `_handleBorrowerDefault` all execute inside `stopEpoch`.
- Loss: 100% of vault TVL plus all pending receipts, indefinitely.

### Likelihood Explanation
Low-to-moderate likelihood, critical impact. It requires (a) APR == 0 mode, an explicitly supported configuration with dedicated accounting (`apr0Users`, `apr0RateByEpoch`, `prepareStopEpochWithApr0`), (b) at least one pending APR0 withdraw request — a single unprivileged lender suffices, and (c) the manager setting APR ≠ 0 before the epoch stops, which is a routine honest action (the manager orchestrator exists precisely to tune APR). No malicious privileged role is needed; the trigger transaction is an ordinary `requestWithdraw` by any allowed wallet. The window spans the full epoch duration plus buffer, since requests remain "pending" until `stopEpoch` bumps `epochNumber`.

### Recommendation
Do not revert on the APR transition; settle the pending APR0 bucket instead. In `prepareStopEpochWithApr0`, when `unscaledApr != 0` and `apr0TotalPrincipal != 0`, either:

- settle APR0 receipts at the last valid zero-APR rate (`apr0RateByEpoch[epochNumber] = 0`, move principal to settled), or
- pro-rate them into the new fixed-APR interest using the existing `_totalPrincipalForSplit` math,

then set `apr0TotalPrincipal = 0` unconditionally at the end of the function. Alternatively, block APR changes at the CDO/manager layer while `apr0TotalPrincipal != 0` (reverting `setApr` is safer than reverting `stopEpoch`, since the former is recoverable). Add a regression test: request withdraw at APR 0, change APR, then `stopEpoch` must succeed.

### Proof of Concept
```solidity
// Foundry fork test against the epoch-variant CDO + IdleCreditVault
function testStopEpochBrickedByAprChangeWithPendingApr0() external {
    // pool configured with unscaledApr == 0
    uint256 amount = 10_000 * ONE_SCALE;
    uint256 mintedAA = idleCDO.depositAA(amount);   // KYC'd lender
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, 0, _expectedFundsEndEpoch()); // epoch 1 starts buffer

    // Unprivileged lender files an APR0 withdraw request during buffer
    vm.prank(user1);
    cdoEpoch.requestWithdraw(mintedAA / 2, address(AAtranche));
    assertGt(strategy.apr0TotalPrincipal(), 0);

    _startEpochAndCheckPrices(1);

    // Honest manager raises APR mid-epoch (routine operation)
    vm.prank(manager);
    cdoEpoch.setApr(initialProvidedApr); // unscaledApr != 0 now

    // Borrower repays in full; funds are available
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.warp(cdoEpoch.epochEndDate() + 1);

    // Every stopEpoch reverts -> permanent freeze
    vm.prank(manager);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.stopEpoch(0, expectedInterest);

    // And it can never recover: apr0TotalPrincipal cannot be cleared,
    // epochNumber cannot advance, no claim/default/close path is reachable.
    vm.prank(manager);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.stopEpoch(0, 1); // even the close-pool sentinel reverts
}
```
