### Title
Confirmations counted against stale keys after `DeleteKey` allows request execution below the intended live-member threshold - (File: multisig/src/lib.rs)

### Summary
`MultiSigContract::confirm` in `multisig/src/lib.rs` compares the size of a request's `confirmations: HashSet<PublicKey>` against `self.num_confirmations` without verifying that each key in that set still corresponds to a currently valid multisig key. The `DeleteKey` action only purges *outstanding requests signed by* the deleted key, but never scrubs that key's *confirmations already recorded on other, still-pending requests*. This lets a request accumulate the required number of confirmations even though one or more of the confirming keys have since been removed from the account, so a request can execute with fewer live, authorized signers than `num_confirmations` demands.

### Finding Description
`confirm()` does the threshold check purely on set cardinality: [1](#0-0) 
counts `confirmations.len() as u32 + 1 >= self.num_confirmations` with no cross-check against a live key set.

`MultiSigRequestAction::DeleteKey` execution only cleans up requests *originated* by the deleted key and the `num_requests_pk` counter, but does not touch the `confirmations` map for other requests that key had already confirmed: [2](#0-1) 

Because `confirmations` is keyed by `RequestId -> HashSet<PublicKey>` independent of the current access-key set on the account, a public key that confirmed request X and was later deleted via a separate `DeleteKey` request still counts toward X's confirmation threshold. The binding that should hold is: `count(confirmations for request X that belong to currently-valid keys) >= num_confirmations`; instead the contract enforces `count(confirmations recorded historically) >= num_confirmations`, which can diverge once membership changes between the first confirmation and execution.

### Impact Explanation
This breaks the "confirmations counted versus live members" custody binding: a multisig request (e.g., a `Transfer` moving NEAR out of the account) can be executed with confirmations from fewer *live* signers than the configured `num_confirmations` threshold requires. This is a Critical-class impact per the given criteria ("a multisig request executed below threshold"), since funds can move, or account-modifying actions (adding/deleting keys, deploying new contract code) can execute, without the intended number of currently-authorized parties agreeing.

### Likelihood Explanation
The scenario requires a benign sequence of legitimate multisig operations that is entirely plausible in normal contract lifecycle: (1) key A confirms request X (one of several outstanding requests), (2) the remaining live signers separately confirm and execute a `DeleteKey` request removing key A (e.g., because A's device was lost/compromised, a common security operation), (3) request X only needs one more confirmation from any remaining key to hit `num_confirmations`, even though A is no longer a valid signer. No attacker collusion beyond normal multisig usage/rotation is required — the stale confirmation persists silently since there is no explicit cleanup or re-validation step.

### Recommendation
When executing `MultiSigRequestAction::DeleteKey`, iterate over all outstanding requests' `confirmations` sets (not just requests originated by that key) and remove the deleted public key from each. Alternatively, when counting confirmations in `confirm()`, filter `confirmations` against the current valid key set (which would require tracking valid keys explicitly, since NEAR doesn't expose access keys to contracts) before comparing against `num_confirmations`.

### Proof of Concept
1. Initialize a 2-of-3 multisig with keys `A`, `B`, `C` (`num_confirmations = 2`).
2. Key `A` calls `add_request_and_confirm` for `Transfer{amount}` targeting an external receiver → request `X` has 1 confirmation (`A`).
3. Separately, keys `B` and `C` create and confirm a `DeleteKey{public_key: A}` request, which executes and removes `A`'s access key from the account (per `execute_request`'s `DeleteKey` branch at `multisig/src/lib.rs:198-216`); this only clears requests *signed* by `A`, not `A`'s confirmation already stored on request `X`.
4. Request `X`'s `confirmations` set still contains `A`'s (now-revoked) public key with length 1.
5. Key `B` calls `confirm(X)`. `confirmations.len() as u32 + 1` (`1 + 1 = 2`) `>= num_confirmations (2)` → the transfer executes with only `B` as a live confirming signer, i.e., below the intended 2-live-signer threshold.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
