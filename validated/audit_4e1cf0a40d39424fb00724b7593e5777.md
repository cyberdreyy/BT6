### Title
Stale confirmations from removed multisig members are still counted toward `num_confirmations`, allowing a request to execute below the live-member threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::confirm` in `multisig2/src/lib.rs` decides whether a request has reached quorum purely by checking the *size* of the `confirmations` set stored for that `request_id`, without re-validating that every entry in that set still corresponds to a current member of `self.members`. `delete_member` only purges confirmations/requests that were *originated* by the removed member, not confirmations that member previously *cast* on other members' requests. As a result, a request can execute with fewer live-member approvals than `num_confirmations` requires, because a stale confirmation from an account/key that has since been removed from the multisig is still counted.

### Finding Description
Confirmations are tracked in `confirmations: LookupMap<RequestId, HashSet<String>>`, keyed by the string form of a `MultisigMember` (`multisig2/src/lib.rs:128`). [1](#0-0) 

`confirm()` only checks:
1. That the caller (predecessor/signer) is *currently* a member, via `assert_valid_request` → `current_member()` (`multisig2/src/lib.rs:407-423`, `323-339`).
2. That the caller hasn't already confirmed.
3. Whether `confirmations.len() + 1 >= self.num_confirmations`.

It never checks that the *existing* entries in `confirmations` still belong to current members of `self.members`.

`delete_member()` is the only path that prunes stale confirmation data, and it does so incompletely: [2](#0-1) 

It removes confirmation sets only for requests where `r.member == member` — i.e., requests *created* by the member being removed. It does **not** scan `self.confirmations` for entries where the removed member appears as a *confirmer* on requests created by someone else. Those confirmations remain in the `HashSet<String>` for that `request_id` indefinitely, and continue to count toward `num_confirmations` in any subsequent `confirm()` call by a different (still-valid) member.

This breaks the intended binding: `confirmations counted == live members who approved`. After a member is removed, this becomes `confirmations counted > live members who approved`, since a since-removed member's earlier confirmation is still tallied.

### Impact Explanation
This is a Critical-impact issue per the multisig threshold-enforcement guarantee: "a multisig request executed below threshold." An attacker (or negligent operator) can get a sensitive request — e.g., `Transfer`, `FunctionCall`, `AddKey`, `DeployContract` — executed with fewer *live* approvals than `num_confirmations` mandates, by:
1. Getting a request partially confirmed by a member who is later removed (e.g. because the key was compromised, or the member legitimately rotated out).
2. Having only `num_confirmations - 1` currently-live members confirm afterward.

The stale confirmation from the removed member still counts, so the request executes with one fewer live approval than configured, undermining the K-of-N security guarantee the contract exists to provide (e.g. moving NEAR funds, adding a rogue full-access key, or deploying new contract code) with insufficient live authorization.

### Likelihood Explanation
This requires no privileged access beyond being a normal, valid multisig member (or even just the ordinary lifecycle of member rotation, which multisig deployments are expected to do periodically). It doesn't require the removed member to be malicious — a routine member-rotation event (revoking a lost/compromised key, replacing personnel) combined with any request that received a partial confirmation before the rotation is sufficient to trigger under-threshold execution. This makes it a realistic, not merely theoretical, scenario for any long-lived multisig with membership turnover.

### Recommendation
When counting confirmations in `confirm()`, filter `confirmations` to only those entries whose `MultisigMember` is still contained in `self.members` before comparing against `self.num_confirmations` (and persist the pruned set). Additionally, `delete_member()` should scan all outstanding `confirmations` maps (not just requests created by the removed member) and strip the removed member's entry from every confirmation set, so stale approvals can never be counted, and re-evaluate/no-op any request whose live-confirmation count then falls below threshold.

### Proof of Concept
1. Deploy multisig2 with `members = [A, B, C, D]`, `num_confirmations = 3`.
2. `A.add_request(R)` where `R` is a sensitive `Transfer` action → `confirmations[R] = {}`.
3. `B.confirm(R)` → `confirmations[R] = {B}` (len 1 < 3).
4. `C.confirm(R)` → `confirmations[R] = {B, C}` (len 2 < 3, not executed).
5. Separately, via a properly-confirmed `DeleteMember { member: C }` request, `C` is removed from `self.members`. Per `multisig2/src/lib.rs:356-379`, this only clears requests/confirmations *created* by `C`; `R`'s confirmation set (created by `A`) still contains `C`.
6. `D.confirm(R)`: `assert_valid_request` passes (`D` is a live member). `confirmations[R].len() == 2`, `2 + 1 >= 3` → threshold met → `execute_request(R)` runs.
7. Result: `R` (e.g. a fund transfer) executes with approvals effectively from only `B` and `D` as *live* members plus a stale, no-longer-valid confirmation from removed member `C` — one fewer live approval than the configured `num_confirmations = 3`. [1](#0-0) [2](#0-1)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
