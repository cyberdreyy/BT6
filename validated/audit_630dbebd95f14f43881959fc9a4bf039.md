### Title
Missing role-based access control on `GET /v2/external_initiators` exposes External Initiator `AccessKey` and `OutgoingToken` to lowest-privilege authenticated users - (File: core/web/router.go)

### Summary
The Sherlock finding is about `RollerPeriphery.mint()` lacking any access-control modifier, letting any unprivileged caller invoke a sensitive privileged operation. The Chainlink analog is `ExternalInitiatorsController.Index`, registered at `authv2.GET("/external_initiators", paginatedRequest(eia.Index))`, which — unlike its sibling `Create`/`Destroy` routes — is wired with no role-gating wrapper at all, while every other mutating/administrative route on that group is wrapped in `auth.RequiresEditRole` or `auth.RequiresAdminRole`. [1](#0-0) 

### Finding Description
The `authv2` route group only enforces base authentication (`auth.Authenticate(..., auth.AuthenticateByToken, auth.AuthenticateBySession)`), which succeeds for any valid session/API-token regardless of role, including the lowest-privilege `UserRoleView`. [2](#0-1) 

For the External Initiators routes, `Create` and `Destroy` are explicitly wrapped with `auth.RequiresEditRole`, which blocks `view` and `run` roles: [3](#0-2)  But `Index` (the `GET` list endpoint) is registered with only `paginatedRequest(eia.Index)` — no `RequiresEditRole`/`RequiresAdminRole` modifier is applied: [1](#0-0) 

`Index` returns `presenters.ExternalInitiatorResource` for every external initiator in the node, including the `AccessKey` and `OutgoingToken` fields: [4](#0-3) [5](#0-4) 

`AccessKey` is the credential used together with the (separately-hashed) `Secret` to authenticate as that external initiator via `AuthenticateExternalInitiator`, which grants the caller the `Run` role — sufficient to trigger job runs: [6](#0-5)  `OutgoingToken` is a distinct secret generated for the initiator (`utils.NewSecret(utils.DefaultSecretSize)`) alongside `OutgoingSecret`: [7](#0-6) 

Because `Index` requires no elevated role, any authenticated principal holding only a `view`-role session/API token (the lowest privilege tier in the node's RBAC model) can enumerate this list and obtain the `AccessKey`/`OutgoingToken` values for every configured external initiator — a capability that is otherwise gated behind `edit` role for creating/deleting the same resource.

### Impact Explanation
Disclosure of `AccessKey` values undermines the external-initiator authentication scheme (`X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers), reducing the security of the run-triggering credential to only the unexposed `Secret`/`HashedSecret` half. It also breaks the RBAC invariant enforced everywhere else on this resource (`RequiresEditRole` on Create/Destroy), letting a `view`-role user access data an `edit`-role gate was clearly intended to protect — a role-bypass/information-disclosure issue analogous to a missing access-control modifier on a privileged function.

### Likelihood Explanation
Exploitation only requires a valid, low-privilege (`view`-role) node API token or session — a credential level explicitly designed to be safe for read-only/monitoring users. No additional bypass of authentication is needed, only the absence of role authorization on this single route, making the path directly and easily reachable.

### Recommendation
Wrap `authv2.GET("/external_initiators", ...)` with `auth.RequiresEditRole` (or at minimum `auth.RequiresRunRole` if broader read access is intentionally desired), consistent with the `Create`/`Destroy` handlers on the same resource, and/or redact `AccessKey`/`OutgoingToken` from the list response for lower-privileged roles.

### Proof of Concept
1. Create a node user with `UserRoleView` and obtain a valid session cookie or API token (`AuthenticateByToken`/`AuthenticateBySession` only checks credential validity, not role, at the group middleware level — role checks happen per-route).
2. As that `view` user, issue `GET /v2/external_initiators` (as exercised in `TestExternalInitiatorsController_Index`, which uses `client.Get("/v2/external_initiators?size=1")` with no role escalation): [8](#0-7) 
3. The response includes `accessKey` and `outgoingToken` for every configured external initiator, per `NewExternalInitiatorResource`: [9](#0-8) 
4. Compare with attempting `POST /v2/external_initiators` or `DELETE /v2/external_initiators/:Name` as the same `view` user — these are rejected by `RequiresEditRole`, confirming `Index` is the outlier lacking the same protection.

// RequiresEditRole extracts the user object from the context, and asserts the user's role is at least
// 'edit'
func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

func (eic *ExternalInitiatorsController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	externalInitiators, count, err := eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)
	resources := make([]presenters.ExternalInitiatorResource, 0, len(externalInitiators))
	for _, initiator := range externalInitiators {
		resources = append(resources, presenters.NewExternalInitiatorResource(initiator))
	}

	paginatedResponse(c, "externalInitiators", size, page, resources, count, err)
}
