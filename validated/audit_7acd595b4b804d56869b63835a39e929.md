### Title
External Initiator credentials can trigger job runs for arbitrary jobs via `POST /v2/jobs/:ID/runs`, bypassing intended EI-to-job binding - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` gates the "run any job by integer ID" code path on `isUser, _ := auth.GetAuthenticatedUser(c)`, intending that only session/token users (not external initiators) can trigger arbitrary jobs by numeric ID. However, `AuthenticateExternalInitiator` sets the exact same context key (`SessionUserKey`) that session/token auth uses, so `GetAuthenticatedUser` returns `ok=true` for EI-authenticated requests too, defeating the intended check.

### Finding Description
The `userOrEI` route group wraps `POST /v2/jobs/:ID/runs` with `auth.Authenticate(..., auth.AuthenticateExternalInitiator, auth.AuthenticateByToken, auth.AuthenticateBySession)` followed by `auth.RequiresRunRole(prc.Create)` [1](#0-0) .

When a request authenticates via EI credentials, `AuthenticateExternalInitiator` calls `store.FindExternalInitiator(ctx, eia)` (implemented by `orm.FindExternalInitiator`, which looks up strictly by `access_key`, with no job binding), validates the secret, and then sets `c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})` in addition to `c.Set(SessionExternalInitiatorKey, ei)` [2](#0-1) [3](#0-2) .

`RequiresRunRole` passes because the synthetic user's role is `UserRoleRun` [4](#0-3) .

Inside `PipelineRunsController.Create`, the code explicitly comments that only real users (not EIs) should be allowed to run jobs by integer ID:
```go
_, isUser := auth.GetAuthenticatedUser(c)
// only users are allowed to run jobs using int IDs - EIs not allowed
if isUser {
    ...
    jobRunID, err := prc.App.RunJobV2(ctx, jobID, nil)
    ...
}
``` [5](#0-4) 

But `GetAuthenticatedUser` simply reads the `SessionUserKey` from the gin context [6](#0-5)  — the same key that `AuthenticateExternalInitiator` populates. Because both real users and EIs populate this identical key, `isUser` evaluates to `true` for EI-authenticated requests, exactly the scenario the inline comment says should be excluded. This lets an EI credential holder call `prc.App.RunJobV2(ctx, jobID, nil)` for **any** integer job ID in the system — not just a job that references their external initiator via `external_initiator_webhook_specs`. There is no lookup or comparison anywhere in this path between the authenticated `ExternalInitiator` (available via `auth.GetAuthenticatedExternalInitiator(c)`) and the target job's bound initiator.

### Impact Explanation
An attacker holding only valid EI access-key/secret credentials (a low-privilege, narrowly-scoped credential intended to trigger only their own bound webhook job) can trigger pipeline runs for arbitrary jobs owned by other integrations/users by supplying that job's integer ID. This maps to Chainlink's "unauthorized job run triggering" impact class — it allows cross-tenant/cross-integration triggering of pipeline execution (e.g., forcing execution of bridge/HTTP tasks, consuming node resources, or triggering side effects tied to job execution) without any authorization relationship between the EI and the targeted job.

### Likelihood Explanation
Preconditions are minimal: attacker only needs one valid, unrevoked EI access key/secret (obtainable by any actor previously granted an EI credential, e.g., a partner integration) and knowledge or a guessable/enumerable integer job ID. No other role or session privilege is required. The request is a straightforward single HTTP call (`POST /v2/jobs/:ID/runs` with EI headers and an integer ID), fully repeatable, and does not require racing or timing.

### Recommendation
Fix `PipelineRunsController.Create` to check EI vs. user identity independent of the shared `SessionUserKey`. Concretely:
- Use `auth.GetAuthenticatedExternalInitiator(c)` to detect EI-authenticated requests and explicitly reject (or separately route) integer-ID job runs for EIs, since the comment already states EIs should not use this path.
- Alternatively, stop overloading `SessionUserKey` for external initiators; introduce a distinct authentication-kind marker (e.g., separate context key or an explicit `AuthKind` field) so `GetAuthenticatedUser` cannot be satisfied by EI authentication.
- If EI-triggered runs by job ID are meant to be supported, enforce a lookup verifying the target job's `external_initiator_webhook_specs` includes the authenticated EI before calling `RunJobV2`.

### Proof of Concept
Handler-level integration test:
1. Create two OCR/non-webhook jobs with integer IDs, `jobA` and `jobB`.
2. Create one External Initiator `ei1` via `POST /v2/external_initiators` (edit-role session), capturing its `AccessKey`/`Secret`.
3. Send `POST /v2/jobs/{jobB.ID}/runs` using only headers `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` set to `ei1`'s credentials (no session/token) — i.e., no binding exists between `ei1` and `jobB`.
4. Assert current (vulnerable) behavior: response is `200`/`201` with a created pipeline run (`prc.App.RunJobV2` executed for `jobB`), proving unauthorized cross-job triggering.
5. Expected behavior after fix: response should be `401 Unauthorized` (or `422`) because the EI has no relationship to `jobB`.
6. Add unit test for `PipelineRunsController.Create` mocking `auth.GetAuthenticatedExternalInitiator` to return `ok=true` and assert the integer-ID path is not taken for EI-authenticated contexts.

func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionExternalInitiatorKey, ei)

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

func (o *orm) FindExternalInitiator(ctx context.Context, eia *auth.Token) (*ExternalInitiator, error) {
