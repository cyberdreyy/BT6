### Title
Post-default instant withdraw receipts are written into the defaulted epoch's claim slot and paid from `defaultRecoveryReserve` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestInstantWithdraw` (IdleCreditVault.sol:356-375) is missing the `defaultRecoveryFinalized` handling that `requestWithdraw` has (lines 247-258). After a borrower default is finalized, a user can still open an instant-withdraw request. Because `epochNumber` no longer advances once the pool is defaulted/closed, the new receipt is recorded under `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` — the same slot that `_claimDefaultedInstantWithdrawRequest` (lines 842-856) treats as a defaulted-epoch receipt eligible for payment out of `defaultRecoveryReserve` at `defaultRecoveryPrice`. The attacker then calls `claimInstantWithdrawRequest` and is paid from the recovery reserve that was sized during finalization exclusively for pre-default claimants, diluting/stealing their recovery.

### Finding Description
The bug class in the external report is memory corruption (arbitrary state corruption). The closest analog in this codebase is corruption of per-epoch accounting state: writing a *new* receipt into a *finalized* epoch's storage slot.

- `requestWithdraw` explicitly branches on `defaultRecoveryFinalized` and routes post-default requests into `postDefaultRequests`, which are 1:1 backed by a freshly haircut amount and never touch the recovery-reserve entitlement of old claimants (lines 247-258).
- `requestInstantWithdraw` has no equivalent branch. It unconditionally executes `instantWithdrawsRequestsByEpoch[_user][epochNumber] += _amount` and `instantWithdrawClaimsByEpoch[epochNumber] += _amount` (lines 371-372).
- `epochNumber` is only incremented in `deposit()` when an epoch is running (lines 607-611). After default finalization no new epoch starts, so `epochNumber == defaultRecoveryEpoch` for any subsequent request.
- `claimInstantWithdrawRequest` (lines 380-393) first calls `_claimDefaultedInstantWithdrawRequest` whenever `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`. That function reads `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` — now including the post-default request — and pays `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` via `_transferDefaultRecovery`, which decrements `defaultRecoveryReserve` (lines 912-917). It also decrements `instantWithdrawClaimsByEpoch[defaultEpoch]`, so the manipulation is self-consistent and non-reverting.
- The reserve guard in `_transferFundedClaim` (lines 899-905) does not help: the payout goes through `_transferDefaultRecovery`, which is *designed* to spend the reserve — it just spends it on a receipt that was created after the reserve was sized.
- The normal withdraw path's `epochNumber <= lastWithdrawRequest` gating (line 326) and the `lossRecoveryPrice`/`_hasWithdrawRequest` guards in `requestWithdraw` do not cover the instant path, and there is no funding precondition inside `_claimDefaultedInstantWithdrawRequest` — the reserve itself is the funding.

Net effect: an attacker converts a post-default request (which should be unfunded or routed through `postDefaultRequests`-style accounting) into a claim on the already-finalized recovery reserve.

### Impact Explanation
Direct theft of the default recovery reserve. The reserve was sized at finalization to pay defaulted-epoch receipts at `defaultRecoveryPrice`. Every unit the attacker extracts via a post-default instant receipt is a unit unavailable to legitimate defaulted-epoch claimants (who will then revert on `defaultRecoveryReserve -= _amount` underflow or receive less). Attacker cost is only the haircut implicit in `defaultRecoveryPrice`; payout scales linearly with the tranche-token amount they hold or acquire post-default. Any KYC-passed tranche holder can execute this.

### Likelihood Explanation
Requires a defaulted-and-finalized vault (`defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`) plus the CDO still permitting `requestInstantWithdraw` post-default (the strategy enforces only `_onlyIdleCDO`; whether `IdleCDOEpochVariant.requestInstantWithdraw` reverts after default is the one path I could not fully trace in this pass — if the CDO blocks it, this vector is dead and the issue degrades to defense-in-depth). No privileged or honest-actor mistake is needed beyond the default finalization itself, which is a normal protocol flow.

### Recommendation
Mirror the `requestWithdraw` post-default branch in `requestInstantWithdraw`: after `defaultRecoveryFinalized`, either revert, or record the request in a post-default bucket keyed separately from `defaultRecoveryEpoch` (e.g., `postDefaultInstantRequests`) so it can never be paid by `_claimDefaultedInstantWithdrawRequest`/`_transferDefaultRecovery`. Additionally, have `_claimDefaultedInstantWithdrawRequest` snapshot/compare against `instantWithdrawClaimsByEpoch[defaultEpoch]` as finalized rather than trusting a slot that remains writable.
