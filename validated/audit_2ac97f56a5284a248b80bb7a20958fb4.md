### Title
Silent oldest-first eviction of pending webapi-trigger callbacks combined with unauthenticated, attacker-controlled `MessageId` reuse enables cross-user response hijacking - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
`handler.pruneCallbacks` evicts entries from `h.savedCallbacks` purely by age (oldest-first) once the map exceeds `MaxSavedCallbacks`, with no notion of ownership/importance, and `HandleLegacyUserMessage` inserts into that same map keyed solely by the fully attacker-controlled `msg.Body.MessageId` with no uniqueness/allowlist check (the code even has a `// TODO: apply allowlist and rate-limiting here` comment). An unprivileged caller can flood the map to force eviction of a victim's still-pending callback, and because `MessageId` is attacker-chosen and unauthenticated, an attacker can subsequently register a new callback under the same (now-evicted) `MessageId`; a late-arriving genuine node response for the victim's original request is matched purely by `MessageId` in `handleWebAPITriggerMessage`, so it gets delivered to whichever caller currently owns that map entry.

### Finding Description
`HandleLegacyUserMessage` accepts any signed `web_api_trigger` message and stores the caller's callback keyed by the message's own `MessageId`: [1](#0-0) [2](#0-1) 

There is no per-sender allowlist, no uniqueness check against existing entries, and no scoping of the map key by sender — the insert is a raw `h.savedCallbacks[msg.Body.MessageId] = &savedCallback{...}` overwrite. `MessageId` is fully caller-supplied, as shown in the reference invocation script and tests where it is a static/arbitrary string chosen by the client: [3](#0-2) 

`pruneCallbacks` runs periodically and, once `len(h.savedCallbacks) > MaxSavedCallbacks`, sorts strictly by `createdAt` and deletes the oldest half regardless of who owns them or whether they are close to expiry: [4](#0-3) 

When the real node eventually responds, `handleWebAPITriggerMessage` looks the entry up purely by `MessageId`: [5](#0-4) 

If the entry was silently evicted, the response is dropped with no error/notice to the victim (`found` is `false`, function returns `nil`). Worse, if an attacker re-registers a new callback under that same `MessageId` (trivial since `MessageId` is attacker-chosen and unchecked for collisions), and the victim's original in-flight node response arrives afterward, it will be matched to the *attacker's* callback entry and delivered to the attacker instead of the victim — because nothing ties the stored callback to the request's origin/sender beyond the bare string key.

### Impact Explanation
This is cross-user response confusion: an unprivileged, low-cost flood of the gateway's `web_api_trigger` endpoint can (a) silently drop a targeted victim's pending request/response mapping (denial of service on a specific user's in-flight call, which simply hangs until the client's own timeout), and (b) under `MessageId` reuse, cause the eventual genuine DON node response intended for the victim to be delivered to a different caller who registered the same ID afterward, leaking response content (which may include trigger/target payload data) to an unauthorized party.

### Likelihood Explanation
The precondition is only that an attacker can submit `MaxSavedCallbacks/2 + 1` (default `defaultMaxSavedCallbacks = 20000`, so ~10001) distinct, validly-signed `web_api_trigger` messages before the victim's response is delivered, which the code explicitly does not rate-limit or allowlist for this path (`// TODO: apply allowlist and rate-limiting here`). Any address that can produce an ECDSA signature can sign such messages — no privileged role or authentication beyond signature validity is required — making this reachable by any unprivileged external caller. Repeatability is high since `pruneCallbacks` runs on a fixed timer (`defaultCallbackPruneIntervalSec`), and exploiting the ID-reuse hijack only additionally requires guessing or choosing the same `MessageId` the victim used (feasible if IDs are predictable/low-entropy, or if the attacker targets any ID and waits for coincidental victim reuse in a busy queue).

### Recommendation
- Enforce sender-based allowlisting and rate limiting on `HandleLegacyUserMessage` as already flagged by the TODO, so unprivileged/unauthenticated flooding of `savedCallbacks` is not possible.
- Reject inserts into `savedCallbacks` for a `MessageId` that already has an active entry (return an error instead of silently overwriting) to prevent ID-collision hijacking.
- Namespace `savedCallbacks` keys by sender/DON member in addition to `MessageId` so a returned node response can only match a callback registered for the same originating request context.
- When `pruneCallbacks` evicts an entry, proactively notify the pending callback with an error response instead of dropping it silently, so callers fail fast rather than hang.

### Proof of Concept
Go unit test plan in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct a `handler` with `MaxSavedCallbacks` set to a small value (e.g., 10) for test speed.
2. Register a "victim" callback via `HandleLegacyUserMessage` with `MessageId = "victim-1"` at `t0`.
3. Register `MaxSavedCallbacks` attacker callbacks with distinct `MessageId`s at `t0+ε` each, exceeding the size threshold.
4. Call `h.pruneCallbacks()` directly and assert `h.savedCallbacks["victim-1"]` no longer exists (oldest-first eviction confirmed) while none of the victim's request context was ever notified of failure.
5. Register a new "attacker" callback reusing `MessageId = "victim-1"` via `HandleLegacyUserMessage`.
6. Simulate the delayed genuine node response for the victim's original request by calling `h.HandleNodeMessage` (or `handleWebAPITriggerMessage`) with `MessageId = "victim-1"` and a payload distinguishable as "victim's data".
7. Assert that the *attacker's* callback (registered in step 5) receives the victim's payload via `SendResponse`, confirming cross-user response delivery, and that the original victim callback never receives any response (dangling, silently dropped).

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}

	// If there are still too many callbacks, sort them by creation time and remove the oldest ones.
	maxSize := h.config.MaxSavedCallbacks
	var evicted int
	if len(h.savedCallbacks) > maxSize {
		type entry struct {
			id        string
			createdAt time.Time
		}
		entries := make([]entry, 0, len(h.savedCallbacks))
		for id, cb := range h.savedCallbacks {
			entries = append(entries, entry{id, cb.createdAt})
		}
		sort.Slice(entries, func(i, j int) bool {
			return entries[i].createdAt.Before(entries[j].createdAt)
		})
		// Trim to maxSize/2 to avoid sorting the list too frequently.
		for _, e := range entries[:len(entries)-maxSize/2] {
			delete(h.savedCallbacks, e.id)
			evicted++
		}
	}
