## Title
Client-supplied `message_id` allows cross-user callback hijacking in the WebAPI Gateway capabilities handler - (File: core/services/gateway/handlers/capabilities/handler.go)

## Summary
The External Report describes a MessageProcessor bug where anyone can capture and rebroadcast another user's signed message from the mempool to hijack the benefit intended for the honest sender (a reward payout), while the honest sender's own transaction reverts. The closest reachable analog in this chainlink codebase is not a "reward theft" but a structurally similar **request/response identity confusion**: the gateway's `HandleLegacyUserMessage` keys pending callbacks purely by the client-supplied `msg.Body.MessageId`, with no verification that the ID is bound to the sender, and unconditionally overwrites any existing entry for that ID.

## Finding Description
`HandleLegacyUserMessage` in [1](#0-0)  stores the caller's callback in a shared map keyed only by `msg.Body.MessageId`:
```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
```
`Message.Validate()` in [2](#0-1)  enforces only length/format constraints on `MessageId` (max length, no trailing null byte) — it never ties `MessageId` to the message's signer/sender. The signer is derived independently via `ExtractSigner()` and stored separately in `m.Body.Sender`.

When a node later responds, `handleWebAPITriggerMessage` looks the callback up again solely by `MessageId` and delivers the response to whichever callback is currently registered under that key [3](#0-2) :
```go
savedCb, found := h.savedCallbacks[msg.Body.MessageId]
delete(h.savedCallbacks, msg.Body.MessageId)
...
return savedCb.SendResponse(...)
```
Because the map write in `HandleLegacyUserMessage` is an unconditional overwrite (no check for an existing, still-pending entry, and no per-sender namespacing of the key), any unprivileged client that submits a request using the same `MessageId` as another in-flight, legitimate request will silently replace the original caller's callback. When the DON eventually responds to that `MessageId`, the response is delivered to the attacker's callback instead of the honest requester's — a cross-user response confusion / response-hijack primitive. Depending on what data the target request returns (compute/workflow output, trigger acknowledgement, etc.), this can leak response content intended for another user, or let an attacker silently swallow/redirect another user's request outcome, echoing the frontrunning report's theme of an unprivileged actor intercepting the benefit of someone else's pending, still-mempool-like (in-flight) request.

## Impact Explanation
An attacker who can predict or observe another client's `MessageId` (e.g., because IDs are deterministically derived, as seen in test helpers computing `MessageId` from a hash of `url + parts` [4](#0-3) , or because IDs are otherwise observable/guessable) can hijack the response channel for a legitimate, still-pending request. This is a request-impersonation / cross-user response confusion issue reachable from an unprivileged gateway client, matching the accepted bug classes in scope.

## Likelihood Explanation
Exploitation requires the attacker to send a request carrying an identical `MessageId` to a currently pending legitimate request before that request completes — a timing/guessing race, similar in spirit to the original report's requirement to observe and rebroadcast a mempool transaction before it lands. If `MessageId` generation is predictable in any client integration (as the hashing pattern in the codebase's own test helpers suggests is a plausible real-world pattern), the race is straightforward to win by simply submitting the crafted request slightly ahead of or concurrently with the legitimate one.

## Recommendation
Namespace `savedCallbacks` (and any equivalent pending-request maps) by both `Sender` and `MessageId`, or embed a server-verified, sender-bound component in the key (e.g., `sender + separator + MessageId`, similar to the `authorizedOwner + RequestIDSeparator + originalRequestID` pattern already used in the vault gateway's `authorizeAndStamp` [5](#0-4) ). Additionally, reject registration of a callback if an unexpired entry already exists for the same key instead of silently overwriting it.

## Proof of Concept
1. Legitimate user U sends a `web_api_trigger` request via `HandleLegacyUserMessage` with `MessageId = "X"`; the gateway stores U's callback under `savedCallbacks["X"]` and forwards the request to DON nodes.
2. Before the DON responds, attacker A sends their own request also using `MessageId = "X"` (predicted/observed/guessed). The gateway overwrites `savedCallbacks["X"]` with A's callback, discarding U's.
3. When a DON node later responds with `MessageId = "X"` (destined for U's original request), `handleWebAPITriggerMessage` delivers that response to A's callback instead, per [3](#0-2) .

Note: I could not fully verify how `MessageId` is generated/enforced unique on the production client paths that call `HandleLegacyUserMessage` (only test-helper ID generation was found in the indexed code), so the actual guessability/predictability of `MessageId` in a real deployment is unconfirmed and would need further investigation — a Devin session with full repository access could trace all production callers that construct `api.Message.Body.MessageId` to confirm whether IDs are attacker-predictable in practice.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}

func messageID(url string, parts ...string) string {
	h := sha256.New()
	h.Write([]byte(url))
	for _, p := range parts {
		h.Write([]byte(p))
	}
	hash := hex.EncodeToString(h.Sum(nil))
	p := []string{ghcapabilities.MethodWorkflowSyncer, hash}
	return strings.Join(p, "/")
}
