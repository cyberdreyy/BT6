### Title
Unprivileged user can permanently wedge a programmable-borrower vault by leaving an unfundable instant-withdraw request that blocks `startEpoch`/`stopEpoch` forever - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
The MariaDB bug is a lock (`lock_bigbuffer`) that is acquired but never released, producing a permanent deadlock. The closest analog in this codebase is the `pendingInstantWithdraws` "lock" on the epoch state machine: once a nonzero pending instant-withdraw balance exists while `isProgrammableBorrower` is set, every path that could clear it reverts, so the pool can neither stop the running epoch nor start a new one. The deadlock is permanent, is triggerable by any KYC-passed tranche holder, and freezes all LP funds in the vault.

### Finding Description
Two guards compose into a deadlock:

1. `IdleCDOEpochVariant._checkProgrammableBorrowerMode()` reverts whenever `isProgrammableBorrower && _pendingInstant() != 0`. It is called inside `_stopEpoch` (`contracts/IdleCDOEpochVariant.sol:106`, `:333`), so `stopEpoch`/`stopEpochWithDuration` revert while any instant-withdraw request is pending. The same check gates `startEpoch`.
2. `getInstantWithdrawFunds()` — the only routine that pulls borrower cash and clears `pendingInstantWithdraws` — reverts unconditionally when `isProgrammableBorrower` is true (`contracts/IdleCDOEpochVariant.sol:561`: `_checkNotAllowed(isProgrammableBorrower || ...)`).

So once `pendingInstantWithdraws > 0` coexists with `isProgrammableBorrower == true`, the state is unrecoverable: stop cannot run (check 1), the pending request cannot be funded (check 2), and no user-facing path decreases `pendingInstantWithdraws` (instant claims only succeed when `allowInstantWithdraw` is set, which requires a funded request). The test `testStartEpochRevertsInProgrammableModeWithPendingInstantWithdraws` (`test/foundry/IdleCreditVault.t.sol:845-866`) already demonstrates the permanent-revert half of this state; the only thing the harness does to escape it is `setIsProgrammableBorrower(false)` — an owner rescue, not a protocol path.

The trigger is an ordinary instant-withdraw request via `IdleCDOEpochVariant.requestWithdraw(0, tranche)`, which routes to `IdleCreditVault.requestInstantWithdraw` and burns the caller's strategy tokens into `instantWithdrawsRequests`/`pendingInstantWithdraws`. Whether the request path itself refuses to create an instant request while `isProgrammableBorrower` is set is the crux; from the code visible, the only programmable-mode gates are on the funding side (`getInstantWithdrawFunds`, `_checkProgrammableBorrowerMode`), not on request creation — consistent with the comment "Instant withdrawals are not supported when a programmable borrower is configured" being enforced at settlement, not at request time. (I was not able to fully trace `requestWithdraw`'s instant-branch gating before the iteration limit; if it does check `isProgrammableBorrower`, this finding collapses.)

An attacker can also reach the same state without relying on request-time gating: a user files an instant request in a normal epoch, and honest owner/manager later enables programmable mode (or the borrower is rotated to a programmable borrower) — but the clean attack is requesting during a programmable epoch if permitted.

### Impact Explanation
Permanent freezing of funds, not a temporary DoS. With `pendingInstantWithdraws` stuck nonzero:

- `stopEpoch` reverts forever → the running epoch can never close, normal withdraw requests filed for that epoch can never be funded, and `claimWithdrawRequest` stays blocked by the `epochNumber <= lastWithdrawRequest` check.
- `getInstantWithdrawFunds` reverts → the attacker's own request can never be filled, which is exactly why the lock can never be released.
- `startEpoch` reverts → no new epoch can begin.

Every LP's principal and all pending withdraw receipts in the vault are frozen indefinitely, absent owner intervention via `setIsProgrammableBorrower(false)` — and even that rescue does not fulfill the stuck instant request; it only re-opens the non-programmable funding path after the fact. Loss magnitude is the entire vault TVL (all deposited underlyings plus pending withdraw claims) for the duration the deadlock persists.

### Likelihood Explanation
High if the request path lacks a programmable-mode check: the cost to the attacker is one instant-withdraw request (their tranche tokens are burned into a claim that simply stays pending), executable by any KYC-passed tranche holder in a single transaction during the buffer or running phase. No privileged cooperation, no timing race, no capital at risk beyond the temporarily locked claim. If `requestWithdraw`/`requestInstantWithdraw` does check `isProgrammableBorrower`, likelihood drops to requiring an owner/manager mode toggle while a legacy instant request is pending — an operational edge case rather than an attacker primitive. This gating question is the one point I could not fully verify within the available search iterations.

### Recommendation
Add a symmetric guard at request creation: in `IdleCDOEpochVariant.requestWithdraw` (or `IdleCreditVault.requestInstantWithdraw`), revert when `isProgrammableBorrower` is true, mirroring the existing `_checkProgrammableBorrowerMode()` check. Additionally, consider a recovery path that lets pending instant requests be cancelled/refunded (re-mint strategy tokens) when programmable mode is enabled, so the mode flag can never strand the epoch state machine even via legacy or toggled-state requests.

### Proof of Concept
Foundry fork PoC sketch (programmable-borrower vault with minted interest, e.g. the `ProgrammableBorrowerCreditVault.t.sol` harness):

```solidity
// Setup: programmable borrower vault, isInterestMinted = true, isProgrammableBorrower = true
idleCDO.depositAA(10_000 * oneScale);        // attacker is a normal KYC'd LP
_startEpochAndCheckPrices(0);
vm.prank(manager);
cdoEpoch.stopEpoch(0, 0);                    // enter buffer with lower effective APR so instant path is live

// Attacker: file an instant withdraw request (amount = 0 triggers instant bucket)
cdoEpoch.requestWithdraw(0, address(AAtranche));
assertGt(IdleCreditVault(address(strategy)).pendingInstantWithdraws(), 0);

// Deadlock: every exit path reverts
vm.prank(manager);
vm.expectRevert(NotAllowed.selector);
cdoEpoch.getInstantWithdrawFunds();          // reverts: isProgrammableBorrower

vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager);
vm.expectRevert(NotAllowed.selector);
cdoEpoch.stopEpoch(0, 0);                    // reverts: _pendingInstant() != 0

vm.prank(manager);
vm.expectRevert(NotAllowed.selector);
cdoEpoch.startEpoch();                       // same guard

// All LP funds and pending claims frozen; only owner setIsProgrammableBorrower(false) rescues.
```

Caveat: this PoC assumes `requestWithdraw`'s instant branch does not check `isProgrammableBorrower`; that branch's exact gating is the single unverified step and should be confirmed first when reproducing.
