### Title
Unstaked balance withdrawal decrements ledger before confirming NEAR transfer succeeds - (File: staking-pool/src/internal.rs)

### Summary
`internal_withdraw` in the staking pool contract fires a native NEAR transfer `Promise` and immediately decrements the user's `unstaked` balance and the contract's `last_total_balance`, without any `.then()` callback to verify the transfer succeeded and roll back state on failure.

### Finding Description
`internal_withdraw` deducts `account.unstaked` and `self.last_total_balance` synchronously, then fires `Promise::new(account_id).transfer(amount)` with no attached callback: [1](#0-0) 

This is inconsistent with the rest of the codebase's pattern for cross-contract effects. Every other asynchronous state-changing operation in this contract family attaches a callback that checks `is_promise_success()` and reverts/records the outcome before finalizing state, e.g. the lockup's foundation withdrawal: [2](#0-1) 

and the owner-callback pattern used elsewhere in `lockup`, which rolls back state if `is_promise_success()` returns `false`: [3](#0-2) 

In `internal_withdraw`, if the outgoing `Promise::new(account_id).transfer(amount)` receipt fails for any reason on the receiving side (e.g., the account doesn't exist, is a non-existent implicit account, or the receipt otherwise fails asynchronously), the ledger entry (`account.unstaked`, `self.last_total_balance`) has already been permanently decremented with no recovery path. There is no `withdraw` callback such as `on_withdraw` anywhere in `staking-pool/src/lib.rs`.

### Impact Explanation
This breaks the "value debited versus value delivered" invariant: the contract's recorded unstaked/total balance is reduced even though the corresponding NEAR may never reach the recipient. Because `internal_withdraw` is also invoked from `withdraw` / `withdraw_all` — both callable by any unprivileged delegator — a user (or an attacker targeting another account's withdraw path indirectly through account state) could end up with funds effectively burned from the ledger without delivery, an accounting divergence where the contract's total balance no longer matches actual holdings. This falls under the High-impact category: "an accounting value diverging from reality where another party settles on it," since other accounts' shares and the pool's `last_total_balance` are computed against this now-incorrect total.

### Likelihood Explanation
The transfer itself is a native NEAR `Promise::new().transfer()`, which typically only fails in edge cases (e.g., malformed/implicit non-existent receiver, receipt-level failures) rather than "false-return" ERC20-style failures — so likelihood of triggering the failure is lower than the classic ERC20 unchecked-transfer bug class. However, unlike ERC20 `transfer`, NEAR's own promise execution is asynchronous and its failure is silently unhandled here, which is a deviation from the safe pattern used consistently elsewhere in this same codebase (`lockup`, `staking-pool-factory`, `lockup-factory` all use `is_promise_success()` callbacks for exactly this reason).

### Recommendation
Attach a callback to `Promise::new(account_id).transfer(amount)` in `internal_withdraw` (mirroring the `on_staking_pool_withdraw`/`on_withdraw_unvested_amount` patterns used in `lockup`) that checks `is_promise_success()` and restores `account.unstaked` and `self.last_total_balance` if the transfer promise failed, instead of decrementing state unconditionally before the transfer resolves.

### Proof of Concept
1. Delegator calls `withdraw_all()` / `withdraw(amount)` on `staking-pool`.
2. `internal_withdraw` immediately does `account.unstaked -= amount; self.internal_save_account(...); Promise::new(account_id).transfer(amount); self.last_total_balance -= amount;` — see [1](#0-0) .
3. If the transfer receipt subsequently fails (no callback exists to detect this), the pool's ledger (`account.unstaked`, `last_total_balance`) is permanently reduced while the delegator never received the NEAR — an unrecoverable state/asset mismatch, unlike the checked pattern used in `lockup/src/foundation.rs`'s `termination_withdraw` at [2](#0-1) .

    /// Called after the given amount was requested to transfer out from the staking pool to this
    /// account.
    /// This method needs to update staking pool status.
    pub fn on_staking_pool_withdraw(&mut self, amount: WrappedBalance) -> bool {
        assert_self();

        let withdraw_succeeded = is_promise_success();
        self.set_staking_pool_status(TransactionStatus::Idle);

        if withdraw_succeeded {
            {
                let staking_information = self.staking_information.as_mut().unwrap();
                // Due to staking rewards the deposit amount can become negative.
                staking_information.deposit_amount.0 = staking_information
                    .deposit_amount
                    .0
                    .saturating_sub(amount.0);
            }
            env::log(
                format!(
                    "The withdrawal of {} from @{} succeeded",
                    amount.0,
                    self.staking_information
                        .as_ref()
                        .unwrap()
                        .staking_pool_account_id
                )
                .as_bytes(),
            );
        } else {
            env::log(
                format!(
                    "The withdrawal of {} from @{} failed",
                    amount.0,
                    self.staking_information
                        .as_ref()
                        .unwrap()
                        .staking_pool_account_id
                )
                .as_bytes(),
            );
        }
        withdraw_succeeded
    }
