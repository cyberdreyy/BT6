### Title
Stale per-epoch instant-withdraw receipt lets `finalizeDefaultRecovery` count already-paid funds as reserve and enables double claims — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to the Axis bug (a balance already decremented per-claim is subtracted again, corrupting the payout/refund math), `IdleCreditVault.claimInstantWithdrawRequest` clears only the aggregate `instantWithdrawsRequests[_user]` but never clears `instantWithdrawsRequestsByEpoch[_user][epoch]` nor decrements `instantWithdrawClaimsByEpoch[epoch]` when a prefunded instant receipt is paid out pre-default. `defaultPendingClaimBasis` / `_defaultPrefundedInstantReserve` then treat already-paid claims and already-transferred cash as if still outstanding at `finalizeDefaultRecovery`, inflating `defaultRecoveryPrice` and `defaultRecoveryReserve`, and the stale per-epoch receipt is replayable through `_claimDefaultedInstantWithdrawRequest`. Result: recovery claims revert via underflow / reserve is drained by a double-claim — the same "claim proceeds" denial as the source report.

### Finding Description
In `claimInstantWithdrawRequest` the strategy burns the user's receipt and pays funded underlyings via `_transferFundedClaim`, but only zeroes the aggregate counter: [1](#0-0) . `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` (written at request time, line 371) and `instantWithdrawClaimsByEpoch[currentEpoch]` (line 372) are left untouched — they are only cleared inside `_claimDefaultedInstantWithdrawRequest`, which runs solely after finalization [2](#0-1) .

Consequences at `finalizeDefaultRecovery`:
- `defaultPendingClaimBasis` includes `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0`, so already-claimed receipts are counted in `totalBasis` again [3](#0-2) .
- `_defaultPrefundedInstantReserve` returns `instantBasis - pendingInstant` and this amount is folded into `reserveAmount` [4](#0-3) [5](#0-4) . For an already-claimed receipt, those underlyings left the contract — the reserve assumes cash that does not exist, inflating `recoveryPrice` for every claimant.
- After finalization, `claimInstantWithdrawRequest` routes through `_claimDefaultedInstantWithdrawRequest` when `defaultInstantWithdrawsFinalized` is set [6](#0-5) . The stale `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` is still non-zero, so the same receipt is paid a second time out of `defaultRecoveryReserve` via `_transferDefaultRecovery` (`defaultRecoveryReserve -= _amount`) [7](#0-6) .

Attack path (unprivileged lender): user requests an instant withdraw that is partially prefunded during `startEpoch`, claims the funded portion before default, borrower defaults, `finalizeDefaultRecovery` runs — the stale receipt both inflates the recovery price and remains claimable again.

### Impact Explanation
Two coupled losses: (1) `recoveryPrice` is computed over a `reserveAmount` that includes cash already paid out, so every defaulted receipt and active-LP NAV is over-priced and the reserve underflows — `defaultRecoveryReserve -= _amount` in `_transferDefaultRecovery` or the ERC20 `safeTransfer` reverts once claims exceed real cash, permanently freezing remaining claimants' recovery (the direct analog of `prefundingRefund` underflow blocking `claimProceeds`). (2) The user holding the stale per-epoch receipt can be paid twice: once pre-finalization via `_transferFundedClaim`, once post-finalization at `claimBasis * defaultRecoveryPrice`, directly stealing reserve earmarked for honest claimants. Loss is bounded by the prefunded instant-claim amount but can be the dominant share of the reserve when recovery is small.

### Likelihood Explanation
Requires a partially-prefunded instant queue entering the defaulted epoch (`pendingInstantWithdraws != 0` at finalization while `instantWithdrawClaimsByEpoch[epochNumber] > pendingInstantWithdraws`) — a documented, tested state (see `testFinalizeDefaultHaircutsPendingInstantRedeems`). The attacker is an ordinary KYC'd tranche holder performing only `requestWithdraw`/claim calls; all privileged actors behave honestly. Note the mixed-claim path partially mitigates the simplest variant because `instantWithdrawsRequests[_user] -= claimBasis` can underflow when the aggregate was already zeroed — but a second instant request in a later epoch (or claiming only part) restores a non-zero aggregate and makes the double-claim succeed; independently, the reserve inflation alone is enough to break finalization payouts.

### Recommendation
In `claimInstantWithdrawRequest`, clear per-epoch bookkeeping exactly like `_claimDefaultedInstantWithdrawRequest` does: decrement `instantWithdrawsRequestsByEpoch[_user][epoch]`, `instantWithdrawClaimsByEpoch[epoch]`, and reconcile `pendingInstantWithdraws` for every epoch whose receipt is being paid (or iterate/record the claimed epoch at request time). Alternatively, compute `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` from only still-unclaimed receipts (e.g., subtract already-claimed amounts from `instantWithdrawClaimsByEpoch`) so prefunded-but-paid cash is never counted in `reserveAmount` or `totalBasis`.

### Proof of Concept
Foundry fork sketch (mirroring `test/foundry/IdleCreditVault.t.sol` around `testFinalizeDefaultHaircutsPendingInstantRedeems`, lines 4435-4470):

```solidity
// setup: deposit as instantUser, enable instant withdraws
_startEpochAndCheckPrices(0);
_stopEpochAndCheckPrices(0, apr, fundsEnd);

// user requests instant withdraw; only partially funded at startEpoch
vm.prank(instantUser);
uint256 instantClaimBasis = cdoEpoch.requestWithdraw(0, address(AAtranche));

_startEpochAndCheckPrices(1);
uint256 pendingInstant = creditVault.pendingInstantWithdraws();
uint256 prefunded = instantClaimBasis - pendingInstant; // > 0

// fund the remainder, then CLAIM BEFORE default finalization
vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
vm.prank(manager);
cdoEpoch.getInstantWithdrawFunds(); // may default here; arrange partial so claim succeeds
vm.prank(instantUser);
cdoEpoch.claimInstantWithdrawRequest();
// instantWithdrawsRequestsByEpoch[instantUser][epochNumber] is STILL non-zero

// borrower defaults and finalizeDefaultRecovery runs
_checkDefault();
cdoEpoch.finalizeDefault(recovered, manager);

// 1) defaultRecoveryPrice inflated: reserve counted prefunded cash that already left
// 2) stale receipt payable again:
vm.prank(instantUser);
cdoEpoch.claimInstantWithdrawRequest(); // pays claimBasis * recoveryPrice a 2nd time,
// or reverts on `instantWithdrawsRequests[_user] -= claimBasis` / reserve underflow,
// freezing all remaining recovery claims
```

Assert `creditVault.instantWithdrawsRequestsByEpoch(instantUser, epoch) != 0` after the pre-finalization claim, and `defaultRecoveryReserve` > `underlying.balanceOf(strategy)` post-finalization as the broken solvency invariant.

```text
  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```
