### Title
Instant-withdraw receipts from a pre-default epoch escape the default recovery haircut and are paid at par, draining funds reserved for other claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`defaultPendingClaimBasis()` only counts instant-withdraw claims recorded under the *current* `epochNumber` (`instantWithdrawClaimsByEpoch[epochNumber]`). Instant receipts requested in an earlier epoch that were never funded are therefore excluded from the default recovery basis, but `claimInstantWithdrawRequest()` still pays them out 1:1 through `_transferFundedClaim`. The result is a shape-confusion analog of the capnp list-downgrade bug: an epoch-keyed receipt set is read under the wrong epoch shape at finalization, so old unfunded instant receipts are treated as fully funded and overpay their holders at the expense of everyone else's funded claims.

### Finding Description
When a user calls `requestInstantWithdraw`, the receipt is recorded per epoch in `instantWithdrawsRequestsByEpoch[user][currentEpoch]` and `instantWithdrawClaimsByEpoch[currentEpoch]`, and the global `pendingInstantWithdraws` is increased ( [1](#0-0) ). `collectInstantWithdrawFunds` only decrements the global `pendingInstantWithdraws`; it never clears `instantWithdrawClaimsByEpoch` for past epochs ( [2](#0-1) ).

At default finalization, `finalizeDefaultRecovery` builds the recovery basis from `defaultPendingClaimBasis()`, which adds only `instantWithdrawClaimsByEpoch[epochNumber]` — the current epoch — and only when `pendingInstantWithdraws != 0` ( [3](#0-2) ). An instant receipt from an older epoch that remains unfunded contributes zero basis, zero haircut, and gets no reserve allocation.

After finalization, `claimInstantWithdrawRequest` clears only the `defaultRecoveryEpoch` entry via `_claimDefaultedInstantWithdrawRequest` ( [4](#0-3) ), then pays the entire remaining `instantWithdrawsRequests[user]` at par via `_transferFundedClaim` ( [5](#0-4) ). `_transferFundedClaim` only protects `defaultRecoveryReserve` ( [6](#0-5) ), so the old receipt is paid from the strategy's other underlying — the pool backing funded normal/APR0 withdraw receipts collected via `collectWithdrawFunds` ( [7](#0-6) ).

### Impact Explanation
An attacker holding an unfunded instant-withdraw receipt from epoch N−k claims it at full par after default finalization, while all defaulted-epoch claimants and active LPs absorb the recovery haircut. The payout is sourced from underlying held for funded withdraw receipts, so honest claimants' later `claimWithdrawRequest` calls revert or underpay — direct theft and insolvency of the funded-claims pool. Loss equals the attacker's unfunded instant basis, bounded only by how large an instant request they could open pre-default (a KYC-passing lender/tranche holder is a valid attacker).

### Likelihood Explanation
Requires: (1) a user opens an instant withdraw in epoch E, it stays unfunded or partially funded (the CDO only funds instant claims when the APR drops below the configured delta, so unfunded remainder is normal operation); (2) `epochNumber` advances past E via a later `stopEpoch`; (3) the borrower defaults and `finalizeDefault`/`finalizeDefaultRecovery` runs while `pendingInstantWithdraws != 0`. Each step is reachable through honest-privileged sequencing and unprivileged user actions; no privileged misbehavior needed. The guard structure explicitly acknowledges unfunded instant receipts exist across epochs but only indexes the current epoch for the recovery basis.

### Recommendation
In `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()`, aggregate `instantWithdrawClaimsByEpoch` across all epochs with unfunded receipts (or track a separate aggregate `instantWithdrawClaimsTotal`), and in `_claimDefaultedInstantWithdrawRequest` clear every per-epoch entry contributing to `instantWithdrawsRequests[user]`, not just `defaultRecoveryEpoch`. Alternatively, force old instant receipts through the recovery price when `defaultRecoveryFinalized` instead of paying them via `_transferFundedClaim`.

### Proof of Concept
Foundry fork PoC sketch (standard `IdleCDOEpochVariant` + `IdleCreditVault`, instant withdrawals enabled via `setInstantWithdrawParams`):

```solidity
// setup: users deposit, epoch 1 running with instant withdraws enabled
// attacker (KYC'd lender) holds tranches
uint256 tr = _depositWithUser(attacker, 100e6);

// epoch 1: attacker requests instant withdraw; keep it unfunded
// (apr stays above minAprDelta so processWithdrawalClaims never runs,
//  or only partially funds the instant bucket)
cdoEpoch.requestInstantWithdraw(tr);          // instantWithdrawsRequestsByEpoch[attacker][1] = X

// epoch rolls: stopEpoch bumps epochNumber to 2, startEpoch
_stopCurrentEpoch(); cdoEpoch.startEpoch();
// attacker's instant receipt stays in epoch-1 bucket; epochNumber now 2

// borrower defaults; manager/orchestrator runs default flow
cdoEpoch._handleBorrowerDefault();            // defaulted() = true
strategy.finalizeDefaultRecovery(recovered, source);
// defaultPendingClaimBasis() adds only instantWithdrawClaimsByEpoch[2]
// -> attacker's epoch-1 instant receipt excluded from basis & haircut

// funded normal withdraw claims of honest users sit in strategy underlying
uint256 pre = underlying.balanceOf(attacker);
cdoEpoch.claimInstantWithdrawRequest(attacker);
// _claimDefaultedInstantWithdrawRequest clears epoch-2 entry only (0 for attacker)
// then _transferFundedClaim pays full X at par from funded-claims pool
assertGt(underlying.balanceOf(attacker) - pre, 0);
// honest user's claimWithdrawRequest later reverts/underpays by X
```

Key assertion: `strategy.instantWithdrawClaimsByEpoch(1) > 0` after `finalizeDefaultRecovery`, while `defaultRecoveryEpoch == 2`, proving the epoch-1 instant basis was omitted from `totalBasis` yet still payable at par.

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```
