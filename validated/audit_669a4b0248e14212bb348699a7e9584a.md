### Title
`BlockRejection` signature only binds `signer_signature_hash`, allowing the reject reason/metadata to be forged under a valid signer signature - ([File: libsigner/src/v0/messages.rs])

### Summary
`BlockRejection::hash()` computes the signed digest over **only** `self.signer_signature_hash` (the block being rejected), while `reason`, `reason_code`, and the entire `response_data` (`BlockResponseData`, which carries `reject_reason`, `failed_txid`, `tenure_extend_timestamp`, `read_count_extend_timestamp`) are left outside the signed payload. Any relayer/gossip participant that has a legitimately-signed `BlockRejection` for a given `signer_signature_hash` from any signer can splice in a different `reason_code`/`response_data.reject_reason`/`failed_txid` and the ECDSA signature will still verify, because the check is only against `signer_signature_hash`.

### Finding Description
`BlockRejection::hash()` is:
```rust
pub fn hash(&self) -> Sha256Sum {
    let domain_tuple = make_structured_data_domain("block-rejection", "1.0.0", self.chain_id);
    let data = Value::buff_from(self.signer_signature_hash.as_bytes().into()).unwrap();
    structured_data_message_hash(data, domain_tuple)
}
``` [1](#0-0) 

`sign()`/`verify()`/`recover_public_key()` all operate over this same hash, which is a function of `chain_id` and `signer_signature_hash` alone: [2](#0-1) 

Meanwhile the struct also carries `reason`, `reason_code`, and `response_data: BlockResponseData` (containing `reject_reason`, `failed_txid`, and the two extend timestamps) that are *not* part of the signed digest. This is unlike `BlockAccepted`-style signatures, which sign over the full block header hash used to determine consensus; here the auxiliary decision-relevant fields ride unauthenticated alongside a valid signature.

Downstream, `handle_block_rejection` in the signer trusts `rejection.response_data.reject_reason` directly to update local state and tallies:
```rust

    sortition_state,
    &mut block_info,
    &signer_address,
    (&rejection.response_data.reject_reason).into(),
);
``` [3](#0-2) 

and for unseen blocks the pending-rejection path stores this same unauthenticated field:
```rust

    block_hash,
    &signer_address,

On the node side, `stackerdb_listener.rs` also consumes `rejected_data.reason_code`/`response_data.failed_txid` to accumulate per-txid rejection weight (`total_weight`/`problematic_weight`) used to temporarily or **permanently exclude transactions** from block templates: [5](#0-4) [6](#0-5) 

Because none of `reason_code`, `response_data.reject_reason`, or `failed_txid` are covered by the signature, a single relaying party (a miner or any StackerDB reader/writer with access to a signer's already-broadcast rejection chunk) can re-serialize the message with a different `reason_code`/`failed_txid`/`response_data` while keeping the original valid `signature` and `signer_signature_hash` — the receiver-side `verify()`/`recover_public_key()` checks still pass, because they recompute the same hash from the (now-tampered) `signer_signature_hash`+`chain_id`, which were left unchanged.

### Impact Explanation
This lets a one-slot actor (miner or relayer) forge a *different rejection reason* for a real, valid signer rejection signature. Concretely:
- It can flip a benign rejection reason into `RejectCode::ValidationFailed(ValidateRejectCode::ProblematicTransaction)` for an arbitrary `failed_txid`, causing that transaction to accumulate "problematic" weight toward the `blocking_minority` threshold that permanently excludes it from block templates (`signer_coordinator.rs`), effectively censoring a transaction using someone else's genuine signature without their consent.
- It can alter `response_data`'s `tenure_extend_timestamp`/`read_count_extend_timestamp`, which feed `update_idle_timestamp`/`update_read_count_timestamp` in the miner-activity tracking on the node side, letting an attacker distort the node's model of signer liveness/idle-state using a signature the signer never actually attached to that data.
- Within `stacks-signer`, it can change which `RejectReason` a peer is recorded as having voted, which feeds `compute_reject_code_signing_weight` and the `RejectReasonPrefix`-keyed weight bookkeeping used to decide "does a reason-specific reject weight make the threshold impossible" — effectively letting an attacker miscategorize a legitimate rejection under a reason bucket the real signer never intended, corrupting per-reason tallying used in the signer's/coordinator's decisions.

This does not itself flip a Reject into a counted Accept (the top-level `signer_signature_hash`/weight-approved counters are untouched), so it falls short of "signature signing an invalid block" or "rejection recounted as acceptance." It is best characterized as a metadata-forgery/miscount of the *reason* attached to a genuine signature, which is a real integrity gap analogous to the CVE's "the thing that should be authenticated by the crypto isn't fully authenticated," but the concrete safety/liveness break required by the rules (an equality broken between "signed vs validated," "one-per-height," "approved-parent vs canonical," "aggregated-weight vs verified-accepts", or a full state-machine wedge) is not clearly demonstrated — the core Accept/Reject weight tallies used for consensus (`total_weight_approved`, `total_weight_rejected`) are computed from fields (`signer_signature_hash`, and the accept/reject *kind* itself, which is structurally the enum variant, not signed content) that remain intact under this manipulation.

### Likelihood Explanation
Requires only that the attacker can observe/relay one signer's already-published `BlockRejection` StackerDB chunk (trivial, since these are broadcast in the clear on StackerDB) and re-post a modified message on their own slot; no majority or private key compromise needed. However, the ability to make the *node* accept the tampered version depends on `signer_coordinator.rs`/`stackerdb_listener.rs`'s per-slot pubkey/slot binding — I was not able to fully trace whether the node's slot-ownership check (`signer_pubkey`/`slot_id`) would reject a resubmission of another signer's rejection payload under a different slot, which is a prerequisite for the txid-exclusion and idle-timestamp impacts described above. This limits confidence that the exploit is practically reachable end-to-end versus being confined to the local signer's own already-authenticated rejection re-interpretation.

### Recommendation
Include `reason_code`, `response_data` (or at minimum `reject_reason` and `failed_txid`), and any other decision-relevant fields inside the `structured_data_message_hash` computed by `BlockRejection::hash()`, so that the signature authenticates the full semantic content of the rejection, not just the rejected block's hash and chain id.

### Proof of Concept
Conceptual (not fully verified against slot-ownership enforcement on the node path):
1. Signer A broadcasts a valid `BlockRejection` for block `H` with `reason_code = RejectReason::SortitionViewMismatch` and `response_data.failed_txid = None`, signed with A's key over `hash() = domain("block-rejection") || H`.
2. An attacker observes this chunk, constructs a new `BlockRejection` with the same `signer_signature_hash = H`, same `chain_id`, but `reason_code = RejectCode::ValidationFailed(ValidateRejectCode::ProblematicTransaction)` and `response_data.failed_txid = Some(target_txid)`, copying A's original `signature` field unchanged.
3. `BlockRejection::verify()`/`recover_public_key()` on the receiving signer/node recompute `hash()` from `signer_signature_hash` and `chain_id` (unchanged), so verification succeeds and the message is attributed to A.
4. Receivers process the forged `reason_code`/`failed_txid` as if A genuinely reported `target_txid` as a problematic transaction, feeding `compute_reject_code_signing_weight` (stacks-signer) and `failed_txids` weight accumulation (signer_coordinator.rs) under A's identity though A never made that claim.

    /// Sign the block rejection and set the internal signature field
    fn sign(&mut self, private_key: &StacksPrivateKey) -> Result<(), String> {
        let signature_hash = self.hash();
        self.signature = private_key.sign(signature_hash.as_bytes())?;
        Ok(())
    }

    /// Verify the rejection's signature against the provided signer public key
    pub fn verify(&self, public_key: &StacksPublicKey) -> Result<bool, String> {
        if self.signature == MessageSignature::empty() {
            return Ok(false);
        }
        let signature_hash = self.hash();
        public_key
            .verify(&signature_hash.0, &self.signature)
            .map_err(|e| e.to_string())
    }

    /// Recover the public key from the rejection signature
    pub fn recover_public_key(&self) -> Result<StacksPublicKey, &'static str> {
        if self.signature == MessageSignature::empty() {
            return Err("No signature to recover public key from");
        }
        let signature_hash = self.hash();
        StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            signature_hash.as_bytes(),
            &self.signature,
        )
    }
}
