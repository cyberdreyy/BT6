### Title
Deleted multisig members' stale confirmations remain counted toward `num_confirmations`, allowing requests to execute below the live-member threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` in `multisig2/src/lib.rs` only purges outstanding requests that were *originated* by the removed member, but never scans the `confirmations` set of other still-open requests to strip that member's existing confirmation entries. Because `confirm()` counts confirmations purely by set size against the fixed `num_confirmations`, a confirmation cast by a member before their removal continues to count after removal, letting a request execute with fewer *currently live* confirming members than the configured threshold requires.

### Finding Description
`add_request`/`confirm` store confirmations in a `HashSet<String>` keyed by member identity, and a request executes once `confirmations.len() + 1 >= self.num_confirmations`: [1](#0-0) 

`delete_member` is the only place that cleans confirmation state on membership change, and it filters requests strictly by the removed member being the request's *originator* (`r.member == member`), removing that request's confirmations wholesale — it never inspects or trims confirmations that the removed member cast on requests originated by *other* members: [2](#0-1) 

This breaks the intended binding: "confirmations counted" should equal "confirmations from currently-live members." Concretely:
1. Members A, B, C exist, `num_confirmations = 2`.
2. A calls `add_request` (request R, unconfirmed).
3. B calls `confirm(R)` → `confirmations = {B}` (1 < 2, stored, not yet executed).
4. Members later execute a `DeleteMember { member: B }` request (via a separate, properly-confirmed multisig request) removing B. `delete_member` checks `requests` for entries where `r.member == B` — R was added by A, so it is untouched; R's confirmation set still contains B.
5. C calls `confirm(R)`. `confirmations.len() (1, containing dead member B) + 1 (C) = 2 >= num_confirmations (2)` → R executes.

R is executed on the strength of one live confirmation (C) plus one phantom confirmation from a member who no longer has any authority over the account, i.e., the request is authorized below the actual live-member threshold the operator configured.

The same pattern exists in the legacy `multisig/src/lib.rs` contract, where `DeleteKey` only removes requests whose `signer_pk == pk` and likewise never scans other requests' confirmation sets for stale entries from the deleted key: [3](#0-2) 

### Impact Explanation
This directly matches the in-scope Critical impact category "a multisig request executed below threshold." Any pending request that a removed member had previously confirmed can later be pushed to execution using that member's stale confirmation, letting `Transfer`, `FunctionCall`, `AddKey`/`AddMember`, or `DeployContract` actions execute with fewer genuinely-authorized approvals than `num_confirmations` mandates — moving NEAR or granting access rights the remaining live members did not fully authorize.

### Likelihood Explanation
No privileged role is required beyond ordinary multisig membership dynamics that already occur in normal operation (member rotation via `DeleteMember`/`DeleteKey`, which is a documented, expected action). Any pending, unconfirmed-but-partially-confirmed request combined with a subsequent, unrelated member removal is sufficient — no attacker needs to control the removed member's key, only to time a final confirming call after the removal. This can also be triggered opportunistically by any remaining member who confirms last.

### Recommendation
When `delete_member` (or `DeleteKey` in `multisig/src/lib.rs`) removes a member, iterate all entries in `self.confirmations` (not just requests originated by that member) and remove the deleted member's identity from every confirmation set, re-persisting the trimmed sets. Alternatively, validate at `confirm()`-execution time that every account/key in a request's confirmation set is still a current member before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `[A, B, C]`, `num_confirmations = 2`.
2. `A.add_request(request_R)` → unconfirmed.
3. `B.confirm(request_R)` → stored, `confirmations = {B}` (see `multisig2/src/lib.rs:292-315`).
4. Separately get a properly-confirmed `DeleteMember { member: B }` request executed (e.g., A and C confirm it) → `delete_member` runs; since `request_R.member == A`, `request_R`'s confirmations are left untouched (see `multisig2/src/lib.rs:356-379`).
5. `C.confirm(request_R)` → `confirmations.len() (1) + 1 (C) = 2 >= num_confirmations (2)` → `request_R` executes, backed by only one live member (C) plus a phantom confirmation from removed member B.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
