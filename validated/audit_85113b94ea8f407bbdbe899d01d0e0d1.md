Based on my review of the reorg-timing check in `stacks-signer/src/chainstate/mod.rs`, I found a fail-open logic flaw that maps to the report's bug class (a check meant to gate an "equality"/timing invariant can be forced onto its permissive branch by a value the signer itself cannot verify, defeating the very protection it is supposed to enforce).### Title
Reorg-timing guard fails open when a signer has no local `approved_time` for the reorged tenure's block, letting a malicious next-tenure miner bypass the anti-reorg timing check - (File: stacks-signer/src/chainstate/mod.rs)

### Summary
`SortitionData::check_parent_tenure_choice` (stacks-signer/src/chainstate/mod.rs) is the analog of the sandwich report's "price band" gate: it is the check that is supposed to bound how far a miner can deviate from the expected/canonical state (here: reorging a tenure that already produced a block) before the signer refuses. Just as the SpotHedgeBaseMaker's price-band check could be defeated by manipulating which price value the check observed, this guard can be forced onto its permissive branch by manipulating which *local* value (`approved_time`) the signer has recorded, rather than the real-world timing the check is supposed to measure.

### Finding Description
When a miner's sortition does not build off the prior sortition, the signer must decide whether the reorg of the earlier tenure is legitimate ("the old tenure's first block was proposed right at the burn-block transition, a genuine race") or malicious (an attempt to discard an already-mined tenure). This is gated by `first_proposal_burn_block_timing` in: [1](#0-0) 

The intended measurement is `sortition_state_received_time - local_block_info.approved_time`, i.e., how close (in real wall-clock terms) the old tenure's first-block proposal was to the new burn block. But when `local_block_info.approved_time` is `None`, the code substitutes `0`:
```
} else {
    info!("We did not sign over the reorged tenure's first block, considering it as a late-arriving proposal");
    0
};
if Duration::from_secs(proposal_to_sortition) < *first_proposal_burn_block_timing {
    ...
    superseded_tenures.push(tenure);
    continue;
}
```
`proposal_to_sortition = 0` is always `< first_proposal_burn_block_timing`, i.e., it *always* lands on the permissive ("this looks like a legitimate race, allow reorg") branch. This is the same pattern as the sandwich bug: the check is supposed to bound a real external quantity (elapsed time, analogous to real exchange price), but when that quantity is unknown to the checker, the code substitutes a value that trivially satisfies the "safe" condition instead of failing closed. `approved_time` is stamped only when *this specific signer* pre-committed to or locally accepted the earlier block (`docs/signer-flows.md:156-158`, `mark_pre_committed`/`mark_locally_accepted` in `signerdb.rs`), so any signer that:
- restarted/wiped its `signerdb` after having validated the earlier tenure's block but before another proposal for that tenure arrives, or
- never received/validated that specific proposal (e.g., it was gossip-starved or joined the signer set/reward cycle after that tenure began), or
- was simply behind in processing when the competing proposal was submitted,

will have `local_block_info.approved_time == None` and will unconditionally treat the reorg attempt as legitimate, regardless of how long the earlier tenure's block had actually been standing. This defeats the entire purpose of `first_proposal_burn_block_timing`, which exists specifically to stop a miner from reorging a tenure that already produced a block outside of a genuine race window.

This directly maps to the rules' High-impact category: **"losing the equivocation guard on restart"** - the guard silently reverts to "always permit" for exactly the signers whose local state doesn't contain the timestamp, which is the common case after a signerdb wipe/restart or gossip gap, not an exotic edge case.

### Impact Explanation
`check_parent_tenure_choice` is called from both the v1 (`SortitionsView::check_proposal`) and v2 (`GlobalStateView::check_proposal` via `validate_tenure_change_payload`) proposal-evaluation paths, and its `Ok(false)` result is what turns into `RejectReason::ReorgNotAllowed`. A signer that hits the fail-open branch will instead return `Ok(true)`, i.e., it treats a non-canonical/illegitimate reorg proposal as valid and proceeds to validate and potentially sign it - a signer contributing its weight toward signing a block that reorgs an already-produced tenure block without the timing guarantee the protocol relies on to distinguish a legitimate race from an attack. For any single such signer this is a loss of its personal equivocation/anti-reorg guard (matching the High bucket verbatim: "losing the equivocation guard on restart"). If this state (missing `approved_time`) is shared by a large-enough weighted subset of signers at once (e.g., a coordinated restart, upgrade rollout, or a miner that deliberately gossips the vulnerable tenure's first proposal only to a subset of signers so the rest never locally validate it), the same bypass could contribute toward the 70% signing threshold and let an actually-malicious reorg (of a globally accepted, single-block tenure) get signed - a signer signing a non-canonical/conflicting block, which is the Critical bucket. The severity is therefore restart/gossip-dependent: at minimum it is a per-signer High (loss of the reorg guard on restart), and it escalates toward Critical if the affected weight is large enough to matter for consensus.

### Likelihood Explanation
This does not require compromising a majority of signers or their keys - it is triggered purely by ordinary signer lifecycle events (restart, DB reset, catching up, late join) combined with a miner that proposes a tenure reorg. Signer restarts/upgrades and gossip delays are routine operational events in this system, and the code path itself acknowledges the scenario is expected ("We did not sign over the reorged tenure's first block, considering it as a late-arriving proposal") - it is not a theoretical corner case but a deliberately handled branch whose chosen default is unsafe. A one-slot miner only needs to attempt a reorg while some signers are in this state; it can also actively increase the likelihood by controlling gossip timing to a subset of signers to induce `approved_time == None` for them specifically.

### Recommendation
Do not default the "unknown local timing" case to the permissive branch. When `local_block_info.approved_time` is `None`, the signer should either:
- fail closed (treat the reorg as *not* proven-safe and require corroboration from the node's own record of when the tenure/block was first seen, e.g., using `get_burn_block_receive_time`/burn-block-observed timestamps rather than a per-signer local field), or
- explicitly query the node for the tenure/proposal's original observed time instead of substituting `0`.
In general, any branch of `check_parent_tenure_choice` that cannot determine the real elapsed time should resolve to "disallow reorg" (mirroring how `conflict_still_blocks` and other node-query failures in the same file consistently fail closed toward "keep blocking"/"treat as unsafe") rather than resolve to the value that happens to always satisfy the permissive threshold comparison.

### Proof of Concept
