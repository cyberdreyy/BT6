### Title
Incomplete Signature Iteration in `validate_proof` Causes Multi-Signer Bridge Proof Validation to Always Abort — (`File: crates/sui-axelar-cgp/move/sources/validators.move`)

---

### Summary

The `validate_proof` function in the Axelar CGP bridge module declares its outer loop counter `i` as **immutable**, so the loop never advances past `signatures[0]`. Any bridge proof requiring more than one signer to meet the weight threshold will abort with an out-of-bounds vector access, permanently blocking multi-signer cross-chain message delivery.

---

### Finding Description

In `validate_proof`, the loop variables are declared as:

```move
let (i, mut weight, mut operator_index) = (0, 0, 0);
``` [1](#0-0) 

`i` has no `mut` qualifier. The outer while loop condition `while (i < total_signatures)` is evaluated with `i` permanently fixed at `0`. The loop body borrows `signatures[i]` — always index 0 — and never increments `i`:

```move
while (i < total_signatures) {
    let mut signature = *vector::borrow(&signatures, i);   // always index 0
    normalize_signature(&mut signature);
    let signed_by = ecdsa::secp256k1_ecrecover(&signature, &approval_hash, 0);
    while (operator_index < operators_length && &signed_by != vector::borrow(&operators, operator_index)) {
        operator_index = operator_index + 1;
    };
    // assert!(operator_index == operators_length, 0); // commented out
    weight = weight + *vector::borrow(&weights, operator_index);
    if (weight >= threshold) { return true };
    operator_index = operator_index + 1;
};
abort ELowSignaturesWeight
``` [2](#0-1) 

**Execution trace for a two-signer proof (threshold not met by one signer):**

- **Iteration 1** (`i=0`): recovers signer of `signatures[0]`, finds it at `operator_index = X`, adds `weights[X]`. Weight < threshold → `operator_index = X+1`.
- **Iteration 2** (`i=0` still): recovers the same signer of `signatures[0]` again. The inner loop starts at `X+1` and scans forward; the signer is at `X < X+1`, so the inner loop runs to `operator_index = operators_length`. The commented-out guard is absent, so execution falls through to `vector::borrow(&weights, operators_length)` → **out-of-bounds abort**.

The function either returns `true` (single signer meets threshold) or aborts (multiple signers needed). It can never accumulate weight across multiple distinct signers.

The public entry point that triggers this path is `process_commands` in `gateway.move`:

```move
entry fun process_commands(validators: &mut AxelarValidators, input: vector<u8>) {
    ...
    let mut allow_operatorship_transfer = validate_proof(validators, to_sui_signed(*&data), proof);
``` [3](#0-2) 

Any ordinary user can call `process_commands` with a valid multi-signer proof and the transaction will always abort.

The existing tests only exercise a **single-operator** committee, which is why the bug was not caught:

```move
let operators = vector[
    x"037286a4f1177bea06c8e15cf6ec3df0b7747a01ac2329ca2999dfd74eff599028"
];
``` [4](#0-3) 

---

### Impact Explanation

If the Axelar CGP bridge is deployed with a multi-signer operator set (the normal production configuration), **no cross-chain message that requires more than one operator's weight to reach the threshold can ever be processed**. Assets locked on the source chain waiting for a bridge approval that can never be validated are permanently inaccessible. This matches the bounty's **High/Medium** impact class of "permanent fund lock" and "harmful smart-contract behavior."

---

### Likelihood Explanation

The bug is triggered by any caller submitting a valid multi-signer proof to `process_commands`. No special privilege is required — it is a public `entry` function on a shared object. The only condition is that the deployed operator set requires more than one signature to reach the threshold, which is the standard security configuration for any production bridge.

---

### Recommendation

Declare `i` as mutable and increment it at the end of each outer loop iteration:

```move
// Before (broken):
let (i, mut weight, mut operator_index) = (0, 0, 0);

// After (fixed):
let (mut i, mut weight, mut operator_index) = (0, 0, 0);

while (i < total_signatures) {
    let mut signature = *vector::borrow(&signatures, i);
    normalize_signature(&mut signature);
    let signed_by = ecdsa::secp256k1_ecrecover(&signature, &approval_hash, 0);
    while (operator_index < operators_length
        && &signed_by != vector::borrow(&operators, operator_index)) {
        operator_index = operator_index + 1;
    };
    assert!(operator_index < operators_length, EMalformedSigners); // restore guard
    weight = weight + *vector::borrow(&weights, operator_index);
    if (weight >= threshold) { return true };
    operator_index = operator_index + 1;
    i = i + 1;   // ← missing increment
};
abort ELowSignaturesWeight
```

Also restore the commented-out `assert!(operator_index == operators_length, EMalformedSigners)` guard (corrected to `operator_index < operators_length`) to prevent out-of-bounds access when a signature does not match any registered operator.

---

### Proof of Concept

1. Deploy the `axelar` package. The `init` function creates and shares an `AxelarValidators` object.
2. Call `transfer_operatorship` to register an operator set with **two** operators, each with weight 50, and a threshold of 100 (requiring both signatures).
3. Construct a valid proof containing two valid ECDSA signatures — one from each operator — over the same `approval_hash`.
4. Call `process_commands` with that proof.
5. **Observed**: the transaction aborts with a vector out-of-bounds error on the second iteration of the outer loop (when `operator_index` reaches `operators_length`).
6. **Expected**: the function should accumulate weight from both signatures (50 + 50 = 100 ≥ threshold) and return `true`, allowing the bridge command to be processed.

The root cause is identical to the Nexus `checkERC7739Support` bug: a loop that is supposed to iterate over a collection (signatures) never advances its index, so only the first element is ever examined. [5](#0-4)
