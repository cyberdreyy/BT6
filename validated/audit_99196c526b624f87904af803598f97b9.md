### Title
Stale, connection-lifetime-cached `total_stake` snapshot lets QUIC clients retain an inflated TPU stream-throttling quota indefinitely - (File: streamer/src/nonblocking/swqos.rs)

### Summary
The report's bug class is "a time-weighted/cached value used for a critical gating decision goes stale relative to the real, fast-moving underlying quantity, and this staleness is exploitable by an economic actor." In Agave's QUIC TPU ingest path, the analogous mechanism is `SwQos`'s stake-weighted stream throttling, where a peer's `total_stake` is snapshotted once at connection acceptance and then reused for the entire lifetime of the connection to compute that peer's share of the staked ingest quota, and separately the cluster-wide load signal used to enable/disable throttling is a slow EMA that lags real instantaneous load.

### Finding Description
When a QUIC connection is accepted, `SwQos::build_connection_context` calls `get_connection_stake` once and stores the resulting `total_stake` (cluster-wide total) and the peer's own `stake` into `SwQosConnectionContext`, which is held for the life of the connection [1](#0-0) . For every new stream opened on that connection, `max_streams_per_throttling_interval` calls `available_load_capacity_in_throttling_duration(conn_context.peer_type, conn_context.total_stake)`, i.e. it always uses the `total_stake` value captured at connection-accept time, never refreshed [2](#0-1) [3](#0-2) .

When staked throttling is active, a peer's stream budget is computed as `max_staked_load_in_throttling_window * stake / total_stake` [4](#0-3) . Because `total_stake` is frozen at connection-open time, a connection opened while total delegated stake was low locks in a proportionally larger share of the fixed `max_staked_load_in_throttling_window` budget for as long as the connection stays alive (QUIC connections are long-lived and there is no periodic re-evaluation of `conn_context.total_stake` in the per-stream path). As real total stake grows (new validators, delegation changes) other, later-connecting peers get a correctly shrunk share, but the long-lived connection keeps consuming from the stale, larger allocation.

Separately, the aggregate signal gating whether staked throttling is even enabled, `staked_throttling_enabled`, is derived from a lagging EMA (`STREAM_LOAD_EMA_INTERVAL_MS = 5`, `STREAM_LOAD_EMA_INTERVAL_COUNT = 40`, i.e. a slow-responding average window) that is only recomputed opportunistically from `increment_load`/`on_stream_error`/`on_stream_closed` callbacks [5](#0-4) . This is directly analogous to the Chainlink TWAP: a smoothed, time-lagged signal is used for a real-time admission/throttle decision. The code comment even acknowledges the intended tolerance ("absorb a burst of ~50K transactions … before throttling activates") [6](#0-5) , but combined with the frozen `total_stake` snapshot, an attacker-controlled or opportunistically-timed connection can retain an outsized, unrevoked share of the staked TPU stream budget well beyond the intended fairness window.

### Impact Explanation
This affects only the QoS/throttling layer that gates how many QUIC unistreams (carrying transactions) a peer may push into the TPU per throttling interval; it does not bypass transaction sanitization, fee/rent accounting, or consensus. The impact is a fairness/availability degradation of TPU ingest capacity: a staked peer can maintain a disproportionately large, stale-favorable slice of the staked stream budget indefinitely by simply keeping a long-lived connection open from a moment when total stake was smaller, at the expense of other staked peers whose fair share should have shrunk. Combined with the slow EMA activation lag, this can let a peer push bursts above its intended fair-share rate for extended periods, reducing TPU ingest capacity available to fairly-behaving stakers - an ingest-starvation class impact, but bounded to QoS fairness rather than fund loss or consensus divergence.

### Likelihood Explanation
Reachable by any ordinary QUIC client presenting a staked identity to the TPU/TPU-forwards port; no privileged access or leaked keys are required, only knowledge of when to open/maintain a connection relative to total-stake growth. However, the practical benefit is bounded by `QUIC_MAX_STAKED_CONCURRENT_STREAMS`/`max_connections_per_staked_peer` and by the fact that total stake typically changes slowly (epoch boundaries), so the exploitable delta per connection is generally small; sustained benefit requires the connection to survive multiple epochs of stake growth, which competes with other pruning/eviction logic (`prune_random`, `max_staked_connections`) in `swqos.rs`.

### Recommendation
- Re-derive or periodically refresh `conn_context.total_stake` (and `peer_type`/stake) from `StakedNodes` on a bounded interval instead of caching it for the full connection lifetime, so throttling share tracks current stake distribution.
- Reduce reliance on a single long EMA window for enabling staked throttling; consider a faster-reacting or dual-window (fast+slow) load signal so bursts are capped closer to real time, consistent with the report's recommendation to avoid using a lagging time-weighted signal for decisions that need to react to fast-changing conditions.

### Proof of Concept
1. A validator/staked identity opens (or keeps open) a long-lived QUIC connection to a leader's TPU while total network stake is `T0`, locking in `conn_context.total_stake = T0` in `SwQosConnectionContext` [1](#0-0) .
2. Over subsequent epochs, total stake grows to `T1 > T0` (new stake delegated cluster-wide). New connections correctly compute their share against `T1`, but the long-lived connection keeps using `T0` on every `on_new_stream` call via `max_streams_per_throttling_interval` [2](#0-1) .
3. The peer's effective quota `max_staked_load_in_throttling_window * stake / T0` remains larger than the fair `.../ T1` value other peers receive, letting it push proportionally more streams/transactions into the TPU than intended, until it is evicted/pruned or reconnects.

impl QosController<SwQosConnectionContext> for SwQos {
    fn build_connection_context(&self, connection: &Connection) -> SwQosConnectionContext {
        let remote_address = connection.remote_address();
        get_connection_stake(connection, &self.staked_nodes).map_or(
            SwQosConnectionContext {
                peer_type: ConnectionPeerType::Unstaked,
                total_stake: 0,
                remote_pubkey: None,
                in_staked_table: false,
                remote_address,
                stream_counter: None,
                last_update: Arc::new(AtomicU64::new(timing::timestamp())),
            },
            |(pubkey, stake, total_stake)| {
                // The heuristic is that the stake should be large enough to have 1 stream pass through within one throttle
                // interval during which we allow max (MAX_STREAMS_PER_MS * STREAM_THROTTLING_INTERVAL_MS) streams.

                let peer_type = {
                    let max_streams_per_ms = self.staked_stream_load_ema.max_streams_per_ms();
                    let min_stake_ratio =
                        1_f64 / (max_streams_per_ms * STREAM_THROTTLING_INTERVAL_MS) as f64;
                    let stake_ratio = stake as f64 / total_stake as f64;
                    if stake_ratio < min_stake_ratio {
                        // If it is a staked connection with ultra low stake ratio, treat it as unstaked.
                        ConnectionPeerType::Unstaked
                    } else {
                        ConnectionPeerType::Staked(stake)
                    }
                };

                SwQosConnectionContext {
                    peer_type,
                    total_stake,
                    remote_pubkey: Some(pubkey),
                    in_staked_table: false,
                    remote_address,
                    last_update: Arc::new(AtomicU64::new(timing::timestamp())),
                    stream_counter: None,
                }
            },
        )

    fn ema_function(current_ema: u128, recent_load: u128) -> u128 {
        // Using the EMA multiplier helps in avoiding the floating point math during EMA related calculations
        const STREAM_LOAD_EMA_MULTIPLIER: u128 = 1024;
        let multiplied_smoothing_factor: u128 =
            2 * STREAM_LOAD_EMA_MULTIPLIER / (u128::from(STREAM_LOAD_EMA_INTERVAL_COUNT) + 1);

        // The formula is
        //    updated_ema = recent_load * smoothing_factor + current_ema * (1 - smoothing_factor)
        // To avoid floating point math, we are using STREAM_LOAD_EMA_MULTIPLIER
        //    updated_ema = (recent_load * multiplied_smoothing_factor
        //                   + current_ema * (multiplier - multiplied_smoothing_factor)) / multiplier
        (recent_load * multiplied_smoothing_factor
            + current_ema * (STREAM_LOAD_EMA_MULTIPLIER - multiplied_smoothing_factor))
            / STREAM_LOAD_EMA_MULTIPLIER
    }

    fn update_ema(&self, time_since_last_update_ms: u128) {
        // if time_since_last_update_ms > STREAM_LOAD_EMA_INTERVAL_MS, there might be intervals where ema was not updated.
        // count how many updates (1 + missed intervals) are needed.
        let num_extra_updates =
            time_since_last_update_ms.saturating_sub(1) / u128::from(STREAM_LOAD_EMA_INTERVAL_MS);

        let load_in_recent_interval =
            u128::from(self.load_in_recent_interval.swap(0, Ordering::Relaxed));

        let mut updated_load_ema = Self::ema_function(
            u128::from(self.current_load_ema.load(Ordering::Relaxed)),
            load_in_recent_interval,
        );

        for _ in 0..num_extra_updates {
            updated_load_ema = Self::ema_function(updated_load_ema, 0);
            if updated_load_ema == 0 {
                break;
            }
        }

        let Ok(updated_load_ema) = u64::try_from(updated_load_ema) else {
            error!("Failed to convert EMA {updated_load_ema} to a u64. Not updating the load EMA");
            self.stats
                .stream_load_ema_overflow
                .fetch_add(1, Ordering::Relaxed);
            return;
        };

        if self.staked_throttling_on_load_threshold > 0 {
            self.staked_throttling_enabled.store(
                updated_load_ema >= self.staked_throttling_on_load_threshold,
                Ordering::Relaxed,
            );
        }

        self.current_load_ema
            .store(updated_load_ema, Ordering::Relaxed);
        self.stats
            .stream_load_ema
            .store(updated_load_ema as usize, Ordering::Relaxed);
    }

    pub(crate) fn available_load_capacity_in_throttling_duration(
        &self,
        peer_type: ConnectionPeerType,
        total_stake: u64,
    ) -> u64 {
        match peer_type {
            ConnectionPeerType::Unstaked => self.max_unstaked_load_in_throttling_window,
            ConnectionPeerType::Staked(stake) => {
                if self.staked_throttling_enabled.load(Ordering::Relaxed) {
                    // 1 is added to `max_unstaked_load_in_throttling_window` to guarantee that staked
                    // clients get at least 1 more number of streams than unstaked connections.
                    self.max_staked_load_in_throttling_window
                        .saturating_mul(stake)
                        .checked_div(total_stake)
                        .unwrap_or(self.max_unstaked_load_in_throttling_window + 1)
                        .max(self.max_unstaked_load_in_throttling_window + 1)
                } else {
                    self.max_staked_load_in_throttling_window
                }
            }
        }
    }
