### Title
Withdrawal requests can front-run APR changes and lock stale fixed-rate payouts - ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary

A KYC-passed lender can front-run a manager’s APR reduction with `requestWithdraw` and permanently fix a withdrawal receipt using the old, higher APR. [1](#0-0)  The strategy then records that inflated amount in `pendingWithdraws`, creating a borrower funding obligation that survives the subsequent APR update. [2](#0-1) 

### Finding Description

`requestWithdraw` calculates the receipt as principal plus projected next-epoch interest using the currently configured strategy APR and epoch duration. [3](#0-2)  The interest calculation reads the current strategy APR through `_calcInterest`, while `_calcInterestWithdrawRequest` scales it back to the epoch-only period. [4](#0-3) [5](#0-4) 

`IdleCreditVault.setAprs` can be called directly by the manager and immediately changes both `unscaledApr` and `lastApr`, without suspending withdrawal requests or applying a timelock. [6](#0-5)  The manager orchestrator also exposes a direct raw APR update path through `setStrategyAprsRaw`. [7](#0-6) 

During the buffer phase, `requestWithdraw` remains enabled through `allowAAWithdrawRequest` and `allowBBWithdrawRequest`. [8](#0-7)  Therefore, an attacker who observes a pending APR decrease can first submit `requestWithdraw`, causing the strategy to mint a receipt for the larger amount and add it to `pendingWithdraws`. [9](#0-8)  The later APR update does not reprice that receipt.

If instant withdrawals are disabled, or the APR decrease is below `instantWithdrawAprDelta`, the request follows the fixed normal-withdrawal path rather than the principal-only instant path. [10](#0-9) 

### Impact Explanation

The attacker receives a fixed payout greater than the payout available under the updated APR. [11](#0-10)  At the following `stopEpoch`, the protocol attempts to pull the full stale `pendingWithdraws` amount from the borrower and transfer it to the strategy for claims. [12](#0-11) 

For example, with a 100,000 USDC withdrawal, a 36.5-day epoch, and an APR reduction from 10% to 5%, the excess fixed receipt is approximately:

```text
100,000 * (10% - 5%) * 36.5 / 365 = 500 USDC
```

The precise amount varies with tranche share, management fees, performance fees, and the APR split ratio. [13](#0-12)  The loss is borne by the borrower funding reserve and can delay or impair withdrawals if the borrower does not fund the excess amount.

### Likelihood Explanation

The attack only requires a KYC-passed lender and an observable manager transaction that lowers the strategy APR while withdrawal requests are enabled. [8](#0-7)  No privileged role is required, and the strategy accepts manager APR updates directly. [14](#0-13) 

The attack is not available while the epoch is running because withdrawal requests are disabled by `startEpoch`. [15](#0-14)  Its practical likelihood is therefore concentrated in the buffer phase or whenever management changes APR outside the atomic `stopEpoch` flow.

### Recommendation

Do not allow raw APR changes while withdrawal requests can be created. Possible mitigations include:

- Restrict `setApr`/`setAprs` during non-running epochs to the CDO’s atomic `stopEpoch` path.
- Temporarily disable withdrawal requests before broadcasting parameter changes and re-enable them afterward.
- Add a timelock or two-step commit for APR updates.
- Store the effective APR for the next epoch separately from the APR used to quote withdrawal receipts.
- Requote or invalidate receipts when epoch parameters change before the next `startEpoch`.

### Proof of Concept

The following test can be added to `TestIdleCreditVault` in `test/foundry/IdleCreditVault.t.sol`. The existing setup disables Keyring by setting `keyring` to zero, gives 100% of yield to AA in the tested configuration, and uses a 36.5-day epoch with a 5-day buffer. [16](#0-15) 

```solidity
function testFrontRunAprDecreaseLocksStaleWithdrawalRate() external {
  uint256 depositAmount = 100_000 * ONE_SCALE;
  uint256 oldApr = 10e18;
  uint256 newApr = 5e18;

  // Disable instant withdrawals so the request takes the fixed receipt path.
  vm.prank(owner);
  cdoEpoch.setInstantWithdrawParams(3 days, 1.5e18, true);

  deal(defaultUnderlying, address(this), depositAmount);
  IERC20Detailed(defaultUnderlying).approve(address(idleCDO), depositAmount);
  idleCDO.depositAA(depositAmount);

  uint256 oldScaledApr = _scaleAprWithBuffer(oldApr);
  uint256 newScaledApr = _scaleAprWithBuffer(newApr);

  vm.prank(manager);
  IdleCreditVault(address(strategy)).setAprs(oldApr, oldScaledApr);

  // Snapshot the post-update quote for comparison.
  uint256 snapshot = vm.snapshot();
  vm.prank(manager);
  IdleCreditVault(address(strategy)).setAprs(newApr, newScaledApr);
  uint256 newQuote = cdoEpoch.requestWithdraw(0, address(AAtranche));
  vm.revertTo(snapshot);

  // Attacker front-runs the pending APR reduction and locks the old APR.
  uint256 staleQuote = cdoEpoch.requestWithdraw(0, address(AAtranche));

  // Honest manager transaction then reduces the APR.
  vm.prank(manager);
  IdleCreditVault(address(strategy)).setAprs(newApr, newScaledApr);

  assertGt(staleQuote, newQuote, "stale APR was not locked");
  assertEq(
    IdleCreditVault(address(strategy)).pendingWithdraws(),
    staleQuote,
    "pending liability should retain stale quote"
  );

  // For the default test parameters and a 36.5-day epoch, the excess is
  // approximately 100_000 * 5% * 36.5 / 365 = 500 USDC.
  uint256 expectedDelta =
    depositAmount * (oldApr - newApr) * cdoEpoch.epochDuration()
      / (365 days * 100e18);
  assertApproxEqAbs(staleQuote - newQuote, expectedDelta, 2);
}
```

    _checkTranche(_tranche);
    _checkNotAllowed(
      (_tranche == AATranche ? !allowAAWithdrawRequest : !allowBBWithdrawRequest) ||
      !isWalletAllowed(msg.sender)
    );
  
    // we check if there are donated assets to the pool and transfer them to the feeReceiver if any
    _skimDonatedAssets();

    // we trigger an update accounting to check for eventual losses
    _updateAccounting();

    IdleCreditVault creditVault = IdleCreditVault(strategy);
    if (_amount == 0) {
      _amount = _userTrancheBal(msg.sender, _tranche);
    }
    _underlyings = _trancheToUnderlyings(_amount, _tranche);

    // Programmable borrower deployments do not support instant withdrawals.
    // If apr decresed wrt last epoch, request instant withdraw and burn tranche tokens directly
    // we compare unscaled aprs
    if (_isInstantWithdrawEnabled()) {
      uint256 currentApr = creditVault.unscaledApr();
      if (lastEpochApr > (currentApr + instantWithdrawAprDelta)) {
        // burn strategy tokens from cdo and mint an equal amount to msg.sender as receipt
        creditVault.requestInstantWithdraw(_underlyings, msg.sender);
        // burn tranche tokens and decrease NAV
        _withdrawOps(_amount, _underlyings, _tranche);
        return _underlyings;
      }
    }

    uint256 principal = _underlyings;
    (uint256 interest, int256 diff) = _calcInterestWithdrawRequest(_underlyings, _tranche);
    uint256 totalFees = _totalWithdrawFees(principal, interest);
    // user is requesting principal + interest minus upfront management fee and net performance fee
    _underlyings = principal + interest - totalFees;
    // add expected fees to pending withdraw fees counter
    pendingWithdrawFees += totalFees;

    /// if there is an AA withdrawal the overperformance that the amount withdrawed would have generated for BB tranches
    /// is saved in interestForOverUnderPerformance. This is used to calculate the interest that should be added to the
    /// expectedEpochInterest at the startEpoch.
    /// If there is a BB withdrawal this amount is subtracted from the expectedEpochInterest
    interestForOverUnderPerformance += diff;

    // The receipt is fixed now and leaves live NAV. Charge management fees upfront
    // for the time it waits outside live NAV: remaining buffer plus the next epoch.
    creditVault.requestWithdraw(_underlyings, msg.sender, principal);
    // burn tranche tokens and decrease NAV without interest for the next epoch as it was not yet counted in NAV
    _withdrawOps(_amount, principal, _tranche);

  function _calcInterestWithdrawRequest(uint256 _amount, address _tranche) internal view returns (uint256 _interest, int256 _diff) {
    uint256 _duration = epochDuration;
    if (_duration == 0) {
      return (_interest, _diff);
    }

    uint256 _buffer = bufferPeriod;
    // calculate total vault interest (they don't get the interest for the buffer period for withdraw requests so 
    // we scale it back since _calcInterest is scaling the interest with tht buffer period),
    uint256 totInterest = _calcInterest(_managedContractValue()) * _duration / (_duration + _buffer);
    // calculate total tranche interest for the whole tranche supply
    uint256 totTrancheInterest = _calcTrancheInterestShare(totInterest, _tranche);
    // calculate interest for the given tranche and given amount
    uint256 _trancheBal = _lastSavedNAV(_tranche);
    _interest = _trancheBal == 0 ? 0 : _amount * totTrancheInterest / _trancheBal;
    // calculate the interest that the _amount would have received if there was no split ratio (ie interest split based only on tvl).
    // This is used to calculate the interest that should be added to the expectedEpochInterest when 
    // withdrawing an AA tranche or the interest that should be removed from expectedEpochInterest when
    // withdrawing a BB tranche
    uint256 interestWithoutSplitRatio = _calcInterest(_amount) * _duration / (_duration + _buffer);
    // difference between total interest and tranche interest (positive for AA, negative for BB)
    _diff = int256(interestWithoutSplitRatio) - int256(_interest);
  }

  /// @notice set both the scaled and unscaled apr
  /// @dev only cdo and manager can set the apr.

  function setAprs(uint256 _unscaledApr, uint256 _apr) external {
    unscaledApr = _unscaledApr;
    // here we also check that msg.sender is allowed
    setApr(_apr);
  }

  /// @notice set both the unscaled APR and APR scaled by epoch plus buffer duration.
  /// @dev only CDO and manager can set the APR through `setApr`.
  /// @param _unscaledApr unscaled APR
  /// @param _duration epoch duration
  /// @param _buffer buffer duration
  function setAprsWithBuffer(uint256 _unscaledApr, uint256 _duration, uint256 _buffer) external {
    unscaledApr = _unscaledApr;
    setApr(_duration == 0 ? _unscaledApr : _unscaledApr * (_duration + _buffer) / _duration);
  }

  /// @notice set the fixed apr
  /// @dev only cdo and manager can set the apr. If manager manually set apr from 
  /// here it will not be scaled to include the buffer period
  function setApr(uint256 _apr) public {
    address _cdo = idleCDO;

    // if cdo is not yet set we skip the check (this can happen only during the setup)
    if (_cdo != address(0)) {
      if (msg.sender != _cdo && msg.sender != manager) revert NotAllowed();
    }
    uint256 _maxApr = maxApr;
    if (_maxApr != 0 && _apr > _maxApr) revert NotAllowed();
    lastApr = _apr;
  }
