### Title
Replay of a captured, validly-signed WebAPITrigger `api.Message` re-triggers workflow execution because `Validate()` and the legacy gateway path perform no MessageId/nonce uniqueness check - ([File: core/services/gateway/api/message.go])

### Summary
`api.Message.Validate()` only checks signature correctness and field-length/null-byte constraints; it never records or checks `MessageId` for prior use. The legacy gateway trigger path (`HandleLegacyUserMessage` in `core/services/gateway/handlers/capabilities/handler.go`) and the DON-side `triggerConnectorHandler.processTrigger` in `core/capabilities/webapi/trigger/trigger.go` also do not track previously-seen `MessageId`/`TriggerEventId` values, so a captured, still-fresh signed trigger message can be resent to re-fire the workflow trigger.

### Finding Description
`Validate()` performs only the following checks and nothing about message freshness/uniqueness: [1](#0-0) 

The gateway's legacy request path calls `msg.Validate()` and then dispatches straight to the handler with no message-ID cache: [2](#0-1) 

`HandleLegacyUserMessage` (used for `MethodWebAPITrigger`) only checks payload decode success and a coarse staleness window (`payload.Timestamp` vs `MaxAllowedMessageAgeSec`), then unconditionally stores/overwrites a callback keyed by `MessageId` and forwards the request to every DON node - it never rejects a `MessageId` it has already seen and processed: [3](#0-2) 

On the DON side, `triggerConnectorHandler.processTrigger` computes a deterministic `TriggerEventID := body.Sender + payload.TriggerEventId` and unconditionally emits a new `TriggerResponse` on the trigger channel for every call - there is no local cache/guard rejecting a `TriggerEventID` (or `MessageId`) that was already processed: [4](#0-3) 

By contrast, other gateway handlers in the same codebase (vault, confidential relay, v2 HTTP trigger) explicitly implement replay/duplicate-request guards on top of `Message.Validate()`/JSON-RPC request ID: [5](#0-4) [6](#0-5) 

This shows dedup is a handler-layer responsibility by design, but the legacy `MethodWebAPITrigger` handler path lacks it. As long as the replayed message's embedded `payload.Timestamp` is still within `MaxAllowedMessageAgeSec`, `Validate()` will pass again (same signature is still valid over the same body bytes), the handler will re-forward the request to DON nodes, and `processTrigger` will re-emit the trigger event, causing the associated workflow to execute a second time from the identical signed request.

### Impact Explanation
This allows duplicate execution of a workflow trigger under the original signer's identity from a single captured signed message, within the message's staleness window. This falls under "unauthorized/duplicate job run" impact class in the Chainlink bounty program - a workflow with real-world side effects (e.g., initiating payments, on-chain transactions, external calls) could be triggered more than once from one legitimate request, purely because the gateway/DON path lacks MessageId/nonce-based replay protection that exists in sibling handlers (vault, confidential relay).

### Likelihood Explanation
Preconditions match the stated ones: the attacker only needs to capture one of their own previously sent, validly signed `MethodWebAPITrigger` messages (e.g., from their own client logs or by sniffing their own request) and resend the identical JSON-RPC payload before `payload.Timestamp + MaxAllowedMessageAgeSec` expires. No credentials beyond the attacker's own signing key are required, and the replay window is fully attacker/timestamp controlled since `Timestamp` is part of the signed payload the attacker originally chose. This is fully repeatable for every distinct message the attacker (or anyone who intercepts their traffic) has captured.

### Recommendation
Add a `MessageId`-scoped (or `TriggerEventId`-scoped) dedup/replay guard to the legacy WebAPI trigger path, mirroring the patterns already used elsewhere in the codebase:
- In `core/services/gateway/handlers/capabilities/handler.go`'s `HandleLegacyUserMessage`, reject requests whose `MessageId` (or sender+`TriggerEventId`) was already seen within the retention window, similar to `savedCallbacks` but explicitly rejecting duplicates rather than overwriting.
- In `core/capabilities/webapi/trigger/trigger.go`'s `processTrigger`, maintain a bounded, TTL-based cache of seen `TriggerEventID` values (per workflow) and short-circuit re-emission of `capabilities.TriggerResponse` for already-processed IDs, similar to `vault.RequestReplayGuard`.

### Proof of Concept
Handler-level Go test plan (extending `core/services/gateway/handlers/capabilities/handler_test.go`):
1. Build a valid signed `api.Message` via `triggerRequest(...)` (as in existing tests).
2. Call `handler.HandleLegacyUserMessage(ctx, msg, cb1)`; assert `don.SendToNode` invoked for all DON members and the trigger accepted (`cb1` receives success).
3. Call `handler.HandleLegacyUserMessage(ctx, msg, cb2)` again with the exact same `msg` (same `Signature`, `MessageId`, `Body`) before `MaxAllowedMessageAgeSec` elapses.
4. Assert (post-fix) that `don.SendToNode` is NOT invoked a second time and `cb2` receives an explicit duplicate/replay error - currently (pre-fix) the test would show `SendToNode` invoked again and `cb2` succeeding, demonstrating the duplicate trigger.
5. Complementary DON-side test in `core/capabilities/webapi/trigger/trigger.go`: call `processTrigger` twice with identical `body`/`payload` (same `MessageId`/`TriggerEventId`) and assert the trigger channel only receives one `TriggerResponse` post-fix, versus two today.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil

// CheckAndRecord returns ErrRequestAlreadySeen if the digest was previously
// recorded and has not yet expired. Otherwise it records the digest with
// the given expiry timestamp (unix seconds, UTC).
//
// Expired entries are cleaned up on every call.
func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}

func (h *handler) HandleJSONRPCUserMessage(ctx context.Context, req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) error {
	if req.ID == "" {
		return errors.New("request ID cannot be empty")
	}
	if len(req.ID) > 200 {
		return errors.New("request ID is too long: " + strconv.Itoa(len(req.ID)) + ". max is 200 characters")
	}

	l := logger.With(h.lggr, "method", req.Method, "requestID", req.ID)
	l.Debugw("handling confidential relay request")

	ar, err := h.newActiveRequest(req, callback)
	if err != nil {
		return err
	}

	return h.fanOutToNodes(ctx, l, ar)
