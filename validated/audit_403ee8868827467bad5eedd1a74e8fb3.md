### Title
Stale `instantWithdrawsRequestsByEpoch` entries survive a funded instant claim and are paid out again after a same-epoch default finalization - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The Linux bug "wait all existing dio write IOs before block removal, otherwise a previous direct write IO may overwrite data in the block reused by other inode" maps to the credit-vault surface as: a completed (funded) instant-withdraw receipt is not fully removed before the per-epoch receipt ledger is reused by default-recovery accounting. The funded claim path in `claimInstantWithdrawRequest` zeroes only the aggregate `instantWithdrawsRequests[_user]` (lines 387-392) but never clears `instantWithdrawsRequestsByEpoch[_user][epoch]` or decrements `instantWithdrawClaimsByEpoch[epoch]`. If the same `epochNumber` later defaults with `pendingInstantWithdraws != 0`, `finalizeDefaultRecovery` sets `defaultRecoveryEpoch = epochNumber` and `defaultInstantWithdrawsFinalized = true`, and `_claimDefaultedInstantWithdrawRequest` reads the stale per-epoch entry and pays it again from `defaultRecoveryReserve` at `defaultRecoveryPrice` — a second payout for a receipt already fully paid at par. The stale basis also inflates `defaultPendingClaimBasis`, diluting `defaultRecoveryPrice` for every other defaulted claimant.

### Finding Description
Bug class translation: pending/completed async write must be quiesced before the block (per-epoch receipt slot) is reused. Here:

1. During epoch `E`, a user calls `requestInstantWithdraw` → `instantWithdrawsRequestsByEpoch[user][E] += amount`, `instantWithdrawClaimsByEpoch[E] += amount`, `pendingInstantWithdraws += amount` (lines 366-374).
2. `getInstantWithdrawFunds` / `collectInstantWithdrawFunds` funds the request, reducing `pendingInstantWithdraws` to 0 but leaving `instantWithdrawClaimsByEpoch[E]` untouched (lines 398-403).
3. User calls `claimInstantWithdrawRequest` → the funded path burns `instantWithdrawsRequests[user]` and pays at par via `_transferFundedClaim`, but `instantWithdrawsRequestsByEpoch[user][E]` and `instantWithdrawClaimsByEpoch[E]` retain the full basis (lines 387-392). Compare with `_claimDefaultedInstantWithdrawRequest`, which does clear both (lines 847-853) — confirming the omission.
4. Still within epoch `E`, a second user's instant request is only partially funded (`pendingInstantWithdraws > 0`), and the borrower defaults. `finalizeDefaultRecovery` computes `basis = pendingWithdraws + instantWithdrawClaimsByEpoch[E]`, which still includes the attacker's already-paid receipt → recovery price is diluted, and `defaultInstantWithdrawsFinalized = true` (lines 644-649, 693-696).
5. The attacker calls `claimInstantWithdrawRequest` again; `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized` routes into `_claimDefaultedInstantWithdrawRequest`, which reads the stale `instantWithdrawsRequestsByEpoch[user][E] = amount`, burns nothing extra (balance already burned — `_burn(_user, claimBasis)` will revert only if the user has no receipt tokens; note the receipt tokens from step 1 were already burned, so this step requires the attacker to hold at least `claimBasis` strategy tokens, obtainable cheaply by depositing or via a subsequent `requestInstantWithdraw`/`requestWithdraw` receipt since `requestInstantWithdraw` after default... see caveat), and pays `amount * defaultRecoveryPrice` from `defaultRecoveryReserve` (lines 842-855).

### Impact Explanation
Direct theft from the isolated `defaultRecoveryReserve`: the attacker is paid twice for one instant-withdraw receipt (once at par, once at the recovery ratio). Additionally, because `instantWithdrawClaimsByEpoch[E]` retains the paid basis, `totalBasis` in `finalizeDefaultRecovery` is inflated, lowering `defaultRecoveryPrice` for all active LPs and pending redeemers. The reserve is drained by early claimants so later legitimate claimants' `_transferDefaultRecovery` either underflows the reserve accounting or reverts on insufficient balance — permanent freezing/theft of unclaimed recovery yield, proportional to the attacker's claimed amount.

### Likelihood Explanation
Requirements: (a) an instant-withdraw epoch where one request is fully funded and claimed, (b) another instant request in the same `epochNumber` left partially unfunded (`pendingInstantWithdraws != 0`), (c) borrower default finalized in that epoch. Instant withdrawals are a first-class flow (`setInstantWithdrawParams`, `getInstantWithdrawFunds`), partial funding occurs whenever CDO liquidity is short, and per-epoch keys are only checked when `defaultInstantWithdrawsFinalized` — which is exactly the partially-funded case. The attacker needs a fresh strategy-token balance to satisfy the second `_burn`, which post-default `requestWithdraw` (minting `postDefaultRequests` receipts, line 254-256) or a simple deposit provides. Uncertainty: I could not fully verify the CDO-side `allowInstantWithdraw` gating in `IdleCDOEpochVariant.sol` — if the CDO blocks a funded claim whenever `pendingInstantWithdraws > 0` for *any* user, the attacker's own claim must occur while `pending == 0`, meaning the stale entry and the unfunded remainder must coexist within one epoch via two sequential instant rounds (fully-funded round claims first, then a later round is left partially unfunded at finalization). The code supports this ordering, but the exact CDO gating condition should be confirmed.

### Recommendation
In `claimInstantWithdrawRequest`'s funded path, clear the per-epoch ledgers symmetrically with `_claimDefaultedInstantWithdrawRequest`: iterate or track the user's request epochs to zero `instantWithdrawsRequestsByEpoch[_user][epoch]` and decrement `instantWithdrawClaimsByEpoch[epoch]` by the claimed amount (a per-user list of request epochs may be needed since aggregate claims can span epochs). Alternatively, store the funded-claim epoch per user and clear that slot.

### Proof of Concept
Foundry fork PoC sketch:

```solidity
// epoch E running, instant withdraws enabled
// 1. attacker deposits, requests instant withdraw of X
cdoEpoch.requestInstantWithdraw? // via strategy, amount X
// 2. manager collects funds fully -> pendingInstantWithdraws == 0
cdoEpoch.getInstantWithdrawFunds();
// 3. attacker claims funded receipt at par
cdoEpoch.claimInstantWithdrawRequest(); // attacker receives X underlying
//    instantWithdrawsRequestsByEpoch[attacker][E] still == X  (STALE)
// 4. same epoch E: victim requests instant withdraw Y; only partial collect
//    pendingInstantWithdraws > 0
// 5. borrower defaults; manager calls finalizeDefault(recovered, manager)
//    basis includes attacker's stale X -> defaultRecoveryPrice diluted
//    defaultInstantWithdrawsFinalized == true, defaultRecoveryEpoch == E
// 6. attacker deposits again (or uses post-default request) to hold >= X strategy tokens
// 7. attacker calls claimInstantWithdrawRequest again
cdoEpoch.claimInstantWithdrawRequest();
//    receives X * defaultRecoveryPrice / 1e18 from defaultRecoveryReserve
// assert attacker balance gain > 0 and reserve decreased by the extra payout
```

Expected assertions: `underlying.balanceOf(attacker)` increases twice for a single receipt; `defaultRecoveryReserve` is reduced by the double-claim; a later victim claim reverts or pays less than `claimBasis * defaultRecoveryPrice` implied before the attack.
