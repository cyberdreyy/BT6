### Title
Authentication type confusion allows External Initiator credentials to bypass "EIs not allowed" restriction on job runs - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` gates the numeric-ID job-run path on `isUser` from `auth.GetAuthenticatedUser(c)`, intending to exclude External Initiators (EIs) per the comment "only users are allowed to run jobs using int IDs - EIs not allowed". However, `AuthenticateExternalInitiator` synthesizes and stores a `*clsessions.User{Role: clsessions.UserRoleRun}` under the same `SessionUserKey` used for real user sessions/tokens, so `GetAuthenticatedUser` returns `ok=true` for EI-authenticated requests as well, defeating the intended EI/user distinction.

### Finding Description
`PipelineRunsController.Create` at [1](#0-0)  checks `_, isUser := auth.GetAuthenticatedUser(c)` and only allows the numeric-ID job-run path (`prc.App.RunJobV2`) when `isUser` is true, with an explicit comment that EIs are not allowed to use this path.

`auth.GetAuthenticatedUser` simply reads whatever `*clsessions.User` object is stored under `SessionUserKey` in the gin context: [2](#0-1) . It has no way to distinguish whether that user object came from a real session/token authentication or was synthesized for an EI.

`AuthenticateExternalInitiator`, the authMethod used to validate EI access-key/secret headers, explicitly sets `SessionUserKey` to a synthetic user object after successfully validating the EI credentials: [3](#0-2) . The comment in the code even acknowledges this is intentional so EI-authenticated requests can pass role checks like `RequiresRunRole` — but this same mechanism causes `GetAuthenticatedUser` (and thus `isUser`) to return true for EI callers, which is exactly the case `PipelineRunsController.Create` tries to exclude.

As a result, an attacker holding only valid EI access key/secret (no real user session or API token) can authenticate via EI headers, and the resulting synthetic user object causes `isUser` to evaluate `true` in `Create`, allowing them to reach `prc.App.RunJobV2` for any numeric job ID — the exact behavior the code comment says should be blocked.

### Impact Explanation
An EI credential holder — a lower-trust identity intended only to post external initiator job triggers via UUID-based webhook flows — can trigger job runs by numeric ID for arbitrary jobs on the node, matching the "unauthorized job run" bounty impact class. This crosses an intended authorization/identity boundary (EI vs. user), even though the resulting action (`RunJobV2`) is the same one a legitimate low-privileged "run"-role user could perform; the issue is that the restriction explicitly coded to exclude EIs is bypassed due to a shared representation format between EI and user identities.

### Likelihood Explanation
Precondition is only a valid EI access key/secret pair — no operator/admin credentials or user session are required. Any endpoint route configured with `AuthenticateExternalInitiator` as one of its accepted `authMethod`s for job-run creation would trigger this; the exploit is deterministic and repeatable given valid EI credentials.

Note: I could not verify from the router.go contents (search returned matches but content wasn't fully retrieved before the tool budget ended) whether `PipelineRunsController.Create`'s route is actually configured to accept `AuthenticateExternalInitiator` as one of its middleware auth methods. This is the key remaining question to confirm real-world reachability — if the `/v2/jobs/:ID/runs` route only accepts `AuthenticateBySession`/`AuthenticateByToken` and never `AuthenticateExternalInitiator`, the EI code path would never populate `SessionUserKey` for this route and the bug would be unreachable from an EI credential holder in practice.

### Recommendation
Do not rely on `SessionUserKey`/`GetAuthenticatedUser` alone to distinguish EI callers from real users. Either:
1. Check `auth.GetAuthenticatedExternalInitiator(c)` in `Create` and explicitly reject the request if an EI is present, in addition to (or instead of) checking `isUser`, or
2. Avoid setting `SessionUserKey` to a synthetic user in `AuthenticateExternalInitiator`; instead thread EI role information through a distinct context key that role-checking middleware (`RequiresRunRole`, etc.) can consult, so that `SessionUserKey` is only ever populated by genuine user authentication.

### Proof of Concept
Handler-level integration test in `core/web/pipeline_runs_controller_test.go` (or new test file):
1. Set up a test app with a configured External Initiator (valid access key/secret) and a job with a known numeric ID.
2. Send `POST /v2/jobs/<int-id>/runs` using only the EI headers (`X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` equivalents per `static.ExternalInitiatorAccessKeyHeader`/`SecretHeader`), with no session cookie and no `X-API-KEY`/`X-API-SECRET`.
3. Assert on the route's configured auth methods (confirm whether `AuthenticateExternalInitiator` is included for this route in `core/web/router.go`).
4. If confirmed reachable: assert that the response is `422 bad job ID` / `401 Unauthorized` (expected/fixed behavior) rather than `200`/`201` with a created pipeline run resource (current buggy behavior), proving `isUser` incorrectly evaluates true for EI-only authentication.
5. Unit-test alternative: directly call `auth.AuthenticateExternalInitiator(c, mockStore)` then `auth.GetAuthenticatedUser(c)` and assert `ok` should be `false` (or a distinguishable EI marker) rather than `true`.

	obj, ok := c.Get(SessionUserKey)
