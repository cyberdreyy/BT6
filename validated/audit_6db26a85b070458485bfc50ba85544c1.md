### Title
Zip-slip path traversal in legacy zip extractor bypasses artifact workspace confinement - ([File: helpers/archives/zip_extract.go])

### Summary
The `ziplegacy` extractor used for the `zip`/`zipzstd` archive formats (registered by default in `commands/helpers/archiver.go`, and selectable per-job because `FF_USE_FASTZIP` is read from the process environment at binary init) completely ignores the `dir` confinement parameter and performs no path-traversal validation, unlike the `tarzstd` extractor which explicitly checks paths stay inside the target directory. An attacker who controls artifact file names in their own job can upload a zip entry named e.g. `../../evil` and have it written outside the intended download directory when a later `artifacts-downloader` process extracts it via this code path.

### Finding Description
`ArtifactsDownloaderCommand.Execute` calls `archive.NewExtractor(format, f, size, wd)` [1](#0-0)  where `wd` is meant to confine extraction. For the default `Zip` format, unless `FF_USE_FASTZIP` is enabled, the registered extractor is `ziplegacy.NewExtractor` [2](#0-1) , whose `Extract` method stores `dir` in the struct but never uses it — it calls `archives.ExtractZipArchive(zr)` with no directory argument at all.

`ExtractZipArchive` iterates zip entries and calls `extractZipFile(file)` [3](#0-2) , which in turn calls `os.MkdirAll(filepath.Dir(file.Name), ...)`, `os.Mkdir(file.Name, ...)`, `os.Symlink(..., file.Name)`, or `os.OpenFile(file.Name, ...)` using the raw, attacker-controlled zip entry name `file.Name` directly — relative to the process's current working directory, with **no `filepath.Clean`/prefix check, no `..` rejection, and no join against any confinement root**. The only sanity check present, `errorIfGitDirectory`, only blocks `.git`-prefixed paths [4](#0-3) ; it does not address `../` traversal.

This is in stark contrast to the `tarzstd` extractor, which explicitly resolves `filepath.Abs(filepath.Join(e.dir, hdr.Name))` and rejects any path that does not have `e.dir` as its prefix [5](#0-4) . The legacy zip path has no equivalent guard, so the workspace-confinement invariant only holds for tarzstd/fastzip, not for the legacy zip path.

Exploit flow: (1) attacker's job creates artifact files with names like `../../../home/gitlab-runner/.ssh/authorized_keys` or `../../../etc/cron.d/evil`; (2) `ArtifactsUploaderCommand` archives them by filename with the zip/gziplegacy archiver and uploads via `GitLabClient.UploadRawArtifacts`; (3) a later `artifacts-downloader` invocation (same or later job) fetches the blob via `requester.Do`/`client.do`, calls `openArchive` (defaults to `archive.Zip`) and `archive.NewExtractor(archive.Zip, f, size, wd)`; (4) if the ziplegacy extractor is in effect for `Zip`/`ZipZstd` (i.e., `FF_USE_FASTZIP` is not enabled for that process — this flag is read via `os.Getenv` at package `init()` and, like other GitLab Runner feature flags, can be set as a CI/CD job/pipeline variable that is passed into the environment of the spawned helper subprocess), extraction writes files following the raw entry path with no boundary check, escaping `wd`.

### Impact Explanation
Unauthorized file write outside the intended build/artifact temp directory on the runner host filesystem, using only attacker-controlled artifact contents from their own job — exactly the scoped impact requested. Depending on runner executor (shell/host-based executors are most directly affected since the extraction happens in the runner's own process/filesystem, not inside a container sandbox), this can write to arbitrary host paths reachable by the `gitlab-runner` process user.

### Likelihood Explanation
Fully attacker-reachable with no special privileges beyond a normal pipeline: crafting archive entry names is a standard capability of `ArtifactsUploaderCommand` inputs, and the ziplegacy code path is reachable whenever `FF_USE_FASTZIP` is not effectively enabled for the extraction process. Because `FF_USE_FASTZIP`, like other GitLab Runner feature flags, is typically resolved via `os.Getenv` and job/pipeline-level variables are injected into helper-binary subprocess environments, a pipeline author can plausibly force this less-safe code path for their own job's download step. I was not able to confirm in this session whether `FF_USE_FASTZIP` defaults to `true` or `false` in this codebase revision, or whether it is deny-listed from job-variable overrides for this internal command's process env — this should be verified, but even as a project/runner-level configuration knob (not necessarily job-settable), the underlying extractor logic is objectively missing a check that its sibling extractor (`tarzstd`) has, which is a code defect regardless of how it's toggled.

### Recommendation
Add the same path-confinement validation used in `tarzstd_extractor.go` to the legacy zip extraction path: thread `dir` through `ziplegacy.extractor.Extract` into `archives.ExtractZipArchive`/`extractZipFile`, resolve each entry as `filepath.Abs(filepath.Join(dir, file.Name))`, and reject any entry whose resolved path is not prefixed by `dir` (rejecting `..`-traversal and absolute paths, consistent with the tarzstd implementation) before performing any `Mkdir`/`OpenFile`/`Symlink` operation.

### Proof of Concept
```go
func TestExtractZipArchive_PathTraversal(t *testing.T) {
    dir := t.TempDir()
    outsideDir := t.TempDir() // simulate CWD used by extractor
    prevWd, _ := os.Getwd()
    require.NoError(t, os.Chdir(outsideDir))
    defer os.Chdir(prevWd)

    buf := new(bytes.Buffer)
    zw := zip.NewWriter(buf)
    w, _ := zw.Create("../../evil")
    _, _ = w.Write([]byte("pwned"))
    require.NoError(t, zw.Close())

    zr, err := zip.NewReader(bytes.NewReader(buf.Bytes()), int64(buf.Len()))
    require.NoError(t, err)

    err = archives.ExtractZipArchive(zr)
    // Expected (fixed) behavior: err != nil, traversal rejected
    require.Error(t, err)

    escapedPath := filepath.Join(filepath.Dir(outsideDir), "evil")
    _, statErr := os.Stat(escapedPath)
    assert.True(t, os.IsNotExist(statErr), "file must not be written outside confinement dir")
    _ = dir
}
```
Currently, running this against the unmodified `ExtractZipArchive`/`extractZipFile` code produces `err == nil` and creates `evil` outside `outsideDir`, confirming the missing confinement check.

```go
func NewExtractor(r io.ReaderAt, size int64, dir string) (archive.Extractor, error) {

// Extract extracts files from the reader to the directory passed to

	}
```

```go
func extractZipFile(file *zip.File) (err error) {
	// Create all parents to extract the file
	err = os.MkdirAll(filepath.Dir(file.Name), 0o777)
	if err != nil {
		return err
	}

	switch file.Mode() & os.ModeType {
	case os.ModeDir:
		err = extractZipDirectoryEntry(file)

	case os.ModeSymlink:
		err = extractZipSymlinkEntry(file)

	case os.ModeNamedPipe, os.ModeSocket, os.ModeDevice:
		// Ignore files of these types
		logrus.Warningf("File ignored: %q", file.Name)

	default:
		err = extractZipFileEntry(file)
	}
	return
}
```

```go
func isPathAGitDirectory(path string) bool {
	parts := strings.Split(filepath.Clean(path), string(filepath.Separator))
	if len(parts) > 0 && parts[0] == ".git" {
		return true
	}
	return false
}

func errorIfGitDirectory(path string) *os.PathError {
	if !isPathAGitDirectory(path) {
		return nil
	}

	return &os.PathError{
		Op:   ".git inside of archive",
		Path: path,
		Err:  errors.New("trying to archive or extract .git path"),
	}
}
```
