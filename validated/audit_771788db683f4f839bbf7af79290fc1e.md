### Title
DKG vault result export/verify endpoints require only edit-role, disclosing raw DKG share/key material to non-admin users - ([File: core/web/router.go], [File: core/web/vault_controller.go])

### Finding Description
`VaultController.ExportDKGResult` in `core/web/vault_controller.go` reads the stored `ReportWithResultPackage` for a given `instanceId` from the vault ORM and returns it hex-encoded, unredacted, directly to the caller: [1](#0-0) 

This is the raw DKG result package (containing the node's decryptable share material), analogous in sensitivity to an exported key file. `VerifyDKGResult` similarly reads and processes the same raw package: [2](#0-1) 

Neither handler performs any additional in-handler privilege check — both rely entirely on the role middleware wired at the route-group level in `core/web/router.go`, where the `/v2/vault/dkg_results/verify` and `/v2/vault/dkg_results/export` routes are registered under `RequiresEditRole` rather than `RequiresAdminRole`. Every other key/secret export endpoint in the router (`ekc.Export` for ETH keys, `ocrkc.Export` for OCR keys, `vrfkc.Export` for VRF keys, etc.) is instead gated behind `RequiresAdminRole`, establishing a consistent codebase convention that any endpoint disclosing raw private key/secret material requires the highest privilege tier. The vault DKG export endpoint breaks this convention, allowing an edit-role (non-admin) credential to retrieve raw DKG result/share material.

### Impact Explanation
An attacker holding only an edit-role API token/session (not admin) can call `POST /v2/vault/dkg_results/export` with a known or guessed `instanceId` and receive the hex-encoded `ReportWithResultPackage`, which contains DKG share material usable to reconstruct or misuse the node's cryptographic key material for the Vault/DKG capability. This is a secret/key-material disclosure to a lower-privilege role than the equivalent `ekc.Export`/`ocrkc.Export`/`vrfkc.Export` endpoints permit, matching the "unintended disclosure of confidential data" / privileged key export impact class.

### Likelihood Explanation
Exploitation requires only an edit-role API credential (a role explicitly weaker than admin, and available to more operators/tokens in typical deployments) and knowledge of a valid `instanceId` for a completed DKG round. No additional bypass or timing constraints are needed — a single authenticated HTTP POST triggers full disclosure, making this trivially repeatable for any edit-role holder.

### Recommendation
Change the route group registration for `/v2/vault/dkg_results/verify` and `/v2/vault/dkg_results/export` in `core/web/router.go` to require `RequiresAdminRole`, consistent with `ekc.Export`, `ocrkc.Export`, and `vrfkc.Export`. Alternatively, keep `verify` at edit-role (since it does not return raw material) but move `export` specifically to admin-only.

### Proof of Concept
1. Add a Go handler-level integration test in `core/web/vault_controller_test.go` (or a new test) that creates an edit-role-only session/token (not admin), seeds a DKG result row via the vault ORM, and issues `POST /v2/vault/dkg_results/export` with that credential.
2. Assert the current behavior returns `200 OK` with the hex-encoded `ReportWithResultPackage` in the response body (confirming the gap).
3. As a comparison assertion, issue the same edit-role credential against `/v2/keys/eth/export/:keyID` (or equivalent `ekc.Export`/`ocrkc.Export` route) and assert it returns `403 Forbidden`, demonstrating the inconsistency.
4. After applying the recommended fix (moving vault export to `RequiresAdminRole`), re-run the test and assert `/v2/vault/dkg_results/export` also returns `403` for the edit-role credential and `200` only for an admin-role credential.
