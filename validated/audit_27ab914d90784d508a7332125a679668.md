### Title
Delayed authorization revocation allows compromised signer key to authorize HTTPTriggerRequests during the metadata sync window - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
`WorkflowMetadataHandler.Authorize` validates signer keys strictly against the in-memory `h.authorizedKeys` map, which is only refreshed by the periodic `syncMetadata` ticker running at `MetadataAggregationIntervalMs` (default 60s). A signer key removed by the workflow owner (on-chain or via node metadata push) remains valid for authorization until the next tick fires, allowing a holder of a revoked key to continue authorizing `HTTPTriggerRequests` for that workflow.

### Finding Description
`Authorize` (core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go:80-108) verifies the JWT signature/replay, then checks membership of the recovered signer against `h.authorizedKeys[workflowID]`: [1](#0-0) 

`h.authorizedKeys` is a plain map populated exclusively inside `syncMetadata`, which itself is invoked only from a background ticker started in `Start()`: [2](#0-1) [3](#0-2) 

`syncMetadata` itself builds its view from each shard's `WorkflowMetadataAggregator.Aggregate()`, which is fed by `OnMetadataPush`/`OnMetadataPullResponse` (pulled every `MetadataPullIntervalMs`, default 60s). So the full path from an on-chain/off-chain key removal to `h.authorizedKeys` reflecting the removal requires: (1) nodes to observe/report the updated metadata (push or next pull cycle), and (2) the next `syncMetadata` tick to run. Until both complete, `Authorize` continues to accept JWTs signed by the removed key because the check at line 101 only consults the stale snapshot — there is no live/on-demand revocation check, no TTL per key, and no invalidation trigger tied to a metadata update event.

An attacker who possessed a legitimate signer key before revocation can, immediately after the owner removes/rotates that key, sign and submit an `HTTPTriggerRequest` (`gateway_common.MethodWorkflowExecute` via `HandleJSONRPCUserMessage` → `triggerHandler.HandleUserTriggerRequest` → eventually calling `Authorize`) and have it accepted, because the cached map still contains the old key entry.

### Impact Explanation
This allows continued unauthorized triggering of a victim's workflow (action impersonation / unauthorized job run attributed to the workflow owner) using a credential the owner believes has been revoked, for up to `MetadataPullIntervalMs + MetadataAggregationIntervalMs` (default ~2 minutes, operator-configurable). This maps to the "unauthorized job run" / "request impersonation" bounty impact class since the attacker can invoke the victim's workflow's HTTP trigger and any downstream side effects (calling external endpoints tied to the workflow, consuming outbound HTTP action budget under that workflow's owner) after revocation.

### Likelihood Explanation
Preconditions require the attacker to have previously held a valid signer key for the workflow (e.g., a compromised private key that the owner is in the process of rotating out) — no additional privilege is needed beyond what they already had. The exploit is trivially repeatable: sign and send an `HTTPTriggerRequest` immediately after revocation and before the next aggregation tick; this is a deterministic timing window rather than a race requiring luck, bounded by fixed, low, configurable intervals.

### Recommendation
Do not treat `syncMetadata`'s ticker cadence as the authorization freshness boundary for security-sensitive revocation. Options: (1) trigger an immediate `syncMetadata`-equivalent refresh (or targeted key invalidation) as soon as a metadata push/pull response indicates a key was removed, rather than waiting for the next ticker; (2) attach a short TTL/generation counter to `authorizedKeys` entries so revoked keys expire independent of the sync cycle; (3) allow the workflow owner to explicitly force-refresh/revoke via an authenticated path that synchronously updates `h.authorizedKeys` under `h.mu` before an ack is returned, closing the "undeletable" access window.

### Proof of Concept
Go unit test in `core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler_test.go`:
1. Construct a `WorkflowMetadataHandler` with a `workflowID` and manually seed `h.authorizedKeys[workflowID] = {K: {}}` (simulating a completed `syncMetadata` cycle where key K was authorized).
2. Build a signed JWT/request for K and call `Authorize(workflowID, token, req)` — assert success (baseline).
3. Simulate revocation by directly mutating the aggregator's underlying source data (or by never calling `syncMetadata` again after removing K from the aggregator's collected metadata) — i.e., do NOT call `syncMetadata`.
4. Call `Authorize(workflowID, token2, req2)` again with a fresh JWT signed by K — assert that it currently **succeeds** (demonstrating the vulnerability) despite K no longer being present in the upstream/source-of-truth metadata.
5. Add assertion that after invoking `h.syncMetadata(ctx)` (simulating the next tick with updated metadata that excludes K), a subsequent `Authorize` call with K fails with `"is not authorized for workflow"` — confirming the gap only exists in the pre-tick window.
