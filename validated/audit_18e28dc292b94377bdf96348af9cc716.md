### Title
Cross-user callback hijacking via duplicate MessageId in `HandleLegacyUserMessage` - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
`HandleLegacyUserMessage` stores each incoming trigger request's callback in `h.savedCallbacks` keyed solely by the attacker-controlled `msg.Body.MessageId`, without checking whether that ID is already in use. An attacker who sends a signed message with the same `MessageId` as a victim's in-flight request silently overwrites the victim's saved callback, so the node's eventual response for that ID is delivered to whichever callback is currently stored in the map.

### Finding Description
`MessageId` is a free-form string (length-bounded only) supplied by the caller and validated purely for length/format in `Message.Validate()`, with no per-sender namespacing or uniqueness enforcement: [1](#0-0) . The gateway's dispatcher `ProcessRequest` accepts any signed legacy request and forwards it straight to `HandleLegacyUserMessage` without any allowlist/quota check — a TODO in the handler itself confirms this: `// TODO: apply allowlist and rate-limiting here` [2](#0-1) .

In `HandleLegacyUserMessage`, after basic payload/timestamp/method validation, the handler unconditionally writes into the shared map under the mutex, overwriting any prior entry with the same key: [3](#0-2) 

When a node later responds, `handleWebAPITriggerMessage` looks up and deletes the callback purely by `MessageId` and sends the response to whatever callback is currently stored — it has no knowledge of which sender originally owned that ID: [4](#0-3) 

Exploit flow: (1) victim sends a `web_api_trigger` request with `MessageId = "X"`; the gateway forwards it to the DON and stores victim's callback under key `"X"`. (2) Before the DON responds, attacker sends their own independently-signed request also using `MessageId = "X"` (attacker fully controls this field and only needs a valid ECDSA signature over their own message, which any unprivileged sender can produce). This second call replaces `h.savedCallbacks["X"]` with the attacker's callback. (3) When the DON eventually sends its trigger response for ID `"X"` (in response to the victim's original forwarded request, since `respMsg`/node-side echoing keeps the same ID), `handleWebAPITriggerMessage` delivers it to the attacker's callback instead of the victim's — the victim's HTTP call to the gateway hangs until timeout while the attacker receives the victim's trigger-execution response. The reverse (attacker's request overwritten by a later-arriving victim ID collision) is also possible, causing the victim to receive/consume a response tied to the attacker's own request instead of their own.

No component checks for collision/duplication of `MessageId` in `savedCallbacks` before insertion.

### Impact Explanation
This is cross-user response confusion / request-impersonation: attacker-controlled data (or attacker-visibility of another user's trigger response) crosses a trust boundary between distinct callers of the gateway, and a victim's request can be silently starved (denial of response) while an unrelated party receives it. This matches the "cross-user capability-execution response redirection/consumption" impact class explicitly called out in the audit scope, since the gateway offers no logical isolation between two different senders who happen to choose the same `MessageId`.

### Likelihood Explanation
The precondition is simply the ability to send an arbitrarily signed legacy gateway message (any unprivileged/unauthenticated gateway caller can do this — the handler itself notes allowlisting is not yet implemented). The attacker must guess or otherwise learn a `MessageId` that a victim is concurrently using; if `MessageId`s are predictable, sequential, or otherwise not high-entropy/random (this is caller-chosen, not gateway-generated), collision is trivial to engineer by simply choosing a fixed low-entropy ID and racing a victim, or by an attacker who also acts as (or colludes with) a caller that can observe/predict victim IDs. Since the field is entirely attacker-supplied with no server-side uniqueness guarantee, likelihood is moderate-to-high in any deployment where `MessageId`s are not cryptographically random per caller.

### Recommendation
Reject (rather than silently overwrite) an incoming `HandleLegacyUserMessage` request whose `MessageId` already has a live, non-expired entry in `h.savedCallbacks`, returning a conflict-style error response (e.g., a new `api.ErrorCode` such as `DuplicateMessageIdError`) to the second sender instead of clobbering the map. Additionally consider deriving the map key from `(Sender, MessageId)` or `(DonId, Sender, MessageId)` rather than `MessageId` alone, so that different senders can never collide regardless of ID reuse.

### Proof of Concept
Add a table test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Build two `*api.Message` via `triggerRequest` helper, both using the same `MessageId` ("dup-id") but signed with two different private keys (`nodes[0].PrivateKey` and a second freshly generated key representing an unrelated sender/attacker).
2. Call `handler.HandleLegacyUserMessage(ctx, msgVictim, cbVictim)` and confirm `handler.savedCallbacks["dup-id"]` is set with `Callback == cbVictim`.
3. Call `handler.HandleLegacyUserMessage(ctx, msgAttacker, cbAttacker)` with the same ID from the different signer.
4. Assert (expected fix behavior) that the second call returns an error / rejection response (via `cbAttacker.Wait`) rather than silently succeeding, and that `handler.savedCallbacks["dup-id"].Callback` still equals `cbVictim` (i.e., unchanged).
5. Currently (pre-fix), the test would show the second call succeeds and `handler.savedCallbacks["dup-id"].Callback` becomes `cbAttacker`, demonstrating the victim's callback was overwritten — confirming the vulnerability.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
