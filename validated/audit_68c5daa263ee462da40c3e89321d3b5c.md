### Title
Unprotected ERC4626 deposit lets vault users inflate share price and strand tranche principal - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary

`ProgrammableBorrower` deposits the entire facility balance into an arbitrary same-asset ERC4626 vault at epoch start without a minimum-share or post-deposit value check. A user of that vault can execute a first-depositor/share-price-inflation transaction immediately before `startEpoch`, causing `ProgrammableBorrower` to receive an economically inadequate number of shares and then redeem vault liquidity against the inflated price.

The adapter records the pre-deposit asset amount as epoch principal, but `_vaultNetInterest` only nets the resulting principal shortfall against epoch interest rather than burning strategy tokens or otherwise reducing CDO NAV. In minted-interest mode with no pending withdrawals, `stopEpoch` can therefore succeed while the pool remains silently undercollateralized; the missing principal later surfaces as a default or withdrawal shortfall.

### Finding Description

The programmable-borrower vault is configurable and is validated only for a nonzero address and matching underlying asset; no pricing safety, deposit cap, minimum-share requirement, or protected implementation is enforced. [1](#0-0) 

At `onStartEpoch`, the contract snapshots cash plus current vault assets, deposits its full on-hand underlying balance through raw `vault.deposit`, resets `epochDepositedToVault` to zero, and marks accounting active. [2](#0-1)  The actual deposit helper likewise accepts whatever share amount the external vault returns. [3](#0-2) 

For an ERC4626 implementation whose share mint is based on raw `assets * supply / totalAssets`, an attacker can:

1. Deposit one wei as the first vault user.
2. Transfer-donate `R - 1` underlying directly to the vault, making the apparent price `R` assets per share.
3. Let `startEpoch` deposit pool principal `A`.
4. Cause `ProgrammableBorrower` to receive `floor(A / R)` shares.
5. Redeem the attacker's share against the combined `A + R` vault balance.

With `A / 2 < R <= A`, the facility receives one share while the attacker redeems approximately `(A + R) / 2`; choosing `R` just above `A / 2` removes nearly `A / 4` from the facility's recoverable principal. Vaults that permit a zero-share deposit can strand the full deposit.

`epochStartVaultAssets` intentionally includes the pre-deposit cash amount, while `epochDepositedToVault` is reset to zero. [4](#0-3)  `_vaultNetInterest` then compares current vault assets plus tracked withdrawals to that principal baseline, so the sandwich is detected only as vault loss. [5](#0-4) 

However, the only pool-facing adjustment is `totalInterestDueNow`, which clamps the net result at zero. [6](#0-5)  In minted-interest mode, `IdleCDOEpochVariant` does not pull interest cash and only pulls pending withdrawals; with no pending withdrawals the borrower pull amount is zero. [7](#0-6)  The successful stop path then calls `_updateAccounting` and clears the running epoch without passing the vault shortfall as `_lossAmount` or burning strategy tokens. [8](#0-7) 

The CDO's `_skimDonatedAssets` guard only removes raw underlying held directly by the CDO before epoch accounting. [9](#0-8)  It cannot detect a donation made to the separate ERC4626 vault to manipulate `convertToAssets`.

### Impact Explanation

This is a direct theft and delayed insolvency issue. The attacker removes underlying from the ERC4626 vault, while tranche holders retain strategy-token accounting that still treats the deposited principal as available until a withdrawal or close exposes the shortfall.

For a principal deposit `A`, an attacker using the ordinary one-share rounding outcome can steal approximately `A / 4`; for a vault that mints zero shares, the stranded amount can be the full `A`. In minted-interest mode with no pending withdrawals, the loss is not realized in tranche prices during the compromised stop because vault loss merely reduces `totalInterestDueNow` to zero. The pool can therefore continue operating with inflated NAV, and later depositors or withdrawal requesters absorb the missing principal.

If pending withdrawals or a pool close require liquidity, `onStopEpoch` can withdraw at most the remaining vault position; when economic coverage is absent it returns `true` so that the subsequent CDO `transferFrom` fails and enters the default path. [10](#0-9)  That converts the extracted principal into a borrower-style default even though the configured borrower may not owe the missing vault funds. [11](#0-10) 

### Likelihood Explanation

Likelihood depends on the configured ERC4626 vault's minting defense. A vault with effective virtual-share/asset offsets may limit the theft to dust, but `ProgrammableBorrower` does not enforce that property and can be initialized or later switched to any same-asset ERC4626 vault. [12](#0-11) 

The attack requires no privileged protocol role: an ordinary vault user only needs to deposit first or otherwise manipulate the vault's assets-per-share before a scheduled epoch start. The honest manager still calls `startEpoch`, and the honest owner/manager later calls `stopEpoch`; all manipulated actions are performed by unprivileged vault users or ordinary pool depositors.

A mainnet deployment using a hardened vault such as a properly configured MetaMorpho vault may not be practically exploitable at the full bound, but the adapter itself lacks an explicit slippage invariant and therefore carries an unsafe integration assumption.

### Recommendation

Add an explicit minimum-share/slippage invariant around every ERC4626 deposit:

```solidity
uint256 shares = vault.deposit(_assetAmount, address(this));
uint256 receivedAssets = vault.convertToAssets(shares);
if (receivedAssets + maxDepositSlippage < _assetAmount) {
  revert DepositSlippageExceeded();
}
```

Preferably pass a caller-supplied `minShares` or use a vault integration that supports `mint` with a bounded asset cost. Apply the same check to the initial `onStartEpoch` deposit and any repayment redeposit.

Separately, when `_vaultNetInterest` reports a principal loss that exceeds interest, propagate that loss into `IdleCDOEpochVariant` as `_lossAmount` or another explicit NAV reduction instead of only clamping `totalInterestDueNow` to zero. Restrict configured vaults to audited implementations with inflation resistance and enforce this at initialization and `setVault`.

### Proof of Concept

The following Foundry fork test can be added to `test/foundry/ProgrammableBorrowerCreditVault.t.sol`. It uses the same production deployment setup as the existing programmable-borrower tests, but configures the minimal balance-accounting ERC4626 already present in that harness because it admits the share-price manipulation that production code does not guard against.

```solidity
function testProgrammableBorrowerStartEpochShareInflation() external {
  MockStopEpochLiquidityVault vulnerableVault =
    new MockStopEpochLiquidityVault(USDC);
  address attacker = makeAddr("vaultUser");
  uint256 depositAmount = 100_000 * oneScale;

  vm.prank(manager);
  programmableBorrower.setVault(address(vulnerableVault));

  // Ordinary ERC4626 vault user seeds one share and inflates price.
  deal(USDC, attacker, depositAmount, true);
  vm.startPrank(attacker);
  underlying.approve(address(vulnerableVault), type(uint256).max);
  vulnerableVault.deposit(1, attacker);

  // R just above A/2 causes PB's A deposit to mint only one share.
  uint256 inflatedPrice = depositAmount / 2 + 1;
  underlying.transfer(address(vulnerableVault), inflatedPrice - 1);
  vm.stopPrank();

  deal(USDC, address(this), depositAmount, true);
  idleCDO.depositAA(depositAmount);

  vm.prank(manager);
  cdoEpoch.startEpoch();

  assertEq(
    vulnerableVault.balanceOf(address(programmableBorrower)),
    1,
    "facility deposit minted only one inflated share"
  );

  uint256 pbAssetsBefore = vulnerableVault.convertToAssets(
    vulnerableVault.balanceOf(address(programmableBorrower))
  );
  assertLt(pbAssetsBefore, depositAmount, "principal was stranded");

  vm.prank(attacker);
  vulnerableVault.redeem(1, attacker, attacker);

  uint256 stolen = depositAmount - vulnerableVault.convertToAssets(
    vulnerableVault.balanceOf(address(programmableBorrower))
  );

  // With R ~= A/2, theft approaches A/4 for a one-share deposit.
  assertGt(stolen, depositAmount / 5, "attacker recovered pool principal");

  vm.warp(cdoEpoch.epochEndDate() + 1);
  assertEq(
    programmableBorrower.totalInterestDueNow(),
    0,
    "principal loss only clamps reported interest"
  );

  vm.prank(manager);
  cdoEpoch.stopEpoch(0, 0);

  assertFalse(cdoEpoch.defaulted(), "minted-interest stop hides vault loss");
  assertLt(
    programmableBorrower.totalUnderlying(),
    depositAmount,
    "pool remains undercollateralized"
  );
}
```

The important assertion is not the mock itself: `ProgrammableBorrower` accepts the returned share count without comparing it to a minimum or checking that `convertToAssets(shares)` approximately equals the deposited assets. [3](#0-2)
