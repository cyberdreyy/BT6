### Title
`lockup-factory::create` lets the deposit-funder pick an arbitrary staking-pool whitelist, letting the lockup owner route locked/unvested NEAR to a self-controlled fake pool - ([File: lockup-factory/src/lib.rs])

### Summary
`LockupFactory::create` accepts an optional `whitelist_account_id` parameter that, if supplied, overrides the factory's foundation-configured `staking_pool_whitelist_account_id` for the newly deployed lockup contract, with no restriction that this be the Foundation's official whitelist. [1](#0-0)  This breaks the custody binding the whole lockup/whitelist/staking-pool design depends on: "an account trusted as a pool or whitelist versus the code and arguments that trust was granted for."

### Finding Description
`create` is a `#[payable]`, unauthenticated method - any caller who attaches `MIN_ATTACHED_BALANCE` can invoke it for any `owner_account_id`. [2](#0-1)  The `whitelist_account_id` argument, when present, is used verbatim as the lockup's `staking_pool_whitelist_account_id` instead of the factory's own configured (Foundation-controlled) whitelist:

```
// Defaults to the whitelist account ID given on init call.
let staking_pool_whitelist_account_id = if let Some(account_id) = whitelist_account_id {
    account_id.into()
} else {
    self.whitelist_account_id.clone()
};
``` [3](#0-2) 

This value is passed straight into the lockup contract's `new` constructor and stored as `staking_pool_whitelist_account_id`, which the lockup relies on for the entire remaining lifetime of the contract. [4](#0-3) 

The README documents the exact guarantee this binding is supposed to enforce: the staking pool "should be able to recover delegated tokens back to the lockup from a staking pool... only approved (whitelisted) accounts of staking pool contracts can receive delegated tokens from lockup contracts," and this guarantee underpins the statement "The owner can not lose tokens or block contract operations by using methods under the staking section." [5](#0-4) [6](#0-5) 

When the owner later calls the owner-only `select_staking_pool`, the lockup contract checks the chosen pool against `self.staking_pool_whitelist_account_id` - which, due to the factory bug, can be an account fully controlled by the same party that funded/created the lockup:

```
ext_whitelist::is_whitelisted(
    staking_pool_account_id.clone(),
    &self.staking_pool_whitelist_account_id,
    NO_DEPOSIT,
    gas::whitelist::IS_WHITELISTED,
)
``` [7](#0-6) 

If the attacker deploys their own trivial "whitelist" contract (`is_whitelisted` always returns `true`) and their own "staking pool" contract that merely mimics the expected interface (`deposit_and_stake`, `get_account_staked_balance`, `unstake`, `withdraw`) while giving the attacker a full-access key to move the underlying NEAR balance directly, the owner can then call `select_staking_pool` against that fake pool, `deposit_and_stake` locked/unvested funds into it, and subsequently drain the NEAR from the pool account outside of the lockup contract's control - all without the lockup contract's staking/vesting/termination logic ever being able to intervene.

The equality this breaks:
```
lockup.staking_pool_whitelist_account_id  ==  factory.whitelist_account_id (the Foundation-vetted whitelist)
```
is violated whenever `create` is called with a non-default `whitelist_account_id`, because the factory performs no check that the supplied whitelist account is the Foundation's whitelist, is on any approved list, or is even restricted to Foundation-only callers.

### Impact Explanation
This matches the Critical impact bucket: "locked or unvested tokens released early" / "a wrongly whitelisted or wrongly parameterised deployment." A lockup contract intentionally created (or funded) with an attacker-controlled whitelist can have its entire locked, vesting-restricted, and even foundation-clawback-protected balance delegated to an attacker-controlled "staking pool" and then extracted outside the lockup's schedule and outside the Foundation's termination/clawback mechanism. This directly defeats the lockup contract's core purpose.

### Likelihood Explanation
High/certain reachability: `create` has no access control beyond attaching the minimum deposit, and `whitelist_account_id` is an explicit, documented, unauthenticated parameter of the public API (also exercised by the existing test `test_create_lockup_with_custom_whitelist_success`, which confirms the override path is live functionality, not dead code). [8](#0-7)  Any funder/creator of a lockup can trigger this; no oracle desync, no multisig compromise, no privileged role is required.

### Recommendation
Remove the caller-suppliable `whitelist_account_id` override (or restrict it to be settable only by the Foundation account / restricted to a Foundation-maintained allow-list of whitelist contracts), so every lockup deployed by the factory always uses the canonical `self.whitelist_account_id` configured at factory `new()`/init time.

### Proof of Concept
1. Attacker deploys `EvilWhitelist` with `is_whitelisted(_) -> true` for any account.
2. Attacker deploys `EvilPool` mimicking the staking-pool interface (`deposit_and_stake`, `get_account_staked_balance`, `unstake`, `withdraw_all`) but with a full-access key retained by attacker allowing direct NEAR withdrawal outside contract logic.
3. Attacker calls `lockup_factory.create(owner_account_id: <attacker-or-victim>, ..., whitelist_account_id: Some(EvilWhitelist))` with the required deposit. [1](#0-0) 
4. The deployed lockup stores `staking_pool_whitelist_account_id = EvilWhitelist`. [9](#0-8) 
5. Owner calls `select_staking_pool(EvilPool)`; `is_whitelisted` call to `EvilWhitelist` returns `true`, so `EvilPool` is accepted. [7](#0-6) 
6. Owner calls `deposit_and_stake` to move locked/unvested NEAR into `EvilPool`.
7. Attacker withdraws the NEAR from `EvilPool` directly using the retained full-access key, bypassing lockup/vesting/termination restrictions entirely.

Note: I was not able to fully inspect `lockup/src/owner.rs`'s `deposit_and_stake`/staking amount-limiting logic within the available iterations (only grep match counts were returned, not full content), so the exact cap on how much of the lockup balance (all vs. only "liquid" portion) can be staked in one call is not fully confirmed from source in this session - this should be verified directly in `lockup/src/owner.rs` and `lockup/src/internal.rs` before final write-up.
