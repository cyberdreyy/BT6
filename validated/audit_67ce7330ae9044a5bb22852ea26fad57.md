**Analysis:**

`EncodedChildrenHeader::encode_flexible_data` writes `child.unwrap().pos` — the child's `ArenaPos` — into the flexible children slot purely as an in-memory pointer used later to *locate* the child node within the same arena, not as data that ends up in the hashed/serialized representation.

The actual hash computation path is decoupled from arena positions:

- Each non-leaf node's `CryptoHash` is computed once at construction time in `MemTrieNodeId::new_impl` / `to_raw_trie_node_with_size_non_leaf`, which recursively pulls `view.node_hash()` from children — themselves either previously-computed cached hashes (`NonLeafHeader`) or recomputed for leaves — and this hash is stored in the node's `NonLeafHeader` field, not derived from `pos`. [1](#0-0) [2](#0-1) 

- `ChildrenView::get`/`iter` use the stored `pos` only to construct a `MemTrieNodePtr` for navigation via `read_ptr_at`, and `to_children()` converts children into a `Children` struct populated with `node_view.node_hash()` (a `CryptoHash`), never with the raw `pos` value. [3](#0-2) 

- Likewise, `compute_hashes_and_serialized_nodes` in `memtrie_update.rs` builds `RawTrieNode`/`Children` purely from `CryptoHash` values (`get_hash` returns `CryptoHash`), and the final `node_hash` fed into consensus-relevant `TrieChanges::new_root` is `hash(&node_serialized)` of that borsh-serialized `RawTrieNodeWithSize`, which contains only `CryptoHash` fields for children, never arena positions. [4](#0-3) 

Since `pos` is an ephemeral, process-local navigation aid that never enters the `RawTrieNode`/`RawTrieNodeWithSize` structures that get borsh-serialized and hashed, there is no mechanism by which arena-layout-dependent values leak into `node_hash()`. The differential scenario described (fresh `loading.rs` load vs. incremental `memtrie_update.rs` application) would produce different arena layouts (different `pos` values), but both code paths independently recompute or propagate `CryptoHash` values that are purely functions of the trie's logical content (keys/values), so `node_hash()` and thus the state root remain deterministic and layout-independent. This is confirmed by the existing unit tests (`core/store/src/trie/mem/node/tests.rs`) that assert `node_hash()` equals `hash(borsh::to_vec(raw_node))` regardless of arena allocation order. [5](#0-4) 

There is no unprivileged-attacker-reachable path here either — this is an internal invariant of the memtrie data structure, not something influenced by transaction inputs.

    pub fn to_children(&self) -> Children {
        let mut nodes = [None; NUM_CHILDREN];
        if self.mask == 0 {
            return Children(nodes);
        };

        // cspell:words ptrs
        let mut node_ptrs = [None; NUM_CHILDREN];
        let mut j = size_of::<usize>() * self.mask.count_ones() as usize;
        // Execute all `read_ptr_at` in reverse to avoid repeat bound checks.
        // Additionally, issue reads for the node kinds before moving on to compute sha256 hashes,
        // thus hopefully giving CPU more time to load the relevant lines into the cache.
        for i in (0..NUM_CHILDREN).rev() {
            let bit = self.mask & (1 << i);
            if bit != 0 {
                j -= size_of::<usize>();
                let ptr = MemTrieNodePtr::from(self.children.read_ptr_at(j));
                let kind = ptr.get_kind();
                node_ptrs[i] = Some((ptr, kind));
            }
        }

        for (node, node_ptr) in std::iter::zip(nodes.iter_mut().rev(), node_ptrs.into_iter().rev())
        {
            if let Some((node_ptr, kind)) = node_ptr {
                let node_view = node_ptr.view_kind(kind);
                *node = Some(node_view.node_hash());
            }
        }

        Children(nodes)
    }
