## Title
Removing a multisig member/key does not purge that member's existing confirmations on other pending requests, allowing a request to execute with confirmations from fewer *live* members than `num_confirmations` requires — (File: `multisig2/src/lib.rs`)

## Summary
This is the same root cause as the reported `Gov.sol` bug: a party is stripped of its role (governor removed / multisig member deleted), but state that grants authority derived from that party (`pendingGov` / a stored confirmation) is not cleared, so the removed party's authority can still be exercised later. In the NEAR multisig contracts, deleting a member (or deleting a key in the legacy `multisig`) only purges requests *created* by that member, but leaves that member's already-recorded confirmations on *other* still-pending requests untouched. `confirm()` never re-validates that stored confirmations still belong to current members, so a request can be pushed past `num_confirmations` even though fewer currently-live members actually approved it.

## Finding Description
`delete_member` in `multisig2/src/lib.rs` removes the member from `self.members`, but when scrubbing state it only removes requests where the request was *originated* by that member: [1](#0-0) 

Any request created by a *different* member that the now-removed member had previously confirmed keeps that confirmation entry in `self.confirmations` (`LookupMap<RequestId, HashSet<String>>`), because that map is only cleaned for requests filtered by `r.member == member` (the creator), not by scanning confirmation sets for the removed member's string identity.

`confirm()` then decides whether to execute purely by counting entries in that (now stale) `HashSet`: [2](#0-1) 

There is no check inside `confirm()`, `execute_request()`, or `assert_valid_request()` that every account/key present in the stored confirmations set is still a current member — it only validates that the *caller* confirming right now is a current member: [3](#0-2) 

The equality that should hold is:
`confirmations counted toward num_confirmations == confirmations from currently live members`

But after a member removal, `confirmations counted` can include votes cast by accounts that are no longer members, breaking this binding.

The same pattern exists in the legacy `multisig/src/lib.rs`: `DeleteKey` only removes requests where `r.signer_pk == pk` (the requester), not the deleted key's confirmations recorded on other requests: [4](#0-3) 

## Impact Explanation
This maps to the explicitly listed Critical impact: "a multisig request executed below threshold." A request can be executed on-chain (e.g., a `Transfer`, `FunctionCall`, or `AddKey`/`AddFullAccessKey` action against the multisig account) with fewer live-member approvals than the contract's configured `num_confirmations`, undermining the entire security assumption of the multisig (that N-of-M *current* members must agree before any privileged action executes).

## Likelihood Explanation
Member/key rotation is a normal, expected multisig operation (e.g., replacing a suspected-compromised key, offboarding a member). Any time a member is removed after having confirmed — but not created — a pending request, that stale confirmation persists and silently counts toward execution. No special privilege beyond ordinary multisig membership and normal request/confirm/delete-member flows is required to trigger the divergence; it does not depend on redeploys, foundation-only calls, or social engineering.

## Recommendation
When deleting a member (or a key in `multisig`), scan `self.confirmations` for *all* pending requests and remove the deleted member's/key's entry from every confirmation set, not just from requests it created. Alternatively, re-validate at `confirm()`/execution time that every entry in the stored confirmation set still corresponds to a current member before counting it toward `num_confirmations`.

## Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C, D]`, `num_confirmations = 3`.
2. Member `B` calls `add_request` to create request `R` (e.g., `Transfer` funds out of the multisig account).
3. Member `A` calls `confirm(R)` — recorded confirmations for `R`: `{A}` (1/3).
4. Separately, members confirm and execute a `DeleteMember { member: A }` request (a legitimate, self-request action requiring 3 confirmations from B, C, D) — `A` is removed from `self.members`. Because `R` was created by `B`, not `A`, the filter in `delete_member` does not touch `R` or its confirmations; `A`'s vote `{A}` on `R` survives.
5. `B` and `C` (now only 3 live members remain: B, C, D) call `confirm(R)`. Confirmation set for `R` becomes `{A, B, C}` — length 3 — meeting `num_confirmations = 3`, so `execute_request(R)` fires via `confirm()`'s branch at `multisig2/src/lib.rs:304-309`.
6. `R` executes even though only 2 of the 3 currently-live members (`B`, `C`) actually approved it post-removal — the configured 3-of-N threshold was bypassed using a stale confirmation from a removed member. [5](#0-4)

        self.assert_valid_request(request_id);

            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);

        }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
