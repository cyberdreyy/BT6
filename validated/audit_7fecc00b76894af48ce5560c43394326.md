### Title
Missing RunnerID/SystemID ownership check in `resumeDependencies` allows cross-job container hijack via forged `EnvironmentKey` - (executors/docker/docker.go)

### Summary
`resumeDependencies` (executors/docker/docker.go:1515-1577) parses `e.Build.EnvironmentKey()` and immediately trusts `fields.buildContainerID` to call `e.dockerConn.ContainerInspect`, adopting whatever container is returned as `e.buildContainer`/`e.buildContainerID`. Unlike the equivalent autoscaler code path, it never verifies that the `EnvironmentKey`'s `RunnerID`/`SystemID` actually match the runner instance processing the resume, so a forged or replayed key pointing at an unrelated container is accepted at face value.

### Finding Description
The suspend/resume protocol is: `Build.suspendEnvironment` (common/build.go:289-308) mints an `EnvironmentKey{RunnerID, SystemID, Fields}` and serializes it as `<runner-id>/<system-id>/<fields>` [1](#0-0) . On resume, `Build.EnvironmentKey()` exposes `b.Job.SuspendOptions.EnvironmentKey` verbatim whenever the `SuspendableEnvironments` feature flag is on [2](#0-1) .

In the docker executor, `resumeDependencies` calls `common.ParseEnvironmentKey` and `parseEnvKeyFields`, then goes directly to `ContainerInspect(fields.buildContainerID)` with no check that the parsed `envKey.RunnerID`/`envKey.SystemID` correspond to this runner/machine: [3](#0-2) 

Compare this to the autoscaler executor's `validateEnvKey`, which explicitly rejects keys not issued by the current runner/machine before trusting any embedded fields: [4](#0-3) 

`parseEnvKeyFields` itself only checks for non-empty strings — it performs no ownership, label, or provenance validation of the IDs: [5](#0-4) 

Because Docker's `ContainerInspect` accepts any ID/prefix that resolves on the shared daemon (it is not scoped per caller), and gitlab-runner's docker executor performs no equivalent of `validateEnvKey`'s ownership check, `resumeDependencies` will happily adopt a container ID supplied through the job's `SuspendOptions.EnvironmentKey`, even if that ID belongs to a different job/project on the same shared Docker host. Once adopted, `e.buildContainer`/`e.buildContainerID` are used by the executor for subsequent `exec` operations, so job steps run inside the foreign job's container.

The originally proposed exploit mechanism (guessing a short/ambiguous ID prefix that collides with a live victim container) is impractical on its own, since Docker container IDs are 64-character random hex values minted by the daemon and not disclosed to other tenants, and `Suspend()` records the full ID rather than a truncated one. However, the actual root cause is broader than prefix collision: nothing stops an attacker (who can influence/replay the `EnvironmentKey` value returned by the backend for their job) from submitting the exact full container ID of any container they can observe/target, since there is no cryptographic or ownership binding checked in this code path.

### Impact Explanation
If a job's `EnvironmentKey`/`SuspendOptions` value is not itself protected against tampering/replay before reaching `resumeDependencies`, a job can be made to adopt an arbitrary container running on the shared Docker host as its own `buildContainer`. Subsequent script execution steps run via `docker exec` inside that container, exposing that container's filesystem, environment variables (including `CI_JOB_TOKEN` and masked/predefined variables), and running processes to the resuming job — a direct cross-project confinement violation and secret-exfiltration path.

### Likelihood Explanation
Requires: (1) `SuspendableEnvironments` feature flag enabled, (2) a shared Docker host used across jobs/projects, and (3) the ability to influence the `EnvironmentKey` string delivered back to the runner for a job (this last precondition is asserted by the question but is enforced/mediated by the GitLab backend, which is outside this repository — its actual enforceability could not be verified from the Runner codebase alone). Given precondition (3) holds, exploitation is deterministic and repeatable since there is no defense-in-depth check in `resumeDependencies` itself.

### Recommendation
Add an ownership check in the docker executor's resume path mirroring the autoscaler's `validateEnvKey`: verify `envKey.RunnerID == e.Build.Runner.ID` and `envKey.SystemID == e.Build.Runner.GetSystemID()` before trusting any fields, and additionally validate that the inspected container carries labels matching the current job/runner (as already used elsewhere via `executors/docker/internal/labels`) before adopting it as `e.buildContainer`.

### Proof of Concept
```go
// executors/docker/docker_test.go
func TestResumeDependencies_RejectsForeignEnvironmentKey(t *testing.T) {
    c := docker.NewMockClient(t)
    e := executorWithMockClient(c)
    e.Build.Runner = &common.RunnerConfig{RunnerCredentials: common.RunnerCredentials{ID: 1}, SystemID: "sys-1"}
    e.Build.Runner.FeatureFlags = map[string]bool{featureflags.SuspendableEnvironments: true}

    // Forged key: RunnerID/SystemID do not match this runner, but points at
    // a real container belonging to another job on the shared host.
    e.Build.Job.SuspendOptions.EnvironmentKey =
        "999/other-sys/build-container-id=victim-cid&helper-id=victim-helper-cid"

    err := e.resumeDependencies()

    require.Error(t, err) // should be rejected due to RunnerID/SystemID mismatch
    assert.Empty(t, e.buildContainerID, "must not adopt a container from a mismatched runner/system-id")
}
```
Expected today: the test fails because `resumeDependencies` has no such check and proceeds to `ContainerInspect("victim-cid")`, setting `e.buildContainerID` to the foreign container — demonstrating the missing validation.

```go
func (e *executor) resumeDependencies() error {
	envKey, err := common.ParseEnvironmentKey(e.Build.EnvironmentKey())
	if err != nil {
		return err
	}
	fields, err := parseEnvKeyFields(envKey.Fields)
	if err != nil {
		return err
	}

	buildInspect, err := e.dockerConn.ContainerInspect(e.Context, fields.buildContainerID)
	if err != nil {
		return fmt.Errorf("build container %s not found: %w", fields.buildContainerID, err)
	}
	e.buildContainerID = buildInspect.ID
	e.buildContainer = &buildInspect
```

```go
func validateEnvKey(envKey string, runnerID int64, systemID string) (string, url.Values, error) {
	key, err := common.ParseEnvironmentKey(envKey)
	if err != nil {
		return "", nil, err
	}

	if key.RunnerID != runnerID {
		return "", nil, errors.New("environment key was not issued by this runner")
	}
	if key.SystemID != systemID {
		return "", nil, errors.New("environment key was not issued by this machine")
	}

	data, executorFields, err := parseEnvKeyFields(key.Fields)
	if err != nil {
		return "", nil, fmt.Errorf("environment key fields: %w", err)
	}

	return data.acqKey, executorFields, nil
}
```

```go
func parseEnvKeyFields(fields url.Values) (envKeyFields, error) {
	k := envKeyFields{
		buildContainerID:  fields.Get(envKeyBuildContainerIDField),
		helperContainerID: fields.Get(envKeyHelperIDField),
	}
	if k.buildContainerID == "" {
		return envKeyFields{}, fmt.Errorf("%s is required", envKeyBuildContainerIDField)
	}
	if k.helperContainerID == "" {
		return envKeyFields{}, fmt.Errorf("%s is required", envKeyHelperIDField)
	}
	if raw := fields.Get(envKeyServiceIDsField); raw != "" {
		k.serviceContainerIDs = strings.Split(raw, ",")
		for _, id := range k.serviceContainerIDs {
			if id == "" {
				return envKeyFields{}, fmt.Errorf("%s contains an empty ID", envKeyServiceIDsField)
			}
		}
	}
	return k, nil
}
```
