### Title
Stale confirmations from removed multisig members are still counted toward the execution threshold, allowing requests to execute below the live-member quorum - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::confirm` in `multisig2/src/lib.rs` decides whether to execute a request purely by comparing the size of the stored `confirmations: HashSet<String>` against `num_confirmations`. When a member is removed via `delete_member`, only requests *created* by that member are purged; confirmations that member previously cast on requests created by other members remain in the `confirmations` map. Those stale confirmations still count toward the threshold check in `confirm`, so a request can execute with fewer live, currently-authorized confirmers than `num_confirmations` requires.

### Finding Description
- `confirm` (multisig2/src/lib.rs#L294-315) computes `confirmations.len() as u32 + 1 >= self.num_confirmations` to decide execution, using whatever is already in the `confirmations` set for that `request_id`. [1](#0-0) 
- `delete_member` (multisig2/src/lib.rs#L356-379) removes a member and cleans up only the requests that member *authored* (`filter_map(... if r.member == member ...)`), clearing `confirmations` for those. It does not iterate over `confirmations` values of other, still-active requests to strip out the removed member's confirmation entry. [2](#0-1) 
- `assert_valid_request`, called from both `confirm` and `delete_request`, only checks that the *caller* is currently a member; it performs no validation over the historical entries already stored inside `confirmations`. [3](#0-2) 

The binding that should hold is: `confirmations counted == confirmations from accounts that are members at execution time`. Because stale entries from removed members are never purged from requests they didn't author, this equality is violated — the count can include confirmers who are no longer part of the multisig.

### Impact Explanation
This crosses the authorization/threshold boundary explicitly called out in the rules ("confirmations counted versus live members"). A request (e.g., `Transfer`, `AddKey`/`AddMember`/`DeleteMember`, `FunctionCall`) can execute — moving NEAR or granting access — with real approval from fewer live members than `num_confirmations` mandates. This matches the Critical impact category: "a multisig request executed below threshold."

### Likelihood Explanation
No special privilege is required beyond being an existing member who confirms a request before being later removed — a routine, expected lifecycle event for any multisig (member rotation/removal is a first-class supported action, `DeleteMember`). Any remaining member(s) confirming afterward will unknowingly execute a request that is effectively short of live approvals. No malicious node, redeploy, or victim key is needed — this is triggered purely through the contract's own supported member-management and confirmation flow.

### Recommendation
When executing `DeleteMember`, iterate over all `confirmations` entries (not just requests authored by the removed member) and strip the removed member's identifier from every confirmation set; alternatively, revalidate at `confirm`-time that every entry in `confirmations.get(&request_id)` still belongs to `self.members` before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with 3 members (A, B, C) and `num_confirmations = 2`.
2. Member A calls `add_request` to create a `Transfer` request (not self-confirmed).
3. Member B calls `confirm(request_id)` — this only inserts B into the `confirmations` set since `1 + 1 < 2` (len 0 +1 = 1, not >= 2), so it's stored, not yet executed.
4. Members reach consensus to remove B (e.g., key compromise) via a separate `DeleteMember { member: B }` request that reaches quorum and executes through `delete_member` — this only purges requests *authored* by B; the transfer request from step 2 (authored by A) is untouched, so B's confirmation entry remains in its `confirmations` set. [2](#0-1) 
5. Member C calls `confirm(request_id)` on the original transfer request. `confirmations.len()` is `1` (B's stale entry) `+ 1 (C) >= 2`, so `execute_request` runs the transfer. [4](#0-3) 
6. Result: funds moved with approval from only one live member (C) plus one phantom, removed member (B) — the 2-of-3 threshold was never actually satisfied by live members.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************

            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);

        }
