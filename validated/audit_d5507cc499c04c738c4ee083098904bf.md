### Title
Miner-controlled activity-timer refresh via repeated non-progressing proposals stalls the fallback-to-prior-tenure mechanism - (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary
`check_latest_block_in_tenure` treats certain rejected/non-progressing block proposals as valid "miner activity" and refreshes a per-tenure activity timestamp via `SignerDb::update_last_activity_time`. That timestamp is the sole input to the miner-inactivity timeout that lets the signer set fall back to a prior, working tenure when the current miner stalls. A malicious (or simply non-cooperative) current-tenure miner — who holds exactly one sortition slot and needs no signer majority — can therefore keep sending cheap, non-canonical/insufficient proposals at a cadence just inside the grace window to perpetually reset the clock, exactly mirroring the MonoX pattern of periodic "micro-transactions" used solely to keep a stale/attacker-favorable state alive and block everyone else.

### Finding Description
`check_latest_block_in_tenure` rejects a proposal that does not confirm as many blocks as expected (`block.header.chain_length <= info.block.header.chain_length`), but before returning `Ok(false)` it checks whether the existing signed tip is still "fresh enough" per `reorg_attempts_activity_timeout`, and if so calls `signer_db.update_last_activity_time(...)` to mark the attempt as legitimate miner activity: [1](#0-0) 

A second, similar path exists for proposals that only conflict with a locally pre-committed (unsigned) block — again refreshing activity purely because a proposal arrived, independent of whether it will ever become canonical: [2](#0-1) 

`update_last_activity_time` unconditionally overwrites the tenure's last-activity timestamp on every call: [3](#0-2) 

Per `docs/signer-flows.md`, this timestamp is exactly what gates the miner-inactivity fallback: a signer only reverts to `make_miner_state(prior sortition)` once it has been "inactive past `block_proposal_timeout`," measured as time since last recorded activity, and never times out at all if it has already signed a block in the tenure: [4](#0-3) 

Put together: the current miner does not need to produce a valid, canonical, or even node-acceptable block to keep its tenure "alive" in the eyes of the signer set. It only needs to send a proposal often enough (faster than `block_proposal_timeout`, and within `reorg_attempts_activity_timeout` of the last real signed block) that gets rejected by `check_latest_block_in_tenure` for insufficient height/conflicting with the current tip. Each such rejected proposal still refreshes `last_activity_time`, resetting the inactivity clock the fallback logic depends on. This breaks the liveness invariant that a stalled/malicious miner will eventually be timed out and replaced by falling back to the prior tenure — the equivalent of MonoX's malicious lister keeping the stale price "fresh" via periodic microtrades to block real economic activity in the pool, except here the "pool" is the signer set's ability to make progress on a working tenure.

### Impact Explanation
This is a High-impact liveness wedge: a single miner (one sortition slot, no majority of signers required) can indefinitely suppress the state machine's own inactivity-timeout/fallback mechanism by gossiping cheap, doomed-to-be-rejected block proposals. While wedged, the network makes no progress in that tenure, and signers never fall back to a prior working miner, matching the impact category "a signer wedged into never signing valid blocks... or acting on a stale reward set/threshold" via a stale/never-progressing tenure being kept artificially "active."

### Likelihood Explanation
Likelihood is high because: (1) it requires only the already-elected current-tenure miner (a single actor achievable by any miner who wins a sortition), (2) it uses ordinary `BlockProposal` gossip that already flows through the normal proposal path (`handle_block_proposal` → `check_block_against_state` → chainstate `check_proposal` → `check_latest_block_in_tenure`), and (3) the timing constraints (`reorg_attempts_activity_timeout`, `block_proposal_timeout`) are locally-known configuration values a miner can trivially stay under, requiring no signer collusion, no signature forgery, and no protocol-version straddling.

### Recommendation
Do not treat a rejected/non-progressing proposal (one that fails the height/conflict check in `check_latest_block_in_tenure`) as evidence of legitimate miner activity for the purposes of the inactivity-timeout fallback. Either: (a) stop calling `update_last_activity_time` from the rejection branches in `check_latest_block_in_tenure` entirely, or (b) require the refreshed activity to be tied to a proposal that actually advances the tip (e.g. only count it if the proposal is provably higher than any tip the signer has already seen, not merely "not stale yet"), or (c) bound the number of times a single tenure's activity timer can be refreshed by non-progressing proposals before the fallback path is forced regardless.

### Proof of Concept
1. Miner M wins sortition and starts tenure T. Some signers sign an initial block, giving `get_last_signed_block(T)` a real tip at height H.
2. M refuses (or is unable) to produce any further valid/canonical block, but instead broadcasts a stream of proposals at height ≤ H (e.g., re-proposing the same/lower height, or a competing block conflicting with the pre-committed but unsigned tip) at an interval shorter than `block_proposal_timeout` and within `reorg_attempts_activity_timeout` of the last signed block's timestamp.
3. Each proposal is correctly rejected by `check_latest_block_in_tenure` (per lines 390-419 / 422-448 in `stacks-signer/src/chainstate/mod.rs`), but every rejection still calls `signer_db.update_last_activity_time(T, now)`.
4. `check_miner_inactivity`/`is_timed_out` (docs/signer-flows.md section 8) never observes `now - last_activity_time > block_proposal_timeout`, so `FALL["fall back to prior tenure"]` is never triggered.
5. The signer set is wedged waiting on tenure T indefinitely, with no other miner's tenure taking over, even though M never produces a usable block.

    pub fn update_last_activity_time(
        &mut self,
