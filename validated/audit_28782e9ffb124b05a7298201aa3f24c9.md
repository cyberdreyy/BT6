### Title
Pending withdraw receipts from earlier epochs escape `stopEpochWithDuration` loss haircut and are paid at par — ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`collectWithdrawFunds` distributes a realized stop-epoch loss across *all* pending withdraw receipts (`pendingWithdraws` is a global aggregate), but stores the haircut under a single key: `lossRecoveryPriceByEpoch[epochNumber]`. The claim path, `_claimLossAdjustedWithdrawRequest`, only clears the per-epoch receipts recorded under `lastWithdrawRequest[_user]`. Receipts the same user opened in an earlier epoch and left unclaimed remain in the `withdrawsRequests` aggregate and are then paid at par by `_claimFundedWithdrawRequest`. The pool was only funded with the haircutted total, so the user extracts more than their funded share.

### Finding Description
The bug chain:

1. `collectWithdrawFunds` computes the loss on the *global* `pendingWithdraws` basis and stores a single `lossRecoveryPriceByEpoch[epochNumber]` [1](#0-0) 
2. `requestWithdraw` records receipts per epoch via `withdrawsRequestsByEpoch[_user][currentEpoch]` but also into the aggregate `withdrawsRequests[_user]`, and updates `lastWithdrawRequest[_user]` to the newest epoch. The guard at lines 263–271 only blocks a *new* request when the epoch pointed at by `lastWithdrawRequest` already has a stored loss price — it cannot protect a loss applied later [2](#0-1) 
3. On claim, `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` and calls `_clearWithdrawClaimForEpoch(_user, lossEpoch, false)`, which only zeroes `withdrawsRequestsByEpoch[_user][lossEpoch]` and decrements the aggregate by that epoch's piece [3](#0-2) [4](#0-3) 
4. `_claimFundedWithdrawRequest` then pays the entire remaining `withdrawsRequests[_user]` at par (plus APR0 buckets) [5](#0-4) 

So a user with a stale unclaimed receipt from epoch N plus a fresh request in epoch M (loss epoch) gets: `M_receipt * lossRecoveryPrice + N_receipt * 100%`, although the borrower funded only `pendingBasis * lossRecoveryPrice` total. The haircut computed on `pendingBasis` implicitly included the N-epoch receipt — its loss share is simply never collected.

This mirrors the OpenCloud bug class: scope validation is keyed to a single epoch ("the link"), while the underlying claimable resource (the aggregate `withdrawsRequests`) spans multiple epochs, letting the caller reach funds outside the validated scope.

### Impact Explanation
Direct theft / insolvency. The strategy is funded with `pendingBasis - pendingLoss` but pays out more than that. With a 50% `lossRecoveryPrice`, a user holding 100 old + 100 new receipts claims 150 against 100 funded — excess 50 comes from underlyings reserved for other claimants (`_transferFundedClaim` only protects `defaultRecoveryReserve`, not other users' funded claims), causing last-claimant insolvency or permanent loss for other withdrawers.

### Likelihood Explanation
Requires an unprivileged KYC'd lender to: (a) request a withdraw in epoch N and not claim, (b) request again in epoch M (allowed because `lastWithdrawRequest` has no loss price yet), (c) the manager/borrower calls `stopEpochWithDuration` with a partial funding (`_lossAmount > 0`). The attacker cannot force the loss, but the path is deterministic whenever a partial-loss stop occurs while stale receipts exist — a realistic stressed-epoch scenario rather than an edge case, and the stale-receipt state persists indefinitely since claims are permissionless any time after the epoch ends.

### Recommendation
Attribute the loss haircut to every epoch contributing to `pendingBasis`, not just `epochNumber`. Options: iterate per-user request epochs when clearing (store pending epochs per user or a global list of contributing epochs), or on `requestWithdraw` force-claim/rollover all prior receipts into the current request epoch so `withdrawsRequestsByEpoch` has a single non-zero epoch per user, making `lossRecoveryPriceByEpoch[lastWithdrawRequest]` exhaustive.

### Proof of Concept
Foundry fork PoC (sketch, against `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
// 1. user deposits AA, manager startEpoch (epoch N begins)
uint256 t1 = _depositWithUser(user, 100e6);
_stopCurrentEpoch();                 // epoch N+1 buffer
// 2. epoch N+1 running: user requests withdraw of 100
_requestWithdrawWithUser(user, t1);  // withdrawsRequestsByEpoch[user][N+1] = 100
// 3. user does NOT claim; next epoch N+2 starts
_startEpoch();
_requestWithdrawWithUser(user, t2);  // lastWithdrawRequest=N+2, per-epoch[N+2]=100, aggregate=200
// 4. borrower partially funds: manager stopEpochWithDuration with loss covering 50% of pendingBasis=200
//    collectWithdrawFunds(100) -> lossRecoveryPriceByEpoch[N+2] = 0.5e18, pendingWithdraws=0
// 5. user claims:
//    _claimLossAdjustedWithdrawRequest: pays 100 * 0.5 = 50 (clears epoch N+2)
//    _claimFundedWithdrawRequest: pays remaining withdrawsRequests[user] = 100 at par
//    total received = 150 > 100 funded  -> drains other claimants' funded claims
assertGt(claimed, fundedToStrategy); // insolvency / theft of excess 50
```

Confirm with `strategy.withdrawsRequestsByEpoch(user, N+1) != 0` surviving the loss-adjusted claim while being paid via `_claimFundedWithdrawRequest`.

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
