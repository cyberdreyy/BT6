### Title
Permanent ETH Fund Lock When EVM Recipient Contract Lacks `receive()` Function — (`bridge/evm/contracts/BridgeVault.sol`)

---

### Summary

When a user bridges ETH from Sui to Ethereum via `bridge::send_token`, the Sui-side token is **burned immediately and irrevocably**. On the Ethereum side, `BridgeVault.transferETH()` unwraps WETH and attempts a raw ETH call to the recipient. If the recipient is a contract without a `receive()` or `fallback()` function, the call fails and the entire transaction reverts. Because `isTransferProcessed[message.nonce]` is only set **after** a successful transfer, the message is never marked processed, every future execution attempt reverts for the same reason, and the WETH remains permanently locked in the vault with no protocol-level rescue path.

---

### Finding Description

**Sui-side burn (irreversible):**

In `bridge.move`, `send_token_internal()` burns the token before storing the bridge record:

```move
inner.treasury.burn(token);   // token destroyed here
inner.token_transfer_records.push_back(message.key(), BridgeRecord { ... });
``` [1](#0-0) 

There is no rollback path on the Sui side once the burn executes.

**Ethereum-side ETH delivery (hard revert on failure):**

`BridgeVault.transferETH()` unwraps WETH and sends raw ETH:

```solidity
wETH.withdraw(amount);
(bool success,) = recipientAddress.call{value: amount}("");
require(success, "ETH transfer failed");
``` [2](#0-1) 

If `recipientAddress` is a contract without `receive()` or `fallback()`, the call returns `success = false` and the `require` reverts the entire transaction, including the `wETH.withdraw()`. The WETH is restored to the vault.

**Message never marked processed:**

In `SuiBridge.transferBridgedTokensWithSignatures()`, `isTransferProcessed` is set **after** `_transferTokensFromVault()` returns:

```solidity
_transferTokensFromVault(...);          // reverts if ETH delivery fails
isTransferProcessed[message.nonce] = true;  // never reached
``` [3](#0-2) 

Because the revert unwinds the entire call, the nonce is never consumed. Every subsequent attempt to relay the same signed message will hit the same revert. The message is permanently unexecutable.

**No recipient validation on either side:**

The Sui-side `send_token()` only validates address length:

```move
assert!(target_address.length() == EVM_ADDRESS_LENGTH, EInvalidEvmAddress);
``` [4](#0-3) 

There is no check that the EVM address is an EOA or that it can receive ETH. The same applies to `send_token_v2()`. [5](#0-4) 

**No vault rescue path:**

`BridgeVault` exposes no admin function to withdraw WETH directly or redirect a stuck transfer. The only egress paths are `transferETH` and `transferERC20`, both callable only by the `SuiBridge` owner and only through a valid signed bridge message. [6](#0-5) 

---

### Impact Explanation

**Permanent fund lock (High/Medium).** The user's Sui-side tokens are burned at the moment `send_token` executes. The ETH equivalent is permanently trapped in `BridgeVault` as WETH because the bridge message can never be successfully executed and no protocol-level rescue exists. The user suffers a total loss of the bridged amount with no recourse within the protocol.

---

### Likelihood Explanation

**Medium.** Contract addresses are common bridge recipients: multisig wallets (e.g., Gnosis Safe), smart-contract treasuries, DeFi vaults, and DAO contracts. Many such contracts do not implement `receive()`. The bridge UI and protocol provide no warning that the EVM recipient must be capable of receiving raw ETH. A developer or DAO bridging ETH to their treasury contract is a realistic scenario.

---

### Recommendation

1. **Fallback to WETH on failed ETH delivery.** In `BridgeVault.transferETH()`, if the raw ETH call fails, transfer WETH instead of reverting. This mirrors the intent of the original `_sendEthOrWeth()` pattern and ensures the recipient always receives value in some form.

2. **Or: validate recipient at deposit time.** On the Sui side, require the caller to attest that the EVM recipient is an EOA, or enforce this check off-chain before accepting the bridge request.

3. **Add an emergency redirect function.** Add a governance-controlled function to `BridgeVault` or `SuiBridge` that can redirect a stuck transfer to an alternate address, providing a recovery path when delivery fails.

---

### Proof of Concept

```solidity
// Step 1: Deploy a contract with no receive() function
contract NoReceive {
    // No receive() or fallback() — ETH transfers will fail
}

// Step 2: On Sui, bridge ETH to NoReceive's address
// bridge::send_token<ETH>(bridge, ETH_CHAIN_ID, noReceive_address_bytes, token, ctx)
// → token is BURNED on Sui (irreversible)

// Step 3: Validators sign the bridge message

// Step 4: Anyone calls on Ethereum:
bridge.transferBridgedTokensWithSignatures(signatures, message);
// → _transferTokensFromVault() → vault.transferETH(noReceive, amount)
// → wETH.withdraw(amount)  ✓
// → noReceive.call{value: amount}("")  ✗ (no receive function)
// → require(success, "ETH transfer failed")  → REVERT
// → isTransferProcessed[nonce] never set

// Step 5: Retry indefinitely — always reverts with "ETH transfer failed"
// Result: Sui tokens burned, WETH permanently locked in BridgeVault
```

The exact corrupted state: `BridgeVault.wETH.balanceOf(vault)` retains the bridged amount permanently; `isTransferProcessed[nonce]` remains `false` forever; the user's Sui coin supply is reduced by the bridged amount with no corresponding EVM credit.
