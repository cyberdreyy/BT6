### Title
Post-default instant withdraw requests collide with the defaulted epoch's receipt key and drain `defaultRecoveryReserve` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external bug class (prototype pollution: an attacker-controlled key overwriting/merging with an existing object's property) maps onto `IdleCreditVault`'s per-epoch receipt ledgers. `requestInstantWithdraw` writes `instantWithdrawsRequestsByEpoch[_user][epochNumber]` with no `defaultRecoveryFinalized` guard, unlike `requestWithdraw` which explicitly branches on it. After a default is finalized, `epochNumber` stays equal to `defaultRecoveryEpoch`, so a fresh instant request lands on the exact same mapping key that `_claimDefaultedInstantWithdrawRequest` treats as a defaulted-epoch receipt.

### Finding Description
`requestWithdraw` defends this boundary: when `defaultRecoveryFinalized` is set it rejects users with open receipts and routes the request to the isolated `postDefaultRequests` ledger, paid 1:1 from the recovery reserve. `requestInstantWithdraw` has no such branch — it always mints receipt tokens and increments `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epochNumber]`, `instantWithdrawClaimsByEpoch[epochNumber]`, and `pendingInstantWithdraws`.

Two consequences:

1. Post-finalization theft: a user (or the queue contract as `_user`) creates an instant request after `finalizeDefaultRecovery`. Because `epochNumber == defaultRecoveryEpoch`, the new receipt is indistinguishable from a defaulted-epoch receipt. On `claimInstantWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest(_user)` reads `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]`, pays `(claimBasis * defaultRecoveryPrice) / RECOVERY_FULL` from `defaultRecoveryReserve`, and decrements `pendingInstantWithdraws`/reserve — spending recovery funds earmarked for genuine pre-default claimants.

2. Pre-finalization dilution: an instant request made after default but before `finalizeDefaultRecovery` inflates `instantWithdrawClaimsByEpoch[epochNumber]`, which `defaultPendingClaimBasis()` adds verbatim to the haircut basis whenever `pendingInstantWithdraws != 0`. This dilutes `defaultRecoveryPrice` for all legitimate claimants while giving the attacker a pro-rata recovery on a receipt created after the loss was known.

The analog is faithful to CWE-1321: attacker input (a new request) pollutes a shared key (`[user][defaultRecoveryEpoch]`) that a later code path interprets as belonging to a different object class (defaulted receipts).

### Impact Explanation
Direct theft of the isolated default recovery reserve. Every post-finalization instant request of size `X` pays `X * defaultRecoveryPrice / 1e18` from `defaultRecoveryReserve`, which `_transferDefaultRecovery` decrements without checking that the receipt predates the default. Genuine defaulted claimants (pre-default normal and instant withdrawers) are left with unbacked claims; if the reserve is drained, `_transferDefaultRecovery` reverts on underflow, permanently freezing their recovery. Loss is bounded by reserve size and scales linearly with attacker request size.

### Likelihood Explanation
Requires the pool to have defaulted and recovery finalized, plus instant withdrawals still callable through the CDO after that point. I could not fully read `IdleCDOEpochVariant.requestInstantWithdraw`'s post-default gating (whether `defaulted()` or liquidity checks revert the call), so reachability of path (1) depends on the CDO continuing to forward instant requests — the strategy itself imposes no barrier, and the asymmetric hardening (present in `requestWithdraw`, absent here) suggests this path was not intended. Path (2) requires an instant request between default and finalization, a smaller window but the same missing guard.

### Recommendation
Mirror the `requestWithdraw` post-default handling in `requestInstantWithdraw`: if `defaultRecoveryFinalized`, revert when the user has open receipts and route the receipt to a post-default ledger (or reject instant withdrawals outright post-finalization). Additionally, record the request's epoch against `defaultRecoveryEpoch` and reject when `epochNumber == defaultRecoveryEpoch`, and exclude receipts created after default from `defaultPendingClaimBasis`/`instantWithdrawClaimsByEpoch` for the defaulted epoch.
