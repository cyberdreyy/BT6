### Title
Stale confirmations from deleted multisig members allow request execution below the live-member confirmation threshold - (File: multisig2/src/lib.rs)

### Summary
`delete_member` removes a departing member's own pending *requests*, but never scrubs that member's *confirmations* recorded on requests created by other members. Because `confirm` counts raw entries in the `confirmations: LookupMap<RequestId, HashSet<String>>` set regardless of whether the confirming identity is still in `members`, a removed member's stale confirmation continues to count toward `num_confirmations`, letting a request execute with fewer live, currently-authorized confirmations than the configured threshold.

### Finding Description
`confirm` decides whether to execute a request purely by comparing the size of the stored confirmation set to `self.num_confirmations`, with no check that every entry in that set still belongs to a current member: [1](#0-0) 

When a member is removed via `DeleteMember`, `delete_member` only clears requests *authored* by that member (`r.member == member`), and only removes the `num_requests_pk` bookkeeping and the member's access key; it does **not** scan `self.confirmations` for entries where the removed member had confirmed someone else's still-pending request: [2](#0-1) 

Confirmations are keyed by `member.to_string()` in a plain `HashSet<String>`, so once inserted there is nothing linking that entry back to `self.members` for later invalidation: [1](#0-0) [3](#0-2) 

**Binding broken as an equality:** the protocol's invariant is `confirmations counted == confirmations from live members`. After a `DeleteMember` execution, this becomes `confirmations counted > confirmations from live members`, because the departed member's stale entry is still summed toward `num_confirmations`.

### Impact Explanation
This crosses the threshold/authorization boundary explicitly called out as Critical: "a multisig request executed below threshold." A request (including `Transfer`, `FunctionCall`, `AddKey`/full-access-key grants, or further `DeleteMember`/`AddMember` actions) can be pushed to execution with fewer genuinely-current-member confirmations than `num_confirmations` requires, because a since-removed member's earlier confirmation is silently still counted. This directly weakens the K-of-N custody guarantee the multisig is meant to enforce over the account's NEAR balance and access keys.

### Likelihood Explanation
The precondition — a member confirms a request, is later removed from the multisig (a routine `DeleteMember` operation, e.g. offboarding a key or rotating a compromised signer), while that other request remains pending/unconfirmed — is an ordinary, expected multisig-management sequence rather than a contrived edge case. No `require the foundation, a contract owner ... a redeploy` step is needed beyond the multisig's own normal `DeleteMember` flow, which any legitimate member set can and does perform.

### Recommendation
When executing `DeleteMember`, iterate all pending `requests`/`confirmations` (not just the ones the departing member authored) and strip the departing member's identity string from every confirmation `HashSet`. Alternatively, when counting confirmations in `confirm`/before executing, filter the stored set to intersect with `self.members` before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `MultiSigContract::new(members = [A, B, C], num_confirmations = 2)`.
2. Member `B` calls `add_request` for a `Transfer` request `X` (no auto-confirm) — `confirmations[X] = {}`.
3. Member `A` calls `confirm(X)` — since `0 + 1 < 2`, this only inserts `A` into `confirmations[X] = {A}`; not yet executed. [4](#0-3) 
4. Separately, members reach 2-of-3 consensus on a `DeleteMember{ member: A }` request and it executes, removing `A` from `self.members` — but `confirmations[X]` is untouched because `X` was authored by `B`, not `A`: [5](#0-4) 
5. Now only `B` and `C` are live members. `C` calls `confirm(X)`: `confirmations[X].len() == 1` (still containing stale `A`), `1 + 1 >= 2` ⇒ request `X` executes, even though only `C` is a currently-live confirmer besides the (never-confirming) requester `B`. `A`, no longer a member, effectively still supplied one of the two required signatures.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
