### Title
Incomplete request-body redaction blacklist in web request logger exposes tokens/secrets/keys to log readers - ([File: core/web/router.go])

### Summary
The request logging middleware `loggerFunc` (wired into every `/v2` route via `engine.Use(... loggerFunc(app.GetLogger()) ...)` in `NewRouter`) logs the raw request body at Debug level after passing it through `readSanitizedJSON`/`isBlacklisted`, but the redaction blacklist only matches field names containing "password" — not `token`, `secret`, `key`, or similar credential field names. This is the "request logging path near `jsonAPIError`" used by every /v2 controller (the same middleware chain that ultimately calls `jsonAPIError` on error responses), and it will write credential-bearing JSON body fields to the node's logs in plaintext if their key names don't contain "password".

### Finding Description
`loggerFunc` in `core/web/router.go` wraps the full request handling: it buffers the request body, calls `c.Next()`, then logs `"body", readBody(rdr, lggr)` and `"query", redact(c.Request.URL.Query())` at Debug level for every request, including every controller reachable through `jsonAPIError`. [1](#0-0) 

`readBody` calls `readSanitizedJSON`, which iterates top-level JSON keys and redacts only keys matched by `isBlacklisted`: [2](#0-1) 

The blacklist is hardcoded to password-only variants and a substring check for "password": [3](#0-2) 

No entries exist for `token`, `secret`, `apikey`, `accesskey`, or key-export-related field names. Any `/v2` endpoint whose JSON request body contains a credential field not named with "password" (e.g., API-token creation/rotation payloads, external-initiator secrets, key-export passphrase-adjacent fields with different naming, webhook/EI secrets) will have that field logged in cleartext into the node's log output whenever request logging is enabled at Debug level.

The blacklist also only redacts top-level keys — nested JSON objects/arrays are not recursively sanitized, so even a legitimately-named sensitive field nested one level deep would bypass redaction entirely.

However, a caveat for scoping this to the "attacker capability: view-role user" model: this logging happens in a middleware that wraps *every* request the node processes, not something an attacker can specifically target to exfiltrate *another* user's secret — the attacker only sees data from their *own* request logged (assuming they can read logs at all, which requires host/log access, not something a view-role API user has by default). The prompt's threat framing ("obtained through a lower-severity bug") is speculative and not something demonstrated in this codebase — no separate bug elsewhere in this repo is shown that grants a view-role user read access to node logs.

### Impact Explanation
If an attacker with only log-read access (via some other means) can view logs, they would see plaintext values for any request body field not matching the "password" blacklist, including tokens/secrets an authenticated user submits. This matches a credential-disclosure class issue, but it is bounded by: (1) the attacker only ever sees data submitted in requests, i.e., generally their own submitted secrets or other users' secrets only if those users' requests happen to be logged and the attacker can read the log store; (2) it does not directly expose node blockchain private keys or key-export bundles unless those endpoints pass such material through a request body field with a non-"password" name — key export bundles in this codebase are typically returned in the *response* body (via `jsonAPIResponseWithStatus`), and `loggerFunc` does not log response bodies, only request bodies. So the "Critical - key export bundle theft" impact claimed in the question is not substantiated by this code path; at most this is a body-logging redaction gap for request-side credential fields (e.g., token/secret values submitted by the client), which is a real but lower-severity information-disclosure/hardening issue than claimed.

### Likelihood Explanation
Exploitability requires: (1) Debug-level logging enabled on the node (not default in all deployments), (2) the attacker (or an insider) already has read access to the node's log stream/store, and (3) a target request contains a credential-bearing field whose name doesn't include "password" and isn't nested. Given the stated attacker model (only view-role API access, no host/DB/log access), this path is **not reachable** by that attacker alone — log access itself is the actual precondition, which is explicitly excluded from the "attacker controls" in this question ("no operator, admin, host, DB... privileges"). This breaks the required precondition chain, so the specific Critical impact class described (server credential/key theft by an unprivileged view-role API user) is not achievable via `jsonAPIError`/`loggerFunc` alone.

### Recommendation
Expand `blacklist`/`isBlacklisted` in `core/web/router.go` to cover common credential field name patterns (`token`, `secret`, `apikey`, `api_key`, `accesskey`, `privatekey`, `mnemonic`, etc.), make redaction recursive for nested JSON structures, and consider defaulting to redact-by-default for any field not explicitly on an allowlist rather than blacklist-based matching. Also confirm no key-export or secret material is ever routed through request bodies logged in this path.

func readSanitizedJSON(buf *bytes.Buffer) (string, error) {
	var dst map[string]any
	err := json.Unmarshal(buf.Bytes(), &dst)
	if err != nil {
		return "", err
	}

	cleaned := map[string]any{}
	for k, v := range dst {
		if isBlacklisted(k) {
			cleaned[k] = "*REDACTED*"
			continue
		}
		cleaned[k] = v
	}

	b, err := json.Marshal(cleaned)
	if err != nil {
		return "", err
	}
	return string(b), err
}

// NOTE: keys must be in lowercase for case insensitive match
var blacklist = map[string]struct{}{
	"password":             {},
	"newpassword":          {},
	"oldpassword":          {},
	"current_password":     {},
	"new_account_password": {},
}

func isBlacklisted(k string) bool {
	lk := strings.ToLower(k)
	if _, ok := blacklist[lk]; ok || strings.Contains(lk, "password") {
		return true
	}
	return false
}
