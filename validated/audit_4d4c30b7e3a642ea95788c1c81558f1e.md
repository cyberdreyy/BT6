### Title
Signer running v1 chainstate rules can be tricked into double-signing a tenure via a narrower duplicate-block check - (File: `stacks-signer/src/chainstate/v1.rs`)

### Summary
`v1.rs::validate_tenure_change_payload` guards against signing two conflicting tenure-start blocks in the same tenure by calling `signer_db.get_last_globally_accepted_block`, which only matches blocks in `BlockState::GloballyAccepted`. `v2.rs::validate_tenure_change_payload` uses `get_last_signed_block`, which matches both `LocallyAccepted` and `GloballyAccepted`. Because global acceptance is a strictly later, network-wide event than local acceptance, a v1 signer can be made to sign a second, different tenure-start block C for the same tenure after having already signed block B, as long as B has not yet reached `GloballyAccepted`.

### Finding Description
The claimed equality — "two distinct blocks (B, C) in the same tenure both end up signed by this v1 signer" — is real and is confirmed by the codebase's own regression test comment.

- `stacks-signer/src/chainstate/v1.rs:505-518`: the duplicate check queries `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` and only rejects with `RejectReason::DuplicateBlockFound` if a prior block in that tenure is already `GloballyAccepted`. [1](#0-0) 
- `stacks-signer/src/signerdb.rs:1680-1690`: `get_last_globally_accepted_block` filters strictly on `state = GloballyAccepted`. [2](#0-1) 
- By contrast, `stacks-signer/src/chainstate/v2.rs:340-357` performs the same duplicate check but via `get_last_signed_block`, and the code comment explicitly documents the rationale: "Only blocks we have signed (locally or globally accepted) count here." [3](#0-2) 
- `stacks-signer/src/signerdb.rs:1564-1585`: `get_last_signed_block` matches `GloballyAccepted` OR `LocallyAccepted`. [4](#0-3) 
- The codebase itself carries a regression test proving this exact gap was closed for v2 (`check_tenure_change_rejects_when_locally_accepted_block_exists`), with its doc comment stating: "previously, the check used `get_last_globally_accepted_block`, which would miss blocks in `LocallyAccepted` or `PreCommitted` state and incorrectly allow a duplicate tenure change." [5](#0-4) 
- Crucially, no equivalent fix or test exists in `stacks-signer/src/chainstate/v1.rs` or `stacks-signer/src/chainstate/tests/v1.rs` — the regression fix was applied only to v2, leaving v1 with the original narrower (and now proven-unsafe) check.
- `docs/signer-flows.md:428-431` documents this divergence directly: "v2 counts locally or globally accepted blocks (`get_last_signed_block`); v1 counts only globally accepted ones (`get_last_globally_accepted_block`)." [6](#0-5) 

Exploit flow: the attacker wins a single miner slot for tenure `T` with their own BTC. They propose tenure-start block `B` for `T`; the network's signers evaluate it normally and (through ordinary operation — no majority-signer collusion required by the attacker) enough weight signs it so the v1 signer under attack marks `B` as `LocallyAccepted` in its own `signerdb` (`mark_locally_accepted`), but global acceptance (the node observing/accepting the block) has not yet happened — a normal, non-adversarial timing window (e.g., slow propagation to the node, or the group threshold reached just before the node ingests it). Before `B` reaches `GloballyAccepted`, the same attacker (still the tenure's own miner) crafts a second, different tenure-start block `C` for the same tenure `T` (same `tenure_consensus_hash`) and sends it as a `BlockProposal` to the targeted v1 signer. `SortitionsView::check_proposal` (v1) delegates to `validate_tenure_change_payload`, which calls `get_last_globally_accepted_block(T)` — returns `None` because `B` is only `LocallyAccepted` — so `DuplicateBlockFound` never fires, and the proposal for `C` proceeds through pre-commit and signing, producing a second signature over a conflicting block in the same tenure from the same signer, violating the equivocation guard's uniqueness property.

Existing guards that were considered and shown not to prevent this on v1: `check_latest_block_in_tenure`/`get_tenure_last_block_info` (also keyed on `get_last_signed_block`, i.e. it *would* catch this) is **not** re-run for the tenure-change duplicate check — the docs explicitly note "the duplicate check never runs again" and is only exercised in `validate_tenure_change_payload`'s own tenure branch, which on v1 uses the narrower query. The node-side proposal endpoint validates chain-state validity/canonicity but does not by itself prevent the *signer* from placing a second signature — the signer-side check is the intended equivocation guard, and it is the one shown to be narrower on v1.

### Impact Explanation
This breaks the signer's uniqueness/equivocation-guard safety property: a single v1 signer can be induced to place valid signatures over two distinct, conflicting blocks within the same tenure. If this happens across enough v1 signers during a mixed-protocol-version rollout, `C` could gather enough conflicting signature weight to compete with `B`, undermining the "one signed block per tenure" invariant that downstream tenure-advance and reorg logic depend on — a chain-safety issue, matching the Critical category ("a signer signing an invalid, non-canonical, or conflicting block"). The exploit is repeatable each time the attacker wins a miner slot and a v1 signer's local acceptance of the tenure's first block outruns global acceptance.

### Likelihood Explanation
Preconditions are modest and attacker-controllable within the stated threat model: the attacker needs only to win a single sortition slot (their own BTC, as permitted) and to be able to gossip a second `BlockProposal` for the same tenure to a signer still running v1 rules, timed to land in the local-accepted-but-not-yet-globally-accepted window — a window that occurs naturally under normal network latency and is not attacker-privileged. No majority of signers, no compromised keys, and no auth_token are required. The only externally-dependent condition is that the target is still operating under v1 chainstate rules, which the question specifies is the scenario ("mixed-protocol-version rollout").

### Recommendation
In `stacks-signer/src/chainstate/v1.rs::validate_tenure_change_payload`, replace the `signer_db.get_last_globally_accepted_block(...)` call with `signer_db.get_last_signed_block(...)` (matching v2's fix), so the duplicate-tenure-block check rejects proposals when any prior block in the tenure is `LocallyAccepted` or `GloballyAccepted`, not just `GloballyAccepted`.

    /// Return the last signed block in a tenure (identified by its consensus hash).
    /// A block is considered signed if it is locally or globally accepted. Blocks that
    /// have only been pre-committed are excluded, because a pre-commit does not put a
    /// signature over the block and may be safely superseded by a competing proposal.
    ///
    /// This answers "what is the tenure's signed tip?", a different question from
    /// [`SignerDb::has_signed_block_in_tenure`]'s "does a signature bind us to this tenure?",
    /// which is why the predicates deliberately differ on rejected blocks (see there).
    pub fn get_last_signed_block(
        &self,
        tenure: &ConsensusHash,
    ) -> Result<Option<BlockInfo>, DBError> {
        let query = "SELECT block_info FROM blocks WHERE consensus_hash = ?1 AND state IN (?2, ?3) ORDER BY stacks_height DESC LIMIT 1";
        let args = params![
            tenure,
            &BlockState::GloballyAccepted.to_string(),
            &BlockState::LocallyAccepted.to_string(),
        ];
        let result: Option<String> = query_row(&self.db, query, args)?;

        try_deserialize(result)
    }
