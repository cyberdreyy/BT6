## Title
Reorg-permission check under-counts signed blocks in a reorged tenure by only querying `GloballyAccepted` state - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`SortitionData::check_parent_tenure_choice` decides whether a new miner is allowed to reorg a prior tenure by checking, per reorged tenure, whether `get_globally_accepted_block_count_in_tenure` returns `> 1`. This mirrors the reported bug class: the code assumes a narrow, locally-observable signal ("has the node confirmed more than one block from this tenure?") is equivalent to the real safety-relevant fact ("has the signer set already produced quorum signatures — i.e., bearer-instrument commitments — over more than one block in this tenure?"). Those two are not equivalent, because a block can cross the 70% signature threshold and be `mark_locally_accepted(true)`-ed (which the docs explicitly call "a bearer instrument" that binds the signer no matter what) without yet being `GloballyAccepted`, since global acceptance additionally requires the node to observe/process the block.

### Finding Description
`check_parent_tenure_choice` in [1](#0-0)  permits a reorg of `tenure` when `globally_accepted_blocks <= 1`, where `globally_accepted_blocks = signer_db.get_globally_accepted_block_count_in_tenure(&tenure.consensus_hash)`. This function only counts blocks whose `BlockState` is `GloballyAccepted` — a state reached only via `mark_globally_accepted`, which itself only fires from `NewBlock` events or when the node's tenure tip is observed to have advanced to the block (see `check_latest_block_in_tenure`'s tip-adoption branch, [2](#0-1) ).

By contrast, `store_and_process_block_signature` moves a block to `LocallyAccepted` with `signed_group` set as soon as ≥70% signature weight is gathered [3](#0-2) , and per the design doc this is deliberately treated as an irrevocable commitment: "a rejection is a revocable opinion, while a signature is a bearer instrument … a block we signed binds us no matter what state it later fell to" [4](#0-3) . This means a tenure can have two (or more) blocks that have each cleared the 70% quorum threshold — i.e., are fully signed and about to be pushed to the node — while the node has not yet processed either of them, so `get_globally_accepted_block_count_in_tenure` reports `0`. `check_parent_tenure_choice` will then treat the tenure as having produced "zero blocks or one block," satisfying the `<= 1` bound and permitting the reorg, even though two independently-quorum-signed blocks already exist for that tenure.

Once the reorg is "permitted," `record_superseded_tenure`/`mark_tenure_superseded` is invoked [5](#0-4) , and the superseded tenure's signed blocks are excluded from conflict checks going forward via `reorg_permit_stands` in the pre-commit signing path [6](#0-5) . That is precisely the "our signature must not block a replacement we sanctioned" carve-out described in the docs [7](#0-6) , but here it is invoked on a mistaken premise: the reorg was sanctioned by miscounting already-quorum-signed blocks as if none existed.

### Impact Explanation
This breaks the "aggregated weight vs verified accepts" equality: the check is supposed to gate a reorg on whether the signer set already reached quorum over the tenure's blocks, but it substitutes a weaker, node-confirmation-dependent predicate (`GloballyAccepted`) for the correct one (quorum-signed / `has_signed_block_in_tenure`-style predicate, which the codebase itself distinguishes from `has_approved_block_in_tenure` for exactly this reason — see [8](#0-7) ). A single miner (one slot) who proposes a tenure whose predecessor tenure has two quorum-signed-but-not-yet-globally-accepted blocks can get that predecessor tenure wrongly marked `superseded`, causing the signer set's own already-signed blocks to stop vetoing a conflicting/non-canonical replacement chain — a safety break in the "approved-parent vs canonical" category (an improper reorg permission granted, letting a signer's binding signature be worked around).

### Likelihood Explanation
The race window is real but narrow: it requires the timing where signature aggregation crosses 70% for two separate blocks in the same tenure before the node has processed/confirmed either as its canonical tip (e.g., node lag, network delay, or a burst of two blocks produced quickly in one tenure). This is plausible under normal tenure-extend/rapid-block conditions and does not require compromising a majority of signers or any signer's key — it only requires a miner to propose the reorging tenure at the right moment, matching the "one-slot miner (plus gossip)" trigger class in scope. I could not fully trace every downstream consumer of `mark_tenure_superseded`/`is_tenure_superseded` to confirm there is no secondary safeguard that would catch this specific miscount before a signature is withheld from a legitimately-superseded conflict, so likelihood should be treated as moderate rather than certain without further test-level verification.

### Recommendation
In `check_parent_tenure_choice`, replace (or supplement) `get_globally_accepted_block_count_in_tenure` with a count based on quorum-signed blocks regardless of node confirmation state — i.e., blocks in `LocallyAccepted` (with `signed_group` set) or `GloballyAccepted`, mirroring the distinction the codebase already draws between `has_approved_block_in_tenure` (pre-commit-inclusive, not usable for commitment questions) and `has_signed_block_in_tenure` (signature-only, used for commitment). Add a signerdb helper analogous to `has_signed_block_in_tenure` but returning a count, and use it here instead of the globally-accepted-only count.

### Proof of Concept
1. Tenure T1 produces two blocks B1 (height h) and B2 (height h+1); the full signer set (≥70% weight) signs both B1 and B2 in quick succession, so both reach `LocallyAccepted` with `signed_group` set — but the stacks-node has not yet processed either (no `NewBlock` event, no advanced tenure tip).
2. `get_globally_accepted_block_count_in_tenure(T1)` returns `0` because neither block is `GloballyAccepted` yet.
3. A new tenure T2 is proposed with `parent_tenure_id` pointing to a sortition prior to T1 (a reorg of T1). `check_parent_tenure_choice` iterates the reorged tenures, finds T1's `globally_accepted_blocks == 0 <= 1`, and does not reject the reorg on this basis (assuming the timing/other checks also pass).
4. T1 is recorded as superseded via `mark_tenure_superseded`. Signers that already signed B1/B2 will, per `reorg_permit_stands`, stop treating their own B1/B2 signatures as conflicts blocking T2's replacement blocks, even though two blocks with full signer-quorum signatures already exist for T1 — a state the "at most one signed block" rule was specifically meant to prevent.

permitted — the node cannot answer this one at signing time, since it still
serves the reorged tenure as fully live until the replacement lands. What _is_
still derived from the node is the permit's own validity: the record carries the
permitting tenure's sortition, and it only excludes conflicts while that
sortition remains canonical (section 5, `reorg_permit_stands`), so a burnchain
fork that orphans the permitting tenure automatically voids the permit. A record
more than `MAX_FORK_DEPTH` (100) burn blocks below the tip is dropped; a fork
that deep would cause far bigger problems than a stale conflict.
