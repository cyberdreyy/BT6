### Title
Confidential-relay request-ID collision leaks pending-request existence and allows cross-user response hijack via unbounded, unauthenticated ID reuse - ([File: core/services/gateway/handlers/confidentialrelay/handler.go])

### Summary
`newActiveRequest` maps every confidential-relay request solely by the caller-supplied `req.ID` with no per-sender namespacing, so any unprivileged gateway client can pick an ID currently in-flight for a different user and learn (via the distinct "request ID already exists" error vs. normal fan-out success) whether that exact ID is currently pending for someone else. Because the same global key space is also used to route DON node responses back to the callback (`getActiveRequest`/`HandleNodeMessage`), an attacker with a colliding-but-rejected request cannot hijack another user's response, but the ID-existence oracle itself is a real information leak on caller-controlled data with no session/user binding.

### Finding Description
`HandleJSONRPCUserMessage` calls `h.newActiveRequest(req, callback)` [1](#0-0) , which under `h.mu.Lock()` checks `h.activeRequests[req.ID] != nil` and either returns `"request ID already exists: " + req.ID"` or inserts the new entry [2](#0-1) . The check and insert happen while holding the same exclusive `sync.RWMutex` write lock (`Lock`/`Unlock`) for the whole function, so the check-then-act sequence is atomic with respect to other calls to `newActiveRequest`; there is no TOCTOU window between the map lookup and the map write within this function.

However, `req.ID` is fully attacker-controlled (any string ≤200 chars, validated only for emptiness/length in `HandleJSONRPCUserMessage`) and is never combined with a sender identity, auth token, or connection identifier before being used as the map key [3](#0-2) . The gateway's `ProcessRequest` decodes the raw request and forwards `jsonRequest.ID` verbatim to `HandleJSONRPCUserMessage` without any per-caller ID scoping [4](#0-3) . This means two different, unrelated unprivileged callers hitting the same gateway/DON with the same chosen `req.ID` will collide in the same global namespace, and the second caller receives a distinct, observable error ("request ID already exists") instead of normal processing, revealing that some other party currently has a request with that exact ID in flight.

### Impact Explanation
This is an information-disclosure oracle only: an attacker can enumerate/guess IDs and learn whether a specific ID is currently active for another (unknown) user, potentially useful for traffic-correlation or timing side channels against a target user's ID-generation scheme, but it does not provide response hijacking — the "already exists" branch returns an error to the caller and does not attach that caller's callback to the existing `activeRequest`, so the original request's `gwhandlers.Callback` is never overwritten or handed to the second caller [5](#0-4) . There is no cross-user response confusion here because insertion is refused, not overwritten. This does not map to a "cross-user response delivery" impact in this function; it is a low-severity information leak (existence of an in-flight ID) contingent on the attacker already knowing/guessing the victim's exact request ID, which is normally client-generated and not predictable without other leakage.

### Likelihood Explanation
Low. Exploiting the oracle requires the attacker to already know or correctly guess a victim's exact `req.ID` string (up to 200 chars, no format constraint enforced), which is chosen client-side and not disclosed by the gateway elsewhere in this file. Absent a separate ID-predictability weakness, the practical likelihood of colliding with a real victim's ID is negligible.

### Recommendation
Not required as a security fix for cross-user hijack (none exists), but to remove the existence oracle, scope the `activeRequests` key by a value that incorporates the authenticated sender identity (e.g., `sender+req.ID`) rather than the raw client-supplied `req.ID` alone, so that ID collisions across different senders cannot occur and cannot be distinguished from any other internal handler error.

### Proof of Concept
A Go test in `confidentialrelay` calling `h.newActiveRequest` twice with the same `req.ID` from two goroutines (simulating two senders) would show:
1. Exactly one call succeeds and returns a non-nil `*activeRequest`; the other receives the "request ID already exists" error — confirming atomicity is preserved (no double-insert), because the whole check-and-insert path is guarded by `h.mu.Lock()`.
2. The losing caller's `callback` is never invoked/associated with the winning `activeRequest.Callback`, so no cross-user response delivery occurs.
This confirms the atomicity invariant holds and rules out the "race allows two winners" and "cross-user response hijack" hypotheses; only the ID-existence signal (distinguishing "already exists" from other responses) remains as a low-impact, low-likelihood oracle contingent on ID predictability that is out of scope of this function alone. func (h *handler) HandleJSONRPCUserMessage(ctx context.Context, req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) error {
	if req.ID == "" {
		return errors.New("request ID cannot be empty")
	}
	if len(req.ID) > 200 {
		return errors.New("request ID is too long: " + strconv.Itoa(len(req.ID)) + ". max is 200 characters")
	}

	l := logger.With(h.lggr, "method", req.Method, "requestID", req.ID)
	l.Debugw("handling confidential relay request")

	ar, err := h.newActiveRequest(req, callback)
	if err != nil {
		return err
	}

	return h.fanOutToNodes(ctx, l, ar)
}

func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	ar := &activeRequest{
		Callback:  callback,
		req:       req,
		createdAt: h.clock.Now(),
		responses: map[string]*jsonrpc.Response[json.RawMessage]{},
	}
	h.activeRequests[req.ID] = ar
	return ar, nil
}
