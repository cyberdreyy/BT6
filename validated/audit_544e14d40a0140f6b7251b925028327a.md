### Title
Missing per-sender allowlist/rate-limiting in `HandleLegacyUserMessage` allows unauthenticated DON fan-out flooding and cross-user callback eviction - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.HandleLegacyUserMessage` accepts any structurally-valid, signed legacy gateway message and immediately fans it out to every DON member via `don.SendToNode`, and stores a callback keyed by message ID in the shared `h.savedCallbacks` map, all without any per-sender allowlist or quota check — the enforcement is explicitly left as a `TODO`. Because `gateway.ProcessRequest` calls `HandleLegacyUserMessage` directly with no upstream rate-limiting for this path, a single low-privilege sender can flood the handler, exhausting `savedCallbacks` capacity and forcing `pruneCallbacks` to evict other users' pending callbacks prematurely.

### Finding Description
The request path is: `gateway.ProcessRequest` (core/services/gateway/gateway.go:218-292) decodes an incoming legacy JSON-RPC message, validates its structure/signature via `msg.Validate()`, resolves the handler by `msg.Body.DonId`, and calls `h.HandleLegacyUserMessage(ctx, msg, callback)` directly — there is no per-sender rate limiter or allowlist check anywhere in this call path. [1](#0-0) 

Inside `HandleLegacyUserMessage` (core/services/gateway/handlers/capabilities/handler.go:341-421), after payload decoding and a staleness/timestamp check, the code explicitly notes the missing control: [2](#0-1) 

It then stores a `savedCallback` in the shared, unbounded-by-sender `h.savedCallbacks` map and fans the request out to *every* DON member: [3](#0-2) 

The only capacity control is the periodic `pruneCallbacks` job, which removes expired entries and, if the map still exceeds `MaxSavedCallbacks` (default 20000), evicts the oldest half regardless of which sender created them: [4](#0-3) [5](#0-4) 

The existing `nodeRateLimiter` in this handler only throttles outbound messages keyed by `nodeAddr` in `handleWebAPIOutgoingMessage` (i.e., DON-node-to-external-client traffic), not inbound user requests into `HandleLegacyUserMessage`: [6](#0-5) 

Because no allowlist or per-sender/global quota exists on the ingress path, any caller able to submit a structurally valid signed message (there is no gating on *who* the signer is — `msg.Validate()`/`ValidatedRequestFromMessage` check message well-formedness and signature presence, not sender identity against a permitted list) can submit an unbounded volume of `MethodWebAPITrigger` requests, each of which is broadcast to all DON members and consumes a `savedCallbacks` slot.

### Impact Explanation
This is a resource-exhaustion / availability issue: an unprivileged sender can (a) trigger unlimited DON node fan-out traffic (amplification: 1 request → N `SendToNode` calls, one per DON member) and (b) fill the shared `savedCallbacks` map, causing `pruneCallbacks` to evict legitimate, unrelated pending callbacks from other users before their DON responses arrive, causing those users' requests to fail/time out. This matches a denial-of-service / resource-exhaustion impact class rather than fund loss or key disclosure, but it directly causes cross-user disruption (other users' in-flight requests are silently dropped due to eviction).

### Likelihood Explanation
The only precondition is the ability to submit a well-formed, signed legacy gateway message with a valid `DonId` — no special role, node operator status, or elevated credential is required, matching the "unprivileged/unauthenticated gateway caller" threat model. The attack is trivially repeatable (loop of HTTP calls to the gateway's user-facing port) and requires no coordination with other actors. The `TODO` comment in the code confirms the control is known to be absent, increasing confidence that no other layer enforces it.

### Recommendation
Implement the intended per-sender allowlist and rate-limiting/quota mechanism in `HandleLegacyUserMessage` before adding entries to `h.savedCallbacks` and before dispatching to `don.SendToNode`, e.g., a `ratelimit.RateLimiter` keyed by `msg.Body.Sender` (mirroring `nodeRateLimiter`), combined with a configurable allowlist of permitted senders from `HandlerConfig`/`DONConfig`, and reject/short-circuit with `handlers.UserCallbackPayload` errors (as already done for other validation failures) when limits are exceeded — before mutating `savedCallbacks` or calling `SendToNode`.

### Proof of Concept
Go handler-level integration test plan (in `core/services/gateway/handlers/capabilities/handler_test.go`):
1. Construct a `handler` via `NewHandler` with a small `MaxSavedCallbacks` (e.g., 10) and short `CallbackPruneIntervalSec`, backed by a mock `handlers.DON` (`don.SendToNode` returns nil) as used in existing tests.
2. From a single sender address/key, generate and sign N > `MaxSavedCallbacks` distinct legacy `api.Message`s with `Method = MethodWebAPITrigger` and valid non-stale `Timestamp`, each with a unique `MessageId`.
3. Concurrently call `h.HandleLegacyUserMessage(ctx, msg, callback)` for all N messages and assert:
   - All N calls succeed without any error/rejection referencing rate limit or allowlist (i.e., `err == nil` and `don.SendToNode` mock recorded N × len(donConfig.Members) calls) — proving no per-sender quota exists.
4. Separately, submit one legitimate callback from a different simulated "victim" sender first, then flood with attacker messages exceeding `MaxSavedCallbacks`, trigger `h.pruneCallbacks()` (or wait for the ticker), and assert that the victim's `savedCallback` entry was evicted from `h.savedCallbacks` (checked via exported test hook or by asserting the victim's `callback.Wait(ctx)` times out) — proving the flood causes eviction of an unrelated user's pending callback.

func (h *handler) pruneCallbacks() {
	h.mu.Lock()
	defer h.mu.Unlock()

	// First, remove expired callbacks.
	maxAge := time.Duration(h.config.CallbackMaxAgeSec) * time.Second
	now := time.Now()
	var expired int
	for id, cb := range h.savedCallbacks {
		if now.Sub(cb.createdAt) > maxAge {
			delete(h.savedCallbacks, id)
			expired++
		}
	}

	// If there are still too many callbacks, sort them by creation time and remove the oldest ones.
	maxSize := h.config.MaxSavedCallbacks
	var evicted int
	if len(h.savedCallbacks) > maxSize {
		type entry struct {
			id        string
			createdAt time.Time
		}
		entries := make([]entry, 0, len(h.savedCallbacks))
		for id, cb := range h.savedCallbacks {
			entries = append(entries, entry{id, cb.createdAt})
		}
		sort.Slice(entries, func(i, j int) bool {
			return entries[i].createdAt.Before(entries[j].createdAt)
		})
		// Trim to maxSize/2 to avoid sorting the list too frequently.
		for _, e := range entries[:len(entries)-maxSize/2] {
			delete(h.savedCallbacks, e.id)
			evicted++
		}
	}

	if expired > 0 || evicted > 0 {
		h.lggr.Infow("Pruned savedCallbacks", "expired", expired, "evicted", evicted, "remaining", len(h.savedCallbacks))
	}
}
