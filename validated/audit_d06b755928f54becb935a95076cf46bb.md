### Title
Cross-user response hijacking via `MessageId` collision overwrite in `savedCallbacks` map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.HandleLegacyUserMessage` stores the caller's callback in `h.savedCallbacks[msg.Body.MessageId]` without checking for an existing entry, and `msg.Body.MessageId` is a client-supplied string that is never tied to the sender's identity in the map key. An unprivileged attacker who submits a legacy gateway request with the same `MessageId` as another user's in-flight request overwrites the victim's saved callback, causing the eventual DON node response for that `MessageId` to be delivered to the attacker instead of the victim.

### Finding Description
`HandleLegacyUserMessage` validates payload/timestamp/method, then unconditionally does: [1](#0-0) 
This overwrites any existing entry keyed only by `msg.Body.MessageId`, with no check for `found` and no binding to the requester's signer/sender address.

`MessageId` originates directly from the attacker-controlled request. For legacy JSON-RPC-wrapped messages, `ValidatedMessageFromReq` sets `m.Body.MessageId = req.ID` directly from the JSON-RPC request ID supplied by the client: [2](#0-1) 
`Message.Validate()` only checks length/format constraints on `MessageId` (non-empty, ≤128 bytes, no trailing NUL) — it does not enforce uniqueness or bind the ID to the sender: [3](#0-2) 
The `Sender` field is derived from the message signature (`ExtractSigner`), but this sender is never checked against the `MessageId` key when saving or looking up callbacks.

When a node later responds with `MethodWebAPITrigger` for that `MessageId`, `handleWebAPITriggerMessage` looks the callback up purely by `MessageId`, deletes it, and forwards the response to whichever callback is currently stored — the attacker's, if the attacker's later request overwrote the victim's: [4](#0-3) 

Exploit flow:
1. Victim sends a legacy `web_api_trigger` message with `MessageId = "X"`, signed with victim's key. Handler stores `savedCallbacks["X"] = victimCallback` and forwards the request to all DON members.
2. Before a node responds, attacker sends their own legacy `web_api_trigger` message, also with `MessageId = "X"` (attacker chooses this arbitrarily and signs with their own key — nothing prevents reuse). Handler overwrites `savedCallbacks["X"] = attackerCallback`.
3. A DON node responds for `MessageId = "X"` (which could be the response to either request, since the node protocol doesn't disambiguate beyond DonId/MethodId/MessageId matching client expectations). `handleWebAPITriggerMessage` finds `savedCallbacks["X"]` → now attacker's callback → sends the response payload to the attacker.
4. The victim's callback is silently dropped/overwritten and never receives the node's response; the attacker instead receives data intended to be routed back to the victim's caller.

No allowlist, per-sender namespacing, or signer-binding on `MessageId` prevents this collision.

### Impact Explanation
This is a cross-user response confusion vulnerability: an unauthenticated/unprivileged gateway client can intercept web API trigger responses destined for another user by predicting or guessing their `MessageId`, or simply racing with a known/observed ID. Because `Payload`/`Response` content routed back to a user via `savedCallbacks` can include node computation results, this allows data intended for one user's HTTP callback/session to be redirected to an attacker-controlled callback, and simultaneously the victim never gets their expected response (denial of service for that request). This matches the "request impersonation / cross-user response confusion" bounty impact class.

### Likelihood Explanation
Requires only the ability to send a signed gateway message to the `web_api_trigger` capabilities handler — no special role or DON/operator access, any address capable of signing a gateway message qualifies. The main precondition is knowing/guessing the victim's `MessageId` while their request is still in-flight (i.e., before a node responds), which is plausible if MessageIds are predictable, low-entropy, sequential, or observable via other integration points. This is a repeatable race condition, not a one-off flaw, since the map is shared for all users of that DON/handler and `MessageId` uniqueness is never enforced.

### Recommendation
Bind the saved-callback key to both the `MessageId` and the sender identity (e.g., key by `sender+":"+MessageId`), or reject `HandleLegacyUserMessage` requests whose `MessageId` already exists in `savedCallbacks` (return a conflict error) instead of silently overwriting. Additionally consider generating/validating `MessageId` uniqueness server-side rather than trusting the client-supplied value verbatim.

### Proof of Concept
Go handler-level integration test plan (in `core/services/gateway/handlers/capabilities/handler_test.go`):
1. Build two `api.Message`s with identical `Body.MessageId = "collide-1"` but signed by two different `ecdsa.PrivateKey`s (`victimKey`, `attackerKey`), using the existing `triggerRequest` helper.
2. Create two separate `handlers.Callback` instances, `victimCb` and `attackerCb` (via `hc.NewCallback()`), each wrapped to track which one received a response.
3. Call `handler.HandleLegacyUserMessage(ctx, victimMsg, victimCb)`, then `handler.HandleLegacyUserMessage(ctx, attackerMsg, attackerCb)` — assert both succeed with no error and no "already exists" rejection (demonstrating the missing check).
4. Simulate a node response for `MessageId = "collide-1"` via `handler.HandleNodeMessage(ctx, resp, nodeAddr)`.
5. Assert `attackerCb.Wait(ctx)` returns the node response payload, while `victimCb.Wait(ctx)` times out / never resolves — proving the victim's callback was silently overwritten and the response was misdelivered to the attacker.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
