### Title
Trace section marker forgery via unescaped CR/ESC round-trip in command echo - (functions/script_legacy/internal/trace_section.go)

### Summary
`writeSectionStart` embeds the (escaped) job command into a `printf` argument that is quoted with `$'...'` (ANSI-C mode) or `"..."` (POSIX mode). Both `EscapeForAnsiC` and `EscapeForPosix` are designed to preserve the *original byte content* of the command faithfully once the shell re-parses the quoted string at execution time, so any raw `\r`/ESC bytes an attacker embeds in a job script line pass straight through into the trace output, letting them fabricate a byte-identical `section_start:`/`section_end:` marker inside what is supposed to be a harmless "$ command" preview line.

### Finding Description
`WriteSection` → `writeSectionStart` builds the visible header line as:
`section_start:<timestamp>:section_<name>[<opts>]` + raw `\r` + `ansiClear` (`\033[0K`) + escaped(`ansiBoldGreen + "$ " + command + ansiResetTrace`), all as a single unquoted-then-quoted shell word passed to `printf '%s\n' ...` [1](#0-0) .

`escape()` routes the command through `EscapeForAnsiC` (wrapped in `$'...'`) or `EscapeForPosix` (wrapped in `"..."`) depending on `posixMode` [2](#0-1) .

`EscapeForAnsiC` converts raw `\r`, `\n`, and other control bytes (including ESC, 0x1B) into their textual two-character/`\xHH` forms specifically so the resulting `$'...'` literal is a *byte-faithful* representation — bash's ANSI-C quoting will decode `\r`→CR, `\x1b`→ESC, etc. back to the exact original bytes when the script executes [3](#0-2) . `EscapeForPosix` is even less restrictive: it has no case for CR, LF, or ESC at all, so those bytes are written completely unescaped into the double-quoted string, and most shells pass them through raw inside `"..."` [4](#0-3) .

Because both escaping paths guarantee **byte-for-byte fidelity** of the original command text once the shell executes the generated script, an attacker who controls the job's script line (a normal pipeline author) can author a command whose literal content contains the exact byte sequence `section_end:<digits>:section_<name>\r\033[0K` or `section_start:<digits>:section_<name>[opts]\r\033[0K` (achievable in YAML via double-quoted scalars using `\r` and `\e`/`\x1B` escapes). When `printf` writes the header line, this attacker-controlled substring is emitted verbatim as part of the "$ command" preview text, indistinguishable at the byte level from a genuine marker written by `writeSectionStart`/`writeSectionEnd`.

No existing check filters or neutralizes this pattern: the escape functions only protect the *shell source* from breaking quoting/injecting new statements (backslash, quote, `$`, backtick), not the *semantic content* of the resulting trace bytes. There is no allow-list, no stripping of `section_start:`/`section_end:` look-alike substrings, and no separator/authentication distinguishing runner-emitted markers from job-echoed text.

### Impact Explanation
An attacker-controlled job can inject a forged `section_end:`/`section_start:` byte sequence into the trace stream, which GitLab's section-based collapsible-log parser matches as a substring pattern rather than as an authenticated protocol frame. This lets a malicious pipeline close a legitimate section early or open a new fake one, causing subsequent (potentially malicious or suspicious) command output to be nested inside an unexpectedly collapsed/mislabeled section — degrading trace/log integrity and helping hide activity from a human reviewing the job log in the GitLab UI. Impact is limited to the visual/structural integrity of that job's own trace; it does not cross job/project boundaries or leak secrets by itself.

### Likelihood Explanation
Preconditions are minimal and fully within an unprivileged pipeline author's control: `trace_sections=true` (the default section-wrapping behavior of this code path) and a script line containing a handful of YAML-escapable control bytes (`\r`, `\e`). No special runner configuration, privileges, or race conditions are required, and the result is deterministic/repeatable on every run of the crafted job.

### Recommendation
Do not rely solely on byte-fidelity escaping for the command preview text. Either:
1. Strip/replace raw `\r` and ESC (and other bytes that could reconstruct the `\r\033[0K` marker separator) from the *displayed* command preview before embedding it in the section header, independent of shell-quoting escaping, or
2. Reject/neutralize any command substring that matches the `section_(start|end):\d+:section_[^\r\n]+(\[.*])?` pattern before it is echoed, or
3. Change the marker format so runner-emitted section markers cannot be confused with job-echoed text (e.g., prefix with a value the job cannot produce, or emit markers via a channel not subject to job-controlled interpolation).

```go
func TestWriteSectionStart_MarkerForgery(t *testing.T) {
    w := NewTraceSectionWriter(false /*checkForErrors*/, false /*posixMode*/)
    var buf strings.Builder

    // Attacker-controlled command containing a forged section_end marker,
    // as it would appear after YAML double-quoted-scalar decoding:
    // script: - "echo hi\rsection_end:0:section_step_0\e[0K"
    evil := "echo hi\rsection_end:0:section_step_0\x1b[0K"

    w.writeSectionStart(&buf, "script_step_0", evil)
    script := buf.String()

    // Simulate bash decoding of the generated $'...' literal to get the
    // bytes that would actually reach the trace stream.
    decoded := decodeAnsiCLiteral(t, script) // helper invoking `bash -c "printf ..."`

    forged := regexp.MustCompile(`section_end:\d+:section_[\w-]+\r\x1b\[0K`)
    if forged.MatchString(decoded) {
        t.Fatalf("forged section_end marker reproduced verbatim in trace output: %q", decoded)
    }
}
```
Expected (current buggy) result: the assertion fails — `forged.MatchString(decoded)` is `true`, proving the attacker's fake `section_end:` byte sequence appears intact in the emitted trace text, matching GitLab's section marker regex and confirming the boundary-forging path.

```go
func EscapeForAnsiC(s string) string {
	var buf strings.Builder

	for i := 0; i < len(s); i++ {
		c := s[i]
		switch c {
		case '\\':
			buf.WriteString("\\\\")
		case '\'':
			buf.WriteString("\\'")
		case '\n':
			buf.WriteString("\\n")
		case '\r':
			buf.WriteString("\\r")
		case '\t':
			buf.WriteString("\\t")
		case '\a':
			buf.WriteString("\\a")
		case '\b':
			buf.WriteString("\\b")
		case '\f':
			buf.WriteString("\\f")
		case '\v':
			buf.WriteString("\\v")
		default:
			// Hex-escape control characters (0x00-0x1F, 0x7F) and non-ASCII (>0x7F)
			// This prevents ANSI escape sequences (ESC = 0x1B) from manipulating terminal
			if c < 0x20 || c == 0x7F || c > 0x7F {
				fmt.Fprintf(&buf, "\\x%c%c", hextable[c>>4], hextable[c&0x0f])
			} else {
				buf.WriteByte(c)
			}
		}
	}

	return buf.String()
}
```

```go
func EscapeForPosix(s string) string {
	if s == "" {
		return "''"
	}

	var buf strings.Builder
	needsQuoting := false

	for _, r := range s {
		switch r {
		case '`', '"', '\\', '$':
			buf.WriteRune('\\')
			buf.WriteRune(r)
			needsQuoting = true
		case ' ', '!', '#', '%', '&', '(', ')', '*', '<', '=', '>', '?', '[', '|':
			buf.WriteRune(r)
			needsQuoting = true
		default:
			buf.WriteRune(r)
		}
	}

	if needsQuoting {
		return `"` + buf.String() + `"`
	}

	return buf.String()
}
```
