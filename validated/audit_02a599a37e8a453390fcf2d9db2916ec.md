### Title
Consumed instant-withdraw receipts leave stale per-epoch claim basis that is re-read at default finalization, letting an attacker arbitrarily dilute `defaultRecoveryPrice` and strand the recovery reserve — ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`claimInstantWithdrawRequest` zeroes only the aggregate `instantWithdrawsRequests[_user]` (line 391) but never clears `instantWithdrawsRequestsByEpoch[_user][epoch]` or the global `instantWithdrawClaimsByEpoch[epoch]` written at request time (lines 371–372). This is a "use-after-free" analog: receipt state that was logically consumed is later re-read by `defaultPendingClaimBasis` (lines 644–649) and `_claimDefaultedInstantWithdrawRequest` (lines 842–856) during default finalization, inflating the recovery basis with phantom claims.

### Finding Description
On `requestInstantWithdraw`, the vault records the request in three places: the per-user aggregate `instantWithdrawsRequests`, the per-user-per-epoch `instantWithdrawsRequestsByEpoch`, and the per-epoch total `instantWithdrawClaimsByEpoch`. On a normal funded claim, only the aggregate is reset — the two per-epoch mappings are "freed" for payout purposes but remain populated:

- `claimInstantWithdrawRequest` burns and pays `instantWithdrawsRequests[_user]` then sets it to 0 (lines 387–392); it never touches `instantWithdrawsRequestsByEpoch` or `instantWithdrawClaimsByEpoch`.
- If the borrower later defaults and `finalizeDefaultRecovery` runs while `pendingInstantWithdraws != 0`, `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` — which still contains every receipt ever requested in that epoch, including ones already fully claimed at par (lines 646–648).
- `recoveryPrice = reserveAmount * 1e18 / totalBasis` (line 688) is therefore pushed toward zero by attacker-controlled phantom basis.

An unprivileged attacker (any KYC-passing lender routing through the honest IdleCDO) can, inside a single epoch before `stopEpoch`, loop `requestInstantWithdraw` → wait for the honest CDO/borrower funding via `collectInstantWithdrawFunds` → `claimInstantWithdrawRequest`, recovering their capital each cycle while `instantWithdrawClaimsByEpoch[epochNumber]` accumulates without bound. A final small unfunded request keeps `pendingInstantWithdraws != 0` so the inflated bucket is included.

Existing guards do not stop this: `_onlyIdleCDO` is satisfied (the CDO relays the calls), no flag or epoch gate clears the stale basis, and the guard in `requestWithdraw` (lines 263–271) only covers normal withdraw epochs, not instant receipts.

### Impact Explanation
Near-total theft/freezing of default recovery value. With `instantWithdrawClaimsByEpoch` inflated by a factor `k`, `defaultRecoveryPrice` shrinks by ~`k`, so every honest defaulted receipt (pending withdraws via `_claimDefaultedWithdrawRequest`, instant receipts via `_claimDefaultedInstantWithdrawRequest`, and post-default requests) pays out at a fraction of the intended haircut. Because `defaultRecoveryReserve` is only debited by actual payouts (line 915), the difference — the lion's share of recovered funds — remains locked in the strategy permanently with no sweep path (no function returns `defaultRecoveryReserve` to the CDO or lender). Attacker cost is only gas plus one small sacrificed unfunded request; the claimed receipts are recycled capital.

Additionally, any user whose per-epoch basis exceeds their remaining aggregate hits `instantWithdrawsRequests[_user] -= claimBasis` underflow in `_claimDefaultedInstantWithdrawRequest` (line 848), permanently reverting their claim path.

### Likelihood Explanation
Requires a borrower default (or default finalization) in the same epoch the attacker cycles instant withdrawals — an honest-manager event the attacker cannot force but can prepare for cheaply, since instant request/claim cycling is costless and can be repeated every epoch as persistent preparation. No privileged cooperation, timing exoticism, or oracle dependence is needed; the accounting flaw is deterministic once finalization runs with `pendingInstantWithdraws != 0`.

### Recommendation
In `claimInstantWithdrawRequest`, clear `instantWithdrawsRequestsByEpoch[_user][requestEpoch]` and decrement `instantWithdrawClaimsByEpoch[requestEpoch]` for the claimed amount (tracking each user's request epoch, or clearing proportionally), so that consumed receipts cannot be re-counted by `defaultPendingClaimBasis` or `_claimDefaultedInstantWithdrawRequest` at finalization.

### Proof of Concept
Foundry fork sketch ( vault = `IdleCreditVault`, cdo = `IdleCDOEpochVariant`, attacker = KYC'd lender):

```solidity
// Epoch N running; borrower honest so far.
// 1) Attacker deposits via cdo.depositAA, then cycles M times in epoch N:
for (uint i; i < M; ++i) {
    cdo.requestInstantWithdraw(amt);        // IdleCreditVault.requestInstantWithdraw
    // honest borrower/manager funds via stop/start mechanics or direct funding;
    cdo.claimInstantWithdrawRequest();      // pays out; per-epoch basis NOT cleared
}
// instantWithdrawClaimsByEpoch[N] == M * amt, instantWithdrawsRequests[attacker] == 0
// 2) Attacker leaves one small unfunded instant request so pendingInstantWithdraws != 0.
cdo.requestInstantWithdraw(dust);
// 3) Borrower defaults; owner/manager calls finalizeDefault* which invokes
//    IdleCreditVault.finalizeDefaultRecovery(recovered, source).
// 4) Assert: defaultRecoveryPrice() is ~1e18 / (1 + M*amt/(honestBasis))
//    i.e. diluted ~M*amt/(real basis); honest user's claim pays ~0 and
//    defaultRecoveryReserve retains ~the full recovered amount, unsweepable.
```

Key assertions: `defaultRecoveryPrice` far below `reserve/basis` without inflation, honest claimant payout ≈ diluted share, and `underlyingToken.balanceOf(strategy) - defaultRecoveryReserve == 0` with the reserve stuck after all claims.
