### Title
Cross-user response hijacking via attacker-controlled `MessageId` collision in `savedCallbacks` map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.HandleLegacyUserMessage` stores each user's response callback in `h.savedCallbacks` keyed solely by the attacker-controlled `msg.Body.MessageId`, with no allowlist/authorization check on the sender at this stage. `handleWebAPITriggerMessage` later looks up and deletes the callback by `MessageId` alone and delivers the node's response to whatever callback currently occupies that key. Because a second (attacker) request can be signed and submitted with the same `MessageId` as a legitimate in-flight request, it overwrites the entry, causing the original requester's response to be delivered to the attacker's callback instead.

### Finding Description
`MessageId` is fully attacker-controlled — it flows in from the JSON-RPC `id` field via `gateway.ProcessRequest` and `common.ValidatedMessageFromReq` (`m.Body.MessageId = req.ID`), or is chosen and signed directly by the caller in the legacy `api.Message` payload (see `api.Message.Sign` at `core/services/gateway/api/message.go:96-108`, where `MessageId` is part of the data the caller signs themselves, so any caller can choose any ID string it wants). Nothing binds `MessageId` uniqueness to the requester's signer/address.

In `HandleLegacyUserMessage` (`core/services/gateway/handlers/capabilities/handler.go:341-421`), after validating payload structure/timestamp/method, the code stores the callback with an unconditional overwrite: [1](#0-0) 
There is no check for an existing entry under the same key, and there is explicitly no sender allowlist/authorization at this point — the code even has a `// TODO: apply allowlist and rate-limiting here` comment: [2](#0-1) 

Later, `handleWebAPITriggerMessage` resolves the response purely by `MessageId`: [3](#0-2) 
It does not verify that the callback belongs to the same sender/signer that originated the request the node is responding to — `HandleNodeMessage` only checks that the response came from the expected `nodeAddr` (`msg.Body.Sender != nodeAddr`), not anything about the original requester.

Exploit flow:
1. Victim A sends a legitimate `HandleLegacyUserMessage` request with `MessageId == "X"`. It is stored in `h.savedCallbacks["X"]` and forwarded to all DON members.
2. Before the DON responds, the attacker sends their own signed request with the same `MessageId == "X"` (attacker fully controls and signs this field). `h.savedCallbacks["X"]` is overwritten with the attacker's callback.
3. When a DON node responds to A's original message (which still carries `MessageId == "X"`), `handleWebAPITriggerMessage` looks up `h.savedCallbacks["X"]`, finds the attacker's callback, deletes the entry, and delivers A's execution response to the attacker via `savedCb.SendResponse`.
4. Victim A's own `callback.Wait` ultimately times out or receives nothing.

The existing test suite explicitly acknowledges the gap: `handler_test.go` contains the comment `// TODO: Validate Senders and rate limit check, pending question in trigger about where senders and rate limits are validated`, confirming sender-binding was never implemented. [4](#0-3) 

### Impact Explanation
An unauthenticated/unprivileged gateway client can intercept another user's capability-execution response by colliding on `MessageId`. This is a cross-user response confusion / request impersonation issue: the attacker receives data intended for another user's request (potentially containing execution results tied to a workflow trigger), and the legitimate requester's flow is disrupted (denial of response / timeout). This matches the "cross-user response confusion" bounty class explicitly called out in the audit scope.

### Likelihood Explanation
Feasibility is high within the same DON: `MessageId` is entirely chosen by the caller (it is part of the data the caller signs, per `Message.Sign`/`GetRawMessageBody`), so no guessing of secret material is required — only knowledge/interception of a victim's `MessageId` value, which is plausible where IDs are predictable, sequential, reused by client tooling, or observable via any shared channel. No privileged credentials are required; the attacker only needs to be able to sign a message with their own key and submit it through the normal gateway request path, which currently has no allowlist/authorization gate before the callback is stored (`// TODO: apply allowlist and rate-limiting here`). The race window is the time between the victim's request being sent to DON nodes and the first node's response arriving, which is realistically several hundred milliseconds to seconds.

### Recommendation
Bind `savedCallbacks` entries to the originating sender, not merely `MessageId` — e.g., key the map by a composite of `(DonId, Sender, MessageId)`, or store the expected `Sender` address alongside the callback and verify it matches the signer of the message the node is echoing back before delivering the response. Additionally, reject `HandleLegacyUserMessage` calls that attempt to reuse a `MessageId` still present in `savedCallbacks` (return a conflict error) rather than silently overwriting, and implement the pending sender allowlist/rate-limiting noted in the TODO.

### Proof of Concept
Add a concurrency test in `core/services/gateway/handlers/capabilities/handler_test.go` alongside `setupHandler`/`triggerRequest` helpers:
1. Build two signed `api.Message`s with two different private keys (victim and attacker) but the identical `MessageId` (e.g., `"12345"`), using the existing `triggerRequest` helper modified to accept a custom message ID.
2. Call `handler.HandleLegacyUserMessage(ctx, victimMsg, victimCb)` — assert `h.savedCallbacks["12345"]` is the victim's callback.
3. Call `handler.HandleLegacyUserMessage(ctx, attackerMsg, attackerCb)` — assert `h.savedCallbacks["12345"]` is now overwritten with the attacker's callback.
4. Simulate a DON node responding to the victim's original request via `handler.HandleNodeMessage(ctx, hc.ValidatedResponseFromMessage(victimMsg), nodes[0].Address)`.
5. Assert `attackerCb.Wait(ctx)` returns the victim's response payload while `victimCb.Wait(ctx)` times out/never resolves — demonstrating the response is delivered to the wrong (attacker) callback, violating the isolation invariant.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
