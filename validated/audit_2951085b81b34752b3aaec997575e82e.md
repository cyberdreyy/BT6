### Title
JWT Replay Protection Race Condition Allows Anti-Replay Bypass - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

### Summary
The gateway's HTTP trigger JWT replay-protection cache performs its "already used" check (`isReplay`) and its "mark as used" write (`recordUsage`) as two separate, non-atomic operations inside `Authorize`. This is the same class of bug as the reported PI interest-rate issue: a security-critical decision is made from an instantaneous read of shared mutable state, and that state is only updated *after* other logic runs, leaving a window in which multiple concurrent operations can each observe the "not yet consumed" state and proceed as if they were each the first (and only) user of that state.

### Finding Description
`WorkflowMetadataHandler.Authorize` in `core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go` implements JWT replay protection like this: [1](#0-0) 

The sequence is:
1. `h.jwtCache.isReplay(claims.ID)` — takes an `RLock`, checks map membership, releases the lock.
2. Authorized-key lookup/verification logic runs (no lock held on `jwtCache`).
3. `h.jwtCache.recordUsage(claims.ID)` — takes a separate `Lock`, writes to the map, releases the lock. [2](#0-1) 

Because the check (`isReplay`) and the update (`recordUsage`) are two independent critical sections rather than a single atomic check-and-set, two (or more) concurrent `Authorize` calls carrying the *same* JWT (`jti`) can both execute `isReplay` before either has called `recordUsage`. Both will observe `exists == false` and both will be treated as valid, unused tokens — exactly analogous to the reported issue where `_errI` is only updated once per block, letting an attacker pair two state-changing operations (deposit+withdraw / borrow+repay) inside that same "stale window" to bypass the intended protection.

### Impact Explanation
JWT replay protection exists specifically to prevent a single signed authorization token from being used more than once (the JWT explicitly carries a `jti` for this purpose, and the cache is documented as anti-replay: `JWTReplayPeriodMs is how long JWT IDs are cached to prevent replay attacks`, see `core/services/gateway/handlers/capabilities/v2/http_handler.go` field comment). A successful race lets an unprivileged client resend the same captured/intercepted token concurrently to trigger multiple HTTP-trigger workflow executions or metadata operations that were only supposed to be authorized once — i.e., request impersonation / replay of a single-use credential, undermining the authentication guarantee the anti-replay cache is meant to provide.

### Likelihood Explanation
Exploitation only requires an attacker (or a legitimate holder of a JWT who wants to double-spend it) to fire the same signed request twice at nearly the same time — no privileged access or node compromise is needed, only network-level ability to send two HTTP requests concurrently to the gateway. The race window is small but real, and can be enlarged in practice by the attacker deliberately delaying step 2 (authorized-key lookup work) relative to their two concurrent submissions, or simply by firing many parallel duplicates to increase the chance of hitting the window.

### Recommendation
Make the "check and mark used" operation atomic under a single lock (or use a `sync.Map`/dedicated primitive with an atomic `LoadOrStore`), e.g.:
```go
func (cache *jwtReplayCache) checkAndRecord(jti string) (alreadyUsed bool) {
    cache.mu.Lock()
    defer cache.mu.Unlock()
    if _, exists := cache.cache[jti]; exists {
        return true
    }
    cache.cache[jti] = time.Now()
    return false
}
```
and call this single atomic method from `Authorize` instead of the separate `isReplay`/`recordUsage` calls, ensuring `recordUsage` happens immediately as part of the same critical section as the check (before, not after, the downstream authorized-key verification logic if possible, or otherwise guarded so the two calls can't interleave for the same `jti`).

### Proof of Concept
1. Obtain (or intercept) one valid signed JWT for a workflow HTTP trigger request.
2. Send the exact same JSON-RPC request (same token, same `jti`) twice concurrently (e.g., two goroutines/clients firing at the same instant) to the gateway's `Authorize` path.
3. Both requests call `h.jwtCache.isReplay(claims.ID)` before either calls `h.jwtCache.recordUsage(claims.ID)`; both observe `exists == false`.
4. Both requests pass authorization and are dispatched to the DON as if each carried an independent, unused token — the replay protection is bypassed for one of the two calls. [1](#0-0) [2](#0-1)

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

}

func (cache *jwtReplayCache) recordUsage(jti string) {
