### Title
Post-default withdraw receipts pay 1:1 from an under-collateralized `defaultRecoveryReserve`, draining recovery funds from earlier defaulted claimants - (contracts/strategies/idle/IdleCreditVault.sol)

### Summary
When `defaultRecoveryFinalized` is true, `requestWithdraw` mints the user a strategy-token receipt and records `postDefaultRequests[_user] = _amount`, which is later paid 1:1 from `defaultRecoveryReserve` via `_claimPostDefaultWithdrawRequest` → `_transferDefaultRecovery`. The reserve was sized at `finalizeDefaultRecovery` to cover the fixed `totalBasis` of defaulted claims at `recoveryPrice` (< 1e18 in a lossy default). Post-default claims draw from the same reserve at par, so each post-default request spends `1/recoveryPrice` more reserve per token than a defaulted claim. This over-allocates the finite reserve: post-default requesters are paid in full while earlier defaulted-epoch claimants (who are entitled to `claimBasis * recoveryPrice`) find the reserve exhausted and their claims permanently frozen/unpayable.

### Finding Description
`finalizeDefaultRecovery` computes `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` and stores `defaultRecoveryReserve = reserveAmount` (IdleCreditVault.sol:686-692). The reserve is therefore only sufficient to pay every defaulted claim at `recoveryPrice`.

After finalization, `requestWithdraw` takes the `defaultRecoveryFinalized` branch (lines 247-257): it burns `_amount` CDO strategy tokens, mints `_amount` receipt tokens to the user, and sets `postDefaultRequests[_user] = _amount`. No underlying is added to `defaultRecoveryReserve` — burning strategy tokens does not create or move any underlying into the reserve.

`_claimPostDefaultWithdrawRequest` then pays `_amount` at par via `_transferDefaultRecovery`, which does `defaultRecoveryReserve -= _amount` (lines 760-767, 912-917). Defaulted-epoch claimants in `_claimDefaultedWithdrawRequest` only receive `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` from the same reserve (lines 772-784).

The broken invariant is reserve solvency: `sum(claims at recoveryPrice) == reserve` only holds if all claimants are paid at `recoveryPrice`. Paying new claims at 1:1 makes the aggregate obligation `defaultedBasis * recoveryPrice + postDefaultBasis`, which exceeds the reserve as soon as `postDefaultBasis > defaultedBasis * (1 - recoveryPrice)`. The haircut the post-default depositor nominally "took" by burning strategy tokens at the depressed `virtualPrice` does not translate into underlying backing inside the strategy — those burned tokens represented already-haircut NAV, not cash.

### Impact Explanation
Theft / permanent freezing of recovery funds. An unprivileged user (any KYC-passing lender or tranche holder still holding shares after default) calls `requestWithdraw` post-finalization and claims at par, extracting more underlying than their haircut receipt is worth. Because `defaultRecoveryReserve` is finite and only decremented, the excess is taken directly from the reserve earmarked for defaulted-epoch claimants; the last claimants' `_transferDefaultRecovery` calls revert on insufficient balance and their recovery is permanently frozen. Quantified: each post-default claim of `X` steals up to `X * (1 - recoveryPrice)` of reserve value beyond its fair share.

### Likelihood Explanation
Requires a borrower default that is finalized with `recoveryPrice < 1e18`, and at least one user holding active tranche shares post-default who calls `requestWithdraw` before earlier claimants withdraw. Both conditions are routine operational states, not attacker-controlled edge cases; the first post-default claimant is guaranteed profit at the expense of slower claimants, so the incentive exists.

### Recommendation
Fund post-default receipts independently of `defaultRecoveryReserve`: either (a) require the CDO to transfer `_amount` underlying into the strategy and credit `defaultRecoveryReserve` when creating a `postDefaultRequests` entry, or (b) price post-default claims at `defaultRecoveryPrice` like defaulted claims (store the request basis and pay `basis * defaultRecoveryPrice / RECOVERY_FULL`). Alternatively, keep the burned strategy tokens' value by routing post-default claims through a distinct, fully-funded bucket so they can never spend reserve earmarked for defaulted claimants.

### Proof of Concept
Foundry fork test sketch (extends `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
function testPostDefaultRequestDrainsRecoveryReserve() external {
    // Setup: deposit, run epoch, force borrower default via stopEpoch with loss
    idleCDO.depositAA(10_000 * ONE_SCALE);
    _depositWithUser(attacker, 10_000 * ONE_SCALE, true); // attacker stays active
    _depositWithUser(victim, 10_000 * ONE_SCALE, true);
    _startEpochAndCheckPrices(0);
    // victim requests withdraw during epoch
    vm.prank(victim);
    cdoEpoch.requestWithdraw(0, address(AAtranche));
    // borrower underpays -> default -> finalizeDefaultRecovery with recoveryPrice 0.5e18
    // (partial recovery funded from recovery source)
    _finalizeDefaultAtPrice(0.5e18);
    // attacker, still holding active shares, requests withdraw post-finalization
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche)); // -> postDefaultRequests[attacker] = amt
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest(); // paid 1:1 from defaultRecoveryReserve
    // victim's defaulted claim now reverts or is underpaid: reserve exhausted
    vm.prank(victim);
    vm.expectRevert(); // safeTransfer underflow on reserve
    cdoEpoch.claimWithdrawRequest();
}
```

Uncertainty: I could not fully trace `IdleCDOEpochVariant.claimWithdrawRequest`/`stopEpoch` to confirm no companion funding transfer credits the reserve for post-default requests (tool output was truncated this session); the strategy-side code clearly adds none, and the reserve is only grown by `_recoveredAmount`, prefunded instant backing, and `reserveDefaultRecovery` calls, all tied to the finalization event rather than subsequent user requests.
