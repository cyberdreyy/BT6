### Title
Out-of-bounds panic when JSON/JSON-parsed encoding a compiled instruction whose `program_id_index`/account indices exceed `account_keys` length - (File: transaction-status/src/lib.rs)

### Summary
`parse_ui_instruction` and its fallback helper `make_ui_partially_decoded_instruction` index `account_keys` directly with attacker-influenced `u8` indices (`instruction.program_id_index`, `instruction.accounts[..]`) without any bounds check, unlike the sibling `parse_*` functions in the same crate (`parse_system`, `parse_stake`, `parse_token`, `parse_associated_token`, `parse_address_lookup_table`), which all explicitly validate `instruction.accounts.iter().max() < account_keys.len()` before indexing. [1](#0-0) 

### Finding Description
`parse_ui_instruction` first calls `parse_instruction::parse(program_id, ...)`, dereferencing `account_keys[instruction.program_id_index as usize]` before that call to obtain `program_id`, and falls back to `make_ui_partially_decoded_instruction` when the program is not one of the recognized, parsable programs. Both `parse_ui_instruction` and `make_ui_partially_decoded_instruction` index `account_keys` with `instruction.program_id_index` and every entry of `instruction.accounts` with no bounds checking at all: [2](#0-1) 

By contrast, every dedicated instruction parser in the crate explicitly guards against out-of-range indices with a comment noting this is normally guaranteed by runtime sanitization, e.g. in `parse_system`, `parse_stake`, `parse_associated_token`, and `parse_address_lookup_table`: [3](#0-2) [4](#0-3) 

These functions rely on the invariant that a `Message`/`VersionedMessage` has already been sanitized (which validates that `program_id_index` and each instruction account index are within `account_keys` bounds) before being encoded as JSON/JSON-parsed. That invariant is normally enforced when transactions are submitted via `sendTransaction`/`simulateTransaction`, which call `sanitize_transaction` before further processing. However, `Message::encode`/`v0::Message::encode`/`v1::Message::encode` (and the `EncodableWithMeta` variants) — which invoke `parse_ui_instruction` — are also the code path used to encode transactions that are read back out of the `Blockstore` for `getTransaction`/`getBlock`/`getBlockTime` style RPC calls and pubsub notifications. A transaction that reaches the ledger with an out-of-range account/program index would trigger an unguarded slice-index panic when re-encoded with `json`/`jsonParsed` encoding, crashing the RPC-serving process from a single unprivileged query — the direct analog to the external report's "malicious peer/message causes deserializer/decoder panic during blocksync/processing" bug class, here occurring at the decode/encode-for-display boundary instead of the P2P blocksync boundary.

### Impact Explanation
An out-of-bounds slice index in Rust causes an immediate `panic!`, which — absent `catch_unwind` around this specific code path — aborts the thread processing the RPC/pubsub request. If this happens within the tokio worker context and is not isolated, it can crash the entire JSON-RPC/pubsub service of the validator, taking down node availability for all clients on that node (DoS), which matches the "concrete validator-process crash…from one request" acceptance criterion in the validation rules.

### Likelihood Explanation
Likelihood depends on the reachability of an unsanitized/invalid-index instruction reaching the JSON encoding path — the standard `sendTransaction` path is expected to sanitize before persisting, so the panic would require either a bug elsewhere that stores an unsanitized transaction, or a currently-unverified path where `Message::encode`/`encode_with_meta` is called on a transaction that bypassed full sanitization (e.g., blockstore entries produced by a version mismatch, or partial/legacy message paths). I was not able to fully trace, within the available tool budget, every caller of `Encodable`/`EncodableWithMeta` for `Message`/`v0::Message`/`v1::Message` to confirm whether any of them can supply an unsanitized `CompiledInstruction` with out-of-range indices to `parse_ui_instruction`. This should be verified against `blockstore::get_complete_transaction`/`get_rooted_transaction` and the RPC `get_transaction`/`get_block` call sites to determine whether transaction sanitization is guaranteed for every transaction that gets persisted and later re-encoded.

### Recommendation
Add the same defensive bounds check used elsewhere in the crate (`instruction.accounts.iter().max()` and `instruction.program_id_index` compared against `account_keys.len()`) to `parse_ui_instruction`/`make_ui_partially_decoded_instruction` before indexing, returning a decode error (fallback to raw/compiled representation) instead of panicking, consistent with the defensive pattern already used in `parse_system`, `parse_stake`, `parse_token`, `parse_associated_token`, and `parse_address_lookup_table`.

### Proof of Concept
Not independently reproduced in this analysis (no execution/tooling access). Conceptually: construct a `CompiledInstruction` with `program_id_index` or an entry in `accounts` set to a value `>= account_keys.len()` for a `VersionedTransaction`, get it persisted into the `Blockstore` (bypassing/absent the normal sanitize gate), then call `getTransaction`/`getBlock` with `encoding: "json"` or `"jsonParsed"`; the resulting call into `parse_ui_instruction` → `account_keys[instruction.program_id_index as usize]` (or the `.map(|&i| account_keys[i as usize])` in `make_ui_partially_decoded_instruction`) would panic with an index-out-of-bounds. This needs confirmation that such an unsanitized instruction can actually reach the blockstore/read path given the codebase's sanitization guarantees.

fn make_ui_partially_decoded_instruction(
    instruction: &CompiledInstruction,
    account_keys: &AccountKeys,
    stack_height: Option<u32>,
) -> UiPartiallyDecodedInstruction {
    UiPartiallyDecodedInstruction {
        program_id: account_keys[instruction.program_id_index as usize].to_string(),
        accounts: instruction
            .accounts
            .iter()
            .map(|&i| account_keys[i as usize].to_string())
            .collect(),
        data: bs58::encode(instruction.data.clone()).into_string(),
        stack_height,
    }
}

pub fn parse_ui_instruction(
    instruction: &CompiledInstruction,
    account_keys: &AccountKeys,
    stack_height: Option<u32>,
) -> UiInstruction {
    let program_id = &account_keys[instruction.program_id_index as usize];
    if let Ok(parsed_instruction) = parse(program_id, instruction, account_keys, stack_height) {
        UiInstruction::Parsed(UiParsedInstruction::Parsed(parsed_instruction))
    } else {
        UiInstruction::Parsed(UiParsedInstruction::PartiallyDecoded(
            make_ui_partially_decoded_instruction(instruction, account_keys, stack_height),
        ))
    }
}
