## Finding

### Title
Stale confirmations from removed multisig members are still counted toward the execution threshold, allowing a request to execute with fewer live-member approvals than `num_confirmations` requires - ([File: multisig2/src/lib.rs])

### Summary
`confirm()` counts entries in the `confirmations: LookupMap<RequestId, HashSet<String>>` set to decide whether a request has reached `num_confirmations` and should execute. When a member is removed via `DeleteMember`, `delete_member()` only purges *requests originated by* that member (`r.member == member`), never scrubbing that member's identity out of the `confirmations` sets of *other* pending requests it had previously confirmed. A removed member's stale confirmation therefore continues to count toward the threshold of any request it confirmed before removal.

### Finding Description
In `confirm()`, the check is purely a cardinality check on the `confirmations` `HashSet<String>`: [1](#0-0) 

In `delete_member()`, cleanup is scoped only to requests whose `MultiSigRequestWithSigner.member` (i.e., the original creator/signer) equals the removed member — it never inspects or scrubs the `confirmations` map of requests created by *other* members: [2](#0-1) 

This is the same class of bug as the referenced report: an index/membership-tracking structure (`voucherIndexes` in the Union report, `confirmations` here) is not kept consistent when the underlying entity (a voucher staker / a multisig member) is removed, so a stale reference is later trusted as if it were still valid. Here, the "custody binding" that breaks is: *number of confirmations counted toward threshold == number of live members who actually approved*. That equality is violated because a confirmation from an account no longer in `self.members` (an `UnorderedSet<MultisigMember>`) is never removed from `confirmations`.

### Impact Explanation
This lets a request execute (including `Transfer`, `FunctionCall`, `AddKey`, `DeployContract`, etc.) with fewer *currently valid* member approvals than `num_confirmations` mandates, because one or more of the counted "confirmers" is no longer a member. This is a "multisig request executed below threshold" scenario — Critical impact per the rubric, since it can move funds or grant privileged access without the intended quorum of live signers.

### Likelihood Explanation
This requires only the ordinary, unprivileged sequence of multisig operations already supported by the contract: a member confirms a pending request, that member is later removed (a routine `DeleteMember` action any multisig can perform for legitimate reasons, e.g. rotating out a compromised or departing signer), and the request is later pushed over threshold by a remaining member. No special privileges beyond normal multisig membership are required, and the flow does not depend on any deployment misconfiguration — it is a logic gap in `delete_member`/`confirm` present under the documented initialization.

### Recommendation
When a member is deleted, iterate all pending requests' `confirmations` sets (not just requests it authored) and remove the member's `to_string()` key from each. Alternatively, re-validate at confirm/execute time that every entry in the `confirmations` set still corresponds to a current member of `self.members`, discarding stale entries before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `MultiSigContract::new(members = [A, B, C, D], num_confirmations = 3)`.
2. `B` calls `add_request(transfer_request)` → `request_id`.
3. `A` calls `confirm(request_id)` → confirmations = `{A}`.
4. `D` calls `confirm(request_id)` → confirmations = `{A, D}` (below threshold, not yet executed) — see [3](#0-2) .
5. Members separately pass a `DeleteMember { member: D }` request (e.g. because D is suspected compromised). `delete_member` runs: it only looks for requests where `r.member == D` (requests *created* by D) — the transfer request from step 2 was created by `B`, so it is untouched and its `confirmations = {A, D}` remains intact — see [4](#0-3) . Members are now `[A, B, C]`, still `>= num_confirmations (3)`, so the removal succeeds.
6. `C` calls `confirm(request_id)` → confirmations becomes `{A, D, C}`, length 3 `>= num_confirmations (3)`, so `remove_request` + `execute_request` runs the transfer — even though `D` is no longer a member and only two live members (`A`, `C`) plus `B`'s original creation actually participated with current standing. [5](#0-4)

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }

    /// Removes request, removes confirmations and reduces num_requests_pk - used in delete, delete_key, and confirm
    fn remove_request(&mut self, request_id: RequestId) -> MultiSigRequest {
        // remove confirmations for this request
        self.confirmations.remove(&request_id);
        // remove the original request
        let request_with_signer = self
            .requests
            .remove(&request_id)
            .unwrap_or_else(|| env::panic_str("Failed to remove existing element"));
        // decrement num_requests for original request signer
        let original_member = request_with_signer.member;
        let mut num_requests = self
            .num_requests_pk
            .get(&original_member.to_string())
            .unwrap_or(0);
        // safety check for underrun (unlikely since original_signer_pk must have num_requests_pk > 0)
        if num_requests > 0 {
            num_requests = num_requests - 1;
        }
        self.num_requests_pk
            .insert(&original_member.to_string(), &num_requests);
        // return request
        request_with_signer.request
    }
