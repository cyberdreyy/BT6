### Title
Asset-token decimals validation lives only in the factory, not in `B20AssetStorage::initialize` - (File: `crates/common/precompiles/src/b20_asset/storage.rs`)

### Summary
`B20AssetStorage::initialize` writes `decimals` (and all other B20-asset creation fields) to storage with no bounds check of its own. The only place `decimals` is checked against `MIN_DECIMALS`/`MAX_DECIMALS` is a separate helper, `TokenCreateParams::validate_asset`, called by the factory *before* `initialize` runs. This is structurally identical to the Atlendis/`LoanState` pattern: a storage-writing constructor that has no self-contained validation and instead assumes an external caller already validated the data.

### Finding Description
`B20AssetStorage::initialize` is the atomic writer for a newly created asset B-20 token: [1](#0-0) 

Its doc comment for the `decimals` field states plainly that the field is *not* self-validated: "Custom decimal precision for this token; range is validated by the factory." [2](#0-1) 

The actual bound check (`MIN_DECIMALS`/`MAX_DECIMALS`) lives entirely in `TokenCreateParams::validate_asset`, in a different module (`b20_factory/logic/v1.rs`), and is invoked by the factory's `create_b20` flow strictly *before* it calls `init_asset_token` → `B20AssetStorage::initialize`: [3](#0-2) [4](#0-3) 

This mirrors exactly the report's flagged anti-pattern: `LoanState`'s constructor had no validation of `totalPaymentsCount`, and the actual checks lived in `LoanFactoryBase.deployLoan`, a separate contract that callers had to remember to invoke. Here, `B20AssetStorage::initialize` (the "constructor" of the token's on-chain storage) has no self-contained decimals check; it depends entirely on `FactoryV1::create_b20`/`TokenCreateParams::validate_asset` running first. There is currently exactly one production call site that performs this sequencing correctly (`FactoryV1::init_asset_token`) [5](#0-4) , but nothing in `B20AssetStorage::initialize` itself enforces it, so any future code path (a new factory version, an admin/migration entry point, a differently-ordered refactor) that calls `initialize` without first calling `validate_asset` would silently persist an out-of-range `decimals` value with no revert.

The read path does not re-clamp on the way out either: `B20AssetStorage::decimals()` only substitutes `MIN_DECIMALS` when the stored value is exactly `0`; any other out-of-range value (e.g., `255`) is returned verbatim. [6](#0-5) 

### Impact Explanation
`decimals` is a creation-time-only field (never mutated after `initialize`), so any bug that lets an out-of-range value slip through is permanent and unrecoverable for that token. Downstream code (WAD-scaled `multiplier` arithmetic, ERC-20 `decimals()` display, and any DeFi integration reading the value) assumes `decimals ∈ [MIN_DECIMALS, MAX_DECIMALS]` (`[6, 18]`). A token created with a decimals value outside that range would produce inconsistent/incorrect scale semantics relative to every other B20 asset on Base, which can lead to accounting corruption or user-facing fund-value misrepresentation for that specific token — a Medium-severity, permanent-freeze/corruption-adjacent data-integrity issue rather than a chain-wide halt.

### Likelihood Explanation
No currently reachable transaction sequence bypasses `validate_asset` today, since `create_b20`'s only production path calls it before `initialize`. The risk is the same one Trail of Bits flagged for Atlendis: it takes only one future code change (a new factory version, an alternate init entry point, or a refactor that reorders these two calls) to silently drop the check, because `initialize` gives no compile-time or run-time signal that it depends on external validation having already run. This is a data-validation architecture weakness rather than an actively exploitable bug in the current call graph.

### Recommendation
- Short term: Move the `decimals` (and any other creation-time invariant) check into `B20AssetStorage::initialize` itself, so the storage writer cannot be called with invalid data regardless of caller.
- Long term: Apply the same principle project-wide to all `initialize`/storage-writer functions in the B20 asset/stablecoin/factory precompiles — validate as close as possible to the point of storage mutation rather than relying on a separate caller-side helper (`TokenCreateParams::validate`) that a future code path could bypass.

### Proof of Concept
Not applicable as an active exploit against the current codebase — no production caller today invokes `B20AssetStorage::initialize` without first calling `TokenCreateParams::validate_asset`. The finding is a structural data-validation weakness (validation-at-a-distance) analogous to the reported `LoanState`/`LoanFactoryBase` pattern, demonstrated by the code paths cited above: `initialize` at `crates/common/precompiles/src/b20_asset/storage.rs:68-75` performs no bound check, while the only enforcement is `validate_asset` at `crates/common/precompiles/src/b20_factory/logic/v1.rs:322-331`, invoked from `create_b20` at `crates/common/precompiles/src/b20_factory/logic/v1.rs:194-200` — one call removed from the write.

/// Creation-time parameters for an asset B-20 token.

/// Passed to [`B20AssetStorage::initialize`] to write all fields atomically.
#[derive(Debug)]
pub struct B20AssetInit {
    /// ERC-20 token name.
    pub name: String,
    /// ERC-20 token symbol.
    pub symbol: String,
    /// Maximum total supply.
    pub supply_cap: U256,
    /// Multiplier at WAD precision.
    pub multiplier: U256,
    /// Custom decimal precision for this token; range is validated by the factory.
    pub decimals: u8,
}

impl<'a> B20AssetStorage<'a> {
    /// Creates a `B20AssetStorage` instance targeting `addr`.
    pub fn from_address(addr: Address, storage: StorageCtx<'a>) -> Self {
        Self::__new(addr, storage)
    }

    /// Writes all creation-time fields atomically.
    pub fn initialize(&mut self, init: B20AssetInit) -> Result<()> {
        self.b20.name.write(init.name)?;
        self.b20.symbol.write(init.symbol)?;
        self.b20.supply_cap.write(init.supply_cap)?;
        self.asset.decimals.write(init.decimals)?;
        self.asset.multiplier.write(init.multiplier)?;
        Ok(())
    }

impl Factory for FactoryV1 {
    fn create_b20(
        &self,
        storage: &mut B20FactoryStorage<'_>,
        call: IB20Factory::createB20Call,
        address_hash: B256,
        upgrade: BaseUpgrade,
    ) -> Result<Address> {
        let variant = B20Variant::from_abi(call.variant)
            .ok_or_else(|| BasePrecompileError::revert(IB20Factory::InvalidVariant {}))?;
        ActivationRegistryStorage::new(storage.storage())
            .ensure_activated(variant.activation_feature().id())?;
        let params = TokenCreateParams::decode(variant, &call.params)?;
        Self::check_version(params.version(), variant)?;
        params.validate()?;
        let (token_address, _) = variant.compute_address_from_hash(address_hash);

        let already_deployed = storage
            .storage()
            .with_account_info(token_address, |info| Ok(!info.is_empty_code_hash()))?;
        if already_deployed {
            return Err(BasePrecompileError::revert(IB20Factory::TokenAlreadyExists {
                token: token_address,
            }));
        }

        let checkpoint = storage.storage().checkpoint();
        let stub = Bytecode::new_legacy(Bytes::from_static(&[0xef]));
        storage.storage().set_code(token_address, stub)?;

        let init_calls = call.initCalls;
        match params {
            TokenCreateParams::Stablecoin { common, init } => {
                self.init_stablecoin(storage, token_address, common, init, init_calls, upgrade)?;
            }
            TokenCreateParams::Asset { common, init } => {
                self.init_asset_token(storage, token_address, common, init, init_calls, upgrade)?;
            }
        }

        checkpoint.commit();
        Ok(token_address)
    }
