### Title
Miner/coordinator `StackerDBListener` thread can be permanently crashed by a signer entry lookup failure on `slot_id` - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The `StackerDBListener::run()` loop, which is the miner-side coordinator that tallies signer approvals/rejections needed to reach the 70% signing threshold, terminates the entire listener thread with `Err(...)` the moment it processes any signer message whose `slot_id` is not present in its locally-cached `signer_entries` map. Because this lookup failure returns out of the `run()` loop (not just `continue`s the single message), a single unexpected/mismatched message permanently kills the coordinator thread for that mining tenure, wedging the miner's ability to ever gather signatures again — an availability/liveness break analogous to the Mattermost Calls-plugin panic, where a single malformed request (missing header) crashed a whole in-process component.

### Finding Description
In `handle_event_match`'s counterpart on the node side, `StackerDBListener::run()` iterates over every incoming `SignerMessages` batch and, for each `(slot_id, _pk, message)` triple, does: [1](#0-0) 

```rust
for (slot_id, _pk, message) in messages.into_iter() {
    let Some(signer_entry) = &self.signer_entries.get(&slot_id) else {
        return Err(NakamotoNodeError::SignerSignatureError(
            "Signer entry not found".into(),
        ));
    };
    ...
```

`self.signer_entries` is a `HashMap<u32, NakamotoSignerEntry>` populated once, at listener construction time, from `reward_set.signers().iter().enumerate()`: [2](#0-1) 

`slot_id` itself comes straight from the raw StackerDB chunk metadata (`chunk.slot_id`) supplied by whichever signer wrote the chunk, threaded through unmodified in `libsigner/src/events.rs`'s `TryFrom<StackerDBChunksEvent>`: [3](#0-2) 

Note that this code path only verifies that `chunk.recover_pk()` succeeds (i.e., *some* valid signer key signed the chunk) and that the payload type matches the message-id "lane" — it never cross-checks that `chunk.slot_id` is the slot actually assigned to that recovered pubkey, nor that it falls inside the range the coordinator's `signer_entries` map was built from. The correctness of `slot_id -> signer_entries[slot_id]` therefore depends entirely on the write-side StackerDB slot-ownership enforcement and on `signer_entries` being built from the exact same reward-set ordering/size used to authorize StackerDB slot writes for that reward cycle. If those two derivations ever diverge even slightly (e.g., different signer-entry filtering/ordering, index vs. `signer_id` mismatch, a reward-cycle boundary, or any signer legitimately holding a slot number outside the coordinator's locally cached range), a completely ordinary signer message with a valid signature will fail this lookup.

Instead of skipping/ignoring that single message (as every other malformed-input case in this same function does — e.g. line 378-383's `signer_pubkey` parse failure, or the various `continue`-on-error branches for invalid signatures, unknown blocks, etc.), the `slot_id` lookup miss does `return Err(...)`, which propagates out of the `for` loop **and out of the entire `run()` method**, ending the listener's `loop { ... }` for good. Every other branch in this exact function treats untrusted/unexpected signer input defensively with `continue`; this one branch alone treats it as fatal.

### Impact Explanation
`StackerDBListener` is the coordinator that a Nakamoto miner uses to gather 70%-weighted approvals to push a block. Killing this single background thread wedges the miner into a state where it can never again observe or tally signer accept/reject votes for the remainder of that tenure/reward-cycle registration — a High-severity liveness break matching the rules' definition: "a signer [participant/coordinator] wedged into never signing/counting valid responses." Unlike a majority-signer or auth-token-gated attack, this requires only a single message from a single legitimately-signing signer (or an out-of-band/gossip-relayed chunk with a valid recovered signature but a slot number the coordinator doesn't expect) to reach this code path — no majority collusion, no StackerDB flooding, and no access to node secrets is needed.

### Likelihood Explanation
The trigger condition ("a message arrives whose signer-recovered `slot_id` is not a key in `self.signer_entries`") is plausible any time the miner's cached signer-entry index mapping and the StackerDB slot-authorization mapping are not perfectly identical for a given reward cycle — e.g., during a reward-set/registration edge case, a differently-ordered/filtered signer list, or simply a stale/mismatched entry produced during a rolling reward-cycle transition. Given that every neighboring validation failure in the same block of code is handled by `continue` rather than `return Err`, this asymmetry strongly suggests the fatal `return Err` here is an oversight rather than an intentional "this can never happen" invariant — making it a realistic single-message DoS path rather than a purely theoretical one.

### Recommendation
Change the `slot_id` lookup-miss branch to `continue` (log and skip the message) instead of `return Err(...)`, consistent with how every other malformed/unexpected-input case in this function is handled (invalid signature, invalid pubkey format, mismatched block hash, unknown block, etc.). This prevents a single anomalous or mismatched signer message from tearing down the entire coordinator thread and wedging block-signature collection for the rest of the tenure.

### Proof of Concept
1. A signer set is registered for reward cycle `R`; `StackerDBListener::new()` builds `signer_entries` from `reward_set.signers().enumerate()` at listener startup (`stacks-node/src/nakamoto_node/stackerdb_listener.rs:227-239`).
2. Any process capable of writing a validly-signed chunk to the `.signers-R-<parity>` StackerDB contract (i.e., any registered signer, using their normal signing key) produces a `StackerDBChunkData` whose `slot_id` does not match a key currently present in the coordinator's in-memory `signer_entries` (achievable whenever the coordinator's index mapping and the on-chain/StackerDB slot assignment diverge, e.g. at a reward-cycle boundary or ordering mismatch).
3. `SignerEvent::<SignerMessageV0>::try_from` (`libsigner/src/events.rs:580-613`) successfully recovers the sender's pubkey and deserializes the payload — the message is accepted as a valid `SignerMessages` event with the attacker/legitimate signer's chosen `slot_id`.
4. `StackerDBListener::run()` reaches `self.signer_entries.get(&slot_id)` (`stacks-node/src/nakamoto_node/stackerdb_listener.rs:373-377`), finds `None`, and executes `return Err(NakamotoNodeError::SignerSignatureError(...))`, unwinding out of `run()`'s `loop`.
5. The coordinator thread exits; the miner can no longer receive or tally any subsequent `BlockResponse`/`StateMachineUpdate` messages for the remainder of that tenure/reward cycle, wedging block signature collection (liveness break) until the node/miner process is restarted.
