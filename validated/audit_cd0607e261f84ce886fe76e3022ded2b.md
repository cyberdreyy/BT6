### Title
`get_builder_withdrawals` credits the requested amount to `withdrawal.amount` while `apply_withdrawals` clamps the balance decrease, minting Gwei to the builder's fee recipient when a pending withdrawal exceeds the builder's balance - ([File: specs/gloas/beacon-chain.md])

### Summary
In the Gloas (EIP-7732) builder-payment flow, `get_builder_withdrawals` copies the *requested* `withdrawal.amount` from `state.builder_pending_withdrawals` verbatim into the `Withdrawal` object that is committed to the execution payload, without checking it against the builder's actual balance. `apply_withdrawals`, which runs later in the same block, then only decreases `state.builders[builder_index].balance` by `min(withdrawal.amount, builder_balance)`. The execution layer credits the full, uncapped `withdrawal.amount` Gwei to `withdrawal.fee_recipient` (this is what a `Withdrawal` entry in an execution payload means - a real ETH credit), but the consensus-layer state only removes the smaller, capped amount from the builder's balance. This breaks the invariant that every Gwei credited by a withdrawal must be deducted from consensus-layer balance, i.e. it creates Gwei out of nothing and pays it to an address the state didn't actually debit.

### Finding Description
`get_builder_withdrawals` (specs/gloas/beacon-chain.md) builds the withdrawal list straight from `withdrawal.amount` with no clamp: [1](#0-0) 

Compare this to `get_pending_partial_withdrawals` (validator partial withdrawals), which explicitly clamps the requested amount against the actual balance before it is placed in the `Withdrawal`: [2](#0-1) 

For builders, no such clamp exists at withdrawal-construction time. The clamp is instead applied only when the balance is *decreased*, inside `apply_withdrawals`: [3](#0-2) 

So if `builder_pending_withdrawals` contains an entry whose `.amount` exceeds `state.builders[builder_index].balance` (e.g. because the builder's balance was independently reduced by a slashing-equivalent event, another concurrent pending withdrawal, or simply because the requester over-specified the amount when the pending withdrawal was queued), the `Withdrawal` object placed into `state.payload_expected_withdrawals` (and thus into the execution payload that the execution layer will honor) still carries the full requested `amount`. The execution layer pays `fee_recipient` the full uncapped amount, while `apply_withdrawals` only debits `builder_balance` (capping at zero). The difference between the amount paid out on the execution layer and the amount debited on the consensus layer is Gwei created from nothing.

This is exactly analogous to the PoolTogether `_computeAvailable()` bug: the reported "available" (here, "amount to withdraw") value is computed independently of the true clamp against the real balance, and only the *balance mutation* is clamped - not the *value that is actually paid out*.

### Impact Explanation
This falls under Critical impact: "Gwei created ... paid to a non-owner" and "a payload executed or paid that the block did not commit to accurately" - the block's execution payload contains a withdrawal amount that is not backed by an equivalent consensus-layer balance decrease, silently inflating total ETH supply and crediting `fee_recipient` with unearned funds.

### Likelihood Explanation
The mismatch requires `builder_pending_withdrawals[i].amount > state.builders[builder_index].balance` at the moment the sweep runs. Whether the current queuing logic in `process_execution_payload_bid` / wherever `builder_pending_withdrawals` entries are appended (`BuilderPendingWithdrawal`) guarantees `amount <= balance` at insertion time could not be fully confirmed from the excerpts examined; balances can change between enqueue time and processing time (e.g. multiple pending withdrawals against the same builder, or other balance-affecting operations), so the guarantee, if any, would need to hold across all intervening state transitions, not just at insertion. Given the test suite's own comments ("Builder withdrawals always processed, amount capped to available balance") acknowledge the balance side is capped but not that the payload's committed `amount` is capped too, this looks like a genuine spec-level gap rather than a defense-in-depth redundancy.

### Recommendation
Clamp the `amount` field written into the `Withdrawal` object in `get_builder_withdrawals` to `min(withdrawal.amount, state.builders[builder_index].balance)`, mirroring the pattern already used in `get_pending_partial_withdrawals`. Alternatively, prove (and add an explicit invariant/assert) that `builder_pending_withdrawals[i].amount` can never exceed `builders[i].balance` at processing time under all intervening state transitions, and cite the exact enqueue-side check that enforces it.

### Proof of Concept
Concrete state trace:
1. `state.builders[0].balance = 1 ETH` (1_000_000_000 Gwei).
2. `state.builder_pending_withdrawals = [BuilderPendingWithdrawal(builder_index=0, fee_recipient=X, amount=5_000_000_000)]` (5 ETH requested, e.g. queued while balance was higher, then balance dropped due to another payment/consolidation before this sweep).
3. `get_builder_withdrawals` runs: appends `Withdrawal(validator_index=builder_index_as_validator(0), address=X, amount=5_000_000_000)` unchanged. [4](#0-3) 
4. This `Withdrawal` is placed in `state.payload_expected_withdrawals`, which the execution layer is required to honor exactly - crediting address `X` with 5 ETH.
5. `apply_withdrawals` executes: `builder_balance = 1_000_000_000`; `state.builders[0].balance -= min(5_000_000_000, 1_000_000_000)` → balance becomes 0. [5](#0-4) 
6. Net effect: consensus-layer state debited only 1 ETH from builder 0, but the execution layer paid out 5 ETH to `X`. 4 ETH was created from nothing and paid to a non-owner (`X`), confirmed by the accompanying test file's own note that "Builder withdrawals always processed, amount capped to available balance" refers only to the balance side, not the payload amount: [6](#0-5)
