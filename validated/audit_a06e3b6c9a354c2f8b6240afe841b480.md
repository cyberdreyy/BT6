### Title
Stale confirmations from removed multisig members allow request execution below live `num_confirmations`, enabling arbitrary-receiver Transfer theft - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::confirm` counts confirmations recorded in a `HashSet<String>` without verifying that every confirmer is still a current member of `self.members`. `delete_member` only removes requests *created* by the removed member, leaving that member's confirmation entries on other, unrelated requests intact. Combined with the fact that `Transfer` actions in `execute_request` never call `assert_self_request` (unlike `AddMember`/`DeleteMember`/`AddKey`/`SetNumConfirmations`/`SetActiveRequestsLimit`), an attacker who is a minority member can reach the confirmation threshold using one live confirmation plus a stale confirmation from an already-removed member, and send the full contract balance to an account they control.

### Finding Description
The broken binding: `count(distinct members ∈ self.members that confirmed request R) == self.num_confirmations` is what should gate execution, but the code actually checks `confirmations.get(&request_id).len() + 1 >= self.num_confirmations` at [5](#0-4) , where `confirmations` is a raw `HashSet<String>` of member identities recorded at confirmation time, never re-validated against the live `self.members` set.

Root cause / code path:
1. Member D confirms request R (`Transfer { amount: full_balance }`, `receiver_id: attacker`). D's string identity is inserted into `self.confirmations[R]` via [6](#0-5) .
2. A separate request removes D via `DeleteMember`. `delete_member` at [7](#0-6)  only deletes requests where `r.member == member` (requests *authored* by D) and removes D from `self.members` and `num_requests_pk`; it does not touch `self.confirmations` entries for request R that D merely confirmed (as opposed to authored).
3. Attacker (still a live member) calls `confirm(R)`. `assert_valid_request` only checks the caller is a current member, not that existing confirmers still are, at [1](#0-0) .
4. `confirmations.len() (1, stale D) + 1 (attacker) >= num_confirmations (2)` passes, so `execute_request(R)` runs.
5. In `execute_request`, the `Transfer` arm at [8](#0-7)  performs `promise.transfer(amount.into())` to `request.receiver_id` with no `assert_self_request` call (contrast with `AddMember`/`DeleteMember`/`AddKey` at lines 236, 240, 247, and `SetNumConfirmations`/`SetActiveRequestsLimit` at lines 276, 283), so `receiver_id` can be any attacker-chosen account.

Existing guards fail because: `assert_self_request` is irrelevant to `Transfer` by design (receiver_id is meant to be arbitrary for fund transfers), and no code path re-verifies confirmer membership at confirm-time or scrubs stale confirmations from requests a removed member had confirmed but not authored.

### Impact Explanation
The full NEAR balance held by the multisig contract can be transferred to an attacker-chosen account using fewer live-member confirmations than `num_confirmations` requires, directly matching the Critical category "a multisig request executed below `num_confirmations` live members." This is a one-time drain per stale-confirmation window per multisig instance, but is repeatable across any multisig2-deployed contract with member turnover between confirmation and removal.

### Likelihood Explanation
Preconditions: the attacker must already be one of the multisig's members (a legitimate but minority/malicious signer), and there must be at least one other member (D) who confirms the malicious Transfer request and is later removed via a separate `DeleteMember` request before the Transfer request is deleted or otherwise invalidated. This requires some social/organizational timing (D confirms without executing, then is legitimately removed for unrelated reasons, e.g. offboarding) but requires no cryptographic or gas cost beyond normal transaction fees, and no privileged role beyond ordinary membership. Given how multisig membership changes are a normal, expected operation, this is a realistic race window rather than a purely theoretical one.

### Recommendation
When confirming a request, filter `confirmations` to only those entries whose corresponding `MultisigMember` is still present in `self.members` before comparing against `num_confirmations` (or equivalently, when a member is removed via `delete_member`, iterate all `confirmations` entries and remove that member's string key from every request's confirmation set, not just requests it authored).

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,

        // delete outstanding requests by public_key
