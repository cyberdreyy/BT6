### Title
Job-controlled `DOCKER_AUTH_CONFIG` `credsStore`/`credHelpers` allows an unprivileged job to query the runner host's shared native credential store and exfiltrate other tenants' registry credentials - (File: helpers/docker/auth/auth.go)

### Summary
`readConfigsFromCredentialsStore`/`readConfigsFromCredentialsHelper` only guard against **path traversal** in the helper name (`filepath.Base` equality check); they do not restrict *which* legitimately-installed `docker-credential-<name>` binary a job may invoke, nor do they scope what the invoked helper returns. Because `config.CredentialsStore`/`config.CredentialHelpers` are populated directly from the fully job-controlled `DOCKER_AUTH_CONFIG` variable, a pipeline author can name any real helper installed on the shared Runner host and have the Runner process (running on the host, not inside the job's container) execute it and merge its results into the job's resolved auth configs.

### Finding Description
`resolveAuthConfigForImage` (executors/docker/internal/pull/manager.go:276-302) delegates to `auth.Resolver.ConfigForImage` → `AllConfigs` → `getUserConfiguration(dockerAuthConfig)` (helpers/docker/auth/auth.go:188-198, 128-142), which parses the job-supplied `DOCKER_AUTH_CONFIG` string with `readConfigsFromReader` (auth.go:323-352). That function honors both `config.CredentialsStore` and `config.CredentialHelpers` straight from job input: [1](#0-0) 

`readConfigsFromCredentialsStore` calls `store.GetAll()`, i.e. it reads **every** entry the named helper's backing store holds, not anything scoped to the image/registry the job is pulling: [2](#0-1) 

`readConfigsFromCredentialsHelper` iterates the job-controlled `credHelpers` map and, for each attacker-chosen registry key, calls `store.Get(registry)` using an attacker-chosen helper name: [3](#0-2) 

The only validation, `helper != filepath.Base(helper)` / `config.CredentialsStore != filepath.Base(config.CredentialsStore)`, blocks `../` traversal but does nothing to prevent naming a genuinely-installed system helper (`osxkeychain`, `wincred`, `pass`, `secretservice`, `desktop`, etc.). `credentials.NewNativeStore(config, helper)` (docker/cli) resolves and executes `docker-credential-<helper>` via the **Runner host's PATH**, on the **Runner process's host**, not inside the job's container/sandbox.

Exploit flow:
1. Runner host is long-lived/shared across jobs (typical for docker/shell executors on a static host) and has a native credential helper installed with secrets cached from legitimate prior use (admin `docker login`, or another job/tenant's cached login).
2. Attacker's pipeline sets `DOCKER_AUTH_CONFIG` to `{"credsStore":"<installed-helper-name>"}` (or `credHelpers` mapping an attacker-chosen registry key to that helper).
3. `readConfigsFromCredentialsStore` calls `GetAll()`, pulling every stored credential from the shared host keychain/store into the job's resolved `RegistryInfos`, matched by `ConfigForImage`'s longest-prefix lookup (auth.go:103-120) against the image reference the job supplies.
4. By pointing the job's image reference (or `credHelpers` key) at an attacker-controlled hostname/registry, or at a well-known registry hostname the store already has cached creds for, the Runner authenticates the subsequent `docker pull` (manager.go:268-273, `pullDockerImage`) using credentials that belong to another tenant/the runner admin — leaking them to whatever server receives the pull's Basic Auth handshake.

The existing `TestResolveAuthConfigForImageErrorsOnPathTraversal` protection only stops filesystem traversal in the helper name; it does not address that any valid, installed helper name is fully attacker-selectable and that its return value (via `GetAll()`/`Get()`) is not scoped to the job's own registry.

### Impact Explanation
On a shared Runner host with a native credential store/helper configured (common for self-managed docker/shell executors that persist `~/.docker/config.json` with `credsStore`), an unprivileged job can cause the Runner process to read out cached registry credentials belonging to another project/tenant or the runner administrator, and relay them (via a pull request's Basic Auth) to an attacker-controlled registry endpoint, achieving cross-tenant secret disclosure — a direct violation of the stated invariant that job-supplied `DOCKER_AUTH_CONFIG` must never read credentials outside the job's own registry configuration.

### Likelihood Explanation
Requires: (1) the Runner host is reused across multiple jobs/tenants and is not ephemeral per-job, and (2) a native credential helper is installed and has previously-cached secrets (from an admin login or a prior job/tenant's `docker login`/`credsStore` usage) reachable by the Runner's OS user. Both conditions are realistic for long-lived, non-ephemeral self-managed Docker/shell executor hosts, making this feasible and repeatable rather than purely theoretical.

### Recommendation
Do not honor `credsStore`/`credHelpers` when parsing the job-supplied `DOCKER_AUTH_CONFIG` variable at all — restrict credential-helper/-store resolution to Runner admin-controlled sources (config.toml or the Runner's own home-directory docker config), and only allow literal `auths` (base64 user/pass) entries from the job-controlled source. If helper support from job input must be retained, resolve results per-registry only (never `GetAll()`) and cross-check that the returned server address exactly matches the registry the job is pulling from, discarding unrelated entries.

### Proof of Concept
Add a unit test in `helpers/docker/auth/auth_test.go` that stubs a fake `docker-credential-<name>` executable on `PATH` (as `TestResolveAuthConfigForImageErrorsOnPathTraversal` already sets up an environment for helper execution) which, on `list`/`get`, returns credentials for a server address (`victim-registry.example.com`) never mentioned by the "attacker" input:

```go
func TestCredentialsStoreLeaksUnrelatedHostEntries(t *testing.T) {
    // fakeHelper simulates a legitimately installed docker-credential-<name>
    // binary whose backing store already contains a credential entry for
    // "victim-registry.example.com" cached by another tenant/admin.
    installFakeHelper(t, "testhelper", map[string]types.AuthConfig{
        "victim-registry.example.com": {Username: "victim", Password: "s3cr3t"},
    })

    dockerAuthConfig := `{"credsStore":"testhelper"}`
    _, authConfigs, err := getUserConfiguration(dockerAuthConfig)
    require.NoError(t, err)

    // Assert: the job's DOCKER_AUTH_CONFIG (which never named
    // "victim-registry.example.com") must NOT surface credentials for it.
    for _, ac := range authConfigs {
        assert.NotEqual(t, "victim-registry.example.com", ac.ServerAddress,
            "job-controlled credsStore leaked another tenant's cached credentials")
    }
}
```

Expected current (vulnerable) result: the assertion fails — `authConfigs` contains the `victim-registry.example.com` entry pulled via `store.GetAll()`, proving the job obtained credentials it never configured itself.

func readConfigsFromCredentialsStore(config *configfile.ConfigFile) (map[string]types.AuthConfig, error) {
	if config.CredentialsStore != filepath.Base(config.CredentialsStore) {
		// Fail processing if credential store attempting path traversal are detected
		return nil, errPathTraversal
	}

	store := credentials.NewNativeStore(config, config.CredentialsStore)
	newAuths, err := store.GetAll()
	if err != nil {
		return nil, err
	}

	return newAuths, nil
}

func readConfigsFromCredentialsHelper(config *configfile.ConfigFile) (map[string]types.AuthConfig, error) {
	helpersAuths := make(map[string]types.AuthConfig)

	for registry, helper := range config.CredentialHelpers {
		if helper != filepath.Base(helper) {
			// Fail processing if credential helpers attempting path traversal are detected
			return nil, errPathTraversal
		}

		store := credentials.NewNativeStore(config, helper)

		newAuths, err := store.Get(registry)
		if err != nil {
			return nil, err
		}

		helpersAuths[registry] = newAuths
	}

	return helpersAuths, nil
}
