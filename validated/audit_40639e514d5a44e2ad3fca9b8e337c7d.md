### Title
Post-default withdraw requests pay 1:1 from the fixed default-recovery reserve, draining recoveries owed to defaulted-epoch claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.requestWithdraw` creates post-default receipts (`postDefaultRequests`) that are paid 1:1 out of `defaultRecoveryReserve` via `_claimPostDefaultWithdrawRequest` → `_transferDefaultRecovery`, without pulling any underlying into the strategy at request time. The reserve was sized at `finalizeDefaultRecovery` to exactly cover `Σ(claimBasis_i * defaultRecoveryPrice)` for defaulted-epoch receipts. Every 1:1 post-default payout therefore consumes reserve belonging to other claimants, causing an OOB-style over-read of the recovery buffer: later (or slower) defaulted-epoch claimants hit an underflow revert in `_transferDefaultRecovery` and their recovery is permanently frozen.

### Finding Description
The external bug (CVE-2020-11760) is an out-of-bounds read during RLE uncompression: the decoder reads past the end of the input buffer because consumed output is not bounded by what was actually encoded. The credit-vault analog is spending past an accounted boundary: `defaultRecoveryReserve` is a fixed "buffer" allocated in `finalizeDefaultRecovery` (lines 686–692) as `reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` with `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis`, i.e. precisely sized so that all defaulted-epoch claims sum to the reserve.

After finalization, `requestWithdraw` (lines 247–257) takes the `defaultRecoveryFinalized` branch: it only checks the caller has no pending receipts, then `_burn`s/`_mint`s receipts and sets `postDefaultRequests[_user] = _amount` — **no `underlyingToken.safeTransferFrom` and no `reserveDefaultRecovery` call occurs**, so the reserve is unchanged while a new 1:1 claim against it is created.

`claimWithdrawRequest` (lines 301–314) then routes to `_claimPostDefaultWithdrawRequest` (lines 760–767), which pays `amount` 1:1 through `_transferDefaultRecovery` (lines 912–917), decrementing `defaultRecoveryReserve`. Since the reserve only contains `Σ basis_i * price`, each post-default payment makes the accounting equation `reserve >= Σ remaining basis_i * price` false; when defaulted-epoch claimants later call `claimWithdrawRequest`, `_claimDefaultedWithdrawRequest` → `_transferDefaultRecovery` reverts on `defaultRecoveryReserve -= _amount` underflow (or pays out leaving the reserve short for others).

A comment at line 252 says post-default requests are "already backed by default recovery reserve," but the reserve's sizing math in `finalizeDefaultRecovery` provably contains no headroom for them: `totalBasis` counts only `activeBasis + pendingBasis` (line 679–680), i.e. defaulted-epoch receipts.

### Impact Explanation
Direct theft plus permanent freezing: any KYC-passing lender (or tranche holder able to trigger `IdleCDOEpochVariant.requestWithdraw` post-default) can front-run defaulted-epoch claimants and extract up to the full remaining `defaultRecoveryReserve` at par, instead of at `defaultRecoveryPrice`. Quantified worst case: with recovery price `p < 1`, a post-default requester withdraws `X` while defaulted claimants holding total basis `B` are only owed `B·p`; every unit paid post-default removes `1/p` units of a defaulted claimant's entitlement. The last claimants' withdrawals revert permanently — recovery is frozen in the contract (no sweep/rescue function for `defaultRecoveryReserve` exists).

### Likelihood Explanation
Requires a borrower default to be finalized with `defaultRecoveryPrice < RECOVERY_FULL` and residual reserve — a real but episodic state. Once in that state, the attacker needs only to pass `isWalletAllowed`/Keyring KYC and make one post-default withdraw request before legitimate claimants claim. The only mitigating factor is whether `IdleCDOEpochVariant`'s post-default request path separately tops up the reserve via `reserveDefaultRecovery` (which the code does not do inside `requestWithdraw` itself); if the CDO does push matched funding, the attack reduces to reserve accounting dust. This is the key assumption to verify in the PoC.

### Recommendation
In `requestWithdraw`'s post-default branch, either (a) pull `_amount` underlying from the CDO/recovery source into the strategy and add it to `defaultRecoveryReserve` before minting the receipt, or (b) pay post-default claims through a separate accounting bucket funded by the CDO, never via `_transferDefaultRecovery`. Also consider applying `defaultRecoveryPrice` to post-default claims for consistent haircut semantics.

### Proof of Concept
Foundry fork PoC sketch:

```solidity
// Setup: standard epoch CDO + IdleCreditVault, AA depositors, APR0 or fixed-APR.
// 1. userA deposits, epoch runs, userA requests withdraw in epoch E (receipt basis B_A).
// 2. Borrower defaults; owner calls handleBorrowerDefault, then finalizeDefaultRecovery
//    with recoveredAmount R < totalBasis  => defaultRecoveryPrice p = R/basis < 1e18,
//    defaultRecoveryReserve = R (+ prefunded).
// 3. Attacker (fresh KYC'd address, no prior requests) deposits post-default dust if
//    needed, then calls cdo.requestWithdraw(X, tranche) -> strategy mints
//    postDefaultRequests[attacker] = X with NO underlying inflow.
// 4. attacker calls cdo.claimWithdrawRequest() -> _transferDefaultRecovery pays X at
//    par; defaultRecoveryReserve -= X.
// 5. userA calls claimWithdrawRequest() -> _claimDefaultedWithdrawRequest computes
//    amount = B_A * p / 1e18; _transferDefaultRecovery reverts (reserve - amount < 0)
//    whenever X > R - B_A*p. userA's recovery is permanently frozen.
// Assert: attackerBalanceDelta == X; vm.expectRevert on userA claim;
//         defaultRecoveryReserve < remainingBasis * defaultRecoveryPrice / 1e18.
```

Caveat: step 3–4 must be validated against `IdleCDOEpochVariant.requestWithdraw`/`stopEpoch` post-default handling to confirm no compensating `reserveDefaultRecovery`/`collectWithdrawFunds` top-up occurs on the CDO side; if such a top-up exists, the drain is neutralized and no vulnerability remains.
