### Title
Attacker-controlled multi-line command content can forge fake `section_start`/`section_end` trace markers in its own job log - ([File: functions/script_legacy/internal/trace_section.go])

### Summary
`TraceSectionWriter.writeSectionStart` embeds the full, attacker-controlled multi-line command text as a decorative "$ preview" inside the same `printf` statement that emits the real `section_start:...` marker, using `EscapeForAnsiC` + ANSI-C `$'...'` quoting. Because ANSI-C quoting is a byte-faithful round-trip encoding, any control byte (including `\r`, `\n`, and ESC `0x1B` via `\x1b`) in the job's command is reconstructed verbatim by bash when the line is printed, letting a crafted command fabricate a look-alike `section_end:...\r\033[0K` (or `section_start:...`) byte sequence inside the trace stream.

### Finding Description
`ProcessCommand` → `shouldUseTraceSection` (true when `trace_sections=true` and the command is multi-line) → `TraceSectionWriter.WriteSection` → `writeSectionStart`: [1](#0-0) [2](#0-1) 

`writeSectionStart` builds `command = w.escape(ansiBoldGreen + commandPrefix + command + ansiResetTrace)` and interpolates it directly, unseparated by a shell-word boundary, into the same `printf` invocation as the real `section_start:...\r%s` marker prefix. `escape` wraps the result in `$'...'` using `EscapeForAnsiC`: [3](#0-2) 

`EscapeForAnsiC` converts `\n`→`\n`, `\r`→`\r`, and every other control/non-ASCII byte to `\xHH`: [4](#0-3) 

The function's own comment claims this "prevents jobs from ... rewriting logs using ANSI escape sequences" — that claim is incorrect. ANSI-C quoting (`$'...'`) is defined to be a lossless encoding: bash decodes `\n`, `\r`, and `\xHH` back into the literal original bytes when the string is expanded and printed by `printf`. So `EscapeForAnsiC` only prevents the payload from breaking out of the *shell syntax* during script generation (i.e., command injection); it does **not** neutralize the bytes once they reach the printed trace output. Since the escaped command sits directly adjacent (no space) to the literal `section_start:...[opts]\r<clear>` prefix in the same `printf` argument, an attacker who controls the job command can include, as ordinary text within a multi-line command, a sequence that decodes to `\n` + `section_end:<digits>:section_script_step_<N>` + `\r` + ESC`[0K` — i.e., a byte-for-byte forged section marker — embedded inside the "preview" portion of the genuine `section_start` line.

Because the real `writeSectionEnd` still emits its own genuine `section_end` marker afterward, the trace stream now contains an extra, unmatched marker before the real one, unbalancing the start/end marker count for that job's own log.

### Impact Explanation
Within the codebase available, `TraceSectionWriter`/`CommandProcessor` hold no state that persists or is shared across jobs, retries, or runner cache reuse — `index` is purely a per-invocation counter used to name sections (`script_step_N`) inside one generated script; I found no cross-job or cross-project shared trace-section state in this repository. The claimed "persistent log corruption affecting other projects' pipelines sharing the runner" is not substantiated by any code found here — GitLab's server-side trace/section parsing operates per-job-trace, and no shared index/state mechanism exists in Runner to carry corruption across jobs.

The concrete, verifiable impact is scoped to **that job's own trace/log rendering**: a forged marker inside the section preview can desynchronize the start/end count for that job, causing GitLab's UI to render an incorrectly nested/never-closed (or prematurely closed) collapsible section for that single job's log. This is a real log-integrity/UI-spoofing issue for the attacker's own job, but not the described cross-project/shared-runner persistence.

### Likelihood Explanation
Preconditions match exactly what's stated: `trace_sections=true` and a job command containing embedded control bytes/newlines (fully attacker-controlled via `.gitlab-ci.yml` `script:` multi-line entries). No special privileges are required beyond being a normal pipeline author. The path is directly reachable through `ProcessCommand` whenever `isMultiline(command)` is true.

### Recommendation
Do not interpolate the full, escaped, user-controlled command as a raw unquoted-adjacent fragment inside the same `printf` argument as the literal marker text. Either:
- Truncate/sanitize the preview to a single line (strip/replace `\n`, `\r`, ESC before display) so no control bytes reach the shell's `$'...'` decode step, or
- Emit the marker text and the command preview as separate, clearly delimited `printf` arguments/lines so a forged sequence in the preview cannot be adjacent to (and thus mistaken as part of) the real marker line, or
- Filter/reject literal occurrences of `section_start:`/`section_end:` patterns (and control bytes that could reconstruct them) from the preview text specifically.

### Proof of Concept
```go
func TestTraceSectionWriter_ForgedSectionMarker(t *testing.T) {
    writer := NewTraceSectionWriter(false, false)
    var buf strings.Builder

    // Crafted multi-line command; \r and \n bytes are attacker-controlled input.
    payload := "line1\nsection_end:9999999999:section_script_step_0\r\x1b[0K\nline2"

    writer.WriteSection(&buf, 0, payload)
    result := buf.String()

    // Count section_end occurrences reachable in the raw generated script text
    // (proxy for what would appear in the decoded trace once bash evaluates it).
    startCount := strings.Count(result, "section_start:")
    endCount := strings.Count(result, "section_end:")

    // Expect exactly 1 start and 1 end per WriteSection call; a forged marker
    // embedded via the escaped preview breaks this invariant once bash decodes
    // the $'...' string (verified by shelling out to bash and inspecting stdout).
    assert.Equal(t, 1, startCount)
    assert.Equal(t, 1, endCount, "forged section_end text injected via command preview")
}
```
A full end-to-end PoC would pipe the generated script through an actual `bash` interpreter and assert that the decoded stdout contains more than one `section_end:`/`section_start:` occurrence for a single `WriteSection` call, confirming the marker-count invariant is violated for that job's trace.

// writeSectionStart writes the section_start marker with command preview.
// Format: section_start:TIMESTAMP:section_NAME[options]\r\e[0K\e[32;1m$ COMMAND\e[0;m
func (w *TraceSectionWriter) writeSectionStart(buf *strings.Builder, sectionName, command string) {
	command = w.escape(ansiBoldGreen + commandPrefix + command + ansiResetTrace)

	fmt.Fprintf(buf, "printf '%%s\\n' "+
		"section_start:%s:section_%s[%s]\r%s%s\n",
		timestampCommand,
		sectionName,
		traceSectionOptions,
		ansiClear,
		command)
}

func EscapeForAnsiC(s string) string {
	var buf strings.Builder

	for i := 0; i < len(s); i++ {
		c := s[i]
		switch c {
		case '\\':
			buf.WriteString("\\\\")
		case '\'':
			buf.WriteString("\\'")
		case '\n':
			buf.WriteString("\\n")
		case '\r':
			buf.WriteString("\\r")
		case '\t':
			buf.WriteString("\\t")
		case '\a':
			buf.WriteString("\\a")
		case '\b':
			buf.WriteString("\\b")
		case '\f':
			buf.WriteString("\\f")
		case '\v':
			buf.WriteString("\\v")
		default:
			// Hex-escape control characters (0x00-0x1F, 0x7F) and non-ASCII (>0x7F)
			// This prevents ANSI escape sequences (ESC = 0x1B) from manipulating terminal
			if c < 0x20 || c == 0x7F || c > 0x7F {
				fmt.Fprintf(&buf, "\\x%c%c", hextable[c>>4], hextable[c&0x0f])
			} else {
				buf.WriteByte(c)
			}
		}
	}

	return buf.String()
}
