### Title
Signer and miner block signatures omit chain/network identifier, permitting cross-context signature replay - ([File: stackslib/src/chainstate/nakamoto/mod.rs])

### Summary
The Nakamoto block header signature preimages computed by `miner_signature_hash_inner` and `signer_signature_hash_inner` in `stackslib/src/chainstate/nakamoto/mod.rs` never commit to a chain ID, network ID, or any other value that scopes the signature to a specific chain/deployment. Only `NakamotoBlockHeader` fields (`version`, `chain_length`, `burn_spent`, `consensus_hash`, `parent_block_id`, `tx_merkle_root`, `state_index_root`, `timestamp`, and conditionally `problematic_txs`) are hashed, plus `miner_signature` for the signer hash. [1](#0-0)  This is analogous to the reported ERC20Permit issue: because no chain-scoping value is folded into the signed digest, a miner/signer signature that is valid for one chain/network deployment is equally valid for another chain/deployment that happens to produce an identical header (e.g., a hard-forked or independently-run chain sharing the same signer keys and header field values).

### Finding Description
`verify_signer_signatures` in the same file recovers each signer's public key purely from `self.signer_signature_hash()` and matches it against `reward_set.signers()` — no chain-scoping data is checked. [2](#0-1)  Notably, other message types in the signer protocol *do* domain-separate by chain ID — for example `BlockRejection::hash()` explicitly folds `self.chain_id` into a structured-data domain tuple before hashing [3](#0-2)  — showing that chain-ID domain separation is a known pattern used elsewhere in this codebase but is absent from the actual consensus-critical block header signature that miners and signers produce.

The `NakamotoBlockProposal` RPC wrapper used by `postblock_proposal.rs` does carry a `chain_id` field that is checked for a `NetworkChainMismatch` at proposal-validation time, as shown in the test cases (`Invalid \`chain_id\`` -> `NetworkChainMismatch`). [4](#0-3)  However, that check only gates whether a *node* will accept a proposal over its RPC endpoint; it is not part of the digest that miners sign (`miner_signature_hash`) or that signers sign (`signer_signature_hash`), and it is not re-derived or embedded anywhere in the persisted `NakamotoBlockHeader` or in `verify_signer_signatures`. Consequently, once a valid miner/signer signature over a given header exists, nothing in the signature itself binds it to a particular chain ID, network ID, or genesis/fork identity.

### Impact Explanation
This breaks the "cross-context-valid signature" invariant: a miner or signer signature collected under one chain/network context can be replayed as a valid signature for an identical header in a different context (e.g., mainnet vs. a permissionless L2/subnet fork built from the same stacks-core codebase and reusing the same signer key set, or two independently-launched chains that happen to produce matching `consensus_hash`/`parent_block_id`/`state_index_root` sequences). Because `verify_signer_signatures` only checks recoverability against the reward set's public keys — and reward-set membership is derived purely from stacking, independent of chain ID — a signature harvested from context A satisfies the equality check performed by context B's chainstate, letting an attacker present a block as validly signed on a chain it was never intended for.

### Likelihood Explanation
Exploitability requires a scenario where two chain contexts share (a) the same signer private keys/reward set and (b) produce headers with byte-identical hashed fields. This is plausible for permissioned or semi-permissioned deployments derived from stacks-core (subnets, testnets reusing production signer keys, or a hard fork retaining the same signer set and continuing to produce compatible headers), similar to the classic EIP-2612 hard-fork replay scenario the external report describes. It does not require a majority of signers or another signer's key — a single one-slot miner (plus the gossip of signer responses that are already broadcast) can trigger the replay by re-submitting a captured signature/block pair into the other context.

### Recommendation
- **Short term**: Bind the miner and signer signature preimages to a chain-scoping value, analogous to `block.chainid`/`DOMAIN_SEPARATOR` recomputation in EIP-2612. Concretely, include a `chain_id` (or equivalent network/genesis identifier) field in `miner_signature_hash_inner` and `signer_signature_hash_inner` in `stackslib/src/chainstate/nakamoto/mod.rs`, and validate it during `verify_signer_signatures` and `recover_miner_pk`, mirroring the domain-separation approach already used for `BlockRejection::hash()` in `libsigner/src/v0/messages.rs`.
- **Long term**: Document and enforce a policy that any chain ID / network ID / genesis-hash identifier used across the miner-signer protocol is consistently embedded in every signed digest (block header signatures, `BlockAccepted`, `BlockRejection`, `MockProposal`, etc.), so that no signature produced under one chain context can satisfy verification under another without an explicit, intentional cross-chain design decision.

### Proof of Concept
1. Deploy (or observe) two chain contexts — e.g., mainnet and a subnet/testnet fork of stacks-core — that use the same signer key set (a realistic scenario for chains bootstrapped from the same signer/stacker infrastructure).
2. Construct two `NakamotoBlockHeader`s, one intended for context A and one for context B, with identical `version`, `chain_length`, `burn_spent`, `consensus_hash`, `parent_block_id`, `tx_merkle_root`, `state_index_root`, `timestamp`, and `miner_signature` (achievable if the two contexts start from a common fork point or are deliberately crafted to match).
3. Have context A's signers sign the header via the standard flow (`signer.rs` -> `create_block_rejection`/acceptance path producing a signature over `signer_signature_hash()`). [5](#0-4) 
4. Submit the identical header plus the harvested signature to context B's chainstate; `verify_signer_signatures` in `stackslib/src/chainstate/nakamoto/mod.rs` will recompute the same `signer_signature_hash()` (since no chain-scoping field differs) and accept the signature as valid for context B, since the check never references any chain identifier.
