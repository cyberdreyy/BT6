## Analysis

The report's core complaint — "the default assumption of the error handlers is that everything went according to plan" and "errors are not trapped when they are found" — has a direct, concrete Go analog in `core/sessions/oidcauth/oidc.go`'s `handleTokenExchange`, the HTTP handler that completes the OIDC login flow.

### Title
Missing `return` after failed email-claim extraction allows OIDC sessions to be created with an empty/shared identity - (`core/sessions/oidcauth/oidc.go`)

### Summary
In `handleTokenExchange`, when the verified ID token's claims do not contain a string `"email"` field, the handler logs the error and writes an HTTP 500 response but **fails to `return`**, so execution falls through and creates a real, persisted OIDC session using the zero-value empty string as the user's email.

### Finding Description [1](#0-0) 

```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims. error: %v", err)
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
}
oi.lggr.Tracef("Received and validated ID claims: %v\n", idClaims)
```

There is no `return` statement after `c.String(...)`, so the handler continues past the error branch exactly as if the email had been extracted successfully. The uninitialized `email` variable defaults to `""` and is used to persist a new session row: [2](#0-1) 

The session cookie is then set and the client receives `ExchangeTokenResponse{Success: true}` at the end of the function, despite the server having already written a conflicting 500 response earlier in the same request (a second violation of "fail early and loudly" — Gin does not prevent writing headers/body twice, but the client-visible outcome here is the final `200 OK`).

This is the same anti-pattern the report describes: an error is detected, a failure signal is emitted, but the caller (in this case, the same function) does not stop and instead proceeds under the assumption that everything succeeded, propagating a default/zero value (`email = ""`) into persistent state used for authorization decisions.

### Impact Explanation
Any user completing an OIDC login whose verified ID token lacks a string `email` claim (e.g., IdP configuration/scope differences, accounts without a verified email, or any other provider-side reason the claim is absent) gets a fully valid, cookie-backed session persisted in `oidc_sessions` with `user_email = ''`. Because multiple distinct users can all end up with the same empty-string email, this value becomes a shared session key across unrelated identities. Downstream code keys off `user_email` for a cross-session operation: [3](#0-2) 

`ClearNonCurrentSessions` looks up the email tied to the caller's own session ID and then deletes every other session row with the same (lowercased) email. If a user with an empty-email session invokes this action, it will terminate the sessions of every other unrelated user who also happens to have `user_email = ''` — an unprivileged, authenticated actor unintentionally (or intentionally) terminating other users' sessions, i.e., cross-user response/session confusion caused directly by the unhandled error path.

### Likelihood Explanation
This requires only a normal OIDC login where the IdP-issued, signature-verified ID token omits the `email` claim — no forging or malicious peer/network behavior is needed, and the request path (`/oidc/exchange` style token-exchange endpoint) is reachable by any unauthenticated caller completing a real OAuth code exchange with the configured provider. This satisfies "unprivileged client request" and does not depend on a malicious node/operator.

### Recommendation
Add `return` immediately after writing the error response in the `email` extraction branch (and audit the rest of `handleTokenExchange`/`ldap.go`/`gw_handler.go` `errorResponse` helpers for the same missing-`return` pattern after `c.String`/`c.JSON` error writes). Reject the login instead of continuing with a zero-value email, and consider making `email` a required, explicitly validated field rather than a silently-defaulted one before it is persisted to `oidc_sessions`.

### Proof of Concept
1. Configure the node with OIDC auth enabled.
2. Have the identity provider issue a valid, correctly signed ID token for a user whose token does not include an `email` claim (or a claim that isn't a string), while still including the mapped role claim (e.g., `EditClaim`/`AdminClaim` group membership).
3. Complete the `/exchange`-style token flow; the server logs "Failed to get email from claims" and writes a 500, but continues execution.
4. A row is inserted into `oidc_sessions` with `user_email = ''`, the role from step 2, and the response ultimately returned to the browser is `200 OK` / `Success: true` with a valid session cookie.
5. Repeat with a second such account; both share `user_email = ''`. Calling the "clear other sessions" action from either session (`ClearNonCurrentSessions`) deletes the other account's sessions as a side effect of the collision.

// ClearNonCurrentSessions removes other oidc_sessions for the user tied to sessionID.
func (oi *oidcAuthenticator) ClearNonCurrentSessions(ctx context.Context, sessionID string) error {
	var email string
	if err := oi.ds.GetContext(ctx, &email, "SELECT user_email FROM oidc_sessions WHERE id = $1", sessionID); err != nil {
		return err
	}
	_, err := oi.ds.ExecContext(ctx, "DELETE FROM oidc_sessions WHERE lower(user_email) = lower($1) AND id != $2", email, sessionID)
	return err
}
