### Title
Loss-adjusted haircut stored under a single latest-request epoch lets an older unclaimed withdraw receipt claim at par, draining other claimants' funded pool - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` tracks a user's withdraw receipts both as an aggregate (`withdrawsRequests[_user]`) and per request epoch (`withdrawsRequestsByEpoch[_user][epoch]`), but keeps only a single `lastWithdrawRequest[_user]` pointer. When `stopEpochWithDuration` realizes a loss, `collectWithdrawFunds` funds the *aggregate* `pendingWithdraws` at a pro-rata haircut and stores the ratio in `lossRecoveryPriceByEpoch[epochNumber]` — indexing by the current epoch only. On claim, `_claimLossAdjustedWithdrawRequest` loads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` and haircuts only the basis recorded under that latest epoch; any earlier still-unclaimed receipt falls through to `_claimFundedWithdrawRequest` and is paid 1:1. This is the analog of CVE-2015-6764's "improperly loads array elements" bug: the per-epoch element is read at only one index while the loss was actually spread over the whole aggregate.

### Finding Description
Relevant code:

- `requestWithdraw` (IdleCreditVault.sol:243–295) allows a second request while an earlier funded receipt is unclaimed, only reverting when the *previous* `lastWithdrawRequest` epoch itself carries a non-zero `lossRecoveryPriceByEpoch`. It then overwrites `lastWithdrawRequest[_user] = currentEpoch` (line 282).
- `collectWithdrawFunds` (lines 411–430) computes `lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis` over the **aggregate** `pendingWithdraws` (which includes all unclaimed receipts across epochs) and stores it under `lossRecoveryPriceByEpoch[epochNumber]` (line 421). `epochNumber` is only incremented later in `stopEpoch` via `_strategy.deposit` (IdleCDOEpochVariant.sol:466 → IdleCreditVault.sol:610), so the index matches the request epoch — but only for receipts opened in that epoch.
- `_claimLossAdjustedWithdrawRequest` (lines 789–801) looks up `lossEpoch = lastWithdrawRequest[_user]` and clears only `withdrawsRequestsByEpoch[_user][lossEpoch]` via `_clearWithdrawClaimForEpoch`, paying `claimBasis * lossRecoveryPrice`.
- `_claimFundedWithdrawRequest` (lines 319+) then pays the remaining `withdrawsRequests[_user]` aggregate — including the pre-loss epoch's receipt — at full par from strategy-held underlyings.

Broken invariant: "one receipt, one haircut-adjusted payout." The funded amount for the epoch is `p * (W_old + W_new)`, but the user extracts `W_old + p * W_new`. Every earlier-epoch receipt that overlaps a later loss-epoch request is systematically overpaid by `(1 - p) * W_old`.

### Impact Explanation
Direct theft / insolvency. An attacker (any KYC-passing lender / tranche holder) deliberately leaves a large withdraw receipt unclaimed, opens a small second request in a subsequent epoch, and waits for a `stopEpochWithDuration` loss. The old receipt — whose funding was haircut pro rata inside `pendingBasis` — is paid at full par, while honest claimants' loss-adjusted receipts draw from the same underfunded strategy balance. Quantified loss to the pool per attack: `(1 - p) * W_old` underlying, bounded only by the attacker's deposited size. If the attacker is last to claim, remaining claimants' `claimWithdrawRequest` calls revert on insufficient underlying balance (temporary/permanent freezing of unclaimed funded claims, since `withdrawsRequestsByEpoch` was already zeroed for them).

### Likelihood Explanation
- Attacker requirements are unprivileged: deposit, `requestWithdraw` twice across epochs, claim. No privileged role needed; the loss event is produced by honest manager `stopEpochWithDuration` calls or any partial borrower repayment.
- The re-request path is explicitly supported ("if a user does not claim a withdraw request and instead requests another withdraw, he will have to wait for another epoch to claim both requests", lines 323–324), so the state is reachable in normal operation, not only adversarially.
- Existing guards do not stop it: the request-time check (lines 263–271) only inspects `lossRecoveryPriceByEpoch[lastWithdrawRequest]` at request time, when the future loss epoch does not yet exist; the skim/donation logic, `_onlyIdleCDO`, and KYC gating are irrelevant to this accounting path.
- Caveat: requires a loss-epoch to occur while the attacker holds two stacked receipts; the attacker cannot force the loss themselves but can keep a stale receipt parked indefinitely at low cost.

### Recommendation
Track *all* epochs with pending basis per user, or enforce the invariant at request time. Two options:
1. In `requestWithdraw`, revert whenever `withdrawsRequests[_user] != 0` (or `apr0Users` principal) unless the prior receipt's epoch has already been fully funded without loss — i.e., require users to claim any outstanding receipt before opening a new one, mirroring the post-default guard at lines 249–251.
2. Alternatively, apply the aggregate haircut at claim time: in `_claimFundedWithdrawRequest`, scale the residual `withdrawsRequests[_user]` payout by `lossRecoveryPriceByEpoch[epoch]` for every epoch in which the user had basis, requiring a per-user epoch set or a checkpoint of pending basis.

The assertion `underlying.balanceOf(attacker) - pre > p * (W_old + W_new)` demonstrates over-collection; a subsequent honest claimant's `claimWithdrawRequest` reverts or is shortchanged by `(1-p)*W_old`.
