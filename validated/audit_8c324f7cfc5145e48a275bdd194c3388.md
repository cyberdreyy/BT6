### Title
Unauthenticated forwarding of LOOP plugin `/debug/pprof/*` (including `trace`) enables information disclosure and a runtime side-channel - ([File: core/web/loop_registry.go])

### Summary
`LoopRegistryServer.pluginPPROFHandler` is registered on the top-level `api` route group with no `auth.Authenticate` middleware, unlike the equivalent node-level pprof routes (`metricRoutes`) which are explicitly nested under the authenticated `authv2` group. As a result, any unauthenticated caller can hit `/plugins/:name/debug/pprof/*profile` (including `trace`, `profile`, `heap`, `goroutine`) and have it transparently forwarded to the LOOP plugin's internal pprof server, receiving full runtime execution/scheduling data back in the response.

### Finding Description
In `core/web/router.go`, `loopRoutes(app, api)` is called directly on the `api` group at `core/web/router.go:91`, where `api` is only wrapped with the rate limiter and `sessions.Sessions(...)` middleware (`core/web/router.go:78-85`) — `sessions.Sessions` merely attaches a session store to the context, it does not require or validate a session/token. No `auth.Authenticate(...)` call is applied to `loopRoutes`.

Contrast this with the node's own pprof endpoints: `metricRoutes(authv2)` (`core/web/router.go:446`) is deliberately placed inside the `authv2` group, which is protected by `auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateByToken, auth.AuthenticateBySession)` (`core/web/router.go:245-248`).

`pluginPPROFHandler` (`core/web/loop_registry.go:150-166`) itself performs no authentication or authorization check — it only validates that `pluginName` exists in the local registry, then forwards the request via `doRequest` (`core/web/loop_registry.go:190-215`) to `http://<loopHostName>:<PrometheusPort>/debug/pprof/<profile>` and streams the raw response back to the caller. `pluginPPROFPOSTSymbolHandler` behaves the same way.

Because the whole `api` group (including this route) shares the single rate limiter `rateLimiter(rl.AuthenticatedPeriod(), rl.Authenticated())` (`core/web/router.go:78-83`), there is no separate/stricter throttling for this unauthenticated forwarding path — an anonymous client gets the same generous "authenticated" quota as a logged-in user, allowing repeated invocation of expensive endpoints like `trace` and `profile` (each can run up to `seconds` + `PPROFOverheadSeconds`, `core/web/loop_registry.go:130-148`).

### Impact Explanation
An unauthenticated attacker who can reach the node's HTTP API can repeatedly pull goroutine dumps, heap profiles, and execution traces (`/debug/pprof/trace`, `/goroutine`, `/heap`) from any LOOP plugin process (e.g., an OCR2 median/relayer plugin) without any credentials. This is an information-disclosure vulnerability: profiling output can reveal internal state, stack traces, memory addresses, goroutine counts tied to specific operations (e.g., signing loops), and potentially indirectly aid timing analysis of scheduling patterns around signing operations. This maps to Chainlink's "sensitive information disclosure" bounty class. Note that a full cryptographic key-extraction via this timing channel is not concretely demonstrated here and would additionally require a non-constant-time signing implementation, which is outside what can be confirmed from this code path alone.

### Likelihood Explanation
Exploitation requires zero credentials — only network reachability to the node's web server and a registered LOOP plugin name (obtainable via the also-unauthenticated `/discovery` and `/plugins/:name/metrics` endpoints, `core/web/router.go:232-233`). This is trivially repeatable up to the shared "authenticated" rate limit, since there is no distinct/stricter limiter or auth gate on the pprof-forwarding route.

### Recommendation
Wrap `loopRoutes` (or at minimum the `/plugins/:name/debug/pprof/*` and `/plugins/:name/debug/pprof/symbol` routes) with the same `auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateByToken, auth.AuthenticateBySession)` middleware used for `authv2`'s `metricRoutes`, and consider requiring an admin/run role via `auth.RequiresAdminRole`/`auth.RequiresRunRole`. Additionally, apply a distinct, stricter rate limiter to profiling endpoints given their cost and sensitivity.

### Proof of Concept
Go handler-level integration test plan (using `httptest` + the real `gin` router from `NewRouter`):
1. Build an `Application` test harness with a registered fake LOOP plugin (as in `plugins.NewTestLoopRegistry`) exposing a local pprof server on a known port.
2. Construct the router via `web.NewRouter(app, nil)` without setting any session cookie or `Authorization` header.
3. Issue `GET /plugins/<name>/debug/pprof/trace?seconds=1` with no credentials.
   - Assert: response status `200` and body contains valid pprof trace data (not `401`/`403`), proving the route is reachable unauthenticated.
4. Issue the same unauthenticated request `N` times in a loop up to `rl.Authenticated()` limit within `rl.AuthenticatedPeriod()`.
   - Assert: requests succeed until the shared authenticated quota is exhausted, then receive `429`, showing the anonymous caller consumes the same quota bucket as an authenticated caller (same `mgin.NewMiddleware(limiter.New(...))` instance for the whole `api` group).
5. Contrast with `GET /v2/debug/pprof/trace` (under `authv2`) with no credentials — assert `401 Unauthorized`, confirming the double-standard between node-level and plugin-level pprof exposure documented at `core/web/router.go:446` vs `core/web/router.go:91,234`.
