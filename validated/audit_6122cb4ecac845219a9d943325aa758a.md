### Title
Builder payment to an unvetted `fee_recipient` is spec-valid — `process_execution_payload_bid` never checks the bid against the proposer's committed preference - (File: specs/gloas/beacon-chain.md)

### Summary
`process_execution_payload_bid`, the state-transition function that determines block validity for a builder's bid, never checks `bid.fee_recipient` (or `bid.gas_limit`) against the proposer's own `SignedProposerPreferences`. That compatibility check exists only in the p2p gossip validator, a non-authoritative layer that can be bypassed by any off-protocol bid-delivery path the spec explicitly allows.

### Finding Description
`process_execution_payload_bid` records a `BuilderPendingPayment`/`BuilderPendingWithdrawal` using `bid.fee_recipient` taken verbatim from the builder-signed bid, with no assertion tying it to the proposer's declared preference: [1](#0-0) 

The *only* place `bid.fee_recipient` and `bid.gas_limit` are checked against `SignedProposerPreferences` is inside gossip validation (`validate_gossip` for the `execution_payload_bid` topic), and both failures are `GossipIgnore`, not `GossipReject`: [2](#0-1) 

Yet `validator.md` tells the proposer that satisfying `process_execution_payload_bid`'s verification conditions is the *complete* MUST-list for accepting a bid, and explicitly permits obtaining the bid by "other off-protocol means" (e.g., a relay), bypassing gossip entirely: [3](#0-2) 

This is the exact shape of the Ajna `repayDebt()` bug: a user-facing "limit" control (`limitIndex_` there, `SignedProposerPreferences.fee_recipient`/`target_gas_limit` here) is documented as authoritative but is enforced only in a side path (the collateral-pull branch there; the gossip topic here) and is silently skipped by the canonical state-transition check that actually gates validity (`BorrowerActions.repayDebt` there; `process_execution_payload_bid` here).

### Impact Explanation
A builder can sign and deliver (via a relay/off-protocol channel, which the spec allows) a bid whose `fee_recipient` differs from the proposer's broadcast preference — e.g., pointing back to the builder's own address, or any third address — while still winning the block (highest `bid.value`) and being fully valid per `process_execution_payload_bid`. `settle_builder_payment`/`process_builder_pending_payments` will later pay that address, not the proposer's actual chosen recipient, misdirecting the builder payment away from the intended party with no consensus-level rejection possible. This matches the "builder payment ... misdirected" High-impact bucket, since the misdirection is invisible to spec-following validity checks and is not reliably prevented by gossip rules that a relay/off-protocol path can bypass.

### Likelihood Explanation
Likelihood is high in any deployment using relays/off-protocol bid delivery (which `validator.md` explicitly sanctions), since gossip-layer `GossipIgnore` checks are advisory for propagation, not block validity. Any builder or relay that skips honoring `target_gas_limit`/`fee_recipient` can still produce a spec-valid block.

### Recommendation
Move the `fee_recipient`/`target_gas_limit` compatibility checks (or equivalents) from gossip-only `validate_gossip` into `process_execution_payload_bid` (or another consensus-enforced path) so that bid validity is conditioned on matching the proposer's most-recently-signed `SignedProposerPreferences`, closing the gap between the documented "MUST satisfy `process_execution_payload_bid`" guarantee and what that function actually enforces.

### Proof of Concept
1. Proposer P broadcasts `SignedProposerPreferences{fee_recipient=A, target_gas_limit=G}` for slot `s`.
2. Builder B, instead of honoring these preferences, submits (via a relay, not gossip) `SignedExecutionPayloadBid{fee_recipient=X≠A, gas_limit≠G, value=V}` with valid signature.
3. Proposer's client accepts B's bid via the relay (off-protocol path per `validator.md`), includes it in the block.
4. Block state transition calls `process_execution_payload_bid`, which only checks balance, blob count, slot/parent/randao/hash fields — none reference `fee_recipient` or `gas_limit` against `SignedProposerPreferences` — so the block is valid. [4](#0-3) 
5. At payment settlement, `V` is paid to `X`, not `A`, even though the proposer never received a bid conforming to their committed preferences and no consensus rule caught it.

def process_execution_payload_bid(
    state: BeaconState, signed_bid: SignedExecutionPayloadBid
) -> None:
    bid = signed_bid.message
    builder_index = bid.builder_index
    amount = bid.value

    # For self-builds, amount must be zero regardless of withdrawal credential prefix
    if builder_index == BUILDER_INDEX_SELF_BUILD:
        assert amount == 0
        assert signed_bid.signature == bls.G2_POINT_AT_INFINITY
    else:
        # Verify that the builder is active
        assert is_active_builder(state, builder_index)
        # Verify that the builder is a payload builder
        assert state.builders[builder_index].version == PAYLOAD_BUILDER_VERSION
        # Verify that the builder has funds to cover the bid
        assert can_builder_cover_bid(state, builder_index, amount)
        # Verify that the bid signature is valid
        assert verify_execution_payload_bid_signature(state, signed_bid)

    # Verify commitments are under limit
    assert (
        len(bid.blob_kzg_commitments)
        <= get_blob_parameters(get_current_epoch(state)).max_blobs_per_block
    )

    # Verify that the bid is for the current slot
    assert bid.slot == state.slot
    assert state.slot > GENESIS_SLOT
    # Verify that the bid is for the right parent block
    assert bid.parent_block_hash == state.latest_block_hash
    # Verify that the bid's block hash differs from its parent block hash
    assert bid.block_hash != bid.parent_block_hash
    assert bid.parent_block_root == get_block_root_at_slot(state, state.slot - 1)
    assert bid.prev_randao == get_randao_mix(state, get_current_epoch(state))

    # Record the pending payment if there is some payment
    if amount > 0:
        pending_payment = BuilderPendingPayment(
            weight=Gwei(0),
            withdrawal=BuilderPendingWithdrawal(
                fee_recipient=bid.fee_recipient,
                amount=amount,
                builder_index=builder_index,
            ),
            proposer_index=get_beacon_proposer_index(state),
        )
        state.builder_pending_payments[SLOTS_PER_EPOCH + bid.slot % SLOTS_PER_EPOCH] = (
            pending_payment
        )

    # Cache the signed execution payload bid
    state.latest_execution_payload_bid = bid

##### Signed execution payload bid

To obtain `signed_execution_payload_bid`, a block proposer building a block on
top of a `state` MUST take the following actions in order to construct the
`signed_execution_payload_bid` field in `BeaconBlockBody`:

- Listen to the `execution_payload_bid` gossip global topic and save an accepted
  `signed_execution_payload_bid` from a builder. The block proposer MAY obtain
  these signed messages by other off-protocol means.
- The `signed_execution_payload_bid` MUST satisfy the verification conditions
  found in `process_execution_payload_bid` with the alias
  `bid = signed_execution_payload_bid.message`, that is:
  - For external builders, the signature MUST be valid.
  - For self-builds, set `bid.builder_index` to `BUILDER_INDEX_SELF_BUILD`.
  - For self-builds, the signature MUST be `bls.G2_POINT_AT_INFINITY` and the
    `bid.value` MUST be zero.
