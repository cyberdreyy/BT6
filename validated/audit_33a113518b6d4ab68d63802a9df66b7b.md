### Title
Zero-priced write-off requests let anyone seize escrowed tranche tokens - ([contracts/IdleCreditVaultWriteOffEscrow.sol](contracts/IdleCreditVaultWriteOffEscrow.sol))

### Summary
`IdleCreditVaultWriteOffEscrow.createWriteOffRequest` rejects a zero tranche amount but does not reject `underlyingsRequested == 0`, while `fullfillWriteOffRequest` is intentionally callable by any wallet and only requires the supplied payment to be at least the requested amount. A lender can therefore create a request escrowing nonzero tranche tokens for zero underlying, and an unprivileged attacker can fulfill it with zero payment and receive all escrowed tranche tokens.

### Finding Description
The escrow pulls `amount` tranche tokens from the requester, but validates only `amount != 0` before recording `underlyingsRequested` in `userRequests[msg.sender]` and `pendingUnderlyings` [1](#0-0) .

Fulfillment loads the victim's request, requires an exact tranche amount, and rejects only when `_underlyings < currentRequest.underlyings` [2](#0-1) . When the stored request asks for zero underlying, passing `_underlyings = 0` satisfies that check. The function then deletes the request, transfers zero underlying to the victim, and transfers the full escrowed tranche balance to the arbitrary caller [3](#0-2) .

This is the credit-vault analogue of the reported missing write-access guard: an open write/fulfillment path permits an unauthorized actor to mutate a victim's request and remove its escrowed asset without providing the consideration implied by a write-off purchase. The intended open-buyer design does not require restricting fulfillment to the borrower, but it does require a nonzero ask.

### Impact Explanation
A tranche-token holder who accidentally or through malformed integration creates a request with `underlyingsRequested = 0` loses the entire escrowed tranche position. An attacker receives those tranche tokens for no payment and can later redeem, sell, or use them subject to the vault's normal withdrawal and wallet-allowlist rules. The direct loss equals the full value of the escrowed tranche tokens.

### Likelihood Explanation
Likelihood is lower than a universally exploitable accounting flaw because it requires a victim to create a malformed zero-price request. Once such a request exists, exploitation is permissionless, atomic, and does not depend on borrower, owner, manager, queue, or Keyring cooperation. The public `fullfillWriteOffRequest` path is explicitly unrestricted [4](#0-3) .

### Recommendation
Reject zero-consideration requests in `createWriteOffRequest`:

```solidity
if (amount == 0 || underlyingsRequested == 0) revert NotAllowed();
```

For defense in depth, also require `_underlyings != 0` in `fullfillWriteOffRequest`. If zero-price transfers are ever intentionally supported, put them behind a distinct explicitly confirmed flow rather than the purchase path.

### Proof of Concept
The following Foundry test extends the existing fork setup in `test/foundry/IdleCreditVaultWriteOffEscrow.t.sol`:

```solidity
function testZeroPriceRequestCanBeFulfilledForFree() external {
    uint256 requestedTranches = 10_000e18;
    address attacker = makeAddr("attacker");

    uint256 sellerTranchePre = tranche.balanceOf(LP);
    uint256 sellerUnderlyingPre = underlying.balanceOf(LP);

    vm.prank(LP);
    escrow.createWriteOffRequest(requestedTranches, 0);

    uint256 attackerTranchePre = tranche.balanceOf(attacker);

    // No underlying approval or balance is required because the payment is zero.
    vm.prank(attacker);
    escrow.fullfillWriteOffRequest(LP, requestedTranches, 0);

    (uint256 tranches, uint256 underlyings) = escrow.userRequests(LP);
    assertEq(tranches, 0);
    assertEq(underlyings, 0);
    assertEq(escrow.pendingUnderlyings(), 0);

    assertEq(tranche.balanceOf(attacker) - attackerTranchePre, requestedTranches);
    assertEq(tranche.balanceOf(LP), sellerTranchePre - requestedTranches);
    assertEq(underlying.balanceOf(LP), sellerUnderlyingPre);
}
```
