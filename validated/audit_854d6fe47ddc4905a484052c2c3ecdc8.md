### Title
Stale/evicted builder payments and the builder sweep can both mint a `Withdrawal` against the same `Builder.balance`, causing the execution layer to credit more Gwei than the builder actually staked - (specs/gloas/beacon-chain.md)

### Summary
`get_builders_sweep_withdrawals` computes the withdrawal amount for a sweep-eligible builder directly from `state.builders[builder_index].balance`, unlike the analogous validator-sweep helper, which explicitly nets out any withdrawals already included earlier in the same payload. Combined with the "evicted payment" fallback in `apply_parent_execution_payload`, which unconditionally appends a `BuilderPendingWithdrawal` for a builder without re-checking that builder's current eligibility/balance, a single execution payload can end up containing two independent `Withdrawal` entries that both draw on the same, single unit of builder stake — one via `get_builder_withdrawals` (paid to `fee_recipient`) and one via `get_builders_sweep_withdrawals` (paid to `execution_address`), each carrying a non-zero amount. Since the execution layer credits `Withdrawal.amount` verbatim for every entry in the payload's withdrawals list (it has no visibility into the consensus layer's internal `Builder.balance` bookkeeping), this results in Gwei being created on the execution layer beyond what the builder ever staked.

### Finding Description
`get_expected_withdrawals` (specs/gloas/beacon-chain.md) builds the withdrawals list in this order: builder pending withdrawals, pending partial (validator) withdrawals, builder sweep withdrawals, validator sweep withdrawals. [1](#0-0) 

For validators, the sweep helper is careful to avoid double-counting balance already spent by an earlier withdrawal in the *same* payload: it calls `get_balance_after_withdrawals(state, validator_index, all_withdrawals)`, which subtracts every withdrawal already queued for that validator index in the same block before deciding eligibility/amount. [2](#0-1) [3](#0-2) 

The builder-sweep analogue does **not** do this. It reads `builder.balance` straight off state and uses that raw value as both the eligibility check and the withdrawal amount, ignoring `prior_withdrawals`/`all_withdrawals` entirely for amount computation: [4](#0-3) 

Meanwhile, `get_builder_withdrawals` drains `state.builder_pending_withdrawals` (queued via `settle_builder_payment`/`process_builder_pending_payments`) and emits a `Withdrawal` to `fee_recipient` for the full queued `amount`, again independent of the builder's live balance: [5](#0-4) 

Critically, one path that populates `builder_pending_withdrawals` bypasses any liveness/eligibility re-check on the builder entirely. In `apply_parent_execution_payload`, when a bid's payment entry has already aged out of `builder_pending_payments` (older than the previous epoch), the withdrawal is appended directly using only the stale bid data, with no check of the builder's current `withdrawable_epoch`/`balance`/exit status: [6](#0-5) 

`apply_withdrawals` (the only place that actually decrements `Builder.balance` in the CL's own bookkeeping) clamps each application to the builder's *current* balance: [7](#0-6) 

but this clamp only protects the consensus layer's internal accounting. The `Withdrawal.amount` values that were already committed into the block body via `assert list(payload.withdrawals) == expected.withdrawals` are the values the execution layer will apply — and per EIP-4895 (Capella withdrawals) semantics the EL performs an unconditional balance credit for every withdrawal entry, it does not re-derive or clamp the amount against any builder-balance model of its own. So if the payload contains two withdrawals both computed from the same underlying `Builder.balance` (one from `get_builder_withdrawals`, one from `get_builders_sweep_withdrawals`), the EL will credit both `fee_recipient` and `execution_address` their full stated amounts, even though only one unit of stake backed them.

### Impact Explanation
This breaks the equality "every Gwei paid out to an address must be backed by real, uncommitted stake" — the execution layer can be made to create/duplicate Gwei relative to what the builder actually deposited, paid to addresses (`fee_recipient` and/or `execution_address`) that the block's *intended* accounting did not actually commit doubly. This matches the report's bug class ("funds are paid out without deducting an obligation that is still outstanding, denying/mismatching the rightful claim") mapped onto Gloas's builder-withdrawal bookkeeping. Per the scoring rubric this is Critical-severity in kind (Gwei created / paid beyond entitlement), since it is not merely an attacker losing their own stake — the excess is paid to whichever address(es) are named in the two withdrawal entries.

### Likelihood Explanation
The precise trigger sequence — a builder's bid payment aging past the `builder_pending_payments` retention window (`SLOTS_PER_EPOCH`-sized queue spanning roughly two epochs) so that it falls into the "evicted, append directly" branch, while that same builder is concurrently within its sweep window (`withdrawable_epoch <= epoch`, `balance > 0`) in the identical slot's `get_expected_withdrawals` call — is a narrow, timing-dependent window and depends on details of `get_pending_balance_to_withdraw_for_builder` (used to gate `process_builder_exit_request`) that could not be fully inspected in this pass. Whether that helper also accounts for payments still sitting in `builder_pending_payments` (which would close this window by blocking exit while any bid is unsettled) was not directly confirmed from the available spec excerpts, so likelihood carries genuine uncertainty; it should not be treated as a fully proven exploit, only a concrete structural asymmetry with a plausible, but unverified, end-to-end trigger.

### Recommendation
Make `get_builders_sweep_withdrawals` compute the swept amount from a balance that accounts for any prior withdrawals already assembled for the same builder in the current payload (analogous to `get_balance_after_withdrawals` for validators), and have the "evicted payment" fallback branch in `apply_parent_execution_payload` re-check the builder's current eligibility/balance (or clamp the appended `BuilderPendingWithdrawal.amount` to `min(amount, builder.balance)`) before queuing it, rather than blindly trusting the stale bid data.

### Proof of Concept
1. Builder `B` submits a winning bid; the payment enters `state.builder_pending_payments`.
2. Due to skipped/delayed settlement (the payment entry ages out of the two-epoch `builder_pending_payments` window before `settle_builder_payment` runs on it), `apply_parent_execution_payload`'s `elif parent_bid.value > 0:` branch appends a `BuilderPendingWithdrawal(fee_recipient=..., amount=X, builder_index=B)` straight to `state.builder_pending_withdrawals`, with no re-validation of `B`'s current state [8](#0-7) .
3. Independently, builder `B` has since become sweep-eligible (`withdrawable_epoch <= epoch`, `balance == X > 0`).
4. In the same block's `get_expected_withdrawals` call: `get_builder_withdrawals` emits `Withdrawal(amount=X, address=fee_recipient)`; later `get_builders_sweep_withdrawals` independently reads the still-unmodified `state.builders[B].balance == X` (since only `apply_withdrawals` mutates it, and that happens after the whole list is built) and emits a second `Withdrawal(amount=X, address=execution_address)` [9](#0-8) .
5. Both withdrawals, each for amount `X`, are committed into `payload.withdrawals` and pass `assert list(payload.withdrawals) == expected.withdrawals` in `process_withdrawals`. The execution layer credits both `fee_recipient` and `execution_address` `X` Gwei each — `2X` total paid out against a builder stake of only `X`.

def get_builder_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    for withdrawal in state.builder_pending_withdrawals:
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder_index = withdrawal.builder_index
        withdrawals.append(
            Withdrawal(
                index=withdrawal_index,
                validator_index=convert_builder_index_to_validator_index(builder_index),
                address=withdrawal.fee_recipient,
                amount=withdrawal.amount,
            )
        )
        withdrawal_index += 1
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count

```python
def get_builders_sweep_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    epoch = get_current_epoch(state)
    builders_limit = min(len(state.builders), MAX_BUILDERS_PER_WITHDRAWALS_SWEEP)
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    builder_index = state.next_withdrawal_builder_index
    for _ in range(builders_limit):
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder = state.builders[builder_index]
        if builder.withdrawable_epoch <= epoch and builder.balance > 0:
            withdrawals.append(
                Withdrawal(
                    index=withdrawal_index,
                    validator_index=convert_builder_index_to_validator_index(builder_index),
                    address=builder.execution_address,
                    amount=builder.balance,
                )
            )
            withdrawal_index += 1

        builder_index = (builder_index + 1) % len(state.builders)
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count

def get_balance_after_withdrawals(
    state: BeaconState,
    validator_index: ValidatorIndex,
    withdrawals: Sequence[Withdrawal],
) -> Gwei:
    withdrawn = sum(
        withdrawal.amount
        for withdrawal in withdrawals
        if withdrawal.validator_index == validator_index
    )
    return state.balances[validator_index] - withdrawn
