### Title
Missing duplicate `MessageId` check in the Gateway's legacy WebAPI trigger handler allows callback overwrite / cross-user response hijack - (File: `core/services/gateway/handlers/capabilities/handler.go`)

### Summary
The `EscrowManager._findCheckpoint`/`_moveVotes` bug class described in the report is "a shared, attacker-influenced key is used to index into a state map/array without checking for an existing entry, so a second write at the same key silently clobbers the first, nullifying previously-recorded state." The same root-cause pattern exists in the Gateway's legacy user-message handler (`handler.HandleLegacyUserMessage`), which stores per-request callbacks keyed by the fully client-controlled `MessageId`/JSON-RPC request `ID` without ever checking whether that key is already in use.

### Finding Description
In `core/services/gateway/handlers/common/message_util.go`, the legacy Gateway message's `MessageId` is set directly from the caller-controlled JSON-RPC request ID: [1](#0-0) 

`core/services/gateway/handlers/capabilities/handler.go`'s `HandleLegacyUserMessage` then stores the callback for this request keyed by `msg.Body.MessageId` with a plain map write and **no existence check**: [2](#0-1) 

When a node responds, the handler looks up and deletes the entry by the same `MessageId` and forwards the response to whatever callback is currently stored there: [3](#0-2) 

This is the exact "checkpoint" anti-pattern from the report: a shared index (here, `MessageId`) is written without verifying uniqueness, so a second request using the same ID overwrites (nullifies) the first request's tracked state (the `savedCallback` pointing at the first caller's response channel). This is inconsistent with the rest of the gateway handler codebase, which explicitly guards against this: the vault handler, the confidential-relay handler, and the v2 HTTP trigger handler all reject a request whose ID is already active: [4](#0-3) [5](#0-4) [6](#0-5) 

The dummy handler (`core/services/gateway/handlers/handler.dummy.go`) has the identical unguarded overwrite pattern, confirming this is a systemic gap rather than a one-off: [7](#0-6) 

### Impact Explanation
An unprivileged Gateway user submits legacy JSON-RPC requests carrying arbitrary `MessageId`/`ID` values. If an attacker submits a second legacy request using the same `MessageId` as another in-flight legacy request (own or another user's, if the value is guessable/observable), the second write to `h.savedCallbacks[msg.Body.MessageId]` silently replaces the first entry. When a DON node subsequently replies with that `MessageId`:
- The original caller's callback reference is gone; their request will hang until any external caller-side timeout, effectively nullifying/DoS-ing their in-flight request.
- The response payload — which was destined for the original caller — is instead delivered to whichever callback is currently registered for that ID, i.e., the attacker's callback, producing cross-user response confusion (a response payload delivered to the wrong requester).

This matches the "unauthorized state nullification" and "cross-user response confusion" impact classes.

### Likelihood Explanation
Exploitability requires the attacker to cause a `MessageId` collision with a currently in-flight legacy request. Since `MessageId` is entirely attacker-supplied (the JSON-RPC `ID` field) and there is no per-sender namespacing of the `savedCallbacks` map, colliding with *your own* concurrent duplicate requests is trivially possible; colliding with *another user's* request requires knowing/guessing their concurrently-used `MessageId`, which lowers but does not eliminate likelihood (e.g., predictable/sequential or externally observable IDs, or races within the same account/session). The missing check itself is unconditionally reachable by any client hitting the legacy WebAPI trigger message path, with no privilege required.

### Recommendation
Add the same duplicate-ID guard used elsewhere in the gateway handlers (vault, confidentialrelay, v2 http trigger) to `HandleLegacyUserMessage` before storing into `h.savedCallbacks`: reject (or return a JSON-RPC "already in flight"/conflict error) instead of overwriting an existing entry for `msg.Body.MessageId`. Apply the same fix to `dummyHandler.HandleLegacyUserMessage` for consistency.

### Proof of Concept
1. Attacker calls the Gateway's legacy user-message endpoint twice with the same JSON-RPC `ID` (`MessageId`) value — once as their own legitimate request, and once again while the first is still pending (or, if the target's `MessageId` can be predicted/observed, using the target's ID).
2. Both calls hit `handler.HandleLegacyUserMessage`; the second call's `h.savedCallbacks[msg.Body.MessageId] = &savedCallback{...}` (`core/services/gateway/handlers/capabilities/handler.go:412`) overwrites the first entry without any existence check.
3. When a DON node responds with that `MessageId`, `handleWebAPITriggerMessage` (`core/services/gateway/handlers/capabilities/handler.go:148-162`) looks up `h.savedCallbacks[msg.Body.MessageId]`, finds only the second (attacker's) callback, and delivers the response there — the first request's caller never receives a response and the response is misdelivered.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}

func (d *dummyHandler) HandleLegacyUserMessage(ctx context.Context, msg *api.Message, callback Callback) error {
	d.mu.Lock()
	d.savedCallbacks[msg.Body.MessageId] = &savedCallback{msg.Body.MessageId, callback}
	don := d.don
	d.mu.Unlock()
	params, err := json.Marshal(msg)
	if err != nil {
		return err
	}
	rawParams := json.RawMessage(params)
	req := &jsonrpc.Request[json.RawMessage]{
		Version: "2.0",
		ID:      msg.Body.MessageId,
		Method:  msg.Body.Method,
		Params:  &rawParams,
	}
	for _, member := range d.donConfig.Members {
		err = errors.Join(err, don.SendToNode(ctx, member.Address, req))
	}
	return err
}
