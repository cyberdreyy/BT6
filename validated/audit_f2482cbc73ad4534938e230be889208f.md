No vulnerability found for this question.

**Rationale:** `parse_data_id_from_received_data_key` is only called from two places: [1](#0-0)  inside `StateRecord::from_raw_key_value_impl`, which is explicitly documented as "not safe to be running during block production... only used during `state_dump`" [2](#0-1) , and propagates the `io::Error` via `?` rather than `.unwrap()`/`.expect()` [1](#0-0) . The other call site is a unit test [3](#0-2) .

A search of `runtime/runtime/src/lib.rs` (the actual apply-path receipt processing, e.g. `process_receipt`/`apply_action_receipt`) shows no calls to `parse_data_id_from_received_data_key` at all — the apply path constructs `TrieKey::ReceivedData` directly from the typed `data_id: CryptoHash` already present in the `DataReceipt`/`Receipt` struct [4](#0-3)  and [5](#0-4) , never parsing/re-deriving `data_id` from a raw trie key byte slice during block application. Since `data_id` in this path is always a valid, already-typed 32-byte `CryptoHash` (deserialized via Borsh from the receipt, not sliced from a raw key with attacker-controlled length), the panic scenario described (raw key byte length differing from 32 causing an `.unwrap()` abort) is not reachable from the apply path.
