### Title
ProgrammableBorrower.onStopEpoch trusts `convertToAssets` coverage instead of checking actual vault liquidity, permanently blocking `stopEpoch` when the ERC4626 vault is drained - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
The kernel bug is a missing `sendpage_ok()` precondition check: the driver asked the wrong question (implicitly "is there a page") before enabling `MSG_SPLICE_PAGES`, instead of "is this page eligible for splice". The analog in `ProgrammableBorrower.onStopEpoch` is the same class: before deciding whether to unwind the ERC4626 position itself, it checks `shortfall > _currentVaultAssets()`, where `_currentVaultAssets()` is `vault.convertToAssets(shares)` — the vault's *accounting* value, not its *redeemable liquidity* (`maxWithdraw`/`maxRedeem`). When the shares are nominally covered but the vault has no withdrawable cash, `vault.withdraw` reverts and the hook reverts with `StopEpochVaultLiquidityUnavailable`, aborting the entire `stopEpoch` instead of letting the intended default path run.

### Finding Description
In `onStopEpoch` (contracts/strategies/idle/ProgrammableBorrower.sol:240-253):

```solidity
uint256 onHand = underlyingToken.balanceOf(address(this));
if (_amountRequired > onHand) {
  uint256 shortfall = _amountRequired - onHand;
  if (shortfall > _currentVaultAssets()) return true;
  try vault.withdraw(shortfall, address(this), address(this)) returns (uint256 shares) {
    ...
  } catch {
    revert StopEpochVaultLiquidityUnavailable();
  }
}
```

`_currentVaultAssets()` (lines 546-549) is `vault.convertToAssets(vault.balanceOf(this))`. For lending-style ERC4626 vaults (Morpho/ERC4626 pools, utilization-gated vaults), `convertToAssets` reflects the share price over *total* assets including lent-out or otherwise illiquid assets, while `vault.withdraw` reverts when idle liquidity is insufficient. The correct precondition — the `sendpage_ok()` equivalent — is `vault.maxWithdraw(address(this))` / `maxRedeem`, not `convertToAssets`.

The intended design is explicit in the comment: "Only an otherwise-covered ERC4626 withdrawal failure should make stopEpoch retryable." But the coverage test is wrong: a liquidity-drained vault still reports full coverage via `convertToAssets`, so the code takes the `try vault.withdraw` branch, which reverts, and the `catch` reverts the whole transaction. `stopEpoch` can therefore never complete, `settleBorrowerInterest`/`onDefault` are never reached, and the pool is stuck with `isEpochRunning = true` and `epochAccountingActive = true` for as long as the vault stays illiquid.

### Impact Explanation
All lender funds routed through the programmable borrower become frozen while the vault lacks liquidity: `stopEpoch` always reverts, no default can be declared through this path, pending withdraw requests (`epochPendingWithdraws`) cannot be funded, and buffer-phase claims cannot proceed. The freeze persists for the entire duration of the vault's liquidity shortage, which the attacker controls by keeping the vault's cash borrowed. If the vault's illiquidity is permanent (e.g., the vault itself suffers a credit default that keeps `convertToAssets` inflated but blocks withdrawals), the freezing is effectively permanent. Loss magnitude: up to the full pool TVL parked in the vault sleeve.

### Likelihood Explanation
The attacker is explicitly in scope as "a user of the programmable borrower's ERC4626 vault". No privileged role is needed: anyone who can draw down the vault's underlying liquidity (borrowing against collateral in a lending vault, or redeeming ahead of the borrower in a liquidity-limited vault) sets up the condition. Epoch stops are periodic and externally timed, so the attacker can drain liquidity just before `epochEndDate` and hold it. The only mitigating factor is that the vault itself is owner-selected, but the code is clearly designed to support external ERC4626 vaults (the `try/catch` exists precisely because vault withdrawals can fail).

### Recommendation
Replace the accounting-value check with a liquidity check, mirroring `sendpage_ok()`:

```solidity
uint256 withdrawable = vault.maxWithdraw(address(this));
if (shortfall > withdrawable) return true; // let transferFrom fail -> default path
```

Use `convertToAssets` only as a sanity bound, or additionally compare against `maxRedeem`/`previewRedeem`. This routes genuinely-covered-but-illiquid stops into the same default path the code already intends for uncovered ones, instead of reverting `stopEpoch`.

### Proof of Concept
Foundry fork/test outline:

1. Deploy `IdleCDOEpochVariant` + `IdleCreditVault` + `ProgrammableBorrower` wired to a public ERC4626 lending vault (e.g., a utilization-gated vault mock or a forked Morpho-style vault where `convertToAssets` stays constant while idle liquidity goes to zero).
2. Lender deposits via `depositAA`; manager calls `startEpoch()` → `onStartEpoch` parks idle funds into the vault.
3. Attacker (unprivileged vault user) borrows/redeems all liquid assets from the ERC4626 vault. `vault.convertToAssets(shares)` is unchanged; `vault.maxWithdraw(pb)` returns `0`.
4. Warp past `epochEndDate`; borrower is dealt sufficient funds, but manager calls `stopEpoch`.
5. `onStopEpoch` computes `shortfall <= _currentVaultAssets()` → does not `return true` → `vault.withdraw(shortfall,...)` reverts → `catch` reverts `StopEpochVaultLiquidityUnavailable`.
6. Repeat step 5 while the attacker keeps liquidity drained: every `stopEpoch` reverts; `defaulted` is never set; pending withdraw receipts are never funded. Assert `cdoEpoch.isEpochRunning() == true` and lender claims remain frozen — temporary (or permanent, if the vault never regains liquidity) freezing of the full TVL.

Uncertainty note: I could not re-verify the exact revert propagation in `IdleCDOEpochVariant.stopEpoch`/`_beforeStopEpoch` within the available iterations, but `onStopEpoch` is called inside the stop flow and its revert necessarily aborts `stopEpoch`, so the freeze conclusion holds regardless of the wrapper's internal ordering.
