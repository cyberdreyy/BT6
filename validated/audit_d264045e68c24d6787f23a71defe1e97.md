### Title
Gateway forwards legacy-request messages to DON nodes without verifying Sender-to-DonId subscription/membership - ([File: core/services/gateway/gateway.go], [File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`gateway.ProcessRequest` selects the handler purely by `msg.Body.DonId` and relies on `msg.Validate()` to authorize the request, but `Validate()` only checks field lengths/formatting and recovers the signer address into `Body.Sender` — it never checks that the recovered signer is an authorized subscriber/workflow-owner of that `DonId`. The downstream `HandleLegacyUserMessage` in the capabilities handler also has no sender allowlist check (explicitly marked TODO) before fanning the message out to all nodes of the targeted DON.

### Finding Description
In `gateway.ProcessRequest`, for legacy (DonId-bearing) requests, the code does: [1](#0-0) 
`msg.Validate()` (`core/services/gateway/api/message.go`) only validates string lengths/suffixes and recovers `Body.Sender` from the ECDSA signature over the message body (which includes `DonId`, but the DonId is attacker-chosen and self-consistent with the signature - any key can sign any DonId value): [2](#0-1) 
There is no lookup here, or anywhere in `ProcessRequest`, of whether the recovered `Sender` is a registered participant/subscriber of `Body.DonId`. `handlerKey` is derived solely from `Body.DonId`, and `g.handlers[handlerKey]` binds by DON ID only.

The message is then passed to the resolved handler's `HandleLegacyUserMessage`. In the capabilities handler (`core/services/gateway/handlers/capabilities/handler.go`), the method explicitly documents the missing check and forwards the request to all DON members regardless of sender authorization: [3](#0-2) 
This is corroborated by the handler's own test suite, which explicitly flags this gap as unresolved: [4](#0-3) 

As a result, any attacker holding a valid ECDSA key (whether or not it is a legitimate subscriber of any DON) can sign `Body.DonId = "DON_A"` and have the gateway forward the resulting trigger request to all of DON_A's nodes as an apparently well-formed, signature-valid message, with no verification that the signer is entitled to submit requests to DON_A.

### Impact Explanation
This allows cross-DON/cross-subscriber request impersonation: an unprivileged holder of any ECDSA key can submit gateway trigger requests that get dispatched to a DON they are not a subscriber of, potentially triggering workflow executions (`MethodWebAPITrigger`) bound to that DON. This maps to unauthorized job/workflow trigger and request impersonation impact classes.

### Likelihood Explanation
Feasible and repeatable: the attacker needs only an arbitrary ECDSA keypair (trivial to generate) and knowledge of a valid `DonId` string configured on the target gateway (`g.handlers` keys, which correspond to configured DON IDs and are not secret). No node/operator/admin access, no membership in the target DON, and no additional secrets are required. The gap is explicit and acknowledged as a TODO in the current code and tests, not merely theoretical.

### Recommendation
Before dispatching a legacy request to a DON handler, verify that `msg.Body.Sender` (recovered in `Validate()`) is present in that DON's configured/authorized member or subscriber allowlist (e.g., cross-reference against `donConfig.Members`/workflow registry subscription for the given `DonId`) and reject with an authorization error otherwise. This check should occur in `gateway.ProcessRequest` or at the very start of `handler.HandleLegacyUserMessage` prior to fan-out.

### Proof of Concept
Table-driven Go test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Set up a handler configured for `donID = "workflow_don_1"` with a fixed set of authorized member/subscriber keys (as in `setupHandler`).
2. Generate a fresh ECDSA key NOT in that DON's member/subscriber set (representing a key that may be legitimate elsewhere but not for this DON).
3. Build an `api.Message` via `triggerRequest(t, otherKey, ...)` with `Body.DonId = "workflow_don_1"`, sign with the unauthorized key, call `msg.Validate()` (expect it to succeed, proving Validate does not check membership).
4. Call `handler.HandleLegacyUserMessage(ctx, msg, cb)` and assert that `don.SendToNode` is NOT called (i.e., current code fails this assertion because it forwards regardless), or after the fix, assert an authorization error is returned via the callback instead of fan-out to `don.SendToNode`.
5. Repeat for multiple DonId values against senders not registered for that DonId, confirming rejection only occurs after adding the sender-to-DonId membership check.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
