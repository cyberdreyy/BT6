### Title
Multi-epoch withdraw receipts skip the loss haircut: only `lastWithdrawRequest` epoch is priced by `lossRecoveryPriceByEpoch`, earlier receipts are paid at par — ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The kernel bug (CVE-2025-38437) is a double-put/double-release on an error path: state is released twice, so a later accessor uses freed memory. The vault analog is a double-settlement invariant break in `claimWithdrawRequest`: when a user's receipts span multiple request epochs and one epoch's stop was funded at a loss via `stopEpochWithDuration`, `collectWithdrawFunds` stores a single aggregate `lossRecoveryPriceByEpoch[epochNumber]` haircut for *all* pending receipts, but `_claimLossAdjustedWithdrawRequest` applies that haircut only to `lastWithdrawRequest[_user]`'s epoch. Receipts from every other epoch are silently paid at par by `_claimFundedWithdrawRequest`, paying out underlyings that were never funded.

### Finding Description
In `IdleCreditVault`:

1. `collectWithdrawFunds(_amount)` is called by the CDO at `stopEpochWithDuration`. If `_amount < pendingWithdraws` (borrower underpaid due to a realized loss), it writes `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis` and zeroes `pendingWithdraws` (lines 411–426). `pendingWithdraws` is an *aggregate across all users and all request epochs*, so the haircut economically applies to every outstanding receipt, not just the ones whose `lastWithdrawRequest == epochNumber`.

2. `claimWithdrawRequest` (lines 301–314) routes through `_claimLossAdjustedWithdrawRequest`, which uses `lossEpoch = lastWithdrawRequest[_user]` as the *only* epoch checked against `lossRecoveryPriceByEpoch` (lines 789–801). It calls `_clearWithdrawClaimForEpoch(_user, lossEpoch, false)` which clears only `withdrawsRequestsByEpoch[_user][lossEpoch]` and subtracts only that epoch's piece from `withdrawsRequests[_user]` (lines 811–837).

3. `_claimFundedWithdrawRequest` then pays the entire remaining `withdrawsRequests[_user]` **at par** (lines 338–349), even though the loss-epoch funding shortfall covered the whole aggregate.

Two exploitable shapes:

- **Shape A (earlier loss epoch):** user requests in epoch e1 → loss-adjusted stop stores `lossRecoveryPriceByEpoch[e1]` → user requests again in epoch e2 (allowed; `requestWithdraw` updates `lastWithdrawRequest` and re-adds `pendingWithdraws`) → e2 stops fully funded → `claimWithdrawRequest`: `lossEpoch = e2`, `lossRecoveryPriceByEpoch[e2] == 0`, so the loss path returns 0 and the funded path pays `w1 + w2` at par. The w1 receipt was only funded at `w1 * price < w1`.
- **Shape B (earlier non-loss epoch, last epoch loss):** requests in e1 and e2 where e2's stop is loss-adjusted. Only e2's basis gets the haircut via `_clearWithdrawClaimForEpoch`; e1's remainder pays at par, but the aggregate `pendingWithdraws` haircut at `collectWithdrawFunds` already underfunded it.

Both break the solvency / "one receipt one funded payout" invariant: the strategy transfers out more underlyings than `collectWithdrawFunds`/`safeTransferFrom` ever deposited for those receipts.

### Impact Explanation
Direct theft / insolvency. The overpayment `w_other_epochs * (1 - lossRecoveryPrice)` is drawn from the strategy's underlying balance, which is the funded pool backing *other* users' pending claims (`_transferFundedClaim` sends from the strategy's own balance). First claimer drains funds owed to later claimants; the last claimers' transactions revert on insufficient balance — permanent loss of unclaimed withdrawals. Quantified example: w1 = 100k USDC receipt in the loss epoch, `lossRecoveryPrice = 0.5e18`, w2 = 1 wei in the next epoch ⇒ attacker extracts 50k USDC more than was funded.

### Likelihood Explanation
Requires only unprivileged actions: a KYC-passing lender calls `requestWithdraw` twice across consecutive buffer periods, and the honest manager/borrower executes a `stopEpochWithDuration` with a partial-loss repayment in one of those epochs — a normal operating event (the function and `previewLossAdjustedWithdrawFunds` exist precisely for partial losses). No privileged misbehavior, no oracle manipulation, no reentrancy. Every gate (`epochNumber <= lastWithdrawRequest`, `defaultRecoveryFinalized` routing, per-epoch clearing) behaves exactly as written; the bug is that the haircut is applied per-latest-epoch while the underfunding was applied per-aggregate.

### Recommendation
Track the haircut per user receipt, not per latest epoch. Either:
- Store per-epoch funded price and, in `claimWithdrawRequest`, iterate/accumulate over all epochs in `withdrawsRequestsByEpoch[_user]` applying each epoch's `lossRecoveryPriceByEpoch` (default `RECOVERY_FULL`) instead of paying the non-last remainder at par; or
- At `collectWithdrawFunds`, when a loss is recorded, proactively reprice every still-pending per-epoch bucket (e.g., write `lossRecoveryPriceByEpoch` for each epoch that contributed to `pendingBasis`, or migrate old receipts into the loss epoch's haircut bucket) so `_claimFundedWithdrawRequest` never sees un-haircutted basis.

### Proof of Concept
Foundry fork PoC (Shape A), in the style of `test/foundry/IdleCreditVault.t.sol`:

```solidity
function testLossHaircutSkippedForEarlierEpochReceipt() external {
    // attacker = KYC'd user; deposit into AA tranche
    address attacker = makeAddr('attacker');
    uint256 w1 = 100_000 * ONE_SCALE;
    _depositWithUser(attacker, w1, true);

    // buffer of epoch e1: attacker requests withdraw of full position
    vm.prank(attacker);
    uint256 req1 = cdoEpoch.requestWithdraw(0, address(AAtranche)); // ~w1 basis

    // epoch e1 runs; borrower repays only half of pending basis via stopEpochWithDuration
    _startEpochAndCheckPrices(0);
    IdleCreditVault strat = IdleCreditVault(address(strategy));
    uint256 pendingBasis = strat.pendingWithdraws();
    uint256 activeBasis = cdoEpoch.getContractValue() + cdoEpoch.expectedEpochInterest();
    uint256 totalBasis = activeBasis + pendingBasis;
    uint256 lossAmount = pendingBasis / 2; // 50% loss on pending bucket
    (uint256 pendingToFund, ) = strat.previewLossAdjustedWithdrawFunds(lossAmount);
    uint256 repay = cdoEpoch.expectedEpochInterest() + pendingToFund;
    deal(defaultUnderlying, strat.borrower(), repay, true);
    vm.prank(strat.borrower());
    IERC20Detailed(defaultUnderlying).approve(address(cdoEpoch), repay);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(initialProvidedApr, 0, cdoEpoch.epochDuration(), lossAmount);
    assertGt(strat.lossRecoveryPriceByEpoch(strat.epochNumber()), 0);
    assertLt(strat.lossRecoveryPriceByEpoch(strat.epochNumber()), ONE_TRANCHE);

    // buffer of epoch e2: attacker requests a second, tiny withdraw -> lastWithdrawRequest = e2
    _depositWithUser(attacker, 10 * ONE_SCALE, true);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(1, address(AAtranche));

    // epoch e2 stops fully funded (no loss)
    _startEpochAndCheckPrices(1);
    _stopEpochAndCheckPrices(1, initialProvidedApr, _expectedFundsEndEpoch());

    // attacker claims: loss path checks only epoch e2 (no loss price), funded path pays w1+w2 AT PAR
    uint256 balPre = IERC20Detailed(defaultUnderlying).balanceOf(attacker);
    uint256 fundedBalance = IERC20Detailed(defaultUnderlying).balanceOf(address(strat));
    vm.prank(attacker);
    uint256 paid = cdoEpoch.claimWithdrawRequest();

    uint256 haircutPayout = req1 * strat.lossRecoveryPriceByEpoch(1) / ONE_TRANCHE;
    // BUG: paid > funded share; attacker receives req1 at par instead of haircutPayout
    assertGt(paid, haircutPayout, 'loss haircut was not applied to e1 receipt');
    // The excess comes out of other users' funded claims -> insolvency for later claimers
    assertLt(fundedBalance, paid + /* other pending claims */ 0, 'strategy paid unfunded amount');
}
```

Key assertion: `paid` equals `req1 + req2` at par while the strategy only ever received `req1 * lossRecoveryPrice + req2` from the borrower — the difference is stolen from underlyings reserved for other receipt holders.
