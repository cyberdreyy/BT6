### Title
Unbounded, synchronously-iterated replay-guard map in Vault request authorization can be grown by unprivileged clients to degrade/DoS all Vault requests - ([File: core/capabilities/vault/request_replay_guard.go])

### Summary
`RequestReplayGuard`, used by `authorizer.AuthorizeRequest` on every single Vault gateway request (both `AllowListBasedAuth` and `JWTBasedAuth` paths), stores one entry per unique request digest in an in-memory map with no upper bound on size. Every call to `CheckAndRecord` — which runs on the hot path for *every* authorized Vault request — walks the entire `seen` map while holding a mutex before inserting the new entry. This is structurally the same bug class as the reported `addPool`/`GLPbackingNeeded` issue: an ever-growing collection that core functionality must fully iterate on each call, with no cap on growth and no external bound on the iteration cost.

### Finding Description
`RequestReplayGuard.CheckAndRecord` locks a mutex, calls `clearExpiredLocked()` (which does a full `for digest, expiry := range g.seen` scan of the map), then checks for the digest and inserts it if not present: [1](#0-0) 

The cleanup loop itself: [2](#0-1) 

This guard is invoked unconditionally in `authorizer.AuthorizeRequest`, on the return path of *both* authentication mechanisms, for every Vault request that reaches the gateway: [3](#0-2) 

Unlike the gateway's generic `requestCache`, which enforces an explicit `maxCacheSize` and rejects new entries once full (`core/services/gateway/handlers/common/requestcache.go:64-66`), `RequestReplayGuard` has no size limit at all — entries only leave the map when their `expiresAtUnix` has passed, and only as a side effect of a *subsequent* call to `CheckAndRecord` or an explicit `ClearExpired()`. If a client (or many distinct clients) submits many distinct, individually-valid requests (each producing a unique digest, e.g. via distinct nonces/JWT claims/parameters) at a rate faster than expiry, or with a far-future expiry, the `seen` map grows without bound. Because every future `CheckAndRecord` call must scan the entire map under a single mutex, per-request authorization latency grows linearly with the number of stored entries, and the mutex serializes *all* Vault authorization for all users/workflows — turning an unbounded map into an increasingly expensive, single-threaded bottleneck for all Vault traffic (analogous to the unbounded `poolInfo` array making `GLPbackingNeeded` prohibitively expensive for every caller).

### Impact Explanation
This directly maps to "core functionality bricking" from unbounded growth: as more distinct valid requests accumulate, every subsequent Vault request (secrets create/update/delete/list, public key get) pays an increasing linear-scan cost while holding a global mutex, degrading throughput/latency for all users of the Vault capability and, in the worst case, causing sustained resource exhaustion/DoS of the Vault authorization path for the whole gateway/DON. Unlike the smart-contract analog, there's no hard block-gas-limit wall, but the growth is unbounded, the scan is synchronous and mutex-serialized, and there is no capacity limit or backpressure comparable to `requestCache.maxCacheSize`.

### Likelihood Explanation
Moderate-to-low: exploitation requires an actor able to generate many distinct, authorization-passing digests (e.g., a legitimate but abusive user/workflow submitting many uniquely-parameterized Vault requests, or requests with long-lived expiries), rather than a fully unauthenticated attacker. It does not require privileged/admin access — any client capable of issuing authorized Vault requests through the gateway (allowlisted workflow owner or valid JWT holder) can drive this growth, which is a materially lower bar than the original report's "malicious admin" precondition.

### Recommendation
Bound `RequestReplayGuard`'s `seen` map size (e.g., reject/evict when a configurable maximum is exceeded, similar to `requestCache.maxCacheSize`), and/or run expiry cleanup on a periodic background timer instead of doing a full unbounded scan synchronously inside the hot authorization path while holding the lock that serializes all requests.

### Proof of Concept
Not independently verified in this pass — I could not fully trace how `expiresAtUnix` and `digest` are derived in `AllowListBasedAuth`/`JWTBasedAuth` (`core/capabilities/vault/allow_list_based_auth.go`, `core/capabilities/vault/jwt_based_auth.go`) before running out of tool iterations, so I cannot confirm the exact attacker-controllable range for digest uniqueness/expiry duration, nor definitively prove there is no separate, unseen size cap enforced elsewhere in these files. func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
```

func (g *RequestReplayGuard) clearExpiredLocked() {
	now := g.nowFunc().UTC().Unix()
	for digest, expiry := range g.seen {
		if now > expiry {
			delete(g.seen, digest)
		}
	}
}
```
