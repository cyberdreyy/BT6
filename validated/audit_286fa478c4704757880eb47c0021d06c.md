### Title
Uncontrolled recursion in JSON-RPC request parsing enables stack-overflow DoS - (File: rpc/src/rpc_service.rs)

### Summary
The go-ethereum fix adds a GraphQL query-depth limit because deeply nested queries let an attacker exhaust CPU/memory (and in the underlying JSON/graphql-go parser, stack) before existing timeouts kick in. Agave's JSON-RPC HTTP server has an equivalent unprotected input surface: incoming request bodies are handed to the `jsonrpc-http-server`/`jsonrpc-core` stack, which uses `serde_json` to deserialize the request (and its `params`) recursively. The server enforces only a byte-size cap via `max_request_body_size`, with no bound on JSON nesting depth.

### Finding Description
`JsonRpcService::new` builds the HTTP server with `ServerBuilder::with_meta_extractor(...)` and configures only `max_request_body_size(max_request_body_size)`, defaulting to `MAX_REQUEST_BODY_SIZE` (50 KB) or an operator-configurable value from `--rpc-max-request-body-size`. [1](#0-0) [2](#0-1) 

There is no configuration of a JSON parsing depth limit anywhere in this pipeline (no analog of `graphql.MaxDepth()`), and no `catch_unwind` guard wraps RPC request handling in `rpc/src`, meaning a Rust stack overflow triggered during `serde_json` deserialization of a request body is not a catchable panic — it aborts the process. Because the byte-size limit is the only guard, an attacker can pack many nesting levels into a small payload (each level costs only 2 bytes, e.g. `[` / `]`), so even the default 50 KB cap permits tens of thousands of nesting levels — far beyond what recursive-descent JSON parsers/deserializers can handle without overflowing the thread stack.

### Impact Explanation
A crafted, tiny HTTP POST to the public JSON-RPC endpoint (`getAccountInfo`, `sendTransaction`, or even a malformed top-level array) with deeply nested JSON can overflow the stack of the `solJsonRpcSvc`/`solRpcEl` worker thread during body deserialization, aborting the validator process. This is an unauthenticated, pre-execution DoS reachable by any RPC client — matching the "RPC crash / ingest starvation" impact category.

### Likelihood Explanation
Likelihood is limited by two factors that I could not fully rule out from the available code: (1) whether the specific `serde_json` version vendored by Agave has depth-limiting since some servers use bounded stacks or `serde_stacker`-style guards, and (2) whether `jsonrpc-http-server`'s internal streaming parser front-loads validation that rejects deeply nested arrays before full deserialization. I was not able to find any explicit depth guard or `catch_unwind` protection for the RPC HTTP request path in this repo, which is the basis for flagging this, but I could not execute a proof-of-concept crash against the running binary to confirm exploitability with the exact vendored dependency versions.

### Recommendation
Add an explicit JSON nesting-depth limit when parsing RPC request bodies (mirroring the go-ethereum `maxQueryDepth`/`graphql.MaxDepth()` pattern), e.g. via a bounded/iterative JSON pre-check or a `serde_json` deserializer wrapped with a stack-depth guard (such as `serde_stacker`), and wrap the JSON-RPC request-parsing/dispatch path in `catch_unwind` so a worst-case failure degrades to a single rejected request rather than terminating the whole validator process.

### Proof of Concept
Send an HTTP POST to the validator's RPC port with a body consisting of many thousands of nested arrays within the 50 KB body-size limit, e.g.:
```
POST / HTTP/1.1
Content-Type: application/json
Content-Length: <small>

[[[[[[[[[[ ... repeated ~20000+ times ... ]]]]]]]]]]
```
Because only `max_request_body_size` (50 KB by default) is enforced and no depth limit exists, this payload is accepted by the size check yet forces deep recursive parsing, which can exhaust the worker thread's stack and crash the process — analogous to the unmitigated GraphQL deep-nesting DoS in the referenced go-ethereum fix.

Note: I was unable to verify empirically (no sandbox/terminal access) whether the exact `serde_json`/`jsonrpc-core` versions pinned in `Cargo.lock` are vulnerable to this specific stack-overflow pattern or already guard against it internally; this assessment is based on the absence of any depth-limiting or panic-catching code found in the Agave RPC request-handling path.
