### Title
Sequential withdrawal requests reprice remaining tranche interest and transfer yield to later withdrawers - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`requestWithdraw` calculates a withdrawal’s epoch interest from the **current aggregate vault NAV**, but divides that class-wide interest by only the **remaining NAV of the selected tranche**. After a withdrawal, both values decrease, and when the tranche’s interest share is higher than its NAV share, the next withdrawal from that same tranche receives a higher interest rate for identical principal. Splitting one withdrawal therefore creates more interest than requesting it atomically, while `interestForOverUnderPerformance` only preserves the aggregate borrower obligation and passes the shortfall to the remaining tranche holders.

### Finding Description
During the buffer phase, `requestWithdraw` converts tranche tokens to underlying, calls `_calcInterestWithdrawRequest`, adds the result to the withdrawal receipt, and removes only principal from live NAV. [1](#0-0) 

The quoted interest is:

```solidity
_interest = _amount * totTrancheInterest / _trancheBal;
```

where `totTrancheInterest` is derived from `_managedContractValue()`, while `_trancheBal` is `_lastSavedNAV(_tranche)`. [2](#0-1)  Thus, the numerator uses all remaining AA plus BB NAV, but the denominator uses only the selected tranche’s remaining NAV. [3](#0-2) 

For example, assume:

- `lastNAVAA = 50`
- `lastNAVBB = 50`
- total epoch interest `I = 10`
- AA interest share = 70%
- no fees
- an AA holder withdraws `25`, then another `25`

The first request receives:

```text
25 * (10 * 70%) / 50 = 3.5 interest
```

After principal is removed, `AA = 25` and `TVL = 75`, so the second request receives:

```text
25 * ((7.5 * 70%) / 25) = 5.25 interest
```

The two identical `25` principal withdrawals receive `8.75` interest instead of the class entitlement of `7`, creating `1.75` excess interest. `interestForOverUnderPerformance` reduces `expectedEpochInterest` so total obligations remain conserved. [4](#0-3)  In this example, the remaining BB holders retain only `1.25` of their original `3` interest entitlement.

`IdleCreditVault.requestWithdraw` allows an ordinary pending request to be accumulated into the same epoch receipt and does not prevent another request by the same user. [5](#0-4)  A contract wallet can therefore perform both requests in one transaction.

The same exploit applies symmetrically to BB withdrawals when BB’s APR allocation exceeds its NAV share. More generally, whichever class has `interestShare > navShare` sees its withdrawal interest rate increase after each withdrawal from that class.

### Impact Explanation
A KYC-passing tranche holder can steal yield that belongs to the other tranche by splitting a withdrawal into multiple requests. In the stated example, the attacker receives `8.75` instead of `7` epoch interest, a `25%` increase over the fair AA interest entitlement and a transfer equal to `17.5%` of total epoch interest.

The issue is larger when the allocation/NAV mismatch is larger. For example, with `AA = 25`, `BB = 75`, and a 90% AA interest split, two AA withdrawals of `12.5` produce approximately `15.75` interest instead of the AA entitlement of `9` on total interest `10`, draining `5.75` from the remaining class.

This is theft of unclaimed yield rather than merely a rounding discrepancy. It breaks the fair burn/payout invariant because two identical withdrawal amounts receive different interest rates based solely on request ordering.

### Likelihood Explanation
No privileged action is required during exploitation: the attacker only needs an allowed wallet and tranche tokens, then calls `requestWithdraw` multiple times during the request/buffer phase. [6](#0-5) 

The exploit is available whenever either tranche’s configured interest share exceeds its share of current NAV. `trancheAPRSplitRatio` need not equal the tranche TVL ratio, so this state is expected during normal operation. Instant withdrawals do not prevent it; if instant withdrawal is unavailable or the APR delta condition is false, execution continues into the vulnerable normal-request path. [7](#0-6) 

The attacker can execute both requests atomically, so no other user transaction is required after funding the position.

### Recommendation
Track each tranche’s remaining epoch-interest entitlement separately and calculate withdrawal interest as:

```solidity
interest = principal * remainingTrancheInterest / remainingTrancheNAV;
```

Initialize `remainingTrancheInterest` from the tranche’s fixed share of the epoch’s projected interest and decrement it by the interest paid to each withdrawal request. Do not recompute the class interest numerator from the post-request aggregate NAV for every request.

Alternatively, snapshot `AAInterest`, `BBInterest`, `lastNAVAA`, and `lastNAVBB` at the beginning of each request epoch and use those fixed values for all requests in that epoch. The snapshot should also prevent a new request from changing the interest rate paid to later requests.

Add invariant tests proving that, absent rounding, splitting a request produces the same payout as one atomic request for every combination of AA/BB NAV and `trancheAPRSplitRatio`.

### Proof of Concept
The following Foundry test is intended to be added to `test/foundry/IdleCreditVault.t.sol`, which already exposes the same `idleCDO`, `cdoEpoch`, `strategy`, `AAtranche`, `BBtranche`, `underlying`, `ONE_SCALE`, owner, and manager fixtures used by the existing epoch tests. [8](#0-7) 

```solidity
function testSplitWithdrawRequestStealsTrancheInterest() external {
    // Assumes the fixture whitelists `attacker`; KYC is an allowed attacker path.
    address attacker = makeAddr("attacker");
    IdleCreditVault cv = IdleCreditVault(address(strategy));

    _setFeeParams(TL_MULTISIG, 0, 0, 0);

    // Set an intentionally AA-heavy yield allocation: AA owns 50% of NAV
    // but receives 70% of interest.
    vm.prank(owner);
    cdoEpoch.setTrancheAPRSplitRatio(70_000);

    uint256 attackerDeposit = 50 * ONE_SCALE;
    uint256 bbDeposit = 50 * ONE_SCALE;

    deal(address(underlying), attacker, attackerDeposit);
    vm.startPrank(attacker);
    underlying.approve(address(idleCDO), attackerDeposit);
    idleCDO.depositAA(attackerDeposit);
    vm.stopPrank();

    deal(address(underlying), address(this), bbDeposit);
    underlying.approve(address(idleCDO), bbDeposit);
    idleCDO.depositBB(bbDeposit);

    // Buffer/request phase. Instant withdrawals are disabled by default, so both
    // calls enter `_calcInterestWithdrawRequest`.
    vm.startPrank(attacker);
    uint256 firstReceipt = cdoEpoch.requestWithdraw(25 * ONE_SCALE, address(AAtranche));
    uint256 secondReceipt = cdoEpoch.requestWithdraw(25 * ONE_SCALE, address(AAtranche));
    vm.stopPrank();

    uint256 duration = cdoEpoch.epochDuration();
    uint256 buffer = cdoEpoch.bufferPeriod();
    uint256 scaledApr = cv.getApr();

    // Matches `_calcInterest(totalTVL) * duration / (duration + buffer)`.
    uint256 totalEpochInterest =
        (100 * ONE_SCALE) *
        (scaledApr / 100) *
        duration /
        (365 days * ONE_TRANCHE_TOKEN) *
        duration /
        (duration + buffer);

    uint256 fairAAInterest = totalEpochInterest * 70_000 / FULL_ALLOC;
    uint256 expectedAtomicReceipts = 50 * ONE_SCALE + fairAAInterest;
    uint256 actualReceipts = firstReceipt + secondReceipt;

    // The second identical principal request is quoted at a higher interest rate.
    assertGt(secondReceipt - 25 * ONE_SCALE, firstReceipt - 25 * ONE_SCALE);

    // Combined split requests exceed the entire AA interest entitlement.
    assertGt(actualReceipts, expectedAtomicReceipts);
}
```

For a 10% unscaled APR and a 30-day epoch, `totalEpochInterest` is approximately `0.8219178` underlying on `100` principal. The expected receipts are approximately `50.575342`, while the split requests produce approximately `50.719178`; the attacker captures approximately `0.143836` extra underlying from the BB class’s interest entitlement.

  function _calcInterest(uint256 _amount) internal view returns (uint256) {
    return _calcInterestAtApr(_amount, IdleCreditVault(address(strategy)).getApr());
  }

  function _calcInterestAtApr(uint256 _amount, uint256 _apr) internal view returns (uint256) {
    return _amount * (_apr / 100) * cdoEpoch.epochDuration() / (365 days * ONE_TRANCHE_TOKEN);
  }

  function _calcInterestWithdrawRequest(uint256 _amount, address _tranche) internal view returns (uint256) {
    uint256 _duration = cdoEpoch.epochDuration();
    if (_duration == 0) {
      return 0;
    }

    // calculate total vault interest (they don't get the interest for the buffer period),
    uint256 tvl = cdoEpoch.getContractValue();
    uint256 totInterest = _calcInterest(tvl) * _duration / (_duration + cdoEpoch.bufferPeriod());
    // calculate total tranche interest
    uint256 _trancheAprRatio = _tranche == address(AAtranche) ? cdoEpoch.trancheAPRSplitRatio() : FULL_ALLOC - cdoEpoch.trancheAPRSplitRatio();
    uint256 _instantBalance = _tranche == address(AAtranche) ? cdoEpoch.lastNAVAA() : cdoEpoch.lastNAVBB();
    uint256 totTrancheinterest = totInterest * _trancheAprRatio / FULL_ALLOC;
    // calculate interest for the given tranche and given amount
    return _instantBalance == 0 ? 0 : _amount * totTrancheinterest / _instantBalance;
  }
