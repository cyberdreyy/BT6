### Title
APR0 withdrawal interest is omitted from the programmable-borrower liquidity reservation - ([File: contracts/strategies/idle/ProgrammableBorrower.sol])

### Summary
`ProgrammableBorrower` reserves only the pending-withdrawal balance known at `onStartEpoch`, but `IdleCreditVault.prepareStopEpochWithApr0` can later add APR0 withdrawal interest to `pendingWithdraws`. A borrower can therefore draw all liquidity above the stale principal reservation, leaving the stop-epoch withdrawal payment underfunded and forcing a protocol default despite the borrower position remaining contractually solvent.

### Finding Description
During `startEpoch`, `IdleCDOEpochVariant` reads `strategy.pendingWithdraws()` and passes that fixed amount to `ProgrammableBorrower.onStartEpoch`. [1](#0-0)  `onStartEpoch` stores that value in `epochPendingWithdraws`, which `availableToBorrow` subtracts from total on-hand and ERC4626 assets when determining borrowable liquidity. [2](#0-1) [3](#0-2) 

At epoch stop, however, `prepareStopEpochWithApr0` computes a pro-rata APR0 interest allocation and increases `pendingWithdraws` after the reservation was already fixed. [4](#0-3)  `IdleCDOEpochVariant` then reads the enlarged `pendingWithdraws` value and requires that amount from the programmable borrower before collecting it. [5](#0-4) 

This is analogous to an omitted final reservation bucket: the initial reservation covers receipt principal, but not the final interest component assigned to the same receipt epoch. With a 10,000-asset pool, a 5,000-asset APR0 withdrawal, and the configured borrower drawing the allowed 5,000 free assets, the borrower adapter retains roughly 5,000 assets while the stop flow can require approximately 5,900 assets once borrower interest is allocated to the APR0 receipt. [6](#0-5) 

### Impact Explanation
The broken invariant is that assets reserved for matured withdrawal receipts must remain unavailable to the borrower until the receipts are funded. Because the reservation omits APR0 interest, the borrower can legally drain the assets needed for the final receipt balance.

A normal `stopEpoch` then attempts to pull more cash than the adapter holds. `onStopEpoch` does not recall borrower debt for this shortfall; if the required amount exceeds the adapter's remaining vault assets, the later `transferFrom` fails and `_handleBorrowerDefault` marks the pool defaulted. [7](#0-6) [8](#0-7) [9](#0-8) 

Using the repository's programmable-borrower test configuration—365% borrower APR and a 36.5-day epoch—a 5,000-asset draw accrues approximately 1,825 assets of contractual interest. A 50% APR0 withdrawal therefore adds roughly 912 assets to the withdrawal obligation, producing an approximately 912-asset liquidity shortfall and temporarily freezing both active LP value and pending claims until default recovery is finalized.

### Likelihood Explanation
No privileged malicious action is required. A KYC-passing tranche holder makes a normal withdrawal request, the configured borrower calls `borrow(0)` through an explicitly supported path, and the honest manager later calls `stopEpoch`. The programmable mode is explicitly designed around minted interest, while the test deployment sets the strategy APR flow to zero, making this sequence part of the intended operating mode. [10](#0-9) [11](#0-10) 

### Recommendation
Make the programmable-borrower reservation dynamic and inclusive of the complete stop-epoch cash obligation. In particular, `availableToBorrow` should reserve at least `epochPendingWithdraws` plus a conservative bound on the APR0 interest that may be added by `prepareStopEpochWithApr0`, such as `totalInterestDueNow()` when an exact strategy-side allocation is unavailable.

Alternatively, expose the APR0 principal and total split basis to the programmable borrower and reserve `epochPendingWithdraws + projectedApr0NetInterest`. Do not rely on the stale value captured by `onStartEpoch`, because it is finalized before the APR0 interest component exists.

### Proof of Concept
This test can be added to `test/foundry/ProgrammableBorrowerCreditVault.t.sol`, whose setup already initializes a mainnet fork, programmable borrower, and APR0 strategy configuration. [12](#0-11)

function testApr0StopInterestEscapesBorrowerReservation() external {
    uint256 amount = 10_000 * oneScale;

    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);

    // Deposit 10k and queue a normal APR0 withdrawal for half the pool.
    idleCDO.depositAA(amount);
    cdoEpoch.requestWithdraw(
        aaTranche.balanceOf(address(this)) / 2,
        address(aaTranche)
    );

    uint256 reservedPrincipal = strategy.pendingWithdraws();
    assertGt(reservedPrincipal, 0);

    _startEpochAndCheckPrices(0);

    // The programmable borrower only reserved the request-time principal.
    assertEq(
        programmableBorrower.epochPendingWithdraws(),
        reservedPrincipal
    );

    // The configured borrower can draw every asset above that stale reservation.
    uint256 freeLiquidity = programmableBorrower.availableToBorrow();
    assertGt(freeLiquidity, 0);

    vm.prank(revolvingBorrower);
    programmableBorrower.borrow(0);

    assertApproxEqAbs(
        programmableBorrower.totalUnderlying(),
        reservedPrincipal,
        2,
        "only request-time principal remains reserved"
    );

    vm.warp(cdoEpoch.epochEndDate() + 1);

    // Borrower interest accrued during the epoch. prepareStopEpochWithApr0 will
    // add the APR0 share to pendingWithdraws after the reservation was fixed.
    uint256 poolInterest = programmableBorrower.totalInterestDueNow();
    assertGt(poolInterest, 0);

    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    // The adapter does not hold pending principal plus the newly added APR0
    // interest, so the borrower pull fails and the pool is marked defaulted.
    assertTrue(cdoEpoch.defaulted(), "stop should default from under-reservation");
    assertFalse(cdoEpoch.isEpochRunning(), "epoch is stopped by default path");
}

  function onStopEpoch(uint256 _amountRequired, bool _isRequestingAllFunds) external nonReentrant returns (bool success) {
    _checkOnlyIdleCDO();
    _accrueBorrowerInterest();
    // if we want to close the pool and the borrower still owes any amount, consider it a failure and let IdleCDO handle it as a default instead of a close. 
    if (_isRequestingAllFunds && (borrowerPrincipal != 0 || borrowerInterestDebt != 0 || borrowerInterestAccrued != 0)) {
      return false;
    }

    uint256 onHand = underlyingToken.balanceOf(address(this));
    if (_amountRequired > onHand) {
      uint256 shortfall = _amountRequired - onHand;
      // If the vault shares do not economically cover the shortfall, let IdleCDO's later
      // transferFrom fail and use the existing default path. Only an otherwise-covered ERC4626
      // withdrawal failure should make stopEpoch retryable.
      if (shortfall > _currentVaultAssets()) return true;
      try vault.withdraw(shortfall, address(this), address(this)) returns (uint256 shares) {
        if (epochAccountingActive) {
          epochWithdrawnFromVault += shortfall;
        }
        emit WithdrawnFromVault(shortfall, shares, address(this));
      } catch {
        revert StopEpochVaultLiquidityUnavailable();
      }
    }

    // `totalInterestDueNow()` was already read by IdleCDO before calling this hook, so once the
    // stop flow begins we can clear the previous carry and snapshot the remaining vault sleeve
    // as the baseline for measuring buffer-period vault PnL before the next epoch starts.
    bufferedVaultDelta = 0;
    bufferInterest = 0;
    bufferStartVaultAssets = _currentVaultAssets();

    // Stop reserving epoch-end withdraw liquidity once IdleCDO has started the stop flow.
    epochPendingWithdraws = 0;
    epochAccountingActive = false;
    emit EpochAccountingStopped();
    success = true;

  function _borrow(uint256 assets) internal returns (uint256 withdrawnShares) {
    if (!epochAccountingActive) revert NotAllowed();
    // `0` is treated as "draw the full currently borrowable amount" after reserving epoch-end obligations.
    uint256 borrowable = availableToBorrow();
    if (assets == 0) {
      if (borrowable == 0) revert InvalidAmount();
      assets = borrowable;
    }

    // Borrows are capped by the live "reserved vs free" view so epoch-end obligations always stay covered.
    if (assets > borrowable) revert InsufficientBorrowable();

    _accrueBorrowerInterest();

    uint256 onHand = underlyingToken.balanceOf(address(this));
    if (onHand < assets) {
      uint256 shortfall = assets - onHand;
      withdrawnShares = vault.withdraw(shortfall, address(this), address(this));
      if (epochAccountingActive) {
        epochWithdrawnFromVault += shortfall;
      }
      emit WithdrawnFromVault(shortfall, withdrawnShares, address(this));
    }

    // Executors can trigger the draw, but proceeds are always delivered to the borrower wallet.
    borrowerPrincipal += assets;
    underlyingToken.safeTransfer(borrower, assets);
    emit Borrowed(assets);
