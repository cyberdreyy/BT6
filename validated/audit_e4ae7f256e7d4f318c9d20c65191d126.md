### Title
Post-default instant-withdraw receipts bypass recovery accounting and drain funded-claim liquidity - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary

`requestInstantWithdraw` in `IdleCreditVault` never checks `defaultRecoveryFinalized`. `requestWithdraw` was patched to route post-default requests into the reserve-backed `postDefaultRequests` bucket (`IdleCreditVault.sol:247-257`), but the instant path was not given the equivalent treatment. After a borrower default is finalized, an unprivileged user can still open an instant-withdraw receipt that mints receipt tokens at par, and `claimInstantWithdrawRequest` then pays it through `_transferFundedClaim`, which only protects the `defaultRecoveryReserve` — not the non-reserve balance earmarked for older, already-funded withdraw claimants. This is the stale-state / use-after-free analog of CVE-2020-6386: a receipt object created against a dead (finalized) epoch is consumed by a claim path that assumes the pre-default accounting world still exists.

### Finding Description

After `finalizeDefaultRecovery` sets `defaultRecoveryFinalized = true` (`IdleCreditVault.sol:690`), the vault holds two disjoint pots:

- `defaultRecoveryReserve`: pays all defaulted-epoch and post-default claims at `defaultRecoveryPrice`.
- Non-reserve balance: underlyings collected via `collectWithdrawFunds`/`collectInstantWithdrawFunds` for funded receipts not yet claimed (`_transferFundedClaim`, `IdleCreditVault.sol:897-907`, enforces `balance - reserve >= amount` only).

`requestInstantWithdraw` (`IdleCreditVault.sol:356-375`) performs `_ensureDefaultRecoveryInitialized()` but has no `defaultRecoveryFinalized` branch. It:

1. Burns CDO strategy tokens and mints a 1:1 receipt to the user (lines 360-363).
2. Increments `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epochNumber]`, `instantWithdrawClaimsByEpoch[epochNumber]`, and `pendingInstantWithdraws` (lines 366-374) — all against the *current* epoch, which post-default is `> defaultRecoveryEpoch`.

On claim (`claimInstantWithdrawRequest`, `IdleCreditVault.sol:380-393`):

- `_claimDefaultedInstantWithdrawRequest` clears only `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` (line 844), so the attacker's new-epoch basis survives in `instantWithdrawsRequests[_user]`.
- `amount = instantWithdrawsRequests[_user]` includes the post-default receipt, and `_transferFundedClaim` pays it **at par** from the non-reserve pot as long as `balance - reserve >= amount`.

Result: a receipt created after the recovery price was crystallized is paid 1:1 from funds owed to legitimate funded-epoch claimants, breaking the "one receipt, one haircut/one funded payout" invariant and the isolation between the default-reserve and funded pots. When the funded pot is later exhausted, honest `claimWithdrawRequest`/`claimInstantWithdrawRequest` calls for genuinely funded receipts revert on the `balance - reserve < _amount` guard — permanent freezing of their claims. If the funded pot is empty, the attacker's own claim reverts (self-inflicted freeze only), so the theft requires pending unclaimed funded liquidity, which is the normal post-stopEpoch state.

### Impact Explanation

Direct theft of underlying: an attacker holding tranche tokens after default finalization can request an instant withdrawal and, once the CDO funds it (or if non-reserve liquidity already sits in the strategy), claim underlying at par from the bucket reserved for earlier funded withdraw claimants. Loss equals the attacker's receipt amount, up to the full unclaimed funded balance; correspondingly, honest funded claimants' claims become permanently unpayable (insolvency of the funded pot). The invariant broken is fair payout ordering + reserve isolation introduced by the default-recovery accounting.

### Likelihood Explanation

Requires: (a) a finalized borrower default (a real, supported mode — `_handleBorrowerDefault`/`finalizeDefaultRecovery`), (b) `allowInstantWithdraw` still enabled on the CDO (a config flag; it is checked only on the CDO `claimInstantWithdrawRequest` path at `IdleCDOEpochVariant.sol:975-979`, not on request), and (c) unclaimed funded liquidity in the strategy — the common case right after a `stopEpoch`/`collectWithdrawFunds`. The attacker is any tranche holder, an explicitly in-scope unprivileged role. Note: whether `IdleCDOEpochVariant`'s request entry point additionally reverts when `defaulted()` could not be fully confirmed in this pass; the vault-level guard is absent regardless, and `requestWithdraw` shows the codebase intentionally permits post-default requests, making it unlikely the CDO blanket-blocks this path.

### Recommendation

In `requestInstantWithdraw`, mirror `requestWithdraw`: when `defaultRecoveryFinalized` is true, revert (or route the amount into `postDefaultRequests` so it is paid from `defaultRecoveryReserve` at the finalized haircut). At minimum add an explicit `if (defaultRecoveryFinalized) revert NotAllowed();` before the mint/`pendingInstantWithdraws` updates, and ensure `instantWithdrawsRequests[_user]` cannot mix defaulted-epoch and post-default basis.

### Proof of Concept

Foundry fork sketch (extend `test/foundry/IdleCreditVault.t.sol` default-recovery tests):

```solidity
function testPostDefaultInstantWithdrawDrainsFundedPot() external {
    // 1. Victim deposits, epoch runs, victim requests normal withdraw.
    _depositWithUser(victim, 10_000 * ONE_SCALE, true);
    _startEpochAndCheckPrices(0);
    vm.prank(victim);
    cdoEpoch.requestWithdraw(0, address(AAtranche)); // pending receipt, epoch 1

    // 2. stopEpoch funds the receipt (non-reserve liquidity in strategy),
    //    then borrower defaults on the *next* epoch and recovery is finalized.
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(initialProvidedApr, 0);       // victim receipt now funded, unclaimed
    _startEpochAndCheckPrices(0);
    _triggerBorrowerDefaultAndFinalize();            // defaultRecoveryFinalized = true

    // 3. Attacker (any tranche holder) opens an instant request post-finalization.
    _depositWithUser(attacker, 5_000 * ONE_SCALE, true); // pre-default deposit path or existing shares
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(attackerAmount, address(AAtranche));

    // 4. Attacker claims at par: _claimDefaultedInstantWithdrawRequest misses the
    //    new-epoch basis, funded path pays from non-reserve pot.
    uint256 pre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    assertEq(underlying.balanceOf(attacker) - pre, attackerAmount); // paid 1:1

    // 5. Victim's already-funded claim now reverts on the reserve guard.
    vm.prank(victim);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.claimWithdrawRequest();
}
```

If step 3/4 is blocked by a `defaulted()` check inside `IdleCDOEpochVariant.requestInstantWithdraw` that could not be confirmed from the indexed excerpts, the issue degrades to dead code inconsistency rather than exploitable theft — verify that entry point before reporting.
